# 1. RAG基础理论知识

## 1.1 RAG是什么
1. 大模型（LLM）本质上是一个“概率型语言压缩器”：它擅长把输入变成合理的输出，但不保证事实正确，也不自带你私有文档的最新知识。
RAG 的思想很朴素：回答前先检索证据，再让模型在证据约束下生成。

2. 可以把它理解成：
	- LLM = 写作与推理引擎（会说话、会归纳、会推理，但可能瞎编）
	- Retriever = 图书管理员（负责把“最可能有答案的资料”找出来）
	- Generator = 记者/律师（在证据范围内组织成回答）

## 1.2 RAG的两个关键假设
1. RAG 能成立，依赖两个假设（也是它的软肋）：
	1. 问题的答案存在于你的语料里。如果语料没有，RAG 再强也只能“检索不到”，或者把相近内容拿来硬套。
	2. 检索能把“包含答案的片段”找出来。也就是：你得能把“对的证据”召回到上下文里。

## 1.3 RAG的标准流水线（理论模块）

1. **知识库构建（Indexing）**
    - 把原始文档变成“可检索”的形态：
        - 文档 → 清洗 → 切分成 chunks
        - chunks → 向量化（embedding）→ 存到向量索引
        - 同时保存 元数据：来源、日期、章节、地区、版本、权限等
    - 理论点：这一步是在做“把世界离散化”的工作。切分策略决定了你未来检索的上限。

2. **查询理解（Query Understanding）**
    - 用户问一句话，系统通常会做一些“理解增强”：
        - 改写/扩写：让问题更完整、更可检索
        - 拆解：复杂问题拆成子问题（多跳检索会用到）
        - 结构化：提取关键实体/时间/范围（医疗政策特别吃这一套）
    - 理论点：检索不是“对话”，检索是“匹配”。你得把 query 变成更容易匹配知识库的形式。

3. **召回（Retrieval）**
    - 从索引里拿 topK 候选证据：
        - 语义召回（向量相似度）
        - 关键词召回（BM25/倒排索引）
        - 混合召回（两者结合）
    - 理论点：召回追求的是 高召回率（宁可多抓一点，后面再筛），否则答案直接“丢失在宇宙里”。

4. **重排与压缩（Rerank & Compress）**
    - 把 topK 候选进一步提纯：
        - Rerank：用更精的模型/打分器重新排序
        - 去重：同段重复浪费上下文
        - 压缩：摘要、抽取关键句、只保留与问题相关的部分
    - 理论点：上下文窗口是稀缺资源（token 预算）。这一层是在做“把证据浓缩成可喂给 LLM 的口粮”。

5. **生成（Generation）**
    - 把“问题 + 证据”喂给 LLM，要求它：
        - 基于证据回答
        - 引用证据（可选但强烈推荐）
        - 证据不足就说不足（防幻觉的关键开关）
    - 理论点：这一步不是让模型“知道”，而是让模型“在给定证据约束下写出答案”。

## 1.4 RAG vs 纯微调（Fine-tuning）
1. 理论上的分工
    - 微调更像“改模型的习惯/风格/技能”：让它更懂你的任务格式、术语风格、流程话术。
    - RAG更像“给模型喂最新事实/私有知识”：把知识放在外部，随时更新，能引用。

2. 很多生产系统是：微调（或指令优化） + RAG 叠加：
    - 微调负责“怎么答”，RAG 负责“答什么依据”。

## 1.5 RAG 的天然边界（理论上你必须承认的）
1. 检索错了：LLM 会“用错证据写得很像对的”，比直接胡说更迷惑。
2. 需要深推理但证据分散：单轮 topK 可能不够，要做多跳检索或工具调用。
3. 语料本身有冲突/过期：RAG 只会把冲突带进来，必须用版本/日期/权威性规则解决。
4. 不可检索的信息：例如表格计算、跨页图表、复杂 PDF 排版，如果解析失败，检索就失真。

# 2. RAG知识库构建

## 2.1 知识库构建
1. 知识库构建的目标（理论上到底要达成什么）
    - 最终你想得到的是一堆记录（每条记录≈一个 chunk），每条记录至少包含：
        - chunk_text：可供模型引用的正文
        - embedding_vector：chunk 的语义向量
        - metadata：来源、章节、页码/段落号、发布时间、生效期、地区/机构、版本号、权限、文档类型等
        - （可选）keywords/lexical fields：便于关键词检索或过滤（药品名、编码、条款号、科室名等）

2. 知识库构建的核心步骤（从原始到可检索）
    1. 文档采集与统一化（Ingestion & Normalization）
        - 为什么要统一化？ 因为 PDF、网页、Word、Markdown、数据库导出，结构差异巨大，不统一后面切分会崩。
        - 常见统一输出结构（理论模型）：
            - Document { doc_id, text, structure, metadata }

    2. 清洗与去噪（Cleaning）
        - 目标：减少“会被召回但没用”的噪声，否则检索会很容易被目录、页眉页脚、免责声明、页码干扰。
        - 典型噪声：
            - 页眉页脚（医院名、文件名、页码）
            - 目录与重复标题
            - 扫描 PDF 的断行、连字符、乱码
            - 表格转文本的对齐符号、重复空格
        - 理论原则：清洗不是为了“好看”，是为了提高 检索信号/噪声比（SNR）。噪声越多，embedding 越“平均化”，越难区分。

    3. 文档分块（Chunking / Segmentation）
        - 这是知识库构建里最关键的“理论难点”。
        - 为什么必须 chunk？
            - LLM 上下文有限，不能把整本政策喂进去
            - 向量检索的“匹配单元”必须是有限长度，否则：
                - 太长：语义混杂、向量被稀释（一个 chunk 里有十个主题）
                - 太短：信息不完整，召回来了也回答不出来
        - Chunk 的三种经典切法（理论维度）
            - 固定长度切分（按 token/字符 N 切）
                - 优点：实现简单
                - 缺点：容易把“定义 + 条件 + 例外”切断，语义残缺
            - 结构化切分（按标题/段落/条款切）
                - 优点：语义边界更自然，召回更稳定
                - 缺点：文档结构提取要求更高（PDF 很坑）
            - 语义切分（按句向量相似度找断点）
                - 优点：更贴近语义主题
                - 缺点：计算贵，且对噪声敏感
            - 医疗规则常用组合拳：标题层级 + 条款/段落 + 适度长度约束。

    4. 元数据设计（Metadata）——RAG 的“可控性开关”
        - 纯向量检索在生产里最大的问题是：它很会“猜相似”，但不懂你的业务边界。
        - 元数据是你把业务规则强行塞给检索系统的方式，比如：
            - region=上海/广东
            - policy_version=2024Q3
            - effective_date_start/end
            - doc_authority=国家医保局/省医保局/医院内部
            - department=门诊/住院
            - access_level=内部/公开
        - 理论上，元数据过滤能把问题从：
            - “在整个宇宙里找相似语义”
            - 变成“在正确的宇宙子集里找相似语义”
            - 这对医疗政策这种“版本/地区差一个字就翻车”的领域是刚需。

    5. 向量化（Embedding）——把 chunk 投影到“语义空间”
        - embedding 的理论直觉：
            - 把文本映射成一个高维向量，使得“语义相近”的文本在空间里更近（常用 cosine 相似度）。
            - 但要注意一个现实理论点：
                - embedding 表示的是“整体语义”，不是精确逻辑。
                - 所以对于：
                    - 编码、药品名、条款号
                    - 精确数值阈值（如“≥3 天”“≤500 元”）
                    - embedding 可能不靠谱，这也是为什么很多系统要加关键词检索/混合检索。

    6. 建索引与存储（Indexing in Vector DB）
        - 理论上你要决定两件事：
            - 你用什么近似最近邻（ANN）结构来加速相似度检索
            - 你怎么组织存储以支持过滤、更新、删除

        - 向量库内部常见是 HNSW 这类图索引（不展开实现细节也行），你需要知道的理论点是：
            - ANN 牺牲一点点精确度换速度
            - 索引参数影响“召回率 vs 延迟 vs 内存”
            - 生产里还要考虑增量更新、版本切换、回滚

3. 知识库构建的“质量标准”（怎么判断做得好）
    - 你可以用三个问题做验收（非常工程化）：
        - 可追溯性：召回的 chunk 能否定位到原文（页码/章节/链接）？
        - 可控性：能否按版本/地区/生效期过滤，避免引用过期政策？
        - 可召回性：给定一批真实问题，“包含答案的 chunk”是否能稳定进 topK？

4. 这一阶段最常见的失败模式（理论解释）
    - 切分不合理：chunk 太长→语义稀释；太短→信息断裂
    - 噪声没清：目录/页眉页脚被 embedding 当成主题
    - 元数据缺失：不同版本政策混在一起，检索出来“互相打架”
    - 只做向量不做关键词：遇到编码/专名/条款号就“语义失明”

## 2.2 chunk 粒度怎么选、overlap 怎么选、以及为什么医疗规则更适合‘结构化切分 + 元数据过滤 + 混合检索

1. Chunk 粒度怎么选：别凭感觉，按“可回答性 + 可检索性”定
    - 你在平衡两种失败
        - chunk 太大：一个 chunk 里塞了多个主题，embedding 被“平均化”，召回时不够尖锐；同时把噪声也带进上下文，模型容易走偏。
        - chunk 太小：召回到了也不够信息闭环（只有条件没结论，或只有结论没适用范围），模型只能猜。

    - 最实用的标准：一个 chunk 必须“自洽”
        - 对规则类文本，一个 chunk 理想上能独立回答“这条规则讲的是什么”，至少包含以下之一的闭环：
            - 定义（术语是什么）
            - 条件 → 结论（满足什么条件会发生什么）
            - 范围 → 例外（适用谁/不适用谁）

    - 粒度的经验区间（按 token，而不是字数）
        - 在中文政策/规章场景里，常见可用区间是：
            - 主体 chunk：200–400 tokens（大概 300–800 中文字的量级，视断句、标点而变）
            - “高价值小块”特例：80–160 tokens（定义、公式、阈值、例外条款、处罚条款这类必须精确命中的段落）
            - 很少建议 >600 tokens（除非它是一个天然结构块，比如“某条款下的完整流程”且内部主题非常单一）

        - 为什么是这个量级？因为它通常能同时满足：
            - 语义足够集中，便于召回（可检索性）
            - 信息足够完整，能支撑回答（可回答性）
            - 不会把上下文窗口迅速吃光（可扩展性）

    - 规则文档的“推荐切分单位”
        - 比固定长度更稳的是按结构切：
            - 以 条款/款/项 为基本单位（例如“第X条”“（一）（二）”）
            - 标题层级做“分组边界”（H2/H3 下的段落不要跨组乱拼）
            - 表格：优先转成结构化字段；退而求其次用“行块”切分并保留表头上下文

2. Overlap 怎么选：它不是越大越好，是“防边界事故”的保险
    - overlap 解决的核心问题
        - 切分边界很容易把信息切成：
            - 上一块末尾：条件/前提
            - 下一块开头：结论/例外
            - 如果没有 overlap，你可能永远召回不到“条件+结论同时出现”的证据块。

    - overlap 的常用取值
        - 按比例：10%–20% 的 chunk 长度
        - 按 token：40–80 tokens 是非常常见的甜点区间
        - （chunk 300 tokens，overlap 60 tokens，就是 20%）

    - 什么时候需要更大 overlap（但别太夸张）
        - 规则经常“跨段落引用上一段定义”
        - PDF 解析导致断行/断句不稳定
        - 文档喜欢在段尾写“除外情况见下一款”
        - 这时可以上到 20%–30%（或 80–120 tokens），但要意识到代价：索引变大、重复召回增多、上下文去重压力变大。

    - 什么时候 overlap 反而应该小
        - 你是严格按“条款/项”切分，且每块天然自洽
        - 你后面有 rerank + 压缩做得很好
        - 这种情况下 overlap 5%–10% 就够用，甚至可以对“定义块”设为 0（定义本身就短）。

    - 关键思路：结构化切分越强，overlap 越可以小；切分越粗暴，overlap 越得大。

3. 为什么医疗规则更适合“结构化切分 + 元数据过滤 + 混合检索”
    - 医疗规则/医保政策文档，有几个“天生反 RAG 玄学”的特性：
        - 版本、地区、生效期会致命
        - 同一句“可报销/不可报销”，在不同地区、时间、人群下结论可能相反。
        - 只靠向量相似度会把“语义很像但版本不对”的 chunk 拉出来，模型照样能写得头头是道——这就是生产事故。
        - 所以必须用 元数据过滤把检索空间先砍对：
            - region / hospital
            - policy_version / publish_date / effective_date
            - patient_type（门诊/住院）
            - authority_level（国家/省/市/院内）
            - doc_status（现行/废止/征求意见稿）
        - 这不是优化，这是底线。
        - 大量“精确匹配”元素，向量不擅长
        - 医保领域有很多“语义不重要但字符精确重要”的东西：
            - 药品名、耗材名、项目编码、ICD/手术编码
            - 条款号、附件表格编号
            - 数值阈值（≤、≥）、比例、封顶线
    - 医疗政策通常有清晰结构（定义、适用范围、条件、流程、例外、附表）。
    - 你按结构切分后，每个 chunk 更“主题单一 + 自洽”，embedding 表达更稳定，检索更可控；同时引用也更容易（第几条第几款/表几）。

4. 一套“可直接落地”的推荐组合
    - 切分：按标题层级 + 条款/款/项；每块尽量自洽
    - chunk 大小：主体 200–400 tokens；定义/阈值/例外块 80–160 tokens
    - overlap：结构化切分为主时 40–80 tokens（10%–20%）；结构弱时可到 80–120
    - 检索：hybrid（向量 + BM25）召回 topK（例如各取 20 合并去重）
    - 过滤：先按 region/version/effective_date 等元数据缩小宇宙，再做相似度
    - 后处理：去重 + rerank +（必要时）压缩，控制 token 预算

# 3. RAG查询理解

## 3.1 查询理解到底在解决什么问题

1. 用户的原始问题通常有这些天然缺陷：
    - 信息不全：缺地区、缺时间、缺人群、缺业务场景（门诊/住院、统筹/个人、特殊病种等）
    - 表达模糊：比如“能不能报”“怎么走流程”——缺指向哪条政策、哪个版本
    - 口语化：检索更吃“关键术语/编码/条款号”，用户未必会说
    - 一问多事：把 3 个子问题揉成一句
    - 带上下文：多轮对话里“这个/那种情况”必须回指前文
    - 查询理解就是把这些坑填上、把“检索信号”提纯。

## 3.2 Query Understanding 的核心产物（你最终想得到什么）
1. 我建议你把查询理解的输出想象成一个结构体（工程上很爽）：
    - intent：用户想要什么类型的答案（规则判定 / 流程步骤 / 资格条件 / 对比差异 / 例外情况 / 失败原因排查…）
    - entities：关键实体（药品名、项目名、编码、机构、科室、票据/结算类型）
    - constraints：约束条件（地区、医院、版本、生效期、人群、门诊/住院、医保类型、金额阈值…）
    - query_rewrites：一组更“适合检索”的改写（通常不止一个）
    - keywords：用于 BM25/倒排的关键词集合（含同义词、别名、缩写）
    - sub_questions：如果是复杂问题，拆成可检索的子问题序列

2. 这玩意儿的作用：让后续召回“先过滤再相似”，而不是在整个宇宙里靠语义碰运气。

## 3.3 查询理解常见的子模块（理论到工程的映射）

1. 意图识别（Intent Classification）
    - 同一句“XX 怎么报销”，可能是：
        - 规则判定：能不能报？条件是什么？
        - 流程操作：窗口/系统怎么走？需要哪些材料？
        - 异常排查：为什么报销失败？错误码含义？
        - 差异对比：门诊 vs 住院、地区 A vs 地区 B

    - 意图识别决定你后面要检索的“证据类型”不同：
        - 规则判定更吃“条件/例外/阈值”，异常排查更吃“错误码说明/处理手册”。

2.  实体抽取与规范化（Entity Extraction & Normalization）
    - 医疗规则场景里，这是命门之一。
    - 抽取：
        - 疾病/诊断、药品/耗材、项目、编码（ICD、手术码、收费项目码）、人群类型、险种、机构
    - 规范化（很关键）：
        - 同义词/别名：比如药品商品名 vs 通用名
        - 缩写展开：DRGs/DIP、门慢门特等
        - 编码校验：看起来像编码就当成关键词强信号

    - 理论点：embedding 负责语义近似，实体/编码负责精确定位。两者要合体。
 
3. 约束补全与过滤条件生成（Constraint Inference → Metadata Filters）
    - RAG 最怕的事故：召回到了“语义很像但版本/地区不对”的条款。
    - 所以查询理解要尽力把约束补出来，哪怕只补出“需要用户补充”的缺口。
    - 典型约束：
        - 地区/医院：上海？广东？某院内？
        - 生效期/版本：2024 年新政？当前执行？
        - 场景：门诊/住院/急诊？统筹/个人账户？特殊病种？
        - 人群：职工/居民/异地/军人/学生？

    - 工程上可以做两档：
        - 硬过滤：用户明确给了的（如“上海 2025 年”）必须过滤
        - 软提示：用户没给、但强相关的（如门诊/住院）可以先召回两类，再在回答前要求确认；或者在 query rewrite 里生成多候选查询

4. Query 改写/扩写（Rewrite / Expansion）
    - 目的不是“把问题写得更漂亮”，而是提高召回概率与精确性。
    - 常见做法：
        - 术语化改写：把口语换成文档里常出现的表述
        - “能不能报”→“报销条件/支付范围/限定支付/不予支付”
        - 同义扩写：加入同义词、别名、缩写
        - 多查询生成：生成 3～5 个不同角度的检索 query（用于多路召回合并）
    - 理论点：这相当于在检索前做“查询分布扩展”，提升召回率上限。

5. 复杂问题拆解（Decomposition / Multi-hop Planning）
    - 遇到这种问题就该拆：
        - “糖尿病患者在门诊开 XX 药，为什么这次结算失败？还能怎么处理？”
        - 拆成子问题更稳：
            - 找该药的支付政策（限定/适应症/人群/剂量等）
            - 找门诊 vs 住院差异条款
            - 找结算失败原因/错误码对照/处理流程
            - 找替代方案（材料补充、改走门特、改走住院等）
    - 理论点：单轮 topK 往往只能覆盖一个主题；拆解=让检索分阶段聚焦。

5. 对话上下文对齐（Conversational Grounding）
    - 多轮问答里，“这个/那种情况/上面说的”都必须解析到前文实体与约束。
    - 常见工程策略：维护一个 “conversation state”：
        - 当前地区、险种、场景、疾病、药品、版本等槽位
        - 新一轮 query 优先补齐槽位再检索

## 3.4 医疗规则为什么尤其依赖 Query Understanding
1. 因为它同时满足“三大麻烦”：
    - 约束维度多（地区/人群/场景/时间/机构）
    - 精确匹配强（编码、阈值、条款号、表格）
    - 术语密度高（用户口语和政策术语差一层“翻译”）

2. 所以你会看到：医疗 RAG 的效果上限，往往不是向量库决定的，是查询理解把约束和术语提纯到什么程度决定的。

# 4. RAG召回

## 4.1 介绍

1. 召回在 RAG 里到底干嘛
- 召回的核心目标是 高召回率（Recall）：
    - 只要“真正包含答案的 chunk”能进到 topK 候选里，后面就还有救；如果 topK 里压根没有答案，那模型再强也只能编或者含糊其辞。
    - 所以召回阶段更像“撒网捕鱼”，而不是“精确狙击”。

2. 召回的输入与输出
    - 输入一般是：
        - 用户 query（可能已被 Query Understanding 改写/扩写/拆解）
        - 过滤条件（metadata filters，比如地区、版本、生效期、门诊/住院）
        - topK 参数（要抓多少条候选）
    - 输出是：
        - 一组候选 chunks（通常带分数、来源、元数据）
        - 可能还带“召回解释信息”（用的是哪路检索、命中了哪些关键词等，便于调试）

3. 语义召回（Dense Retrieval / Vector Search）
    - 把 query embed 成向量，在向量库里找“最相近”的 chunk（常见 cosine/L2）。
    - 优点：
        - 用户口语、同义表达也能召回到（“怎么报销”能搜到“支付范围/限定支付”）
        - 对长文本、概念性问题很强
    - 缺点（也是医疗场景大坑）：
        - 对编码、条款号、药品名这种“必须精确命中”的字符串不靠谱
        - 容易把“语义很像但版本/地区不对”的内容抓上来（因此强依赖 metadata 过滤）

4. 关键词召回（Sparse Retrieval / BM25）
    - 基于倒排索引，按关键词匹配打分（BM25 是经典方案）。
    - 优点：
        - 对专名、编码、条款号、表格字段名特别强
        - 解释性好（命中哪些词一目了然）
    - 缺点：
        - 用户口语化、同义词变化大时容易漏（召回率掉）

5. 混合召回（Hybrid Retrieval）
    - 最常见的生产选择：Dense + Sparse 两路都召回，再融合。
    - 融合常用做法：
        - 简单 union：两路各取 topK，合并去重
        - RRF（Reciprocal Rank Fusion）：按名次融合，鲁棒性很好
        - 加权融合：向量分数与 BM25 分数归一化后加权（更难调，但可控）
    - 医疗/政策类为什么常用 hybrid：因为它同时需要“语义理解（dense）”和“精确定定位（sparse）”。

6. 召回的关键参数怎么理解
    1. topK：抓多少候选
        - K 太小：漏掉答案（召回率差）
        - K 太大：噪声爆炸，重排/压缩压力大，成本和延迟上升
        - 常见经验：先用离线评测找“拐点”，比如从 K=10 增到 30 收益明显，再增到 80 基本没收益，那 30 左右就是甜点。

    2. 候选池 vs 返回集
        - 有些系统会这样做：
            - 召回先抓候选池（比如 200 条）
            - 按 metadata 过滤/去重/简单规则过滤后，保留 30 条给 rerank
        - 这能兼顾召回率和后续成本。

    3. 过滤（metadata filters）
        - 医疗场景里，这个不叫优化，叫“防事故装置”：
        - 地区/机构：上海 vs 广东，院内 vs 省级
            - 生效期/版本：2023 政策 vs 2025 政策
            - 场景：门诊/住院/急诊，职工/居民
        - 先过滤再相似，系统才不会在错误的宇宙里算相似度。

4. 召回策略：从“单 query 单路”进化到“多 query 多路”

    - 召回的上限经常来自 Query Understanding 输出的一组 rewrites / sub_questions。
    - 常见做法：
        - 多 query 召回：对 3~6 条 rewrites 分别检索，再合并
        - 子问题分阶段召回：先找定义/范围，再找条款/例外，再找流程/材料
        - 领域词扩展：把“能不能报”扩展成“支付范围/限定支付/不予支付/适应症/门慢门特”等检索词
    - 这类做法的本质是：用多个“投影角度”去照同一个问题，提高包含答案的 chunk 被照亮的概率。

5. 召回的“常见坑”
    - 只用向量：编码/条款号/专名命中率低
    - 不做过滤：召回到过期/异地政策，模型还会写得像真的
    - chunk 切分不自洽：召回来了“半句话证据”，后续生成只能猜
    - K 设置靠拍脑袋：没有离线评测就只能玄学调参
    - 没做去重与多样性控制：topK 全是同一段附近的重复内容，浪费上下文
    - （可用 MMR 或简单的“相似度阈值去重”来提高证据覆盖面）

6. 怎么衡量召回好不好
    - 召回阶段最关键的指标是：
        - Recall@K：答案 chunk 是否出现在 topK
    - 配合看：
        - MRR / nDCG：答案在列表里排得靠不靠前（给 rerank 减负）
        - Latency：延迟是否可接受（召回通常是性能瓶颈之一）
        - Coverage：不同类型问题（规则/流程/排错/对比）是否都能抓到证据

## 4.4 在医疗政策场景，如何设计 metadata 的“硬过滤 vs 软过滤”，避免漏召回同时不召回错误版本
1. 医疗政策 RAG 里，metadata 过滤的正确姿势是：先把“绝对不能错的维度”当硬过滤（Hard Filter），再把“可能相关但用户没说清”的维度当软过滤（Soft Filter）做多路召回/降权/提示确认。核心目标就俩：
	•	不召回错误版本/错误地区（避免事故）
	•	不因为过滤太狠把答案过滤没了（避免漏召回）

### 4.2.1 先定义：哪些维度“错了就翻车”
1. 硬过滤（Hard Filter）：错了就直接不可用
    - 通常包括这些（按事故级别排序）：
        - doc_status / validity：现行 vs 废止 vs 征求意见
        - jurisdiction（管辖范围）：国家/省/市/区/医院
        - region / city / hospital_id：地区或机构明确时必须硬过滤
        - effective_date（生效期）：有明确时间点时硬过滤

2. 软过滤（Soft Filter）：错了不一定翻车，但会影响结论
    - 常见维度：
        - visit_type：门诊/住院/急诊（用户没说时不要硬卡死）
        - insurance_type：职工/居民/商保（没说就先别硬卡）
        - population / eligibility：儿童/孕产/慢病/门特/异地等
        - provider_level：基层/二级/三级、定点/非定点
        - payment_rules：起付线/封顶线/比例口径（很多条款分段）

### 4.2.2 把过滤做成“两阶段”，同时保召回率
1. 阶段 A：硬过滤宇宙（缩小到“正确宇宙”）
    - status=有效
    - region/city/hospital（若已知）
    - effective_date（若已知）
    - authority/jurisdiction（若已知）

2. 阶段 B：软过滤与排序（不删，先降权/分桶）
    - 对候选证据做：
        - 分桶：门诊桶、住院桶、门特桶、异地桶…
        - 打标签：coverage=“覆盖用户条件/缺条件/条件冲突”
        - 重排时把“覆盖更多已知约束”的 chunk 排前面

### 4.2.3 关键：如何“避免漏召回”——设计回退策略（Fallback）
1. 硬过滤很强，但也最容易把答案过滤没。生产里必须配“回退阶梯”，而且要可解释、可审计。
2. 回退阶梯示例（从严格到宽松）
    - 假设用户说：上海 + 2025 + 职工 + 门诊
        - 严格：region=上海 AND year=2025 AND status=有效
        - 放松时间窗口：region=上海 AND effective_date ∈ [2024-01, 2026-12]
        - 放松到“最新有效”：region=上海 AND status=有效，按 effective_date desc 排序
        - 放松地域层级（慎用）：region=上海市 → 上海所属省级/国家级指导文件（用于补概念/定义，不用于给最终结论）
    - 每次回退要记录：为什么回退、回退了哪条规则，并在最终回答里标注“依据不足/使用了上级指导口径”。
    - 重点：回退不是“瞎放开”，是“有序放开”，并且对“权威性/层级”要降权。

### 4.2.4 关键：如何“避免召回错误版本”——引入“版本优先级与冲突检测”
1. 就算硬过滤做对了，库里也可能同时存在多个“有效但不同版本/口径”的条款。你需要两个机制：
    1. 版本优先级（Version precedence）
        - 给每份文档/条款一个 rank：
            - authority_level（国家>省>市>院内，或按你业务定义）
            - publish_date / effective_date（新优先）
            - doc_type（正式文件>解读稿>FAQ>新闻）
            - explicit_scope_match（是否明确适用于“职工/门诊/门特”等）
        - 重排时：优先级更高者排前。
    2. 冲突检测（Conflict detection）
        - 当 topN 证据出现明显冲突（如“可报销” vs “不予支付”），不要让模型自己“投票”。策略是：
            - 同时把冲突证据都给 LLM
            - 让它输出：冲突点、各自适用范围、缺失条件（例如“门特资格/适应症/定点机构”）
            - 给出“需要确认的条件清单”，而不是强行下结论
        - 这会让系统从“胡乱给结论”变成“像审计员一样谨慎”。

### 4.2.5 一个可落地的“硬/软”配置模板（你可以直接抄到设计文档）

1. Hard filters（默认必须满足）：
    - status = active
    - region/city/hospital：用户明确 → 必须；不明确 → 不设
    - effective_date：用户明确 → 必须；不明确 → 取最新 active
    - jurisdiction/authority：用户明确 → 必须；不明确 → 允许多层级但降权

2. Fallback ladder：
    - 时间窗口放宽（±6~18 月）
    - 地域层级上探（市→省→国家，仅用于补概念）
    - 约束缺失时多路召回（门诊/住院各一套 query）

### 4.2.6 工程实现小抄：两种实现路径
1. 两种实现路径
    - 路径 1：向量库支持 metadata filter（推荐）
        - 在检索 API 里直接传 filter：region="上海" AND status="active" AND effective_date<=today
        - 然后对结果做 soft rerank
    - 路径 2：FAISS 不支持过滤（你现在 demo 的情况）
        - 先大召回（比如 100~300）
        - 在应用层按 hard filters 过滤
        - 不足再触发回退阶梯
        - soft constraints 用重排/打分实现

# 5. 重排与压缩（Rerank & Compress）

## 5.1 介绍
1. 这一阶段的核心目标
    - 重排（Rerank）
    - 把召回的候选 chunks（可能几十到几百）按“与问题真正相关 + 能支撑答案”的程度重新排序，选出最有用的 topN。
    - 压缩（Compress）
    - 把选出的证据进一步“浓缩成对回答有贡献的最小片段”，降低 token、减少噪声、提升可引用性。
    - 一句话总结：Rerank 决定你用哪几份证据；Compress 决定每份证据给 LLM 喂哪几口。

2. 为什么必须做重排
    - 向量召回/BM25 召回的排序，本质是“相似度/词频相关”，不等于“能回答问题”。
    - 典型错误：
        - 召回到“主题相近”的段落，但关键条件/例外不在这段
        - 召回到“解释性文字”，却缺结论或执行口径
        - 医疗政策里：召回到了另一地区/旧版本的条款（即使你做了过滤，也可能有边界冲突）
    - 重排要解决的就是：让“能直接用来回答”的证据排前面。

3. 重排的常见方法（从便宜到强）
    1. 规则重排（Rule-based）
        - 适合做“硬性加权”和“质量门槛”，成本极低：
            - 命中条款号/编码/药品名：加分
            - metadata 匹配更多（地区/门诊住院/险种/生效期）：加分
            - 来源权威性更高、版本更新：加分
            - chunk 太短且无结论/无条件：降分
        - 优点：可控、可解释
        - 缺点：覆盖有限，遇到复杂语义容易漏

    2. 交叉编码器重排（Cross-Encoder Reranker）
        - 思想：把 (query, chunk) 一起输入一个更“精读型”的模型，让它直接判断相关性（比纯 embedding 相似度更准）。
            - 召回：快（向量/关键词）
            - 重排：准（精读判断）
        - 工程上常见做法：召回 50200 → rerank 取 top 520
        - 优点：准确率显著提升
        - 缺点：成本更高（要对每个 chunk 跑一次模型/打分）

    3. LLM-as-a-reranker（用大模型当裁判）
        - 让 LLM 看 query + 多个候选，输出最相关的 N 个（或打分）。
        - 优点：能理解复杂语义、能按业务规则“挑证据”
        - 缺点：贵、慢、稳定性依赖提示词；需要强约束输出格式

    4. 学习排序（LTR, Learning to Rank）
        - 用标注数据训练一个排序模型（融合 BM25、向量分数、元数据、文本特征等）。
        - 优点：极致效果、可长期迭代
        - 缺点：需要数据闭环与标注成本

4. 重排到底“排什么”：不只是相关性
    1. 在医疗政策场景，重排目标通常至少包含四个维度（可以变成一个综合分）：
        - 相关性：这段是不是在讲用户问的主题/实体
        - 适用性：地区/险种/门诊住院/人群等约束是否匹配
        - 权威与时效：是否最新、是否有效、是否权威来源
        - 可用性：是否包含“条件/结论/例外/阈值”这些可落地信息（而非纯背景）

    2. 所以你会看到很多系统做“两段式重排”：
        - 第一段：语义相关（cross-encoder）
        - 第二段：业务加权（metadata + 规则）

5. 压缩（Compress）：让证据“足够短但不丢要点”
    - 压缩不是摘要那么简单，它更像“证据提取”。
    - 去重（Dedup）
        - 召回经常把同一段附近的内容抓很多遍，必须去重：
            - 文本哈希/相似度阈值去重
            - 同一来源同一章节只保留最强一条

    2. 片段抽取（Extractive compression）✅（更适合政策/规则）
        - 从 chunk 里抽取与 query 最相关的句子/条款行：
            - 只保留“条件句、结论句、例外句、数值阈值、定义”
            - 保留上下文 1~2 句避免断章取义
        - 优点：不容易改写原意，适合高风险领域
        - 缺点：需要好的句子级打分/规则

    3. 结构化压缩（Policy-aware compression）✅（医疗非常推荐）
        - 把证据压成结构化字段再喂给 LLM，例如：
            - 适用范围：
            - 报销/支付结论：
            - 限定条件（适应症/资格/定点/额度）：
            - 例外条款：
            - 引用位置（第X条/附件表Y/页码）：
        - 这样 LLM 的“自由发挥空间”更小，更像在填表而不是作文。

    4. 生成式摘要（Abstractive summary）
        - 让模型重写成更短的摘要。
        - 优点：更短、更顺
        - 缺点：可能引入偏差/幻觉（在医疗政策里要慎用，除非你能对齐引用）

6. 一个推荐的生产流水（非常通用）
    1. 召回候选池：dense top100 + BM25 top100 合并
    2. 硬过滤：有效性/地区/版本/生效期
    3. 去重 + 多样性：避免全是同一章节
    4. rerank：cross-encoder 选 top 10~20
    5. 压缩：抽取关键句 + 结构化整理
    6. 最终给 LLM：top 5~10 条“短而硬”的证据 + 引用信息

7. 这一步最常见的坑
    - rerank 只看语义不看 metadata：相关但不适用的条款被顶上来
    - 压缩把“例外条款”剪掉：结论直接反转，事故级
    - 只做摘要不留引用：无法审计/无法追溯
    - topN 选太少：证据不够覆盖“条件+例外+流程”，回答变猜谜
    - 没做多样性：证据集中在一个角度，遗漏关键限制条件

# 6. 生成（Generation）

## 6.1 介绍

1. 生成阶段的输入
	1.	用户问题（原问题 + Query Understanding 结构化信息）
        - intent、实体、约束（地区/险种/门诊住院/时间）、子问题
	2.	证据包（Context / Evidence Pack）
        - rerank 后 topN chunks
        - 每条 chunk 带：来源、版本、生效期、章节/页码、可信度/权威级别
	3.	输出规范（Response Spec）
        - 必须引用、必须声明不确定、必须列出缺失条件
        - 输出格式（JSON / Markdown / 分段结构）
	4.	风险控制规则（Safety / Policy Rules）
        - “证据不足不得下结论”
        - “冲突证据不得强行选择，必须提示差异与补充条件”
        - 医疗合规：不提供诊断/治疗建议（如果你系统面向患者端）

2. 生成阶段的核心任务（不只是“回答”）
    1. 证据对齐（Grounding）
        - 每个关键结论必须能指向证据片段（引用 id / 来源）
	2.	条件化结论（Conditional Answering）
        - 医疗政策几乎都是“如果 A 且 B，则 C；除非 D”。
        - 生成必须按条件输出，不允许一句话拍板。
    3. 冲突处理（Conflict Handling）
        - 证据冲突时：列出冲突点、各自适用范围、需要补充的判定条件
        - 不让模型“投票决定谁对”
    4. 不确定性管理（Uncertainty / Abstention）
        - 缺地区/版本/门诊住院/险种 → 明确说“缺关键约束，无法确定”
        - 给出“需要你补充的信息清单”
    5. 可执行建议（Actionable Next Steps）
        - 对“结算失败/流程问题”类：给排查路径（材料、资格、定点、编码、门特门慢、处方限制…）
        - 对“规则判定”类：给“最小补充信息”与“验证入口”（例如查看哪份文件的哪个条款）

3. 医疗政策场景：推荐的输出结构（强约束、少幻觉）
    1. 结论（带条件）
        - 例：在 上海职工医保 且 门诊慢病资格已备案 且 药品属于目录并满足适应症/限定支付 的情况下，通常可以按政策支付/报销。
    2. 依据（证据引用）
        - 列出 3~5 条最关键证据，每条：来源/版本/生效期/章节/摘要/引用ID
    3. 例外与限制
        - 限定支付、适应症限制、定点机构限制、额度/封顶线、处方天数限制等
    4. 结算失败排查（若用户问了）
        - 资格（门特/慢病备案/异地就医）
        - 目录（药品/项目是否在目录、支付类别）
        - 编码与收费（ICD/项目编码匹配、套打/上传规则）
        - 机构（定点/等级、处方外配、统筹区限制）
        - 系统（HIS/医保接口错误码、对照表）
    5. 需要补充的信息清单
        - 城市/统筹区、政策年份、门诊/住院、险种、是否门特门慢、药品规格、诊断编码等

4. 提示词（Prompt）怎么设计：把模型当“审计员”
    - 生成阶段最关键不是“写得好”，是“写得可控”。你要在系统提示里明确：
        - 必须先读证据，再回答
        - 所有结论必须有引用
        - 证据不足/冲突时必须拒答或条件化
        - 不得引入证据外的新事实
    - 一种很实用的写法是“硬规则 + 输出格式”，例如（伪模板）：
        1. 规则：
            - 只允许使用 evidence 中信息
            - 每条结论必须引用至少 1 条 evidence_id
            - 如果 evidence 不包含答案，输出“不足”并列出需要补充的信息
            - 若 evidence 冲突，输出冲突对照与澄清条件，不得强行选择
            - 输出结构固定（如上 5 段）

5. 生成阶段常用的两种模式
    - 直接生成（Direct Answering）
        - 一次性输出完整答案。适合简单问题、证据一致时。
    - 先“证据推理表”，再“最终回答”（两段式）
        - 先让模型输出一个结构化中间结果（内部可见或也可返回）：
            - facts：从证据抽取到的事实
            - rules：条款/限制
            - missing：缺失条件
            - conflicts：冲突点
        - 再输出最终回答。

6. 生成阶段的“事故点”与防护
    1. 证据漂移（evidence drift）：模型开始引用证据外的常识
        - 防护：强制“证据内回答”，并在输出里要求引用 id
    2. 忽略例外条款：只看结论不看限制
        - 防护：输出结构里专门留“例外与限制”段；压缩时保证例外不丢
    3. 冲突时瞎裁决：模型选一个看起来更像真的
        - 防护：要求冲突对照输出 + 需要澄清的条件
    4. 过度确定性：其实缺地区/版本却给确定结论
        - 防护：把关键约束列成“必填槽位”，缺一个就只能条件化或拒答

7. 生成质量怎么评估（别只看“像不像人话”）
    - 至少看这些指标：
        - Faithfulness / Groundedness：回答是否被证据支持（是否“有据可查”）
        - Citation accuracy：引用的证据是否真的支持那句话
        - Completeness：是否覆盖用户 intent 的所有子问题（规则+流程/排错等）
        - Safety：是否在证据不足时收敛（敢说不知道）
