# Redis 常见面试题题目清单

# 一、基础与数据结构类

## 1. Redis 为什么快？从内存、I/O 模型、线程模型、数据结构几个角度讲。

### 标准答案

Redis 快，核心不是单一原因，而是**内存访问 + 非阻塞 I/O + 少锁竞争 + 高效数据结构**这几件事叠加出来的结果。

第一，**基于内存**。
Redis 的数据主要放在内存里，读写不需要像 MySQL 那样频繁走磁盘随机 I/O，内存访问延迟远低于磁盘，这是它高性能的基础。

第二，**I/O 模型高效**。
Redis 采用 **I/O 多路复用**，通过 `epoll`、`kqueue` 这类机制，用少量线程监听大量连接事件。这样一个线程就能高效处理很多客户端请求，避免为每个连接都创建线程带来的上下文切换成本。

第三，**命令执行层通常是单线程**。
Redis 的核心命令处理长期是单线程模型，这样带来的最大好处是：**没有复杂的锁竞争和线程切换开销**。因为绝大多数命令都在一个线程里串行执行，所以实现简单、CPU 利用率高、延迟也更稳定。
注意，Redis 6.x 之后引入了多线程，但主要是**网络 I/O 读写和协议解析**可以多线程，命令执行核心路径仍然主要是单线程。

第四，**数据结构设计很适合高频读写**。
Redis 并不是简单用 Java 里那种通用集合，它内部针对不同场景做了优化，比如：

- String 底层有 **SDS（Simple Dynamic String）**，**SDS 是 Redis 为了替代 C 字符串而设计的动态字符串结构，核心价值是“带长度、可扩容、二进制安全、性能更稳定”。**长度获取是 O(1)，还能减少缓冲区溢出问题
- Hash、Set 底层有哈希表，查找效率高
- ZSet 结合了 **跳表 + 哈希表**，既支持按 member 快速查，也支持按 score 有序范围查询
- rehash 采用**渐进式 rehash**，避免一次性迁移导致长时间阻塞

第五，**大多数操作时间复杂度低**。
Redis 官方推荐的常用命令，大量都是 O(1) 或接近 O(logN) 的复杂度，只要你不去滥用 `KEYS`、大范围 `ZRANGE`、超大集合操作，性能通常很稳。

第六，**协议简单、实现路径短**。
Redis 使用 RESP 协议，序列化和反序列化成本相对低，服务端处理链路短，没有关系型数据库那种复杂优化器、执行器、事务调度链路，所以单请求执行非常轻。

### 一句话总结

Redis 快，本质上是：**数据在内存、网络处理高效、核心执行少锁少切换、内部数据结构专门为高频操作优化**。

## 2. Redis 是单线程吗？为什么单线程还能这么快？6.x 之后多线程体现在哪？

### 标准答案

Redis 不能简单说成“就是单线程”，更准确的说法是：**Redis 的核心命令执行模型长期是单线程的，但在 6.x 之后，网络 I/O 读写可以引入多线程。**

第一，**为什么大家常说 Redis 是单线程**。
因为 Redis 最核心的部分，也就是**命令执行、数据读写、键值操作**，长期主要由一个主线程串行处理。客户端命令最终还是按顺序在主线程里执行，这也是 Redis 避免锁竞争、保证实现简单和延迟稳定的关键。

第二，**单线程为什么还能很快**。
原因主要有 4 个：

1. **Redis 是内存数据库**
  操作主要发生在内存里，不像 MySQL 那样大量依赖磁盘 I/O，所以单次访问非常快。
2. **单线程避免了锁竞争和线程切换**
  多线程系统里，经常会有锁、竞争、上下文切换、伪共享这些开销。Redis 核心执行单线程，天然避免了这些复杂成本，执行路径非常短。
3. **I/O 多路复用提升了连接处理效率**
  Redis 虽然命令执行是单线程，但网络层会用 `epoll` 这类 I/O 多路复用机制监听大量连接，所以一个线程也能高效处理很多 socket 事件。
4. **Redis 内部数据结构做了高度优化**
  常见操作复杂度低，大量命令是 O(1) 或 O(logN)，所以单线程就足以支撑很高吞吐。

第三，**Redis 6.x 之后多线程体现在哪**。
Redis 6 引入的多线程，主要不是把“命令执行逻辑”彻底并行化，而是把**网络 I/O 相关工作**拆出来，比如：

- socket 读
- 请求解析
- 响应写回

这些环节可以交给多个 I/O 线程处理。
但真正对键值数据的命令执行，仍然主要在主线程串行完成。

所以 Redis 6.x 的改进本质是：

> 用多线程减轻网络 I/O 和协议处理开销，让主线程更专注于执行命令。

第四，**为什么 Redis 不把命令执行也彻底多线程化**。
因为 Redis 的核心优势之一就是简单、少锁、可预测。如果命令执行全面多线程化，就要面对：

- 数据并发访问控制
- 锁设计
- 死锁风险
- 实现复杂度上升
- 延迟抖动加大

这会破坏 Redis 原本“简单高效”的设计哲学。所以 Redis 选择的是一个折中方案：**I/O 多线程，执行尽量保持串行。**

### 一句话总结

Redis 核心执行模型主要还是单线程，但它快是因为：**内存访问快、I/O 多路复用高效、没有复杂锁竞争、内部数据结构优化好**；Redis 6.x 之后的多线程，主要体现在**网络 I/O 读写和协议处理**，不是把所有命令执行都并行化。

### 高频追问点

如果面试官继续追问，你顺手可以补一句：

- Redis 单线程快，不代表不会被慢命令拖死
- 像 big key、长 Lua、`KEYS`、大范围聚合命令，一样会阻塞主线程，导致整个实例 RT 抖动

## 3. 跳表为什么适合做 ZSet？为什么不用红黑树？

### 标准答案

Redis 的 ZSet 之所以适合用**跳表**，核心是因为它要同时满足两类需求：

- 按 member 快速查找、更新 score
- 按 score 做**有序范围查询、排名查询、顺序遍历**

所以 Redis 实际上不是只用跳表，而是 **跳表 + 哈希表** 组合：

- **哈希表**：根据 member 快速定位元素，时间复杂度接近 O(1)
- **跳表**：按 score 维持有序结构，支持范围查找、排名、顺序遍历，复杂度 O(logN)

第一，**为什么跳表适合 ZSet**。
因为 ZSet 的典型操作很多都和“有序集合”有关，比如：

- 查某个分数区间的数据
- 查 TopN / 排行榜
- 查某个元素的排名
- 按 score 顺序遍历

**跳表天然就是一种支持有序查找和范围扫描的数据结构，插入、删除、查找平均复杂度都是 O(logN)，而且顺序遍历非常自然，特别适合排行榜这类场景。**

第二，**为什么不用红黑树**。
红黑树理论上也能做到 O(logN)，但 Redis 选跳表更偏工程实现上的综合收益，主要有几个原因：

1. **实现更简单**
  跳表本质上是多层有序链表，代码实现和维护成本比红黑树低很多。
   红黑树插入、删除都要处理复杂旋转和染色，代码更难写，也更难维护。
2. **范围查询和顺序遍历很友好**
  跳表底层是链式结构，找到起点后顺着 next 指针往后扫就行，做区间遍历很自然。
   红黑树虽然也能中序遍历，但工程上做范围扫描不如跳表直接。
3. **性能上足够好，而且更稳定**
  跳表平均复杂度是 O(logN)，对 Redis 这种以内存为主、强调工程可维护性的系统来说已经够用。
   Redis 不追求“理论最优的教科书优雅”，更看重**实现复杂度、常数因子、维护成本和实用性**。
4. **更适合做 rank / 范围操作扩展**
  Redis 的跳表节点里还能维护 span 等辅助信息，用来支持排名计算，这对 ZSet 很实用。
   换成红黑树，当然也能做，但实现会更复杂。

第三，**为什么 Redis 不是只用跳表**。
因为如果只用跳表，按 member 找元素会比较慢。
而 ZSet 又经常需要这种操作，比如：

- 给某个 member 改 score
- 判断某个 member 在不在
- 删除某个指定 member

所以 Redis 才会同时维护：

- 一个 dict：member -> score
- 一个 skiplist：按 score 排序

这样就把“查 member 快”和“按 score 有序”两件事同时满足了。

### 一句话总结

跳表适合 ZSet，是因为它**实现简单、支持有序范围查询和顺序遍历、平均复杂度 O(logN) 且工程上很好维护**；不用红黑树，不是因为红黑树不行，而是**Redis 更看重实现复杂度和区间操作友好性**，跳表在 ZSet 这个场景下是更合适的工程选择。

## 4. Redis 的 Dict 是怎么实现的？rehash 过程中会发生什么？

### Redis 的 Dict 实现与 Rehash 过程

Redis 的 `Dict` 本质上是 **渐进式 rehash 的哈希表实现**，底层不是单表，而是 **两个哈希表 + 一个 rehash 进度指针**。这样设计的核心目标是：**避免一次性扩容/缩容带来的长时间阻塞**。

Redis 的字典结构可以概括为三层：

`dict`：字典总控结构，内部维护 `ht[0]`、`ht[1]` 两个哈希表，以及 `rehashidx`
`dictht`：单个哈希表，包含 `table` 数组、`size`、`sizemask`、`used`
`dictEntry`：桶中的节点，保存 `key`、`value`、`next`，也就是 **数组 + 链表** 的结构，属于 **拉链法解决哈希冲突**

可以理解成：

1. 正常情况下只使用 `ht[0]`
2. 当需要扩容或缩容时，给 `ht[1]` 分配新空间
3. 然后把 `ht[0]` 的数据**一点一点搬到** `ht[1]`
4. 搬完后让 `ht[1]` 替代 `ht[0]`

---

### Dict 的核心结构

源码层面可以简化理解为：

```c
typedef struct dictEntry {
    void *key;
    union {
        void *val;
        uint64_t u64;
        int64_t s64;
        double d;
    } v;
    struct dictEntry *next;
} dictEntry;

typedef struct dictht {
    dictEntry **table;
    unsigned long size;
    unsigned long sizemask;
    unsigned long used;
} dictht;

typedef struct dict {
    dictType *type;
    void *privdata;
    dictht ht[2];
    long rehashidx; // -1 表示当前没有在 rehash
    unsigned long iterators;
} dict;
```

几个关键点：

`table` 是桶数组
每个桶挂一个 `dictEntry` 链表  
** `size` 通常是 **2 的幂**，这样定位桶位时可以用 `hash & sizemask`，比取模更快 **  
`ht[0]` 是当前使用表，`ht[1]` 只在 rehash 时存在
`rehashidx = -1` 说明当前没有 rehash

---

### 为什么要有两个哈希表

因为 Redis 不希望在扩容时一次性把所有数据搬迁完。
假设字典里有几百万个 key，如果一次性 rehash，会导致主线程卡顿，直接拉高请求延迟。

所以 Redis 采用 **渐进式 rehash**：

新表先建好
旧表数据分批迁移
每次增删改查时顺带搬一点
把大开销拆成很多小开销

这就是 Redis Dict 的关键工程设计。

---

### 什么时候触发 rehash

主要两类：

**1）扩容**

当哈希表负载因子达到一定条件时扩容。一般可以理解为：

负载因子 = `used / size`

常见经验是：

没有执行 `BGSAVE` / `BGREWRITEAOF` 时，负载因子较高就可能扩容
如果后台正在进行持久化子进程操作，为了减少写时复制开销，扩容会更保守

**2）缩容**

当负载因子过低，并且表里元素明显变少时，可能触发缩容，避免空间浪费。

---

### rehash 过程中会发生什么

rehash 开始时，会发生这几件事：

**第一步：为 `ht[1]` 分配新空间**

如果是扩容，`ht[1]` 的大小一般选择 **大于等于当前元素数量的最小 2 的幂**
如果是缩容，也是分配一个更合适的新表

**第二步：设置 `rehashidx = 0`**

表示开始从 `ht[0].table[0]` 这个桶往后迁移

**第三步：渐进迁移桶数据**

每次 rehash 并不是迁一个元素，而是迁 **一个或多个桶**。
Redis 会把 `ht[0][rehashidx]` 桶上的链表节点重新计算索引，挂到 `ht[1]` 对应桶中，然后把旧桶清空，再让 `rehashidx++`

**第四步：迁移完成后切换表**

当 `ht[0].used == 0` 时，说明旧表搬空了，此时：

让 `ht[0] = ht[1]`
重置 `ht[1]` 为空表
设置 `rehashidx = -1`
rehash 完成

---

### 渐进式 rehash 的关键行为

在 rehash 期间，Redis 的字典操作会有一些特殊表现：

**1）新写入的数据只进 `ht[1]`**

一旦进入 rehash，新增 key 不会再写入旧表 `ht[0]`，而是直接写入新表 `ht[1]`。
这样可以保证数据迁移方向单向，避免反复搬运。

**2）查询要查两张表**

查找一个 key 时：

先查 `ht[0]`
再查 `ht[1]`

因为数据可能还没迁过去，也可能已经迁过去了。

**3）删除/更新也可能发生在两张表**

因为 key 所在位置不确定，所以也要同时考虑两张表。

**4）每次字典操作会顺带做一次 rehash**

例如 `dictAdd`、`dictFind`、`dictDelete` 这些操作，若发现当前正在 rehash，通常会顺手推进一次 `dictRehashStep()`。
这就是所谓的 **借业务操作分摊迁移成本**。

---

### 为什么不会阻塞太久

因为 Redis 不是一次性搬完，而是把搬迁拆散到很多小步骤里。

也就是说，单次命令最多只额外承担少量桶迁移成本，而不是把整张表全搬一遍。
这样虽然总成本没变，但 **单次请求的延迟尖刺会小很多**，这是典型的“用吞吐换尾延迟稳定性”的工程做法。

---

### rehash 时是否还能正常提供服务

可以，**Dict 在 rehash 期间是可读可写的**。

这也是双表设计的意义：

旧表还没搬完的数据继续在旧表
新数据直接进新表
查找时查两边
迁移过程对上层业务基本透明

所以 Redis 在 rehash 期间仍然可以正常处理命令，只是单次命令可能多承担一点迁移成本。

---

### 生产里要注意的点

第一，**渐进式 rehash 不是完全没有成本**。如果某个桶链表特别长，迁这个桶时仍可能出现一次性抖动，所以哈希函数分布质量很重要。

第二，**fork 持久化期间扩容更谨慎**，因为大量内存页变更会放大 COW 成本，增加内存压力。

第三，虽然 Redis 现在很多结构都尽量优化，但 Dict 从本质上仍然是 **哈希表 + 冲突链**，不是 JDK8 那种链表转红黑树结构。

---

### 小结

Redis 的 Dict 本质是 **两个哈希表 + 链地址法 + 渐进式 rehash**。
rehash 时不会一次性迁移全部数据，而是：

创建新表
开启 `rehashidx`
每次操作顺带迁移部分桶
新数据写入新表
查询两张表
迁移完成后切换新旧表

这样做的核心收益是：**避免大 key 空间扩缩容时阻塞主线程，控制延迟抖动。**

## 5. 什么是渐进式 rehash？为什么要渐进，而不是一次性迁移？

### 什么是渐进式 rehash？为什么不用一次性迁移？

渐进式 rehash，就是 **Redis 在哈希表扩容或缩容时，不一次性把旧表所有数据搬到新表，而是分多次、分批次迁移**。实现上通常是保留两张表：旧表 `ht[0]` 和新表 `ht[1]`，然后通过一个 `rehashidx` 记录当前迁移到哪个桶。后续在处理读写命令时，顺带把一部分桶从旧表搬到新表，直到全部迁移完成。

之所以要“渐进”，核心原因是 **Redis 是单线程事件驱动模型**，如果一次性迁移整张哈希表，数据量一大就会导致主线程长时间阻塞。比如字典里有几十万、几百万个 key，一次性 rehash 会让某个命令执行时间突然变得很长，直接拉高 P99/P999 延迟，严重时会让客户端感觉 Redis 卡顿。渐进式 rehash 的本质，就是把一次大开销拆成很多次小开销，避免出现明显的延迟尖刺。

在渐进式 rehash 期间，Redis 仍然可以正常提供服务。新增数据直接写入新表，查询、删除、更新则可能同时检查旧表和新表，因为数据可能还没迁完，也可能已经迁过去了。这样对外部业务基本透明，只是每次操作会顺带承担一点点迁移成本。

如果采用一次性迁移，优点是实现简单，迁移完成也更快，但缺点非常明显：**单次阻塞时间不可控**。这在内存数据量大、线上请求高峰、对延迟敏感的场景下不可接受。Redis 选择渐进式 rehash，本质上是典型的工程取舍：**牺牲一点实现复杂度和迁移期间的查询成本，换取更平滑的服务延迟和更好的线上稳定性**。

小结一下：渐进式 rehash 就是“边处理请求，边搬数据”，目的不是减少总迁移成本，而是 **把大成本摊薄，避免阻塞主线程**。这也是 Redis 这种高性能内存数据库必须采用的设计。

## 6. Redis 的 ziplist / quicklist / listpack 分别是什么？为什么底层实现会演进？

这三个都是 Redis 为了 **节省内存、提升访问效率**，在不同阶段采用的紧凑型数据结构实现。可以把它理解成一条演进路线：

**ziplist：早期的紧凑连续内存结构**
**quicklist：为了解决大链表场景下 ziplist 的问题，引入的“链表 + ziplist”混合结构**
**listpack：为了解决 ziplist 设计缺陷而重新设计的新一代紧凑结构**

---

### ziplist 是什么

`ziplist` 本质上是 **一段连续内存**，里面顺序存放多个 entry。每个 entry 可以是整数，也可以是字符串。它的优点很明显：**没有普通链表那种大量前后指针开销，内存利用率高，CPU cache 友好**，所以非常适合存放小量数据。

Redis 早期会在很多“小对象”场景使用它，比如小的 `Hash`、`ZSet`，以及早期某些列表场景。

但它的问题也很明显：

第一，**插入/删除中间元素可能导致整段内存搬移**，时间复杂度高。
第二，**连锁更新（cascade update）问题** 比较麻烦。因为 ziplist 的节点会记录前一个节点长度，如果前一个节点长度变化，当前节点编码长度可能也要变，进而引发后续节点连续调整。
第三，整体实现比较绕，边界处理复杂，维护成本高。

所以 ziplist 适合“小而紧凑”的场景，但一旦数据变大或频繁修改，问题就会暴露出来。

---

### quicklist 是什么

`quicklist` 是 Redis 为 `List` 类型引入的折中方案，本质上是 **双向链表 + ziplist 的组合**。

你可以把它理解成：
不是一个链表节点只存一个元素，而是 **一个链表节点里放一个 ziplist**，这个 ziplist 再存多个列表元素。

这样设计的目的，是同时利用两种结构的优点：

链表负责分段，避免整条大列表都在一块连续内存里
ziplist 负责节点内紧凑存储，减少普通链表一个元素一个节点的巨大指针开销

这样一来，相比纯双向链表：

内存占用更低
局部遍历更友好
头尾插入删除仍然比较方便

相比单个超大 ziplist：

不会因为一个元素改动就频繁移动整大块内存
单个节点可控，降低大对象操作代价

所以 `quicklist` 实际上是 Redis List 的一次工程化升级，核心目标是：**既要内存紧凑，又要避免大连续内存结构的修改代价过高**。

---

### listpack 是什么

`listpack` 可以看成是 **ziplist 的改进重构版**，也是一种 **连续内存的紧凑结构**，但它不是简单修补 ziplist，而是重新设计编码方式，重点解决 ziplist 的历史问题。

它的核心特点是：

结构更简单
entry 编码更清晰
避免 ziplist 那种复杂的前驱长度连锁更新问题
更利于维护，也更安全

简单说，`listpack` 仍然追求“紧凑存储”，但它不再沿用 ziplist 那套容易引发连锁更新和实现复杂度高的方案，而是换了一套更干净的设计。

后来 Redis 在一些数据结构的小对象编码上，逐步用 `listpack` 替代 `ziplist`，比如较新的 `Hash`、`ZSet` 等小数据场景。

---

### 为什么底层实现会演进

核心原因就一句话：**Redis 一直在做“内存占用、访问性能、修改代价、实现复杂度”之间的工程平衡**。

先看 ziplist。它最早解决的是“节省内存”的问题，因为普通链表、哈希结构、跳表这些通用结构指针开销太大，小数据场景不划算。所以 ziplist 很适合早期需求。

但随着 Redis 使用场景越来越复杂，ziplist 的问题变得更突出，尤其是：

中间插入删除代价高
大对象修改开销明显
连锁更新风险存在
代码维护复杂

于是 List 类型先演进到了 quicklist。因为 List 天然是高频头尾操作、大量元素场景，仅靠单个 ziplist 已经不合适，必须做“分段”。

再往后，Redis 发现 ziplist 本身这套格式设计就有历史包袱，于是推出 listpack，逐步替代 ziplist 作为新的紧凑存储基础。也就是说：

**quicklist 主要解决的是 List 的大规模存储和操作问题**
**listpack 主要解决的是 ziplist 自身格式设计的问题**

这两个演进方向不冲突，甚至是叠加关系。

---

### 三者的关系怎么理解

可以这样记：

`ziplist`：老的紧凑连续内存结构
`quicklist`：List 的组织方式，链表节点内部用紧凑结构存数据
`listpack`：新的紧凑连续内存结构，用来替代 ziplist

所以它们不是完全同一层面的概念。
`ziplist` 和 `listpack` 更像是“节点内部的紧凑编码格式”；
`quicklist` 更像是“List 整体的组织结构”。

---

### 标准结论

`ziplist` 是 Redis 早期的紧凑列表结构，节省内存但存在连锁更新、插入删除代价高、实现复杂等问题。
`quicklist` 是 Redis List 的改进实现，本质是 **双向链表 + 紧凑存储块**，解决大列表场景下纯 ziplist 或纯链表都不够理想的问题。
`listpack` 是新一代紧凑存储结构，用来替代 ziplist，目标是 **更简单、更安全、更易维护，并规避 ziplist 的设计缺陷**。

底层演进的根本原因是：**Redis 在不断优化“小数据省内存”和“大数据可修改性、可维护性”之间的平衡。**

## 7. Stream 是什么？和 List 做消息队列相比有什么差别？

`Stream` 是 Redis 提供的 **面向消息队列场景的数据结构**，可以把它理解成一个 **支持消息持久保存、按 ID 有序追加、支持消费组消费的日志流**。它不是简单的先进先出队列，而更接近一个轻量级的 `MQ / Log Broker` 模型。每条消息都会有一个全局唯一的消息 ID，消息内容是一个或多个 `field-value` 键值对，生产者通过 `XADD` 追加消息，消费者通过 `XREAD` 或 `XREADGROUP` 消费消息。

如果拿 `List` 来做消息队列，本质上通常是 `LPUSH/RPOP` 或 `RPUSH/LPOP` 这种模型，它更像一个最原始的 FIFO 队列。能用，但能力比较弱，尤其一到“消费者组、消息确认、失败重投、积压管理”这些真正的 MQ 需求时，List 就明显不够用了。

两者最核心的差别在于：**List 是队列模型，取走就没了；Stream 是日志流模型，消息会保留，并且支持多消费者协作消费。**

先说 List。用 List 做队列时，消息被消费者弹出后，Redis 里就没有这条消息了。如果消费者拿到消息后业务处理失败，或者还没处理完就宕机，这条消息很可能已经丢了。虽然可以通过 `BRPOPLPUSH` 之类方式做一个“处理中队列”来缓解，但你要自己维护确认、超时重投、死信、幂等等整套机制，工程成本很高，且容易出 bug。

再说 Stream。Stream 天生支持这些消息队列核心能力：

第一，**消息有唯一 ID 且按时间有序**。不像 List 只是一个值，Stream 的每条消息是结构化的，便于扩展字段。

第二，**消息不会因为被读取就立刻删除**。消费是“读”，不是“弹出删除”，所以可以支持消息回溯、重复读取、多个消费者独立消费。

第三，**支持 Consumer Group**。同一个消费组里的多个消费者可以协同消费一条流里的消息，Redis 会把不同消息分配给不同消费者，这才真正接近 MQ 的消费组模型。

第四，**支持 ACK 机制**。消费者读到消息后，需要 `XACK` 确认，没确认的消息会进入 PEL（Pending Entries List，待确认列表）。这样就能知道哪些消息“已投递但未确认”，便于失败恢复和重试。

第五，**支持消息重分配**。某个消费者宕机后，其他消费者可以通过 `XCLAIM` / `XAUTOCLAIM` 抢回长时间未确认的消息，避免消息永久卡死。

所以如果问题是“Redis 里哪个更适合做消息队列”，标准答案是：**简单临时队列可以用 List，稍微像样一点的消息队列需求优先用 Stream。**

再具体对比一下：

从**消息语义**看，List 更像“管道”，Stream 更像“消息日志”。
从**消费模式**看，List 更适合单消费者或非常简单的抢占式消费；Stream 支持消费组和多消费者协作。
从**可靠性**看，List 默认没有确认机制，Stream 有 Pending + ACK 机制。
从**消息追溯**看，List 弹出后消息消失；Stream 天然可保留历史消息。
从**运维管理**看，List 需要你自己补齐很多机制；Stream 内建的 MQ 能力更多。
从**复杂度**看，List 简单，性能直观；Stream 功能更强，但学习和维护成本更高。

但要注意，**Stream 也不是专业 MQ 的完全替代品**。它适合轻量级消息队列、异步解耦、站内任务流转、低到中等规模业务队列。如果你的场景需要特别强的吞吐、海量堆积、跨机房容灾、复杂路由、严格顺序分区、长期消息存储，还是更适合 Kafka、RocketMQ、RabbitMQ 这类专业中间件。Redis Stream 更适合作为“够用且轻量”的方案，而不是无限拔高使用边界。

小结一下：`List` 做消息队列，优点是简单，但缺少 ACK、消费组、重投、消息追溯等能力；`Stream` 是 Redis 专门为消息流场景设计的数据结构，支持消息 ID、消费组、待确认队列和失败恢复，更接近真正可用的消息队列实现。

## 8. Redis 中 big key 和 hot key 分别是什么？为什么危险？

### Redis 中 big key 和 hot key 是什么？为什么危险？

`big key` 指的是 **单个 key 对应的 value 特别大**，这里的大可以是两种含义：一种是 **字符串 value 很大**，比如一个 key 存了几 MB 甚至几十 MB 的 JSON；另一种是 **集合类型成员很多**，比如一个 `hash/set/zset/list` 里塞了几十万、几百万个元素。它的本质不是“key 名字大”，而是 **这个 key 持有的数据体量大**。

`hot key` 指的是 **访问频率特别高的 key**，在某个时间窗口内，大量请求都打到同一个 key 上。比如首页配置、爆款商品库存、热点活动详情、统一验证码计数、某个明星用户信息等。它的本质不是数据大，而是 **流量过度集中**。

这两类 key 危险的原因不一样，但都会直接影响 Redis 的稳定性。

对于 `big key`，最大风险是 **单次操作过重**。因为 Redis 是单线程处理命令，读取、删除、序列化、网络发送这些动作如果落在 big key 上，就可能让一次命令执行时间明显变长，导致其他请求排队，拉高整体延迟。比如读取一个超大字符串会占用网络带宽和序列化时间；删除一个包含几十万元素的 hash/list/set/zset，可能导致阻塞；做持久化时 big key 还会放大 fork 后的内存写时复制开销，增加内存压力，严重时甚至引发延迟抖动和 OOM 风险。

对于 `hot key`，最大风险是 **局部流量打爆单点**。Redis 虽然快，但如果大量请求都集中访问一个 key，那么这个 key 所在实例的 CPU、网络、连接数都会迅速上升。尤其在集群模式下，一个 key 只会落到一个分片槽位，热点流量无法天然均摊，最终可能出现单分片被打满，而其他分片很空闲的情况。结果就是整体看 QPS 不高，但某一个 Redis 节点已经到瓶颈，出现响应变慢、超时、甚至雪崩。

再往生产视角讲，`big key` 和 `hot key` 的危险通常体现在这几类事故里：

第一类是 **延迟尖刺**。big key 的大读取、大删除、大遍历，会让主线程卡顿；hot key 的高并发访问，会让单实例排队加剧，P99 明显升高。

第二类是 **资源倾斜**。big key 会吃掉更多内存、带宽和持久化资源；hot key 会把 CPU、网卡、中断、连接压力集中到一个节点。

第三类是 **放大故障影响面**。一个热点 key 一旦失效，可能瞬间把大量请求打到数据库，形成缓存击穿；一个 big key 一旦操作不当，比如 `DEL`、全量返回、频繁 rewrite，也可能引发连锁抖动。

第四类是 **集群不均衡**。特别是 hot key，在 Redis Cluster 里会造成“逻辑上分片了，实际上热点没分散”。这类问题很典型，也很隐蔽。

标准结论就是：

`big key` 是 **数据量过大的单个 key**，危险在于单次操作重、阻塞风险高、内存和网络开销大；
`hot key` 是 **访问量过高的单个 key**，危险在于请求集中、单节点被打满、容易引发延迟抖动和缓存击穿。

两者一个偏“体积问题”，一个偏“流量问题”，本质上都会破坏 Redis “小而快、均匀分布、短平快命令”的运行前提。

# 二、持久化与数据安全类

## 1. Redis 的 RDB 和 AOF 有什么区别？分别适合什么场景？

`RDB` 是 **某一时刻 Redis 内存数据的快照**，本质上是把当下数据整体写到一个二进制文件里；`AOF` 是 **追加记录写命令日志**，本质上是把导致数据变化的命令按顺序记录下来，重启时通过重放命令恢复数据。两者最大的区别，不在“都能持久化”，而在于：**RDB 保留的是结果快照，AOF 保留的是变更过程**。

先说 RDB。它的优点是文件紧凑、恢复速度快、适合做冷备和全量备份。因为它直接保存数据结果，不需要像 AOF 那样一条条重放命令，所以 Redis 重启加载时通常更快。对性能影响也相对可控，因为 RDB 常见做法是通过 `fork` 子进程生成快照，主进程继续处理请求。它很适合“更关注恢复效率、备份归档、可以接受少量数据丢失”的场景，比如缓存型 Redis、从库备份、灾备文件导出。

但 RDB 的问题也很明显：**可能丢失最后一次快照之后的数据**。比如你配置 5 分钟做一次快照，那么 Redis 宕机时，理论上最多可能丢 5 分钟数据。所以如果 Redis 承担的是比较重要的业务状态，仅靠 RDB，数据安全性通常不够。

再说 AOF。AOF 会把每次写操作追加到日志文件里，默认策略通常是每秒刷盘一次，也就是 `appendfsync everysec`。它的优点是：**数据丢失窗口更小，可读性更好，数据恢复更接近真实写入过程**。如果是每秒刷盘，机器故障时通常最多丢 1 秒左右数据，因此比 RDB 更适合“不能接受较多数据丢失”的场景，比如订单状态、任务状态、计数类业务、轻量级消息流转等。

但 AOF 也有代价。第一，AOF 文件通常比 RDB 更大，因为它记录的是写命令过程；第二，恢复时需要重放日志，通常比 RDB 加载慢；第三，随着写入增多，AOF 会膨胀，所以 Redis 需要做 `AOF rewrite`，把冗余命令压缩成更精简的恢复内容。也就是说，AOF 在数据安全上更强，但在文件体积、恢复速度、运行维护复杂度上通常不如 RDB 简单。

所以标准对比可以这样记：

RDB 是 **快照持久化**，优点是恢复快、文件小、适合备份，缺点是可能丢较多数据；
AOF 是 **写日志持久化**，优点是数据更安全、丢失更少，缺点是文件更大、恢复更慢、维护更复杂。

在生产里怎么选，通常看 Redis 承担什么角色。

如果 Redis 主要是 **纯缓存**，数据丢了可以从 DB 重建，那一般 RDB 就够了，甚至有些极端缓存场景可以关闭持久化。因为这类场景更关心性能和运维简单性，而不是绝对数据安全。

如果 Redis 承担的是 **半持久化业务数据**，比如排行榜、计数器、任务状态、用户会话、轻量消息队列等，通常更适合开启 AOF，至少用 `everysec`，因为这类数据不能接受丢太多。

如果 Redis 比较重要，生产上更常见的做法是 **RDB + AOF 同时开启**。这样既有 RDB 的快速恢复和备份能力，又有 AOF 的更高数据安全性。Redis 重启时通常优先使用 AOF 恢复，因为它的数据通常更新更完整。

结论就是：**RDB 偏备份和快速恢复，AOF 偏更高的数据安全；缓存场景优先考虑 RDB，业务状态场景优先考虑 AOF，核心生产环境通常两者同时开启。**

## 2. RDB 的优缺点是什么？为什么说它更适合冷备和全量恢复？

`RDB` 是 Redis 的 **快照持久化**，本质上是在某个时间点把内存中的数据整体生成一个二进制快照文件。它的核心优点是：**文件紧凑、恢复速度快、适合做全量数据备份**。

先说优点。

第一，**RDB 文件体积通常更小**。因为它保存的是某一时刻的数据结果，而不是像 AOF 那样记录大量写命令，所以压缩后更适合传输、归档和备份。

第二，**恢复速度快**。Redis 重启加载 RDB 时，是直接把快照中的数据整体恢复到内存，不需要逐条重放命令，所以全量恢复效率通常比 AOF 更高。这也是它特别适合“整库恢复”的关键原因。

第三，**适合做定时备份和灾备副本**。比如每小时、每天生成一个 RDB 文件，拷贝到其他机器、对象存储或者异地机房，都比较方便。对运维来说，这种文件化快照也更容易管理。

第四，**对运行期性能影响相对可控**。RDB 通常通过 `fork` 子进程执行持久化，主进程继续处理请求，正常情况下不会像同步落盘那样每次写都直接阻塞业务线程。

再说缺点。

第一，**数据安全性不如 AOF**。因为 RDB 记录的是“某一个时刻”的快照，如果 Redis 宕机，最后一次快照之后的数据就会丢失。所以它不适合对数据实时性要求高、不能接受较多数据丢失的场景。

第二，**fork 子进程有成本**。当数据量很大时，`fork` 本身会带来瞬时阻塞，而且持久化期间如果内存页大量修改，还会放大 `COW`（写时复制）开销，增加内存压力。

第三，**不适合高频小粒度恢复**。因为它保存的是整库快照，不像 AOF 那样接近“操作日志”，所以更适合整体验证、整体恢复，而不适合追求非常细粒度的数据回放。

之所以说它更适合 **冷备和全量恢复**，原因就在于它的形态是“完整快照”。

所谓冷备，就是把某个时间点的完整数据保存下来，用于归档、容灾、异地备份，这时候最重要的是：**文件小、易复制、易存储、易恢复**，RDB 正好符合这个特点。

所谓全量恢复，就是机器故障、实例重建、主从重搭、灾难恢复时，希望尽快把整库数据恢复出来。这时候最重要的是：**恢复路径简单、加载速度快**，而 RDB 是直接加载结果数据，不需要逐条执行命令，所以天然更适合全量恢复。

标准结论就是：

`RDB` 的优点是 **文件紧凑、恢复快、适合备份归档、适合整库恢复**；
缺点是 **可能丢失最后一次快照后的数据，且大实例下 fork / COW 有成本**。

因此它更适合 **冷备、灾备、定时全量备份、实例级恢复**，而不适合单独承担高可靠业务数据的实时持久化。

## 3. AOF 的 `always`、`everysec`、`no` 三种刷盘策略怎么选？

这三种策略的区别，本质上就是一句话：**在性能、数据安全、延迟抖动之间做取舍**。

`always` 表示 **每条写命令都立即 fsync 刷盘**。理论上数据最安全，Redis 宕机时几乎不会丢数据，因为命令刚写入 AOF 就同步到了磁盘。但它的代价也最大：每次写请求都要承担磁盘刷盘开销，吞吐会明显下降，延迟也更容易抖动。所以它只适合 **数据极其敏感、写量不高、可以接受性能下降** 的场景。比如非常关键的小规模状态数据，或者某些实验/审计型场景。大多数高并发生产业务，一般不会选它。

`everysec` 表示 **AOF 先写入系统缓冲区，每秒 fsync 一次**。这是生产里最常用、也是最推荐的折中方案。它的好处是：Redis 写请求不需要每次都等磁盘刷盘完成，性能比 `always` 好很多；同时即使机器异常宕机，通常最多只丢失 1 秒的数据。对于绝大多数业务，这个丢失窗口是可以接受的。所以如果你的 Redis 承担的是 **重要业务数据，但又不能牺牲太多性能**，通常就选 `everysec`。这也是标准答案里最常见的推荐。

`no` 表示 **Redis 不主动 fsync，由操作系统决定什么时候把缓冲区刷到磁盘**。它的性能最好，因为 Redis 基本不管刷盘这件事，但数据安全最差，宕机时可能丢失多少数据不可控，取决于 OS 刷盘时机。所以它一般只适合 **对数据可靠性要求很低、更加追求性能** 的场景，比如纯缓存型 Redis，或者本来就不依赖 Redis 做强持久化的数据。

怎么选，可以直接记这个结论：

如果你追求 **最高数据安全**，并且写入不大，选 `always`；
如果你追求 **性能和可靠性的平衡**，绝大多数生产环境选 `everysec`；
如果你追求 **最高性能，且能接受较多数据丢失**，选 `no`。

标准生产建议是：**绝大多数线上场景优先 `everysec`**。因为 `always` 太重，`no` 风险太大，只有 `everysec` 在性能、可靠性、延迟之间最均衡。

## 4. AOF 重写（rewrite）是干什么的？为什么需要它？

AOF rewrite 的作用是 **压缩 AOF 文件，把“很多条历史写命令”重写成“恢复当前数据所需的最少命令集合”**。它不是把旧 AOF 简单截断，也不是修改内存数据，而是基于 Redis 当前内存里的真实数据，重新生成一份更精简的新 AOF 文件。

为什么需要它？因为 AOF 采用的是 **追加写日志** 模式，随着时间增长，文件会不断膨胀。比如一个 key 被 `SET` 了 100 次，AOF 里可能真有 100 条修改记录，但恢复时其实只需要最后那次结果。再比如一个 list 不断 `LPUSH`、`LPOP`，中间大量历史操作对“最终状态”已经没有意义了。如果不做 rewrite，AOF 会越来越大，带来两个问题：**磁盘占用越来越高，重启恢复越来越慢**。

AOF rewrite 的核心思想就是：**不要保留无意义的历史过程，只保留恢复当前状态所需的命令**。例如：

一个字符串 key，最终值是 `k=v`，那重写后可能只需要一条 `SET k v`
一个 hash、list、set、zset，则生成对应的批量写入命令，把当前数据状态重新表达出来

这样生成的新 AOF 文件通常会比旧文件小很多。

它为什么叫“重写”而不是“压缩”？因为它不是对原文件做字节级压缩，而是 **按当前数据状态重新构造一份新的逻辑日志**。

再补一句关键点：AOF rewrite 期间 Redis 仍然可以处理新请求。通常是后台子进程根据当前内存快照生成新的 AOF，同时主进程把 rewrite 期间新增的写命令写到 AOF 缓冲区，最后再追加到新文件里，保证新 AOF 既包含重写时的全量状态，也不会丢失重写期间的新写入。

标准结论就是：

AOF rewrite 是 **为了给 AOF“瘦身”**，把冗余历史命令压缩成恢复当前数据所需的最小命令集合。
它的价值主要有两个：**减少 AOF 文件体积**，以及 **加快 Redis 重启时的恢复速度**。

## 5. BGREWRITEAOF 和 BGSAVE 的过程分别是怎样的？

两者都是 Redis 的 **后台子进程持久化机制**，共同点是都会先 `fork` 出一个子进程去干重活，避免主线程长期阻塞；区别在于：**BGSAVE 是生成 RDB 快照，BGREWRITEAOF 是重写 AOF 文件**，目标完全不同。

先说 `BGSAVE`。它的过程比较直接：

第一步，Redis 主进程执行 `fork`，创建一个后台子进程。
第二步，子进程基于 `fork` 时刻的内存数据快照，把当前全量数据写入临时 RDB 文件。
第三步，在子进程写 RDB 期间，主进程继续处理客户端请求。此时如果主进程修改了内存数据，会触发 `COW`（写时复制），也就是被修改的内存页复制一份，保证子进程看到的仍然是 fork 那一刻的数据视图。
第四步，子进程写完临时 RDB 文件后，用原子方式 `rename` 替换旧的 RDB 文件。这样可以保证要么旧文件在，要么新文件完整生效，不会出现半写状态。
第五步，后台保存完成。

所以 `BGSAVE` 的本质是：**子进程把某一时刻的内存全量快照落成 RDB 文件**。

再说 `BGREWRITEAOF`。它会更复杂一点，因为它不仅要重写 AOF，还要保证 rewrite 期间的新写命令不丢。

它的大致过程是：

第一步，主进程执行 `fork`，创建后台重写子进程。
第二步，子进程基于 fork 时刻的内存数据，不去读取旧 AOF 做“压缩”，而是直接根据当前内存中的真实数据状态，重新生成一份新的 AOF 临时文件。也就是说，它输出的是“恢复当前数据最少所需命令集合”。
第三步，在子进程重写期间，主进程仍然继续处理新的写请求。这些写请求一方面会继续追加到现有 AOF 文件，保证线上 AOF 正常工作；另一方面也会写入 **AOF rewrite buffer**，专门记录 rewrite 期间新增的写命令。
第四步，子进程把新的 AOF 临时文件写完后，主进程会把 rewrite buffer 中这段“增量写命令”再追加到新 AOF 临时文件末尾，确保新文件既包含 fork 时刻的全量状态，也包含 rewrite 期间的新变更。
第五步，最后再用原子 `rename` 把新的 AOF 文件替换旧的 AOF 文件，完成切换。

所以 `BGREWRITEAOF` 的本质是：**子进程根据当前内存重建一份更精简的新 AOF，同时主进程额外缓存重写期间的增量命令，最后合并进去**。

两者再总结一下区别：

`BGSAVE` 是把当前内存直接做成 **RDB 快照文件**，重点是“全量快照”；
`BGREWRITEAOF` 是根据当前内存生成 **新的精简 AOF 文件**，重点是“日志瘦身”；
两者都会 `fork`，都依赖 `COW`，都会让主进程继续对外服务；
但 `BGREWRITEAOF` 比 `BGSAVE` 多了一层 **rewrite buffer 增量合并**，因为它必须保证重写期间的新写命令也进入新 AOF。

## 6. Redis 持久化为什么通常用 fork？fork 带来什么代价？

Redis 持久化通常用 `fork`，核心原因是：**既要拿到某一时刻的内存快照，又不能长时间阻塞主线程处理请求**。`fork` 之后，子进程会复制父进程的地址空间页表，初始阶段父子进程共享同一份物理内存，子进程就可以基于这个时间点的数据视图去做 `BGSAVE` 或 `BGREWRITEAOF`，而主进程继续对外提供读写服务。这就实现了“后台持久化”。

之所以不用主线程自己去落盘，是因为无论生成 RDB，还是重写 AOF，都是重 CPU、重 IO、重内存扫描的操作。如果由主线程直接做，Redis 在这段时间里几乎就不能正常处理请求，延迟会非常高。用了 `fork` 以后，主线程只承担一次创建子进程的成本，真正的持久化工作交给子进程完成，这是 Redis 在单线程模型下非常关键的工程设计。

`fork` 的关键基础是 **写时复制（COW）**。也就是说，`fork` 完成后，父子进程先共享内存页；如果主进程后续有写操作，才会把对应内存页复制一份。这样子进程看到的始终是 `fork` 那一刻的旧数据，保证快照一致性。

但 `fork` 不是没有代价，主要有三类。

第一，**fork 本身会有阻塞开销**。虽然不是把整个内存真的拷贝一遍，但要复制页表。实例内存越大，页表越大，`fork` 时间越长。大实例下，这个瞬时阻塞可能很明显，直接拉高请求延迟。

第二，**会带来 COW 内存放大**。持久化期间如果主进程持续修改很多数据，被修改过的内存页都要复制，导致实际内存占用上升。所以 Redis 做持久化时，机器不能只按“数据本身大小”来配内存，还要预留 fork/COW 余量，否则容易触发内存压力，严重时可能 OOM。

第三，**会增加 CPU 和 IO 压力**。子进程要扫描内存、写磁盘文件，主进程还在继续处理请求，这相当于一台机器上同时跑两套重活。数据量大、写入频繁时，磁盘带宽、CPU、内存带宽都会受到影响，容易出现延迟抖动。

标准结论就是：Redis 持久化使用 `fork`，是为了让 **子进程在不阻塞主线程的前提下，基于某一时刻的一致性内存视图完成后台持久化**；它的代价主要是 **fork 瞬时阻塞、COW 导致额外内存消耗，以及持久化期间的 CPU/磁盘压力上升**。

## 7. 什么是写时复制（Copy-On-Write）？它会带来哪些线上风险？

写时复制（`Copy-On-Write，COW`）是指：**父子进程在 fork 之后，并不会立刻把内存真正复制两份，而是先共享同一份物理内存页；只有当其中一方对某个内存页发生写入时，操作系统才会复制这个页，改为各自持有。**

在 Redis 里，`BGSAVE` 和 `BGREWRITEAOF` 都依赖这个机制。主进程 `fork` 出子进程后，子进程拿到的是 fork 那一刻的内存视图，用来生成 RDB 或重写 AOF。此时父子进程最开始共享同一批内存页。后续如果主进程继续处理写请求，修改了某些 key，对应的内存页就会触发 COW：系统复制这一页，主进程写新页，子进程仍然读旧页。这样就保证了子进程看到的数据始终是 fork 时刻的一致性快照。

它的好处是明显的：**不用在 fork 时把整个 Redis 内存立即完整复制一遍**，否则代价太大；但它也不是“没有复制”，而是把复制成本延后到真正发生写入的时候。

线上风险主要有这几类。

第一，**内存瞬间膨胀**。这是最典型的风险。假设 Redis 当前用了 20GB 内存，fork 之后如果主进程在持久化期间持续高频写入，大量内存页都会被复制，实际内存占用可能明显上涨。如果机器可用内存余量不够，就可能触发内存淘汰、swap，严重时甚至 OOM，被系统杀进程。

第二，**延迟抖动**。COW 发生时，需要复制内存页，这本身就有 CPU 和内存带宽开销。如果线上写流量大、修改范围广，主线程处理写命令时会额外承担页复制成本，容易出现 RT 上升，P99/P999 抖动明显。

第三，**fork + COW 叠加放大问题**。大实例本来 fork 就慢，如果 fork 完之后又赶上业务高峰，持续触发大量 COW，整个 Redis 实例的 CPU、内存、IO 压力都会上升，容易形成“持久化窗口期抖动”。

第四，**AOF rewrite / RDB 期间更容易暴露问题**。因为这两个后台任务往往持续时间不短，数据量越大，窗口越长，主进程在这段时间里越可能改动更多页，COW 累积开销就越明显。

第五，**热点大对象风险更高**。如果业务里存在 big key、大 hash、大 list，修改这类对象更容易触发较重的页复制开销。虽然复制是按页而不是按 key，但大对象更容易跨多个页，写入时对 COW 更不友好。

标准答案可以概括为：

写时复制就是 **fork 后父子进程先共享内存页，只有发生写操作时才复制对应页**。
Redis 借助它实现后台持久化时的数据快照隔离。
它带来的线上风险主要是 **内存膨胀、请求延迟抖动、CPU/内存带宽压力上升，以及在大实例和高写入场景下可能引发 OOM 或性能雪崩**。

## 8. Redis 宕机后，RDB/AOF 恢复流程大致是什么？

Redis 宕机重启后，会先检查持久化配置和本地持久化文件，然后决定 **用哪种方式恢复数据**。标准结论是：**如果同时开启了 AOF 和 RDB，通常优先使用 AOF 恢复；如果没有 AOF，再使用 RDB 恢复。**

大致流程可以分成几步来看。

第一步，Redis 启动时先读取配置，判断是否开启了 AOF。如果开启了 AOF，并且 AOF 文件存在，Redis 会优先加载 AOF。因为 AOF 记录的是更接近最新状态的写命令，通常比 RDB 快照更新，数据更完整。

第二步，如果走 AOF 恢复，Redis 会读取 AOF 文件中的命令日志，然后按顺序重新执行这些写命令，把内存数据恢复出来。本质上就是“**重放日志恢复状态**”。如果 AOF 文件经过 rewrite，那么前半部分可能是重写后的精简命令，后半部分是增量追加命令，Redis 一样会顺序执行，最终恢复到宕机前尽可能新的状态。

第三步，如果没有开启 AOF，或者 AOF 文件不存在，那么 Redis 就会走 RDB 恢复。此时 Redis 直接加载 RDB 快照文件，把其中保存的 key/value 数据一次性恢复到内存。本质上就是“**加载某个时间点的全量快照**”。

第四步，如果 AOF 和 RDB 都没有，或者对应文件不可用，那 Redis 就只能以空库启动。

再补一个很关键的点：**AOF 恢复和 RDB 恢复的差别，本质上是“重放过程”和“直接装载结果”的差别。**
AOF 是按命令恢复，所以通常数据更新更完整，但恢复速度一般更慢；
RDB 是直接装载快照结果，所以恢复更快，但可能丢失最后一次快照之后的数据。

如果 AOF 文件异常，比如宕机时文件尾部还没写完整，Redis 在启动时会检查 AOF 文件完整性。对于不完整或损坏的 AOF，通常需要先修复，再启动恢复；而 RDB 如果损坏，则可能导致加载失败，最终无法用该快照恢复。

标准总结就是：

Redis 重启恢复时，**优先 AOF，其次 RDB**。
AOF 恢复是 **顺序重放写命令日志**；
RDB 恢复是 **直接加载全量快照文件**。
AOF 更完整但通常更慢，RDB 更快但数据可能更旧。

## 9. AOF 文件损坏了怎么办？

标准处理思路是：**先停止直接启动 Redis，先校验 AOF，再修复，修复不了就降级用 RDB 或空库恢复。**

Redis 如果发现 AOF 文件尾部不完整、格式异常，启动时通常会报错并拒绝加载，因为它无法保证继续重放不会把数据恢复错。这时候不能直接硬拉起，而是应该按下面的顺序处理。

第一步，**先备份原始 AOF 文件**。这一点很重要。无论后面是修复、截断还是放弃，原文件都要先保留一份，避免误操作导致彻底不可恢复。生产上一般先复制一份到安全目录，再对副本动手。

第二步，**判断损坏类型**。最常见的是两类：一种是 Redis 异常宕机导致 **AOF 末尾半条命令不完整**；另一种是磁盘损坏、文件篡改、内容严重错乱导致 **中间内容损坏**。如果只是尾部不完整，通常比较好修；如果中间已经坏了，恢复代价会更大，丢数也可能更多。

第三步，**使用 `redis-check-aof` 修复**。这是 Redis 官方提供的 AOF 检查修复工具。它的典型做法是扫描 AOF 文件，定位出最后一个完整命令的位置，然后把损坏尾部截断掉。这样 Redis 至少可以重新加载一份“到最后一个完整命令为止”的 AOF。代价是：**损坏点之后的那一小段数据会丢失**。

第四步，**修复后再重启 Redis 验证恢复结果**。重启成功不代表万事大吉，还要看关键业务数据是否完整，比如订单状态、任务状态、缓存预热标记、消费位点这些敏感数据是否缺失。如果 Redis 承担的是业务状态，而不是纯缓存，这一步必须做校验。

如果 AOF 已经坏得比较严重，或者修复后丢失数据不可接受，那就进入第五步：**尝试用 RDB 恢复**。如果你同时开启了 RDB，那么可以暂时关闭 AOF 加载，优先用最近一次 RDB 快照把实例拉起来。这样虽然可能回退到更早的数据点，但通常比完全起不来更好。恢复后再结合业务做补偿、对账、重建。

如果既没有可用 AOF，也没有可用 RDB，那就只能 **空库启动**。这在纯缓存场景还可以接受，回源重建即可；但如果 Redis 承担了业务状态，就需要走补偿、重放、对账甚至人工兜底。

再补一个面试里常答的点：**为什么 AOF 会坏？** 常见原因包括 Redis 异常退出、机器掉电、磁盘问题、文件系统异常、AOF rewrite 期间异常中断等。尤其是开启 `appendfsync everysec` 时，理论上最多丢 1 秒数据，但如果恰好文件尾部刷盘不完整，就可能出现“最后一段命令损坏”。

标准结论可以这样说：

AOF 文件损坏时，处理顺序是 **先备份原文件，再用 `redis-check-aof` 检查并修复，修复后重新启动验证；如果 AOF 无法用，则回退到 RDB 恢复；再不行就空库启动并做业务补偿**。
本质上这是一个 **可用性优先 + 数据损失最小化** 的恢复过程。

## 10. 为什么生产上经常说 Redis 不能只依赖持久化保证绝对不丢数据？

因为 Redis 的持久化机制，本质上只能做到 **“尽量少丢”**，很难做到传统关系型数据库那种 **强一致、零丢失承诺**。无论是 RDB 还是 AOF，都存在天然边界，所以生产上不能把“数据绝对不丢”这件事只押在 Redis 持久化上。

先看 `RDB`。它是定时快照，快照和宕机之间天然存在时间窗口。只要机器在下一次快照前挂掉，这段时间内的数据就会丢。所以 RDB 从设计上就不是“零丢失方案”。

再看 `AOF`。虽然它比 RDB 更强，但也不是绝对安全。比如最常用的 `appendfsync everysec`，本身就意味着最多可能丢 1 秒数据；即使是 `always`，也只是尽量把命令同步刷盘，仍然无法覆盖所有极端情况，比如磁盘故障、文件系统异常、OS 崩溃、主从切换时复制未完成等问题。也就是说，AOF 能显著降低丢失概率，但不能从系统层面绝对消灭丢失。

再往生产里看，Redis 还有几个更现实的风险点。

第一，**主从复制本身是异步的**。如果主节点刚写入一批数据，还没来得及同步到从节点，主节点就挂了，然后发生故障转移，新主上就可能缺这部分数据。这不是持久化文件能单独解决的问题。

第二，**持久化文件也可能损坏或回退**。比如 AOF 尾部损坏、RDB 文件不完整、磁盘故障、误删文件、机器回滚，这些都会导致恢复出来的数据不是“最新且完整”的。

第三，**持久化与故障切换之间存在竞态**。你以为数据已经写进 Redis 了，但它可能还没真正刷到磁盘，或者还没复制到足够多副本，或者主节点已写成功但故障切换选出的新主并不包含这次写入。

第四，**Redis 的定位本来就不是强事务持久化数据库**。它优先追求的是高性能、低延迟、内存访问速度，而不是像 MySQL / PostgreSQL 那样围绕 WAL、提交日志、崩溃恢复、事务一致性去设计“绝对可靠持久化”。

所以生产上更靠谱的观点是：

Redis 持久化只能作为 **降低数据丢失概率的手段**，不能作为 **绝对不丢数据的最终保障**。
真正重要的数据，通常还要配合：

**主从复制 / 哨兵 / 集群高可用**，降低单点故障影响
**业务落库**，把关键状态写入 MySQL 等持久化数据库
**幂等、补偿、对账、重放机制**，在异常时修正数据
**多副本确认或降级策略**，提高关键写入成功的可信度

标准结论就是：**Redis 持久化解决的是“尽量恢复”和“少丢数据”，不是“绝对零丢失”**。只要生产系统对数据正确性要求高，就不能把最终可靠性只建立在 Redis 持久化之上。

# 三、高可用与集群类

## 1. Redis 主从复制的流程是什么？全量复制和增量复制分别发生在什么时候？

标准答案：

Redis 主从复制的核心流程可以概括为：**建立连接 → 身份确认/协商 → 数据同步 → 命令传播**。

从库启动后会主动连接主库，发送 `PSYNC` 命令请求同步。主库根据当前复制状态判断是执行**全量复制**还是**增量复制**。同步完成后，主库后续收到的写命令会持续异步发送给从库，从而保持主从数据尽量一致。

主从复制整体流程通常分为这几步：

第一步是**建立 socket 连接**。从库配置了主库地址后，会与主库建立网络连接。

第二步是**复制协商**。从库会向主库发送 `PSYNC`，并携带自己保存的 `runId` 和复制偏移量 `offset`。主库根据这些信息判断能不能继续以前的复制进度。

第三步是**数据同步**。如果不能继续旧进度，就走全量复制；如果能接上断点，就走增量复制。

第四步是**命令传播**。同步完成后，主库执行的写命令会持续复制给从库，从库重放这些命令，保持数据更新。

---

**全量复制发生的时机**主要有这些：

一是**从库第一次连接主库**时，因为没有历史复制进度，必然触发全量复制。

二是**从库保存的主库 runId 不匹配**，比如主库重启了、发生了主从切换，说明已经不是原来的主库了，这时无法基于旧 offset 继续复制，只能全量复制。

三是**从库请求的 offset 太旧，主库 backlog 中已经找不到这段增量数据**。因为主库只会保留一段有限长度的复制积压缓冲区，如果断线时间过长、写入量过大，缺失的数据被覆盖了，也只能重新全量复制。

全量复制的过程是：主库执行 `BGSAVE` 生成 RDB 快照，把 RDB 文件发送给从库；同时主库会把生成快照期间的新写命令暂存在缓冲区；从库加载 RDB 完成后，再继续接收并执行这部分缓存命令，最后进入正常命令传播阶段。

---

**增量复制发生的时机**主要是：

当从库曾经和主库同步过，只是**短暂断线后重新连接**，并且它提交的 `runId` 仍然是当前主库，且请求的 `offset` 之后的数据还保存在主库的 `repl_backlog_buffer` 中，这时主库就可以只把缺失的那部分命令发给从库，这就是增量复制。

增量复制的好处是明显的：**不需要重新生成和传输整个 RDB**，开销更小，恢复更快，对主库压力也更小。

---

小结：

Redis 主从复制本质上是从库通过 `PSYNC` 向主库申请同步，主库根据 `runId + offset` 判断是走全量还是增量。

**全量复制**一般发生在第一次同步、主库变更、积压缓冲区数据丢失时。
**增量复制**一般发生在短暂网络闪断后恢复连接，且 backlog 中还能找到缺失数据时。

面试里一句话总结就是：**第一次通常全量，断线重连优先增量，接不上断点才退化为全量。**

## 2. `psync` 是怎么工作的？为什么 2.8 之后复制能力更强了？

标准答案：

`PSYNC` 是 Redis 用来支持**断点续传复制**的命令，它解决了早期主从复制里“只要断线就容易全量重同步”的问题。

在 Redis 2.8 之前，复制主要使用 `SYNC`。`SYNC` 的问题是比较粗暴：一旦从库和主库连接断开后重新连上，通常就只能重新做一次**全量复制**，也就是主库重新生成 RDB、传输给从库、从库再重新加载。这样在网络抖动频繁或者实例较大时，代价非常高。

Redis 2.8 之后引入了 `PSYNC`，核心就是靠两个关键数据实现**部分重同步**：

第一个是 **master runid**。它可以理解为主库实例的身份标识。主库启动后会生成自己的 runid，从库会记住当前正在复制的主库是谁。

第二个是 **复制偏移量 offset**。主从双方都会维护复制流的偏移量。主库每发送一段复制数据，offset 就往前推进；从库每接收并处理一段数据，也记录自己处理到哪里了。

这样，从库断线重连时，就会发送类似下面的请求：

`PSYNC <runid> <offset>`

意思是：**我之前跟的是这个主库，我已经同步到这个偏移量了，后面的数据请继续发给我。**

主库收到后会判断：

如果从库带过来的 `runid` 和自己一致，说明还是原来那个主库；同时从库请求的 offset 之后那段数据，主库的 **repl_backlog_buffer** 里还保留着，那么主库就回复继续复制，直接把缺失的那部分增量数据发给从库，这就是**部分重同步 / 增量复制**。

如果 `runid` 不一致，说明主库已经变了，比如主库重启了或者发生了故障切换；或者虽然 `runid` 一致，但从库缺失的数据太久远，主库 backlog 里已经覆盖掉了，那就无法断点续传，只能退回到**全量复制**。

所以 `PSYNC` 的工作原理可以一句话概括为：

**从库带着“主库身份 + 已复制位置”来请求续传，主库如果还能找到断点后的数据，就只补发缺失部分；否则重新全量同步。**

Redis 2.8 之后复制能力更强，主要强在这几点：

第一，**支持部分重同步**。这是最核心的提升。网络短暂抖动、从库短暂重连时，不需要频繁全量复制，恢复速度快很多。

第二，**引入了复制积压缓冲区 `repl_backlog_buffer`**。主库会把最近一段时间的复制命令存在 backlog 里，这样从库断线后只要别断太久，就能从这个缓冲区补数据，而不是全量重来。

第三，**主从复制状态更可追踪**。有了 runid 和 offset，主从双方都清楚“复制到哪里了”，复制不再是黑盒式的全量覆盖，而是可续传、可判断的流式同步。

第四，**大幅降低主库压力**。因为全量复制会触发 `BGSAVE`、RDB 传输、从库全量加载，这对 CPU、内存、磁盘 IO、网络带宽都有压力。2.8 之后大量短时断线场景可以走增量复制，生产上稳定性明显更好。

面试里可以直接总结为：

`**SYNC` 时代，断线后往往只能全量复制；`PSYNC` 时代，借助 runid、offset 和 backlog，可以优先做部分重同步，所以 Redis 2.8 之后主从复制的容错性、恢复速度和整体性能都更强。**

再补一句常见追问点：

`PSYNC` 不是保证“一定增量复制”，而是**优先尝试增量复制**；如果 runid 对不上，或者 backlog 不够，就仍然会退化成全量复制。

## 3. replication backlog 是什么？它解决了什么问题？

标准答案：

**replication backlog** 就是 Redis 主库维护的一块**复制积压缓冲区**，本质上是一个**固定长度的环形缓冲区**。主库会把最近传播给从库的复制命令写到这块缓冲区里，用来支持从库断线后的**增量复制**。

它解决的核心问题是：

**从库短暂断线重连时，不需要直接全量复制，而是可以从 backlog 中把缺失的数据补回来。**

在没有 backlog 或者早期 `SYNC` 机制下，只要从库和主库断开后重新连接，往往就只能重新做一次全量复制。全量复制成本很高，因为主库要 `BGSAVE` 生成 RDB，传输整个快照给从库，从库再加载数据，整个过程对 CPU、磁盘 IO、网络带宽都会有明显压力。

有了 replication backlog 之后，主库会把最近一段时间发给从库的写命令保存在 backlog 中，并且维护复制偏移量 `offset`。从库重连时会通过 `PSYNC` 把自己上次同步到的位置告诉主库。主库如果发现这个 offset 之后的数据仍然在 backlog 里，就可以直接把缺失的那一段发给从库，这样就完成了**部分重同步**，也就是增量复制。

所以它主要解决了两个问题：

第一，解决了**网络短暂抖动就触发全量复制**的问题。以前链路只要闪断，恢复代价很大；现在只要 backlog 还保留着缺失数据，就能续传。

第二，解决了**主从复制恢复成本过高**的问题。通过增量补数据，减少 `BGSAVE`、RDB 传输和从库全量加载的次数，降低主库压力，提高复制恢复速度和系统稳定性。

面试里可以这样一句话回答：

**replication backlog 是主库用于保存最近复制数据的环形缓冲区，它配合 `PSYNC` 和复制 offset，让从库断线重连后可以优先做增量复制，而不是频繁全量复制。**

## 4. Redis 哨兵（Sentinel）是怎么做故障发现和主从切换的？

标准答案：

Redis Sentinel 主要负责三件事：**监控、通知、自动故障转移**。它通过持续检查主库和从库是否正常工作，在主库故障时完成**故障发现、故障确认、选举领导者、主从切换、通知其他节点更新主库信息**这一整套流程。

故障发现的第一步是 **主观下线**。每个 Sentinel 都会定期向主库、从库以及其他 Sentinel 发送 `PING`。如果某个 Sentinel 在配置的 `down-after-milliseconds` 时间内一直没有收到主库有效回复，它就会认为这个主库已经不可用，这叫 **主观下线**，也就是 SDOWN。注意这时只是“我自己认为它挂了”，还不能直接发起切换。

第二步是 **客观下线**。当一个 Sentinel 认为主库主观下线后，它会向其他 Sentinel 询问这个主库的状态。如果达到配置的 `quorum` 数量，都认为这个主库有问题，那么这个主库就会被判定为 **客观下线**，也就是 ODOWN。到了这一步，说明不是单个 Sentinel 误判，而是多数 Sentinel 基本达成一致，故障才算真正被确认。

故障确认之后，会进入 **领导者选举**。因为可能有多个 Sentinel 同时发现主库客观下线，但真正执行故障转移的只能有一个，否则会乱。于是各个 Sentinel 会基于 Raft 风格的投票机制，在一个纪元内选出一个领导 Sentinel。拿到多数票的 Sentinel 才有资格执行后续的 failover。

选出领导者后，就进入 **主从切换**。领导 Sentinel 会先从现有从库里选一个最合适的新主库。选择标准通常包括：优先选择和旧主库数据最接近的从库，也就是复制 offset 更大的；其次看 `slave-priority`，优先级越小越优先；如果这些都一样，再比较复制 ID、运行状态等，最后一般会看从库节点 ID 作为兜底排序。核心原则就是：**尽量选数据最新、状态最好、优先级最高的从库提升为新主库。**

选定之后，Sentinel 会向这个从库发送 `SLAVEOF NO ONE`，让它解除复制关系，正式升级为新的主库。然后再把其他从库重新指向这个新主库，也就是给它们发送新的 `SLAVEOF <newMasterHost> <newMasterPort>`。这样整个主从拓扑就重新建立起来了。

最后一步是 **配置传播和客户端感知**。Sentinel 会更新自己维护的主库地址信息，并通过发布订阅、通知脚本等方式对外通知主库已经切换。客户端如果是通过 Sentinel 获取主库地址，那么下一次获取主节点地址时就会连到新主库。

面试里可以总结成一条主线：

**Sentinel 先通过 PING 做健康检查，先判定主观下线，再通过多个 Sentinel 协商形成客观下线；随后通过投票选出领导 Sentinel，由它挑选一个最合适的从库升级为新主库，再让其他从库复制新主库，最终完成主从切换。**

补一句常见追问点：

Sentinel 能提升 Redis 的高可用，但它解决的是**故障发现和自动切换**问题，不解决强一致问题。故障切换过程中仍然可能出现少量数据丢失，比如主库刚写入但还没来得及复制到从库就宕机了。

## 5. 哨兵为什么要有 quorum 和 leader 选举？

标准答案：

哨兵之所以需要 **quorum**，是为了避免**单个 Sentinel 误判主库故障**；之所以需要 **leader 选举**，是为了避免**多个 Sentinel 同时执行故障转移**。

先说 **quorum**。

Sentinel 会定期通过 `PING` 检查主库状态，但网络抖动、短暂阻塞、机器负载过高，都可能导致某一个 Sentinel 暂时连不上主库。如果只要一个 Sentinel 认为主库挂了就立刻切换，那么很容易发生误切换。

所以 Redis 设计了两层判断：

第一层是**主观下线**，某个 Sentinel 自己觉得主库挂了。
第二层是**客观下线**，需要有足够多的 Sentinel 也认为主库挂了。

这里的 **quorum** 就是“至少需要多少个 Sentinel 认同主库故障，才能把主观下线升级为客观下线”的门槛。

它解决的是：**降低误判概率，避免因为单点观察错误导致错误故障转移。**

再说 **leader 选举**。

即使多个 Sentinel 都已经通过 quorum 确认主库客观下线了，也不能让它们同时去做主从切换。因为故障转移是一个会修改集群拓扑的动作，比如：

把某个从库提升为新主库
把其他从库重新挂到新主库
更新配置并对外通知

如果多个 Sentinel 同时执行，就可能出现竞争和混乱，比如两个 Sentinel 各自挑了不同的从库当新主库，导致系统出现**脑裂式切换**或者拓扑不一致。

所以必须先从多个 Sentinel 中选出一个 **leader Sentinel**，由它**唯一地执行这次 failover**，其他 Sentinel 负责协同和承认结果。

它解决的是：**避免重复切换、冲突切换和拓扑混乱。**

面试里可以直接总结为：

**quorum 用来解决“要不要切”的问题，防止误判；leader 选举用来解决“由谁来切”的问题，防止多个 Sentinel 同时切换。**

再补一句更完整的表达：

**quorum 保证故障判断尽量基于多数意见，leader 选举保证故障转移动作全局只有一个执行者，这两个机制一起保证 Sentinel 的故障发现和主从切换既谨慎又有序。**

## 6. 主从切换时会不会丢数据？哪些场景下风险最大？

标准答案：

**会，Redis 主从切换时是有可能丢数据的。**
因为 Redis 主从复制默认是**异步复制**，主库写成功并不代表这个数据已经同步到从库了。如果主库刚接收到写请求，还没来得及把这部分数据复制给从库就宕机，而这时哨兵又把某个从库提升为新主库，那么这段还未来得及同步的数据就会丢失。

最典型的丢数据场景有这几类：

第一类是**主库刚写入成功，还没同步到从库就宕机**。
这是最常见的情况，也是异步复制天然存在的风险。客户端已经收到主库“写成功”，但从库还没有这条数据，故障切换后这条数据就没了。

第二类是**主库和从库之间复制延迟较大**。
比如网络抖动、主库压力大、从库处理慢，都会导致主从复制滞后。如果此时主库故障，那么从库落后越多，切换后丢的数据就可能越多。

第三类是**发生网络分区，导致脑裂**。
比如主库其实没挂，只是 Sentinel 和主库之间网络不通，Sentinel 误以为主库故障，于是把某个从库提升成了新主库。但原主库如果还在继续接收客户端写请求，就会出现两个主库同时写入。等网络恢复后，旧主库通常会被降为从库并重新同步新主库，这时旧主库上那部分“孤儿写入”会被覆盖掉，数据就丢了。这个场景风险非常大。

第四类是**AOF/RDB 持久化策略不够强**。
如果新提升的主库本身也还没把最新数据刷盘，后续又再次宕机，那么不仅有复制丢失风险，还可能叠加持久化丢失风险。比如 AOF 每秒刷盘时，理论上最多还可能再丢 1 秒数据。

风险最大的通常是两种场景：

一是**主从复制延迟明显时发生主库故障**，因为从库本身就落后很多。
二是**网络分区导致脑裂**，因为这不只是“少同步几条”的问题，而是可能出现两边同时写、恢复后旧主数据整体被覆盖。

面试里可以直接总结为：

**Redis 主从切换会丢数据，根因是主从复制默认异步。风险最大的是主库写入尚未复制完成就宕机，以及网络分区导致脑裂这两类场景。**

再补一句常见追问回答：

要降低风险，生产上通常会结合 `**min-replicas-to-write` / `min-replicas-max-lag`**、合理的持久化策略、客户端走 Sentinel 感知新主、以及业务层幂等和补偿机制，一起控制数据丢失窗口。

# 四、缓存设计与经典问题类

## 1. 什么是缓存穿透？怎么解决？

缓存穿透是指：**请求的数据既不在 Redis 中，也不在数据库中，但请求依然持续打过来，导致每次都绕过缓存直接访问数据库。**
因为这类数据本来就不存在，所以缓存永远命中不了，请求会不断“穿透”到 DB，这就叫缓存穿透。

典型场景是：有人反复请求一个根本不存在的商品 ID、用户 ID、订单号，或者被恶意构造了大量随机 key。如果没有保护措施，Redis 形同虚设，数据库会被持续打压，严重时会把 DB 拖垮。

常见解决方案有三种。

第一，**缓存空值**。
当查询发现数据库里也没有这条数据时，不要直接返回就结束，而是把一个空结果也写入缓存，比如写一个 `null` 标记，并设置一个较短的 TTL。这样后续再查同一个不存在的数据，就可以直接从 Redis 返回，不再打数据库。

这种方案最常用，优点是实现简单、见效快。缺点是如果攻击者构造大量随机 key，会产生很多无意义空值缓存，占用内存，所以 TTL 一般要短一些。

第二，**布隆过滤器（Bloom Filter）**。
把“系统中可能存在的 key”预先放入布隆过滤器，请求进来先判断：如果布隆过滤器判定这个 key 一定不存在，就直接拦截，不再查 Redis 和 DB；只有可能存在的 key，才继续往下查。

这个方案特别适合 **数据规模大、key 比较稳定、穿透风险高** 的场景。优点是拦截效率高、内存占用低；缺点是布隆过滤器有误判率，且数据更新时要维护过滤器。

第三，**接口层限流与参数校验**。
比如用户 ID 必须是正整数、订单号必须满足固定格式、商品 ID 必须在合法区间内，不合法请求直接拦截。同时对高频异常请求做限流、黑名单、验证码、网关风控。这类手段不能替代缓存方案，但在生产里非常重要，特别是防恶意攻击时。

标准答案一般这样总结：

缓存穿透就是 **查询一个不存在的数据，缓存和数据库都没有，导致请求每次都打到数据库**。
常见解决方案是：**缓存空值、布隆过滤器、接口限流和参数合法性校验**。

其中最常见落地方案是：**缓存空值 + 短 TTL + 布隆过滤器 + 网关限流**。这样效果通常最好。

## 2. 什么是缓存击穿？怎么解决？

缓存击穿是指：**某个热点 key 在失效的瞬间，大量并发请求同时到来，因为缓存没命中，这些请求会一起打到数据库。**
它和缓存穿透的区别是：**击穿的数据是存在的，而且通常还是热点数据；穿透的数据是根本不存在的。**

缓存击穿最典型的场景就是：一个访问量很高的商品详情、活动配置、首页推荐结果，本来一直在 Redis 里，突然 TTL 到期了，这一瞬间成千上万请求同时过来，发现缓存失效，于是一起查 DB。结果就是数据库瞬时压力暴涨，严重时把后端服务打垮。

解决思路的核心就是一句话：**不要让大量请求在缓存失效时同时回源数据库。**

最常见方案是 **互斥锁 / 单飞机制**。
当发现某个热点 key 缓存失效后，不是所有线程都去查数据库，而是先通过 Redis 分布式锁、本地锁或者 singleflight 机制，只让一个线程去回源加载数据并重建缓存，其他线程等待一下，或者短暂重试后再读缓存。这样就把“并发打 DB”变成“单请求打 DB”。

第二种方案是 **逻辑过期**。
不是依赖 Redis 的真实 TTL 让 key 突然消失，而是缓存数据里自己带一个“过期时间”字段。请求来了以后，即使 Redis 里有旧值，也先返回旧值；如果发现逻辑上过期了，就异步触发后台线程去更新缓存。这样用户先拿到旧数据，系统后台再慢慢刷新，优点是不会因为某一刻缓存失效导致大量请求一起穿透到 DB。这个方案很适合 **热点数据、可接受短暂旧数据** 的场景。

第三种方案是 **热点数据永不过期或提前续期**。
对于极高频、非常核心的热点 key，可以不给它设置过期时间，而是通过后台任务定时刷新，或者在快过期时提前续期。这样就尽量避免“热点 key 恰好过期”这个危险时刻。

第四种方案是 **多级缓存 + 限流降级**。
比如本地缓存 + Redis + DB，多挡一层；同时在 DB 侧加限流、熔断、降级兜底，避免 Redis 某个热点 key 失效时把数据库直接冲垮。这通常是高并发核心链路里的增强手段。

标准结论就是：

缓存击穿是 **热点 key 失效瞬间，大量并发请求同时回源数据库**。
常见解决方案是：**互斥锁防止并发回源、逻辑过期避免瞬时失效、热点 key 永不过期或提前刷新，以及必要的限流降级保护**。

面试里最标准的回答通常是：**热点 key + 过期 + 高并发 = 击穿；核心方案是加锁重建缓存。**

## 3. 什么是缓存雪崩？怎么解决？

缓存雪崩是指：**大量缓存 key 在同一时间段集中失效，或者 Redis 整体不可用，导致海量请求同时回源到数据库，最终把数据库或下游系统压垮。**
它和缓存击穿的区别是：**击穿通常是一个热点 key 失效；雪崩通常是一批 key 同时失效，或者整个缓存层出问题。**

最典型的场景有两种：

第一种是 **同一批缓存设置了相同 TTL**，比如一大批 key 都在 10:00:00 同时过期，结果这一刻大量请求一起打到 DB。
第二种是 **Redis 实例宕机、主从切换异常、集群不可用**，导致原本应该由缓存承接的流量，瞬间全部落到数据库。

它危险的地方在于：**不是单点压力，而是整体流量洪峰直冲后端**。如果数据库、服务、MQ、ES 没有足够保护，很容易发生连锁故障。

解决思路主要有几类。

第一，**给 TTL 加随机值，打散过期时间。**
不要让大量 key 用完全相同的过期时间，而是设置成“基础 TTL + 随机偏移量”，这样就能避免同一时刻大批 key 集中过期。这是最基础、最常用的手段。

第二，**热点数据不过期或由后台主动刷新。**
对核心热点 key，可以不依赖被动过期，而是由定时任务、消息驱动或异步线程提前刷新，尽量避免关键缓存在高峰期突然失效。

第三，**构建高可用缓存架构。**
比如 Redis 主从 + Sentinel，或者 Redis Cluster，多副本部署，提升缓存层可用性。因为雪崩很多时候不是 TTL 问题，而是 Redis 整体故障导致的。

第四，**加限流、降级、熔断。**
即使缓存失效，也不能让所有请求无限制打到 DB。要在网关层、服务层、数据访问层做限流和降级，比如只允许部分请求回源，其余返回兜底数据、默认值或稍后重试，保护数据库。

第五，**多级缓存。**
可以加本地缓存 + Redis 的组合。即使 Redis 出现短时问题，本地缓存还能挡住一部分流量，减轻下游压力。

标准结论就是：

缓存雪崩是 **大量缓存同时失效，或缓存层整体不可用，导致请求集中回源数据库**。
常见解决方案是：**过期时间加随机值、热点数据提前刷新、Redis 高可用、限流降级熔断、多级缓存保护**。

一句话记忆就是：**雪崩不是一个 key 的问题，而是一批 key 或整个缓存层同时出问题。**

## 4. 布隆过滤器为什么能防穿透？它的误判问题怎么理解？

布隆过滤器能防缓存穿透，核心原因是它可以在请求到达 Redis 和数据库之前，**先快速判断“这个 key 大概率存在不存在”**。如果布隆过滤器判断某个 key **一定不存在**，那这个请求就可以直接拦截，不必再访问缓存和数据库。这样，大量针对不存在数据的请求，就不会反复穿透到 DB。

它为什么能做到这一点？因为布隆过滤器底层本质上是 **一个位数组 + 多个哈希函数**。系统把所有“可能存在的数据 key”提前映射进去。后续来了一个查询 key，就用同样的多个哈希函数计算出几个位置：

如果这些位置里 **只要有一个位是 0**，就说明这个 key 一定没加入过，因此它 **一定不存在**；
如果这些位置 **全都是 1**，那它就会认为这个 key **可能存在**，于是继续往 Redis / DB 查。

所以布隆过滤器特别适合防穿透，因为缓存穿透的问题恰恰就是：**大量请求查的都是根本不存在的数据**。而布隆过滤器最擅长的，就是高效拦住这种“不存在”的请求。

它的误判问题要这样理解：

布隆过滤器的特点是：**可以判断“肯定不存在”，但不能 100% 判断“肯定存在”。**
也就是说，它有 **假阳性**，但没有 **假阴性**。

假阳性就是：某个 key 实际上根本不存在，但经过多个哈希映射后，对应的位碰巧都被其他 key 占满了，于是布隆过滤器误以为它“可能存在”。这时这个请求还是会继续往 Redis / DB 查一次。

但要注意，这种误判的后果只是 **少拦了一次本该拦住的请求**，不会把真实存在的数据误判成不存在。因为如果真实存在的数据被误判成不存在，那就会把正常请求错杀，这才是严重问题。布隆过滤器设计上恰好避免了这种情况。

所以它的误判，本质上是：

**会把一小部分不存在的数据放过去，但不会把存在的数据错拦掉。**

这也是为什么它能用于生产防穿透。因为防穿透的目标不是做到绝对精确，而是 **以很低内存成本拦住绝大多数无效请求**，把数据库压力大幅降下来。

标准结论就是：

布隆过滤器能防穿透，是因为它能在访问缓存和数据库前，先判断某个 key **是否一定不存在**，从而拦截大量无效请求。
它的误判是指：**可能把不存在的数据误认为存在**，但**不会把存在的数据误认为不存在**。
所以它适合做“前置拦截”，但不能单独替代缓存和数据库查询。

## 5. 为什么给缓存过期时间加随机值能缓解雪崩？

因为缓存雪崩最典型的问题就是：**大量 key 在同一时刻集中失效**，导致原本应该被 Redis 挡住的请求，瞬间一起回源到数据库。给过期时间加随机值，本质上就是把这些 key 的失效时间**打散**，避免它们在同一个时间点集中过期。

比如你有 10 万个商品缓存，如果全部设置成固定 `TTL=30 分钟`，那它们很可能会在某一批次同时失效。一旦这时正好有流量进来，大量请求会同时打 DB，这就容易形成雪崩。

如果改成：

`TTL = 30 分钟 + 0~5 分钟随机值`

那么这批 key 的过期时间就会分散到一个时间区间里，而不是卡在同一个点上。这样原本一次性的回源洪峰，就会被摊平为一段时间内陆续发生的小流量，数据库压力会平滑很多。

所以它能缓解雪崩的核心逻辑就是：

**把“同时失效”变成“分批失效”**
**把“瞬时洪峰”变成“持续小流量”**

要注意，这种做法缓解的是 **因大量 key 同时过期导致的雪崩**，不是解决所有雪崩问题。
如果是 Redis 整体宕机、主从切换失败、网络分区，这种随机 TTL 就没用了，还得靠高可用、限流、降级、多级缓存来兜底。

标准答案可以概括为：

给缓存过期时间加随机值，是为了**打散 key 的失效时间，避免大量缓存同一时刻集中过期**，从而把数据库瞬时回源压力摊薄，缓解缓存雪崩。

## 6. 热点 key 打爆 Redis 怎么办？

标准处理思路是：**先限流抗洪峰，再把热点流量打散，最后做多级缓存和降级兜底。**

热点 key 打爆 Redis，本质上不是 Redis 整体性能不够，而是 **流量过度集中到单个 key、单个分片、单台实例**。尤其在 Redis Cluster 里，一个 key 只能落到一个槽位，所以再多分片也不会自动分摊这个热点。

常见解决方案有这几类。

第一，**本地缓存兜一层**。
在应用 JVM 内加 Caffeine/Guava 本地缓存，把极热点数据先挡在应用侧。这样很多重复请求根本不会到 Redis。这是最直接、最有效的手段之一，特别适合读多写少、允许短时间数据不一致的场景。

第二，**热点 key 拆分 / 复制多份**。
比如把一个热点 key 复制成多个副本：`hot_key_1`、`hot_key_2`、`hot_key_3`……读取时随机打到不同副本上，把原来集中到一个 key 的流量分散到多个 key、多个槽位、多个实例。这个方案适合纯读热点，但要注意更新时需要同时刷新多个副本。

第三，**限流、降级、熔断**。
当热点流量已经超过 Redis 或下游承载能力时，必须在网关或服务层限流。比如只放部分请求进来，其余直接返回兜底值、默认页、稍后重试提示，避免把 Redis 和 DB 一起打穿。

第四，**热点数据提前预热，避免失效瞬间抖动**。
热点 key 一旦过期，容易叠加缓存击穿问题。所以这类 key 一般不要让它自然过期，通常采用“后台主动刷新”或“逻辑过期 + 异步重建”。

第五，**读写分离或专门热点集群**。
如果业务里有稳定的大热点，可以把这类 key 单独放到专门 Redis 实例，避免影响普通业务流量。也可以结合只读副本分担读压力，但前提是业务能接受主从复制延迟。

第六，**多级缓存架构**。
典型做法是：`浏览器/CDN → Nginx/OpenResty 本地缓存 → JVM 本地缓存 → Redis → DB`。真正的大热点，一般不会只靠单层 Redis 扛。

标准结论就是：

热点 key 打爆 Redis，本质是 **流量集中问题**，核心手段不是只靠“升级机器”，而是 **本地缓存挡流量、热点 key 分片/复制打散、限流降级保护、热点数据不过期或主动刷新、必要时独立热点集群隔离**。

面试里一句话回答可以记成：**先挡、再拆、再降级。**

## 7. big key 对 Redis 有什么影响？怎么发现和治理？

`big key` 指的是 **单个 key 占用的数据量特别大**，可能是一个超大的 String，也可能是元素特别多的 Hash、List、Set、ZSet。它的危险不在“数量多”，而在于 **一次操作就很重**，会破坏 Redis 这种“单线程、短平快命令”的运行前提。

它的影响主要有几类。

第一，**拉高请求延迟**。Redis 处理命令是单线程的，读取 big key、删除 big key、序列化 big key、传输 big key，都会让一次命令执行时间明显变长，其他请求只能排队，P99/P999 很容易抖动。

第二，**放大网络和带宽开销**。比如一个 key 对应几 MB 甚至几十 MB 数据，一次返回就会占用很大网络带宽，客户端处理也会变慢，严重时影响整个实例吞吐。

第三，**删除和修改代价高**。尤其是大集合类型，执行 `DEL`、大范围修改、过期淘汰时，可能产生明显阻塞。虽然 Redis 后来提供了惰性删除、`UNLINK` 等优化，但 big key 依然是风险源。

第四，**持久化成本更高**。RDB、AOF rewrite、主从复制时，big key 会放大序列化、磁盘 IO、网络同步和 `COW` 成本，容易引发持久化窗口期抖动。

第五，**更容易触发集群倾斜和故障放大**。一个大 key 落在某个分片上，会让该节点内存、带宽、复制压力明显高于其他节点，迁移和故障恢复也更麻烦。

发现 big key，常见方式有几种。

第一，**用 Redis 自带扫描能力排查**。生产里最常见的是 `redis-cli --bigkeys`，它会按类型扫描并统计较大的 key。这适合离线巡检，但要注意它本质还是扫描，线上高峰慎用。

第二，**按类型查看大小**。比如 String 看 `STRLEN`，List 看 `LLEN`，Hash 看 `HLEN`，Set 看 `SCARD`，ZSet 看 `ZCARD`。这适合怀疑某些 key 时定点检查。

第三，**结合慢日志和监控看异常 key**。如果某些命令经常进入 `SLOWLOG`，或者某个实例网络出口、主从同步、AOF rewrite 时异常抖动，很可能背后就是 big key。

第四，**业务侧埋点和采样**。生产上更靠谱的是在写入链路上对 value 大小、集合元素个数做采样告警，提前发现，而不是等线上抖动后再查。

治理思路核心是：**不要让单个 key 承载过多数据。**

第一，**拆 key**。这是最根本的办法。比如一个大 List 拆成按页、按时间片、按业务分桶多个 key；一个超大 Hash 可以按 field 分段；一个大 JSON 可以拆成多个子对象 key。

第二，**控制 value 大小和集合成员数上限**。在业务层设阈值，比如单个 Hash 不超过多少 field，单个 List 不超过多少条，超过就分片。这个比事后治理更重要。

第三，**避免一次性全量读取**。能分页就不要全量拉，能按范围查就不要整个 key 取出。比如 List 用范围读取，ZSet 用 score/rank 分段查。

第四，**删除大 key 时用异步删除**。优先 `UNLINK`，不要直接 `DEL` 大对象，降低阻塞风险。

第五，**热点 big key 要同时治理体积和流量**。这类最危险，往往既大又热，通常要配合本地缓存、分片、副本分摊一起做。

标准结论就是：

big key 会带来 **延迟抖动、网络放大、删除阻塞、持久化和复制压力上升、集群负载倾斜**。
发现它主要靠 `**--bigkeys`、类型长度统计、慢日志和监控、业务埋点**。
治理核心是 **拆分 key、限制单 key 大小、避免全量操作、删除时用 `UNLINK`、在业务侧提前设上限**。

## 8. 缓存和数据库双写一致性怎么做？

标准答案是：**不要追求强行“双写同时成功”，生产上通常采用“先更新数据库，再删除缓存”作为基础方案，并结合重试、延迟双删、订阅 binlog/消息补偿，来尽量保证最终一致性。**

因为缓存和数据库是两个独立系统，天然不存在本地事务，所谓“双写一致性”本质上很难做到严格强一致，所以工程上一般追求的是 **最终一致性**，而不是绝对实时一致。

最常见、也是最推荐的方案是 **Cache Aside Pattern**：

读请求时，先查缓存，缓存没有再查数据库，并回填缓存；
写请求时，**先更新数据库，再删除缓存**。

之所以不是“先删缓存，再更新数据库”，是因为如果先删缓存，随后还没来得及更新数据库，这时一个并发读请求进来，会从数据库读到旧值，再把旧值写回缓存，导致脏数据回填。

而“先更新数据库，再删除缓存”虽然也不是绝对完美，但问题相对更少。它的主要风险是：数据库更新成功了，但删除缓存失败了，这样缓存里还留着旧值。对此，生产上通常会加 **重试和补偿机制**，比如删除失败写入 MQ，异步重试删缓存。

如果并发特别高，还会加 **延迟双删**。也就是：

先更新数据库
删除缓存
等待一小段时间
再次删除缓存

这样做是为了降低这样一种并发问题：某个读请求正好在你更新数据库之前查了旧值，等你第一次删完缓存后，它又把旧值回填进来了。延迟再删一次，可以把这类脏缓存再清掉。但要注意，延迟双删只能缓解，不能从理论上彻底消灭所有并发窗口问题。

再往生产里走，更稳的方案通常是 **异步补偿**：

更新数据库成功后，发 MQ 或写本地消息表
消费者异步删除缓存
失败持续重试，直到成功

或者直接走 **binlog 订阅**，由 Canal 这类组件监听 MySQL 变更，再去删缓存。这样一致性链路更统一，也更适合多服务场景。

所以标准结论可以这样答：

缓存和数据库双写一致性，生产上通常采用 **先更新数据库，再删除缓存**；
如果要求更高，再配合 **删除失败重试、延迟双删、MQ 异步补偿、binlog 订阅删缓存**；
本质目标是 **保证最终一致性**，而不是追求缓存和数据库的严格实时强一致。

## 9. 为什么“先更新数据库，再删缓存”比“先删缓存，再更新数据库”更常见？

因为 **“先删缓存，再更新数据库”更容易把旧数据重新写回缓存**，并发下风险更大；而 **“先更新数据库，再删缓存”虽然也不是绝对无问题，但脏数据窗口更短，更容易通过重试和补偿兜住**，所以生产上更常见。

先看“先删缓存，再更新数据库”的问题。假设线程 A 先把缓存删了，但数据库还没更新完成；这时线程 B 过来读数据，发现缓存没了，就会去查数据库。由于数据库此刻还是旧值，线程 B 会把旧值重新回填到缓存。接下来线程 A 再把数据库更新成新值，这样就出现了：**数据库是新值，缓存却被并发读请求回填成旧值**。这类问题在高并发读多写少场景里非常典型，而且一旦发生，脏缓存可能会持续很久，直到下次失效或再次删除。

再看“先更新数据库，再删缓存”。它的流程是先把 DB 改成新值，再删除缓存。这样即使有并发读请求进来，只要删缓存成功，后续读请求回源数据库时读到的也是新值，再回填缓存也不会脏。它的主要问题变成：**数据库更新成功了，但删缓存失败了**，导致缓存里暂时还保留旧值。这个问题虽然也存在，但它更容易治理，因为可以通过 **重试删缓存、MQ 补偿、订阅 binlog 再删一次、延迟双删** 等方式补救。

所以两种方案本质区别在于：

“先删缓存，再更新数据库”最大问题是 **会把旧值重新写回缓存**，而且这是并发读自然触发的，比较难兜；
“先更新数据库，再删缓存”最大问题是 **删缓存可能失败**，但这是一个更容易被工程化补偿的问题。

标准结论就是：**生产上更常用“先更新数据库，再删缓存”，因为它把主要风险收敛成“删缓存失败”问题，而这个问题比“旧值回填缓存”更容易通过重试和补偿机制处理。**

## 10. 延迟双删是什么？为什么它不是银弹？

延迟双删是指在更新数据库时，不只删一次缓存，而是按下面这个顺序做：

先更新数据库
再删除一次缓存
等待一小段时间
再删除一次缓存

它的目的，是解决这样一种并发场景：某个读请求在你更新数据库之前，已经从数据库读到了旧值；等你第一次删完缓存后，这个读请求又把旧值回填进缓存，导致缓存重新变脏。此时如果后面再补一次删除，就有机会把这份被“回填进去的旧缓存”再次清掉，这就是延迟双删的意义。

所以它本质上是在补救一种典型并发窗口问题：**第一次删缓存之后，旧值可能被并发读请求重新写回缓存。**

但它不是银弹，原因有几个。

第一，**延迟时间很难精确确定**。延迟太短，那个并发读请求可能还没完成旧值回填，第二次删除起不到作用；延迟太长，脏数据又已经对外暴露了一段时间。这个时间窗口没有统一标准，受数据库 RT、网络延迟、线程调度、GC、系统负载等多种因素影响。

第二，**它不能彻底消灭所有并发时序问题**。因为实际线上不是只有两个线程那么简单，可能有多个读、多个写交错发生。即使做了第二次删除，也仍然可能在新的并发窗口里再次出现旧值回填或者覆盖问题。

第三，**第二次删除也可能失败**。既然第一次删缓存可能失败，第二次一样可能失败。所以它本质上只是“多给一次修正机会”，并没有从根上解决一致性问题。

第四，**它更像经验型优化，不是严格一致性方案**。延迟双删只能降低脏缓存概率，不能从理论上证明在所有并发场景下一定正确。所以生产里它通常只是辅助手段，而不是最终方案。

标准结论就是：

延迟双删是 **更新数据库后，删除缓存，再延迟一段时间后再删一次缓存**，目的是降低并发读导致旧值回填缓存的问题。
但它不是银弹，因为 **延迟时间不可精确控制、无法覆盖所有并发时序、第二次删除也可能失败**，本质上只能缓解问题，不能彻底保证双写一致性。

## 11. 旁路缓存（Cache Aside）模式怎么理解？

旁路缓存（`Cache Aside`）可以理解成：**缓存并不主动和数据库同步，而是由业务代码在读写时“顺路”去操作缓存。**
也就是说，缓存放在数据库旁边，但不是数据库的一部分，应用自己决定什么时候查缓存、什么时候查数据库、什么时候更新或删除缓存，所以叫“旁路”。

它的标准流程分成读和写两部分。

读流程是：

先查缓存
缓存命中，直接返回
缓存没命中，再查数据库
查到数据后，把结果写入缓存
再返回给调用方

这就是最常见的“懒加载”缓存模式，也叫 **按需回填缓存**。

写流程通常是：

先更新数据库
再删除缓存

注意这里一般不是“更新数据库后同步更新缓存”，而是“删缓存”。因为直接更新缓存更容易遇到并发覆盖、脏写、复杂对象局部更新不一致等问题，所以生产上更常见的是 **更新 DB，删除缓存，让后续读请求再从 DB 回填新值**。

所以 Cache Aside 的核心思想就是：

**读的时候，缓存没有再查库并回填；写的时候，先改库再删缓存。**

它为什么常用？因为实现简单、职责清晰、和业务代码结合自然。缓存只是加速层，数据库仍然是数据最终来源，整体比较符合大多数互联网业务场景。

但它也有边界：

第一，它不是强一致方案，只能做到 **最终一致性**。
第二，高并发下可能出现缓存和数据库短暂不一致，需要配合重试、延迟双删、MQ 补偿等手段。
第三，如果缓存失效瞬间并发很高，还要考虑缓存击穿、雪崩这些问题。

标准结论就是：

`Cache Aside` 是最常见的旁路缓存模式，**读走“先查缓存，未命中查库再回填”，写走“先更新数据库，再删除缓存”**。
它的优点是简单、实用、易落地，缺点是只能保证最终一致性，不能天然保证强一致。

## 12. 读写穿透、写回、写直达分别是什么？

这几个词本质上说的是：**应用、缓存、数据库三者之间，读写请求到底怎么流转。**

**写直达（Write Through）** 是指：应用写数据时，**先写缓存，缓存再同步写数据库**，只有两边都成功，这次写才算完成。也就是说，应用主要面对的是缓存层，缓存层负责把数据“直达”到底层存储。它的优点是缓存和数据库一致性相对更好，读请求命中缓存时通常就是新值；缺点是写链路更长，延迟更高，而且缓存层实现更复杂。

**写回（Write Back / Write Behind）** 是指：应用写数据时，**先只写缓存，立即返回成功，数据库异步批量落盘**。它的好处是写性能很好，吞吐高，因为数据库不在主写路径上；但风险也最大，如果缓存还没来得及把数据刷到数据库就宕机，就可能丢数据。所以它适合对写性能要求高、能容忍短暂不一致，甚至能接受一定风险的场景，不适合核心交易数据。

**读写穿透（Read Through / Write Through 常一起说）** 里的“读穿透（Read Through）”是指：应用读数据时，**不自己先查缓存再查库，而是只请求缓存层；如果缓存没有，缓存层再去数据库加载并回填后返回**。也就是说，数据加载逻辑封装在缓存层里，不暴露给业务代码。对应地，“写穿透”很多时候就是上面说的写直达：应用写给缓存，缓存负责同步写库。

你可以这样理解三者区别：

**Cache Aside** 是业务代码自己管缓存和数据库；
**Read/Write Through** 是缓存层帮你管数据库访问；
**Write Back** 则更进一步，连数据库写入都延后异步化了。

标准总结就是：

**读穿透（Read Through）**：缓存未命中时，由缓存层去查数据库并回填。
**写直达（Write Through）**：写请求先到缓存，再由缓存同步写数据库。
**写回（Write Back）**：写请求只先写缓存，数据库异步落盘。

其中：**一致性最好理解的是写直达，性能最好的是写回，业务里最常见真正落地的还是旁路缓存 Cache Aside。**

## 13. 本地缓存 + Redis 二级缓存怎么设计？会遇到什么一致性问题？

标准设计可以理解成：**JVM 本地缓存做一级缓存，Redis 做二级缓存，数据库做最终数据源。**
目标是让最热点请求尽量在应用进程内命中，减少对 Redis 的访问压力，同时又利用 Redis 在多实例之间共享数据。

典型读流程是：

先查本地缓存
本地没命中，再查 Redis
Redis 命中则回填本地缓存并返回
Redis 也没命中，再查数据库
查到后写 Redis，再回填本地缓存

典型写流程一般是：

先更新数据库
再删除 Redis
再删除本地缓存

如果是多实例部署，删除本地缓存不能只删当前节点，还需要通过 **MQ / Redis PubSub / 配置中心事件** 通知其他应用节点一起失效本地缓存，否则其他机器上还会保留旧值。

所以二级缓存的核心不是“多一层缓存”这么简单，而是：

**本地缓存负责抗热点、降 Redis QPS**
**Redis 负责跨实例共享缓存数据**
**数据库仍然是最终真相**

常见设计要点有几个。

第一，**本地缓存只放小而热的数据**。因为 JVM 内存宝贵，而且太多本地缓存会带来 GC 压力，所以一般只缓存高频热点、小对象、读多写少的数据。

第二，**本地缓存 TTL 通常比 Redis 更短**。这样即使通知失效偶尔丢了，本地缓存也能更快自然过期，降低脏数据持续时间。

第三，**本地缓存容量一定要有上限**。通常用 Caffeine 这类支持 `maximumSize`、`expireAfterWrite`、统计命中率的组件，避免把 JVM 撑爆。

第四，**热点 key 可以只进本地缓存，不必每次都打 Redis**。这是二级缓存最大的价值点。

它会遇到的一致性问题，主要有三类。

第一类，**本地缓存和 Redis 不一致**。
比如数据库已经更新，Redis 也删掉了，但某台应用机器上的本地缓存还没删掉，这时这台机器仍然会返回旧值。这是二级缓存最常见的问题。

第二类，**多节点本地缓存不一致**。
A 节点已经清掉本地缓存，B 节点因为通知延迟、消息丢失、实例短暂不可用，没有及时清理，于是不同机器返回不同版本的数据。

第三类，**Redis 和数据库短暂不一致会继续放大到本地缓存**。
如果 Redis 中短暂存在旧值，而本地缓存又从 Redis 回填，那么脏数据会先污染 Redis，再污染各个 JVM 本地缓存，扩散更快。

所以生产上一般会这样处理：

更新时统一采用 **先更新数据库，再删 Redis，再广播删本地缓存**；
本地缓存设置较短 TTL，作为兜底；
失效通知必须可重试，不能完全依赖一次性广播；
对强一致要求高的数据，不走本地缓存，或者只走 Redis；
对热点读多写少数据，才适合二级缓存。

标准结论就是：

本地缓存 + Redis 二级缓存的设计，本质是 **用本地缓存抗热点、用 Redis 做共享层、用数据库做最终数据源**。
典型流程是 **读：本地 → Redis → DB，写：先改 DB，再删 Redis，再通知各节点删本地缓存**。
它最大的问题是 **多级缓存一致性变复杂**，尤其是多实例下本地缓存失效不及时，容易出现短暂脏读。

# 五、并发控制与分布式锁类

## 1. Redis 分布式锁一般怎么实现？最基本的 `SET NX EX` 为什么比 `setnx + expire` 更安全？

Redis 分布式锁最基本的实现方式，就是利用 **一个唯一 key 表示锁资源**，谁能先成功写入这个 key，谁就拿到锁。生产里最常见的基础写法是：

```redis
SET lock_key requestId NX EX 30
```

这里几个参数分别表示：

`NX`：只有 key 不存在时才能设置成功，也就是“抢锁”
`EX 30`：锁 30 秒后自动过期，避免死锁
`requestId`：写入一个唯一值，表示这把锁是谁加的，后续释放锁时要校验这个值，防止误删别人的锁

所以 Redis 分布式锁最小闭环其实是三件事：

**加锁要原子成功**
**锁要有过期时间，防止死锁**
**解锁要校验 owner，防止误删**

最基础流程可以这样理解：

线程 A 执行 `SET lock_key uuidA NX EX 30`，成功则拿到锁
线程 B 同时执行同样命令，因为 key 已存在而失败
线程 A 业务执行完成后，通过 Lua 脚本判断 `lock_key` 的值是否还是 `uuidA`，如果是再删除

释放锁的标准做法一般是 Lua 脚本，而不是先 `GET` 再 `DEL`，因为那样不是原子操作。典型脚本如下：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

---

### 为什么 `SET NX EX` 比 `setnx + expire` 更安全？

因为 `SET NX EX` 是 **原子操作**，而 `setnx + expire` 是 **两个命令**，中间存在故障窗口。

先看不安全的写法：

```redis
SETNX lock_key uuidA
EXPIRE lock_key 30
```

这两步看起来没问题，但风险在于：如果执行完 `SETNX` 成功后，**程序还没来得及执行 `EXPIRE` 就宕机了**，那这个锁就会变成一个**没有过期时间的死锁**。

也就是说：

锁已经加上了
但没有 TTL
其他客户端永远拿不到这把锁
除非人工删除

这就是 `setnx + expire` 最大的问题，本质上是 **加锁和设置过期时间不是一个原子动作**。

而 `SET key value NX EX seconds` 是 Redis 提供的增强版单命令，它会把：

**“key 不存在才设置”**
和
**“设置成功后立即带上过期时间”**

合并成一次原子执行。这样就不存在“锁加成功了但 TTL 没设上”的中间态，所以更安全。

---

### 标准结论

Redis 分布式锁最基本的实现，是用：

```redis
SET lock_key uniqueId NX EX 过期时间
```

来原子加锁，并在解锁时用 **Lua 脚本校验唯一标识后再删除**。
之所以 `SET NX EX` 比 `setnx + expire` 更安全，是因为前者把 **加锁和设置过期时间做成了原子操作**，而后者是两条命令，中间如果进程崩溃，就可能导致**锁没有过期时间，形成死锁**。

## 2. 分布式锁为什么要带唯一值？释放锁为什么要用 Lua 脚本？

分布式锁必须带唯一值，本质上是为了回答一个关键问题：**这把锁到底是不是我加的。**
因为 Redis 锁的 key 只是一个共享资源标记，如果没有唯一值，释放锁时你只能知道“锁存在”，却不知道“这个锁是不是当前线程 / 当前进程 / 当前机器持有的”。

典型风险场景是这样的：

线程 A 拿到锁，设置了过期时间 30 秒
线程 A 业务执行太久，锁自动过期了
线程 B 随后拿到了同一个锁
这时线程 A 执行完了，准备释放锁

如果锁里没有唯一值，线程 A 直接 `DEL lock_key`，就会把 **线程 B 正在持有的锁删掉**。这样就会导致并发安全彻底失效。

所以锁里必须存一个唯一标识，比如 `UUID + threadId + 机器标识`。这样解锁时先判断当前 value 是不是自己写进去的那个值，只有相等才允许删除。唯一值的作用，本质上就是：**标识锁的 owner，防止误删别人的锁。**

释放锁为什么要用 Lua 脚本，是因为“先判断再删除”这两个动作必须原子执行。

错误做法通常是这样：

```java
String val = redis.get(lockKey);
if (requestId.equals(val)) {
    redis.del(lockKey);
}
```

这段代码看起来合理，但它不是原子操作，中间有并发窗口。比如：

线程 A 先 `GET` 到 value 还是自己的 `uuidA`
这时锁刚好过期了
线程 B 立刻拿到了新锁，value 变成 `uuidB`
线程 A 接着执行 `DEL`

结果就是：**线程 A 把线程 B 的锁删掉了。**

所以必须把“比较 value”和“删除 key”合成一个不可分割的原子操作。Redis 里最常见的做法就是 Lua 脚本，因为 Lua 脚本在 Redis 执行期间是单线程、原子完成的。

标准脚本就是：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

它的含义很直接：

如果当前锁的 value 还是我自己的唯一值
就删除
否则不删

这样就避免了“GET 和 DEL 之间被别人插队”的问题。

标准结论就是：

分布式锁带唯一值，是为了 **标识锁的持有者，防止线程在锁过期后误删别人新拿到的锁**；
释放锁要用 Lua 脚本，是为了把 **校验 value 和删除 key 做成原子操作**，避免 `GET` 和 `DEL` 分开执行时产生并发竞态。

## 3. Redis 分布式锁会遇到哪些问题？比如锁过期、误删、锁续期、主从切换。

Redis 分布式锁能用，但它不是“写个 `SET NX EX` 就万事大吉”的东西，线上真正麻烦的地方主要在这几类：**锁过期导致并发失效、误删别人的锁、业务执行超时需要续期、Redis 主从切换导致锁丢失**。这几个是最常见、也最容易被面试追问的点。

先说 **锁过期问题**。如果线程 A 拿到锁后，业务执行时间超过了锁 TTL，比如锁只设了 10 秒，但业务跑了 20 秒，那么 10 秒后锁就自动过期了。此时线程 B 就可能重新拿到同一把锁，结果就是 A 和 B 同时在执行业务逻辑，分布式互斥失效。这类问题本质上是：**锁的租期小于真实业务执行时间**。解决思路通常是两种，要么把过期时间评估得更保守，要么引入 **锁续期机制**，也就是业务没跑完时自动延长锁时间，Redisson 的 watchdog 就是在解决这个问题。

再说 **误删问题**。这是为什么锁里必须带唯一值、解锁必须用 Lua 的根本原因。典型场景是：线程 A 拿到锁后执行太久，锁过期了；线程 B 拿到新锁；这时线程 A 执行完了，如果只是简单 `DEL lock_key`，就会把 B 的锁删掉。这样互斥性就被破坏了。所以正确做法一定是：**锁 value 写唯一 requestId，解锁时通过 Lua 脚本校验 value 相等再删**，防止把别人的锁误删。

第三个问题是 **锁续期**。即使你一开始把 TTL 设大一点，也很难精确覆盖所有场景，因为线上有慢 SQL、Full GC、网络抖动、外部 RPC 超时、线程池阻塞这些不确定因素。TTL 设太短，锁容易提前过期；TTL 设太长，一旦服务挂了，别人又要等很久才能拿到锁。所以很多生产方案会做 **自动续期**：只要线程还活着、业务还没结束，就周期性延长锁过期时间。但这里也有新风险，比如应用发生长时间 Stop-The-World GC、机器卡顿、网络抖动，续期线程没按时执行，锁还是会过期。所以续期能缓解问题，但不是绝对保险。

第四个问题是 **主从切换导致锁丢失**，这是 Redis 分布式锁里最经典的坑。场景通常是这样：线程 A 在主节点加锁成功，但这条写命令还没来得及同步到从节点，主节点就挂了；哨兵或集群发生故障转移，从节点晋升为新主；由于新主上根本没有那把锁，线程 B 又能重新加锁成功。于是 A 和 B 都认为自己拿到了锁，互斥彻底失效。这个问题本质上来自 Redis 复制是 **异步复制**，所以单机 Redis 锁无法天然保证故障切换场景下的强一致性。这个坑靠唯一值、Lua、续期都解决不了。

再往下还有几个常见问题也经常会被追问。

一个是 **业务执行成功，但解锁失败**。比如业务已经提交了，结果 Redis 短时抖动，Lua 解锁失败，锁要等 TTL 到期才能释放。这会影响吞吐和后续请求时延，所以通常要有重试、告警、幂等保护。

一个是 **客户端暂停导致锁语义失真**。比如 JVM 发生长时间 Full GC，线程被挂起很久，醒来以后它以为自己还持有锁，但实际上锁早过期并被别人拿走了。这类问题在 Java 场景特别典型，所以不要把“拿到 Redis 锁”理解成绝对安全执行业务，还要结合业务幂等和状态校验。

还有一个是 **锁重入、锁公平性、阻塞等待** 这些高级语义。最基础的 `SET NX EX` 只解决“抢占一个简单互斥锁”，它不支持天然可重入、公平排队、读写锁、多条件等待。要这些能力，通常要靠像 Redisson 这种客户端框架来补。

标准结论可以这样答：

Redis 分布式锁常见问题主要有四类：
**锁过期** 导致业务未执行完锁已失效，多个线程并发进入；
**误删锁** 导致一个旧线程把新线程持有的锁删掉；
**锁续期** 解决长任务问题，但续期线程受 GC、卡顿、网络影响，不是绝对可靠；
**主从切换** 因为异步复制可能导致锁丢失，出现多个客户端同时持锁。

所以 Redis 分布式锁本质上更适合 **对一致性要求没那么极端的互斥场景**，真正高一致、强互斥、不能接受极小概率失效的场景，通常还要结合数据库状态机、幂等、防重表，或者考虑 ZooKeeper 这类更偏 CP 的方案。

## 4. Redisson 的看门狗机制是什么？解决了什么问题？

Redisson 的看门狗机制，本质上就是 **自动续期机制**。
它解决的是：**业务执行时间不确定，锁设置固定过期时间后，可能在业务还没执行完时就提前过期** 的问题。

如果只用最原始的 Redis 锁，一般会这样加锁：

```redis
SET lock_key requestId NX EX 30
```

这里的 30 秒就是锁租期。但线上业务执行时间往往不稳定，可能受慢 SQL、远程调用、线程池阻塞、GC 暂停影响。如果线程实际跑了 50 秒，而锁 30 秒就过期了，那么第 31 秒其他线程就可能再次拿到这把锁，导致两个线程同时执行业务，分布式锁失效。

Redisson 的看门狗就是为了解决这个问题。它的做法是：

当你**不显式指定锁租期**时，Redisson 默认给这把锁一个内部租期，比如默认 30 秒；
然后启动一个后台续期任务，只要持锁线程还活着、业务还没结束，它就会在锁快到期前，周期性地把过期时间往后延长。
这样锁就不会因为业务执行时间过长而自动失效。

可以把它理解成：

**先给你 30 秒锁**
**业务还没结束，就每隔一段时间再续 30 秒**
**直到你主动 unlock，才停止续期**

所以它解决的核心问题就是：**固定 TTL 难以覆盖长耗时业务，导致锁提前过期。**

---

### 它具体缓解了什么问题

第一，缓解了**业务耗时不可预估**的问题。
很多业务不是固定 2 秒、5 秒能完成，可能偶发慢请求。如果手工写死过期时间，要么设太短导致锁失效，要么设太长导致异常时别人等待太久。看门狗把这个矛盾缓解掉了。

第二，缓解了**人工评估 TTL 很困难**的问题。
开发时很难准确估计所有线上极端情况，看门狗让你不用过度依赖一个静态超时时间。

第三，提升了**长事务、长任务场景下锁的可用性**。
比如批处理、复杂聚合、跨服务调用链较长的任务，更适合用自动续期。

---

### 它没有解决什么问题

要注意，看门狗不是银弹，它只是解决“**锁还该属于我，但因为 TTL 到了要过期**”这个问题。

它**不能解决主从切换导致锁丢失**。
如果主节点刚加锁成功还没同步到从节点就挂了，新主上可能根本没有这把锁，这不是续期能解决的。

它**也不能解决长时间 STW GC、进程假死、严重网络抖动**。
如果应用卡住太久，续期线程没来得及跑，看门狗也续不上，锁一样会过期。

---

### 标准结论

Redisson 的看门狗机制，就是 **在未指定固定租期时，为持有中的锁自动续期**。
它主要解决的是 **业务执行时间超过锁 TTL，导致锁提前过期、并发互斥失效** 的问题。
本质上，它让分布式锁从“固定过期时间”变成了“业务没结束就持续续租，业务结束再释放”。

## 5. Redis 锁适合哪些场景，不适合哪些场景？

标准结论是：**Redis 锁适合做“高性能、可容忍极低概率失效、以互斥为主”的业务控制；不适合做“强一致、绝不能双执行、失败代价极高”的核心场景。**

先说适合的场景。

Redis 锁最适合 **性能优先、锁粒度简单、持锁时间较短** 的场景。比如：

同一用户短时间内防重复提交
同一订单防重复支付触发
同一任务防重复调度
库存扣减前的短临界区互斥控制
定时任务集群模式下只允许一个节点执行
缓存重建时防止并发回源数据库

这些场景有几个共同点：第一，锁主要是为了“**减少并发冲突**”；第二，即使极端情况下锁偶发失效，业务通常还能靠 **幂等、状态机、唯一索引、防重表** 再兜一层；第三，大家更看重 Redis 的 **低延迟和实现简单**。

再说不适合的场景。

Redis 锁不适合 **要求绝对强互斥、不能接受极小概率双写/双执行** 的场景。比如：

分布式事务里的核心提交控制
金融扣款、资金划拨这类强一致关键路径
不能重复执行且重复一次代价极大的任务
主从切换期间也必须保证绝对单持有的锁
需要严格顺序、公平排队、强会话语义的协调场景

原因很简单：Redis 锁本质上还是 AP 倾向的工程方案，存在 **锁过期、续期失败、GC 卡顿、网络抖动、主从切换导致锁丢失** 这些天然边界，所以它不是严格意义上的“强一致分布式协调器”。

所以生产上更靠谱的理解是：

**Redis 锁适合做第一道并发控制，不适合做最终一致性的唯一保障。**
真正关键的地方，通常要再配合：

数据库唯一约束
状态机校验
幂等 token
防重表
乐观锁 / 悲观锁
消息去重与补偿

标准总结就是：

Redis 锁适合 **高性能、防重复、短临界区、允许最终兜底的业务场景**；
不适合 **金融级强一致、绝不能双执行、故障切换期间也必须严格互斥** 的场景。
一句话记忆：**Redis 锁更像高性能互斥工具，不是绝对可靠的分布式一致性组件。**

## 6. 秒杀场景里，为什么很多时候 Lua 比单纯 Java 代码 + 分布式锁更稳？

标准答案是：**因为 Lua 能把“判断库存、判断是否重复下单、扣减库存、写入抢购标记”等多个操作放到 Redis 里一次原子执行，减少网络往返和并发窗口；而 Java 代码 + 分布式锁通常链路更长、状态更多、更容易在高并发下出现性能抖动和边界问题。**

先看 Java + 分布式锁的典型思路。一般是：

先抢 Redis 锁
拿到锁后查库存
判断是否重复下单
扣减库存
写用户购买标记
释放锁

这个方案不是不能做，但在秒杀场景下有几个天然问题。

第一，**链路长，往返多**。
即使库存和购买标记都在 Redis，Java 方案通常也是多次网络交互：加锁一次、查库存一次、查购买标记一次、扣库存一次、写标记一次、解锁一次。高并发下，网络 RTT、线程切换、连接池争用都会放大延迟。

第二，**锁竞争会非常激烈**。
秒杀是典型热点资源争抢，大家都抢同一把锁。大量请求会阻塞、重试、失败，Redis 和应用线程池都会承压。你以为加锁是在“保正确”，实际上很多时候先被拖垮的是吞吐和 RT。

第三，**锁方案边界复杂**。
要考虑锁过期、业务没执行完锁提前失效、解锁误删、续期、主从切换这些问题。秒杀流量一大，这些问题更容易被放大。

第四，**Java 侧原子性是“靠锁拼出来的”**。
本质上，库存判断、去重判断、扣减这些逻辑并不是天然一体，必须依赖外部锁保证串行化。一旦锁语义有抖动，就可能出现超卖、重复下单。

而 Lua 的优势在于：**把核心判断和写操作收敛到 Redis 单线程里一次执行完。**

比如秒杀核心脚本通常就是：

先判断库存是否大于 0
再判断用户是否已经抢过
符合条件则扣库存
写入用户抢购标记
必要时把下单信息写入 Stream/List 供异步下单

这些逻辑在一个 Lua 脚本里执行时，对 Redis 来说是**原子操作**。执行期间不会被其他命令插队，所以：

不会出现“刚判断完有库存，别人先扣掉了”的并发窗口
不会出现“刚判断用户没下单，别人已经插入标记了”的并发窗口
也不需要额外再加分布式锁

这就是为什么 Lua 在秒杀里通常更稳，核心原因有三点：

**第一，原子性更强。**
不是靠外部加锁串起来，而是 Redis 直接一次执行。

**第二，性能更高。**
多步操作合成一次请求，减少网络往返和线程调度成本。

**第三，失败边界更少。**
不用单独处理锁抢占、锁续期、锁释放这些复杂问题。

但要注意，Lua 更稳，不代表“只写 Lua 就够了”。真正生产级秒杀通常是：

**Lua 负责前置原子校验和预扣减**
**MQ / Stream 负责异步削峰**
**MySQL 负责最终订单落库**
**幂等、防重、补偿负责最终一致性**

也就是说，Lua 解决的是“Redis 前置并发控制”这一段，不是整个秒杀系统的全部可靠性。

标准结论就是：

秒杀场景里 Lua 往往比 Java + 分布式锁更稳，是因为 **Lua 可以把库存校验、去重、扣减等操作放在 Redis 内部原子执行，减少锁竞争、网络往返和并发窗口**；而 Java + 分布式锁方案链路更长、热点锁竞争更重、边界条件更多，在超高并发下更容易抖动。

## 7. 用 Redis 做计数器、限流器时，为什么 Lua 脚本很常见？

因为这类场景的核心诉求通常是：**多个步骤要一起做，而且必须原子执行。**
单纯用 Java 代码一条一条发 Redis 命令，虽然也能实现，但中间会有并发窗口；而 Lua 可以把这些操作放到 Redis 内部一次执行完，所以更稳。

先看计数器场景。很多时候不是简单 `INCR` 就结束，而是：

先自增
再判断是否超过阈值
第一次创建时顺便设置过期时间
或者超过阈值后返回特定标记

如果这些步骤拆成多条命令，比如 `INCR` 后再 `EXPIRE`，或者 `GET` / `INCR` / `EXPIRE` 分开执行，就会有问题。典型例子是：计数刚加上，程序还没来得及设置过期时间就挂了，这个 key 可能就成了**永久计数器**；又或者多个并发请求同时判断阈值，可能出现边界不一致。

限流器更明显。比如固定窗口限流常见逻辑是：

请求来了先给 key 计数
如果第一次出现则设置窗口过期时间
然后判断当前计数是否超过限制
超过就拒绝，否则放行

这些动作如果分开发命令，高并发下很容易出现：

多个线程都以为自己是“第一次”
过期时间设置不一致
计数和判断之间被别人插队
阈值边界出现误差

而 Lua 的好处就是：**把“计数 + 过期 + 判断 + 返回结果”放在一个脚本里原子完成。**
Redis 执行 Lua 脚本时是单线程串行的，脚本执行过程中不会被其他命令打断，所以天然适合这类“读改写一体”的场景。

它常见还有两个工程优势。

第一，**减少网络往返**。
原本 Java 侧可能要发 2~4 条命令，现在一次 `EVAL` 或 `EVALSHA` 就够了。在高 QPS 限流场景下，这能明显减少 RTT 和连接池压力。

第二，**逻辑收敛，客户端更简单**。
规则直接放在脚本里，应用侧只关心传参和结果，不用在 Java 里拼很多分支，尤其在多服务复用同一套限流逻辑时更方便。

所以标准结论是：

Redis 做计数器、限流器时 Lua 很常见，是因为这类场景往往需要把 **自增、设置过期、判断阈值、返回结果** 等多个操作合并成一次**原子执行**，从而避免并发竞态和网络往返开销。
一句话记：**凡是 Redis 上有“读 + 改 + 判断”组合逻辑，Lua 往往就很适合。**

## 8. Redis 事务是什么？`MULTI/EXEC/WATCH` 能不能保证严格事务语义？

Redis 事务本质上是 **把一组命令打包，按顺序一次性执行** 的机制，核心命令是 `MULTI`、`EXEC`、`DISCARD`，再配合 `WATCH` 做乐观锁控制。它解决的主要不是关系型数据库那种完整 ACID 事务问题，而是：**让一批命令在执行阶段不被其他客户端命令插入。**

最基本流程是这样的：

先执行 `MULTI`，表示开启事务
后续命令不会立刻执行，而是先进入队列
执行 `EXEC` 时，队列中的命令按顺序依次执行
如果执行 `DISCARD`，则放弃这批命令

所以 Redis 事务最核心的能力是：**批量入队，统一串行执行。**

`WATCH` 是额外的乐观锁机制。它的作用是：在执行事务前先监视某些 key，如果这些 key 在 `EXEC` 前被其他客户端改过，那么 `EXEC` 就不会执行这批命令，而是直接返回空结果。它更像一个 **CAS 检测机制**，而不是传统数据库里的锁。

---

### 它能保证什么

第一，**命令串行执行，不会被别的客户端命令插队。**
一旦进入 `EXEC` 执行阶段，这批命令会连续跑完，中间不会夹进其他客户端命令。

第二，**事务队列本身要么提交执行，要么放弃。**
也就是 `EXEC` 前只是入队，不会执行；`EXEC` 后统一执行。

第三，**配合 `WATCH` 可以实现乐观并发控制。**
如果监视的 key 被改过，事务直接失败，业务可以重试。

---

### 它不能保证严格事务语义

标准答案是：**不能。Redis 的 `MULTI/EXEC/WATCH` 不能保证关系型数据库那种严格事务语义。**

原因主要有几条。

第一，**没有传统意义上的回滚。**
Redis 事务执行时，如果某条命令运行报错，比如类型不匹配，前面已经成功执行的命令不会回滚，后面的命令还会继续执行。也就是说，它不是“全成功全失败”的数据库式原子回滚。

例如事务里前两条成功了，第三条失败了，Redis 不会撤销前两条。

第二，**隔离性不是数据库那套完整隔离级别。**
Redis 只是利用单线程保证 `EXEC` 阶段命令连续执行，但没有像 MySQL 那样的 Read Committed、Repeatable Read、Serializable 这些完整隔离语义。

第三，**持久化层面也不是事务提交日志模型。**
Redis 不是围绕 WAL + undo/redo log + crash recovery 去实现事务一致性，所以不能类比数据库事务。

第四，`**WATCH` 本质是乐观锁，不是严格锁。**
它只能做到“提交前检查是否被改过”，如果冲突了就失败重试，但它不阻塞别人修改，也不保证像悲观锁那样的强控制。

---

### 怎么理解更准确

可以把 Redis 事务理解成：

**批量命令执行机制 + 执行阶段串行化 + 基于 `WATCH` 的乐观并发控制**

它适合做一些简单的：

批量写操作
基于版本冲突检测的更新
不要求回滚的轻量事务逻辑

但如果你要的是：

强一致
失败自动回滚
复杂隔离级别
跨多步严格事务控制

那 Redis 事务并不适合，通常更推荐直接用 **Lua 脚本**，因为很多场景下 Lua 比 `MULTI/EXEC/WATCH` 更直接，也更接近“原子执行一段逻辑”。

---

### 标准结论

Redis 事务是通过 `MULTI/EXEC` 把多条命令入队后统一顺序执行，`WATCH` 用来做乐观锁冲突检测。
它能保证的是 **事务中的命令在执行阶段不会被其他命令插入**。
但它**不能保证关系型数据库那种严格事务语义**，因为：

**没有真正的回滚机制**
**没有完整的 ACID 隔离语义**
`**WATCH` 只是乐观锁，不是强事务锁**

所以 `MULTI/EXEC/WATCH` 只能算 **弱事务能力**，不能等同于 MySQL 那种严格事务。

## 9. Lua 脚本在 Redis 里为什么能保证原子性？

因为 Redis 执行 Lua 脚本时，**会把整个脚本当成一个不可分割的命令来执行**。在脚本执行期间，Redis 不会去处理其他客户端的命令请求，所以脚本里的多步操作对外表现为“要么全部执行完，要么在执行完成前不会被别人插入”。这就是它原子性的来源。

本质上原因有两个。

第一，**Redis 本身是单线程串行执行命令的**。
Lua 脚本进入 Redis 后，不是脚本里每一行都变成一个可被别人打断的独立命令，而是整个脚本由当前线程连续跑完。既然 Redis 同一时刻只处理一个执行单元，那么这个执行单元是普通命令也好，是 Lua 脚本也好，在执行期间都不会被其他请求并发打断。

第二，**脚本里的多个 Redis 操作是在服务端一次完成的**。
比如你在 Lua 里先 `GET`，再判断，再 `INCR`，再 `EXPIRE`，这些动作虽然逻辑上是多步，但它们都封装在同一个脚本执行过程中。外部客户端看不到中间状态，也无法在这些步骤之间插入命令，所以不会出现“刚判断完，别人先改了”的并发窗口。

所以它适合解决这类问题：

先读一个值
再做判断
再修改
再返回结果

如果这些步骤放在 Java 里分多次发命令，中间就可能被别的线程插队；而放到 Lua 里，就能在 Redis 内部一次性完成。

但要注意，这里的“原子性”是 **Redis 命令执行层面的原子性**，不是数据库那种完整事务语义。它的含义更准确地说是：

**脚本执行期间不会被其他命令打断，脚本内部逻辑按顺序完整执行。**

标准结论就是：

Lua 脚本在 Redis 里能保证原子性，是因为 **Redis 单线程串行执行命令，Lua 脚本会被当成一个整体执行单元，在执行完成前不会被其他客户端命令插入**。
因此脚本里的多步读改写逻辑可以合并成一次服务端原子操作。

# 六、淘汰策略与内存管理类

## 1. Redis 的过期策略是什么？为什么不是单纯“到点立刻删”？

Redis 的过期策略本质上是 **惰性删除 + 定期删除** 的组合，而不是给每个 key 到期时都立刻触发删除。

惰性删除指的是：当客户端访问一个 key 时，Redis 先检查它是否过期，如果过期了就顺手删掉并返回不存在。这个方式的优点是 CPU 开销小，因为不会主动扫描所有过期 key；缺点是如果某些过期 key 一直没人访问，它们会继续占用内存。

定期删除指的是：Redis 会周期性地随机抽取设置了过期时间的 key 做检查，把其中已经过期的删除掉。这个方式是为了弥补惰性删除的缺陷，避免大量过期 key 长时间堆积在内存里。但它也不是全量扫描，而是“抽样 + 限时”处理，避免删除过期 key 本身把 CPU 打满。

之所以不是单纯“到点立刻删”，核心原因是 **成本太高，不适合 Redis 的高性能模型**。如果给每个 key 都维护一个精确的定时删除任务，那么海量 key 场景下会带来很重的调度成本、时间管理成本和额外内存开销；而且 Redis 是单线程执行命令的，若大量 key 在同一时刻集中到期，还会形成明显的 CPU 抖动，影响正常请求延迟。所以 Redis 选择了“访问时顺手删 + 后台周期抽样删”的折中方案，在 **CPU 成本、内存释放及时性、系统吞吐** 之间做平衡。

面试里可以再补一句：Redis 过期策略解决的是“过期 key 什么时候删除”的问题，而如果内存仍然不够，还会再配合 **内存淘汰策略**，比如 LRU、LFU、random、ttl 等，这两个机制不要混淆。

## 2. 惰性删除和定期删除分别是什么？各自优缺点是什么？

惰性删除是指：**key 到期后不会主动立刻删除，而是在这个 key 再次被访问时，Redis 才检查它是否过期**。如果已经过期，就删除并返回不存在。它的优点是实现简单、CPU 开销低，因为只在访问时才处理，不会额外主动扫描大量 key。缺点是明显的：如果某些过期 key 长时间没人访问，它们会一直留在内存里，造成内存浪费，所以单靠惰性删除不够。

定期删除是指：**Redis 后台周期性地随机抽取一部分设置了过期时间的 key，检查并删除其中已过期的 key**。它不是全量遍历，而是按一定频率做抽样清理。它的优点是能主动回收一部分无人访问但已经过期的 key，减少内存堆积问题。缺点是它是一种“近似清理”机制，不保证过期 key 会在到期瞬间被删掉；另外如果定期删除做得太激进，会增加 CPU 消耗，影响正常命令处理。

所以两者的关系可以这样理解：**惰性删除偏向节省 CPU，定期删除偏向释放内存**。Redis 把两者结合起来使用，本质上是在 **CPU 开销和内存占用之间做平衡**。

## 3. Redis 的内存淘汰策略有哪些？`LRU`、`LFU`、`TTL`、`random` 分别适合什么业务？

Redis 的内存淘汰策略，是指 **当内存使用达到 `maxmemory` 上限后，Redis 允许淘汰哪些 key、以及按什么规则淘汰**。常见策略可以先分两类记：

**不淘汰类**：`noeviction`，达到内存上限后，写请求直接报错。适合数据绝不能被 Redis 随便删的场景，但前提是你能严格控制容量，否则业务容易报错。

**淘汰类**：主要从设置了过期时间的 key 中淘汰，或者从所有 key 中淘汰。常见有：
`volatile-lru`、`allkeys-lru`
`volatile-lfu`、`allkeys-lfu`
`volatile-random`、`allkeys-random`
`volatile-ttl`
还有早期版本常见的 `volatile-noeviction` 本质上就是只允许淘汰带过期时间 key，不满足时写失败，实际面试里重点还是前面这些。

`LRU` 是 **最近最少使用**，更适合“最近访问过的数据未来大概率还会再访问”的场景。比如商品详情缓存、用户会话附近数据、热点接口结果缓存。这类业务通常有明显的“最近访问热点”，所以淘汰长时间没被访问的数据比较合理。Redis 里不是严格 LRU，而是近似 LRU，但面试里这么回答就够了。

`LFU` 是 **最近一段时间访问频率最低**，更适合“长期热点比较稳定”的场景。比如热门商品、热门榜单、配置字典、地区编码、医院科室信息这类高频公共数据。因为这类数据不一定最近刚访问，但整体访问次数一直很高，用 LFU 比 LRU 更能保护“长期热 key”。如果业务热点分布比较稳定，通常 LFU 比 LRU 更合适。

`TTL` 指的是 `volatile-ttl`，优先淘汰 **剩余生存时间最短** 的 key。它只会在设置了过期时间的 key 里选。适合明确依赖过期时间表达业务价值的数据，比如验证码、短期令牌、临时查询结果、限时缓存。因为这些数据本来就快过期了，先淘汰它们，对业务影响通常更小。但它不适合那种“虽然快过期但其实很热”的数据场景，所以使用面没有 LRU/LFU 广。

`random` 是随机淘汰，适合对缓存命中率不敏感、只要求实现简单和低开销的场景，比如一些临时性数据、实验性缓存、兜底缓存池。它的优点是简单、开销小；缺点是不可预测，容易把热点数据也淘汰掉，所以生产核心缓存一般不优先选它。

实际落地时，可以这样记：
如果是 **通用缓存，热点主要看最近访问**，优先 `allkeys-lru`；
如果是 **长期热点明显、热数据比较稳定**，优先 `allkeys-lfu`；
如果是 **大量临时 key，且都设置了过期时间**，可以考虑 `volatile-ttl`；
如果 **Redis 不是缓存，而是偏持久状态存储**，通常不建议依赖淘汰策略兜底，更常见是 `noeviction` 加容量治理。

小结一下：**LRU 看“最近”，LFU 看“频率”，TTL 看“谁快过期”，random 看“无差别随机”**。面试里再补一句：生产上最常用、最稳妥的，通常还是 `allkeys-lru` 和 `allkeys-lfu`。

## 4. `volatile-*` 和 `allkeys-*` 的区别是什么？

两者的核心区别是：**淘汰范围不同**。

`volatile-*` 表示 **只在设置了过期时间的 key 中进行淘汰**。也就是说，只有带 `expire/ttl` 的 key 才有资格被选中删除。如果没有设置过期时间的 key，再占内存也不会被这类策略淘汰。

`allkeys-*` 表示 **在所有 key 中进行淘汰**，不管这个 key 有没有设置过期时间，只要符合淘汰规则，都可能被删掉。

比如：
`volatile-lru`：只从“设置了过期时间的 key”里，淘汰最近最少使用的
`allkeys-lru`：从“全部 key”里，淘汰最近最少使用的

所以它们不是淘汰算法不同，而是 **候选集合不同，后面的 LRU / LFU / random 才是具体淘汰算法**。

实际理解上：
如果 Redis 里只有一部分数据是缓存，并且这些缓存都显式设置了过期时间，希望“只有缓存能被淘汰，其他核心数据别动”，那更适合 `volatile-*`。
如果 Redis 整体就是一个缓存池，大部分 key 都可以被淘汰，那更适合 `allkeys-*`。

再补一句面试里常说的话：如果用了 `volatile-*`，但很多 key 没设置过期时间，可能会出现 **可淘汰 key 不足** 的问题，导致内存压力下写请求表现不符合预期；而 `allkeys-*` 一般更适合纯缓存场景。

## 5. Redis 的 LRU 是精确 LRU 吗？为什么不是？

Redis 的 LRU **不是精确 LRU，而是近似 LRU**。

原因在于：如果要实现精确 LRU，通常需要为所有 key 维护一个严格有序的访问链表或类似结构，每次读写都要更新这个顺序。这样虽然淘汰时能精确找到“最久没访问的 key”，但代价很高，会带来额外的 **内存开销、指针维护成本、更新开销**，在 Redis 这种追求高性能、低延迟的内存数据库里不划算。

Redis 的做法是：给对象维护一个 **LRU 时间戳**，在淘汰时不是全量排序所有 key，而是 **随机采样一批 key**，再从这批样本里挑出最久没访问的淘汰。所以它只能保证“在采样集合里尽量接近 LRU”，不能保证全局绝对最老。

这么设计的核心原因就是两个字：**性能**。Redis 希望把更多 CPU 留给正常读写命令，而不是花在维护一个精确的淘汰顺序上。尤其在海量 key 场景下，精确 LRU 的维护成本会明显影响吞吐和延迟，所以 Redis 选择了“效果足够好、成本更低”的近似 LRU。

面试里可以补一句：**Redis 用近似 LRU，本质上是在淘汰精度和系统性能之间做权衡**。对缓存场景来说，这种近似策略通常已经够用了。

## 6. LFU 是怎么近似实现的？它相比 LRU 在什么场景更有优势？

Redis 的 LFU 也不是精确统计的 LFU，而是 **近似 LFU**。它没有给每个 key 维护一个无限增长的精确访问次数，而是用了一个压缩过的计数思路：对象里保存一个 **访问频率计数器** 和 **最近衰减时间**。每次 key 被访问时，计数器并不是简单线性加一，而是按一定概率增长，访问次数越高，后面越难继续涨；同时随着时间推移，计数器还会衰减，避免“历史上热过一次的 key 永远占优”。所以 Redis 里的 LFU，本质上统计的是 **一段时间内的大致热度**，而不是生命周期总访问次数。

这样做的目的和 LRU 一样，都是为了控制成本。因为如果做精确 LFU，就要为每个 key 维护真实频次，还要解决老热点长期霸榜的问题，内存和计算开销都更大。Redis 通过 **概率递增 + 时间衰减**，实现了一个足够轻量、适合缓存场景的近似频率淘汰。

LFU 相比 LRU，更有优势的场景是：**热点是长期稳定的，而不是短期突发的**。
比如热门商品、热门医院、地区字典、配置项、公共基础数据，这类 key 可能不是“刚刚被访问”，但长期访问次数一直很高。此时如果用 LRU，短时间流量波动可能把老热点挤掉；而 LFU 更能识别“长期高频数据”，保护真正的稳定热点。

相反，如果业务更看重“最近访问行为”，比如会话数据、刚浏览过的页面、临时查询结果这类明显有时效性的缓存，LRU 往往更合适。因为这类数据的价值更多来自“最近被用过”，而不是“历史累计访问很多次”。

所以可以直接记一句：**LRU 更适合应对最近热点，LFU 更适合应对长期热点**。

## 7. 如果 Redis 内存满了，会发生什么？

这要看 Redis 配置的 `**maxmemory`** 和 **内存淘汰策略**。

如果内存达到 `maxmemory` 上限，Redis 不会无限继续分配，而是先看当前配置的淘汰策略怎么处理。若配置的是 `allkeys-lru`、`allkeys-lfu`、`volatile-ttl` 这类淘汰策略，Redis 会先按对应规则淘汰一部分 key，腾出空间后再继续处理写请求。

如果配置的是 `noeviction`，那就不会淘汰任何数据，此时 **写操作会直接报错**，常见现象就是返回类似 `OOM command not allowed when used memory > 'maxmemory'`。这里的“写操作”包括新增数据、修改导致内存继续增长的数据；而纯读请求通常还能继续执行。

如果配置的是 `volatile-*`，还要注意一个边界：**只有设置了过期时间的 key 才能被淘汰**。如果这类 key 数量不够，或者根本没有可淘汰 key，那么最终效果也会很像 `noeviction`，写请求一样可能失败。

再补一层理解：Redis 内存满了后，影响最大的通常不是“读不到”，而是 **写不进去、命中率下降、延迟抖动变大**。因为一旦频繁触发淘汰，Redis 要不断做采样和删除，业务侧也可能因为热点 key 被淘汰，导致大量请求回源到 MySQL，进一步把后端打高。

所以面试里标准回答可以收束为一句：**Redis 内存满了以后，要么按淘汰策略删除部分 key 再写入，要么直接拒绝写请求，具体取决于 `maxmemory-policy` 配置。**

## 8. 为什么线上不能把 Redis 内存打到 100%？

线上不能把 Redis 内存打到 100%，因为 **Redis 实际内存使用并不等于你看到的数据大小**，还要考虑对象元数据、哈希表扩容、复制缓冲区、AOF 重写缓冲区、主从同步缓冲区、碎片内存等额外开销。如果把内存顶满，Redis 很容易在瞬时内存波动时直接触发 OOM，导致写请求失败。

另外，Redis 在接近满内存时，**淘汰压力会明显变大**。一旦频繁触发淘汰，CPU 开销会上升，命令延迟会抖动，热点数据还可能被不断挤出，造成缓存命中率下降，进而把流量打到 MySQL 或下游服务，容易引发连锁故障。

还有一个很关键的点是 **内存碎片和 fork 开销**。Redis 做 RDB 快照或 AOF rewrite 时会触发 `fork`，虽然是写时复制，但如果此时内存已经非常满，父子进程共享页在写入过程中会额外放大内存压力，严重时可能导致快照失败、rewrite 失败，甚至实例被系统 OOM killer 干掉。

如果是主从架构，还要预留 **复制 backlog、网络缓冲、主从同步期间的数据积压空间**。这些都不是业务 key 本身，但都要占内存。线上如果没有安全水位，一旦出现流量突增、批量写入、bigkey、主从重同步，就非常危险。

所以生产上一般不会让 Redis 跑到 100%，而是会预留安全余量。常见思路是：**业务数据只吃掉总内存的一部分，剩下的给碎片、fork、复制缓冲和突发流量留空间**。本质上这是在给 Redis 的运行时波动留缓冲，否则它不是“满了才危险”，而是“接近满了就开始不稳定”。

## 9. 内存碎片率是什么？为什么碎片率高会有问题？

内存碎片率一般指 **Redis 向操作系统申请到的实际物理内存**，和 **Redis 当前真正用于存放数据的有效内存** 之间的比值，常见可理解为 `mem_fragmentation_ratio`。如果这个值大于 1，说明 Redis 实际占用的内存比业务数据本身更多；越高，说明碎片越明显。

碎片产生的原因主要是：Redis 底层内存分配器在频繁申请、释放不同大小对象时，很难把内存完全整齐复用。比如 key 大小差异大、频繁新增删除、bigkey 拆分变化、Hash/List/Set 等结构不断伸缩，都会让内存出现很多“不连续的小空洞”。这些空洞加起来可能不少，但因为不连续，未必能高效复用，所以看起来数据不多，实际占用却很大。

碎片率高的问题，首先是 **浪费内存**。业务上可能只存了 10G 数据，但 Redis 实际占了 15G 甚至更多，等于可用容量被白白吃掉。其次是 **更容易触发 maxmemory、淘汰和 OOM**，因为 Redis 判断压力看的是实际内存使用，不是你主观感觉的数据量。再往后，碎片率高还会放大 **fork 成本和写时复制压力**，在做 RDB 或 AOF rewrite 时更容易出现额外内存膨胀，导致持久化失败或实例抖动。

所以碎片率高的本质问题不是“统计值不好看”，而是 **同样的数据占了更多内存，压缩了安全水位，增加了淘汰、延迟抖动和 OOM 风险**。生产里如果长期偏高，就需要结合 `used_memory`、`used_memory_rss`、bigkey、删除模式、持久化时机一起排查。

## 10. Redis 主从 + 持久化场景下，为什么要预留更多内存？

因为这种场景下，Redis 占用的内存不只是业务数据本身，还要额外承担 **复制缓冲 + 持久化 fork + 写时复制 + 重写缓冲 + 内存碎片** 等运行时成本。如果不预留足够空间，实例平时看着还能跑，一到主从同步、RDB 快照、AOF rewrite，就很容易内存突增，最终触发 OOM、持久化失败，甚至被系统杀掉。

先看主从复制。主节点为了支持从节点同步，会维护 **replication backlog**、客户端输出缓冲区，以及主从网络抖动时的数据积压。这部分内存不是业务 key，但必须占用。尤其从节点重连、网络闪断、短时间积压增大时，这块内存会明显膨胀。

再看持久化。无论是 RDB 还是 AOF rewrite，本质上都会触发 **fork 子进程**。fork 本身虽然不是立刻复制整份内存，但它会带来页表复制成本，更关键的是后续父进程继续处理写请求时，会触发 **写时复制（COW）**。也就是说，原本父子共享的内存页，只要父进程改了，就要额外拷贝一份，这会导致实际内存瞬时上涨。写流量越大、脏页越多，COW 带来的额外内存就越明显。

如果同时存在主从和持久化，风险会叠加。比如主库正在做 RDB/AOF rewrite，这时业务还有持续写入，从库又在同步，那么 **复制缓冲、AOF 重写缓冲、COW 内存增长** 会一起吃内存。此时如果 Redis 平时就把内存打得很满，基本没有缓冲区，一波流量上来就可能把机器顶爆。

另外还不能忽略 **内存碎片**。Redis 申请到的 RSS 往往大于真正业务数据占用，碎片率高时，看起来还有空间，实际上可用余量已经不多。到了 fork 或同步时，这部分隐性占用会进一步放大风险。

所以结论就是：**主从 + 持久化场景下，Redis 必须预留更大的安全水位，因为运行时会出现多种非业务数据内存和瞬时放大内存，不能只按 key/value 数据量来算容量。** 面试里再补一句就很完整：预留内存本质上是在防 **复制放大、COW 放大、缓冲区膨胀、碎片放大**。

# 七、线上排障与生产事故类

## 1. Redis QPS 下降，你会从哪些维度排查？

我会按 **客户端、网络、Redis 实例本身、命令模型、内存与持久化、主从复制、系统资源** 这几个维度排查。

先看 **客户端侧**。确认是不是业务请求量本身下降，还是 Redis 真处理慢了。要看连接池有没有打满、有没有大量短连接、超时配置是否过小、是否出现重试风暴、pipeline 是否失效、慢客户端是否把 Redis 拖慢。很多时候看起来像 Redis QPS 下降，其实是客户端拿不到连接或者请求在业务线程池里堆住了。

再看 **网络层**。检查应用到 Redis 之间有没有网络抖动、丢包、延迟升高、带宽打满，尤其跨机房、跨可用区时更常见。还要看是否出现网卡拥塞、连接重传、容器网络抖动，因为 Redis 本身很轻，一旦网络出问题，QPS 和 RT 往往会一起恶化。

然后看 **Redis 实例运行状态**。重点关注 `connected_clients`、`blocked_clients`、`instantaneous_ops_per_sec`、`rejected_connections`、`used_cpu_sys`、`used_cpu_user`、`latency`、`slowlog`。如果 blocked clients 增多，说明可能有阻塞命令；如果 slowlog 里开始出现大命令、聚合命令、Lua 脚本执行过长，那很可能就是直接原因。

再看 **命令与数据模型**。排查是不是出现了 bigkey、热 key、O(N) 命令、全量扫描类命令，比如 `keys`、大范围 `hgetall`、`smembers`、`lrange 0 -1`、大 Lua 脚本等。Redis 是单线程执行命令，任何慢命令都会直接拉低整体吞吐。还要看是否有突发热 key，把单核打满。

接着看 **内存与淘汰**。如果内存接近 `maxmemory`，频繁触发淘汰，QPS 往往会下降，延迟会上升。还要看是否碎片率过高、是否频繁主动过期清理、是否有大量 key 同时过期，导致 CPU 被回收逻辑吃掉。

再看 **持久化影响**。如果正在做 RDB 或 AOF rewrite，要关注 fork 耗时、COW 内存放大、磁盘 IO 是否打满。AOF 如果刷盘压力大，也会拖慢 Redis。很多线上 QPS 下降，其实是持久化时机撞上高峰流量。

然后排查 **主从复制**。看是否有从库重同步、复制积压变大、输出缓冲区膨胀。主节点如果既要处理业务流量，又要承担主从同步和持久化，吞吐会明显下降。

最后看 **宿主机资源**。包括 CPU 是否被打满，尤其 Redis 单核是否 100%；内存是否紧张；磁盘 IO 是否高；是否发生 swap；容器 CPU limit 是否被限流；NUMA、虚拟化噪音邻居问题也要考虑。Redis 最怕 swap，一旦发生，QPS 通常会断崖式下降。

标准落地上，我一般会这样收束：**先确认是流量问题还是处理能力问题，再看慢命令/热 key，再看内存淘汰与持久化，再看主从复制和机器资源。** 这是排 Redis QPS 下降最常见也最有效的路径。

## 2. Redis RT 飙高，你会优先怀疑哪些问题？

我会优先怀疑这几类问题：**慢命令 / 大 key、热 key、网络抖动、内存压力、持久化影响、主从复制干扰、客户端连接池问题、宿主机资源异常**。

第一优先通常是 **慢命令和大 key**。因为 Redis 是单线程处理命令，只要有 `keys`、大范围 `hgetall`、`smembers`、超大 `lrange`、大 Lua 脚本这类命令进来，其他请求就都要排队，RT 会立刻被拉高。bigkey 读写、删除大 key 也很容易造成瞬时阻塞。

第二个高频原因是 **热 key**。某一个 key 被高并发集中访问，会把 Redis 单核打满，即使 QPS 总量不算特别大，RT 也会明显上升。尤其秒杀、排行榜、全局配置、爆款详情这类场景很常见。

第三个要怀疑的是 **网络问题**。比如应用到 Redis 之间网络抖动、丢包、重传、带宽打满，或者跨机房访问导致时延突然变大。这个时候 Redis 本身可能没慢，但业务看到的 RT 已经飙高了。

第四个是 **内存接近上限**。如果频繁触发淘汰、过期清理压力变大、碎片率偏高，Redis 会把更多 CPU 花在内存管理上，导致请求处理变慢。大量 key 同时过期也会造成 RT 抖动。

第五个是 **持久化影响**。如果刚好在做 RDB snapshot 或 AOF rewrite，fork 和写时复制会带来额外开销；如果 AOF 刷盘压力大，磁盘 IO 抖动也会间接影响 RT。

第六个是 **主从复制干扰**。比如从库重同步、复制 backlog 增大、输出缓冲区膨胀，主节点除了处理业务请求，还要处理复制流量，RT 往往会上升。

第七个是 **客户端问题**。比如连接池耗尽、大量新建连接、线程池阻塞、超时后重试风暴、pipeline 使用不当，这些都会让业务侧感觉 Redis RT 很高，但根因不一定在 Redis 服务端。

最后还要看 **机器资源**。重点看 CPU 单核是否打满、是否发生 swap、内存是否紧张、磁盘 IO 是否异常、容器是否被 CPU limit 限流。Redis 对这些系统层问题非常敏感。

面试里可以收一句：**Redis RT 飙高，优先排查慢命令 / bigkey / 热 key，其次看网络、内存淘汰、持久化、主从复制，再看客户端和宿主机资源。**

## 3. 如何排查 hot key？如何排查 big key？

排查 hot key，核心看 **是不是少数 key 承担了异常高的访问流量**。常见做法是先从业务现象入手：如果 Redis CPU 单核打满、QPS 不算特别夸张但 RT 很高、某些接口在高峰期异常抖动，就要优先怀疑 hot key。然后结合监控看调用维度，比如哪个接口、哪个缓存前缀、哪个业务场景在峰值时段最明显。再往下可以用 Redis 自带能力辅助判断，例如开启 `redis-cli --hotkeys` 去抽样分析热点 key，但这个前提是实例配置了 LFU/LRU 相关统计能力，而且更适合辅助定位，不是百分百准确。线上更常见的是在客户端埋点统计 key 访问次数，按 key 前缀、模板 key、具体 key 做 topN 聚合，这样最容易和业务接口对应上。也可以看代理层、网关层、缓存 SDK 日志，统计哪些 key 被高频命中。生产里最靠谱的方法通常不是只靠 Redis 端，而是 **业务埋点 + Redis 指标 + 接口流量** 联合判断。

排查 big key，核心看 **是不是单个 key 占用空间特别大，或者单次读写元素特别多**。Redis 里 big key 不只是“value 字节数大”，还包括集合类 key 元素数量过多，比如一个 hash 几十万 field，一个 zset 几百万成员。排查时可以先用 `redis-cli --bigkeys` 做全库抽样扫描，快速找出不同数据类型里体积最大的 key；如果 Redis 版本支持，也可以用 `redis-cli --memkeys` 看内存占用更直观。针对单个 key，可以用 `MEMORY USAGE key` 看大致内存占用；集合类型再结合 `HLEN`、`LLEN`、`SCARD`、`ZCARD` 看元素数量。业务侧如果某些接口一查 Redis 就慢，而且 slowlog 里经常出现大范围 `hgetall`、`smembers`、`zrange`、`lrange`，通常也说明背后有 big key 或“大集合一次性读取”问题。

两类问题的排查思路其实不同。**hot key 关注“访问频率异常高”**，重点看 top key、流量分布、CPU 抖动；**big key 关注“单个 key 体积异常大”**，重点看内存占用、元素数量、慢命令和网络包大小。hot key 不一定大，可能只是一个很小的字符串被疯狂访问；big key 也不一定热，可能平时访问不多，但一读就把 Redis 卡住。

线上排查时还要注意两个生产级细节。第一，不要轻易用 `KEYS *` 这类命令扫描生产库，容易把 Redis 打挂，优先用 `SCAN`、`--bigkeys`、`--hotkeys` 这类渐进式方式。第二，最好把排查建立在“前缀规范化”基础上，例如 key 设计成 `业务:子业务:对象ID`，否则即使查到热点 key，也很难快速映射回具体业务。

小结一下：**hot key 用访问分布来找，big key 用空间占用和元素规模来找；前者偏流量问题，后者偏数据模型问题。**

## 4. Redis CPU 飙高可能有哪些原因？

Redis CPU 飙高，优先怀疑这几类：**慢命令 / O(N) 命令、hot key、大量过期 key 清理、内存淘汰压力、big key 读写、大量连接或频繁建连、Lua 脚本执行过重、持久化或主从复制带来的额外开销**。

最常见的是 **慢命令和高复杂度命令**。比如 `keys`、`sort`、大范围 `hgetall`、`smembers`、`zrange`、`lrange 0 -1`，这些命令本身就会消耗大量 CPU。Redis 是单线程执行命令，只要某些命令太重，就会把主线程打满。

第二类是 **hot key**。某一个 key 被超高并发集中访问，会导致 Redis 单核 CPU 很快被打满。即使整体 QPS 不算夸张，只要访问过于集中，也会出现 CPU 飙高和 RT 抖动。

第三类是 **big key 相关操作**。比如超大的 hash、set、zset，被一次性读取、删除、序列化，都会造成 CPU 突增。尤其删除大 key，如果不是异步删除，影响会更明显。

第四类是 **过期删除和内存淘汰**。如果大量 key 在同一时间过期，或者 Redis 已经接近 `maxmemory`，开始频繁淘汰 key，Redis 会花不少 CPU 做采样、过期检查和淘汰处理，CPU 很容易升高。

第五类是 **Lua 脚本过重**。Lua 虽然能保证原子性，但如果脚本里处理的数据量太大、循环太多，本质上还是阻塞 Redis 主线程，CPU 会明显上升。

第六类是 **大量连接问题**。比如连接池配置不合理、频繁创建和关闭连接、大量客户端同时连入，Redis 会在连接处理上增加额外开销。虽然这通常不是最大头，但高峰期也很常见。

第七类是 **持久化和主从复制的间接影响**。比如 RDB/AOF rewrite 期间，虽然主要不是主线程一直算 CPU，但 fork、写时复制、复制流量处理，都会让整体资源变紧，进而放大 CPU 压力。主从同步时如果数据量大，也会明显影响主节点。

最后还要考虑 **业务流量本身上涨**。如果请求量突然变大，哪怕没有明显慢命令，Redis CPU 也可能直接被正常流量打满。所以要先区分是“命令变重了”，还是“流量变大了”。

面试里可以收一句：**Redis CPU 飙高，最先排查慢命令、hot key、big key，其次看过期淘汰、Lua、连接、持久化和主从复制。**

## 5. Redis 内存持续上涨，你怎么判断是业务增长、过期不及时、big key，还是客户端问题？

先说结论：这种问题不能只看一个指标，要按 **“总量趋势 + key 数量 + 过期情况 + 大对象分布 + 连接与缓冲区”** 这几个维度一起判断。通常我会先分清：**是业务数据真的变多了，还是 Redis 运行时内存膨胀了。**

如果是 **业务增长**，典型特征是：`used_memory` 持续上涨的同时，`dbsize` 或 key 总数也在增长，而且增长趋势和业务量、QPS、新增用户数、订单量这些指标基本一致。再往下看 key 前缀分布，会发现是某一类正常业务 key 在持续增加，比如订单缓存、会话缓存、排行榜、明细聚合结果等。这种场景下，本质不是故障，而是容量规划不足，重点是看增长是否符合预期，TTL 是否合理，是否需要分片、扩容或归档。

如果是 **过期不及时**，常见现象是：很多 key 明明设置了 TTL，但内存下降不明显，或者业务低峰过后内存也回不来。这时要重点看 `expired_keys` 增长是否偏慢，抽样检查 key 的 TTL 分布，看看是不是有大量 key 虽然设置了过期时间，但因为访问少，只能依赖定期删除，导致过期 key 长时间堆积。还有一种很常见的情况是大量 key 在同一时间集中到期，但 Redis 没法瞬时全部清掉，于是内存表现为“该降没降”。这类问题本质上是 **过期机制回收不够及时**，不是没有过期。

如果是 **big key**，通常不是 key 数量明显增长，而是少数 key 把内存吃上去了。表现上经常是：`used_memory` 涨得很快，但 `dbsize` 增长不明显；或者慢日志里开始出现大范围集合读取；再或者网络流量、命令耗时突然变大。这时就要查大对象分布，比如看哪些 string 特别大，哪些 hash/set/zset/list 元素数量异常多。big key 的特点是 **不是“多”，而是“单个特别大”**，所以总 key 数不一定异常，但内存涨得会很明显。

如果是 **客户端问题**，要重点怀疑不是业务数据本身变多，而是 **连接缓冲区、输出缓冲区、查询缓冲、异常连接堆积** 把内存占上去了。典型现象是：`used_memory` 上涨，但按业务 key 去看又找不到明显增长点；这时要看 `connected_clients`、各类 client buffer、pubsub buffer、replication buffer、master/slave output buffer 是否异常。如果存在慢客户端、大量积压连接、订阅消费不及时、主从同步缓冲膨胀，Redis 的内存也会持续上涨，而且这部分不是业务 key，占用却很可观。尤其在主从复制、Pub/Sub、大量 pipeline 返回堆积时很常见。

实际排查时，我一般这样收口：

第一步看 `**used_memory` 和 `used_memory_rss`**，先判断是业务内存增长还是 RSS/碎片增长。
第二步看 **key 总量和前缀分布**，判断是不是业务自然增长。
第三步看 **TTL 和 `expired_keys`**，判断是不是过期回收不及时。
第四步看 **big key / 大集合分布**，判断是不是少量大对象吃内存。
第五步看 **clients / replication / output buffer**，排除是不是客户端和复制缓冲问题。

面试里可以直接总结成一句：**业务增长看 key 总量和业务趋势，过期不及时看 TTL 与 `expired_keys`，big key 看单 key 内存和集合规模，客户端问题看连接数和各种 buffer 占用。**

## 6. Redis 阻塞可能由哪些命令引起？

Redis 阻塞，核心上是 **某些命令执行时间过长，卡住了主线程**。因为 Redis 处理命令是单线程模型，所以只要一个命令很重，后面的请求都得排队。

最常见的是 **全量扫描或高复杂度命令**，比如 `KEYS *`、`SORT`、`SMEMBERS`、`HGETALL`、`LRANGE 0 -1`、大范围 `ZRANGE`。这类命令的问题不是不能用，而是当 key 很大、元素很多时，会一下子遍历大量数据，直接把 Redis 卡住。

第二类是 **大 key 的删除和改写命令**。比如对超大 `hash/set/list/zset` 执行 `DEL`，可能会一次性释放大量内存，造成明显阻塞。还有对大集合做 `SUNION`、`ZUNIONSTORE`、`SDIFF` 这类聚合计算，也可能把 CPU 打高，拖慢整个实例。

第三类是 **Lua 脚本**。`EVAL` / `EVALSHA` 本身是原子执行的，脚本执行期间 Redis 不会处理其他命令。所以如果脚本里循环很多、处理的数据量很大，或者脚本逻辑本身过重，就会把 Redis 阻塞住。

第四类是 **事务里塞了重命令**。`MULTI/EXEC` 本身不是问题，但如果事务里包含大量重操作、大 key 操作、批量集合操作，执行时一样会长时间占住主线程。

第五类是 **阻塞型命令本身**，比如 `BLPOP`、`BRPOP`、`BZPOPMIN`、`XREAD BLOCK`。这类命令是“对客户端连接阻塞等待数据”，不是把整个 Redis 实例卡死。面试里要分清：它们会阻塞当前客户端，不一定等于阻塞整个 Redis 主线程。

第六类是 **持久化相关的间接阻塞**。比如执行 `SAVE` 会同步做 RDB 持久化，这是明确的重阻塞命令；相比之下 `BGSAVE` 是后台做，不会像 `SAVE` 那样直接长时间卡住主线程。AOF rewrite、RDB fork 虽然主要不是命令级阻塞，但在某些时刻也会带来延迟抖动。

所以标准回答可以总结为：**最容易引起 Redis 阻塞的是 O(N) 命令、大 key 操作、Lua 脚本、重事务，以及像 `SAVE` 这样的同步持久化命令。** 其中 `BLPOP` 这类阻塞命令要特别说明，它主要是阻塞客户端连接，不是把整个 Redis 服务停住。

## 7. `KEYS`、`FLUSHALL`、`MONITOR` 为什么在线上危险？

`KEYS` 危险在于它是 **一次性全量扫描**，时间复杂度是 O(N)。当线上 key 数量很大时，执行 `KEYS *` 会长时间占用 Redis 主线程，导致其他正常请求排队，轻则 RT 飙高，重则实例看起来像“卡死”。所以线上查 key 一般用 `SCAN` 做渐进式遍历，而不是用 `KEYS`。

`FLUSHALL` 危险在于它会 **清空整个 Redis 的所有库数据**。这不是性能问题，而是直接的数据级事故。一旦在线上误执行，缓存、会话、分布式锁、配置缓存、热点数据可能瞬间全没，业务会大量回源数据库，严重时把 MySQL 和下游服务一起打崩。即使某些版本支持异步清理，本质风险也没有变：它依然是“全库清空”这个高危操作。

`MONITOR` 危险在于它会 **实时输出 Redis 收到的每一条命令**。线上流量一大，这个命令会带来明显的额外开销：Redis 要持续复制命令流给监控连接，既消耗 CPU，也消耗网络带宽。如果实例本来就忙，再开 `MONITOR` 很容易雪上加霜。而且它输出的是全量请求细节，还可能暴露敏感数据，所以线上只能非常谨慎地短时间使用，通常不作为常规排查手段。

小结一下：`**KEYS` 会阻塞主线程，`FLUSHALL` 会清空全库数据，`MONITOR` 会放大运行时开销并泄露全量命令流**，所以这三个命令在线上都属于高危操作。

## 8. `SCAN` 为什么比 `KEYS` 更适合线上？它有没有副作用？

`SCAN` 比 `KEYS` 更适合线上，核心原因是：**它不是一次性把全量 key 都扫出来，而是分多次、渐进式遍历**。这样单次执行时间短，不会像 `KEYS` 那样一次 O(N) 扫描把 Redis 主线程长时间卡住，所以对线上实例更友好。

`KEYS` 的问题在于它会立刻遍历整个数据库，key 一多就容易造成明显阻塞；而 `SCAN` 是基于游标的增量迭代，每次只返回一部分结果，业务或运维脚本可以边扫边处理，降低对 Redis RT 和 QPS 的冲击。这就是它更适合线上排查和批量治理的根本原因。

但 `SCAN` 不是没有副作用，也不是“绝对安全”。

第一，它是 **弱一致性遍历**。在扫描过程中，如果有新的 key 写入、旧 key 删除，返回结果可能出现 **重复** 或 **遗漏**。所以 `SCAN` 适合做统计、排查、渐进式处理，不适合要求严格精确一次性的场景。

第二，`SCAN` 虽然单次开销小，但如果你一次扫太快、`COUNT` 设太大、或者边扫边做重操作，整体还是可能给 Redis 带来不小压力。也就是说，`SCAN` 只是把风险从“一次性大阻塞”变成了“可控的小步遍历”，不是完全零成本。

第三，`SCAN` 返回数量 **不是严格等于 `COUNT`**。`COUNT` 更像一个 hint，不是硬保证，所以不能拿它当精确分页工具。面试里这一点经常会追问。

第四，如果你在 `SCAN` 的同时，对扫描结果立刻做 `DEL`、`HGETALL`、`SMEMBERS` 这类重操作，真正危险的可能不是 `SCAN` 本身，而是你后续对结果的处理。

所以标准回答可以总结成一句：`**SCAN` 比 `KEYS` 更适合线上，是因为它采用游标式增量遍历，单次阻塞小；但它有重复、遗漏、结果不稳定的问题，而且如果扫描过快或后续处理过重，依然可能影响线上性能。**

## 9. Redis 慢查询怎么排查？`slowlog` 能看到什么，看不到什么？

排查 Redis 慢查询，通常我会按 **“先看现象，再看慢日志，再结合命令与数据模型定位”** 这个顺序来做。

第一步先确认是不是 Redis 本身真的慢。要结合业务 RT、Redis QPS、CPU、网络、连接数一起看。因为很多“Redis 慢”其实是客户端连接池满了、网络抖动、线程池阻塞，不一定是 Redis 命令执行慢。

第二步看 `slowlog`。`slowlog` 记录的是 **执行时间超过阈值的命令**，可以先用 `SLOWLOG GET` 看最近慢命令，再看是不是某类命令反复出现，比如 `HGETALL`、`SMEMBERS`、`KEYS`、`EVAL`、`ZRANGE`、`DEL` 之类。如果慢日志里反复出现某个 key 或某类前缀，基本就能顺着业务往下查是 big key、热 key，还是命令用法不当。

第三步结合数据模型继续定位。比如：
如果慢的是 `HGETALL`、`SMEMBERS`、`LRANGE 0 -1`，通常要怀疑大集合一次性读取；
如果慢的是 `DEL`，要怀疑 big key 删除；
如果慢的是 `EVAL`，要怀疑 Lua 脚本逻辑太重；
如果慢的是 `KEYS`、`SORT` 这类命令，就是典型高复杂度命令在线上误用。

第四步再结合实例状态看是不是“命令本身不重，但环境拖慢了”。比如内存接近上限导致淘汰频繁、持久化期间 fork/COW 抖动、主从同步带来额外压力、CPU 单核打满，这些都可能让慢命令变多。

`slowlog` 能看到的，主要有这几类信息：**慢命令的执行时间、执行时间点、命令内容、部分参数、客户端来源信息**。它适合用来回答“到底是哪些命令执行慢了”。

但 `slowlog` 也有明显看不到的东西。

第一，它看到的是 **命令在 Redis 服务端真正执行的耗时**，**看不到网络耗时**。也就是说，应用到 Redis 之间网络抖动、丢包、排队等待，这些不在 `slowlog` 里。

第二，它 **看不到客户端排队时间**。比如连接池拿连接很慢、请求在业务线程池里堆积、pipeline 返回处理慢，这些都不算 Redis 命令执行时间。

第三，它 **看不到所有慢请求**，只看得到 **超过阈值** 的那部分，而且日志数量有限，旧记录会被覆盖。所以它不是完整审计日志。

第四，它 **不直接告诉你根因**。它只能告诉你“哪个命令慢了”，但为什么慢，还得结合 big key、hot key、CPU、内存、持久化、主从复制去判断。

面试里可以直接总结成一句：`**slowlog` 适合定位“Redis 服务端哪些命令执行慢”，但看不到网络耗时、客户端排队耗时，也不能单独说明根因。**

## 10. AOF 重写 / RDB fork 导致 RT 抖动，你怎么识别？

先看结论：这类问题的识别关键是 **“RT 抖动时间点，是否和 `bgrewriteaof` / `bgsave` / fork 耗时峰值重合”**。如果 Redis 在某个时间段突然 RT 升高、QPS 下降，但业务流量并没有明显突增，同时实例又正好发生了 AOF 重写或 RDB 快照，那就要优先怀疑是 fork 和写时复制带来的抖动。

排查时第一步看 Redis 的持久化状态指标。重点看 `INFO persistence` 里的 `rdb_bgsave_in_progress`、`aof_rewrite_in_progress`、`latest_fork_usec`。如果 RT 抖动时，这几个指标显示后台持久化正在进行，或者 `latest_fork_usec` 明显偏高，基本就对上了。因为 fork 虽然是子进程做持久化，但 fork 这个动作本身会让主线程短暂卡顿，内存越大、页表越大，这个卡顿越明显。

第二步看现象是不是符合持久化抖动特征。典型特征是：**RT 突然毛刺升高，不一定持续很久，但会周期性出现**；有时候 QPS 同时掉一下；CPU 不一定暴涨得特别夸张，但系统层面的内存、page fault、磁盘 IO 可能会变差。如果是 fork 影响，常常是某个瞬间抖一下；如果是 AOF rewrite / RDB 期间叠加写流量大，抖动可能会持续更久，因为后面还有 **COW 写时复制** 成本。

第三步看时间点是否有规律。如果 RT 抖动总是在某些固定时段发生，比如凌晨定时快照、业务低峰触发自动 rewrite、或者 AOF 文件达到阈值后触发重写，那就更像持久化导致，而不是业务随机流量问题。

第四步结合系统指标确认。比如看宿主机是否在抖动时出现：
内存使用突增
page fault 增多
磁盘 IO 升高
CPU sys 占比上升
这些都很符合 fork + COW + rewrite 的特征。尤其是写流量大的时候，父进程不断修改内存页，会导致写时复制额外占内存和 CPU，RT 就容易持续抖。

第五步做排除法。如果 slowlog 没有明显慢命令、没有 hot key、没有 big key、网络也没异常，但 RT 还是在持久化时段规律性变差，那基本就能把根因收敛到 AOF rewrite / RDB fork。

所以标准回答可以收束为一句：**通过 `INFO persistence` 看后台持久化状态和 `latest_fork_usec`，再把 RT 抖动时间点与 `bgsave` / `bgrewriteaof` 的发生时间做对齐，如果两者明显重合，再结合内存、page fault、磁盘 IO 变化，就能较准确识别是 AOF 重写或 RDB fork 导致的抖动。**

## 11. 主从延迟很大时，你会怎么排查？

先说结论：我会按 **网络链路、主库负载、复制积压、从库负载、全量/增量同步状态、持久化与大命令干扰** 这几个方向排查，因为主从延迟本质上就三种可能：**主库发不出来、链路传不过去、从库消费不过来**。

第一步先确认延迟现象是不是持续性的。看 `INFO replication`，重点看从库是否一直落后，还是偶发抖动；看 `master_link_status` 是否正常，`master_last_io_seconds_ago` 是否持续变大，`slave_repl_offset` 和 `master_repl_offset` 差距是不是越来越大。如果 offset 差距持续扩大，说明从库明显追不上。

第二步查 **网络链路**。主从延迟很大，最先要怀疑网络抖动、带宽打满、丢包、跨机房延迟高。因为复制本质就是主库不断把写命令流发给从库，网络一差，延迟马上上来。尤其跨地域、跨可用区部署时，这个问题非常常见。

第三步查 **主库是不是太忙**。如果主库 CPU 很高、慢命令很多、hot key 明显、big key 操作频繁，主线程自己都很忙，就可能影响复制流发送。再看是否正在做 RDB、AOF rewrite、过期清理、内存淘汰，这些都会放大主库压力。

第四步查 **复制 backlog 和同步状态**。如果从库只是短暂掉线，理论上可以走增量同步；但如果 backlog 不够，或者断线时间太长，Redis 就会退化成全量同步。全量同步会触发主库 `bgsave`，然后传 RDB 给从库，这个过程很重，一旦开始，全链路延迟都会变大。所以要看是不是频繁发生 full resync。

第五步查 **从库自己是不是处理不过来**。比如从库 CPU 高、磁盘 IO 高、内存紧张、正在重写 AOF、正在加载 RDB，或者从库本身还承担查询流量，这都会导致它消费主库复制流变慢。很多时候不是主库发慢了，而是从库应用复制命令跟不上。

第六步查 **是否有大命令、大 key、批量写入**。如果主库突然来了大事务、大 Lua、大 key 写入、批量删除、批量集合操作，复制流会瞬间变大，从库应用这些命令也会更慢，延迟会明显拉大。

第七步查 **从库配置和机器资源**。比如 `replica-read-only` 不是问题本身，但如果从库被拿去跑复杂查询、跑扫描命令，也会拖慢复制。还要看机器是否发生 swap、磁盘是否抖动、容器 CPU limit 是否过紧。

标准回答可以收束成一句：**主从延迟大，就按“主库写得出吗、网络传得动吗、从库跟得上吗”来排查；具体落到网络、主库负载、backlog 是否足够、是否退化全量同步、从库资源是否吃满、大命令和持久化是否干扰。**

## 12. Redis 集群某个节点热点特别高，怎么做流量打散？

先说结论：如果 Redis 集群某个节点热点特别高，核心思路不是盲目扩容，而是 **先判断是 hot key 问题，还是 hot slot 问题，再分别做“key 打散、读流量分摊、本地缓存兜底、业务拆分”**。

如果是 **单个 hot key**，最常见的做法是 **副本 key 打散**。比如原来是一个 `product:1001`，可以扩成多个副本：`product:1001:1`、`product:1001:2`、`product:1001:3`，写的时候同时写多份，读的时候按随机或一致性策略读其中一个。这样本来集中打到一个 key 的请求，就被分摊到多个 key 上了。这是最直接的流量打散方式，但代价是写放大、更新复杂度上升，而且要处理多副本一致性。

如果热点主要是 **读多写少**，更稳的办法通常是 **本地缓存 + Redis**。把超热点数据先放到应用节点本地缓存里，比如 Caffeine，Redis 只做二级缓存。这样很多请求直接在 JVM 内存命中，不再全部打到 Redis。同一个热点 key 即使再热，也不会把 Redis 单点打满。这个方案在线上非常常见，特别适合商品详情、配置、字典、医院科室信息这类更新不频繁的数据。

如果是 **集群槽位热点**，就不是单 key 问题，而是很多 key 因为命名或 hash tag 设计不合理，集中落在同一个 slot / 节点上。这时要做的是 **重新设计 key 分布**，避免大量业务 key 因为相同前缀、相同 hash tag 被强制路由到同一节点。比如不要为了事务或 Lua 方便，把本来可以分散的 key 全塞进同一个 `{tag}` 里，否则天然制造热点节点。

如果业务允许，还可以做 **业务维度拆分**。比如按地区、医院、租户、活动场次，把原本全局共享的热点数据拆成多个局部热点，让不同用户流量命中不同 key，而不是所有人都打一个全局 key。这个本质上也是打散，只不过是在业务建模层处理。

对于极端热点，还可以加 **前置限流 / 请求合并 / 异步刷新**。比如缓存失效瞬间，不让所有请求同时回源重建，而是只让一个线程加载，其他线程等待或返回旧值；或者通过网关限流，避免无意义突发流量把 Redis 打穿。

所以可以总结成一句：**单 key 热点，用多副本 key、本地缓存、请求合并；slot 热点，用重新散列和调整 key 设计；全局热点，用业务拆分和前置限流。** 真正落地时，最常见也最有效的组合通常是 **本地缓存 + Redis 多副本 key 打散**。

## 13. 线上误删 key、批量 key 操作失误、热点 key 打爆，你分别怎么止血？

**误删 key**，第一优先不是马上“恢复全部”，而是先 **止住继续扩散**。如果是脚本、任务、人工命令导致的，立刻停掉对应任务、下线脚本、回收高危权限，避免继续删。然后看删掉的是缓存数据、会话数据，还是偏状态型数据。
如果只是普通缓存，止血重点是 **防止数据库被打穿**，做法通常是临时限流、降级、本地缓存兜底、热点数据预热，把最核心的 key 先回填。
如果删的是会话、分布式锁、业务状态，就要立刻评估业务影响面，必要时先降级部分功能，避免状态错乱扩大。
如果有 RDB/AOF 且数据价值高，可以评估从备份或从库恢复，但线上一般不会直接全量回灌，而是 **按业务优先级恢复核心 key**，不然恢复过程本身也可能把实例打死。

**批量 key 操作失误**，比如误执行大范围 `DEL`、`EXPIRE`、`RENAME`、批量扫描删除，这类问题的止血核心是 **立刻停操作 + 降低实例冲击**。如果任务还在跑，马上终止脚本或下线发布；如果是应用代码缺陷，先回滚版本。
然后判断当前 Redis 是“数据被改坏了”，还是“实例被批量操作打慢了”。
如果是性能抖动，先暂停一切非核心流量，必要时临时摘流或切只读，避免 Redis 被进一步拖垮。
如果是数据被批量改错，例如大量 TTL 被改短、大量 key 被误删，要尽快锁定影响前缀和范围，优先恢复核心业务 key。
这种场景下，最怕一边排查一边继续跑新的批处理，所以止血重点永远是 **先让错误操作停下来**。

**热点 key 打爆**，第一优先是 **把流量从 Redis 节点上卸下来**。最常见的止血动作是：
先在应用侧加 **本地缓存** 或临时静态缓存，让一部分读请求不再直打 Redis；
再做 **限流、熔断、降级**，比如非核心请求直接降级返回默认值；
如果是读多写少的热点 key，可以临时做 **多副本 key 打散**，把一个 key 拆成多个副本，读流量随机分摊；
如果是缓存击穿叠加热点，还要加互斥重建、逻辑过期或旧值兜底，避免请求同时回源数据库。
如果已经是单节点过热，必要时可以做流量切分、业务降载，避免把整个 Redis 集群拖崩。

这三类问题的共同原则是：**先止扩散，再保核心链路，最后再做恢复和修复。**
误删 key，重点是防回源雪崩；
批量操作失误，重点是立刻停错操作；
热点 key 打爆，重点是把流量快速打散和降下来。

# 八、和 MySQL / MQ / 业务一致性结合类

## 1. 为什么不能把 Redis 当数据库来设计核心账务系统？

不能，因为核心账务系统最看重的是 **强一致性、事务完整性、持久化可靠性、可审计性、可恢复性**，而 Redis 的设计目标主要是 **高性能内存访问**，不是为核心账务这种强约束场景设计的。

第一，Redis 的事务能力不适合账务系统。它的 `MULTI/EXEC` 不是传统数据库那种严格 ACID 事务，失败回滚能力有限，也不支持复杂隔离级别，做多表、多账户、多步骤扣减时，很难像 MySQL 那样稳定保证严格一致性。

第二，Redis 的持久化机制决定了它更适合“高性能缓存/状态存储”，不适合做账务事实来源。无论是 RDB 还是 AOF，本质上都存在数据丢失窗口、重写风险、主从切换一致性风险。账务系统要求的是“每一笔都不能丢、不能重、不能乱”，而 Redis 很难天然满足这个级别。

第三，Redis 不擅长复杂查询和审计追溯。账务系统通常需要余额、流水、对账、补单、审计、时间点回放、条件检索，这些能力是关系型数据库强项。Redis 更像 KV/内存结构存储，做账务主存会让查询、对账、追责变得非常痛苦。

第四，Redis 在主从复制和故障切换下，天然是 **最终一致** 倾向，不是强一致。主节点刚写成功但还没同步到从节点就宕机，切换后就可能丢数据。对于缓存可以接受，但对于“扣了一笔钱却没账”这种场景是不能接受的。

第五，账务系统通常需要非常稳定的约束能力，比如唯一约束、外键语义、精确事务边界、幂等落库、对账补偿基础，这些更适合放在 MySQL/PostgreSQL 这类关系型数据库里。Redis 可以辅助做余额缓存、幂等标记、限流、防重、流水号段，但不应该做账务主账本。

所以标准结论是：**Redis 可以做账务系统的加速层、状态辅助层、幂等与防重组件，但不能作为核心账务数据的最终可信存储。核心账务主存应该放在支持强事务和可靠持久化的关系型数据库中。**

## 2. Redis 做库存扣减有哪些风险？如何避免超卖？

Redis 做库存扣减的风险，核心在于：**它很快，但天然不是强事务库存系统**。如果只靠 Redis 扣库存，常见风险有这几类。

第一是 **并发超卖**。如果扣减逻辑不是原子操作，比如先查库存再减库存，在高并发下多个请求可能同时看到还有库存，最后把库存扣成负数。这个问题通常出在把“读库存”和“扣库存”拆成多条命令执行。

第二是 **Redis 成功、数据库失败**。比如 Redis 先扣了库存，但订单落库失败、支付失败、消息发送失败，结果就是缓存里的库存少了，但真实业务单没成，造成库存不一致。

第三是 **数据库成功、Redis 失败**。比如订单已经创建成功，但 Redis 没扣成功或回补失败，也会造成缓存库存和真实库存不一致。

第四是 **主从切换或持久化丢失**。Redis 扣减成功后，如果还没同步到从库主库就挂了，切主后这次扣减可能丢失。对于秒杀库存这种强敏感数据，这是明显风险。

第五是 **重复请求和重复扣减**。同一个用户重试、MQ 重投、接口超时重试，如果没有幂等控制，可能把一笔请求扣多次。

第六是 **回滚和补偿复杂**。比如下单占库存后未支付，要回补；支付成功后取消订单，也要回补。如果没有清晰的预扣、确认、释放机制，库存很容易越改越乱。

避免超卖，最核心的是这几条。

第一，**扣减动作必须原子化**。常见做法是用 Lua 脚本把“判断库存是否足够 + 扣减库存”放在一条脚本里执行，避免并发下先查后改导致超卖。

第二，**Redis 只做预扣或快速闸门，不做最终事实库存**。真正可信的库存还是要落到 MySQL 这类关系库里。比较稳的做法是：Redis 先做快速扣减拦截流量，订单创建后异步落库，数据库层再做最终扣减校验。

第三，**数据库层仍然要有兜底约束**。比如用 `update ... set stock = stock - 1 where item_id = ? and stock > 0` 这种方式，依靠数据库原子更新保证最终不扣成负数。也就是说，Redis 可以挡流量，但最终防超卖不能只靠 Redis。

第四，**一定要做幂等**。请求号、订单号、用户 + 活动维度都可以作为幂等键，防止重复请求、重复消费导致多扣。

第五，**要有补偿机制**。下单未支付超时，要回补 Redis 和数据库库存；MQ 消费失败要重试；最终还要靠对账任务纠偏。

第六，**热点场景要控制流量**。秒杀这类场景，除了 Redis 原子扣减，还要加限流、排队、令牌桶、异步化，避免瞬时流量把 Redis 和数据库一起打穿。

标准结论可以收成一句：**Redis 扣库存的主要风险是并发超卖、缓存和数据库不一致、主从切换丢失、重复扣减和补偿复杂；避免超卖要靠 Lua 原子扣减 + 数据库最终校验 + 幂等 + 补偿对账。**

## 3. Redis 预扣库存 + MySQL 最终落单，这类最终一致性怎么设计？

标准做法是把它设计成 **“Redis 负责高并发拦截与预占，MySQL 负责最终事实落库，MQ/任务负责异步确认与补偿”** 的最终一致性方案，而不是把 Redis 当最终库存来源。

第一步是 **Redis 预扣库存**。用户下单时，先通过 Lua 脚本原子执行“校验库存是否足够 + 预扣库存 + 记录预占标记”，这里通常还要带上业务单号或请求号，避免重复预扣。Redis 这一步的目标不是形成最终订单，而是先在高并发入口把超卖拦住，把流量快速削峰。

第二步是 **异步创建订单并落 MySQL**。Redis 预扣成功后，不要在主链路里做太多重操作，通常是投递 MQ，由下游订单服务异步消费。消费时在 MySQL 里开启本地事务，完成订单创建、库存流水记录、正式库存扣减或预占记录落表。MySQL 这里才是最终可信数据源。

第三步是 **用业务状态机管理库存状态**。最稳的方式不是只有“扣了/没扣”，而是至少区分成：`预占`、`已确认`、`已释放`。
也就是：
Redis 扣掉的是“可售库存”
MySQL 记录的是这笔单当前处于预占还是最终确认
支付成功或订单确认后，把预占转正式占用
超时未支付或下单失败，则释放预占库存

第四步是 **保证幂等**。这套方案里最容易出问题的是重复请求、MQ 重投、消费者重试。所以无论 Redis 预扣、MQ 消费、MySQL 落单，都必须基于 `requestId/orderNo` 做幂等控制。否则很容易出现 Redis 扣一次、数据库扣两次，或者反过来。

第五步是 **失败补偿**。这是最终一致性的关键。
如果 Redis 预扣成功，但 MQ 投递失败，要有重试或事务消息/Outbox 保证消息最终送达。
如果 MQ 消费到了，但 MySQL 落单失败，要触发重试；重试仍失败，则把 Redis 预扣库存回补。
如果订单创建成功但用户超时未支付，要通过延迟消息或定时任务释放 Redis 和 MySQL 里的预占库存。
如果某一步出现异常不确定状态，最终靠对账任务按订单状态和库存流水做纠偏。

第六步是 **数据库层做最终兜底防超卖**。即使前面有 Redis 预扣，MySQL 最终扣减时仍然要有条件更新，例如 `where available_stock >= ?` 这类约束，防止极端情况下 Redis 与 DB 状态漂移后出现最终超卖。也就是说，Redis 负责“快”，MySQL 负责“准”。

这类方案的标准链路可以概括为：

用户请求
→ Redis Lua 原子预扣
→ 发送 MQ
→ 订单服务消费并本地事务落 MySQL
→ 成功则确认预占
→ 失败则重试/回补
→ 超时未支付走延迟释放
→ 定时对账纠偏

小结一下：**Redis 预扣库存 + MySQL 最终落单，本质是“缓存闸门 + 数据库事实 + 消息驱动补偿”的最终一致性设计。关键点不是只会扣库存，而是要把幂等、状态机、补偿、延迟释放、对账兜底一起设计完整。**

## 4. Redis 做消息队列为什么很多场景不如专业 MQ？

因为 Redis 的定位首先是 **内存 KV / 缓存系统**，消息队列能力只是“能做”，但很多关键能力不如专业 MQ 完整，尤其在 **高可靠、可堆积、可追踪、可回溯、可扩展消费** 这些场景下差距很明显。

第一，**消息可靠性不如专业 MQ 稳**。Redis 无论是 List 方案还是 Pub/Sub，天然都不是围绕“消息可靠投递”设计的。Pub/Sub 甚至是典型的“订阅者不在线就丢消息”。即使用 Stream，虽然比 List 和 Pub/Sub 强很多，但在消息持久化、故障恢复、主从切换后的可靠性保证上，仍然不如 RocketMQ、Kafka、RabbitMQ 这类专业 MQ 完整。

第二，**消费语义支持弱一些**。专业 MQ 通常对消息确认、重试、死信队列、延迟消息、顺序消息、事务消息、消费组管理这些能力支持更系统。Redis 要么没有，要么支持得没那么完整，很多都得业务自己补，工程复杂度会转移到应用层。

第三，**消息堆积能力和成本模型不一样**。Redis 是内存型系统，消息大量堆积时内存压力很大，成本高，而且容易影响原本缓存业务。专业 MQ 一般更适合承接长时间堆积、海量积压、削峰填谷这类场景，尤其 Kafka、RocketMQ 这类对磁盘顺序写和堆积处理更强。

第四，**可观测性和运维能力不如专业 MQ 完整**。专业 MQ 一般天然提供更完善的消费位点、积压监控、重试次数、死信处理、消费失败治理、消息轨迹等能力。Redis 做队列时，很多状态要自己补埋点和治理体系。

第五，**多消费者协作能力弱一些**。像广播、集群消费、顺序消费、重平衡、分区并行消费这些机制，专业 MQ 通常是体系化设计好的；Redis 做简单队列可以，但一旦进入复杂消费模型，能力边界就比较明显。

第六，**会和缓存场景互相争资源**。很多公司 Redis 主要承担缓存、分布式锁、计数器、会话等核心职责，如果再拿它承载大量消息队列流量，容易和原有业务互相影响。专业 MQ 的好处就是职责单一，不容易把缓存系统一起拖垮。

所以标准结论是：**Redis 适合做轻量、低复杂度、短链路、可容忍一定简化语义的队列；但在高可靠、高堆积、强治理、复杂消费语义场景下，通常不如专业 MQ。**
面试里再补一句就很完整：**Redis 更适合“临时能用”，专业 MQ 更适合“长期稳定上线”。**

## 5. 用 Redis Stream 做消息队列时，消费者组怎么理解？

消费者组可以理解成：**一组消费者共同消费同一条 Stream，但组内一条消息只会被其中一个消费者处理**。它的作用，本质上就是把 Stream 从“所有人都看到同一批消息”，变成“组内协同分摊消费”。

如果没有消费者组，你用普通读取方式看 Stream，更像自己去读日志；而有了消费者组后，Redis 会帮你维护这个组的消费进度，还会把消息分发给组内某个消费者，并记录这条消息当前是否已经被确认。

这里有三个关键点。

第一，**消费者组维护的是组级别消费位点**。也就是这个组读到哪里了，Redis 会记住。所以下次继续消费时，不需要自己再传上次 offset。

第二，**组内消费者是分工消费，不是广播消费**。比如一个组里有 `c1`、`c2`、`c3`，新消息进来后，会分配给其中某个消费者处理，不会每个人都处理一遍。
如果你想让多套系统都各自消费同一批消息，就应该建多个消费者组，而不是在一个组里放多个消费者。

第三，**消息消费后不是自动彻底完成，还要 ACK**。某个消费者读到消息后，Redis 会先把它放进 Pending List，表示“这条消息已经投递给某个消费者了，但还没确认处理完成”。只有业务处理成功后执行 `XACK`，这条消息才算真正消费完成。否则它会一直留在待确认列表里，后续可以被重新领取。

所以可以把消费者组理解成一句话：**它是 Redis Stream 提供的“组内分摊消费 + 消费进度管理 + 待确认机制”模型。**
面试里再补一句通常就够了：**多个消费者组之间是广播关系，单个消费者组内部多个消费者之间是竞争消费关系。**

## 6. 订单状态、支付状态这类数据，哪些适合放缓存，哪些不适合？

结论先说：**可以缓存“查询型、展示型、短暂加速型”状态；不适合只放缓存的是“最终事实型、强一致驱动型、资金结果型”状态。**

**适合放缓存** 的，通常是这几类：
一类是 **读多写少、允许短时间不绝对实时** 的状态展示数据，比如订单列表页状态文案、订单详情页聚合展示信息、支付结果页的展示字段。这类数据即使短时间有几百毫秒到几秒延迟，业务通常能接受，缓存价值很高。
另一类是 **热点查询数据**，比如某个活动订单、热门支付单、用户最近订单摘要，这类放缓存可以明显减轻数据库压力。
还有一类是 **中间态加速数据**，比如“支付处理中”“订单校验中”“待回调确认”这类短生命周期状态，可以放 Redis 做快速查询和削峰，但前提是数据库里仍然有最终状态来源。

**不适合只放缓存** 的，主要是这几类：
第一类是 **最终订单事实状态**，比如订单是否创建成功、是否已取消、是否已完成。这些状态应该以 MySQL 为准，缓存只能做加速读，不能做唯一真相源。
第二类是 **支付结果状态**，尤其是“是否支付成功”“是否已退款”“是否已结算”这类和资金有关的状态，不能只信缓存。因为这类状态要求强一致、可审计、可追溯，必须落可靠存储。
第三类是 **驱动后续核心业务流转的状态**，比如“支付成功后发货”“退款成功后回补额度”“核销成功后记账”。这类状态如果只从缓存读，一旦缓存丢失、延迟、穿透，就可能触发错误业务动作。
第四类是 **需要对账和审计的状态**，凡是后面要拿来做账务核对、投诉追踪、补偿修复的，都不能把缓存当依据。

落地上一般这样设计：
**数据库存最终事实，缓存存查询加速结果。**
更新时先改数据库，再删缓存或异步刷新缓存；
读时优先查缓存，没命中再回源数据库。
对于支付结果这类关键状态，核心链路判断要以数据库或可靠消息结果为准，缓存只用于提升查询性能，不用于做最终决策。

一句话总结：**订单状态里“展示和查询”适合缓存，“事实和资金”不适合只放缓存；支付状态尤其不能把缓存当最终依据。**

## 7. 为什么有些场景 Redis 更适合做“加速层”，而不是“真相层”？

因为 Redis 的核心优势是 **快**，而很多业务真正需要的是 **准、稳、可追溯**。所以它更适合做加速层，不适合轻易做真相层。

Redis 适合做加速层，是因为它基于内存，读写延迟低，吞吐高，非常适合承接热点查询、短时状态、计数、限流、分布式锁、缓存聚合结果这类“高频访问但允许通过其他系统兜底”的数据。也就是说，Redis 很擅长把数据库前面的高并发流量挡住，提升系统性能和用户体验。

但真相层要求的东西不一样。真相层通常要求 **数据强一致、事务完整、故障后可恢复、状态可审计、结果可对账**。而 Redis 在这些方面天然不是最强项。比如它的事务能力不是传统关系型数据库那种严格 ACID；主从复制切换下可能有短暂数据丢失窗口；持久化也不是为“绝对不能丢一条”设计的；复杂条件查询、历史追溯、对账审计也不是它的长项。

所以凡是那种 **数据错了代价很高** 的场景，比如账务余额、支付结果、订单最终状态、库存最终事实、清结算流水，这些都更适合放在 MySQL 这类关系型数据库里做真相层。Redis 可以缓存它们、加速它们、做预扣和闸门，但不适合独自承担最终可信来源。

本质上可以这样理解：**Redis 擅长提升性能，不擅长单独承担最终正确性。**
所以很多系统设计里，Redis 放在前面做缓存、预热、削峰、快速状态查询；MySQL 放在后面做最终落库、事务保证、审计对账。
这就是为什么很多场景里，Redis 更适合做“加速层”，而不是“真相层”。

# 九、面试高频开放题 / 设计题

## 1. 设计一个登录 token 存储方案，为什么选 String / Hash？过期怎么做？

标准做法一般是：**Redis 存登录会话，用 token 作为索引，数据库不存会话明细；Redis 负责快速鉴权和过期控制。**

最常见的 key 设计有两种。

第一种是 **String 方案**。
比如：

`login:token:{token} -> userId|deviceId|loginTime|roles...`

或者 value 直接存一段 JSON。
这种方案优点是简单，读写都是一次 GET/SET，性能最好，代码实现也最直接。
如果你的登录态字段不多，而且通常是“整体读、整体写”，String 最合适。
生产上大多数登录 token 存储，其实优先会选 String。

第二种是 **Hash 方案**。
比如：

`login:token:{token}`
`userId=1001`
`deviceId=ios_01`
`loginTime=...`
`status=...`

Hash 更适合字段比较多，或者会做局部更新的场景。比如你想单独更新最近活跃时间、设备信息、扩展属性，而不想每次整包覆盖。
它的优势是结构化、字段级更新方便；缺点是实现和维护比 String 稍复杂一点，而且如果本来就是整取整存，Hash 的收益不明显。

所以选择上可以这样答：

**字段少、整体读写、追求简单高性能：选 String。**
**字段多、需要局部更新、会话属性扩展较多：选 Hash。**

过期一般直接用 **TTL 机制**。
登录成功时：

`SET login:token:{token} value EX 1800`

或者 Hash 场景下：

`HSET login:token:{token} ...`
`EXPIRE login:token:{token} 1800`

也就是给整个 token key 设置过期时间，比如 30 分钟、2 小时、7 天，取决于业务安全要求。

常见还有两种过期策略：

第一种是 **固定过期**。
登录后 2 小时失效，不管用户中间有没有操作，到点就过期。
这种简单、安全边界清晰，适合后台管理系统、风控要求高的系统。

第二种是 **滑动过期**。
用户每次访问时，如果 token 还有效，就续期一次，比如重新续成 30 分钟。
这种更适合用户体验要求高的 App、门户系统。
但要注意不能每个请求都无脑续期，否则 Redis 写放大明显。生产上通常会做成：**剩余 TTL 小于某个阈值时再续期**，比如剩余不到 10 分钟才续。

再补一个生产级设计点：
通常不只是存 `token -> session`，还会按需要补一个：

`login:user:{userId}:{deviceType} -> token`

这样可以支持 **单端登录、踢人下线、查看当前登录设备**。
比如新登录时先查用户旧 token，再删旧 token，最后写新 token。

小结就是：**登录 token 存储优先 String，复杂会话属性再考虑 Hash；过期用 Redis TTL，固定过期更安全，滑动过期体验更好。**

## 2. 设计一个排行榜系统，用 Redis 怎么做？如果数据量很大怎么办？

标准方案一般用 **ZSet**。因为排行榜天然需要两个核心能力：**按分数排序**，以及 **快速拿名次和分数**，这正好对应 Redis 有序集合的能力。

最基础的设计是这样：

key 例如：
`rank:game:202603`

member 存用户 ID：
`userId`

score 存积分、热度、战力之类的排名分值。

常用操作就是：
用户分数增加：`ZINCRBY`
查询 TopN：`ZREVRANGE`
查某个用户分数：`ZSCORE`
查某个用户排名：`ZREVRANK`

如果有并列分数，一般要提前定义规则。常见做法是：
一是直接接受同分并列，Redis 再按 member 字典序兜底；
二是把时间因子编码进 score，比如“分数优先，时间次优”，保证分数相同的人按先后排序；
三是业务侧单独存 tie-break 字段，再做二次处理。
面试里一般答到“要定义并列规则”就够了。

如果排行榜只需要展示前 100、前 1000，这种方案非常直接，Redis 做实时榜单很合适。因为它查询快、更新快，特别适合游戏积分榜、热度榜、活动榜、步数榜这类场景。

如果 **数据量很大**，就不能只停留在“一个大 ZSet 全扔进去”这个层面了，要从几个方向优化。

第一种是 **分榜设计**。
不要所有数据都放一个总榜，可以按周期、区域、业务维度拆分，比如日榜、周榜、月榜、区服榜、城市榜。这样每个 key 的规模会小很多，读写压力也更容易分散。

第二种是 **只保留热点区间**。
很多业务其实只关心 TopN 和“我的附近排名”，没必要把历史所有用户都长期放在 Redis。可以把全量结果沉到 MySQL / ES / 离线存储，Redis 只保留活跃用户和榜单头部数据。
也就是说，Redis 做实时热榜，数据库做全量归档。

第三种是 **分片或分桶**。
如果单个榜单成员非常多，比如几千万级，可以按业务维度拆榜，或者按用户区间、区服、活动池做分片。
不过要注意，**ZSet 跨分片做全局精确排序不便宜**，所以一旦上分片，通常要接受“分榜展示”或者引入离线合并。

第四种是 **冷热分层**。
实时变动的数据放 Redis，历史沉淀数据放 MySQL / ClickHouse / ES。
比如近 7 天活跃榜在 Redis，全年总榜由离线任务定时计算后写入结果。
这样可以把 Redis 的职责控制在“高频更新、高频查询”的部分。

第五种是 **异步聚合**。
如果更新频率特别高，比如点赞榜、热度榜，不一定每次事件都直接 `ZINCRBY`。可以先写 MQ 或本地缓冲，按秒级或批量聚合后再刷 Redis，减少写放大。

所以标准回答可以收束为：

**小到中等规模排行榜，用 Redis ZSet 最合适；核心操作是 `ZINCRBY`、`ZREVRANGE`、`ZREVRANK`、`ZSCORE`。如果数据量很大，就要做分榜、冷热分层、只保留热点数据，必要时结合 MySQL/ES/离线计算，Redis 只承担实时排行榜能力。**

## 3. 设计一个“附近的人”功能，Redis 能怎么做？

标准做法一般用 **Redis GEO**。因为“附近的人”本质上就是 **按地理位置存点，再按半径查周边对象**，Redis 原生提供了这套能力。

最基础的设计是：
用一个 GEO key 存某一类用户的位置，比如：

`geo:user:online`

member 存用户 ID，坐标存经纬度。
用户上报位置时，用 `GEOADD` 写入；
查询附近的人时，用 `GEOSEARCH` 或旧版本里的 `GEORADIUS` 按“当前位置 + 半径”查出一定范围内的用户；
如果要显示距离，可以带上距离参数一起返回。

一个典型链路是这样：

用户打开“附近的人”
→ 客户端上报当前位置
→ 服务端写 Redis GEO
→ 查询指定半径内用户
→ 过滤自己、过滤离线用户、过滤隐私设置不允许展示的人
→ 再去用户服务补昵称、头像、性别、标签等资料
→ 返回结果

为什么 Redis 适合做这个？
因为它查附近点的性能好，实现简单，特别适合这种 **实时位置检索 + 高频查询** 场景。对于“查 1km、3km、5km 内的人”这种需求，非常合适。

但生产上不能只停留在“GEO 一把梭”。

第一，要加 **在线态和时效控制**。
“附近的人”通常只展示最近一段时间活跃且在线的人，所以位置写入时，往往还要配合一个在线状态 key 或最近活跃时间 key。
否则 GEO 里可能查出来很多已经下线或几小时前的用户。
常见做法是：
Redis GEO 存位置
Redis String / ZSet / Hash 存最近活跃时间和在线状态
查询后做二次过滤

第二，要考虑 **隐私和精度**。
不是所有用户都愿意暴露精确位置，所以很多业务不会直接展示真实距离和精确点，而是展示“约 500 米内”“同一区域”这类模糊信息。
位置上报也通常会做限频，避免每次移动一点点就刷 Redis。

第三，要考虑 **数据清理**。
Redis GEO 本身不是带 TTL 的单成员过期结构，所以如果用户下线或长时间不上报位置，要有额外机制清理。
常见做法是：
每次上报位置时，顺带更新最近活跃时间
定时任务清除超时未活跃用户
或者查询后只保留最近 N 分钟活跃的数据

第四，如果数据量很大，要做 **分区或分桶**。
比如按城市、国家、区域拆 key：

`geo:user:online:shanghai`
`geo:user:online:beijing`

这样查询范围更小，管理更容易。
如果全国所有人都塞一个 key，虽然能用，但规模上来后维护和过滤成本都会增加。

第五，要注意 **Redis GEO 适合近邻检索，不适合复杂 GIS**。
它很适合“附近的人”“附近门店”“附近司机”这种半径查询，
但如果你要多边形围栏、复杂路线、行政区边界判断，那通常要引入专业地理空间方案，比如 ES geo、PostGIS，或者地图服务。

所以标准答案可以收束为：

**“附近的人”一般用 Redis GEO 实现，位置通过 `GEOADD` 存储，查询通过 `GEOSEARCH/GEORADIUS` 按半径检索；生产上再结合在线状态、活跃时间、隐私过滤、分城市分桶和定时清理，组成完整方案。数据量很大时，Redis 做实时近邻检索，复杂地理计算交给更专业的 GIS 系统。**

## 4. 设计一个签到系统，Redis 怎么做最省空间？

最省空间的做法一般是 **Bitmap**。

因为签到本质上是一个“某天签了 / 没签”的二值问题，用 1 bit 就能表示一天的状态，比 String、Hash、Set 都省得多。比如按“用户 + 月份”设计一个 key：

`sign:{userId}:202603`

然后把这个月的第几天作为 offset。
例如 3 月 18 日签到，就把 offset=17 的位设为 1：

`SETBIT sign:{userId}:202603 17 1`

这样一个用户一个月的签到记录，理论上只需要 31 bit，约 4 个字节就够了，空间利用率非常高。

查询某天是否签到，用 `GETBIT`；
统计当月签到天数，可以用 `BITCOUNT`；
如果要查连续签到，通常把整月位图取出来后在业务侧做位运算判断，或者取某一段后自行遍历。

为什么它最省空间？
因为：
用 Set 存每天签到日期，至少一条记录一个元素，开销很大；
用 Hash 存 `day -> signed` 也有字段和对象开销；
用 String/JSON 存整月状态，可读性还行，但空间和更新效率都不如 Bitmap。
而 Bitmap 本质是按 bit 压缩存储，非常适合签到、活跃标记、打卡这类场景。

标准结论就是：**签到系统最省空间的 Redis 方案是 Bitmap，按“用户 + 月份”建 key，按“天”映射 bit 位，用 `SETBIT`、`GETBIT`、`BITCOUNT` 完成签到、查询和统计。**

## 5. 设计一个短信验证码系统，要考虑哪些安全和性能问题？

标准设计思路是：**验证码只是一个短生命周期、高风险的校验凭证，核心目标不是“能发出去”，而是“防刷、防爆破、防重放、防滥发、可追踪、可降级”。**

先说 **核心存储设计**。通常会用 Redis 存验证码，例如：

`sms:code:{bizType}:{mobile}` -> 验证码摘要 / 发送时间 / 错误次数 / requestId

验证码本身不建议明文长期暴露，生产上更稳的是存 **摘要值**，校验时对用户输入做同样摘要再比对。TTL 一般 3~5 分钟，不宜太长。发送成功后还要配一个发送状态和频控 key，比如：

`sms:send:mobile:{mobile}`
`sms:send:ip:{ip}`
`sms:send:device:{deviceId}`

这样可以做多维限流。

安全上，第一要考虑的是 **防滥发**。要限制同一个手机号、同一个 IP、同一个设备、同一个用户、同一个业务场景的发送频率。常见规则是：60 秒内只能发一次，1 小时最多 N 次，1 天最多 M 次。否则很容易被短信轰炸，既有成本风险，也有骚扰风险。

第二要考虑 **防爆破**。验证码位数不能太短，通常 6 位；校验次数要有限制，比如 5 次失败就失效或冻结；校验成功后要立刻删除，避免重复试。对于登录、找回密码、支付确认这类高风险场景，还应该叠加图形验证码、人机校验、行为风控。

第三要考虑 **防重放**。验证码不能“一次生成，多次使用”。所以校验成功后必须立即失效；并且最好和业务场景绑定，比如注册验证码只能用于注册，登录验证码只能用于登录，不能混用。必要时还要绑定 requestId、sessionId 或设备信息，避免验证码被截获后跨场景复用。

第四要考虑 **手机号枚举和账号探测**。例如“该手机号是否已注册”“该账号是否存在”这类返回信息不能太直接，否则攻击者可以批量探测用户数据。对外返回要尽量统一，比如“验证码已发送，如号码有效请注意查收”。

性能上，第一要考虑 **削峰**。短信发送不是每次请求都直接同步调用供应商接口，生产上更稳的做法通常是：接口先做参数校验、频控、风控，再异步投递 MQ，由短信发送服务消费后调用短信通道。这样可以抗住突发流量，也方便失败重试和多供应商切换。

第二要考虑 **幂等**。同一请求因为超时重试、前端重复点击、网关重放，可能多次进入发送链路，所以发送接口最好带 requestId 或幂等号，避免同一请求发出多条短信。

第三要考虑 **供应商容灾**。短信通道本身可能超时、失败、限流，所以要支持主备供应商、失败切换、超时控制、重试策略。重试也不能无限重试，否则可能导致同一用户收到多条不同验证码。更稳的方式是：一次验证码生成后，在有效期内重复发送时可复用同一个验证码，但前提是业务允许。

第四要考虑 **可观测性**。要能追踪每条验证码请求的全链路：谁发起、发给谁、业务类型、模板、供应商响应、发送耗时、是否成功、校验是否通过、失败原因是什么。否则线上出了“收不到短信”“验证码总失败”“被恶意刷短信”时很难排查。

再补几个生产级要点。验证码不要打到日志里，避免敏感信息泄露；接口要全程 HTTPS；短信模板要区分业务类型；高风险场景下验证码不能作为唯一安全手段，最好结合登录态校验、设备指纹、风控评分一起做；对账上还要能统计发送成功率、到达率、失败率和短信成本。

小结一下：**短信验证码系统的重点不是 Redis 怎么存，而是频控、防爆破、防重放、异步削峰、供应商容灾和审计追踪。Redis 负责短期存储和频控，MQ 负责削峰，数据库和日志系统负责审计，风控系统负责拦截异常流量。**

## 6. 设计一个限流系统，单机限流和分布式限流分别怎么做？

标准答案先说：**单机限流解决的是“一个实例自己别被打垮”，分布式限流解决的是“整个集群总量别超标”**。单机一般用 JVM 内存算法实现，分布式一般用 Redis + Lua 实现。

**单机限流**，最常见有这几种：

第一种是 **固定窗口**。比如 1 秒最多 100 个请求，计数器到 100 就拒绝。实现简单，但问题是窗口切换时可能出现突刺，例如前 500ms 100 个，后 500ms 再来 100 个，瞬时就翻倍了。

第二种是 **滑动窗口**。把一个大窗口拆成多个小格子，统计最近一段时间的总请求数。这样比固定窗口更平滑，能减少临界突刺。单机里可以用数组、环形队列、时间片计数器实现。

第三种是 **令牌桶**。系统按固定速率往桶里放令牌，请求来了先拿令牌，拿到才放行。它的优点是既能限制平均速率，又允许一定程度突发流量，工程上非常常用。

第四种是 **漏桶**。请求先进桶，再按固定速率流出，重点是强行把流量整平。它更适合保护下游稳定处理能力，但对突发流量不如令牌桶友好。

单机限流一般直接放在 **网关层、Servlet Filter、Spring Interceptor、业务方法入口**。比如 Guava RateLimiter、Sentinel 本地限流，都是典型实现。它的优点是性能高、无外部依赖；缺点是只能限制当前节点，**多实例部署后，总限额会被放大**。

**分布式限流**，核心是多个实例要共享同一份限流状态。最常见方案是 **Redis + Lua**。

最基础做法是 **Redis 固定窗口计数**：
对某个限流维度，比如 `接口 + 用户ID`，构造 key：

`rate_limit:{api}:{userId}:{second}`

每次请求进来执行：
`INCR`
第一次创建时再 `EXPIRE 1`

如果计数超过阈值就拒绝。
这个方案简单，但仍然有固定窗口突刺问题。

更稳一点的是 **Redis 滑动窗口**。常见做法是用 **ZSet**：
score 存请求时间戳，member 存请求唯一 ID。
每次请求时用 Lua 原子执行三步：
删除窗口外旧数据
统计当前窗口内请求数
如果未超限则插入新请求记录并放行

这样能做到比较精确的滑动窗口分布式限流，但代价是实现和内存成本比简单计数器高。

再常见的是 **Redis 令牌桶**。Redis 里记录当前令牌数、上次补充时间，请求进来时用 Lua 原子计算应补充多少令牌，再判断是否可获取。这个方案更适合需要“限制平均速率 + 允许突发”的场景，比如短信发送、支付接口、登录接口。

分布式限流通常要先明确 **限流维度**，否则方案不完整。常见维度有：
按 IP 限
按用户限
按接口限
按租户限
按 appKey 限
按系统总量限

生产里往往不是只做一种，而是 **多级限流**。例如：
网关做全局限流
应用实例做单机限流
业务关键接口再做用户维度限流

这样能同时保护入口、集群和具体资源。

还要补一句生产注意事项：
分布式限流不能只说 Redis，还要考虑 **Redis 故障时怎么降级**。常见做法是 Redis 不可用时，退化到单机限流或默认放行/默认拒绝，具体看业务。对于核心写接口，通常宁可保守一点；对于普通查询接口，可以更偏向可用性。

小结一下：**单机限流常用固定窗口、滑动窗口、令牌桶、漏桶，适合保护单实例；分布式限流常用 Redis 计数器、ZSet 滑动窗口、Redis 令牌桶，适合集群统一控流。工程上一般是网关分布式限流 + 应用单机限流组合使用。**

## 7. 设计一个秒杀库存扣减方案，Redis 在里面扮演什么角色？

标准方案一般是：**Redis 负责高并发入口拦截、快速预扣、削峰和防超卖第一道闸门；MySQL 负责最终订单落库和最终库存事实；MQ 负责异步削峰与最终一致性。**

一个比较稳的秒杀链路通常是这样：

用户请求先到网关层，这里先做 **活动合法性校验、用户资格校验、限流、防重复下单**。通过后进入 Redis 扣减阶段。
Redis 里提前放好秒杀库存，比如：

`seckill:stock:{skuId}`

同时还会有：
用户是否已抢购标记
请求幂等标记
活动状态标记

扣减时不能用“先查再减”，而要用 **Lua 脚本原子执行**，把这几步放一起：
判断活动是否有效
判断用户是否已抢过
判断库存是否大于 0
库存减 1
写入抢购成功标记

这样可以在 Redis 层先把绝大多数并发拦住，避免并发超卖和数据库被直接打穿。

Redis 扣减成功后，不是当场同步下单到底，而是通常 **投递 MQ**，由订单服务异步消费。订单服务在 MySQL 里开启本地事务，完成订单创建、库存流水落表、最终库存确认。
如果 MySQL 落单成功，这次秒杀才算真正成功；
如果落单失败，就要做补偿，把 Redis 预扣库存回补，或者通过状态机和对账任务纠偏。

所以 Redis 在秒杀库存扣减里主要扮演 4 个角色：

**第一，流量闸门。**
高并发先打到 Redis，不让请求直接冲数据库。

**第二，原子预扣器。**
通过 Lua 脚本原子判断和扣减，快速拦截超卖。

**第三，削峰缓冲层。**
Redis 扣减成功后配合 MQ 异步下单，把瞬时流量摊平。

**第四，热点承压层。**
秒杀是典型热点场景，Redis 比 MySQL 更适合扛这种短时高并发读写。

但要特别强调：**Redis 不是最终库存真相层**。
因为 Redis 可能有主从切换、持久化丢失、补偿失败等问题，所以最终库存和订单事实必须以 MySQL 为准。
也就是说，Redis 负责“快”和“挡”，MySQL 负责“准”和“落”。

这类方案的核心原则可以总结成一句：**Redis 预扣防超卖，MQ 异步削峰，MySQL 最终落单，补偿和对账保证最终一致。**

## 8. 设计一个热点数据缓存系统，如何防止热点失控和缓存层雪崩？

标准方案是：**用“多级缓存 + 过期错峰 + 单飞重建 + 限流降级 + 热点探测”来控制热点和雪崩风险。**

先说整体结构。比较稳的热点缓存系统通常不是只有一层 Redis，而是：

**本地缓存 + Redis + 数据库**。

本地缓存负责拦住最热的一小部分请求，Redis 负责承接大部分缓存访问，数据库只作为最终回源。这样即使某个热点 key 被打爆，也不至于所有流量都直接压到 Redis 单点上。

防止 **热点失控**，核心看这几件事。

第一是 **热点识别**。要能提前知道哪些 key 访问量异常高，可以通过业务埋点、Redis top key 统计、接口维度监控来识别热点 key，而不是等 Redis CPU 打满了才发现。

第二是 **热点隔离**。对于超热点数据，不能和普通缓存一视同仁。常见做法是把它们放入本地缓存，或者做多副本 key 打散，例如一个热点 key 扩成多个副本，读请求随机打散，避免一个 key、一个 slot、一个节点被压穿。

第三是 **缓存重建保护**。热点 key 一旦失效，最容易引发击穿。要用互斥锁、singleflight、逻辑过期这类方式，确保同一时刻只有一个线程去回源重建，其他线程等待、快速失败，或者返回旧值，不能所有请求一起打数据库。

再说 **防缓存雪崩**。

第一是 **过期时间错峰**。不能让大量 key 用完全相同的 TTL，否则一到整点会集体失效。通常做法是基础 TTL + 随机抖动，比如 30 分钟 ± 5 分钟，把失效时间打散。

第二是 **多级兜底**。Redis 故障或大面积失效时，本地缓存要能顶住一部分热点流量；同时业务侧要有降级能力，比如返回默认值、旧值、静态页摘要，而不是所有请求都硬回源数据库。

第三是 **限流与熔断**。当缓存命中率突然下降、数据库回源流量暴增时，要及时在网关层或应用层限流，保护数据库。对非核心接口可以直接降级，对核心接口也要做排队和削峰。

第四是 **预热机制**。对明确可预知的热点，比如秒杀商品、首页榜单、活动配置，应该提前预热到 Redis 和本地缓存里，而不是等流量来了再临时构建。

再补两个生产上常见点。

一个是 **空值缓存**，防止缓存穿透。数据库查不到的数据，也短暂缓存一个空对象，避免恶意或异常请求一直打穿缓存层。

另一个是 **可观测性**。至少要监控命中率、回源 QPS、热点 key 分布、Redis CPU、RT、淘汰次数、过期 key 波动、数据库兜底流量。否则热点失控和雪崩来之前没有预警。

小结一下：**热点数据缓存系统的核心不是“把数据放进 Redis”，而是通过本地缓存挡热点、TTL 错峰防雪崩、单飞重建防击穿、限流降级保下游、热点探测做提前治理。**
