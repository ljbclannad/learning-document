# 1. InnoDb和MyISAM的区别
1. InnoDb提供事务支持，提供行级锁，支持外键，支持MVCC，默认隔离级别为可重复读
2. MyISAM不提供事务，且只有表级锁，不支持外键，不支持MVCC
3. 实际业务开发重为啥不推荐外键：
	1. 性能影响
		- 外键在插入、更新、删除时要额外检查关联表数据，影响写入性能；
		- 特别是在大数据量、高并发的系统中，不希望数据库增加开销。
	 2. 限制分布式架构
		- 外键只能在**同一个数据库实例内生效**；
		- 无法跨数据库或微服务进行约束，不利于数据库水平拆分（Sharding）。
    3. 控制权转移到数据库
		- 外键会自动触发级联删除等操作，开发人员无法完全控制，存在隐患；
		- 很多团队更愿意将数据一致性控制权交给应用层。
# 2. 锁
1. **表级锁：** MySQL 中锁定 **粒度最大** 的一种锁，对当前操作的整张表加锁，实现简单，资源消耗也比较少，加锁快，不会出现死锁。其锁定粒度最大，触发锁冲突的概率最高，并发度最低，MyISAM 和 InnoDB 引擎都支持表级锁。
2. **行级锁**： MySQL 中锁定 粒度最小 的一种锁，只针对当前操作的行进行加锁。 行级锁能大大减少数据库操作的冲突。其加锁粒度最小，并发度高，但加锁的开销也最大，加锁慢，会出现死锁。
	1. **行锁是数据库层面的一种锁类型**，由 InnoDB 在 UPDATE/DELETE/SELECT ... FOR UPDATE 时自动或手动触发； 而**悲观锁和乐观锁是并发控制策略**，**乐观锁依赖版本判断，悲观锁依赖行锁阻塞控制**；
	2. ┌──────────────┐
		│  乐观锁（业务层） │
		│  - 不加锁     │
		│  - version判断 │
		└──────┬───────┘
		       ↓
		    提交 UPDATE 时
		       ↓
		┌──────────────┐
		│  行锁（InnoDB） │ ← 自动加锁（Record Lock）
		│  - 保证更新原子性│
		└──────────────┘
		       ↑
		┌──────────────┐
		│  悲观锁（业务层） │
		│  - SELECT FOR UPDATE │
		│  - 显式加锁，提前锁住行 │
		└──────────────┘
3. **锁分类**：​
	1. 共享锁（share lock）：被称为读锁，其他用户可以并发读取数据，但任何事务都不能获取数据上的排他锁，直到已释放所有共享锁。（SELECT ... FOR SHARE）
		1. 例子：如果事务1对对象A上了锁，那么其他事务只能再对对象A上共享锁，而不能加锁，直到事务1释放了对对象A的S锁，这就保证了其他事务可以读取A，但是在事务1利用完A期间A不会被其他事务改变
	2. 排他锁（exclusive lock）：在事务1对对象A进行操作的时候，其他事务都不能读取或者修改对象A（select  for update）
4.  #Mysql 不可重复读（读取已提交），可重复读，幻读
	1. 很多人容易搞混不可重复读和幻读，确实这两者有些相似。但不可重复读重点在于update和delete，而幻读的重点在于insert。
	2. 如果使用锁机制来实现这两种隔离级别，在可重复读中，该sql第一次读取到数据后，就将这些数据加锁，其它事务无法修改这些数据，就可以实现可重复读了。但这种方法却无法锁住insert的数据，所以当事务A先前读取了数据，或者修改了全部数据，事务B还是可以insert数据提交，这时事务A就会发现莫名其妙多了一条之前没有的数据，这就是幻读，不能通过行锁来避免。需要Serializable隔离级别 ，读用读锁，写用写锁，读锁和写锁互斥，这么做可以有效的避免幻读、不可重复读、脏读等问题，但会极大的降低数据库的并发能力。

# 4. ACID

1. 原子性（Atomicity）：事务是最小的执行单位，不允许分割。事务的原子性确保动作要么全部完成，要么完全不起作用。
2. 一致性（Consistency）：执行事务前后，数据保持一致，例如转账业务中，无论事务是否成功，转账者和收款人的总额应该是不变的。
3. 隔离性（Isolation）：并发访问数据库时，一个用户的事务不被其他事务所干扰，各并发事务之间数据库是独立的
4. 持久性（Durability）：一个事务被提交之后。它对数据库中数据的改变是持久的，即使数据库发生故障也不应该对其有任何影响
5. 主要通过锁、Redo Log、Undo Log、MVCC来实现事务
	1. Redo Log（重做日志）:记录事务对数据库的所有修改，在崩溃时恢复未提交的更改，用来满足事务的持久性，如果宕机后数据页未写入，但 redo log 已提交，可以“重放日志”恢复数据。
	2. Undo Log（回滚日志）:记录事务的反向操作，简单地说就是保存数据的历史版本，用于事务的回滚，使得事务执行失败之后可以恢复之前的样子。实现原子性和隔离性。
	3. #Mysql **Redo Log和Undo Log的区别**
	
	   | 特性         | redo log                 | undo log                     |
	   | ------------ | ------------------------ | ---------------------------- |
	   | **作用**     | 用于恢复已提交事务的修改 | 用于回滚未提交事务的修改     |
	   | **记录内容** | 数据的物理修改           | 数据的逻辑修改（旧版本快照） |
	   | **写入时机** | 数据被修改时立即写入     | 数据被修改时立即写入         |
	   | **应用场景** | 崩溃恢复，持久性保障     | 事务回滚，MVCC 实现          |
# 5. MVCC在MySQL的InnoDB中的实现
1. 在InnoDB中，会在**每行数据后添加两个额外的隐藏的值来实现MVCC**，这两个值一个记录这行数据何时被创建，另外一个记录这行数据何时过期（或者被删除）。 在实际操作中，**存储的并不是时间，而是事务的版本号**，每开启一个新事务，事务的版本号就会递增。 在**可重读**Repeatable reads事务隔离级别下
	- **SELECT时，读取创建版本号<=当前事务版本号，删除版本号为空或>当前事务版本号。**
	- **INSERT时，保存当前事务版本号为行的创建版本号**
	- **DELETE时，保存当前事务版本号为行的删除版本号**
	- **UPDATE时，插入一条新纪录，保存当前事务版本号为行创建版本号，同时保存当前事务版本号到原来删除的行**
2. 通过MVCC，虽然每行记录都需要额外的存储空间，更多的行检查工作以及一些额外的维护工作，但可以减少锁的使用，大多数读操作**都不用加锁**，读数据操作很简单，性能很好，并且也能保证只会读取到符合标准的行，也只锁住必要行。

# 7. 数据库分表操作
1. 数据库分表（Sharding）是将大表的数据拆分成多个小表的技术，旨在提高性能和可维护性。分表可以根据不同的策略进行，以下是分表的常见方法、实施步骤和注意事项。
2. ![[Pasted image 20250305143312.png]]
## 1. **分表的目的**
- **提升性能**：减小单个表的数据量，提高查询速度和写入效率。
- **扩展性**：分布数据到多个物理存储上，支持更高的并发。
- **维护方便**：小表更易于管理和维护，比如备份和索引管理。
## 2. **分表策略**
- **水平分表**：
  - 将数据按行划分为多个表。例如，将用户表按用户ID范围分成多个表。
  - 例如：
    - `users_1`（用户ID 1-1000）
    - `users_2`（用户ID 1001-2000）
- **垂直分表**：
  - 按列划分，将一个表的不同列分到不同的表中。例如，将用户信息和用户日志分在不同的表。
  - 例如：
    - `users_info`（存储用户基本信息）
    - `users_logs`（存储用户操作日志）
## 3. **分表的实施步骤**
1. **分析数据和查询需求**：
   - 了解表的结构、数据量以及常用的查询模式，以确定分表的合适策略。
2. **设计分表方案**：
   - 确定分表的方式（水平或垂直）和分表的规则（如按用户ID、日期等）。
3. **创建新表**：
   - 根据分表设计，创建新的表结构。
4. **数据迁移**：
   - 将原表中的数据迁移到新表中。可以使用 SQL 脚本或 ETL 工具进行数据迁移。
5. **修改应用逻辑**：
   - 更新应用程序中的数据库访问逻辑，确保它能根据分表规则访问不同的表。
6. **测试和验证**：
   - 在分表后进行充分的测试，确保数据完整性和查询性能符合预期。
7. **监控和调整**：
   - 监控新结构的性能，并根据需要进行调整，例如重新分表或优化查询。
## 4. **注意事项**
- **数据一致性**：
  - 确保在分表过程中数据的一致性，特别是在高并发的环境下。
- **查询复杂性**：
  - 分表可能导致查询逻辑更加复杂，需要通过代码或中间件来处理跨表查询。
- **维护成本**：
  - 分表后需要管理多个表，可能增加维护成本。
- **分表限制**：
  - 不同的数据库管理系统对表的数量和大小有不同的限制，需根据具体情况进行规划。
- **索引设计**：
  - 确保在新表中进行合理的索引设计，以优化查询性能。
## 5. **示例**
假设有一个用户表 `users`，并决定按用户ID进行水平分表，以下是一个简单的示例：
### 原始表
```sql
CREATE TABLE users (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    email VARCHAR(100)
);
```
### 分表后的设计
```sql
CREATE TABLE users_1 (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    email VARCHAR(100)
);

CREATE TABLE users_2 (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    email VARCHAR(100)
);
```
### 数据迁移示例

```sql
INSERT INTO users_1 (id, name, email)
SELECT id, name, email FROM users WHERE id BETWEEN 1 AND 1000;

INSERT INTO users_2 (id, name, email)
SELECT id, name, email FROM users WHERE id BETWEEN 1001 AND 2000;

-- 删除原表数据
DROP TABLE users;
```
## 总结
数据库分表是一种有效的性能优化和扩展策略，但实施时需要谨慎规划。通过合理的设计、充分的测试和监控，可以有效提高系统的性能和可维护性。

# 8. 索引
## 1. 索引类型
1. 普通索引
2. 唯一索引
3. 主键索引
4. 组合索引
5. 全文索引
## 2. 虽然索引大大提高了查询速度，同时却会降低更新表的速度，如对表进行insert、update和delete。因为更新表时，不仅要保存数据，还要保存一下索引文件
## 3. 使用索引的技巧和注意事项
1. **索引不会包含有null值的列**，只要列中包含有null值都将不会被包含在索引中，复合索引中只要有一列含有null值，那么这一列对于此复合索引就是无效的。所以我们在数据库设计时不要让字段的默认值为null。
2. **使用短索引对串列进行索引**，如果可能应该指定一个前缀长度。例如，如果有一个char(255)的列，如果在前10个或20个字符内，多数值是惟一的，那么就不要对整个列进行索引。短索引不仅可以提高查询速度而且可以节省磁盘空间和I/O操作
3. **索引列排序查询只使用一个索引**，因此如果where子句中已经使用了索引的话，那么order by中的列是不会使用索引的。因此数据库默认排序可以符合要求的情况下不要使用排序操作；尽量不要包含多个列的排序，如果需要最好给这些列创建复合索引
4. **like语句操作**,一般情况下不推荐使用like操作，如果非使用不可，如何使用也是一个问题。like “%aaa%” 不会使用索引而like “aaa%”可以使用索引
5. 不要在列上进行运算 这将导致索引失效而进行全表扫描
	1. ```SELECT * FROM table_name WHERE YEAR(column_name)<2017;```
6. 不使用not in和<>操作
## 4.B-Tree
1. 数据结构
	1. d为大于1的一个正整数，称为B-Tree的度。
	2. h为一个正整数，称为B-Tree的高度。
	3. 每个非叶子节点由n-1个key和n个指针组成，其中d<=n<=2d。
	4. 每个叶子节点最少包含一个key和两个指针，最多包含2d-1个key和2d个指针，叶节点的指针均为null。
	5. 所有叶节点具有相同的深度，等于树高h。
	6. key和指针互相间隔，节点两端是指针。
	7. 一个节点中的key从左到右非递减排列。
	8. 如果某个指针在节点node最左边且不为null，则其指向节点的所有key小于。![[Pasted image 20241202143419.png]]
	9. 由于插入删除新的数据记录会破坏B-Tree的性质，因此在插入删除时，需要对树进行一个分裂、合并、转移等操作以保持B-Tree性质

## 5.B+Tree
1. 带有顺序访问指针的B+Tree![[Pasted image 20241202144124.png]]
2. 为什么不建议使用过场的字段或者字符串做为主键
	1. 因为所有辅助索引都引用主索引，过长的主索引会令辅助索引变得过大。再例如，用非单调的字段作为主键在InnoDB中不是个好主意，因为InnoDB数据文件本身是一颗B+Tree，非单调的主键会造成在插入新记录时数据文件为了维持B+Tree的特性而频繁的分裂调整，十分低效，而使用自增字段作为主键则是一个很好的选择
3. 优势
	1. 高效的查找性能
	2. 树的高度增长不会过快，查询磁盘的I/O次数减少
	3. 范围查询能力强
## 6. #Mysql 索引失效
1. **未遵循最左前缀匹配导致索引失效**
2. **使用函数导致索引失效**
3. **计算导致索引失效**
4. **类型转换导致索引失效**
5. **如果联合索引的使用不符合索引的顺序，可能会导致索引失效。例如，对于 `(a, b)` 的联合索引，查询 `WHERE b = value` 而没有 `a` 的条件可能会失效**
6. **不等于（不使用 = 或 IN）**
7. **在使用范围查询时，比如 `>`, `<`, `BETWEEN`，后面的条件可能导致索引失效**
8. **like模糊匹配以通配符开头导致索引失效**
9. **OR 前后存在非索引的列，索引失效**

## 7. #Mysql 覆盖索引
1. 二级索引中包含了查询所需的所有字段，从而使查询可以仅通过访问二级索引而不需要访问实际的表数据

2. **索引包含所有查询列**：

    - 覆盖索引包含了查询中所有需要的列，包括 `SELECT` 语句中的列和 `WHERE` 子句中的列。

 3. **避免回表**：
    - 使用覆盖索引时，查询的所有数据都可以从索引中获取，避免了额外的 I/O 操作，提高查询性能。

4. **提高性能**：

    - 由于减少了对表的访问，覆盖索引在读取大量数据时会显著提高性能，尤其是在大数据集的情况下。

5. 示例：

    1. CREATE INDEX idx_covering ON users(age,name,email);
    2. SELECT name,email FROM users WHERE age = 30;

    
# 9. #Mysql SQL优化
1. 应尽量避免在`WHERE`子句中对字段进行`NULL`值判断，否则将导致引擎放弃使用索引而进行全表扫描
2. 值分布很稀少的字段不适合建索引，例如"性别"这种只有两三个值的字段
3. 使用多列索引时主意顺序和查询条件保持一致，同时删除不必要的单列索引（最左匹配原则）
4. 不做列运算：`SELECT id WHERE age + 1 = 10`，任何对列的操作都将导致表扫描，它包括数据库教程函数、计算表达式等等，查询时要尽可能将操作移至等号右边
5. 尽量不用函数和触发器，在应用程序实现
6. 分页的优化（覆盖索引+子查询）：对于大数据SELECT * from user limit **100001**,**20** 优化为select * from user where id>(select id from user where id>=**100000** limit **1**) limit **20**
7. Join时尽量让小表做驱动表，因为驱动表需要全表扫描，而被驱动表需要通过索引查询
8. **/etc/mysql/conf.d**配置中slow_query_log = 1，slow_query_log_file = /var/lib/mysql/slow.log，long_query_time = 5配置属性或者设置SET GLOBAL slow_query_log = 'ON';SET GLOBAL slow_query_log_file = '/var/log/mysql/mysql-slow.log';SET GLOBAL long_query_time = 2.0;SET GLOBAL log_queries_not_using_indexes = 'ON'; 查看slow.log日志，寻找慢查询sql 
# 10.MySQL执行过程
在 MySQL 中，一条 SQL 语句的执行过程可以分为多个步骤。以下是一个典型的执行过程，从 SQL 语句的输入到结果的返回：
## 1. **解析（Parsing）**
当 SQL 语句发送到 MySQL 服务器时，首先会进行解析。这个步骤包括：
- **语法分析**：MySQL 会检查 SQL 语句的语法是否正确。如果语法错误，服务器将返回错误信息。
- **词法分析**：将 SQL 语句分解为不同的词法单元（tokens），如关键字、表名、列名和常量等。
## 2. **优化（Optimization）**
在解析完成后，MySQL 会对 SQL 语句进行优化，以生成执行计划：
- **查询重写**：优化器可能会对查询进行重写，优化查询结构。
- **选择索引**：优化器会决定使用哪个索引（如果有的话），以提高查询效率。
- **生成执行计划**：基于表的统计信息（如行数、数据分布等），优化器生成执行计划，描述如何执行查询。
## 3. **执行（Execution）**
生成执行计划后，MySQL 开始执行查询。这一过程包括：
- **检索数据**：根据执行计划，从相应的表中检索数据。
- **过滤数据**：应用 `WHERE` 子句中的条件，以过滤不符合条件的行。
- **排序和分组**：如果有 `ORDER BY` 或 `GROUP BY` 子句，MySQL 会对结果进行排序和分组。
## 4. **返回结果（Returning Results）**
一旦执行完成，MySQL 将结果集返回给客户端：
- **结果格式化**：将结果集格式化为客户端能够理解的格式（如 JSON、CSV 等）。
- **发送结果**：通过网络将结果发送回请求的客户端。
## 5. **缓存和优化（Caching and Optimization）**
- **查询缓存**：如果启用了查询缓存，MySQL 会检查缓存中是否已有相同的查询结果。如果有，则直接返回缓存结果，而不执行查询。MySQL8.0之后抛弃
- **优化器统计信息更新**：在执行过程中，MySQL 可能会收集一些运行时统计信息，以便在未来的查询中优化执行计划。
## 示例
假设我们执行以下 SQL 语句：
```sql

1. **解析**：检查语法，识别表 `employees` 和条件 `department = 'Sales'`。

# 11. #Mysql MySQL的ChangeBuffer
1. MySQL 的 Change Buffer 是一个用于优化插入和更新操作的机制，特别是在使用 InnoDB 存储引擎时。它的主要目的是提高对非唯一索引的性能，尤其是在大量插入、更新或删除操作的情况下。
## Change Buffer 概述
1. **背景**：
   - 当对 InnoDB 表的非唯一索引进行插入或删除操作时，通常会直接修改索引页。这可能导致频繁的磁盘 I/O 操作，从而影响性能。
2. **Change Buffer 的作用**：
   - Change Buffer 允许将对非唯一索引的修改暂时保存在内存中，而不是立即写入磁盘。这减少了磁盘 I/O 的次数，提高了性能。
## 工作原理
- **缓冲操作**：
  - 当对非唯一索引执行插入、更新或删除操作时，InnoDB 会将这些操作记录到 Change Buffer 中，而不是直接进行索引的物理修改。
- **合并操作**：
  - 在合适的时机（如后台线程运行时），InnoDB 会将 Change Buffer 中的修改合并到相应的索引页中。这一过程称为“合并”或“刷新”。
- **条件**：
  - 只有在没有足够的内存空间或在特定的条件下，才会将 Change Buffer 中的操作写入到磁盘的非唯一索引结构中。
## 优势
- **减少 I/O 操作**：通过将多个变化合并为单个 I/O 操作，Change Buffer 减少了磁盘访问的次数，从而提高性能。
- **提高插入性能**：在插入大量数据时，Change Buffer 能够显著提高性能，特别是在高并发的写入场景中。
## 注意事项
- **影响唯一索引**：Change Buffer 只适用于非唯一索引，唯一索引的修改仍然会立即写入。
- **内存使用**：Change Buffer 占用一部分内存，过多的变更未合并可能会导致内存不足或性能下降。
- **监控和调整**：可以通过监控系统性能和 Change Buffer 的使用情况，调整相关参数以优化性能。
## 配置参数
- **innodb_change_buffer_max_size**：控制 Change Buffer 的最大大小，默认值为 16% 的 InnoDB 缓冲池大小。
## 总结
MySQL 的 Change Buffer 是一种有效的性能优化机制，尤其适用于高写入负载的场景。通过暂存对非唯一索引的修改，Change Buffer 能够显著减少磁盘 I/O，从而提高整体性能。在实际使用中，合理配置和监控 Change Buffer 的使用情况可以进一步优化数据库的性能。

# 12. #Mysql 聚簇索引和非聚簇索引
1. 聚簇索引（Clustered Index）和非聚簇索引（Non-Clustered Index）是数据库中常用的两种索引类型，它们在存储结构、访问方式和性能方面有显著的区别。以下是它们的主要区别：
## 1. **定义**
- **聚簇索引**：
  - 数据库表的物理存储顺序与索引的顺序相同。即，聚簇索引决定了数据的存储顺序。
  - 每个表只能有一个聚簇索引，因为表的数据行只能按一种方式排序。
  - ![[Pasted image 20250305110339.png]]
- **非聚簇索引**：
  - 索引的存储顺序与数据的物理存储顺序无关。非聚簇索引包含索引键和指向数据行的指针。
  - 一个表可以有多个非聚簇索引。
## 2. **存储结构**
- **聚簇索引**：
  - 数据行和索引存储在一起，索引实际上就是数据。
  - 例如，在 InnoDB 中，聚簇索引的叶子节点存储了数据行。
- **非聚簇索引**：
  - 索引和数据存储在不同的地方，叶子节点存储的是索引键和指向数据行的指针（通常是行ID）。
  - 数据行可以在任何地方，非聚簇索引指向这些数据行的物理位置。
## 3. **性能**
- **聚簇索引**：
  - 由于数据和索引存储在一起，查询性能通常较好，尤其是在范围查询和排序时。
  - 但在插入、更新和删除时，可能会导致数据的移动，影响性能。
- **非聚簇索引**：
  - 查询时需要额外的 I/O 操作来访问数据行，通常性能稍差于聚簇索引。
  - 插入、更新和删除操作对非聚簇索引的影响较小，因为数据和索引是分开的。
## 4. **使用场景**
- **聚簇索引**：
  - 适合对主键或经常用于排序和范围查询的列。
  - 例如，在用户表中，使用用户ID作为聚簇索引。
- **非聚簇索引**：
  - 适合对查询频繁但不适合作为聚簇索引的列。
  - 例如，在订单表中，可以对订单状态或客户ID创建非聚簇索引。
## 5. **示例**
- **聚簇索引示例**：
  ```sql
  CREATE TABLE Employees (
      ID INT PRIMARY KEY,
      Name VARCHAR(100),
      Age INT
  );  ```
  在这个例子中，`ID` 列是聚簇索引，数据将按 `ID` 排序存储。
- **非聚簇索引示例**：
  ```sql
  CREATE INDEX idx_age ON Employees (Age);
  ```
  这里创建的 `idx_age` 是一个非聚簇索引，存储 `Age` 列的值和指向数据行的指针。
## 总结
![[Pasted image 20250305110813.png]]

1. 聚簇索引和非聚簇索引各有优缺点和适用场景。聚簇索引更适合需要频繁排序和范围查询的情况，而非聚簇索引则更灵活，可以在一个表上创建多个索引，以满足不同的查询需求。在设计数据库时，合理选择和组合这两种索引可以有效提高查询性能。

# 13.MySQL中的回表
1. **回表**指的是在使用非聚簇索引查询数据时，数据库需要先通过索引查找到对应的数据行，再通过数据行的指针访问聚簇索引或表中的实际数据。这一过程称为“回表”，因为它需要从索引回到表中去获取完整的数据。
## 回表的过程
1. **查询索引**：当执行查询时，MySQL 会首先查找非聚簇索引，以获取匹配的记录的指针（通常是行 ID 或主键）。
2. **访问数据行**：使用从索引中获取的指针，MySQL 随后访问聚簇索引或表中的实际数据行，以获取完整的结果。
## 示例
假设有一个表 `Employees`，其定义如下：
```sql
CREATE TABLE Employees (
    ID INT PRIMARY KEY,
    Name VARCHAR(100),
    Age INT,
    Salary DECIMAL(10, 2)
);
```
并且有一个非聚簇索引在 `Age` 列上：
```sql
CREATE INDEX idx_age ON Employees(Age);
```
如果我们执行以下查询：
```sql
SELECT Name FROM Employees WHERE Age = 30;
```
1. **使用非聚簇索引**：MySQL 首先会查找 `idx_age` 索引，以找到 `Age = 30` 的记录。
2. **回表**：由于所需的列 `Name` 不在索引中，MySQL 将使用找到的行 ID 回到 `Employees` 表中，以获取 `Name` 列的值。
## 回表的影响
- **性能**：回表会导致额外的 I/O 操作，因为数据库需要进行两次查找（一次在索引上，一次在表中）。因此，回表会影响查询性能，尤其是在数据量较大时。
- **列选择**：如果查询的所有列都在索引中（即覆盖索引），则不需要回表，查询性能会更高。
## 如何优化回表
1. **使用覆盖索引**：创建一个包含查询所需所有列的非聚簇索引。例如，如果查询 `SELECT Name, Salary FROM Employees WHERE Age = 30;`，可以创建一个覆盖索引：
   ```sql
   CREATE INDEX idx_age_salary ON Employees(Age, Name, Salary);
   ```
2. **减少返回的列**：仅选择必要的列，可以减少回表的开销。
3. **考虑聚簇索引**：如果主键和查询条件一致，直接使用聚簇索引可以避免回表。
4. **定期监控和优化索引**：使用 `EXPLAIN` 语句分析查询性能，判断是否存在回表情况，并根据需要调整索引设计。
## 总结
回表是 MySQL 中非聚簇索引查询的一部分，虽然它可以提高查询的灵活性，但也可能导致性能下降。通过合理设计索引和优化查询，可以有效减少回表的发生，提高数据库的查询性能。

# 14.MySQL的死锁
1. 在 MySQL 中，死锁是指两个或多个事务相互等待对方持有的锁，从而导致它们都无法继续执行。死锁会影响数据库性能，因此及时识别和解决死锁问题非常重要。以下是处理 MySQL 死锁的步骤和建议：
## 1. **识别死锁**
- **使用 `SHOW ENGINE INNODB STATUS`**：
  这个命令可以查看 InnoDB 引擎的状态，包括死锁信息。
  ```sql
  SHOW ENGINE INNODB STATUS;
  ```
- **查看错误日志**：
  MySQL 会在错误日志中记录死锁信息，可以检查日志文件以获取详细信息。
## 2. **死锁处理机制**
MySQL 的 InnoDB 存储引擎会自动检测死锁，并会选择回滚其中一个事务以解除死锁。一般来说，回滚的事务是持有锁较少的那个事务。
## 3. **解决死锁的方式**
1. **优化事务设计**：
   - **缩短事务时间**：尽量减少每个事务持有锁的时间，避免长时间占用资源。
   - **减少锁争用**：通过合理的查询和更新顺序，降低锁之间的争用。
2. **保持一致的访问顺序**：
   - 确保所有事务以相同的顺序访问表和行，以避免循环等待的情况。
3. **使用适当的隔离级别**：
   - 根据业务需求选择合适的事务隔离级别，较低的隔离级别（如读已提交）可以减少锁的竞争。
4. **使用行级锁**：
   - 如果可能，使用行级锁而不是表级锁，以减少锁的粒度，从而降低死锁的可能性。
5. **分析和调整索引**：
   - 确保查询使用优化的索引，以减少全表扫描和锁的争用。
## 4. **监控和排查死锁**
- **定期检查死锁**：
  定期监控数据库的死锁情况，分析发生死锁的原因，并进行相应的优化。
- **应用层处理**：
  在应用层捕获死锁错误（通常是错误代码 1213），并重试失败的事务。可以设置重试机制，在捕获到死锁时重新执行事务。
## 5. **示例：重试机制**
以下是一个基本的重试机制示例（使用 Python 和 MySQLdb）：
```python
import MySQLdb

def execute_transaction():
    conn = MySQLdb.connect(...)
    cursor = conn.cursor()

    retry_count = 3
    for attempt in range(retry_count):
        try:
            # 开始事务
            conn.begin()
            # 执行 SQL 语句
            cursor.execute("...")
            # 提交事务
            conn.commit()
            break
        except MySQLdb.OperationalError as e:
            if e.args[0] == 1213:  # Deadlock detected
                print("Deadlock detected, retrying...")
                conn.rollback()  # 回滚事务
                continue  # 重试
            else:
                raise
    else:
        print("Max retries exceeded.")
    
    cursor.close()
    conn.close()
```
## 总结
死锁是数据库管理中常见的问题，理解其原因并采取相应的措施可以有效减少死锁的发生。在设计数据库和应用程序时，优化事务处理和锁的使用是预防死锁的关键。通过监控和分析，能够及时发现和解决死锁问题，提高系统的整体性能和稳定性。

# 16. Doublewrite Buffer
1. Doublewrite Buffer（双写缓冲）是一种用于提高数据库系统可靠性和性能的技术，特别是在处理数据写入时。它主要用于防止数据丢失和提高故障恢复能力。以下是有关 Doublewrite Buffer 的详细说明：
## 什么是 Doublewrite Buffer？
Doublewrite Buffer 是一种机制，通过将数据首先写入一个缓冲区，然后再从缓冲区写入到最终的存储介质（如磁盘）来确保数据的完整性。这个过程通常涉及两个主要步骤：
1. **写入缓冲区**：当数据库需要将数据写入磁盘时，它首先将数据写入一个内存中的缓冲区（即双写缓冲）。
2. **写入磁盘**：然后，数据库会将缓冲区中的数据写入到磁盘的实际数据文件中。
## 工作原理
- **数据写入过程**：
  1. 数据首先写入 Doublewrite Buffer。
  2. 一旦数据成功写入缓冲区，系统会将其写入到磁盘的实际数据页。
  3. 最后，系统会更新元数据，指示数据已成功写入。
- **故障恢复**：如果在写入过程中发生故障（如系统崩溃），数据库可以使用 Doublewrite Buffer 中的数据恢复到一致的状态，从而避免数据丢失或损坏。
## 优势
1. **数据安全性**：通过确保数据在物理写入前先写入缓冲区，Doublewrite Buffer 有助于防止部分写入或损坏的数据页。
2. **故障恢复**：在系统崩溃的情况下，可以利用缓冲区中的数据进行恢复，确保数据的一致性和完整性。
3. **性能提升**：虽然额外的写入步骤可能在某些情况下引入延迟，但总的来看，Doublewrite Buffer 可以减少因写入失败而导致的重试次数，从而提升整体性能。
## 应用场景
- **数据库引擎**：许多现代数据库系统（如 MySQL 的 InnoDB 存储引擎）采用 Doublewrite Buffer 来提高数据的安全性和可靠性。
- **文件系统**：一些文件系统也采用类似的概念，以确保文件写入的原子性和一致性。
## 可能的缺点
1. **性能开销**：尽管可以提高数据安全性，但 Doublewrite Buffer 可能引入额外的写入延迟。
2. **内存占用**：需要额外的内存来存储缓冲区，可能会增加系统的内存消耗。
## 总结
Doublewrite Buffer 是一种有效的数据保护机制，旨在提高数据库的可靠性和数据完整性。通过将数据先写入缓冲区再写入磁盘，它能够有效防止数据损坏和丢失，尤其是在系统崩溃或写入失败的情况下。尽管引入了一定的性能开销，但在许多应用场景中，数据的安全性和一致性是更为重要的考虑因素。

# 17. #Mysql Delete、Truncate和Drop的区别
1. 在 SQL 中，`DELETE`、`TRUNCATE` 和 `DROP` 是用于删除数据或数据库对象的命令，但它们之间有显著的区别。以下是这三者的详细比较：
## 1. `DELETE`
- **功能**：用于删除表中的一行或多行数据。
- **语法**：
  ```sql
  DELETE FROM table_name WHERE condition;
  ```
- **特性**：
  - **可控性**：可以通过 `WHERE` 子句指定要删除的行。如果没有 `WHERE` 子句，将删除表中的所有行。
  - **事务支持**：`DELETE` 操作是可回滚的，意味着你可以在事务中执行 `DELETE`，然后选择提交或回滚。
  - **触发器**：`DELETE` 操作会触发相关的触发器（如果存在）。
  - **行级删除**：逐行删除，性能相对较低，尤其在删除大量数据时。
## 2. `TRUNCATE`
- **功能**：用于快速删除表中的所有数据，但保留表结构。
- **语法**：
  ```sql
  TRUNCATE TABLE table_name;
  ```
- **特性**：
  - **快速执行**：`TRUNCATE` 通常比 `DELETE` 更快，因为它不会逐行删除，而是直接释放整个数据页。
  - **无法恢复**：`TRUNCATE` 是不可回滚的，执行后无法恢复被删除的数据。
  - **不支持 WHERE 子句**：`TRUNCATE` 会删除表中的所有行，不能指定条件。
  - **不会触发触发器**：`TRUNCATE` 不会激活 `DELETE` 触发器。
## 3. `DROP`
- **功能**：用于删除整个表或其他数据库对象（如视图、索引、数据库等）。
- **语法**：
  ```sql
  DROP TABLE table_name;
  ```
- **特性**：
  - **删除对象**：`DROP` 会删除整个表及其结构，包括所有数据、索引和约束。
  - **不可恢复**：执行后，无法恢复被删除的表及其数据。
  - **数据依赖**：如果其他对象依赖于被删除的对象，可能会导致错误。
  - **不支持事务**：在大多数数据库中，`DROP` 操作不能回滚。
## 总结
| 操作         | 影响范围  | 能否回滚 | 触发器  | 速度  |
| ---------- | ----- | ---- | ---- | --- |
| `DELETE`   | 删除行   | 可回滚  | 会触发  | 较慢  |
| `TRUNCATE` | 删除所有行 | 不可回滚 | 不会触发 | 较快  |
| `DROP`     | 删除整个表 | 不可回滚 | 不会触发 | 最快  |
在选择使用 `DELETE`、`TRUNCATE` 还是 `DROP` 时，应根据具体需求（是否需要保留结构、是否需要回滚、数据量大小等）做出决策。

# 18.设计原则
在设计 MySQL 数据库表时，遵循一些基本原则可以帮助提高数据库的性能、可维护性和扩展性。以下是一些关键的表设计原则：

### 1. **规范化（Normalization）**
- **第一范式（1NF）**：确保每个字段只包含原子值，避免重复数据。
- **第二范式（2NF）**：确保每个非主属性完全依赖于主键，消除部分依赖。
- **第三范式（3NF）**：确保每个非主属性直接依赖于主键，消除传递依赖。

### 2. **合理选择数据类型**

- 使用适当的数据类型来节省存储空间和提高性能。例如，尽量使用 `INT` 替代 `BIGINT`，使用 `VARCHAR` 替代 `TEXT`，并根据实际需要选择字段长度。

### 3. **设置主键**
- 每个表应有一个主键，以唯一标识每一行记录。主键应该是简单且稳定的，避免使用自然键（如社会安全号码）作为主键。

### 4. **使用外键约束**
- 通过外键约束维护数据的完整性和一致性，确保表之间的关系是有效的。

### 5. **避免冗余数据**
- 尽量减少数据重复，避免冗余数据存储，这有助于减少数据不一致的风险，并简化更新操作。

### 6. **合理设计索引**
- 在常用的查询条件列上创建索引，可以显著提升查询性能。但要注意，过多的索引会影响插入、更新和删除操作的性能。

### 7. **考虑查询模式**
- 在设计表结构时，考虑将要执行的查询类型，优化表的结构以适应常见的查询模式。例如，可以通过合并表或引入摘要表来加速复杂查询。

### 8. **使用合适的命名规范**
- 表和列的命名应简洁且具有描述性，以便于理解和维护。通常使用小写字母和下划线分隔单词（例如，`patient_data`）。

### 9. **文档化设计**
- 对表的设计、字段的含义、约束和索引等进行详细文档化，以便于团队成员和后续维护。

### 10. **考虑扩展性**
- 在设计时考虑未来的需求，确保结构能够灵活应对变化，例如字段的添加、约束的修改等。

### 11. **定期审查和优化**
- 定期审查和优化数据库设计，随着应用需求的变化，及时调整表结构和索引策略。

### 总结
良好的数据库表设计能够提高性能、确保数据一致性和完整性，并为后续的维护和扩展打下良好的基础。遵循以上原则可以帮助设计出高效且可维护的数据库结构。

# 19. #Mysql Group By和HAVING的关系

`GROUP BY` 和 `HAVING` 是 SQL 中用于分组和筛选分组结果的重要子句。它们各有作用，且通常一起使用以满足分组和筛选的需求。

---

## **1. GROUP BY 的作用**

`GROUP BY` 用于将查询结果按照指定的列进行分组，并对每组数据应用聚合函数（如 `SUM`、`COUNT`、`AVG` 等）进行计算。

### **使用场景**

- 按特定列分组并计算统计信息（如总和、平均值、计数）。

### **示例**

#### 表：`sales`

|product|category|amount|
|---|---|---|
|A|X|100|
|B|X|200|
|C|Y|300|
|D|Y|400|

#### 查询：按 `category` 分组，计算每个类别的总销售额

```sql
SELECT category, SUM(amount) AS total_sales
FROM sales
GROUP BY category;
```

#### 结果：

|category|total_sales|
|---|---|
|X|300|
|Y|700|

---

## **2. HAVING 的作用**

`HAVING` 用于对分组后的结果进行筛选，类似于 `WHERE` 子句，但它针对的是聚合结果。

### **使用场景**

- 筛选分组后的结果（如只显示总销售额大于某个值的分组）。

### **示例**

#### 查询：筛选总销售额大于 500 的类别

```sql
SELECT category, SUM(amount) AS total_sales
FROM sales
GROUP BY category
HAVING total_sales > 500;
```

#### 结果：

|category|total_sales|
|---|---|
|Y|700|

---

## **3. GROUP BY 和 HAVING 的区别**

|特性|`GROUP BY`|`HAVING`|
|---|---|---|
|**作用**|用于对数据进行分组|用于筛选分组后的聚合结果|
|**处理对象**|原始数据|分组后的聚合数据|
|**是否支持聚合函数**|不支持直接使用聚合函数|支持聚合函数|
|**筛选时机**|在分组前进行|在分组和聚合后进行|
|**替代方式**|无直接替代|可以在部分场景中用子查询替代|

---

## **4. WHERE 与 HAVING 的关系**

- `WHERE` 和 `HAVING` 都可用于筛选，但作用的阶段不同：
    - **`WHERE`**：在分组前筛选原始数据。
    - **`HAVING`**：在分组后筛选聚合结果。

### 示例：

#### 查询：只统计销售额大于 150 的产品，并按类别筛选总销售额大于 500 的分组

```sql
SELECT category, SUM(amount) AS total_sales
FROM sales
WHERE amount > 150
GROUP BY category
HAVING total_sales > 500;
```

#### 执行流程：

1. **`WHERE` 子句**：筛选 `amount > 150`，只保留产品 B、C、D。
2. **`GROUP BY` 子句**：按 `category` 分组。
3. **聚合函数**：计算每组的 `SUM(amount)`。
4. **`HAVING` 子句**：筛选聚合结果中 `total_sales > 500` 的分组。

---

## **5. 注意事项**

1. **`GROUP BY` 的字段**
    - 查询中非聚合字段必须出现在 `GROUP BY` 子句中，否则会报错（在严格 SQL 模式下）。
2. **`HAVING` 的效率**
    - 如果可以使用 `WHERE` 代替 `HAVING`，优先使用 `WHERE`，因为它在分组前执行，效率更高。

---

## **总结**

- **`GROUP BY`**：用于分组原始数据并进行聚合计算。
- **`HAVING`**：用于筛选分组后的聚合结果。
- 二者常结合使用，`WHERE` 子句可以与 `GROUP BY` 配合，优先过滤原始数据，减少处理量。

# 20.MySQL合理的数据类型
在设计 MySQL 数据库时，选择合适的数据类型非常重要，不仅影响存储空间的使用，还会影响查询效率和应用程序的灵活性。以下是常用的数据类型及其适用场景的详细说明：

---

## **1. 整数类型**

### **常用整数类型及范围**

| 数据类型        | 存储大小 | 有符号范围                                                  | 无符号范围                          |
| ----------- | ---- | ------------------------------------------------------ | ------------------------------ |
| `TINYINT`   | 1 字节 | -128 到 127                                             | 0 到 255                        |
| `SMALLINT`  | 2 字节 | -32,768 到 32,767                                       | 0 到 65,535                     |
| `MEDIUMINT` | 3 字节 | -8,388,608 到 8,388,607                                 | 0 到 16,777,215                 |
| `INT`       | 4 字节 | -2,147,483,648 到 2,147,483,647                         | 0 到 4,294,967,295              |

### **选择指南**

1. **优先使用适合的最小类型**：
    - 如果只需要存储小范围整数，例如年龄，可以选择 `TINYINT`。
2. **使用无符号类型（UNSIGNED）**：
    - 如果数据永远不会出现负值，例如 ID、自增字段，使用无符号类型可以扩大范围。
3. **避免过大类型**：
    - 过大的类型（如 `BIGINT`）会浪费存储空间，影响性能。

---

## **2. 浮点和定点数类型**

### **常用类型**

| 数据类型      | 描述                                  |
| --------- | ----------------------------------- |
| `FLOAT`   | 4 字节，存储近似小数值，精度有限，适合科学计算或非精确值（如温度）。 |
| `DOUBLE`  | 8 字节，存储近似小数值，精度更高。                  |
| `DECIMAL` | 存储精确的小数值，适合需要高精度的场景，如财务数据。          |

### **选择指南**

1. **非精确计算**：选择 `FLOAT` 或 `DOUBLE`，如测量值或科学计算。
2. **精确计算**：选择 `DECIMAL`，适合存储金额等需要高精度的场景。
3. **避免使用浮点数存储金额**：浮点数可能产生精度问题，财务数据建议使用 `DECIMAL`。

---

## **3. 字符串类型**

### **常用类型**

| 数据类型         | 描述                           |
| ------------ | ---------------------------- |
| `CHAR(n)`    | 固定长度字符串，适合存储定长数据（如邮编、性别）。    |
| `VARCHAR(n)` | 可变长度字符串，适合存储长度可变的数据（如姓名、地址）。 |
| `TEXT`       | 长文本数据，适合存储大块文字内容（如评论、文章）。    |
| `BLOB`       | 二进制大对象，适合存储图片、文件等二进制数据。      |

### **选择指南**

1. **固定长度数据**：使用 `CHAR`，存储和访问效率较高，但可能浪费存储空间。
2. **可变长度数据**：使用 `VARCHAR`，节省存储空间，适合大多数字符串数据。
3. **大文本数据**：使用 `TEXT`，注意 `TEXT` 不支持索引前缀，查询效率较低。
4. **二进制数据**：使用 `BLOB`，避免在表中存储过大文件，推荐使用文件存储结合路径。

---

## **4. 日期和时间类型**

### **常用类型**

| 数据类型        | 存储大小 | 范围                                                | 精度  |
| ----------- | ---- | ------------------------------------------------- | --- |
| `DATE`      | 3 字节 | 1000-01-01 到 9999-12-31                           | 天   |
| `DATETIME`  | 8 字节 | 1000-01-01 00:00:00 到 9999-12-31 23:59:59         | 秒   |
| `TIMESTAMP` | 4 字节 | 1970-01-01 00:00:01 UTC 到 2038-01-19 03:14:07 UTC | 秒   |
| `TIME`      | 3 字节 | -838:59:59 到 838:59:59                            | 秒   |
| `YEAR`      | 1 字节 | 1901 到 2155                                       | 年   |

### **选择指南**

1. **仅存日期**：使用 `DATE`，节省存储空间。
2. **日期和时间**：使用 `DATETIME` 或 `TIMESTAMP`。
    - `TIMESTAMP` 适合需要存储 UTC 时间或时间戳的场景，受系统时区影响。
    - `DATETIME` 不受时区影响，适合更广的时间范围。
3. **存储时间间隔**：使用 `TIME`。
4. **存储年份**：使用 `YEAR`。

---

## **5. 枚举和集合类型**

### **常用类型**

|数据类型|描述|
|---|---|
|`ENUM`|枚举类型，适合存储有限的选项（如性别：`'male', 'female'`）。|
|`SET`|集合类型，适合存储多选值（如标签：`'tag1', 'tag2', 'tag3'`）。|

### **选择指南**

1. **有限选项**：使用 `ENUM`，存储效率高，但不易扩展。
2. **多选值**：使用 `SET`，便于存储，但查询复杂时效率较低。

---

## **6. JSON 类型**

- **适用场景**：
    - 存储半结构化数据，例如配置、动态属性等。
- **优点**：
    - 数据灵活性强，可以直接查询 JSON 字段。
- **缺点**：
    - 查询性能不如标准化表结构。

---

## **总结**

### **字段设计原则**

1. **尽量选择更小的数据类型**，减少存储空间并提高性能。
2. **为字段选择适合的数据类型**，避免类型转换带来的额外开销。
3. **避免使用过大类型**，如 `TEXT` 或 `BLOB`，可能影响查询性能。
4. **考虑未来扩展**，确保字段类型能满足业务增长需求。
5. **存储金额用 `DECIMAL`，存储时间用 `DATETIME` 或 `TIMESTAMP`，避免精度和时区问题。**

根据具体的业务需求，合理选择数据类型能够显著提升 MySQL 数据库的性能和效率！

# 22. B+树详解
MySQL 的 B+树是一种常用的索引数据结构，特别是在 InnoDB 存储引擎中，**B+树索引**用于加速查询。它是对 B 树的优化，适用于磁盘存储，查询效率高且平衡性好。

---

## **1. B+树简介**

![[Pasted image 20250305104837.png]]
### **B+树的结构特点**

1. **多叉树**：
    
    - 每个节点可以有多个子节点。
    - 节点的子节点数量（称为“阶”）取决于磁盘页的大小。
2. **所有值存储在叶子节点**：
    
    - 非叶子节点只存储键值和指向子节点的指针，用于指导查询路径。
    - 叶子节点存储完整的数据或指向实际数据的指针。
3. **叶子节点链表**：
    
    - 叶子节点通过双向链表连接，便于范围查询和顺序遍历。
4. **平衡性**：
    
    - 所有叶子节点在同一层，保证查询路径长度一致。

### **B+树 vs. B 树**

|特性|B 树|B+树|
|---|---|---|
|**数据存储**|数据存储在所有节点|数据存储在叶子节点|
|**查询性能**|每个节点可能存储数据，需逐层检查|非叶子节点只存储键值，查询效率更高|
|**范围查询**|需要逐层遍历|叶子节点链表直接遍历|

---

## **2. B+树在 MySQL 中的存储**

### **B+树索引的组织**

- **InnoDB 的主键索引（聚簇索引）**：
    
    - B+树的叶子节点存储完整的数据行。
    - 主键索引决定数据在表中的物理存储顺序。
- **辅助索引（二级索引）**：
    
    - B+树的叶子节点存储主键值，而非完整数据。
    - 查询时需要回表，根据主键值在聚簇索引中找到完整数据。

### **页面（Page）存储结构**

1. **节点单位：页（Page）**：
    
    - InnoDB 默认页大小为 16KB。
    - 每个页中存储多个键值和指针。
2. **页的分裂与合并**：
    
    - 插入新值时，若当前页已满，则进行“页分裂”。
    - 删除值时，若页中数据过少，则进行“页合并”。
3. **根节点与叶子节点**：
    
    - 根节点：树的起点。
    - 叶子节点：存储实际数据或主键。

---

## **3. B+树的查询过程**

### **查询路径**

假设有一个 `id` 列的 B+树索引，查询 `id = 15` 的过程如下：

1. **从根节点开始**：
    
    - 比较根节点中的键值，确定查询范围。
    - 根据指针找到对应的子节点。
2. **逐层查找**：
    
    - 在每一层节点中重复比较键值和查找指针的过程。
3. **到达叶子节点**：
    
    - 在叶子节点中找到目标键值。
    - 返回目标键值对应的记录（聚簇索引）或主键值（二级索引）。

### **范围查询**

对于 `id BETWEEN 10 AND 20`：

1. **找到起点**：
    
    - 按上述路径定位到 `id = 10` 的叶子节点。
2. **顺序遍历**：
    
    - 沿着叶子节点的链表，依次读取 `id` 的值，直到 `id = 20`。

---

## **4. 示例：B+树存储与查询**

假设有一张用户表 `users`，包含如下数据：

|id|name|
|---|---|
|1|Alice|
|3|Bob|
|5|Charlie|
|7|David|
|9|Eve|

### **B+树结构（示例）**

假设每个节点最多存储 2 个键值：

```
                +-------+
                | 5     |
                +-------+
               /         \
        +-------+       +-------+
        | 1, 3  |       | 7, 9  |
        +-------+       +-------+
```

### **存储结构**

- 根节点：`[5]`，表示小于 5 的值在左子树，大于等于 5 的值在右子树。
- 叶子节点：
    - 左子树：`[1, 3]`
    - 右子树：`[7, 9]`

### **查询 `id = 7` 的过程**

1. **从根节点 `[5]` 开始**：
    
    - `7 > 5`，进入右子树。
2. **到达叶子节点 `[7, 9]`**：
    
    - 找到键值 `7`，返回对应记录。

### **范围查询 `id BETWEEN 3 AND 9` 的过程**

1. **从根节点 `[5]` 开始**：
    
    - `3 <= 5`，进入左子树。
2. **从叶子节点 `[1, 3]` 开始**：
    
    - 定位到 `3`，顺序遍历链表：
        - `[3] → [5] → [7] → [9]`

---

## **5. B+树的优点**

1. **平衡性**：
    
    - 所有叶子节点在同一层，查询路径长度一致。
2. **适合磁盘存储**：
    
    - 每个节点对应一个页，减少磁盘 I/O 操作。
3. **高效的范围查询**：
    
    - 叶子节点链表支持顺序遍历，查询连续范围的数据非常快。

---

## **6. 实际案例**

假设一张大表 `orders`，包含以下索引：

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    order_date DATETIME NOT NULL,
    amount DECIMAL(10, 2)
) ENGINE=InnoDB;
```

### **查询过程示例**

1. 查询单条记录：
    
    ```sql
    SELECT * FROM orders WHERE id = 1001;
    ```
    
    - B+树根据主键 `id`，从根节点逐层定位到叶子节点。
2. 查询范围：
    
    ```sql
    SELECT * FROM orders WHERE id BETWEEN 500 AND 1000;
    ```
    
    - 通过叶子节点链表顺序遍历范围内的记录。
3. 查询二级索引：
    
    ```sql
    CREATE INDEX idx_customer_date ON orders (customer_id, order_date);
    SELECT * FROM orders WHERE customer_id = 123;
    ```
    
    - 二级索引的叶子节点存储主键 `id`。
    - 查询需要先通过二级索引定位主键，再回表获取完整记录。

---

## **总结**

1. **B+树在 MySQL 中用于存储索引**：
    
    - 主键索引：叶子节点存储完整数据。
    - 二级索引：叶子节点存储主键值。
2. **B+树查询过程高效**：
    
    - 分层定位到叶子节点。
    - 范围查询通过链表顺序遍历叶子节点。
3. **设计优化**：
    
    - 合理设计索引，减少树的深度。
    - 避免频繁分裂和合并页，减少维护成本。

# 23. #Mysql MySQL中的隐式类转换
在 MySQL 中，当查询中的数据类型不匹配时，MySQL 会尝试进行 **隐式类型转换** 来使操作符、表达式或函数能够正确执行。这种机制虽然便于开发，但在某些情况下可能导致性能问题或不符合预期的结果。

---

## **1. 隐式类型转换的规则**

MySQL 在以下情况下会执行隐式类型转换：

1. **比较操作符**（`=`、`>`, `<`, `LIKE` 等）。
2. **数学运算**（如加减乘除）。
3. **函数调用**（如 `CONCAT()`、`ROUND()` 等）。

### **转换方向**

- **字符串 → 数值**：如果操作需要数值，而提供的是字符串，MySQL 会将字符串转换为数值。
- **数值 → 字符串**：如果操作需要字符串，而提供的是数值，MySQL 会将数值转换为字符串。
- **字符串 → 日期**：在需要日期类型时，MySQL 会尝试将字符串解析为日期。

---

## **2. 常见隐式类型转换场景**

### **2.1 数值与字符串**

#### 示例 1：字符串转数值

```sql
SELECT '123' + 1; -- 结果：124
```

**解析**：

- `'123'` 被隐式转换为数值 123，然后与 1 相加。

#### 示例 2：非数值字符串

```sql
SELECT 'abc' + 1; -- 结果：1
```

**解析**：

- 非数值字符串 `'abc'` 被转换为 0（MySQL 将无法解析的字符串视为 0）。

---

### **2.2 日期与字符串**

#### 示例 1：字符串转日期

```sql
SELECT '2023-01-01' + INTERVAL 1 DAY; -- 结果：'2023-01-02'
```

**解析**：

- `'2023-01-01'` 被隐式转换为日期类型。

#### 示例 2：无效日期

```sql
SELECT 'abc' + INTERVAL 1 DAY; -- 结果：NULL
```

**解析**：

- `'abc'` 无法转换为日期，因此返回 NULL。

---

### **2.3 字符串与布尔值**

#### 示例

```sql
SELECT 'abc' = 0; -- 结果：1（TRUE）
SELECT '123' = 123; -- 结果：1（TRUE）
```

**解析**：

- `'abc'` 被转换为 0，`0 = 0` 返回 TRUE。
- `'123'` 被转换为 123，与数值 123 相等。

---

### **2.4 列值的类型转换**

如果查询中比较的字段类型与常量或另一列的类型不匹配，MySQL 会尝试进行类型转换。

#### 示例 1：字符串和整数比较

```sql
SELECT * FROM table WHERE varchar_column = 123;
```

**解析**：

- 如果 `varchar_column` 是字符串类型，MySQL 会将其转换为数值与 `123` 比较。

#### 示例 2：日期与字符串比较

```sql
SELECT * FROM table WHERE date_column = '2023-01-01';
```

**解析**：

- 如果 `date_column` 是日期类型，MySQL 会将字符串 `'2023-01-01'` 转换为日期类型再比较。

---

## **3. 隐式类型转换的影响**

### **3.1 性能问题**

隐式类型转换可能导致索引失效，进而引发全表扫描。

#### 示例

```sql
SELECT * FROM users WHERE phone_number = 1234567890;
```

- 如果 `phone_number` 是 `VARCHAR` 类型，`1234567890` 会被转换为字符串。
- 这种情况下，索引无法使用，查询变为全表扫描。

**优化建议**：

- 确保数据类型匹配，例如：
    
    ```sql
    SELECT * FROM users WHERE phone_number = '1234567890';
    ```
    

---

### **3.2 不符合预期的结果**

隐式类型转换可能导致错误或意外的查询结果。

#### 示例

```sql
SELECT * FROM users WHERE balance = 'abc';
```

- 如果 `balance` 是数值类型，`'abc'` 会被转换为 0。
- 查询结果会返回所有 `balance = 0` 的行。

**优化建议**：

- 避免隐式转换，明确指定数据类型，例如：
    
    ```sql
    SELECT * FROM users WHERE balance = CAST('abc' AS DECIMAL);
    ```
    

---

## **4. 如何避免隐式类型转换**

1. **使用一致的数据类型**：
    
    - 确保表字段的数据类型与查询中的常量或表达式匹配。
2. **显式类型转换**：
    
    - 使用 `CAST` 或 `CONVERT` 明确指定转换类型：
        
        ```sql
        SELECT * FROM users WHERE phone_number = CAST(1234567890 AS CHAR);
        ```
        
3. **检查隐式转换**：
    
    - 使用 `EXPLAIN` 检查查询计划，确保索引未失效。
4. **启用 SQL 模式**：
    
    - 启用严格模式（`STRICT_TRANS_TABLES`）可减少不必要的类型转换。

---

## **5. 总结**

### **隐式类型转换的优缺点**

|优点|缺点|
|---|---|
|提高开发便捷性，减少类型匹配的麻烦|可能导致索引失效，降低查询性能|
|自动处理不同类型的数据比较|可能引发不符合预期的结果|
|提供更大的灵活性|在复杂查询中可能导致难以排查的错误或问题|

### **最佳实践**

1. 避免在查询中依赖隐式类型转换，尤其是在涉及索引时。
2. 在开发阶段使用 `EXPLAIN` 分析查询，确保索引正常使用。
3. 明确字段的类型需求，在设计表结构时保持一致性。

通过合理的设计和规范化操作，可以有效避免隐式类型转换带来的问题，提高 MySQL 的性能和稳定性。

# 25. MVCC、间隙锁、记录锁

---

### MVCC（多版本并发控制）

- MVCC 是 InnoDB 引擎实现的一种**无锁并发读机制**，底层依赖 `undo log` 和事务快照（Read View）控制数据可见性。
- 适用于普通的 `SELECT` 查询，不会加锁。
- 可以防止 **脏读**、**不可重复读**，但**无法防止幻读**。

#### 特点：
- 每条记录都有隐藏的 `trx_id` 和 `roll_pointer` 字段。
- 不加锁，通过对比 `Read View` 与记录版本号，判断是否可见。
- 在 `REPEATABLE READ` 隔离级别下，即使其他事务已插入新数据，当前事务也看不到（读取的是快照）。

---

### 记录锁（Record Lock）

- 是 InnoDB 在更新/删除/加锁操作中对**行记录加的锁**。
- 精确锁定一条记录，防止其他事务修改或删除它。

#### 触发场景：
- `UPDATE`
- `DELETE`
- `SELECT ... FOR UPDATE` / `LOCK IN SHARE MODE`

#### 特点：
- 仅作用于命中的数据行。
- 用于保证事务隔离的一致性。
- 无法防止“幻读”——因为只锁现有行，无法阻止新插入。

---

### 间隙锁（Gap Lock）

- 间隙锁锁住的是**两个索引值之间的空隙范围**，用于防止**“幻插入”**。
- 通常和记录锁组合形成 **Next-Key Lock**，用于防止幻读。

#### 触发场景：
- `REPEATABLE READ` 隔离级别下的：
  - `SELECT ... FOR UPDATE`（范围条件）
  - `DELETE ... WHERE 范围条件`

#### 特点：
- 会锁住类似 `(a, b]` 的范围，禁止往该区间插入数据。
- 不锁已有记录的内容，但阻止插入。
- 防止“第二次查询时，条件内多出新数据”的幻读现象。

---

### Next-Key Lock = Record Lock + Gap Lock

- 是 InnoDB 在 RR 隔离级别下默认使用的组合锁。
- 会锁住一行以及其前面的间隙。
- 插入一条“命中间隙”的数据（比如 `2.5` 落在 `(2,3]`），会被阻塞。

---

### 总结对比表

| 项目 | 加锁对象 | 能否防幻读 | 是否自动触发 | 常见语句 |
|------|----------|-------------|----------------|----------|
| MVCC | 无（版本判断） | ❌ 否 | ✅ 是 | 普通 `SELECT` |
| 记录锁 | 精确某行 | ❌ 否 | ✅ 是 | `UPDATE`, `DELETE`, `FOR UPDATE` |
| 间隙锁 | 范围间隙 | ✅ 是 | ✅ 是（RR下） | 范围 `SELECT ... FOR UPDATE`, `DELETE WHERE 范围` |
| Next-Key Lock | 记录 + 间隙 | ✅ 是 | ✅ 是（RR下） | 范围语句 |

---

### 常见理解误区澄清

- MVCC 不加锁，不能防幻读。
- 间隙锁是 InnoDB 自动加的，不需要手动控制，但只有在 RR 隔离级别下才启用。
- `DELETE WHERE 范围` 会自动加 Next-Key Lock，防止别的事务插入删除区间中的新数据。
- `SELECT ... FOR UPDATE` 会触发记录锁和间隙锁，用于显式加锁防止并发修改或插入。

---

```

# 26. 锁问题

---

## 1. 锁是基于索引实现的

- InnoDB 的行锁是通过**索引加的锁**。
- 如果 WHERE 条件未命中索引，可能加**表锁**。

```sql
-- 没有命中索引，可能锁全表
SELECT * FROM user WHERE name = 'Alice' FOR UPDATE;
```

**建议**：确保加锁语句走索引，避免锁粒度过大。

---

## 2. 间隙锁仅在 REPEATABLE READ 隔离级别下启用

- READ COMMITTED 下不会启用间隙锁。
- 在 RC 下，`SELECT ... FOR UPDATE` 不能防止幻读。

```sql
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
SELECT * FROM orders WHERE amount > 10 FOR UPDATE;
```

---

## 3. Next-Key Lock 是默认行为，不一定只加记录锁

- Next-Key Lock = 行锁 + 前间隙锁
- 除非使用**唯一索引 + 精确等值匹配**，否则 InnoDB 会默认使用 Next-Key Lock

```sql
-- 精确匹配主键，加纯记录锁
SELECT * FROM orders WHERE id = 1 FOR UPDATE;
```

---

## 4. 死锁（Deadlock）

- 两个事务交叉持锁，互相等待，造成死锁。
- InnoDB 会自动检测死锁并回滚其中一个事务。

```sql
-- 会话A
START TRANSACTION;
UPDATE user SET name = 'A' WHERE id = 1;

-- 会话B
START TRANSACTION;
UPDATE user SET name = 'B' WHERE id = 2;

-- 会话A
UPDATE user SET name = 'A2' WHERE id = 2;

-- 会话B
UPDATE user SET name = 'B2' WHERE id = 1;
-- ⚠️ 死锁发生！
```

**建议**：
- 尽量保证加锁顺序一致
- 控制事务大小和持锁时间

---

## 5. 隐式表锁可能被触发

- 条件未走索引，或范围过宽，InnoDB 会主动使用表锁
- 行锁数量超限，也可能自动升级为表锁

---

## 6. 大事务延迟锁释放

- InnoDB 使用两阶段锁协议：执行时加锁，提交后释放
- 大事务占锁时间长，影响其他事务并发和性能

**建议**：
- 拆小事务、尽快提交
- 写前读后，减少锁冲突

---

## 7. RC + FOR UPDATE 不等于可重复读

- 在 RC 隔离级别下，即使加了 `FOR UPDATE`，也不能保证数据一致性
- 因为 `Read View` 每次查询都会更新

---

## 8. 外键约束可能引发锁冲突

- 删除父表记录会锁子表做一致性校验
- 多事务同时操作外键关联表，容易出现隐式锁、阻塞或死锁

---

## ✅ 常见锁问题汇总表

| 问题                             | 说明                         | 建议                         |
|----------------------------------|------------------------------|------------------------------|
| 没走索引导致表锁                 | 锁粒度放大，性能差            | 确保 WHERE 命中索引         |
| 死锁                             | 事务交叉持锁引发              | 保持加锁顺序一致             |
| 大事务长时间占锁                 | 影响并发，易死锁              | 拆小事务，尽快提交           |
| 间隙锁阻塞插入                   | 插入被卡，事务等待            | 明确隔离级别和加锁策略       |
| SELECT 不加锁                    | 数据可能已变                  | 用 `FOR UPDATE` 或乐观锁控制 |
| 多事务插入相邻值时发生死锁       | 索引页竞争                    | 控制插入顺序或加随机间隔     |
