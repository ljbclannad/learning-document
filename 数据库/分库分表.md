# 1. Shardingsphere基础配置文件
```
spring:
  shardingsphere:
    datasource:
      names: ds0, ds1

      ds0:
        url: jdbc:mysql://localhost:3306/db0?useSSL=false&serverTimezone=UTC
        username: root
        password: root
        driver-class-name: com.mysql.cj.jdbc.Driver

      ds1:
        url: jdbc:mysql://localhost:3306/db1?useSSL=false&serverTimezone=UTC
        username: root
        password: root
        driver-class-name: com.mysql.cj.jdbc.Driver

    rules:
      sharding:
        tables:
          b_check_in_customer_sport:
            actual-data-nodes: ds${0..1}.b_check_in_customer_sport_${202401..202412}
            database-strategy:
              standard:
                sharding-column: customer_id
                sharding-algorithm-name: db-hash
            table-strategy:
              standard:
                sharding-column: check_in_date
                sharding-algorithm-name: table-date

        sharding-algorithms:
          db-hash:
            type: HASH_MOD
            props:
              sharding-count: 2

          table-date:
            type: CLASS_BASED
            props:
              strategy: standard
              algorithmClassName: com.example.sharding.DateShardingAlgorithm

    props:
      sql-show: true

```

# 2. shardingsphere触发union all的情况
在使用 **ShardingSphere-JDBC 分库分表** 时，有些查询会触发 **`UNION ALL` 合并执行**，这通常是 ShardingSphere 自动生成的逻辑，表示：

> ⚠️ **这个 SQL 涉及多个分片表，ShardingSphere 无法定位到唯一的目标表，因此会拆成多张表的 SQL 再用 `UNION ALL` 合并结果。**

---

## 🔍 常见会触发 `UNION ALL` 的场景

---

### ✅ 场景 1：**未传分片字段**

比如你配置了按照 `check_in_date` 分表，但你写的 SQL 是：

```sql
SELECT * FROM b_check_in_customer_sport WHERE sport_type = '有氧运动';
```

- ❌ **没有带 `check_in_date`（分表字段）**
- ✅ ShardingSphere 无法判断该查哪一张表，只能：
    - 查 `b_check_in_customer_sport_202401`
    - 查 `b_check_in_customer_sport_202402`
    - …
    - 全查一遍，然后 `UNION ALL`

---

### ✅ 场景 2：**多分片键中缺失其中之一**

比如你配置了：

- 分库字段：`customer_id`
- 分表字段：`check_in_date`

你写的 SQL：

```sql
SELECT * FROM b_check_in_customer_sport WHERE customer_id = 'cust_001';
```

- ✅ 有分库字段 → 能定位库
- ❌ 没有分表字段 → 表不知道查哪个，只能所有分表都查

所以会变成：

```sql
SELECT * FROM b_check_in_customer_sport_202401 WHERE customer_id = 'cust_001'
UNION ALL
SELECT * FROM b_check_in_customer_sport_202402 WHERE customer_id = 'cust_001'
UNION ALL
...
```

---

### ✅ 场景 3：范围查询 / LIKE 查询

```sql
SELECT * FROM b_check_in_customer_sport WHERE check_in_date >= '2024-01-01';
```

- ❌ 范围值 → 会命中多个表 → 触发多个 SQL + `UNION ALL`

---

## 🔥 那怎么避免呢？

---

### ✅ 方式 1：**强烈建议 WHERE 条件中包含分库、分表字段**

```sql
SELECT * FROM b_check_in_customer_sport 
WHERE customer_id = 'cust_001' 
  AND check_in_date = '2024-03-20';
```

- ✅ 能唯一定位：哪个库 + 哪张表
- ✅ ShardingSphere 只执行 1 条 SQL，效率最高！

---

### ✅ 方式 2：控制好分页等查询场景

分页时也建议加上分片字段：

```sql
SELECT * FROM b_check_in_customer_sport 
WHERE check_in_date = '2024-03-20'
ORDER BY create_time 
LIMIT 10 OFFSET 0;
```

---

### ✅ 方式 3：避免在分表表上做聚合（可考虑中间表）

例如：

```sql
SELECT SUM(kcal) FROM b_check_in_customer_sport;
```

会触发全分表计算。

✅ 优化方式：

- 做中间表或汇总表
- 用作业任务合并
- 避免直接全表聚合查询

---

## ✅ 查看真实 SQL 执行（是否触发 `UNION ALL`）

打开 SQL 日志：

```yaml
spring:
  shardingsphere:
    props:
      sql-show: true
```

你会看到类似：

```
Actual SQL: ds0 ::: SELECT * FROM b_check_in_customer_sport_202401 ...
Actual SQL: ds0 ::: SELECT * FROM b_check_in_customer_sport_202402 ...
```

ShardingSphere 自动用多个 SQL 分发并最终 `UNION ALL` 合并结果。

---

## ✅ 总结：避免 `UNION ALL` 的最佳实践

|建议 ✅|原因|
|---|---|
|查询中必须包含所有分片键|让 SQL 精确路由到目标库表|
|避免模糊匹配、范围查询|避免跨表扫描|
|聚合/汇总操作放在业务处理或汇总表中执行|提升效率，避免全库全表扫描|
|分页查询时也建议传分片字段|降低路由范围|
