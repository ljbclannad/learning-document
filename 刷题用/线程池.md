为什么要使用线程池：

```
1. **降低资源消耗**：通过池化技术重复利用已创建的线程，降低线程创建和销毁造成的损耗。
1. **提高响应速度**：任务到达时，无需等待线程创建即可立即执行。
1. **提高线程的可管理性**：线程是稀缺资源，如果无限制创建，不仅会消耗系统资源，还会因为线程的不合理分布导致资源调度失衡，降低系统的稳定性。使用线程池可以进行统一的分配、调优和监控。
1. **提供更多更强大的功能**：线程池具备可拓展性，允许开发人员向其中增加更多的功能。比如延时定时线程池ScheduledThreadPoolExecutor，就允许任务延期执行或定期执行。
```



线程池解决的问题是什么：

```
1. 频繁申请/销毁资源和调度资源，将带来额外的消耗，可能会非常巨大。
1. 对资源无限申请缺少抑制手段，易引发系统资源耗尽的风险。
1. 系统无法合理管理内部的资源分布，会降低系统的稳定性。
```



线程池的几种类型：

```
 1. newFiexedThreadPool：固定数目线程的线程池
  	1. 核心线程数量和最大线程数量相同，keepAliveTime为0，阻塞队列采用无界队列
  	2. 流程：提交任务，如果小于coolPoolSize则执行任务，如果大于则添加至阻塞队列，等待执行
  	3. 由于采用的是无界的消息队列，如果前置任务执行时间过长，并且在往队列中不断的添加新的任务，可能会导致out of memory（oom）
 2. newCacheThreadPool:拥有缓存的线程池
  	1. 核心线程数量为0，最大线程数量为2的31次-1，阻塞队列采用syncronousQueue，非核心线程存活时间为60s
  	2. 提交任务，由于没有coolPoolSize，直接将任务提交到队列，判断是否有空余非核心线程，如果有则新建一个线程去执行，如果非核心线程空闲的时间超过60s就回收线程
  	3. 适用于并发执行量较大但是比较短期的小任务
 3. newSignleThreadPool:核心线程数为1的线程池：
  	1. 核心线程数量和最大线程数量都为1，采用无界的消息队列，不存在keepAliveTime
  	2. 如果线程池有一个线程存在，就将任务提交到阻塞队列，如果没有直接执行，一次只能执行一条
  	3. 适用于串行执行任务的流程
 4. newScheduledThreadPool(int corePoolSize):
  	1. 核心线程数量手动设置，最大线程数量为2的31次-1，阻塞队列是delayedWorkQueue，keepAliveTime为0
  	2. 线程池中的线程从 DelayQueue 中取任务,线程从 DelayQueue 中获取 time 大于等于当前时间的task,执行完后修改这个 task 的 time 为下次被执行的时间,这个 task 放回DelayQueue队列中
```



线程池的几个参数：

```
    CoolPoolSize:核心线程数量

​	MaximumPoolSize:线程池最大线程数量

​	keepAliveTime:线程池中除核心线程之外的线程存活时间

​	unit:keepAliveTime的单位

​	WorkQueue:采用的队列

​	ThreadFactory:用户设置创建线程的工程

​	handler:线程数量满时的拒绝策略
```



线程池创建任务的流程：

​	

```
    提交一个任务，如果当前线程数小于coolPoolSize,直接添加至核心线程

​	如果当前线程数大于coolPoolSize并且阻塞队列没有满，添加任务到阻塞队列

​	如果阻塞队列已满，但是maximumPoolSize未满，创建非核心线程执行

​	如果超过maximumPoolSize:执行拒绝策略
```



线程池的workQueue：

```
    syncronousQueue:直接提交的队列

​	ArrayBlockingQueue:有界的队列

​	LinekedBlockingQueue:无界的队列

​	delayQueue:（延迟队列）是一个任务定时周期的延迟执行的队列。根据指定的执行时间从小到大排序，否则根据插入到队列的先后排序。newScheduledThreadPool线程池使用了这个队列。
```



线程池的拒绝策略，如果要手动创建策略该怎么操作:

​	

```
    AbortPolicy:直接拒绝

​	DiscardPolicy:删除当前任务

​	DiscardOldestPolicy:删除最先的任务

​	CallerRunsPolicy:使用新线程执行
```



线程池的状态：

​	

```
 RUNNING：该状态的线程池会接收新任务，并处理阻塞队列中的任务

​	SHUTDOWN：该状态的线程池不会接收新任务，但会处理阻塞队列中的任务，队列为空，并且线程池中执行的任务也为空,进入TIDYING状态;

​	STOP：该状态的线程不会接收新任务，也不会处理阻塞队列中的任务，而且会中断正在运行的任务；

​	TIDYING：该状态表明所有的任务已经运行终止，记录的任务数量为0。

​	TERMINATED：该状态表示线程池彻底终止
```

如何确认线程池的大小：

​	

```
 CPU密集型： 这种任务消耗的主要是 CPU 资源，可以将线程数设置为 N（CPU 核心数）+1，比 CPU 核心数多出来的一个线程是为了防止线程偶发的缺页中断，或者其它原因导致的任务暂停而带来的影响。一旦任务暂停，CPU 就会处于空闲状态，而在这种情况下多出来的一个线程就可以充分利用 CPU 的空闲时间。

​	I/O 密集型任务(2N)： 这种任务应用起来，系统会用大部分的时间来处理 I/O 交互，而线程在处理 I/O 的时间段内不会占用 CPU 来处理，这时就可以将 CPU 交出给其它线程使用。因此在 I/O 密集型任务的应用中，我们可以多配置一些线程，具体的计算方法是 2N。

可以动态设置线程池大小
```



线程池的的核心设计：

​	

```
 线程池核心实现类是ThreadPoolExecutor，UML为ThreadPoolExecutor继承AbstractExecutorService，实现ExecutorService,实现Executor。

​	顶层接口Executor提供了一种思想：将任务提交和任务执行进行解耦。用户无需关注如何创建线程，如何调度线程来执行任务，用户只需提供Runnable对象，将任务的运行逻辑提交到执行器(Executor)中，由Executor框架完成线程的调配和任务的执行部分。

​	ExecutorService接口中增加了一些能力：扩充执行任务的能力，补充可以为一个或一批异步任务生成Future的方法（提供submit方法）；

​	最下层的ThreadPoolExecutor实现最复杂的运行部分，ThreadPoolExecutor一方面维护自身的生命周期，另一方面同时管理线程和任务
```

​	生命周期管理：

​	线程池运行的状态是伴随着线程池的运行由内部维护的，线程池使用两个变量维护：运行状态(Runstate)和线程数量（workerCount）

​	private final AtomicInteger ctl = new AtomicInteger(ctlOf(RUNNING, 0));

​	`ctl`这个AtomicInteger类型，是对线程池的运行状态和线程池中有效线程的数量进行控制的一个字段， 它同时包含两部分的信息：线程池的运行状态 (runState) 和线程池内有效线程的数量 (workerCount)，高3位保存runState，低29位保存workerCount，两个变量之间互不干扰。

​	内部获取生命周期状态，获取线程池数量的计算方法如下：

```
private static int runStateOf(int c)     { return c & ~CAPACITY; } //计算当前运行状态
private static int workerCountOf(int c)  { return c & CAPACITY; }  //计算当前线程数量
private static int ctlOf(int rs, int wc) { return rs | wc; }   //通过状态和线程数生成ctl
```
