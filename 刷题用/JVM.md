## 1. 运行时数据区域：
1. 线程公有的：
    - 堆：此内存区域的唯一目的就是用来存放对象实例，几乎所有的对象实例以及数组都在这里分配内存。Java 堆是垃圾收集器管理的主要区域，因此也被称作GC 堆（Garbage Collected Heap）
    - 方法区：它用于存储已被虚拟机加载的类信息、常量、静态变量、即时编译器编译后的代码等数据。
    - 运行时常量：运行时常量：JDK1.7 及之后版本的 JVM 已经将运行时常量池从方法区中移了出来，在 Java 堆（Heap）中开辟了一块区域存放运行时常量池。（1.8之后开辟出来称为元空间）
    -  为什么用元空间替代永久代？
	    - 永久代的问题：
		    - 永久代大小固定（可通过 -XX:PermSize 和 -XX:MaxPermSize 设置），容易因为类加载过多导致 OutOfMemoryError。
		    - 管理困难，需要频繁调整大小。
		- 元空间的优势：
			- 使用本地内存（Native Memory），不受堆内存限制。
			- 自动扩展：只要本地内存充足，元空间可以动态调整大小。
2. 线程私有的：
    1. 程序计数器：字节码解释器通过改变程序计数器来依次读取指令，从而实现代码的流程控制，如：顺序执行、选择、循环、异常处理。在多线程的情况下，程序计数器用于记录当前线程执行的位置，从而当线程被切换回来的时候能够知道该线程上次运行到哪儿了。程序计数器私有主要是为了线程切换后能恢复到正确的执行位置。
    2. 虚拟机栈：局部变量，操作栈，动态连接，返回地址等部分
    3. 局部变量：用来存储临时8个基本数据类型，对象引用地址
    4. 操作栈：操作数栈就是用来操作的，例如代码中有个 i = 66，他在一开始的时候就会进行操作，读取我们的代码，进行计算后再放入局部变量表中去
        1. 动态链接：假如我方法中，有个 service.add()方法，要链接到别的方法中去，这就是动态链接，存储链接的地方。
        2. 出口：出口正常的话就是return 不正常的话就是抛出异常
    5. 本地方法栈：虚拟机使用到的 Native 方法服务
3. 静态变量放在方法区，静态的对象放在堆中
4. 内存溢出：在申请内存时没有足够的内存够其使用
5. 内存泄漏：无法释放已申请的内存空间，内存泄漏会导致内存溢出
6. 内存溢出的分类：
    1. JAVA堆溢出：只要不断的创建对象，并且保证GC ROOTS到对象之间有可达路径来避免垃圾回收机制清除这些对象。那么在对象数量达到最大堆的容量限制后就会产生内存溢出异常
    2. 虚拟机栈和本地方法栈溢出：
        1. 如果线程请求的栈深度大于虚拟机所允许的最大深度，将抛出StackOverFlowError异常
        2. 如果虚拟机在扩展栈时无法申请到足够的内存空间，则抛出OutOfMemoryError异常。
        3. 在单个线程下，无论是栈帧太大还是虚拟机容量太小，当内存无法分配时，抛出的都是StackOverFlowError异常。
        4. 为每个线程分配的内存越大，就越容易产生内存溢出异常。（可建立的线程数量变少，容易把剩下的内存耗尽）
    3. 方法区和运行时常量溢出
        1. 方法区存放类名，访问修饰符，常量池，方法描述等，基本的思路是运行时产生大量的类
        2. 本机直接内存溢出-XX:MaxDirectMemorySize指定容量。
7. String s1 = new String("abc");这句话创建了几个字符串对象？
    1. 将创建 1 或 2 个字符串。如果池中已存在字符串常量“abc”，则只会在堆空间创建一个字符串对象“abc”。如果池中没有字符串常量“abc”，那么它将首先在池中创建，然后在堆空间中创建，因此将创建总共 2 个字符串对象

## 2. java堆内存空间：

1. eden,s0(Survivor From),s1 (Survivor To),tentired，其中新生代和老年代的比例一般为1：2，新生代中的各个空间比例又为8:1:1
2. minorGC（清理新生代）：
    1. 首先，把Eden和SurvivorFrom区域中存活的对象复制到SurvicorTo区域（如果有对象的年龄以及达到了老年的标准，则赋值到老年代区），同时把这些对象的年龄+1（如果ServicorTo不够位置了就放到老年区）
    2. 清空eden和SurvivorFrom空间
    3. 将SurvicorTo的内容转移到SurvivorFrom，原ServicorTo成为下一次GC时的ServicorFrom区
4. 为什么新生代要分Eden和两个 Survivor 区域？
    1. Survivor的存在意义，就是减少被送到老年代的对象，进而减少Full GC的发生，Survivor的预筛选保证，只有经历15次Minor GC还能在新生代中存活的对象，才会被送到老年代。
    2. 设置两个Survivor区最大的好处就是解决了碎片化，刚刚新建的对象在Eden中，经历一次Minor GC，Eden中的存活对象就会被移动到第一块survivor space S0，Eden被清空；等Eden区再满了，就再触发一次Minor GC，Eden和S0中的存活对象又会被复制送入第二块survivor space S1
5. 对象分配规则：
    1. 对象优先分配在eden区：
        1. 当 eden 区没有足够空间进行分配时，虚拟机将发起一次 Minor GC.新生代 GC（Minor GC）:指发生新生代的的垃圾收集动作，Minor GC 非常频繁，回收速度一般也比较快。
    2. 大对象优先分配在老年区：
        1. 目的是为了避免eden区和两个survivor区之间产生大量的内存复制
        2. 为了避免为大对象分配内存时由于分配担保机制带来的复制而降低效率。如果不分配给老年区的话，可能会存在eden区大小不够，进行了minor GC,复制到survivor的时候survivor空间不足，会产生分配担保，分配至老年代
    3. 长期存活的对象将进入老年代：
        1. 虚拟机给每个对象一个对象年龄（Age）计数器。如果对象在 Eden 出生并经过第一次 Minor GC 后仍然能够存活，并且能被 Survivor 容纳的话，将被移动到 Survivor 空间中，并将对象年龄设为 1.对象在 Survivor 中每熬过一次 MinorGC,年龄就增加 1 岁，当它的年龄增加到一定程度（默认为 15 岁），就会被晋升到老年代中。
        2. 设置年龄过小导致老年代内存过大，设置年龄过大导致eden容易满，发生fullGc
6. 空间分配担保：
    1. 在发生Minor GC时（前），虚拟机会检测之前每次晋升到老年代的平均大小（因为当次会有多少对象会存活是无法确定的，所以取之前的平均值/经验值）是否大于老年代的剩余空间大小，如果大于，则改为直接进行一次Full GC。如果小于，则查看HandlePromotionFailure设置是否允许担保失败；如果允许，那只会进行Minor GC；如果不允许，则也要改为进行一次Full GC。取平均值进行比较其实仍然是一种动态概率手段，也就是说如果某次Minor GC存活后的对象突增，远远高于平均值的话，依然会导致担保失败（Handle Promotion Failure），这样会触发Full GC。
7. 判断对象是否死亡：
    1. 引用计数法：给对象中添加一个引用计数器，每当有一个地方引用它，计数器就加 1；当引用失效，计数器就减 1；任何时候计数器为 0 的对象就是不可能再被使用的。
    2. 可达性分析算法：这个算法的基本思想就是通过一系列的称为 “GC Roots” 的对象作为起点，从这些节点开始向下搜索，节点所走过的路径称为引用链，当一个对象到 GC Roots 没有任何引用链相连的话，则证明此对象是不可用的。可作用GC Roots的对象包括下面几种：虚拟机栈中引用的对象，方法区中类静态属性引用的对象，方法去中常量引用的对象，本地方法栈中native的对象
    3. 要宣告一个对象死亡，至少需要两次标记过程：如果没有和GCroots相连的引用链，则会标记第一次并进行一次筛选，筛选是否有必要执行finalized()，当对象没有覆盖finalized或者已经被虚拟机调用过，就为没有必要执行，判断为对象死亡。
    4. 如果需要执行finalize(),可以在方法中尝试与引用链上的任意一个对象关联起来即可，譬如把自己赋值给某个变量，但是一个系统只会自动调用一次finalized
8. 引用的四种类型：
    1. 强引用：那就类似于必不可少的生活用品，垃圾回收器绝不会回收它。
    2. 软引用：可有可无的生活用品。如果内存空间足够，垃圾回收器就不会回收它，如果内存空间不足了，就会回收这些对象的内存
    3. 弱引用：弱引用与软引用的区别在于：只具有弱引用的对象拥有更短暂的生命周期。在垃圾回收器线程扫描它所管辖的内存区域的过程中，一旦发现了只具有弱引用的对象，不管当前内存空间足够与否，都会回收它的内存。
    4. 虚引用：在任何时候都可能被垃圾回收。
    5. **强引用 (Strong Reference)**:
    
       - 默认的引用方式，例如`Object obj = new Object();`。
       - 对象只要有强引用存在，就永远不会被回收。
       - **场景**：几乎所有普通对象都属于强引用。可以通过对象池或者设置为null。
    
       **软引用 (Soft Reference)**:
    
       - 通过`SoftReference`类实现。
       - 对象会在内存不足时被GC回收，可用于内存敏感的数据缓存。
       - **场景**：图片缓存、数据缓存。
    
       **弱引用 (Weak Reference)**:
    
       - 通过`WeakReference`类实现。
       - GC会在下一次垃圾回收时回收弱引用对象。
       - **场景**：弱引用被用于`WeakHashMap`，实现内存敏感的键值对存储。
    
       **虚引用 (Phantom Reference)**:
    
       - 通过`PhantomReference`类实现。
       - 不能单独使用，必须和`ReferenceQueue`结合，用于跟踪对象的生命周期。
       - **场景**：清理资源或监控对象回收。

## 3. 垃圾收集算法：

1. 标记-清除算法：该算法分为“标记”和“清除”阶段：首先标记出所有需要回收的对象，在标记完成后统一回收所有被标记的对象。它是最基础的收集算法，后续的算法都是对其不足进行改进得到，会有大量空间碎片
2. 复制算法：为了解决效率问题，“复制”收集算法出现了。它可以将内存分为大小相同的两块，每次使用其中的一块。当这一块的内存使用完后，就将还存活的对象复制到另一块去，然后再把使用的空间一次清理掉。
3. 每次使用eden和其中一块survivor，将eden和survivor上刚才存活的对象一次性的复制到另外一个survivor上，如果survivor内存不足，则会依赖老年代进行分配担保
4. 标记-整理算法：标记过程仍然与“标记-清除”算法一样，但后续步骤不是直接对可回收对象回收，而是让所有存活的对象向一端移动，然后直接清理掉端边界以外的内存。效率较低
5. 分代收集算法：一般将 java 堆分为新生代和老年代，这样我们就可以根据各个年代的特点选择合适的垃圾收集算法。（新生代用复制，老年代用标记清除）
	1. 老年代用标记清除原理：老年代对象存活时间长、存活比例高。标记-清除算法不需要频繁移动对象，适合老年代。内存碎片问题可以通过优化和整理算法解决。
	2. 新生代用复制原理：
		1. 回收效率高：**垃圾回收主要清理短命对象**：由于大多数对象在新生代中是短命的，所以存活对象数量很少。**复制效率高**：复制存活对象的成本低，直接清空内存效率比标记-清除或标记-整理算法更高
		2. 避免空间碎片：复制算法通过将存活对象移动到另一块内存空间，保持内存连续性，不会产生碎片。对新生代频繁分配和释放对象的场景非常有利。
		3. 实现简单：复制算法只需要两个对等大小的内存空间，逻辑相对简单。- 不需要复杂的标记和清理操作，适合新生代频繁 GC 的需求。

## 4. 收集器

1. Serial收集器：新生代收集器:单线程的收集器，对于限定单个CPU的环境来说，serial收集器由于没有线程的交互，可以获得最高的单线程收集效率。
2. ParNew收集器：新生代收集器：在serial收集器的基础上使用了多线程进行垃圾收集，可以用-XX:parallelGCThreads参数来限制垃圾收集的线程数
3. paraller（pei re lao） Scavenge收集器：是一个新生代收集器，关注于吞吐量（运行用户代码时间/运行用户代码时间+垃圾收集时间），其他垃圾收集器关注于缩短垃圾收集的线程停顿时间，停顿时间越短就适合需要与用户交互的程序，良好的响应时间能提升用户的体验。而高吞吐量则可以高效率的利用CPU，用于后台计算。
    1. 2个参数：控制最大垃圾收集停顿时间的-XX:MaxGCPauseMills（不是越小越好，越小可能会导致垃圾回收频率加快，减少吞吐量）
    2. -XX:GCTimeRatio参数可以直接设置吞吐量：是垃圾收集时间占总时间的比率，相当于吞吐量的倒数。即运行用户代码时间/垃圾回收时间，如果为19，说明运行代码时间为19，垃圾回收时间为1，吞吐量为19/（1+19）
    3. -GC自适应的调节策略：-XX：+UseAdpativeSizePolicy，当开关打开时，会动态调整参数以提供最合适的停顿时间或最大的吞吐量。也是paraller Scavenge收集器与Parnew收集器的一个重要区别
4. serial Old收集器：是serial收集器的老年代版本。
5. paraller old收集器：是paraller scavenge收集器的老年代版本，
6. CMS收集器：CMS是基于标记-清除算法，运行步骤：
    1. 初始标记。暂停所有的其他线程，并记录下直接与 root 相连的对象，速度很快;
    2. 并发标记。同时开启 GC 和用户线程，用一个闭包结构去记录可达对象。但在这个阶段结束，这个闭包结构并不能保证包含当前所有的可达对象。因为用户线程可能会不断的更新引用域，所以 GC 线程无法保证可达性分析的实时性。所以这个算法里会跟踪记录这些发生引用更新的地方。重新标记。
    3. 重新标记阶段就是为了修正并发标记期间因为用户程序继续运行而导致标记产生变动的那一部分对象的标记记录，这个阶段的停顿时间一般会比初始标记阶段的时间稍长，远远比并发标记阶段时间短
    4. 并发清除。开启用户线程，同时 GC 线程开始对为标记的区域做清扫。
    5. 初始标记和重新标记仍然属于单线程，并发标记和并发清除可以和用户一起操作
    6. CMS的缺点：
        1. CMS可能会占有一部分线程导致应用程序变慢，默认为（CPU数量+3）/4，如果CPU数量不足4的时候，对应用程序的影响就很大
        2. .CMS无法处理浮动垃圾：在标记过程之后产生的垃圾，需要在下一次GC时再清理称为浮动垃圾（产生的原因是因为在进行CMS收集时，用户应用程序还在运行）
        3. **CMS是基于“标记-清除”算法实现的收集器：标记-清除算法的缺点是会产生大量的空间碎片**，空间碎片过多时，可能会导致老年代没有足够大的连续空间来存放大对象，不得不触发一次full gc。
    7. G1收集器:
        1. 运行步骤
            1. 初始标记
            2. 并发标记
            3. 最终标记
            4. 清除阶段
        2. 允许并发和并行
        3. 允许分代收集
        4. 不会产生空间碎片，分配对象时不会因为找不到连续内存空间而触发GC。由于G1使用了独立区域（Region）概念，G1从整体来看是基于“标记-整理”算法实现收集，从局部（两个Region）上来看是基于“复制”算法实现的，但无论如何，这两种算法都意味着G1运作期间不会产生内存空间碎片。
        5. 可预测的停顿。
            1. 在G1之前的收集器进行收集的范围都是整个新生代或者老年代，但是使用G1时，将堆内容布局分为多个大小相等的独立区域，新生代和老年代不再隔离，都是一部分不需要连续的集合
            2. 初始标记和最终标记时都会产生stw，最后标记是为了处理在并发标记时由于代码原因重新失效的数据
    8. 什么时候触发GC：		
        1. 程序调用system.gc时触发
        2. 大多数情况下，对象在新生代Eden区中分配，当Eden区没有足够空间进行分配时，虚拟机将发起一次Minor GC；同理，当老年代中没有足够的内存空间来存放对象时，虚拟机会发起一次Major GC/Full GC。只要老年代的连续空间大于新生代对象总大小或者历次晋升的平均大小就会进行Minor GC，否则将进行Full CG（要满足分配担保）。
    9. GC调优:
        1. GC调优的目的：将转移到老年代的对象数量降低到最小； 减少 GC 的执行时间。减少STW（STOP THE WORD）
        2. GC调优策略：
            1. 将新对象预留在新生代。由于 Full GC 的成本远高于 Minor GC（复制算法和标记清除算法），因此尽可能将对象分配在新生代是明智的做法，减少fullGC
            2. 大对象进入老年代。-XX:PretenureSizeThreshold 可以设置直接进入老年代的对象大小。
            3. 设立设置老年代年龄：-XX:MaxTenuringThreshold 设置对象进入老年代的年龄大小，减少老年代的内存占用，降低 full gc 发生的频率。
            4. 设置稳定的堆大小（过小的eden会增加GC次数，过大的eden会增加GC时间，过小的老年代会增加fullGC次数）
            5. 如果没有STW，中途线程可能结束释放对象引用，导致在fullGC时部分对象可能变为垃圾对象，影响fullGC
        3. 能否对JAVA虚拟机调优，让系统几乎不发起fullGC:调大年轻代
    10. 单服务器高并发：
        1. 单服务器配置要高，年轻代老年代空间大，但是由于空间大，垃圾收集时寻找垃圾时间过长，stw时间过长，导致系统卡顿时间长，这时候需要修改使用的垃圾收集器
        2. 可以采用分批GC，年轻代一定的大小就触发GC，采用G1收集器，设置MaxGCPauseMillis（目标）
    11. 对象的创建流程：
        1. 类加载检查：虚拟机遇到一条 new 指令时，首先将去检查这个指令的参数是否能在常量池中定位到这个类的符号引用，并且检查这个符号引用代表的类是否已被加载过、解析和初始化过。如果没有，那必须先执行相应的类加载过程。
        2. 分配内存：在类加载检查通过后，接下来虚拟机将为新生对象分配内存。
        3. 初始化零值：内存分配完成后，虚拟机需要将分配到的内存空间都初始化为零值（不包括对象头）
        4. 设置对象头：初始化零值完成之后，虚拟机要对对象进行必要的设置，例如这个对象是那个类的实例、如何才能找到类的元数据信息、对象的哈希码、对象的 GC 分代年龄等信息。 这些信息存放在对象头中。
        5. 执行init：在上面工作都完成之后，从虚拟机的视角来看，一个新的对象已经产生了，但从 Java 程序的视角来看，对象创建才刚开始， 方法还没有执行，所有的字段都还为零。所以一般来说，执行 new 指令之后会接着执行方法，
        6. 把对象按照程序员的意愿进行初始化类加载的时机：​		
            1. 遇到new指令时
            2. 利用reflect包的方法进行反射调用时，如果类没有初始化，则需要先触发初始化
            3. 当初始化一个类时，发现父类没有初始化，则需要先复发父类的初始化。​
            4. 当虚拟机启动时，用户需要指定一个要执行的主类（包含main()）的那个方法。类加载过程：加载-链接-初始化 链接包括验证-准备-解析​	
                1. 加载： 这个阶段会在内存中生成一个代表这个类的 java.lang.Class 对象（字节码指令）， 作为方法区这个类的各种数据的入口。​		
                2. 验证：确保 Class 文件的字节流中包含的信息是否符合当前虚拟机的要求​
                    1. 文件格式验证：字节流是否符合Class文件格式的规范，并且能被当前的虚拟机处理。

                    3. 字节码验证：对类的方法体进行校验验证，保证被校验类的方法在运行时不会做出危害虚拟机安全的事件​
                    4. 符号引用的校验：类似于能否在符号引用中的方法（private,public,protected,default）是否可以被当前类访问。
                3. 准备：在方法区分配这些变量所使用的空间，并设置0值，类似于（int value =123），在这步是value=0​
                4. 解析：虚拟机将常量池中的符号引用替换为直接引用的过程​
                    1. 符号引用：可以是任何形式的字面量，只要使用时能定位到目标即可。
                    2. 直接引用：可以直接指向指针，偏移量等目标​,在java中，一个java类将会编译成一个class文件。在编译时，java类并不知道引用类的实际内存地址，因此只能使用符号引用来代替。比如org.simple.People类引用org.simple.Tool类，在编译时People类并不知道Tool类的实际内存地址，因此只能使用符号org.simple.Tool(假设)来表示Tool类的地址。而在类装载器装载People类时，此时可以通过虚拟机获取Tool类 的实际内存地址，因此便可以既将符号org.simple.Tool替换为Tool类的实际内存地址，及直接引用地址。​
                5. 初始化：到了初始阶段，才开始真正执行类中定义的 Java 程序代码，如果一个类中没有对静态变量赋值也没有静态语句块，那么编译器可以不为这个类生成()方法类加载器：

                    2. 只有在两个类是由同一个类加载器加载的前提下才有意义。​
                    3. 启动类加载器：负责加载 JAVA_HOME\lib 目录中的， 或通过-Xbootclasspath 参数指定路径中的， 且被虚拟机认可（按文件名识别， 如 rt.jar） 的类​

                    5. 应用程序类加载器：负责加载用户路径（classpath）上的类库​

## 5. 收集器详解

Java提供了多种垃圾收集器（Garbage Collectors），用于自动管理内存中的对象回收。每种垃圾收集器适用于不同的场景，具有独特的优缺点。

------

### **1. 垃圾收集器分类**

Java垃圾收集器可根据工作机制分为以下几类：

| **分类**           | **代表垃圾收集器**           |
| ------------------ | ---------------------------- |
| **串行垃圾收集器** | Serial GC                    |
| **并行垃圾收集器** | Parallel GC                  |
| **并发垃圾收集器** | CMS（Concurrent Mark-Sweep） |
| **低延迟收集器**   | G1（Garbage-First） GC       |
| **现代收集器**     | ZGC、Shenandoah GC           |

------

### **2. 各垃圾收集器详解**

#### **2.1 Serial GC**

- 特点：

  - 单线程垃圾收集器。
  - 适合单核CPU、内存较小的场景。
  - 在垃圾回收期间会暂停所有应用线程（Stop-The-World，STW）。

- 应用场景：

  - 单线程程序或客户端模式。

- 启动参数：

  ```bash
  -XX:+UseSerialGC
  ```

------

#### **2.2 Parallel GC（并行垃圾收集器）**

- 特点：

  - 多线程垃圾收集器，默认适用于新生代和老年代。
  - 注重高吞吐量（Throughput），适合高并发、大数据量处理场景。
  - 新生代采用复制算法，老年代采用标记-整理算法。

- 应用场景：

  - 后台任务较多，对延迟要求不高的服务。

- 启动参数：

  ```bash
  -XX:+UseParallelGC
  ```

------

#### **2.3 CMS（Concurrent Mark-Sweep）**

- 特点：

  - 主要用于低延迟应用。
  - 采用“标记-清除”算法进行老年代的垃圾回收。
  - 并发标记和清除阶段不会完全暂停应用线程。
  - 缺点：容易产生内存碎片。

- 工作流程：

  1. **初始标记（Initial Mark）：** 标记GC Roots直接可达的对象，STW。
  2. **并发标记（Concurrent Mark）：** 多线程标记可达对象。
  3. **重新标记（Remark）：** 修正并发标记期间发生的引用变化，STW。
  4. **并发清除（Concurrent Sweep）：** 清除不可达对象。

- 应用场景：

  - 注重低延迟的Web应用。

- 启动参数：

  ```bash
  -XX:+UseConcMarkSweepGC
  ```

------

#### **2.4 G1（Garbage-First）GC**

- 特点：

  - 默认收集器（Java 9及以上）。
  - 分为多个独立的内存区域（Region），每个Region可以是Eden、Survivor或Old区。
  - 通过分代收集和增量式整理，减少STW的时间。
  - 可预测GC暂停时间（可通过`-XX:MaxGCPauseMillis`设置）。

- 工作流程：

  1. 标记阶段：标记出存活对象。
  2. 复制阶段：将存活对象复制到新的Region中。
  3. 混合收集：回收部分老年代Region。

- 应用场景：

  - 大内存、低延迟的应用。

- 启动参数：

  ```bash
  -XX:+UseG1GC
  ```

------

#### **2.5 ZGC（Z Garbage Collector）**

- 特点：

  - 极低延迟，最大暂停时间通常小于10ms。
  - 使用“标记-整理”算法，支持TB级内存。
  - 并发处理几乎所有的垃圾回收任务。

- 应用场景：

  - 超大内存应用，要求低延迟的场景。

- 启动参数：

  ```bash
  -XX:+UseZGC
  ```

------

#### **2.6 Shenandoah GC**

- 特点：

  - 类似于ZGC，注重低延迟。
  - 通过并发压缩内存减少停顿时间。
  - 暂停时间与堆大小无关。

- 应用场景：

  - 高并发、大内存应用。

- 启动参数：

  ```bash
  -XX:+UseShenandoahGC
  ```

------

### **3. 垃圾收集器选择**

| **收集器**        | **优势**                   | **劣势**                   | **适用场景**             |
| ----------------- | -------------------------- | -------------------------- | ------------------------ |
| **Serial GC**     | 简单高效，低内存占用       | 暂停时间长，不支持并发     | 单线程应用，内存小       |
| **Parallel GC**   | 高吞吐量，多线程并行回收   | 停顿时间长                 | 高吞吐量需求的批处理系统 |
| **CMS**           | 低延迟                     | 容易产生碎片，停顿时间随机 | 延迟敏感的应用           |
| **G1 GC**         | 可预测低延迟，内存分区优化 | 复杂性高                   | 大内存低延迟应用         |
| **ZGC**           | 极低延迟，支持TB级内存     | 实现复杂，实验性功能       | 超大内存低延迟场景       |
| **Shenandoah GC** | 延迟低，与堆大小无关       | 实现复杂                   | 延迟敏感的高并发场景     |

------

### **4. 垃圾收集器调优**

1. **分析GC日志：**
   - 使用`-XX:+PrintGCDetails`打印详细GC日志。
   - 配合`jstat`、VisualVM、JMC等工具分析性能瓶颈。
2. **调整参数：**
   - 堆内存大小：`-Xms`和`-Xmx`。
   - 新生代与老年代比例：`-XX:NewRatio`。
   - GC暂停时间：`-XX:MaxGCPauseMillis`。
   - Full GC避免：减少系统资源耗尽。

------

### **总结**

- **选择垃圾收集器：** 根据具体应用场景选择合适的GC（如吞吐量、延迟、内存规模）。
- **调优：** 通过日志分析和参数调整，优化GC性能以满足应用需求。

# 6. 类加载和双亲委派
### **类加载（Class Loading）**

Java的类加载机制负责将类的字节码文件（`.class`文件）加载到内存，并转化为JVM可以识别的**类对象（Class对象）**。类加载过程是Java运行时动态实现的。

---

#### **1. 类加载过程**

类加载包括以下三个主要阶段：

1. **加载（Loading）：**
   
    - 通过类加载器（ClassLoader）将字节码文件加载到内存中。
    - 加载后的字节码被存储在方法区，并在堆中创建对应的`Class`对象。
2. **链接（Linking）：** 链接分为以下三步：
   
    - **验证（Verification）：** 验证字节码文件的格式、元数据的合法性和安全性。
    - **准备（Preparation）：** 为类的静态变量分配内存，并赋予默认初值。
    - **解析（Resolution）：** 将类、字段和方法的符号引用解析为直接引用。
3. **初始化（Initialization）：**
   
    - 执行类的静态初始化块和静态变量的赋值操作。
    - 只有在真正使用类时（如访问静态字段或调用静态方法）才触发初始化。

---

#### **2. 类加载时机**

类加载不是一次性加载所有类，而是根据需要动态加载。以下情况会触发类的加载：

- 创建类的实例（`new`）。
- 访问类的静态字段或静态方法。
- 反射（`Class.forName`）。
- 子类加载时先加载父类。
- JVM启动时加载入口类（`public static void main`所在类）。

---

### **双亲委派模型**

**双亲委派模型（Parent Delegation Model）**是Java类加载机制的核心设计，它规定了类加载器的工作方式：  
当一个类加载器尝试加载类时，它会首先将请求委托给它的父加载器，只有在父加载器无法完成加载时，才由当前加载器自己加载。

---

#### **1. 类加载器的层次结构**

JVM中的类加载器按层次划分为以下三种：

1. **Bootstrap ClassLoader（启动类加载器）：**
   
    - JVM内置，用于加载核心类库（如`rt.jar`）。
    - 不由Java实现，使用本地代码实现（C/C++）。
2. **Extension ClassLoader（扩展类加载器）：**
   
    - 加载`lib/ext`目录下的扩展类库。
    - 由Java实现，父加载器为启动类加载器。
3. **Application ClassLoader（应用类加载器）：**
   
    - 加载应用程序类路径（`CLASSPATH`）下的类。
    - 默认加载用户代码。

此外，开发者可以自定义类加载器（Custom ClassLoader）来实现特殊需求。

---

#### **2. 双亲委派模型的工作原理**

双亲委派的工作机制如下：

1. 当前类加载器接收到加载类的请求。
2. 它将加载请求委托给父加载器。
3. 如果父加载器能够加载该类，则直接返回。
4. 如果父加载器无法加载，则由当前加载器尝试加载。

---

#### **3. 双亲委派的好处**

1. **避免类重复加载：**
   
    - 保证一个类在内存中只有一个定义。
    - 例如，核心类库中的类（如`java.lang.String`）始终由Bootstrap ClassLoader加载，避免自定义加载器重新定义。
2. **提高安全性：**
   
    - 防止用户代码加载和覆盖JDK核心类。
    - 例如，防止用户自定义一个`java.lang.Object`类。
3. **模块化与扩展性：**
   
    - 不同的类加载器加载各自范围的类，便于扩展。

---

#### **4. 双亲委派模型的破坏与使用场景**

双亲委派机制在某些情况下可能会被破坏，常见的场景包括：

1. **自定义类加载器：**
   
    - 某些框架（如Tomcat、OSGi）需要自定义类加载器来隔离不同模块的类加载。
2. **打破双亲委派：**
   
    - 某些类需要由当前加载器优先加载，而不是由父加载器加载。
    - 例如`SPI（Service Provider Interface）`机制中，服务提供者的类通常由应用类加载器直接加载。
3. **破坏实现：**
   
    - 重写`ClassLoader`的`findClass`或`loadClass`方法。

---

#### **5. 示例代码：自定义类加载器**

```java
import java.io.*;

public class MyClassLoader extends ClassLoader {
    private String classPath;

    public MyClassLoader(String classPath) {
        this.classPath = classPath;
    }

    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        try {
            byte[] classData = loadClassData(name);
            if (classData == null) {
                throw new ClassNotFoundException();
            }
            return defineClass(name, classData, 0, classData.length);
        } catch (IOException e) {
            throw new ClassNotFoundException(name, e);
        }
    }

    private byte[] loadClassData(String className) throws IOException {
        String fileName = classPath + className.replace('.', '/') + ".class";
        InputStream inputStream = new FileInputStream(fileName);
        ByteArrayOutputStream outputStream = new ByteArrayOutputStream();
        int len;
        while ((len = inputStream.read()) != -1) {
            outputStream.write(len);
        }
        inputStream.close();
        return outputStream.toByteArray();
    }

    public static void main(String[] args) throws Exception {
        MyClassLoader classLoader = new MyClassLoader("/path/to/classes/");
        Class<?> clazz = classLoader.loadClass("com.example.MyClass");
        Object obj = clazz.newInstance();
        System.out.println("Class loaded by: " + clazz.getClassLoader());
    }
}
```

---

### **总结**

- **类加载机制**通过加载、链接、初始化三个阶段，将类的字节码文件加载到JVM。
- **双亲委派模型**通过委托机制提高了类加载的安全性和一致性。
- 在特定场景下，可以通过自定义类加载器实现更灵活的类加载逻辑，但需要小心破坏双亲委派可能导致的安全问题。

# 7. 为什么 G1 GC 使用 Humongous Region 来管理大对象？这种设计如何优化大对象的管理？

### **1. 为什么 G1 使用 Humongous Region？**

1. **分区化管理：**
    
    - G1 GC 将堆划分为多个固定大小的 **Region**（通常为 1MB 或 2MB）。
    - 每个 Region 可以充当 **Eden 区**、**Survivor 区** 或 **Old 区**。
    - 大对象（**Humongous Object**）是指其大小超过单个 Region 的容量。
2. **Humongous Region 的设计：**
    
    - 为了管理大对象，G1 引入了 **Humongous Region**。
    - 一个大对象会占用连续的多个 Humongous Region（类似“超级块”），并且这些 Region 会被标记为 **Humongous**。
    - 这避免了大对象分布在老年代时可能造成的内存碎片问题。
3. **减少 GC 次数：**
    
    - 因为 Humongous Region 是独立管理的，当大对象生命周期结束时，只需要回收这些 Region，而不是遍历整个堆。

---

### **2. G1 的大对象管理机制**

1. **大对象直接进入老年代：**
    
    - 大对象通常会直接分配到老年代的 Humongous Region，避免频繁的 Minor GC。
2. **回收 Humongous Region：**
    
    - G1 的垃圾回收基于 **Region 的回收成本**，如果 Humongous Region 的回收收益较高（如大对象已无引用），G1 会优先回收这些 Region。
3. **避免内存碎片：**
    
    - 传统老年代的标记-清除算法容易导致内存碎片问题，而 Humongous Region 通过连续的分配和回收策略，显著降低了碎片化的可能性。

---

### **3. 优化大对象分配的建议**

1. **调整 Region 大小：**
    
    - 使用 `-XX:G1HeapRegionSize` 参数调整 Region 大小（1MB 到 32MB）。
        
        ```bash
        -XX:G1HeapRegionSize=2M
        ```
        
    - Region 大小越大，大对象就越少占用多个 Region，减少内存管理开销。
2. **监控和分析大对象：**
    
    - 启用 GC 日志，查看 Humongous Region 的分配和回收情况：
        
        ```bash
        -Xlog:gc+humongous=debug
        ```
        
3. **代码层面的优化：**
    
    - 避免分配不必要的大对象，例如：
        - 优化大数组的初始化和使用。
        - 使用合适的数据结构（如 `ArrayList` 代替 `HashMap`，根据需求）。
    - 分块处理大数据，减少单次分配的内存量。

---

### **4. G1 的 Humongous Region 与传统老年代的对比**

|**特性**|**传统老年代**|**G1 的 Humongous Region**|
|---|---|---|
|**大对象存储位置**|老年代中的内存块|独立的连续 Humongous Region|
|**内存碎片问题**|容易产生内存碎片|减少内存碎片，连续分配和回收|
|**GC 回收策略**|标记-清除或标记-整理|按收益优先回收 Humongous Region|
|**调优复杂度**|难以控制大对象对老年代的影响|通过 Region 大小和 G1 参数灵活调优|

# 8. 怎么处理大对象
### **1. 分解大对象**

1. **分块处理：**
    
    - 将大对象（如大数组或字符串）分解成多个小块，分别存储或处理。
    - **示例：处理大数组**
        
        ```java
        public class ChunkProcessor {
            public void processLargeArray(int[] largeArray) {
                int chunkSize = 1000; // 每次处理1000个元素
                for (int i = 0; i < largeArray.length; i += chunkSize) {
                    int end = Math.min(i + chunkSize, largeArray.length);
                    int[] chunk = new int[end - i];
                    System.arraycopy(largeArray, i, chunk, 0, end - i);
                    processChunk(chunk);
                }
            }
        
            private void processChunk(int[] chunk) {
                // 执行具体的处理逻辑
            }
        }
        ```
        
2. **分段存储：**
    
    - 对于需要长期保留的大对象（如缓存中的大数据），将其分解成多个部分分别存储在多个数据结构中，减少堆内存的占用。

---

### **2. 控制分配速率**

1. **限流机制：**
    
    - 通过队列或令牌桶机制控制大对象的分配速率，避免瞬时分配过多大对象导致 GC 频繁。
    - **示例：令牌桶限流**
        
        ```java
        public class RateLimiter {
            private final Semaphore semaphore;
        
            public RateLimiter(int maxPermits) {
                this.semaphore = new Semaphore(maxPermits);
            }
        
            public boolean tryAllocate() {
                return semaphore.tryAcquire();
            }
        
            public void release() {
                semaphore.release();
            }
        }
        ```
        
2. **任务调度：**
    
    - 将大对象的创建分摊到多个时间片中，避免同时分配多个大对象导致 GC 压力。

---

### **3. 内存池优化**

1. **对象复用：**
    
    - 使用对象池管理大对象，减少频繁创建和销毁大对象的开销。
    - **示例：大对象池**
        
        ```java
        public class LargeObjectPool {
            private final Queue<byte[]> pool = new LinkedList<>();
        
            public byte[] borrow(int size) {
                if (!pool.isEmpty()) {
                    return pool.poll();
                }
                return new byte[size]; // 分配新的大对象
            }
        
            public void release(byte[] object) {
                pool.offer(object);
            }
        }
        ```
        
2. **预分配内存：**
    
    - 在程序启动时，预分配部分大对象的内存，减少运行时频繁的内存分配。

---

### **4. 数据分布与外部存储**

1. **分布式处理：**
    
    - 将大对象的处理分布到多个节点中，利用分布式系统的内存和计算资源。
    - **示例：将大对象切片后分发到消息队列中供不同节点处理。**
2. **外部存储：**
    
    - 将大对象存储在磁盘、数据库或分布式存储系统中，只在需要时加载到内存中。
    - **示例：使用 Redis、HBase 等分布式存储系统来保存大对象。**

---

### **5. 使用更高效的数据结构**

1. **压缩存储：**
    
    - 对大对象的数据进行压缩，例如对字符串或文件使用 GZIP 压缩后再存储。
    - **示例：使用 ByteBuffer 存储高效的二进制数据。**
2. **精简数据结构：**
    
    - 优化大对象的字段，移除不必要的数据。

---

### **6. G1 GC 调优的配合**

1. **优化 Region 大小：**
    
    - 调整 `-XX:G1HeapRegionSize`，避免大对象占用过多 Region。
        
        ```bash
        -XX:G1HeapRegionSize=2M
        ```
        
2. **监控 Humongous Region：**
    
    - 通过 GC 日志或工具（如 VisualVM）监控大对象在 Humongous Region 的分配情况，动态调整参数。

---

### **总结**

在频繁分配大对象的场景中，可以从以下几个方面优化：

1. **减少单次分配的内存量：** 通过分块处理或分段存储优化大对象的分配方式。
2. **控制分配频率：** 使用限流或调度机制，减少大对象的并发分配。
3. **提高内存复用率：** 使用对象池或预分配机制复用大对象。
4. **引入分布式和外部存储：** 减少对 JVM 堆内存的依赖。
5. **结合 G1 GC 调优：** 通过调整 Region 大小和参数，减少大对象对垃圾回收的影响。

通过这些手段，可以有效缓解频繁分配大对象对系统性能的影响，同时提升内存管理的效率。

# 9.什么是 Stop-The-World（STW）？哪些场景会触发 STW？如何优化 STW 的影响？

### **1. 什么是 Stop-The-World（STW）？**

**STW** 是指 JVM 在执行某些操作时，会暂停所有应用线程（用户线程），只允许 GC 线程或其他 JVM 内部线程运行。这种暂停是为了确保内存一致性和安全性。

- **本质：** STW 是由 JVM 自动触发的，开发者无法直接控制，但可以通过调优来减少其影响。
- **影响：**
    - STW 会导致应用程序暂停，用户无法感知程序运行。
    - 在延迟敏感的应用（如 Web 服务）中，过长的 STW 会显著影响用户体验。

---

### **2. 哪些场景会触发 STW？**

#### **2.1 垃圾回收（GC）**

1. **新生代 GC（Minor GC）：**
    
    - Eden 区满时触发。
    - 需要暂停所有线程以标记和复制存活对象。
    - 通常暂停时间较短。
2. **老年代 GC（Major GC 或 Full GC）：**
    
    - 老年代空间不足或触发全堆 GC 时触发。
    - 由于扫描整个堆并清理，STW 时间较长。
3. **并发垃圾收集器的标记阶段：**
    
    - 如 **CMS GC** 的初始标记和重新标记阶段，或 **G1 GC** 的初始标记和最终标记阶段。

#### **2.2 类加载**

- 加载类或静态变量初始化时可能触发 STW，尤其是当大量类在运行时动态加载时（如反射操作）。

#### **2.3 内存快照**

- JVM 生成堆快照（Heap Dump）或线程快照（Thread Dump）时，暂停所有线程以确保一致性。

#### **2.4 锁竞争**

- 在 JVM 内部出现死锁或高竞争时，也可能引发类似 STW 的暂停行为。

---

### **3. 如何优化 STW 的影响？**

#### **3.1 使用低延迟垃圾收集器**

选择合适的垃圾收集器是减少 STW 影响的关键：

1. **CMS GC（Concurrent Mark-Sweep）：**
    - 减少老年代 GC 的停顿时间，但可能产生内存碎片。
    - 启用参数：
        
        ```bash
        -XX:+UseConcMarkSweepGC
        ```
        
2. **G1 GC（Garbage-First）：**
    - 通过分区和并行回收降低 STW 时间。
    - 可设置目标暂停时间：
        
        ```bash
        -XX:+UseG1GC
        -XX:MaxGCPauseMillis=200
        ```
        
3. **ZGC（Z Garbage Collector）：**
    - 极低延迟，STW 时间通常小于 10ms，适合延迟敏感的大内存应用。
    - 启用参数：
        
        ```bash
        -XX:+UseZGC
        ```
        

---

#### **3.2 调整内存分配**

1. **增大堆内存：**
    
    - 减少 GC 的频率，延长 Minor GC 和 Major GC 的触发间隔：
        
        ```bash
        -Xms1G -Xmx2G
        ```
        
2. **调整新生代和老年代比例：**
    
    - 增大新生代（`-XX:NewRatio`）或 Survivor 区大小（`-XX:SurvivorRatio`），减少晋升到老年代的对象数量。
3. **减少对象分配频率：**
    
    - 优化代码，减少无用对象的创建，避免临时对象大量堆积。

---

#### **3.3 调整 GC 参数**

1. **降低 Full GC 触发概率：**
    
    - 提高老年代使用率的阈值（CMS 中可用 `-XX:CMSInitiatingOccupancyFraction` 参数）。
2. **优化大对象分配：**
    
    - 设置大对象直接进入老年代，避免新生代频繁触发 GC：
        
        ```bash
        -XX:PretenureSizeThreshold=1M
        ```
        
3. **延长对象晋升到老年代的时间：**
    
    - 通过调整 `-XX:MaxTenuringThreshold`，让对象尽可能留在新生代。

---

#### **3.4 监控和调优**

1. **启用 GC 日志：**
    
    - 观察 STW 时间和 GC 频率：
        
        ```bash
        -Xlog:gc*:file=gc.log:time,uptime,level,tags
        ```
        
2. **使用监控工具：**
    
    - 使用 VisualVM、JConsole 或 Java Mission Control 查看 STW 时间和线程暂停情况。

---

### **4. 总结**

- **STW 是 JVM 内存管理的必要机制，无法完全避免，但可以优化其时间和频率。**
- **核心优化思路：**
    1. 选择合适的垃圾收集器（如 G1、ZGC）。
    2. 调整内存配置，减少 GC 触发。
    3. 监控应用内存使用情况，优化代码中的对象分配逻辑。

# 10. G1垃圾收集器工作原理详解
G1（Garbage First）收集器是 Java 的一种垃圾收集器，旨在提供高效的垃圾回收性能，特别是在大内存和低延迟场景下使用。它的设计目标是替代 CMS 收集器，减少垃圾回收的停顿时间（STW，Stop-The-World）并提高整体吞吐量。

---
### **1. G1 收集器的内存划分**

G1 将堆划分为多个大小固定的 **Region**，每个 Region 是一块连续的内存空间。所有的内存都分布在这些 Region 中，而不再严格区分 Eden 区、Survivor 区和老年代。

- **Region 类型**：
    - **Eden 区**：分配新对象的区域。
    - **Survivor 区**：存放从 Eden 区晋升的存活对象。
    - **老年代区**：存放生命周期较长的对象。
    - **Humongous 区**：存放大对象（超过 Region 大小 50% 的对象）。

---

### **2. G1 的垃圾回收目标**

G1 的核心目标是 **低延迟垃圾回收**，其主要机制是通过增量式垃圾回收和优先处理垃圾最多的区域（Region）来达到目标。

- **设定停顿时间目标**： 用户可以通过参数配置期望的垃圾回收最大停顿时间（如 `-XX:MaxGCPauseMillis=200`），G1 会尝试在此时间内完成垃圾回收。

---

### **3. G1 的工作流程**

G1 的工作流程可以分为以下几个阶段：

#### **（1）年轻代垃圾回收（Young GC）**

- **触发条件**：Eden 区填满时触发。
- **回收内容**：回收 Eden 区的所有垃圾对象，并将存活对象复制到 Survivor 区或老年代。
- **特点**：
    - 采用并行回收，停顿时间较短。
    - 存活对象较少，复制效率高。

#### **（2）并发标记（Concurrent Marking）**

并发标记是 G1 的老年代回收机制，类似 CMS 收集器的标记阶段，用于标记老年代的存活对象。

1. **初始标记阶段（Initial Marking）**：
    
    - 标记从 GC Root 可达的对象。
    - 发生在 Young GC 时，伴随一次短暂的 STW。
2. **并发标记阶段（Concurrent Marking）**：
    
    - 在应用线程运行的同时，遍历老年代的 Region 并标记存活对象。
    - 此阶段不会暂停应用线程。
3. **最终标记阶段（Final Marking）**：
    
    - 完成剩余的标记工作，并计算各个 Region 的垃圾比例。
    - 伴随一次短暂的 STW。
4. **筛选回收阶段（Cleanup）**：
    
    - 根据标记结果，优先回收垃圾最多的 Region。
    - 更新 Region 状态，可能需要短暂的停顿。

#### **（3）混合垃圾回收（Mixed GC）**

- **触发条件**：老年代垃圾过多或堆内存即将耗尽时。
- **回收内容**：同时回收年轻代（Eden 和 Survivor）和部分老年代的 Region。
- **特点**：
    - 根据并发标记的结果，优先选择垃圾比例最高的老年代 Region。
    - 停顿时间受目标停顿时间控制（`MaxGCPauseMillis`）。

#### **（4）Humongous 区回收**

- Humongous 区用于存放超大对象（如大数组、大字符串）。
- 若 Humongous 区占用过多，也可能触发 Full GC。

#### **（5）Full GC**

- **触发条件**：当 G1 无法满足内存分配需求时。
- **回收内容**：对整个堆进行垃圾回收。
- **特点**：通常由单线程完成，停顿时间较长，应尽量避免。

---

### **4. G1 的优先级机制**

G1 的名字 **Garbage First** 反映了它的核心思想：**优先回收垃圾最多的区域**。

- **优先选择高收益的 Region**：
    - 每个 Region 都会计算其垃圾比例（垃圾对象占用的内存比例）。
    - 优先选择垃圾比例高的 Region 进行回收，从而在有限的停顿时间内回收更多内存。

---

### **5. 参数调优**

#### 常见参数：

- `-XX:MaxGCPauseMillis=<N>`：设定最大停顿时间目标（默认 200 毫秒）。
- `-XX:InitiatingHeapOccupancyPercent=<N>`：设定并发标记的触发阈值（默认 45%）。
- `-XX:ParallelGCThreads=<N>`：设置 GC 并行线程数量。
- `-XX:G1HeapRegionSize=<N>`：设置 Region 大小（默认 1MB～32MB）。

---

### **6. 优点与缺点**

#### **优点**：

1. **低延迟**：通过分阶段回收和控制 STW 时间，实现较低的垃圾回收延迟。
2. **空间整合**：采用标记-整理算法，减少内存碎片问题。
3. **高吞吐量**：优先回收垃圾最多的 Region，提高回收效率。

#### **缺点**：

1. **复杂性**：G1 的内部实现复杂，调优难度较高。
2. **吞吐量可能低于 Parallel GC**：在某些高吞吐量场景下，可能不如 Parallel GC 高效。

---

### **7. 总结**

G1 收集器通过分区和优先级回收机制，将垃圾回收的延迟和停顿时间控制在可接受范围内，非常适合大内存和对响应时间敏感的应用场景。其工作流程核心是 **年轻代回收、并发标记和混合回收**，并结合用户设置的目标停顿时间进行优化。
