ddd的核心思想：

​	解耦与聚合，即原来需要多方协作的业务，比如订单系统，你订单系统设计的时候需要建议商品表，支付表等，久而久之你下一个订单的业务中掺杂着许多本不属于订单的代码（比如操作商品，操作余额），ddd就是为了解耦这种情况，将商品等作为订单的一个属性（值对象或者实体进行跨领域业务编排），内部只有订单的操作，如需再操作商品的时候增加逻辑仅需在商品的领域模型中自行处理，不需要再在订单领域模型中处理，减少Service的臃肿和不易维护。（这一步和微服务很像，但是ddd与微服务不同的点，说上去比较抽象，个人理解是数据行为的差距，微服务是从表结构出发编写代码，微服务这种模型会导致产生贫血模型，而ddd是通过业务出发，设计了领域模型，保证了充血模型）



领域驱动设计的优势：

​	降低复杂度，service只是用来编排业务的功能，具体功能都通过各自的领域进行实现，分而治之

​	增加可维护性和可读性

​	结构清晰，代码充实

​	与MVC最大的区别就是service层和领域，采用事件驱动



贫血模型：

​	针对业务生成多个POJO对象，一个复杂的业务可能需要定义多个对象，这类对象中大多数只有GET和SET方法，不包含依赖持久层的业务逻辑，优点是方便阅读，简单易编写，但是业务一旦庞大POJO数量过于多

​	大部分情况下，我们开发的系统业务可能都比较简单，简单到就是基于SQL 的 CRUD 操作，所以，我们根本不需要动脑子精心设计充血模型，贫血模型就足以应付这种简单业务的开发工作。



充血模型：

​	充血模型是领域模式中存在的一个概念，包含了所有的业务逻辑

与贫血模型的区别就是针对领域的操作都在domin领域中实现，（通过Bind方式）,各个POJO都可以使用一个领域的方法解决



MVC的开发逻辑：

​	需求-》研发需求-》数据库结构-》代码层实现-》最终产物

​	OOP：面向对象变成，遇到新需求时往往考虑优先建立表结构，再通过表类的方法进行业务填充（贫血模型）



领域模型的开发逻辑：

​	需求-》研发需求-》业务确认-》领域模型-》仓储管理，业务修改时仅增加领域的行为即可

​	DDD：在遇到新需求时设立各个领域，将一个需求拆分给不同领域组合完成。（充血模型）



领域模型中的组件介绍：

​	实体：实体具有唯一标识，类似于ID，属性是可变的，可通过表结构中的关联字段实现

​	值对象：不可变的，没有唯一标识，区分实体和值对象为了强壮领域模型

​	聚合：聚合是领域对象的显式分组，旨在支持领域模型的行为和不变性，同时充当一致性和事务性边界。类似于订单，单独领域中的独体

​	领域事件

​	应用服务层：应用层通过应用服务接口来暴露系统的全部功能。负责编排和转发

编排有2种情况：直接调用其他领域的应用服务及事件监听，如果有强绑定关系（类似于需要应用结果进行后续操作的走调用，通知等异步操作可以使用事件监听）

​	工厂层：数据模型转换层，包括PO，DTO，和聚合之间的转换，抽象

​	仓储：在领域模型中定义（归属各个领域，划分界限），在基础设施层中实现，使用Mybatis-plus或者mybatis实现，仓储只能查询自己领域的内容，减少sql返回数据多样化，不够清晰	

​	基础设施层：所有与具体平台、框架相关的实现会在infrastructure中提供。与domin领域事件的区别：domin是最底层的内容，用于处理业务逻辑(修改状态等可以定义方法修改领域的属性值)，与数据层交互需要交给基础设施层处理

​	

CQRS 在 DDD 中是一种常常被提及的模式，它的用途在于将领域模型与查询功能进行分离，让一些复杂的查询摆脱领域模型的限制，以更为简单的 DTO 形式展现查询结果。同时分离了不同的数据存储结构，让开发者按照查询的功能与要求更加自由的选择数据存储引擎。ddd刚好满足CQRS的思想，自身设计时采用queryapplication及application区分读写，是一种思想



事件驱动模型：

​	假设有一个业务需求，创建订单，需要下发优惠券，正常的调用service也能实现，那为啥要用事件驱动模型：如果双11需要赠送小礼品等操作，需要在创建订单操作时拼接很多业务逻辑，双11结束又需要注释，来来回回代码会变的越来越冗余，在这个案例中，当第一步创建订单成功之后，发布一个创建订单成功的领域时间，其他积分领域，礼品领域等监听这个时间，实现代码解耦

​	Spring提供的事件驱动机制：

​	监听事件使用@EventListener

​	发送事件使用ApplicationEventPublisher.publishEvent

​	@TransactionalEventListener	事务触发时间：BEFORE_COMMIT，AFTER_COMMIT，AFTER_ROLLBACK，AFTER_COMPLETION

​	

事件划分之后可以在不影响主要业务逻辑的同时进行事务单独管理。可做降级处理



幂等：

​	业务开发中，经常会遇到重复提交的情况，无论是由于网络问题无法收到请求结果而重新发起请求，或是前端的操作抖动而造成重复提交情况。

​	比如用户在APP上连续点击了多次提交订单，后台应该只产生一个订单；向支付宝发起支付请求，由于网络问题或系统BUG重发，支付宝应该只扣一次钱。

什么情况下需要保证幂等性：

1. `SELECT col1 FROM tab1 WHER col2=2`，无论执行多少次都不会改变状态，是天然的幂等。
2. `UPDATE tab1 SET col1=1 WHERE col2=2`，无论执行**成功**多少次**状态**都是一致的，因此也是幂等操作。
3. `UPDATE tab1 SET col1=col1+1 WHERE col2=2`，每次执行的结果都会发生变化，这种不是幂等的。

实现幂等的操作：

​	首先去查询上一次的执行状态，如果没有则认为是第一次请求

​	设置全局唯一ID

​	创建去重表：这种方法适用于在业务中有唯一标的插入场景中，比如在以上的支付场景中，如果一个订单只会支付一次，所以订单ID可以作为唯一标识。这时，我们就可以建一张去重表，并且把唯一标识作为唯一索引，在我们实现时，把创建支付单据和写入去去重表，放在一个事务中，如果重复创建，数据库会抛出唯一约束异常，操作就会回滚。





DDD改造的个人经验总结：

 	1. 当初提出DDD改造的时候，网上查阅各种文章，大多数文章都是理论化，领域设计，六边形架构等。怎么看怎么懵逼。真的是听君一席话如听一席话，后来总结下ddd其实就是一个设计思想，思想的核心是将我们的代码解耦（当然微服务也能做到），行为绑定（这点我觉得是个人处理下来感触最深的一点）。
 	2. 平台代码实践时步骤：
     	1. 将原来的代码划分各个领域（根据业务划分），将各个领域先建立不同的Controller，根据对各个业务的熟悉程度安排开发
     	2. 正式着手，个人方面：按照CQRS原则优先处理查询逻辑，将原来的查询Service进行解耦，建立自己领域的查询，涉及其他领域的查询写上TODO处理
     	3. 查询编写：建立一个通用的仓储PO，建立一个Convernt，所有关于领域查询的全部只返回PO，再由PO转换成domin或者响应的DTO，转化方法在Convernt类中编写，易懂且易维护，一般很少存在需要返回其他领域字段的情况，如果有，也可以通过domin中的实体或者值对象进行转化返回给前端，这样子就完成了查询，同时将原来到处连表查询等操作转为各个领域的原子操作（解耦）,整体调用步骤为：Controller->QueryApplication->queryRespority->mapper（由于mybatis-plus的原因，queryMapper被舍弃）。
     	4. 业务代码编写：通过Command接受需要操作的内容（针对这个领域，如你要修改这个订单，command就传入这个订单的信息）。在application中对原来的Service进行业务编排。如果需要进行业务操作，通过领域的bind方法（一般行为可能通过直接写update set SQL语句进行操作，不直观，行为直接绑定在领域上，体现了充血模型）进行修改，然后调用save方法直接入库。
     	5. 整体可根据demo展示一下ddd的架构迁移，PO,DTO,domin要区分好，代码规范要写的规范
