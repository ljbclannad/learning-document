## 1. 个人价值

### 1.1 核心表达

1. 我将我的职业规划分为三部分，一为业务能力、二为技术深度、三为AI工程化能力
   1. 业务能力指的是业务理解能力，能迅速抓住核心目标、能主动补齐关键规则和边界、能识别业务风险、能提出下一步的优化。
   2. 技术深度：能构建出高性能、高可用、高扩展、高可观测性、高业务适配性的系统。
   3. AI工程化 能力：能合理使用Coding AI进行提效（包括编码、单测、问题排查）等，同时想要有AI应用落地的能力。

### 1.2 面试 QA

#### 1. 为什么离职？

1. 回答方向：
   - 主要是希望寻找一个更匹配长期发展的平台。上一段经历让我积累了后端开发、项目交付和问题处理经验，但我也希望后续能接触更复杂的业务场景，在系统设计、稳定性建设、工程效率方面继续提升。
   - 所以这次机会我会比较关注岗位内容、团队方向和自己的成长匹配度。
2. 注意点：
   - 不要抱怨前公司、前领导或团队。
   - 可以讲成长空间和岗位匹配，不要只讲薪资。

#### 2. 为什么选择我们公司或这个岗位？

1. 回答方向：
   - 我比较看重这个岗位和后端技术方向的匹配度。一方面岗位要求里的业务系统开发、接口设计、系统稳定性这些，和我之前的经验比较契合；另一方面我也希望进入一个有真实业务复杂度的团队，在交付中继续提升技术深度。
   - 如果团队后续有 AI 应用、研发效率提升或数据智能相关场景，我也希望能结合自己的后端和 AI 工程化经验参与落地。
2. 关键点：
   - 要体现提前了解过岗位。
   - 把“我能做什么”和“我想成长什么”结合起来。

#### 3. 你的职业规划是什么？

1. 回答方向：
   - 我的主线还是在后端技术方向持续深入。短期希望快速熟悉业务，做到独立负责模块、稳定交付；中期希望参与更复杂系统设计，比如性能优化、稳定性建设、分布式方案；长期希望成为既懂业务又有技术深度的人。
   - 同时我也会关注 AI 在研发效率和业务系统中的应用，不是为了追热点，而是看它能不能真正提升效率和业务价值。
2. 一句话收口：
   - 我希望自己后续不是只会写功能，而是能把业务理解、系统稳定性、工程效率和长期可维护性一起做好。

#### 4. 你怎么看技术成长？

1. 回答方向：
   - 我理解的技术成长，不是单纯学更多框架或者追新技术，而是解决问题的能力持续提升。
   - 初级阶段可能更多关注功能能不能实现；再往后就要关注代码质量、边界条件、性能、稳定性、可观测性、可维护性，以及这个方案对业务和团队效率有没有帮助。
2. 结合 AI：
   - AI 是一个很重要的能力增量，但我不会为了 AI 而 AI。对后端来说，更有价值的是把 AI 能力工程化落地，比如模型调用、上下文管理、RAG、权限控制、成本控制、效果评估和降级兜底。

#### 5. 你做过最有价值或最有挑战的项目是什么？

1. 回答结构：
   - 背景是什么。
   - 问题是什么。
   - 我负责什么。
   - 怎么解决。
   - 结果如何。
   - 复盘学到什么。
2. 示例表达：
   - 我印象比较深的是智能体重健康管家里的 AI 升级链路。它不是单纯调用一个大模型，而是要把患者对话、用户画像、长期记忆、任务升级、医生协同和风险控制串成一条稳定链路。
   - 业务准确性：引入画像、上下文、记忆机制。
   - 业务可用性：引入缓存、异步更新、单会话串行限流、上下文阈值截取、降级能力。
   - 业务可靠性：引入对话生命周期，高风险问题人工介入。
   - 业务可观测性：引入监控、审计、日志、人为干预能力。
   - 业务可扩展性：agent能力平台化，AI能力工程化。
   - 我主要负责把普通 AI 对话和医生助手 Agent 做分层整合，让患者消息先进入 `ai-chat-service` 做上下文、画像、记忆和分流判断，命中任务型场景时再升级到 `doctor-assistant-agent`。
   - 这个项目让我意识到，AI 应用真正难的不是模型能不能回复，而是怎么把不确定的模型能力收敛成可控、可降级、可观测的后端系统。在能力平台化的时候我终于有茅塞顿开的感觉，一个成熟的平台都具有：注册、生命周期、执行、编排、监测。

#### 6. 遇到线上问题你怎么处理？

1. 回答方向：
   - 我会先判断影响范围和严重程度，优先止损，比如回滚、降级、限流、临时修复或切换开关，保证业务先恢复。
   - 然后根据日志、监控、链路追踪、错误码和关键状态数据定位原因。
   - 问题恢复后会做复盘，包括根因、监控缺口、测试缺口、流程缺口和后续改进项，避免同类问题重复发生。
2. 关键词：
   - 先止损、再定位、后复盘。

#### 7. 如果项目延期了怎么办？

1. 回答方向：
   - 我不会等到最后才暴露风险。发现延期风险后，会先拆清楚原因，是需求变更、技术难点、依赖阻塞还是评估不足。
   - 然后及时同步相关方，说明影响范围，并给出可选方案，比如调整优先级、拆分版本、增加资源、压缩非核心范围。
2. 关键点：
   - 透明沟通。
   - 关键目标优先交付。
   - 不把风险藏到最后。

#### 8. 和产品、测试、前端意见不一致怎么办？

1. 回答方向：
   - 我会先确认分歧点到底是什么，是目标不一致、信息不完整，还是对成本和风险判断不同。
   - 然后尽量用事实和数据沟通，比如开发成本、线上风险、用户影响、排期影响。
   - 如果确实有多种方案，我会把优缺点讲清楚，推动大家基于业务优先级做选择，而不是单纯争对错。

#### 9. 你怎么看加班？

1. 回答方向：
   - 我能接受关键节点或线上问题时必要的加班，因为研发需要对交付和稳定性负责。
   - 但我也认为长期依赖加班不是最优解，还是要通过更好的计划、风险前置、流程优化和技术沉淀提高效率。
2. 一句话收口：
   - 我的态度是关键时候能顶上，平时也会关注怎么把事情做得更高效。

#### 10. 你觉得一个研发怎样才算靠谱？

1. 回答方向：
   - 我理解靠谱不只是代码能写出来，而是对结果负责。
   - 比如需求理解清楚，方案考虑边界和风险，开发过程中及时同步进度，遇到问题不隐瞒，交付后关注线上效果。
   - 如果发现历史问题，也能根据优先级推动优化，而不是只完成手上的任务。

#### 11. 你怎么看 AI 对研发的影响？

1. 回答方向：
   - 我觉得 AI 会明显提升研发效率，比如辅助编码、测试生成、日志分析、文档整理和知识检索。
   - 但它不会替代研发对业务、系统设计、稳定性和工程质量的判断。
   - 对后端来说，更重要的是理解 AI 能力如何工程化落地，比如模型调用、数据处理、权限控制、成本控制、效果评估和系统稳定性。
2. 一句话收口：
   - 我的态度是积极使用，但也要关注边界和实际价值。

#### 12. 如果让你重构现有系统，第一步你会做什么？你会先看哪些瓶颈？

1. 回答方向：
   - 我不会一上来就改代码，而是先把“为什么要重构”讲清楚。第一步通常是先做现状盘点：这套系统当前最影响业务的点到底是什么，是性能瓶颈、稳定性问题、迭代效率低，还是系统耦合过重导致改一处动全身。
   - 然后我会结合日志、监控、链路追踪、业务成功率、发布频率、故障记录，把问题分成几类：性能瓶颈、稳定性瓶颈、架构瓶颈、研发效率瓶颈。因为很多系统真正的问题，不是某个接口慢，而是链路过长、职责不清、同步调用太多、状态分散、缺少观测和灰度能力。
   - 在明确主瓶颈之前，我不会直接做大规模重写，而是优先选“收益最大、风险可控”的点切入，比如先拆主链路和扩散链路、先补监控和开关、先治理慢 SQL 和线程池，再决定要不要继续做更深层的架构调整。
2. 常见瓶颈可以这样讲：
   - 性能层面：慢 SQL、缓存命中率低、线程池阻塞、下游调用过多、同步链路太长。
   - 稳定性层面：没有限流降级、没有熔断隔离、异常补偿不足、发布不可灰度、问题不可回滚。
   - 架构层面：模块职责不清、服务边界混乱、强耦合同步调用太多、核心状态分散。
   - 工程层面：监控不完整、日志不可追踪、测试覆盖薄弱、上线过度依赖人工经验。
3. 一句话收口：
   - 我理解系统重构的第一步不是重写，而是先识别真正瓶颈，先把最影响业务和稳定性的点收敛清楚，再做分阶段演进。

#### 13. 在决定引入一项新技术时，你的决策流程是怎样的？怎么平衡前沿技术和业务稳定性？

1. 回答方向：
   - 我的判断顺序一般是四步：先看业务问题，再看技术是否真的匹配，再看接入成本和风险，最后看能不能小范围验证。
   - 第一，不会因为技术新就引入，而是先确认当前到底缺什么能力。比如是为了提升研发效率、降低延迟、增强可扩展性，还是为了增加 AI 场景能力。如果现有方案已经够用，我不会为了“技术先进”去增加系统复杂度。
   - 第二，会评估这项技术带来的收益和代价，包括学习成本、迁移成本、运维成本、团队掌握程度、社区成熟度、可观测性、故障处理难度，以及和现有技术栈的兼容性。
   - 第三，我更倾向于先做 PoC 或小流量试点，而不是一上来全量替换。比如新微服务框架会先在非核心模块验证吞吐、稳定性和治理能力；大模型能力会先在低风险场景验证效果、成本、时延、降级和人工兜底能力。
   - 第四，如果要正式落地，我会要求配套的灰度、监控、回滚、降级和评估机制一起到位。因为真正的风险通常不在“能不能跑起来”，而在“出问题时能不能及时收敛”。
2. 平衡方式可以这样讲：
   - 前沿技术可以积极关注，但生产落地一定要分层。核心交易链路优先稳定，创新能力先放在边缘场景、辅助场景或可灰度链路验证。
   - 对我来说，技术选型不是选最新，而是选当前阶段最合适、团队能驾驭、出了问题能兜住的方案。
   - 如果收益不够确定，我会先保守试点；如果收益明确，但风险较高，就通过隔离、灰度、开关和双轨并行来降低切换风险。
3. 一句话收口：
   - 我的原则是对新技术保持开放，但对生产系统保持敬畏，先验证价值，再控制风险，最后再逐步放量。

#### 17. 你做过的项目里，哪个最能体现你的个人价值？

1. 回答方向：
   - 这类题不要只讲“项目很大”或者“功能很多”，而要讲你在这个项目里到底解决了什么关键问题，以及没有你会怎样。
   - 我会优先讲智能体重管理项目里的 AI 升级链路，因为它比较能体现我不只是做功能，而是在业务、系统稳定性和工程化之间做平衡。
   - 这个项目的难点不是把模型接进来，而是要把患者对话、用户画像、长期记忆、任务升级、医生协同、风险控制、异步沉淀和降级能力收敛成一条真实可落地的链路。
   - 我在里面最有价值的部分，是把“普通聊天”和“任务型 Agent”分层，把轻链路和重链路拆开，同时补上缓存、MQ、降级、审计和人工兜底能力，让这套 AI 能力不是 demo，而是能进生产。
2. 回答时要落到结果：
   - 体现了业务价值：提高回答连续性、个性化和任务闭环能力。
   - 体现了工程价值：降低主链路复杂度，提升可观测性、可降级性和可恢复性。
   - 体现了个人价值：不仅能写模块代码，还能把一个复杂能力收敛成可交付、可治理的系统。
3. 一句话收口：
   - 我希望面试官感受到的不是“我做过 AI 项目”，而是“我能把复杂能力稳定地落到真实业务系统里”。

#### 18. 如果访问量突然涨 10 倍，你会优先看哪里？

1. 回答方向：
   - 我不会先说扩容，而是先判断瓶颈会先出现在入口、应用、缓存、数据库还是下游依赖。
   - 一般会先看几个关键指标：Gateway QPS 和 RT、应用线程池和 JVM、Redis 命中率、MySQL 连接池和慢 SQL、MQ 堆积、第三方接口超时率。
   - 如果系统本来就偏同步链路，我会重点看数据库和下游依赖，因为很多时候不是应用机器不够，而是连接池、慢 SQL、缓存回源和重试把后面打穿了。
2. 处理顺序可以这样讲：
   - 先止血：限流、降级、关闭非核心功能、拉长缓存 TTL、必要时做热点隔离。
   - 再扩容：应用副本、消费者、副本读能力按瓶颈点扩，不盲目整体放大。
   - 再做结构优化：缓存前置、异步削峰、线程池隔离、数据库索引和读写分流。
3. 一句话收口：
   - 流量涨 10 倍时，真正关键的不是“加多少机器”，而是先判断最先被打穿的是哪一层，然后按瓶颈点治理。

#### 19. 如果别人不认同你的方案，你怎么推进？

1. 回答方向：
   - 我不会一开始就把它当成“谁说服谁”，而是先确认分歧到底来自目标不同、信息不全，还是对风险和成本判断不同。
   - 然后我会尽量把讨论从观点拉回事实，比如业务收益、开发成本、线上风险、排期影响、回滚难度和后续维护成本。
   - 如果确实存在多种可行方案，我会把边界讲清楚，比如什么场景选 A，什么场景选 B，而不是非黑即白地争一个绝对正确。
2. 推进方式：
   - 小问题快速对齐，大问题拿数据、PoC 或灰度结果说话。
   - 对核心链路方案，优先考虑能不能保守落地、能不能分阶段推进，而不是一步到位。
   - 如果最终方案不是我最初主张的，只要决策过程合理、风险可控，我也会配合把结果做好。
3. 一句话收口：
   - 我更看重把事情往前推进，而不是证明自己是对的。

#### 20. 你怎么体现自己不是只写代码，而是在对结果负责？

1. 回答方向：
   - 我理解对结果负责，至少体现在四件事上：需求阶段能识别风险，方案阶段能考虑边界，开发阶段能及时同步问题，交付后能关注线上效果。
   - 比如我不会只把接口写完就结束，而是会继续关注监控、日志、成功率、异常补偿、灰度发布和回滚方案有没有准备好。
   - 如果发现历史问题影响当前链路，我也会推动一起治理，而不是说“这不是我负责的代码”就停下。
2. 可以结合项目讲：
   - 在 AI 链路里，我关注的不只是模型能不能回复，还关注上下文是否连续、风险场景是否可拦截、异步沉淀是否可恢复、故障时能不能降级到安全路径。
   - 在业务系统里，我也会更关注最终成功率、状态一致性和用户体验，而不是只看某个方法有没有跑通。
3. 一句话收口：
   - 我希望自己交付的不是一段代码，而是一个上线后还能稳定跑、出了问题也能收得住的结果。

#### 21. 你怎么做项目复盘？复盘最重要的产出是什么？

1. 回答方向：
   - 我理解复盘不是追责会，而是把一次问题或一次项目里的经验，沉淀成团队后面可复用的能力。
   - 一般我会复盘四件事：目标有没有达成、问题根因是什么、哪些风险其实可以提前发现、后续要补哪些机制。
   - 复盘时不会只停留在“某个人写错了”，而是继续往下看，是不是监控没补、测试没覆盖、流程没卡住、设计上本来就容易出问题。
2. 我更看重的复盘产出：
   - 能落地的改进项，比如补监控、补日志、补自动化测试、补压测、补 SOP、补灰度和回滚预案。
   - 哪些经验能沉淀成规范，比如接口幂等、线程池隔离、配置变更流程、第三方依赖降级策略。
   - 哪些认知要更新，比如过去默认稳定的组件现在已经成瓶颈，或者某类链路不适合继续同步推进。
3. 一句话收口：
   - 对我来说，复盘最重要的不是把问题解释清楚，而是让同类问题下次更难发生。

### 1.4 一句话人设

1. 我是一个后端基础扎实、愿意承担责任、重视交付质量的人。
2. 我不只关注技术实现，也关注业务结果、系统稳定性、团队协作和长期可维护性。
3. 短期我能快速融入团队并稳定交付，中长期希望承担更复杂的问题，在后端技术深度、业务理解和 AI 工程化方向持续成长。

## 2. 生产问题排查与上线闭环

### 2.1 总体思路

1. 我希望自己处理生产问题时，不是靠经验乱猜，而是形成一套可复用的闭环：
   1. **发现问题**：从告警、监控、日志、用户反馈或业务指标里确认异常。
   2. **定位问题**：先判断影响范围，再沿着入口、应用、缓存、数据库、MQ、下游依赖逐层收敛。
   3. **解决问题**：先止血恢复业务，再做根因修复，避免直接在线上做大改动。
   4. **发布到生产**：本地复现、测试环境验证、灰度发布、监控观察、保留回滚方案。
   5. **复盘沉淀**：补监控、补日志、补压测、补测试用例或自动化巡检，避免同类问题重复出现。
2. 面试里可以先说一句：
   - 我处理线上问题一般遵循“先止血、再定位、后修复、灰度上线、复盘沉淀”的顺序。因为生产问题最重要的不是马上证明谁对谁错，而是先控制影响面，然后用数据把根因找出来。

### 2.2 第一步：发现问题

1. **从用户侧发现**
   - 用户反馈接口慢、页面打不开、重复提交、支付状态不一致、AI 回复超时。
   - 这类问题要先拿到时间点、用户 ID、订单号、会话 ID、接口路径、错误截图或 traceId。

2. **从业务指标发现**
   - 挂号成功率下降。
   - 支付回调成功率下降。
   - AI 对话成功率下降。
   - 订单创建量突然下降。
   - MQ 消费延迟变大。
   - 业务指标比技术指标更接近真实影响，比如接口没有大量 500，但预约成功率下降，也一定要排查。

3. **从系统监控发现**
   - Gateway：QPS、4xx/5xx、P95/P99 RT、限流次数。
   - 应用：接口耗时、异常率、线程池队列、拒绝次数。
   - JVM：CPU、堆内存、Young GC、Full GC、线程数。
   - Redis：命中率、慢查询、热 key、大 key、连接数、内存、网络流量。
   - MySQL：慢 SQL、连接池等待、锁等待、CPU/IO、主从延迟。
   - RabbitMQ：`messages_ready`、`messages_unacked`、publish rate、ack rate、消费者错误率。
   - 下游依赖：Feign 调用 RT、超时率、熔断次数、重试次数。

4. **发现阶段不要急着下结论**
   - RT 变慢不一定是代码慢，可能是数据库连接池等待。
   - MQ 堆积不一定是生产太快，可能是消费端失败重试。
   - Redis 命中率下降不一定是 Redis 问题，可能是 key 设计或缓存失效策略问题。
   - CPU 高不一定是业务计算，也可能是 GC、锁竞争或日志刷盘。

### 2.3 第二步：定位问题

1. **先定影响范围**
   - 是单个接口慢，还是整个服务慢。
   - 是单个用户、单个医生、单个机构，还是全站异常。
   - 是最近发布后出现，还是流量高峰自然出现。
   - 是读链路问题，还是写链路问题。
   - 是同步主链路问题，还是异步 MQ 链路问题。

2. **再看时间线**
   - 问题开始时间。
   - 最近是否有发版。
   - 是否有配置变更、限流规则变更、数据库变更、缓存清理、定时任务执行。
   - 流量是否比平时高，是否命中热点活动或放号高峰。

3. **按链路分层排查**
   - 入口层：Gateway、Nginx、Sentinel，看 QPS、限流、状态码、入口 RT。
   - 应用层：Controller、Service、线程池、JVM，看接口耗时、异常栈、线程状态、GC。
   - 缓存层：Redis，看命中率、热 key、大 key、慢查询、连接数。
   - 数据层：MySQL，看慢 SQL、执行计划、锁等待、连接池、事务时长。
   - 消息层：RabbitMQ，看生产速率、消费速率、堆积、重试、死信。
   - 依赖层：Feign / 第三方接口，看超时、熔断、降级、重试是否放大故障。
   - 配置层：Nacos，看开关、阈值、灰度比例、超时参数是否符合预期。

4. **用 traceId 串一次请求**
   - 入口生成 traceId，贯穿 Gateway、业务服务、数据库日志、MQ 消息、下游调用。
   - 如果是订单或挂号链路，还要用业务 ID 串联，比如 `orderId`、`scheduleId`、`conversationId`。
   - 这样能判断时间到底耗在哪一段，而不是只看某个服务自己的日志。

5. **定位时常用判断**
   - QPS 升高 + RT 升高 + 错误率不高：可能是容量不足、缓存命中率下降、连接池排队。
   - QPS 正常 + RT 升高：可能是慢 SQL、下游变慢、线程池阻塞、GC。
   - 错误率升高 + RT 不高：可能是参数、配置、权限、依赖快速失败。
   - RT 升高 + Full GC 增多：优先看内存泄漏、对象洪峰、大对象或缓存无界。
   - MQ ready 上升 + ack rate 下降：消费端处理不过来或下游依赖变慢。
   - DB 连接池 wait 上升：不是简单加连接，先看慢 SQL、事务长度、缓存回源和线程池放量。

### 2.4 第三步：解决问题

1. **先止血**
   - 收紧 Gateway / Sentinel 限流。
   - 关闭非核心功能开关。
   - 降级推荐、统计、短信、AI 辅助分析等非核心链路。
   - 回滚最近发布或切回旧链路。
   - 对热点查询返回缓存快照或简化结果。
   - 暂停异常定时任务或异常消费者。

2. **再修根因**
   - 慢 SQL：补索引、改查询字段、拆分页、减少事务范围。
   - Redis：治理热 key、大 key、缓存穿透、击穿、雪崩，调整 TTL 和预热策略。
   - RabbitMQ：修消费者异常、控制重试次数、补幂等、增加死信处理和补偿任务。
   - JVM：修内存泄漏、限制本地缓存、清理 ThreadLocal、调整对象创建和 GC 参数。
   - 线程池：隔离慢依赖，设置有界队列、拒绝策略、超时和告警。
   - Feign / 下游：设置合理超时、熔断、降级，避免无脑重试放大故障。
   - Nacos 配置：把限流阈值、灰度比例、开关、超时参数做成可动态调整。

3. **解决问题时要区分临时方案和长期方案**
   - 临时方案：限流、降级、回滚、扩容、开关切换，目标是恢复业务。
   - 长期方案：代码修复、架构调整、索引优化、监控补齐、压测验证，目标是避免复发。

### 2.5 第四步：发布到生产

1. **本地和测试环境复现**
   - 尽量用同样的入参、数据规模、并发模型复现问题。
   - 如果是慢 SQL，要拿类似数据量跑执行计划。
   - 如果是 MQ 堆积，要模拟消费失败、下游慢、重复投递。
   - 如果是 Redis 热点，要模拟热点 key 集中访问。
   - 如果是 JVM 问题，要看堆快照、GC 日志或压测对象增长趋势。

2. **修复后先验证边界**
   - 正常路径是否通过。
   - 异常路径是否有降级。
   - 重复请求是否幂等。
   - 消息重复投递是否安全。
   - 回滚后数据是否还能收敛。

3. **上线方式**
   - 小改动可以走普通发布，但要避开高峰。
   - 风险较高的改动要走灰度发布，比如按用户、机构、医生、接口或流量比例放量。
   - 配置类修复优先用 Nacos 开关，先小范围生效，再逐步扩大。
   - 核心链路改动要准备回滚方案，包括代码回滚、配置回滚、接口级回退和数据补偿。

4. **上线观察**
   - 观察 QPS、P95/P99 RT、异常率、业务成功率。
   - 观察 Redis 命中率、MySQL 慢 SQL、连接池等待、RabbitMQ 堆积、JVM GC。
   - 观察是否出现新的异常日志或重试放大。
   - 灰度阶段如果指标异常，先回滚或降低灰度比例，不要硬顶全量。

5. **发布后复盘**
   - 根因是什么。
   - 为什么监控没有提前发现。
   - 为什么测试没有覆盖。
   - 有没有配置、流程、代码或架构上的防复发动作。
   - 是否需要补告警、补压测、补 e2e、补运维手册。

### 2.6 组件化排查清单

1. **Gateway / Sentinel**
   - 发现：入口 RT 高、5xx 增多、限流次数增多。
   - 定位：看路由维度 QPS、状态码、限流规则、热点参数、系统保护规则。
   - 解决：调整限流阈值、热点参数限流、黑名单、防刷、熔断降级。
   - 发布：规则走 Nacos / Dashboard 灰度生效，观察入口 RT 和业务成功率。

2. **应用服务 / JVM**
   - 发现：接口整体变慢、CPU 高、Full GC 增多、线程数异常。
   - 定位：看接口指标、日志、线程栈、GC 日志、堆内存趋势。
   - 解决：修慢代码、减少对象创建、清理无界缓存、处理 ThreadLocal、优化线程池。
   - 发布：压测验证，灰度观察 CPU、GC、P99、线程池队列。

3. **线程池**
   - 发现：队列堆积、拒绝次数增加、接口 RT 飙升。
   - 定位：看活跃线程、队列长度、任务耗时、下游 RT。
   - 解决：核心链路和慢依赖隔离，队列有界，拒绝策略明确，非核心任务异步补偿。
   - 发布：先小流量验证，观察拒绝次数、队列长度和下游错误率。

4. **Redis**
   - 发现：缓存命中率下降、Redis CPU 高、命令耗时变长、网络流量异常。
   - 定位：看 hotkeys、bigkeys、slowlog、业务 cache hit/miss、key TTL。
   - 解决：热点 key 拆分或本地短缓存，大 key 拆分，空值缓存，互斥重建，缓存预热。
   - 发布：灰度缓存策略，观察命中率、回源量、Redis CPU 和接口 RT。

5. **MySQL**
   - 发现：慢 SQL 增多、连接池等待、接口 P99 变差、锁等待。
   - 定位：慢日志、EXPLAIN、连接池 active/wait、事务时长、`show engine innodb status`。
   - 解决：补索引、字段裁剪、避免深分页、缩短事务、处理锁顺序、读写分离。
   - 发布：先测试环境验证执行计划，再低峰上线，观察慢 SQL 和连接池等待。

6. **RabbitMQ**
   - 发现：`messages_ready` 增长、`messages_unacked` 高、ack rate 下降、死信增多。
   - 定位：看生产速率、消费速率、消费者异常、下游依赖 RT、重试次数。
   - 解决：修消费异常、限速、扩消费者、降低非核心消息优先级、死信补偿、幂等兜底。
   - 发布：先在测试环境模拟重复投递和消费失败，再灰度消费者，观察堆积是否追平。

7. **OpenFeign / 第三方依赖**
   - 发现：下游超时、慢调用比例升高、熔断次数增加。
   - 定位：看下游 RT、超时配置、重试次数、熔断规则、调用量。
   - 解决：合理超时、熔断降级、减少重试、改异步、缓存兜底。
   - 发布：配置先小范围生效，观察主链路 RT 和下游错误率。

8. **AI 链路**
   - 发现：AI 回复慢、模型调用失败、RAG 召回差、Agent 工具调用失败。
   - 定位：看模型 RT、token 消耗、检索耗时、召回结果、工具执行轨迹、状态机推进。
   - 解决：降级普通回复、缩短上下文、调整 topK、工具超时兜底、人工审批、异步沉淀。
   - 发布：按用户或场景灰度，观察成功率、转人工率、成本、P95 RT 和投诉率。

### 2.7 常见生产问题口述模板

#### 1. 接口突然变慢怎么排查？

1. 我会先看是单接口慢还是全站慢，再看问题是否和最近发布、流量高峰或配置变更相关。
2. 指标上先看 Gateway 的 QPS、P95/P99、错误率，再看应用线程池、JVM GC、数据库连接池、Redis 命中率和下游 Feign RT。
3. 如果发现 DB 连接池等待升高，就继续看慢 SQL、事务长度和缓存命中率；如果 Full GC 增多，就看堆趋势和对象引用；如果 MQ 堆积，就看消费端和下游依赖。
4. 处理上先限流或降级非核心链路，恢复主链路；根因确认后再做 SQL、缓存、线程池或下游调用优化，最后灰度发布并观察同一组指标。

#### 2. MQ 消息堆积怎么排查？

1. 我不会只看队列里有多少消息，而是同时看 `publish rate`、`ack rate`、`messages_ready`、`messages_unacked` 和消费者错误率。
2. 如果生产速率突然升高，可能是上游流量洪峰；如果 ack rate 下降，可能是消费者处理慢或下游依赖慢；如果 unacked 很高，可能是消费者拿到消息但卡住了。
3. 解决时先判断这条消息是不是核心链路。如果是短信、统计这类非核心任务，可以先限速或延后消费；如果是订单状态推进，就要优先保证幂等和补偿。
4. 修复后要在测试环境模拟重复投递、消费失败、死信和补偿，再灰度消费者上线。

#### 3. 数据库连接池打满怎么排查？

1. 我会先看连接池 active、idle、wait、acquire time，再看 MySQL 慢 SQL、CPU、IO、锁等待。
2. 如果 active 高且慢 SQL 多，说明连接被慢查询长期占住；如果 SQL 不慢但 wait 高，可能是瞬时并发太高、事务太长或线程池放量超过数据库能力。
3. 处理上不会第一反应就加连接数，因为数据库本身可能已经到瓶颈。更优先看 SQL、索引、缓存命中率、事务范围和入口限流。
4. 修复后用类似数据量验证执行计划，再低峰或灰度上线，观察慢 SQL 数、连接池等待和接口 P99。

#### 4. Redis 热 key 或大 key 怎么排查？

1. 现象通常是 Redis 单节点 CPU 高、网络流量异常、缓存命中后接口仍然慢。
2. 排查时看业务 cache 指标、Redis slowlog、hotkeys、bigkeys，再结合接口维度看是不是某个医生、科室、活动资源特别热。
3. 热 key 可以做 key 拆分、本地短缓存、热点预热、限流；大 key 要做结构拆分、分页读取、避免一次性全量操作。
4. 上线时要灰度缓存 key 和 TTL 策略，避免一次切换导致大面积缓存失效。

#### 5. Full GC 或 OOM 怎么排查？

1. 我会先看 GC 日志和内存趋势，区分是对象洪峰、内存泄漏、大对象、Metaspace 还是直接内存问题。
2. 如果 Full GC 后内存下降很少，优先怀疑泄漏或强引用，比如本地缓存无上限、ThreadLocal 未清理、集合持续增长、监听器未注销。
3. 处理时先通过限流、扩容或降级缓解，再在副本或低峰抓堆分析 GC Root 引用链。
4. 修复后要压测验证堆增长趋势，而不是只看功能测试通过。

### 2.8 面试表达

> “我现在希望自己处理生产问题时有一套固定框架，而不是遇到问题靠感觉猜。我的思路是先从告警、业务指标或用户反馈确认问题，再看影响范围和时间线，比如是不是某个接口、某个用户群、某次发布之后才出现。定位时我会按链路分层，从 Gateway 入口、应用线程池和 JVM、Redis、MySQL、RabbitMQ、下游 Feign 调用一路往下看，用 traceId 和业务 ID 把一次请求串起来。解决时先止血，比如限流、降级、回滚、开关切换，保证主链路恢复；再做根因修复，比如 SQL 优化、缓存治理、线程池隔离、MQ 幂等补偿或下游熔断。最后上线不会直接全量推，而是先复现、测试环境验证、灰度发布、观察同一组指标，并准备回滚方案。问题结束后再复盘，补监控、补日志、补测试和压测，避免同类问题重复出现。”
