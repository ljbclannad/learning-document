# 技术取舍分析框架

> 目标：从“知识点记忆”切换到“工程判断”。这份文档先搭建统一框架，后续再逐题补充案例、反例、项目映射和表达模板。

---

## 1. 这份文档解决什么问题

很多技术问题，真正难的不是“是否知道这个技术”，而是：

1. 为什么要上这个方案，而不是继续维持现状。
2. 为什么选 A，不选 B / C。
3. 这个方案解决了什么问题，又引入了什么成本。
4. 什么时候现在不该做，什么时候以后要升级。
5. 这个判断和业务阶段、团队能力、系统复杂度之间是什么关系。

所以这份文档的重点不是背概念，而是形成统一的分析方法。

---

## 2. 总体方法：先业务，后技术；先问题，后方案

### 2.1 一个核心原则

技术选型不是“找最先进的技术”，而是：

> 在当前业务阶段下，用可接受的成本解决当前最关键的问题。

### 2.2 一个常见误区

错误思路：

1. 先看到热门技术。
2. 再去给业务找使用理由。

更合理的思路：

1. 先确认当前最痛的问题是什么。
2. 再判断问题是否已经严重到值得引入新复杂度。
3. 最后才比较不同方案的收益、代价和落地条件。

### 2.3 技术取舍的本质

绝大多数技术方案，本质上都在做这些交换：

1. 用复杂度换扩展性。
2. 用资源成本换性能。
3. 用一致性换可用性。
4. 用实时性换吞吐。
5. 用工程灵活性换标准化治理。
6. 用短期开发效率换长期维护成本，或者反过来。

## 3. 通用分析主线

以后看任何一个“要不要上某技术”的问题，都优先沿着这条主线展开。

### 3.1 第一步：先定义问题

先回答：

1. 当前到底遇到了什么问题。
2. 这个问题是性能问题、稳定性问题、一致性问题、协作问题，还是成本问题。
3. 这个问题是偶发，还是已经持续影响业务。
4. 这个问题的影响范围有多大，是否已经影响核心链路。

如果问题本身定义不清，后面很容易“为技术而技术”。

### 3.2 第二步：判断问题是否值得现在解决

不是所有问题都值得立刻上更重的方案，要先看：

1. 这是当前主矛盾，还是次要矛盾。
2. 这个问题对收入、转化、投诉、可用性、交付效率是否有实质影响。
3. 是否可以先用更轻的手段缓解。
4. 如果暂时不做，风险是否可控。

很多过度设计，都是因为把“未来可能的问题”当成“现在必须解决的问题”。

### 3.3 第三步：明确业务约束

同一个技术方案，在不同业务约束下结论会完全不同。至少要看：

1. 业务量级：QPS、数据量、峰谷差、增长速度。
2. 链路属性：核心链路还是边缘链路。
3. 一致性要求：能否接受短暂不一致。
4. 时效性要求：能否接受异步。
5. 可用性要求：失败能否重试，是否允许降级。
6. 数据价值：丢一条数据的代价有多大。
7. 合规要求：审计、权限、隐私、留痕是否严格。

### 3.4 第四步：明确工程约束

很多方案不是“理论不可行”，而是“团队阶段不适合”。要看：

1. 团队人数和分工是否支持。
2. 团队对该技术是否有运维和排障经验。
3. 当前监控、链路追踪、报警体系是否足够支撑。
4. 发布流程、测试能力、灰度能力是否成熟。
5. 当前系统边界是否清晰，是否已经具备拆分条件。

### 3.5 第五步：列方案，不要只列一个

至少列出：

1. 维持现状。
2. 轻量优化方案。
3. 中等成本方案。
4. 重型治理方案。

这样才能避免一上来就在“单个方案里自我说服”。

### 3.6 第六步：比较每个方案的收益与代价

每个方案都要看：

1. 解决了哪些问题。
2. 没解决哪些问题。
3. 新引入了哪些复杂度。
4. 对研发、测试、运维、排障分别增加了什么成本。
5. 是一次性成本，还是持续性成本。

### 3.7 第七步：给出阶段性结论

结论最好不是“永远正确”的，而是：

1. 当前阶段为什么选这个。
2. 哪些前提一旦变化，结论会变化。
3. 未来什么时候要升级。
4. 升级路径是什么。

## 4. 一个统一的判断模板

后面几乎所有取舍题，都可以套这个模板。

### 4.1 六段式模板

1. 背景  
   当前业务处于什么阶段，系统有什么特点。

2. 问题  
   当前最突出的矛盾是什么。

3. 约束  
   一致性、性能、成本、团队能力、交付效率上有什么要求。

4. 备选方案  
   至少给出 2 到 4 个方案，不要只讲最终方案。

5. 取舍理由  
   为什么最终选这个，而不是其他方案。

6. 风险与边界  
   这个方案的代价是什么，什么情况下要调整。

### 4.2 压缩版模板

如果只想快速分析一个问题，可以先问自己这 6 句：

1. 我到底在解决什么问题？
2. 这个问题现在真的值得解决吗？
3. 业务能接受什么，不能接受什么？
4. 有没有更轻的替代方案？
5. 这个方案最大的收益是什么？
6. 这个方案最大的代价是什么？

## 5. 常用判断维度清单

后面每一类题，都建议从这些维度中选重点展开。

### 5.1 业务维度

1. 核心链路还是非核心链路。
2. 用户量、请求量、数据量。
3. 增长速度是否快。
4. 峰值是否明显。
5. 故障代价是否高。
6. 是否有强监管和审计要求。

### 5.2 一致性维度

1. 是否要求强一致。
2. 是否能接受最终一致性。
3. 不一致持续 1 秒、10 秒、1 分钟，业务影响分别是什么。
4. 是否允许人工补偿。
5. 是否允许重复执行。

### 5.3 性能维度

1. 更敏感的是吞吐、延迟，还是资源利用率。
2. 压力是稳定高压，还是瞬时峰值。
3. 瓶颈在 CPU、IO、网络、数据库，还是锁竞争。
4. 优化是针对读多写少，还是写多读少。

### 5.4 可用性维度

1. 单点失败能否接受。
2. 下游失败时能否降级。
3. 能否异步削峰。
4. 是否需要隔离、熔断、限流。
5. 是否需要跨机房、跨可用区容灾。

### 5.5 成本维度

1. 开发成本。
2. 测试成本。
3. 运维成本。
4. 机器资源成本。
5. 学习与团队磨合成本。
6. 长期维护成本。

### 5.6 组织协作维度

1. 团队是 3 人、10 人还是几十人协作。
2. 模块边界是否清晰。
3. 是否经常因为联调、发版相互阻塞。
4. 是否需要独立扩缩容、独立发布、独立故障隔离。

### 5.7 治理维度

1. 日志、指标、追踪是否完备。
2. 是否支持灰度、回滚、压测。
3. 故障定位是否清晰。
4. 是否有自动化测试和回归能力。

## 6. 常见取舍的“底层矛盾”分类

把高频问题先按本质归类，后面补题时更容易归档。

### 6.1 复杂度 vs 扩展性

典型问题：

1. 单体 vs 微服务。
2. 本地模块化 vs 独立服务化。
3. 同库同表 vs 分库分表。
4. 同步处理 vs MQ 解耦。

### 6.2 一致性 vs 可用性 / 吞吐

典型问题：

1. 强一致性 vs 最终一致性。
2. 本地事务 vs 分布式事务。
3. XA / AT / TCC / 可靠消息最终一致性怎么选。
4. 先扣库存再支付，还是支付成功后异步扣库存。

### 6.3 性能 vs 成本

典型问题：

1. 数据库直查 vs Redis 缓存。
2. 本地缓存 vs Redis。
3. ES 检索 vs 数据库模糊查询。
4. 批处理 vs 实时处理。

### 6.4 灵活性 vs 标准化

典型问题：

1. 通用平台化设计 vs 针对场景快速落地。
2. 自研组件 vs 直接使用成熟中间件。
3. 高可配置能力 vs 简单稳定实现。

### 6.5 交付效率 vs 长期演进

典型问题：

1. 先堆功能还是先治理架构。
2. 先快速上线还是先抽象通用层。
3. 是否提前为未来 10 倍规模设计。

## 7. 高频取舍题总目录

这部分先列目录，后面可以逐题展开成独立章节。

### 7.1 架构层

1. 单体什么时候拆微服务。
2. 微服务拆到什么粒度合适。
3. 为什么不是一开始就上微服务。
4. 为什么有些系统适合保持单体。
5. 同步调用和异步解耦怎么选。
6. 网关层要不要做统一聚合。
7. BFF 是否有必要引入。

### 7.2 存储与缓存层

1. 数据库直查 vs Redis 缓存。
2. 本地缓存 vs Redis。
3. 缓存一致性如何权衡。
4. 旁路缓存、读写穿透、双写一致性怎么选。
5. 什么时候要分库分表。
6. 什么时候值得上 Elasticsearch。
7. 热点数据怎么处理。

### 7.3 消息与异步层

1. 什么时候要引入 MQ。
2. 可靠消息和同步调用怎么选。
3. 削峰填谷和实时性怎么取舍。
4. 订单、库存、支付链路哪些环节适合异步。
5. Outbox 是否值得做。

### 7.4 分布式事务层

1. 为什么不能所有场景都用本地事务。
2. XA、AT、TCC、SAGA、可靠消息最终一致性怎么选。
3. 什么时候考虑 Seata AT。
4. 什么时候考虑 Seata TCC。
5. TCC 为什么不适合所有业务。
6. 什么时候宁可接受最终一致性。
7. 人工补偿和自动补偿怎么权衡。

### 7.5 并发控制层

1. 乐观锁 vs 悲观锁。
2. 分布式锁是否真的有必要。
3. 锁、队列、令牌桶、幂等表分别适合什么场景。
4. 防重、幂等、一致性三者怎么区分。

### 7.6 稳定性治理层

1. 限流、熔断、降级什么时候优先做。
2. 可用性和用户体验怎么平衡。
3. 强校验和高可用如何取舍。
4. 失败重试是否一定是好事。

### 7.7 数据处理层

1. 实时计算 vs 离线计算。
2. 宽表冗余 vs Join 查询。
3. 强规范建模 vs 面向查询建模。

### 7.8 AI / 智能体系统层

1. 普通对话链路和 Agent 链路是否应该拆开。
2. Prompt 内联处理 vs 工作流编排。
3. 记忆前置、检索前置、追问前置怎么选。
4. 在线实时推理 vs 异步任务处理。
5. 自研编排 vs 使用现成框架。

## 8. 每道取舍题的展开模板

后面你补具体题目时，建议每道题都按下面结构写。

### 8.1 标准章节结构

1. 题目定义  
   这道题本质在比较什么。

2. 背景前提  
   业务规模、团队规模、链路属性。

3. 核心矛盾  
   真正要解决的问题是什么。

4. 备选方案  
   方案 A、方案 B、方案 C。

5. 适用条件  
   每个方案分别适合什么前提。

6. 不适用条件  
   每个方案在哪些情况下会出问题。

7. 主要收益  
   这个方案能带来什么。

8. 主要代价  
   这个方案会增加什么复杂度。

9. 推荐判断顺序  
   实际做选型时，先看什么，后看什么。

10. 项目映射  
    结合自己的项目，怎么把这个判断讲出来。

11. 反例  
    常见误用、过度设计、错误直觉是什么。

12. 结论  
    用一句话总结“什么情况下选它”。

### 8.2 极简速记版

如果后面想做一页速记卡片，每题至少保留：

1. 解决什么问题。
2. 适合什么场景。
3. 最大优点。
4. 最大代价。
5. 不该在什么情况下用。

## 9. 建议优先补的 10 道题

如果要先做一版最有价值的内容，建议优先补这 10 个。

1. 单体什么时候拆成微服务。
2. 微服务拆分粒度怎么定。
3. 同步调用 vs MQ 异步解耦。
4. Redis 缓存什么时候值得引入。
5. 本地缓存 vs Redis。
6. 分库分表什么时候做，什么时候坚决不做。
7. Elasticsearch 什么时候引入。
8. XA / AT / TCC / 可靠消息最终一致性怎么选。
9. 乐观锁、悲观锁、分布式锁怎么选。
10. 限流、熔断、降级分别解决什么问题，优先级怎么定。

## 10. 两个高频案例的起手思路

这里先只放“分析方向”，不展开最终答案。

### 10.1 单体升级微服务

优先看：

1. 当前痛点到底是性能瓶颈，还是组织协作瓶颈。
2. 模块边界是否已经清晰。
3. 是否存在频繁发布互相影响。
4. 不同模块是否有明显不同的资源模型和扩容诉求。
5. 当前团队是否有服务治理能力。

如果这些前提都不明显，单体通常仍然更划算。

### 10.2 Seata TCC 什么时候考虑

优先看：

1. 业务是否要求高一致性。
2. 是否不能接受最终一致性的短暂延迟。
3. Try / Confirm / Cancel 是否能被清晰建模。
4. 是否能接受较强的业务侵入。
5. 团队是否具备补偿、幂等、空回滚、防悬挂治理能力。

如果业务链路复杂，但一致性要求又没有高到必须实时闭环，很多时候可靠消息最终一致性更务实。

## 12. 下一步建议

建议下一步直接从下面 3 组里选一组展开：

1. 架构演进：单体 vs 微服务、拆分粒度、同步 vs 异步。
2. 分布式一致性：XA / AT / TCC / 可靠消息最终一致性。
3. 存储与性能：缓存、分库分表、ES、热点数据处理。

等这些主干题补完，这份文档就会从“框架”升级成“可反复复用的技术判断手册”。
