## 1. 这份文档解决什么问题

很多技术问题，真正难的不是“是否知道这个技术”，而是：

1. 为什么要上这个方案，而不是继续维持现状。
2. 为什么选 A，不选 B / C。
3. 这个方案解决了什么问题，又引入了什么成本。
4. 什么时候现在不该做，什么时候以后要升级。
5. 这个判断和业务阶段、团队能力、系统复杂度之间是什么关系。

所以这份文档的重点不是背概念，而是形成统一的分析方法。

## 2. 总体方法：先业务，后技术；先问题，后方案

### 2.1 一个核心原则

技术选型不是“找最先进的技术”，而是：

> 在当前业务阶段下，用可接受的成本解决当前最关键的问题。

### 2.2 一个常见误区

错误思路：

1. 先看到热门技术。
2. 再去给业务找使用理由。

更合理的思路：

1. 先确认当前最痛的问题是什么。
2. 再判断问题是否已经严重到值得引入新复杂度。
3. 最后才比较不同方案的收益、代价和落地条件。

### 2.3 技术取舍的本质

绝大多数技术方案，本质上都在做这些交换：

1. 用复杂度换扩展性。
2. 用资源成本换性能。
3. 用一致性换可用性。
4. 用实时性换吞吐。
5. 用工程灵活性换标准化治理。
6. 用短期开发效率换长期维护成本，或者反过来。

## 3. 通用分析主线

以后看任何一个“要不要上某技术”的问题，都优先沿着这条主线展开。

### 3.1 第一步：先定义问题

先回答：

1. 当前到底遇到了什么问题。
2. 这个问题是性能问题、稳定性问题、一致性问题、协作问题，还是成本问题。
3. 这个问题是偶发，还是已经持续影响业务。
4. 这个问题的影响范围有多大，是否已经影响核心链路。

如果问题本身定义不清，后面很容易“为技术而技术”。

### 3.2 第二步：判断问题是否值得现在解决

不是所有问题都值得立刻上更重的方案，要先看：

1. 这是当前主矛盾，还是次要矛盾。
2. 这个问题对收入、转化、投诉、可用性、交付效率是否有实质影响。
3. 是否可以先用更轻的手段缓解。
4. 如果暂时不做，风险是否可控。

很多过度设计，都是因为把“未来可能的问题”当成“现在必须解决的问题”。

### 3.3 第三步：明确业务约束

同一个技术方案，在不同业务约束下结论会完全不同。至少要看：

1. 业务量级：QPS、数据量、峰谷差、增长速度。
2. 链路属性：核心链路还是边缘链路。
3. 一致性要求：能否接受短暂不一致。
4. 时效性要求：能否接受异步。
5. 可用性要求：失败能否重试，是否允许降级。
6. 数据价值：丢一条数据的代价有多大。
7. 合规要求：审计、权限、隐私、留痕是否严格。

### 3.4 第四步：明确工程约束

很多方案不是“理论不可行”，而是“团队阶段不适合”。要看：

1. 团队人数和分工是否支持。
2. 团队对该技术是否有运维和排障经验。
3. 当前监控、链路追踪、报警体系是否足够支撑。
4. 发布流程、测试能力、灰度能力是否成熟。
5. 当前系统边界是否清晰，是否已经具备拆分条件。

### 3.5 第五步：列方案，不要只列一个

至少列出：

1. 维持现状。
2. 轻量优化方案。
3. 中等成本方案。
4. 重型治理方案。

这样才能避免一上来就在“单个方案里自我说服”。

### 3.6 第六步：比较每个方案的收益与代价

每个方案都要看：

1. 解决了哪些问题。
2. 没解决哪些问题。
3. 新引入了哪些复杂度。
4. 对研发、测试、运维、排障分别增加了什么成本。
5. 是一次性成本，还是持续性成本。

### 3.7 第七步：给出阶段性结论

结论最好不是“永远正确”的，而是：

1. 当前阶段为什么选这个。
2. 哪些前提一旦变化，结论会变化。
3. 未来什么时候要升级。
4. 升级路径是什么。

## 4. 一个统一的判断模板

后面几乎所有取舍题，都可以套这个模板。

### 4.1 六段式模板

1. 背景  
   当前业务处于什么阶段，系统有什么特点。

2. 问题  
   当前最突出的矛盾是什么。

3. 约束  
   一致性、性能、成本、团队能力、交付效率上有什么要求。

4. 备选方案  
   至少给出 2 到 4 个方案，不要只讲最终方案。

5. 取舍理由  
   为什么最终选这个，而不是其他方案。

6. 风险与边界  
   这个方案的代价是什么，什么情况下要调整。

### 4.2 压缩版模板

如果只想快速分析一个问题，可以先问自己这 6 句：

1. 我到底在解决什么问题？
2. 这个问题现在真的值得解决吗？
3. 业务能接受什么，不能接受什么？
4. 有没有更轻的替代方案？
5. 这个方案最大的收益是什么？
6. 这个方案最大的代价是什么？

## 5. 常用判断维度清单

后面每一类题，都建议从这些维度中选重点展开。

### 5.1 业务维度

1. 核心链路还是非核心链路。
2. 用户量、请求量、数据量。
3. 增长速度是否快。
4. 峰值是否明显。
5. 故障代价是否高。
6. 是否有强监管和审计要求。

### 5.2 一致性维度

1. 是否要求强一致。
2. 是否能接受最终一致性。
3. 不一致持续 1 秒、10 秒、1 分钟，业务影响分别是什么。
4. 是否允许人工补偿。
5. 是否允许重复执行。

### 5.3 性能维度

1. 更敏感的是吞吐、延迟，还是资源利用率。
2. 压力是稳定高压，还是瞬时峰值。
3. 瓶颈在 CPU、IO、网络、数据库，还是锁竞争。
4. 优化是针对读多写少，还是写多读少。

### 5.4 可用性维度

1. 单点失败能否接受。
2. 下游失败时能否降级。
3. 能否异步削峰。
4. 是否需要隔离、熔断、限流。
5. 是否需要跨机房、跨可用区容灾。

### 5.5 成本维度

1. 开发成本。
2. 测试成本。
3. 运维成本。
4. 机器资源成本。
5. 学习与团队磨合成本。
6. 长期维护成本。

### 5.6 组织协作维度

1. 团队是 3 人、10 人还是几十人协作。
2. 模块边界是否清晰。
3. 是否经常因为联调、发版相互阻塞。
4. 是否需要独立扩缩容、独立发布、独立故障隔离。

### 5.7 治理维度

1. 日志、指标、追踪是否完备。
2. 是否支持灰度、回滚、压测。
3. 故障定位是否清晰。
4. 是否有自动化测试和回归能力。

## 6. 常见取舍的“底层矛盾”分类

把高频问题先按本质归类，后面补题时更容易归档。

### 6.1 复杂度 vs 扩展性

典型问题：

1. 单体 vs 微服务。
2. 本地模块化 vs 独立服务化。
3. 同库同表 vs 分库分表。
4. 同步处理 vs MQ 解耦。

### 6.2 一致性 vs 可用性 / 吞吐

典型问题：

1. 强一致性 vs 最终一致性。
2. 本地事务 vs 分布式事务。
3. XA / AT / TCC / 可靠消息最终一致性怎么选。
4. 先扣库存再支付，还是支付成功后异步扣库存。

### 6.3 性能 vs 成本

典型问题：

1. 数据库直查 vs Redis 缓存。
2. 本地缓存 vs Redis。
3. ES 检索 vs 数据库模糊查询。
4. 批处理 vs 实时处理。

### 6.4 灵活性 vs 标准化

典型问题：

1. 通用平台化设计 vs 针对场景快速落地。
2. 自研组件 vs 直接使用成熟中间件。
3. 高可配置能力 vs 简单稳定实现。

### 6.5 交付效率 vs 长期演进

典型问题：

1. 先堆功能还是先治理架构。
2. 先快速上线还是先抽象通用层。
3. 是否提前为未来 10 倍规模设计。

## 7. 高频取舍题总目录

这部分先列目录，后面可以逐题展开成独立章节。

### 7.1 架构层

1. 单体什么时候拆微服务。
2. 微服务拆到什么粒度合适。
3. 为什么不是一开始就上微服务。
4. 为什么有些系统适合保持单体。
5. 同步调用和异步解耦怎么选。
6. 网关层要不要做统一聚合。
7. BFF 是否有必要引入。

### 7.2 存储与缓存层

1. 数据库直查 vs Redis 缓存。
2. 本地缓存 vs Redis。
3. 缓存一致性如何权衡。
4. 旁路缓存、读写穿透、双写一致性怎么选。
5. 什么时候要分库分表。
6. 什么时候值得上 Elasticsearch。
7. 热点数据怎么处理。

### 7.3 消息与异步层

1. 什么时候要引入 MQ。
2. 可靠消息和同步调用怎么选。
3. 削峰填谷和实时性怎么取舍。
4. 订单、库存、支付链路哪些环节适合异步。
5. Outbox 是否值得做。

### 7.4 分布式事务层

1. 为什么不能所有场景都用本地事务。
2. XA、AT、TCC、SAGA、可靠消息最终一致性怎么选。
3. 什么时候考虑 Seata AT。
4. 什么时候考虑 Seata TCC。
5. TCC 为什么不适合所有业务。
6. 什么时候宁可接受最终一致性。
7. 人工补偿和自动补偿怎么权衡。

### 7.5 并发控制层

1. 乐观锁 vs 悲观锁。
2. 分布式锁是否真的有必要。
3. 锁、队列、令牌桶、幂等表分别适合什么场景。
4. 防重、幂等、一致性三者怎么区分。

### 7.6 稳定性治理层

1. 限流、熔断、降级什么时候优先做。
2. 可用性和用户体验怎么平衡。
3. 强校验和高可用如何取舍。
4. 失败重试是否一定是好事。

### 7.7 数据处理层

1. 实时计算 vs 离线计算。
2. 宽表冗余 vs Join 查询。
3. 强规范建模 vs 面向查询建模。

### 7.8 AI / 智能体系统层

1. 普通对话链路和 Agent 链路是否应该拆开。
2. Prompt 内联处理 vs 工作流编排。
3. 记忆前置、检索前置、追问前置怎么选。
4. 在线实时推理 vs 异步任务处理。
5. 自研编排 vs 使用现成框架。

## 8. 每道取舍题的展开模板

后面你补具体题目时，建议每道题都按下面结构写。

### 8.1 标准章节结构

1. 题目定义  
   这道题本质在比较什么。

2. 背景前提  
   业务规模、团队规模、链路属性。

3. 核心矛盾  
   真正要解决的问题是什么。

4. 备选方案  
   方案 A、方案 B、方案 C。

5. 适用条件  
   每个方案分别适合什么前提。

6. 不适用条件  
   每个方案在哪些情况下会出问题。

7. 主要收益  
   这个方案能带来什么。

8. 主要代价  
   这个方案会增加什么复杂度。

9. 推荐判断顺序  
   实际做选型时，先看什么，后看什么。

10. 项目映射  
    结合自己的项目，怎么把这个判断讲出来。

11. 反例  
    常见误用、过度设计、错误直觉是什么。

12. 结论  
    用一句话总结“什么情况下选它”。

### 8.2 极简速记版

如果后面想做一页速记卡片，每题至少保留：

1. 解决什么问题。
2. 适合什么场景。
3. 最大优点。
4. 最大代价。
5. 不该在什么情况下用。

## 9. 两个高频案例的起手思路

这里先只放“分析方向”，不展开最终答案。

### 9.1 单体升级微服务

优先看：

1. 当前痛点到底是性能瓶颈，还是组织协作瓶颈。
2. 模块边界是否已经清晰。
3. 是否存在频繁发布互相影响。
4. 不同模块是否有明显不同的资源模型和扩容诉求。
5. 当前团队是否有服务治理能力。

如果这些前提都不明显，单体通常仍然更划算。

### 9.2 Seata TCC 什么时候考虑

优先看：

1. 业务是否要求高一致性。
2. 是否不能接受最终一致性的短暂延迟。
3. Try / Confirm / Cancel 是否能被清晰建模。
4. 是否能接受较强的业务侵入。
5. 团队是否具备补偿、幂等、空回滚、防悬挂治理能力。

如果业务链路复杂，但一致性要求又没有高到必须实时闭环，很多时候可靠消息最终一致性更务实。

## 10. 高频题：单体什么时候拆成微服务

### 10.1 题目定义

这道题本质不是在比较“单体先进还是微服务先进”，而是在判断：

1. 当前系统复杂度是否已经超过单体的舒适区。
2. 当前瓶颈是不是已经主要来自组织协作和系统耦合。
3. 引入分布式复杂度后，收益是否真的大于成本。

### 10.2 核心矛盾

单体和微服务的核心矛盾，本质上是：

> 用更高的分布式复杂度，换更好的模块解耦、独立演进和组织协作效率。

所以这不是纯技术题，而是业务规模、团队规模、系统边界、治理能力共同决定的问题。

### 10.3 先明确：单体不是落后方案

很多系统在相当长一段时间里，单体都是最优解，因为它天然有这些优点：

1. 开发快，调试简单，部署路径短。
2. 本地事务天然好用，不需要额外处理分布式一致性。
3. 调用都在进程内，链路更短，排障更容易。
4. 对小团队非常友好，认知成本低。

所以判断重点不是“要不要升级架构”，而是“现有单体是否已经明显不适配当前阶段”。

### 10.4 什么时候优先保持单体

以下情况，通常优先保持单体更合适：

1. 业务还在快速试错，需求变化大，边界并不稳定。
2. 团队人数不多，大家对全链路都有认知，不存在明显协作阻塞。
3. 当前主要问题不是模块耦合，而是业务本身还没跑通。
4. 系统规模还不大，部署、发布、排障成本都可控。
5. 没有明显的独立扩缩容诉求。
6. 监控、灰度、链路追踪、自动化测试等治理能力还不成熟。

这种阶段如果硬拆微服务，很容易出现：

1. 业务边界反复变化，拆完又改。
2. 服务数量变多，但问题没有减少。
3. 团队时间大量花在联调、网关、注册中心、配置中心、调用治理上。

### 10.5 什么时候开始认真考虑拆微服务

当下面几类信号开始同时出现时，就可以认真考虑拆分了。

#### 10.5.1 组织协作已经成为主要瓶颈

典型信号：

1. 多个团队同时改一个应用，频繁互相影响。
2. 发版要排队，一个模块上线牵动整个系统发布。
3. 某个模块出问题会拖累整站发布节奏。
4. 代码仓越来越大，新人理解全局成本明显上升。

这说明问题已经不只是“代码多”，而是组织协作被系统边界限制住了。

#### 10.5.2 模块边界已经逐渐稳定

只有边界稳定，拆分才有意义。典型信号包括：

1. 用户、订单、支付、库存、消息等领域边界已经相对清晰。
2. 模块之间的职责划分已经比较明确。
3. 某些模块的改动频率、资源模型、故障特征和其他模块明显不同。

如果边界还不清晰，拆分往往只是把单体里的混乱复制到网络上。

#### 10.5.3 独立扩缩容诉求已经出现

例如：

1. 搜索模块读流量极高，但下单链路相对平稳。
2. 报表、推荐、检索等模块资源消耗明显高于主交易链路。
3. 某些模块需要单独横向扩容，而不是整个系统一起扩。

这时候微服务的收益开始变得具体，因为拆分后可以按模块独立配置资源。

#### 10.5.4 故障隔离诉求明显增强

典型场景：

1. 某个非核心模块异常时，不希望拖垮核心交易链路。
2. 某个重任务模块抖动时，不希望影响主站响应。
3. 某些高风险功能希望单独隔离、单独熔断、单独限流。

微服务的一个重要收益，就是把故障面缩小，而不是所有问题都在一个进程里共振。

### 10.6 不要把性能问题简单等价成“该拆微服务”

这是很常见的误区。

单体出现性能问题，不一定意味着要拆服务，可能只是：

1. SQL 没优化好。
2. 缓存没用起来。
3. 线程池、连接池参数不合理。
4. 某几个模块代码实现低效。
5. 读写压力不均，需要先做缓存或读写分离。

如果系统瓶颈还在单点性能层面，通常应该先做局部优化，而不是直接上微服务。

### 10.7 拆微服务前最好先满足的前置条件

微服务不是“拆开就结束”，它依赖治理能力。至少要看这些前置条件：

1. 有比较清晰的领域边界或模块边界。
2. 有基本的日志、指标、链路追踪能力。
3. 有配置中心、注册发现、网关、权限、灰度等基础设施。
4. 有自动化测试、回归测试和发布回滚能力。
5. 团队对分布式问题有基本认知，比如超时、重试、幂等、雪崩、事务一致性。

如果这些能力没有跟上，微服务经常会把“代码复杂度问题”升级成“系统治理问题”。

### 10.8 拆分时通常有哪些可选路径

不是只有“单体”和“纯微服务”两个极端，中间有很多过渡方案。

#### 10.8.1 方案 A：继续保持单体，但加强模块化

适合：

1. 边界初步清晰，但还没到必须拆分的阶段。
2. 希望先降低代码耦合，再看是否需要独立部署。

优点：

1. 成本最低。
2. 能先把领域边界理顺。
3. 为后续拆服务做准备。

缺点：

1. 组织协作和独立部署问题没有彻底解决。

#### 10.8.2 方案 B：单体为主，只拆少量高价值服务

适合：

1. 只有少数模块具备明确独立性。
2. 只有少数模块有明显独立扩容或隔离诉求。

优点：

1. 风险较低。
2. 能在关键点上获得微服务收益。
3. 不会一下子把所有治理复杂度引进来。

缺点：

1. 单体和服务混合架构会持续存在一段时间。
2. 边界处理不好时，容易形成“双重复杂度”。

#### 10.8.3 方案 C：按领域逐步演进为微服务

适合：

1. 组织协作和模块边界都已经比较成熟。
2. 有持续治理微服务的能力。

优点：

1. 独立发布、独立扩容、独立治理收益更明显。
2. 更适合中大型团队并行开发。

缺点：

1. 引入分布式调用、链路复杂度、数据一致性和运维成本。

### 10.9 为什么很多团队拆完以后反而更痛苦

典型原因有：

1. 按数据库表拆，而不是按业务能力拆。
2. 边界没理顺，结果服务之间频繁互调。
3. 把“一个大泥球”拆成“多个小泥球”。
4. 治理能力没跟上，线上问题定位更困难。
5. 团队认知还停留在单体开发习惯，但系统已经变成分布式。

所以真正的重点不只是“拆”，而是“拆完之后系统是不是更容易演进和治理”。

### 10.10 推荐判断顺序

看到“要不要从单体升微服务”这个题时，建议按这个顺序判断：

1. 当前主要痛点到底是性能，还是协作与耦合。
2. 模块边界是否已经足够稳定。
3. 是否已经出现独立扩容、独立发布、故障隔离诉求。
4. 团队是否具备基本微服务治理能力。
5. 有没有更轻的过渡方案，比如先模块化、先拆高价值服务。

### 10.11 一句话结论

只有当系统的主要矛盾已经从“功能实现”升级为“模块耦合、组织协作、独立扩缩容和故障隔离”时，微服务拆分才真正值得做；否则单体往往更划算。

## 11. 高频题：同步调用 vs MQ 异步解耦

### 11.1 题目定义

这道题本质上是在比较：

1. 立即完成一个动作的确定性。
2. 用异步方式换取系统解耦、削峰和可用性的能力。

也可以理解成：

> 是优先追求“当场完成”，还是优先追求“整体更稳、更松耦合、更能抗峰值”。

### 11.2 两种方案各自解决什么问题

#### 11.2.1 同步调用

同步调用擅长解决：

1. 需要立刻拿到结果。
2. 当前链路必须在一个请求里闭环。
3. 业务流程强依赖下游返回。
4. 调用链比较短、依赖关系比较稳定。

#### 11.2.2 MQ 异步解耦

MQ 擅长解决：

1. 上下游解耦。
2. 瞬时流量削峰。
3. 下游处理慢，但不必要求当前请求立刻完成。
4. 主链路只需要确认“任务已接收”，不要求立即处理完。
5. 一个事件要被多个下游消费。

### 11.3 先问自己：这个动作是否必须“当场完成”

这是最关键的第一判断。

如果当前动作必须在用户请求返回前完成，比如：

1. 登录鉴权。
2. 支付结果同步确认。
3. 创建订单时的核心库存校验。
4. 风控校验必须先通过才能继续。

那同步调用通常更自然。

如果当前动作不要求当场完成，比如：

1. 下单后发短信、推消息、发优惠券。
2. 更新搜索索引。
3. 同步埋点、日志、审计记录。
4. 生成报表、异步计算画像、异步记忆沉淀。

那异步往往更合适。

### 11.4 什么时候优先同步调用

同步更适合下面这些情况：

1. 用户必须立即知道结果，否则体验不完整。
2. 当前步骤是主交易链路中的关键决策点。
3. 不拿到下游结果，后续就没法继续。
4. 业务上很难接受“先成功接单，后面再慢慢处理”。
5. 下游响应稳定，容量可预期，调用路径不长。

同步的优势是直观、简单、因果明确，但代价也很明显：

1. 上游强依赖下游可用性。
2. 调用链一长，超时和雪崩风险会上升。
3. 峰值时所有压力会沿链路传递。

### 11.5 什么时候优先 MQ 异步解耦

MQ 更适合下面这些情况：

1. 当前请求只需要先完成主流程，后续步骤可以稍后处理。
2. 下游处理慢、耗时长，或者吞吐不稳定。
3. 流量峰谷差明显，需要削峰填谷。
4. 同一个事件要广播给多个系统。
5. 希望主链路和非核心链路做隔离。

典型例子：

1. 订单创建后异步发券、发短信、积分入账。
2. 患者完成咨询后异步沉淀画像、记忆、审计日志。
3. 商品变更后异步刷新搜索索引和推荐数据。

### 11.6 什么时候不要轻易引入 MQ

MQ 不是“更高级的调用方式”，引入它也有很重的代价。

以下情况通常不值得：

1. 业务本身很简单，下游也很稳定，同步已经足够。
2. 这个动作强依赖立即结果，异步反而让流程更绕。
3. 团队还不具备消息可靠投递、消费重试、死信处理、幂等治理能力。
4. 只是为了“看起来更解耦”而把本来简单的流程做复杂。

很多系统不是“没用 MQ 所以不高级”，而是“同步本来就是正确答案”。

### 11.7 引入 MQ 之后新增的复杂度

这部分很重要，因为很多人只讲优点，不讲代价。

引入 MQ 后，通常要额外处理：

1. 消息丢失问题。
2. 消息重复消费问题。
3. 消费顺序问题。
4. 生产成功但业务事务失败的问题。
5. 业务成功但消息没发出去的问题。
6. 消费失败后的重试、死信、补偿问题。
7. 消费积压和下游处理能力不匹配的问题。

所以 MQ 的本质不是“更优雅”，而是“把时间和耦合问题转移成消息可靠性治理问题”。

### 11.8 三种常见选择方式

#### 11.8.1 方案 A：纯同步

适合：

1. 流程短。
2. 强依赖立即结果。
3. 下游稳定。

优点：

1. 简单直接。
2. 链路因果关系清晰。
3. 排障更容易。

缺点：

1. 耦合度高。
2. 抗峰值能力弱。
3. 下游慢时会直接拖慢上游。

#### 11.8.2 方案 B：主流程同步，非核心环节异步

这是最常见、也最务实的方案。

适合：

1. 主交易链路必须立即完成。
2. 但附属动作不必阻塞主请求。

优点：

1. 能兼顾用户体验和系统解耦。
2. 主链路更短，非核心逻辑更松耦合。

缺点：

1. 需要明确区分核心环节和附属环节。
2. 要治理消息可靠性。

#### 11.8.3 方案 C：事件驱动为主

适合：

1. 一个业务事件需要驱动多个下游系统。
2. 下游之间不希望强耦合。
3. 业务天然适合事件广播。

优点：

1. 扩展性强。
2. 下游新增能力时不必反向侵入上游。

缺点：

1. 全链路可观测性要求更高。
2. 排障难度明显上升。
3. 一致性收敛比同步方案复杂。

### 11.9 推荐判断顺序

1. 当前动作是否必须在请求返回前完成。
2. 如果不立即完成，用户和业务是否能接受。
3. 下游是否慢、重、波动大，是否需要削峰。
4. 是否有一对多事件分发诉求。
5. 团队是否具备消息可靠性治理能力。

### 11.10 一句话结论

凡是“必须立刻有结果”的关键步骤，优先同步；凡是“可以稍后完成、需要削峰、需要解耦、需要广播”的步骤，优先考虑 MQ 异步，但前提是团队能处理消息可靠性和幂等复杂度。

## 12. 高频题：XA / AT / TCC / 可靠消息最终一致性怎么选

### 12.1 题目定义

这道题本质上是在比较：

1. 一致性要多强。
2. 对性能和可用性能牺牲多少。
3. 业务能否接受异步和补偿。
4. 团队是否能承受方案复杂度。

所以这题不是“哪种分布式事务最好”，而是：

> 在一致性、性能、业务侵入性、实现复杂度之间找平衡。

### 12.2 先明确：能不用分布式事务就尽量不用

因为一旦跨服务、跨库，就会引入额外复杂度：

1. 网络不可靠。
2. 服务可能部分成功、部分失败。
3. 重试可能导致重复执行。
4. 事务边界不再天然统一。

所以第一判断不是“用 XA 还是 TCC”，而是：

1. 这个流程能否收敛成单库本地事务。
2. 这个流程能否通过业务重构减少跨服务写操作。
3. 这个流程是否真的需要事务式一致性。

### 12.3 先看一致性要求有多强

这里可以粗分成三类：

#### 12.3.1 强一致要求非常高

特征：

1. 不能接受中间状态长期暴露。
2. 资金、库存额度、核心配额等对错误极其敏感。
3. 出错后的人工修复代价高。

这类场景才值得考虑更重的事务方案。

#### 12.3.2 可以接受短暂不一致，但最终必须收敛

特征：

1. 允许短时间延迟。
2. 能通过重试、补偿、对账收敛。
3. 业务流程本身更关注“最终正确”，而不是“当场强闭环”。

这类场景通常更适合可靠消息最终一致性。

#### 12.3.3 实际上不需要事务一致性

例如：

1. 发送通知。
2. 记录埋点。
3. 刷新缓存。
4. 更新搜索索引。

这类动作很多时候只需要失败重试，不需要引入事务框架。

### 12.4 XA：最强一致，但最重

#### 12.4.1 XA 解决什么问题

XA 通过两阶段提交，追求比较强的事务一致性。

适合：

1. 对一致性要求高。
2. 参与方支持 XA。
3. 事务链路较短，参与资源较少。

#### 12.4.2 XA 的主要优点

1. 事务语义直观。
2. 一致性最强。
3. 业务侧侵入相对较少。

#### 12.4.3 XA 的主要问题

1. 性能开销大。
2. 锁持有时间长。
3. 阻塞明显，吞吐差。
4. 某个参与方卡住时，整体可用性受影响。

所以 XA 更适合少量高价值、低并发、必须强一致的场景，不适合大规模高并发链路。

### 12.5 AT：对业务侵入较低，但依赖数据库代理和回滚日志

#### 12.5.1 AT 的特点

AT 可以理解为：

1. 业务侧侵入较小。
2. 对现有本地事务改造成本相对低。
3. 通过代理数据源和 `undo_log` 做自动回滚。

#### 12.5.2 适合什么场景

1. 以关系型数据库更新为主。
2. 希望尽量少改业务代码。
3. 一致性要求较高，但又不想上 XA 那么重。
4. 事务链路比较清晰，SQL 比较规范。

#### 12.5.3 AT 的代价和边界

1. 依赖数据库代理机制。
2. 对 SQL 形态和隔离级别有要求。
3. 全局锁和回滚日志会带来额外开销。
4. 遇到复杂业务、复杂 SQL、非关系型资源时不适合。

所以 AT 常适合“数据库更新型”的中等复杂场景，但不适合把所有问题都往里塞。

### 12.6 TCC：业务可控性强，但侵入最重

#### 12.6.1 TCC 的核心思想

TCC 把一个业务动作拆成：

1. Try：预留资源。
2. Confirm：正式提交。
3. Cancel：取消释放。

它的本质是把“事务控制权”交回业务层。

#### 12.6.2 TCC 适合什么场景

1. 一致性要求高。
2. 资源预留语义清晰。
3. 业务能明确拆出 Try / Confirm / Cancel。
4. 团队能处理幂等、空回滚、防悬挂等问题。

典型场景：

1. 资金冻结与扣减。
2. 库存预占与确认。
3. 配额预留与正式消耗。

#### 12.6.3 TCC 的优点

1. 业务可控性高。
2. 不像 XA 那样强依赖底层资源锁。
3. 更适合关键资源预留型场景。

#### 12.6.4 TCC 的代价

1. 对业务侵入非常强。
2. 开发量大。
3. 对幂等、空回滚、防悬挂要求高。
4. 设计不严谨时，非常容易留下边界 bug。

所以 TCC 不是“更高级的标准答案”，而是“关键场景下愿意付出高成本换强控制力”的方案。

### 12.7 可靠消息最终一致性：最务实、最常见

#### 12.7.1 核心思路

先保证本地事务成功，再通过可靠消息把后续动作异步推进，并通过重试、补偿、对账把状态最终收敛。

典型做法包括：

1. 本地事务 + 发送消息。
2. Outbox 表 + 异步投递。
3. 消费侧幂等 + 重试 + 死信治理。
4. 对账任务 + 补偿任务。

#### 12.7.2 适合什么场景

1. 可以接受短暂不一致。
2. 更关注吞吐、解耦和系统可用性。
3. 业务上允许异步收敛。
4. 有成熟的重试、补偿和对账机制。

#### 12.7.3 优点

1. 吞吐更好。
2. 链路阻塞更少。
3. 更适合高并发系统。
4. 架构弹性更强。

#### 12.7.4 代价

1. 一致性不是立即达成。
2. 需要完整的消息可靠性治理。
3. 需要幂等、补偿、对账体系。
4. 排障链路更长。

很多互联网业务最终都会倾向这条路线，因为它在工程上更可持续。

### 12.8 一个实用的选择顺序

可以按下面顺序判断：

1. 能不能不做分布式事务，改成单库闭环。
2. 能不能接受最终一致性。
3. 如果能接受，优先考虑可靠消息最终一致性。
4. 如果不能接受，再看是否只是数据库更新型场景，能否用 AT。
5. 如果是关键资源预留型强一致场景，再考虑 TCC。
6. 只有在参与方支持、并发不高且必须追求更强一致时，才慎重考虑 XA。

### 12.9 常见误区

#### 12.9.1 误区一：一致性越强越好

不是。一致性越强，通常意味着：

1. 性能更差。
2. 阻塞更多。
3. 可用性更受影响。
4. 事务成本更高。

工程里追求的是“足够的一致性”，不是“无限强一致”。

#### 12.9.2 误区二：TCC 比可靠消息更高级

不是。TCC 只是更重、更强控制力，不代表更普适。

如果业务允许异步收敛，可靠消息通常更务实。

#### 12.9.3 误区三：AT 可以无脑覆盖所有数据库事务场景

也不是。只要业务复杂度高、SQL 特性复杂、资源类型不统一，AT 就会遇到边界问题。

### 12.10 结合 Seata 的一个实际判断

如果问题换成“什么时候考虑 Seata TCC”，可以这么看：

1. 是否属于核心资源操作。
2. 是否不能接受最终一致性延迟。
3. 是否能把业务动作明确抽成 Try / Confirm / Cancel。
4. 是否愿意承担较高业务侵入和补偿复杂度。

如果这些条件不满足，通常优先考虑更轻的方案。

### 12.11 一句话结论

能不用分布式事务就不用；能接受最终一致性，优先可靠消息；数据库更新型中等复杂场景可以考虑 AT；关键资源预留型强一致场景再考虑 TCC；XA 只适合少数必须强一致且能接受高成本的场景。

## 13. 高频题：Redis 缓存什么时候值得引入

### 13.1 题目定义

这道题本质上不是“Redis 好不好用”，而是在判断：

1. 当前性能瓶颈是否已经明显集中在数据读取。
2. 用额外的缓存复杂度，能否换来明显的性能收益和成本收益。
3. 引入缓存后的不一致、失效、穿透、击穿等问题，是否值得承担。

所以关键不是“会不会用 Redis”，而是“当前业务阶段值不值得引入缓存层”。

### 13.2 先明确：不是所有系统都应该先上缓存

缓存是典型的“用复杂度换性能”的方案。

它的收益很明显：

1. 降低数据库压力。
2. 提升热点读性能。
3. 减少高峰期数据库抖动。

但代价也同样明确：

1. 数据一致性变复杂。
2. 失效策略需要设计。
3. 容量、过期、淘汰、热点问题要治理。
4. 代码路径和排障路径变长。

所以判断重点不是“Redis 能不能加”，而是“它是不是当前最划算的优化手段”。

### 13.3 什么时候值得认真考虑引入 Redis

#### 13.3.1 数据库读压力已经成为主要瓶颈

典型信号：

1. 大量请求都在重复读取相似数据。
2. 数据库 CPU、连接数、IO 压力持续偏高。
3. 高峰期数据库 RT 明显上升。
4. 慢查询不多，但整体读请求量太大。

这种场景说明问题不一定是 SQL 写得差，而是重复读本身已经值得缓存。

#### 13.3.2 存在明显热点数据

例如：

1. 商品详情页、医生主页、活动配置、字典配置。
2. 某些固定榜单、推荐结果、热门查询条件。
3. 会被高频重复读取，但更新频率不高的数据。

这类数据天然适合缓存，因为读远大于写，且缓存命中率通常较高。

#### 13.3.3 对读取延迟比较敏感

典型场景：

1. 首页展示。
2. 搜索结果前置过滤条件。
3. 风控规则读取。
4. AI 主链路中的画像、配置、Prompt 模板片段读取。

如果每次都直查数据库会拉长主链路 RT，而数据本身又相对稳定，那缓存收益会比较直接。

#### 13.3.4 峰值明显，需要缓冲数据库压力

例如：

1. 秒杀、活动、挂号抢号、热点问诊时段。
2. 某些内容被推荐后瞬时流量暴涨。

这时候 Redis 不只是提速，更是保护数据库。

### 13.4 什么时候不急着上 Redis

以下情况通常不应该把 Redis 当成第一选择：

1. 业务还很早期，流量规模并不大。
2. 真正问题在慢 SQL、索引缺失、表设计不合理。
3. 数据变化非常频繁，缓存命中率不会高。
4. 读取并不高频，但团队习惯性“先上缓存再说”。
5. 还没有搞清楚瓶颈在哪，就先把缓存当万能药。

很多时候数据库本身没到极限，只是基础优化还没做。

### 13.5 引入 Redis 前最好先做的排查

建议先确认这些问题：

1. SQL 是否已经优化。
2. 索引是否合理。
3. 是否存在不必要的大字段查询。
4. 是否可以先做分页、裁剪字段、读写分离等轻量优化。
5. 读压力到底是全局性的，还是个别热点接口导致的。

如果这些问题没看清，直接上 Redis 很可能只是把问题藏起来，而不是解决掉。

### 13.6 Redis 最适合缓存什么数据

比较适合缓存的数据通常有这些特征：

1. 读多写少。
2. 更新频率可控。
3. 短时间不一致可接受。
4. 访问模式相对稳定。
5. 命中率有保障。

典型例子：

1. 用户基础信息快照。
2. 商品详情、医生主页、机构信息。
3. 配置项、字典项、规则集。
4. 会话级状态、短时令牌、验证码。
5. 热点排行榜、统计快照、预计算结果。

### 13.7 Redis 不太适合缓存什么数据

1. 强一致要求极高的数据。
2. 高频写入且读取模式不稳定的数据。
3. 数据量极大但命中率很低的数据。
4. 缓存失效后回源代价极高且无保护机制的数据。
5. 生命周期极短、还没命中就失效的数据。

这类场景硬上缓存，往往收益不明显，反而增加维护成本。

### 13.8 常见引入路径

#### 13.8.1 方案 A：数据库直查

适合：

1. 流量不大。
2. 读压力可控。
3. 一致性要求高。

优点：

1. 最简单。
2. 数据语义最直接。
3. 不会引入缓存一致性问题。

缺点：

1. 高峰期数据库容易成为瓶颈。
2. 热点读性能有限。

#### 13.8.2 方案 B：只缓存少量高价值热点数据

适合：

1. 只有少数接口存在明显热点。
2. 希望用最小成本获得收益。

优点：

1. 风险低。
2. 收益集中。
3. 有利于逐步建立缓存治理能力。

缺点：

1. 无法解决全局性读压力问题。

#### 13.8.3 方案 C：系统性构建缓存层

适合：

1. 读流量大且持续增长。
2. 热点和常规读取都已经明显依赖缓存。
3. 团队已有较成熟的缓存治理能力。

优点：

1. 整体性能和扩展性更强。
2. 数据访问分层更清晰。

缺点：

1. 一致性、预热、淘汰、降级等复杂度显著上升。

### 13.9 引入 Redis 后新增的典型问题

1. 缓存和数据库双写一致性问题。
2. 缓存穿透。
3. 缓存击穿。
4. 缓存雪崩。
5. 热点 key 问题。
6. 大 key 问题。
7. 失效时间设置不合理导致抖动。

所以缓存从来不是“加一层就结束”，而是进入新的治理阶段。

### 13.10 推荐判断顺序

1. 当前瓶颈是否真的在读路径。
2. 瓶颈是数据库整体压力，还是少数热点数据。
3. 数据是否具备“读多写少、可接受短暂不一致”的特征。
4. 是否已经做过基础 SQL / 索引优化。
5. 团队是否能处理一致性和热点治理问题。

### 13.11 一句话结论

只有当读压力、热点访问或低延迟诉求已经明显，且数据本身适合缓存时，引入 Redis 才真正划算；如果基础优化还没做完，或者数据天然不适合缓存，先上 Redis 往往只是过早复杂化。

## 14. 高频题：本地缓存 vs Redis

### 14.1 题目定义

这道题本质上不是“哪个性能更好”，而是在判断：

1. 是优先追求极致低延迟。
2. 还是优先追求多实例之间的数据共享和统一治理。

也可以理解成：

> 用一致性和集中管理能力，去换性能；或者用极低读取开销，去换更高的一致性治理成本。

### 14.2 两者的本质区别

#### 14.2.1 本地缓存

本地缓存存放在应用实例内部。

特点：

1. 读取最快。
2. 不依赖网络。
3. 单实例命中成本极低。

但问题也很明显：

1. 多实例之间天然不共享。
2. 数据更新时很难同时失效。
3. 容易出现实例间数据不一致。

#### 14.2.2 Redis

Redis 是集中式缓存。

特点：

1. 多实例共享同一份缓存数据。
2. 统一失效、统一治理更容易。
3. 更适合分布式系统。

但代价是：

1. 需要网络访问。
2. 读取性能虽然高，但仍慢于本地内存。
3. Redis 本身也需要治理和容量规划。

### 14.3 什么时候优先本地缓存

本地缓存更适合这些场景：

1. 数据更新非常少，几乎是只读。
2. 对延迟极其敏感。
3. 单实例内高频重复访问同一份数据。
4. 即便短时间实例间不一致，业务影响也很小。
5. 数据量不大，能安全放进应用内存。

典型例子：

1. 字典项。
2. 配置快照。
3. 固定规则集。
4. 很少变化的白名单、黑名单。

### 14.4 什么时候优先 Redis

Redis 更适合这些场景：

1. 服务是多实例部署。
2. 需要多节点共享缓存。
3. 数据更新后希望尽快全局生效。
4. 数据量较大，不适合每个实例都存一份。
5. 希望统一控制 TTL、淘汰、统计、热点治理。

典型例子：

1. 用户会话状态。
2. 登录令牌。
3. 用户信息快照。
4. 热点详情页缓存。
5. 跨实例共享的限流计数和幂等状态。

### 14.5 什么时候两者结合更合适

很多时候不是二选一，而是两级缓存更合适：

1. 本地缓存负责极致低延迟。
2. Redis 负责集中共享和跨实例一致性。

这种方案适合：

1. 热点数据读取非常高频。
2. 既想降低 Redis 压力，又想比纯本地缓存更可控。
3. 团队能处理缓存刷新广播或版本控制。

但这也是复杂度最高的方案，因为要同时处理：

1. 本地缓存失效。
2. Redis 失效。
3. 两级缓存数据不一致。
4. 刷新顺序和广播延迟问题。

### 14.6 本地缓存常见风险

1. 多实例数据不一致。
2. 发布新实例后缓存冷启动。
3. 缓存更新无法及时通知所有节点。
4. 内存占用失控。
5. 某些节点命中高、某些节点命中低，效果不稳定。

### 14.7 Redis 常见风险

1. 额外网络开销。
2. Redis 成为共享依赖，需要高可用治理。
3. 热点 key 可能集中打爆单点。
4. 大量 key 过期造成抖动。
5. 如果所有读取都强依赖 Redis，Redis 异常会放大影响面。

### 14.8 三种常见选择方式

#### 14.8.1 方案 A：纯本地缓存

适合：

1. 几乎只读。
2. 小数据集。
3. 不强调全局强一致。

优点：

1. 最快。
2. 成本低。
3. 实现简单。

缺点：

1. 多实例一致性差。
2. 扩容后每台机器都要重新预热。

#### 14.8.2 方案 B：纯 Redis

适合：

1. 分布式部署。
2. 共享状态明显。
3. 一致性和统一治理要求更高。

优点：

1. 数据共享简单。
2. 管理统一。
3. 更适合业务状态型缓存。

缺点：

1. 性能不如本地内存。
2. 引入网络依赖。

#### 14.8.3 方案 C：本地缓存 + Redis 两级缓存

适合：

1. 热点读非常高。
2. Redis 压力明显。
3. 团队能接受更高治理复杂度。

优点：

1. 性能最好。
2. 扩展性更强。

缺点：

1. 最难治理。
2. 失效和一致性问题最复杂。

### 14.9 推荐判断顺序

1. 数据是否需要多实例共享。
2. 数据更新频率高不高。
3. 是否能接受短时间实例间不一致。
4. 读取延迟是否极其敏感。
5. 团队是否能承受两级缓存治理复杂度。

### 14.10 一句话结论

如果数据天然只读、变化极少、对极致低延迟敏感，可以优先本地缓存；如果是分布式共享状态或需要统一治理，优先 Redis；只有在热点极高且团队能驾驭复杂度时，才考虑两级缓存。

## 15. 高频题：分库分表什么时候做，什么时候坚决不做

### 15.1 题目定义

这道题本质上不是“数据大了就分”，而是在判断：

1. 当前单库单表是否真的已经逼近性能或容量边界。
2. 分库分表带来的收益，是否足以覆盖随之而来的开发、运维和查询复杂度。

所以核心不是“会不会分库分表”，而是“现在是不是已经值得为扩展性付出这么高的成本”。

### 15.2 先明确：分库分表是重型方案

它解决的问题主要是：

1. 单表数据量过大。
2. 单库写入或存储压力过大。
3. 热点访问集中。
4. 横向扩展空间不足。

但它的代价也非常重：

1. 跨分片查询复杂。
2. 分页、排序、聚合、Join 难度上升。
3. 主键、路由键设计变重要。
4. 数据迁移和扩容成本很高。
5. 运维、排障、对账复杂度明显提高。

所以分库分表通常不是“优化手段”，而是“架构阶段性升级”。

### 15.3 什么时候可以开始认真考虑分库分表

#### 15.3.1 单表数据量已经持续增长到不可忽视

典型信号：

1. 单表数据规模非常大。
2. 索引体积持续膨胀。
3. 查询和写入 RT 随数据量持续恶化。
4. 归档之后仍然增长很快。

注意重点不是死记某个绝对数字，而是看增长趋势和实际瓶颈。

#### 15.3.2 单库写入压力已经明显接近瓶颈

例如：

1. 高并发订单写入。
2. 高频交易流水写入。
3. 日志型业务写入量巨大。
4. 某个核心表已经成为全站写热点。

这类问题如果已经不是单纯索引或 SQL 能解决的，就要考虑横向拆分能力。

#### 15.3.3 业务天然可以按某个维度拆分

比如按：

1. 用户 ID。
2. 商户 ID。
3. 订单号。
4. 租户 ID。
5. 时间区间。

只有当业务天然存在稳定路由键时，分片方案才容易落地。

#### 15.3.4 已经明确需要长期横向扩展

如果能够预见未来数据和写入规模会持续增长，而且已经不是短期活动波动，而是长期趋势，那提前设计分片会更稳。

### 15.4 什么时候坚决不要急着做

以下情况通常不应该轻易上分库分表：

1. 当前性能问题主要是慢 SQL、索引不合理、表结构设计差。
2. 数据量虽然在增长，但离瓶颈还很远。
3. 业务边界和路由键还不稳定。
4. 团队还没有处理分布式数据层复杂度的经验。
5. 只是为了“显得架构更高级”而提前做。

很多系统真正的问题不是“单库不行”，而是“数据库基本功还没做好”。

### 15.5 分库分表前最好先做哪些轻量手段

在走到分库分表之前，通常优先尝试：

1. SQL 优化。
2. 索引优化。
3. 冷热数据归档。
4. 读写分离。
5. 缓存前置。
6. 垂直拆表。
7. 按时间分区或归档表。

这些方案成本通常远低于分库分表，而且很多时候已经足够。

### 15.6 分库分表更适合什么类型的数据

更适合：

1. 交易流水类数据。
2. 日志类数据。
3. 订单类数据。
4. 明细类数据。
5. 用户维度天然独立的大表。

这类数据通常有明确的路由键，而且跨分片事务和复杂 Join 需求相对更容易控制。

### 15.7 分库分表不太适合什么类型的数据

1. 强依赖多表 Join 的复杂关系型查询。
2. 经常需要跨全量范围统计的数据。
3. 路由键不稳定或经常变更的数据。
4. 规模还不大，但业务逻辑已经很复杂的数据。

如果这些场景强行分片，业务代码和查询层会迅速变重。

### 15.8 常见演进路径

#### 15.8.1 方案 A：单库单表

适合：

1. 规模尚可控。
2. 结构稳定。
3. 开发效率优先。

优点：

1. 最简单。
2. 查询能力最强。
3. 运维和排障最低成本。

缺点：

1. 扩展上限有限。

#### 15.8.2 方案 B：单库分表

适合：

1. 单表过大，但单库还能扛住。
2. 主要矛盾是单表索引和数据规模。

优点：

1. 比分库更轻。
2. 能先解决单表膨胀问题。

缺点：

1. 单库资源上限仍在。
2. 跨表查询已开始复杂化。

#### 15.8.3 方案 C：分库分表

适合：

1. 数据量和写入压力都很大。
2. 已经明确需要横向扩展。
3. 路由规则稳定。

优点：

1. 水平扩展空间更大。
2. 能分散单点写入和存储压力。

缺点：

1. 架构和业务复杂度显著上升。

### 15.9 分库分表后新增的典型问题

1. 分布式主键设计。
2. 路由规则变更困难。
3. 跨分片分页、排序、聚合复杂。
4. 跨分片事务和一致性处理更麻烦。
5. 数据迁移、扩容、再平衡成本高。
6. 运维排障、数据修复和对账更难。

所以分库分表不是“做完就完”，而是后面长期都要为它付维护成本。

### 15.10 推荐判断顺序

1. 当前瓶颈到底是单表、单库，还是 SQL / 索引本身。
2. 是否已经做过归档、缓存、读写分离等轻量优化。
3. 数据增长是否是长期趋势，而不是短期波峰。
4. 是否存在稳定且合理的分片键。
5. 团队是否能接受查询、事务、迁移、运维复杂度提升。

### 15.11 一句话结论

只有当单库单表已经真实逼近容量或写入瓶颈、轻量优化不再有效、业务又具备稳定分片键时，分库分表才值得做；否则它很容易成为一次过早而昂贵的复杂化。

## 16. 高频题：Elasticsearch 什么时候引入

### 16.1 题目定义

这道题本质上不是“搜索都该上 ES”，而是在判断：

1. 当前查询需求是否已经超出关系型数据库的舒适区。
2. 是否值得用额外的数据同步、索引维护和一致性复杂度，换取更强的检索能力。

所以关键不是“会不会用 ES”，而是“数据库能不能继续承担这类查询任务，以及继续承担的代价有多高”。

### 16.2 先明确：ES 不是数据库的直接替代品

ES 更擅长的是：

1. 全文检索。
2. 多条件组合搜索。
3. 相关性排序。
4. 海量数据下的复杂检索体验优化。

它不擅长的地方也很明显：

1. 事务一致性弱。
2. 数据实时一致性不如数据库。
3. 数据同步链路更复杂。
4. 运维和索引治理成本不低。

所以 ES 更像“面向检索场景的专用引擎”，而不是“把数据库替换掉”的通用解法。

### 16.3 什么时候开始认真考虑引入 ES

#### 16.3.1 查询需求已经明显偏全文检索

典型场景：

1. 搜文章、病历摘要、商品标题、问答内容。
2. 需要按关键词召回，而不是按主键或精确条件查。
3. 需要分词、模糊匹配、同义词扩展。

这种场景数据库即使能做 `like`，效果和性能通常都不理想。

#### 16.3.2 需要复杂筛选 + 排序 + 分页的搜索体验

例如：

1. 商品搜索要同时支持品牌、价格区间、标签、库存状态、销量排序。
2. 医生搜索要支持科室、职称、擅长方向、地区、在线状态组合筛选。
3. 内容搜索要支持时间、热度、相关性混合排序。

这种“搜索产品型需求”往往比普通数据库查询复杂得多。

#### 16.3.3 数据规模和搜索性能压力已经明显上来

典型信号：

1. 模糊搜索 SQL 越来越慢。
2. 为搜索需求加了很多索引，但收益越来越有限。
3. 查询高峰时数据库压力明显增大。
4. 搜索接口成为系统性能短板。

这种时候继续在数据库上硬撑，成本会越来越高。

#### 16.3.4 业务已经需要“搜索体验”，不只是“能查到”

例如：

1. 要支持高亮。
2. 要支持拼写纠错、同义词、联想建议。
3. 要支持相关性排序，而不是单纯按时间倒排。

一旦需求从“查得到”变成“查得像搜索引擎”，ES 的价值就会明显上升。

### 16.4 什么时候不急着上 ES

以下情况通常不应该第一时间引入 ES：

1. 查询本质仍是精确查询或简单列表查询。
2. 数据量并不大，数据库完全能承受。
3. 模糊搜索只是少数长尾需求，不值得专门建索引体系。
4. 团队还没有处理数据同步、索引设计、集群运维的经验。
5. 只是因为“听说搜索就该上 ES”。

如果数据库已经足够，提前上 ES 只会带来额外链路和一致性负担。

### 16.5 引入 ES 前最好先做的判断

建议先确认：

1. 这是“搜索问题”还是“普通查询问题”。
2. 当前瓶颈是 SQL 写法、索引设计，还是数据库天然不适合这类查询。
3. 搜索是否已经成为用户核心入口。
4. 是否能接受数据库和 ES 之间的最终一致性。
5. 数据同步失败时有没有补偿和重建能力。

### 16.6 ES 最适合承载什么数据

更适合：

1. 商品、内容、文档、问答、病历摘要这类文本型数据。
2. 需要多维过滤 + 搜索 + 排序的数据。
3. 查询远多于更新的数据。
4. 可接受短暂索引延迟的数据。

### 16.7 ES 不太适合承载什么数据

1. 强事务一致要求的数据。
2. 高频更新且必须立刻精确可见的数据。
3. 只是按主键或精确条件查询的数据。
4. 规模不大但维护要求很高的数据。

这些场景继续留在数据库里通常更稳妥。

### 16.8 常见演进路径

#### 16.8.1 方案 A：数据库查询

适合：

1. 精确查询为主。
2. 数据量还可控。
3. 搜索需求不复杂。

优点：

1. 简单。
2. 一致性最好。
3. 维护成本低。

缺点：

1. 全文检索能力弱。
2. 搜索体验天花板低。

#### 16.8.2 方案 B：数据库为主，少量搜索接口单独上 ES

适合：

1. 只有核心搜索场景明显需要 ES。
2. 想控制引入成本。

优点：

1. 风险更低。
2. 能把复杂度集中在高价值接口。

缺点：

1. 数据源双轨并存。
2. 仍要处理同步一致性问题。

#### 16.8.3 方案 C：系统性建设搜索平台

适合：

1. 搜索是核心产品能力。
2. 多个业务域都依赖搜索。
3. 团队具备索引治理和集群治理能力。

优点：

1. 搜索能力更强。
2. 更适合长期演进。

缺点：

1. 数据链路、资源成本、治理复杂度都显著上升。

### 16.9 引入 ES 后新增的典型问题

1. 数据同步延迟。
2. 索引 mapping 设计错误后调整成本高。
3. 重建索引和回填复杂。
4. 查询 DSL 和相关性调优门槛较高。
5. 集群容量、分片、冷热数据治理复杂。

### 16.10 推荐判断顺序

1. 需求到底是搜索还是普通查询。
2. 数据库是不是已经不适合这类查询。
3. 搜索是否已经成为核心用户体验。
4. 是否能接受最终一致性。
5. 团队是否能承受索引和集群治理成本。

### 16.11 一句话结论

只有当查询需求已经明显演变成“搜索产品问题”，数据库在性能或体验上都开始吃力，且业务能接受索引最终一致性时，引入 Elasticsearch 才真正值得。

## 17. 高频题：乐观锁 vs 悲观锁 vs 分布式锁

### 17.1 题目定义

这道题本质上是在比较：

1. 用失败重试控制并发冲突。
2. 用提前阻塞控制并发冲突。
3. 或者在多实例分布式环境中，用外部协调来控制并发冲突。

所以它不是单纯的“哪种锁更高级”，而是：

> 冲突频率、资源范围、并发成本、系统部署方式不同，控制手段也不同。

### 17.2 先明确：先区分问题类型，再谈锁

很多并发问题并不一定非要靠“锁”解决。先判断：

1. 是单机并发问题，还是多实例并发问题。
2. 是数据库行更新冲突，还是业务动作防重。
3. 是资源抢占问题，还是顺序执行问题。

如果问题本质没分清，很容易上错工具。

### 17.3 乐观锁适合什么场景

乐观锁的核心思路是：

1. 默认冲突不频繁。
2. 提交时再检测是否被别人改过。
3. 发生冲突时失败重试或返回失败。

常见实现方式：

1. 版本号。
2. CAS 思路。
3. 更新时间戳比对。

适合：

1. 读多写少。
2. 冲突概率不高。
3. 可以接受少量重试。
4. 更关注吞吐，不希望大量阻塞。

典型例子：

1. 用户资料更新。
2. 配置修改。
3. 普通状态流转。

### 17.4 悲观锁适合什么场景

悲观锁的核心思路是：

1. 默认认为冲突会发生。
2. 操作前先锁住资源。
3. 其他并发请求先等待。

典型实现：

1. 数据库行锁。
2. `select ... for update`。

适合：

1. 写冲突频繁。
2. 不能接受多次重试带来的业务复杂度。
3. 需要在一个事务里强控制更新顺序。
4. 资源范围能被数据库事务很好覆盖。

典型例子：

1. 高冲突库存扣减。
2. 核心账户余额修改。
3. 同一记录的串行状态变更。

### 17.5 分布式锁适合什么场景

分布式锁适合这些情况：

1. 多实例部署下，多个节点会同时竞争同一资源。
2. 问题范围已经超出单数据库事务或单 JVM。
3. 需要跨进程协调“同一时刻只能一个执行者处理”。

典型例子：

1. 定时任务只允许一个实例执行。
2. 某个全局唯一动作不能重复触发。
3. 跨实例共享资源需要排他处理。

### 17.6 什么时候不要轻易上分布式锁

这是很常见的误区。以下情况通常不应该先想到分布式锁：

1. 实际上只是数据库单行更新冲突，用乐观锁或悲观锁就够了。
2. 实际问题是接口幂等，不是资源互斥。
3. 可以通过唯一索引、状态机、消息串行化解决。
4. 团队没有处理锁续期、超时、误删、可重入等边界经验。

很多问题不是“必须分布式锁”，而是“先把业务约束建模清楚”。

### 17.7 三种方案的核心取舍

#### 17.7.1 乐观锁

优点：

1. 吞吐高。
2. 不容易长时间阻塞。
3. 实现相对轻量。

缺点：

1. 冲突高时重试成本大。
2. 失败率可能高。
3. 对调用方补偿和重试设计有要求。

#### 17.7.2 悲观锁

优点：

1. 冲突处理直接。
2. 事务内控制力强。
3. 更适合高冲突资源。

缺点：

1. 容易阻塞。
2. 吞吐会下降。
3. 锁持有时间长时容易放大问题。

#### 17.7.3 分布式锁

优点：

1. 能解决跨实例互斥问题。
2. 适用范围比单库事务更广。

缺点：

1. 实现和治理最复杂。
2. 锁失效、续期、脑裂、误释放都要考虑。
3. 如果使用不当，容易把问题做得更脆弱。

### 17.8 一个很重要的判断顺序

建议按这个顺序想：

1. 能不能通过唯一索引、状态约束、幂等设计解决。
2. 如果是数据库单行并发更新，冲突低不低。
3. 冲突低，优先考虑乐观锁。
4. 冲突高且事务范围在数据库内，考虑悲观锁。
5. 只有当问题跨实例、跨进程、跨本地事务边界时，才考虑分布式锁。

### 17.9 常见误区

#### 17.9.1 误区一：分布式系统就应该优先用分布式锁

不是。分布式锁通常是成本最高、边界最多的工具，应该最后考虑，不是第一反应。

#### 17.9.2 误区二：乐观锁一定比悲观锁高级

不是。冲突高时，乐观锁反而可能造成大量无效重试，整体效果比悲观锁更差。

#### 17.9.3 误区三：有锁就等于解决了一致性问题

也不是。锁只解决“并发进入”的一部分问题，不自动解决幂等、补偿、事务边界和跨系统一致性。

### 17.10 一句话结论

冲突低、可重试，优先乐观锁；冲突高、事务范围在数据库内，优先悲观锁；只有在跨实例互斥确实无法靠数据库约束和业务幂等解决时，才考虑分布式锁。

## 18. 高频题：限流、熔断、降级分别什么时候优先做

### 18.1 题目定义

这道题本质上是在比较：

1. 是先控制流量进入。
2. 还是先阻断故障传播。
3. 还是先牺牲部分功能保证主链路可用。

也可以理解成：

> 限流、熔断、降级不是同一个动作，而是分别应对“流量过大”“下游不稳”“资源不够时保核心”的三种问题。

### 18.2 先明确三者分别解决什么问题

#### 18.2.1 限流

限流解决的是：

1. 请求太多，系统吃不下。
2. 高峰流量可能把服务直接打垮。
3. 需要把流量控制在系统承载范围内。

重点是“控制进入量”。

#### 18.2.2 熔断

熔断解决的是：

1. 下游已经明显失败或变慢。
2. 如果继续调用，只会让更多线程、连接、资源被拖死。
3. 需要快速失败，阻断故障扩散。

重点是“切断坏依赖”。

#### 18.2.3 降级

降级解决的是：

1. 系统资源不足时，核心功能优先。
2. 非核心能力可以暂时关闭、简化、延后。
3. 用户至少还能完成关键动作。

重点是“牺牲部分体验，保整体可用”。

### 18.3 什么时候优先做限流

限流通常优先出现在这些场景：

1. 峰值流量明显高于系统承载能力。
2. 活动、秒杀、热点事件会带来突发流量。
3. 某些接口天然容易被刷。
4. 核心服务前必须有流量闸门。

典型例子：

1. 登录接口防暴力请求。
2. 秒杀下单入口。
3. 网关层统一流量保护。

### 18.4 什么时候优先做熔断

熔断通常优先出现在这些场景：

1. 强依赖下游服务，但下游不稳定。
2. 下游一慢就会把上游线程池、连接池拖满。
3. 某些依赖属于非关键能力，失败时应该尽快止损。

典型例子：

1. 推荐服务异常时，不应拖慢下单主链路。
2. 外部三方接口波动时，不应无限等待。
3. AI 模型服务抖动时，需要快速回退保守回复。

### 18.5 什么时候优先做降级

降级通常优先出现在这些场景：

1. 系统资源紧张时，必须优先保核心业务。
2. 某些功能虽然重要，但不是当前请求闭环必须项。
3. 可以接受功能变弱，但不能接受整链路不可用。

典型例子：

1. 首页先关闭个性化推荐，保基础内容可见。
2. AI 链路先关闭记忆增强或复杂工具调用，保基础问答可用。
3. 下单链路保支付和订单写入，临时关闭积分、消息、推荐回写。

### 18.6 三者的关系，不是互斥，而是分层配合

常见协同方式是：

1. 用限流守入口。
2. 用熔断守依赖。
3. 用降级守核心链路。

也就是说：

1. 限流更多是“别让系统被洪峰冲垮”。
2. 熔断更多是“别让坏下游把我拖死”。
3. 降级更多是“资源不够时先保命，再谈完整体验”。

### 18.7 什么时候不要只会说“都做”

面试或设计时，如果不区分场景，一句“限流熔断降级都做”其实没信息量。

真正要看的是：

1. 当前最大的风险到底是流量洪峰，还是依赖抖动，还是资源不足。
2. 哪个问题最先会击穿系统。
3. 哪个动作收益最大、落地最快。

工程上永远是先打主矛盾。

### 18.8 一个实用的优先级判断

#### 18.8.1 如果主要风险是流量超过承载

优先限流。

因为如果入口不控流，后面再怎么熔断和降级也只是延缓崩溃。

#### 18.8.2 如果主要风险是依赖服务不稳定

优先熔断。

因为问题核心不在“请求太多”，而在“坏依赖持续拖住资源”。

#### 18.8.3 如果主要风险是资源紧张时核心链路和次要链路抢资源

优先降级。

因为真正要解决的是资源分配和功能优先级问题。

### 18.9 常见误区

#### 18.9.1 误区一：限流就是稳定性全部

不是。限流只管入口流量，不解决坏依赖拖垮和非核心功能抢资源的问题。

#### 18.9.2 误区二：熔断越敏感越好

不是。熔断阈值过于激进，会导致系统频繁抖动，正常请求也被误伤。

#### 18.9.3 误区三：降级就是报错

也不是。好的降级不是简单失败，而是提供“弱化但可用”的替代能力。

### 18.10 一句话结论

流量扛不住时优先限流，下游不稳时优先熔断，资源不够但必须保核心链路时优先降级；三者不是替代关系，而是不同层次的稳定性手段。

## 19. 高频题：微服务拆分粒度怎么定

### 19.1 题目定义

这道题本质上不是“拆得越细越好”，而是在判断：

1. 服务边界应该按什么能力划分。
2. 拆到什么程度，收益开始小于复杂度。

也就是说，这题真正比较的是：

> 用更细的边界换更强的独立性，但边界过细又会把进程内复杂度转移成网络和治理复杂度。

### 19.2 先明确：拆分粒度过粗和过细都会出问题

拆得过粗，问题通常是：

1. 服务内部仍然像一个小单体。
2. 发布耦合没有真正改善。
3. 不同模块资源模型差异仍然绑在一起。

拆得过细，问题通常是：

1. 服务之间调用链过长。
2. 联调、测试、排障成本显著上升。
3. 一个业务动作要跨太多服务协同。
4. 数据一致性和事务复杂度迅速增加。

所以拆分粒度的重点不是“细”，而是“边界是否稳定、协作是否顺畅、治理是否可控”。

### 19.3 优先按什么维度拆

通常优先考虑这些维度：

1. 业务能力边界。
2. 领域模型边界。
3. 团队协作边界。
4. 独立扩缩容边界。

最不建议优先按这些方式硬拆：

1. 按数据库表拆。
2. 按 Controller 包拆。
3. 按代码层次拆。

因为这些拆法往往只是在代码结构上切开，并没有形成真正稳定的业务边界。

### 19.4 什么样的边界通常比较健康

一个相对健康的服务边界，通常具备这些特征：

1. 业务职责比较单一清晰。
2. 数据主责清楚，谁维护主数据比较明确。
3. 大部分核心逻辑可以在服务内部闭环。
4. 对外提供的是能力，而不是零散表操作。
5. 和其他服务的交互关系相对稳定。

换句话说，好的服务边界应该更像“能力单元”，而不是“代码搬运单元”。

### 19.5 什么时候说明拆得太粗

典型信号：

1. 一个服务里塞了多个差异很大的业务域。
2. 同一个服务的不同模块发布频率完全不同。
3. 某个局部热点模块扩容时，被迫整个服务一起扩。
4. 一个服务出问题，会影响很多本不相关的功能。

这说明服务边界还不够收敛，拆分收益可能还没吃到。

### 19.6 什么时候说明拆得太细

典型信号：

1. 完成一个简单业务流程要串很多服务。
2. 服务之间频繁同步调用，网络往返非常密集。
3. 大量接口只是透传，没有形成独立能力。
4. 小改一个需求，要改很多服务并联调很久。
5. 分布式事务和跨服务一致性问题明显增多。

这说明不是系统更优雅了，而是把原本能在本地完成的协同拆成了分布式协同。

### 19.7 一个常见误区：按“最小可复用单元”无限细拆

很多人会直觉认为：

1. 越小越灵活。
2. 越小越可复用。

但工程上经常相反：

1. 粒度太小，可复用性不一定提升。
2. 反而会形成大量细碎依赖。
3. 每个服务都很小，但整体协作成本巨大。

所以“可复用”不能脱离业务上下文单独追求。

### 19.8 常见拆分策略

#### 19.8.1 方案 A：粗粒度服务

适合：

1. 业务刚完成单体到服务化过渡。
2. 团队治理能力还在建设中。
3. 希望优先降低拆分风险。

优点：

1. 服务数量少。
2. 链路短。
3. 治理和排障相对容易。

缺点：

1. 服务内仍可能存在局部耦合。
2. 独立扩缩容收益有限。

#### 19.8.2 方案 B：中等粒度、按领域能力拆分

这是通常最平衡的方案。

适合：

1. 领域边界较清晰。
2. 团队已有基础治理能力。
3. 希望在独立性和复杂度之间取得平衡。

优点：

1. 边界比较稳定。
2. 服务数量可控。
3. 更适合长期演进。

缺点：

1. 仍然需要认真处理边界争议和公共能力沉淀。

#### 19.8.3 方案 C：细粒度服务

适合：

1. 平台化程度高。
2. 团队规模大。
3. 治理体系成熟。
4. 确实存在明显独立演进诉求。

优点：

1. 独立性最强。
2. 更容易按能力平台化。

缺点：

1. 调用链和治理成本最高。
2. 最容易出现“为了拆而拆”。

### 19.9 推荐判断顺序

1. 先看业务能力边界是否稳定。
2. 再看协作是否真的被当前边界卡住。
3. 再看是否有独立扩缩容和故障隔离诉求。
4. 最后看团队治理能力能承受到什么粒度。

### 19.10 一句话结论

微服务拆分粒度通常以“领域能力闭环 + 边界稳定 + 服务数量可控”为宜；拆得过粗吃不到收益，拆得过细又会把本地复杂度升级成分布式复杂度。

## 20. 高频题：什么时候该引入 Outbox

### 20.1 题目定义

这道题本质上是在判断：

1. 业务数据变更和消息发送之间，是否已经存在明显的不一致风险。
2. 是否值得用额外的本地存储和异步投递机制，换取“本地事务提交后消息最终一定能发出”的保障。

所以 Outbox 不是为了“架构更好看”，而是为了处理一个很具体的问题：

> 本地事务成功了，但消息没发出去；或者消息发出去了，但本地事务没成功。

### 20.2 先明确：Outbox 主要解决什么问题

在“数据库更新 + 发 MQ 消息”这类场景里，天然会遇到两个经典问题：

1. 先写数据库，再发消息。
   数据库成功，消息发送失败。
2. 先发消息，再写数据库。
   消息出去后，本地事务失败。

如果这两个问题一旦发生会导致后续系统状态不一致，Outbox 就开始有价值了。

### 20.3 什么时候值得认真考虑 Outbox

#### 20.3.1 数据变更之后必须驱动下游动作

例如：

1. 订单创建后必须通知库存、积分、通知系统。
2. 支付成功后必须驱动履约、发票、对账。
3. 医疗主链路状态变更后必须异步沉淀审计、索引、画像。

如果这些下游动作不是可有可无，而是业务闭环的一部分，那消息可靠性就很重要。

#### 20.3.2 不能接受“本地成功但下游完全不知道”

这是 Outbox 最典型的适用前提。

如果业务上能接受：

1. 偶发漏消息后人工补。
2. 或者下游没收到也没关系。

那就不一定非要引入 Outbox。

但如果不能接受“主库状态已经变了，下游完全没跟上”，Outbox 会更合适。

#### 20.3.3 有较多跨系统异步联动

当一个核心事件需要被多个系统消费时，消息就不再只是“顺手发一下”，而会变成核心集成链路。

这时靠业务代码里临时 `try-catch` 发消息，风险通常不够可控。

### 20.4 什么时候不急着上 Outbox

以下情况通常不需要一开始就上 Outbox：

1. 这个消息只是通知性质，丢了影响很小。
2. 下游动作本身非核心，可通过定时补偿轻松兜底。
3. 业务仍然很早期，链路简单，可靠性要求没到这个程度。
4. 当前主要问题不是消息可靠性，而是根本不该异步化。

Outbox 是可靠性增强手段，不是所有 MQ 场景的默认标配。

### 20.5 Outbox 带来的收益

1. 业务数据和待发消息可以一起进入本地事务。
2. 本地事务成功后，消息至少不会“凭空丢失”。
3. 可以通过后台投递、重试、补偿把消息最终发出。
4. 整个消息状态更可观测、可审计。

### 20.6 Outbox 带来的代价

1. 多了一张 Outbox 表或类似存储。
2. 需要异步扫描、投递、重试机制。
3. 要处理重复投递和消费幂等。
4. 表膨胀、清理、补偿、监控都要治理。

所以 Outbox 不是“无脑更优”，而是“更稳但更重”。

### 20.7 常见方案对比

#### 20.7.1 方案 A：本地事务后直接发消息

适合：

1. 对可靠性要求一般。
2. 偶发漏消息可接受。
3. 链路简单。

优点：

1. 实现最简单。
2. 开发成本低。

缺点：

1. 本地成功但消息失败的窗口真实存在。

#### 20.7.2 方案 B：本地事务 + Outbox + 异步投递

适合：

1. 业务核心事件不能轻易漏发。
2. 下游联动比较重要。
3. 能接受最终一致性，但不能接受完全丢消息。

优点：

1. 工程上比较稳妥。
2. 可靠性和可观测性都更好。

缺点：

1. 链路更长。
2. 治理成本更高。

#### 20.7.3 方案 C：更重的事务一体化方案

适合：

1. 强一致要求更高。
2. 团队愿意承担更重的中间件或事务方案成本。

优点：

1. 一致性语义更强。

缺点：

1. 成本通常高于 Outbox。
2. 不一定适合高吞吐链路。

### 20.8 推荐判断顺序

1. 这个消息丢了，业务后果到底有多大。
2. 下游动作是不是核心闭环的一部分。
3. 能不能接受最终一致，但不能接受完全漏发。
4. 是否已经具备重试、幂等、补偿治理能力。

### 20.9 一句话结论

当“本地数据变更成功后，下游事件绝不能轻易漏发”时，Outbox 就值得考虑；如果消息只是弱通知或业务仍很轻，直接发消息往往更简单。

## 21. 高频题：热点数据 / 热点 Key 怎么处理

### 21.1 题目定义

这道题本质上是在判断：

1. 高并发是否集中打在极少数数据上。
2. 是读热点、写热点，还是读写同时热点。
3. 应该优先做缓存、隔离、削峰、拆分，还是改业务路径。

所以热点治理不是一个单点技巧，而是：

> 识别热点类型，然后用不同手段把“集中打爆一个点”的风险拆开。

### 21.2 先区分三类热点

#### 21.2.1 读热点

特征：

1. 大量请求都在读取同一份数据。
2. 数据更新不频繁。
3. 瓶颈更多在读取放大。

典型例子：

1. 热门商品详情。
2. 活动配置。
3. 热门医生主页。

#### 21.2.2 写热点

特征：

1. 大量请求都在修改同一条或同一小批数据。
2. 冲突和锁竞争明显。
3. 瓶颈更多在串行化更新。

典型例子：

1. 秒杀库存扣减。
2. 热门号源剩余量。
3. 单账户余额或单资源配额变更。

#### 21.2.3 读写同时热点

特征：

1. 同一份数据既被高频读，又被高频写。
2. 缓存一致性和数据库压力同时变大。

这种情况通常最难治理。

### 21.3 先明确：热点问题往往不是“某个中间件扛不住”，而是访问模式有问题

也就是说，不要一上来就问：

1. Redis 怎么扛。
2. 数据库怎么扛。

而要先问：

1. 为什么这么多请求都集中到同一个点。
2. 这个热点能不能被打散、预计算、异步化、前移或降级。

很多热点治理的关键，不在“抗”，而在“拆”。

### 21.4 读热点怎么处理

常见思路：

1. Redis 缓存前置。
2. 本地缓存或两级缓存。
3. 热点数据预热。
4. 热 key 副本或多副本分担。
5. 查询结果降级或静态化。

适合前提：

1. 数据相对稳定。
2. 可接受短暂不一致。
3. 命中率足够高。

### 21.5 写热点怎么处理

常见思路：

1. 串行化处理。
2. MQ 削峰。
3. 乐观锁 / 悲观锁控制冲突。
4. 资源预扣或令牌化设计。
5. 将强竞争动作从主链路前移或收口。

这类场景重点不是“让大家同时写得更快”，而是“减少无效竞争和冲突放大”。

### 21.6 读写同时热点怎么处理

这类场景往往要组合治理：

1. 读侧缓存。
2. 写侧削峰或串行化。
3. 状态分层。
4. 主链路和展示链路分离。
5. 必要时做降级和限流。

比如库存场景，展示库存和最终扣减库存就不一定要完全走同一条高实时路径。

### 21.7 什么时候优先做“业务降压”而不是“技术硬扛”

这是很重要的思路。

如果热点已经明显超过系统正常承载，通常更优先考虑：

1. 限流。
2. 排队。
3. 预约。
4. 令牌发放。
5. 页面静态化或结果延迟刷新。

因为有些热点问题本质上是业务流量模型问题，不是单纯的技术参数问题。

### 21.8 常见方案对比

#### 21.8.1 方案 A：直接扩容硬扛

适合：

1. 热点不集中。
2. 只是整体流量增长。

优点：

1. 最直接。

缺点：

1. 对真正单点热点效果有限。
2. 成本高。

#### 21.8.2 方案 B：缓存 / 削峰 / 串行化的局部治理

适合：

1. 热点集中但类型清晰。
2. 可以识别具体热点点位。

优点：

1. 针对性强。
2. 成本更可控。

缺点：

1. 需要先把热点定位清楚。

#### 21.8.3 方案 C：业务规则重构

适合：

1. 热点是长期稳定存在的核心问题。
2. 单靠中间件优化已经收益有限。

优点：

1. 能从根上改变访问模式。

缺点：

1. 改造成本最高。
2. 可能涉及产品规则调整。

### 21.9 热点治理时的常见误区

1. 把所有热点都当成缓存问题。
2. 只会加机器，不改访问模型。
3. 没区分读热点和写热点。
4. 只看平均 QPS，不看单点命中集中度。
5. 忽略热点失效瞬间的回源风险。

### 21.10 推荐判断顺序

1. 先确认是读热点、写热点还是混合热点。
2. 再确认热点能不能打散、预热、削峰或前移。
3. 再选择缓存、锁、队列、限流、降级等具体手段。
4. 最后再决定是否需要业务规则改造。

### 21.11 一句话结论

热点治理的关键不是单纯“把机器堆上去”，而是先识别热点类型，再用缓存、削峰、串行化、限流或业务规则重构把集中压力拆散。

## 22. 高频题：什么时候该做读写分离

### 22.1 题目定义

这道题本质上不是“数据库压力大就上读写分离”，而是在判断：

1. 当前数据库压力是否主要来自读。
2. 是否值得用复制延迟、路由复杂度和一致性成本，换取更高的读取扩展能力。

所以关键不是“会不会配主从”，而是“当前瓶颈是否真的适合用读写分离解决”。

### 22.2 先明确：读写分离主要解决什么问题

它主要解决的是：

1. 读请求远多于写请求。
2. 主库读压力过高。
3. 希望把查询流量分摊到从库。

它不直接解决的问题包括：

1. 写入瓶颈。
2. 单表设计差。
3. 慢 SQL。
4. 不合理索引。

也就是说，读写分离不是数据库性能的万能药，它更像是“读扩展手段”。

### 22.3 什么时候值得认真考虑读写分离

#### 22.3.1 读远大于写

典型场景：

1. 商品详情。
2. 内容列表。
3. 配置查询。
4. 历史记录浏览。

当绝大多数请求都在读，而写入量相对稳定时，读写分离的收益会比较明显。

#### 22.3.2 主库读压力已经影响整体稳定性

典型信号：

1. 主库 CPU 持续偏高。
2. 连接数和查询 RT 在高峰时明显上升。
3. 写请求也开始被大量读请求拖慢。

这种时候，把一部分只读查询移出去，通常会直接改善主库稳定性。

#### 22.3.3 读取对一致性要求不是“刚写完立刻必须读到”

如果业务能接受短时间主从延迟，比如：

1. 列表页稍晚几百毫秒看到新数据。
2. 某些统计页晚一点更新。

那读写分离比较适合。

### 22.4 什么时候不急着做读写分离

以下情况通常不应该优先上读写分离：

1. 真正瓶颈是慢 SQL。
2. 写压力才是主矛盾。
3. 业务存在大量“写后立刻读”的强一致场景。
4. 数据规模还不大，主库远没到瓶颈。
5. 团队还没有处理主从延迟、读路由、故障切换的经验。

很多时候问题不在“读太多”，而在“读得很差”。

### 22.5 读写分离带来的收益

1. 主库读压力下降。
2. 读取能力更容易横向扩展。
3. 读写资源可以相对隔离。

### 22.6 读写分离带来的代价

1. 主从延迟带来短暂不一致。
2. 读路由策略变复杂。
3. 故障切换和一致性排障更复杂。
4. 某些事务内查询不能随便走从库。

所以它不是“零成本扩容”，而是“用一致性和复杂度换读能力”。

### 22.7 常见演进路径

#### 22.7.1 方案 A：单库直读直写

适合：

1. 规模尚可控。
2. 一致性要求高。
3. 读压力还没成为主矛盾。

优点：

1. 最简单。
2. 一致性语义最直接。

缺点：

1. 所有读压力都集中在主库。

#### 22.7.2 方案 B：局部查询走从库

适合：

1. 只有部分接口是明显读热点。
2. 想先小步验证读写分离收益。

优点：

1. 风险更低。
2. 便于逐步验证主从延迟影响。

缺点：

1. 路由管理需要更精细。

#### 22.7.3 方案 C：系统性读写分离

适合：

1. 读多写少长期成立。
2. 主库读压力持续偏大。
3. 团队能稳定治理复制和路由问题。

优点：

1. 读扩展收益最大。

缺点：

1. 一致性边界和故障边界最复杂。

### 22.8 推荐判断顺序

1. 当前主要瓶颈是读还是写。
2. 是否已经做过 SQL、索引、缓存优化。
3. 业务是否能接受主从延迟。
4. 哪些查询可以安全走从库。
5. 团队是否能处理路由和故障切换复杂度。

### 22.9 一句话结论

只有当数据库压力主要来自读、缓存和基础优化已不足以解决问题、业务又能接受短暂主从延迟时，读写分离才真正值得做。

## 23. 高频题：什么时候要做灰度发布 / 蓝绿发布

### 23.1 题目定义

这道题本质上是在判断：

1. 发布风险是否已经高到不能再靠“一把梭上线”。
2. 应该优先选择逐步放量验证，还是优先选择整套环境快速切换。

也就是说，这题真正比较的是：

> 用更复杂的发布流程，换更低的变更风险和更强的回滚能力。

### 23.2 先明确两种方式主要解决什么问题

#### 23.2.1 灰度发布

核心思路：

1. 先让少量流量进入新版本。
2. 观察指标、日志、错误率、业务结果。
3. 再逐步扩大比例。

它更擅长解决：

1. 新版本行为不确定。
2. 希望逐步验证线上效果。
3. 想控制影响范围。

#### 23.2.2 蓝绿发布

核心思路：

1. 保留两套完整环境。
2. 新版本先在“绿”环境准备好。
3. 切流时整体从“蓝”切到“绿”。

它更擅长解决：

1. 切换和回滚要足够快。
2. 希望减少原地升级风险。
3. 基础设施和环境差异要尽量可控。

### 23.3 什么时候优先考虑灰度发布

灰度更适合：

1. 业务逻辑变化大，线上行为需要观察。
2. 需要验证新功能对真实流量的影响。
3. 风险主要在“代码行为未知”，而不是“环境切换复杂”。
4. 希望按用户、按租户、按流量比例逐步放量。

典型例子：

1. 推荐算法改版。
2. AI 路由策略变更。
3. 新支付流程、小流量新链路验证。

### 23.4 什么时候优先考虑蓝绿发布

蓝绿更适合：

1. 系统对停机和回滚速度非常敏感。
2. 发布主要风险在环境切换或部署过程本身。
3. 需要尽量避免原地覆盖式升级。

典型例子：

1. 核心网关。
2. 高可用 API 集群。
3. 对回滚窗口要求极短的核心服务。

### 23.5 什么时候不需要把发布策略做得太重

以下情况通常不需要一开始就上复杂发布体系：

1. 业务仍然早期，变更范围小。
2. 发布频率不高，影响面有限。
3. 当前主要问题不是发布风险，而是测试和观测体系还不完善。

如果没有足够观测能力，灰度和蓝绿都可能流于形式。

### 23.6 灰度发布的代价

1. 流量分配逻辑更复杂。
2. 新旧版本并存时要考虑兼容性。
3. 数据模型变更时要谨慎处理双版本共存问题。

### 23.7 蓝绿发布的代价

1. 资源成本更高。
2. 两套环境保持一致并不容易。
3. 数据库等共享资源仍然可能成为难点。

### 23.8 一个实用判断方式

如果你最担心的是：

1. 新代码线上效果未知。
   优先灰度。
2. 切换和回滚必须足够快。
   优先蓝绿。
3. 两者都担心。
   可能需要灰度 + 蓝绿组合。

### 23.9 常见误区

1. 灰度发布等于测试环境不足。
2. 蓝绿发布等于零风险。
3. 只关注流量切换，不关注指标观察和回滚预案。

### 23.10 一句话结论

当主要风险是“新版本行为未知”时，优先灰度发布；当主要风险是“切换和回滚必须极快”时，优先蓝绿发布；前提都是你有足够的观测和回滚能力支撑。

## 24. 高频题：幂等到底该在哪一层做

### 24.1 题目定义

这道题本质上不是“做不做幂等”，而是在判断：

1. 重复请求最可能从哪里出现。
2. 哪一层最有信息、最有能力、最经济地消化重复。

也就是说，这题真正要回答的是：

> 幂等不是单点技巧，而是一种分层治理能力；关键不是“有没有做”，而是“放在哪一层最合适”。

### 24.2 先明确：重复是怎么来的

常见来源包括：

1. 用户重复点击。
2. 前端重试。
3. 网关重试。
4. 服务超时后的调用方重试。
5. MQ 重投递。
6. 补偿任务重复执行。

不同来源，最合适的幂等落点通常不同。

### 24.3 为什么不能只在一层做

因为不同层解决的是不同问题：

1. 接口层更适合拦重复请求。
2. 业务层更适合保证语义唯一。
3. 存储层更适合用唯一约束兜底。
4. 消费层更适合处理消息重复投递。

所以幂等通常不是“选一层”，而是“主落点 + 兜底层”。

### 24.4 接口层幂等适合什么场景

接口层更适合：

1. 防止用户短时间重复提交。
2. 防止网络抖动导致同一请求重复进入。
3. 给调用方提供明确的重复请求语义。

常见做法：

1. 幂等 token。
2. 请求唯一流水号。
3. 去重键 + 过期时间。

优点：

1. 能较早拦截无效重复。
2. 降低后端压力。

缺点：

1. 只能处理“你看得见的重复请求”。
2. 不能替代业务语义层面的幂等。

### 24.5 业务层幂等适合什么场景

业务层是最关键的一层，因为它最懂“什么叫重复”。

适合：

1. 同一个订单只能创建一次。
2. 同一个支付回调只能生效一次。
3. 同一个状态流转不能重复推进。

常见做法：

1. 状态机约束。
2. 业务唯一键。
3. 幂等记录表。

优点：

1. 最贴近业务真实语义。
2. 最不容易被外围重试绕过去。

缺点：

1. 设计不好时容易和业务逻辑强耦合。

### 24.6 存储层幂等适合什么场景

存储层更适合做最后一道硬约束。

典型方式：

1. 唯一索引。
2. 去重表。
3. 条件更新。

适合：

1. 需要绝对兜底。
2. 重复写入后果严重。

优点：

1. 强约束。
2. 不容易被应用层绕过。

缺点：

1. 语义表达能力有限。
2. 只能兜底，不能替代上层治理。

### 24.7 消费层幂等适合什么场景

消息消费层必须假设消息可能重复。

适合：

1. MQ 至少一次投递语义。
2. 消费失败重试。
3. 补偿任务重复推进。

常见做法：

1. 消息唯一 ID 去重。
2. 消费记录表。
3. 业务状态判重。

### 24.8 一个实用判断原则

可以按这个思路落：

1. 接口层负责挡明显重复。
2. 业务层负责定义“什么才算重复”。
3. 存储层负责最终兜底。
4. 消费层负责消息重投递场景。

这比单纯问“到底在哪一层做幂等”更接近真实工程答案。

### 24.9 常见误区

1. 以为有防重 token 就等于幂等。
2. 以为唯一索引就能覆盖所有业务语义。
3. 以为消费层判重后，业务层就不用防重复。

### 24.10 一句话结论

幂等不应该只押在单一层上；通常是接口层早拦截、业务层定语义、存储层做兜底、消费层处理重复投递，其中业务层往往是最关键的主落点。

## 25. 高频题：什么时候该做接口聚合 / BFF

### 25.1 题目定义

这道题本质上不是“前端接口多就上 BFF”，而是在判断：

1. 前端页面或客户端的编排复杂度，是否已经高到不适合继续由前端直接拼装。
2. 是否值得用一层额外服务，换更稳定的接口形态和更可控的聚合逻辑。

也就是说，这题真正比较的是：

> 是让前端自己编排多个后端能力，还是在服务端增加一层面向终端的组装层。

### 25.2 先明确：接口聚合 / BFF 主要解决什么问题

它主要解决的是：

1. 一个页面或一个终端请求，需要依赖多个后端服务。
2. 前端为了一个页面要发很多请求，时延和复杂度都偏高。
3. 不同终端对同一业务能力的展示和裁剪需求不同。

它不主要解决的问题包括：

1. 核心领域边界混乱。
2. 后端服务本身设计不合理。
3. 不该由展示层承担的业务编排。

所以 BFF 更适合解决“终端适配和接口组织问题”，而不是替代领域服务设计。

### 25.3 什么时候值得认真考虑做 BFF

#### 25.3.1 前端需要聚合多个服务，且调用编排越来越重

典型场景：

1. 首页要同时拉用户信息、推荐数据、营销配置、活动状态。
2. 工作台页面要汇总多个系统的状态和待办。
3. 一个详情页要拼接主数据、标签、统计、权限、操作按钮状态。

如果这些编排都堆在前端，通常会让页面逻辑越来越重。

#### 25.3.2 不同终端对同一业务能力有明显差异化诉求

例如：

1. App、Web、管理后台需要的字段不同。
2. 同一业务流程在医生端、患者端、运营端展示完全不同。
3. 小程序更关注轻量返回，后台更关注完整上下文。

这种场景让终端直连领域服务，常常会导致接口越来越“折中”，谁都不满意。

#### 25.3.3 希望把前端频繁变化和后端领域服务隔离开

如果页面改版频繁、交互变化快，而领域服务希望保持稳定，那么增加一层 BFF 作为适配层会更合适。

### 25.4 什么时候不急着做 BFF

以下情况通常不应该为了“架构完整”就先做 BFF：

1. 页面很简单，调用链也很短。
2. 终端数量不多，接口差异不明显。
3. 当前问题不是接口组织，而是后端服务本身边界混乱。
4. 团队维护人力有限，再加一层只会增加调用链和排障复杂度。

很多时候没有必要为了“看起来像大厂架构”而强行加一层。

### 25.5 BFF 带来的收益

1. 前端调用更简单。
2. 页面级数据编排更集中。
3. 不同终端可以有更合适的返回结构。
4. 终端变化和领域服务可以适度解耦。

### 25.6 BFF 带来的代价

1. 调用链更长。
2. 增加一层部署和运维成本。
3. 如果边界拿捏不好，BFF 容易演变成“大杂烩中台”。
4. 容易把本该属于领域层的逻辑错误地下沉到展示聚合层。

### 25.7 常见演进路径

#### 25.7.1 方案 A：前端直连后端服务

适合：

1. 页面简单。
2. 接口依赖少。
3. 终端差异小。

优点：

1. 结构简单。
2. 调用链短。

缺点：

1. 页面复杂后，前端编排成本会迅速上升。

#### 25.7.2 方案 B：少量页面级聚合接口

适合：

1. 只有少数复杂页面需要聚合。
2. 想先局部引入适配层。

优点：

1. 风险低。
2. 收益集中。

缺点：

1. 容易逐步演化成零散聚合接口集合，需要后续整理边界。

#### 25.7.3 方案 C：明确职责的 BFF 层

适合：

1. 多终端并存。
2. 页面聚合需求长期稳定存在。
3. 团队能维护清晰的适配层边界。

优点：

1. 终端适配能力最强。
2. 更适合长期演进。

缺点：

1. 对边界治理要求高。

### 25.8 推荐判断顺序

1. 当前问题是前端编排复杂，还是领域服务本身设计问题。
2. 是否存在明显多服务聚合和多终端差异。
3. 页面变化是否快于领域服务变化。
4. 团队能否守住 BFF 只做适配和聚合，不做领域污染。

### 25.9 一句话结论

当页面级聚合复杂度、多终端差异和前后端解耦诉求都已经明显时，BFF 才真正有价值；否则前端直连或少量聚合接口往往更简单。

## 26. 高频题：什么时候该把同步链路改成任务化

### 26.1 题目定义

这道题本质上不是“异步一定更高级”，而是在判断：

1. 当前同步链路是否已经太长、太慢、太脆弱。
2. 是否值得把“立即完成”改成“先受理，再异步推进”，用更复杂的状态管理换更好的吞吐和稳定性。

也就是说，这题真正比较的是：

> 是坚持请求内闭环，还是把部分动作升级成有状态的任务流转。

### 26.2 先明确：任务化主要解决什么问题

任务化主要适合解决：

1. 单次处理耗时长。
2. 需要多阶段推进。
3. 依赖多个外部系统，失败概率高。
4. 当前请求不必在一个同步响应内拿到最终结果。

它不主要解决的问题包括：

1. 只是代码写得差。
2. 本来可以在几十毫秒内完成的普通同步调用。
3. 业务上必须立刻闭环的核心动作。

### 26.3 什么时候值得认真考虑任务化

#### 26.3.1 链路过长，超时和失败放大明显

典型信号：

1. 一个请求要串很多下游。
2. 任意一个下游慢一点，整体 RT 就明显抖动。
3. 用户请求线程长时间占用。

这说明同步闭环的成本已经越来越高。

#### 26.3.2 业务天然是多阶段推进

例如：

1. 审批流。
2. 导出大报表。
3. 复杂 AI 任务。
4. 多步履约或工单处理。

这类场景本来就不是“一个请求一次做完”最自然。

#### 26.3.3 用户只需要先知道“已受理”

如果用户更关心的是：

1. 系统已经接单。
2. 后续结果会异步通知。

那任务化就更容易成立。

### 26.4 什么时候不急着任务化

以下情况通常不应该过早任务化：

1. 本来就是核心同步交易动作。
2. 用户必须立即知道最终结果。
3. 当前耗时问题其实通过局部优化就能解决。
4. 团队还没有状态机、重试、补偿、任务观测能力。

任务化不是“性能优化快捷键”，它会把简单请求改造成有生命周期的系统对象。

### 26.5 任务化带来的收益

1. 主请求更短。
2. 更容易削峰和隔离慢任务。
3. 更适合失败重试和断点恢复。
4. 更适合多阶段编排和人工介入。

### 26.6 任务化带来的代价

1. 状态管理复杂度上升。
2. 用户体验从“同步结果”变成“异步感知”。
3. 需要任务表、状态机、补偿、超时治理。
4. 排障从单次请求变成任务生命周期排障。

### 26.7 常见演进路径

#### 26.7.1 方案 A：纯同步闭环

适合：

1. 链路短。
2. 处理快。
3. 用户必须立即知道结果。

优点：

1. 简单直接。
2. 状态最少。

缺点：

1. 长链路时稳定性差。

#### 26.7.2 方案 B：主流程同步，重动作任务化

适合：

1. 主动作要快速确认。
2. 后续重处理可以异步推进。

优点：

1. 平衡体验和稳定性。
2. 是最常见、最务实的演进方式。

缺点：

1. 需要明确同步边界和任务边界。

#### 26.7.3 方案 C：完整任务流转模型

适合：

1. 业务天然多阶段。
2. 需要审计、重试、人工介入、恢复执行。

优点：

1. 对复杂流程控制力最强。

缺点：

1. 系统复杂度最高。

### 26.8 推荐判断顺序

1. 这个动作是否必须请求内闭环。
2. 当前问题是偶发慢，还是同步模型本身已经不适配。
3. 用户能否接受“先受理，后完成”。
4. 团队能否承接任务状态和补偿治理复杂度。

### 26.9 一句话结论

当同步链路已经过长、过慢、易受下游波动影响，且业务允许“先受理后完成”时，把链路任务化通常更划算；否则同步闭环仍然更直接。

## 27. 高频题：一致性、可用性、成本三者冲突时怎么排优先级

### 27.1 题目定义

这道题本质上不是在找一个通用答案，而是在判断：

1. 当前业务里，什么损失最不能接受。
2. 哪个维度一旦牺牲，会直接伤到核心业务。

也就是说，这题真正想说明的是：

> 一致性、可用性、成本没有永远固定的绝对顺序，顺序取决于业务后果和系统阶段。

### 27.2 先明确：这不是纯技术排序题

很多时候不能简单回答：

1. 一致性永远第一。
2. 可用性永远第一。
3. 成本最后考虑。

更合理的思路是：

1. 先看业务底线。
2. 再看故障代价。
3. 再看当前阶段能承担多大成本。

### 27.3 什么场景下一致性优先级最高

通常是：

1. 资金。
2. 核心库存额度。
3. 法规和审计强约束数据。
4. 一旦错了，人工修复代价极高的核心状态。

这类场景里，可用性和成本都重要，但通常不能靠牺牲核心一致性来换。

### 27.4 什么场景下可用性优先级更高

通常是：

1. 用户入口链路。
2. 大促流量入口。
3. 搜索、浏览、咨询入口。
4. 允许稍后收敛的非核心状态同步。

这类场景如果因为追求强一致而频繁阻塞主入口，业务损失可能更大。

### 27.5 什么场景下成本约束会反过来主导选择

这不只是“省钱”，而是：

1. 当前业务阶段还不值得上重型治理。
2. 团队没有足够人力维护复杂方案。
3. 方案理论上更强，但长期维护成本过高。

例如早期业务阶段，很多问题并不是不能上更重方案，而是“不值得现在上”。

### 27.6 一个更实用的排序方法：先看“不可接受的后果”

可以按这个问题来排：

1. 如果不一致，会造成什么损失。
2. 如果不可用，会造成什么损失。
3. 如果成本太高，会压垮什么。

谁的后果最不可接受，谁的优先级就应该更高。

### 27.7 阶段性排序往往不同

#### 27.7.1 业务早期

通常更偏：

1. 可用性 / 交付速度。
2. 成本可控。
3. 足够的一致性。

因为这个阶段先活下来、先跑通闭环往往更重要。

#### 27.7.2 业务成熟期

通常更偏：

1. 核心一致性。
2. 稳定可用。
3. 治理成本可接受。

因为核心业务已经跑起来，错误代价会变高。

#### 27.7.3 强监管行业

通常更偏：

1. 核心一致性和审计可追溯。
2. 稳定可用。
3. 成本放到后面，但也不能无限失控。

### 27.8 常见误区

1. 把 CAP 结论机械套到所有工程问题里。
2. 以为一致性和可用性只能二选一，忽略分层设计。
3. 只讲原则，不讲业务代价。
4. 为了省成本，把关键链路做得过于脆弱。
5. 为了追求最强一致，把所有链路都做得又重又慢。

### 27.9 一个实用回答框架

遇到这类题时，可以先说：

1. 先按业务链路分层，不会全系统统一排序。
2. 核心资源链路优先保一致性。
3. 用户入口链路优先保可用性。
4. 成本决定方案能不能长期持续，而不是最后完全不考虑。

### 27.10 一句话结论

一致性、可用性、成本的优先级不是固定的，关键是先看业务底线和错误后果；核心资源链路通常先保一致性，用户入口链路通常先保可用性，而成本决定方案能不能长期成立。

## 28. 项目映射：智能体重管理项目

### 28.1 为什么这一步很重要

前面的内容解决的是“知道怎么判断”。

这一部分要解决的是：

1. 怎么把判断落到自己的项目里。
2. 怎么避免回答成纯理论。
3. 怎么让技术取舍和业务背景、系统演进、个人价值连起来。

也就是说，真正有说服力的表达不是：

1. 我知道微服务优缺点。
2. 我知道 MQ、缓存、TCC、限流怎么选。

而是：

1. 在我的项目里，为什么当时要这么选。
2. 为什么不是另一个方案。
3. 这个判断背后的业务代价和工程代价是什么。

### 28.2 这个项目最适合承载哪些取舍题

你的智能体重管理项目，天然适合映射这些题：

1. 为什么要把普通对话链路和 Agent 链路拆开。
2. 为什么有些链路保持同步，有些链路异步化。
3. 为什么画像、记忆、审计、索引等能力要异步沉淀。
4. 为什么某些数据要缓存，某些不能只靠缓存。
5. 为什么要优先保证患者主链路可用，而不是让所有增强能力都强同步。
6. 为什么 AI 场景里更容易引入“任务化”而不是一把同步做完。

### 28.3 可直接映射的几个核心判断

#### 28.3.1 普通对话链路 vs Agent 链路为什么拆开

可以映射到：

1. 微服务拆分边界。
2. 同步链路与任务化链路的权衡。
3. 可用性与复杂度的平衡。

可重点讲：

1. 普通对话更关注高并发、低时延、成本和可降级。
2. Agent 链路更关注多步推理、工具调用、风险审批、恢复执行和审计。
3. 如果不拆，轻链路会被重逻辑拖慢，系统平均 RT 和复杂度都会明显上升。

本质上是在说明：

1. 不是为了“微服务而微服务”。
2. 而是因为两类链路的目标函数完全不同。

#### 28.3.2 为什么不是所有请求都直接进 Agent

可以映射到：

1. 同步调用 vs 异步升级。
2. 限流、熔断、降级思路。
3. 成本与体验的平衡。

可重点讲：

1. 不是所有请求都值得走重链路。
2. 先做粗判和短路，是为了把寒暄、事实问答、画像补全这类轻请求挡在轻链路。
3. 重链路只在确实有任务升级价值时才放行。

这能说明你不是在堆能力，而是在做入口分层。

#### 28.3.3 为什么画像、记忆、审计、索引更多做异步沉淀

可以映射到：

1. 同步调用 vs MQ / 异步解耦。
2. 什么时候该把同步链路改成任务化。
3. 一致性、可用性、成本怎么平衡。

可重点讲：

1. 主链路最重要的是本轮响应时延和连续性。
2. 长期资产沉淀虽然重要，但不值得阻塞用户当前响应。
3. 同步做完会让每轮对话都背上向量写入、索引更新、抽取加工的成本。

这会比纯理论答案更像真实工程判断。

#### 28.3.4 为什么画像不是每轮都强制拉

可以映射到：

1. 缓存 / 远程读取 / 性能优化取舍。
2. 主链路低时延诉求。
3. “不是所有信息都值得每次强一致获取”。

可重点讲：

1. visitor、casual chat、fact query 这类请求，拉画像的收益不大。
2. 如果所有请求都强制画像 RPC，会无意义抬高轻链路 RT。
3. 应该让高价值请求承担更高成本，而不是一刀切。

这体现的是“按请求价值分配系统成本”的能力。

#### 28.3.5 为什么需要患者可见回复和结构化结果分离

可以映射到：

1. BFF / 适配层思路。
2. 面向不同消费方的数据组织方式。
3. 终端适配与内部结构解耦。

可重点讲：

1. 患者视图、医生视图、系统治理视图关注的信息不同。
2. 如果只追求一个统一输出，就会互相污染。
3. 所以要把 patientSafeReply、structuredResult、doctorWorkbenchPayload 分开沉淀。

这能体现你对“不同消费方，不同接口语义”的理解。

### 28.4 这个项目里最适合讲的几个“优先级判断”

#### 28.4.1 为什么优先保患者主链路可用

可以映射到“一致性、可用性、成本怎么排优先级”：

1. 患者入口是直接用户体验链路。
2. Agent、记忆、审计、索引这些能力虽然重要，但不能轻易反向拖死主入口。
3. 所以主链路优先保可用，增强链路允许降级、回退或异步化。

#### 28.4.2 为什么风险高的动作要放到更可控的链路里

可以映射到：

1. 限流、熔断、降级。
2. 任务化与状态化控制。
3. 强一致 / 强可控优先级更高的子链路设计。

可重点讲：

1. 医疗场景最危险的不是回复慢，而是错执行。
2. 所以涉及工具调用、风险分级、人工审批恢复执行的链路，宁可更重，也要更可控。

这很能体现“按风险分层设计”，而不只是追求性能。

### 28.5 这个项目里可以怎么讲“为什么不是另一个方案”

这一点很关键，面试官往往更在意“为什么不是另一个方案”。

#### 28.5.1 为什么不是所有东西都同步强一致

可以说：

1. AI 主链路对时延很敏感。
2. 很多增强能力属于“重要但不必请求内闭环”的长期资产沉淀。
3. 如果都做成同步强一致，系统体验和吞吐都会明显变差。

#### 28.5.2 为什么不是一个大一统 AI 服务把所有事都做完

可以说：

1. 普通对话和任务型 Agent 目标函数不同。
2. 轻重链路混在一起会互相拖累。
3. 风险控制、工具调用、审批恢复不应该成为所有请求的通用负担。

#### 28.5.3 为什么不是把所有能力都塞进前端工作流

可以说：

1. 业务规则、风控和审计必须在服务端可控。
2. 前端适合展示和轻编排，不适合承担核心治理逻辑。
3. 终端差异和领域能力要适度解耦。

### 28.6 一句话总结这个项目最适合传递的技术判断形象

这个项目最适合传递出来的，不是“我会很多 AI 名词”，而是：

1. 我会按链路价值、风险等级、时延诉求、可审计要求去分层设计系统。
2. 我知道什么时候该同步，什么时候该异步，什么时候该升级成状态化任务链路。
3. 我知道怎么在用户体验、系统可用性和治理复杂度之间做现实取舍。

## 29. 项目映射：互联网医院 / 问诊 / 预约场景

### 29.1 这类项目最容易承载哪些取舍题

互联网医院、问诊、预约、排班、支付这类项目，很适合承载下面这些题：

1. 单体什么时候拆微服务。
2. 同步调用 vs MQ 异步解耦。
3. XA / AT / TCC / 可靠消息最终一致性。
4. 乐观锁 / 悲观锁 / 分布式锁。
5. 限流、熔断、降级。
6. 热点数据治理。

因为这些项目天然同时包含：

1. 强交易属性。
2. 强入口属性。
3. 强并发时段。
4. 强一致和高可用冲突。

### 29.2 哪些业务动作天然适合同步闭环

例如：

1. 预约时段校验。
2. 支付结果确认。
3. 核心库存 / 号源扣减。

这类动作可重点讲：

1. 用户必须立即知道结果。
2. 如果不当场确认，后续体验和纠纷成本都高。
3. 所以主动作要尽量同步闭环，但要控制同步链路长度。

### 29.3 哪些动作更适合异步解耦

例如：

1. 短信通知。
2. 站内消息。
3. 审计日志。
4. 搜索索引更新。
5. 部分统计和报表沉淀。

这种场景正好适合映射“主流程同步、附属流程异步”的判断。

### 29.4 哪些地方最适合讲分布式事务取舍

最典型的是：

1. 预约单创建。
2. 号源占用。
3. 支付状态更新。
4. 退款回退。

这里可以这样映射：

1. 如果是核心号源、支付、订单状态这类资源链路，需要先看是否能单库闭环。
2. 如果不能，再看是否允许最终一致。
3. 如果允许，优先可靠消息 + 补偿。
4. 只有当资源预占和实时闭环要求特别强时，才考虑更重的 TCC 思路。

### 29.5 哪些地方最适合讲锁和热点

最典型的是：

1. 热门医生号源。
2. 热门时段抢号。
3. 退款或重复支付回调。

可重点讲：

1. 高冲突库存类资源，悲观锁或更强串行化更自然。
2. 重复回调、重复创建，更像幂等和唯一约束问题。
3. 跨实例互斥只有在数据库约束覆盖不了时，才考虑分布式锁。

### 29.6 哪些地方最适合讲限流、熔断、降级

例如：

1. 挂号入口限流。
2. 外部支付或短信接口异常时熔断。
3. 高峰期关闭非核心推荐、营销、画像增强能力做降级。

这类表达很容易体现“不同稳定性手段解决的是不同问题”。

### 29.7 一句话总结这类项目最适合传递的技术判断形象

这类项目最适合传递出来的形象是：

1. 我能处理强交易链路中的一致性问题。
2. 我知道入口链路和核心资源链路的优先级不一样。
3. 我能在高峰流量、资源竞争和用户体验之间做工程取舍。

## 30. 追问预案：常见取舍题的反问点和扩展追问

### 30.1 为什么要准备这一部分

很多时候，第一轮回答只是开始。

真正拉开差距的是：

1. 面试官追问时，你还能不能继续展开。
2. 你有没有提前想到对方会追哪里。

所以这一部分不是知识点，而是“追问预案”。

### 30.2 单体 vs 微服务常见追问

常见追问：

1. 为什么不是先模块化单体，而是直接拆？
2. 你们当时是按什么边界拆的？
3. 拆完后最大的副作用是什么？
4. 有没有拆得过细或过粗的问题？

回答重点：

1. 不要只讲收益，要主动讲副作用。
2. 要说明当时的组织协作、发布、扩容、故障隔离诉求。

### 30.3 同步 vs MQ 常见追问

常见追问：

1. 为什么这个动作不能同步做完？
2. 异步后如果消息丢了怎么办？
3. 为什么不是先重试而是上 MQ？

回答重点：

1. 先说主链路目标。
2. 再说异步是否允许。
3. 最后补消息可靠性、幂等、补偿。

### 30.4 分布式事务常见追问

常见追问：

1. 为什么不用 TCC？
2. 为什么不用强一致？
3. 最终一致性怎么兜底？

回答重点：

1. 要主动讲成本。
2. 要主动讲业务是否能接受短暂不一致。
3. 要主动讲补偿、对账、幂等。

### 30.5 缓存常见追问

常见追问：

1. 为什么不直接查数据库？
2. 缓存不一致怎么办？
3. 本地缓存和 Redis 为什么这么选？

回答重点：

1. 先说读压力和时延目标。
2. 再说一致性接受边界。
3. 最后说治理成本。

### 30.6 锁和幂等常见追问

常见追问：

1. 这是不是分布式锁问题？
2. 为什么不是唯一索引就够？
3. 幂等到底放在哪一层？

回答重点：

1. 先区分问题类型。
2. 明确是互斥、幂等、状态约束，还是事务一致性。

### 30.7 稳定性治理常见追问

常见追问：

1. 为什么这里优先限流，不是熔断？
2. 降级后用户体验怎么保证？
3. 灰度发布的收益怎么验证？

回答重点：

1. 不要把限流、熔断、降级混成一件事。
2. 要明确当前主风险是什么。

### 30.8 一个统一的追问应对结构

后面遇到追问时，尽量按这个顺序收口：

1. 先澄清问题本质。
2. 再给出当时的业务约束。
3. 再比较另一个方案为什么没选。
4. 最后补代价和边界。

这会让你的回答显得非常稳。

## 31. 速答版：高频取舍题

### 31.1 这一部分怎么用

前面的章节更适合系统化理解和展开。

这一部分的目标是：

1. 把长分析压缩成可直接说出口的短版。
2. 面试时先快速作答，再根据追问展开。

使用方式建议是：

1. 先用这里的 3 到 6 句起手。
2. 对方追问时，再回到前面的完整框架展开。

### 31.2 单体什么时候拆微服务

我一般不会把“要不要拆微服务”看成技术升级，而是看当前主要矛盾是不是已经从功能实现，变成了模块耦合、团队协作、独立扩缩容和故障隔离问题。如果业务边界还不稳定、团队也不大，单体通常反而成本最低。只有当模块边界已经清晰，发布互相影响明显，不同模块资源模型差异大时，拆微服务才真正有收益。

### 31.3 同步调用 vs MQ 异步解耦

我会先看这个动作是不是必须在当前请求里闭环。如果用户必须立刻拿到结果，比如支付确认、库存校验，那优先同步；如果只是后续通知、索引更新、审计沉淀这类动作，可以异步解耦。MQ 的本质是用消息可靠性治理复杂度，去换系统解耦、削峰和更好的主链路可用性。

### 31.4 XA / AT / TCC / 可靠消息最终一致性怎么选

我会先看能不能不做分布式事务，尽量通过单库闭环解决；如果不能，再看业务能不能接受最终一致性。能接受的话，我通常优先可靠消息 + 补偿，因为吞吐和工程可持续性更好；数据库更新型中等复杂场景可以考虑 AT；关键资源预占、强一致要求高、业务又能清晰拆 Try / Confirm / Cancel 时，才考虑 TCC；XA 一般只适合少数必须强一致且能接受高成本的场景。

### 31.5 Redis 缓存什么时候值得引入

我不会一上来就上 Redis，而是先看数据库读压力是不是已经明显、有没有热点数据、以及主链路是否对时延敏感。如果基础 SQL 和索引优化还没做完，先上缓存通常只是把问题藏起来。只有当读压力、热点访问和低延迟诉求都已经明显，而且数据又适合缓存时，引入 Redis 才真正划算。

### 31.6 本地缓存 vs Redis

本地缓存适合几乎只读、更新极少、对极致低延迟敏感的数据，因为它最快，但多实例一致性差。Redis 更适合分布式共享状态和统一治理，因为多节点共享更自然。只有在热点非常高、又能接受更高治理复杂度时，我才会考虑本地缓存加 Redis 的两级缓存。

### 31.7 分库分表什么时候做

我会先确认当前瓶颈到底是单表、单库，还是 SQL / 索引本身。如果归档、缓存、读写分离这些轻量优化还没到头，就不应该急着分库分表。只有当单库单表已经真实逼近容量或写入瓶颈，而且业务又有稳定分片键时，分库分表才值得做。

### 31.8 Elasticsearch 什么时候引入

我会先看这是“普通查询问题”还是“搜索问题”。如果已经需要全文检索、多条件筛选、相关性排序和搜索体验优化，数据库继续硬撑的成本会越来越高，这时 ES 才有价值。它不是数据库替代品，而是用数据同步和索引治理复杂度，换更强的检索能力。

### 31.9 乐观锁 vs 悲观锁 vs 分布式锁

我会先区分这是数据库并发更新问题，还是跨实例互斥问题。冲突低、可重试，我优先乐观锁；冲突高、事务范围在数据库里，我优先悲观锁；只有当问题跨实例、数据库约束和幂等都覆盖不了时，才考虑分布式锁，因为它的治理成本最高。

### 31.10 限流、熔断、降级什么时候优先做

我会先看当前主风险是什么。流量洪峰先做限流，因为入口不控流，后面都只是延缓崩溃；下游不稳先做熔断，避免坏依赖拖死自己；资源不够但必须保核心链路时，就优先降级。三者不是替代关系，而是解决不同层次的问题。

### 31.11 微服务拆分粒度怎么定

我不会追求拆得越细越好，而是看服务边界是不是按领域能力闭环、边界是不是稳定、服务数量是不是可控。拆得太粗，吃不到独立性收益；拆得太细，就会把本地复杂度升级成分布式复杂度。通常中等粒度、按领域能力拆分是最平衡的。

### 31.12 什么时候该引入 Outbox

当业务数据变更成功后，下游事件不能轻易漏发时，Outbox 就开始有价值。它本质上是在解决“本地事务成功了，但消息没发出去”的问题。对弱通知场景没必要一开始就上，但对核心异步联动链路，Outbox 往往比简单 try-catch 发消息更稳。

### 31.13 热点数据 / 热点 Key 怎么处理

我会先分清楚是读热点、写热点，还是读写混合热点。读热点优先考虑缓存、预热、多副本；写热点更关注串行化、削峰、锁冲突控制；混合热点通常要把展示链路和最终写链路拆开。热点治理的关键不是堆机器，而是先识别热点类型，再把集中压力拆散。

### 31.14 什么时候该做读写分离

只有当数据库压力主要来自读、业务又能接受短暂主从延迟时，读写分离才值得做。它解决的是读扩展，不解决写瓶颈、慢 SQL 和差表结构问题。如果真正问题还在基础优化层，就不应该急着上读写分离。

### 31.15 什么时候要做灰度发布 / 蓝绿发布

如果我主要担心的是新版本行为未知，就优先灰度发布，用小流量逐步验证；如果我主要担心的是切换和回滚必须足够快，就优先蓝绿发布。两者都不是为了显得流程高级，而是用更复杂的发布方式换更低的变更风险。

### 31.16 幂等到底该在哪一层做

幂等我通常不会只押在一层。接口层更适合拦明显重复，业务层最适合定义“什么才算重复”，存储层做最终兜底，消费层处理消息重投递。真正最关键的主落点，通常还是业务层。

### 31.17 什么时候该做接口聚合 / BFF

当一个页面需要拼很多后端能力、不同终端对同一能力的展示差异又很明显时，BFF 才有价值。它本质上是终端适配层，不应该替代领域服务设计。如果页面简单、终端差异不大，前端直连或少量聚合接口通常更简单。

### 31.18 什么时候该把同步链路改成任务化

当同步链路已经过长、过慢、失败放大明显，而且业务允许“先受理后完成”时，任务化就更划算。它适合多阶段、长耗时、可异步推进的流程，但代价是要引入任务状态、重试、补偿和生命周期治理。

### 31.19 一致性、可用性、成本怎么排优先级

我不会给固定排序，而是先看哪个后果最不能接受。核心资源链路通常优先保一致性，用户入口链路通常优先保可用性，而成本决定方案能不能长期成立。真正的关键不是背原则，而是按业务底线分层排序。

## 32. 答题索引：智能体重管理项目

### 32.1 这一部分怎么用

这一部分可以理解成“题目到项目表达的映射表”。

用法是：

1. 面试官抛一个取舍题。
2. 你快速判断能不能挂到这个项目。
3. 如果能，就沿着这里的索引切进你的项目案例。

### 32.2 如果被问“为什么要拆服务”

优先联想到：

1. `普通对话链路 vs Agent 链路拆分`
2. `轻链路和重链路目标函数不同`
3. `高并发低时延 vs 强控制强审计`

可以重点讲：

1. 为什么不是一个大一统 AI 服务。
2. 为什么要按链路价值和复杂度拆边界。

### 32.3 如果被问“为什么不是所有逻辑都同步做”

优先联想到：

1. `记忆、审计、索引、画像沉淀异步化`
2. `主链路保时延，长期资产异步沉淀`
3. `主流程同步，附属流程异步`

可以重点讲：

1. 为什么用户当前响应优先级更高。
2. 为什么长期资产不值得阻塞本轮回复。

### 32.4 如果被问“为什么不把所有请求都直接送进 Agent”

优先联想到：

1. `入口粗判与分层路由`
2. `轻请求挡在轻链路`
3. `成本、时延、稳定性的综合权衡`

可以重点讲：

1. 为什么不是能力越强越全量放开。
2. 为什么重链路只对高价值请求开放。

### 32.5 如果被问“为什么这里要异步 / 任务化”

优先联想到：

1. `画像、记忆、审计、索引的异步沉淀`
2. `Agent 风险动作的状态化控制`
3. `复杂流程适合任务化，而不是强同步`

可以重点讲：

1. 哪些动作只要先受理即可。
2. 哪些动作必须请求内闭环。

### 32.6 如果被问“你们最看重哪个优先级”

优先联想到：

1. `患者主链路优先保可用`
2. `高风险工具调用优先保可控`
3. `增强能力允许降级或回退`

可以重点讲：

1. 为什么入口链路和高风险链路优先级不同。
2. 为什么不是整条系统一套优先级。

### 32.7 如果被问“这个项目里能体现你技术判断的点是什么”

可以优先从这几句收口：

1. 我不是简单堆 AI 能力，而是在按链路价值和风险等级做分层。
2. 我重点判断哪些能力该同步、哪些该异步、哪些该状态化。
3. 我会优先保护患者主链路体验，再把增强能力按可降级、可回退、可审计方式接进去。

## 附录 B：最容易说乱的 10 个问题对比表

### B.1 单体 vs 微服务

1. 单体更适合边界未稳、小团队、快速试错。
2. 微服务更适合边界清晰、协作阻塞、独立扩缩容诉求明显的阶段。
3. 本质是用分布式复杂度换独立演进能力。

### B.2 同步调用 vs MQ 异步解耦

1. 同步适合必须请求内闭环、立刻拿结果的动作。
2. 异步适合可稍后完成、需要削峰、需要解耦和广播的动作。
3. 本质是用消息治理复杂度换主链路可用性和系统弹性。

### B.3 AT vs TCC

1. AT 更适合数据库更新型、中等复杂度、希望少改业务代码的场景。
2. TCC 更适合关键资源预占、强一致要求高、业务能清晰拆 Try / Confirm / Cancel 的场景。
3. 本质是低侵入自动回滚 vs 高侵入强业务控制。

### B.4 Redis vs 数据库直查

1. 数据库直查适合规模可控、一致性要求高、读压力不大的场景。
2. Redis 适合读多写少、热点明显、低时延要求高的场景。
3. 本质是用一致性和治理复杂度换读取性能。

### B.5 本地缓存 vs Redis

1. 本地缓存更快，但多实例一致性差。
2. Redis 稍慢，但共享状态和统一治理更自然。
3. 本质是极致延迟 vs 分布式共享。

### B.6 乐观锁 vs 悲观锁

1. 乐观锁适合冲突低、可重试、关注吞吐的场景。
2. 悲观锁适合冲突高、事务内必须强控制顺序的场景。
3. 本质是失败重试 vs 提前阻塞。

### B.7 幂等 vs 锁

1. 幂等解决“重复执行后结果仍正确”。
2. 锁解决“同一时刻不要让多个执行者同时进入”。
3. 二者不等价，很多重复问题更像幂等，不一定要上锁。

### B.8 限流 vs 熔断 vs 降级

1. 限流管入口流量。
2. 熔断管坏依赖扩散。
3. 降级管资源不足时的功能优先级。
4. 三者不是一个东西，只是都属于稳定性治理。

### B.9 BFF vs 聚合接口

1. 少量聚合接口适合局部复杂页面。
2. 明确职责的 BFF 适合多终端、多页面、长期存在的适配诉求。
3. 本质是局部聚合优化 vs 独立终端适配层。

### B.10 同步链路 vs 任务化链路

1. 同步链路适合短链路、低时延、必须立即返回结果的动作。
2. 任务化适合长耗时、多阶段、可异步推进的流程。
3. 本质是请求内闭环 vs 生命周期治理。
