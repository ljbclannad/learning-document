## 一、服务注册与发现（Nacos）

### 1. Nacos的服务注册与发现原理？
**答：**

**服务注册流程：**
```
1. 服务启动
   ↓
2. 向Nacos Server注册实例信息
   - 服务名、IP、端口、元数据、健康状态
   ↓
3. Nacos Server存储实例信息
   - 临时实例：内存存储
   - 持久实例：持久化存储
   ↓
4. 发送心跳（临时实例，默认5秒）
   ↓
5. Nacos Server检测心跳
   - 15秒未收到心跳：标记不健康
   - 30秒未收到心跳：剔除实例
```

**服务发现流程：**
```
1. 消费者订阅服务
   ↓
2. Nacos Server推送实例列表
   ↓
3. 消费者本地缓存实例列表
   ↓
4. Nacos Server定期推送更新（10秒）
   ↓
5. 消费者根据负载均衡策略选择实例
```

**代码示例：**
```yaml
# application.yml
spring:
  application:
    name: order-service
  cloud:
    nacos:
      discovery:
        server-addr: localhost:8848
        namespace: dev
        group: DEFAULT_GROUP
        ephemeral: true  # 临时实例
```

```java
@SpringBootApplication
@EnableDiscoveryClient
public class OrderServiceApplication {
    public static void main(String[] args) {
        SpringApplication.run(OrderServiceApplication.class, args);
    }
}
```

**项目实例：** 医疗平台5个微服务都注册到Nacos，实现服务自动发现

### 2. Nacos的临时实例和持久实例的区别？
**答：**

| 特性 | 临时实例（默认） | 持久实例 |
|------|----------------|----------|
| **存储方式** | 内存 | 持久化（MySQL） |
| **健康检查** | 客户端心跳 | 服务端主动探测 |
| **实例下线** | 心跳超时自动剔除 | 标记不健康，不剔除 |
| **适用场景** | 微服务 | 数据库、MQ等基础设施 |
| **数据一致性** | AP（最终一致性） | CP（强一致性） |

**配置：**
```yaml
spring:
  cloud:
    nacos:
      discovery:
        ephemeral: true   # 临时实例（默认）
        # ephemeral: false  # 持久实例
```

**选择建议：**
- 微服务：临时实例（快速上下线）
- 基础设施：持久实例（需要持久化）

**项目实例：** 医疗平台微服务使用临时实例，MySQL、Redis使用持久实例

### 3. Nacos配置中心如何实现动态刷新？
**答：**

**原理：长轮询 + @RefreshScope**

**配置：**
```yaml
# bootstrap.yml
spring:
  application:
    name: order-service
  cloud:
    nacos:
      config:
        server-addr: localhost:8848
        namespace: dev
        group: DEFAULT_GROUP
        file-extension: yaml
        refresh-enabled: true  # 开启动态刷新
```

**使用：**
```java
@RestController
@RefreshScope  // 支持动态刷新
public class ConfigController {
    
    @Value("${order.timeout:3000}")
    private Integer timeout;
    
    @GetMapping("/config")
    public Integer getConfig() {
        return timeout;
    }
}
```

**刷新流程：**
```
1. 客户端发起长轮询请求（29.5秒超时）
   ↓
2. Nacos Server hold住请求
   ↓
3. 配置变更时立即返回 或 超时返回304
   ↓
4. 客户端收到变更，拉取最新配置
   ↓
5. 发布RefreshEvent事件
   ↓
6. @RefreshScope Bean重新初始化
```

**注意事项：**
- 只有@RefreshScope的Bean才会刷新
- 静态变量不会刷新
- 构造器注入的属性不会刷新

**项目实例：** 医疗平台使用Nacos Config统一管理配置，支持动态刷新

## 二、服务保护（Sentinel）

### 4. Sentinel的限流算法有哪些？
**答：**

**1. 滑动窗口算法（默认）**
```
时间轴：|--500ms--|--500ms--|--500ms--|--500ms--|
请求数：    10        15        20        18
当前QPS = (10+15+20+18) / 2s = 31.5

优点：精确统计
缺点：内存占用稍高
```

**2. 漏桶算法（匀速排队）**
```
请求 → 漏桶（固定容量） → 固定速率流出

优点：流量平滑
缺点：无法应对突发流量
```

**3. 令牌桶算法（预热模式）**
```
令牌桶 ← 固定速率生成令牌
   ↓
请求消耗令牌
   ↓
令牌不足则拒绝

优点：可以应对突发流量
缺点：实现复杂
```

**配置示例：**
```java
// 1. 滑动窗口（默认）
FlowRule rule = new FlowRule("queryOrder");
rule.setGrade(RuleConstant.FLOW_GRADE_QPS);
rule.setCount(100);  // QPS阈值

// 2. 匀速排队
FlowRule rule = new FlowRule("queryOrder");
rule.setGrade(RuleConstant.FLOW_GRADE_QPS);
rule.setCount(10);
rule.setControlBehavior(RuleConstant.CONTROL_BEHAVIOR_RATE_LIMITER);
rule.setMaxQueueingTimeMs(5000);  // 最大排队时间

// 3. 预热模式
FlowRule rule = new FlowRule("queryOrder");
rule.setGrade(RuleConstant.FLOW_GRADE_QPS);
rule.setCount(100);
rule.setControlBehavior(RuleConstant.CONTROL_BEHAVIOR_WARM_UP);
rule.setWarmUpPeriodSec(10);  // 预热时长
```

**项目实例：** 医疗平台核心接口使用滑动窗口限流，秒杀接口使用匀速排队

### 5. Sentinel的熔断降级策略？
**答：**

**三种熔断策略：**

**1. 慢调用比例**
```java
DegradeRule rule = new DegradeRule("queryOrder");
rule.setGrade(RuleConstant.DEGRADE_GRADE_RT);
rule.setCount(1000);  // RT阈值（毫秒）
rule.setSlowRatioThreshold(0.5);  // 慢调用比例阈值
rule.setMinRequestAmount(5);  // 最小请求数
rule.setStatIntervalMs(1000);  // 统计时长
rule.setTimeWindow(10);  // 熔断时长（秒）
```

**2. 异常比例**
```java
DegradeRule rule = new DegradeRule("queryOrder");
rule.setGrade(RuleConstant.DEGRADE_GRADE_EXCEPTION_RATIO);
rule.setCount(0.5);  // 异常比例阈值
rule.setMinRequestAmount(5);
rule.setStatIntervalMs(1000);
rule.setTimeWindow(10);
```

**3. 异常数**
```java
DegradeRule rule = new DegradeRule("queryOrder");
rule.setGrade(RuleConstant.DEGRADE_GRADE_EXCEPTION_COUNT);
rule.setCount(10);  // 异常数阈值
rule.setStatIntervalMs(60000);  // 统计时长（1分钟）
rule.setTimeWindow(10);
```

**熔断状态机：**
```
关闭状态（正常）
   ↓ 触发熔断条件
开启状态（熔断）
   ↓ 熔断时长后
半开状态（探测）
   ↓ 探测成功
关闭状态
   ↓ 探测失败
开启状态
```

**使用示例：**
```java
@Service
public class OrderService {
    
    @SentinelResource(value = "queryOrder", 
                      blockHandler = "handleBlock",
                      fallback = "handleFallback")
    public Order queryOrder(Long orderId) {
        return orderMapper.selectById(orderId);
    }
    
    // 限流/降级处理
    public Order handleBlock(Long orderId, BlockException ex) {
        log.warn("订单查询被限流: {}", orderId);
        return Order.builder().status("系统繁忙").build();
    }
    
    // 异常降级处理
    public Order handleFallback(Long orderId, Throwable ex) {
        log.error("订单查询异常: {}", orderId, ex);
        return Order.builder().status("查询失败").build();
    }
}
```

**项目实例：** 医疗平台订单服务调用支付服务，使用熔断降级保护

## 三、服务网关（Gateway）

### 6. Gateway的工作原理？
**答：**

**核心概念：**
- **Route（路由）**：网关的基本单元，包含ID、目标URI、断言、过滤器
- **Predicate（断言）**：匹配请求的条件
- **Filter（过滤器）**：处理请求和响应

**请求流程：**
```
客户端请求
   ↓
Gateway Handler Mapping（匹配路由）
   ↓
Gateway Web Handler（执行过滤器链）
   ↓
Pre Filter（前置过滤器）
   ↓
代理请求到目标服务
   ↓
Post Filter（后置过滤器）
   ↓
返回响应
```

**配置示例：**
```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: order-service
          uri: lb://order-service  # 负载均衡
          predicates:
            - Path=/order/**       # 路径匹配
            - Method=GET,POST      # 方法匹配
          filters:
            - StripPrefix=1        # 去除前缀
            - AddRequestHeader=X-Request-Source, gateway
```

**项目实例：** 医疗平台使用Gateway作为统一入口，实现路由、鉴权、限流

### 7. 如何在Gateway中实现统一鉴权？
**答：**

**自定义全局过滤器：**
```java
@Component
@Slf4j
public class AuthFilter implements GlobalFilter, Ordered {
    
    @Autowired
    private RedisTemplate<String, String> redisTemplate;
    
    // 白名单
    private static final List<String> WHITE_LIST = Arrays.asList(
        "/login", "/register", "/captcha"
    );
    
    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        ServerHttpRequest request = exchange.getRequest();
        String path = request.getURI().getPath();
        
        // 1. 白名单放行
        if (WHITE_LIST.stream().anyMatch(path::startsWith)) {
            return chain.filter(exchange);
        }
        
        // 2. 获取token
        String token = request.getHeaders().getFirst("Authorization");
        if (StringUtils.isEmpty(token)) {
            return unauthorized(exchange, "未登录");
        }
        
        // 3. 验证token
        String userId = redisTemplate.opsForValue().get("token:" + token);
        if (StringUtils.isEmpty(userId)) {
            return unauthorized(exchange, "token无效或已过期");
        }
        
        // 4. 将用户ID传递给下游服务
        ServerHttpRequest newRequest = request.mutate()
            .header("X-User-Id", userId)
            .build();
        
        return chain.filter(exchange.mutate().request(newRequest).build());
    }
    
    private Mono<Void> unauthorized(ServerWebExchange exchange, String message) {
        ServerHttpResponse response = exchange.getResponse();
        response.setStatusCode(HttpStatus.UNAUTHORIZED);
        response.getHeaders().setContentType(MediaType.APPLICATION_JSON);
        
        String body = JSON.toJSONString(Result.fail(401, message));
        DataBuffer buffer = response.bufferFactory().wrap(body.getBytes());
        
        return response.writeWith(Mono.just(buffer));
    }
    
    @Override
    public int getOrder() {
        return -100;  // 优先级最高
    }
}
```

**项目实例：** 医疗平台Gateway统一鉴权，下游服务无需重复校验

## 四、分布式事务（Seata）

### 8. Seata AT模式的原理？
**答：**

**AT模式：自动补偿，基于undo log**

**执行流程：**
```
一阶段（业务执行）：
1. 开启全局事务（TM）
   ↓
2. 注册分支事务（RM）
   ↓
3. 执行业务SQL（UPDATE account SET balance = balance - 100）
   ↓
4. 生成前镜像（balance = 1000）
   ↓
5. 执行SQL
   ↓
6. 生成后镜像（balance = 900）
   ↓
7. 插入undo_log表
   ↓
8. 提交本地事务（释放锁）
   ↓
9. 报告分支状态给TC

二阶段（提交/回滚）：
全局提交：
   TC通知所有RM → 删除undo_log → 完成

全局回滚：
   TC通知所有RM → 读取undo_log → 生成反向SQL → 执行回滚 → 删除undo_log
```

**代码示例：**
```java
@Service
public class OrderService {
    
    @Autowired
    private OrderMapper orderMapper;
    
    @Autowired
    private AccountService accountService;
    
    @Autowired
    private StorageService storageService;
    
    // 全局事务入口
    @GlobalTransactional(name = "create-order", rollbackFor = Exception.class)
    public void createOrder(Order order) {
        // 1. 创建订单（本地事务）
        orderMapper.insert(order);
        
        // 2. 扣减库存（远程调用）
        storageService.deduct(order.getProductId(), order.getCount());
        
        // 3. 扣减账户余额（远程调用）
        accountService.deduct(order.getUserId(), order.getMoney());
        
        // 任何一步失败，Seata自动回滚所有操作
    }
}
```

**undo_log表结构：**
```sql
CREATE TABLE `undo_log` (
  `id` bigint(20) NOT NULL AUTO_INCREMENT,
  `branch_id` bigint(20) NOT NULL,
  `xid` varchar(100) NOT NULL,
  `context` varchar(128) NOT NULL,
  `rollback_info` longblob NOT NULL,  -- 前后镜像
  `log_status` int(11) NOT NULL,
  `log_created` datetime NOT NULL,
  `log_modified` datetime NOT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `ux_undo_log` (`xid`,`branch_id`)
) ENGINE=InnoDB;
```

**优缺点：**
- **优点**：无侵入，性能好
- **缺点**：依赖数据库事务，隔离性较弱

**项目实例：** 医疗平台预约流程使用AT模式，保证数据一致性

### 9. Seata TCC模式的原理？
**答：**

**TCC模式：手动补偿，Try-Confirm-Cancel**

**三个阶段：**
```
Try阶段：
- 预留资源（冻结金额）
- 不实际扣款

Confirm阶段：
- 确认提交
- 扣减冻结金额

Cancel阶段：
- 回滚
- 解冻金额
```

**代码示例：**
```java
@LocalTCC
public interface AccountTccService {
    
    /**
     * Try阶段：冻结金额
     */
    @TwoPhaseBusinessAction(
        name = "accountTcc",
        commitMethod = "commit",
        rollbackMethod = "rollback"
    )
    boolean prepare(@BusinessActionContextParameter(paramName = "userId") Long userId,
                    @BusinessActionContextParameter(paramName = "money") BigDecimal money);
    
    /**
     * Confirm阶段：扣减冻结金额
     */
    boolean commit(BusinessActionContext context);
    
    /**
     * Cancel阶段：解冻金额
     */
    boolean rollback(BusinessActionContext context);
}

@Service
public class AccountTccServiceImpl implements AccountTccService {
    
    @Autowired
    private AccountMapper accountMapper;
    
    @Override
    @Transactional
    public boolean prepare(Long userId, BigDecimal money) {
        // 1. 检查余额
        Account account = accountMapper.selectById(userId);
        if (account.getBalance().compareTo(money) < 0) {
            throw new BusinessException("余额不足");
        }
        
        // 2. 冻结金额
        accountMapper.freeze(userId, money);
        
        return true;
    }
    
    @Override
    @Transactional
    public boolean commit(BusinessActionContext context) {
        Long userId = context.getActionContext("userId", Long.class);
        BigDecimal money = context.getActionContext("money", BigDecimal.class);
        
        // 扣减冻结金额
        accountMapper.deductFreeze(userId, money);
        
        return true;
    }
    
    @Override
    @Transactional
    public boolean rollback(BusinessActionContext context) {
        Long userId = context.getActionContext("userId", Long.class);
        BigDecimal money = context.getActionContext("money", BigDecimal.class);
        
        // 解冻金额
        accountMapper.unfreeze(userId, money);
        
        return true;
    }
}
```

**账户表设计：**
```sql
CREATE TABLE `account` (
  `id` bigint(20) NOT NULL,
  `user_id` bigint(20) NOT NULL,
  `balance` decimal(10,2) NOT NULL,   -- 可用余额
  `frozen` decimal(10,2) NOT NULL,    -- 冻结金额
  PRIMARY KEY (`id`)
) ENGINE=InnoDB;
```

**优缺点：**
- **优点**：性能好，灵活
- **缺点**：代码侵入大，需要实现三个方法

**项目实例：** 电商平台订单流程使用TCC模式，性能更好

### 10. AT模式和TCC模式如何选择？
**答：**

| 特性 | AT模式 | TCC模式 |
|------|--------|---------|
| **实现方式** | 自动补偿 | 手动补偿 |
| **代码侵入** | 无侵入 | 侵入大 |
| **性能** | 较好 | 最好 |
| **隔离性** | 较弱 | 强 |
| **适用场景** | 常规业务 | 核心业务、跨库 |

**选择建议：**
- **AT模式**：优先选择，简单易用
- **TCC模式**：性能要求高、需要强隔离性

**项目实例：**
- 医疗平台预约流程：AT模式（简单）
- 电商平台订单流程：TCC模式（性能）

## 五、RPC框架（Dubbo）

### 11. Dubbo的调用流程？
**答：**

**完整调用流程：**
```
1. 消费者调用代理对象
   ↓
2. 代理对象通过Cluster获取Invoker列表
   ↓
3. 通过LoadBalance选择一个Invoker
   ↓
4. 通过Filter链处理（日志、监控等）
   ↓
5. 通过Protocol进行远程调用
   ↓
6. 通过Codec编码请求
   ↓
7. 通过Transporter发送请求（Netty）
   ↓
8. 提供者接收请求
   ↓
9. 通过Codec解码请求
   ↓
10. 通过Filter链处理
   ↓
11. 通过Invoker调用实际服务
   ↓
12. 返回结果
```

**核心组件：**
- **Proxy**：代理层，生成代理对象
- **Cluster**：集群层，负载均衡、容错
- **Protocol**：协议层，RPC调用
- **Transport**：传输层，网络通信（Netty）

**项目实例：** 电商平台使用Dubbo实现服务间高性能调用

---

### 12. Dubbo的负载均衡策略？
**答：**

**四种负载均衡策略：**

**1. Random（随机，默认）**
```java
@DubboReference(loadbalance = "random")
private UserService userService;

// 按权重随机
// 权重越大，被选中的概率越高
```

**2. RoundRobin（轮询）**
```java
@DubboReference(loadbalance = "roundrobin")
private UserService userService;

// 按权重轮询
// 权重越大，轮询次数越多
```

**3. LeastActive（最少活跃调用数）**
```java
@DubboReference(loadbalance = "leastactive")
private UserService userService;

// 选择活跃调用数最少的提供者
// 活跃调用数：正在处理的请求数
```

**4. ConsistentHash（一致性哈希）**
```java
@DubboReference(loadbalance = "consistenthash")
private UserService userService;

// 相同参数的请求总是发到同一提供者
// 适合有状态服务
```

**配置示例：**
```yaml
dubbo:
  consumer:
    loadbalance: random  # 全局配置
```

```java
// 接口级配置
@DubboReference(loadbalance = "leastactive")
private UserService userService;

// 方法级配置
@DubboReference(methods = {
    @Method(name = "queryUser", loadbalance = "consistenthash")
})
private UserService userService;
```

**项目实例：** 电商平台订单服务使用LeastActive，保证负载均衡

### 13. Dubbo如何实现服务降级？
**答：**

**三种降级方式：**

**1. Mock降级（推荐）**

## 六、项目场景深挖题（重点）

### 14. 微服务如何拆分？
**答：**

**拆分原则：**

**1. 按业务领域拆分（DDD）**
```
电商平台：
- 用户服务：用户注册、登录、信息管理
- 商品服务：商品管理、分类、库存
- 订单服务：订单创建、支付、物流
- 营销服务：优惠券、活动、积分
```

**2. 按团队拆分**
```
- 每个团队负责1-2个服务
- 团队规模：5-10人
```

**3. 按数据拆分**
```
- 每个服务独立数据库
- 避免跨库JOIN
```

**拆分步骤：**
```
1. 识别业务边界
   ↓
2. 定义服务接口
   ↓
3. 拆分数据库
   ↓
4. 实现服务
   ↓
5. 服务治理
```

**注意事项：**
- 避免过度拆分（服务数量 < 团队人数 × 2）
- 避免循环依赖
- 保持服务自治

**项目实例：** 医疗平台按业务领域拆分5个服务，每个服务独立数据库

### 15. 服务间如何通信？

**1. HTTP（OpenFeign，推荐）**
```java
@FeignClient(name = "user-service", fallback = UserServiceFallback.class)

public class OrderService {

        User user = userServiceClient.getUser(order.getUserId());

```

**2. RPC（Dubbo）**
```java
// 提供者
@DubboService
public class UserServiceImpl implements UserService {
    
    @Override
    public User getUser(Long userId) {
        return userMapper.selectById(userId);
    }
}

// 消费者
@Service
public class OrderService {
    
    @DubboReference
    private UserService userService;
    
    public void createOrder(Order order) {
        User user = userService.getUser(order.getUserId());
        // 业务逻辑
    }
}
```

**3. 消息队列（RabbitMQ）**
```java
// 生产者
@Service
public class OrderService {
    
    @Autowired
    private RabbitTemplate rabbitTemplate;
    
    public void createOrder(Order order) {
        orderMapper.insert(order);
        
        // 发送MQ
        rabbitTemplate.convertAndSend("order.exchange", "order.create", order);

        stockMapper.deduct(order.getProductId(), order.getCount());
    }
}
```

**选择建议：**
- **同步调用**：HTTP（简单）、RPC（性能）
- **异步调用**：MQ（解耦）

- 医疗平台：HTTP（OpenFeign）
- 电商平台：RPC（Dubbo）+ MQ（RabbitMQ）

## 七、生产事故深挖题（重点）

### 16. 生产事故：服务雪崩
**场景：** 某个服务故障，导致整个系统不可用

**问题原因：**
```
订单服务 → 库存服务（故障，响应慢）
   ↓
订单服务线程池耗尽
   ↓
订单服务不可用
   ↓
用户服务调用订单服务失败
   ↓
用户服务线程池耗尽
   ↓
整个系统雪崩
```

**解决方案：**

**1. 服务降级（Sentinel）**
```java
@Service
public class OrderService {
    
    @SentinelResource(value = "createOrder", 
                      blockHandler = "handleBlock",
                      fallback = "handleFallback")
    public Order createOrder(OrderDTO dto) {
        // 调用库存服务
        stockService.deduct(dto.getProductId(), dto.getCount());
        
        // 创建订单
        return orderMapper.insert(order);
    }
    
    // 降级处理
    public Order handleFallback(OrderDTO dto, Throwable ex) {
        log.error("订单创建失败，降级处理", ex);
        
        // 返回默认值或从缓存获取
        return Order.builder()
            .status("处理中")
            .message("系统繁忙，订单稍后处理")
            .build();
    }
}
```

**2. 服务熔断**
```java
// 配置熔断规则
DegradeRule rule = new DegradeRule("stockService");
rule.setGrade(RuleConstant.DEGRADE_GRADE_EXCEPTION_RATIO);
rule.setCount(0.5);  // 异常比例50%
rule.setTimeWindow(10);  // 熔断10秒
```

**3. 限流**
```java
// 配置限流规则
FlowRule rule = new FlowRule("createOrder");
rule.setGrade(RuleConstant.FLOW_GRADE_QPS);
rule.setCount(100);  // QPS 100
```

**4. 线程池隔离**
```yaml
# Hystrix线程池隔离
hystrix:
  threadpool:
    default:
      coreSize: 10
      maxQueueSize: 100
```

**项目实例：** 医疗平台使用Sentinel熔断降级，避免服务雪崩

### 18. 生产事故：Seata分布式事务失败
**场景：** 订单创建成功，但库存未扣减

**排查过程：**

**1. 查看Seata日志**
```bash
# Seata Server日志
tail -f seata-server.log

# 发现全局事务超时
Global transaction timeout, xid=xxx
```

**2. 查看业务日志**
```bash
# 订单服务日志
2024-05-14 10:00:00 [INFO] 订单创建成功, orderId=1001

# 库存服务日志
2024-05-14 10:00:30 [ERROR] 库存扣减超时
```

**问题原因：**
- 库存服务处理慢（30秒）
- Seata全局事务超时（默认60秒）
- 全局事务回滚，但订单已提交

**解决方案：**

**1. 调整超时时间**
```yaml
seata:
  client:
    tm:
      default-global-transaction-timeout: 120000  # 120秒
```

**2. 优化业务逻辑**
```java
@GlobalTransactional(timeoutMills = 120000)
public void createOrder(Order order) {
    // 1. 创建订单
    orderMapper.insert(order);
    
    // 2. 异步扣减库存（优化）
    CompletableFuture.runAsync(() -> {
        stockService.deduct(order.getProductId(), order.getCount());
    });
}
```

**3. 补偿机制**
```java
// 定时任务检查订单状态
@Scheduled(fixedDelay = 60000)
public void checkOrder() {
    List<Order> orders = orderMapper.selectPendingOrders();
    
    for (Order order : orders) {
        // 检查库存是否扣减
        if (!stockService.isDeducted(order.getId())) {
            // 补偿扣减库存
            stockService.deduct(order.getProductId(), order.getCount());
        }
    }
}
```

**项目实例：** 电商平台调整Seata超时时间，添加补偿机制
