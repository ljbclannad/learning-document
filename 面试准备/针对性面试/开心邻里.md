## Agent 工程执行闭环：Superpowers + 项目规范 + Jenkins

我会把 Superpowers 作为 Agent 的工程执行骨架，但不会让它脱离项目实际规则运行。任务进入后，Agent 先加载 `using-superpowers`，再强制读取项目内的 `CLAUDE.md`、`AGENTS.md`、`README.md`、`docs` 和 CI/CD 配置，提取技术栈、编码规范、测试命令、分支策略、提交规范、Jenkins job、构建参数、发布环境和禁止事项；如果 Superpowers 流程和项目规范冲突，以项目规范为准。

整体流程会拆成四个闭环：

1. **需求到设计**
   - 判断任务类型：需求、开发、修复、调试、发布或 CI/CD。
   - 对需求类任务先走 `brainstorming`，沉淀用户故事、验收标准和设计方案。
   - 设计文档写入 `docs/superpowers/specs/...`，需要用户确认后再进入实现计划。

2. **计划到实现**
   - 使用 `writing-plans` 生成 `docs/superpowers/plans/...`。
   - 计划中明确本地测试命令、Jenkins job 名称、Jenkins 参数、预期构建产物、成功标准和失败排查路径。
   - 开发前通过 `using-git-worktrees` 创建独立分支或 worktree，避免直接在 `main/master` 上实现。
   - 开发阶段按 `test-driven-development` 执行：先写失败测试，再实现最小代码，随后跑本地测试并小步提交。
   - 对可并行任务使用 `subagent-driven-development`，对明确计划使用 `executing-plans`。

3. **本地验证到 Jenkins**
   - 完成开发后先走 `verification-before-completion`，执行单元测试、集成测试、lint、format 和 build。
   - 只有本地验证通过，才触发 Jenkins。
   - Jenkins 信息从 `Jenkinsfile`、`docs/ci.md`、`CLAUDE.md` CI 说明或项目脚本中读取，例如 `sh/build.sh`、`sh/deploy.sh`。
   - 触发方式可以是 Jenkins CLI、REST API、GitHub webhook 或浏览器操作，参数至少包含 branch、commit SHA、environment、profile、version 或 tag。
   - 触发后记录 build number 和 build URL，并轮询构建结果。

4. **失败排查到发布收尾**
   - Jenkins 构建后读取 console log，检查 checkout、compile、test、package、docker、artifact upload、deploy 等阶段是否成功。
   - 如果失败，进入 `systematic-debugging`：先读日志定位失败阶段，再分析根因，修复后重新做本地验证并再次触发 Jenkins。
   - 如果成功，进入 `requesting-code-review` 和 `finishing-a-development-branch`。
   - 创建 PR 时附上变更摘要、本地测试结果、Jenkins build URL、构建产物、发布影响和回滚方案。
   - 发布后继续检查服务健康状态，例如 actuator health、smoke test、错误日志和关键 metrics；如果异常，优先按预案触发 rollback job，再继续定位问题。

### Superpowers 插件整体流程

Superpowers 的价值不是提供某一个单点工具，而是把 Agent 的工作拆成一套可跳转、可审计的工程流程。它的入口是 `using-superpowers`，作用是让 Agent 在回答、澄清、写代码、调试之前先判断当前任务是否匹配某个 skill，只要有可能匹配，就必须先加载对应 skill，再按 skill 里的流程做事。

整体可以理解成一条状态机：

1. **入口识别**
   - 用户提出任务后，先进入 `using-superpowers`。
   - 判断任务类型：需求澄清、功能开发、bug 修复、测试失败、代码评审、发布收尾或 skill 创建。
   - 如果项目内存在 `CLAUDE.md`、`AGENTS.md` 等本地规范，优先读取并作为最高约束。

2. **需求类任务**
   - 进入 `brainstorming`。
   - 先理解项目上下文，再一轮一问澄清目标、约束和成功标准。
   - 提供 2-3 个方案和取舍，得到用户确认后写入 `docs/superpowers/specs/...`。
   - 设计确认后跳转到 `writing-plans`。

3. **计划和实现类任务**
   - `writing-plans` 负责把设计拆成可执行步骤，明确文件、测试、风险和验收方式。
   - `using-git-worktrees` 负责隔离分支和工作目录。
   - `test-driven-development` 要求先写失败测试，再写最小实现，再跑测试。
   - 如果任务已经有明确计划，使用 `executing-plans` 按计划推进。
   - 如果任务可以拆成多个独立方向，使用 `subagent-driven-development` 或 `dispatching-parallel-agents` 并行处理。

4. **调试和收尾类任务**
   - 遇到 bug、测试失败、构建失败，进入 `systematic-debugging`，要求先收集证据，再定位根因，避免靠猜测修复。
   - 完成后进入 `verification-before-completion`，用真实命令验证结果。
   - 需要评审时用 `requesting-code-review`，收到评审意见时用 `receiving-code-review`。
   - 准备合并、PR 或保留分支时，用 `finishing-a-development-branch` 做收尾决策。

### Skill 跳转和使用规则

Skill 跳转的核心原则是：**先判断任务性质，再选择流程 skill；流程 skill 决定下一步能跳到哪里，而不是 Agent 随意调用工具。**

- `using-superpowers` 是入口，负责识别当前任务是否需要 skill。
- `brainstorming` 的终点是 `writing-plans`，不能直接跳到实现。
- `writing-plans` 之后通常进入 `using-git-worktrees`、`test-driven-development` 或 `executing-plans`。
- 任何 bug、失败构建、失败测试，都优先跳到 `systematic-debugging`。
- 声称完成前必须跳到 `verification-before-completion`，用命令结果支撑结论。
- 代码完成后，如果需要质量把关，跳到 `requesting-code-review`。
- 评审反馈回来后，跳到 `receiving-code-review`，先判断反馈是否成立，再决定是否修改。
- 准备合并、推送、创建 PR 或保留分支时，跳到 `finishing-a-development-branch`。
- 创建或改造 skill 本身时，跳到 `writing-skills`。

面试里可以强调：我会把 skill 当成 Agent 的“流程路由表”。例如用户说“帮我做一个功能”，不是立刻写代码，而是 `using-superpowers -> brainstorming -> writing-plans -> using-git-worktrees -> test-driven-development -> verification-before-completion -> requesting-code-review -> finishing-a-development-branch`。如果中间 Jenkins 失败，则从当前阶段切到 `systematic-debugging`，修复后再回到本地验证和 Jenkins 验证。

### 创建 Prompt 的要点

为了让 Agent 稳定走完 Superpowers + Jenkins 的闭环，Prompt 不能只写“帮我实现某功能”，而要把角色、边界、输入、流程、验证和产出都说清楚。

1. **明确角色和优先级**
   - 说明 Agent 的角色是工程执行者，不是单纯代码生成器。
   - 明确优先级：用户指令和项目 `CLAUDE.md/AGENTS.md` 最高，其次是 Superpowers skill，最后才是模型默认习惯。

2. **明确上下文读取范围**
   - 要求先读取 `CLAUDE.md`、`AGENTS.md`、`README.md`、`docs`、`Jenkinsfile`、`docs/ci.md` 和构建脚本。
   - 要求提取技术栈、测试命令、分支策略、提交规范、Jenkins job、参数、环境和禁止事项。

3. **明确流程跳转**
   - 需求不清时先 `brainstorming`，不能直接实现。
   - 设计确认后生成 spec，再进入 plan。
   - 开发前创建独立分支或 worktree。
   - bug 和 CI 失败必须走 `systematic-debugging`。
   - 完成前必须执行 `verification-before-completion`。

4. **明确验证标准**
   - 本地验证至少包含单元测试、集成测试、lint、format 和 build。
   - Jenkins 验证要记录 build number、build URL、console log 关键阶段和最终状态。
   - 没有真实命令输出时，不能声称“已通过”。

5. **明确最终产出**
   - PR 描述必须包含变更摘要、测试结果、Jenkins build URL、发布影响、风险点和回滚方案。
   - 如果失败，要输出失败阶段、根因、已尝试方案、下一步动作，而不是只说构建失败。

一个比较完整的 Prompt 模板可以这样写：

```text
你是项目工程 Agent。开始任何任务前，先加载 using-superpowers，并读取项目 CLAUDE.md、AGENTS.md、README.md、docs、Jenkinsfile 和 CI 脚本。

请先判断任务类型，并按 Superpowers skill 路由执行：
- 需求不清：brainstorming -> writing-plans
- 功能开发：using-git-worktrees -> test-driven-development -> verification-before-completion
- 已有计划：executing-plans
- bug / 测试失败 / Jenkins 失败：systematic-debugging
- 完成后：requesting-code-review -> finishing-a-development-branch

如果项目规范和 Superpowers 冲突，以项目规范为准。
开发完成后必须先跑本地测试、lint、format、build；全部通过后再触发 Jenkins。
触发 Jenkins 时传入 branch、commit SHA、environment、profile、version/tag 等参数，记录 build number 和 build URL，轮询构建结果并分析 console log。
成功后在 PR 中写入变更摘要、测试结果、Jenkins build URL、风险和回滚方案；失败时先定位失败阶段和根因，修复后重新本地验证和 Jenkins 验证。
```

面试时可以这样总结：**我不会只让 Agent 写代码，而是把它约束在项目规范、测试验证、CI 构建、日志分析、PR 交付和发布后检查这条链路里。这样 Agent 的输出不是一次性代码生成，而是可验证、可追踪、可回滚的工程交付流程。**
