# 扩展点与处理器链：让核心流程稳定，让变化能力可插拔

## 1. 一句话理解

**不要把所有新需求都塞进主流程；主流程只保存稳定的业务骨架，把容易变化的规则放到明确阶段的可插拔处理器中。**

这是一种**面向扩展点编程**的思维。常见实现形态包括处理器链、责任链、拦截器链、过滤器链和生命周期回调。

它的关键不在于写一个 `for` 循环，而在于完成职责划分：

```text
稳定主流程：负责事情怎样完成
    ↓ 在预先定义的阶段调用
可插拔能力：负责在该阶段附加什么规则
    ↓ 由装配层决定
启用策略与顺序：负责系统实际运行哪些能力
```

## 2. 从堆叠 if/else 到扩展点

以“创建订单”为例。初期直接把逻辑写进一个应用服务通常没有问题：

```text
创建订单
  → 参数校验
  → 计算优惠
  → 风控检查
  → 保存订单
  → 发放积分
  → 发送通知
  → 记录审计日志
```

当优惠、风控、营销、通知不断增加，主流程会变成一个“知道一切”的类。每增加一项能力，都要修改它；某项能力的开关、顺序、失败策略也会散落在这个类中。

用扩展点思维重新划分后：

```text
OrderCreationService（稳定编排）
  ├─ beforeCreate：校验、优惠、风控
  ├─ persist：保存订单（核心业务动作）
  └─ afterCreate：积分、通知、审计

各处理器（独立变化）
  ├─ CouponProcessor
  ├─ RiskCheckProcessor
  ├─ PointsProcessor
  └─ AuditProcessor
```

主流程只知道“这个阶段需要执行一组能力”，不需要知道每项能力的具体细节。

## 3. 先划分阶段，再抽象接口

最容易犯的错误是先定义一个万能的 `process()` 接口，再把所有事情硬塞进去。正确顺序相反：**先找业务生命周期的稳定阶段，再决定每个阶段需要的处理器协议。**

例如：

| 业务阶段 | 可放入的能力 | 不应放入的能力 |
| --- | --- | --- |
| `beforeCreate` | 参数校验、资格判断、价格计算、风控 | 发送“创建成功”通知 |
| `afterPersist` | 审计记录、领域事件、异步通知 | 改写创建请求的核心字段 |
| `beforePay` | 支付渠道选择、限额校验 | 已支付后的积分发放 |
| `afterPaySuccess` | 积分、通知、发票、异步履约 | 决定是否允许支付 |

阶段是一份业务契约：它说明“此时哪些数据已经可靠存在、能改什么、失败会造成什么结果”。

## 4. 什么时候采用

满足下面多个信号时，优先考虑处理器链或扩展点：

1. **同一流程周边的能力会持续增加。** 例如下单后未来可能增加积分、会员成长值、消息通知、数据同步。
2. **不同租户、环境或产品线启用的能力不同。** 例如 A 租户需要风控和积分，B 租户只需要审计。
3. **能力有独立的配置、测试、负责人或迭代节奏。** 它们虽然挂在同一流程上，但不应共用一个巨型类。
4. **能力的顺序有业务意义。** 如先校验、再计算优惠、最后风控；顺序本身应成为显式规则。
5. **主流程已经出现不断增长的 if/else、策略判断或“顺手加一行”。** 这是主流程正在承担变化的信号。
6. **能力具有横切性。** 如审计、权限、幂等、埋点、脱敏、通知等，可能会挂接在多个业务流程上。

## 5. 什么时候不要采用

不是所有逻辑都需要“插件化”。下面情况直接写在应用服务中往往更清晰：

1. **步骤是核心业务不变量。** 例如扣库存、创建支付单、更新订单状态之间存在严格一致性关系。
2. **预计不会变化，且只有两三行逻辑。** 过早抽象会让阅读者需要跳转多个类才能理解一个简单行为。
3. **处理器之间共享大量隐式状态。** 这通常说明它们实际上是一个完整业务步骤，应该聚合在一个领域服务里。
4. **失败语义无法统一。** 有些步骤必须中断，有些步骤允许重试或忽略；若没有先设计清楚，简单的链式调用会掩盖风险。

一个实用判断：如果新能力加入时，只是“在某阶段多做一件相对独立的事”，适合扩展点；如果它会改变“这件核心业务到底是什么、怎样才算完成”，应回到主流程或领域模型中设计。

## 6. 设计时必须讲清楚的五件事

### 6.1 处理对象是什么

处理器拿到的应该是明确的上下文，例如 `OrderCreationContext`，而不是任意 `Map`。上下文中需要区分：只读输入、可修改的中间结果、最终输出。

### 6.2 能否改变结果

常见有三类：

- **校验型**：只通过或抛出业务异常。
- **变换型**：计算折扣、补充字段，返回修改后的结果或修改受控上下文。
- **副作用型**：记录审计、发布事件、发送通知，不应悄悄篡改核心结果。

把三类能力混在一个无约束接口中，会让调用者无法判断影响范围。

### 6.3 顺序如何定义

不要依赖“注册先后”这种隐式约定。为处理器提供显式优先级，或让装配层维护一个可读的顺序表。顺序应能被测试：例如校验必须先于扣库存，审计必须在成功持久化后执行。

### 6.4 失败如何处理

每个阶段都应声明失败策略：

| 类型 | 常见策略 |
| --- | --- |
| 前置校验、风控 | 失败立即中断，不创建订单 |
| 核心持久化 | 失败回滚事务 |
| 审计、通知 | 通常转为可靠事件或重试任务，不能拖垮主交易 |

特别是外部调用，不要在核心事务里简单串行执行后置处理器。更稳妥的方案是先提交核心数据，再通过 Outbox/消息队列可靠地执行后续副作用。

### 6.5 幂等与可观测性

后置处理器可能因重试被执行多次，因此需要幂等键、去重记录或天然幂等的写入方式。同时应记录：处理器名称、阶段、耗时、结果和失败原因，避免排障时只看到“订单创建失败”。

## 7. 与常见模式的关系

| 名称 | 关注点 | 典型例子 |
| --- | --- | --- |
| 模板方法 | 固定整体步骤，留少数子类钩子 | 容器 `refresh()` 生命周期 |
| 责任链/处理器链 | 同一阶段依次经过多个处理器 | 参数校验链、Bean 后处理器 |
| 策略模式 | 多个方案中通常选择一个 | 不同支付渠道、不同计价规则 |
| 观察者/事件 | 发布者不等待或不直接编排订阅者 | 订单创建后发领域事件 |
| AOP | 围绕方法调用织入通用横切逻辑 | 日志、鉴权、事务 |

它们可以组合使用。例如：订单创建主流程通过前置处理器完成同步校验；保存成功后发布领域事件；通知和积分由事件订阅者异步处理。

## 8. 复杂度：代码简单，设计不简单

若一个阶段有 `n` 个处理器，遍历成本是 **O(n)**；处理器数量通常很少，算法复杂度几乎不是问题。

真正的复杂度来自业务设计：

- 阶段划分是否准确；
- 排序是否稳定且可解释；
- 错误、事务、重试、幂等如何定义；
- 是否出现处理器之间的隐式依赖；
- 启用哪些能力是否可追踪。

因此，处理器链适合“有边界的可变性”，不适合用来隐藏复杂的核心业务协作。

## 9. 最小设计检查清单

新增一个处理器前，先回答：

- 它属于哪个业务阶段？该阶段的数据是否已准备好？
- 它是校验、变换，还是副作用？
- 失败时要中断、回滚、重试，还是记录后忽略？
- 它与其他处理器的先后关系是什么？
- 是否可能被重复执行？如何保证幂等？
- 它是否真的独立变化，还是应该留在核心领域服务？

## 10. 记忆句

**核心流程对变化关闭，但对阶段性的扩展开放；先定义稳定阶段，再让独立能力按规则接入。**
