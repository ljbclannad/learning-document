# 1. 为什么要用延时队列

在开发中，往往会遇到一些关于延时队列的需求：

1. 生成订单20分钟未支付则取消。
2. 生成订单60秒后给用户发送短信。

对上述的任务，我们给一个专业的名字来形容，那就是延时任务。

## 延时任务和定时任务的区别：

	1.  定时任务有明确的触发时间（定时触发），延时任务没有。
	1.  定时任务有明确的执行周期（每隔几秒触发），延时任务没有。
	1.  定时任务一般处理的是批操作，而延时任务一般是单个任务。



# 2. 延时任务的实现方案分析

## 2.1 数据库轮询

1. 思路：

   该方案在小型项目中使用，通过一个定时线程定时的去扫描数据库，通过订单时间来决定后续业务逻辑。

2. 实现：

   - 通过@Scheduler注解配置定时任务
   - 通过配置定时线程池发起定时任务。

3. 优点：

   - 简单易行，支持集群操作

4. 缺点：

   - 对服务器内存消耗大
   - 存在延迟，如果你设置3分钟，最快的延迟时间就是3分钟，针对订单时间没有明确的界限
   - 如果订单量大，每隔几分钟就这样扫描，数据库损耗极大。

## 2.2 JDK 延迟队列

1. 思路：

​		使用JDK自带的DelayQueue实现延迟队列，将任务放入队列中，从队列中获取满足时间的任务。

2. 实现：
   - 创建Task（任务），任务需要实现Delayed接口，一般都拥有时间变量
   - 创建一个DelayQueue,每次业务处理完毕都往队列中添加任务，传入需要执行的时间。
   - 运行delayQueue.take方法，从队列中执行任务。
3. 优点：
   - 效率高，任务触发时间延迟低。
4. 缺点：
   - 服务器重启后，队列中内容消失。
   - 集群扩展麻烦，容易发生重复。
   - 因为队列问题，订单数量太多容易发生OOM。
   - 代码复杂度较高。

## 2.3 时间轮算法

1. 原理及实现参考：时间轮算法分析.md
2. 优点：
   - 效率比delayQueue高
3. 缺点：
   - 基于HashedWheelBucket实现任务存储。一旦系统宕机任务消息就会消失。
   - 因为存在于本地，容易出现OOM异常。

## 2.4 Redis sorted set

1. 原理及实现：
   - 使用redis的zsort数据结构，设置score为time，自动排序，按照一定的时间区间去轮询获取redis中的数据，并进行业务处理。
   - 由于该方法在集群模式下可能存在一个订单被多次获取的情况，所以要对针对这业务代码加入分布式锁。
2. 优点：
   - 使用redis缓存作为介质，redis又支持响应的持久化机制，保证数据可靠性。
   - 做集群扩展相当方便。
3. 缺点：
   - 增加了代码复杂度，需要考虑各种并发情况。

## 2.5 redis过期回调

1. 原理及实现：

   - Redis本身存在过期回调的机制

   - 在redis.conf中加入一条配置：```notify-keyspace-events Ex```

   - 代码实现：

     ```java
     @Configuration 
     public class RedisListenerConfig {    
       	@Bean 
       	RedisMessageListenerContainer container(RedisConnectionFactory connectionFactory) {         
           RedisMessageListenerContainer container = new RedisMessageListenerContainer();
           container.setConnectionFactory(connectionFactory);        
           return container;    
         } 
     }
     ```

     编写Redis过期监听方法：

     ```java
     @Component
     public class RedisKeyExpirationListener extends KeyExpirationEventMessageListener {
     
         public RedisKeyExpirationListener(RedisMessageListenerContainer listenerContainer) {
             super(listenerContainer);
     		}
     		
     		@Override
     		public void onMessage(Message message, byte[] pattern) {
         		String expiredKey = message.toString();
        		  System.out.println("监听到key：" + expiredKey + "已过期");
     		}
     }
     ```

2. 优点：

   - 使用redis缓存作为介质，redis又支持响应的持久化机制，保证数据可靠性。
   - 做集群扩展相当方便。

3. 缺点：

   - Redis的发布/订阅目前是即发即弃(fire and forget)模式的，因此无法实现事件的可靠通知。也就是说，如果发布/订阅的客户端断链之后又重连，则在客户端断链期间的所有事件都丢失了。因此，该方案不是太推荐。当然，如果你对可靠性要求不高，可以使用。



## 2.6 使用消息队列

1. 原理：

   利用 `RabbitMQ` 做延时队列是比较常见的一种方式，而实际上`RabbitMQ` 自身并没有直接支持提供延迟队列功能，而是通过 `RabbitMQ` 消息队列的 `TTL`和 `DXL`这两个属性间接实现的。

   先来认识一下 `TTL`和 `DXL`两个概念：

   `Time To Live`(`TTL`) ：

   `TTL` 顾名思义：指的是消息的存活时间，`RabbitMQ`可以通过`x-message-tt`参数来设置指定`Queue`（队列）和 `Message`（消息）上消息的存活时间，它的值是一个非负整数，单位为微秒。

   ```
   RabbitMQ` 可以从两种维度设置消息过期时间，分别是`队列`和`消息本身
   ```

   - 设置队列过期时间，那么队列中所有消息都具有相同的过期时间。
   - 设置消息过期时间，对队列中的某一条消息设置过期时间，每条消息`TTL`都可以不同。

   如果同时设置队列和队列中消息的`TTL`，则`TTL`值以两者中较小的值为准。而队列中的消息存在队列中的时间，一旦超过`TTL`过期时间则成为`Dead Letter`（死信）。

   `Dead Letter Exchanges`（`DLX`）

   `DLX`即死信交换机，绑定在死信交换机上的即死信队列。`RabbitMQ`的 `Queue`（队列）可以配置两个参数`x-dead-letter-exchange` 和 `x-dead-letter-routing-key`（可选），一旦队列内出现了`Dead Letter`（死信），则按照这两个参数可以将消息重新路由到另一个`Exchange`（交换机），让消息重新被消费。

   `x-dead-letter-exchange`：队列中出现`Dead Letter`后将`Dead Letter`重新路由转发到指定 `exchange`（交换机）。

   `x-dead-letter-routing-key`：指定`routing-key`发送，一般为要指定转发的队列。

   队列出现`Dead Letter`的情况有：

   - 消息或者队列的`TTL`过期
   - 队列达到最大长度
   - 消息被消费端拒绝（basic.reject or basic.nack）
