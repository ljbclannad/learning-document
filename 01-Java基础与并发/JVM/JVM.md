# JVM：运行机制、对象生命周期与回收边界

> 阅读基线：以 JDK 17/21 的 HotSpot 为主，GC 重点使用 G1；JDK 8 的 CMS 作为历史背景。规范规定的语义、HotSpot 的实现与具体运行参数分开说明。本文集中解释机制；案例、诊断命令、调优与可复现实验统一见 [[01-Java基础与并发/JVM/JVM项目实践与故障排查|JVM 项目实践与故障排查]]。官方资料核对日期：2026-10-28。
>
> 项目案例取材于知识库中的医生助手、画像缓存与数据库访问方案，属于教学推演，不代表项目已出现这些故障，也不代表已完成生产压测。实践篇区分独立实验与待项目验证的场景。

## 1. 从一次请求建立 JVM 全景

假设医生助手收到一个患者分析请求：读取画像，查询历史记录，调用模型和工具，最后生成 JSON 响应。理解 JVM，可以沿这次请求追踪四条线：

```text
类的生命周期：读取字节码 → 加载/链接 → 初始化 → 使用 → 满足条件后卸载
方法的执行：进入栈帧 → 解释执行或执行编译代码 → 正常返回/异常退出
对象的生命周期：分配 → 初始化 → 被请求/队列/缓存持有 → 不可达 → 回收
资源的生命周期：取得连接/缓冲 → 使用 → 显式关闭/归还 → 后续内存回收
```

它们互相影响，但不是同一件事。方法返回不会自动销毁它创建的对象；请求结束也不意味着异步任务结束。连接对象被 GC 发现不可达，更不能代替事务结束和连接归还。

一次延迟抖动可能来自 GC，也可能来自编译预热、类初始化锁、线程池排队、CPU 限流或数据库等待。先建立时间线，再判断哪一层阻塞了进度。

学习时始终追问三个问题：**对象由谁持有、资源何时释放、证据从哪里取得**。例如，`byte[]` 数量很多只是现象；“任务队列中的闭包引用了完整患者上下文”才接近原因。

## 2. 运行时内存与进程内存账本

### 2.1 规范中的区域与 HotSpot 的实现

| 区域 | 负责什么 | 排查时的边界 |
| --- | --- | --- |
| Java 堆 | 实例与数组的分配空间，GC 管理的主要对象 | `-Xmx` 只约束堆，不约束整个进程 |
| 方法区、运行时常量池 | 类结构、方法与字段信息、运行时符号信息 | 是规范概念，不是“元空间加上一切”的物理地址图 |
| Java 虚拟机栈 | 方法调用的栈帧、局部变量、操作数栈等 | 引用私有不意味着引用指向的对象私有 |
| 程序计数器 | 当前线程执行位置的抽象状态 | 不是源码行号；执行 native 方法时规范未定义其值 |
| 本地方法栈 | 支持 native 调用 | 具体实现可以与平台线程栈结合 |

上述是抽象执行模型，不能据此推断 JIT 优化后的每个变量必有一个固定栈槽。依据：[JVMS 运行时数据区与栈帧](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-2.html#jvms-2.5)。

在本文的 HotSpot 基线中，还要分清：

- 类元数据主要放在本地内存中的 Metaspace；JDK 8 用它替代永久代。
- `java.lang.Class` 镜像对象在 Java 堆中，静态字段值由镜像相关存储承载。`static` 引用指向的普通对象仍是堆对象，不能笼统说“static 都在元空间”。
- JIT 编译后的机器码位于 Code Cache，与 Metaspace 分开核算。
- 字符串驻留对象位于堆中；StringTable 是管理驻留字符串的结构，不能把哈希表结构和字符串对象本体混为一谈。

### 2.2 为什么堆没满，容器还是被杀

进程内存的工程预算可以写成：

```text
堆 + 元空间/类空间 + Code Cache + 平台线程栈
+ GC/JIT 内部结构 + 直接缓冲/本地库 + 其他映射与余量
```

这是一张预算清单，不是可以从不同工具直接相加的精确公式。`reserved` 表示保留的虚拟地址空间，`committed` 表示已提交内存，RSS 反映驻留物理页；容器统计还可能包含文件缓存等项目。它们的统计口径不同。

因此，4 GiB 容器不能简单配置 `-Xmx4g`。例如可以先为堆预算 2 GiB，再按压测为其他区域留空间，但这只是实验起点，不能推广为所有服务的固定百分比。

若容器被内核直接终止，JVM 可能来不及抛 OOM 或写 dump。退出码 137 只能说明收到 SIGKILL，不能单独证明 OOM；需要结合容器终止原因、内存事件和系统日志。

### 2.3 不同失败需要不同证据

| 现象 | 可能耗尽的资源 | 首要证据 |
| --- | --- | --- |
| `Java heap space` | 堆空间、单个大对象分配空间 | GC 后占用、对象持有链、单次申请大小 |
| `Metaspace` | 类元数据容量 | 加载类数量、ClassLoader 数量与引用链 |
| `Direct buffer memory` 或直接缓冲分配失败 | NIO 直接缓冲配额或本地内存 | BufferPool 指标、缓冲池指标、RSS |
| `unable to create native thread` | 本地内存、线程数或系统限制 | 平台线程数量、栈配置、PID/线程限制 |
| `StackOverflowError` | 当前线程调用深度 | 重复递归栈、循环对象序列化、代理调用链 |
| 容器 `OOMKilled` | 容器总内存 | 容器与进程指标，不只看堆 |

`StackOverflowError` 与 OOM 是不同异常。增大 `-Xss` 可能推迟深递归失败，也会提高平台线程的内存预算，不能修复无限递归。

## 3. 对象的分配、布局与发布

### 3.1 从 `new` 到构造完成

以普通堆对象为例，HotSpot 需要确认类可用、取得内存、保证字段默认值、设置类型与运行时头信息，再执行实例初始化和构造器。实现可以合并或重排内部操作，但必须保持 Java 可观察语义。

“构造器执行前字段有默认值”不等于“其他线程一定只能看见构造完成后的状态”。如果构造过程中把 `this` 注册到共享监听器，其他线程可能提前访问半初始化对象。正常构造后也需要通过锁、`volatile`、线程安全容器等方式安全发布；`final` 字段另有初始化安全规则，不能代替整个可变对象的同步策略。

在 JDK 17/21 的普通构造流程中，实例字段先具备默认值，随后沿构造链执行父类构造，再执行当前类字段初始化器、实例初始化块及构造器剩余部分。父类构造器若调用可覆写方法，会动态分派到子类实现，此时子类字段可能仍是默认值；这个问题甚至不需要多线程就能出现。

字节码中的 `new` 与构造器调用也分开：常见赋值形态为 `new → dup → invokespecial <init> → astore`。前者产生未初始化引用，后者执行构造；不能把一条 `new` 指令理解为已经完成全部业务初始化。构造器抛异常时，正常赋值不会完成，但构造期间提前发布的引用可能已经被外部保存。依据：[JLS 12.5 实例创建过程](https://docs.oracle.com/javase/specs/jls/se21/html/jls-12.html#jls-12.5)。

### 3.2 TLAB 解决分配竞争，不提供访问隔离

在 G1 的常见分配路径里，线程从 Eden 中取得一小块 TLAB，分配小对象时推进自己的指针，减少每次分配都竞争共享空间的成本。空间不足时可能申请新 TLAB，或者走 TLAB 外的分配路径。

TLAB 在堆里。对象从哪个线程的 TLAB 分配，不决定以后能否被其他线程访问。对象被放入共享队列后，依然需要遵循并发访问规则。

大对象、不适合剩余 TLAB 空间的对象或分配压力下的对象，可能进入其他路径。因此“每个对象必先进入 Eden”不成立。

### 3.3 对象大小不能只加字段大小

常见 HotSpot 对象布局包括对象头、实例字段、对齐填充；数组还包含长度信息。对象头中的 Mark Word 承载运行时状态，类型信息用于关联类元数据。具体尺寸受 JDK、压缩指针、对齐和对象头实现影响。

估算容量时至少区分：

- **Shallow Size**：对象本体的大小。例如 `ArrayList` 本体不包含所有元素。
- **Retained Size**：如果某对象不可达，随之能够释放的对象图大小。共享子对象不能简单重复累加。
- **业务载荷**：例如 JSON 的 UTF-8 长度；它通常远小于解析后对象图及解析期间的峰值。

一万个 `Integer` 和一个 `int[]` 即使表达相同数字，也有不同的对象数、引用与访问成本。是否改为紧凑结构要看实际热点；不要为省少量字节把业务模型改得不可维护。

### 3.4 局部变量与线程安全的准确关系

```java
List<Patient> snapshot = new ArrayList<>(sharedPatients);
```

局部引用 `snapshot` 不共享，但这只是浅拷贝：其中的 `Patient` 仍可能共享。若 `sharedPatients` 本身在并发修改，复制过程也必须有一致性保障。

线程安全取决于可变状态是否共享、是否正确同步，而不是变量是否写在方法内部。只在单线程中使用的局部 `ArrayList` 完全可以安全；把局部对象交给其他线程才改变了访问边界。**逃逸分析是编译器的分析手段，不是导致竞争的原因。**

## 4. 解释执行、JIT 与逃逸分析

### 4.1 为什么同一个接口刚启动时更慢

HotSpot 可以先解释执行字节码，收集热点与类型信息，再通过分层编译生成机器码。内联能够消除调用开销，也让跨方法优化成为可能；当优化假设不再成立时，可能发生去优化并重新编译。

因此启动阶段同时存在类加载、初始化、连接池建立、缓存预热与 JIT 编译。不要仅凭“热身后变快”就把收益全部归于 JIT，也不要把单次冷启动耗时当成稳态吞吐。

### 4.2 标量替换不是把完整对象搬到栈上

如果编译器证明对象不会以可观察方式逃逸，并且适合优化，可以把对象拆成若干标量，消除对象分配或部分锁操作。标量可能进入寄存器，也可能进入栈槽。

本文基线的 HotSpot Server Compiler 不会把完整堆对象直接改成完整栈对象；主要讨论分配消除、标量替换与锁消除，不能列出“逃逸分析后自动栈上分配”作为已实现路径。

“不逃逸”是优化机会，不是优化承诺：内联深度、调用形态、控制流与编译器实现都可能影响结果。HotSpot 的逃逸分析不能概括成“方法里 new 的对象都在栈上”。依据：[HotSpot 性能增强：分层编译与逃逸分析](https://docs.oracle.com/en/java/javase/21/vm/java-hotspot-virtual-machine-performance-enhancements.html)。

这也解释了微基准中的陷阱：如果循环计算的结果从未被使用，优化器可能消除整个计算。评估分配优化应使用 JMH 等基准工具并观察分配量，而不是只在循环外调用两次 `nanoTime()`。

逃逸判断应放在编译上下文中理解。源码中返回对象，在方法被内联后仍可能被消除；写入成员字段也不自动证明线程共享，还要看宿主对象是否逃逸。对仅在当前线程内使用的对象，JIT 可能消除不必要的同步，但业务正确性不能依赖“锁大概会被消除”。

### 4.3 字符串问题应区分语义与物理分配

`new String("abc")` 在 Java 语义上创建一个新的 `String` 实例，字面量对应驻留字符串。但字面量何时解析、底层数组是否共享、分配是否被优化，都影响物理对象数量。

所以“固定创建两个对象”缺少统计边界。真正的项目问题通常是：字符串是否被反复拼接、是否同时保留原始 JSON 与解析树、是否把敏感大响应放入日志队列。应对这些路径做分配剖析，而不是围绕一句表达式猜整个 JVM 的对象计数。

## 5. 可达性、引用与对象保留

### 5.1 GC 判断能否到达，不理解业务是否需要

GC 从根集合出发追踪对象图。线程执行状态中的有效引用、JNI 句柄，以及可达类相关的静态引用等都可以形成保留路径。两个对象互相引用，只要整个环从根不可达，仍然可以回收。

```text
仍存活的平台线程 → ThreadLocalMap → Entry.value → 患者上下文 → 大量历史记录
线程池 → 工作队列 → Runnable 闭包 → 请求对象 → JSON/向量结果
静态缓存 → Map.Entry → 画像快照 → 历史版本
```

对象业务上已过期但路径仍在，就是内存泄漏的常见形式。泄漏不一定来自某种特殊指针，普通集合就足够制造它。

方法的源码作用域也不是对象必须存活到的边界。JIT 可在最后一次使用后不再把引用视为活跃；反过来，闭包、异常、集合、缓存可以让对象比方法调用活得更久。

### 5.2 引用强度不等于可预测缓存策略

| 引用 | 机制与边界 | 适合解决的问题 |
| --- | --- | --- |
| 强引用 | 普通可达路径使对象存活 | 正常对象关系 |
| 软引用 | GC 可按内存压力等策略清除，不提供确定 TTL/命中率 | 可丢弃的辅助数据，不能替代有界缓存设计 |
| 弱引用 | 当对象达到弱可达条件时可被清除；并非“任意一次 GC 必清所有弱引用” | 避免某些关联关系单独延长对象寿命 |
| 虚引用 | `get()` 不返回目标对象，配合引用队列观察状态 | 清理机制中的通知与跟踪 |

引用队列中的通知不等于“此刻已经收回了精确多少物理内存”。具体语义见 [java.lang.ref](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/ref/package-summary.html)。

`WeakHashMap` 的 key 是弱引用，value 仍可强引用 key；这种反向关系可能使 key 无法消失。软引用缓存也可能在内存压力下集体失效，诱发后端请求洪峰。

### 5.3 ThreadLocal 的 key 弱，value 仍然强

线程存活时，其 ThreadLocalMap 中的 value 可能一直被持有。key 被回收后，遗留 value 的清理依赖后续操作中的清扫等机制，不保证立即发生。即使 key 是静态字段、一直可达，忘记结束请求上下文也会造成跨请求污染。

```java
contextHolder.set(context);
try {
    process();
} finally {
    contextHolder.remove();
}
```

这只是生命周期形态。在线程池中还需要定义上下文是否传播、由谁恢复旧值；嵌套作用域不能盲目覆盖后直接删除。单纯改用 ThreadLocal，不会自动修复容量问题。

### 5.4 外部资源必须显式释放

`finalize()` 已被弃用并标记待移除，不应承担资源正确性。Cleaner 可以做兜底，但清理时机不可作为业务承诺，清理动作本身也不能错误地强引用待清理对象。

数据库连接、文件、游标等资源使用 `try-with-resources` 或框架定义的释放协议。GC 解决对象内存回收，不保证连接池不会耗尽。

## 6. GC 算法为何需要屏障与安全点

### 6.1 先分清三组概念

| 概念 | 含义 | 容易混淆的地方 |
| --- | --- | --- |
| 标记与回收 | 判断存活，与释放/整理空间是不同阶段 | 并发标记完成不代表老年代已全部回收 |
| 并行与并发 | 多个 GC 线程同时工作；GC 与应用同时工作 | 并行 GC 仍可能全程暂停应用 |
| 分代与分区 | 按生命周期组织；按固定块组织空间 | G1 分区但仍是分代收集器 |

标记-清除保留存活对象位置，可能产生碎片；复制将存活对象移入目标空间，需要额外容量；标记-整理在搬迁后形成可用空间，成本包括定位和修正引用。收集器把这些思想与并行、并发、分代组合起来，不是一张算法表就能推导全部性能。

分代假设是“许多对象寿命短”。收益依赖实际负载：如果队列让本来短命的请求对象熬过多次回收，就会增加复制与晋升压力。年龄阈值是实现策略，不是对象必须存活 15 次才进老年代的规范。

### 6.2 只回收年轻代，为什么不会漏掉老年代的引用

如果一个老对象指向年轻对象，而 GC 只从线程栈扫描年轻代，就可能误判该年轻对象死亡。解决方向是记录跨区域引用：应用修改引用时执行 GC 写屏障，更新卡表等辅助信息，收集时扫描相关位置。

以 G1 为例，Remembered Set 帮助定位来自其他 Region 的引用，避免每次年轻代回收都遍历整个老年代。它记录的是扫描线索，具体粒度与表示随实现变化，并不是简单维护“所有对象地址的大列表”。

大量跨 Region 引用更新会增加屏障、辅助结构维护和暂停扫描成本。这就是“对象数量没明显增加，但更新大缓存后 GC 阶段变慢”的一个待验证假设。

### 6.3 对象晋升看年龄，也看承接空间

经典复制式年轻代可用 `Eden + From → To/Old` 理解；G1 使用一组 Survivor Region，不能套成两块固定地址、固定比例的 Survivor。年龄描述幸存对象的回收经历，不是毫秒寿命；对象进入老年代后，也不意味着永不回收。

晋升需要区分三条路径：达到当前晋升阈值，Survivor 目标空间不足而转入 Old，以及特定分配策略绕过年轻代，例如 G1 的 Humongous。Old 也没有空间时，问题是分配或转移失败，不能继续解释成“再提前晋升就好”。

动态年龄阈值不是“某年龄及以上对象超过 Survivor 一半”。在核对的 HotSpot 年龄表实现中，从较小年龄开始向上累计存活量，超过目标 Survivor 容量时选取阈值，再受 `MaxTenuringThreshold` 限制。目标容量由收集器策略传入，不能统一写成固定一半。比如目标为 10 MiB，年龄 1、2、3 的存活量分别为 4、4、5 MiB，累计到年龄 3 才超过目标；实际晋升仍由收集器使用阈值和空间状态决定。[JDK 17.0.11 AgeTable 源码](https://github.com/openjdk/jdk17u/blob/jdk-17.0.11%2B9/src/hotspot/share/gc/shared/ageTable.cpp)。

在实验实例上可用 `-Xlog:gc+age=trace` 观察年龄表和新阈值。阈值下降只是证据：应继续确认队列等待、存活量和目标容量，不能直接把阈值调高当作修复。

### 6.4 并发标记时，对象图正在变化

把三色标记当作解释模型：白色尚未发现，灰色已发现但未扫描完，黑色已扫描。例如黑色对象 A 尚未指向白色对象 C，灰色对象 B 持有 C；应用先建立 `A.ref = C`，再删除 `B.ref`，无屏障的标记器可能既不重扫 A，也无法再从 B 发现 C。这说明需要处理引用迁移，不能只说“凭空新增一个不可达对象的引用”。

G1 使用 SATB（Snapshot-At-The-Beginning）思路：引用覆盖前，通过屏障保留必要的旧引用信息，帮助维持标记开始时的存活视图。它与用于跨 Region 引用追踪的屏障职责不同。

SATB 的保守性意味着某些本轮已变成垃圾的对象仍可能被视作存活，留待后续回收。因此“一轮并发标记后空间没完全下降”并不自动证明泄漏。相关实现语义见 [G1 标记机制](https://docs.oracle.com/en/java/javase/21/gctuning/garbage-first-g1-garbage-collector1.html)。

GC 屏障是维护回收正确性的机制；Java 内存模型中的可见性与有序性规则解决并发访问语义，不能因为都出现“屏障”就认为有写屏障的普通字段自动线程安全。

### 6.5 STW 与安全点

全局安全点让 Java 线程处于 JVM 能安全检查或修改运行状态的位置，部分 GC 和其他 VM 操作需要这种协调。日志中的到达安全点耗时与安全点内操作耗时，应分别分析。

不能把所有卡顿都叫 STW：数据库锁只阻塞相关请求；一个线程做慢 I/O 也不代表整个 JVM 暂停。反过来，GC 日志没有长暂停，也不能排除非 GC 的安全点操作或 CPU 调度停滞。

更完整的请求耗时可以理解为：

```text
排队 + 实际计算 + 外部等待 + 调度等待 + 与请求重叠的 JVM 暂停
```

这也是为什么仅优化 GC 最大暂停，不一定能改善接口 P99。

## 7. 沿一个周期理解 G1

### 7.1 Region 和回收集合

G1 将堆划成等大的 Region，分别扮演 Eden、Survivor、Old 等角色。年轻代和老年代是逻辑集合，不需要各自占据一整片连续空间。

一次暂停选中的 Region 集合称为 Collection Set。普通 Young GC 处理年轻代集合；Mixed GC 额外加入部分老年代 Region。暂停时间取决于根扫描、外部引用扫描、存活对象复制等成本，不能只按“垃圾最多”排序。

### 7.2 从年轻代回收到混合回收

| 阶段 | 主要工作 | 对应用的影响 |
| --- | --- | --- |
| Young GC | 把选中年轻 Region 的存活对象转移到 Survivor/Old | STW，多个 GC 线程可并行处理 |
| Concurrent Start | 在一次年轻代暂停中启动标记周期 | 有暂停，不是独立的全堆回收 |
| Concurrent Mark | 并发追踪存活性，期间仍可能发生年轻代暂停 | 与应用争用部分 CPU/带宽 |
| Remark | 完成标记收尾和相关处理 | STW |
| Cleanup 及后续准备 | 汇总存活信息、处理空 Region、形成候选集合 | 包含暂停与并发工作，依阶段看日志 |
| Mixed GC | 年轻代加部分老年代 Region 的转移回收 | 多次 STW，逐批释放空间 |
| Full GC | 在无法正常推进等情况下进行全堆整理 | 重型 STW；现代 G1 可并行执行 |

不是每轮标记之后都必然进行同样数量的 Mixed GC；是否值得回收、暂停预算与容量约束都会影响决策。G1 的主要阶段说明见 [官方 GC 周期文档](https://docs.oracle.com/en/java/javase/21/gctuning/garbage-first-g1-garbage-collector1.html)。

### 7.3 并发回收也会来不及

设老年代净增长速率为 `R`，从启动标记到获得足够回收收益所需时间为 `T`，仅这一段就要为新增数据预留约 `R × T` 的容量，此外还要考虑对象转移空间和突发余量。这是容量推理，不是 G1 内部阈值的精确公式。

如果 CPU 配额降低，`T` 可能变长；如果任务积压，`R` 和存活集可能一起上升。即使业务 QPS 不变，也可能更早耗尽空间。

G1 默认使用自适应 IHOP，结合分配和标记历史预测启动时机。`InitiatingHeapOccupancyPercent` 不能解释为“运行全过程固定在总堆 45% 时开始”；关闭自适应后行为也有不同。降低阈值能争取时间，但不能释放仍被队列强引用的对象。

### 7.4 Evacuation Failure 告诉我们什么

转移存活对象需要目标空间。当可用目标空间不足或其他条件导致转移失败时，日志可能出现 evacuation failure 或相关 to-space 信息，并可能进一步进入 Full GC。

排查顺序是：存活量是否突然增加、老年代分配是否过快、并发标记是否来不及、是否有大对象碎片、CPU 是否受限。`G1ReservePercent` 增大预留空间会压缩应用实际可用容量，不能当作免费扩容。

`MaxGCPauseMillis` 是预测目标，不是最大暂停保证。把目标调小可能缩小年轻代、提高 GC 频率，甚至影响吞吐。G1 通常应先保留年轻代自适应，不直接搬用 `-Xmn`、`NewRatio` 或老收集器参数。依据：[G1 调优指南](https://docs.oracle.com/en/java/javase/21/gctuning/garbage-first-garbage-collector-tuning.html)。

### 7.5 Full GC 的触发原因不等于业务根因

| 触发线索 | 说明了什么 | 还不能推出什么 |
| --- | --- | --- |
| G1 分配失败、转移空间不足，随后 Full GC | 正常回收路径未提供足够空间 | 不能单凭这一条证明泄漏 |
| `System.gc()` 等显式请求 | 有代码、库或诊断动作请求回收 | 不代表堆已经满；实际行为受参数影响 |
| `Metadata GC Threshold` 等元数据线索 | 元数据分配触及触发条件 | 不代表已达到 `MaxMetaspaceSize`，也不保证每次都是 Full GC |
| Full GC 后存活量仍高 | 仍有大量可达数据，或存在其他容量限制 | 可能是合法大缓存、积压或泄漏，需看持有关系 |

G1 的并发标记、Mixed GC 和 Full GC 是不同事件；“回收老年代”不必然意味着 Full GC。Full GC 也不是统一意义上的异常事件，例如显式请求可以在堆空间充足时发生。诊断时同时记录原因、停顿、回收效果和业务影响。

元空间触发 GC 时，只有满足卸载条件的类才有机会释放元数据；大量可达加载器不会因为多做一次 Full GC 就自动消失。反过来，堆回收后占用很低，也不能排除直接缓冲、线程或容器内存问题。

## 8. 大对象、Humongous 与真正的流式处理

### 8.1 Humongous 是单个对象的分配属性

在本文 HotSpot 基线中，**对象总大小超过 Region 容量一半**时走 Humongous 路径；边界应按包含对象头和对齐后的大小判断，不能只看数组载荷长度。它占用连续的 Region，逻辑上属于老年代，末尾未用空间可能浪费。官方概述有“达到一半”的表述；精确等号边界按已核对的 [JDK 17.0.11 源码](https://github.com/openjdk/jdk17u/blob/jdk-17.0.11%2B9/src/hotspot/share/gc/g1/g1CollectedHeap.hpp)与 [JDK 21 源码](https://github.com/openjdk/jdk/blob/jdk-21%2B35/src/hotspot/share/gc/g1/g1CollectedHeap.hpp)中 `is_humongous` 的严格大于判断理解。

一个包含很多小对象的 `List`，整体保留量很大，并不代表每个元素都是 Humongous；但其内部引用数组可能达到阈值。反过来，一个短命 `byte[]` 也可能直接走 Humongous 路径。

G1 可在某些年轻代回收中提前回收符合条件的 Humongous 对象，例如部分原始类型数组；不能断言“所有大对象都必须等 Full GC”。回收与搬迁也不同：通常不在普通转移暂停中复制这些大对象。依据：[G1 Humongous Objects](https://docs.oracle.com/en/java/javase/21/gctuning/garbage-first-g1-garbage-collector1.html)。

### 8.2 分块必须从数据源开始

下面的流程没有消除峰值：

```text
读取完整文件为 byte[] → 再复制成很多小块 → 逐块处理
```

完整数组仍存在，复制还额外消耗内存。真正有界的流程是：

```text
输入流/数据库分页 → 固定大小批次 → 同步处理或有界提交 → 释放该批 → 读取下一批
```

流式 API 也可能被中途的 `collect(toList())`、排序、全量响应拼接或日志序列化破坏。数据库游标是否流式还依赖 JDBC 驱动、fetch size、事务与 Mapper 用法；不能只因方法返回 `Stream` 就认为整个链路有界。

### 8.3 优化时必须同时约束三件事

1. **单项大小**：单个请求、图片、模型响应、向量批次的最大字节量。
2. **同时在途数量**：运行中、排队中、重试中的任务总量。
3. **保留时间**：结果何时被消费并解除引用，超时后是否还继续执行。

信号量约束同时持有许可的数量，属于并发控制；令牌桶通常约束一段时间内的进入速率。二者都不能单独替代对象大小上限。每个任务大小差异大时，还需要按字节预算或分档准入。

对象池会把短命对象变成长命对象。只有剖析证明分配/清零等成本值得优化，且借还协议、容量、总字节数明确时，才考虑池化；归还后保留一个曾经扩容到几十 MiB 的缓冲，同样可能抬高长期占用。

## 9. 收集器选择与版本边界

| 收集器 | 主要取舍 | 使用边界 |
| --- | --- | --- |
| Serial | 简单、并行协调成本低，暂停中单线程回收 | 小资源场景是候选，不能按“堆小于 1 GB”一刀切 |
| Parallel | 更关注吞吐，回收时并行暂停 | 批处理等能容忍暂停的负载，仍需验证完成时间 |
| G1 | 增量回收老年代，在吞吐与暂停间折中 | 本文主要分析对象 |
| ZGC | 将更多工作并发化，以低暂停为目标 | 需要 CPU 与内存余量；低 GC 暂停不保证端到端延迟 |
| Shenandoah | 并发回收与对象搬迁，面向低暂停 | 先确认发行版、版本和平台提供该收集器 |
| CMS/ParNew | 历史上的并发老年代与年轻代组合 | CMS 在 JDK 14 移除，不作为 JDK 17/21 新服务选项 |

CMS 的学习价值在于理解标记-清除的碎片、浮动垃圾以及并发周期来不及完成时的退化。无需把历史参数表搬进现代 G1 配置。

JDK 21 的 ZGC 有非分代与分代模式；分代模式使用 `-XX:+UseZGC -XX:+ZGenerational`。JDK 24 已移除非分代模式，因此参数和机制必须随版本核对，不能把“ZGC 不分代”写成通用结论。依据：[JDK 21 收集器说明](https://docs.oracle.com/en/java/javase/21/gctuning/available-collectors.html)、[JDK 24 迁移变化](https://docs.oracle.com/en/java/javase/25/migrate/significant-changes-jdk-24.html)。

更换收集器之前应定义吞吐、P99、CPU、RSS 与成本目标；保持同样数据、负载和资源配额比较。没有 GC 证据时，换收集器不能修复慢数据库、无界队列和无限缓存。

## 10. 类加载、初始化与卸载

### 10.1 五个动作不是五个严格一次完成的时间段

```text
加载 → 链接（验证、准备、解析）→ 初始化
```

加载建立类表示；验证检查字节码约束；准备为静态字段建立存储和默认值；解析处理符号引用，可以按需进行；初始化执行相应静态初始化逻辑。常量变量还有特殊初始化规则，不能把所有 `static final` 都理解为普通赋值。

```java
static final int LIMIT = 100;             // 编译期常量，使用方可能内联
static final Integer BOXED = 100;         // 不是编译期常量变量
static final int SIZE = loadSize();       // 需要执行初始化逻辑
```

修改 `LIMIT` 后只替换定义方 jar，使用方未重新编译，可能继续使用旧值。这是常量内联问题，不一定是部署缓存。

### 10.2 加载不等于初始化

`new`、调用静态方法、访问需要初始化的静态字段等主动使用会触发初始化；读取编译期常量、取得 `SomeClass.class` 不应简单归为相同情况。`Class.forName(name, false, loader)` 可以请求不初始化。

初始化具有同步协议：某线程执行 `<clinit>` 时，其他需要该类初始化完成的线程可能等待。若静态块进行远程配置拉取或慢 I/O，启动卡顿可能表现为大量线程等待类初始化。

初始化失败后，该类在同一个定义加载器中处于错误状态，后续使用可能得到 `NoClassDefFoundError`。此时要回看最早的初始化异常，不能只按“缺少 jar”排查。依据：[JLS 类初始化过程](https://docs.oracle.com/javase/specs/jls/se21/html/jls-12.html#jls-12.4.2)。

### 10.3 类身份与委派

一个运行时类的身份由**二进制名称与定义它的类加载器**共同决定。同名类若由不同加载器定义，可以互不兼容，这解释了某些看似“类型转换成自己”的 `ClassCastException`。

父优先委派是常见加载策略，不是 JVM 规范强制所有加载器只能这样实现。JDK 9+ 常讨论 Bootstrap、Platform、Application；容器和插件系统可能有隔离策略。SPI 可通过线程上下文类加载器发现应用提供者，并不意味着接口本身必然由 Bootstrap 加载。

父优先让子加载器复用父加载器定义的公共类型，但不保证整个 JVM 只有一份同名类。核心类保护也不只依靠委派：`ClassLoader.defineClass` 对 `java.*` 名称有额外限制。自定义加载器仍要遵循类型约束和访问检查。[ClassLoader API](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/ClassLoader.html)。

Tomcat 10.1 的 Webapp 加载器默认对普通应用类优先查找 `WEB-INF/classes` 和 `WEB-INF/lib`；Java SE 类以及容器实现的特定 Jakarta API 仍优先委派。`delegate=true` 又会改变普通应用类的顺序。不同 Web 应用可以隔离依赖，但共享接口若各自复制一份，也可能出现提供者无法转换为接口的错误。[Tomcat 类加载规则](https://tomcat.apache.org/tomcat-10.1-doc/class-loader-howto.html)。

`ServiceLoader.load(Service.class)` 使用当前线程的上下文类加载器寻找提供者，也可以显式传入加载器；模块层还有相应 API。它改变的是“由哪个加载器发起发现”，并不要求那个加载器重写父优先规则。提供者可见后，还必须实现调用方看到的同一份接口。[ServiceLoader API](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/ServiceLoader.html)。

排查时记录类来源、定义加载器、线程上下文加载器和依赖版本，而不是只比较全限定类名。

### 10.4 类卸载为什么与泄漏有关

普通类的卸载与其定义加载器能否被回收密切相关，并且需要相应 GC/卸载过程发生。旧加载器被外部线程的上下文加载器、线程局部值、注册表或静态缓存持有，就可能无法释放类元数据。

重复热部署后 Metaspace 持续上涨，应先比较旧加载器与类数量，再找外部保留路径。加载器内部互相引用本身不等于泄漏；关键是整个对象群是否仍被外部可达路径留住。
