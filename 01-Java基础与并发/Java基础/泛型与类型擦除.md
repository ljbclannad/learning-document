# 泛型与类型擦除

基线：Java 17。本文沿“把一组有类型的数据交给公共方法”解释编译检查与运行时边界。集合实现见 [[集合]]，框架读取类型声明见 [[注解与反射]]。

## 1. 泛型约束的是类型关系

`List<String>` 让编译器检查写入值，并让调用方读取时得到 String 类型。它减少强制转换，但不验证字符串是不是合法业务编号，也不能保证外部 JSON 的每个元素都符合领域规则。

`List<Integer>` 不是 `List<Number>` 的子类型。假设允许这种赋值，调用方就能通过 Number 列表写入 Double，破坏原 Integer 列表的约束。这种不变性与数组不同：`Integer[]` 可以赋给 `Number[]`，但往其中写入 Double 会在运行时抛出 `ArrayStoreException`。

```java
// 编译失败示例，不能作为可运行语句复制进程序。
List<Integer> integers = new ArrayList<>();
List<Number> numbers = integers;
```

使用 raw type（如 `List`）不是“更灵活的泛型”，而是放弃部分静态检查。污染值可能在写入时进入集合，直到远处读取并转换才出现 `ClassCastException`，因此异常堆栈位置不一定是污染源头。

## 2. 用通配符表达输入与输出方向

| 参数类型 | 能安全读取什么 | 能按类型安全写入什么 |
| --- | --- | --- |
| `List<T>` | T | T，前提是列表支持修改 |
| `List<? extends Number>` | Number | 除 null 外，没有可普遍保证安全的新值 |
| `List<? super Integer>` | Object | Integer 及其子类型的值 |
| `List<?>` | Object | 除 null 外，没有可普遍保证安全的新值 |

`extends` 表示某个未知的 Number 子类型，可能是 Integer，也可能是 Double，不能随便放入一个 Number。`super Integer` 表示某个 Integer 父类型，因此能放 Integer，但读出的元素可能是列表原先存储的其他 Object。

PECS 是针对方法的数据流而言：作为 T 的来源使用 `extends T`，作为 T 的去向使用 `super T`。同一个参数同时读写同一种类型时，直接用 T 往往更清楚。

```java
// 方法片段；需要显式导入 java.util.List。
static <T> void copy(List<? extends T> source, List<? super T> target) {
    for (T item : source) {
        target.add(item);
    }
}
```

这个签名允许把 Integer 来源复制到 Number 目标，同时拒绝相反方向。它没有保证目标可修改，也没有承诺 source 与 target 是同一个列表时可用。生产接口应另外定义别名、null、大小与异常行为。

`List<? extends Number>` 也不是不可修改列表：它仍可执行 clear、remove，或通过其他引用被改变。通配符限制的是当前引用的类型操作，不是对象的可变性。真正的不可修改与快照见 [[对象相等与不可变性]]。

## 3. 擦除发生了什么，又保留了什么

编译后，参数化类型擦除到其原始类型；类型变量擦除到最左边界，没有显式上界时通常是 Object。编译器在需要的读取位置插入类型转换，必要时生成桥接方法维持重写关系。依据：[JLS 17 §4.6 类型擦除](https://docs.oracle.com/javase/specs/jls/se17/html/jls-4.html#jls-4.6)。

例如 `class Box<T extends Number>` 中 T 的擦除是 Number，不能简单记为“所有泛型都变成 Object”。`ArrayList<String>` 与 `ArrayList<Integer>` 的对象可以拥有同一个运行时 Class，但字段、方法、父类型声明中的泛型签名仍可通过反射读取；“实例没有自动携带完整类型实参”和“类文件完全没有泛型信息”是不同说法。

```java
// 方法片段：子类实现同时需要保持父类型的调用契约。
interface Reader<T> { T read(); }
final class TextReader implements Reader<String> {
    @Override public String read() { return "正文"; }
}
```

实验通过 `Method.isBridge()` 检查编译器生成的方法。框架枚举方法时若忽略桥接/合成方法，可能把一个逻辑方法重复登记；具体筛选还要考虑继承、重写和注解查找策略。

## 4. 不能由擦除自动解决的事情

- 不能写 `new T()`：T 不提供可直接调用的具体构造器，可显式传入工厂或受约束的 Class。
- 不能创建 `new List<String>[10]`：数组运行时的元素类型检查无法检查 String 类型实参。`List<?>[]` 是不同情况，不应把两者混为一谈。
- 不能用 `instanceof List<String>` 验证任意对象；可以先检查 `List<?>`，再逐项校验。
- `handle(List<String>)` 与 `handle(List<Integer>)` 擦除后签名冲突，不能只靠类型实参重载。
- 泛型可变参数涉及数组，可能产生堆污染。`@SafeVarargs` 是作者对实现安全性的承诺，不能把不安全写入或数组逃逸变安全。

反序列化 `List<Order>` 时，单独传 `List.class` 不足以表达元素类型。类型令牌可保存声明信息，但不能代替校验：仍要检查元素字段、范围、权限和重复业务键。本文不指定某个 JSON 库的配置。

教学场景：SQL 对比工具需要把多种结果行交给报告模块。通用容器可以用 `Result<T>` 表达成功数据类型，但双库值的相等规则必须由比较策略显式定义，不能指望泛型统一 BigDecimal、时区或 null 的业务含义。
