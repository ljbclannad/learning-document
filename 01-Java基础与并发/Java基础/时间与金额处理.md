# 时间与金额处理

基线：Java 17。时间与金额都必须先定义业务语义，再选类型：一个数字不自带币种，一个日期时间字符串也不自带时区。以下费用计算与任务截止时间均为教学场景。

## 1. 金额从输入到结算

BigDecimal 表示十进制数，包含未缩放整数与 scale。用十进制文本构造可以保留输入的十进制值；`new BigDecimal(0.1)` 则精确接收已经是二进制浮点近似值的 double，并不会还原用户原先输入的字符串。`BigDecimal.valueOf(double)` 按 double 的字符串形式转换，但也无法追回更早浮点运算丢失的信息。

```java
// 方法体片段，需要导入 java.math.BigDecimal 和 java.math.RoundingMode。
BigDecimal unitPrice = new BigDecimal("0.10");
BigDecimal quantity = new BigDecimal("3");
BigDecimal amount = unitPrice.multiply(quantity).setScale(2, RoundingMode.HALF_UP);
```

例中选择两位小数和 HALF_UP 是教学规则，不是全部币种或合同的统一要求。应由业务约定币种、计量单位、中间精度、舍入方式、舍入时点和最大值。BigDecimal 不可变，计算后要使用返回值。[BigDecimal API](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/math/BigDecimal.html)。

精度 precision 是有效数字个数，scale 是小数位相关参数，两者不同。`MathContext(2)` 不表示“保留两位小数”。没有指定舍入策略时，`1 / 3` 这种无限十进制结果会使精确 divide 抛 ArithmeticException；`RoundingMode.UNNECESSARY` 可以用于“发生舍入就拒绝”的校验。

## 2. 数值相等、表示相等与累计规则

`new BigDecimal("1.0")` 与 `new BigDecimal("1.00")` 的 compareTo 为 0，而 equals 为 false。HashSet 按 equals/hashCode 去重，TreeSet 默认按自然顺序去重，因此两个集合的元素数可能不同。业务若认为它们是同一金额，应明确规范化尺度或封装相等规则，不能在不同集合间默默切换语义。

先逐行舍入再求和，与先求和最后舍入可能不同：两笔 `0.005` 按两位 HALF_UP 逐笔处理得到 `0.02`，汇总后处理得到 `0.01`。发票行与总账要使用一致的规则，并定义余差分配。

转换为最小单位整数时，先验证尺度与范围，再用 `longValueExact()` 等精确转换；普通 longValue 可能截去小数或溢出。BigDecimal 本身不会替数据库 DECIMAL 的精度/尺度做限制，序列化链路也不应中途转 double。

## 3. 时间类型保存的是什么

| 类型 | 适合表达 | 缺少的信息 |
| --- | --- | --- |
| LocalDate | 生日、业务日期 | 当天的具体时刻与时区 |
| LocalDateTime | 预约墙上时间 | 对应唯一时间点所需的时区/偏移 |
| Instant | 事件发生时间点、截止时间 | 面向用户的地区时间规则 |
| OffsetDateTime | 带 UTC 偏移的日期时间 | 完整地区时区规则 |
| ZonedDateTime | 地区日期时间与时区规则 | 仍需业务明确重叠/缺失时刻处理策略 |

“每天当地 9 点执行”与“每隔 24 小时执行”是不同需求。前者需要日期与地区时区规则，后者关注实际经过时长。不要把 LocalDateTime 直接当作 UTC，也不要把服务器默认时区当作用户时区。

数据库列类型、JDBC 映射、连接时区和 API 序列化应一起约定。本文不声称某种 Java 类型与所有数据库列类型天然无损映射；需要针对实际驱动进行往返验证，尤其检查精度与时区。

## 4. 夏令时与日期边界

地区时间可能存在零个、一个或两个有效偏移：春季跳时产生不存在的时间，秋季回拨产生重复时间。ZonedDateTime 的便捷转换有默认解析策略，并不是总会拒绝异常本地时间；业务要求严格时，可以先查询 `zone.getRules().getValidOffsets(local)` 并明确拒绝或选择。[ZonedDateTime 的缺口与重叠规则](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/time/ZonedDateTime.html)。

实验使用 Europe/Paris 在 2024 年春季切换的历史日期，观察 plusDays(1) 保留当地时刻，而 plusHours(24) 保留经过时长，两者结果不同。时区规则来自运行 JDK 的时区数据库；未来日程不能假定各地规则永不改变。

日期查询建议定义半开区间 `[start, end)`：查询某地区一天的数据时，分别把当天与次日的起点按地区规则转换成 Instant。不要用“23:59:59.999”代表所有存储精度下的当天末尾，也不要假定一天恒为 24 小时。

## 5. 截止时间如何可测

```java
// 完整方法片段，需要导入 java.time.Clock 和 java.time.Instant。
static boolean expired(Instant deadline, Clock clock) {
    return !clock.instant().isBefore(deadline);
}
```

本例约定到达 deadline 的瞬间已经过期。将 Clock 作为依赖传入，测试用固定时钟覆盖前一瞬、相等和后一瞬，避免依赖 sleep 或测试机当前时间。[Clock 官方用途](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/time/Clock.html)。

持久化业务时间点与测量单进程耗时也不同：耗时通常用 `System.nanoTime()` 的差值；其值不表示 UTC 时间，不能跨进程保存成截止日期。分布式租约还涉及权威时钟与偏差，不由本地 Clock 注入解决。
