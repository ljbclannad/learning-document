# 1. HashMap 原理与高并发注意点

`HashMap` 是最常用的 `Map` 实现，底层是 **数组 + 链表 / 红黑树** 的分桶结构。

## 1.1 核心结构

- 底层是一个 `Node[] table` 数组。
- 每个桶位可能是：
  - 空
  - 单个节点
  - 链表
  - 红黑树
- JDK 8 中，链表长度过长时会树化，避免极端冲突下查找退化成 O(n)。

## 1.2 为什么数组长度总是 2 的幂

- 因为这样可以用 `(n - 1) & hash` 代替取模来定位桶位，效率更高。
- 同时也更容易让哈希结果均匀分布到各个桶里。

## 1.3 put / get 主流程

### put

- 先算 key 的 hash
- 再定位桶位
- 桶为空：直接插入
- 桶不为空：
  - key 相同则覆盖 value
  - key 不同则挂到链表或红黑树里

### get

- 先算 hash 找桶
- 再在桶内按 `key.equals()` 查找

## 1.4 扩容机制

- 默认负载因子是 `0.75`
- 阈值 `threshold = capacity * loadFactor`
- 当元素个数超过阈值时扩容，容量通常翻倍
- 扩容本质是重新分布元素，属于 O(n) 操作

### 面试补充

- 负载因子不是越大越好
  - 太大：冲突增多，查询变慢
  - 太小：空间浪费，扩容更频繁

## 1.5 树化条件

- 链表长度 `>= 8` 才考虑树化
- 但如果数组长度 `< 64`，优先扩容而不是树化

原因是：

- 小数组下链表变长，往往是容量不够，不一定是哈希真的很差
- 这时先扩容通常比上红黑树更划算

## 1.6 高并发风险

`HashMap` **不是线程安全的**。

并发写场景下可能出现：

- 数据覆盖
- 结构异常
- 旧版本 JDK 里甚至可能形成环形链表

### 实战结论

- 单线程场景用 `HashMap`
- 多线程场景直接换 `ConcurrentHashMap`
- 不要指望靠“偶尔并发不高”硬顶过去

## 1.7 面试一句话

> HashMap 底层是数组加链表/红黑树的分桶结构，靠 hash 定位桶位，冲突时落到桶内处理；负载因子超过阈值会触发扩容，JDK 8 里链表过长会树化。但它本身不是线程安全的，并发写场景要换 ConcurrentHashMap。

# 2. ArrayList 扩容机制

`ArrayList` 本质上是一个可动态扩容的数组。

## 2.1 基本特点

- 随机访问快，按下标取值是 O(1)
- 尾部追加快，均摊复杂度低
- 中间插入和删除慢，因为要搬移元素

## 2.2 扩容时机

- 当元素个数超过当前数组容量时，会触发扩容
- 常见触发点是 `add()`、`addAll()`

## 2.3 扩容策略

JDK 里常见做法是按 `1.5` 倍扩容：

```java
newCapacity = oldCapacity + (oldCapacity >> 1);
```

这相当于：

- 不会像每次 +1 那样频繁扩容
- 也不会像每次翻倍那样太浪费空间

## 2.4 扩容成本

- 扩容时需要创建新数组
- 把老数组元素整体拷贝过去
- 所以单次扩容是 O(n)

### 实战建议

- 已知数据量时，尽量提前指定容量：

```java
new ArrayList<>(expectedSize)
```

这样可以减少多次扩容带来的拷贝成本。

## 2.5 常见误区

- `ArrayList` 不是链表
- “尾插永远 O(1)” 不准确
  - 不扩容时接近 O(1)
  - 扩容时会触发 O(n) 拷贝

## 2.6 面试一句话

> ArrayList 底层是数组，随机访问快，尾插通常快，但容量不够时会按 1.5 倍扩容并整体拷贝元素，所以如果已知数据规模，最好提前设容量。

# 3. CopyOnWriteArrayList vs Collections.synchronizedList

这两个都能让 `List` 在多线程下安全使用，但思路完全不同。

## 3.1 实现机制

### CopyOnWriteArrayList

- 写时复制
- 每次修改都会复制一份新数组
- 读操作基本无锁

### Collections.synchronizedList

- 本质上是给普通 `List` 包一层全局锁
- 读写都要竞争同一把锁

## 3.2 性能特点

### CopyOnWriteArrayList

- 读快
- 迭代稳定
- 写很贵，修改是 O(n) 拷贝

### Collections.synchronizedList

- 读写都串行化
- 性能取决于锁竞争程度

## 3.3 迭代器行为

### CopyOnWriteArrayList

- 迭代器基于快照
- 遍历时不会抛 `ConcurrentModificationException`
- 但看到的可能是旧数据

### Collections.synchronizedList

- 迭代时要手动加锁：

```java
synchronized (list) {
    Iterator<?> it = list.iterator();
    while (it.hasNext()) {
        ...
    }
}
```

- 否则仍可能出并发问题

## 3.4 适用场景

### CopyOnWriteArrayList 适合

- 读多写少
- 元素规模可控
- 需要稳定遍历快照

典型例子：

- 监听器列表
- 配置快照
- 白名单缓存

### Collections.synchronizedList 适合

- 并发量不高
- 读写都比较均衡
- 只是想快速给已有 List 加线程安全包装

## 3.5 实战选择

- 读 95% 以上、写很少：优先 `CopyOnWriteArrayList`
- 写频繁：不建议用 `CopyOnWriteArrayList`
- 如果本质是队列语义，直接考虑：
  - `ConcurrentLinkedQueue`
  - `LinkedBlockingQueue`
  - `Deque`

## 3.6 面试一句话

> CopyOnWriteArrayList 的核心是写时复制，适合读多写少；Collections.synchronizedList 的核心是一把全局锁，适合简单包装已有 List，但迭代时要自己额外同步。

# 4. ConcurrentHashMap

`ConcurrentHashMap` 是高并发场景下最常用的线程安全 `Map`。

> [!abstract] 本专题是 `ConcurrentHashMap` 的唯一主入口
> 本文维护其实现、使用边界与容器选择；锁、线程池、JMM 与异步编排请回到 [[01-Java基础与并发/并发编程/并发基础]]，避免在多份笔记中复制同一套容器原理。

## 4.1 核心定位

- 目标不是“绝对无锁”
- 而是：**在保证线程安全的前提下，尽量降低锁粒度，提高并发性能**

## 4.2 JDK 7 vs JDK 8

### JDK 7

- `Segment + HashEntry`
- 本质是分段锁

### JDK 8

- `Node[] + CAS + synchronized`
- 去掉了 `Segment`
- 把锁粒度降到桶级别

### 面试重点

JDK 8 并不是“无限并发”，它的并发能力仍受以下因素影响：

- 桶分布是否均匀
- 热点 key 是否集中
- 是否频繁扩容

## 4.3 读写机制

### get 为什么基本无锁

- 依赖 `volatile` 保证可见性
- `table`、节点引用等关键字段对其他线程可见
- 即使扩容过程中，读到 `ForwardingNode` 也能沿新表继续查

### put 为什么不是整表锁

- 桶空：优先 CAS 插入
- 桶冲突：只锁当前桶头节点
- 所以并发线程只要打到不同桶，通常可以并行执行

## 4.4 为什么 JDK 8 用 synchronized 而不是 ReentrantLock

- 锁粒度已经很细，只锁桶头节点
- 如果每个桶额外维护一个 `ReentrantLock`，成本太高
- `synchronized` 在 JDK 8 后优化已经比较成熟

## 4.5 扩容机制

- 扩容不是单线程搬整张表
- 多个线程可以协作迁移
- 已迁移的桶会标记成 `ForwardingNode`
- 后续线程看到这个标记，会去新表查或顺手协助迁移

## 4.6 树化机制

- 链表长度 `>= 8`，并且数组长度 `>= 64` 时才树化
- 如果数组还小，优先扩容而不是树化

## 4.7 为什么不允许 null

- 因为 `get(key)` 返回 `null` 时，没法区分：
  - key 不存在
  - value 本身就是 null

在并发场景下，`containsKey()` 再 `get()` 之间也可能被别的线程修改，所以直接禁止 `null key / null value`。

## 4.8 弱一致性

### size 为什么不是强一致

- 高并发下不可能为了精确 size 锁整张表
- 所以用的是近似计数思路
- 适合监控统计，不适合强一致业务判断

### 迭代器为什么弱一致

- 不会像 `HashMap` 一样 fail-fast
- 遍历时可能看不到某些最新修改
- 但这样避免了遍历时锁住整张表

## 4.9 computeIfAbsent 的使用边界

- 适合懒加载
- 比 `putIfAbsent` 更少无效对象创建

但要注意：

- mappingFunction 不要太重
- 不要递归改同一个 map
- 否则容易拖长临界区

## 4.10 和 HashMap / Hashtable 的区别

| 对比项 | HashMap | Hashtable | ConcurrentHashMap |
| --- | --- | --- | --- |
| 线程安全 | 否 | 是 | 是 |
| 锁粒度 | 无 | 整表锁 | 桶级别 |
| 读性能 | 高 | 低 | 高 |
| null 支持 | 允许 | 不允许 | 不允许 |
| 迭代器 | fail-fast | 枚举/较老语义 | 弱一致 |

## 4.11 适用场景

适合：

- 单机 JVM 内高并发缓存
- 本地状态表
- 懒加载映射

不适合：

- 分布式共享状态
- 强一致扣减
- 跨 key 的复杂事务联动

## 4.12 面试一句话

> ConcurrentHashMap 在 JDK 8 里通过 Node 数组、CAS、synchronized 和 volatile 实现线程安全：读操作基本无锁，写操作只锁冲突桶，扩容还能多线程协作完成，所以比 Hashtable 并发性能高得多，但它只保证单次容器操作安全，不保证复合业务原子性。

# 5. 布隆过滤器

布隆过滤器（Bloom Filter）是一种基于哈希的**概率型数据结构**，常用于“快速判断某个元素大概率在不在集合里”。

## 5.1 核心特点

- 可能误判存在（假阳性）
- 但不会误判不存在（无假阴性）

也就是说：

- 返回“不存在”时，可以相信
- 返回“存在”时，只能说“可能存在”

## 5.2 工作原理

1. 准备一个位数组（bit array）
2. 准备多个哈希函数
3. 插入元素时：
   - 对元素做多次 hash
   - 把对应位置都置为 1
4. 查询元素时：
   - 再做多次 hash
   - 只要有一个位置是 0，就一定不存在
   - 如果全是 1，就可能存在

## 5.3 为什么会有误判

- 因为多个元素可能把同一批 bit 位打成 1
- 所以某个没插入过的元素，查询时也可能碰巧命中一组都为 1 的位置

## 5.4 优缺点

### 优点

- 占用空间小
- 查询快，通常 O(k)
- 适合大数据量过滤

### 缺点

- 有假阳性
- 普通布隆过滤器不支持删除
- 参数设置不合理时误判率会上升

## 5.5 常见应用场景

### 1. 缓存穿透防护

- 先用布隆过滤器判断 key 是否可能存在
- 明显不存在的请求直接拦掉
- 避免每次都打到数据库

### 2. 大规模去重

- 爬虫 URL 去重
- 日志去重
- 黑名单过滤

### 3. 风控和黑名单

- 恶意 IP
- 垃圾邮箱
- 风险用户标识

## 5.6 面试一句话

> 布隆过滤器是一种用空间换时间的概率型数据结构，适合快速判断元素是否可能存在。它有假阳性但没有假阴性，最典型的应用就是缓存穿透防护和大规模去重。

# 6. Redisson 中的布隆过滤器

如果项目里 Redis 已经是基础设施，Java 侧又在用 Redisson，那么布隆过滤器通常会直接用 `RBloomFilter`。

## 6.1 为什么用 Redisson

- 不用自己手写位图和多哈希逻辑
- 可以直接复用 Redis 做分布式共享
- API 简单，适合业务快速落地

## 6.2 基本使用

```java
import org.redisson.Redisson;
import org.redisson.api.RBloomFilter;
import org.redisson.api.RedissonClient;
import org.redisson.config.Config;

public class RedissonBloomFilterExample {
    public static void main(String[] args) {
        Config config = new Config();
        config.useSingleServer().setAddress("redis://127.0.0.1:6379");
        RedissonClient redisson = Redisson.create(config);

        RBloomFilter<String> bloomFilter = redisson.getBloomFilter("user:bloomFilter");

        // 预计插入 100000 个元素，误判率 1%
        bloomFilter.tryInit(100000L, 0.01);

        bloomFilter.add("user1");
        bloomFilter.add("user2");

        System.out.println(bloomFilter.contains("user1")); // true
        System.out.println(bloomFilter.contains("user3")); // false 或极小概率 true

        redisson.shutdown();
    }
}
```

## 6.3 两个最重要的参数

```java
bloomFilter.tryInit(expectedInsertions, falseProbability);
```

### expectedInsertions

- 预计插入元素个数
- 配太小：后期误判率会明显上升

### falseProbability

- 可接受的误判率
- 配得越低，所需空间越大

## 6.4 在 Redis 里的本质

- 底层还是位数组思想
- Redis 里并不会存真实元素集合
- 存的是这些元素经过多次 hash 后打到 bit 位上的结果

## 6.5 常见业务场景

### 缓存穿透

```java
String userKey = "user:12345";

if (!bloomFilter.contains(userKey)) {
    return;
}

// 可能存在，再查 Redis / DB
```

### 防止重复请求

- 比如短信验证码发送前先做一层存在性过滤
- 但这里更适合做前置快速拦截，不能代替真正幂等控制

### 黑名单过滤

- 恶意 IP
- 风险手机号
- 垃圾邮箱

## 6.6 使用边界

- 布隆过滤器适合回答“**一定不存在吗**”
- 不适合直接回答“**一定存在吗**”
- 所以它更适合作为前置过滤层，而不是最终真相源

### 面试补充

- 防缓存穿透时，布隆过滤器只能拦大部分无效 key
- 真正的最终兜底仍然是：
  - 合理 TTL
  - 空值缓存
  - 限流
  - 数据库索引

## 6.7 布隆过滤器 vs HashSet / DB

| 方案 | 内存 | 查询速度 | 是否误判 | 是否适合超大规模 |
| --- | --- | --- | --- | --- |
| HashSet | 高 | 快 | 无 | 一般 |
| 布隆过滤器 | 低 | 快 | 有假阳性 | 适合 |
| MySQL / 索引 | 更高 | 相对慢 | 无 | 不适合做高频前置过滤 |

## 6.8 面试一句话

> Redisson 的 RBloomFilter 本质上是把布隆过滤器的位数组和哈希逻辑封装起来，并借助 Redis 做分布式共享。它最典型的用途是缓存穿透防护和大规模黑名单过滤，但只能用来判断“一定不存在”或“可能存在”，不能代替真正的数据源和幂等控制。
