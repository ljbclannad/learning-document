# 第一组：线程池与并发执行基础

## 1. 互联网医疗项目里，线程池最常见的使用场景有哪些？
- 聚合查询、异步通知、批处理、定时任务、外部系统调用分别适合什么线程池？
	- 聚合查询：
		- 典型场景：患者详情页、挂号订单详情页、门诊结算详情页、健康评估结果页，需要并发查询 MySQL、Redis、标签服务、报告服务、支付状态、医保结算状态、电子票据状态。
		- 适合的线程池：**IO 线程池**，比如 `ioExecutor`，因为本质上是 DB/HTTP/RPC 这类阻塞 IO。
		- 推荐做法：`CompletableFuture + 自定义 ioExecutor + 超时 + 降级`。
		- 不建议：用 `commonPool` 直接跑阻塞 IO，也不建议无限并发开子任务把下游放大打穿。
	- 异步通知：
		- 典型场景：支付成功后发短信、发公众号模板消息、发站内信、记录审计日志、刷一些非关键缓存。  
		- 适合的线程池：**业务异步线程池**，比如 `bizExecutor`。
		- 适合线程池的前提：任务轻量、允许失败重试简单处理、服务重启时偶发丢失不是严重事故。
		- 更适合 MQ 的情况：支付成功后同步 HIS、生成电子票据、更新医保结算主状态、触发履约或随访任务，这些属于可靠异步，不能只靠线程池硬扛。
    - 批处理：
        - 典型场景：日终对账、失败补偿、电子票据补开、医保结算结果补拉、报表导出、批量同步患者数据、批量生成随访计划。
        - 适合的线程池：batchExecutor，也就是独立批处理线程池。
        - 关键点：分页扫描、分批投递、限流执行、幂等处理、失败重试。
        - 不建议：和在线查询、支付通知共用线程池，否则后台任务会把在线流量一起拖进坑里。
    - 定时任务：
        - 典型场景：定时关闭未支付订单、定时拉取医保结算状态、定时补偿支付结果、定时刷新本地规则缓存。
        - 适合的线程池：通常是 scheduledExecutor + 业务执行线程池 两层结构。
        - 推荐模式：scheduledExecutor 只负责“触发”和“扫描”，真正的执行投递到 bizExecutor 或 batchExecutor。
        - 不建议：在 @Scheduled 方法里直接做重查询、重循环、重远程调用，否则一个慢任务能把所有定时任务一起拖延。
    - 外部系统调用：
        - 典型下游：HIS、LIS、PACS、医保平台、电子票据平台、第三方支付网关、短信/消息平台。
        - 适合的线程池：按下游系统隔离的线程池，例如 hisExecutor、insuranceExecutor、invoiceExecutor、paymentExecutor，最差也要按“核心外呼”和“非核心外呼”分池。
        - 原因：这些系统延迟、稳定性、QPS 承载能力差异极大，一个系统慢不能拖垮另外一个系统调用链。
        - 本质上就是舱壁隔离（Bulkhead）。
- 哪些场景适合线程池，哪些更适合 MQ？
    - 适合线程池的场景：本地并发查询、本地轻量异步、线程池隔离下的远程调用、后台批量执行、定时触发后的任务分发。
    - 更适合 MQ 的场景：支付成功后的可靠通知、医保结算状态流转、电子票据生成、订单状态异步推进、跨服务事件传播、需要削峰填谷和失败重试的任务。
- 为什么不能“一个线程池打天下”？
    - 任务类型不同：聚合查询是阻塞 IO，风控/AI 评分可能是 CPU 密集，通知类是轻异步，批处理是长耗时任务。若共用同一资源池，任一类任务变慢都可能挤占其他任务的执行机会。
    - 下游稳定性不同：HIS 和医保平台经常高延迟波动，短信平台一般较轻，支付网关又是另一套故障模型，放一个池里等于绑在同一条船上。
    - 业务优先级不同：挂号、支付、医保结算属于核心链路，短信通知、报表导出属于非核心链路，资源必须隔离。
    - 故障传播太快：一个慢接口把线程占满后，后续请求开始排队，队列越积越多，RT 暴涨，超时增多，重试增多，最后形成线程池级联雪崩。

## 2. 聚合查询接口为什么适合用 `CompletableFuture + 自定义线程池`？
- 什么样的子任务适合并发？
    - 彼此独立，没有强前后依赖
        - 例如：患者详情页里同时查问卷、最新体重、用户标签、评估报告，这些通常互不依赖，就很适合并发。
        - 如果 B 必须依赖 A 的结果，比如先查订单主记录拿到 recordId，再查支付单或处方列表，那就不适合一开始就并发，而应该用 thenCompose 做“先后编排”。
    - 以阻塞 IO 为主，而不是 CPU 重计算
        - 聚合查询大多是：
            - 查 MySQL
            - 查 Redis
            - 调 HTTP/RPC
            - 调 HIS、医保、票据平台
        - 这些任务的主要耗时在“等”，不是“算”，所以并发收益很明显。
        - 如果是大 JSON 解析、报表汇总、复杂规则计算，那更偏 CPU 密集，就不该简单往一个 IO 池里堆。
    - 需要超时控制和降级处理
        - 例如：业务允许时，可选医保状态查询超时 500ms 后返回“未知”；关键 HIS 主状态查询超时则返回明确错误或经过业务确认的缓存结果，不能伪造正常状态。
        - 这要求：
            - 超时时间要根据 SLA 拆分
            - 超时后要快速失败，而不是无限等待
            - 仅对业务明确允许的失败局部降级；关键字段失败及不允许降级的异常应明确传播
            - 是否重试取决于幂等性、剩余总预算和故障类型；仅对允许恢复的失败做有界重试，避免超时后底层调用仍在执行时重复施压
    - 单个任务失败时，接口可以局部降级
        - 比如标签属于可选字段，且其提交拒绝或超时被业务允许降级时，患者详情页仍可展示主体信息，标签返回空列表；权限、参数和程序错误不能因此被吞掉。
        - 可用 CompletableFuture 为子任务设置超时并按异常类型选择 fallback；同步提交拒绝需要在提交处捕获。第 8 节案例只对可选字段的提交拒绝和超时降级，其他异常继续失败。
    - 子任务数量有限且边界明确
        - 常见是 3~8 个子任务并发。
        - 如果一个接口里上来就并发 20 个外呼，那就不是优化，是在给下游做压力测试，顺便把自己也拖下水。
- 并发任务过多会带来什么问题？
    - 放大下游压力
        - 同一请求的 4 个独立调用由串行改为并行，最多可同时发起 4 个调用；这会改变瞬时占用和突发形态，但在请求率、调用次数与重试策略不变时，不会自动增加稳态总调用率。
        - 教学假设：接口稳定在 200 请求/秒，每请求恰好调用 4 个下游各一次，则总调用率为 200 × 4 = 800 次/秒，每个下游为 200 次/秒。800 的单位是调用/秒，不是并发数。
        - 若各调用平均在途时间均为 200ms，则每个下游平均在途调用约为 200 × 0.2 = 40 个，四个下游合计约 160 个；需明确这里是否包含客户端排队。重试、流量上涨或耗时增加都会改变结果，不能从 800 次/秒直接推导线程数或连接数。
    - 排队时间变长，RT 暴涨
        - 原来一个请求串行查 4 个下游、每个平均 200ms，理想耗时约为 800ms；改为并发后，理想耗时接近最慢下游的 200ms 加调度开销。
        - 但并发会在更短时间内占用更多线程、连接和下游配额；当这些资源不足时，队列增长和尾延迟会抵消并行收益，单机 QPS 反而可能下降。
        - 因此要用有界线程池、下游隔离、超时和降级限制并发度；否则排队、超时与重试会形成线程池级联雪崩。
    - 数据库连接池被打满
        - 如果你线程池开得很大，但 MySQL 连接池只有 30 个连接，那么大量并发子任务其实只是在“等连接”，系统看起来很忙，实际上有效吞吐没涨。

## 3. 为什么 `CompletableFuture` 默认的 `commonPool` 不适合互联网医疗里的阻塞 I/O？
CompletableFuture 默认的 commonPool 不适合互联网医疗里的阻塞 I/O，因为它底层是 ForkJoinPool，设计目标是“少量线程跑短小、可拆分、CPU 密集型任务”，而互联网医疗里的大量场景是 DB 查询、Redis 访问、HTTP/RPC 调用、HIS/医保/电子票据平台调用，这些任务的主要耗时不是“计算”，而是“等待”。把阻塞 I/O 丢进 commonPool，本质上是在用一个线程数偏少、全局共享、擅长计算不擅长等待的池子去承载高延迟外呼，结果非常容易出级联故障。
- `commonPool` 被阻塞会发生什么级联故障？
    - 一旦 commonPool 被阻塞，最先发生的是 任务排队：比如患者详情页里并发查问卷、标签、报告、支付状态、医保状态，其中几个子任务调用慢下游卡住，commonPool 线程被占满，后续异步任务只能排队。接着出现 回调延迟：thenApplyAsync、thenComposeAsync、allOf 后续阶段也要拿线程执行，但池子里没空闲 worker，于是整条异步链都慢下来。再往后就是 业务互相拖累：因为 commonPool 是 JVM 级共享池，不是你这个接口独占，别的模块如果也用了默认 CompletableFuture，会一起被拖慢。最后形成 超时—重试—更拥堵 的正反馈：接口超时后上游重试，任务更多，排队更长，RT 更高，线程池更满，整个系统开始雪崩。
- 为什么它更适合 CPU 密集型而不是 DB/HTTP 阻塞调用？
    - commonPool 更适合 CPU 密集型任务，原因有三个：第一，它的并行度通常接近 CPU 核数，适合让有限线程尽量把 CPU 吃满；第二，ForkJoinPool 的强项是 work-stealing，也就是线程把可计算任务拆分后互相“偷活干”，这对纯计算很有效；第三，CPU 任务一般执行时间短，线程不会长时间挂住。但 DB/HTTP/HIS/医保这种阻塞 I/O 恰好相反：线程大部分时间在等网络、等连接、等远端响应，线程一旦阻塞，就既不能继续跑别的任务，也谈不上什么 work-stealing 优势，少量 worker 很快就会被占死。
- 如果用了 `commonPool`，线上会出现什么现象？
    - 如果线上错误地用了 commonPool 跑阻塞 I/O，常见现象是：接口 RT 在高峰期突然升高，而且不是单个接口慢，而是多个“看起来没关系”的异步接口一起变慢；线程池监控里 commonPool worker 长时间活跃但吞吐不升，很多任务处于等待状态；CompletableFuture 的 join/get 超时明显增多；日志里会看到下游慢调用增多后，不只是聚合查询慢，连支付状态刷新、标签服务调用、票据状态查询这类功能也一起抖动；更隐蔽一点的是，CPU 可能并不高，但接口照样卡，因为瓶颈不是算力，而是 共享线程池被阻塞等待占满。

## 4. 在线程池和 `CompletableFuture` 中，TraceId、租户和安全上下文如何传递？

- 为什么会丢上下文？
  - 请求线程里的 `MDC`、租户、机构、操作人等信息通常存放在 `ThreadLocal`；任务一旦提交到线程池或切换到 `CompletableFuture` 的异步阶段，执行线程就变了，新的线程默认没有这些值。
  - `InheritableThreadLocal` 只在线程创建时复制一次，对已经复用的线程池工作线程并不可靠；它还可能把上一请求的上下文带到下一请求。
- 医疗场景里哪些上下文值得传递？
  - **TraceId / 请求 ID**：用于串联患者详情、HIS、医保、票据等调用日志。
  - **租户、机构、数据域**：用于路由和审计；必须在任务入口重新校验授权，不能因为复制了上下文就绕过权限校验。
  - **安全上下文**：使用 Spring Security 时优先使用框架提供的 `DelegatingSecurityContext...` 包装器，而不是自己复制内部对象。
  - 不要把患者病历、大对象或数据库连接放进上下文；上下文应小、可序列化/可审计，并有明确生命周期。
- 正确模式是什么？
  - 在**提交任务时捕获**必要上下文，在**执行任务前设置**，并在 `finally` 中恢复或清理。
  - 将上下文包装集中在 `TaskDecorator`、自定义 `Executor` 或统一的 `CompletableFuture` 工具方法中；业务代码不要到处手动 `MDC.put/remove`。

```java
// Spring TaskDecorator：示意，实际还应纳入租户/机构上下文的 capture 与 restore
TaskDecorator traceDecorator = task -> {
    Map<String, String> capturedMdc = MDC.getCopyOfContextMap();
    return () -> {
        Map<String, String> previousMdc = MDC.getCopyOfContextMap();
        try {
            if (capturedMdc == null) {
                MDC.clear();
            } else {
                MDC.setContextMap(capturedMdc);
            }
            task.run();
        } finally {
            if (previousMdc == null) {
                MDC.clear();
            } else {
                MDC.setContextMap(previousMdc);
            }
        }
    };
};
```

- 如何验证没有串上下文？
  - 并发提交两个不同 TraceId、租户和操作人的任务，断言日志与审计记录始终匹配各自请求。
  - 在线程池复用、异常返回、超时取消三条路径都验证 `finally` 清理；只测正常路径无法证明安全。

## 5. 线程池参数该怎么定？你如何结合医疗业务做容量估算？
- CPU 密集和 I/O 密集线程池怎么估算？
    - CPU 密集任务先看可用核数和分配给本池的 CPU 预算。核数或核数加一只适合作为接近独占计算资源时的经验起点；混合服务还要为请求线程、其他池和 GC 留出预算。
    - 阻塞 I/O 任务需要区分 CPU 时间、阻塞时间及下游限制。不能仅按核数的固定倍数决定线程数；候选值还需与到达率、工作线程实际占用时间、连接配额和延迟目标共同校验。
- 为什么线程池大小不能脱离数据库连接池单独谈？
    - 若 64 个工作线程同时执行各需独占一个连接的任务，而分配给它们的连接只有 20 个，则至多 20 个任务持有连接，其余可能等待；这以所有线程同时进入取连接阶段、没有其他约束为前提。混合任务不能简单断言其余 44 个线程始终都在等数据库。
    - 同一请求执行多条 SQL，不代表同时占多个连接：单事务中顺序执行通常复用连接，持有时间还可能包含应用处理或其他等待；并行查询或独立事务则可能增加同时持有的连接数。应按实际连接获取和归还边界测量。
- 如何根据 QPS、RT、P99 推导线程池容量？
    - 稳定负载、同一统计窗口和边界下，平均在途量可用 `L ≈ λ × W` 估算，其中 λ 是每秒到达率，W 是该边界内的平均停留时间（秒）。接口 200 请求/秒、平均 RT 300ms，对应平均约 60 个在途请求，包括边界内的执行和等待；它不是线程池、数据库连接池各自的最低容量。
    - 每种资源分别计算。例如每请求恰好获取一次数据库连接，平均持有 50ms，则这部分流量的平均连接占用约为 `200 × 0.05 = 10`；若每请求发起两次 HIS 调用、每次平均在途 200ms，则 HIS 平均在途量约为 `200 × 2 × 0.2 = 80`。这些都是教学假设，不是项目实测；连接占用时间不能用接口总 RT 或仅 SQL 执行时间替代。
    - P95/P99 用于观察尾延迟和设计压测场景，不能把平均值公式中的 W 换成 P99 就声称得到并发分位数或严格上界。P99 为 800ms 时，`200 × 0.8 = 160` 只可作为“若平均停留时间恶化到 800ms”的假设场景，不能由 P99 单独推导；超过 P99 的请求仍存在，排队和重试也可能继续放大占用。
    - 先按资源得到平均占用基线，再依据突发、耗时分布和可接受的排队时间留余量，结合数据库容量及下游配额形成候选配置。线程池、连接池的最终数值必须经代表性负载验证，不能从上述示例直接宣布 `ioExecutor=64` 或连接数 40 合理。持续过载下应限流、隔离或扩容，扩大队列不增加稳态处理能力。
    - 定向验证时分别采集接口到达率与平均 RT、各下游调用率与耗时、连接持有时间、工作线程活跃数和排队时间；确认单实例与集群口径一致。再覆盖突发及慢下游场景，检查 P99、拒绝率和超时后残留调用。本轮只核对量纲、算例及主文一致性，未执行压测。

原理与参数边界统一参见 [[01-Java基础与并发/并发编程/Java并发编程|Java 并发编程]] 第 12.1、12.2 节；此处保留医疗聚合查询的应用口径。

## 6. 拒绝策略怎么选？`AbortPolicy` 和 `CallerRunsPolicy` 在医疗业务里分别适合什么场景？
- AbortPolicy：
    - AbortPolicy 的行为是：线程池满了以后，直接抛 RejectedExecutionException。它的优点是明确、可观测、可告警、不会悄悄吞任务。在医疗业务里，凡是涉及 状态推进、资金变更、关键数据落库、可靠异步触发 的任务，我都倾向优先用 AbortPolicy，因为这类场景宁可失败暴露出来，也不能默默丢掉。典型包括：支付成功后的核心状态更新、医保结算结果入库、电子票据生成主流程、就诊订单状态推进、处方履约任务创建、补偿任务正式投递。这些业务一旦任务被静默丢弃，后果通常不是“少发一条通知”，而是 订单状态错乱、票据缺失、医保状态不一致、后续补偿链路断裂。所以这类任务如果线程池打满，我更希望它立刻报错、立刻进入监控、立刻触发降级或补偿，而不是假装执行过。
- CallerRunsPolicy:
    - CallerRunsPolicy 的行为是：线程池满了以后，不再把任务交给线程池，而是由提交任务的那个线程自己执行。它最大的价值不是“兜底不丢任务”，而是天然形成反压（backpressure）。因为调用方线程被拉去执行任务之后，提交速度自然就慢下来了，上游流量就会被压住。这个策略在医疗业务里特别适合 查询类、聚合类、非核心本地异步 场景。比如患者详情页聚合查询、挂号详情页并发查支付和票据状态、普通标签服务刷新、低风险的站内信或短信发送触发、某些报表组装任务。这些场景的特点是：任务虽然重要，但允许调用方变慢，而且“慢一点”通常比“直接丢”更可接受。尤其是在聚合查询里，CallerRunsPolicy 能让请求线程自己去干活，相当于告诉上游：系统忙了，你别再疯狂塞新活了。这种策略很像一种朴素但有效的限流器。
    - 例外是执行器已经 `shutdown`：`CallerRunsPolicy` 不会再由调用线程执行任务，而是直接丢弃。因此关键任务仍要检查提交是否成功，并以持久化任务、MQ 或补偿机制兜底；不能把它当作可靠投递方案。
- 哪些业务必须快速失败？
    - 在互联网医疗里，必须快速失败的业务一般有这几个特征：第一，失败必须被感知，比如支付状态更新失败、医保结算回写失败、票据生成任务投递失败；第二，不能靠调用方无限等待，比如核心交易链路上的异步后处理，如果线程池满了，不应该让上游一直卡着；第三，后续可以走补偿、重试、MQ、人工兜底，也就是说失败要暴露，后面才能接得住。换句话说，凡是“失败之后还有修复路径”的关键链路，更应该快速失败，而不是吞掉。因为你只有知道它失败了，才能重试、补偿、对账；如果它被静默扔了，系统表面风平浪静，实际上数据已经悄悄不一致了，那才是最阴的事故。
- 哪些业务适合通过 `CallerRunsPolicy` 做反压？
    - 适合 CallerRunsPolicy 的业务通常具备三个条件：第一，任务是本地可完成的，不会导致调用线程长时间陷入不可控阻塞；第二，调用方本身允许变慢，比如查询请求、普通异步后处理、非核心日志埋点；第三，系统希望通过“让上游变慢”来自动降速，而不是直接丢任务或快速失败。举例来说，患者详情页聚合查询、门诊详情页多个子任务并发、普通规则计算、非核心通知、低优先级本地审计，都可以用 CallerRunsPolicy。它不太适合那种“调用线程本来就是核心工作线程，而且一旦被拖住会影响更大范围吞吐”的场景，比如 Tomcat/Netty 主线程里做非常重的异步 fallback，就要谨慎，因为反压不能反成“把入口线程都压死”。
- 为什么 `DiscardPolicy` 一般不适合核心医疗业务？
    - DiscardPolicy 的问题不在于它丢任务，而在于它静默丢任务。也就是说，线程池满了以后，任务没执行、没报错、没告警，系统表面上一片安静，实际上关键动作已经消失了。这在核心医疗业务里几乎是不能接受的。因为核心医疗业务最怕的不是失败，而是失败了你还不知道。比如支付成功后票据生成任务被丢了、医保回写任务被丢了、订单状态推进任务被丢了、补偿任务被丢了，如果系统没有任何报错，你要等用户投诉“我为什么没票据”“为什么订单还是处理中”“为什么医保状态没更新”，才会发现问题。到那时候，已经不是一个线程池小问题，而是 一致性事故。所以 DiscardPolicy 一般只适合非常边缘、允许完全丢失且不需要追踪的场景，比如极低价值的调试日志、非关键统计埋点，而且即便如此，我在生产上也很少推荐，因为它太容易把问题藏起来。

## 7. 任务取消与服务优雅停机如何设计？

- `interrupt`、`Future.cancel(true)` 和 `shutdownNow()` 都只是**请求任务停止**，不会自动回滚支付、医保回写或票据生成等已产生的外部副作用。任务必须在可中断点退出，并通过幂等、状态机、对账或补偿保证最终正确。
- 一个服务的停机顺序通常是：
  1. 从负载均衡摘流或将实例标为不可接流量；
  2. 停止新的定时触发和新的本地任务提交；
  3. 对非关键任务选择取消或快速返回，对关键任务记录可恢复状态并转交 MQ/补偿表；
  4. 调用线程池 `shutdown()`，在有限时间内等待；超时后才 `shutdownNow()`；
  5. 关闭连接池和客户端，并由下一实例或补偿任务接续未完成工作。

```java
void shutdownExecutor(ExecutorService executor, Duration timeout) {
    executor.shutdown(); // 不接收新任务，允许已提交任务收尾
    try {
        if (!executor.awaitTermination(timeout.toMillis(), TimeUnit.MILLISECONDS)) {
            executor.shutdownNow(); // 尝试 interrupt，任务仍需自行响应
        }
    } catch (InterruptedException e) {
        executor.shutdownNow();
        Thread.currentThread().interrupt();
    }
}
```

- 医疗业务的取舍：
  - 患者详情页的并发查询可随请求超时取消并返回降级字段；不应为了等一个标签服务而阻塞停机。
  - 支付结果入库、医保结算回写、电子票据生成等关键动作不能只依赖本地线程池“跑完”；必须持久化事件或任务状态，支持幂等重试与对账。
  - 定时补偿任务停机前应停止继续扫描并记录游标/租约，避免旧实例和新实例重复推进同一任务。
- 验证方式：压测期间触发实例下线，检查请求拒绝是否可控、线程池是否在超时内退出、关键任务是否能被补偿，以及 TraceId/审计日志是否完整。

## 8. 患者详情聚合：从并行到可控降级的最小案例

患者基础信息、标签、最近报告和医保状态可以并行查询；其中医保状态是可选字段，不能因为它慢而拖垮整个详情页。这个案例的目标不是“尽可能多地并行”，而是在请求预算内完成关键字段，并将非关键依赖隔离、超时和降级。

```java
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.CompletionException;
import java.util.concurrent.Executor;
import java.util.concurrent.RejectedExecutionException;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.TimeoutException;
import java.util.function.Supplier;

// 方法片段：放在业务类中；本例使用 JDK 17。
// 执行器应有界，采用 AbortPolicy 等明确抛出拒绝异常的策略。
private static <T> CompletableFuture<T> optionalAsync(
        Supplier<T> supplier, Executor ioExecutor, long timeoutMs, T fallback) {
    if (timeoutMs <= 0) {
        throw new IllegalArgumentException("超时预算必须为正数");
    }
    final CompletableFuture<T> task;
    try {
        task = CompletableFuture.supplyAsync(supplier, ioExecutor);
    } catch (RejectedExecutionException rejected) {
        // 提交尚未返回 Future，必须在调用线程处理拒绝。
        return CompletableFuture.completedFuture(fallback);
    }
    return task.orTimeout(timeoutMs, TimeUnit.MILLISECONDS)
            .exceptionally(ex -> {
                Throwable cause = ex;
                while (cause instanceof CompletionException && cause.getCause() != null) {
                    cause = cause.getCause();
                }
                if (cause instanceof TimeoutException) {
                    return fallback;
                }
                // 权限、参数及程序错误继续失败，不伪装成空数据。
                throw new CompletionException(cause);
            });
}

```

以下为业务方法内的编排片段，客户端和领域类型由实际项目提供；本例仅对可选字段的提交拒绝和超时降级，其他异常使聚合结果失败。

```java
// 基础档案是关键字段：失败后由接口层返回明确错误或缓存兜底，而非静默伪造空档案。
CompletableFuture<PatientProfile> profile = CompletableFuture
        .supplyAsync(() -> patientClient.getProfile(patientId), ioExecutor)
        .orTimeout(300, TimeUnit.MILLISECONDS);
CompletableFuture<List<Tag>> tags = optionalAsync(
        () -> tagClient.findTags(patientId), ioExecutor, 200, List.of());
CompletableFuture<InsuranceStatus> insurance = optionalAsync(
        () -> insuranceClient.query(patientId), insuranceExecutor, 500, InsuranceStatus.unknown());

CompletableFuture<PatientDetailView> view = CompletableFuture
        .allOf(profile, tags, insurance)
        .thenApply(ignored -> PatientDetailView.of(profile.join(), tags.join(), insurance.join()));
```

- **拒绝策略前提**：`supplyAsync` 的同步提交拒绝无法被其后注册的 `exceptionally` 捕获；静默丢弃策略不能保证任务有终态，`CallerRunsPolicy` 还可能在调用线程阻塞至任务结束后才注册超时。因此此示例要求明确抛出拒绝异常的执行器。依据：[OpenJDK 21 CompletableFuture 源码中的 asyncSupplyStage](https://github.com/openjdk/jdk21u/blob/master/src/java.base/share/classes/java/util/concurrent/CompletableFuture.java)。
- **资源边界**：`insuranceExecutor` 与普通 `ioExecutor` 隔离，避免医保平台变慢时耗尽患者详情页的全部 I/O 线程；线程池队列必须有界，拒绝后应转为明确的降级结果或错误，而不是无限堆积。
- **时间边界**：子任务超时应来自接口总预算。例如接口预算 800ms，不能给三个串联阶段各配置 800ms；需要预留编排、序列化和网络回写时间。
- **取消边界**：`orTimeout` 只让对应的 `CompletableFuture` 超时完成，不保证取消已经提交的底层 JDBC/HTTP 调用。客户端还应配置连接、读取和调用超时，并避免对非幂等外部请求做盲目重试。
- **一致性边界**：聚合查询只读、允许字段降级；支付、医保状态推进、电子票据生成等写操作不能照搬此模式，必须使用持久化状态与幂等/补偿机制。
- **可观测性**：每个子调用记录下游名、线程池名、排队时间、执行时间、超时/降级原因和 TraceId。只有区分“排队超时”和“下游超时”，容量调整才有依据。

### 本案例的最小回归

下面的方法与 `optionalAsync` 放在同一类中运行，用于防止再次遗漏同步提交拒绝。标准库类型沿用上面的导入；`AssertionError` 不依赖 `-ea`。

```java
public static void main(String[] args) {
    Executor rejected = command -> {
        throw new RejectedExecutionException("模拟线程池饱和");
    };
    String value = optionalAsync(() -> "实际结果", rejected, 100, "降级结果").join();
    if (!"降级结果".equals(value)) {
        throw new AssertionError("可选分支提交拒绝时必须降级");
    }
    try {
        optionalAsync(() -> { throw new SecurityException("无访问权限"); },
                Runnable::run, 100, "降级结果").join();
        throw new AssertionError("权限错误不能被降级吞掉");
    } catch (CompletionException expected) {
        if (!(expected.getCause() instanceof SecurityException)) {
            throw new AssertionError("应保留权限错误", expected);
        }
    }
}
```
