## 1. 线程同步基础

### 1.1 **synchronized**
- 可用于实例方法、静态方法、代码块：保护共享资源的原子性、可见性、有序性。
- 底层依赖对象监视器（monitorenter/monitorexit）与对象头 Mark Word。
    - 同步方法：靠 ACC_SYNCHRONIZED，JVM 隐式加解锁；
    - 同步代码块：靠 monitorenter/monitorexit，手动加解锁。
- monitorenter 和 monitorexit 是 JVM 层面的加锁、解锁指令。执行时会先利用对象头里的 Mark Word 判断和记录锁状态；如果竞争升级，锁会关联到 Monitor，由 Monitor 负责线程阻塞和唤醒
- synchronized 是可重入锁：同一线程拿到锁后再次进入同一 monitor 不会死锁，内部会维护进入次数（递归次数）。

```java
public class SyncSamples {
	public synchronized void syncInstance() { /* ... */ } //锁住的是“当前实例对象”——也就是 this
	public static synchronized void syncStatic() { /* ... */ } //所有线程，只要调用 Demo 的 static synchronized 方法，都会竞争同一把锁。
	public static void bar() { //所有线程，只要调用 Demo 的 static synchronized 方法，都会竞争同一把锁。
		synchronized (SyncSamples.class) {
			// ...
		}
	}
	public void block() {
		synchronized (this) { //锁住的是“当前实例对象”——也就是 this
			// 临界区
		  }
	  }
  }
  ```

### 1.2 **ReentrantLock**
- `java.util.concurrent.locks` 中的显式锁，支持可重入、公平/非公平策略、`tryLock`、`lockInterruptibly`。
- 必须在 `finally` 块中释放锁，支持条件变量（`Condition`）。

	```java
	ReentrantLock lock = new ReentrantLock(true);
	lock.lock();
	try {
		// 临界区
	} finally {
		lock.unlock();
	}
	```

### 1.3 **ReentrantReadWriteLock**
- 读写分离：多个读可以并行，写独占。
- 适合读多写少场景，可配合 `StampedLock` 获取乐观读。

```java
import java.util.concurrent.locks.ReentrantReadWriteLock;

class RWMap<K, V> {
	private final java.util.Map<K, V> map = new java.util.HashMap<>();
	private final ReentrantReadWriteLock rwLock = new ReentrantReadWriteLock();

	/*
	线程 A 拿到 writeLock 后，其他线程在想拿 readLock 或 writeLock 时都会被阻塞；
	map.put(key, value) 正好放在”持有写锁”的这段时间内执行；
	所以：逻辑上是”给 Map 的写操作加了一把锁”，但物理上锁的是 ReentrantReadWriteLock 维护的锁状态，而不是 map。
	*/

	// 读操作，可被多个线程并发访问
	public V get(K key) {
		rwLock.readLock().lock();
		try {
			return map.get(key);
		} finally {
			rwLock.readLock().unlock();
		}
	}

	// 写操作，独占锁
	public void put(K key, V value) {
		rwLock.writeLock().lock();
		try {
			map.put(key, value);
		} finally {
			rwLock.writeLock().unlock();
		}
	}
}
```

### 1.3.1 **StampedLock（JDK 8+）**

`StampedLock` 是 JDK 8 引入的读写同步工具，提供 **乐观读（Optimistic Read）** 模式。在读路径短、写入稀少且验证失败率低时，它可能比传统读锁更合适；是否更快仍取决于竞争、临界区和运行环境。

#### 核心特性

**三种锁模式：**
1. **写锁（Write Lock）**：独占锁，与 ReentrantReadWriteLock 的写锁类似
2. **悲观读锁（Pessimistic Read Lock）**：共享锁，与 ReentrantReadWriteLock 的读锁类似
3. **乐观读（Optimistic Read）**：这是 StampedLock 的核心创新，不加锁，只是获取一个”戳记”（stamp）

#### 为什么需要 StampedLock？

**ReentrantReadWriteLock 的局限：**
- 即使是读锁，也需要进行 CAS 操作来获取和释放锁
- 在读操作非常频繁的场景下，这些 CAS 操作会成为性能瓶颈
- 非公平策略下不保证等待顺序；在持续竞争下要评估尾延迟与饥饿风险

**StampedLock 的特点：**
- **乐观读不获取读锁**：先取得戳记并读取数据，随后必须 `validate`；验证失败时应回退到读锁重读，不能把中间读取结果直接当作一致快照
- **支持锁升级**：乐观读可以升级为悲观读
- **不可重入**：简化实现，提升性能（注意：这也是它的限制）

#### 乐观读的工作原理

```java
class Point {
    private double x, y;
    private final StampedLock sl = new StampedLock();

    // 乐观读示例
    double distanceFromOrigin() {
        long stamp = sl.tryOptimisticRead();  // 获取乐观读戳记（不加锁）

        // 读取数据（此时可能有写线程在修改）
        double currentX = x;
        double currentY = y;

        // 验证：读取期间是否有写操作
        if (!sl.validate(stamp)) {
            // 有写操作，升级为悲观读锁
            stamp = sl.readLock();
            try {
                currentX = x;
                currentY = y;
            } finally {
                sl.unlockRead(stamp);
            }
        }

        return Math.sqrt(currentX * currentX + currentY * currentY);
    }

    // 写操作
    void move(double deltaX, double deltaY) {
        long stamp = sl.writeLock();  // 获取写锁
        try {
            x += deltaX;
            y += deltaY;
        } finally {
            sl.unlockWrite(stamp);
        }
    }

    // 悲观读示例
    double getX() {
        long stamp = sl.readLock();  // 获取悲观读锁
        try {
            return x;
        } finally {
            sl.unlockRead(stamp);
        }
    }
}
```

#### 乐观读的执行流程

```
1. tryOptimisticRead()
   ↓ 返回一个 stamp（版本号）

2. 读取共享数据
   ↓ 此时不持有任何锁，其他线程可以并发写

3. validate(stamp)
   ↓ 检查读取期间是否有写操作

4a. validate 返回 true     4b. validate 返回 false
    ↓ 数据有效                  ↓ 数据可能不一致
    直接使用数据                升级为悲观读锁重新读取
```

#### 三种模式对比

| 模式     | 是否获取锁   | 典型特征 | 适用场景                   | 数据一致性保证     |
| -------- | ------------ | -------- | -------------------------- | ------------------ |
| 乐观读   | 不获取读锁   | 验证失败时需要回退 | 读操作极其频繁，写操作很少 | 需要 validate 验证 |
| 悲观读锁 | 是（共享锁） | 读取期间持有共享锁 | 读多写少，需要强一致性     | 加锁期间保证一致   |
| 写锁     | 是（独占锁） | 写入期间排他 | 写操作                     | 完全独占           |

#### 完整示例：缓存实现

```java
import java.util.concurrent.locks.StampedLock;

class DataCache {
    private Object data;
    private final StampedLock sl = new StampedLock();

    // 读取数据（优先使用乐观读）
    Object getData() {
        // 1. 尝试乐观读
        long stamp = sl.tryOptimisticRead();
        Object currentData = data;

        // 2. 验证读取期间是否有写操作
        if (!sl.validate(stamp)) {
            // 3. 验证失败，升级为悲观读
            stamp = sl.readLock();
            try {
                currentData = data;
            } finally {
                sl.unlockRead(stamp);
            }
        }

        return currentData;
    }

    // 写入数据
    void setData(Object newData) {
        long stamp = sl.writeLock();
        try {
            data = newData;
        } finally {
            sl.unlockWrite(stamp);
        }
    }

    // 条件更新（读锁升级为写锁）
    void updateIfNeeded(Object newData) {
        // 先获取悲观读锁
        long stamp = sl.readLock();
        try {
            while (data == null) {  // 需要更新
                // 尝试升级为写锁
                long ws = sl.tryConvertToWriteLock(stamp);

                if (ws != 0L) {  // 升级成功
                    stamp = ws;
                    data = newData;
                    break;
                } else {  // 升级失败
                    // 释放读锁，获取写锁
                    sl.unlockRead(stamp);
                    stamp = sl.writeLock();
                    // 重新检查条件
                }
            }
        } finally {
            sl.unlock(stamp);  // 统一释放（自动识别锁类型）
        }
    }
}
```

#### 锁转换机制

StampedLock 支持三种锁转换：

```java
// 1. 读锁 → 写锁
long stamp = sl.readLock();
long ws = sl.tryConvertToWriteLock(stamp);
if (ws != 0L) {
    stamp = ws;  // 转换成功
} else {
    sl.unlockRead(stamp);
    stamp = sl.writeLock();  // 转换失败，重新获取
}

// 2. 写锁 → 读锁
long stamp = sl.writeLock();
stamp = sl.tryConvertToReadLock(stamp);  // 降级

// 3. 写锁/读锁 → 乐观读
long stamp = sl.tryConvertToOptimisticRead(stamp);
```

#### 使用注意事项

**1. 不可重入**
```java
// ❌ 错误：会死锁
long stamp = sl.writeLock();
try {
    long stamp2 = sl.writeLock();  // 死锁！
} finally {
    sl.unlockWrite(stamp);
}
```

**2. 不支持 Condition**
- StampedLock 没有 `newCondition()` 方法
- 如果需要条件等待，使用 ReentrantReadWriteLock

**3. 必须正确释放锁**
```java
// ✅ 正确：使用 finally
long stamp = sl.writeLock();
try {
    // ...
} finally {
    sl.unlockWrite(stamp);  // 必须释放
}
```

**4. CPU 占用问题**
- StampedLock 在获取锁时会自旋
- 如果锁竞争激烈，可能导致 CPU 占用过高
- 不适合锁持有时间长的场景

#### StampedLock vs ReentrantReadWriteLock

| 特性         | StampedLock | ReentrantReadWriteLock |
| ------------ | ----------- | ---------------------- |
| 乐观读       | ✅ 支持      | ❌ 不支持               |
| 可重入       | ❌ 不支持    | ✅ 支持                 |
| 条件变量     | ❌ 不支持    | ✅ 支持                 |
| 锁转换       | ✅ 支持      | ❌ 不支持               |
| 性能（读多） | 更高        | 较高                   |
| 公平性/饥饿 | 不提供公平性保证，需按实际负载验证 | 可选公平策略；非公平模式同样不保证等待顺序 |
| 使用复杂度   | 较高        | 较低                   |

#### 适用场景

**适合使用 StampedLock：**
- ✅ 读操作显著多于写操作，且读路径很短
- ✅ 读操作耗时很短
- ✅ 不需要可重入特性
- ✅ 不需要条件变量
- ✅ 追求极致性能

**不适合使用 StampedLock：**
- ❌ 需要可重入锁
- ❌ 需要条件变量（Condition）
- ❌ 锁持有时间长
- ❌ 写操作频繁
- ❌ 代码逻辑复杂，容易出错

#### 性能边界

乐观读只有在读路径短、写入稀少且 `validate` 失败率低时才可能带来收益；数据访问本身昂贵、写入频繁或验证失败后反复回退时，收益会减小甚至消失。锁竞争、CPU 架构、JDK 版本和临界区长度都会改变结果，应以目标 JDK 和真实负载进行 JMH/压测，而不要套用固定百分比。

#### 一句话总结

**StampedLock 通过乐观读提供了不获取读锁的读取路径；在读多写少且验证失败率低的负载中可能带来收益，但不支持可重入和条件变量，必须正确处理戳记、回退和验证逻辑。**


### 1.4 **Condition（条件变量）**
- 结合 `ReentrantLock` 使用，实现更精细的等待/唤醒。

```java
class BoundedBuffer {
	private final ReentrantLock lock = new ReentrantLock();
	private final Condition notEmpty = lock.newCondition();
	private final Condition notFull = lock.newCondition();
	private final int[] buffer = new int[10];
	private int putIdx, takeIdx, count;

	public void put(int val) throws InterruptedException {
		lock.lock();
		try {
			while (count == buffer.length) {
				notFull.await();
			}
			buffer[putIdx] = val;
			putIdx = (putIdx + 1) % buffer.length;
			count++;
			notEmpty.signal();
		} finally {
			lock.unlock();
		}
	  }

	  public int take() throws InterruptedException {
		  lock.lock();
		  try {
			while (count == 0) {
				  notEmpty.await();
			  }
			int val = buffer[takeIdx];
			takeIdx = (takeIdx + 1) % buffer.length;
			  count--;
			  notFull.signal();
			return val;
		  } finally {
			  lock.unlock();
		  }
	  }
}
```

### 1.5 **原子变量家族**
- 位于 `java.util.concurrent.atomic`，内部使用 CAS。
- `AtomicInteger/Long`, `AtomicReference`, `AtomicStampedReference`（含版本号防 ABA）。
    ```java
	AtomicInteger counter = new AtomicInteger();
	int result = counter.incrementAndGet();
	```
- *AtomicStampedReference：*
    - 内部维护 (reference, stamp) 二元组
    - CAS 时同时比较这两个：
    ```java
	AtomicStampedReference<String> ref = new AtomicStampedReference<>("A", 0);
	int stamp = ref.getStamp();

	```

### 1.6 ThreadLocal 概览
- 为每个线程提供独立副本，避免共享数据竞争。
- 适用存储上下文信息（如 TraceId）。详见 [ThreadLocal 实战](#11-threadlocal-实战)。

**小结**：`synchronized` 适合简单场景；需要更强控制能力时选择 `ReentrantLock` 及其配套工具。
| 类型                                         | 锁定对象/机制                        | 特点说明                                                                                                   |
| -------------------------------------------- | ------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| Lock 系列（如 ReentrantLock、ReadWriteLock） | “锁”实例本身，如 new ReentrantLock() | 锁只负责管理 lock/unlock，至于具体保护的数据（如 map/list/其它逻辑）它并不知情，灵活但更考程序员自律与规范 |
| synchronized(obj)                            | obj 的内置锁（monitor）              | 锁定的是 obj 对象（每个对象一个内置锁），只是实现互斥，也不会自动知道锁定的是何种数据                      |

### 1.7 LongAdder

1. 它把“所有线程都抢同一个原子变量”的热点，分散成多个分片计数槽（cells），线程各自更新自己的槽，最后再把所有槽加起来得到总和。
    1. *AtomicLong 为什么会慢：单点 CAS 热点*
        - AtomicLong.incrementAndGet() 本质是：
            - 读当前值 v
            - CAS 把 v 改成 v+1
            - 失败就自旋重试

        - 当并发很高时，很多线程同时 CAS 同一个内存地址：
            - cache line 在多个 CPU 核之间疯狂“抢所有权”
            - CAS 失败率高，自旋重试多
            - 总开销飙升

    2. LongAdder 的核心结构：base + cells[]
        - LongAdder 继承自 Striped64（内部实现核心），大致结构是：
            - volatile long base：低争用时直接更新 base（便宜）
            - volatile Cell[] cells：高争用时启用分片数组
            - 每个 Cell 本质上就是一个带 padding 的 volatile long value（避免伪共享）

    3. 更新逻辑大致是：
        - 先尝试 CAS 更新 base
        - 如果 CAS 失败（说明有竞争）：
            - 确保 cells 已初始化（按需懒初始化）
            - 根据线程的 probe/hash 选择一个 cell：cells[hash & (len-1)]
            - CAS 更新这个 cell.value
        - 如果更新 cell 也失败（这个槽也挤爆了）：
            - 可能 rehash（改变 probe）
            - 或者扩容 cells（通常翻倍），把冲突进一步摊薄

2. 为什么它更快：把竞争概率打散
    - 假设有 N 个线程同时 increment：
        - AtomicLong：所有 N 个线程竞争同一个点，冲突概率接近 1
        - LongAdder：如果 cells 长度是 M，线程被打散到 M 个槽
            - 平均每个槽大概 N/M 个线程竞争，冲突强度大幅下降

    - **在高并发下，只要 M 足够大（通常会扩到接近 CPU 核数/争用水平），每个 cell 上的 CAS 失败率就会明显降低，自旋次数也少，整体吞吐就上来了。**

3. 还有个隐藏大招：避免伪共享（false sharing）
    - Cell 里会做 padding（填充字段，或用 @Contended 之类的手段），目的：
        - 让不同 cell 的 value 尽量落在不同 cache line 上
        - 避免两个线程更新不同 cell，却因为共享同一 cache line 而互相干扰

    - 这点对高并发更新特别关键：不然“分片了”也可能被 cache line 争用拖慢。

4. 为什么它不是总比 AtomicLong 快：读取不是原子一致的
    - LongAdder 的代价是：
        - sum() 需要把 base + Σcells[i] 全部累加
        - sum() 期间别的线程可能还在更新，所以拿到的是近似值（通常叫 weakly consistent）
        - 它不提供像 AtomicLong.getAndIncrement() 那样严格的“全局原子序列语义”

    - 因此结论是：
        - 高频写、低频读（统计计数、QPS、指标埋点）→ LongAdder 通常更合适
        - 需要强一致读/精确时序语义（发号器、严格计数门槛）→ 用 AtomicLong / 锁

5. 总结
    - **AtomicLong 在高并发下是单点 CAS 热点，导致 cache line 争用和大量自旋失败；LongAdder 通过 base+cells 的分片计数把更新分散到多个槽，降低冲突，并通过 padding 避免伪共享，所以高并发写性能更好。但它的 sum 是弱一致的，不适合需要严格原子读的场景。**
    - LongAdder 用于“统计类”高并发计数；Atomic 用于“控制类”并发流程（CAS、状态机、发号、快照替换）。


## 2. 虚拟线程速览

> 第 13 节进一步对比虚拟线程与平台线程，并说明工程上的使用边界。
- **定义**：虚拟线程在 JDK 19、20 为预览特性，JDK 21 正式发布。它由 JVM 调度，可复用少量 carrier（平台）线程执行，而不是与 OS 线程一一绑定。
- **优势**：创建/切换成本低，易于在 IO 密集型场景实现“每请求一线程”的直观模型。
- **特性**：
  - `Thread.ofVirtual().start(() -> {...})`
  - 支持 `Executors.newVirtualThreadPerTaskExecutor()`
- 与传统同步 API 兼容；许多 JDK 支持的阻塞点会卸载虚拟线程，但 native 调用、长时间持有监视器等情形仍可能阻塞 carrier，需要在第 13 节的边界下评估。

    ```java
    try (var executor = Thread.ofVirtual().factory().newThreadPerTaskExecutor()) {
        executor.submit(() -> Files.readString(Path.of("/tmp/data")));
    }
    ```

- **适用场景**：高并发 IO（网关、RPC、爬虫）、大量短生命周期任务。
- **注意**：
  - 仍需关注外部资源限制（数据库连接、文件句柄）。
  - 监控/Profiler 需升级以识别虚拟线程。

## 3. 线程池与调度策略

### 3.1 核心概念
- 线程复用、任务排队、资源上限控制。
- 核心类：`Executor` -> `ExecutorService` -> `ThreadPoolExecutor`。

### 3.2 常用线程池类型
- `Executors.newFixedThreadPool(n)`：固定大小，但默认使用无界队列；任务积压时可能耗尽内存。
- `Executors.newCachedThreadPool()`：使用 `SynchronousQueue` 且最大线程数接近无上限；慢任务或突发流量可能创建过多线程。
- `Executors.newSingleThreadExecutor()`：顺序执行，常用于串行化任务。
- `Executors.newScheduledThreadPool(n)`：定时/周期任务。
- **最佳实践**：生产服务优先显式构造 `ThreadPoolExecutor`，为队列、最大线程数、线程名、拒绝策略和监控设定可观测的边界。

### 3.3 ThreadPoolExecutor 参数
- `corePoolSize`：常驻线程。
- `maximumPoolSize`：峰值线程。
- `keepAliveTime`：非核心线程空闲超时。
- `workQueue`：如 `ArrayBlockingQueue`、`LinkedBlockingQueue`、`SynchronousQueue`。
- `ThreadFactory`：自定义线程名、优先级、异常处理。
- `RejectedExecutionHandler`：拒绝策略（Abort-抛异常、CallerRuns-自己执行、Discard-舍弃、DiscardOldest-舍弃最老的 或自定义）。

#### 3.3.1 ArrayBlockingQueue vs LinkedBlockingQueue

**核心区别对比**

| 维度         | ArrayBlockingQueue         | LinkedBlockingQueue                      |
| ------------ | -------------------------- | ---------------------------------------- |
| **底层结构** | 数组（循环数组）           | 链表（单向链表）                         |
| **容量**     | 必须指定固定容量           | 可选容量（默认 Integer.MAX_VALUE）       |
| **锁机制**   | **单锁**（一把锁控制读写） | **双锁**（读锁 takeLock + 写锁 putLock） |
| **内存占用** | 预分配数组空间             | 按需分配节点（每个节点额外开销）         |
| **吞吐量**   | 较低（读写互斥）           | 较高（读写可并发）                       |
| **公平性**   | 支持公平/非公平            | 只支持非公平（FIFO 保证顺序）            |

**1. 锁机制差异（最关键）**

*ArrayBlockingQueue：单锁*
```java
// 伪代码
final ReentrantLock lock = new ReentrantLock();

public void put(E e) {
    lock.lock();
    try {
        // 入队操作
    } finally {
        lock.unlock();
    }
}

public E take() {
    lock.lock();  // 和 put 竞争同一把锁
    try {
        // 出队操作
    } finally {
        lock.unlock();
    }
}
```
- **生产者和消费者互斥**：一个在写，另一个必须等待
- 适合读写速度接近的场景

*LinkedBlockingQueue：双锁*
```java
// 伪代码
final ReentrantLock takeLock = new ReentrantLock();  // 读锁
final ReentrantLock putLock = new ReentrantLock();   // 写锁

public void put(E e) {
    putLock.lock();
    try {
        // 入队操作
    } finally {
        putLock.unlock();
    }
}

public E take() {
    takeLock.lock();  // 不和 put 竞争
    try {
        // 出队操作
    } finally {
        takeLock.unlock();
    }
}
```
- **生产者和消费者可并发**：一个写头、一个读尾，互不干扰
- 吞吐量更高

**2. 容量限制**

*ArrayBlockingQueue*
```java
// 必须指定容量
BlockingQueue<String> queue = new ArrayBlockingQueue<>(100);
```
- 强制有界，防止内存溢出
- 适合需要严格流控的场景

*LinkedBlockingQueue*
```java
// 可以不指定（危险！）
BlockingQueue<String> queue1 = new LinkedBlockingQueue<>();
// 默认 Integer.MAX_VALUE，相当于无界

// 也可以指定
BlockingQueue<String> queue2 = new LinkedBlockingQueue<>(100);
```
- 不指定容量时相当于无界队列，可能导致 OOM
- **Executors.newFixedThreadPool() 默认用的就是无界 LinkedBlockingQueue**，这是个坑

**3. 内存使用**

*ArrayBlockingQueue*
- 创建时就分配整个数组空间
- 内存占用固定，无额外节点开销
- 适合容量较小的场景

*LinkedBlockingQueue*
- 按需创建节点，每个节点有额外的 `next` 指针开销
- 空队列时几乎不占内存
- 适合容量较大或动态变化的场景

**4. 性能对比**

*高并发场景（生产消费都很快）*
- **LinkedBlockingQueue 更优**：双锁允许读写并发

*低并发或读写不均衡*
- **ArrayBlockingQueue 更优**：
  - 无节点分配开销
  - 缓存友好（数组连续内存）
  - 单锁开销更小

**使用场景建议**

*选择 ArrayBlockingQueue*
```java
// 1. 需要严格容量限制
new ArrayBlockingQueue<>(100);

// 2. 需要公平策略（按等待时间排队）
new ArrayBlockingQueue<>(100, true);

// 3. 队列容量较小（几百以内）
// 4. 生产消费速度接近
```

*选择 LinkedBlockingQueue*
```java
// 1. 高吞吐量场景（生产消费都很快）
new LinkedBlockingQueue<>(1000);

// 2. 容量较大或动态变化
// 3. 生产消费速度差异大（双锁优势明显）

// ⚠️ 避免无界队列
// 错误：new LinkedBlockingQueue<>();  // 可能 OOM
// 正确：new LinkedBlockingQueue<>(10000);
```

**线程池中的选择**

```java
// ❌ 不推荐：Executors 默认用无界 LinkedBlockingQueue
ExecutorService bad = Executors.newFixedThreadPool(10);

// ✅ 推荐：显式指定有界队列
ThreadPoolExecutor good = new ThreadPoolExecutor(
    10, 10, 0L, TimeUnit.MILLISECONDS,
    new ArrayBlockingQueue<>(100),  // 或 new LinkedBlockingQueue<>(100)
    new ThreadPoolExecutor.CallerRunsPolicy()
);
```

**总结**
- **ArrayBlockingQueue**：有界、单锁、数组实现，适合**容量小、需要严格限流**的场景
- **LinkedBlockingQueue**：可选有界、双锁、链表实现，适合**高吞吐、容量大**的场景，但**必须指定容量**避免 OOM

#### 3.3.2 ArrayBlockingQueue 为什么采用单锁模式

**核心原因：数组结构的限制**

ArrayBlockingQueue 使用**循环数组**作为底层存储，这导致读写操作必须共享同一组索引变量：

```java
// ArrayBlockingQueue 内部结构（简化）
final Object[] items;       // 存储元素的数组
int takeIndex;              // 下次取元素的位置
int putIndex;               // 下次放元素的位置
int count;                  // 当前元素数量
```

**1. 索引竞争问题**

如果用双锁，会出现这种情况：

```java
// 假设用双锁（错误示例）
final ReentrantLock takeLock = new ReentrantLock();
final ReentrantLock putLock = new ReentrantLock();

public void put(E e) {
    putLock.lock();
    try {
        items[putIndex] = e;
        putIndex = (putIndex + 1) % items.length;  // 循环
        count++;  // ⚠️ 问题：count 被两个锁同时访问
    } finally {
        putLock.unlock();
    }
}

public E take() {
    takeLock.lock();
    try {
        E x = items[takeIndex];
        items[takeIndex] = null;
        takeIndex = (takeIndex + 1) % items.length;
        count--;  // ⚠️ 问题：count 被两个锁同时访问
    } finally {
        takeLock.unlock();
    }
}
```

问题：
- `count`、`putIndex`、`takeIndex` 这些共享变量需要在两个锁之间同步
- 即使用 `volatile` 也无法保证 `count++` 和 `count--` 的原子性
- 需要额外的 CAS 或第三把锁来保护这些变量，反而更复杂

**2. 数组边界的特殊情况**

循环数组在满/空状态时，`putIndex` 和 `takeIndex` 可能指向同一位置：

```
空队列：putIndex == takeIndex == 0
满队列：putIndex == takeIndex（但 count == capacity）
```

如果用双锁：
- 生产者和消费者可能同时操作同一个数组位置
- 需要复杂的同步机制来判断"满"还是"空"

**3. 与 LinkedBlockingQueue 的对比**

LinkedBlockingQueue 为什么能用双锁？

```java
// LinkedBlockingQueue 内部结构
static class Node<E> {
    E item;
    Node<E> next;
}

Node<E> head;  // 消费者只操作 head
Node<E> last;  // 生产者只操作 last
AtomicInteger count;  // 用原子类解决计数问题
```

关键差异：
- **链表的头尾分离**：生产者只操作 `last`，消费者只操作 `head`，天然隔离
- **独立的计数器**：用 `AtomicInteger` 保证 `count` 的原子性
- **无循环索引**：不需要共享 `putIndex/takeIndex`

**单锁的优势**

对于 ArrayBlockingQueue 来说，单锁反而更简单高效：

```java
final ReentrantLock lock = new ReentrantLock();

public void put(E e) {
    lock.lock();
    try {
        // 所有操作都在锁保护下，逻辑简单清晰
        while (count == items.length) {
            notFull.await();  // 等待非满
        }
        items[putIndex] = e;
        putIndex = (putIndex + 1) % items.length;
        count++;
        notEmpty.signal();  // 通知消费者
    } finally {
        lock.unlock();
    }
}
```

优点：
1. **实现简单**：无需复杂的同步协议
2. **无竞态条件**：所有共享变量都在同一把锁保护下
3. **Condition 变量天然支持**：`notFull` 和 `notEmpty` 可以直接绑定到同一把锁

**性能权衡**

单锁的代价：
- 生产者和消费者互斥，吞吐量受限

但对于 ArrayBlockingQueue：
- 数组操作本身很快（O(1) 读写）
- 锁竞争的开销相对较小
- 适合**容量较小、操作快速**的场景

如果需要高吞吐量：
- 用 `LinkedBlockingQueue`（双锁）
- 或用 `ConcurrentLinkedQueue`（无锁）
- 或用 `Disruptor`（环形缓冲区 + 无锁）

**总结**

ArrayBlockingQueue 采用单锁是因为：
1. **数组结构决定**：循环数组的 `putIndex`、`takeIndex`、`count` 必须强同步
2. **双锁成本高**：需要额外机制保护共享变量，反而更复杂
3. **设计取舍**：牺牲并发度换取实现简单性和正确性
4. **适用场景**：本身定位就是**有界、容量小、操作快**的队列，单锁够用

如果需要高并发吞吐，应该选择 LinkedBlockingQueue（双锁）或其他无锁数据结构。

#### 3.3.3 线程池执行流程详解

**完整执行流程图：**

```
提交任务 execute(task)
    ↓
┌─────────────────────────────────────────┐
│ 1. 当前线程数 < corePoolSize ?         │
│    ├─ 是 → 创建核心线程执行任务 ✓      │
│    └─ 否 → 继续                        │
└─────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────┐
│ 2. 工作队列未满 ?                       │
│    ├─ 是 → 任务入队 ✓                  │
│    └─ 否 → 继续                        │
└─────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────┐
│ 3. 当前线程数 < maximumPoolSize ?      │
│    ├─ 是 → 创建非核心线程执行任务 ✓    │
│    └─ 否 → 继续                        │
└─────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────┐
│ 4. 执行拒绝策略 ⚠️                     │
│    - AbortPolicy: 抛异常               │
│    - CallerRunsPolicy: 调用者执行      │
│    - DiscardPolicy: 静默丢弃           │
│    - DiscardOldestPolicy: 丢弃最老任务 │
└─────────────────────────────────────────┘
```

**关键点说明：**

1. **核心线程优先**：即使有空闲核心线程，也会创建新线程（直到达到 corePoolSize）
2. **队列其次**：核心线程满后，任务进队列
3. **非核心线程兜底**：队列满后，创建非核心线程（直到 maximumPoolSize）
4. **拒绝策略最后**：所有资源耗尽，执行拒绝策略

**示例演示：**

```java
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    2,    // corePoolSize
    5,    // maximumPoolSize
    60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(3),  // 队列容量 3
    new ThreadPoolExecutor.AbortPolicy()
);

// 提交 10 个任务，每个任务执行 10 秒
for (int i = 1; i <= 10; i++) {
    try {
        int taskId = i;
        executor.execute(() -> {
            System.out.println("Task " + taskId + " running on " +
                             Thread.currentThread().getName());
            sleep(10000);
        });
        System.out.println("Task " + i + " submitted");
    } catch (RejectedExecutionException e) {
        System.out.println("Task " + i + " rejected!");
    }
}
```

**执行过程分析：**

```
Task 1: 创建核心线程 1 执行 ✓          [核心线程: 1/2, 队列: 0/3, 总线程: 1/5]
Task 2: 创建核心线程 2 执行 ✓          [核心线程: 2/2, 队列: 0/3, 总线程: 2/5]
Task 3: 核心线程满，任务入队 ✓         [核心线程: 2/2, 队列: 1/3, 总线程: 2/5]
Task 4: 任务入队 ✓                    [核心线程: 2/2, 队列: 2/3, 总线程: 2/5]
Task 5: 任务入队 ✓                    [核心线程: 2/2, 队列: 3/3, 总线程: 2/5]
Task 6: 队列满，创建非核心线程 3 执行 ✓ [核心线程: 2/2, 队列: 3/3, 总线程: 3/5]
Task 7: 创建非核心线程 4 执行 ✓        [核心线程: 2/2, 队列: 3/3, 总线程: 4/5]
Task 8: 创建非核心线程 5 执行 ✓        [核心线程: 2/2, 队列: 3/3, 总线程: 5/5]
Task 9: 所有资源耗尽，拒绝 ⚠️          [核心线程: 2/2, 队列: 3/3, 总线程: 5/5]
Task 10: 拒绝 ⚠️                      [核心线程: 2/2, 队列: 3/3, 总线程: 5/5]
```

**常见误区：**

```java
// ❌ 误区 1：以为会先创建到 maximumPoolSize
// 实际：先填满队列，再创建非核心线程

// ❌ 误区 2：以为队列无界就不会拒绝
ThreadPoolExecutor bad = new ThreadPoolExecutor(
    2, 5, 60, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>()  // 无界队列
);
// 问题：maximumPoolSize 永远用不上！任务会一直入队，可能 OOM

// ✅ 正确：有界队列
ThreadPoolExecutor good = new ThreadPoolExecutor(
    2, 5, 60, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(100)  // 有界队列
);
```

#### 3.3.4 四种拒绝策略详解

**1. AbortPolicy（默认）：抛异常**

```java
public static class AbortPolicy implements RejectedExecutionHandler {
    public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
        throw new RejectedExecutionException("Task " + r.toString() +
                                             " rejected from " + e.toString());
    }
}
```

**特点：**
- 抛出 `RejectedExecutionException`
- 调用者可以捕获异常并处理

**适用场景：**
- 任务不能丢失，必须感知拒绝
- 需要记录日志或告警
- 可以重试或降级

**实战示例：**
```java
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    2, 5, 60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(10),
    new ThreadPoolExecutor.AbortPolicy()
);

try {
    executor.execute(task);
} catch (RejectedExecutionException e) {
    log.error("任务被拒绝，尝试降级处理", e);
    fallbackHandler.handle(task);  // 降级处理
}
```

---

**2. CallerRunsPolicy：调用者执行**

```java
public static class CallerRunsPolicy implements RejectedExecutionHandler {
    public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
        if (!e.isShutdown()) {
            r.run();  // 在调用线程中执行
        }
    }
}
```

**特点：**
- 任务在调用线程（通常是主线程或 Web 请求线程）中执行
- 不会丢失任务
- 会阻塞调用线程

**适用场景：**
- 任务不能丢失
- 可以接受调用线程被阻塞
- 天然的负反馈机制（调用线程被占用，提交速度自然降低）

**实战示例：**
```java
// Web 应用中的异步任务处理
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    10, 20, 60, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(100),
    new ThreadPoolExecutor.CallerRunsPolicy()  // 请求线程自己执行
);

@GetMapping("/process")
public String process() {
    executor.execute(() -> {
        // 异步处理
    });
    // 如果线程池满，任务会在 Tomcat 线程中执行
    // 虽然慢，但不会丢失任务
    return "submitted";
}
```

**优缺点：**
- ✅ 优点：不丢任务，天然限流
- ❌ 缺点：阻塞调用线程，可能影响吞吐量

---

**3. DiscardPolicy：静默丢弃**

```java
public static class DiscardPolicy implements RejectedExecutionHandler {
    public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
        // 什么都不做，静默丢弃
    }
}
```

**特点：**
- 直接丢弃任务
- 不抛异常，不通知
- 调用者无感知

**适用场景：**
- 任务可以丢失（如日志、监控埋点）
- 允许部分数据丢失
- 对实时性要求不高

**实战示例：**
```java
// 监控指标上报（丢失部分数据可接受）
ThreadPoolExecutor metricsExecutor = new ThreadPoolExecutor(
    2, 4, 60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(1000),
    new ThreadPoolExecutor.DiscardPolicy()  // 丢弃超出的指标
);

public void reportMetric(Metric metric) {
    metricsExecutor.execute(() -> {
        httpClient.post("/metrics", metric);
    });
    // 如果线程池满，指标会被丢弃，但不影响主流程
}
```

**⚠️ 危险：**
- 任务丢失无感知，可能导致数据不一致
- 建议配合监控：记录拒绝次数

---

**4. DiscardOldestPolicy：丢弃最老任务**

```java
public static class DiscardOldestPolicy implements RejectedExecutionHandler {
    public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
        if (!e.isShutdown()) {
            e.getQueue().poll();  // 丢弃队列头部（最老）任务
            e.execute(r);         // 重新提交当前任务
        }
    }
}
```

**特点：**
- 丢弃队列中最老的任务
- 为新任务腾出空间
- 优先保证新任务

**适用场景：**
- 新任务优先级更高（如实时数据处理）
- 老任务可以丢弃（如过期的缓存刷新）

**实战示例：**
```java
// 实时数据处理（老数据可以丢弃）
ThreadPoolExecutor realtimeExecutor = new ThreadPoolExecutor(
    5, 10, 60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(50),
    new ThreadPoolExecutor.DiscardOldestPolicy()
);

public void processRealtimeData(Data data) {
    realtimeExecutor.execute(() -> {
        // 处理实时数据
        // 如果队列满，丢弃最老的数据，处理最新的
    });
}
```

**⚠️ 注意：**
- 可能导致任务饥饿（老任务永远得不到执行）
- 不适合所有任务优先级相同的场景

**5. 自定义拒绝策略**

```java
// 记录日志 + 降级处理
public class LogAndFallbackPolicy implements RejectedExecutionHandler {

    private final FallbackHandler fallbackHandler;

    @Override
    public void rejectedExecution(Runnable r, ThreadPoolExecutor executor) {
        // 1. 记录日志
        log.error("任务被拒绝: {}, 线程池状态: poolSize={}, queueSize={}, activeCount={}",
                 r, executor.getPoolSize(), executor.getQueue().size(),
                 executor.getActiveCount());

        // 2. 监控告警
        metrics.increment("threadpool.rejected");

        // 3. 降级处理
        try {
            fallbackHandler.handle(r);
        } catch (Exception e) {
            log.error("降级处理失败", e);
        }
    }
}

// 使用
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    10, 20, 60, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(100),
    new LogAndFallbackPolicy(fallbackHandler)
);
```

| 策略                    | 任务丢失       | 异常抛出 | 阻塞调用线程 | 适用场景                         |
| ----------------------- | -------------- | -------- | ------------ | -------------------------------- |
| **AbortPolicy**         | ❌ 否           | ✅ 是     | ❌ 否         | 任务不能丢失，需要感知拒绝       |
| **CallerRunsPolicy**    | ❌ 否           | ❌ 否     | ✅ 是         | 任务不能丢失，可接受调用线程阻塞 |

| **DiscardOldestPolicy** | ✅ 是（老任务） | ❌ 否     | ❌ 否         | 新任务优先级更高                 |

### 5.1 Thread.join

#### 原理
- `join()` 方法让当前线程等待目标线程执行完成
- 底层通过 `wait()` 实现，目标线程结束时会调用 `notifyAll()`
- 可以指定超时时间：`join(long millis)`

#### 使用场景
- 主线程等待子线程完成后汇总结果
- 确保任务按顺序执行

#### 代码示例

**基本用法**：
```java
public class JoinExample {

    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(() -> {
            System.out.println("线程1开始执行");
            sleep(2000);
            System.out.println("线程1执行完成");
        }, "Thread-1");

        Thread t2 = new Thread(() -> {
            System.out.println("线程2开始执行");
            sleep(1000);
            System.out.println("线程2执行完成");
        }, "Thread-2");

        t1.start();
        t2.start();

        // 主线程等待 t1 和 t2 完成
        t1.join();
        t2.join();

        System.out.println("所有线程执行完成，主线程继续");
    }

    private static void sleep(long millis) {
        try {
            Thread.sleep(millis);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}
```

**顺序执行示例**：

### 5.2 CountDownLatch

#### 原理
- 基于 AQS（AbstractQueuedSynchronizer）实现
- 内部维护一个计数器，初始值为线程数量
- `countDown()` 递减计数器，`await()` 阻塞直到计数器为 0
- **一次性使用**，计数器不能重置

#### 使用场景
- 主线程等待多个子线程完成后继续执行
- 多个线程等待某个条件满足后同时开始执行
- 并行任务的结果汇总

#### 代码示例

**等待多个线程完成**：
```java
public class CountDownLatchExample {

    public static void main(String[] args) throws InterruptedException {
        int threadCount = 5;
        CountDownLatch latch = new CountDownLatch(threadCount);

        // 启动多个工作线程
        for (int i = 0; i < threadCount; i++) {
            final int taskId = i;
            new Thread(() -> {
                try {
                    System.out.println("任务 " + taskId + " 开始执行");
                    Thread.sleep((long) (Math.random() * 3000));
                    System.out.println("任务 " + taskId + " 执行完成");
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                } finally {
                    latch.countDown();  // 计数器减 1
                }
            }).start();
        }

        System.out.println("主线程等待所有任务完成...");
        latch.await();  // 阻塞直到计数器为 0
        System.out.println("所有任务完成，主线程继续执行");
    }
}
```

### 5.3 CyclicBarrier

#### 原理
- 基于 ReentrantLock 和 Condition 实现
- 让一组线程在屏障处等待，所有线程到达后统一释放
- **可重用**，屏障打开后自动重置
- 可选的屏障动作（barrierAction），在所有线程到达后、释放前执行

#### 使用场景
- 多线程分阶段任务，每个阶段需要所有线程完成后才能进入下一阶段
- MapReduce 计算模型
- 多线程游戏中的回合制同步

#### 代码示例

**基本用法**：
```java
public class CyclicBarrierExample {

    public static void main(String[] args) {
        int parties = 3;
        CyclicBarrier barrier = new CyclicBarrier(parties, () -> {
            // 所有线程到达屏障后执行
            System.out.println("所有线程已到达屏障，开始下一阶段\n");
        });

        for (int i = 0; i < parties; i++) {
            final int workerId = i;
            new Thread(() -> {
                try {
                    System.out.println("Worker " + workerId + " 执行阶段1");
                    Thread.sleep((long) (Math.random() * 2000));
                    System.out.println("Worker " + workerId + " 完成阶段1，等待其他线程");
                    barrier.await();  // 等待其他线程

                    System.out.println("Worker " + workerId + " 执行阶段2");
                    Thread.sleep((long) (Math.random() * 2000));
                    System.out.println("Worker " + workerId + " 完成阶段2，等待其他线程");
                    barrier.await();  // 等待其他线程

                    System.out.println("Worker " + workerId + " 执行阶段3");
                    Thread.sleep((long) (Math.random() * 2000));
                    System.out.println("Worker " + workerId + " 完成阶段3");

                } catch (InterruptedException | BrokenBarrierException e) {
                    e.printStackTrace();
                }
            }).start();
        }
    }
}
```

### 5.4 Semaphore

#### 原理
- 基于 AQS 实现
- 维护一组许可证（permits），线程获取许可证才能执行
- `acquire()` 获取许可证（阻塞），`release()` 释放许可证
- 支持公平模式和非公平模式

#### 使用场景
- 限制同时访问某个资源的线程数量
- 连接池、线程池的资源管理
- 限流控制
- 实现互斥锁（permits=1）

#### 代码示例

**限制并发访问数量**：
```java
public class SemaphoreExample {

    public static void main(String[] args) {
        // 只允许 3 个线程同时访问
        Semaphore semaphore = new Semaphore(3);

        for (int i = 0; i < 10; i++) {
            final int taskId = i;
            new Thread(() -> {
                try {
                    System.out.println("任务 " + taskId + " 等待获取许可证");
                    semaphore.acquire();  // 获取许可证
                    System.out.println("任务 " + taskId + " 获得许可证，开始执行");

                    // 模拟任务执行
                    Thread.sleep(2000);

                    System.out.println("任务 " + taskId + " 执行完成，释放许可证");
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                } finally {
                    semaphore.release();  // 释放许可证
                }
            }).start();
        }
    }
}
```

```java
public class ConnectionPool {

    private final Semaphore semaphore;
    private final List<Connection> connections;

    public ConnectionPool(int poolSize) {
        this.semaphore = new Semaphore(poolSize);
        this.connections = new ArrayList<>(poolSize);

        // 初始化连接池
        for (int i = 0; i < poolSize; i++) {
            connections.add(new Connection(i));
        }
    }

    public Connection getConnection() throws InterruptedException {
        semaphore.acquire();  // 获取许可证
        return getAvailableConnection();
    }

    public void releaseConnection(Connection connection) {
        if (returnConnection(connection)) {
            semaphore.release();  // 释放许可证
        }
    }

    private synchronized Connection getAvailableConnection() {
        for (Connection conn : connections) {
            if (!conn.isInUse()) {
                conn.setInUse(true);
                return conn;
            }
        }
        return null;
    }

    private synchronized boolean returnConnection(Connection connection) {
        connection.setInUse(false);
        return true;
    }

    static class Connection {
        private final int id;
        private boolean inUse;

        public Connection(int id) {
            this.id = id;
            this.inUse = false;
        }

        public void execute(String sql) throws InterruptedException {
            System.out.println("连接 " + id + " 执行: " + sql);
            Thread.sleep(1000);
        }

        public boolean isInUse() {
            return inUse;
        }

        public void setInUse(boolean inUse) {
            this.inUse = inUse;
        }
    }

    public static void main(String[] args) {
        ConnectionPool pool = new ConnectionPool(3);

        // 10 个线程竞争 3 个连接
        for (int i = 0; i < 10; i++) {
            final int taskId = i;
            new Thread(() -> {
                try {
                    System.out.println("任务 " + taskId + " 请求连接");
                    Connection conn = pool.getConnection();
                    System.out.println("任务 " + taskId + " 获得连接");

                    conn.execute("SELECT * FROM users WHERE id = " + taskId);

                    pool.releaseConnection(conn);
                    System.out.println("任务 " + taskId + " 释放连接");
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            }).start();
        }
    }
}
```

**限流器实现**：
```java
public class RateLimiter {

    private final Semaphore semaphore;
    private final int maxPermits;
    private final long periodMillis;

    public RateLimiter(int maxPermits, long periodMillis) {
        this.semaphore = new Semaphore(maxPermits);
        this.maxPermits = maxPermits;
        this.periodMillis = periodMillis;

        // 定期补充许可证
        schedulePermitRefresh();
    }

    public boolean tryAcquire() {
        return semaphore.tryAcquire();
    }

    public void acquire() throws InterruptedException {
        semaphore.acquire();
    }

    private void schedulePermitRefresh() {
        new Thread(() -> {
            while (true) {
                try {
                    Thread.sleep(periodMillis);
                    // 重置许可证
                    int availablePermits = semaphore.availablePermits();
                    if (availablePermits < maxPermits) {
                        semaphore.release(maxPermits - availablePermits);
                    }
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    break;
                }
            }
        }, "PermitRefresher").start();
    }

    public static void main(String[] args) {
        // 每秒最多 5 个请求
        RateLimiter limiter = new RateLimiter(5, 1000);

        for (int i = 0; i < 20; i++) {
            final int requestId = i;
            new Thread(() -> {
                try {
                    if (limiter.tryAcquire()) {
                        System.out.println("请求 " + requestId + " 通过限流，时间: " + System.currentTimeMillis());
                    } else {
                        System.out.println("请求 " + requestId + " 被限流");
                    }
                } catch (Exception e) {
                    e.printStackTrace();
                }
            }).start();

            try {
                Thread.sleep(100);  // 每 100ms 发送一个请求
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }
    }
}
```

### 5.5 ReentrantLock + Condition

#### 原理
- ReentrantLock 提供显式锁机制
- Condition 提供线程间的协调机制（类似 wait/notify）
- 一个 Lock 可以创建多个 Condition，实现更精细的控制
- 支持公平锁和非公平锁

#### 使用场景
- 需要精确控制线程执行顺序
- 多个条件的复杂协调
- 生产者-消费者模式
- 交替打印、顺序执行等场景

#### 代码示例

**交替打印（两个线程）**：
```java
public class AlternatePrinting {

    private final ReentrantLock lock = new ReentrantLock();
    private final Condition condition = lock.newCondition();
    private boolean flag = true;  // true: 线程1打印, false: 线程2打印

    public void printOdd(int num) {
        lock.lock();
        try {
            while (!flag) {
                condition.await();  // 等待
            }
            System.out.println("线程1: " + num);
            flag = false;
            condition.signal();  // 唤醒线程2
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        } finally {
            lock.unlock();
        }
    }

    public void printEven(int num) {
        lock.lock();
        try {
            while (flag) {
                condition.await();  // 等待
            }
            System.out.println("线程2: " + num);
            flag = true;
            condition.signal();  // 唤醒线程1
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        } finally {
            lock.unlock();
        }
    }

    public static void main(String[] args) {
        AlternatePrinting printer = new AlternatePrinting();

        new Thread(() -> {
            for (int i = 1; i <= 10; i += 2) {
                printer.printOdd(i);
            }
        }).start();

        new Thread(() -> {
            for (int i = 2; i <= 10; i += 2) {
                printer.printEven(i);
            }
        }).start();
    }
}
```

**有界阻塞队列实现**：
```java
public class BoundedBlockingQueue<T> {

    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull = lock.newCondition();
    private final Condition notEmpty = lock.newCondition();
    private final Object[] items;
    private int putIndex, takeIndex, count;

    public BoundedBlockingQueue(int capacity) {
        this.items = new Object[capacity];
    }

    public void put(T item) throws InterruptedException {
        lock.lock();
        try {
            while (count == items.length) {
                notFull.await();  // 队列满，等待
            }
            items[putIndex] = item;
            putIndex = (putIndex + 1) % items.length;
            count++;
            System.out.println("生产: " + item + ", 队列大小: " + count);
            notEmpty.signal();  // 唤醒消费者
        } finally {
            lock.unlock();
        }
    }

    @SuppressWarnings("unchecked")
    public T take() throws InterruptedException {
        lock.lock();
        try {
            while (count == 0) {
                notEmpty.await();  // 队列空，等待
            }
            T item = (T) items[takeIndex];
            items[takeIndex] = null;
            takeIndex = (takeIndex + 1) % items.length;
            count--;
            System.out.println("消费: " + item + ", 队列大小: " + count);
            notFull.signal();  // 唤醒生产者
            return item;
        } finally {
            lock.unlock();
        }
    }

    public static void main(String[] args) {
        BoundedBlockingQueue<Integer> queue = new BoundedBlockingQueue<>(5);

        // 生产者
        new Thread(() -> {
            try {
                for (int i = 0; i < 10; i++) {
                    queue.put(i);
                    Thread.sleep(100);
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }, "Producer").start();

        // 消费者
        new Thread(() -> {
            try {
                for (int i = 0; i < 10; i++) {
                    queue.take();
                    Thread.sleep(300);
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }, "Consumer").start();
    }
}
```

### 5.6 方法对比总结

| 方法                        | 特点                   | 适用场景              | 可重用 | 复杂度 |
| --------------------------- | ---------------------- | --------------------- | ------ | ------ |
| `Thread.join`               | 简单直接，等待线程结束 | 主线程等待子线程完成  | 否     | 低     |
| `CountDownLatch`            | 一次性计数器，灵活     | 多线程协作、并发测试  | 否     | 中     |
| `CyclicBarrier`             | 可重用屏障，支持回调   | 多阶段任务、MapReduce | 是     | 中     |
| `Semaphore`                 | 许可证机制，限流       | 资源池、限流控制      | 是     | 中     |
| `ReentrantLock + Condition` | 精确控制，多条件       | 复杂协调、顺序执行    | 是     | 高     |

**选择建议**：
- 简单等待：使用 `Thread.join`
- 一次性协作：使用 `CountDownLatch`
- 多轮协作：使用 `CyclicBarrier`
- 资源限制：使用 `Semaphore`
- 复杂协调：使用 `ReentrantLock + Condition`

## 6. CAS 与原子类

### 6.1 基本概念
- Compare-And-Swap：比较期望值与内存中当前值相等，则写入新值；否则重试。
- 依赖 CPU 指令，保证单个变量更新的原子性。

### 6.2 优缺点
- **优点**：无锁、性能好、避免阻塞。
- **缺点**：ABA 问题、自旋开销、一次只能更新一个变量。

### 6.3 示例
```java
public class CasCounter {
	private final AtomicInteger counter = new AtomicInteger();
	public void inc() {
		int expect, update;
		do {
			expect = counter.get();
			update = expect + 1;
		} while (!counter.compareAndSet(expect, update));
	}
}
```

## 7. ABA 问题与解法

### 7.1 问题描述
- 线程读取值 A，准备写入 B；期间其他线程把值改成 C 再改回 A，CAS 仍然成功，但数据已变化。

**ABA 问题示例：**
```java
// ABA 问题示例
AtomicReference<Node> head = new AtomicReference<>(nodeA);

// 线程 1：准备 CAS
Node oldHead = head.get();  // 读到 A
// ... 准备把 A 改成 B

// 线程 2：快速执行
head.compareAndSet(nodeA, nodeC);  // A -> C
head.compareAndSet(nodeC, nodeA);  // C -> A（又变回 A）

// 线程 1：继续 CAS
head.compareAndSet(oldHead, nodeB);  // 成功！但 A 已经不是原来的 A
```

**问题本质：** CAS 只比较引用相等，不知道中间发生了什么。

### 7.2 方案
1. **AtomicStampedReference / AtomicMarkableReference**：引入版本号或标记。

```java
AtomicStampedReference<String> ref = new AtomicStampedReference<>("A", 0);
int stamp = ref.getStamp();
boolean ok = ref.compareAndSet("A", "B", stamp, stamp + 1);
```

2. **LongAdder / LongAccumulator**：分段累加，避免单点 CAS 热点，适合计数场景。
3. **锁（ReentrantLock / synchronized）**：在逻辑复杂或需要批量更新数据时，使用显式锁串行化。

### 7.3 什么情况下使用原子类

#### 1. 高并发计数/累加场景

```java
    }

        return requestCount.get();

// ❌ 错误：普通变量

```

- 限流器的计数
- 监控指标埋点
- 分布式 ID 生成（本地部分）

#### 2. 无锁状态机/标志位

**典型场景：**

- 任务状态流转
- 单次初始化标志（`AtomicBoolean initialized`）
- 优雅停机标志

#### 3. 无锁数据结构/算法

```java
// ✅ 需要原子类：无锁栈
public class LockFreeStack<T> {
    private AtomicReference<Node<T>> top = new AtomicReference<>();

    public void push(T value) {
        Node<T> newNode = new Node<>(value);
        Node<T> oldTop;
        do {
            oldTop = top.get();
            newNode.next = oldTop;
        } while (!top.compareAndSet(oldTop, newNode));  // CAS 重试
    }

    public T pop() {
        Node<T> oldTop, newTop;
        do {
            oldTop = top.get();
            if (oldTop == null) return null;
            newTop = oldTop.next;
        } while (!top.compareAndSet(oldTop, newTop));
        return oldTop.value;
    }
}
```

**典型场景：**
- 无锁队列/栈
- 无锁链表
- 对象池的引用管理

#### 4. 替代简单的 synchronized

```java

// ❌ 过度设计：简单计数用锁太重
public class HeavyIdGenerator {
    private long id = 0;
    private final Object lock = new Object();

    public long nextId() {
        synchronized (lock) {
            return ++id;
        }
    }
}
```

**何时用原子类代替锁：**
- 单个变量的简单操作（读、写、CAS）
- 无需保护多个变量的一致性
- 追求更高性能（无锁）

### 7.4 什么情况下需要考虑 ABA 问题

#### 1. 需要考虑 ABA 的场景

**场景 1：链表/栈的节点复用**

```java
// ⚠️ 有 ABA 风险：节点可能被回收后重新分配到同一地址
public class LockFreeStack<T> {
    private AtomicReference<Node<T>> top = new AtomicReference<>();

    public T pop() {
        Node<T> oldTop, newTop;
        do {
            oldTop = top.get();  // 读到节点 A
            if (oldTop == null) return null;
            newTop = oldTop.next;

            // 问题：如果 oldTop 被其他线程 pop 后又 push 回来
            // 地址相同但 next 可能已经变了
        } while (!top.compareAndSet(oldTop, newTop));
        return oldTop.value;
    }
}

// ✅ 解决：使用 AtomicStampedReference
public class SafeLockFreeStack<T> {
    private AtomicStampedReference<Node<T>> top =
        new AtomicStampedReference<>(null, 0);

    public T pop() {
        Node<T> oldTop, newTop;
        int[] stampHolder = new int[1];
        do {
            oldTop = top.get(stampHolder);
            int oldStamp = stampHolder[0];
            if (oldTop == null) return null;
            newTop = oldTop.next;
        } while (!top.compareAndSet(oldTop, newTop, oldStamp, oldStamp + 1));
        return oldTop.value;
    }
}
```

**场景 2：内存回收/对象池**

```java
// ⚠️ 有 ABA 风险：对象被回收后重新分配
public class ObjectPool<T> {
    private AtomicReference<T> available = new AtomicReference<>();

    public T acquire() {
        T obj;
        do {
            obj = available.get();
            if (obj == null) return createNew();
        } while (!available.compareAndSet(obj, null));
        return obj;
    }

    public void release(T obj) {
        T old;
        do {
            old = available.get();
        } while (!available.compareAndSet(old, obj));
        // 问题：obj 可能是之前被回收的对象，地址复用
    }
}
```

**场景 3：账户余额/库存扣减（业务逻辑依赖历史）**

```java
// ⚠️ 有 ABA 风险：余额从 100 -> 50 -> 100，但中间发生了交易
public class Account {
    private AtomicInteger balance = new AtomicInteger(100);

    public boolean withdraw(int amount) {
        int oldBalance, newBalance;
        do {
            oldBalance = balance.get();  // 读到 100
            if (oldBalance < amount) return false;
            newBalance = oldBalance - amount;

            // 问题：如果余额从 100 -> 50（消费）-> 100（充值）
            // CAS 会成功，但业务上可能需要知道中间发生了变化
        } while (!balance.compareAndSet(oldBalance, newBalance));
        return true;
    }
}

// ✅ 解决：使用版本号
public class SafeAccount {
    private AtomicStampedReference<Integer> balance =
        new AtomicStampedReference<>(100, 0);

    public boolean withdraw(int amount) {
        int[] stampHolder = new int[1];
        Integer oldBalance, newBalance;
        do {
            oldBalance = balance.get(stampHolder);
            int oldStamp = stampHolder[0];
            if (oldBalance < amount) return false;
            newBalance = oldBalance - amount;
        } while (!balance.compareAndSet(oldBalance, newBalance,
                                        oldStamp, oldStamp + 1));
        return true;
    }
}
```

#### 2. 不需要考虑 ABA 的场景

**场景 1：简单计数/累加**

```java
// ✅ 不需要担心 ABA：只关心最终值
AtomicLong counter = new AtomicLong(0);
counter.incrementAndGet();  // 从 5 -> 3 -> 5 无所谓，只要能加 1
```

**场景 2：状态标志（只关心当前状态）**

```java
// ✅ 不需要担心 ABA：只关心当前是否启用
AtomicBoolean enabled = new AtomicBoolean(true);
enabled.compareAndSet(true, false);  // true -> false -> true 无所谓
```

**场景 3：不可变对象的引用**

```java
// ✅ 不需要担心 ABA：对象内容不变
AtomicReference<String> name = new AtomicReference<>("Alice");
name.compareAndSet("Alice", "Bob");  // String 不可变，没有 ABA 风险
```

### 7.5 决策树

```
是否需要多线程共享变量？
├─ 否 → 用普通变量
└─ 是 → 继续

是否只是简单的读/写/计数？
├─ 是 → 用 AtomicXxx（不用担心 ABA）
└─ 否 → 继续

是否涉及链表/栈/队列的节点操作？
├─ 是 → 考虑 ABA，用 AtomicStampedReference

```

## 8. AQS 工作原理
- `AbstractQueuedSynchronizer` 是多数同步器（`ReentrantLock`、`Semaphore`、`CountDownLatch` 等）的基础。

### 8.1 组成
- `state`：整型共享状态。
- FIFO 双向链表队列：保存等待线程（Node）。
- 模式：独占 (`EXCLUSIVE`) 与共享 (`SHARED`)。

### 8.2 核心模板方法
- `tryAcquire/tryRelease`
- `tryAcquireShared/tryReleaseShared`
- `isHeldExclusively`

### 8.3 获取/释放流程
1. 调用 `acquire(arg)`：若 `tryAcquire` 成功则返回，否则将线程封装为 Node 入队并挂起（`park`）。
2. 释放时调用 `release(arg)`：更新 `state`，唤醒队列下一个节点。
3. 共享模式下可同时唤醒多个节点。

定制同步器、队列节点、源码与时序图见 [[01-Java基础与并发/并发编程/并发深入了解#11. AQS：定制同步器、源码与队列时序]]。

## 9. synchronized 深入理解

`synchronized` 是基于对象监视器的可重入互斥机制，适合结构简单、作用域清晰的临界区；需要可中断获取、超时、公平策略或多个条件队列时，选择 `ReentrantLock`。

字节码、Mark Word 与 HotSpot 锁优化属于实现细节，见 [[01-Java基础与并发/并发编程/并发深入了解#12. synchronized：字节码、对象头与 JVM 锁优化]]。

### 9.4 与 ReentrantLock 对比

| 特性      | synchronized  | ReentrantLock                |
| --------- | ------------- | ---------------------------- |
| 加锁/释放 | 自动          | 手动                         |
| 公平性    | 不支持        | 支持公平/非公平              |
| 可中断    | 不可中断      | `lockInterruptibly`          |
| 条件队列  | `wait/notify` | 多个 `Condition`             |
| 监控指标  | 无直接 API    | `isLocked`、`getQueueLength` |

**结论**：简单场景首选 `synchronized`；需要灵活性或监控时使用 `ReentrantLock`。

## 10. 内存模型、指令重排与 volatile

### 10.1 指令重排类型
- 编译器优化、CPU 流水线、JIT 优化。
- 在单线程下等价，在多线程下可能破坏先后顺序。

### 10.2 Java 内存模型 (JMM)
- 线程之间通过主内存共享数据；每个线程有工作内存副本。
- `happens-before` 规则确保可见性与有序性。

完整规则推导见 [[01-Java基础与并发/并发编程/并发深入了解#13. JMM：happens-before 规则推导]]。

### 10.3 volatile 的作用
- 对同一 `volatile` 变量的写入，对后续读取该变量的线程可见；写之前的普通写也会随之对读线程可见。
- 建立必要的有序性约束：编译器和处理器不能把 `volatile` 读/写两侧的一些内存操作随意重排。不要将 JMM 的“主内存/工作内存”抽象理解为每次访问的物理内存路径。
- 不保证复合操作的原子性（如 `count++` 仍需锁或原子类）。volatile 只管“这一次读/写”和前后操作的有序与可见，不负责把“一串操作”变成一个不可分割的大原子块。（只是建立了屏障，不能保证屏障内的原子操作。）

```java
class StopFlag {
	private volatile boolean running = true;
	void stop() { running = false; }
	void work() {
		while (running) {
			// do work
		}
	}
}
```

### 10.4 双重检查锁 (DCL) 单例
```java
class Singleton {
	private static volatile Singleton INSTANCE;
	static Singleton getInstance() {
		if (INSTANCE == null) {
			synchronized (Singleton.class) {
				if (INSTANCE == null) {
					INSTANCE = new Singleton();
				}
			}
		}
		return INSTANCE;
	}
}
```

## 11. ThreadLocal 实战

### 11.1 基本用法
	``` java
	class ContextHolder {
		private static final ThreadLocal<String> TRACE_ID = ThreadLocal.withInitial(() -> "");
		static void set(String id) { TRACE_ID.set(id); }
		static String get() { return TRACE_ID.get(); }
		static void clear() { TRACE_ID.remove(); }
	}
	```

### 11.2 适用场景
- 请求上下文、每线程临时状态、`SimpleDateFormat` 等非线程安全对象的隔离。数据库连接应由连接池/框架管理，不要把裸连接作为跨业务生命周期的 `ThreadLocal` 状态。

### 11.3 注意事项
- 在线程池中必须调用 `remove()`，否则复用线程会携带旧数据，导致内存泄漏或脏数据。
- 对象过大或生命周期过长不适合放入 ThreadLocal。
- 可结合 `InheritableThreadLocal` 在子线程继承上下文（虚拟线程中需注意性能）。

### 11.4 ThreadLocal 内存泄漏原理

#### 1. 底层数据结构

```java
// Thread 类中的字段
public class Thread {
    ThreadLocal.ThreadLocalMap threadLocals = null;  // 每个线程持有自己的 Map
}

// ThreadLocalMap 是 ThreadLocal 的静态内部类
static class ThreadLocalMap {
    static class Entry extends WeakReference<ThreadLocal<?>> {
        Object value;  // 强引用

        Entry(ThreadLocal<?> k, Object v) {
            super(k);  // key 是弱引用
            value = v;
        }
    }

    private Entry[] table;  // 数组存储
    private int size;
}
```

**关键结构：**
- 每个 `Thread` 对象持有一个 `ThreadLocalMap`
- `ThreadLocalMap` 内部是 `Entry[]` 数组
- `Entry` 的 key 是 `ThreadLocal` 对象（**弱引用**）
- `Entry` 的 value 是实际存储的值（**强引用**）

#### 2. 引用链关系

```
Thread (强引用)
  └─> ThreadLocalMap (强引用)
        └─> Entry[] (强引用)
              └─> Entry (强引用)
                    ├─> key: ThreadLocal (弱引用) ⚠️
                    └─> value: 实际对象 (强引用) ⚠️
```

#### 3. 内存泄漏发生过程

**场景：线程池中使用 ThreadLocal**

```java
// 步骤 1：创建 ThreadLocal 并设置值
ThreadLocal<BigObject> threadLocal = new ThreadLocal<>();
threadLocal.set(new BigObject());  // 10MB 对象

// 步骤 2：业务逻辑执行完毕
// threadLocal 局部变量出栈，没有强引用指向 ThreadLocal 对象

// 步骤 3：GC 发生
// - ThreadLocal 对象被回收（因为 Entry 的 key 是弱引用）
// - Entry 变成 key=null, value=BigObject(10MB)

// 步骤 4：线程池复用线程
// - Thread 对象还活着（线程池中）
// - ThreadLocalMap 还在
// - Entry[key=null, value=BigObject(10MB)] 还在 ⚠️ 内存泄漏！
```

**时间线演示：**

```
T0: threadLocal.set(bigObject)
    Thread → ThreadLocalMap → Entry[key=ThreadLocal对象, value=bigObject(10MB)]

T1: 方法执行完毕，threadLocal 局部变量出栈
    无强引用指向 ThreadLocal 对象

T2: GC 触发
    ThreadLocal 对象被回收（弱引用）
    Thread → ThreadLocalMap → Entry[key=null, value=bigObject(10MB)] ⚠️

T3: 线程被线程池复用，执行新任务
    bigObject(10MB) 仍然占用内存，无法回收 ⚠️
```

#### 4. 为什么 key 用弱引用？

**如果 key 是强引用会怎样？**

```java
// 假设 Entry 的 key 是强引用
Thread → ThreadLocalMap → Entry[key=ThreadLocal对象(强引用), value=bigObject]
                                    ↑
                                    永远无法回收！
```

- ThreadLocal 对象永远无法被 GC
- 即使业务代码不再使用，ThreadLocal 对象也会一直存在
- 更严重的内存泄漏

**用弱引用的好处：**
- ThreadLocal 对象可以被 GC
- 至少 key 能被回收，Entry 变成 `key=null`
- ThreadLocalMap 有机会清理这些 `key=null` 的 Entry

#### 5. ThreadLocalMap 的自清理机制

ThreadLocalMap 在以下时机会清理 `key=null` 的 Entry：

```java
// 1. set() 时
public void set(ThreadLocal<?> key, Object value) {
    // ...
    // 遇到 key=null 的 Entry，会清理
    if (k == null) {
        replaceStaleEntry(key, value, i);
        return;
    }
}

// 2. get() 时
public Entry getEntry(ThreadLocal<?> key) {
    // ...
    // 遇到 key=null 的 Entry，会清理
    if (e != null && e.get() == null) {
        expungeStaleEntry(i);
    }
}

// 3. remove() 时
public void remove(ThreadLocal<?> key) {
    // 直接清理 Entry
    e.clear();
    expungeStaleEntry(i);
}
```

**但是：** 如果线程一直不调用 `set/get/remove`，这些 `key=null` 的 Entry 永远不会被清理！

#### 6. 内存泄漏的真正原因

```
❌ 常见误解：弱引用导致内存泄漏
✅ 真正原因：
   1. 线程长期存活（线程池）
   2. ThreadLocal 使用后没有调用 remove()
   3. Entry 的 value 是强引用，无法被 GC
   4. 自清理机制没有触发（线程不再调用 set/get）
```

#### 7. 实战案例：内存泄漏复现

```java
public class ThreadLocalLeakDemo {

    // 10MB 的大对象
    static class BigObject {
        private byte[] data = new byte[10 * 1024 * 1024];
    }

    public static void main(String[] args) throws Exception {
        ExecutorService executor = Executors.newFixedThreadPool(1);

        // 提交 10 个任务
        for (int i = 0; i < 10; i++) {
            executor.submit(() -> {
                // ❌ 错误：没有 remove()
                ThreadLocal<BigObject> local = new ThreadLocal<>();
                local.set(new BigObject());  // 10MB

                System.out.println("Task executed, memory leaked!");
                // local 出栈，ThreadLocal 对象被 GC
                // 但 BigObject(10MB) 还在 ThreadLocalMap 中
            });

            Thread.sleep(1000);
            System.gc();  // 手动 GC
        }

        // 结果：线程池中的 1 个线程，ThreadLocalMap 中有 10 个 Entry
        // 每个 Entry 的 value 是 10MB，总共 100MB 泄漏！

        executor.shutdown();
    }
}
```

**内存分析：**
```
线程池线程 Thread-1:
  ThreadLocalMap:
    Entry[0]: key=null, value=BigObject(10MB)  // 第 1 次任务
    Entry[1]: key=null, value=BigObject(10MB)  // 第 2 次任务
    Entry[2]: key=null, value=BigObject(10MB)  // 第 3 次任务
    ...
    Entry[9]: key=null, value=BigObject(10MB)  // 第 10 次任务

总泄漏：100MB
```

#### 8. 正确使用方式

```java
// ✅ 方式 1：手动 remove（推荐）
public void handleRequest() {
    ThreadLocal<User> userContext = new ThreadLocal<>();
    try {
        userContext.set(getCurrentUser());
        // 业务逻辑
    } finally {
        userContext.remove();  // 必须调用！
    }
}

// ✅ 方式 2：使用 static final（避免重复创建）
public class UserContext {
    private static final ThreadLocal<User> USER = new ThreadLocal<>();

    public static void set(User user) {
        USER.set(user);
    }

    public static User get() {
        return USER.get();
    }

    public static void clear() {
        USER.remove();  // 必须在请求结束时调用
    }
}

// Controller 层
@RestController
public class UserController {

    @GetMapping("/user")
    public String getUser() {
        try {
            UserContext.set(loadUser());
            return service.process();
        } finally {
            UserContext.clear();  // 必须清理
        }
    }
}

// ✅ 方式 3：使用拦截器统一清理（Spring）
@Component
public class ThreadLocalCleanInterceptor implements HandlerInterceptor {

    @Override
    public void afterCompletion(HttpServletRequest request,
                                HttpServletResponse response,
                                Object handler, Exception ex) {
        UserContext.clear();  // 统一清理
        TraceContext.clear();
        // 清理所有 ThreadLocal
    }
}
```

#### 10. 总结

| 问题                    | 原因                           | 解决方案                          |
| ----------------------- | ------------------------------ | --------------------------------- |
| **内存泄漏**            | 线程池复用线程 + 没有 remove() | 必须在 finally 中调用 remove()    |
| **脏数据**              | 线程复用，读到上次请求的数据   | 每次使用前 set()，使用后 remove() |
| **为什么 key 是弱引用** | 让 ThreadLocal 对象可以被 GC   | 减轻泄漏程度，但不能完全避免      |
| **为什么还会泄漏**      | value 是强引用 + 线程长期存活  | 主动调用 remove()                 |

**核心原则：**
```java
// 线程池环境下使用 ThreadLocal 的铁律
try {
    threadLocal.set(value);
    // 业务逻辑
} finally {
    threadLocal.remove();  // 必须！必须！必须！
}
```

## 12. 死锁：条件、排查与治理

### 12.1 四个必要条件
1. **互斥**：资源一次只供一个线程使用。
2. **占有且等待**：持有资源同时请求其他资源。
3. **不可抢占**：资源不能被强制抢走。
4. **循环等待**：两个或多个线程形成环状等待链。

### 12.2 示例
```java
Object lockA = new Object();
Object lockB = new Object();
		new Thread(() -> {
	synchronized (lockA) {
		sleep(100);
		synchronized (lockB) {}
	}
}).start();
		new Thread(() -> {
	synchronized (lockB) {
		sleep(100);
		synchronized (lockA) {}
	}
}).start();
```

### 12.3 排查手段
- `jps -l` 查进程 ID，`jstack <pid>` 定位死锁线程，输出 `Found one Java-level deadlock`。
- 可使用 `jconsole`、`VisualVM`、`Java Flight Recorder` 实时监控线程状态。

### 12.4 预防策略
- **统一加锁顺序**：所有线程按同样顺序申请锁，破坏循环等待。
- **tryLock + 超时**：获取失败时释放已持有锁并重试，避免长期阻塞。
- **资源层限流**：减少同时持有多把锁的需求。
- **监控告警**：线程池堆栈定期采样，发现长时间阻塞及时告警。

### 12.5 进一步实践建议
- 建立统一的线程池与锁使用规范（命名、监控、降级策略）。
- 在关键并发组件上补充单元测试 + JMH 基准，验证可见性与性能假设。
- 结合分布式场景（如分布式锁、跨 JVM 协调）时，先确保本地并发模型牢固，再延伸到多节点一致性策略。

## 13. 虚拟线程和普通线程

### 13.1 先给结论
- **普通线程（platform thread）**：OS 级线程，1:1 绑定内核线程，创建/切换成本高。
- **虚拟线程（virtual thread）**：JDK 自带的用户态线程，极轻量，可在同一 OS 线程上挂载和切换海量虚拟线程。
- **用法**：语法几乎一致，差别主要在创建方式与调度器。
- **场景**：虚拟线程适合 I/O 密集型高并发请求；CPU 密集且线程数有限的场景收益有限。

### 13.2 核心概念
**普通线程（Platform Thread）**
- `new Thread(...)`、`Executors.newFixedThreadPool(...)` 创建的就是平台线程。
- 每个 Java 线程都绑定一个 OS 线程，默认 1MB 左右栈空间，切换由操作系统完成。
- 高并发 I/O 场景下需要开大量线程，容易耗尽内存并导致上下文切换抖动。

**虚拟线程（Virtual Thread）**
- 来自 Project Loom，JDK 21 已 GA。
- JVM 在用户态调度，可将栈拆分成分段堆分配；对 JDK 支持的阻塞 I/O 和 `LockSupport.park()`，通常会挂起虚拟线程并释放 carrier thread；某些 native 调用或同步代码可能造成 carrier 被占用。
- 阻塞结束后再把虚拟线程挂回某个 carrier OS 线程继续执行。

> 一句话：普通线程“贵又大”，虚拟线程“便宜又小，可以批发”。

### 13.3 基本用法示例
**平台线程**
```java
Thread t = new Thread(() ->
	System.out.println("hello from platform thread: " + Thread.currentThread())
);
t.start();

ExecutorService executor = Executors.newFixedThreadPool(200);
executor.submit(() -> {
	// do something
});
```

**虚拟线程（推荐 `Thread.ofVirtual()`）**
```java
Thread t = Thread.ofVirtual().start(() ->
	System.out.println("hello from virtual thread: " + Thread.currentThread())
);
```

**按任务建虚拟线程的执行器**
```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
	for (int i = 0; i < 10_000; i++) {
		int id = i;
		executor.submit(() -> handleRequest(id));
	}
} // try-with-resources 自动优雅关闭
```

> 虚拟线程通常不应放入传统固定大小线程池；可直接使用 `newVirtualThreadPerTaskExecutor()`。但它不替代对数据库连接、下游 QPS、内存和任务数量的限流或背压控制。

### 13.4 工程维度差异
| 关注点   | 平台线程                 | 虚拟线程                                           |
| -------- | ------------------------ | -------------------------------------------------- |
| 调度模型 | OS 调度，1:1 映射        | JVM M:N 调度到少量 carrier 线程                    |
| 阻塞 I/O | 阻塞通常占用 OS 线程       | JDK 支持的阻塞点通常会挂起虚拟线程；需留意 pinning 与 native 调用 |
| 线程数量 | 上限受 OS 线程、线程栈与内存限制 | 可创建数量通常更多，仍受堆、任务栈与外部资源限制 |
| 内存开销 | 固定大栈                 | 栈分段、按需增长、可挂到堆上                       |
| 代码风格 | 为高并发常用 NIO/回调    | 直接写同步阻塞代码，JVM 伪非阻塞                   |
| 观测调试 | Thread dump 可见业务线程 | Thread dump 同样可见虚拟线程栈，carrier 主要跑调度 |

### 13.5 典型场景
**非常适合**
1. **高并发 I/O 服务**：Web/RPC 网关、HTTP 客户端、爬虫——“一个请求一个虚拟线程”，不再纠结线程池 size。
2. **批处理 / ETL / 爬虫**：大量网络或数据库 I/O，虚拟线程能自动弹性。
3. **长连接/协议服务**：IM、WebSocket、长连接网关——一个连接一个虚拟线程即可。

**收益有限**
1. **CPU 密集场景**：瓶颈在 CPU，虚拟线程不能“变出”额外核心，仍需合理的 platform 线程池/ForkJoinPool。
2. **依赖阻塞 native 调用**：若 native 层阻塞 OS 线程，虚拟线程无法解挂，会退化为平台线程的成本。

### 13.6 线程池与协程思维
- 虚拟线程极轻量，传统“少量线程复用任务”的线程池意义降低，`newVirtualThreadPerTaskExecutor()` 本质是“一任务一线程”。
- 模型类似 Go 的 goroutine（M:N 调度），不同之处在于 Java 仍然保留 `Thread` 抽象，对旧代码更友好。

### 13.7 实战注意事项
1. **避免 busy-wait**：虚拟线程里长时间 `while(!flag){}` 会占满 carrier 线程，改用 `LockSupport.park()`、`Condition`、`CountDownLatch` 等同步工具。
2. **评估第三方库**：大锁或长时间阻塞的库会拖慢虚拟线程；必要时隔离在 platform 线程池中。
3. **谨慎使用 ThreadLocal**：虚拟线程数量巨大，ThreadLocal 滥用会成为内存炸弹，能参数传递就传参。
4. **CPU 密集任务单独托管**：将重计算任务下发到专门的平台线程池，避免占用 carrier。

### 13.8 一句话总结
> 虚拟线程让 Java 可以以同步、阻塞的代码风格处理更多 I/O 等待任务。它提升的是并发规模与吞吐潜力，不会让单次计算或外部调用天然更快；仍需评估限流、连接池与 pinning。

## 14. CompletableFuture实战

### 14.1 它到底是什么：Future + CompletionStage 的混合体

```java
 //这货有两个身份：
public class CompletableFuture<T>
        implements Future<T>, CompletionStage<T> {
}
```
- 作为 Future：表示“将来某个时间会给你一个 T 结果”，可以 get()/join()、cancel()。
- 作为 CompletionStage：可以在完成后触发一系列“后续动作”（thenXXX），形成 异步任务流水线。

多了两个字 "Completable"，意思是：
- 既可以自己跑异步得到结果（supplyAsync/runAsync），
- 也可以由别人来调用 complete() / completeExceptionally() 把它“完成”。

等价于 Java 版的 Promise。

### 14.2 常见创建姿势：谁来算、在哪儿算

1. 直接 new，之后手动 complete
```java
CompletableFuture<String> cf = new CompletableFuture<>();
```
2. 起一个“有返回值”的异步任务
```java
CompletableFuture<String> cf1 =
        CompletableFuture.supplyAsync(() -> {
            return queryFromDb();
        });
```
3. 起一个“无返回值”的异步任务
```java
CompletableFuture<Void> cf2 =
        CompletableFuture.runAsync(() -> {
            doSomething();
        });
```
4. 指定线程池
    ```java
    ExecutorService executor = Executors.newFixedThreadPool(8);
    CompletableFuture<String> cf3 =
            CompletableFuture.supplyAsync(() -> queryFromDb(), executor);
    ```
    - 不传 executor 时，会用 ForkJoinPool.commonPool() 这个全局池。
    - 在虚拟线程时代，可以这样配合：
        ```java
        ExecutorService vExecutor = Executors.newVirtualThreadPerTaskExecutor();
        CompletableFuture<String> cf4 =
                CompletableFuture.supplyAsync(() -> queryFromDb(), vExecutor);
        ```
        - 逻辑上就是“每个任务跑在一个虚拟线程里”。

### 14.3 最核心的能力：链式操作（流式异步）
1. 基于结果的“变换”/“消费”
    - 假设有一个 CompletableFuture<T>：
    - thenApply(fn)：接收前一步结果，计算一个新结果，返回 CompletableFuture
        ```java
            CompletableFuture<User> userFuture = queryUserAsync();
            CompletableFuture<String> nameFuture =
                userFuture.thenApply(user -> user.getName());
        ```
    - thenAccept(consumer)：接收结果，消耗一下，不返回新值
        ```java
        userFuture.thenAccept(user -> log.info("user: {}", user));
        ```

    - thenRun(runnable)：只关心“完成事件”，不关心结果
        ```java
        userFuture.thenRun(() -> log.info("user loaded."));
        ```
2. thenApply vs thenCompose
    - 这是面试爱问点。
    - thenApply：结果 -> 另一个 CompletableFuture，但不会“拆开”
        ```java
        CompletableFuture<CompletableFuture<Order>> nested =
            userFuture.thenApply(user -> queryOrderAsync(user.getId()));
        ```
    - thenCompose：把 CompletableFuture<CompletableFuture> 拉平成 CompletableFuture
        ```java
        CompletableFuture<Order> flat =
            userFuture.thenCompose(user -> queryOrderAsync(user.getId()));
        ```
    - 记忆方法：
        - thenApply：普通函数 T -> U
        - thenCompose：扁平化异步 T -> CompletableFuture，类似 Stream 里的 flatMap。
    - 典型场景：前一个异步结果出来后，发起下一个异步，不用嵌套 future。

3. 多任务组合：并发 + 汇总
    - 两个任务结果合并：thenCombine
        ```java
        CompletableFuture<User> userFuture = queryUserAsync();
        CompletableFuture<List<Order>> orderFuture = queryOrdersAsync();
        CompletableFuture<UserWithOrders> result =
            userFuture.thenCombine(orderFuture, (user, orders) -> {
                return new UserWithOrders(user, orders);
            });
        ```
    - 两者谁先完成都行，thenCombine 会在两者都完成后执行合并函数。

4. 等一群任务都完：allOf
    ```java
    CompletableFuture<Void> all =
        CompletableFuture.allOf(cf1, cf2, cf3);
    all.join(); // 等所有都执行完
    ```
    - 如果你想拿回结果：
        ```java
        List<Object> results = Stream.of(cf1, cf2, cf3)
            .map(CompletableFuture::join)
            .collect(Collectors.toList());
        ```
    - 常见用法：并行请求多个下游接口 / 多个库，最后一起汇总。

5. 谁先好用谁：anyOf
    ```java
    CompletableFuture<Object> any =
        CompletableFuture.anyOf(cf1, cf2, cf3);
    Object fastest = any.join();
    ```
    - 典型场景：多机房/多实例“竞速请求”，谁先回就用谁，其它取消或忽略。

### 14.4 异常处理：异常不处理就是地雷
1. 异常怎么传下去？
    - 任意一个 stage 抛出异常，这个 CompletableFuture 会变为“完成异常”状态。
    - 默认情况：后续依赖它的 stage 会拿到这个异常：
    - join() 时会 CompletionException 包一层
    - 要么你绑处理器，要么就等它炸。
2. 三种常用处理 API
    - exceptionally(Function<Throwable, ? extends T>)
        - 给一个兜底值：
            ```java
            CompletableFuture<String> result =
                queryFromRemote()
                    .exceptionally(ex -> {
                        log.error("远程失败: {}", ex.getMessage());
                        return "fallback";
                    });
            ```
        - 只在前面出异常时执行。
    - handle(BiFunction<T, Throwable, U>)
        - 同时看到正常值 & 异常，二选一：
        ```java
        CompletableFuture<String> result =
            queryFromRemote()
                .handle((value, ex) -> {
                    if (ex != null) {
                        log.error("error", ex);
                        return "fallback";
                    }
                    return "ok: " + value;
                });
        ```
    - whenComplete(BiConsumer<T, Throwable>)
        - 像 finally：不改变结果，只做收尾
        ```java
        CompletableFuture<String> result =
            queryFromRemote()
                .whenComplete((value, ex) -> {
                    log.info("调用结束，成功={}，值={}", ex == null, value);
                })
                .exceptionally(ex -> "fallback"); // 真正兜底在这里
        ```

### 14.5 同步 vs Async 回调：到底在哪个线程执行？

1. 每个 thenXXX 基本都有三个版本：
    - thenApply(...)              → 当前执行的线程里跑回调（“同步依附版”）
    - thenApplyAsync(...)         → 交给 默认 ForkJoinPool 执行
    - thenApplyAsync(..., exec)   → 交给你指定的 Executor 执行
    - 如果你在 web 线程里写：
        ```java
        cf.thenApply(r -> slowCall());
        ```
        - 只要 cf 在这个 web 线程里完成，那 slowCall() 也会在 web 线程里跑，
        - 等价于你自己同步调用，压根没“异步优化”。
    - 所以经验：
        - 想利用线程池并行 → 用 xxxAsync，或者保证前一个 stage 本身已是异步（在其他线程池跑）。
        - 在虚拟线程里用 thenApply 问题不大，因为虚拟线程本身很轻，你只是串起来任务逻辑而已。

### 14.6 典型业务场景示例
- 场景：下单接口，要并行查用户、库存、优惠券
    ```java
    ExecutorService ioPool = Executors.newFixedThreadPool(16);
    public CompletableFuture<OrderResult> placeOrder(String userId, String skuId) {
        CompletableFuture<User> userFuture =
                CompletableFuture.supplyAsync(() -> loadUser(userId), ioPool);
        CompletableFuture<Stock> stockFuture =

        CompletableFuture<Coupon> couponFuture =

        return userFuture
            .thenCombine(stockFuture, (user, stock) -> checkAndReserve(user, stock))
            .thenCombine(couponFuture, (orderDraft, coupon) -> applyCoupon(orderDraft, coupon))
            .thenApply(order -> saveOrder(order))
            .exceptionally(ex -> {
                log.error("下单失败", ex);
                return buildFailResult(ex);
            });
    }
    ```
    - 三个 IO 任务并行
    - 中间两个 thenCombine 做逻辑拼装
    - exceptionally 做统一兜底

}

### 14.7 取消 & 超时

1. 取消
    ```java
    CompletableFuture<String> cf = new CompletableFuture<>();
    cf.cancel(true);
    ```
    - cancel() 只是改变 future 状态为“已取消”，
    - 如果底层线程不检查这个状态，它还是会继续跑。
    - 想实现真正的“可取消”，你要在任务中轮询某种取消信号。

2. 超时（JDK 9+）
    ```java
    cf.orTimeout(3, TimeUnit.SECONDS)      // 超时后抛 TimeoutException
      .exceptionally(ex -> "timeout fallback");
    ```
    - 或者：
    ```java
    cf.completeOnTimeout("fallback", 3, TimeUnit.SECONDS);
    ```
    - 这个是“超时没结果就直接填一个默认值”。

### 14.8 内部实现大致长什么样（只说个轮廓）

1. 别太细抠源码，先建立抽象模型就行：
    - CompletableFuture 内部有：
        - 一个 结果字段（result）：可能是值，也可能是异常、取消标记
        - 一个 回调链表（stack / next）：所有 thenXXX 都会注册成“依赖这个结果的节点”
    - 当任务完成（正常 / 异常 / 取消）时：
        - 设置 result
        - 遍历这些依赖节点，挨个触发：
            - 如果是普通 thenApply：直接在当前线程调回调
            - 如果是 thenApplyAsync：丢到对应 executor 里去执行
    - 每个节点执行自己逻辑后，又会完成自己的 CompletableFuture，再触发下一批节点……

2. 所以：
    - 不要在回调里写长时间 blocking 操作（尤其是用 commonPool 时）。
    - 你可以通过自定义 executor，把某些 stage 确认放到独立线程池中跑（比如 IO 密集 vs 计算密集分开）。

```java
下面给你一个“下单/支付聚合查询”的完整可运行示例（单文件、无外部依赖）。它演示了你想要的工程要点：
	•	线程池隔离：DB / 远程调用 / CPU 处理分开
	•	并行聚合：多个数据源并行查询，最后汇总
	•	依赖编排：先查订单基础信息，再基于 orderId 去查支付/医保/票据（thenCompose）
	•	超时降级：单个下游超时就返回默认值（或 UNKNOWN），不拖垮整体
	•	限流保护：用 Semaphore 控制远程调用并发（防把下游打爆）
	•	异常兜底：下游失败不影响整体返回（按字段降级）

直接复制到 OrderPaymentAggregationDemo.java，Java 11+ 可跑（用到了 orTimeout/completeOnTimeout，JDK9+）。

import java.math.BigDecimal;
import java.time.Instant;
import java.util.Objects;
import java.util.Random;
import java.util.concurrent.*;
import java.util.function.Supplier;

/**
 * 下单/支付聚合查询 Demo：
 * - 订单详情页 / 支付结果页：需要同时展示订单信息、支付状态、医保结算、电子票据等
 * - 目标：并行聚合 + 超时降级 + 线程池隔离 + 远程限流
 */
public class OrderPaymentAggregationDemo {

    // ======== 线程池隔离：DB / Remote / CPU ========
    private static final ExecutorService DB_POOL =
            Executors.newFixedThreadPool(16, named("db-"));
    private static final ExecutorService REMOTE_POOL =
            Executors.newFixedThreadPool(64, named("remote-"));
    private static final ExecutorService CPU_POOL =
            Executors.newFixedThreadPool(4, named("cpu-"));

    // 远程调用限流（比如你们支付/医保/票据下游都扛不住“无限并发”）
    private static final Semaphore REMOTE_SEMAPHORE = new Semaphore(50);

    private static final Random RND = new Random();

    public static void main(String[] args) {
        // 模拟多个并发请求（像网关/Controller层同时进来很多“查订单详情”）
        CompletableFuture<?>[] requests = new CompletableFuture[10];
        for (int i = 0; i < requests.length; i++) {
            String orderId = "ORD-" + (1000 + i);
            requests[i] = queryOrderDetailView(orderId)
                    .thenAccept(view -> System.out.println(Thread.currentThread().getName() + " => " + view))
                    .exceptionally(ex -> {
                        System.err.println("聚合查询失败: " + root(ex));
                        return null;
                    });
        }

        CompletableFuture.allOf(requests).join();

        shutdownPools();
    }

    /**
     * 聚合查询入口：返回“订单详情视图”
     */
    public static CompletableFuture<OrderDetailView> queryOrderDetailView(String orderId) {
        long start = System.nanoTime();

        // 1) 先查订单基础信息（DB）——后续很多调用依赖 orderBase
        CompletableFuture<OrderBase> orderBaseF = supplyDb(() -> dbLoadOrderBase(orderId))
                .orTimeout(200, TimeUnit.MILLISECONDS); // DB 通常也要给个 SLA

        // 2) 基于订单基础信息，再并行查：支付/医保/票据/风控等（Remote + 部分DB）
        CompletableFuture<PaymentInfo> paymentF = orderBaseF.thenCompose(ob ->
                        supplyRemote(() -> remoteQueryPayment(ob.orderId()))
                                .completeOnTimeout(PaymentInfo.unknown("PAY_TIMEOUT"), 300, TimeUnit.MILLISECONDS)
                                .exceptionally(ex -> PaymentInfo.unknown("PAY_ERR:" + root(ex).getClass().getSimpleName()))
                );

        CompletableFuture<InsuranceInfo> insuranceF = orderBaseF.thenCompose(ob ->
                        supplyRemote(() -> remoteQueryInsurance(ob.orderId(), ob.userId()))
                                .completeOnTimeout(InsuranceInfo.degraded("INS_TIMEOUT"), 350, TimeUnit.MILLISECONDS)
                                .exceptionally(ex -> InsuranceInfo.degraded("INS_ERR:" + root(ex).getClass().getSimpleName()))
                );

        CompletableFuture<InvoiceInfo> invoiceF = orderBaseF.thenCompose(ob ->
                        supplyRemote(() -> remoteQueryInvoice(ob.orderId()))
                                .completeOnTimeout(InvoiceInfo.pending("INV_TIMEOUT"), 300, TimeUnit.MILLISECONDS)
                                .exceptionally(ex -> InvoiceInfo.pending("INV_ERR:" + root(ex).getClass().getSimpleName()))
                );

        // 例子：DB 查订单扩展信息（并行）
        CompletableFuture<OrderExt> orderExtF = orderBaseF.thenCompose(ob ->
                        supplyDb(() -> dbLoadOrderExt(ob.orderId()))
                                .completeOnTimeout(OrderExt.empty(), 150, TimeUnit.MILLISECONDS)
                                .exceptionally(ex -> OrderExt.empty())
                );

        // 例子：CPU 侧做一段“汇总计算/字段派生”（不要在 remote/db 线程里做重CPU）
        CompletableFuture<OrderDetailView> viewF =
                orderBaseF
                        .thenCombine(orderExtF, (ob, ext) -> new Pair<>(ob, ext))
                        .thenCombine(paymentF, (pair, pay) -> new Triple<>(pair.a, pair.b, pay))
                        .thenCombine(insuranceF, (triple, ins) -> new Quad<>(triple.a, triple.b, triple.c, ins))
                        .thenCombine(invoiceF, (quad, inv) -> new Quint<>(quad.a, quad.b, quad.c, quad.d, inv))
                        .thenApplyAsync(q -> assembleView(q.a, q.b, q.c, q.d, q.e), CPU_POOL)
                        // 3) 整体 SLA：比如接口 600ms 必须返回
                        .orTimeout(600, TimeUnit.MILLISECONDS)
                        // 4) 整体兜底（如果 DB 基础信息都拿不到，那只能失败/返回最小信息，看你业务）
                        .exceptionally(ex -> {
                            Throwable t = root(ex);
                            return OrderDetailView.fail(orderId, "AGG_FAIL:" + t.getClass().getSimpleName());
                        })
                        .whenComplete((v, ex) -> {
                            long costMs = TimeUnit.NANOSECONDS.toMillis(System.nanoTime() - start);
                            // 这里可以打埋点：耗时、降级次数、超时来源等
                            if (ex == null) {
                                System.out.println("[metric] orderId=" + orderId + " costMs=" + costMs
                                        + " pay=" + v.payment.status
                                        + " ins=" + v.insurance.status
                                        + " inv=" + v.invoice.status);
                            }
                        });

        return viewF;
    }

    // ======== 组装逻辑（CPU） ========
    private static OrderDetailView assembleView(OrderBase base, OrderExt ext, PaymentInfo pay,
                                               InsuranceInfo ins, InvoiceInfo inv) {
        // 例：派生“是否允许重试支付/是否展示发票入口”等
        boolean allowRepay = (pay.status == PaymentStatus.FAILED || pay.status == PaymentStatus.UNKNOWN)
                && base.amount.compareTo(BigDecimal.ZERO) > 0;

        return new OrderDetailView(
                base.orderId, base.userId, base.amount, base.createdAt,
                ext,
                pay,
                ins,
                inv,
                allowRepay,
                "OK"
        );
    }

    // ======== 统一封装：DB 异步 ========
    private static <T> CompletableFuture<T> supplyDb(Supplier<T> supplier) {
        return CompletableFuture.supplyAsync(supplier, DB_POOL);
    }

    // ======== 统一封装：Remote 异步 + Semaphore 限流 ========
    private static <T> CompletableFuture<T> supplyRemote(Supplier<T> supplier) {
        return CompletableFuture.supplyAsync(() -> {
            boolean acquired = false;
            try {
                acquired = REMOTE_SEMAPHORE.tryAcquire(50, TimeUnit.MILLISECONDS);
                if (!acquired) {
                    throw new RejectedExecutionException("REMOTE_LIMIT");
                }
                return supplier.get();
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                throw new RuntimeException("INTERRUPTED", e);
            } finally {
                if (acquired) REMOTE_SEMAPHORE.release();
            }
        }, REMOTE_POOL);
    }

    // ======== 模拟：DB & Remote 数据源 ========

    private static OrderBase dbLoadOrderBase(String orderId) {
        sleep(randomBetween(50, 160));
        // 少量模拟 DB 抖动/异常
        if (RND.nextInt(100) < 2) throw new RuntimeException("DB_BASE_FAIL");
        return new OrderBase(orderId, "U-" + orderId.substring(orderId.lastIndexOf('-') + 1),
                new BigDecimal("128.50"), Instant.now());
    }

    private static OrderExt dbLoadOrderExt(String orderId) {
        sleep(randomBetween(30, 120));
        if (RND.nextInt(100) < 3) throw new RuntimeException("DB_EXT_FAIL");
        return new OrderExt("HOSP-001", "门诊挂号", "CARD-" + orderId);
    }

    private static PaymentInfo remoteQueryPayment(String orderId) {
        sleep(randomBetween(80, 420));
        int p = RND.nextInt(100);
        if (p < 6) throw new RuntimeException("PAY_SVC_500");
        PaymentStatus status = (p < 35) ? PaymentStatus.PAID : (p < 60) ? PaymentStatus.PAYING : PaymentStatus.FAILED;
        return new PaymentInfo(status, "PAY-" + orderId, null);
    }

    private static InsuranceInfo remoteQueryInsurance(String orderId, String userId) {
        sleep(randomBetween(80, 450));
        int p = RND.nextInt(100);
        if (p < 8) throw new RuntimeException("INS_SVC_500");
        InsuranceStatus status = (p < 40) ? InsuranceStatus.SETTLED : (p < 70) ? InsuranceStatus.PROCESSING : InsuranceStatus.NOT_ELIGIBLE;
        return new InsuranceInfo(status, "SET-" + orderId, null);
    }

    private static InvoiceInfo remoteQueryInvoice(String orderId) {
        sleep(randomBetween(60, 380));
        int p = RND.nextInt(100);
        if (p < 7) throw new RuntimeException("INV_SVC_500");
        InvoiceStatus status = (p < 30) ? InvoiceStatus.ISSUED : (p < 65) ? InvoiceStatus.PENDING : InvoiceStatus.NOT_SUPPORTED;
        return new InvoiceInfo(status, status == InvoiceStatus.ISSUED ? "INV-" + orderId : null, null);
    }

    // ======== 工具 ========

    private static ThreadFactory named(String prefix) {
        return new ThreadFactory() {
            private final ThreadFactory delegate = Executors.defaultThreadFactory();
            private int idx = 0;
            @Override public Thread newThread(Runnable r) {
                Thread t = delegate.newThread(r);
                t.setName(prefix + (++idx));
                return t;
            }
        };
    }

    private static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }

    private static long randomBetween(int min, int max) {
        return min + RND.nextInt(Math.max(1, max - min + 1));
    }

    private static Throwable root(Throwable ex) {
        Throwable t = ex;
        while (t instanceof CompletionException || t instanceof ExecutionException) {
            if (t.getCause() == null) break;
            t = t.getCause();
        }
        return t;
    }

    private static void shutdownPools() {
        DB_POOL.shutdown();
        REMOTE_POOL.shutdown();
        CPU_POOL.shutdown();
    }

    record InvoiceInfo(InvoiceStatus status, String invoiceNo, String degradeReason) {

    }

    record OrderDetailView(
```

### 14.10 commonPool的问题
1. CompletableFuture 默认把 supplyAsync/runAsync/thenApplyAsync 这些任务丢进 ForkJoinPool.commonPool。这个池子最擅长的是 短小、CPU 密集、可分治 的任务；最怕的是 阻塞 I/O。一旦你把阻塞任务塞进去，commonPool 被“占满”，就会出现很典型的级联故障：本来只是某个下游慢，最后变成整个应用的异步链路集体变慢/超时/雪崩。

2. commonPool 被阻塞会发生什么级联故障？

    - 现象 A：异步任务排队，链路整体延迟暴涨
        - commonPool 的线程数通常接近 CPU 核数（大概 NCPU-1 量级）。如果这些线程都在做阻塞 I/O（HTTP/JDBC/Redis 等）：
            - 线程被挂住（等待网络/磁盘/锁）
            - 新提交的异步任务只能排队
            - 你的 CompletableFuture 链条后续 stage（尤其 xxxAsync）也排队
        - 结果：一个接口里“并行查 4 个下游”的设计，反而变成“排队串行”。

    - 现象 B：超时成片出现，线程池“自我放大”故障
        - 当排队严重时，业务线程为了拿结果会开始：
            - join()/get() 阻塞等待
            - 或者继续提交更多异步任务（重试/降级/补偿）
        - 这会导致：
            - 任务更多 → 排队更长 → 超时更多 → 重试更多
            - 典型正反馈环（雪崩环）。

    - 现象 C：不相关业务被拖死（“旁路业务一起死”）
        - commonPool 是 JVM 进程级共享资源：
            - 你这个模块用它跑阻塞 I/O
            - 别的模块也可能用它跑计算/异步回调
            - 某些库也可能间接使用它
        - 于是你会看到：A 业务的下游慢，B 业务的异步逻辑也开始超时。这就是“级联”：跨业务传播。

    - 现象 D：回调链卡住，甚至看起来像“死锁”
        - 很多人写法是：
            - CompletableFuture.supplyAsync(ioCall) // 默认 commonPool
            - .thenApplyAsync(parse)            // 也默认 commonPool
            - .thenComposeAsync(nextIoCall);    // 还是 commonPool
        - 如果 commonPool 线程都卡在第一步 ioCall，后面的 parse/compose 任务根本拿不到线程执行，链条就“停在半路”。
        - 你会感觉像“future 不回调”，其实是回调没有线程可跑。

3. 为什么 commonPool 不适合阻塞 I/O？
    - 原因 1：ForkJoinPool 设计目标不是“很多阻塞等待”
        - ForkJoinPool 的设计假设是：
            - 任务短
            - CPU 密集
            - 线程不会长时间阻塞
        - 阻塞 I/O 恰恰相反：线程大部分时间在等，吞吐靠“更多线程覆盖等待”，而 commonPool 线程数很少（接近核数），一阻塞就没工人了。

    - 原因 2：工作窃取(work-stealing)对阻塞没用，还可能更糟
        - ForkJoin 的优势在于：线程忙完自己队列的任务，可以去偷别人的任务继续跑。
        - 但阻塞 I/O 时线程是“挂死”等待，没法偷，也没法跑，工作窃取优势发挥不出来。

    - 原因 3：共享池 + 不隔离 = 故障扩散
        - 阻塞 I/O 是“不可控延迟源”（网络抖动、下游超时、连接池耗尽都能让它卡很久）。
        - 把这种任务丢在全局共享池，相当于把不稳定性注入到全局调度器，自然容易“扩散”。

4. 实战解法
    - 做法 A：显式传业务线程池（I/O 专用）
        - CompletableFuture.supplyAsync(() -> httpCall(), ioPool);
        - 并把 I/O 池设置为：
            - 有界队列
            - 合理拒绝策略（CallerRuns 或快速失败）
            - 配合下游限流（Semaphore/Resilience4j/Sentinel）

    - 做法 B：JDK 21+：用虚拟线程 executor 承载阻塞 I/O
        - Executor vExec = Executors.newVirtualThreadPerTaskExecutor();
        - CompletableFuture.supplyAsync(() -> jdbcCall(), vExec);
        - 这样阻塞不再稀缺，但仍需限流资源（DB 连接数、下游 QPS）。

    - 做法 C：减少 join/get，链式组合把等待推迟到最外层
        - 避免在池内线程 join() 另一个 future，尽量用 thenCompose/thenCombine/allOf 做编排。

5. 总结
    - commonPool 线程数接近 CPU 核数，适合短小 CPU 任务；如果用它跑阻塞 I/O，会把池线程占满，导致后续异步任务排队、回调无线程执行、join/get 堵塞业务线程，触发超时重试的正反馈，甚至让不相关模块一起变慢，这是典型的 thread starvation 级联故障。所以阻塞 I/O 必须用隔离的 executor（或虚拟线程），并配合限流/超时/降级。

## 15. 并发容器入口

这里仅保留选择原则：

- 需要线程安全的键值映射时，优先评估 `ConcurrentHashMap`；它只保证单次容器操作，不保证跨操作或跨 key 的业务原子性。
- 需要按顺序协作或传递任务时，优先根据是否需要阻塞、容量上限和背压选择 `BlockingQueue`、`ConcurrentLinkedQueue` 或专用队列。
- 容器安全不等于业务安全：涉及配额、状态迁移、扣减或多键一致性时，应使用原子组合操作、锁、数据库条件更新或事务边界。

## 16. 线程生命周期与中断语义

线程状态帮助定位“线程在等什么”；中断则是 Java 中最常用的**协作式取消信号**。两者都不等同于“强制杀死线程”。

### 16.1 Java 线程状态

`Thread.State` 只有六种状态：

| 状态 | 含义 | 常见原因 |
| --- | --- | --- |
| `NEW` | 已创建但未启动 | `new Thread(...)` 后尚未调用 `start()` |
| `RUNNABLE` | 可在 JVM 中运行 | 正在执行、等待 CPU 时间片，或执行某些 native 调用 |
| `BLOCKED` | 等待进入 `synchronized` 监视器 | 其他线程持有同一个 monitor |
| `WAITING` | 无限期等待其他线程显式唤醒 | `Object.wait()`、`Thread.join()`、`LockSupport.park()` |
| `TIMED_WAITING` | 带超时的等待 | `sleep()`、带超时的 `wait/join/park`、`tryLock(timeout)` |
| `TERMINATED` | `run()` 已结束 | 正常返回或未捕获异常退出 |

> [!tip] 排查要点
> `BLOCKED` 只表示在等待内置监视器，不包括 `ReentrantLock` 等 AQS 锁的等待；后者在线程转储中常表现为 `WAITING (parking)`。`RUNNABLE` 也不必然意味着正在占用 CPU，需要结合 CPU、栈顶方法和锁信息判断。

### 16.2 中断是什么，不是什么

- `interrupt()` 向目标线程发送中断请求；本质上是设置中断标志，并唤醒一部分可中断阻塞操作。
- 它**不会**强制终止线程、回滚业务操作或自动释放已持有的锁。
- 任务代码必须在合适的边界检查中断状态或响应 `InterruptedException`，取消才能真正生效。

```java
Thread worker = new Thread(() -> {
    while (!Thread.currentThread().isInterrupted()) {
        doOneUnitOfWork();
    }
    cleanup();
});

worker.start();
worker.interrupt(); // 请求 worker 在下一个可响应点退出
```

### 16.3 `isInterrupted()`、`interrupted()` 与 `InterruptedException`

| API | 作用对象 | 是否清除中断标志 | 典型用途 |
| --- | --- | --- | --- |
| `thread.interrupt()` | 指定线程 | 不适用 | 请求取消 |
| `thread.isInterrupted()` | 指定线程 | 否 | 观察某线程是否收到中断请求 |
| `Thread.interrupted()` | 当前线程（静态方法） | 是 | 需要“读取并消费”当前中断状态时使用 |
| `InterruptedException` | 当前阻塞线程 | 抛出前通常会清除 | 让阻塞操作尽快返回，由调用方决定如何结束 |

`sleep`、`wait`、`join`、`Condition.await`、许多 `BlockingQueue` 操作以及 `lockInterruptibly` 都会响应中断并抛出 `InterruptedException`。普通 `synchronized` 的进入过程不可中断；已进入 `synchronized` 后收到中断也不会自动退出临界区。

### 16.4 正确处理 `InterruptedException`

处理策略只有两种：**向上声明并交给更高层决定**，或**当前层结束工作并恢复中断标志**。不要只记录日志后继续执行，那会吞掉取消请求。

```java
// 方案一：当前方法不决定策略，交由调用方处理
public Message take() throws InterruptedException {
    return queue.take();
}

// 方案二：当前任务以中断为退出信号
public void runWorker() {
    try {
        while (true) {
            process(queue.take());
        }
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt(); // 恢复被异常清除的标志
        // 清理本任务拥有的资源，然后返回
    }
}
```

如果捕获中断后仍需继续执行，必须明确说明为什么取消不应在这一层生效；这应是少数例外，而不是默认写法。

### 16.5 与线程池、Future 和虚拟线程的关系

- `ExecutorService.shutdown()` 不再接收新任务，但会等待已提交任务自然结束；`shutdownNow()` 会尝试中断正在运行的任务，并返回尚未开始的任务。两者都不保证任务一定停止。
- `Future.cancel(true)` 会尝试中断执行该任务的线程；任务若不检查标志、卡在不响应中断的 I/O 或 native 调用中，仍可能继续运行。
- 在线程池任务中，中断是线程复用前的重要边界：任务应及时退出，且不要随意清除由框架或上层传入的中断状态。
- 虚拟线程沿用相同的中断语义；它降低的是线程等待的成本，不改变外部资源、不可中断调用或业务补偿的约束。

### 16.6 实践清单

1. 将中断视为取消协议的一部分：任务循环、队列消费、批处理分页和重试等待都要设计可退出点。
2. 优先使用可中断 API，例如 `BlockingQueue.take()`、`Condition.await()`、`lockInterruptibly()`；不要用忙等替代等待。
3. 任务获取资源后使用 `try/finally` 清理；中断只请求退出，不替你完成清理或一致性补偿。
4. 在线程转储中先区分 `BLOCKED`、`WAITING (parking)` 与 `TIMED_WAITING`，再定位锁持有者、队列、超时和上游取消链。
