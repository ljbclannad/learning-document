## 1. JMM 问题导览

本节用重排序问题建立直觉；完整的 happens-before 规则与证明关系统一见 [第 13 节](#13-jmmhappens-before-规则推导)。

### 1.1 程序看起来是“顺序执行的”，但实际上可能被重排序
举例：假设有如下代码片段，在单线程下看起来是顺序执行的：

```java
int a = 1;
int b = 2;
int c = a + b;
```

但在编译器或处理器进行优化时，可能会发生指令重排序。例如，如果 `a` 和 `b` 之间没有数据依赖，甚至 `b = 2` 可能会被提前到 `a = 1` 之前执行。

在多线程环境下，这种重排序的影响更为明显。如下例（两个线程）：

**示例一：双线程指令重排问题**

```java
// 线程1
x = 1;
flag = true;

// 线程2
if (flag) {
	System.out.println(x);
}
```

假设 `flag` 不是 `volatile`，编译器、处理器或缓存可让线程 2 观察到 `flag = true`，却仍读到 `x` 的旧值。这里描述的是缺少 happens-before 时的可见性与有序性问题，而不是“某条语句先写入物理主内存”的固定过程；打印结果可能为 0。

**总结：**
- 看起来是“顺序执行”的代码，在没有数据依赖或者内存屏障时，编译器或CPU可能为了效率进行指令重排。
- 在并发环境下，如果没有使用 `volatile`、`synchronized` 等内存屏障机制做限定，重排序会导致线程间可见性问题，从而破坏预期的执行顺序。

**关键点：**
指令重排序不会改变单线程程序的执行结果，但会影响多线程中的可见性与有序性，因此并发编程时需显式约束。

**解决方法：**
使用 `volatile` 关键字，可以保证变量的可见性和有序性。
```java
/*
	a = 1;
	// StoreStore 屏障
	// StoreLoad 屏障
	flag = true; // volatile 写，在 volatile 写之前的普通写（a = 1）不能被重排到 volatile 写后面；
	// StoreLoad 屏障
	if (flag) { // 读屏障，在读取 flag 之前，必须先读取 flag 的最新值；
		//之后的读（读 a）不能跑到 volatile 读前面；
		System.out.println(x);
	}
*/
int x = 0;
volatile boolean flag = false;
```

使用 `synchronized` 关键字，可以保证变量的可见性和有序性。
```java
/*
	monitorenter（加锁） → 获取（acquire）语义
		阻止后面的读/写被重排到锁前面；
		同时从内存中“刷新”其他线程释放锁前的写。
	monitorexit（解锁） → 释放（release）语义
		阻止前面的读/写被重排到锁后面；
		把本线程的写刷新到主内存，供后续获取锁的线程可见。
*/
int a = 0;
boolean flag = false;
final Object lock = new Object();

// 线程1
synchronized (lock) {
	a = 1;
	flag = true;
}

// 线程2
synchronized (lock) {
	if (flag) {
		System.out.println(a);
	}
}
```

## 2. Final修饰词

Final修饰词是Java中的一个关键字，用于修饰变量、方法和类。它表示变量、方法和类一旦被修饰，就不能被修改。

### 2.1 Final修饰词的作用

1. **变量**：被Final修饰的变量，一旦被赋值，就不能再被修改。
2. **方法**：被Final修饰的方法，不能被重写。
3. **类**：被Final修饰的类，不能被继承。
4. **初始化安全（initialization safety）**：正确构造并发布的对象，其final字段对读线程是安全可见的

### 2.2 Final修饰词的实现原理（内存语义）
1. 禁止构造器内对 final 字段的写被重排到构造器外；(建立了内存屏障)
2. 反过来，读线程中，对 final 字段的读，也不能被重排到“获取对象引用”之前。
3. 保证“正确构造并发布的对象”的final字段，对其他线程是安全可见的（happens-before）。

## 3. synchronized和ReentrantLock的差异

### 3.1 重入性
synchronized：
- 同一线程已经持有某个对象的 monitor，再次进入 synchronized(lock)：允许；
- JVM 里有一个“重入计数”，退出时多次 monitorexit 才真的释放。
- 重入粒度：以“锁对象”为单位。

ReentrantLock：
- 同一线程已经持有某个对象的 monitor，再次进入 ReentrantLock.lock()：允许；
- JVM 里有一个“重入计数”，退出时多次 unlock() 才真的释放。
- 重入粒度：以“锁对象”为单位。

### 3.2 公平锁支持
synchronized 不支持公平锁，ReentrantLock 支持公平锁。

```java
// 非公平锁（默认）
ReentrantLock lock = new ReentrantLock();
// 公平锁
ReentrantLock fairLock = new ReentrantLock(true);
```
### 3.3 可中断锁获取
synchronized 不可中断，ReentrantLock 可中断。

```java
// 非公平锁
lock.lock();// 不可中断，和 synchronized 类似
lock.lockInterruptibly(); // 可中断获取锁
boolean acquired = lock.tryLock(timeout, unit);
```

### 3.4 性能和 JVM 优化手段

下面的锁状态与对象头描述是 **HotSpot 的实现视角，不是 Java 语言规范保证**。其中包含偏向锁的路径仅适用于 JDK 8 等旧版本：JDK 15 起默认禁用且可显式重新开启，JDK 18 起已移除。现代 JDK 不应把“偏向 → 轻量级 → 重量级”当作固定升级链路。

HotSpot 会针对 `synchronized` 做优化，典型思路包括：
1. 偏向锁（Biased Locking，历史实现）：对象记录偏向线程，后续无竞争进入可避免 CAS；发生竞争时需要撤销偏向。
2. 轻量级锁（Thin / Lightweight Lock）：在无竞争或少量竞争场景下，用 CAS + 栈上记录来实现，避免 OS 互斥量；
3. 锁膨胀（Heavyweight Lock）：真正竞争激烈时才升级成重量级监视器，可能涉及内核挂起/唤醒；
4. 锁消除（Lock Elimination）：JIT 分析发现某个锁是线程本地的，不可能被别的线程看到，直接去锁；
5. 锁粗化（Lock Coarsening）：十几个连续的小 synchronized 可以合并成一个大块，减少 enter/exit 次数。

ReentrantLock：基于 AQS，灵活、功能强，在竞争激烈时可调度性好，但没有那么多 JIT 专属优化。

## 4. 锁升级（HotSpot JDK 8 历史实现）

本节的完整“无锁 → 偏向锁 → 轻量级锁 → 重量级锁”演化用于理解 JDK 8 的 HotSpot 实现。它不是规范化状态机，也不适用于 JDK 18 及之后已移除偏向锁的 HotSpot；排查现代应用时应优先看 JFR、线程转储和实际竞争数据。

### 4.1 锁升级中的几个常用对象

主要针对对象的 Mark Word（对象头里的一个 word） 做手脚：
1. 哈希码（hashCode）
2. GC 分代年龄
3. 锁标志位（无锁、偏向、轻量级、重量级）
4. 偏向线程 ID、偏向时间戳（epoch）等

### 4.2 从“无锁”开始的完整演化过程

假设有这么个代码：
```java
class Counter {
	int count;
	synchronized void inc() {
		count++;
	}
}
```
#### 4.2.1 刚创建对象：无锁状态
新建 `Counter c = new Counter();`，此时 `c` 的对象头 Mark Word 处于 无锁 状态（普通标志位 + hash/age等）。

#### 4.2.2 第一次被某个线程进入 synchronized：偏向锁
1. 线程 T1 第一次执行：`synchronized (c) { ... }`

2. **偏向锁的动作：**
JVM 把 `c` 的 Mark Word 改成“偏向锁状态”：标记为“已偏向”记录“偏向线程 ID = T1”之后 T1 再次进入同一个 synchronized(c)：只要对象头里还是自己线程 ID，就直接当作已经持有锁，连 CAS 都省了。
3. 此阶段特征：
	1. 几乎没有 CAS、没有阻塞、没有 OS 互斥 → 超便宜。
	2. 适合单线程反复进入小锁的场景（比如局部对象、线程私有对象）。


#### 4.2.3 有第二个线程也来抢这把锁：偏向锁撤销 → 升级
1. 现在另一个线程 T2 也执行：`synchronized (c) { ... }`
它看到：`c` 的对象头里：偏向标志 = true，偏向线程 ID = T1，不是自己；
JVM 发现：“啊，这是一个偏向了别的线程的对象”。这时候就要做 “偏向锁撤销（Biased Lock Revocation）”。

2. **偏向锁撤销怎么搞？**
偏向锁的撤销比较“重”，通常需要在一个 安全点（safepoint） 暂停相关线程，原因是：
- 要确认 T1 当前是不是还在用这把锁；
- 要修正对象头和 T1 栈里保存的锁记录。

3. **撤销过程（简化版）：**
	- 暂停涉及的线程（至少要让持有偏向的线程停住）。
	- 检查：
		- 如果 T1 其实不在临界区里（锁已经结束，只是偏向标记没清）：
			- 直接把偏向清掉，还原成 无锁状态 或升到轻量级。
		- 如果 T1 还在临界区：
			- 把这把锁升级成更通用的形式（比如轻量级/重量级），让 T2 能正常排队。
	- 恢复线程执行。

#### 4.2.4 偏向撤销后：轻量级锁（Spin + CAS 的阶段）
1. **轻量级锁干的事情：**
	- 每个线程在自己的栈帧里为这把锁创建一个 Lock Record（锁记录）；
	- **尝试通过 CAS 把对象的 Mark Word 锁标志改成“指向这个锁记录”的状态；**
	- 如果 CAS 成功 → 该线程拿到轻量级锁；
	- 如果 CAS 失败 → 说明有竞争，就要考虑自旋、升级。

2. **无竞争时：轻量级锁 ≈ CAS 搞定**
	- 只有一个线程尝试加锁：
	- CAS 成功；
	- 退出 synchronized 时，把对象头恢复原状；
	- 这时整个过程都在用户态，几乎没有挂起/唤醒开销。

3. **有竞争时：轻量级锁撑不住了，升级重量级**
    - 如果 T1、T2 都在 CAS 抢这把锁：
        - 一方会失败；
        - JVM 可能让失败的线程先自旋一会儿（busy-wait）：
        - 期望持锁的线程很快执行完释放锁；
        - 自旋时不立刻挂起，可以避免频繁进内核。

4. **如果自旋次数超过阈值，或者等太久，明显存在“真实阻塞情况”，JVM 会把这把锁 膨胀（inflate）成重量级锁：**
	- 创建一个 *ObjectMonitor* 对象；
	- 把对象头 Mark Word 改成指向这个监视器的指针；
	- 让其他竞争线程挂到这个 Monitor 的等待队列里；
	- 挂起/唤醒交给 OS 互斥量 + park/unpark 之类的机制处理。

#### 4.2.5 重量级锁：OS 粗暴接管

1. **重量级锁的特点：**
	- 对应一个 ObjectMonitor 结构（HotSpot 内部）；
	- 获取不到锁的线程会被挂起（使用 park / OS 互斥量），不再自旋浪费 CPU；
	- 释放锁时唤醒一个/多个等待线程。
2. **重量级锁的语义：**
	- 同一时间只有一个线程进入临界区；
	- 其他线程阻塞等待；
	- 可见性/有序性由 monitorenter/monitorexit 的内存语义保障。
3. **重量级锁的成本：**
	- 有内核态切换；
	- 有等待队列维护；
	- 吞吐和延迟都会受影响。

#### 4.2.6 什么叫“锁撤销”，都撤谁？

1. **锁撤销（Revocation） 常说的是“偏向锁的撤销”，而不是“重量级锁没了”。**

2. **典型几种情况：**
	- 一个对象原本偏向线程 T1；
	- 后来 T2 也想加这把锁；
	- JVM 触发偏向锁撤销：
	- 在 safepoint 停下来；
	- 取消这把锁的“偏向状态”；
	- 视情况升级成轻量级或重量级。

3. **批量撤销/批量重偏向（bulk revoke / bulk rebias）**
	- JVM 统计某个类的对象偏向锁使用情况；
	- 如果发现：
	- 这些对象后来经常被不同线程使用，偏向几乎每次都要撤销 → 会选择 对这个类的所有实例做“批量撤销偏向”；
	- 或者某些情况适合“切换偏向目标线程” → 批量重偏向 rebias 到新的 owner。

4. **轻量级/重量级锁本身不会“撤销语义”**
	- 轻量级锁在释放时，Mark Word 恢复正常状态，可以回到无锁（或下次再偏向，视JVM策略）。
	- 重量级锁解除时，monitor 里的队列清空，Mark Word 也可回写；
	- 但这里通常不叫“撤销锁”，而是正常 释放 / 解锁 的过程。

#### 4.2.7 *总结*
锁升级是 HotSpot 为了优化 synchronized 而搞的多阶段实现：
1. 单线程或无竞争 → 偏向锁；
2. 轻微多线程竞争 → 轻量级锁（CAS + 自旋）；
3. 激烈竞争 / 自旋太久 → 重量级锁（内核互斥 + park/unpark）。
4. 锁撤销主要指：偏向锁撤销：当一个偏向了线程 T1 的对象被其它线程争用时，JVM 会在 safepoint 取消偏向，必要时升级锁形态；还可能有批量撤销/重偏向，作为整体优化决策。

## 5. 基于ReentrantReadWriteLock的缓存系统

### 5.1 设计一个读多写少的场景下的读写流程

```java

import java.util.HashMap;
import java.util.Map;
import java.util.concurrent.locks.ReadWriteLock;
import java.util.concurrent.locks.ReentrantReadWriteLock;
import java.util.concurrent.locks.Lock;
import java.util.function.Function;

/**
 * 读多写少场景的本地缓存示例
 * - 读：优先走 readLock
 * - miss：释放读锁 → 获取写锁 → 二次检查 → 回源 → 更新缓存
 */
public class ReadMostlyCache<K, V> {

	private final Map<K, V> cache = new HashMap<>();

	private final ReadWriteLock rwLock = new ReentrantReadWriteLock();
	private final Lock readLock  = rwLock.readLock();
	private final Lock writeLock = rwLock.writeLock();

	/**
	 * 回源逻辑，比如从 DB / 远程服务加载
	 */
	private final Function<K, V> loader;

	public ReadMostlyCache(Function<K, V> loader) {
		if (loader == null) {
			throw new IllegalArgumentException("loader must not be null");
		}
		this.loader = loader;
	}

	/**
	 * 读缓存 → miss → 回源 → 更新缓存
	 */
	public V get(K key) {
		// 1. 先尝试在读锁下读缓存
		readLock.lock();
		try {
			V value = cache.get(key);
			if (value != null) {
				return value;
			}
		} finally {
			readLock.unlock();
		}

		// 2. miss 的情况下，获取写锁（注意不能在持有读锁时“升级”为写锁）
		writeLock.lock();
		try {
			// 3. 双重检查：可能在拿写锁之前，其他线程已经把值写进缓存了
			V value = cache.get(key);
			if (value == null) {
				// 4. 仍然 miss，真正回源
				value = loader.apply(key);
				// 根据业务可以决定是否允许 value 为 null
				cache.put(key, value);
			}
			return value;
		} finally {
			writeLock.unlock();
		}
	}

	/**
	 * 主动写入/更新缓存（例如后台管理修改配置）
	 */
	public void put(K key, V value) {
		writeLock.lock();
		try {
			cache.put(key, value);
		} finally {
			writeLock.unlock();
		}
	}

	/**
	 * 清空缓存
	 */
	public void clear() {
		writeLock.lock();
		try {
			cache.clear();
		} finally {
			writeLock.unlock();
		}
	}

	/**
	 * 简单示例：使用方式
	 */
	public static void main(String[] args) {
		ReadMostlyCache<String, String> cache =
				new ReadMostlyCache<>(key -> {
					// 模拟回源，比如查数据库
					System.out.println("load from backend: " + key);
					return "VALUE_" + key;
				});

		// 第一次 get：会触发回源
		String v1 = cache.get("a");
		System.out.println("v1 = " + v1);

		// 第二次 get：直接命中缓存，不再回源
		String v2 = cache.get("a");
		System.out.println("v2 = " + v2);
	}
}
```

### 5.2 ReadWriteLock的写线程饥饿问题

1. 写线程饥饿是因为 ReentrantReadWriteLock 默认允许“有写在排队时，新的读还能一直进来”，写永远等不到“没有读”的时刻。就是在业务层做一个“写优先开关”：只要有写在等待，就暂缓后续读锁的获取，让当前读流量自然退完，再让写上锁，从而避免写线程被读洪水长期淹没。

## 6. 线程池问题

### 6.1 系统中有一个线程池，workQueue 使用的是无界 LinkedBlockingQueue，maximumPoolSize 设置得很大。描述在高并发任务提交时会出现的三个隐患，并说明为什么这种配置在生产中通常是反模式。

1. 线程数根本长不起来，maximumPoolSize 形同虚设 → 延迟雪崩
	- 如果当前线程数 < corePoolSize → 新建线程执行；
	- 否则，尝试往队列里丢任务；
	- 只有当队列满了，并且线程数 < maximumPoolSize，才会继续创建非核心线程。

2. 而你用了无界LinkedBlockingQueue,结果就是：
	- 线程池线程数基本稳定在 corePoolSize 那个水平；
	- maximumPoolSize 再大也没用，属于“写了个寂寞”。

#### 6.1.1 队列无限膨胀 → 内存压力/OOM/GC抖成狗（任务堆积）
1. 所有多出来的任务统统丢进堆上那条 LinkedBlockingQueue 链表里；
2. 每个任务都是一个 Runnable / Callable 对象；
3. 高并发 + 持续时间长 → 队列里可能堆几十万、几百万个任务。
4. 后果：堆内存占用疯狂上涨；GC 频率变高、停顿时间变长；最惨的：直接 OutOfMemoryError: Java heap space，

#### 6.1.2 没有任何“背压/拒绝”机制 → 故障传播、雪崩放大
1. 无界队列掩盖了系统处理不过来的事实，*把“压力过大”从 RT/错误显性问题，变成了“慢性堆积 → 内存被吃光”的隐性炸弹。*

2. 生产系统一个很关键的点是：当我已经处理不过来时，要能拒绝、限流或快速失败，这样上游/调用方才有机会：降级；熔断；重试到别的实例；返回友好错误。

3. 这会带来几个后果：
	- 上游完全感知不到下游已经很痛苦：不会触发熔断；不会走降级；系统一路顶着，直到内存炸掉。
	- 问题很难排查：线程池看起来“线程数不多，没啥异常”；但 RT 奇高，堆内存占用离谱；很多人第一眼会去怀疑别的模块，殊不知是线程池把任务藏队列里了。
	- 故障放大：一个实例扛不住开始卡队列；上游继续狂打请求；其他实例也可能跟着被拖死（共用下游资源时尤甚）。

#### 6.1.3 无界队列 + 很大 maxPoolSize = 没有“限流/拒绝信号”，系统会悄悄从“处理变慢一点”演变成“全部挂掉”，中间没有明显告警点。


### 6.2 在线上系统中，你发现使用了一个 ScheduledThreadPoolExecutor，其中某个周期任务执行时间偶尔会远超过周期（比如周期 1s，执行时间 5s）

#### 6.2.1 scheduleAtFixedRate vs scheduleWithFixedDelay：周期超时后的真实表现

| 场景             | scheduleAtFixedRate                                                                          | scheduleWithFixedDelay                                                            |
| ---------------- | -------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 核心语义         | 钉在“绝对时间轴”上，尽量守住原始节拍                                                         | 每次执行完再休息 delay，节拍由“执行耗时 + delay”决定                              |
| 周期 1s，执行 5s | 第 1 次：t0→t0+5s；第 2 次：上一轮结束立刻开始（t0+5s）；第 3 次：t0+10s……几乎无间隔“连轴转” | 第 1 次：t0→t0+5s；休息 1s；第 2 次：t0+6s→t0+11s；再休息 1s……整体周期被拉长到 6s |
| 行为特征         | 不会堆积后并发执行，只是串行补课；节拍被“追赶”                                               | 不追时钟，永远是“干完→休息 delay→再干”，越慢越稀疏                                |
| 适合场景         | 心跳、指标采集、需要尽量贴近固定频率                                                         | 扫描、清理、同步等重活，宁可慢也要留喘息时间                                      |

> 小结：**fixedRate** 会在超时后立即补跑下一轮，试图贴紧绝对时间；**fixedDelay** 则把“执行时间 + delay”视为真实周期，绝不追赶节拍。

#### 6.2.2 与线程池并发的配合要点

- **单个 ScheduledFutureTask 永远串行**：不管 fixedRate 还是 fixedDelay，只要上一轮没结束，下一轮必须等待，除非任务内部再手动分发。
- **poolSize 只影响不同任务的并发性**：`ScheduledThreadPoolExecutor` 的 poolSize>1 只能让不同 Runnable 并行，同一个任务实例依旧串行，只是触发策略不同。

#### 6.2.3 选型指南

1. **要“对齐时间轴”**：监控采样、心跳等场景选 `scheduleAtFixedRate`，慢了一次就立刻补，尽量贴住绝对时间。
2. **要“执行完先喘口气”**：清理、同步、批处理等重任务选 `scheduleWithFixedDelay`，执行慢就等得久，避免任务挤爆把系统顶死。

#### 6.2.4 工程师记忆法

- **fixedRate**：节拍器/KPI 模式，上一拍没做完也得赶下一拍。
- **fixedDelay**：劳逸结合模式，干完一单先喝水，再等 delay。

## 7. 并发工具组合场景

并发容器的实现与选择统一见 [[01-Java基础与并发/Java基础/集合]]。本节只讨论在一个业务流程中如何组合并发工具、识别资源上限与失败边界。

### 7.1 如何利用并发工具（如 Future、ConcurrentHashMap、CountDownLatch、Semaphore 等）

组合工具前先界定任务依赖、超时、下游容量和失败策略；并行化并不天然提高吞吐，可能只是把压力同时推向下游。

#### 7.1.1 Future：并行发请求，最后一起收结果

1. 典型场景：聚合服务 / 网关服务

2. 比如你有一个接口，要同时查：
	- 用户基本信息（用户中心）
	- 账户余额（资金服务）
	- 优惠信息（营销服务）

3. 这是三个远程调用，如果串行干：
	- 总耗时 ≈ rpc1 + rpc2 + rpc3
	- 用线程池 + Future：
		- 同时提交 3 个任务到线程池；
		- 每个任务单独发 RPC；
		- 最后 get() 一把收集结果。
	- 好处：
		- 耗时变成接近 max(rpc1, rpc2, rpc3)；
		- 代码还是同步写法，不用硬扯回调地狱。

#### 7.1.2 ConcurrentHashMap：多线程共享缓存 / 状态表

1. 典型场景：本地缓存 / 统计表 / 注册表

2. 场景例子：
	- 本地缓存：ConcurrentHashMap<Key, Value>
	- 多个线程读写同一份缓存；
	- 避免自己手搓 synchronized 包一堆 HashMap。
	- 在线统计：
		- 比如：统计某接口调用次数、IP 访问量等；
		- ConcurrentHashMap<String, AtomicLong> 之类的结构。

3. 特点：
	- 支持并发读写；
	- 不会像 HashMap 那样在多线程下炸链表；
	- 大部分操作无锁读，写时粒度也比较细（JDK8 之后）。

4. ConcurrentHashMap 最常用的场景：一份被多个线程共享、频繁访问的 Map，比如本地缓存。实现与复合操作边界见 [[01-Java基础与并发/Java基础/集合]]。

#### 7.1.3 CountDownLatch：主线程等一批子任务都完成

1. 典型场景：并行做任务，最后汇总 / 等待系统各模块都启动完

2. 例如：
	- 你要并行执行 N 个子任务（读文件、不同分片处理、不同机房请求）；
	- 主线程需要在这些任务都结束后，再继续往下做汇总处理。

3. 流程：
	- 初始化：new CountDownLatch(N)；
	- 每个子任务执行完 countDown()；
	- 主线程调用 await()，在那儿等计数变 0；
	- 计数归零 → 所有子任务都完成 → 主线程继续。

4. 适用于：
	- “一批任务都搞完才能继续下一步”的场景；
	- 比如系统启动：等数据库连接、缓存预热、配置加载都 OK 再对外提供服务。

5. CountDownLatch 最典型用途：一堆线程干活，主线程在门口等它们都说“到”，再往下走。

#### 7.1.4 Semaphore：限制并发访问数（限流 / 资源池）

1. 典型场景：限制同时访问某资源的线程数

2. 比如：
	- 你有一个调用非常贵的第三方接口；
	- 为了保护它/你自己，只允许最多 10 个线程同时调用；
	- 超过的线程要么排队，要么直接拒绝/降级。

3. 做法：
	- 创建：new Semaphore(10)；
	- 每次访问前：acquire() 拿许可证；
	- 完成后：release() 归还许可证；
	- 没票了的线程就阻塞等（或者用 tryAcquire 直接放弃）。

4. 也可以用于：
	- 简易连接池 “pool size = 许可证数”；
	- 控制同时处理的请求数，防止压爆下游数据库/Redis 等。

5. Semaphore 最常用的玩法：用许可证数来表达“最多允许多少个并发访问某个资源”，是最顺手的限并发工具之一。

#### 7.1.5 总结：
	- Future → 把一堆 I/O 异步并行起来，最后一起 get()
	- ConcurrentHashMap → 多线程共享的Map，用于缓存/状态表
	- CountDownLatch → 一批任务一起搞，主线程等它们都完成
	- Semaphore → 给资源发“门票”，控制同时访问的线程数


## 8. 并发场景

### 8.1 设计一个简化版的ForkJoin框架用于并行计算

1. 支持任务拆分（fork）与结果合并（join）
2. 使用工作窃取（work-stealing）思想
3. 描述核心数据结构（如双端队列）和线程之间如何交互，不需要完整代码。

这个题挺爽，相当于手搓一个精简版 ForkJoinPool。我按“设计文档”节奏梳理，专注结构、角色和线程协作，不写样板代码。

#### 1. 目标与使用方式
- **能力诉求**：拆分/合并（fork/join）、并行计算、工作窃取负载均衡。
- **典型使用**：`ForkJoinPool pool = new ForkJoinPool(N);` 然后 `pool.invoke(new MyTask(input));`，在 `MyTask.compute()` 中递归拆分子任务、fork、join。线程池负责把子任务分布到 worker，必要时互相偷活。

#### 2. 核心抽象
##### 2.1 ForkJoinTask（任务对象）
- 字段：`status`（未完成/已完成/异常）、可选 `result`。
- 方法：`compute()` 承载业务，`fork()` 把自己挂到当前 worker 队尾，`join()` 等待任务完成再取结果。
- 注意：`fork/join` 不额外创建线程，调度完全交由池内 worker。

##### 2.2 Worker（工作线程）
- 每个 worker 对应一个真实 Thread。
- 持有一个 `WorkStealingDeque<ForkJoinTask>`：
  - 自己只能在尾部 LIFO push/pop；
  - 其他 worker 只能在头部 FIFO steal。
- 与 `ForkJoinPool` 交互：注册/注销、自旋或 park、随机挑 victim 进行窃取。

##### 2.3 ForkJoinPool（线程池调度器）
- 负责创建 N 个 worker，维护 `workers[]`。
- `submit/invoke`：外部根任务先放到某个 worker 队列（或备用队列），再唤醒该 worker。
- 提供工作窃取支持：空闲 worker 随机挑 victim，从其队头尝试 CAS 抢任务。

#### 3. Work-Stealing 双端队列
- **行为设计**：
	- `push/pop`：只允许 owner 在线程安全的尾部 LIFO 操作；
	- `steal`：其他线程只能在头部 FIFO 取任务。
- **为什么这样**：
	- 自己 LIFO → 保证最新拆分的子任务马上执行，命中缓存，维持递归局部性；
	- 被偷 FIFO → 老任务先被偷走，保留较深的栈帧给 owner，方便继续细分。
- **并发控制（抽象）**：两个索引 `head/tail`；owner 单线程操作 tail，可用普通写；stealer 对 head 做 CAS，`head >= tail` 说明空。真实实现还需考虑数组长度 2^n、环绕、内存屏障等。

#### 4. 执行生命周期（以 `pool.invoke(rootTask)` 为例）
1. **根任务入队**：pool 选一个 worker，将 rootTask 放入其队尾，唤醒线程。
2. **worker 主循环**：
	- 若本地队列有任务 → pop 执行；
	- 否则 → 进入工作窃取流程。
3. **执行 compute()**：
	- `fork()` 子任务 → push 到本地队尾；
	- `join()` 子任务 → 触发“边等边干”策略（见下节）。
4. **任务完成**：设置 status=DONE，唤醒可能等待它的 join。然后回到步骤 2。

#### 5. fork/join 的配合细节
- **fork**：只是把子任务挂到当前 worker 队尾，不阻塞。父任务可继续干活或立即 join。
- **join（忙等策略）**：
	1. 子任务已完成 → 直接返回结果；
	2. 未完成 → 当前 worker 先尝试处理自己队列中的其他任务，若为空再去偷别人的任务执行；每完成一个任务就回头检查子任务是否结束；
	3. 子任务完成 → 返回结果继续后续逻辑。
- 这种 join 是“边等边干”，不会把 CPU 闲置在阻塞等待里。

#### 6. 终止与结果收敛（简化思路）
- `invoke()` 线程本身可以当 worker，或直接 `rootTask.join()`。
- rootTask 只要返回，就意味着整棵任务树已完成，因此可作为终止条件。
- 需要时再配合“活动任务计数”或 `quiescence` 检测，让池子知道何时可以收缩/销毁。

#### 7. 线程协作一段话总结
1. 每个 worker 管理自己的双端队列，尾部 LIFO 执行，提高局部性。
2. `compute()` 中随时可 fork 子任务堆到尾部。
3. join 不闲着：等待期间同样执行其他任务，避免线程空转。
4. 队列空 → 随机 victim，从其队头 FIFO 偷任务。
5. 通过“本地栈式 + 全局抢劫式”调度，既保证并发度，又避免单线程被深度递归压垮。

这套设计涵盖简化版 ForkJoin 框架的主要成分：任务抽象（compute/fork/join）、work-stealing 队列、串行 owner 与并发 stealer 的配合、忙等 join、以及根任务驱动的终止检测。真正落地实现要处理的坑包括：CAS 正确性、内存屏障、异常传播、任务取消、终止检测等等，但从“设计题”的角度，到这里已经相当完整了。


## 9. 并发Bug分析与排查思路

### 9.1 在线上环境中，你发现某个使用 ThreadPoolExecutor 的服务在高峰期出现：
1. 任务响应时间飙升
2. CPU 占用不高
3. 线程池中线程数已经达到 maximumPoolSize
4. 从“线程 dump + 队列监控 + 业务逻辑分析”三个角度入手的排查思路清单。

这个症状组合（RT 飙升 + CPU 不高 + 线程数顶满）几乎等价于：线程都在“排队等资源”。可以从线程 dump、队列监控、业务逻辑三个层面逐层定位。

#### ① 线程 dump：谁在等、等谁
- **看状态占比**：RUNNABLE（真算还是阻塞 IO）、WAITING/TIMED_WAITING（park、sleep、条件等待）、BLOCKED（synchronized）。CPU 不高却线程满，通常 WAITING/TIMED_WAITING/BLOCKED 比例会异常大。
- **聚类热点栈**：把线程按栈顶分组，找出“卡在同一行/同一方法”的热点，例如 `HttpClient.execute`、`PreparedStatement.execute`、大锁（`ReentrantLock.lock`/synchronized）。
- **重点 grep**：
	- 锁：`LockSupport.park`、`Unsafe.park`、`ReentrantLock.lock`、`waiting to lock <...>`。
	- IO：`SocketInputStream.socketRead0`、各类 JDBC/HTTP 客户端。
	- 自己写的排队：`BlockingQueue.take/put`、`Condition.await`、while+sleep。
- **写清结论**：例如“200 线程里 150 个堵在 XXX RPC，30 个等 YYY 锁”。后续分析都围绕这些热点展开。

#### ② 队列监控：是“堆太多”还是“根本进不来”
- **关键指标**：`poolSize/activeCount/queueSize/RejectedExecutionHandler 触发次数` + 队列类型。
- **两类典型曲线**：
	1. 队列持续上涨（无界或大队列）→ 处理能力落后流量，任务在队里排长队，RT 随时间线性拉长，且线程大多在等 IO/锁。
	2. 队列不大却高 RT → 多见于小队列/SynchronousQueue + 上游重试：任务要么同步 handoff，要么被拒绝，但上游放大了压力。
- **识别反模式组合**：
	- `LinkedBlockingQueue` + 巨大 `maximumPoolSize`：实际上只能跑 `corePoolSize`，剩下的任务全堆队列。
	- 很小 `corePoolSize` + 超大 `maximumPoolSize` + `SynchronousQueue`：高峰期线程拉满却都在等下游 IO，线程创建和切换成本白白浪费。
- **要回答的问题**：队列曲线是否反映真实过载，还是池子配置就不合理导致“线程多但都在瞎等”。

#### ③ 业务逻辑：任务到底在做什么
- **单任务是否过重**：串行远程调用链（A→B→C）、多次重试、粗粒度锁、全是同步 IO 且无超时 → 高峰必排队。
- **有没有长阻塞任务混进来**：`Thread.sleep`、`wait`、长轮询、连接保活、WebSocket 心跳等不该跟核心请求共用线程池的任务。
- **下游依赖是否真瓶颈**：对照 DB/Redis/外部服务监控，看线程栈是否集中在某依赖。若是，优先加超时、熔断、缓存、限流。
- **线程套线程**：一条请求链上层层 `submit + get()`，任何一环卡住都会占用多条线程。尽量改成异步/回调/事件，减少线程同时被占。

#### ④ Checklist 串联执行
1. **线程 dump**：统计各状态数量，列出前两大阻塞栈，确认是等 IO、等锁还是人为 park。
2. **线程池/队列监控**：结合 `activeCount/poolSize/queueSize/拒绝次数/队列类型`，判断是任务堆积还是 handoff 失败。
3. **业务剖析**：拆解单任务耗时构成，定位长阻塞、重锁、下游异常、长生命周期任务。
4. **定对策**：
	- 下游慢 → 缓存 / 限流 / 超时 / 熔断；
	- 锁竞争 → 拆锁、缩临界区、换数据结构；
	- 线程池配置反模式 → 调整 core/max、使用有界队列、明确拒绝策略并在上游降级。

> 口诀：线程池只是排队 + 分发。出现“CPU 不高 + 线程满 + RT 高”时，常见原因是线程在等待资源、任务本身未受控，或没有及时拒绝；先搞清楚“在线程里等谁”以及“为什么没快速失败”。

### 9.2 一个系统中存在大量使用 ThreadLocal 存储大对象的代码，线程池线程不销毁，线上出现内存泄漏和 OOM：
1. 描述 ThreadLocalMap 的 key 弱引用设计，以及为什么仍然可能内存泄漏。
2. 设计一套规范 / 机制，减少这种泄漏风险。

这个问题的本质：线程池线程生命周期“无限长”，而 ThreadLocalMap 里 value 是强引用，只要不主动清理就永远挂在堆上。

#### 9.2.1 ThreadLocalMap 结构回顾
每个 `Thread` 内部都维护一个 `ThreadLocalMap`：
```
static class ThreadLocalMap {
	static class Entry extends WeakReference<ThreadLocal<?>> {
		Object value;    // 强引用
	}
	Entry[] table;
}
```
- Entry 继承 `WeakReference<ThreadLocal<?>>`，**只有 key 是弱引用**；value 仍是普通强引用。
- 当 `ThreadLocal` 实例（通常是 static 字段）不再被引用时，GC 会把该 Entry 的 key 置为 `null`，但 value 仍然存在，等待后续操作触发清理。

#### 9.2.2 为什么仍然会泄漏
1. 线程池里的 worker 长期存在，`ThreadLocalMap` 跟随线程一起常驻。
2. 某些 ThreadLocal 被 GC 回收后，Entry 变成 `key=null, value=大对象`。
3. 如果线程后续没有再访问这个 ThreadLocal，就不会触发“stale entry” 清理；value 会一直挂在 Map 里。
4. 业务又喜欢把缓存、上下文、buffer 等大对象放进 ThreadLocal，于是堆内存被这些“僵尸value”占满。

> 记住：弱的是key，不弱的是value；ThreadLocalMap 没有后台扫地工。线程不死、你又不remove，value就一直活着。

#### 9.2.3 防泄漏策略清单
**(1) 编码规范**
- 所有 `ThreadLocal.set()` 必须配套 `try { ... } finally { threadLocal.remove(); }`，在代码模板 / Review 清单里强制执行。
- ThreadLocal 只存“小上下文”：traceId、租户信息等；**禁止**存放大对象、缓存、byte[] 等。
- 公共库暴露 ThreadLocal 时要声明生命周期，并提供统一清理入口。

**(2) 线程池包装 / 框架支持**
- 在 `ExecutorService` 外面加一层 Decorator，提交任务时包装 Runnable/Callable：
	- `beforeExecute` 清理上一次遗留的 ThreadLocal；
	- `afterExecute` 或 finally 块调用 `ThreadLocalHolder.clearAll()`，对框架维护的 ThreadLocal 做集中清理（如 MDC、上下文）。
- Web 容器、RPC 框架都可以在 Filter/Interceptor 的 finally 中执行统一 clear，避免开发者遗漏。

**(3) 统一 ThreadLocal 管理器**
- 用一个集中式工具类创建、获取和清理 ThreadLocal，业务侧不允许随意 `new ThreadLocal`。
- 清理逻辑、监控埋点统一放在管理器里，可一键 dump 当前线程已注册的 ThreadLocal，便于排查。

**(4) 监控 & 审计**
- 定期做 Heap Dump，关注 `ThreadLocalMap$Entry` 数量和大 value 占用，反查未 remove 的调用点。
- 在统一管理器里加计数 / 日志：线程持有超大 value 或持有时间过长时报警。
- 把“ThreadLocal 使用说明 + remove 位置”写进 PR 审核 checklist，禁止在业务代码里滥用。

**(5) 面向流程的预防**
- 线程池初始化时就声明“ThreadLocal 使用白名单”，与编码规范联动。
- 灰度/压测阶段把 `ThreadLocalMap` 相关指标纳入巡检，提前发现堆积趋势。

> Takeaway：ThreadLocal 是“跟线程同寿命的全局变量”。在线程池场景下，如果不用完立即清理，它的生命周期就等于进程生命周期——迟早把堆撑爆。

### 9.3 某模块用 ReentrantReadWriteLock，线上现象
- 读性能很好
- 写偶发极长延迟（秒级甚至十秒级）

#### 9.3.1 为什么会出现“写偶发性超长延迟”？
1. 默认非公平的 ReentrantReadWriteLock 是读倾向（reader-preferred）：
	- 读锁：只要当前没有写锁持有者即可获得；
	- 写锁：必须“无写锁 + 无任何读锁”才行。

2. 关键在于：就算有写线程排队，新来的读线程仍能继续获取读锁（只要此刻还没人持有写锁）。在“读洪流”场景里：
	- 读线程持续进入；
	- 写线程请求写锁，需要等所有已持有的读锁释放；
	- 等待间隙，新读继续进来，读锁很难归零；
	- 写锁理论上能拿到，现实里要等很多秒 → 写被饿。

#### 9.3.2 如何确认是写饥饿
1. 线程 dump 里，少量写线程栈顶长期停在 `ReentrantReadWriteLock$WriteLock.lock`。
	- 同时大量线程在 `ReentrantReadWriteLock$ReadLock.lock` + 你的读方法(...)。
2. 读线程数量高但 CPU 不高 → 读逻辑很快，只是频率高。
3. 出现以上特征，基本可认定是“读多 + 非公平”造成写饥饿。

#### 9.3.3 改造思路（选 1–2 个组合即可）
1. 改用公平锁
	- 把 `new ReentrantReadWriteLock()` 改成 `new ReentrantReadWriteLock(true)`。近似 FIFO，有写在等时新读不插队，写饥饿大幅缓解。代价：吞吐下降一些，读偶尔等待。
2. 在读入口做人为“写优先”
	- 维护 pendingWriters 计数。写入前 `pendingWriters++` 再去拿写锁；写完 `--`。读在加锁前先看 pendingWriters > 0 时退避/短暂等待/降级，不让新读冲进来，给写一个“清空窗口”。
3. 锁拆分 / 数据分区
	- 不要所有 key 争一把锁。按 key hash 分段，每段一个读写锁，降低单锁读流量，写等待时间自然下降。
4. 缩短读锁持有时间
	- 读锁内只做数据访问，复杂计算 / RPC / 拼装移到锁外，或用快照 copy 后在锁外处理。读锁持有越短，写越不容易饿死。
5. 评估换 StampedLock + 乐观读
	- 读多写少且能接受偶尔旧值时，先 `tryOptimisticRead()`，验证戳失败再退回读锁。多数读不阻塞写，但 API 更易踩坑，不适合强一致场景。
#### 9.3.4 压缩版结论
- 本质：非公平读写锁 + 读洪流 → 写看不到“读锁归零”的瞬间 → 写饥饿。
- 快速止血：公平锁，或有写在等时限制新读。
- 后续优化：分段锁；缩小读锁范围；有余力再评估 StampedLock / 快照 / COW 等更合适结构。

## 10. ReentrantReadWriteLock的写锁降级和读锁升级

### 10.1 写锁降级（Write → Read）：允许且常用
1. 目的：你需要先独占修改数据，修改完成后又想继续以“读一致视图”的方式读一段时间（不希望被别的写线程插入破坏视图）。

2. 正确姿势：持有写锁时 先拿读锁，再释放写锁（顺序不能反）。

```java

    // 写锁降级：刷新配置后，继续以读锁方式使用同一版本的 config
    public Config refreshAndRead() {
        rw.writeLock().lock();
        try {
            // 1) 独占更新
            config = loadFromRemote();

            // 2) 在释放写锁之前先获取读锁：完成“降级”
            rw.readLock().lock();
        } finally {
            // 3) 释放写锁（此时仍持有读锁）
            rw.writeLock().unlock();
        }

        try {
            // 4) 在读锁保护下使用一致视图
            return config;
        } finally {
            rw.readLock().unlock();
        }
    }

    private Config loadFromRemote() {
        // 模拟加载
        return new Config("v" + System.currentTimeMillis());
    }

    record Config(String version) {}
}
```
3. 要点：降级后读锁还在，所以别的写线程进不来；但其他读线程可以并发读。

### 10.2 读锁升级（Read → Write）：不允许直接升级，必须“释放读锁再竞争写锁”

1. RRWL 的写锁要求“没有任何读者”。你如果持读锁再去拿写锁，很容易：
    - 自己把自己挡住（等待“读者为 0”，但读者包含自己）
    - 多个线程同时升级时出现“大家都拿着读锁等写锁”的升级死等/饥饿风险

2. 正确做法：释放读锁 → 拿写锁 → 双重检查（DCL 思路）
典型场景：缓存懒加载 / 读多写少的初始化。
```java
        // 1) 先用读锁读
        rw.readLock().lock();
        try {
            if (value != null) {
                return value;
            }
        } finally {
            rw.readLock().unlock();
        }

        // 2) 读锁释放后再竞争写锁（“升级”通过重新加锁实现）
        rw.writeLock().lock();
        try {
            // 3) 双重检查：避免多个线程都走到这里重复加载
            if (value == null) {
                value = loadExpensive();
            }

            // 4) 可选：写锁降级（如果后面还要在一致视图下读/做派生计算）
            rw.readLock().lock();
        } finally {
            rw.writeLock().unlock();
        }

        try {
            return value;
        } finally {
            rw.readLock().unlock();
        }
    }

    private String loadExpensive() {
        return "loaded@" + System.currentTimeMillis();
    }
}
```
4. 常见错误示例：直接在读锁里拿写锁（别这么写）
```java
rw.readLock().lock();
try {
    if (needWrite) {
        rw.writeLock().lock(); // 可能长期等待/死等风险
        try { /* write */ } finally { rw.writeLock().unlock(); }
    }
} finally {
    rw.readLock().unlock();
}
```

### 10.3 一句话记忆法
- 降级（写→读）：持写锁时先拿读锁，再放写锁
- 升级（读→写）：不能直接升；放读锁 → 竞争写锁 → 双重检查（必要时再降级）

### 11.2 自定义公平锁示例
```java
import java.util.concurrent.locks.AbstractQueuedSynchronizer;

class MyLock {
    private abstract static class Sync extends AbstractQueuedSynchronizer {
        abstract boolean fair();

        @Override
        protected final boolean tryAcquire(int acquires) {
            final Thread current = Thread.currentThread();

            // 公平锁：队列前面有人 -> 不能插队
            if (fair() && hasQueuedPredecessors()) {
                return false;
            }

            if (compareAndSetState(0, 1)) {
                setExclusiveOwnerThread(current);
                return true;
            }
            return false;
        }

        @Override
        protected final boolean tryRelease(int releases) {
            if (getState() == 0 || getExclusiveOwnerThread() != Thread.currentThread()) {
                throw new IllegalMonitorStateException();
            }
            setExclusiveOwnerThread(null);
            setState(0);
            return true;
        }

        @Override
        protected final boolean isHeldExclusively() {
            return getState() == 1 && getExclusiveOwnerThread() == Thread.currentThread();
        }
    }

    private static final class FairSync extends Sync {
        @Override boolean fair() { return true; }
    }
    private static final class NonFairSync extends Sync {
        @Override boolean fair() { return false; }
    }

    private final Sync sync;

    public MyLock() { this(false); } // 默认非公平
    public MyLock(boolean fair) { this.sync = fair ? new FairSync() : new NonFairSync(); }

    public void lock() { sync.acquire(1); }
    public void unlock() { sync.release(1); }
}
```

### 11.3 源码展示

1. AQS 里最关键的字段（就是这几个在撑全场）名字和语义和源码一致）
    - volatile int state：同步状态（锁/许可/门闩计数都塞这里）
    - volatile Node head, tail：同步队列的头尾指针（CLH 变体，有一个 dummy head）
    - CAS 方法族：compareAndSetState、compareAndSetHead、compareAndSetTail（底层 VarHandle/Unsafe）

2. Node 结构你要认识（源码里就是一个内部静态类）
    - volatile int waitStatus
        - 状态：CANCELLED、SIGNAL、CONDITION、PROPAGATE
    - volatile Node prev, next
    - volatile Thread thread
    - Node nextWaiter：给共享模式/Condition 用的

3. 队列是啥：CLH 变体 + dummy head（面试官爱你画）
    - head 是一个 dummy 节点（不代表线程）
    - 真实等待线程从 head.next 开始
    - 只有 head 的直接后继有资格去 tryAcquire（减少“惊群”）

4. 独占 acquire 的源码味流程（ReentrantLock 就走这条）
    1. 入口：acquire(arg)逻辑是（语义级伪码，和源码结构一致）：
        ```java
        public final void acquire(int arg) {
            if (!tryAcquire(arg) &&
                acquireQueued(addWaiter(Node.EXCLUSIVE), arg)) {
                selfInterrupt();
            }
        }
        ```
    2. 关键点：先走 快路径：tryAcquire失败才入队：addWaiter入队后在队列里“正确地等待并重试”：acquireQueued

    3. addWaiter(mode)：先试快速入队，失败再 enq
        ```java
        private Node addWaiter(Node mode) {
            Node node = new Node(Thread.currentThread(), mode);
            Node pred = tail;
            if (pred != null) {
                node.prev = pred;
                if (compareAndSetTail(pred, node)) {
                    pred.next = node;
                    return node;
                }
            }
            enq(node);
            return node;
        }
        ```
    4. acquireQueued(node, arg)：核心循环（队头资格 + park）
        ```java
        final boolean acquireQueued(final Node node, int arg) {
            boolean failed = true;
            try {
                boolean interrupted = false;
                for (;;) {
                    final Node p = node.predecessor();
                    if (p == head && tryAcquire(arg)) {
                        setHead(node);
                        p.next = null; // help GC
                        return interrupted;
                    }
                    if (shouldParkAfterFailedAcquire(p, node) &&
                        parkAndCheckInterrupt()) {
                        interrupted = true;
                    }
                }
            } finally {
                if (failed) {
                    cancelAcquire(node);
                }
            }
        }
        ```
    5. shouldParkAfterFailedAcquire(p, node)：SIGNAL 协议（精髓）
        ```java
        private static boolean shouldParkAfterFailedAcquire(Node pred, Node node) {
            int ws = pred.waitStatus;
            if (ws == Node.SIGNAL) {
                return true;
            }
            if (ws > 0) {
                do {
                    node.prev = pred = pred.prev;
                } while (pred.waitStatus > 0);
                pred.next = node;
            } else {
                compareAndSetWaitStatus(pred, ws, Node.SIGNAL);
            }
            return false;
        }
        ```
    6. parkAndCheckInterrupt()：真正阻塞点
        ```java
        private final boolean parkAndCheckInterrupt() {
            LockSupport.park(this);
            return Thread.interrupted();
        }
        ```
    7. unparkSuccessor(node)：唤醒后继
        ```java
        private final void unparkSuccessor(Node node) {
            int ws = node.waitStatus;
            if (ws < 0) {
                compareAndSetWaitStatus(node, ws, 0);
            }
            Node s = node.next;
            if (s == null || s.waitStatus > 0) {
                s = null;
                for (Node p = tail; p != null && p != node; p = p.prev) {
                    if (p.waitStatus <= 0) {
                        s = p;
                        break;
                    }
                }
            }
            if (s != null)
                LockSupport.unpark(s.thread);
        }
        ```
    8. release(arg)：谁来唤醒谁？（unparkSuccessor）
        ```java
        public final boolean release(int arg) {
            if (tryRelease(arg)) {
                Node h = head;
                if (h != null && h.waitStatus != 0)
                    unparkSuccessor(h);
                return true;
            }
            return false;
        }
        ```
    9. unparkSuccessor(head)
        ```java
        private final void unparkSuccessor(Node node) {
        ```

    10. 共享模式：Semaphore / CountDownLatch 的“传播唤醒”长啥样
        ```java
        public final void acquireShared(int arg) {
            if (tryAcquireShared(arg) < 0)
                doAcquireShared(arg);
        ```

    11. doAcquireShared(arg)：共享模式下不是“只唤醒一个”，而是可能连续唤醒，让一串共享获取者通过（比如 latch 归零后大家都能过）。

        ```java
        private void doAcquireShared(int arg) {

            boolean failed = true;
            try {
                boolean interrupted = false;
                for (;;) {

                        setHeadAndPropagate(node, arg);
                        p.next = null; // help GC

                        parkAndCheckInterrupt()) {
                        interrupted = true;
                    }

            }
        ```

        ```java
        private void setHeadAndPropagate(Node node, int propagate) {
        ```

### 11.4 示例解释
1. T0：初始状态
	•	state = 0（锁空闲）
	•	队列未初始化：head = null, tail = null

2. T1：线程 A 调用 lock()，直接拿到锁（快路径）
    - `A` 执行 `acquire(1)`：
        - `tryAcquire(1)`：CAS `state: 0 -> 1` 成功
        - `A` 成为 `owner`，返回
    此时：
        - `state=1`，`owner=A`
        - 队列仍然不存在（`head/tail` 还是 `null`）

3. T2：线程 B 调用 lock()，tryAcquire 失败 → 入队
    - `B` 执行 `acquire(1)`：
        - `tryAcquire(1)` 失败（`state=1`）
        - `addWaiter(EXCLUSIVE)` 发现 `tail==null`，走 `enq()` 初始化队列：
            - 创建 `H(dummy)`，令 `head=tail=H`
            - 把 `N(B)` 挂到 `tail` 后面：`H <-> N(B)`，更新 `tail=N(B)`
            - 进入 `acquireQueued(N(B),1)` 自旋
    - 此时队列大概长这样：
        - `H(ws=0) <-> N(B, ws=0)`
4. T3：B 在 acquireQueued 里准备 park：把前驱 head 标成 SIGNAL
    - `B` 在 `acquireQueued` 里循环：
        - 发现 `p = N(B).prev == head(H)`，说明“我排在队头后继”，有资格去 `tryAcquire`
        - 但 `tryAcquire` 仍失败（A 还持锁）
        - 接着会调用 `shouldParkAfterFailedAcquire(p, node)`：
            - **如果 `p.waitStatus != SIGNAL`，就 CAS 把 前驱 `p.waitStatus` 设为 `SIGNAL`**
            - 也就是把 `H.waitStatus` 从 0 改成 `SIGNAL`：
                - “head 释放锁时，记得叫醒你的后继（B）”

    - 此刻队列：
        - `H(ws=SIGNAL) <-> N(B, ws=0)`
    - `B`：park() 阻塞（LockSupport.park）

5. T4：线程 C 调用 lock()，tryAcquire 失败 → 入队到 B 后面
    - `C` 重复类似流程：
        - `tryAcquire` 失败
        - `addWaiter` 直接快入队：挂到 `tail` 后面
    - 队列变成：
        - `H(ws=SIGNAL) <-> N(B, ws=0) <-> N(C, ws=0)`

6. T5：C 在 acquireQueued 里也准备 park：把前驱 N(B) 标成 SIGNAL
    - `C` 在 `acquireQueued` 循环中：
        - `p = N(C).prev == N(B)`，不是 `head`，所以它没资格 `tryAcquire`（AQS 的规则：只有 `head` 的直接后继才有资格抢锁）
        - 于是进入 `shouldParkAfterFailedAcquire(p,node)`
        - 把 `N(B).waitStatus` CAS 成 `SIGNAL`
    - 队列现在：
        - `H(ws=SIGNAL) <-> N(B, ws=SIGNAL) <-> N(C, ws=0)`
    - `C`：park() 阻塞（LockSupport.park）

7. T6：线程 A unlock()：release 成功 → unparkSuccessor(head) 唤醒 B
    - `A` 执行 `release(1)`：
        - `tryRelease`：`state: 1 -> 0`，`owner=null`
        - 看到 `head!=null && head.waitStatus!=0`（此时 `head` 的 `ws=SIGNAL`）
        - 调 `unparkSuccessor(head)`：
            - 通常会先把 `head.waitStatus` 置回 0（清理 SIGNAL）
            - 找到 `head` 的后继（`head.next`，也就是 `N(B)`）
            - `LockSupport.unpark(B.thread)` → 唤醒 B
    - 队列此刻一般变成：
        - `H(ws=0) <-> N(B, ws=SIGNAL) <-> N(C, ws=0)`

8. T7：B 被唤醒，成为“队头后继”→ tryAcquire 成功 → setHead(B)
    - `B` 从 park 返回，继续 acquireQueued 循环：
        - 现在 `p = N(B).prev == head(H)`，且锁空闲 `state=0`
        - `B tryAcquire CAS 成功：state 0->1，owner=B`
        - `setHead(N(B))：B 节点变成新的 head（并清掉 thread 引用帮助 GC）`
        - 原 head(H) 会被断开（oldHead.next=null）帮助回收
    - 队列形态（逻辑上）变为：
        - `H(=原 N(B), ws=0) <-> N(C, ws=0)`
    - 注意：此时 新 head 是 B 的节点；你之前看到的 dummy head 已经被踢出队列（变成游离节点）。

9. T8：B unlock()：唤醒 C；C 重复同样流程
    - `B` 执行 `unlock()`：
        - `release`：`state: 0 -> 1`，`owner=B`
        - `unparkSuccessor(head)`：唤醒 `head` 的后继（`N(C)`）
    - `C` 被唤醒后：
        - 发现自己是 `head` 的直接后继
        - `tryAcquire` 成功
        - `setHead(N(C))`
        - 队列最终只剩一个 head（没有等待者）
10. 一句话把“SIGNAL 协议”讲明白
    - 谁负责唤醒我？ —— 我的前驱节点负责。
    - 所以我在 park 前，会先把 前驱的 waitStatus 改成 SIGNAL。
    - 释放锁的人只需要 `unparkSuccessor(head)`：唤醒 `head` 的后继即可。

11. 总结
    - AQS 是 CLH 变体 FIFO 队列。
    - B/C 抢不到锁会入队。
    - 每个等待者在 park 前会把前驱的 waitStatus 设为 SIGNAL，表示”前驱释放时要唤醒我”。
    - unlock 时 release 会调用 `unparkSuccessor(head)`，唤醒 `head.next`。
    - 被唤醒的线程只有在自己是 `head` 的直接后继时才会 `tryAcquire`，成功后 `setHead`，把自己变成新 head，队列向前推进。

**关键时刻说明：**

**T0-T1：线程 A 快速获取锁**
- A 直接 CAS `state: 0→1` 成功，无需入队

**T1-T2：线程 B 入队并初始化队列**
- B 的 `tryAcquire` 失败（A 持锁）
- 创建 dummy head + N(B) 节点
- B 发现自己是 head 的直接后继，有资格 `tryAcquire`，但失败（A 还持锁）

**T2-T3：线程 C 入队**
- C 也失败，入队到 B 后面
- C 发现前驱不是 head，无资格 `tryAcquire`

**T3-T4：B 和 C 都 park**
- B 把 head 的 `waitStatus` 设为 `SIGNAL`（”释放时叫醒我”）
- C 把 N(B) 的 `waitStatus` 设为 `SIGNAL`
- 两者都调用 `LockSupport.park()` 阻塞

**T5-T6：A 释放锁，唤醒 B**
- A 调用 `unparkSuccessor(head)`，找到 `head.next = N(B)`
- 唤醒 B
- B 被唤醒后，发现自己是 head 的直接后继，`tryAcquire` 成功
- B 调用 `setHead(N(B))`，把自己变成新 head

**T8-T9：B 释放锁，唤醒 C**
- 重复上述流程
- C 成为新 head，队列最终只剩一个 dummy head

**核心机制总结：**

1. **SIGNAL 协议**：每个节点 park 前，把前驱的 `waitStatus` 设为 `SIGNAL`
2. **队头资格**：只有 head 的直接后继才有资格 `tryAcquire`
3. **setHead 推进**：获取锁成功后，把自己变成新 head，队列向前推进
4. **公平性**：严格按入队顺序唤醒（FIFO）

**图例说明：**
- `H`：head（dummy 节点）
- `N(X)`：线程 X 的节点
- `ws`：waitStatus
- `⇄`：双向链表
- `✓`：成功
- `✗`：失败
- `💤`：阻塞
- `⏰`：被唤醒
- `🔔`：唤醒操作

## 12. synchronized：字节码、对象头与 JVM 锁优化

本节承接基础文档中的 API 选择，讨论 JVM 实现细节；锁状态属于特定 JDK/HotSpot 实现，不应当作所有 JVM 的规范保证。

### 12.1 字节码指令
- `monitorenter` / `monitorexit` 包裹临界区。

### 12.2 对象头 & Mark Word
- 包含锁标志位、是否偏向、线程 ID、GC 信息。
- JDK 8 HotSpot 常用的历史描述是：无锁 → 偏向锁 → 轻量级锁 → 重量级锁；这不是 Java 规范承诺的固定状态机。
- **注意**：偏向锁在 JDK 15 中被标记为废弃且默认禁用，在 JDK 18 中被完全移除。

### 12.3 JVM 锁优化

#### 12.3.1 偏向锁（历史知识）

**⚠️ 重要说明：偏向锁已被废弃**
- **JDK 15（2020年9月）**：偏向锁被标记为废弃（deprecated），默认关闭
- **JDK 18（2022年3月）**：偏向锁被完全移除
- 废弃原因：
  - 现代应用中多线程竞争越来越常见，偏向锁的收益降低
  - 偏向锁的撤销成本较高，在有竞争时反而降低性能
  - 维护偏向锁增加了 JVM 的复杂度
  - 轻量级锁和自适应自旋已经足够高效

**偏向锁的原理（历史知识）：**
- 单线程重复进入时直接绑定线程 ID，避免 CAS
- 适用于"几乎没有竞争"的场景
- 第一次获取锁时，在对象头 Mark Word 中记录线程 ID
- 后续该线程再次进入时，只需检查线程 ID 是否匹配，无需 CAS

**为什么被废弃：**
```
传统应用（单线程为主）          现代应用（多线程为主）
    ↓                              ↓
偏向锁收益大                    偏向锁收益小
撤销成本可接受                  频繁撤销，性能下降
    ↓                              ↓
JDK 8 及之前默认开启            JDK 15-17 默认关闭；JDK 18+ 移除
```

**如何查看和配置（JDK 8-14；JDK 15-17 虽可显式开启但会告警）：**
```bash
# 查看是否启用偏向锁（JDK 8-14）
java -XX:+PrintFlagsFinal -version | grep BiasedLocking

# 禁用偏向锁（JDK 8-14）
-XX:-UseBiasedLocking

# JDK 15-17 默认禁用；JDK 18+ 已移除，相关选项不再适用
```

#### 12.3.2 轻量级锁
- **自旋 + CAS**，适合短时间锁竞争
- 线程通过 CAS 尝试将对象头的 Mark Word 替换为指向锁记录的指针
- 如果 CAS 成功，获取锁；失败则自旋重试
- 竞争持续时，HotSpot 可能根据运行时状态选择继续自旋、阻塞或膨胀为监视器；不存在可依赖的固定自旋次数或必经路径

**工作流程：**
```
1. 线程在栈帧中创建锁记录（Lock Record）
2. 使用 CAS 将对象头的 Mark Word 复制到锁记录
3. CAS 尝试将对象头指向锁记录
4. 成功 → 获取轻量级锁
5. 失败 → 自旋重试或升级为重量级锁
```

#### 12.3.3 自旋锁与自适应自旋
- **自旋锁**：线程不放弃 CPU，而是执行空循环等待锁释放
- **自适应自旋**：根据上次自旋的结果动态调整自旋次数
  - 如果上次自旋成功获取锁，本次可以自旋更久
  - 如果上次自旋失败，本次可能直接阻塞

**自旋的优缺点：**
- ✅ 优点：避免线程切换开销，适合锁持有时间短的场景
- ❌ 缺点：占用 CPU 资源，锁持有时间长时浪费 CPU

#### 12.3.4 锁消除
- **逃逸分析**：JIT 编译器分析对象是否逃逸出线程
- 如果对象未逃逸（只在单线程内使用），则消除同步锁
- 典型场景：方法内部的局部对象加锁

```java
public String concat(String s1, String s2) {
    StringBuffer sb = new StringBuffer();  // 局部对象，未逃逸
    sb.append(s1);  // StringBuffer 内部有 synchronized
    sb.append(s2);  // 但 JIT 会消除这些锁
    return sb.toString();
}
```

#### 12.3.5 锁粗化
- 如果一系列连续操作都对同一个对象反复加锁解锁
- JIT 会将多个锁合并为一个更大范围的锁

```java
// 优化前
for (int i = 0; i < 1000; i++) {
    synchronized(obj) {
        // 操作
    }
}

// JIT 优化后（锁粗化）
synchronized(obj) {
    for (int i = 0; i < 1000; i++) {
        // 操作
    }
}
```

#### 12.3.6 锁升级路径（实现示意）

**JDK 8-14（有偏向锁）：**
```
无锁 → 偏向锁 → 轻量级锁 → 重量级锁
      ↓         ↓           ↓
   单线程    短时竞争    长时竞争/多线程
```

**JDK 18+（偏向锁已移除）：**
```
无锁 → 轻量级锁 → 重量级锁
      ↓           ↓
   短时竞争    长时竞争/多线程
```

**锁状态对比表：**

| 锁状态   | Mark Word 内容       | 是否阻塞   | 适用场景       | JDK 18+ 状态 |
| -------- | -------------------- | ---------- | -------------- | ------------ |
| 无锁     | hashCode、GC 年龄    | 否         | 无竞争         | ✅ 保留       |
| 偏向锁   | 线程 ID、epoch       | 否         | 单线程反复进入 | ❌ 已移除     |
| 轻量级锁 | 指向栈中锁记录的指针 | 否（自旋） | 短时竞争       | ✅ 保留       |
| 重量级锁 | 指向 monitor 的指针  | 是         | 长时竞争       | ✅ 保留       |

**性能边界：** 无竞争时同步开销很低；竞争持续时间、临界区长度、线程调度、JDK 实现与 CPU 都会改变结果。不要根据锁状态图推导固定性能排序，应通过 JFR/JMH 和真实负载定位竞争与停顿。

## 13. JMM：happens-before 规则推导

基础文档保留 JMM、volatile 与 DCL 的使用结论；本节展开规则及其推导。

### 13.1 happens-before 规则详解

**happens-before 的含义：**
- 如果操作 A happens-before 操作 B，那么 A 的结果对 B 可见
- 不是指时间上的先后，而是**可见性保证**

---

**规则 1：程序顺序规则（Program Order Rule）**

```java
int a = 1;      // 操作 1
int b = 2;      // 操作 2
int c = a + b;  // 操作 3
```

**规则：** 在单个线程中，按照代码顺序，前面的操作 happens-before 后面的操作。

**说明：**
- 操作 1 happens-before 操作 2
- 操作 2 happens-before 操作 3
- 但实际执行时，CPU 可能重排序（只要不影响单线程结果）

---

**规则 2：volatile 变量规则（Volatile Variable Rule）**

```java
class VolatileExample {
    private volatile boolean flag = false;
    private int data = 0;

    // 线程 A
    public void writer() {
        data = 42;          // 操作 1
        flag = true;        // 操作 2（volatile 写）
    }

    // 线程 B
    public void reader() {
        if (flag) {         // 操作 3（volatile 读）
            int x = data;   // 操作 4，一定能看到 data=42
        }
    }
}
```

**规则：** 对 volatile 变量的写操作 happens-before 后续对该变量的读操作。

**说明：**
- 操作 2（volatile 写）happens-before 操作 3（volatile 读）
- 根据程序顺序规则：操作 1 happens-before 操作 2
- 根据传递性：操作 1 happens-before 操作 4
- **结论：** 线程 B 读到 `flag=true` 时，一定能看到 `data=42`

---

**规则 3：锁规则（Monitor Lock Rule）**

```java
class LockExample {
    private int data = 0;
    private final Object lock = new Object();

    // 线程 A
    public void writer() {
        synchronized (lock) {
            data = 42;      // 操作 1
        }                   // 操作 2（unlock）
    }

    // 线程 B
    public void reader() {
        synchronized (lock) {  // 操作 3（lock）
            int x = data;      // 操作 4，一定能看到 data=42
        }
    }
}
```

**规则：** 对锁的解锁操作 happens-before 后续对同一把锁的加锁操作。

**说明：**
- 操作 2（unlock）happens-before 操作 3（lock）
- 操作 1 happens-before 操作 2（程序顺序）
- 操作 3 happens-before 操作 4（程序顺序）
- **结论：** 线程 B 获取锁后，一定能看到线程 A 在锁内的所有修改

---

**规则 4：线程启动规则（Thread Start Rule）**

```java
class StartExample {
    private int data = 0;

    public void test() {
        data = 42;          // 操作 1

        Thread t = new Thread(() -> {
            int x = data;   // 操作 2，一定能看到 data=42
        });

        t.start();          // 操作 3
    }
}
```

**规则：** 线程的 `start()` 方法 happens-before 该线程的所有操作。

**说明：**
- 操作 1 happens-before 操作 3（程序顺序）
- 操作 3 happens-before 操作 2（线程启动规则）
- **结论：** 子线程一定能看到 `start()` 之前的所有修改

---

**规则 5：线程终止规则（Thread Termination Rule）**

```java
class JoinExample {
    private int data = 0;

    public void test() throws InterruptedException {
        Thread t = new Thread(() -> {
            data = 42;      // 操作 1
        });

        t.start();
        t.join();           // 操作 2

        int x = data;       // 操作 3，一定能看到 data=42
    }
}
```

**规则：** 线程的所有操作 happens-before 其他线程检测到该线程终止（通过 `join()` 或 `isAlive()`）。

**说明：**
- 操作 1 happens-before 操作 2（线程终止规则）
- 操作 2 happens-before 操作 3（程序顺序）
- **结论：** `join()` 返回后，一定能看到子线程的所有修改

---

**规则 6：线程中断规则（Thread Interruption Rule）**

```java
class InterruptExample {
    private int data = 0;

    public void test() throws InterruptedException {
        Thread t = new Thread(() -> {
            while (!Thread.currentThread().isInterrupted()) {
                // 工作
            }
            int x = data;   // 操作 2，能看到 data=42
        });

        t.start();
        data = 42;          // 操作 1
        t.interrupt();      // 操作 3
    }
}
```

**规则：** 对线程的 `interrupt()` 调用 happens-before 被中断线程检测到中断事件。

**说明：**
- 操作 1 happens-before 操作 3（程序顺序）
- 操作 3 happens-before 操作 2（线程中断规则）
- **结论：** 线程检测到中断时，能看到 `interrupt()` 之前的修改

---

**规则 7：对象终结规则（Finalizer Rule）**

```java
class FinalizerExample {
    private int data = 0;

    public FinalizerExample() {
        data = 42;          // 操作 1
    }

    @Override
    protected void finalize() {
        int x = data;       // 操作 2，一定能看到 data=42
    }
}
```

**规则：** 对象的构造函数结束 happens-before 该对象的 `finalize()` 方法。

**说明：**
- 操作 1 happens-before 操作 2
- **结论：** `finalize()` 中能看到构造函数的所有修改

**注意：** `finalize()` 已被废弃，不推荐使用。

---

**规则 8：传递性规则（Transitivity）**

```java
class TransitivityExample {
    private int a = 0;
    private int b = 0;
    private volatile boolean flag = false;

    // 线程 A
    public void writer() {
        a = 1;              // 操作 1
        b = 2;              // 操作 2
        flag = true;        // 操作 3（volatile 写）
    }

    // 线程 B
    public void reader() {
        if (flag) {         // 操作 4（volatile 读）
            int x = a;      // 操作 5，一定能看到 a=1
            int y = b;      // 操作 6，一定能看到 b=2
        }
    }
}
```

**规则：** 如果 A happens-before B，B happens-before C，则 A happens-before C。

**说明：**
- 操作 1 happens-before 操作 2（程序顺序）
- 操作 2 happens-before 操作 3（程序顺序）
- 操作 3 happens-before 操作 4（volatile 规则）
- 操作 4 happens-before 操作 5（程序顺序）
- **结论：** 通过传递性，操作 1、2 happens-before 操作 5、6

---

**happens-before 规则总结表：**

| 规则         | 场景               | 保证                                 |
| ------------ | ------------------ | ------------------------------------ |
| **程序顺序** | 单线程内           | 前面操作对后面可见                   |
| **volatile** | volatile 变量      | 写操作对后续读操作可见               |
| **锁**       | synchronized/Lock  | unlock 对后续 lock 可见              |
| **线程启动** | Thread.start()     | start() 前的操作对线程内可见         |
| **线程终止** | Thread.join()      | 线程内操作对 join() 后可见           |
| **线程中断** | Thread.interrupt() | interrupt() 前的操作对中断检测后可见 |
| **对象终结** | finalize()         | 构造函数对 finalize() 可见           |
| **传递性**   | 组合规则           | A→B, B→C ⇒ A→C                       |

---

**实战案例：双重检查锁为什么需要 volatile**

```java
// ❌ 错误：没有 volatile
class Singleton {
    private static Singleton INSTANCE;

    public static Singleton getInstance() {
        if (INSTANCE == null) {              // 操作 1
            synchronized (Singleton.class) {
                if (INSTANCE == null) {
                    INSTANCE = new Singleton();  // 操作 2
                }
            }
        }
        return INSTANCE;                     // 操作 3
    }
}
```

**问题：** `new Singleton()` 分为 3 步：
1. 分配内存
2. 初始化对象
3. 将引用指向内存

CPU 可能重排序为：1 → 3 → 2

**时间线：**
```
线程 A: 执行到操作 2，完成步骤 1、3（引用已赋值，但对象未初始化）
线程 B: 执行操作 1，发现 INSTANCE != null，直接返回
线程 B: 使用未初始化的对象 ⚠️ 空指针或错误数据
```

**解决：** 加 `volatile`

```java
// ✅ 正确：加 volatile
class Singleton {
    private static volatile Singleton INSTANCE;  // volatile 禁止重排序

    public static Singleton getInstance() {
        if (INSTANCE == null) {
            synchronized (Singleton.class) {
                if (INSTANCE == null) {
                    INSTANCE = new Singleton();
                    // volatile 写，禁止重排序
                    // 保证：内存分配 → 对象初始化 → 引用赋值
                }
            }
        }
        return INSTANCE;  // volatile 读，能看到完整初始化的对象
    }
}
```

**happens-before 分析：**
- `INSTANCE = new Singleton()`（volatile 写）happens-before 后续的 volatile 读
- 保证线程 B 读到 `INSTANCE != null` 时，对象已完全初始化

## 14. 并发测试与验证

并发代码的“能跑”不等于正确；普通单元测试通常只能覆盖一种时序，无法证明在重排序、可见性或竞争条件下仍然安全。先明确要验证的是**吞吐/延迟**还是**内存语义/原子性**，再选择工具。

### 14.1 JMH：验证性能假设

JMH（Java Microbenchmark Harness）用于比较微小热点，例如 `AtomicLong` 与 `LongAdder` 的争用表现、不同队列实现的吞吐或锁竞争开销。

- 必须使用预热、多个 fork 和结果消费，避免 JIT 尚未稳定、死代码消除或一次性 GC 影响结论。
- 基准只描述指定 JDK、CPU、参数与负载下的结果，不能直接推导生产容量；生产还受网络、数据库连接、GC、限流与任务分布影响。
- 将 JMH 放在独立 benchmark 模块或测试源码中，不要把 `System.currentTimeMillis()` 循环当作可靠微基准。

```java
// imports: org.openjdk.jmh.annotations.*; java.util.concurrent.atomic.LongAdder
@State(Scope.Benchmark)
public class LongAdderBenchmark {
    private final LongAdder adder = new LongAdder();

    @Benchmark
    @Threads(8)
    public long incrementLongAdder() {
        adder.increment();
        return adder.sum();
    }
}
```

### 14.2 JCStress：验证并发正确性

JCStress 用不同线程交错执行 `@Actor` 方法，收集所有允许观察结果，适合验证可见性、重排序、发布安全和无锁算法；它回答的是“这个结果是否可能发生”，不是“代码跑得多快”。

```java
// imports: org.openjdk.jcstress.annotations.*; org.openjdk.jcstress.infra.results.I_Result
@JCStressTest
@State
@Outcome(id = "-1", expect = Expect.ACCEPTABLE, desc = "读线程先执行，尚未发布")
@Outcome(id = "1", expect = Expect.ACCEPTABLE, desc = "读到正确初始化的对象")
@Outcome(id = "0", expect = Expect.ACCEPTABLE_INTERESTING,
         desc = "缺少安全发布时，可能观察到默认值")
public class UnsafePublicationTest {
    private Holder holder;

    static final class Holder {
        int value;

        Holder(int value) {
            this.value = value;
        }
    }

    @Actor
    public void writer() {
        holder = new Holder(1);
    }

    @Actor
    public void reader(I_Result result) {
        Holder observed = holder;
        result.r1 = observed == null ? -1 : observed.value;
    }
}
```

其中 `Holder.value` 应为非 `final` 的普通字段，构造函数写入 `1`；上例仅说明测试形态。真实用例需要根据字段初始化顺序、是否使用 `volatile`/锁和预期结果声明 `@Outcome`。不要把单次偶然通过的压力测试当作内存模型正确性的证明。

### 14.3 工程验证清单

1. **正确性**：并发单测覆盖超时、异常、中断、重复提交和线程池拒绝；关键状态推进再使用数据库唯一键、条件更新或幂等键兜底。
2. **性能**：先用 JMH 验证局部热点，再用压测验证端到端 P95/P99、队列长度、拒绝数、连接池等待和下游错误率。
3. **可观测性**：故障时保留线程转储、JFR、任务提交/开始/结束指标与 TraceId，才能区分锁竞争、线程饥饿和下游阻塞。
4. **回归**：线程池参数、锁策略或 JDK 版本变化后，至少重复关键场景压测；不要只验证功能测试通过。
