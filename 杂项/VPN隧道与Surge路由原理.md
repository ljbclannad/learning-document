# VPN 隧道与 Surge 路由原理

> 本文用一次访问 `www.example.org` 的过程串起 DNS、IP 路由、VPN 隧道与 Surge 分流。示例是教学模型，不代表当前设备配置或实测结果。产品行为以具体版本和配置为准，资料核对于 2026-11-17。

## 1. 一次普通访问经过什么

浏览器访问 `https://www.example.org`，通常先通过 DNS 获得目标 IP，再建立传输连接；HTTPS 使用 TLS 认证服务器并保护应用数据，随后交换 HTTP 请求和响应。HTTP/1.1、HTTP/2 通常基于 TCP，HTTP/3 基于 QUIC/UDP。系统根据目标 IP 查询路由，选择网络接口和下一跳；局域网中再通过链路层找到下一跳，逐跳转发。

```text
域名 → DNS 查询 → 目标 IP → 系统选路 → Wi-Fi / 网关 → 互联网 → 网站
                              ↓
                     TCP + TLS 或 QUIC → HTTP
```

DNS、路由和连接是不同步骤：能解析不等于能连接，能连接 IP 也不等于 TLS 或网站服务一定正常。缓存、已有连接、应用自带 DNS、代理远端解析等会改变这条简化顺序。

## 2. VPN 为什么能改变访问路径

典型的三层 VPN 客户端创建虚拟接口，并设置路由，使匹配的数据包交给该接口。客户端将内部 IP 包加密、认证并封装到发往 VPN 网关的外层包中，外层包通过真实网卡发送。网关验证并解密，再按自己的路由转发；返回包经反向路径回到客户端。具体封装、握手与传输协议取决于 VPN 实现。例如 WireGuard 的握手建立会话密钥，数据包通过 UDP 传输，不能推广为所有 VPN 都使用 UDP。

```text
内层：设备 → 目标网站（原始 IP 包）
外层：设备 ═══ 加密隧道 ═══ VPN 网关 → 目标网站
       真实网卡发往网关       解密、路由或转发
```

网关访问公网时常配合源地址转换（NAT），让目标看到网关的公网出口；企业 VPN 也可能只路由到内部网段，不一定提供公网出口。网关需要转发权限、返回路由及必要的防火墙/NAT 配置。客户端到网关的外层流量必须能走真实网络，避免被自己重新送进隧道；具体实现可能使用更具体的路由或接口绑定。

**加密负责保护隧道，并不自动使网站可达。** 改变路径与出口可能使原本不通的目标可达，但还要满足客户端能到网关、网关能到目标、DNS 正确、目标接受出口以及协议未被阻断。网站仍可按出口 IP、地区或其他条件限制访问。

### 全隧道与分流

- **全隧道**：默认路由通常指向 VPN，大多数目标经网关；仍可能有局域网、服务器地址等例外。
- **分流隧道**：仅指定网段进入 VPN，其他目标走原网络。路由按前缀等规则选择，并非自动测试哪个网站直连不通。

例如 `10.20.0.0/16 → VPN`、默认路由 `0.0.0.0/0 → Wi-Fi`：公司内网进入隧道，其他 IPv4 流量走 Wi-Fi。更具体前缀通常优先；IPv6 有独立路由与策略，不能从 IPv4 配置推断。

## 3. Surge：接管与出口是两次选择

Surge 是本地流量接管与代理策略引擎，不应把它的所有模式等同于传统远程 VPN 隧道。系统代理只影响遵守代理设置的应用；Surge VIF 在 IP 层接管被路由进来的流量，iOS 使用基于 VPN 的接管，Mac 增强模式使用 VIF。VIF 接管有协议、路由和配置边界，不保证所有设备流量均被处理。

```text
应用 → 系统代理 或 系统路由 → Surge VIF → 规则匹配
                                         ├─ DIRECT → 本机网络 → 目标
                                         ├─ 代理策略 → 远端代理 → 目标
                                         └─ REJECT → 拒绝
```

**进入 VIF 不等于进入远程隧道；DIRECT 通常表示 Surge 接管后选择直连，而不是一定绕过 Surge。** 规则模式下按顺序匹配，首条匹配规则决定策略，最终由 `FINAL` 兜底；代理组可能当前选中节点，也可能选中 DIRECT。全局或直接模式的行为不同。示意：

```ini
[Rule]
DOMAIN-SUFFIX,example.org,ProxyGroup
IP-CIDR,192.168.0.0/16,DIRECT,no-resolve
FINAL,DIRECT
```

`ProxyGroup` 是需要另行定义的策略组名称，并非可直接运行的完整配置。命中该组不代表必然远程出站，需检查组的当前选择。规则没有自动保证直连可达，也不保证失败后自动切换。

## 4. DNS、Fake IP 与远端解析

DNS 将域名映射到地址等记录；传统 DNS 常用 UDP 53，较大响应或其他情形可使用 TCP 53；DoT 使用 TLS，DoH 使用 HTTPS。加密 DNS 保护客户端到解析器这一段的查询，不等于隐藏所有连接信息，也不决定后续连接必然走 VPN。DNS 查询本身也有路由与出口，可能与业务连接不同，从而产生 DNS 泄漏或解析结果与实际出口地区不匹配。

Surge VIF 的典型 Fake IP 流程：

```text
应用查询 www.example.org → Surge 返回虚拟 IP，记录对应关系
应用连接虚拟 IP → VIF 接管 → 找回域名 → 匹配规则 → 选择出口并建立真实连接
```

Fake IP 是本地关联标记，不是网站真实地址。Surge 文档描述的范围为 `198.18.0.0/15`；实际行为受 `always-real-ip`、DNS 劫持及其他配置影响。显式代理请求也可能直接携带域名；代理协议和设置决定目标由本地还是远端解析。不能假定所有应用查询都经过同一解析器，浏览器自带安全 DNS、缓存和 IPv6 也会影响结果。

## 5. 为什么关闭 VPN 后反而无法上网

这不是单一故障，常见原因是退出时网络状态未恢复，或存在有意的阻断策略：

| 可能原因 | 现象或排查方向 |
|---|---|
| 系统代理仍指向已停止的本地端口 | 遵守系统代理的应用失败，检查代理设置和监听状态 |
| DNS 仍指向不可达的本地或隧道内解析器 | 域名失败，直接访问已知可达 IP 可能不同；先核对 DNS 配置 |
| 路由或虚拟接口残留 | 默认路由仍指向不可用接口，检查 IPv4 和 IPv6 路由 |
| Kill switch / 防火墙主动阻断 | 为防泄漏而阻止非隧道流量，先确认策略，不要盲目关闭安全设置 |
| 缓存、网络切换或客户端异常 | 重连或按客户端正常退出流程恢复，再检查状态 |

排查先记录现场，不要直接清空网络配置：① 确认 Wi-Fi 和网关；② 检查系统代理；③ 检查 DNS；④ 检查默认路由和 VPN 接口；⑤ 查看客户端与防火墙的阻断策略。`ping` 失败不必然等于 HTTPS 失败，服务可能禁 ICMP；DNS 正常也不证明目标端口可达。涉及安全设置的变更先确认影响。

## 6. 信息边界

VPN 网关可看到它解密后的内部 IP 包及目标信息，但 HTTPS 的端到端 TLS 内容一般仍受保护；网站看到的通常是实际出站 IP。DNS 解析器可能看到所查询域名，具体取决于解析路径。代理类型、TLS 终止、MITM、日志和配置会改变可见性，不能简单说“VPN 使所有人都看不到访问内容”。
