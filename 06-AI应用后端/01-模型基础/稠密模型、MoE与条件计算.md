# LLM 模型选型与部署评估：稠密、MoE 与条件计算

> 本文用于为具体业务选择并上线 LLM。结论不应来自单一排行榜、参数量或模型名称，而应来自：**硬性准入条件 → 真实业务质量 → 目标负载下的 SLO 与成本 → 可回滚的线上验证**。

## 1. 使用方式与决策流程

本文比较的对象可以是自部署开源权重，也可以是托管 API；两者都应按同一业务质量与服务等级目标（SLO）评估；供应商或团队的服务等级协议（SLA）则是另一项约束。[Google SRE：服务等级目标与协议](https://sre.google/sre-book/service-level-objectives/)

评估重点不同：自部署更需要关注权重显存、推理引擎和硬件拓扑，托管 API 更需要关注数据边界、配额、区域和供应商 SLA。

```text
明确任务与约束
  -> 硬性准入检查（不通过即淘汰）
  -> 真实业务集质量评测（不达标即淘汰）
  -> 相同条件下性能、容量与成本压测
  -> 加权决策与风险记录
  -> 灰度上线、监控、回滚
```

## 2. 选型输入：先写清问题，再找模型

开始比较前，为每个业务填写一张选型卡。没有这张卡，后续“哪个模型更好”的讨论没有共同标准。

| 项目 | 需要回答的问题 | 示例 |
| --- | --- | --- |
| 业务任务 | 模型要完成什么，可接受哪些失败？ | 医疗客服知识问答；不能编造就诊规则。 |
| 输入与输出 | 语言、模态、平均/P95 输入输出 token、是否需要 JSON/工具调用？ | 中文；输入 P95 为 8k token；输出必须符合 JSON Schema。 |
| 质量门槛 | 哪些指标必须通过，谁负责判定？ | 专家评分任务成功率 ≥ 90%，高风险规则零容忍。 |
| SLO | 并发、P95 TTFT、P95 TPOT、可用性和超时上限？ | 50 并发；P95 TTFT ≤ 2 秒。 |
| 约束 | 数据、许可证、预算、硬件、交付时间？ | 私有数据不可出域；可用 4 张 GPU。 |
| 回退方案 | 模型不可用或质量退化时如何处理？ | 降级到已验证模型；高风险请求转人工。 |

> P95 是指 95% 请求不超过该值。对于交互式生成，平均时延好看但 P95/P99 恶化，用户仍会明显感到卡顿。

## 3. 硬性准入检查

以下项目不是“评分项”，而是淘汰条件。任一项不满足，就不应继续为该候选模型投入大量评测成本。

### 3.1 能力与接口匹配

- 是否覆盖目标语言、领域、输入模态与所需上下文长度？
- 是否支持业务需要的工具调用、结构化输出、流式输出或多轮对话？
- 使用的推理引擎是否支持该架构、量化格式和所需功能？
- 模型版本、tokenizer 和 chat template 是否明确且能锁定？

### 3.2 合规与供应链

- 许可证是否允许目标用途、商用和再分发？应以模型仓库中的许可证原文和组织法务结论为准。
- 输入、日志、缓存和人工标注数据是否满足数据驻留、脱敏和访问控制要求？
- 托管 API 是否满足所在区域、保留策略、配额和故障处理要求？

### 3.3 部署可行性与显存预估

权重显存的理论下界可粗估为：

```text
权重字节数 ≈ 总参数量 × 每参数字节数
```

FP16/BF16 约为 2 字节/参数，8-bit 约为 1 字节/参数，4-bit 约为 0.5 字节/参数；实际还需要预留量化元数据、运行时工作区、CUDA 图和碎片等开销。

KV Cache 会随**并发序列数**和**上下文长度**增长。对于典型 decoder-only 模型，在不考虑分页/共享/实现优化时，可用下式做数量级估算：

```text
KV Cache 字节数 ≈ 2 × 层数 × 并发序列数 × token 数
                  × KV 头数 × 单头维度 × 元素字节数
```

MoE 的激活参数较少，但常驻权重容量应按**全部需加载的权重**估算，包括路由专家、共享专家、注意力与其他共享层，不能只按单 token 激活参数计算。分片、复制和 CPU 卸载会改变每张卡的实际占用；精确容量须通过目标引擎压测确认。KV 头数为何影响缓存，见 [[06-AI应用后端/01-模型基础/LLM#5.6 MHA、MQA、GQA 为什么影响 KV 显存|LLM：KV 缓存容量]]。

## 4. 架构会如何影响部署

### 4.1 三者的关系

```text
计算方式
├── 稠密计算（Dense）
│   └── 每个 token 走相同的稠密层路径，不做专家选择
└── 条件计算（Conditional Computation）
    └── 按输入/token/任务选择部分计算路径
        └── 混合专家模型（MoE）
            └── router 为 token 选择少数专家网络
```

条件计算是上位思想；MoE 是模型内部条件计算的典型形式。RAG、工具调用也会按需执行，但它们是系统级条件执行，并不因此成为 MoE。

### 4.2 对选型有用的差异

| 类型 | 推理路径 | 常见部署优势 | 必须验证的风险 |
| --- | --- | --- | --- |
| 稠密模型 | 每个 token 使用固定 MLP/FFN | 路径固定；在小 batch、少 GPU 下更容易得到稳定时延 | 权重和每 token 计算通常随模型规模同步增加。 |
| MoE | router 选择 top-k 个专家 FFN | 可扩大总容量，而每 token 只计算少数专家 | 总专家权重、跨卡 all-to-all、专家负载不均与小 batch 利用率。 |
| 其他条件计算 | 可能早退、变深度或调用外部能力 | 可按任务分配预算 | 判断或调度开销、路径不稳定性和额外失败模式。 |

MoE 不能被简单理解为“更省显存”或“必然更快”。Switch Transformer 的原始工作也将通信、路由和训练稳定性列为关键挑战。[Switch Transformers](https://arxiv.org/abs/2101.03961)

### 4.3 一个 token 如何经过 MoE 层

以常见的 **token-choice top-k MoE FFN** 为例，注意力得到 token 的隐藏向量 h 后，router 将 h 投影成每个专家的分数，再选择少量专家。被选专家各自计算 FFN，输出按路由权重聚合，回到原 token 位置并继续后续层。

```text
h → router 分数 → 选择 top-k → 按专家分发 token
  → 各专家 FFN → 按路由权重加权、还原 token 顺序 → 后续层
```

可用 `y = Σ g_e(h) · E_e(h)` 表示聚合，其中求和只覆盖选中专家。真实模型的路由打分、top-k 后是否重新归一化、是否额外缩放、是否有始终参与的共享专家，均取决于模型；不能仅凭“MoE”推断这些细节。专家一般是训练得到的参数网络，并非人工指定的“法律专家”“代码专家”，也不是多个独立聊天模型互相讨论。

教学例设四个专家分别将标量输入乘以 1、2、3、4，router 为第一个 token 给出 `[3,2,0,-1]`，选 top-2 并在选中项内归一化。权重约为 `[0.731,0.269]`，输入 2 得到 `0.731×2 + 0.269×4 ≈ 2.538`。这里刻意把真实非线性 FFN 简化成乘法，以单独观察路由与聚合。

```python
from math import exp, isclose


def moe(x, logits, k=2):
    chosen = sorted(range(len(logits)), key=lambda i: (-logits[i], i))[:k]
    peak = max(logits[i] for i in chosen)
    raw = [exp(logits[i]-peak) for i in chosen]
    weights = [v/sum(raw) for v in raw]
    output = sum(w*(i+1)*x for i, w in zip(chosen, weights))
    return output, chosen, weights


first, ids, weights = moe(2, [3, 2, 0, -1])
second, other_ids, _ = moe(2, [-1, 0, 2, 3])
assert ids == [0, 1] and other_ids == [3, 2]
assert isclose(sum(weights), 1)
assert isclose(first, 2.5378828427399904)
assert isclose(second, 7.46211715726001)
assert len(set(ids + other_ids)) == 4
print("MoE 实验通过：每 token 两个专家，两个 token 合计触及四个专家")
```

验证记录：2026-10-29，Python 3.12.9，以上代码运行通过；两组路由、聚合数值及批次触及专家数符合断言。未测真实 MoE 模型性能。

实验说明：**单 token 激活少，不代表整个 batch 只需存放这几个专家。** 活跃 token 越多，可能触及的专家越多。`activated parameters` 也不是完整 FLOPs 或延迟指标，通常还须计入共享层、路由和数据搬运；不同模型的统计口径应看模型卡。

### 4.4 专家负载、容量和跨卡通信

如果大多数 token 都被送到同一专家，其他专家空闲，热门专家排队，稀疏计算的理论收益会被吞掉。训练中的负载均衡机制旨在避免长期集中，但不同方案可能采用辅助损失或其他路由控制，不能假定都有同一条 loss。

一些实现为每个专家设置 token 容量，超额 token 如何丢弃、走残差、改路由或分批，属于具体算法；另一些实现不丢 token，以动态调度或更多缓冲处理不均衡。“top-k 一定每次完成 k 个专家计算”因此也要结合容量策略判断。Switch 是特定的 top-1 设计，不能拿它代替所有 MoE 的执行语义。

当专家分布在不同设备上，expert parallelism 要把 token 表示送到专家所在卡，再把输出送回聚合。常见通信形态为 all-to-all，代价取决于 token 数、隐藏维度、top-k、互联以及部署映射。**专家并行**分散不同专家，**张量并行**拆分同一算子/权重，两者可组合，不能混为一谈。路由复杂度、通信及训练稳定性是原始 MoE 研究明确讨论的问题。[Switch Transformers](https://arxiv.org/abs/2101.03961)

部署时应把“算得少”拆成可观测的部分：每专家 token 数及最大/平均负载、分发与回收耗时、专家算子耗时、设备利用率，以及业务端 TTFT/TPOT/P95。小 batch 下每个专家分到的 token 很少，矩阵计算利用率可能较差；跨卡通信也可能盖过省下的计算。测试前不能据激活参数量宣称 MoE 比同质量稠密模型更快。

## 5. 真实业务质量评测

### 5.1 建立评测集

公开基准可以提供能力信号，但不能代替业务评测。选型时从真实请求脱敏抽样，按业务场景、难度、输入长度、语言和风险分层，明确字段准确、引用可追溯及不确定时转人工等通过条件；保留代表性失败样本，不只看汇总分数。数据划分、防泄漏、模型裁判和统计比较统一按 [[AI应用评测与错误分析]] 执行，最终验收集不参与反复调 Prompt 或挑模型。

### 5.2 质量指标

| 任务类型 | 首选业务指标 | 需要额外检查的项 |
| --- | --- | --- |
| 信息抽取/结构化输出 | 字段准确率、Schema 合规率、解析成功率 | 漏字段、非法枚举、单位与日期错误。 |
| 知识问答/RAG | 有证据回答率、人工正确率、引用正确率 | 无证据时拒答或澄清是否正确。 |
| 内容生成 | 基于评分量表的人工偏好、返工率 | 风格、事实性、敏感内容。 |
| Agent/工具调用 | 端到端任务成功率、工具参数正确率 | 越权、重复执行、错误后的停止或转人工。 |

对高风险任务，模型评分或 LLM-as-a-judge 只能辅助抽样；最终应有可审计的规则校验或领域专家复核。

## 6. 性能、容量与成本压测

### 6.1 固定实验条件

横向比较必须记录并尽量统一：模型与权重版本、量化格式、推理引擎及版本、GPU 与网络拓扑、chat template、采样参数、缓存策略、输入输出长度分布、热身次数和并发到达方式。

不要把“模型 A 使用 4-bit、模型 B 使用 BF16”或“一个使用短 prompt、另一个使用长 prompt”的结果直接归因于模型架构。

### 6.2 压测矩阵

至少覆盖以下三类请求，且分别以 1、目标并发和超出目标并发进行压测：

| 场景 | 输入/输出特点 | 主要观察指标 |
| --- | --- | --- |
| 短交互 | 短输入、短输出 | P95 TTFT、P95 端到端时延。 |
| 长上下文 | 输入接近业务 P95 | prefill 吞吐、TTFT、KV Cache 峰值。 |
| 长生成 | 输出接近业务 P95 | P95 TPOT、decode 吞吐、超时率。 |

- **TTFT（Time To First Token）**：明确计时边界。服务端口径从收到请求到发出首 token，客户端口径从发起请求到收到首 token；后者还受网络等因素影响。[[06-AI应用后端/01-模型基础/LLM#6.6 从时延现象定位瓶颈|LLM：时延分析]] 使用客户端口径，两者不能混作同一组数据。
- **TPOT（Time Per Output Token）**：生成阶段相邻输出 token 的平均间隔；报告 P95 时应同时说明统计口径。
- **吞吐**：报告 tokens/s 和 requests/s，并注明是在何种请求长度与并发下测得。

### 6.3 成本口径

不要只比较“每百万 token 价格”或“单卡 tokens/s”。建议至少计算：

```text
每成功任务成本 = 测试窗口内的模型、GPU/实例、网络与必要平台成本
                 / 该窗口内通过业务质量判定的任务数
```

它把模型质量、重试和失败请求纳入成本。对于自部署，还应单列 GPU 利用率、峰值显存、排队时长与错误率；对于 API，还应单列输入/输出 token 单价、失败重试和限流影响。

## 7. 形成可审计的决策

质量门槛通过后，再根据本业务的优先级加权比较。权重不是通用常数，应由产品、业务和平台负责人共同确认。

| 候选项 | 是否通过硬门槛 | 业务质量 | P95 TTFT / TPOT | 目标并发吞吐 | 峰值显存 | 每成功任务成本 | 主要风险 | 结论 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 模型 A | 是/否 | 评测结果与置信说明 | 实测值 | 实测值 | 实测值 | 实测值 | 风险与缓解 | 推荐/备选/淘汰 |
| 模型 B | 是/否 | 评测结果与置信说明 | 实测值 | 实测值 | 实测值 | 实测值 | 风险与缓解 | 推荐/备选/淘汰 |

推荐结论必须写明适用前提，例如“仅适用于 4 张高速互联 GPU、并发不低于 32 的部署”；条件变化后不能直接复用旧结论。

## 8. 上线、监控与回滚

1. 使用灰度流量验证离线结论，保留对照模型或人工兜底。
2. 持续监控业务成功率、拒答/转人工率、P95/P99 时延、超时率、tokens/s、GPU/显存、排队与单位成本。
3. 为模型、Prompt、tokenizer/chat template、量化、推理引擎和 RAG 策略建立版本记录；任一关键变更都应运行回归集。
4. 明确降级和回滚触发条件，例如质量回归、超时率异常、成本超预算或供应商不可用。
5. 对 Agent 等有副作用的场景，回滚不等于撤销已执行动作；关键写操作仍需幂等、审计和人工审批边界。

## 附录 A：如何判断模型是不是稠密 / MoE

判断的是**推理时实际走过的计算路径**，而不是模型名称或总参数量。

1. 看模型卡：出现 `Mixture of Experts`、`router`、`gate`、`experts` 或“每个 token 选择 top-k 个专家”是 MoE 证据。
2. 看 Hugging Face `config.json`：`model_type: "..._moe"`、`num_experts`、`num_local_experts`、`n_routed_experts`、`num_experts_per_tok`、`router_aux_loss_coef`、`moe_intermediate_size` 等字段组合是强信号。
3. 配置不明确时看前向代码：所有 token 调用同一个 `MLP/FFN` 是稠密；`router/gate` 对 token 打分、top-k 分发到多个专家再合并，是 MoE。
4. 仅部分层使用专家时，称为混合式 MoE；早退、动态深度或 RAG 没有专家子网络时，属于其他条件计算。

例如 [Qwen1.5-MoE-A2.7B 的配置](https://huggingface.co/Qwen/Qwen1.5-MoE-A2.7B/blob/main/config.json)中有：

以下摘取相关字段，省略其他配置：

```json
{
  "model_type": "qwen2_moe",
  "num_experts": 60,
  "num_experts_per_tok": 4,
  "moe_intermediate_size": 1408,
  "shared_expert_intermediate_size": 5632,
  "router_aux_loss_coef": 0.001
}
```

这里是 **60 个路由专家，每 token 选 4 个，另外还有始终参与的共享专家部分**。官方介绍按细粒度专家容量将共享部分表述为 4 个共享专家；配置中共享中间维度为 `5632 = 4 × 1408`，不能把 `num_experts=60` 当作所有专家的总数。`router_aux_loss_coef` 是辅助损失系数配置，是否实际计算并加入训练损失仍取决于训练实现；推理路由也不等于执行辅助损失。[Qwen 官方架构说明](https://qwenlm.github.io/blog/qwen-moe/)

以上配置与架构说明于 2026-10-29 复核；具体模块组织仍以所用模型版本及前向实现为准。

## 附录 B：术语与面试简答

- **总参数**：存储与加载的全部权重规模；MoE 的专家通常都计入其中。
- **激活参数**：按模型约定统计的每 token 参与计算参数规模；可辅助理解专家计算量，但不等于 FLOPs，还遗漏注意力随上下文增长等成本。
- **稠密模型**：每个 token 走相同的稠密层路径，不按 token 选择专家子网络。
- **条件计算**：根据输入选择计算路径。
- **MoE**：条件计算的一种，router 为 token 选择少数专家。

30 秒回答：稠密模型每个 token 经过固定的稠密层路径，部署路径相对简单；MoE 通过 router 只激活少数专家，能以较低单 token 计算获得更大总容量，但仍要处理专家权重显存、跨卡通信与负载均衡。选型应先以真实业务集设质量门槛，再在同等硬件、量化和负载下比较 P95 TTFT、TPOT、吞吐、显存、稳定性和每成功任务成本。
