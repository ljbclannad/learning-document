# LLM 模型选型与部署评估：稠密、MoE 与条件计算

> 本文用于为具体业务选择并上线 LLM。结论不应来自单一排行榜、参数量或模型名称，而应来自：**硬性准入条件 → 真实业务质量 → 目标负载下的 SLA 与成本 → 可回滚的线上验证**。

## 1. 使用方式与决策流程

本文比较的对象可以是自部署开源权重，也可以是托管 API；两者都应按同一业务质量与服务等级目标（SLA）评估。区别仅在于自部署更需要关注权重显存、推理引擎和硬件拓扑，托管 API 更需要关注数据边界、配额、区域和供应商 SLA。

```text
明确任务与约束
  -> 硬性准入检查（不通过即淘汰）
  -> 真实业务集质量评测（不达标即淘汰）
  -> 相同条件下性能、容量与成本压测
  -> 加权决策与风险记录
  -> 灰度上线、监控、回滚
```

## 2. 选型输入：先写清问题，再找模型

开始比较前，为每个业务填写一张选型卡。没有这张卡，后续“哪个模型更好”的讨论没有共同标准。

| 项目 | 需要回答的问题 | 示例 |
| --- | --- | --- |
| 业务任务 | 模型要完成什么，可接受哪些失败？ | 医疗客服知识问答；不能编造就诊规则。 |
| 输入与输出 | 语言、模态、平均/P95 输入输出 token、是否需要 JSON/工具调用？ | 中文；输入 P95 为 8k token；输出必须符合 JSON Schema。 |
| 质量门槛 | 哪些指标必须通过，谁负责判定？ | 专家评分任务成功率 ≥ 90%，高风险规则零容忍。 |
| SLA | 并发、P95 TTFT、P95 TPOT、可用性和超时上限？ | 50 并发；P95 TTFT ≤ 2 秒。 |
| 约束 | 数据、许可证、预算、硬件、交付时间？ | 私有数据不可出域；可用 4 张 GPU。 |
| 回退方案 | 模型不可用或质量退化时如何处理？ | 降级到已验证模型；高风险请求转人工。 |

> P95 是指 95% 请求不超过该值。对于交互式生成，平均时延好看但 P95/P99 恶化，用户仍会明显感到卡顿。

## 3. 硬性准入检查

以下项目不是“评分项”，而是淘汰条件。任一项不满足，就不应继续为该候选模型投入大量评测成本。

### 3.1 能力与接口匹配

- 是否覆盖目标语言、领域、输入模态与所需上下文长度？
- 是否支持业务需要的工具调用、结构化输出、流式输出或多轮对话？
- 使用的推理引擎是否支持该架构、量化格式和所需功能？
- 模型版本、tokenizer 和 chat template 是否明确且能锁定？

### 3.2 合规与供应链

- 许可证是否允许目标用途、商用和再分发？应以模型仓库中的许可证原文和组织法务结论为准。
- 输入、日志、缓存和人工标注数据是否满足数据驻留、脱敏和访问控制要求？
- 托管 API 是否满足所在区域、保留策略、配额和故障处理要求？

### 3.3 部署可行性与显存预估

权重显存的理论下界可粗估为：

```text
权重字节数 ≈ 总参数量 × 每参数字节数
```

FP16/BF16 约为 2 字节/参数，8-bit 约为 1 字节/参数，4-bit 约为 0.5 字节/参数；实际还需要预留量化元数据、运行时工作区、CUDA 图和碎片等开销。

KV Cache 会随**并发序列数**和**上下文长度**增长。对于典型 decoder-only 模型，在不考虑分页/共享/实现优化时，可用下式做数量级估算：

```text
KV Cache 字节数 ≈ 2 × 层数 × 并发序列数 × token 数
                  × KV 头数 × 单头维度 × 元素字节数
```

MoE 的激活参数较少，但估算权重显存时应以**总专家权重**为主，而不是激活参数。精确容量必须通过目标推理引擎的实际压测确认。

## 4. 架构会如何影响部署

### 4.1 三者的关系

```text
计算方式
├── 稠密计算（Dense）
│   └── 每个 token 固定经过同一套参数
└── 条件计算（Conditional Computation）
    └── 按输入/token/任务选择部分计算路径
        └── 混合专家模型（MoE）
            └── router 为 token 选择少数专家网络
```

条件计算是上位思想；MoE 是模型内部条件计算的典型形式。RAG、工具调用也会按需执行，但它们是系统级条件执行，并不因此成为 MoE。

### 4.2 对选型有用的差异

| 类型 | 推理路径 | 常见部署优势 | 必须验证的风险 |
| --- | --- | --- | --- |
| 稠密模型 | 每个 token 使用固定 MLP/FFN | 路径固定；在小 batch、少 GPU 下更容易得到稳定时延 | 权重和每 token 计算通常随模型规模同步增加。 |
| MoE | router 选择 top-k 个专家 FFN | 可扩大总容量，而每 token 只计算少数专家 | 总专家权重、跨卡 all-to-all、专家负载不均与小 batch 利用率。 |
| 其他条件计算 | 可能早退、变深度或调用外部能力 | 可按任务分配预算 | 判断或调度开销、路径不稳定性和额外失败模式。 |

MoE 不能被简单理解为“更省显存”或“必然更快”。Switch Transformer 的原始工作也将通信、路由和训练稳定性列为关键挑战。[Switch Transformers](https://arxiv.org/abs/2101.03961)

## 5. 真实业务质量评测

### 5.1 建立评测集

公开基准可以提供能力信号，但不能代替业务评测。建立评测集时应：

1. 从真实请求中脱敏抽样，按业务场景、难度、输入长度、语言和风险等级分层。
2. 划分开发集与最终测试集；最终测试集不应被用于反复调 Prompt 或挑模型。
3. 为每类任务写清通过条件和失败类型，例如“金额抽取字段正确”“引用必须可追溯”“不确定时转人工”。
4. 保留代表性失败样本，避免只看一个汇总分数。

### 5.2 质量指标

| 任务类型 | 首选业务指标 | 需要额外检查的项 |
| --- | --- | --- |
| 信息抽取/结构化输出 | 字段准确率、Schema 合规率、解析成功率 | 漏字段、非法枚举、单位与日期错误。 |
| 知识问答/RAG | 有证据回答率、人工正确率、引用正确率 | 无证据时拒答或澄清是否正确。 |
| 内容生成 | 基于评分量表的人工偏好、返工率 | 风格、事实性、敏感内容。 |
| Agent/工具调用 | 端到端任务成功率、工具参数正确率 | 越权、重复执行、错误后的停止或转人工。 |

对高风险任务，模型评分或 LLM-as-a-judge 只能辅助抽样；最终应有可审计的规则校验或领域专家复核。

## 6. 性能、容量与成本压测

### 6.1 固定实验条件

横向比较必须记录并尽量统一：模型与权重版本、量化格式、推理引擎及版本、GPU 与网络拓扑、chat template、采样参数、缓存策略、输入输出长度分布、热身次数和并发到达方式。

不要把“模型 A 使用 4-bit、模型 B 使用 BF16”或“一个使用短 prompt、另一个使用长 prompt”的结果直接归因于模型架构。

### 6.2 压测矩阵

至少覆盖以下三类请求，且分别以 1、目标并发和超出目标并发进行压测：

| 场景 | 输入/输出特点 | 主要观察指标 |
| --- | --- | --- |
| 短交互 | 短输入、短输出 | P95 TTFT、P95 端到端时延。 |
| 长上下文 | 输入接近业务 P95 | prefill 吞吐、TTFT、KV Cache 峰值。 |
| 长生成 | 输出接近业务 P95 | P95 TPOT、decode 吞吐、超时率。 |

- **TTFT（Time To First Token）**：从请求进入服务到返回首 token 的时间，包含排队、prefill 与调度影响。
- **TPOT（Time Per Output Token）**：生成阶段相邻输出 token 的平均间隔；报告 P95 时应同时说明统计口径。
- **吞吐**：报告 tokens/s 和 requests/s，并注明是在何种请求长度与并发下测得。

### 6.3 成本口径

不要只比较“每百万 token 价格”或“单卡 tokens/s”。建议至少计算：

```text
每成功任务成本 = 测试窗口内的模型、GPU/实例、网络与必要平台成本
                 / 该窗口内通过业务质量判定的任务数
```

它把模型质量、重试和失败请求纳入成本。对于自部署，还应单列 GPU 利用率、峰值显存、排队时长与错误率；对于 API，还应单列输入/输出 token 单价、失败重试和限流影响。

## 7. 形成可审计的决策

质量门槛通过后，再根据本业务的优先级加权比较。权重不是通用常数，应由产品、业务和平台负责人共同确认。

| 候选项 | 是否通过硬门槛 | 业务质量 | P95 TTFT / TPOT | 目标并发吞吐 | 峰值显存 | 每成功任务成本 | 主要风险 | 结论 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 模型 A | 是/否 | 评测结果与置信说明 | 实测值 | 实测值 | 实测值 | 实测值 | 风险与缓解 | 推荐/备选/淘汰 |
| 模型 B | 是/否 | 评测结果与置信说明 | 实测值 | 实测值 | 实测值 | 实测值 | 风险与缓解 | 推荐/备选/淘汰 |

推荐结论必须写明适用前提，例如“仅适用于 4 张高速互联 GPU、并发不低于 32 的部署”；条件变化后不能直接复用旧结论。

## 8. 上线、监控与回滚

1. 使用灰度流量验证离线结论，保留对照模型或人工兜底。
2. 持续监控业务成功率、拒答/转人工率、P95/P99 时延、超时率、tokens/s、GPU/显存、排队与单位成本。
3. 为模型、Prompt、tokenizer/chat template、量化、推理引擎和 RAG 策略建立版本记录；任一关键变更都应运行回归集。
4. 明确降级和回滚触发条件，例如质量回归、超时率异常、成本超预算或供应商不可用。
5. 对 Agent 等有副作用的场景，回滚不等于撤销已执行动作；关键写操作仍需幂等、审计和人工审批边界。

## 附录 A：如何判断模型是不是稠密 / MoE

判断的是**推理时实际走过的计算路径**，而不是模型名称或总参数量。

1. 看模型卡：出现 `Mixture of Experts`、`router`、`gate`、`experts` 或“每个 token 选择 top-k 个专家”是 MoE 证据。
2. 看 Hugging Face `config.json`：`model_type: "..._moe"`、`num_experts`、`num_local_experts`、`n_routed_experts`、`num_experts_per_tok`、`router_aux_loss_coef`、`moe_intermediate_size` 等字段组合是强信号。
3. 配置不明确时看前向代码：所有 token 调用同一个 `MLP/FFN` 是稠密；`router/gate` 对 token 打分、top-k 分发到多个专家再合并，是 MoE。
4. 仅部分层使用专家时，称为混合式 MoE；早退、动态深度或 RAG 没有专家子网络时，属于其他条件计算。

例如 [Qwen1.5-MoE-A2.7B 的配置](https://huggingface.co/Qwen/Qwen1.5-MoE-A2.7B/blob/main/config.json)中有：

```json
"model_type": "qwen2_moe",
"num_experts": 60,
"num_experts_per_tok": 4,
"router_aux_loss_coef": 0.001
```

即 60 个专家、每个 token 选择 4 个，并使用路由辅助损失缓解专家负载不均。

## 附录 B：术语与面试简答

- **总参数**：存储与加载的全部权重规模；MoE 的专家通常都计入其中。
- **激活参数**：一次处理 token 时参与计算的参数，较接近单 token FLOPs。
- **稠密模型**：每个 token 走同一套参数路径。
- **条件计算**：根据输入选择计算路径。
- **MoE**：条件计算的一种，router 为 token 选择少数专家。

30 秒回答：稠密模型每个 token 使用固定的一整套参数，部署路径相对简单；MoE 通过 router 只激活少数专家，能以较低单 token 计算获得更大总容量，但仍要处理专家权重显存、跨卡通信与负载均衡。选型应先以真实业务集设质量门槛，再在同等硬件、量化和负载下比较 P95 TTFT、TPOT、吞吐、显存、稳定性和每成功任务成本。
