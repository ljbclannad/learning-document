# Agent（智能体）

## 1. Agent 是什么

在 LLM 应用里，**Agent（智能体）** 是一个以目标为中心、能够结合上下文进行判断，并按需调用外部能力来推进任务的执行体。

它不等于一个聊天机器人，也不等于一次 Tool Calling。一次普通对话通常是“输入 -> 模型生成 -> 输出”；而 Agent 面对的是“完成一个目标”，中间可能需要理解任务、补齐信息、选择工具、观察工具结果、调整下一步，并在满足结束条件后交付结果。

### 1.1 Agent = Model + Harness

常见的表达式是：

```text
Agent = Model + Harness
```

其中，**Model（模型）** 提供理解、归纳、生成和候选决策等概率性能力；**Harness（运行与约束系统）** 则把模型接入一个受控的任务环境，使其能够获得必要信息、调用能力、保存状态，并在规则约束下完成任务。

`harness` 原意是“马具、缰绳或安全带”。这个词强调两件事：一方面把模型能力连接到真实任务中，另一方面对其行动施加边界和保护。它不是某个固定的标准组件或单一框架；不同 Agent 框架对其边界划分不同，但下列能力通常属于 Harness。

| 部分 | Model 负责什么 | Harness 负责什么 |
| --- | --- | --- |
| 判断与行动 | 理解输入、提出下一步候选动作或结论。 | 提供允许调用的 Tool / Skill，校验参数、权限和副作用。 |
| 信息 | 根据已有上下文进行推理。 | 准备 system prompt、当前 context、检索证据和 memory。 |
| 多步执行 | 基于观察结果继续生成下一步。 | 编排循环、状态转换、任务暂停、恢复、重试和结束。 |
| 安全与质量 | 无法自行保证输出或行动一定正确。 | 执行规则校验、人工审批、日志追踪、评测、限流和降级。 |

图示中的 `system prompt`、`context`、`memory`、`tools`、`skills`、`subagents` 都可视为 Harness 的组成部分；但 Harness 通常还包括 Workflow、状态持久化、权限控制、失败恢复和可观测性。

可以用下面的边界理解它们的关系：

```text
用户目标
  -> Harness 准备规则、上下文、记忆与可用能力
  -> Model 判断下一步
  -> Harness 校验并执行 Tool / Skill，记录结果和状态
  -> Model 基于观察结果继续，或由 Harness 暂停、转人工、结束
```

因此，Harness 不是“模型以外所有代码”的随意集合，而是**让模型能力可被使用、被约束、被恢复和被验证的系统性边界**。Skill 是其中可复用的任务能力模块，Tool 是受控的外部操作接口，Workflow 是多步执行的确定性骨架；它们都可以服务于同一个 Agent，但不等同于 Agent 本身。

一个可落地的 Agent 通常包含以下部分：

| 部分 | 作用 |
| --- | --- |
| 目标与约束 | 定义要完成什么、不能做什么，以及何时结束或转人工。 |
| 模型 | 负责理解、归纳、路由、提出候选动作等非确定性判断。 |
| 上下文与记忆 | 提供当前会话、用户画像、历史证据、任务状态等必要信息。 |
| 工具 | 连接检索、数据库、业务 API、文件系统等外部能力；工具执行才会产生可验证的外部事实或副作用。 |
| 编排与状态 | 控制多步任务如何推进、暂停、失败、恢复和结束。 |
| 安全与治理 | 负责权限、参数校验、审计、观测、评测、限流和降级。 |

可以用下面的循环理解其核心行为：

```text
目标 / 当前状态
    -> 模型判断下一步
    -> 调用工具或请求人工确认
    -> 获得可验证的观察结果
    -> 更新显式状态
    -> 继续、结束或回退
```

这里的“模型判断”与“系统执行”必须分开：模型可以建议调用什么工具、给出什么参数或结论，但权限判断、关键状态写入、资金扣减、处方或审批结论等确定性事务，应由系统规则和受控工具最终裁决。

## 2. Agent、工作流与 Skill 的区别

Agent、Workflow（工作流）与 Skill（技能）不是互斥关系。它们分别关注**谁来决定下一步**、**整条链路如何推进**和**某项能力如何复用**。

其中，Agent 与 Skill 最本质的差异在于**自主决策范围**：Agent 围绕一个目标，能根据当前上下文和执行结果判断下一步该做什么、是否调用哪个能力；Skill 则是已经定义边界的可复用能力或流程，被调用后在既定范围内完成一类任务。换言之，Agent 负责“决定怎么做”，Skill 负责“把这件既定的事做好”。

| 维度 | Agent | Workflow（工作流） | Skill（技能） |
| --- | --- | --- | --- |
| 核心角色 | 以目标为中心的执行体，动态决定下一步。 | 预先定义的流程骨架，控制步骤和状态推进。 | 可复用的任务能力模块，封装某类既定工作如何完成。 |
| 关注的问题 | 面对当前目标，该做什么、调用什么、何时结束。 | 多个节点以什么顺序、条件和异常分支运行。 | 同类任务的目标、输入输出、Prompt、工具约束如何沉淀和复用。 |
| 决策权 | Agent 根据目标、上下文和观察结果，动态决定下一步、能力组合与结束条件。 | 开发者预先定义节点、顺序、分支和结束条件。 | 调用方决定何时使用该 Skill；Skill 按预设目标和边界执行，通常不负责选择其他 Skill 或规划全局路径。 |
| 适合的问题 | 目标明确但路径不固定，例如复杂分析、研究、跨系统排障、开放式任务处理。 | 步骤、输入输出和异常分支稳定，例如表单处理、固定审批、确定性数据处理。 | 高频且边界相对稳定的能力，例如知识检索、报告总结、文档处理或代码修改。 |
| 优势 | 对未知输入和路径变化适应性更强，能动态选择信息和工具。 | 可预测、易审计、易测试，成本、时延和风险更容易控制。 | 复用性高，能力边界、权限和评测入口更清晰。 |
| 主要风险 | 路径不稳定，可能选错工具、重复执行或产生越权与幻觉执行。 | 对未预见的分支适应性弱，流程变化需要修改编排。 | 边界划分不当会形成臃肿的“万能 Skill”，或与具体业务场景脱节。 |
| 工程重点 | 上下文、工具边界、状态、验证器、安全与评测。 | 节点编排、状态转换、异常补偿、幂等与可观测性。 | 输入输出契约、工具权限、版本、评测样本与文档化。 |

### 2.1 如何选择

- 任务不确定性高，且下一步动作依赖语义理解或外部观察结果时，适合引入 Agent 或 ReAct 式循环。
- 流程边界固定、合规要求高、错误代价高，或规则已经能稳定覆盖时，应优先选择 Workflow 或传统系统。
- 如果动作完成后没有可靠的验证闭环，不应让 Agent 自主试错；应收敛为人工确认或确定性流程。

生产系统常采用**混合模式**：外层用确定性的 Workflow 管理入口、关键步骤、审批、补偿和审计；只在高不确定的节点使用模型做分类、信息抽取、候选方案生成或动态工具选择。这样既保留模型的适应性，也避免把整条业务链路交给非确定性决策。

### 2.2 Agent 与 Skill：自主决策与能力复用

Skill 更像**能力封装层**，而不是一个会自主规划的执行体。它把任务目标、输入要求、执行步骤、Prompt、可用工具、输出格式和权限约束收敛为一个可独立复用、维护和评测的模块。

可以从决策链路上区分：

```text
Agent：目标 -> 判断当前缺什么 -> 选择 Skill / Tool -> 观察结果 -> 决定下一步
Skill：被调用 -> 按约定的输入、步骤、工具边界完成一项任务 -> 返回约定的结果
```

例如，“生成医疗报告摘要”是一个 Skill：它约定输入哪些数据、遵守哪些脱敏规则、使用哪些工具、返回什么结构化格式。一个 Agent 接到“帮我评估当前风险并给出后续建议”的目标后，才会根据上下文决定是否先使用数据收集 Skill、风险识别 Skill，再使用报告摘要 Skill，或者因信息不足而继续追问或转人工。

因此：

- **Skill 的工具使用通常是预先约束的**：它可调用哪些工具、输入输出格式和权限范围已被定义；它不应自行扩大权限或把模型文本直接变成执行指令。
- **Agent 的“智能”体现在跨能力决策**：它对不确定任务进行规划、选择和调整，并根据工具观察结果决定后续路径。
- **Skill 内部也可以使用模型**：例如从多个固定模板中选一个，或在受限工具集合中作局部选择；这只是 Skill 内部的有限决策。只要它不承担跨能力的目标分解、全局状态推进和动态路径规划，就不等同于完整 Agent。

因此，Skill 与其他概念的关系通常是：

- Prompt 是 Skill 的一种实现细节，用来约束模型如何理解和输出。
- Tool Calling 为 Skill 提供外部能力；Skill 可规定哪些工具可用，但工具层仍应做细粒度权限校验。
- Workflow 可以把 Skill 放在某个节点中执行，负责节点之间的确定性编排。
- Agent 可以根据目标选择或组织多个 Skill；Skill 本身通常不负责跨能力的动态规划和全局状态推进。

### 2.3 Tool Calling 在其中的位置

Tool Calling 解决的是“调用哪个外部能力、携带什么参数”；它本身不是完整的 Agent，也不负责整条任务的状态推进。

- 单轮调用、状态简单、动作副作用小的场景，只用 Tool Calling 可能就足够。
- 一旦涉及多步状态、审批、恢复执行、失败补偿或跨系统副作用，就需要 Workflow、状态机或 Agent 编排来控制整个过程。

## 3. 从对话到任务型 Agent 的分层设计

不应让所有用户请求默认进入重型 Agent 链路。一个更稳妥的设计是把普通对话与任务型决策分层：

```text
用户消息
  -> 会话上下文与轻量分流
  -> 普通对话 / 信息补全 / 任务升级候选
  -> 灰度、熔断、待审批短路等二次放行
  -> 任务型 Agent
  -> 患者（或用户）可见回复 + 结构化结果 + 工作台载荷
```

这样做的原因：

- 普通聊天关注吞吐、时延、成本和对话连续性；任务型 Agent 更关注风险控制、状态一致性、审计与恢复。
- 在升级前先完成画像、短期上下文和长期记忆等治理，Agent 可以复用统一的 `context snapshot`，不必每次从零理解任务。
- 命中任务信号不代表必须执行 Agent；仍可通过灰度、熔断、审批窗口和回退策略决定是否真正放行。
- Agent 返回的用户可见回复应回写主对话链路，避免“聊天系统”和“Agent 系统”各自维护历史，造成后续追问断层。

## 4. 生产级 Agent 的关键设计

### 4.1 显式状态，而不是只靠 Prompt

任务型 Agent 是多步状态推进，不能只把中间过程塞进聊天文本。应保存会话或任务 ID、当前步骤、结构化上下文、工具结果、待审批任务和中断原因等信息。

典型状态可包括：`RUNNING`、`WAITING_APPROVAL`、`FINISHED`、`FAILED`、`BLOCKED_BY_SAFETY`。具体名称可随业务调整，但状态转换要明确且可审计。

为保证一致性：

- 同一任务主流程尽量串行推进，避免并发请求同时覆盖状态；检索、数据准备等相互独立的工作可并发。
- 工具返回先写入结构化状态，再供模型使用；不要把模型自然语言当作系统事实。
- 对有副作用的关键动作使用幂等键、版本号或状态机约束，防止重复执行和重复写入。

### 4.2 工具与事实边界

Agent 应区分三类信息：模型推断、工具返回、系统确认的最终状态。只有后两类才可作为正式状态或下一步的强依据；模型推断应被视为候选判断或建议。

工具层至少应提供：工具白名单、身份与资源权限校验、参数 Schema 校验、超时与重试策略，以及对副作用的幂等保护。不要让模型输出直接变成系统执行指令。

### 4.3 安全与人工介入

安全控制应覆盖三个阶段：

- **输入侧**：识别敏感请求、恶意指令和不可信上下文，划清用户内容与系统指令的边界。
- **执行侧**：采用工具白名单、最小权限、身份鉴权和参数过滤；系统规则对高风险操作拥有最终裁决权。
- **输出侧**：脱敏、拦截高风险结论，必要时转人工审核。

人工介入不是失败后的补丁，而应是正式状态节点。对高风险操作、关键事实不确定、模型与规则冲突或多轮仍未收敛的任务，可以暂停为待审批状态；人工确认后从保存的中断点恢复执行，而不是整条链路重跑。

### 4.4 失败恢复与降级

恢复执行的前提是中间状态可还原。恢复时应从中断步骤继续，对已经执行的有副作用动作先做幂等判断；无副作用步骤才可安全重放。

同时应为 Agent 保留降级路径：当工具、模型或下游服务异常时，可回退到普通对话、固定流程或人工处理，避免重链路的波动中断核心用户入口。

### 4.5 单 Agent 与多 Agent

Multi-Agent 不是默认答案。它适合职责边界已经明显分化、单一 Prompt 持续膨胀、角色互相干扰，或无法独立评测的场景。

拆分后的收益是角色可独立调优和评测；代价是编排、共享状态、冲突收敛和监控都更复杂。因此，多 Agent 间应优先共享显式上下文容器和结构化结果，而不是只靠多个 Agent 互传自然语言。

## 5. 评测、观测与上线治理

不要只评价最终回复“像不像”。先按业务定义任务成功，例如“工单被正确创建且未重复执行”或“高风险请求被正确拦截”；再分别衡量结果、过程、风险和效率：

| 维度 | 示例指标 |
| --- | --- |
| 结果 | 任务完成率、答案准确率、业务目标达成率。 |
| 过程 | 工具选择正确率、参数合法率、平均步数、重试率、超时率。 |
| 风险 | 错误执行率、高风险漏拦截率、越权调用率、转人工率。 |
| 效率 | 平均 RT、P95/P99、单任务 Token 成本、工具调用次数。 |

高风险场景需要单独统计，不能被平均指标掩盖；过程正确与结果正确也应分开观察，避免“最终碰巧成功”的链路被误判为稳定成功。

上线时可按用户、租户或流量比例灰度，必要时通过双跑或影子验证比较新旧链路；持续关注完成率、错误率、转人工率、成本和投诉率，并保证能快速切回旧链路或降级路径。

## 6. 一句话总结

Agent 的价值不在于让模型“自主做更多”，而在于将模型擅长的理解、归纳和候选决策，与系统擅长的状态管理、确定性执行、权限控制、审计和治理结合起来，收敛为可验证、可恢复、可持续优化的业务能力。
