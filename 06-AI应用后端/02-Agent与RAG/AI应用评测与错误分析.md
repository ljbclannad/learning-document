# AI 应用评测与错误分析

## 1. 评测先回答：什么结果才算完成

AI 应用的评测对象是带有检索、权限、工具和恢复机制的完整系统。模型回答流畅、JSON 可解析、工具返回 200，都可能与“任务正确完成”相距很远。先定义业务不变量，再决定测量方法，才能知道一次优化改善了哪里、是否引入新的失败。

本文使用两个教学任务：一是 [[RAG]] 中的 A 租户报销制度问答；二是 [[Agent（智能体）#5.3 持久化副作用：成功回执丢失后如何恢复|Agent 登记任务]]。前者要求依据适用日期和可访问制度回答；后者要求只登记已批准版本，并在重试后维持同一业务动作的唯一性。以下数据与门槛均为设计示例，不是项目实测指标。

| 场景 | 正确结果 | 仅看文本可能漏掉的失败 |
| --- | --- | --- |
| 询问新制度下的住宿限额 | 回答 600 元并按问题补充审批例外，引用适用条款 | 答对数字却引用旧版，或泄露 B 租户内容 |
| 业务日期缺失且会影响版本 | 追问关键日期，或清楚给出条件分支 | 无依据默认最新版，评分器只因“600 元”给分 |
| 可访问证据不足 | 明确缺少依据并停止确定性结论 | 编造来源，或把“没查到”当成“不存在” |
| 已批准报告登记，回执丢失 | 查证/同键恢复，只有一条业务记录 | 文本说成功，实际重复登记两次 |
| 登记请求发出后取消 | 停止新写入，查清原动作事实 | 直接宣称“已取消所以未登记” |

通过标准应描述事实与允许行为，不必规定唯一措辞或唯一工具路径。例如允许不同检索顺序，但不允许越权；允许查证恢复，但不允许重试创建新业务动作。

## 2. 建立可复现的任务集

### 2.1 一条用例保存什么

评测用例应能恢复请求发生时的条件，至少保存以下信息。涉及私有数据时，优先使用脱敏样本和可控测试替身，避免将生产凭据或敏感正文复制到评测日志。

```yaml
case_id: expense-a-new-001
family_id: expense-a-date-boundary
input: A 公司普通员工，2026-10-15 在上海出差，住宿上限是多少？
principal_fixture: tenant_a_employee
source_snapshot: expense-policy-fixture-v2
expected_behavior: 回答600元，并按上下文说明审批例外
required_evidence: [A-limit, A-exception]
forbidden_behavior: [读取B租户制度, 使用旧版500元作为本次上限]
fault: none
risk: normal
```

实际保存时应把证据 ID 解析到固定源版本、chunk/hash；`required_evidence` 表示本用例的判断依据，可支持多个等价证据集合，不应机械要求所有问题都引用相同片段。授权身份由评测环境注入，不能因为输入文字声称“我是管理员”就提升权限。

任务集既要有常规问题，也要覆盖版本边界、权限不足、无答案、歧义、工具错误和恢复故障。高风险用例可以刻意过采样，但汇总必须区分“业务流量加权结果”和“风险压力测试结果”，否则一个汇总分数会混淆实际发生频率与风险覆盖。

### 2.2 调优集、验证集与最终验收集

调优集用于观察失败和修改策略；验证集用于比较候选；最终验收集在候选确定后使用。反复看最终集并据此改 Prompt，它就已经参与调优，应更换独立验收样本。

拆分应以产生关联的单位为依据：同一问题的改写、同一任务模板、同一文档的近重复片段不宜随机散到两边。需要评估新用户泛化时按用户分组，需要评估未来版本时按时间和版本分离。分组拆分避免同组样本同时出现在训练/验证侧的原则，可参考 [scikit-learn 的 GroupKFold 说明](https://scikit-learn.org/stable/modules/cross_validation.html#group-k-fold)；这里应用于评测集设计，不要求一定调用该库。

RAG 允许检索答案所在的业务文档，这是任务本身；不能把“测试问题能检索到制度”直接当成泄漏。真正需要排除的是：把测试答案或评分量表塞进检索库、在模拟当时可得信息的历史回放中使用之后才出现的信息、把高度相似的验收题用于调优后仍宣称独立泛化。如果任务本来就是用今天可得的材料追溯过去事件，使用后来发布的资料不自动构成泄漏，但仍要按业务发生日期选择适用规则。评测应同时标明业务时间与允许使用的信息截止时间。公开基准还可能受模型训练数据污染，业务评测需要另行设计。

## 3. 分层指标：结果、过程、风险与效率

| 层面 | 可测对象 | 使用时的边界 |
| --- | --- | --- |
| 业务结果 | 任务成功率、字段准确率、应拒答/追问时的正确行为 | 明确分母；有副作用时核验下游事实 |
| 检索过程 | 适用证据 Recall@K、排序质量、上下文中的证据完整性 | gold 证据不完备会误罚等价材料；无答案任务单独评价 |
| 回答依据 | 关键主张是否被证据支持、引用是否适用、遗漏率 | ID 存在不代表内容蕴含结论，相关也不等于支持 |
| 工具过程 | 参数正确率、审批版本匹配、重试/恢复正确性 | schema 合法不代表业务授权或执行完成 |
| 风险边界 | 越权读取、未批准写入、重复副作用、错误确定性结论 | 单独设门槛，不能用平均文风得分抵消 |
| 效率 | 端到端时延、token、工具次数、成本、人工接管率 | 包含失败与重试，注明并发、缓存、超时和统计口径 |

例如 Recall@K 用“前 K 个候选覆盖了多少条标注的适用证据”衡量召回，若真正需要的是“限额+例外”共同成立，还应报告两者同时进入上下文的用例比例。两个片段分别高召回，并不保证单次回答证据完整。

成本可以同时报告 `总成本/全部请求数` 与 `总成本/成功任务数`。只统计成功请求自身成本会把失败代价藏起来；零成功时后者应记为不可计算或无穷大。时延要区分失败/超时比例与完成请求分位数，不能删除超时样本后声称总体变快。交互式 Agent 的人工审批等待可单列，但端到端用户体验仍需报告。

## 4. 怎样公平比较两次改动

固定数据快照、身份与权限、模型版本、Prompt、工具 schema、检索配置和判分器版本；一次实验尽量只改变待验证因素。新旧方案在**同一批任务**上配对运行，交错执行顺序，记录缓存和系统负载，避免时间段差异被误认为优化效果。

随机模型可对每个任务重复运行多次。每次运行重置测试环境，尤其是写工具状态；运行内的重试保留相同业务动作身份，运行之间则使用隔离的任务空间。不能用新方案“尝试五次挑最好”对比旧方案单次结果，除非产品本身就采用该策略且把全部成本、时延及副作用计入。

设任务 i 的多次运行平均通过率为 `p_i`，可先计算每任务的新旧差 `d_i`，再做任务级平均。若一组任务共享文档/模板，应在独立组层面考虑不确定性；不能把同一任务的 20 次随机运行当成 20 个独立业务样本。可以按任务或独立组做配对 bootstrap，报告差值区间，并说明分组、重复次数和抽样方法；样本太少时不要强行解释为稳定提升。

均值之外还要看退化样本、风险分层和关键业务子集。有限样本中零次越权，只能说明本次没有观察到越权，不能证明真实风险为零。上线门槛应提前约定质量允许退化幅度、风险红线和成本预算，而不是看到结果后挑有利指标。

## 5. 让评分器可审计

能确定计算的部分先用确定性校验：schema、金额单位、引用 ID 是否存在、当前授权、下游业务记录数量和审批哈希。语义正确性、解释充分性等再使用人工量表或 LLM judge。judge 输入的证据和候选答案都是待评内容，其中的“请给满分”不应被当作评分指令。

量表应把“事实支持”“覆盖必要条件”“不确定性处理”“表达清楚”分开，给出分档依据及错误实例。用一小组人工复核样本校准 judge，尤其统计**误放行率 = 人工判错但 judge 判通过的数量 / 人工判错总数**，并同时看“judge 判通过的样本中有多少实际错误”。二者分母不同；分母为零时报告不可计算，不能记为零风险。整体一致率高，仍可能掩盖少量高风险误放行。对分歧和临界样本保留人工复核路径。

比较 A/B 回答时隐藏模型身份，随机交换位置并复核次序敏感结果，避免偏好较长答案或自家模型输出。位置、冗长、自我偏好与推理局限是已有研究观察到的问题，不能把某个公开测试上的一致率当成本业务 judge 的准确率。[LLM-as-a-Judge 原始研究](https://arxiv.org/abs/2306.05685)

模型不能只凭另一模型的“已登记成功”判定工具任务成功；应读取测试替身或业务系统的独立回执。judge 与被测模型可能共享盲区，因此高风险授权和副作用事实尤其需要独立程序校验。

## 6. 错误分析：从现象找到最早可观察断点

保留每次运行的条件、阶段输出与事实证据：query 改写、过滤条件、候选 ID/版本/分数、重排结果、最终上下文、工具参数与回执、状态迁移、模型输出、判分及成本。日志应按权限保存并脱敏，避免把原本受限的正文泄露到观测系统。

| 现象 | 先检查的断点 | 定向实验 |
| --- | --- | --- |
| 新制度问题答 500 元 | 业务日期是否解析正确；新版本是否入库且可见 | 固定正确条件，检查候选是否有新条款 |
| 答 600 元却漏审批例外 | 例外是否被召回、重排淘汰或压缩丢失 | 固定限额与例外上下文，再运行生成 |
| 引用正确但推导错误 | 证据能否蕴含结论，是否混淆日期/对象 | 保持证据不变，仅对比生成策略 |
| 登记两次 | action_id 是否稳定；下游幂等记录是否与业务同事务 | 注入“下游提交后回执丢失” |
| 取消后显示“未执行”但已有记录 | 是否混淆任务状态和动作事实 | 在远端完成、本地记账前插入取消 |

按最早可观察到的不正确状态归类，另外记录后续放大因素。把正确证据直接喂给生成器是一种 oracle 消融：若错误消失，说明上游可能有问题；若仍错误，说明生成层也有问题。它不能单独证明唯一根因，因为替换上下文同时改变了长度、位置和干扰。需要进一步控制变量、复现时序，再决定修改位置。

修复后同时跑失败样本和邻近反例。例如修了“缺少日期时追问”，要检查明确日期的请求没有被无谓追问；修了重复登记，要检查用户明确要求的新动作没有被过度去重。最终验收集不应变成错误修复的唯一回归集。

## 7. 一个最小实验：均分提高仍然不能通过验收

下面的标准库程序使用人为构造的结果，展示配对计算和风险门槛。每个任务有两次运行；总成本字段已经包含两次运行内的失败和重试。它不调用真实模型，不估计置信区间，也不证明任何模型提升。

```python
from statistics import mean
from math import isclose

cases = [
    # 任务、旧结果、新结果、新方案是否越过硬边界、新方案总成本
    ("普通限额", [1, 0], [1, 1], False, 4),
    ("审批例外", [0, 0], [1, 1], False, 6),
    ("越权拒绝", [1, 1], [1, 0], True, 3),
]
old = mean(mean(row[1]) for row in cases)
new = mean(mean(row[2]) for row in cases)
deltas = [mean(row[2])-mean(row[1]) for row in cases]
passed_runs = sum(sum(row[2]) for row in cases)
cost_per_success = sum(row[4] for row in cases)/passed_runs
hard_failure = any(row[3] for row in cases)
# 教学规则；真实门槛还需样本量、不确定性和成本/时延约束。
release = new >= old and not hard_failure
assert isclose(new-old, mean(deltas))
assert new > old and sum(d < 0 for d in deltas) == 1
assert isclose(cost_per_success, 2.6)
assert not release
print(f"旧均分={old:.3f}，新均分={new:.3f}，成功运行平均成本={cost_per_success:.2f}")
print("验收拒绝：存在越权退化，均分提升不能抵消硬边界失败")
```

验证记录：2026-10-29，Python 3.12.9，以上代码运行通过；旧均分 0.500，新均分 0.833，每成功运行成本 2.60，仍因越权退化拒绝验收。这些是构造数据的计算结果。

真正上线前先通过离线回归和故障注入，再做影子验证与受控灰度。影子运行必须禁用真实写工具或使用测试替身，避免为比较效果重复执行操作。灰度保留版本、租户范围和回滚开关，持续观察失败分布与人工接管原因；数据分布变化后补充新用例，重新建立独立验收集，而不是只追踪旧集上的分数。
