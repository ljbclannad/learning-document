## 1. RAG 是什么，以及解决什么问题

RAG 是一种“先找证据、再生成回答”的应用架构：系统从外部知识库中检索与问题相关的内容，再将这些内容连同问题交给 LLM 生成答案。它适合私有、经常变化、需要追溯来源或受权限控制的知识。

它并不是让模型永久“学会”一份文档，而是在当前请求中给模型补充可用证据。因此，RAG 的价值主要是：

- 知识可更新，无须每次更新都重新训练模型；
- 回答可以附带来源、章节和版本，便于核查；
- 可以在检索前执行权限、地区、时间和版本等业务约束；
- 将“事实从哪里来”与“怎样组织语言”分开治理。

典型链路如下：

```text
原始文档 -> 解析/清洗 -> 切分与标注 -> 索引
用户问题 -> 查询理解 -> 召回 -> 重排/证据压缩 -> LLM 生成带引用的回答
```

RAG 的两个必要前提：答案确实存在于可访问的语料中；检索能够把包含答案的证据带入候选集。任一前提不成立，生成模型都无法可靠补救。

### 1.1 RAG、提示词与微调的边界

| 问题类型 | 优先方案 | 原因 |
| --- | --- | --- |
| 私有、变化快、需要引用的事实 | RAG 或受控工具查询 | 知识在外部，可更新、可审计。 |
| 输出格式、语气、固定流程 | 提示词、结构化输出、规则 | 迭代快，成本低。 |
| 大量稳定样本上的固定行为或分类能力 | 微调或训练专用模型 | 将稳定模式编码进参数。 |
| 有副作用的业务操作 | 工作流、规则、权限与审批 | 正确性不能只依赖概率模型。 |

生产系统常将它们组合：微调或提示词决定“怎么答”，RAG 提供“依据是什么”。

### 1.2 RAG 的边界

- 检索到了错误或过期证据时，LLM 可能写出“有依据但仍错误”的答案。
- 分散在多份文档中的结论可能需要多跳检索、工具调用或确定性计算。
- 扫描件、复杂表格和图片若解析失败，后续检索也会失真。
- RAG 不能替代权限校验、版本治理、业务规则和高风险场景的人审。

## 2. 知识库构建（Indexing）

知识库的基本记录单位通常是 chunk。每条记录至少应保存正文、来源定位和业务元数据，而不只是一个向量：

```text
chunk_id, chunk_text, embedding,
doc_id, title_path, source_url, page_or_anchor,
published_at, effective_from, effective_to,
version, status, authority, region, permissions
```

### 2.1 采集、解析与清洗

先将 PDF、网页、Word、Markdown 或数据库记录统一成具有正文、结构和元数据的文档模型。清洗的目标不是排版美观，而是提升检索信号：应消除重复页眉页脚、目录、页码、乱码和无意义空白；同时保留标题层级、条款号、表格表头、来源链接及页码。

对 PDF 特别要做抽样验收：文本是否按阅读顺序输出、表格行列是否错位、图片中的关键信息是否遗漏。解析质量差时，先修解析或改用结构化数据源，通常比反复调 embedding 更有效。

### 2.2 切分（Chunking）

切分的目标是让每个 chunk 同时具备**可检索性**和**可回答性**：主题足够集中，又包含支撑一个结论所需的条件、结论和例外。

优先按文档结构切分：标题层级 -> 条/款/项 -> 段落；固定 token 长度仅作为上限或兜底。固定长度容易截断“条件—结论—例外”的完整语义，语义切分可作为结构缺失时的补充，但不应抹掉原始定位信息。

没有通用的最佳长度，需以评测集验证。可将 200～400 tokens 视为规则或说明类正文的起始实验区间；定义、阈值、例外等精确片段可更短。chunk 过大时主题混杂、上下文浪费；过小时证据不闭环。

overlap 用于处理边界被切断的情况，而不是越大越好。结构化条款已自洽时可很小甚至为零；按长度切分时可从约 10%～20% 的重叠开始评测。重叠会增加索引体积、重复候选和后续去重成本。

表格不能简单按整页转成一段文本。优先保留结构化字段；若必须入库，可按“表头 + 单行或小行组”建 chunk，并保存行列、附件名和适用范围。对于“条款正文”和“编码/目录表”，通常需要分别优化的索引字段。

### 2.3 元数据与版本治理

向量相似度只表示语义接近，不能判断地域、时效、权限或适用对象。因此元数据是 RAG 可控性的核心。

对于政策、制度、产品规范等高时效知识，应保存生效区间、版本、管辖范围、权威级别和权限。这里有三类不同约束，不能统一视为“没搜到就放宽”：

| 约束 | 来自哪里 | 无结果时怎么处理 |
| --- | --- | --- |
| 安全边界：租户、资源 ACL、用户身份 | 可信认证与授权系统；模型和用户文本不能授予权限 | 不得扩大访问范围；可返回无可访问证据，不能泄露未授权材料是否存在 |
| 适用条件：业务发生日期、地区、员工类型、制度版本 | 用户明确事实、业务记录或经确认的上下文 | 保持条件；关键字段缺失时追问，或分别给条件化解释 |
| 召回策略：查询措辞、候选数、检索器组合 | 应用检索策略 | 可有界扩展，但仍受前两类约束限制 |

例如“今年报销去年出差费用”可能要按出差日判断制度，而不是按查询日选择最新版；实际以制度约定的判定日期为准。时间字段应区分发布时间、业务生效时间与索引更新时间，不能只取最新文档。当前已废止的版本也可能适用于历史问题，应按业务日期和历史效力判断。

无有效依据时，可另行检索**有权访问的背景材料**帮助解释概念，但要与适用证据分开，不能把旧制度或异地规则降权后混入当前结论。缺少决定结论的条件时，软排序不能替代追问。权限撤回、证据过期等变化还需在取回正文和输出前按业务策略重新校验，缓存不能绕过授权。

### 2.4 索引与更新

常见索引包括：

- 稠密向量索引：擅长同义表达和语义近似；
- 稀疏倒排索引（如 BM25）：擅长专名、编码、条款号和精确数值；
- 元数据索引：支持过滤、权限和版本选择。

近似最近邻（ANN）以少量精度损失交换延迟和内存；其参数必须通过 Recall@K 与延迟共同验证。更新时应支持增量写入、删除和版本切换；不要让已废止文档仅因“仍在索引中”而被默认召回。

### 2.5 把文档版本、索引版本与权限版本分开

“文档更新成功”至少涉及源文件接收、解析、切分、编码、索引写入和查询可见几个时点。若写入一个 chunk 就让线上看见，回答可能同时引用新限额和旧例外。应将可见性放在一个完整知识版本的验收边界上，而不是把某次 upsert 成功当作发布完成。

沿用第 7 节的虚构报销制度：A 租户旧版限额为 500 元，2026-10-01 起新版本为 600 元，且必须同时保留审批例外。可以采用以下身份设计，字段名只是应用设计示意：

| 字段 | 表达什么 | 为什么不能混用 |
| --- | --- | --- |
| `tenant_id + doc_id` | 文档在租户内的稳定身份 | 文件名可改，不能当作唯一身份 |
| `source_revision`、`content_hash` | 源系统修订序号、对应内容 | 旧构建晚完成时，不能覆盖新修订 |
| `effective_from/to` | 业务生效区间 | 索引最新不等于历史问题应使用的制度 |
| `chunk_id`、`chunk_hash` | 具体片段身份和内容 | 引用只存页码或数组下标，重切分后会漂移 |
| `index_generation` | 一套验收过的检索数据快照 | 可包含多个历史业务版本，不等于单篇最新版 |
| `embedding_contract` | 模型版本、模板、维度、归一化和度量 | 相同维度不能证明向量空间兼容 |
| `acl_revision`、删除标记 | 当前访问控制和撤销状态 | 不能随旧索引回滚到旧权限 |

`source_revision` 若来自无序 UUID，就不能直接用大小比较先后；应依赖源系统单调序号、事件版本或受控的条件更新。`content_hash` 适合去重与校验，不提供时间顺序。

### 2.6 从接收更新到对查询可见

一种可行的发布流程是：先固定源快照和构建配置，生成候选索引；核对每个源文档的预期 chunk 数、解析失败、正文哈希和索引覆盖率；完成检索回归；最后发布包含稀疏索引、向量索引、文档快照与编码契约的 manifest。新请求读取一次 manifest，并在整个请求中绑定该 generation。已发布的 generation 标识不能绑定另一份内容或配置；相同标识的重复发布只可接受完全相同的快照，变更必须生成新标识。

```text
源快照 S + 构建配置 C → 候选 G2
→ 解析/编码/写入全部完成 → 覆盖与质量验收
→ 原子发布活动 manifest：G1 → G2
→ 新请求绑定 G2；已开始请求按约定完成 G1 或重启
```

若构建期间源数据仍更新，不能只对快照做完就宣布追上实时数据。可记录变更日志水位，回放快照之后的更新和删除，再在明确的追平边界切换；或者短暂冻结写入。变更日志不完整时，必须重新对账，而不是假设双写永远一致。每个工作任务携带源修订号，提交时检查其是否仍适用于候选快照；较旧任务晚完成不得把较新的内容覆盖掉。

跨多个存储发布时，单个引擎的 alias 切换不能自动保证稀疏、向量和正文存储的跨系统事务。应用 manifest 应只指向已准备好的不可变集合；查询固定该 manifest 后，不再分别获取“各自最新”的索引。旧集合要保留到在途请求完成，并满足回滚保留策略。

Elasticsearch 的 alias API 是具体实现例子：可在一个请求中移除旧指向并添加新指向，但应检查操作结果中的错误；官方还说明了部分 action 成功的情形及 `must_exist` 控制。不能只看 HTTP 成功就认定切换完整成功。[Elastic alias 文档](https://www.elastic.co/docs/manage-data/data-store/aliases)

### 2.7 删除、权限撤回与缓存：先阻止继续使用，再完成物理清理

删除事件需要留下带修订号的 tombstone，阻止尚未结束的旧解析任务把内容重新写回来。清理应覆盖向量、倒排、正文、检索结果缓存和答案缓存；备份、审计留存则按独立的数据保留约定处理。**制度到期不必等于删除**：历史出差仍可能需要旧制度。业务失效区间、访问撤销和物理删除是三个不同动作。

权限撤回不能等待所有索引刷新。可由权威授权层先拒绝新读取，再异步同步索引过滤条件；从缓存取出的片段，在加载正文、进入模型上下文和对外返回的边界也要按产品要求校验。涉及实时撤销时还要规定在途请求如何中止或重新生成，因为撤销前已发到模型或客户端的内容不能靠删缓存追回。拿不到权威授权状态时，高敏数据不应默认放行。

缓存键至少要反映租户、授权范围、查询条件、知识 generation 和有关模型/提示词版本；但加入 `acl_revision` 不会自动解决旧请求回填：缓存写入和读取仍需检查当前授权，或使用版本命名空间让旧回填不再可见。回滚内容索引时继续应用**当前** ACL 和 tombstone，不能把已删除或被撤权的资料重新开放。

### 2.8 换 embedding 模型、回滚与引用追溯

换模型时为新编码契约建立独立索引；新查询编码器只能访问与其兼容的向量集合。双跑比较时，两个完整链路各用自己的 query 编码器和索引，再比较最终检索质量；不要把两个空间的相似度分数直接拼接排序。维度检查只能发现一部分错误。

回滚的单位应是完整检索配置及兼容数据：query 编码器、索引、过滤与排序配置一起退回，但授权和删除事实不回退。回滚前确认旧集合仍完整、仍满足当前访问限制，并对当前高风险查询做定向验证。

引用建议记录 `doc_id + source_revision + chunk_id/hash + 页/条款位置`，展示时解析到对应的不可变证据。制度更新后，原回答引用仍应指向当时证据；如果当前用户已无权限，引用入口应拒绝访问，而不是为“可追溯”绕过 ACL。审计保留证据也不等于所有用户都能读取历史快照。

下面是可直接运行的**内存状态模型**，只验证发布与授权边界，不连接真实检索引擎。`ready` 在真实系统中应来自完整构建及验收，不能由调用方随意置为真。

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class Generation:
    name: str
    revision: int
    ready: bool
    text: str


class KnowledgeBase:
    def __init__(self):
        self.active = Generation("g1", 1, True, "500 元")
        self.generations = {self.active.name: self.active}
        self.wanted_revision = 2
        self.allowed = True
        self.deleted = False

    def publish(self, candidate):
        if not candidate.ready or candidate.revision != self.wanted_revision:
            return False
        existing = self.generations.get(candidate.name)
        if existing is not None and existing != candidate:
            return False  # 同一标识不能改绑另一份快照
        self.generations[candidate.name] = candidate
        self.active = candidate
        return True

    def read(self, pinned):
        if not self.allowed or self.deleted:
            raise PermissionError("当前不可读取")
        return pinned.text


kb = KnowledgeBase()
pinned = kb.active
assert not kb.publish(Generation("partial", 2, False, "缺少例外"))
assert kb.publish(Generation("g2", 2, True, "600 元，超标须事前审批"))
current = kb.active
assert kb.publish(current)  # 重复发布同一快照可重入
assert not kb.publish(Generation("g2", 2, True, "同名却换了内容"))
assert kb.active == current
assert not kb.publish(Generation("late", 1, True, "旧任务晚到"))
assert kb.read(pinned) == "500 元"  # 在途请求绑定旧快照
assert kb.read(kb.active).startswith("600")
for reason in ("allowed", "deleted"):
    kb.allowed, kb.deleted = True, False
    setattr(kb, reason, False if reason == "allowed" else True)
    kb.active = pinned  # 模拟内容回滚，不能改变当前授权/删除事实
    try:
        kb.read(pinned)  # 即使片段来自缓存，也必须过当前校验
    except PermissionError:
        pass
    else:
        raise AssertionError("回滚绕过了当前约束")
print("生命周期实验通过：未就绪/陈旧发布被拒绝，快照固定，撤权/删除不回滚")
```

验证记录：2026-10-29，Python 3.12.9，复查先复现同名 generation 可改绑内容的问题；修正后未就绪、陈旧发布与同名异内容发布均被拒绝，相同快照重发、固定快照及撤权/删除断言通过。

这个模型只保留一份制度和一个主体，没有实现多存储原子发布、增量日志、并发授权更新或物理删除。真实验收应额外注入“删除后旧任务回写”“构建途中进程退出”“两类索引仅一类成功”“权限撤回时旧答案仍在生成”等故障，按 [[AI应用评测与错误分析]] 的方法记录结果。

## 3. 查询理解（Query Understanding）

用户的问题往往口语化、信息不全或包含多件事。查询理解的作用是生成适合检索的表示，而非单纯把句子改写得更漂亮。

一个实用的中间结构可以包含：

```text
intent: 规则判定 / 流程查询 / 异常排查 / 对比
entities: 实体、别名、编码、专名
constraints: 地区、时间、版本、对象、场景、权限
queries: 原查询与若干检索改写
keywords: 用于倒排索引的精确词
sub_questions: 复杂问题拆出的子问题
```

主要工作包括：

1. **实体抽取与规范化**：将别名、缩写、商品名或口语映射到可检索的标准术语；编码和条款号应保留为强信号。
2. **约束识别**：从可信身份注入安全过滤，从用户事实或业务记录提取适用条件；模型只能提出查询条件，不能扩大授权。缺失但决定结论的字段应追问或保留分支。
3. **查询改写与扩展**：补充文档常用术语、同义词，或生成少量不同角度的查询，以提高候选覆盖率。
4. **问题拆解**：把需要多份证据的问题拆成可独立检索的子问题，再合并答案。
5. **对话对齐**：多轮场景维护可追溯的会话状态，避免“这个情况”丢失前文指代。

改写数量不是越多越好；它会增加延迟和噪声。应通过离线评测确认每一路查询是否带来增量召回。

## 4. 召回（Retrieval）

召回阶段的目标是把“含有答案的证据”放入候选池，首要指标通常是 Recall@K。候选阶段宁可覆盖更广，但不能把最终回答直接建立在大量未筛选内容上。

### 4.1 稠密、稀疏与混合检索

| 方式 | 擅长 | 局限 |
| --- | --- | --- |
| 稠密检索（embedding） | 同义、口语、概念性表达 | 编码、专名、数值和版本语义不稳定。 |
| 稀疏检索（BM25） | 关键词、条款号、产品名、精确字段 | 同义表达和措辞变化易漏召回。 |
| 混合检索 | 同时覆盖语义与精确匹配 | 需要处理融合、去重和评测。 |

BM25 通常结合倒排索引实现高效召回，具体评分机制与数值实验见第 4.3 节。中文场景中，分词、领域词典、别名扩展和标题/条款号入索引会明显影响效果。

混合检索可先分别召回再合并去重。RRF（Reciprocal Rank Fusion）按名次融合：`score(d) = Σ 1 / (k + rank_i(d))`，名次从 1 开始，未出现在某一路的文档在该路贡献 0。`k` 是平滑常数，不是候选数量 Top-K；同一路重复 ID 应先去重，避免重复计票。它避免直接比较不同检索器的原始分数，但不能纠正错误权限、过期版本或遗漏证据。[Elastic RRF 公式与参数](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)

候选窗口与 `k` 仍应在业务集上验证。加权分数融合需要校准分数尺度；有足够标注数据后才考虑学习排序。

### 4.2 候选池、过滤与多样性

把“各检索器的候选池大小”和“最终给 LLM 的证据数量”分开设计。每路检索都应执行安全过滤，候选正文进入重排器、模型或用户可见日志前必须已授权；不能把权限判断交给生成模型。适用条件也应尽早过滤。若引擎仅支持先召回后过滤，须在可信检索边界内完成，并检查过滤后候选不足造成的漏召回。随后去重、重排，再选少量完整证据进入上下文。具体 K 不能照搬经验值，应画出 K 增加时 Recall@K、延迟和成本的曲线，选择收益开始变小的拐点。

候选去重应同时处理完全重复与近似重复；还要避免候选全来自同一章节。可以按来源/章节设上限，或采用 MMR 等多样性选择方法，以覆盖定义、条件、例外与流程等不同证据角度。

每次检索应留下可诊断日志：原始查询与改写、过滤条件及回退、各路检索的排名/分数、去重原因、重排前后变化、最终引用和响应耗时。这样才能区分问题来自查询理解、索引、召回、重排还是生成。

### 4.3 用小语料理解 BM25 的分数

BM25 根据查询词在文档中的频率、在语料中的稀有程度以及文档长度打分。一种常见的单字段教学公式是：

```text
score(q,d) = Σ IDF(t) × f(t,d)(k1+1) / [f(t,d)+k1(1-b+b·|d|/avgdl)]
IDF(t) = ln[1 + (N-df(t)+0.5)/(df(t)+0.5)]
```

这里对去重后的查询词求和；`f` 是文档词频，`df` 是含该词的文档数，`N` 是文档数，`|d|` 是分词后的长度，`avgdl` 是平均长度。`k1` 控制词频饱和，`b` 控制长度归一化强度。Lucene 9.12.1 文档给出了此 IDF 形式及参数含义；实际引擎还受字段 boost、norm 编码、分片统计和实现中的比例常数影响，不能拿教学分数逐位核对线上 `_score`。[Lucene BM25Similarity](https://lucene.apache.org/core/9_12_1/core/org/apache/lucene/search/similarities/BM25Similarity.html)

若 `b=0`，不做长度归一化，同词频的长短文档该项得分相同；增大 `b`，同词频下更长文档受到更大惩罚。固定长度时，词频加倍不会让得分无限线性增加，所以堆砌关键词收益逐渐变小。稀有词可能很有区分度，但错别字和无意义编码也可能稀有，分析器与领域词规范化仍然重要。

下面将 A 租户三条适用材料人工分词。它与第 7 节的固定名次实验不同，这里真正计算所示 BM25 公式，但没有实现倒排数据结构、中文分词器或搜索服务。

```python
from collections import Counter
from math import log, isclose

corpus = {
    "A-limit": "住宿 限额 600 审批".split(),
    "A-exception": "发票 缺失 财务 核验".split(),
    "A-flow": "报销 系统 提交 行程 凭证".split(),
}
counts = {key: Counter(words) for key, words in corpus.items()}
N = len(corpus)
avgdl = sum(map(len, corpus.values()))/N


def idf(term):
    df = sum(term in words for words in corpus.values())
    return log(1+(N-df+0.5)/(df+0.5))


def tf_factor(freq, length, k1=1.2, b=0.75):
    return freq*(k1+1)/(freq+k1*(1-b+b*length/avgdl))


def score(query, key):
    return sum(idf(t)*tf_factor(counts[key][t], len(corpus[key]))
               for t in set(query))


q = ["住宿", "限额"]
ranked = sorted(corpus, key=lambda key: (-score(q, key), key))
assert ranked[0] == "A-limit"
assert score(q, "A-flow") == 0
assert all(score(["住店"], key) == 0 for key in corpus)  # 词形不重合
assert score(["住宿"], "A-limit") > 0  # 显式别名映射后才命中
assert tf_factor(1, 4) > tf_factor(1, 40)
assert isclose(tf_factor(1, 4, b=0), tf_factor(1, 40, b=0))
assert tf_factor(2, 4) < 2*tf_factor(1, 4)
print("BM25 算术实验通过：", [(key, round(score(q, key), 3)) for key in ranked])
```

验证记录：2026-10-29，Python 3.12.9，7 条 BM25 断言通过；A-limit 得分约 2.025，其余两条为 0。仅验证所示公式，未运行真实 ANN 或 Cross-encoder。

本例统计量在已固定的教学语料上计算。真实引擎的过滤一般不代表重新计算过滤后子集的 IDF；跨分片统计方式也会影响分数。BM25 分数不是概率，不同查询或不同索引下不宜共用未经校准的“相关阈值”。

### 4.4 向量相似度、精确搜索与近似搜索

双塔检索将 query 与文档分别编码，文档向量可预计算，查询时按点积、余弦或距离寻找近邻。语义能力来自编码模型的训练，索引只负责在给定向量空间中找邻居；把差向量交给更精确的索引不能修复语义表示。

对于已 L2 归一化的向量，点积等于余弦，相同向量的余弦为 1；未归一化时，大范数可能改变点积排序。以下人为向量只说明度量差异，不是模型对三句话的真实编码：

```text
query = (1,0)
文档甲 = (0.8,0.6)：点积 0.8，余弦 0.8
文档乙 = (10,10)：点积 10，余弦约 0.707
```

按点积乙更近，按余弦甲更近，因此维度一致还不够，编码、归一化和度量必须匹配。一般也不能把相似度 0.8 理解为“答案正确概率 80%”。

精确搜索扫描候选集合并计算距离，可作为小样本基准；ANN 减少被比较的范围，以召回损失换效率。排查时要区分两个指标：

- **ANN 近邻召回**：相对于相同向量、度量、授权候选集上的精确 Top-K，近似搜索找回多少。
- **业务证据召回**：候选是否覆盖人工标注的适用证据。即使近邻召回达到 100%，编码模型也可能把无关文档排得很近。

### 4.5 索引参数怎样影响召回和延迟

下面借用 Faiss 的术语解释机制，其他引擎同名参数不一定有完全相同的实现或过滤行为。[Faiss 索引说明](https://github.com/facebookresearch/faiss/wiki/Faiss-indexes)

| 索引/参数 | 改变的工作 | 代价与边界 |
| --- | --- | --- |
| Flat 精确搜索 | 比较整个候选向量集合 | 可作近邻基准，成本随数据量与维度增长 |
| HNSW 的 `M` | 图中邻接规模 | 更大通常提高可导航性，也增加内存与构建成本 |
| HNSW 的 `efConstruction` | 建图时探索范围 | 影响图质量与构建时间，不能只调查询参数弥补所有差图 |
| HNSW 的 `efSearch` | 查询时探索范围 | 增大通常增加召回与查询工作量，不等于最终返回数 K |
| IVF 的 `nlist` / `nprobe` | 分区数量 / 查询扫描的分区数 | 未扫描正确分区就会漏邻居；增加 `nprobe` 通常更慢但覆盖更广 |
| PQ 等压缩 | 用紧凑编码近似原始向量 | 降低存储，距离近似误差可能改变排名，需对比精确向量基准 |

调参先固定编码模型、语料和查询，再对照精确搜索逐步扩大探索范围，记录近邻召回、业务证据召回、P95 延迟、内存与构建时间。不要同时更换 embedding 和 ANN 参数后把收益都归因于索引。

严格 ACL 会改变搜索空间。若先全局 Top-K 再过滤，结果可能全部被删掉，而真正有权访问的邻居没有被访问到；应核对引擎是否支持前置过滤、遍历中约束或扩大候选后的安全过滤。无论采用哪种策略，未授权正文都不能进入模型。过滤极窄时，部分引擎可能转用精确搜索，参数与性能曲线也会变化，须在真实授权分布下测量。

## 5. 重排与证据压缩（Rerank & Compress）

召回的“相似”不等于“足以回答”。重排在候选池中找出真正相关、适用、权威且证据完整的片段；压缩则在不改变原意的前提下，减少无关上下文。

### 5.1 重排

常用层次从低成本到高精度：

1. 规则加权：实体命中、元数据匹配、来源权威性、版本和完整性。
2. Cross-encoder：将 query 与候选一起编码，通常比双塔向量相似度更准确，但必须逐条打分，成本更高。
3. 学习排序或 LLM 重排：适合有足够标注与评测能力的复杂业务；需约束输出并监控稳定性。

高风险领域的排序不应只看相关性。一个候选至少应综合相关性、适用范围、时效/权威性与“是否包含条件、结论和例外”。出现冲突证据时，不能让模型按措辞投票；应识别冲突，比较生效时间、范围和权威层级，并输出缺失的判定条件。

#### 5.1.1 双塔与 Cross-encoder：先扩大覆盖，再细判关系

双塔把 query 和每篇文档独立编码，便于预计算和快速查近邻；Cross-encoder 将 query 与单个候选一起送入模型，直接对二者关系打分，因此不能复用一个固定文档向量完成所有查询。候选之间通常可批量处理，但总工作量仍随候选数与输入长度增加。具体质量收益需要验证，不能只凭模型结构宣称一定更准确。[Sentence Transformers 检索与重排](https://sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)

用第 7 节“住宿上限＋无发票怎么办”的问题来看，A-limit 匹配金额，A-exception 支持缺票处理，A-flow 只描述提交步骤。重排应保留对两个子问题都必要的材料；如果召回池没有 A-exception，再强的重排器也不能从 A-flow 中恢复那条事实。

一个可解释的失败分析是：分别记录“召回池包含必需证据”“重排 Top-N 保留必需证据”“压缩后仍保留条件与例外”。第一项失败改召回，第二项失败检查重排训练分布、query 表达和截断，第三项失败改证据组装与压缩。不要只看最终答案然后盲目扩大 K。

重排分数也不必是校准概率。若工具只返回分数，应按本批候选排序并在业务集上验证阈值；若模型返回候选 ID，应校验它们来自本轮授权集合、没有新增或重复 ID。输入过长导致关键例外被截断时，换更强重排模型未必有效，应先调整候选表示或分段策略。

### 5.2 压缩

优先使用抽取式压缩：保留与问题有关的条件句、结论句、例外句、数值阈值，以及必要的上下文和原始定位。生成式摘要更短，但可能改写限制条件；若使用，需将摘要逐句对齐到原文证据。

可将每条证据整理成统一结构，降低 LLM 遗漏限制的概率：

```text
适用范围：...
结论：...
条件与阈值：...
例外：...
来源：文档、版本、生效期、章节/页码、evidence_id
```

## 6. 生成、引用与拒答

给生成模型的输入应包括原问题、已知约束、经过筛选的证据包以及明确的输出规则。关键结论必须引用 evidence_id；证据不足时应说明不足并提出最少的补充信息；证据冲突时应并列差异和适用范围，而不是强行给唯一结论。

一个可靠的回答通常包含：条件化结论、关键依据、例外与限制、下一步核验方式，以及缺失条件。对于医疗、法律、金融等高风险主题，还应遵守业务边界：RAG 可辅助解释资料，不能把不充分的资料包装成专业诊断或确定性决策。

## 7. 评测与迭代

不要只评“最终回答像不像”。至少分层评测：

| 层级 | 关键问题 | 常用指标 |
| --- | --- | --- |
| 索引/解析 | 内容与定位是否可用？ | 解析正确率、覆盖率、抽样审查。 |
| 召回 | 正确证据是否进入候选？ | Recall@K、MRR、NDCG、延迟。 |
| 重排 | 高价值证据是否排在前面？ | nDCG、MRR、人工相关性标注。 |
| 生成 | 结论是否被证据支持？ | Faithfulness、引用准确率、完整性、拒答正确率。 |
| 端到端 | 是否真正完成业务任务？ | 任务成功率、人工复核、成本、P95 延迟。 |

评测集应来自真实问题，覆盖正常、模糊、无答案、冲突版本和权限边界等样本。每次改动只改变少数变量，并保留失败案例；否则很难知道提升究竟来自切分、检索、提示词还是评测集偶然性。

### 7.1 贯穿案例：当前制度、例外与无答案

下面是虚构的企业制度教学语料，不代表真实公司的政策。认证主体属于租户 A、角色为普通员工，问题是：“2026-10-15 在上海出差的普通员工，住宿每晚最多报多少？没有发票怎么办？”本例按住宿发生日选择制度，生效区间为左闭右开。

| chunk ID | 范围与版本 | 内容要点 | 此次用途 |
| --- | --- | --- | --- |
| A-old | A / 普通员工 / 上海；2026-01-01 至 2026-10-01 | 标准上限 500 元/晚 | 历史版本，当前问题排除 |
| A-limit | A / 普通员工 / 上海；2026-10-01 起，v2 第 3 条 | 标准上限 600 元/晚；特殊情形按第 4 条审批 | 当前金额与条件依据 |
| A-exception | 同 v2，第 4 条 | 超标须事前审批；无合规发票不能按常规流程报销，应联系财务核验 | 例外与缺票依据 |
| A-flow | 同 v2，第 5 条 | 在报销系统提交行程与凭证 | 流程背景，不能替代金额/缺票条款 |
| A-manager | A / 仅管理岗可见；2026-10-01 起 | 管理岗另有标准 | 无访问权限，不能进入模型 |
| B-limit | B / 普通员工 / 上海；2026-10-01 起 | 标准上限 900 元/晚 | 跨租户，不可进入候选正文 |

**第一步：解析和切分。** 将第 3 条及其标题、适用对象、生效期保存在 A-limit，保留指向第 4 条的关联。不能把“600 元”孤立切出而丢掉“标准上限”和审批条件。所有 chunk 继承文档权限和版本，附带不可变来源定位。

**第二步：形成查询。** 身份来自认证层，日期与地点来自问题；拆出“住宿标准”和“缺票处理”两个子问题。改写可以加入“住宿费限额”“合规凭证”等检索词，但不能把“无发票”改成“有发票”。普通员工身份缺失时应先确认适用对象，不能根据相似度猜测。

**第三步：过滤、召回与融合。** 对本例，允许的候选只有 A-limit、A-exception、A-flow。假设 BM25 返回 `[A-limit, A-flow]`，向量检索返回 `[A-exception, A-limit]`；这两组名次是人为设定的演示输入，不是实测检索质量。取 `k=60`，RRF 分数分别为：

```text
A-limit     = 1/61 + 1/62 ≈ 0.03252
A-exception = 1/61        ≈ 0.01639
A-flow      = 1/62        ≈ 0.01613
```

**第四步：重排和证据组装。** 若只取 Top-1，缺票子问题仍未被覆盖；应按两个子问题选 A-limit 与 A-exception，并核对它们属于同一有效版本。不是因为 RRF 分高就能删除例外，也不能把跨版本 chunk 去重成一个没有版本的摘要。

**第五步：生成并核对引用。** 合格答案应是：“按给定日期、地点和员工类型，标准上限为 600 元/晚，超标需事前审批〔A-limit、A-exception〕；无合规发票不能按常规流程报销，应联系财务核验〔A-exception〕。”不能推断“任何情况最多 600 元”，也不能把“联系财务”写成“必定获批”。引用校验应同时检查 ID 属于本轮授权证据集、版本适用、原文确实支持该句；只有 ID 存在不够。

### 7.2 最小可运行实验：权限、版本、融合与证据覆盖

以下 Python 3.10+ 标准库脚本验证上面的确定性部分。保存为临时脚本运行即可；它用固定排名代替检索器，用必需证据集合代替语义判定，**不执行 embedding、BM25、模型重排或生成**。

```python
from datetime import date

# tenant、roles 是教学 ACL；真实授权应由服务端计算并注入。
rows = {
    "A-old": ("A", {"employee"}, "2026-01-01", "2026-10-01"),
    "A-limit": ("A", {"employee"}, "2026-10-01", None),
    "A-exception": ("A", {"employee"}, "2026-10-01", None),
    "A-flow": ("A", {"employee"}, "2026-10-01", None),
    "A-manager": ("A", {"manager"}, "2026-10-01", None),
    "B-limit": ("B", {"employee"}, "2026-10-01", None),
}

def eligible(tenant, role, day):
    day = date.fromisoformat(day)
    return {key for key, (owner, roles, start, end) in rows.items()
            if owner == tenant and role in roles
            and date.fromisoformat(start) <= day
            and (end is None or day < date.fromisoformat(end))}

def fuse(rankings, allowed, k=60):
    scores = {}
    for ranking in rankings:
        # 仅模拟可信检索边界内的过滤；不得先把未授权正文交给模型。
        ids = list(dict.fromkeys(x for x in ranking if x in allowed))
        for rank, key in enumerate(ids, 1):
            scores[key] = scores.get(key, 0) + 1 / (k + rank)
    return sorted(scores, key=lambda key: (-scores[key], key))

allowed = eligible("A", "employee", "2026-10-15")
assert allowed == {"A-limit", "A-exception", "A-flow"}
assert "A-old" in eligible("A", "employee", "2026-09-30")
assert "A-old" not in eligible("A", "employee", "2026-10-01")
assert eligible("A", "employee", "2025-01-01") == set()

rankings = [["A-limit", "A-flow"], ["A-exception", "A-limit"]]
ranked = fuse(rankings, allowed)
assert ranked == ["A-limit", "A-exception", "A-flow"]
assert fuse([["B-limit", "A-manager", "A-old", "A-limit"]], allowed) == ["A-limit"]
assert fuse([["A-limit", "A-limit", "A-flow"]], allowed) == ["A-limit", "A-flow"]
required = {"A-limit", "A-exception"}
assert not required.issubset(ranked[:1])
assert required.issubset(ranked[:2])
assert not required.issubset(fuse([["A-limit", "A-flow"]], allowed))
print("权限、时间边界、融合及子问题证据覆盖断言通过")
```

### 7.3 用失败现象区分改动位置

| 失败样本 | 预期行为与定位 | 应改哪里 |
| --- | --- | --- |
| A-old 排名最高 | 当前日期仍排除；历史日期才可适用 | 元数据与过滤，不是让 Prompt 忽略旧版 |
| B-limit 或 A-manager 出现在回答依据中 | 判为隔离失败，即使金额碰巧正确也不合格 | 每路检索、缓存及正文取回的授权边界 |
| 只有 A-limit，没有 A-exception | 金额可回答，缺票部分标证据不足；允许有界补检索 | 子问题拆解、关联条款召回、证据预算 |
| 问 2025 年但无当时有效制度 | 返回无适用依据，不能套用 2026 年制度 | 无答案分支及时间语义 |
| 问深圳，而语料仅覆盖上海 | 不迁用上海标准；追问或说明缺少该地区依据 | 范围识别；本地脚本未实现地域过滤，集成时须补测 |
| 两份同日期、同范围的有效制度互相冲突 | 保留冲突并请求核实，不按相似度强选一个 | 版本发布治理与冲突检测 |
| 引用正确但答案写成“无发票也一定能报销” | 引用 ID 检查可能通过，语义支持检查必须失败 | 生成约束及人工/模型评测 |

本例的完整答案需要两条证据，取 Top-1 的证据 Recall 为 1/2，Top-2 为 2/2；这只说明给定标注下的覆盖，不是实际系统的 Recall@K 成绩。真实评测应固定语料版本，按子问题标注支持证据，分别比较召回、证据完整性和答案正确性。安全失败单独统计，不能被平均相关性分数抵消。
