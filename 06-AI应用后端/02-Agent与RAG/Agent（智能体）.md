# Agent（智能体）

## 1. Agent 是什么

在 LLM 应用里，**Agent（智能体）** 是一个以目标为中心、能够结合上下文进行判断，并按需调用外部能力来推进任务的执行体。

它不等于一个聊天机器人，也不等于一次 Tool Calling。一次普通对话通常是“输入 -> 模型生成 -> 输出”；而 Agent 面对的是“完成一个目标”，中间可能需要理解任务、补齐信息、选择工具、观察工具结果、调整下一步，并在满足结束条件后交付结果。

### 1.1 Agent = Model + Harness

常见的表达式是：

```text
Agent = Model + Harness
```

其中，**Model（模型）** 提供理解、归纳、生成和候选决策等概率性能力；**Harness（运行与约束系统）** 则把模型接入一个受控的任务环境，使其能够获得必要信息、调用能力、保存状态，并在规则约束下完成任务。

`harness` 原意是“马具、缰绳或安全带”。这个词强调两件事：一方面把模型能力连接到真实任务中，另一方面对其行动施加边界和保护。它不是某个固定的标准组件或单一框架；不同 Agent 框架对其边界划分不同，但下列能力通常属于 Harness。

| 部分 | Model 负责什么 | Harness 负责什么 |
| --- | --- | --- |
| 判断与行动 | 理解输入、提出下一步候选动作或结论。 | 提供允许调用的 Tool / Skill，校验参数、权限和副作用。 |
| 信息 | 根据已有上下文进行推理。 | 准备 system prompt、当前 context、检索证据和 memory。 |
| 多步执行 | 基于观察结果继续生成下一步。 | 编排循环、状态转换、任务暂停、恢复、重试和结束。 |
| 安全与质量 | 无法自行保证输出或行动一定正确。 | 执行规则校验、人工审批、日志追踪、评测、限流和降级。 |

运行环境中的 `system prompt`、`context`、`memory`、`tools`、`skills`、`subagents` 都可视为 Harness 的组成部分；但 Harness 通常还包括 Workflow、状态持久化、权限控制、失败恢复和可观测性。

可以用下面的边界理解它们的关系：

```text
用户目标
  -> Harness 准备规则、上下文、记忆与可用能力
  -> Model 判断下一步
  -> Harness 加载 Skill 指引、校验并执行 Tool，记录结果和状态
  -> Model 基于观察结果继续，或由 Harness 暂停、转人工、结束
```

因此，Harness 不是“模型以外所有代码”的随意集合，而是**让模型能力可被使用、被约束、被恢复和被验证的系统性边界**。Skill 是其中可复用的任务能力模块，Tool 是受控的外部操作接口，Workflow 是多步执行的确定性骨架；它们都可以服务于同一个 Agent，但不等同于 Agent 本身。

一个可落地的 Agent 通常包含以下部分：

| 部分 | 作用 |
| --- | --- |
| 目标与约束 | 定义要完成什么、不能做什么，以及何时结束或转人工。 |
| 模型 | 负责理解、归纳、路由、提出候选动作等非确定性判断。 |
| 上下文与记忆 | 提供当前会话、用户画像、历史证据、任务状态等必要信息。 |
| 工具 | 连接检索、数据库、业务 API、文件系统等外部能力；工具执行才会产生可验证的外部事实或副作用。 |
| 编排与状态 | 控制多步任务如何推进、暂停、失败、恢复和结束。 |
| 安全与治理 | 负责权限、参数校验、审计、观测、评测、限流和降级。 |

可以用下面的循环理解其核心行为：

```text
目标 / 当前状态
    -> 模型判断下一步
    -> 调用工具或请求人工确认
    -> 获得可验证的观察结果
    -> 更新显式状态
    -> 继续、结束或回退
```

这里的“模型判断”与“系统执行”必须分开：模型可以建议调用什么工具、给出什么参数或结论，但权限判断、关键状态写入、资金扣减、处方或审批结论等确定性事务，应由系统规则和受控工具最终裁决。

### 1.2 从聊天助手到工程化 Agent

Agent 通常不是一次性建成的，而是随任务复杂度逐步演进。是否称为 Agent 不应只看是否接入了模型或工具，而应看系统是否已经围绕目标形成了“决策、执行、观察、状态更新”的闭环。

| 阶段 | 主要能力 | 适用边界 |
| --- | --- | --- |
| Prompt Assistant | 组织输入与 Prompt，模型直接生成回答。 | 内容生成、简单问答；没有多步任务和外部执行。 |
| RAG / Tool Calling Assistant | 补充私有知识、实时数据或单点外部能力。 | 知识不足或需要一次查询、一次低风险动作的场景。 |
| ReAct Agent | 围绕目标多步决定行动，依据观察结果调整后续路径。 | 路径不固定、工具选择依赖上下文的任务。 |
| 工程化 Agent | 增加显式状态、验证器、审批、恢复、审计和治理。 | 多步、有副作用、高风险或需要长期稳定运行的生产任务。 |

一个任务型 Agent 的最小闭环可写为：

```text
Goal -> Context -> Decision -> Action -> Observation -> State Update
```

- **Goal**：明确本轮要完成的目标、成功条件和禁止事项。
- **Context**：加载与该目标有关的会话、记忆、检索证据、任务状态和业务约束。
- **Decision**：模型或规则判断下一步是追问、调用工具、转入固定流程、请求审批还是结束。
- **Action / Observation**：通过受控能力执行动作，并取得可验证的结果；不能把模型自述当作执行结果。
- **State Update**：将结构化结果写回状态，判断是否继续、暂停、转人工、降级或结束。

其中 ReAct 的“思考 -> 动作 -> 观察”是这个闭环的一种实现方式；生产系统还必须补上目标边界、状态持久化和结束/异常收口。

## 2. Agent、工作流与 Skill 的区别

Agent、Workflow（工作流）与 Skill（技能）不是互斥关系。它们分别关注**谁来决定下一步**、**整条链路如何推进**和**某项能力如何复用**。

其中，Agent 是推进任务的执行体，Skill 是可复用的任务知识与操作指引。Agent 根据目标和观察结果决定下一步；Skill 告诉执行它的 Agent 如何处理某类任务。Skill 可以包含复杂流程和局部决策，但文件本身不会运行，也不会自动获得工具权限。

| 维度 | Agent | Workflow（工作流） | Skill（技能） |
| --- | --- | --- | --- |
| 核心角色 | 以目标为中心的执行体，动态决定下一步。 | 预先定义的流程骨架，控制步骤和状态推进。 | 可复用的任务能力模块，封装某类既定工作如何完成。 |
| 关注的问题 | 面对当前目标，该做什么、调用什么、何时结束。 | 多个节点以什么顺序、条件和异常分支运行。 | 同类任务的目标、输入输出、Prompt、工具约束如何沉淀和复用。 |
| 决策权 | Agent 根据目标、上下文和观察结果，动态决定下一步、能力组合与结束条件。 | 开发者预先定义节点、顺序、分支和结束条件。 | 由用户或 Agent 选择加载；指引可包含步骤、分支或委派建议，实际决策仍由执行它的 Agent 作出。 |
| 适合的问题 | 目标明确但路径不固定，例如复杂分析、研究、跨系统排障、开放式任务处理。 | 步骤、输入输出和异常分支稳定，例如表单处理、固定审批、确定性数据处理。 | 高频且边界相对稳定的能力，例如知识检索、报告总结、文档处理或代码修改。 |
| 优势 | 对未知输入和路径变化适应性更强，能动态选择信息和工具。 | 可预测、易审计、易测试，成本、时延和风险更容易控制。 | 工作方法可复用、版本可维护，便于建立任务评测。 |
| 主要风险 | 路径不稳定，可能选错工具、重复执行或产生越权与幻觉执行。 | 对未预见的分支适应性弱，流程变化需要修改编排。 | 边界划分不当会形成臃肿的“万能 Skill”，或与具体业务场景脱节。 |
| 工程重点 | 上下文、工具边界、状态、验证器、安全与评测。 | 节点编排、状态转换、异常补偿、幂等与可观测性。 | 输入输出契约、工具权限、版本、评测样本与文档化。 |

### 2.1 如何选择

- 任务不确定性高，且下一步动作依赖语义理解或外部观察结果时，适合引入 Agent 或 ReAct 式循环。
- 流程边界固定、合规要求高、错误代价高，或规则已经能稳定覆盖时，应优先选择 Workflow 或传统系统。
- 如果动作完成后没有可靠的验证闭环，不应让 Agent 自主试错；应收敛为人工确认或确定性流程。

生产系统常采用**混合模式**：外层用确定性的 Workflow 管理入口、关键步骤、审批、补偿和审计；只在高不确定的节点使用模型做分类、信息抽取、候选方案生成或动态工具选择。这样既保留模型的适应性，也避免把整条业务链路交给非确定性决策。

### 2.2 Agent 与 Skill：自主决策与能力复用

Skill 可以泛指能力封装；在采用 Agent Skills 格式的系统里，更具体地指以 `SKILL.md` 为入口、可附带参考资料、脚本和模板的资源包。发现阶段先提供名称和适用描述，命中任务后再读取正文及必要附件。这种渐进式加载减少无关流程长期占据上下文。[OpenAI Skills 文档](https://developers.openai.com/api/docs/guides/tools-skills)

```text
Agent：接收目标 -> 发现合适的 Skill -> 读取指引 -> 选择并调用 Tool
       -> 验证观察结果 -> 继续或结束
Skill：任务适用条件 + 工作方法 + 必要参考资料 / 脚本 / 模板
Tool：具有输入输出契约、由执行系统控制的操作接口
```

例如，“生成报告摘要”的 Skill 可以规定先核对时间范围、保留证据来源、只生成草稿，并提供模板。Agent 读取后调用查询和文件工具完成任务；“仅生成草稿”的要求还需通过发布工具权限和审批状态落实，不能只依赖模型遵守文字。

需要区分三种约束：

| 约束 | 作用 | 保证边界 |
| --- | --- | --- |
| Skill 中的规则 | 告诉模型应如何工作、何时停止 | 是行为指引，可能被遗漏或误解 |
| Tool 的 Schema | 约束参数与返回结构 | 类型合法不代表业务正确或有权限 |
| Harness 与业务系统校验 | 校验身份、资源、版本、审批和副作用 | 在每次实际执行时拒绝不符合条件的操作 |

Skill 可以指导 Agent 使用模型、选择工具甚至委派任务；这些能力来自执行环境，不是 Skill 文本产生了新的权限。脚本也要经过正常执行边界，不能因“来自 Skill”而绕过校验。Workflow 可在固定节点使用这些指引，Agent 则可以按任务动态选择。加载方法见 [[Context Engineering（上下文工程）#4.4 工具与 Skill 的按需加载]]。

### 2.3 Tool Calling 在其中的位置

Tool Calling 解决的是“调用哪个外部能力、携带什么参数”；它本身不是完整的 Agent，也不负责整条任务的状态推进。

- 单轮调用、状态简单、动作副作用小的场景，只用 Tool Calling 可能就足够。
- 一旦涉及多步状态、审批、恢复执行、失败补偿或跨系统副作用，就需要 Workflow、状态机或 Agent 编排来控制整个过程。

## 3. 从对话到任务型 Agent 的分层设计

不应让所有用户请求默认进入重型 Agent 链路。一个更稳妥的设计是把普通对话与任务型决策分层：

```text
用户消息
  -> 会话上下文与轻量分流
  -> 普通对话 / 信息补全 / 任务升级候选
  -> 灰度、熔断、待审批短路等二次放行
  -> 任务型 Agent
  -> 患者（或用户）可见回复 + 结构化结果 + 工作台载荷
```

这样做的原因：

- 普通聊天关注吞吐、时延、成本和对话连续性；任务型 Agent 更关注风险控制、状态一致性、审计与恢复。
- 在升级前先完成画像、短期上下文和长期记忆等治理，Agent 可以复用统一的 `context snapshot`，不必每次从零理解任务。
- 命中任务信号不代表必须执行 Agent；仍可通过灰度、熔断、审批窗口和回退策略决定是否真正放行。
- Agent 返回的用户可见回复应回写主对话链路，避免“聊天系统”和“Agent 系统”各自维护历史，造成后续追问断层。

### 3.1 四层架构与 Context Engineering

为了让模型的非确定性决策不侵入全部业务逻辑，可将 Agent 系统按职责拆成四层：

| 层次 | 主要职责 | 不应承担的职责 |
| --- | --- | --- |
| 交互层 | 接收请求、会话标识、流式输出、过程状态展示。 | 直接决定高风险业务动作。 |
| 决策层 | 意图识别、上下文组织、任务路由、下一步判断和结束判断。 | 绕过执行层直接写入业务状态。 |
| 执行层 | RAG、Tool Calling、工作流节点和外部系统交互。 | 以模型自然语言替代系统校验。 |
| 治理层 | 权限、安全、幂等、审批、审计、观测、成本、降级与评测。 | 依赖 Prompt 自觉保证安全。 |

`Context Engineering` 是决策层的重要工作：它不只是修改 Prompt 文案，而是决定模型在当前轮**拿到什么信息、以什么顺序拿到、以及拿多少**。常见输入包括系统规则、用户画像、短期会话、长期记忆、检索证据、工具结果和当前任务状态。

上下文应按任务相关性、可信度、时效性和 Token 预算筛选与组织。全量拼接画像、历史与检索内容，通常会增加成本和噪声，并使关键事实被低价值信息挤出；工具结果也应优先以结构化摘要和关键字段注入，而不是原样堆叠。

## 4. 生产级 Agent 的关键设计

### 4.1 显式状态，而不是只靠 Prompt

任务型 Agent 是多步状态推进，不能只把中间过程塞进聊天文本。应保存会话或任务 ID、当前步骤、结构化上下文、工具结果、待审批任务和中断原因等信息。

典型状态可包括：`RUNNING`、`WAITING_APPROVAL`、`FINISHED`、`FAILED`、`BLOCKED_BY_SAFETY`。具体名称可随业务调整，但状态转换要明确且可审计。

为保证一致性：

- 同一任务主流程尽量串行推进，避免并发请求同时覆盖状态；检索、数据准备等相互独立的工作可并发。
- 工具返回先写入结构化状态，再供模型使用；不要把模型自然语言当作系统事实。
- 对有副作用的关键动作使用幂等键、版本号或状态机约束，防止重复执行和重复写入。

### 4.2 工具与事实边界

Agent 应区分三类信息：模型推断、工具返回、系统确认的最终状态。工具结果须核对来源、资源身份、时效与成功语义，才能转为正式状态；例如“已受理”不能记为“已完成”。模型推断应被视为候选判断或建议。

工具契约同时约束输入与输出，输入按下节的分层检查处理，并配合工具白名单、超时、重试和幂等策略；输出侧宜统一沉淀为“原始数据、面向模型的摘要、状态更新、证据或来源”四类内容。这样工具结果既能供下一轮决策使用，也能形成可回放、可审计的事实链，而不只是拼接到对话历史中的一句自然语言。

#### 4.2.1 结构化输出的四层契约

结构化输出把自然语言候选变成可处理的数据，但“看起来像 JSON”远没有到可执行的程度。运行系统应逐层检查：

| 层次 | 检查内容 | 通过后仍不能说明什么 |
| --- | --- | --- |
| 传输与语法 | 响应完整、调用关联正确、JSON 能解析 | 不保证字段齐全或类型正确 |
| Schema | 必填字段、类型、枚举、额外字段、长度与范围 | 不保证资源存在、业务条件成立 |
| 业务语义 | 参数之间一致、目标资源/版本可用、状态允许转换 | 不保证当前主体有权限或已批准 |
| 授权与执行 | 当前主体、租户、动作范围、审批版本、幂等身份 | 仅获准发送仍不等于下游已完成 |

例如 `{"report_id":"B-1","revision":1}` 可以通过格式和字段校验，但 A 租户用户无权登记 B 的报告。`approved:true` 即使是布尔值，也不能作为审批凭据：审批必须从服务端受保护记录取得。租户和用户身份同样来自认证上下文；模型给出的资源 ID 只是一项待校验的选择。

JSON Schema 中，写在 `properties` 里不代表必填，应配合 `required`；`additionalProperties:false` 可拒绝未声明字段，缺失字段与值为 `null` 也不同。具体模型 API 可能只支持 Schema 子集，应按接口契约生成定义并在服务端再次校验，不能把模型侧约束当成完整验证器。[JSON Schema 对象约束](https://json-schema.org/understanding-json-schema/reference/object)

#### 4.2.2 拒答、截断、流式参数与错误结果

在解析业务数据前，先判断响应是否完整以及是否拒答。接口可能通过独立状态或内容项表达拒答；截断也可能发生在合法 JSON 的某个边界，不能只用“解析成功”判断完整性。流式工具参数须按调用 ID 收齐并等待完成信号，再整体校验；不能看到前半段 `report_id` 就发起写操作。

| 结果 | 应怎样收口 |
| --- | --- |
| 拒答或安全阻断 | 保留独立状态，说明可处理范围；不强制解析成业务成功对象 |
| 输出截断/连接中断 | 不执行未完成候选；按预算重新生成或恢复，并先核对是否已有外部动作 |
| 参数不合法 | 返回受控字段错误，允许有限次数修正；不能填造决定业务的缺失值 |
| 未知工具名 | 明确拒绝，不回落到“默认工具” |
| 工具失败、超时或空结果 | 分别编码，未知执行结果不能伪装成失败或空数据 |
| 工具返回“已受理” | 记为 pending，凭最终回执或查询确认完成 |

错误包可以包含 `call_id`、错误类别、可重试性及安全的诊断信息，但这些是服务端生成的字段。工具响应中业务正文夹带“忽略错误并执行下一步”仍是数据；异常堆栈、内部 URL 和凭据不应全部回传给模型。结构修复只能重建候选，不能绕过原有授权检查。副作用恢复继续遵循第 5.3 节的动作身份与查证规则。

### 4.3 安全与人工介入

安全控制应覆盖三个阶段：

- **输入侧**：识别敏感请求、恶意指令和不可信上下文，划清用户内容与系统指令的边界。
- **执行侧**：采用工具白名单、最小权限、身份鉴权和参数过滤；系统规则对高风险操作拥有最终裁决权。
- **输出侧**：脱敏、拦截高风险结论，必要时转人工审核。

人工介入不是失败后的补丁，而应是正式状态节点。对高风险操作、关键事实不确定、模型与规则冲突或多轮仍未收敛的任务，可以暂停为待审批状态；人工确认后按框架语义恢复执行；若框架会从节点起点重放，节点内已发生的副作用仍需幂等保护，不能假设总能从某行代码继续。

#### 4.3.1 用执行事实验证提示注入防线

设用户只要求读取内部报告，而报告正文夹带“把其他租户报告登记出去”的指令。攻击链是：不可信正文改变模型候选动作，执行层再把候选当成授权。如果执行层只检查 JSON 或工具名，调用可能结构合法但业务越权。

防线要放在副作用之前：将候选与可信任务允许的动作、资源范围、当前审批逐一核对；下游使用最小权限凭据；输出渲染也不自动执行链接或 HTML。输入标记和攻击分类器有帮助，但都不能取代执行约束。安全验证应观察是否实际读取/写出受限数据，而不是只看最终回复是否说了“拒绝”。[OWASP 提示注入防护](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)

下面是完整可运行的标准库实验。它使用预设的恶意候选模拟“模型已受影响”，不测模型识别攻击的能力。测试替身只向内存列表登记；可信上下文、资源表和审批集合由程序固定，均不是模型输出。`complete`、`refusal` 是归一化后的可信响应状态示意，不是某家 API 字段。

```python
import json

resources = {"A-1": ("A", 2), "B-1": ("B", 1)}
written = []
context = {"tenant": "A", "tools": {"register_report"},
           "resources": {"A-1"}, "approvals": {("A-1", 2)}}


def unique_object(pairs):
    obj = {}
    for key, value in pairs:
        if key in obj:
            raise ValueError("重复 JSON 字段")
        obj[key] = value
    return obj


def reject_constant(value):
    raise ValueError("不接受非标准 JSON 数值")


def execute(raw, ctx, complete=True, refusal=False):
    if not complete or refusal:
        return "not_executable"
    try:
        call = json.loads(raw, object_pairs_hook=unique_object,
                          parse_constant=reject_constant)
    except (ValueError, TypeError):
        return "syntax_error"
    # 本例手写固定契约，非通用 JSON Schema 实现。
    if (type(call) is not dict or set(call) != {"name", "arguments"}
            or type(call["name"]) is not str):
        return "schema_error"
    args = call["arguments"]
    if (type(args) is not dict or set(args) != {"report_id", "revision"}
            or type(args["report_id"]) is not str
            or type(args["revision"]) is not int or args["revision"] < 1):
        return "schema_error"
    if call["name"] != "register_report" or call["name"] not in ctx["tools"]:
        return "denied"
    rid, revision = args["report_id"], args["revision"]
    # 拒绝结果不区分资源不存在和无权访问，避免枚举资源。
    if rid not in ctx["resources"] or rid not in resources:
        return "denied"
    tenant, current_revision = resources[rid]
    if tenant != ctx["tenant"]:
        return "denied"
    if revision != current_revision:
        return "stale_revision"
    if (rid, revision) not in ctx["approvals"]:
        return "approval_required"
    written.append((rid, revision))
    return "registered"


def request(rid="A-1", revision=2, name="register_report", **extra):
    return json.dumps({"name": name, "arguments": {
        "report_id": rid, "revision": revision, **extra}})


cases = [
    ("{", context, {}, "syntax_error"),
    (request(revision=True), context, {}, "schema_error"),
    (request(approved=True), context, {}, "schema_error"),
    (request(name="export_all"), context, {}, "denied"),
    (request("B-1", 1), context, {}, "denied"),
    (request(revision=1), context, {}, "stale_revision"),
    (request(), dict(context, approvals=set()), {}, "approval_required"),
    (request(), dict(context, tools=set()), {}, "denied"),
    (request(), context, {"complete": False}, "not_executable"),
    (request(), context, {"refusal": True}, "not_executable"),
    ('{"name":"read","name":"register_report","arguments":{}}',
     context, {}, "syntax_error"),
    (request().replace('"revision": 2', '"revision": NaN'),
     context, {}, "syntax_error"),
]
for raw, ctx, status, expected in cases:
    assert execute(raw, ctx, **status) == expected
    assert written == []
assert execute(request(), context) == "registered"
assert written == [("A-1", 2)]
print("契约与执行边界实验通过：12 个拒绝场景无写入，1 个授权场景成功")
```

验证记录：2026-10-29，Python 3.12.9，12 个拒绝场景均未写入，1 个有效授权场景登记成功。验证对象是固定契约与执行边界，不是模型抗注入成功率。

本例刻意采用严格的整数线协议，因此 Python 的布尔值和 `2.0` 都不作为 revision 接收；这不是所有 JSON Schema 验证器的数值语义。生产实现还要处理输入长度、深度、调用关联、并发版本变化及幂等；本例成功分支没有实现重复写保护，不能替代第 5.5 节的持久化实验。

完整安全评测还应把攻击文本真正放进检索片段或工具结果，使用真实模型观察候选，再验证边界；同时加入合法查询和“解释一段恶意文本”等正常样本统计误拦截率。上下文压缩后的来源保留见 [[Context Engineering（上下文工程）#7.3.1 防止摘要和记忆把外部内容升级为指令]]。

### 4.4 失败恢复与降级

恢复执行的前提是中间状态可还原。恢复时应从中断步骤继续，对已经执行的有副作用动作先做幂等判断；只读步骤通常可重试，但新查询可能得到不同数据，需决定复用原快照还是更新证据版本。

最危险的窗口是“外部操作已成功，本地尚未记成功就崩溃”。恢复后仅凭 checkpoint 会把动作误认为未执行。应先持久化动作意图和稳定幂等键，再调用外部系统；结果不明时按该键查证或幂等重试。若下游既不支持查询也不支持去重，就应进入待核实状态，不能承诺恰好执行一次。

同时应为 Agent 保留降级路径：当工具、模型或下游服务异常时，可回退到普通对话、固定流程或人工处理，避免重链路的波动中断核心用户入口。

### 4.5 单 Agent 与多 Agent

Multi-Agent 不是默认答案。它适合职责边界已经明显分化、单一 Prompt 持续膨胀、角色互相干扰，或无法独立评测的场景。

拆分后的收益是角色可独立调优和评测；代价是编排、共享状态、冲突收敛和监控都更复杂。因此，多 Agent 间应优先共享显式上下文容器和结构化结果，而不是只靠多个 Agent 互传自然语言。

### 4.6 Agentic RAG：受限的检索子流程

Agentic RAG 是让 Agent 根据当前目标和已有证据，动态决定是否检索、如何改写查询、是否继续补检索或转为追问的一种模式。RAG 在这里是 Agent 可调用的知识能力，而不是每次请求都必须经过的固定流水线。

它可以有局部循环，但不应成为第二个无边界的 Agent。推荐由全局 Agent `run` 持有最终决策权和停止权，Agentic RAG 只在一次工具调用的局部预算内完成受限检索：

```text
全局 Agent Run（总步骤、总 Token、总时延预算）
  -> 当前步骤需要外部知识时，调用 retrieve_evidence
      -> query rewrite -> 检索 / 重排 -> 可选的一次补检索 -> 返回证据或“证据不足”
  -> Agent 基于证据决定回答、追问、调用其他工具或结束
```

应避免把多个自治循环无约束嵌套，例如 `Agent -> SubAgent -> Agentic RAG -> 再调用 Agent`。这种结构会让时延、成本和失败概率叠加，也使停止条件和责任边界难以判断。

各层应分别拥有明确预算：

| 层级 | 典型约束 |
| --- | --- |
| 全局 Agent | 最大步骤数、总 Token、总时延、最大工具调用数和最终停止条件。 |
| SubAgent | 单次职责、可用工具集合、局部步骤预算。 |
| Agentic RAG | 最大检索轮数、最大 query 数、Top-K、重排数量与证据不足时的停止策略。 |
| 单个 Tool | 超时、重试次数、并发度、缓存、熔断和降级。 |

效率优化通常先从路由入手：默认走普通 RAG 或不检索；只在多跳、低置信度、跨数据源或证据不足的场景升级到 Agentic RAG。互不依赖的检索和数据读取可以并行；对查询改写、稳定上下文和检索结果可做缓存；先进行低成本召回，再在必要时使用重排或第二跳检索。

### 4.7 Agent Runtime 与平台化治理

当 Agent 数量、工具和业务场景持续增长时，审批、恢复、降级、灰度、审计和评测不应散落在每个 Agent 的业务代码里，而应逐步收敛到统一的 Agent Runtime（运行时）或平台能力中。

可以把一次任务执行视作一个可追踪的 `run`：它串起输入、路由、模型调用、工具执行、状态变更、人工介入、失败补偿和最终输出。围绕这个统一边界，系统才能可靠地进行回放、审计、断点恢复、灰度对比和质量分析。

这与应用框架将事务、鉴权、日志等横切关注点从业务方法中抽离的思路相似：Agent 内部应内聚任务目标、领域判断和能力选择；Runtime 则统一管理生命周期、上下文、权限、执行拦截和治理策略。平台化不意味着必须一开始自研复杂平台，而是随着共性能力重复出现，逐步把它们从业务代码中抽出。

#### 4.7.1 自管与托管：迁移运行责任，不迁移业务正确性

自管 Harness 时，应用负责循环调度、存储、恢复和部署；托管运行时可接管其中的通用基础设施。以 OpenAI 为例，当前 Agents API 提供托管 Harness、会话进度及自动压缩等能力，Agents SDK 则适合由应用控制运行环境。[运行时选项](https://developers.openai.com/api/docs/guides/agents)

选型要核对保存哪些状态、保留多久、如何恢复、数据在哪里执行、业务权限在哪里校验，以及如何导出轨迹。会话保存不等于业务数据库事务，文件快照也不会撤销已经发送的消息。长任务还应区分任务生命周期和单次执行尝试：重新连接或恢复执行不应产生新的业务动作身份。上下文压缩、任务 checkpoint 和长期记忆的分工见 [[Context Engineering（上下文工程）#5.6 上下文压缩不等于任务恢复]]。

### 4.8 动态工具发现：先找能力，再加载契约

工具较少时，一次传入全部定义最简单；工具增长后，大量参数 Schema 会占用输入预算，并增加相似能力的选择干扰。动态发现将过程拆为：

```text
按主体与资源权限筛选能力目录
  -> 根据任务搜索候选工具
  -> 加载候选的完整契约与版本
  -> 模型选择参数
  -> 执行层再次鉴权并调用
```

这是能力检索，不是业务数据检索；MCP 负责工具连接，也不自动保证检索质量或授权正确。OpenAI 的 Tool search 是按需装载工具定义的一种具体实现。[Tool search](https://developers.openai.com/api/docs/guides/tools-tool-search)

隐藏成本是“工具没被找到”会表现得像“工具不存在”。要用真实任务检查发现召回率、同名误选、版本变更和权限撤回；对少数关键工具保留明确入口。工具定义中应解释业务含义、适用条件及副作用，而不只写一个模糊函数名。发现成功也不意味着执行时仍有权限，因此调用前的鉴权不能省略。

### 4.9 程序化工具调用：让代码处理确定性数据流

普通循环中，每次工具返回后都让模型读结果并决定下一步；若只是对多份数据筛选、去重和关联，这会增加往返和上下文成本。程序化工具调用允许模型生成受限程序，组合已授权工具，并把整理后的必要结果交回模型。[Programmatic Tool Calling](https://developers.openai.com/api/docs/guides/tools-programmatic-tool-calling)

例如整理多份报告时，程序按明确规则筛选时间、按报告 ID 去重、保留来源，再让模型归纳。这里不能把“未知的语义判断”偷偷变成固定过滤：字段缺失要返回缺失状态，查询失败不能伪装成空结果，摘要要保留证据引用和被过滤数量。

适用条件是数据流可确定、依赖可描述、输出能有效缩小。若每一步都要重新判断语义，直接工具循环更自然。写操作、审批和不可逆动作应保持可独立审计的边界；把十次调用放进一段程序不会自动形成一个事务。执行环境还需限制循环、调用次数、超时、输出量和可调用工具。

### 4.10 异步执行与中途干预：并发改变了结果的适用范围

并行调用表示多个任务同时运行；异步工具调用进一步允许模型在工具未返回时推进独立工作。它不同于“把整个模型请求放到后台”。例如等待报告查询时可以准备模板，依赖查询结果的内容则必须等待。[Async tool calling](https://developers.openai.com/api/docs/guides/async-tool-calling)

用户还可能在执行中修改范围。一些接口提供 mid-turn steering，将新要求送入正在进行的任务；但它不撤销已发生的动作，也不自动取消已启动工具。[Mid-turn steering](https://developers.openai.com/api/docs/guides/steering)

应用可将任务目标记录为单调递增的 `goalRevision`，每次调用绑定 `callId`、输入范围和修订号。结果返回时先关联原调用，再判断它是否仍适用；旧结果可保留作审计，或经显式兼容性判断后复用，但不能直接覆盖新目标状态。这个修订号是应用设计，不是所有 SDK 自带的保证。

```text
t0：目标 v1，要查询近 90 天，发出调用 C1
t1：用户改为近 30 天，保存目标 v2，发出调用 C2
t2：C2 返回，写入 v2 的证据
t3：C1 迟到，保留其来源，不覆盖 v2 的证据
```

仅在回调入口判断版本还不够：判断后到写入前，目标仍可能变化。检查与更新需使用数据库条件更新、锁或串行事件处理原子完成。取消是尽力而为；真正的业务写入还须在提交边界验证授权、目标和审批版本。

目标版本不能代替证据版本：同一目标下新资料返回，也可能使正在生成的草稿过期。可为已接受的证据集合维护 `evidenceRevision`，生成前保存不可变快照，提交时原子比较目标与证据两个版本。目标或证据更新后，已提交的草稿也应从“当前有效”状态撤下。

回调去重还须区分相同结果与冲突结果：同一 `callId` 的同一终态结果重复到达，不再推进状态；内容不同则记录冲突并处理，不能静默覆盖。去重记录与证据更新必须在同一原子边界内，否则崩溃可能留下“已去重但未应用”的窗口。调用版本来自服务端发起记录，不信任回调自己填写的版本。

### 4.11 沙箱工作空间：把执行环境与控制职责分开

文件、Shell、依赖、预览和快照使 Agent 能实际制作与验证产物，而不仅是返回文字。沙箱负责运行这些操作，Harness 负责工具路由、权限、审批和任务状态。这样的职责拆分可让模型运行代码时只接触必要文件和受限凭据。[Sandbox Agents](https://developers.openai.com/api/docs/guides/agents/sandboxes)

沙箱隔离不等于业务安全：若授予了外网或发布凭据，仍可产生外部副作用；恢复文件快照不能回滚外部 API。任务恢复前也应检查文件、依赖与引用是否仍存在。产物验收要区分“文件已写出”“格式可打开”“内容满足任务”“已对外发布”，避免把写文件成功当成任务完成。

## 5. 评测、观测与上线治理

不要只评价最终回复“像不像”。先按业务定义任务成功，例如“工单被正确创建且未重复执行”或“高风险请求被正确拦截”；再分别衡量结果、过程、风险和效率：

| 维度 | 示例指标 |
| --- | --- |
| 结果 | 任务完成率、答案准确率、业务目标达成率。 |
| 过程 | 工具选择正确率、参数合法率、平均步数、重试率、超时率。 |
| 风险 | 错误执行率、高风险漏拦截率、越权调用率、转人工率。 |
| 效率 | 平均 RT、P95/P99、单任务 Token 成本、工具调用次数。 |

高风险场景需要单独统计，不能被平均指标掩盖；过程正确与结果正确也应分开观察，避免“最终碰巧成功”的链路被误判为稳定成功。

上线时可按用户、租户或流量比例灰度，必要时通过双跑或影子验证比较新旧链路，影子链路的写工具应隔离或替换为测试替身，避免重复产生业务副作用；持续关注完成率、错误率、转人工率、成本和投诉率，并保证能快速切回旧链路或降级路径。

端到端验证不能只覆盖正常回答，还应覆盖工具超时与失败、非法参数、重复请求、步数上限、审批中断与恢复、安全拦截以及降级回退。只有这些异常链路也能稳定收口，Agent 才具备生产可用性。

### 5.1 项目演练：可恢复的报告草稿任务

以下是沿用医生助手场景的教学设计，不表示现有项目已实现；只讨论资料整理与草稿生成，不涉及自动诊疗决策。目标是“整理指定患者近 90 天资料，生成供医生核对的草稿，不发布”。

先定义不变量：患者与租户隔离；结论能追溯证据；最终草稿匹配当前目标及证据版本；没有对应版本审批就不能发布。设计状态至少包含 `taskId`、`goalRevision`、`evidenceRevision`、`scope`、`calls`、`evidenceRefs`、`artifactRef` 和独立的发布状态。

正常路径是读取当前目标、发现只读工具、加载摘要 Skill、异步获取资料、程序化去重、生成文件并验证内容。生成期间目标发生变化，就重新判断现有证据和草稿是否适用。读取数据期间发生压缩，只改变模型可见上下文，不能删除尚未完成调用的持久记录。

| 注入故障 | 应观察到的行为 | 对应设计依据 |
| --- | --- | --- |
| 用户把 90 天改成 30 天，旧查询最后返回 | 旧结果不覆盖当前证据；草稿按新范围生成 | 目标修订号与原子状态更新 |
| 一份资料查询超时 | 标记缺失或重试，不能写成“未发现异常” | 未获取数据不等于否定事实 |
| 文件写出后、任务记账前崩溃 | 按产物标识核实文件及版本，不能误认为已发布 | 文件状态与业务状态分开 |
| 压缩摘要遗漏“不发布” | 执行系统仍拒绝发布，恢复输入重新注入约束 | 权限与任务事实不依赖摘要 |
| 工具调用重复投递或回调重复 | 不重复推进已完成状态 | 调用 ID 去重及状态条件更新 |

可先在本地测试替身中人为调整回调顺序，验证状态不变量；真实权限撤回、存储恢复、审批和模型在压缩后的表现则需要集成测试。该表是验收设计，不是已执行的集群测试报告。

### 5.2 最小可运行实验：旧结果、重复回调与草稿版本

实验文件：[agent_revision_lab.py](实验/agent_revision_lab.py)。使用 Python 3.10+ 标准库，从知识库根目录执行：

```bash
python3 "06-AI应用后端/02-Agent与RAG/实验/agent_revision_lab.py"
```

模型刻意只处理一个任务：`start_call` 绑定当前目标版本；`receive` 先确认调用身份、检查重复与冲突，再决定只归档还是接收证据；`snapshot` 返回不可变的目标和证据快照；`commit` 比较生成开始时与提交时的快照。生成过程在状态转换之外，测试通过插入目标变更或回调来模拟生成耗时窗口，无需真实模型或 sleep。

```text
C1 绑定目标 v1 -> 改目标到 v2 -> C2 返回并接收
-> 保存快照 (目标 v2, 证据 e2)
-> C1 迟到：仅归档；C2 重复：不改变版本
-> 以同一快照提交草稿：成功

保存快照 (v2, e2) -> 同目标的补充证据到达，变为 (v2, e3)
-> 以 (v2, e2) 提交：拒绝；重新读取 (v2, e3) 才能提交
```

| 检查 | 实验断言 |
| --- | --- |
| 旧结果隔离 | 旧回调留有回执，但不改变当前证据及其版本 |
| 重复与冲突 | 相同内容返回 `duplicate`，有效草稿不失效；不同内容报错且保留原证据 |
| 目标变更 | 旧草稿不能覆盖新草稿；最新快照可提交 |
| 同目标补充证据 | 仅目标相同不足以提交，证据版本也须匹配 |
| 提交后的变化 | 目标或证据改变使已有草稿失效 |
| 调用关联 | 未知 ID 与 ID 复用被拒绝；无证据无法生成 |
| 事件顺序 | 穷举旧、新回调各出现两次的 6 种顺序，只接收一次新结果 |

2026-10-29 使用 Python 3.12.9 运行，9 项测试通过，其中包含上述 6 种回调顺序。复查先用反例确认“只校验目标版本”会接受缺少新证据的草稿，再用对应回归测试验证修正。

**边界**：这是内存中的单线程串行事件模型，每个方法视为不可分割的状态转换，不证明多线程、数据库事务、进程崩溃恢复或真实模型质量。回调只模拟成功的终态文本，不包含认证、错误重试、流式分片、审批和发布。不同调用视为不同证据来源；同一来源的刷新或重试需要额外的来源版本与尝试顺序，不能仅按目标版本接受。并发生成多个草稿时，如要求较新的生成尝试优先，还需增加生成尝试版本。实验只验收快照一致性，不验收草稿内容的语义质量。

生产实现需持久化调用绑定、回执与证据，并让回执去重、版本比较、证据更新和草稿失效在事务内原子完成；草稿条件提交也应落在同一受保护边界。已经写出的文件可保留为历史产物，不能因文件存在就标为当前有效或已发布。

### 5.3 持久化副作用：成功回执丢失后如何恢复

前面的医生助手任务明确要求“不发布”，不能因为实现了恢复机制就增加发布权限。下面换成一个**独立的教学任务**：用户已批准把内部学习报告的指定版本登记到工作台；实验只调用本地 SQLite 测试替身，不连接工作台。

登记至少要分清以下身份：

| 身份 | 生命周期 | 用途 |
| --- | --- | --- |
| `task_id` | 一次用户任务 | 绑定目标、取消状态与业务范围 |
| `action_id` | 一次确定的业务登记意图 | 重试时稳定，作为下游幂等键 |
| `attempt_id` | 一次发送尝试 | 每次重试新建，用于诊断耗时与结果 |
| 审批绑定 | 指定内容哈希、目标版本、动作类型和范围 | 防止修改内容后复用旧审批 |
| 下游回执 | 对应实际登记结果 | 证明业务事实，不能以模型“已完成”代替 |

`action_id` 不能每次重试都重新生成，否则下游看到的是多个新动作；也不能只用 payload 哈希代替，因为用户可能明确要求两次内容相同、业务上不同的登记。复用同一 `action_id` 却改变内容，应直接拒绝并产生新的审批流程。

稳定身份还必须落到存储约束：本例每个任务版本只允许一次登记，`(task_id, revision)` 唯一绑定一个 `action_id`。恢复时读取已保存的绑定，不能另造新键绕过下游去重。用户明确要求再次登记相同内容时，建立新任务并重新审批；包含多个动作的真实任务则应使用明确的业务动作槽位，不能照搬“每版本只有一个动作”的教学约束。

按以下时序划分事务：

```text
T1 本地：核对当前版本与审批 → 持久化 action 意图 → 提交
T2 本地：登记新的 attempt，action 进入 UNKNOWN → 提交
   发送请求(action_id, payload_hash, payload)
T3 下游：幂等键、请求摘要与业务登记在同一事务提交
   返回回执
T4 本地：保存回执，action 确认为 CONFIRMED → 提交
```

T1～T4 不在同一个数据库事务中。若 T3 成功而 T4 前中断，本地只知道 `UNKNOWN`。恢复时先按 `action_id` 查证；确认存在则记账，确认没有且仍有授权时才发起同键重试。查证本身若超时，仍是未知。下游返回“暂未查到”也可能只是最终一致性延迟，不能因此更换幂等键。

下游必须对“同键同参数”和“同键不同参数”分别给出契约，并明确去重保留期；如果原动作仍可能存在而幂等记录已经过期，自动重试可能重复登记，应暂停并核实。只有本地去重表、没有下游原子幂等或可核实的业务唯一约束，无法消除 T3/T4 之间的窗口。[AWS 幂等 API 设计](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

### 5.4 取消、审批失效与迟到结果的状态处理

取消是用户希望停止后续执行，不能被解释为“下游肯定没有发生”。任务状态和动作事实应分开存储：任务可为 `CANCELLED`，动作仍可能最终查明为 `CONFIRMED`。恢复器可以继续只读查证并审计，但不能以“恢复”为由继续发送已撤销的写操作；迟到回执只更新原动作事实，不把任务改回运行或覆盖新目标。

| 失败窗口 | 恢复动作 | 必须保留的事实 |
| --- | --- | --- |
| 意图已落库，尚未发送 | 重新检查当前审批与取消状态，再决定发送 | 审批是否仍绑定当前内容与目标 |
| 下游已提交，本地回执未保存 | 查询原动作并补记回执 | 外部操作已完成，不能再次创建新动作 |
| 请求在途时取消 | 阻止新发送，等待/查证原请求 | 取消不保证撤回已经发出的请求 |
| 内容从 v1 改成 v2 | v1 的迟到结果只记到 v1 动作；v2 重新审批 | 旧批准不能授权新 payload |
| 需要撤销已完成登记 | 创建有授权的补偿动作，关联原动作并做幂等 | 补偿也会失败，原事实不能擦除 |

本地“检查未取消”与远端“产生副作用”之间仍存在竞态。若要求取消一定阻止提交，必须由下游参与约束，例如在提交处验证有效授权/单调 fencing token，并定义授权撤销与提交的先后关系；只在调用方加一次检查无法提供这种保证。超时、锁租约到期也不能自动撤销远端操作。

### 5.5 最小持久化实验：独立事务与回执恢复

实验文件：[agent_durable_action_lab.py](实验/agent_durable_action_lab.py)，使用 Python 3.10+ 标准库：

```bash
python3 "06-AI应用后端/02-Agent与RAG/实验/agent_durable_action_lab.py"
```

实验在临时目录创建两个 SQLite 文件，分别模拟本地任务账本和下游登记系统。下游一张表同时保存业务记录与幂等身份，避免“只保存幂等键却漏登记”或相反；本地每次尝试先提交，再调用下游。通过在下游提交后抛出故障、关闭并重新打开连接，检验恢复不会依赖内存状态。

测试覆盖正常登记、回执丢失后的查证恢复、同键重试、同键异参拒绝、过期审批阻断、发送前取消，以及下游已完成后取消仍能查明真实结果；还验证同任务版本不能换键再登记，新的已批准任务则可登记相同内容。数据库记录数断言用来区分“返回成功”与“没有重复登记”。

验证记录：2026-10-29，Python 3.12.9，复查先复现了“同一任务版本误换 action_id 会重复登记”，补入数据库唯一约束与回归后，11 个测试全部通过；同时保留重开数据库后的查证恢复和旧目标迟到结果隔离。

**验证边界**：这是单进程、顺序调用的本地持久化实验。关闭重开连接模拟恢复，不等于操作系统断电或真实服务进程被杀；不实现分布式抢占、租约、下游授权原子校验、网络分区和幂等过期策略，也未调用模型。线上仍需围绕这些窗口做集成验证，评测组织见 [[AI应用评测与错误分析]]。

## 6. 一句话总结

Agent 的价值不在于让模型“自主做更多”，而在于将模型擅长的理解、归纳和候选决策，与系统擅长的状态管理、确定性执行、权限控制、审计和治理结合起来，收敛为可验证、可恢复、可持续优化的业务能力。
