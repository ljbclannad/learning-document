# Context Engineering（上下文工程）

## 1. 什么是 Context Engineering

Context Engineering（上下文工程）是指：在每次模型调用前，围绕当前目标选择、组织、压缩并注入最有用的信息；并在调用后把结果以合适的形式写回状态、记忆或日志。

它不等于“把 Prompt 写得更长”。Prompt 只是上下文的一部分。真正影响模型本轮行为的，还包括当前用户输入、会话历史、任务状态、用户画像、长期记忆、RAG 证据、工具结果、可用工具定义和安全约束。

可以将它理解为模型调用前后的信息供给系统：

```text
原始消息 / 状态 / 记忆 / 知识 / 工具结果
  -> 选择、过滤、重排、压缩、预算控制
  -> 本轮 Context
  -> 模型生成或工具调用
  -> 结构化写回、摘要、记忆提取、审计
```

目标不是尽可能塞满上下文窗口，而是让模型在有限 Token、时延和成本下，获得**最相关、最可信、最及时且边界清晰**的信息。

## 2. 为什么不能只保留全部聊天记录

将全量历史直接拼接到 `messages` 中，开始时实现简单，但会随着会话增长带来几个问题：

- Token 成本和响应时延持续上升。
- 旧话题、重复表达和低价值内容会干扰当前任务。
- 关键事实、待办事项和安全约束容易被长文本淹没。
- 模型能看到历史，不等于能稳定地区分事实、推断、旧结论与当前状态。
- 多步任务中断后，只靠自然语言历史难以可靠恢复到正确步骤。

上下文窗口再大也不能替代上下文管理：长上下文仍有成本，并且不相关或过期信息会降低有效信息密度。

## 3. 上下文不应只有一个“消息槽位”

生产系统通常将不同性质的信息分开管理，再在调用前组成模型输入。

| 槽位 | 保存什么 | 生命周期 | 是否直接注入模型 |
| --- | --- | --- | --- |
| 系统规则与安全约束 | 角色、权限、禁止事项、输出协议。 | 配置或版本级。 | 通常必须注入。 |
| 当前请求 | 用户本轮目标、输入参数、附件引用。 | 单轮。 | 必须注入。 |
| 短期对话历史 | 最近几轮问答及必要的工具消息。 | 会话级。 | 保留窗口内内容。 |
| 会话摘要 | 旧历史的主题、结论、未完成追问。 | 会话级，可滚动更新。 | 通常注入。 |
| 显式任务状态 | 当前步骤、已确认事实、待补字段、已执行动作、失败原因。 | 任务级。 | 按当前任务注入。 |
| 用户画像与长期记忆 | 稳定偏好、长期事实、跨会话经验。 | 跨会话。 | 检索后按需注入。 |
| RAG 证据 | 本轮问题相关的文档片段和来源。 | 单轮或任务级。 | 经筛选、重排后注入。 |
| 工具结果与证据 | 外部系统返回、关键字段、来源、时间戳。 | 任务级或持久化审计。 | 注入摘要和必要字段。 |
| 原始日志 | 完整消息、完整工具请求与响应。 | 长期留存，受合规策略约束。 | 通常不直接全量注入。 |

核心原则是：**对话历史用于连续性，任务状态用于推进，记忆用于跨会话个性化，RAG 用于补充知识，工具结果用于提供可验证事实。**

## 4. 每轮上下文如何组装

可将调用前的组件称为 Context Compiler（上下文编译器）。它不一定是独立服务，也可以是一组清晰的编排规则。

```text
1. 确定当前目标和调用类型
2. 装载不可裁剪的规则与当前任务状态
3. 读取最近对话和会话摘要
4. 按需检索长期记忆、知识库和历史证据
5. 裁剪工具结果与附件内容
6. 按优先级和 Token Budget 组装本轮输入
7. 为模型输出和下一轮工具调用预留空间
```

### 4.1 先确定任务，再决定取什么信息

不同任务不需要相同上下文。普通聊天通常更依赖最近对话；知识问答需要更多检索证据；任务型 Agent 则优先需要显式状态、已执行动作和工具事实。

因此，检索和装载的 query 不宜只使用用户原话。必要时可结合当前意图、实体、时间范围、任务阶段和待补字段，先做 query rewrite 或 structured query，再检索记忆与知识。

### 4.2 Token Budget 是应用层优先级，不是模型内部权重

常见做法是设置总输入预算和各槽位上限。例如：

```text
总输入预算
  = 固定规则 + 当前请求 + 任务状态 + 对话窗口
  + 检索证据 + 工具摘要 + 输出预留
```

系统根据优先级决定谁能占用预算，而不是调整模型内部 attention weight。通常不可轻易裁剪的是系统安全规则、当前用户请求和未完成任务状态；对话历史、低分记忆、长工具响应和低相关证据则可以压缩或舍弃。

具体比例不是固定公式。风险任务应提高规则、状态和证据的预算；普通聊天可保留更多近期对话；RAG 问答应优先保证高质量证据而非长历史。

### 4.3 超预算时的处理顺序

一种稳妥的收缩顺序是：

1. 去除重复、过期和明显无关的内容。
2. 降低低分记忆和检索片段的数量，或裁剪片段长度。
3. 将旧对话和旧工具结果压缩为摘要。
4. 移除已被摘要覆盖的原始历史，但保留日志和引用 ID。
5. 若仍超限，改为追问、分步执行或转入更确定的流程，而不是静默丢掉关键状态。

## 5. 常见的压缩与记忆方案

### 5.1 滑动窗口

只保留最近 N 轮原始消息。它实现简单、延迟低，适合短对话；缺点是超出窗口的关键信息会被直接遗忘，因此常与会话摘要配合使用。

### 5.2 滚动摘要

当历史达到 Token 或轮次阈值时，把较早消息压成摘要，只保留最近少量原始消息。摘要应重点保留：已确认事实、用户偏好、当前主题、未完成事项、关键约束和重要结论。

摘要不是事实源。应保存摘要版本及其覆盖的消息 ID，避免重复摘要，也便于发现遗漏时回溯原始消息。

### 5.3 显式状态

任务型 Agent 不应把进度藏在摘要或聊天文本中，而应将关键状态以结构化字段持久化，例如：

```text
taskId / currentStep / confirmedFacts / missingFields
completedActions / pendingApproval / failureReason / evidenceRefs
```

显式状态用于恢复、并发控制和审计。对有副作用的动作，还应保存幂等键、执行状态和版本信息。

### 5.4 长期记忆

长期记忆保存跨会话仍有价值的信息，例如稳定偏好、已确认的用户事实、长期业务约束或经过沉淀的经验。它应支持按用户、组织、应用等 namespace 隔离，并具备过期、纠错、删除和审计能力。

长期记忆的写入有两种常见方式：

- **热路径写入**：本轮通过规则或模型判断后立即记录，适合明确且需要立即影响后续步骤的信息。
- **异步沉淀**：在对话结束或后台任务中提取、去重、合并和校验，适合降低主链路时延、减少误写。

无论哪种方式，都不应把模型的推测直接写成用户事实。建议记录来源、时间、可信度和可撤销标记。

### 5.5 RAG 与工具结果的按需注入

RAG 解决“本轮缺少外部知识”，不是长期记忆的替代品。检索片段应经过相关性过滤、去重、可选 rerank 和长度裁剪，并保留来源引用。

工具结果则更接近外部事实。完整 JSON、表格和文件内容应保存到外部存储或审计日志中；注入模型的通常是关键字段、结构化摘要和引用 ID。模型生成的解释与工具事实必须分开保存。

## 6. 模型返回后怎么写回

模型的一段返回不应只进入单一槽位，应按用途拆分：

| 返回部分 | 推荐写入位置 | 注意点 |
| --- | --- | --- |
| 面向用户的回复 | 短期对话历史。 | 用于连续追问，不自动视为事实。 |
| 已确认的任务结论与下一步 | 显式任务状态。 | 应有结构化字段与状态转换规则。 |
| 模型推断或建议 | 候选结论。 | 未验证前不能升级为长期事实或直接执行。 |
| 工具调用及结果 | 工具结果、证据和审计日志。 | 保留请求、响应、来源和执行状态。 |
| 待人工确认的动作 | Pending Task / 审批状态。 | 记录断点，审批后从该处恢复。 |
| 稳定的用户事实或偏好 | 长期记忆候选。 | 经规则、用户确认或异步校验后写入。 |

## 7. 生产中容易忽略的问题

### 7.1 可信度与时间性

信息应区分“用户陈述”“工具返回”“系统确认”“模型推断”。同时记录发生时间、有效期和来源；同一事实冲突时，不能简单取最新文本，应按来源可信度和业务规则收敛。

### 7.2 并发与恢复

同一会话或任务的状态更新应避免并发覆盖。任务执行应有 checkpoint；在模型、工具或人工审批中断后，从结构化状态恢复，而不是重新让模型阅读整段历史猜测进度。

### 7.3 Prompt Injection 与数据隔离

检索文档、工具输出、网页内容和用户上传文件都属于不可信输入。它们可以作为证据，不应获得系统指令权限；同时要按用户、租户和资源权限过滤，避免通过记忆或检索跨边界泄露数据。

### 7.4 缓存与版本

稳定的系统提示、工具定义和公共资料可利用缓存降低成本；但上下文组装应记录 Prompt、检索策略、记忆和摘要的版本。否则效果回归时，无法判断差异来自模型、上下文还是工具。

### 7.5 可观测性与评测

除总 Token 和响应时间外，还应观测：

- 每个槽位的 Token 占比与裁剪次数。
- 记忆/RAG 的召回、采纳和错误引用情况。
- 摘要是否遗漏关键约束或待办。
- 工具结果是否被正确消费，任务状态是否正确推进。
- 上下文策略变更后，对完成率、风险拦截率和成本的影响。

## 8. 常见组合与选型

| 场景 | 推荐组合 |
| --- | --- |
| 短问答助手 | 系统规则 + 当前请求 + 最近 N 轮对话。 |
| 长对话助手 | 最近对话 + 滚动摘要 + 必要的用户画像。 |
| 个性化助手 | 会话摘要 + 按需长期记忆召回 + 用户确认/校验后的记忆写入。 |
| RAG 问答 | 最近对话 + query rewrite + 检索、重排、裁剪后的证据。 |
| 任务型 Agent | 显式状态 + 最近对话 + 当前步骤所需证据 + 精简工具结果 + checkpoint。 |
| 多 Agent 系统 | 共享结构化状态与证据引用；每个角色按职责最小化读取上下文。 |

从实现成熟度看，通常会从“滑动窗口 + 摘要”起步，再加入检索记忆和 RAG；当出现多步执行、审批、中断恢复或副作用时，升级为“显式状态 + checkpoint + 按需上下文编译”的状态型 Agent。

## 9. 一句话总结

Context Engineering 的核心不是扩大模型输入，而是让正确的信息在正确的时机、以正确的结构和成本进入模型，同时让模型输出被安全地分流到对话、状态、事实、记忆和审计链路中。
