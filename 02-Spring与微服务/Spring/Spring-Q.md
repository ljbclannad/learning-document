## 1. Spring 容器的 `refresh()` 做了什么？为什么它是启动主线？

**答题要点：** `refresh()` 将容器从 BeanDefinition 准备状态推进到可用状态：准备上下文与 BeanFactory → 执行 BFPP/BDRPP → 注册 BPP → 初始化事件等基础设施 → 实例化非懒加载单例 → 发布刷新完成事件。顺序的目的，是先准备定义与加工规则，再创建业务对象。

- 基础阅读：[[Spring|《Spring》]] 的「9. Spring refresh」。
- 进阶阅读：[[Spring深度解析|《Spring深度解析》]] 的「源码/设计题」中 `refresh()` 阶段与失败处理。

## 2. 为什么要区分 `BeanFactoryPostProcessor` 与 `BeanPostProcessor`？

**答题要点：** BFPP 面向 BeanDefinition 与 BeanFactory，在实例化业务 Bean 前修改“图纸”；BPP 面向 Bean 实例，参与注入、初始化和代理等“加工”。二者对象和时机不同，因此必须分层。

- 基础阅读：[[Spring|《Spring》]] 的「9. Spring refresh」与「12. 依赖注入原理」。
- 进阶阅读：[[Spring深度解析|《Spring深度解析》]] 的「源码/设计题」中 BFPP/BPP 的职责与顺序。

## 3. 为什么要先准备基础设施 Bean，尤其是 `BeanPostProcessor`？

**答题要点：** BPP 是 Bean 创建流水线的一部分；如果业务 Bean 先创建，就会错过自动注入、初始化回调和 AOP 代理等增强。BFPP/BDRPP 同理，必须先完成定义补全，才能可靠地创建对象。

- 基础阅读：[[Spring|《Spring》]] 的「9. Spring refresh」。
- 进阶阅读：[[Spring深度解析|《Spring深度解析》]] 的「源码/设计题」中基础设施提前就绪的原因和故障现象。

## 4. 为什么循环依赖通常只支持单例的 setter/字段注入，构造器循环依赖为何难解？

**答题要点：** Spring 的解法依赖“先实例化、提前暴露早期引用、再填充属性”。setter/字段注入有这个窗口；构造器注入要求依赖在实例化前就完整，无法先得到可暴露的对象。三级缓存也围绕单例池工作，prototype 通常不适用。

- 基础阅读：[[Spring|《Spring》]] 的「1. 循环依赖」和「2. 三级缓存」。
- 进阶阅读：[[Spring深度解析|《Spring深度解析》]] 的「IOC/Bean 生命周期」中循环依赖的边界。

## 5. AOP 代理与循环依赖同时出现时，为什么需要三级缓存？

**答题要点：** 三级缓存保存的是按需生成早期引用的 `ObjectFactory`；真正发生循环依赖时，Spring 才能通过 `getEarlyBeanReference()` 生成可能带代理语义的早期引用，并保证其与最终 Bean 尽量一致。二级缓存只能保存已生成对象，缺少延迟生成和 AOP 早期介入的能力。

- 基础阅读：[[Spring|《Spring》]] 的「2. 三级缓存」。
- 进阶阅读：[[Spring深度解析|《Spring深度解析》]] 的「源码/设计题」中三级缓存、早期代理与引用一致性。
