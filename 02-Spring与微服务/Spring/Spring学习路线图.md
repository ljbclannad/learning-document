## 2. 先建立模型，再跟调用链

每学习一个机制，回答六个问题：它解决什么工程问题，核心状态存在哪里，谁在什么时机修改状态，什么条件会改变路径，失败后留下什么结果，怎样用最小实验确认。

源码阅读从入口、状态和分支出发，不要求先背完整类层次。看到一个接口先找调用方；看到一个缓存先找写入、清理和并发控制；看到一个注解先确认由谁解析、是否依赖代理。

## 4. Mini Spring 练习的边界

可分三步实现教学容器：

1. 用名字注册定义，以构造器参数解析依赖，检测创建中的循环路径并给出清晰错误。
2. 加入单例/原型边界、初始化与销毁回调、正反依赖索引，验证构造失败后的状态清理。
3. 用 JDK 代理实现简单拦截器链，测试前置、正常返回、异常与 finally 的嵌套顺序。

暂不追求复制 Spring 的全部缓存、注解解析、并发刷新和早期代理。练习的目的在于体会状态机、扩展时机和不变量；教学实现通过几个测试不代表可用于生产。

将自己的设计与真实 Spring 对照：为什么分离定义处理与实例处理，为什么工厂对象和产品分开，为什么发布早期引用会影响一致性，为什么资源清理应有统一入口。设计模式名称只能辅助描述，不能代替这些因果关系。

## 5. 项目练习与知识维护

以医生助手任务为贯穿案例：请求认证与参数校验 → 待确认任务保存 → 审批认领 → Outbox → 工作者执行 → 结果查询/推送。每条边标出线程、事务、代理、持久化与恢复责任。

至少推演重复审批、提交后进程退出、执行器拒绝、远程结果未知、SSE 断线五种情况。先说明用户看到什么、系统保存什么，再选择注解和组件。

阅读 [[07-项目复盘与方案/智能体重管理/医生助手Agent/医生助手Agent开发方案-代码实现|医生助手方案]] 与 [[07-项目复盘与方案/通用系统方案/RabbitMQ与Outbox可靠消息方案|Outbox 方案]] 时，将设计描述与实测事实分开。项目方案保留独立上下文，主文维护共通机制，发现问题在对应位置修正或标明边界。

建议最终留下三份实质产物：一张完整调用时序、一组能证伪错误理解的测试、一份故障恢复推演。无需为同一个机制再建立“基础版”“深入版”两套正文。
