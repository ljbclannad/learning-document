# Redis、RabbitMQ、RocketMQ 与 Kafka：消息队列对比与选型

> [!abstract] 先给结论
> 先回答消息是否允许丢失、是否会长时间堆积、下游是否需要复杂路由/回放/顺序/延时，以及团队能否承担相应运维复杂度。Redis 适合轻量短链路；RabbitMQ 擅长灵活路由与工作队列；RocketMQ 适合业务事件及顺序/延时/事务消息；Kafka 擅长高吞吐事件流、数据管道、流式计算和多消费组回放。吞吐结论应以自己的消息大小、分区数、持久化配置及消费逻辑压测为准。

相关笔记：[[03-数据存储与缓存/Redis/Redis生产高频专题|Redis Stream 生产专题]]、[[RabbitMQ/RabbitMQ|RabbitMQ]]、[[RocketMQ|RocketMQ]]、[[Kafka|Kafka]]。

> [!info] 版本边界
> Kafka 列以 Apache Kafka 4.3.x 的常规 Consumer Group 为主；Kafka 4.2 起 Share Groups 已可用于生产，工作队列场景见下文补充。RocketMQ 列以 5.x 为基线。

## 1. 比较前：先区分三种 Redis 用法

“用 Redis 做消息队列”必须说清具体数据结构，否则可靠性结论没有意义。

| Redis 能力 | 语义 | 是否适合关键业务消息 |
| --- | --- | --- |
| Pub/Sub | 在线订阅者收到实时广播；订阅者不在线即错过 | 否，适合缓存失效通知、在线状态等可丢事件 |
| List | 简单 FIFO；弹出后默认不保留 | 仅临时、可丢或能自行补齐确认/重试的任务 |
| Stream | 追加日志、消费者组、Pending（PEL）、`XACK`、认领未确认消息 | 可用于轻量可靠队列；仍要评估内存、持久化和故障切换边界 |

下文的“Redis”默认指 **Redis Stream**。若业务使用 Pub/Sub 或 List，应按上表降低可靠性预期。

## 2. 一张表建立整体判断

| 维度 | Redis Stream | RabbitMQ | RocketMQ | Kafka（常规消费组） |
| --- | --- | --- | --- | --- |
| 原生定位 | 内存 KV 系统的日志流能力 | 通用消息代理 | 持久化业务消息/事件系统 | 分布式事件日志与流处理平台 |
| 主存储 | 内存为主，RDB/AOF 持久化 | 依队列类型使用磁盘与复制 | 磁盘顺序写、逻辑索引 | 分区追加日志、磁盘与页缓存 |
| 消费模型 | 消费者组 + PEL + ACK | Exchange 路由到 Queue，竞争消费或多队列分发 | Topic 多队列 + Consumer Group 独立进度 | Topic 多分区 + Consumer Group 独立 offset |
| 保留与回放 | 可保留，需管理修剪与 PEL | 工作队列通常不作长期日志；Stream 队列可回放 | 按保留期保存，可按消费组进度回溯 | 按时间/容量保留或按 key 压缩；保留期内可重读 |
| 路由能力 | 以 key/Stream 组织 | Exchange + Binding，路由规则灵活 | Topic + Tag/属性过滤 | 主要依靠 Topic、key 和客户端处理；无 Exchange 式复杂路由 |
| 重试与失败隔离 | PEL 认领、死信 Stream 由应用编排 | ack/nack、DLX/DLQ 与策略组合 | Broker/消费组支持重试与 DLQ | 常规组需设计有界重试与隔离 Topic；Share Groups 支持逐条确认/重投 |
| 顺序 | Stream ID 有序；并发消费需约束 | 单队列 FIFO 有条件 | 单 MessageQueue / message group 内顺序 | 单 Partition 日志有序；并发处理仍要约束 |
| 延时能力 | 常用 ZSet/时间轮实现 | TTL + DLX 等方案，需关注版本/拓扑 | 原生定时/延时消息 | 通常借助调度器或应用层延时 Topic |
| 事务边界 | 无原生 MQ 事务消息 | 无原生跨本地事务可见性协议 | half message + 事务回查，服务于发布一致性 | Kafka 内多分区写入和消费位点可同事务；不涵盖外部数据库 |
| 大量积压 | 内存成本高，可能影响缓存 | 需评估队列类型、磁盘与流控 | 适合持久堆积与高吞吐事件流 | 适合高吞吐、保留和多组读取；积压不得超过保留窗口 |
| 运维关注点 | 内存、持久化、PEL、修剪 | 拓扑、队列类型、策略、磁盘 | NameServer、Broker、存储、复制、Topic/队列 | KRaft、Broker、分区/副本、ISR、保留期、lag |

> [!warning] 四者都不自动提供跨外部业务库的端到端 exactly-once
> 发送超时和“业务提交后、消费确认/位点提交前崩溃”都可能带来重复。关键业务应使用稳定 `event_id`、消费端 Inbox/唯一约束、状态机和对账补偿。Kafka 事务的 exactly-once 范围主要是 Kafka 到 Kafka；RocketMQ 事务消息解决上游发布一致性的一部分。

## 3. 从需求反推产品

```text
是否允许订阅者离线时丢消息？
  ├─ 是，且只做实时通知 ───────────────> Redis Pub/Sub
  └─ 否
      ├─ 已有 Redis、流量轻、短暂堆积、可接受自己治理 PEL/重试 ─> Redis Stream
      └─ 需要专业 MQ
          ├─ 强调复杂路由、每个订阅方独立队列、工作分发 ────────> RabbitMQ
          ├─ 业务事件，重视原生延时/事务消息、Broker 重试 ────────> RocketMQ
          └─ 大规模事件流/CDC/流计算、多组独立回放 ─────────────> Kafka
```

### 3.1 选择 Redis Stream 的条件

适合站内异步任务、缓存预热、轻量事件流：已有高可用 Redis 集群，消息量和最大积压都能在内存预算内，且团队愿意实现 PEL 巡检、`XAUTOCLAIM`、死信 Stream、长度修剪与消费幂等。

不适合 Redis 同时承担核心缓存/锁/计数器而消息可能大量堆积的情形；也不适合需要长期回放、复杂订阅路由、原生延时/事务语义或严格审计恢复的链路。

### 3.2 选择 RabbitMQ 的条件

适合一个事件需要按不同规则投递到多个下游、工作队列分发、按优先级或路由键灵活编排。例如“支付成功”同时进入发票、积分、通知等各自独立队列，且各订阅方的限流、重试与死信策略不同。

关键工作队列优先使用 quorum queue；发布端开启 publisher confirm 并处理不可路由消息；消费端手动 ack；重试必须有预算。它不是专门的长期事件日志，若主要诉求是海量保留与回放，应结合业务消息能力或流处理需求评估 RocketMQ、Kafka。

### 3.3 选择 RocketMQ 的条件

适合订单、交易、物流等大量事件持续写入；需要按消费组独立回放、分区顺序、定时/延时触发、Broker 级重试/DLQ，或需要事务消息协调本地事务与消息可见性。

关键决策是按业务并行度设计 Topic 队列数与 message group，设置保留期和磁盘容量，并将消费组、重试、死信、回放权限纳入治理。不要因为“有事务消息”就省略下游幂等和业务对账。

### 3.4 选择 Kafka 的条件

适合埋点、日志、CDC、实时分析和多个下游独立订阅的事件流，尤其当事件要在保留期内反复读取、由 Kafka Streams/Connect 等持续加工时。按业务 key 设计 Partition，控制副本、ISR、保留期与消费组 lag；重试、失败隔离和消费幂等需要明确实现。

Kafka 4.2 起 Share Groups 可提供更接近工作队列的逐条确认与分摊，但其语义与常规消费组不同。若需求主要是复杂路由、成熟的逐队列重试拓扑，仍应与 RabbitMQ 对照；若强调原生定时/延时和业务事务消息，则与 RocketMQ 对照。产品适用性由具体版本、客户端和团队治理能力决定。

## 4. 常见业务场景的推荐

| 场景 | 首选 | 原因 | 必要补充 |
| --- | --- | --- | --- |
| 缓存失效、在线配置通知 | Redis Pub/Sub | 极低延迟，离线消费者无需补历史 | 关键配置须有拉取/版本校验，不能只靠通知 |
| 少量异步任务、已有 Redis | Redis Stream | 少引入一套基础设施，具备消费组和 ACK | PEL 巡检、认领、死信 Stream、内存预算 |
| 多下游按规则分发 | RabbitMQ | Exchange + Binding 路由表达力强 | 每个下游独立队列、confirm、DLQ、幂等 |
| 高峰削峰、长时间消息堆积 | RocketMQ 或 Kafka | 两者的磁盘日志模型均能承接持久积压；按下游处理模型选 | 规划分区、磁盘、保留期和消费者扩容；不能超过保留窗口 |
| 同订单状态事件顺序处理 | RocketMQ | message group 支持细粒度局部顺序 | 以订单号分组、有限重试、状态机兜底 |
| 支付超时关闭、预约超时释放 | RocketMQ | 原生定时/延时消息 | 到期后条件更新，防重复与误关闭 |
| 业务事务成功才允许下游看见事件 | Outbox 优先；必要时 RocketMQ 事务消息 | 两者都服务最终一致，事务消息提供回查机制 | 消费端 Inbox、对账；不要双写两套事实来源 |
| 持久事件回放 | RocketMQ 或 Kafka | 两者都支持按消费组进度重读保留期内的消息 | 审计级长期归档仍应进入专用存储 |
| CDC、埋点、日志进入实时数仓 | Kafka | 高吞吐分区日志适合多个处理链独立读取 | 设计 key、分区、保留期、Schema 与下游 lag 告警 |
| 同一事件供多系统持续加工和回放 | Kafka | 不同消费组有独立位点，可在保留期内重读 | 回放前确认数据仍在、下游具备幂等能力 |

## 5. 容易做错的抉择

### 5.1 “Redis 已经有了，所以全部用 Stream”

基础设施少不等于总成本低。消息堆积会直接占用内存，与缓存命中率、锁和限流竞争资源；Stream 的 Pending 长期不清理也会形成隐患。若消息已是核心业务链路，应将容量隔离、恢复流程和可观测性一并算入成本。

### 5.2 “RabbitMQ 集群天然不丢消息”

集群不等于队列内容自动复制。关键消息要同时考虑 durable 对象、持久消息、合适的队列类型（如 quorum）、publisher confirm、手动 ack 与业务幂等。任何一层缺失都可能留下丢失或重复窗口。

### 5.3 “RocketMQ 事务消息可以实现 exactly-once”

它仅协调上游本地事务与消息的最终可见性；下游消费、数据库写入和外部调用仍会重试或重复。必须保留 Inbox、唯一约束和状态机。

### 5.4 “有顺序消息就不需要状态机”

重试、并发生产、分区扩展和人工回放都会挑战顺序假设。顺序用于减少乱序概率与简化处理，正确性仍应由带条件的状态迁移保证。

### 5.5 “Kafka 开启幂等或事务就能替代业务幂等”

生产者幂等处理同一生产者会话内的重试；Kafka 事务可把 Kafka 内的多分区写入及消费位点一起提交。应用重发、业务数据库和外部接口仍在该保证之外。订单、资金等链路仍需 Outbox/Inbox、状态机和对账。

## 6. 通用落地基线

1. 定义事件契约：`event_id`、业务主键、事件类型、版本、发生时间与 trace 信息。
2. 数据库事实与待发布事件通过 Outbox（或经过充分评估的 RocketMQ 事务消息）建立最终一致；Kafka 事务用于 Kafka 内处理链路时，应单独划定边界。
3. 发送失败或超时按“结果未知”处理；使用同一 `event_id` 重试。
4. 消费者在本地事务提交后才确认或提交位点；Inbox 唯一约束抵御重复。
5. 重试区分短暂与永久错误；设置次数、总时长、退避和最终去向。
6. 死信有告警、归因、修复与受控回放流程，不能无限积压。
7. 监控发送失败、积压年龄、消费失败、重试/DLQ、存储水位与业务对账差集。

## 7. 最终决策口诀

- **能丢的实时通知：**Redis Pub/Sub。
- **轻量、短链路、已有 Redis：**Redis Stream，但把它当需要治理的队列，而非缓存的附属功能。
- **路由复杂、任务队列多、订阅方差异大：**RabbitMQ。
- **高吞吐、可堆积、可回放、顺序/延时/事务能力重要：**RocketMQ。
- **海量事件流、CDC、流式计算、多组独立回放：**Kafka；工作队列场景还可评估 4.2 起的 Share Groups。
- **资金、库存、订单等关键链路：**产品选择之外，始终补齐 Outbox/Inbox、幂等、状态机与对账。
