# Nacos 项目实践：接入、灰度发布、摘流与故障恢复

> 本文沿用 `nacos场景题.md` 文件名以保持已有引用，正文按连续项目实践组织。原理集中在 [[Nacos]]，调用链与时间预算见 [[02-Spring与微服务/Spring/SpringCloud|Spring Cloud]]。
>
> 接入片段面向 Java 17、Spring Cloud Alibaba 2023.x 的 Config Data 方式与 Nacos 2.x Java SDK。需要按项目实际补丁版本验证配置绑定、监听和客户端实现。医院预约案例及参数为教学设计，不代表已部署或压测达标；核查日期：2026-10-28。

## 1. 先定义系统真正要保证的行为

以 Gateway、预约、排班和通知服务为例，Nacos 提供地址目录和配置分发。项目需要另外定义以下验收边界：

| 变化或故障 | 期望行为 | 不应做出的承诺 |
| --- | --- | --- |
| 新排班实例上线 | 就绪后逐步接流量 | 注册成功就代表所有业务可用 |
| 排班实例下线 | 发现视图收敛、存量操作可完成或恢复 | 控制台禁用后瞬间零请求 |
| 配置更新 | 完整校验后采用，失败保留已验证策略 | 收到通知就算所有实例生效 |
| Nacos 暂时断连 | 对允许旧值的业务继续运行并告警 | 所有新实例都能离线启动 |
| 错误配置发布 | 限定范围、拒绝或回滚、确认覆盖率 | 停止推送就恢复旧值 |

将这些边界写进发布平台和监控，才有依据判断一次配置变更是否完成。仅观察控制台状态无法覆盖业务执行事实。

## 2. 把接入坐标变成可核对的契约

### 2.1 环境和身份从部署系统注入

学习示例使用同一 namespace 下的 `MEDICAL_GROUP` 注册业务服务，避免跨业务 group 的调用方无意中查不到目标。配置单独使用 `APPOINTMENT_CONFIG`，说明注册与配置的 group 不需要相同，但各自的读写两端必须一致。

```yaml
# 预约服务的 application.yml 片段。
# 需配套兼容的 Nacos Discovery、Nacos Config starter 和 BOM。
spring:
  application:
    name: appointment-service
  config:
    import:
      - "nacos:appointment-policy.yaml?group=APPOINTMENT_CONFIG&refreshEnabled=true"
  cloud:
    nacos:
      discovery:
        server-addr: ${NACOS_SERVER_ADDR}
        namespace: ${NACOS_NAMESPACE_ID}
        group: MEDICAL_GROUP
        cluster-name: ${DEPLOYMENT_ZONE}
        username: ${NACOS_USERNAME}
        password: ${NACOS_PASSWORD}
      config:
        server-addr: ${NACOS_SERVER_ADDR}
        namespace: ${NACOS_NAMESPACE_ID}
        group: APPOINTMENT_CONFIG
        username: ${NACOS_USERNAME}
        password: ${NACOS_PASSWORD}
```

这里没有提供默认生产地址或凭据，部署时必须显式注入。`${NACOS_NAMESPACE_ID}` 应是控制台对应空间的 ID。真实生产隔离还需要独立权限、网络和必要的集群边界。

导入没有使用 `optional:`，表达该配置是必要依赖；但这不等于“必定绕过本地快照并只接受最新远端值”。是否允许快照、配置缺失时如何失败、过期值是否可用，还需客户端与应用共同校验。[SCA Config Data 接入说明](https://sca.aliyun.com/docs/2023/user-guide/nacos/advanced-guide/)

### 2.2 接入验收要从消费者看出去

发布一个实例后，依次确认：

1. 提供者记录实际 Server 地址、namespace、group、serviceName、注册 IP/端口及 SDK 版本。
2. Nacos 中资源存在，临时/持久类型符合预期，没有注册到错误空间。
3. 消费者能发现该实例，记录筛选前后数量、区域和版本信息。
4. 从消费者网络访问实例业务端口，确认路由、容器地址及防火墙正确。
5. 使用业务请求验证服务就绪，再允许扩大流量。

诊断日志不打印密码、令牌、患者信息或配置全文。必要的版本、坐标和非敏感摘要足以关联多数问题。

### 2.3 锁定版本与实例选择实现

记录 Boot、Cloud、SCA、Nacos Client、Nacos Server 的实际版本，不只记录 `pom.xml` 中直接声明的版本。运行时依赖可能被其他 BOM 或 starter 改写。

同时记录 HTTP 客户端、LoadBalancer 实现、Supplier 链和缓存层。若期望按 Nacos 权重或同区域优先选实例，使用一组可区分实例做采样，验证实际分布；只修改 metadata 不能作为实现证据。[LoadBalancer 4.1 机制](https://docs.spring.io/spring-cloud-commons/reference/4.1/spring-cloud-commons/loadbalancer.html)

## 3. 动态配置采用一个完整策略

### 3.1 参数必须满足共同约束

预约服务调用排班查询时，假设策略包含单次尝试预算、重试次数、调用总预算和最大并发。下例数值仅用于说明字段约束：

```yaml
policy:
  generation: 12
  releaseId: "appointment-policy-20261028-12"
  attemptTimeoutMs: 300
  maxRetries: 1
  totalBudgetMs: 800
  maxConcurrent: 40
```

两次尝试的最小时间占用为 600ms，总预算 800ms 还需为退避和本地开销留余量；配置校验通过不代表整个调用已经满足预算，执行层仍须逐次检查剩余时间，并限制排队与连接等待。

不要给支付写操作照搬查询重试次数。即使参数合法，重试资格仍取决于接口幂等契约和结果查询能力。

### 3.2 Java 示例：拒绝坏策略和乱序覆盖

下面是可独立编译的 Java 17 核心类，保存为 `PolicyStore.java`。它不连接 Nacos；监听适配器负责把完整配置解析成 `Policy`，校验失败时记录拒绝原因，不能先修改正在使用的字段。

```java
import java.util.Objects;
import java.util.concurrent.atomic.AtomicReference;

public final class PolicyStore {
    public record Policy(long generation, String releaseId, int attemptTimeoutMs,
                         int maxRetries, int totalBudgetMs, int maxConcurrent) {
        public Policy {
            Objects.requireNonNull(releaseId, "发布标识不能为空");
            if (generation <= 0 || releaseId.isBlank()) {
                throw new IllegalArgumentException("发布代次与标识无效");
            }
            if (attemptTimeoutMs < 50 || attemptTimeoutMs > 2000
                    || maxRetries < 0 || maxRetries > 2
                    || totalBudgetMs < 100 || totalBudgetMs > 5000
                    || maxConcurrent < 1 || maxConcurrent > 200) {
                throw new IllegalArgumentException("参数超出示例允许范围");
            }
            long minimumBudget = (long) attemptTimeoutMs * (maxRetries + 1);
            if (minimumBudget > totalBudgetMs) {
                throw new IllegalArgumentException("尝试预算超过总预算");
            }
        }
    }

    private final AtomicReference<Policy> active;

    public PolicyStore(Policy initial) {
        active = new AtomicReference<>(Objects.requireNonNull(initial));
    }

    public Policy snapshot() {
        return active.get();
    }

    public boolean install(Policy candidate) {
        Objects.requireNonNull(candidate);
        for (;;) {
            Policy previous = active.get();
            if (candidate.generation() < previous.generation()) {
                return false;
            }
            if (candidate.generation() == previous.generation()) {
                if (!candidate.equals(previous)) {
                    throw new IllegalArgumentException("同一发布代次的内容不一致");
                }
                return false;
            }
            if (active.compareAndSet(previous, candidate)) {
                return true;
            }
        }
    }
}
```

一次请求开始时调用 `snapshot()`，把返回的不可变对象保存到本次调用上下文，后续始终使用它；不要在每读取一个参数时重新取引用。新请求看到新策略，已经开始的请求继续使用原策略，避免一条调用中途混用两个版本。

`generation` 是**应用发布协议**，不是 Nacos 自带的递增版本保证。发布平台必须为同一配置维护唯一、单调递增的代次，且同一代次内容不可变。多发布者需要串行化或可靠的竞争控制，单纯用各机器的时间戳不能保证顺序。

回滚旧内容时应分配更大的 generation 和新的 releaseId，否则会被当作乱序回调拒绝。该类只保证单 JVM 的内存切换，不保证多实例同时采用，也不持久化重启后的代次；若需要防止重启后回退，还需可信的持久化发布状态和启动校验。

### 3.3 收到配置、采用策略和资源生效分别报告

业务监控应在成功 `install` 后从当前快照读取生效标识；收到通知时可单独记录 received 标识。拒绝候选时，保留 active 标识并增加拒绝计数。高频发布的 releaseId 更适合日志或受控诊断端点，避免长期指标标签无限增长。

这段示例没有实现限流器、HTTP timeout 或连接池切换。策略中的 `maxConcurrent` 更新后，实际执行器仍需消费它；如果资源调整失败，不能宣称相关资源已经采用新值。

连接池等资源应采用“创建并验证候选资源 → 切换新请求入口 → 排空旧资源 → 关闭旧资源”的专用流程，或在受控滚动重启中更新。不能仅用 `@RefreshScope` 重建就假设存量事务安全。

## 4. 灰度：分别控制配置、实例与请求

### 4.1 使用独立配置限定首批影响范围

准备稳定配置 `appointment-policy.yaml` 与灰度配置 `appointment-policy-canary.yaml`。仅灰度部署组在启动时导入后者；稳定组仍订阅原配置。两者应共享 schema 和字段约束，发布后比对业务指标与生效版本。

这一方案可以避免坏文本被所有稳定实例同时解析，但会产生配置分叉。灰度完成后，按受控流程将已验证内容发布到稳定坐标，并在不再有订阅者后清理临时配置；不能长期维护多份无人确认的副本。

另一方案是在单个 dataId 中携带两组策略，由应用按可信实例标识选择。它减少配置副本，却扩大了文本解析范围，必须验证一个分组非法时不会拖垮另一分组。

### 4.2 请求灰度要保持用户和链路稳定

入口可以按经过认证的用户或租户标识进行稳定分桶，而不是每次随机掷骰子。选中的灰度标识经过可信传播进入预约服务及排班调用，候选筛选才有机会保持链路版本一致。

“5% 实例”不一定获得“5% 请求”；实例权重、连接复用、用户分布和请求成本都会影响实际比例。观察目标实例上的真实请求量、业务成功率和依赖压力，再决定扩大范围。

灰度集合为空时必须提前确定行为：允许回稳定版本、拒绝新请求，或由业务策略决定。对数据格式不兼容的写链路，静默回稳定版本可能比显式失败更危险。

### 4.3 不把标签当成配置订阅协议

Nacos Naming metadata、Kubernetes label 和 Config 发布标签不是天然贯通的同一机制。若采用内置 beta/tag 灰度，应针对目标 Server/Client 验证匹配条件、扩容后命中、重连后的配置、撤销灰度以及稳定配置覆盖行为。

没有验证这些路径时，独立坐标加部署编排更容易说明边界，但仍要维护配置差异和回收流程。选择哪种方案由隔离要求和平台能力决定，不存在始终最优的单一方案。

## 5. 优雅下线：控制面摘流与业务排空协作

### 5.1 发布过程是一条状态链

```text
运行 → 进入排空 → 取消可发现/可就绪状态 → 观察新流量收敛
    → 等待存量完成或持久记录恢复点 → 关闭资源 → 退出
```

发布系统通过实际接入能力禁用或注销实例，并调整入口就绪状态；同时让应用进入排空状态。控制面操作失败时，不能继续假定已经摘流并立即关闭数据库连接。

`weight=0` 只有在算法尊重权重时才有相应效果；`enabled=false` 或注销仍受消费者缓存影响。必须记录各消费者最后选中时间，而不是只设置固定等待几秒就认为完成。

### 5.2 存量请求不只是 HTTP 连接

还包括正在提交的数据库事务、MQ 消费、定时任务和异步线程。关闭顺序应让业务先停止获取新工作，再等待或记录已有工作的恢复状态，最后关闭其依赖资源。

到达排空截止时间后，也应区分只读查询、可重放任务和结果未知的写操作。强制退出前是否有幂等键、预占凭证或持久任务记录，决定重启后能否恢复。

新实例上线同样要有就绪门槛。SDK 重连后可能执行 redo，管理操作与应用自身生命周期要协调，避免“平台刚摘流，进程又恢复注册”的状态竞争。

### 5.3 用时间线验证下线窗口

记录 `开始摘流`、`Server 视图变化`、`消费者视图变化`、`最后一次新请求`、`存量完成`、`进程退出`。使用多消费者和持续流量，分别验证正常关闭与进程异常退出；后者依赖故障检测，不能复用前者的时序保证。

## 6. 四类故障，按证据定位

### 6.1 控制台可访问，SDK 注册失败

先查看具体异常属于 DNS、连接、鉴权还是服务类型冲突。确认客户端配置的是主端口，再检查派生 gRPC 端口可达性及代理转发；只打通 8848 无法证明 9848 正常。[Nacos 2.x 部署端口](https://nacos.io/en/docs/v2.5/manual/admin/deployment/deployment-overview/)

网络通过后，再查 namespace ID、group、已有服务的 ephemeral 类型和实例地址。不要通过不断重启应用或盲目增加超时掩盖明确的坐标错误。

恢复标准是注册稳定、消费者能发现并访问，而不是启动日志中的异常暂时消失。

### 6.2 实例频繁消失又恢复

gRPC 临时实例重点关联连接断开、redo、Full GC、CPU、Server 负载、代理空闲连接策略和网络时间线；HTTP 兼容实例才进一步核对心跳发送与阈值。持久实例则查看主动探测结果和管理操作。

若所有实例同一时刻抖动，优先排查共同依赖；若只有某一进程抖动，先检查该进程暂停和网络路径。增加心跳阈值可能减少误判，也会延长真实故障保留时间，必须有证据支持调整。

故障期间只保留符合预算的受控重试；不能一边下游不稳定，一边让所有调用层扩大尝试次数。

### 6.3 发布成功，但部分实例仍用旧值

按下面的观测链推进，每一步确认后再进入下一步：

| 层次 | 应核对的证据 | 下一步 |
| --- | --- | --- |
| 发布坐标 | namespace、group、dataId、内容发布号 | 排除改错配置或格式 |
| SDK 查询 | 连接状态、读取发布号、本地覆盖来源 | 定位断连、快照或 failover |
| Spring 环境 | 最终属性值及其来源 | 排查更高优先级属性源 |
| 业务策略 | active/received 标识、校验拒绝原因 | 排查绑定、解析和应用逻辑 |
| 实际资源 | 客户端超时、池容量、路由目标 | 排查值变化但资源未重建 |

主动 `getConfig` 成功只证明查询路径可用，不证明原监听已恢复，也不证明某个业务对象采用了新值。重启同样不是第一步：若原因是错坐标或坏快照，重启只会重现问题。

### 6.4 Nacos 不可用，但业务部分正常

分别观察已有进程、新启动实例、扩容实例和冷启动实例。有内存视图的进程可能继续调用；新实例可能既缺关键配置又缺服务地址。

先冻结不必要的发布和扩缩操作，保留已有缓存，保护业务资源，并修复 Server、数据库或网络故障。不要为了“全部刷新”同时重启所有客户端。

恢复后核对重连、redo、实例视图和业务配置版本；再逐步恢复发布，退出紧急 failover。仅有 Server 健康探针恢复不能作为事故结束标准。

## 7. 坏配置回滚：恢复策略，不掩盖副作用

### 7.1 先判断应该收紧什么

超时变短造成重试骤增时，不应机械地把超时调得很大。先确认是正常耗时被误伤，还是下游已经过载；结合总预算、并发和重试，恢复已验证策略。盲目加长超时会增加线程与连接占用。

限流阈值过高时可收紧入口；连接池配置过大时需平衡存量连接与数据库容量；身份或权限错误可能要求立即拒绝相关请求。这些动作有不同的恢复时限，不能统一随机延迟 30 秒再应用。

### 7.2 回滚也要版本化和校验

从可信发布记录取回已验证内容，确认与当前代码兼容，分配新的发布代次。先对适当范围确认解析和应用成功，再根据风险扩大；对紧急安全或资金相关开关，需要预先定义更快的处置路径。

停止推送只能阻止更多实例接收，不会把已采用新值的实例恢复。回滚内容也不能撤销已经发出的支付请求或已落库的数据，业务对账和补偿必须独立推进。

### 7.3 避免资源重建风暴

普通策略引用切换成本低，连接池、TLS 客户端等资源重建却可能让大量实例同时建立新连接。资源类变更应分批发布，限制切换速率，观测数据库连接、TLS 握手和客户端排队。

只有在业务允许延迟、版本顺序可控时才使用错峰；异步回调必须防止旧版本后到并覆盖新版本。若客户端长期未收敛，先查原因，再执行受控刷新或滚动重启，并确认冷启动所需配置可获得。

## 8. 容灾准备必须包含冷启动和数据恢复

### 8.1 制定旧值使用策略

为配置记录负责人、敏感级别、是否可动态变更、是否允许旧值、可容忍陈旧时间、独立来源和恢复方式。业务允许展示旧医生简介，不代表允许继续使用已撤销支付渠道或过期鉴权材料。

SDK snapshot 不等于应用验证通过的 last-known-good。若应用需要后者，应完整校验后持久化，记录发布代次与摘要，限制文件权限，并在启动时再次校验，而不是直接恢复一个曾经下载成功的文本。

### 8.2 备份与高可用分别验证

多节点 Server 提供的可用性不替代配置数据库备份；外部数据库主备也不替代恢复演练。应在隔离环境验证配置、认证及必要管理数据的恢复，确认对应版本的 schema、插件和权限兼容。

Nacos 节点应跨合适故障域部署，同时保证协议网络与延迟满足要求。恢复节点时保留身份和一致性协议相关数据的处理依据，不把删除 Raft 数据目录当作通用修复命令。

## 9. 验证流程与可观察结果

### 9.1 本地策略实验

从第 3 节提取 Java 类编译，可独立验证：合法配置采用；越界字段拒绝；组合预算非法拒绝；相同代次不同内容拒绝；重复通知不重复采用；旧回调不能覆盖新策略；回滚旧内容使用新代次；并发读取不出现字段混合。

2026-10-28 使用 Java 17 从本文提取代码，完成编译并通过 **8 组策略语义验证**，包括两个写线程、四个读线程的并发场景。这些实验验证的是应用层原子采用逻辑，不验证 Nacos 监听、Spring 绑定、资源重建或集群行为。

### 9.2 隔离环境中的集成演练

以下步骤只在可控制的测试实例执行；记录版本、故障注入方式、时间线、业务结果和恢复耗时。每项结束后恢复基线再进入下一项。

| 场景 | 注入方式 | 观察及验收 |
| --- | --- | --- |
| 注册端口异常 | 阻断测试客户端的 gRPC 路径 | 能区分控制台可达与 SDK 不可达，恢复后完成注册订阅 |
| 消费者旧视图 | 下线单实例并持续查询 | 记录最后命中时间，验证多层缓存和失败预算 |
| 配置解析失败 | 发布无效类型或缺失必填项 | active 策略不变，明确记录拒绝，修正后可恢复 |
| 快速连续发布 | 连续发布两个不同代次 | 最终采用较新代次，无旧回调覆盖 |
| 冷启动断连 | 新实例没有历史缓存时断开 Nacos | 按预设策略失败或进入受限模式，不误连默认环境 |
| 快照包含坏内容 | 业务拒绝配置后重启测试实例 | 不把 SDK 快照直接当作可信业务策略 |
| 灰度集合为空 | 移除灰度测试实例 | 触发事先定义的回退或拒绝，不随机越界 |
| 正常下线与崩溃 | 分别排空和异常退出测试实例 | 分别记录摘流与检测窗口，业务写入可恢复 |
| 回滚与资源切换 | 回滚测试参数并分批调整资源 | 新代次覆盖、资源采用有证据，无连接突增 |

截至 2026-10-28，本轮维护验证范围为文档结构、链接、配置片段语法及独立 Java 策略示例；上述 Nacos/Spring 多进程演练未执行，不能据此宣称集群故障恢复已通过。

## 10. 用一条业务时间线完成交付

一次配置发布的交付记录至少包含：目标坐标与范围、代码/配置兼容条件、发布代次、各实例采用结果、业务指标变化、回滚版本以及未收敛实例的处置。

一次发现故障的交付记录则包含：注册状态、SDK 连接、消费者最终视图、实际调用目标、业务结果和恢复路径。把这些证据串起来，才能区分控制面故障、数据面故障和业务状态不确定，避免只留下“重启后好了”。
