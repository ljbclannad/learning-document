# Sentinel 项目实践

项目中的限流设计从瓶颈和业务结果开始：保护哪段容量，拒绝发生前是否已产生副作用，拒绝后谁负责恢复。规则只是把这些决定落实到请求路径。

本文沿用 [[Sentinel]] 的 Java 1.8.6 源码语义。医疗、支付和租户案例均为设计推演，数字是计算示例，不代表已有项目实测容量或真实事故。持久化与发布流程见 [[Sentinel规则与运维]]。

## 1. 先把挂号链路拆成可解释的资源

一次挂号可能经过排班查询、号源预留、支付提交、支付回调、医保结算和通知。它们的瓶颈、可重试性及优先级不同，不应共用一条 `/api/**` 预算。

| 业务动作 | 资源示例 | 主要瓶颈 | 保护失败后的语义 |
| --- | --- | --- | --- |
| 查询排班 | `schedule:query` | 缓存回源、数据库读 | 允许时返回注明时效的旧数据 |
| 提交挂号 | `appointment:create` | 连接池、号源竞争 | 未受理则明确拒绝，重试保留幂等键 |
| 调用医保 | `insurance:settle` | 外部配额、慢调用 | 区分未调用与结果未知 |
| 接收支付回调 | `payment:notify` | 验签、可靠落库 | 已持久化后才按协议确认接收 |
| 查询支付状态 | `payment:query` | 轮询放大、第三方查询 | 缓存或稍后查询，不伪造终态 |
| 导出报表 | `report:export` | CPU、数据库扫描、I/O | 返回任务标识或明确繁忙 |

号源是否超卖仍需要数据库条件更新、可靠预留或其他原子约束。把挂号入口设为 1000 QPS，并不意味着库存 1000 就安全：持续多秒、重复请求、其他写入口都会突破这个错误推理。

## 2. 容量预算必须同时看实例与共享依赖

### 2.1 单实例安全区间如何得到

在代表性数据与依赖条件下，记录阶梯负载中的吞吐、P95/P99、错误、连接等待、CPU 和 GC。稳定容量是满足目标质量时的持续处理能力，不是短时间压测的最大 QPS。

假设一个实例在 600 次/秒时 P99 满足目标，750 次/秒时连接等待急剧上升，可先选择更保守的阈值灰度。但“乘 0.7”只是可能的初始余量，不是 Sentinel 的算法或普适最佳值。

平均在途量可以帮助估算并发边界，但平均值不能代表长尾。若资源平均耗时 80ms、预计 500 次/秒，平均在途约 40；实际并发阈值要结合耗时分布、连接池分配与其他资源竞争压测，不能只把 40 直接设为上限。

### 2.2 从共享依赖反推入口

假设三方允许总共 600 次/秒，为回调补查和补偿预留 100 次/秒，在线提交预算剩 500。一次入口请求平均产生 1.2 次三方尝试，则入口理论预算不应超过：

```text
500 / 1.2 ≈ 416 次/秒
```

还要扣除重试、探测、后台任务和流量倾斜的余量。扩容应用只增加本机处理能力，并不会增加第三方配额；自动扩容若同时把本地预算成倍扩大，可能更快压垮共享依赖。

### 2.3 网关规则通常也是每实例生效

两个网关实例各配 `count=500`，不能直接称作“网关集群总共 500”。要说明是实例保护、近似均分，还是经过集群判定的共享预算。

网关承担入口洪峰和低成本拒绝；业务资源保护具体方法与下游；连接池和执行器提供硬资源边界。局部阈值必须低于该实例实际安全能力，不能为了“比网关宽松”而越过本机安全线。

若同一批请求中网关拒绝 30%，业务层再拒绝剩余请求的 20%，则最终通过 56%，拒绝 44%。该乘法要求同一人群、同一时间范围且无新增重试；不能拿两个独立看板的百分比直接相乘。

## 3. 编程埋点：入口、业务和退出缺一不可

### 3.1 一个可编译的同步查询包装

下面代码仅依赖 `com.alibaba.csp:sentinel-core:1.8.6`。它将拒绝、业务异常与成功分开；业务函数由调用者注入，不包含真实 HTTP 客户端。资源使用 OUT，表达依赖调用，不重复计为系统入口。

```java
import com.alibaba.csp.sentinel.Entry;
import com.alibaba.csp.sentinel.EntryType;
import com.alibaba.csp.sentinel.SphU;
import com.alibaba.csp.sentinel.Tracer;
import com.alibaba.csp.sentinel.slots.block.BlockException;
import com.alibaba.csp.sentinel.slots.block.RuleConstant;
import com.alibaba.csp.sentinel.slots.block.flow.FlowRule;
import com.alibaba.csp.sentinel.slots.block.flow.FlowRuleManager;
import java.util.Collections;
import java.util.function.Supplier;

public final class ProtectedQuery {
    private static final String RESOURCE = "schedule:query";

    public static void installDemoRule() {
        FlowRule rule = new FlowRule(RESOURCE);
        rule.setGrade(RuleConstant.FLOW_GRADE_QPS);
        rule.setCount(20);
        // 仅用于独立演示：该操作会替换进程内整个普通流控规则集。
        FlowRuleManager.loadRules(Collections.singletonList(rule));
    }

    public static String execute(String hospitalId, Supplier<String> query) {
        Entry entry = null;
        try {
            entry = SphU.entry(RESOURCE, EntryType.OUT, 1, hospitalId);
            return query.get();
        } catch (BlockException ex) {
            return "查询暂不可用，请稍后重试";
        } catch (RuntimeException ex) {
            // 必须在退出前，将业务错误记录到本次 Entry。
            if (entry != null) {
                Tracer.traceEntry(ex, entry);
            }
            throw ex;
        } finally {
            if (entry != null) {
                entry.exit(1, hospitalId);
            }
        }
    }
}
```

这不是 Web 接口的完整返回契约。HTTP 层应根据业务定义映射 429、503 或明确标注的缓存结果，不应把中文字符串作为所有接口的通用协议。热点规则需要额外模块与 ParamFlowRule；仅把参数传进去并不会自动启用热点控制。

如果用了 try-with-resources，需注意错误追踪位置：在外层 catch 才追踪时，资源可能已经关闭。上例显式 finally 的目的，是让 `Tracer.traceEntry` 发生在 exit 前，避免记录到错误的上下文或错过完成统计。

### 3.2 AOP、事务与异步边界

方法注解需要代理拦截。跨 Bean 调用与同类自调用应分别验证；资源名也可能由 Web、Feign、Dubbo 适配器生成，不能把服务名猜成真实 RPC 资源名。

若 Sentinel 切面位于事务之外，事务代理先看到异常并回滚，外层再兜底；若 fallback 在事务代理内部吞掉异常，事务层可能看到正常返回。不要在核心写方法上随意吞异常，必须验证实际 advisor 顺序和数据库最终状态。

`CompletableFuture` 或 `Mono` 的创建不代表业务完成。普通方法切面可能只包住返回对象的过程；应使用适合的异步/Reactive 适配器，在完成、失败和取消时释放 Entry，并正确记录错误。不要在 `finally` 中立刻 exit 后宣称整个异步调用受并发保护。

## 4. 挂号高峰：保护热点，保留正确性约束

### 4.1 总量与单医院预算各自负责什么

资源总规则控制整体容量，医院或医生参数规则控制局部占用。总规则 500、每医院默认 50，并不意味着每家医院都得到保底 50；先到流量仍可能用完总预算。

大型医院正常高峰明显高于小医院，可以为少量稳定医院配置例外阈值，或按业务等级分资源。若把所有三甲医院归成一个参数值 `TERTIARY`，它们共享的是等级预算，不是每医院各有预算。需要个体配额时仍要保留医院身份。

客户端提交的医院 ID 应经过身份与业务归属校验。空值不能直接传给热点规则后认为已被保护；大量随机 ID 则需要总量规则和身份控制兜底。

### 4.2 减少热点不等于减少所有回源

医生排班数据可以短期缓存，热点 miss 可使用合并加载与有界回源，前提是允许的时效已定义。限流后 fallback 再无条件查询数据库，等于绕过原规则，把被拒绝流量重新压向瓶颈。

对可接受旧数据的查询，返回数据时间和降级标记；号源可用量的展示不应作为最终购买承诺。正式预留在写路径检查原子约束，预留失败返回明确业务结果，不伪造挂号成功。

## 5. 支付与医保：不能把不确定性包装成成功

### 5.1 三种状态必须区分

| 事实 | 可以对外表达什么 | 恢复动作 |
| --- | --- | --- |
| 在发起外部调用前被阻断，且没有可靠任务 | 暂未受理 | 同一幂等键退避重试 |
| 请求可能已送达，但响应超时 | 结果未知、需查询 | 按业务流水查询、对账，避免盲目再次扣款 |
| 本地事务已保存待处理任务及必要状态 | 已受理、处理中 | 后台任务重试，提供查询与失败终态 |

仅仅进入 fallback 不满足第三行条件。若准备返回“处理中”，必须先可靠保存能恢复的业务事实，并定义执行者、重试上限、过期与人工处理路径。保存失败时也不能继续返回“已受理”。

### 5.2 资源应该包住一次实际依赖尝试

将医保结算、状态查询、撤销分别建资源，更容易区分它们的配额与风险。对每次调用设连接和响应超时；慢调用与异常熔断只负责减少后续尝试。

内层重试若在单个 Entry 内执行三次，Sentinel 看到的是一次长调用，而第三方已承受三次请求。若目标是限制真实调用量，应在每次尝试处埋点，并同时约束整个业务操作的重试预算。

客户端、网关、服务、SDK 都独立重试时，负载可能成倍放大。选定责任层，采用有上限的退避与抖动，保留同一业务幂等键；结果未知的写操作先查询再决定下一步。

### 5.3 熔断恢复也要留预算

下游刚恢复时，积压补偿、用户重试和多个实例探测可能同时到来。恢复阶段限制补偿并发与速度，保留在线与回调预算；不要把所有待处理记录一次性放进无限队列。

紧急停用依赖应使用已设计的业务开关或显式拒绝策略。把异常比例阈值调低仍需要实际异常完成样本，不是立即执行“强制打开熔断器”。也不能引用不存在的公开 `CircuitBreaker.reset()` API 作为标准运维手段。

## 6. 支付回调：独立通道还需要可靠接收

回调与用户轮询应使用独立路由、资源、连接和必要的执行预算。只拆资源名，却共享已耗尽的数据库连接池，仍无法保证回调可用。

典型处理顺序是：身份/签名与请求合法性校验 → 按平台通知号或业务流水幂等落库 → 提交接收事务 → 按平台协议应答 → 异步执行后续动作。每一步都需要适当超时和容量控制，不能把“核心通道”解释为完全无限制。

数据库提交成功但应答丢失时，上游会重复通知，唯一键和状态机保证重复请求不会重复入账。数据库尚未可靠记录就回复成功，可能导致平台停止重试，从而丢失业务事实。

回调拒绝后的响应必须遵循支付平台约定，不能机械地全部改成 429 或 200。平台是否重试、重试多久、是否支持主动查询，都决定补偿与告警设计。

## 7. Gateway：规则对象、请求身份与异步生命周期

### 7.1 路由与 API 分组

`GatewayFlowRule` 的 resource 可以是 route ID 或自定义 API 分组。使用分组时，要同时加载 `ApiDefinition` 与匹配它的规则；只写一个分组名不会自动把 URL 归进去。

```json
[
  {
    "resource": "payment-query-route",
    "resourceMode": 0,
    "grade": 1,
    "count": 100,
    "intervalSec": 1,
    "controlBehavior": 0,
    "burst": 0
  }
]
```

这是 1.8.6 网关规则形状的示例，表示单网关进程上的路由预算，不包含租户参数，也不是全局集群配额。`intervalSec`、`burst` 与普通 FlowRule 字段不同，Nacos 数据源类型应与 Gateway 规则匹配。

Path 重写、StripPrefix、过滤器顺序与 API 分组的匹配点有关；用真实请求确认到底命中了哪个 route、哪个分组。多个匹配分组可能叠加，不能认为命中一个就跳过其他保护。

### 7.2 参数值代表谁，必须先可信

Header 或 URL 参数可以成为规则维度，但 `tenantId`、VIP 标记和转发 IP 都可能由客户端伪造。应先由可信入口认证，再提取或覆盖内部身份字段；NAT 下多人共用 IP，也会造成不合理的共享预算。

不要对每个陌生 IP 动态添加一条规则。它会让请求路径执行配置变更、放大规则规模，并与配置中心整组替换互相覆盖。需要防刷时使用有限的身份或风险等级，加上总量保护；限流不替代 WAF、认证与授权。

### 7.3 适配器应覆盖订阅到终止

Gateway 是 Reactive 链路，应使用兼容版本的 Sentinel Gateway 适配器，让 Entry 生命周期对应真正请求完成。同步调用 `SphU.entry`、返回 `Mono` 后立即 finally exit，会过早结束统计。

网关的 BlockRequestHandler 与 Servlet 的处理器签名不同，不能互相复制。HTTP 超额可以返回 429，依赖不可用可以按契约表达 503；是否给 Retry-After 取决于是否有可信的恢复时间。对外响应不必暴露内部阈值，日志则保留层级、资源和请求标识。

规则模型参考：[网关流量控制](https://sentinelguard.io/zh-cn/docs/gateway-flow-control.html)。

## 8. 多租户与集群预算

### 8.1 共享预算与资源公平是两件事

共享 Token Server 可以减少本地预算闲置，但不自动保证租户公平，也不保证租户 A 的突发不影响 B。需要按有限、稳定的租户或业务等级定义预算，并评估总预算之间是否超订。

不要把每个新用户拼成资源名。对于高价值、需要严格记录的日/月额度，应使用持久化配额账本；Sentinel 热点状态可被淘汰，Token Server 的内存窗口也不能承担该账本职责。

### 8.2 故障回退必须算最坏情况

假设正常全局规则 count=600，10 个实例在集群故障后回退到同一 FlowRule 的本地检查；不能凭配置名称推断每台自动变成 60。按本地路径仍为 600 的情况估算，整体保护可能放宽到每实例各一份预算。

可以另设稳定的本地保护资源限制单机冲击，但静态本地上限又会影响正常共享配额的利用率，需要明确取舍。对严格第三方配额，故障时阻断的行为必须由真实实现验证；1.8.6 的 `fallbackToLocalWhenFail=false` 是相关失败路径放行，不是拒绝。

多个 Token Server 应明确资源归属、客户端分配及迁移期间预算，不能把复制状态未实现的独立进程当作主从集群。Server 重启、分配切换和网络分区都要进入验收场景。

## 9. 报表与消息消费：等待应在哪里发生

报表任务适合先持久化任务，再由有界消费者执行。任务表或消息队列负责排队、失败恢复与状态查询；Sentinel 控制消费速率，不替代持久化队列。

消息消费限流后如何处理消息取决于消费协议：不能因为没有执行就确认成功；立即重新入队也可能形成高频重投。应结合延迟重试、消费者暂停、有限批次和幂等，避免耗尽消费线程。

在线调用中，排队等待会消耗 HTTP 连接和业务 deadline。执行器的 CallerRunsPolicy 还可能把后台工作压回 HTTP 或事件循环线程，破坏隔离。队列大小、拒绝方式与调用线程模型必须一起设计，不能照搬“CPU 核数乘二”作为固定容量。

## 10. 按业务结果验收保护效果

工程验收是证明运行行为，不是背诵配置。应在隔离环境对每个关键资源记录“输入 → 实际是否执行业务 → 数据库状态 → 返回语义 → 指标”的证据。

| 场景 | 必须确认的结果 |
| --- | --- |
| 前置阻断 | 受保护业务函数确实未执行，未新增订单或发起扣款 |
| 异常被 catch 转为返回值 | 是否仍按设计记录异常，业务失败不被当作成功 |
| 代理自调用与外部调用 | 两条路径的埋点差异可解释 |
| 参数缺失、类型不同、长尾值激增 | 校验、例外项与总量保护仍符合设计 |
| 下游卡住与超时 | 并发有界，不等待熔断样本才保护 |
| 半开、恢复及补偿积压 | 探测和恢复流量不会形成第二波洪峰 |
| 网关重写路径及异步取消 | 资源匹配正确，Entry 不提前退出也不泄漏 |
| 事务提交成功但响应丢失 | 同一幂等键再次调用不会重复业务副作用 |
| 集群服务缺失、超时、重启 | 实际通过量与故障策略一致 |

本轮完成 core 包装代码的编译与定向验证，以及主文记录的 8 组单 JVM 语义实验。上述网关、数据库事务、真实第三方和多进程场景是项目验收要求，未在本轮执行；所有示例阈值仍需项目压测校准。
