# Sentinel：规则持久化与运维

## 1. 规则来源

Dashboard 的规则编辑适合演示和临时操作，但规则默认驻留在应用内存；应用重启后不会自行恢复。生产环境应通过 Nacos、Apollo、ZooKeeper 或自定义 `ReadableDataSource` 作为规则事实来源。

Nacos 示例：

```yaml
spring:
  cloud:
    sentinel:
      datasource:
        flow:
          nacos:
            server-addr: localhost:8848
            data-id: ${spring.application.name}-flow-rules
            group-id: SENTINEL_GROUP
            rule-type: flow
```

数据源依赖、`rule-type`、JSON 格式、命名空间和版本必须一致。Dashboard 若仍用于编辑，需要确认它修改的是配置中心，而不是只推送到单个应用实例。

## 2. 监控与排障

Dashboard 适合查看单机实时指标；长期监控应将业务指标接入 Prometheus / Grafana。至少按资源、规则和业务维度采集：pass、block、异常、RT、并发线程数、熔断状态、Token 请求超时和本地回退次数。

排障顺序：

1. 确认资源名、规则类型和接入方式是否匹配。
2. 检查客户端是否已加载规则、数据源是否连接成功。
3. 区分规则阻断、业务异常和下游超时。
4. 对照规则变更时间、实例数、流量分布与资源指标。

## 3. Dashboard 安全

Dashboard 不应直接暴露到公网。认证账号密码是基础措施；访问网段由 Ingress、Nginx、安全组或防火墙控制，TLS 在终止位置管理证书和轮换。不要假定 Dashboard 自带任意 IP 白名单属性。

## 4. 规则模型与命名

建议一个规则类型对应一个 data ID，避免把流控、熔断、系统和网关规则混在同一 JSON 中。命名应同时表达应用、规则类型和环境，例如：

```text
order-service-flow-rules-prod
order-service-degrade-rules-prod
gateway-gw-flow-rules-prod
```

流控规则至少要能看出资源、阈值类型、数量、流控效果和是否集群模式；熔断规则还要记录统计窗口、最小请求数、熔断时长和策略。发布前校验 JSON 结构，避免“配置中心更新成功，但客户端无法解析”。

## 5. Dashboard 与配置中心的职责

Dashboard 擅长发现机器、查看实时状态和临时调试；配置中心才应是规则事实来源。若 Dashboard 的编辑操作只 push 到应用内存，重启后规则必然消失，也容易与 Nacos 当前内容不一致。

可靠流程是：规则提交到配置中心 → 客户端监听并加载 → 监控确认版本和效果。若要从 Dashboard 编辑规则，需要做经过验证的发布适配，使其写入配置中心并处理失败回滚；不要把“页面显示已保存”当作规则已持久化。

## 6. 监控面板与告警

一个实用面板至少分四层：

| 层次 | 重点问题 | 指标示例 |
| --- | --- | --- |
| 流量 | 是否真的在削峰 | pass/block QPS、限流率 |
| 质量 | 是否在保护而非误伤 | P95/P99、异常率、业务成功率 |
| 熔断 | 下游是否恢复 | OPEN/HALF-OPEN、探测成功率 |
| 配置 | 规则是否可靠到达 | 数据源加载失败、规则版本、回退次数 |

告警不能只以 block QPS 为依据：峰值限流可能是预期保护，也可能是阈值过低。应结合业务成功率、核心链路 RT、CPU/线程池和下游指标判断。

## 7. 标准排障剧本

**规则不生效**：核对资源名、接入模块、规则类型、data ID/group/namespace、依赖与解析日志。  
**规则误伤**：按维度查看 block，确认是否把回调、NAT 用户、核心租户和普通流量混在一起。  
**重启后丢规则**：确认事实来源是否配置中心，而非仅 Dashboard 内存。  
**Dashboard 看不到机器**：检查 Dashboard 地址、心跳、命令端口、防火墙和网络连通性；它不等于应用的限流能力已经失效。

## 8. 数据源选择

| 方案 | 优点 | 局限 | 适用范围 |
| --- | --- | --- | --- |
| 本地文件 | 简单、可随包发布 | 变更需重启，不便集中管理 | 本地开发、演示 |
| Nacos | 动态推送、配置历史、生态集成 | 依赖配置中心可用性 | 已使用 Nacos 的服务 |
| Apollo | 有发布流程与灰度能力 | 需要维护 Apollo 集成 | 已有 Apollo 平台 |
| ZooKeeper | 监听模型成熟 | 运维与数据模型不同 | 已有 ZK 基础设施 |
| 自定义数据源 | 可接数据库或内部平台 | 要自行处理监听、一致性与回滚 | 有统一治理平台 |

选择依据不是“哪个最流行”，而是现有配置中心、发布流程、权限模型和故障模式。无论选哪种，客户端加载失败时的行为都要明确：保留最后成功规则、拒绝启动，还是继续使用空规则，三者的风险完全不同。

## 9. Nacos 规则示例

流控规则通常以 JSON 列表保存：

```json
[
  {
    "resource": "createOrder",
    "limitApp": "default",
    "grade": 1,
    "count": 200,
    "strategy": 0,
    "controlBehavior": 0,
    "clusterMode": false
  }
]
```

其中 `grade`、`strategy`、`controlBehavior` 为版本相关枚举编码。手工编辑前应先以目标版本的序列化结果为样本；不要从不同版本博客复制数值。规则发布后，检查客户端日志和规则管理器，而不是只确认 Nacos 控制台保存成功。

## 10. 发布、灰度与回滚

推荐把规则变更当作代码变更处理：

```text
草案 → JSON 校验 → 测试环境压测 → 小范围实例灰度
  → 观察业务与资源指标 → 全量发布
  → 保留上一版本内容与一键回滚入口
```

灰度可以通过环境、命名空间、专用 data ID 或实例标签实现，但前提是灰度实例确实订阅了不同规则。只在 Dashboard 页面上挑几台机器编辑，往往难以重现和回滚。

## 11. 日志与审计

每次规则发布至少记录：规则内容哈希、操作者、审批单、发布时间、影响资源、灰度范围、回滚版本。运行侧日志至少包含资源名、阻断类型、来源、参数维度（注意脱敏）和请求标识。

对于热点参数，不要把完整用户 ID、手机号或订单号直接写入普通日志；可记录哈希、类别或受控采样。监控目的是识别规则误伤，不应因此扩大敏感数据暴露面。

## 12. 监控告警的分级

| 信号 | 建议级别 | 首先检查什么 |
| --- | --- | --- |
| block 短时升高、RT 正常 | 提示 | 是否为预期峰值保护 |
| block 与业务成功率同时下降 | 警告 | 阈值、流量维度、重试行为 |
| 熔断持续 OPEN | 警告/严重 | 下游状态、探测与 fallback |
| 数据源加载失败 | 严重 | 当前规则是否仍有效、配置中心连通性 |
| 集群回退持续发生 | 严重 | Token Server、网络和配额偏差 |

## 13. 运维练习

1. 故意发布错误 JSON，确认客户端不会静默替换最后一份有效规则。
2. 修改 `data-id` 或 `rule-type`，记录规则不生效时的日志特征。
3. 灰度一条较低阈值规则，验证只有目标实例收到更新。
4. 停止 Dashboard，确认本地已有规则与配置中心监听的区别。
5. 演练配置中心不可用、应用重启和规则回滚三种场景。

## 14. 规则生命周期

```text
编写规则 → 格式校验 → 审批 → 发布到配置中心
  → 客户端监听并解析 → 本地规则替换 → 指标验证
  → 保留版本 → 灰度扩大或回滚
```

生命周期的关键是可观测闭环：配置中心“发布成功”不是终点，必须确认目标客户端已加载、目标资源已命中、业务结果符合预期。任何环节失败都应能定位到具体版本和实例。

## 15. 规则校验清单

- `resource` 是否等于运行时资源名；
- `rule-type` 是否与规则 JSON 类型一致；
- 时间单位、阈值类型和枚举编码是否属于目标版本；
- data ID、group、namespace、环境是否相同；
- 是否存在同资源的旧规则叠加；
- 是否为网关规则误用了普通 `flow`；
- 是否把敏感、高基数参数写进资源名或日志。

## 16. 指标保留与容量

实时 Dashboard 适合短期观察，不能代替长期时序库。长期指标应按资源和实例保留足够时间，用于回答“阈值为何如此设置”“规则变更后是否改善”“同类事故是否重复发生”。

监控标签也应控制基数：资源名、规则类型、实例、环境通常可接受；用户 ID、订单号、完整 URL 参数不应成为 Prometheus 标签。高基数标签会让监控系统自身成为故障源。

## 17. 常见运维场景

**发布后 block 突增**：先确认新版本、命中资源和维度，再决定回滚或调阈值；不要直接删除所有规则。  
**客户端日志报解析错误**：保留最后有效规则，修正 JSON 和版本编码后再发布。  
**Dashboard 与 Nacos 不一致**：以明确指定的事实来源为准，避免双写。  
**实例新扩容未加载规则**：检查启动配置、网络、命名空间和数据源依赖。  
**长期无 block**：不代表规则无用；结合容量、峰值和演练判断是否仍应保留。

## 18. 运维交接材料

每个应用至少维护：资源清单、规则清单、配置中心位置、Dashboard 地址、负责人、阈值依据、回退策略、告警链接、常用排障命令和最近一次演练记录。这样规则不会随着某个维护者离开而失去解释。
