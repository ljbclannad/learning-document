# Sentinel：生产实践

## 1. 容量与阈值

阈值来自目标 RT、错误率下的**稳定吞吐量**，而不是压测瞬时峰值。压测应固定请求模型、并发、机器规格、JDK、Sentinel 与 Spring Cloud Alibaba 版本，并保存完整规则 JSON。

| 场景 | 重点指标 |
| --- | --- |
| 本地限流 | pass/block、P95/P99、CPU、GC、线程数 |
| 熔断 | 慢调用比例、异常比例、OPEN/HALF-OPEN 转换 |
| 热点参数 | 参数基数、淘汰、误伤率 |
| 集群限流 | Token 延迟、超时率、回退次数、配额偏差 |

## 2. 规则变更

规则属于生产变更：应有版本、评审、灰度范围、回滚条件与负责人。高峰期间避免直接把总量阈值调到极限；变更后同时观察业务成功率和资源指标，不能只看 block QPS。

## 3. 应急原则

- 优先保核心读写链路，先限制报表、导出、轮询和低优先级租户。
- 限流响应使用可恢复语义；写操作重试必须依赖幂等键。
- 熔断 fallback 不应伪造“成功”，应返回可解释状态并保留补偿路径。
- 集群限流故障时按预案选择本地回退或拒绝，不能临场猜测配额语义。

## 4. 上线前清单

- 资源名和规则维度可解释，且无高基数资源名。
- 规则已持久化，应用重启与数据源故障均已演练。
- Dashboard 不对公网开放，访问与变更受控。
- 告警同时覆盖流量、RT、错误、熔断、回退和业务成功率。

## 5. 从容量到阈值的步骤

1. 明确资源的业务目标：例如下单要求 P99 小于 300ms，库存依赖允许的并发是多少。
2. 在接近生产的依赖和数据条件下压测，找到目标 RT、错误率下的稳定吞吐量。
3. 为流量倾斜、GC、下游抖动、故障转移预留容量；不要直接使用压测最高峰值。
4. 决定是否允许突发：不允许则用更平滑的策略，允许则限定桶容量或 Warm Up 行为。
5. 灰度规则后，根据业务成功率和资源指标回校阈值。

例如某实例稳定处理 800 QPS，但在 900 QPS 时 P99 明显恶化，则入口规则可以从 600～700 QPS 开始灰度；若有 10 个实例，不能自动把它解释为“严格 7000 QPS”，除非集群配额的故障语义也已设计完成。

## 6. 分层保护的例子

以订单链路为例：

| 层次 | 资源 | 目的 | 示例动作 |
| --- | --- | --- | --- |
| 网关 | 下单路由、租户 | 入口总量与配额 | 非核心租户先返回 429 |
| 订单服务 | `createOrder` | 保护本机线程与数据库 | QPS/线程数限流 |
| 库存依赖 | `deductStock` | 防止慢依赖耗尽调用方 | 慢调用熔断、可重试降级 |
| 支付回调 | 独立路由 | 防止状态丢失 | 与用户轮询分配不同资源和阈值 |

每一层要有不同责任；如果同一资源在每层均配置相同比例的限流，最终拒绝率会叠加，且排障很困难。

## 7. 规则变更模板

一次变更至少记录：

```text
资源与维度：createOrder / route / tenant
旧值 → 新值：500 QPS → 650 QPS
原因：实例扩容并完成容量压测
灰度范围：10% 实例，30 分钟
观察指标：block、P99、错误率、支付成功率、下游 CPU
回滚条件：P99 超过 300ms 或成功率下降 0.5%
负责人和窗口：...
```

配置中心中的规则 JSON 应与这份变更记录关联。紧急修改可以跳过部分流程，但不能跳过可回滚、可审计和后续复盘。

## 8. 压测矩阵

除了稳定 QPS，还应至少覆盖：

- **阶梯加压**：观察阈值附近 RT、GC、线程池的拐点。
- **突发流量**：验证 Warm Up、排队或快速失败是否符合预期。
- **下游变慢/失败**：验证熔断、fallback 和恢复探测。
- **规则变更**：验证客户端动态加载、错误 JSON 与回滚。
- **实例缩容/Token Server 故障**：验证本地回退或拒绝是否与预案一致。

压测结论必须记录版本、规则和流量模型；脱离这些上下文的“Sentinel 开销百分比”没有可迁移性。

## 9. 应急操作顺序

1. 确认是入口洪峰、下游故障、规则误配还是实例容量下降。
2. 先保护核心写链路，收紧导出、轮询、搜索等低优先级资源。
3. 若需要放宽规则，采用小步调整并持续观察；不要一次取消所有保护。
4. 出现资金或状态一致性风险时，优先保证回调、查询和补偿通道，并审计幂等结果。
5. 事件结束后固化阈值依据、监控缺口和演练项。

## 10. 业务优先级设计

限流不是只回答“拒绝多少”，还要回答“先保护谁”。可以将流量分为：核心写操作、核心查询、补偿与回调、普通查询、后台任务、报表与导出。每类应有独立资源名、阈值和响应策略；不要把所有 `/api/**` 请求压在一条规则下。

| 类别 | 典型策略 | 限流后的体验 |
| --- | --- | --- |
| 核心写操作 | 较高优先级、幂等保护 | 明确失败或处理中，可安全重试 |
| 支付回调/补偿 | 独立资源、并发保护 | 尽量接收，失败可补偿 |
| 普通查询 | QPS 限流、缓存降级 | 429 或返回可接受的缓存结果 |
| 导出/报表 | 严格配额、异步化 | 排队或稍后生成 |
| 后台任务 | 独立线程池和限速 | 延迟执行，不抢占在线流量 |

## 11. 规则质量的评估

一个规则的好坏不以“有没有 block”评价，而以它是否在正确时机保护了正确资源评价。上线后至少比较：

- 规则触发前后核心业务成功率是否稳定；
- 资源 P99、线程池队列、连接池等待是否改善；
- 被拒绝流量是否集中在预期的低优先级维度；
- 客户端重试率是否反而上升；
- fallback 是否掩盖了真实故障或制造数据不一致。

若 block 上升但 CPU、RT、下游压力都没有改善，通常说明资源名、阈值、维度或调用方重试策略有问题。

## 12. 常见事故模式

### 12.1 粗粒度路由误伤

将支付下单、查询、回调放在同一条网关配额下，用户轮询可能吃掉回调额度。改进是拆分资源，给回调独立保护和补偿机制，而不是简单把总阈值无限调高。

### 12.2 热点参数一刀切

所有医院、租户或商品使用同一参数阈值，会使大客户在正常高峰被误伤。改进是按业务等级设置有限例外项，或把不同业务类型拆成资源；阈值依据应来自各等级的稳定容量。

### 12.3 系统规则过敏

CPU 或 Load 阈值设置得低于稳定工作区间时，实例会在尚未饱和时大面积拒绝请求。系统规则应是兜底，需要结合容器限制、长期负载、RT 与下游指标校准，不能只套用一个百分比。

### 12.4 规则不持久化

临时在 Dashboard 配置并验证成功，重启后规则消失。改进是把配置中心作为事实来源，并演练重启和数据源不可用时的行为。

## 13. 安全与合规

Dashboard 仅应部署在受控网络中，账号密码、TLS、访问网段和操作审计缺一不可。规则内容和限流日志中可能含资源名、租户、参数值等业务信息，应遵循最小暴露原则并对敏感值脱敏。

限流本身不是安全防护的替代品：IP 限制无法防止凭证滥用，QPS 阈值也不能阻止低频长期攻击。认证、授权、风控、WAF 与限流应分别承担责任。

## 14. 复盘模板

```text
事件：何时、何资源、何用户范围受影响？
保护目标：原规则意图保护什么瓶颈？
触发事实：pass/block、RT、错误、下游指标如何变化？
业务影响：成功率、延迟、补偿量、客户影响？
根因：阈值、维度、资源名、依赖容量、重试还是发布流程？
处置：调整了什么，为什么安全？
防复发：新增什么监控、演练、配置校验或幂等措施？
```

## 15. 生产演练清单

1. 流量突发时，核心和非核心资源是否按预期分层。
2. 下游慢调用时，熔断与恢复探测是否符合业务 SLA。
3. 规则误配时，是否能在分钟级定位并回滚。
4. 配置中心、Dashboard、Token Server 分别故障时，系统行为是否已知。
5. 限流恢复后，客户端重试和补偿任务是否造成二次洪峰。

## 16. 压测报告应包含什么

一份可复用的压测报告至少写明：环境规格、应用与依赖版本、数据规模、请求模型、并发与连接数、规则 JSON、预热时间、持续时间和结果指标。结果不要只写最高 QPS，还要记录各阶段的 P50/P95/P99、错误率、GC、CPU、线程池、连接池和下游容量。

当结论是“阈值设为 700 QPS”时，应能追溯到具体测试和业务目标，而不是“之前项目一直这么配”。

## 17. 灰度观察窗口

灰度不只是把规则发给少量实例，还要给系统足够时间经历正常流量、短时峰值和依赖波动。观察窗口内应对比灰度与对照实例：

- 通过/阻断比例是否符合预期；
- 核心请求 P99 与成功率是否改善；
- 被阻断用户是否集中在低优先级范围；
- 下游压力是否真实下降；
- 客户端重试与补偿量是否异常。

一旦触发回滚条件，应回滚到已验证的完整规则版本，而不是临时修改多个字段后继续观察。

## 18. 依赖保护原则

保护下游依赖时，应先确定其真正瓶颈：QPS、并发连接、慢调用、异常率或成本配额。对数据库、缓存、第三方支付、消息系统分别建资源，不要用一个笼统的 `remoteCall` 混合统计。

fallback 选择也应按依赖类型区分：缓存读取可以返回旧值或默认值；支付与库存写入应返回处理中或失败，并通过可靠事件、查询与补偿达成最终一致。没有补偿路径的“成功降级”往往只是把问题推迟到更难排查的地方。

## 19. 配置审计与合规

规则变更可能直接影响客户访问和业务收入，应遵循最小权限、审批、审计和回滚原则。高风险操作包括：取消核心资源限流、显著提高集群阈值、关闭熔断、把回调加入普通限流组、修改回退策略。

审计记录中应避免存储敏感参数明文；对外响应也不应暴露内部阈值、实例数或依赖名称。

## 20. 生产成熟度自评

| 等级 | 特征 |
| --- | --- |
| 基础 | 有本地规则，但无持久化与演练 |
| 可运行 | 规则持久化、Dashboard 可观测、基本 fallback |
| 可控 | 有灰度、回滚、分层资源和长期监控 |
| 韧性 | 定期演练依赖故障、配置故障、扩缩容和重试洪峰 |

目标不是为所有接口堆叠规则，而是让关键资源在故障与流量变化中保持可解释、可恢复、可验证。
