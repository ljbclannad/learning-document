# Sentinel：核心概念与接入

## 1. 资源与规则

Sentinel 对“资源”做统计和保护。资源可以是 URL、服务方法、RPC 调用、网关路由或自定义代码块；资源名必须稳定、可聚合，避免把订单号、用户 ID 等高基数字段直接拼入资源名。

常见规则：

| 规则 | 保护对象 | 常见阈值 |
| --- | --- | --- |
| 流控 | 入口或下游资源 | QPS、并发线程数 |
| 熔断降级 | 慢或错误的依赖 | 慢调用比例、异常比例、异常数 |
| 系统规则 | 整个实例 | Load、CPU、平均 RT、入口 QPS、线程数 |
| 热点参数 | 某资源中特定参数值 | 参数值维度 QPS |

## 2. 基础接入

Spring Cloud Alibaba 通常通过 `spring-cloud-starter-alibaba-sentinel` 接入。Dashboard 地址仅用于发现、监控和临时规则推送；客户端的本地规则与统计不依赖 Dashboard 每次请求参与。

```yaml
spring:
  cloud:
    sentinel:
      transport:
        dashboard: localhost:8080
```

应用会启动命令端口（常见默认值为 `8719`）供 Dashboard 推送规则。Dashboard 不可用时，已经加载到本地的规则仍按本地逻辑生效；但新规则不能依赖它继续下发。

## 3. `@SentinelResource`

```java
@SentinelResource(
    value = "createOrder",
    blockHandler = "handleBlocked",
    fallback = "handleFailure"
)
public Order createOrder(CreateOrderCommand command) { ... }

public Order handleBlocked(CreateOrderCommand command, BlockException ex) { ... }
public Order handleFailure(CreateOrderCommand command, Throwable ex) { ... }
```

- `blockHandler`：规则触发的 `BlockException`，如流控、熔断、系统保护。
- `fallback`：业务方法已进入后抛出的非 `BlockException` 异常；`exceptionsToIgnore` 可排除不应兜底的异常。
- 处理方法返回值须兼容原方法；`blockHandler` 末尾额外接收 `BlockException`，`fallback` 可在末尾接收 `Throwable`。

Web 层更常使用框架适配器提供的 URL / 路由埋点；注解更适合服务方法和明确的业务资源。

## 4. 选择规则的顺序

先从最靠近瓶颈的规则开始：入口保护用 QPS，线程池/慢依赖保护用并发或熔断，局部热点用参数限流，实例整体濒临饱和时才用系统规则。每条规则都要明确限流维度、超限响应和观测指标，避免“全局一刀切”。

## 5. 流控规则的四个维度

一条流控规则至少包含：资源名、阈值类型、阈值、效果。QPS 保护单位时间内的进入量，线程数保护正在执行的并发量；前者适合多数 HTTP/RPC 入口，后者更适合慢操作或有限连接的下游。

```java
FlowRule rule = new FlowRule("createOrder");
rule.setGrade(RuleConstant.FLOW_GRADE_QPS);
rule.setCount(200);                 // 单实例每秒最多通过 200 次
rule.setLimitApp("default");       // 对所有来源生效
rule.setControlBehavior(RuleConstant.CONTROL_BEHAVIOR_DEFAULT);
FlowRuleManager.loadRules(List.of(rule));
```

常见效果的选择：

| 效果 | 行为 | 适用场景 | 风险 |
| --- | --- | --- | --- |
| 快速失败 | 立即抛出 `BlockException` | 普通读接口、防刷 | 客户端必须正确处理 429 / 降级 |
| Warm Up | 阈值从较低值逐步升至目标值 | 冷启动、缓存预热 | 不适合必须立刻承接峰值的接口 |
| 匀速排队 | 以近似固定间隔放行，超出等待上限则拒绝 | 消息消费、可等待的异步链路 | 会占用请求等待时间，不适合长链路同步调用 |

关联与链路模式解决的是“哪个资源影响哪个资源”的问题，而不是替代服务依赖治理。规则生效前，应先确认资源是否以期望的调用链被埋点；否则配置看似正确也可能完全不触发。

## 6. 熔断、降级与 fallback

熔断是框架依据指标切断调用，降级是业务在被切断或异常时提供的替代体验。二者经常一起出现，但不应混为一个机制。

| 策略 | 判断条件 | 适合发现的问题 |
| --- | --- | --- |
| 慢调用比例 | 慢调用数 / 总请求数达到阈值，且达到最小请求数 | 下游变慢、连接池或线程池拥塞 |
| 异常比例 | 异常数 / 总请求数达到阈值 | 依赖大量失败但仍有部分成功 |
| 异常数 | 统计周期内异常累计达到阈值 | 低 QPS 服务的连续错误 |

fallback 的最低要求是：不重复写入、不伪造成功、能让调用方知道后续动作。例如创建订单被限流时可返回“请求繁忙，请稍后重试”；支付状态查询被熔断时可返回“处理中”并引导轮询或异步通知。对扣款、库存扣减等写操作，必须结合幂等键和补偿流程。

## 7. 系统规则与热点参数

系统规则是实例级最后防线，不是日常业务规则的替代品。它针对 Load、CPU 使用率、平均 RT、并发线程数或入口 QPS 等整体压力起作用；过低阈值会误伤无关接口，因此应以长期监控和压测数据校准。

热点参数限流解决“同一接口中某个参数值突然很热”的问题。例如商品详情可按 `productId` 做保护，避免单一爆款拖垮缓存或数据库。不要把用户 ID、订单号等高基数且没有热点语义的字段直接作为统计维度。

## 8. 接入后的最小验证

1. 访问一个已埋点资源，确认 Dashboard 或日志能看到稳定资源名。
2. 配置很小的 QPS 阈值，验证通过与阻断两类响应。
3. 验证 `blockHandler`、`fallback` 各自只处理预期异常。
4. 重启应用，确认规则来源和恢复行为符合预期。
5. 增加实例后，确认单机阈值与集群总量的差异被正确理解。

## 9. 流控模式：直接、关联与链路

### 9.1 直接模式

直接模式只看当前资源自身的统计，是最常用、最容易解释的模式。

```text
createOrder 的 QPS > 200
  → 阻断 createOrder 的后续请求
```

它适合接口容量明确、资源之间没有明显竞争关系的情况。绝大多数规则应从直接模式开始；只有在确实存在资源耦合时，再考虑关联或链路模式。

### 9.2 关联模式

关联模式表达“资源 B 过热时限制资源 A”。典型目标是保护读写竞争或同一数据库连接池。

```text
writeOrder QPS 上升
  → 限制 queryOrder
  → 给写请求保留数据库与线程资源
```

它的风险是因果关系不直观：用户访问 `queryOrder` 被拒绝，真正的触发原因却是 `writeOrder`。因此必须在规则说明、日志和监控面板中同时展示关联资源，避免排障时误以为 queryOrder 自身超限。

### 9.3 链路模式

链路模式按调用来源区分同一资源。例如 `getUser` 同时被“下单”和“资料页”调用，可以只限制来自资料页的路径。它依赖正确的上下文与调用链埋点；异步切线程、错误的资源嵌套或接入层不支持都会让链路统计与预期不同。

在使用前先回答：资源名是否稳定？调用入口是否可识别？如果不能，宁可定义两个业务资源，也不要用模糊的链路规则猜测。

## 10. 常见阈值误区

| 误区 | 为什么有问题 | 更好的做法 |
| --- | --- | --- |
| 阈值等于压测峰值 | 峰值不含 GC、流量倾斜和依赖波动 | 使用目标 RT 下的稳定吞吐量并预留余量 |
| 所有接口统一 100 QPS | 成本和业务优先级不同 | 按资源、租户、依赖和重要性分层 |
| 只配网关，不配业务 | 网关看不到内部热点和慢依赖 | 网关粗粒度，业务层保护真实瓶颈 |
| 一次配很细的参数规则 | 高基数会增加统计与运维复杂度 | 从少量明显热点开始，观察后扩展 |
| 限流就等于安全 | 被拒绝可能触发客户端重试风暴 | 设计响应、退避、幂等和降级 |

## 11. `@SentinelResource` 的边界

注解依赖 AOP 代理，因此同类内部自调用通常不会经过代理，也就不会像外部调用那样被注解埋点。接口方法、私有方法、异常签名、异步返回类型等也受到具体接入模块和版本约束。对关键路径，应该用集成测试验证“规则真的被触发”，而不是只确认注解写在代码上。

`blockHandlerClass` 和 `fallbackClass` 可把处理逻辑放到独立类中。此时处理方法通常需要满足静态方法、参数和返回值匹配等约束；不要为了复用而把所有业务的 fallback 聚集到一个巨型工具类，错误语义会很快失控。

## 12. 响应设计

限流响应的目标不是隐藏错误，而是让调用方以正确方式恢复。

| 请求类型 | 推荐结果 | 调用方动作 |
| --- | --- | --- |
| 幂等查询 | 429 / 可缓存的降级结果 | 退避后重试或展示稍后刷新 |
| 创建类写操作 | 429 + 幂等键语义 | 保留请求标识，避免盲目重复提交 |
| 支付/状态变更 | 明确“处理中”而非“成功” | 查询最终状态或等待异步通知 |
| 非核心异步任务 | 延迟、入队或丢弃 | 记录可补偿事件 |

若客户端无退避策略，短时限流会诱发同步重试，反而制造第二个流量峰。服务端与客户端必须共同定义最大重试次数、退避时间和幂等边界。

## 13. 基础练习

1. 为 `createOrder` 配置 5 QPS 快速失败规则，分别观察第 6 个请求和下一秒请求的响应。
2. 为查询接口配置 Warm Up，对比冷启动前后允许通过的流量。
3. 将一个方法改为内部自调用，验证注解是否仍生效。
4. 为 `productDetail(productId)` 配置热点参数规则，分别压测热门商品与普通商品。
5. 模拟下游超时，检查 `blockHandler` 与 `fallback` 的日志、响应和指标是否可区分。

## 14. 完整规则示例

下面的示例用代码展示四类本地规则。实际项目更常由配置中心下发，但先用代码理解字段语义更直观。

```java
FlowRule flow = new FlowRule("createOrder")
    .setGrade(RuleConstant.FLOW_GRADE_QPS)
    .setCount(200);

DegradeRule degrade = new DegradeRule("paymentClient")
    .setGrade(CircuitBreakerStrategy.SLOW_REQUEST_RATIO)
    .setCount(800)                 // 慢调用 RT 阈值（毫秒）
    .setSlowRatioThreshold(0.5)
    .setMinRequestAmount(20)
    .setStatIntervalMs(10_000)
    .setTimeWindow(10);

ParamFlowRule param = new ParamFlowRule("productDetail")
    .setParamIdx(0)
    .setCount(50);

SystemRule system = new SystemRule()
    .setMaxThread(300);
```

字段的意义比数值更重要：`count` 在不同规则中可能表示 QPS、线程数、慢调用 RT、比例或异常数，不能看到字段名相同就照搬。规则中所有时间单位也应在目标版本中确认。

## 15. 熔断状态机

```text
CLOSED
  │ 指标达到规则条件
  ▼
OPEN
  │ 熔断时间到期
  ▼
HALF-OPEN ──探测成功──→ CLOSED
  │
  └──探测失败──────────→ OPEN
```

OPEN 期间不是“系统恢复了”，而是主动不再调用被保护资源；HALF-OPEN 也不是全面放流，而是用少量请求验证下游。fallback 应能承接这两个阶段，并且让用户知道结果的确定性：缓存数据、处理中状态和失败提示的业务含义完全不同。

## 16. 线程数规则与 QPS 规则

QPS 规则约束进入速度，线程数规则约束正在执行的请求数。慢接口在同样 QPS 下会积压更多线程，因此当目标是保护数据库连接、第三方 HTTP 连接或有限工作线程时，线程数往往更贴近真实瓶颈。

```text
快接口：200 QPS × 10ms  → 平均并发约 2
慢接口：200 QPS × 2s    → 平均并发约 400
```

这不是让所有慢接口都只配线程数：QPS 控制入口洪峰，线程数控制在途占用，两者可组合，但必须避免阈值互相矛盾导致难以解释的双重阻断。

## 17. 接入检查表

| 项目 | 检查内容 |
| --- | --- |
| 依赖 | Starter、适配器与 Spring Boot BOM 兼容 |
| 资源 | 名称稳定、无用户 ID/订单号等高基数拼接 |
| 异常 | `BlockException` 与业务异常分别处理 |
| 规则 | 明确来源、版本、加载失败策略 |
| 响应 | 429、fallback、重试和幂等语义一致 |
| 监控 | pass/block/RT/异常与业务成功率关联 |
| 演练 | 限流、熔断、规则更新、重启均已验证 |

## 18. 常见问答

**Dashboard 宕机是否会立刻停止限流？** 不会。已加载在客户端内存中的规则仍可本地判定；但发现、监控和临时推送会受影响。  
**一个规则能保护全局集群吗？** 普通规则不能；它只在本机统计。需要共享总量时才使用集群限流，并接受其故障取舍。  
**限流阈值越高越好吗？** 不。过高等同于不保护，过低则误伤；应由稳定容量、优先级和观察结果校准。  
**fallback 是否可以吞掉所有异常？** 不应。参数校验、业务冲突、数据不一致等错误通常要显式反馈或进入补偿流程。
