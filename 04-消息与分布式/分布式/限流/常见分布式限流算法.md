# 1. 计数器算法
**计数器算法**（Counter Algorithm）是一种简单的 **限流（Rate Limiting）** 方式，主要用于控制单位时间内的请求数量，以 **防止系统过载**。这种算法主要应用于 **API 限流、登录防暴力破解、爬虫限制** 等场景。

## 1.1 计数器算法的原理

- 设定一个时间窗口（如 1 秒、1 分钟）。
- 维护一个计数器（Counter），用于记录该时间窗口内的请求数量。
- 如果请求数未超出限制，则放行，并增加计数器。
- 如果超出限制，则 **拒绝请求**（返回 `429 Too Many Requests`）。
- 到达时间窗口结束时，**清零计数器**，重新开始计数。

**示例：** 假设 **最大 QPS（每秒请求数）= 10**：

- **第 1 秒**：
    - 0ms：第 1 次请求 ✅（计数器 = 1）
    - 100ms：第 2 次请求 ✅（计数器 = 2）
    - ...
    - 900ms：第 10 次请求 ✅（计数器 = 10）
    - 950ms：第 11 次请求 ❌（被拒绝）
- **第 2 秒**：
    - 计数器重置为 0，重新开始计数。

## 1.2 计数器算法的实现

```java
import java.util.concurrent.TimeUnit;

public class RateLimiter {
    // 最大请求数
    private final int limit;
    // 时间窗口(秒)
    private final long intervalSeconds;

    // 计数器
    private int counter;
    // 窗口开始时间(毫秒)
    private long startTimeMillis;

    public RateLimiter(int limit, long intervalSeconds) {
        this.limit = limit;
        this.intervalSeconds = intervalSeconds;
        this.counter = 0;
        this.startTimeMillis = System.currentTimeMillis();
    }

    public synchronized boolean allowRequest() {
        long currentTimeMillis = System.currentTimeMillis();

        // 如果超过时间窗口，重置计数器和开始时间
        if (currentTimeMillis - startTimeMillis >= TimeUnit.SECONDS.toMillis(intervalSeconds)) {
            counter = 0;
            startTimeMillis = currentTimeMillis;
        }

        // 判断是否超过限制
        if (counter < limit) {
            counter++;
            return true; // 允许请求
        } else {
            return false; // 拒绝请求
        }
    }

    // 简单测试
    public static void main(String[] args) throws InterruptedException {
        // 每秒最多5个请求
        RateLimiter limiter = new RateLimiter(5, 1);

        for (int i = 0; i < 10; i++) {
            if (limiter.allowRequest()) {
                System.out.println("请求 " + (i + 1) + " 通过");
            } else {
                System.out.println("请求 " + (i + 1) + " 被限流");
            }
            // 间隔200ms发送请求
            Thread.sleep(200);
        }
    }
}
```

> 上述实现仅用于说明固定窗口的逻辑：`counter` 和窗口起点必须在同一临界区更新。单机多线程需要同步或原子状态；多实例部署则需把状态放到 Redis/Lua、网关或专门的限流服务中，不能让每台机器各自按同一个全局阈值放行。

**输出示例：**

```

请求 2 通过 ✅
请求 3 通过 ✅
请求 4 通过 ✅
请求 5 通过 ✅
请求 6 被限流 ❌
请求 7 被限流 ❌
请求 8 被限流 ❌
请求 9 被限流 ❌
请求 10 被限流 ❌
```

（下一秒后计数器重置，新的请求可以通过）

## 1.3 计数器算法的优缺点

### 1.3.1 优点

- **实现简单**，只需要一个计数器。
- **低开销**，适合高性能需求。
- **适用于固定时间窗口**，如 "每秒最多 10 次请求"。

### 1.3.2 缺点

- **突发流量问题**：
    - 如果窗口刚结束，计数器重置，可能导致**瞬间请求量过高**（如在窗口起始时涌入大量请求）。
- **不均匀限流**：
    - 在窗口内如果前几毫秒内请求已达上限，后面的请求都被拒绝。

## 1.4 计数器算法的实际应用

### 1.4.1 API 限流
- 例如：GitHub API 限制 **每个 IP 每分钟最多 60 次请求**。
- Nginx、Cloudflare 等都支持基于计数器的限流。

### 1.4.2 登录防暴力破解
- 限制同一 IP 在 1 分钟内最多尝试 5 次登录，防止暴力破解密码。

### 1.4.3 爬虫访问限制
- 限制同一用户的抓取频率，防止服务器被爬取过载。


# 2. 滑动时间窗口算法

## 2.1 什么是滑动时间窗口算法？

滑动时间窗口（Sliding Window）是一种 **改进版的计数器算法**，用于 **限流** 和 **流量控制**。它比 **固定窗口计数器（Fixed Window Counter）** 更加平滑，能够减少突发流量问题。

### 2.1.1 工作原理

- **维护多个小窗口**，记录一段时间内的请求数量。
- **不断滑动窗口**，计算最近时间段的总请求数。
- **如果请求数超出阈值，则进行限流**。

### 2.1.2 计数器 vs 滑动窗口

| 算法               | 适用场景                      | 问题                               |
| ------------------ | ----------------------------- | ---------------------------------- |
| **固定窗口计数器** | 简单限流，如“每秒 10 次请求”  | 流量突刺，窗口刚重置时流量可能激增 |
| **滑动窗口**       | 平滑限流，适用于 API 速率限制 | 相比计数器算法，计算更复杂         |

## 2.2 滑动窗口的实现

滑动窗口常见有 **两种实现思路**：

1. **滑动日志（Sliding Log）**：基于时间戳记录每一次请求
2. **滑动窗口计数器（Sliding Window Counter）**：将窗口拆分为多个小桶进行近似统计

### 2.2.1 滑动日志（基于时间戳的滑动窗口）

#### 2.2.1.1 思路

- **用一个队列（或有序列表）存储最近的请求时间戳**。
- **每次请求时，清理超过时间窗口的旧请求**。
- **计算最近时间窗口内的请求数**，判断是否超过限制。


```java
import java.util.ArrayDeque;
import java.util.Deque;

public class SlidingWindowRateLimiter {
    // 窗口最大请求数
    private final int maxRequests;
    // 窗口大小(秒)
    private final long windowSizeSeconds;
    // 存储请求时间戳(毫秒)
    private final Deque<Long> requestTimestamps = new ArrayDeque<>();

    public SlidingWindowRateLimiter(int maxRequests, long windowSizeSeconds) {
        this.maxRequests = maxRequests;
        this.windowSizeSeconds = windowSizeSeconds;
    }

    public synchronized boolean allowRequest() {
        long currentTimeMillis = System.currentTimeMillis();
        long windowStart = currentTimeMillis - windowSizeSeconds * 1000L;

        // 清除超出时间窗口的请求
        while (!requestTimestamps.isEmpty() && requestTimestamps.peekFirst() < windowStart) {
            requestTimestamps.pollFirst();
        }

        // 检查当前窗口内的请求数
        if (requestTimestamps.size() < maxRequests) {
            requestTimestamps.addLast(currentTimeMillis);
            return true; // 允许请求
        } else {
            return false; // 被限流
        }
    }

    // 测试
    public static void main(String[] args) throws InterruptedException {
        // 1秒内最多5个请求
        SlidingWindowRateLimiter limiter = new SlidingWindowRateLimiter(5, 1);

        for (int i = 0; i < 10; i++) {
            if (limiter.allowRequest()) {
                System.out.println("请求 " + (i + 1) + " 通过 ✅");
            } else {
                System.out.println("请求 " + (i + 1) + " 被限流 ❌");
            }
            // 每0.2秒发送一个请求
            Thread.sleep(200);
        }
    }
}
```

```
请求 3 通过 ✅
请求 4 通过 ✅

请求 7 被限流 ❌
请求 8 被限流 ❌
请求 9 被限流 ❌

```

（下一秒后计数器滑动，新的请求可以通过）

#### 2.2.1.3 特点

- 适用于 **高并发 API 限流**（如 API Gateway）。
- 可以 **实时计算当前窗口内的请求数**，相比固定窗口更平滑。
- **缺点**：性能消耗较高，需要存储所有请求时间戳（固定窗口仅需要维护一个counter）。

### 2.2.2 滑动窗口计数器（基于分桶统计）

#### 2.2.2.1 思路

- **将时间窗口分成多个小窗口（如 1 分钟拆成 6 个 10 秒的小窗口）。**
- 每次请求到来时，先滑动桶，再统计所有桶内请求总数。
- 它是对“真实滑动窗口”的**近似实现**，精度略低于滑动日志，但更节省内存，适合高性能系统。

#### 2.2.2.2 实现

```java
public class SlidingWindowCounter {
    // 窗口最大请求数
    private final int maxRequests;
    // 窗口大小(秒)
    private final double windowSizeSeconds;
    // 将窗口分成多少个小格子
    private final int numBuckets;
    // 每个小窗口的请求数
    private final int[] buckets;
    // 每个小窗口的时间长度(毫秒)
    private final double bucketDurationMillis;
    // 上次检查时间(毫秒)
    private long lastCheckedMillis;

    public SlidingWindowCounter(int maxRequests, double windowSizeSeconds, int numBuckets) {
        this.maxRequests = maxRequests;
        this.windowSizeSeconds = windowSizeSeconds;
        this.numBuckets = numBuckets;
        this.buckets = new int[numBuckets];
        this.bucketDurationMillis = (windowSizeSeconds * 1000.0) / numBuckets;
        this.lastCheckedMillis = System.currentTimeMillis();
    }

    public SlidingWindowCounter(int maxRequests, double windowSizeSeconds) {
        this(maxRequests, windowSizeSeconds, 10);
    }

    public synchronized boolean allowRequest() {
        long currentTimeMillis = System.currentTimeMillis();
        long elapsedMillis = currentTimeMillis - lastCheckedMillis;

        // 计算需要滑动多少个小窗口
        int numSlides = (int) (elapsedMillis / bucketDurationMillis);

        if (numSlides > 0) {
            // 为了避免超出数组长度，这里最多滑动 numBuckets 个
            int slides = Math.min(numSlides, numBuckets);

            // 滑动窗口: 左移 slides 个 bucket，右侧补 0
            // 等价于 Python: self.buckets = self.buckets[num_slides:] + [0] * num_slides
            // 但我们保持数组长度不变
            System.arraycopy(buckets, slides, buckets, 0, numBuckets - slides);
            for (int i = numBuckets - slides; i < numBuckets; i++) {
                buckets[i] = 0;
            }

            lastCheckedMillis = currentTimeMillis;
        }

        // 计算总请求数
        int totalRequests = 0;
        for (int count : buckets) {
            totalRequests += count;
        }

        if (totalRequests < maxRequests) {
            // 在当前 bucket 添加请求(最新 bucket 在数组末尾)
            buckets[numBuckets - 1]++;
            return true; // 允许请求
        } else {
            return false; // 被限流
        }
    }

    // 测试
    public static void main(String[] args) throws InterruptedException {
        // 1秒最多5个请求
        SlidingWindowCounter limiter = new SlidingWindowCounter(5, 1.0);

        for (int i = 0; i < 10; i++) {
            if (limiter.allowRequest()) {
                System.out.println("请求 " + (i + 1) + " 通过 ✅");
            } else {
                System.out.println("请求 " + (i + 1) + " 被限流 ❌");
            }
            // 每0.2秒发送一个请求
            Thread.sleep(200);
        }
    }
}
```

#### 2.2.2.3 代码里的“滑动”到底是什么意思

这段代码的核心作用是：**时间往前走了几个小桶，就把数组整体左移几个位置，把已经过期的桶丢掉，再在右边补 0，给新的时间片腾位置。**

```java
if (numSlides > 0) {
    int slides = Math.min(numSlides, numBuckets);

    System.arraycopy(buckets, slides, buckets, 0, numBuckets - slides);
    for (int i = numBuckets - slides; i < numBuckets; i++) {
        buckets[i] = 0;
    }

    lastCheckedMillis = currentTimeMillis;
}
```

可以看一个具体例子：

- 假设整个窗口大小是 `1s`
- 一共分成 `5` 个桶
- 那么每个桶代表 `200ms`

如果当前桶数组是：

```text
[2, 1, 3, 0, 1]
```

它表示：

- 最左边的 `2` 是最老的那个 `200ms` 时间片里的请求数
- 最右边的 `1` 是最新的那个 `200ms` 时间片里的请求数

如果这次调用 `allowRequest()` 时，距离上次检查过去了 `250ms`，那么：

```java
numSlides = 250 / 200 = 1
```

说明窗口需要向前滑动 `1` 格，于是数组会从：

```text
[2, 1, 3, 0, 1]
```

变成：

```text
[1, 3, 0, 1, 0]
```

含义是：

- 最左边那个桶已经过期，被丢掉
- 其他桶整体左移
- 最右边补一个 `0`，表示新的时间片刚出现，还没有请求

如果这次过去了 `450ms`，那么：

```java
numSlides = 450 / 200 = 2
```

数组会从：

```text
[2, 1, 3, 0, 1]
```

变成：

```text
[3, 0, 1, 0, 0]
```

如果过去的时间已经超过整个窗口，比如过去了 `1200ms`，那所有旧桶都过期了，数组会被整体清空：

```text
[0, 0, 0, 0, 0]
```

所以你可以把这个过程理解成一条“传送带”：

- 左边是旧时间片
- 右边是新时间片
- 时间往前走，数组就整体左移
- 掉出去的是过期流量
- 新补进来的是空桶

#### 2.2.2.4 特点

- **节省内存**，只存储小窗口数据，不存请求时间戳。
- **比固定窗口更平滑**，但由于分桶统计本身是近似值，边界处仍可能有轻微误差。
- **适用于高并发场景，如 API 限流、负载均衡器。**

## 2.3 适用场景

| 场景                                   | 推荐算法               |
| -------------------------------------- | ---------------------- |
| **简单限流（每秒 N 次请求）**          | 固定窗口计数器         |
| **防止流量突刺，API 限流**             | 滑动窗口（基于时间戳） |
| **高性能限流（如 Nginx、Redis 限流）** | 滑动窗口（基于计数器） |
| **短信验证码、登录防暴力破解**         | 令牌桶算法             |

## 2.4 总结

| 限流算法               | 适用场景                      | 主要特点                         |
| ---------------------- | ----------------------------- | -------------------------------- |
| **固定窗口计数器**     | 低流量 API 限流               | 简单易实现，但可能存在流量突刺   |
| **滑动窗口（时间戳）** | 精确限流，适用于 API 速率限制 | 记录所有请求时间戳，内存占用较大 |
| **滑动窗口（计数器）** | 高性能限流（Redis / Nginx）   | 低内存占用，流量平滑             |

✅ **如果你的 API 需要更平滑的限流，而不是简单的时间段计数，推荐滑动窗口算法！**  
✅ **如果是高并发服务（如 API Gateway、Nginx），建议使用** **滑动窗口计数器或令牌桶算法**。


# 3.漏桶算法（Leaky Bucket Algorithm）

漏桶算法（Leaky Bucket Algorithm）是一种 **限流（Rate Limiting）** 算法，用于 **控制请求速率**，防止流量突刺，保证流量平稳。

## 3.1 漏桶算法原理

- **形象理解：**
    - 想象一个装水的桶，**水滴代表请求**，**桶的出口代表处理能力**。
    - **水（请求）以任意速率流入桶中**。
    - **水只能以固定速率流出（即请求被处理）**。
    - **如果桶满了（请求过多），新来的水（请求）会被丢弃**。
- **特点：**
    - **请求以平稳速率处理（限流）**。
    - **不允许突发流量**，所有请求必须按照设定速率通过。

### 3.1.1 漏桶算法与令牌桶算法对比

| 算法           | 处理方式                 | 适用场景                           |
| -------------- | ------------------------ | ---------------------------------- |
| **漏桶算法**   | 限制请求处理速率（匀速） | **流量稳定输出**（如音视频流）     |
| **令牌桶算法** | 允许突发流量             | **API 限流**（如支付、短信验证码） |

## 3.2 漏桶算法的实现

### 3.2.1 思路

- 维护一个 **桶容量（capacity）** 和 **当前积压水量（water）**。
- **请求到来时，先按照时间流逝计算已经漏掉多少水**。
- **如果加上当前请求后仍未超过桶容量，则允许通过**。
- **如果桶已满，则拒绝新请求**，从而把整体处理速率限制在固定范围内。

### 3.2.2 Java 实现

```java
public class LeakyBucket {
    // 漏桶容量
    private final int capacity;
    // 漏出速率：每秒可处理多少个请求
    private final double leakRate;

    // 当前桶内积压的请求数
    private double water;
    // 上次漏水时间
    private long lastLeakTimeMillis;

    public LeakyBucket(int capacity, double leakRate) {
        this.capacity = capacity;
        this.leakRate = leakRate;
        this.water = 0;
        this.lastLeakTimeMillis = System.currentTimeMillis();
    }

    public synchronized boolean allowRequest() {
        long now = System.currentTimeMillis();
        long elapsedMillis = now - lastLeakTimeMillis;

        if (elapsedMillis > 0) {
            double leaked = (elapsedMillis / 1000.0) * leakRate;
            water = Math.max(0, water - leaked);
            lastLeakTimeMillis = now;
        }

        if (water + 1 <= capacity) {
            water += 1;
            return true;
        }
        return false;
    }

    public static void main(String[] args) throws InterruptedException {
        LeakyBucket bucket = new LeakyBucket(5, 2.0);

        for (int i = 0; i < 10; i++) {
            String req = "请求 " + (i + 1);
            if (bucket.allowRequest()) {
                System.out.println(req + " 通过 ✅");
            } else {
                System.out.println(req + " 被限流 ❌");
            }
            Thread.sleep(300);
        }
    }
}
```

### 3.2.3 结果示例

```
请求 1 通过 ✅
请求 2 通过 ✅
请求 3 通过 ✅
请求 4 通过 ✅
请求 5 通过 ✅
请求 6 被限流 ❌
请求 7 被限流 ❌
请求 8 通过 ✅
请求 9 通过 ✅
请求 10 被限流 ❌
```

### 3.2.4 关键点

- **每次请求时，先按经过的时间计算“漏掉”多少请求**，再决定当前请求能否进入桶。
- **处理速率是固定的**（即每秒只能处理 `leak_rate` 个请求）。
- **如果桶已满，新请求会被丢弃**，防止系统过载。
- 上面的实现使用“当前积压水量”来表示漏桶状态，比“队列 + 手动轮询出队”更接近经典漏桶模型，也避免了嵌套加锁和时间误差累积的问题。

## 3.3 Redis 实现（分布式限流）

在分布式环境中，可以用 **Redis** 实现漏桶算法。

### 3.3.1 思路

1. **使用 Redis 计数器存储桶中的积压请求数**。
2. **使用 Lua 脚本保证原子性**（同时处理“入桶”和“漏水”）。

> 说明：下面的 Redis 版本是工程上常见的“计数近似实现”，重点是原子地维护桶内积压量；它并不严格保存请求队列顺序，因此更适合作为分布式限流器，而不是严格的排队器。

```lua
-- Redis 漏桶限流 Lua 脚本
local key = KEYS[1]  -- 漏桶的 key
local capacity = tonumber(ARGV[1])  -- 漏桶容量
local leak_rate = tonumber(ARGV[2])  -- 处理速率
local current_time = tonumber(ARGV[3])  -- 当前时间戳（毫秒）

if capacity <= 0 or leak_rate <= 0 then
    return redis.error_reply("capacity and leak_rate must be positive")
end

-- 获取当前桶的请求数和上次更新时间
local bucket_info = redis.call("HMGET", key, "requests", "last_time")
local requests = tonumber(bucket_info[1]) or 0
local last_time = tonumber(bucket_info[2]) or current_time

-- 计算时间差，并处理“漏水”
local time_passed = current_time - last_time
local leaks = time_passed / 1000 * leak_rate
requests = math.max(0, requests - leaks)

-- 判断是否能接收新请求
if requests < capacity then
    redis.call("HMSET", key, "requests", requests + 1, "last_time", current_time)
    -- TTL 至少覆盖“桶排空所需时间”，否则 key 提前过期会绕过限流。
    redis.call("PEXPIRE", key, math.ceil(capacity / leak_rate * 1000) + 1000)
    return 1  -- 允许请求
else
    return 0  -- 拒绝请求
end
```

# 4. 令牌桶算法

令牌桶算法（Token Bucket Algorithm）是一种 **流量控制算法**，用于 **限流（Rate Limiting）**，适用于 **API 请求限流、带宽控制、短信验证码防刷等** 场景。

## 4.1 令牌桶算法原理

- **有一个“桶”，里面存储一定数量的令牌（tokens）。**
- **系统按照固定速率向桶中添加令牌（即 refill 过程）。**
- **当请求到来时，从桶中取出一个令牌，才允许通过。**
- **如果桶是空的（令牌用完），则拒绝请求（被限流）。**

### 4.1.1 🆚 令牌桶 vs. 漏桶

| 算法           | 处理方式                 | 适用场景                           |
| -------------- | ------------------------ | ---------------------------------- |
| **漏桶算法**   | 限制请求处理速率（匀速） | **流量稳定输出**（如音视频流）     |
| **令牌桶算法** | 允许突发流量             | **API 限流**（如支付、短信验证码） |

## 4.2 令牌桶算法的 Java 实现

### 4.2.1 🔧 方式 1：基于 `ScheduledExecutorService` 的实现

```java
import java.util.concurrent.Executors;
import java.util.concurrent.ScheduledExecutorService;
import java.util.concurrent.TimeUnit;

public class TokenBucket {
    private final int capacity;  // 令牌桶容量
    private final int refillRate;  // 令牌生成速率（每秒生成多少个）
    private int tokens;  // 当前令牌数
    private final ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(1);

    public TokenBucket(int capacity, int refillRate) {
        this.capacity = capacity;
        this.refillRate = refillRate;
        this.tokens = capacity; // 初始时令牌桶满

        // 定时补充令牌
        scheduler.scheduleAtFixedRate(this::addTokens, 0, 1, TimeUnit.SECONDS);
    }

    private synchronized void addTokens() {
        tokens = Math.min(capacity, tokens + refillRate);  // 不能超过桶的最大容量
    }

    public synchronized boolean allowRequest() {
        if (tokens > 0) {
            tokens--;  // 取一个令牌
            return true;  // 允许请求
        }
        return false;  // 拒绝请求（限流）
    }

    public void stop() {
        scheduler.shutdown();
    }

    public static void main(String[] args) throws InterruptedException {
        TokenBucket bucket = new TokenBucket(5, 2);  // 令牌桶容量 5，每秒生成 2 个令牌

        for (int i = 0; i < 10; i++) {
            if (bucket.allowRequest()) {
                System.out.println("请求 " + (i + 1) + " 通过 ✅");
            } else {
                System.out.println("请求 " + (i + 1) + " 被限流 ❌");
            }
            Thread.sleep(300);  // 每 300ms 发送一个请求
        }

        bucket.stop();
    }
}
```

### 4.2.2 ✅ 运行结果（示例）

```
请求 1 通过 ✅
请求 2 通过 ✅
请求 3 通过 ✅
请求 4 通过 ✅
请求 5 通过 ✅
请求 6 被限流 ❌
请求 7 被限流 ❌
请求 8 通过 ✅
请求 9 通过 ✅
请求 10 被限流 ❌
```

**（前 5 个请求通过，后续请求因令牌不足被限流，1 秒后补充令牌，新的请求被允许）**

### 4.2.3 关键点

- **令牌以固定速率添加**，模拟真实限流。
- **突发请求可行（只要桶内有令牌）**，但长时间持续高频请求会触发限流。
- **适用于 API 限流、爬虫防刷等应用场景。**

```java
import com.google.common.util.concurrent.RateLimiter;

public class GuavaTokenBucket {

}
```

## 4.4 方式 3：Redis 分布式令牌桶（Lua 脚本）

#### 4.4.1 Redis Lua 脚本

```lua
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local refill_rate = tonumber(ARGV[2])
local current_time = tonumber(ARGV[3])  -- 毫秒

if capacity <= 0 or refill_rate <= 0 then
    return redis.error_reply("capacity and refill_rate must be positive")
end

-- 获取当前桶状态
local bucket_info = redis.call("HMGET", key, "tokens", "last_time")
local tokens = tonumber(bucket_info[1]) or capacity
local last_time = tonumber(bucket_info[2]) or current_time

-- 计算令牌补充量
local time_passed = current_time - last_time
local new_tokens = math.min(capacity, tokens + time_passed / 1000 * refill_rate)

-- 判断是否能通过请求
if new_tokens >= 1 then
    redis.call("HMSET", key, "tokens", new_tokens - 1, "last_time", current_time)
    -- 令牌重新攒满后即可过期；TTL 不能写死，否则低速限流会被提前重置。
    redis.call("PEXPIRE", key, math.ceil(capacity / refill_rate * 1000) + 1000)
    return 1  -- 允许请求
else
    return 0  -- 被限流
end
```

#### 4.4.2 Java 代码

```java
import redis.clients.jedis.Jedis;
import java.time.Instant;

public class RedisTokenBucket {
    private static final String LUA_SCRIPT = "【上面 Lua 脚本】";
    private final Jedis jedis;
    private final String key;
    private final int capacity;
    private final int refillRate;

    public RedisTokenBucket(Jedis jedis, String key, int capacity, int refillRate) {
        this.jedis = jedis;
        this.key = key;
        this.capacity = capacity;
        this.refillRate = refillRate;
    }

    public boolean allowRequest() {
        long currentTime = Instant.now().toEpochMilli();
        Object result = jedis.eval(LUA_SCRIPT, 1, key, String.valueOf(capacity), String.valueOf(refillRate), String.valueOf(currentTime));
        return result.equals(1L);
    }

    public static void main(String[] args) {
        Jedis jedis = new Jedis("localhost");
        RedisTokenBucket bucket = new RedisTokenBucket(jedis, "token_bucket", 5, 2);

        for (int i = 0; i < 10; i++) {
            System.out.println(bucket.allowRequest() ? "请求通过 ✅" : "请求被限流 ❌");
            try { Thread.sleep(300); } catch (InterruptedException ignored) {}
        }
    }
}
```

# 5. 四大限流算法优劣势比较图

| 算法               | 优势                                             | 劣势                                               | 是否平滑 | 是否支持突发 | 实现复杂度 | 典型场景                               |
| ------------------ | ------------------------------------------------ | -------------------------------------------------- | -------- | ------------ | ---------- | -------------------------------------- |
| **固定窗口计数器** | 实现最简单，性能开销低，容易落地                 | 容易出现窗口边界突刺，限流不够平滑                 | 较差     | 不支持       | 低         | 简单接口限流、后台管理系统、低流量服务 |
| **滑动日志**       | 精度高，能准确统计“最近一段时间”请求数           | 需要保存大量时间戳，内存开销大，高并发下成本高     | 较好     | 不支持       | 中         | 对限流精度要求高的 API、精细化风控     |
| **滑动窗口计数器** | 比固定窗口更平滑，比滑动日志更省内存，工程上常用 | 本质是近似统计，边界处仍可能有误差                 | 较好     | 不支持       | 中         | 网关限流、Redis 分布式限流、高并发接口 |
| **漏桶**           | 输出速率稳定，流量最平滑，适合保护下游           | 不允许突发流量，请求高峰时体验较差                 | 很好     | 不支持       | 中         | 音视频、消息消费、严格匀速处理场景     |
| **令牌桶**         | 既能限制平均速率，又允许短时突发，弹性最好       | 流量不一定最平滑，参数设置不合理时可能瞬时放大流量 | 中等     | 支持         | 中         | API 网关、秒杀保护、短信验证码、防刷   |

### 5.1 一句话记忆

- **固定窗口计数器**：最简单，但容易在窗口切换时出现流量突刺。
- **滑动日志**：最准确，但最耗内存。
- **滑动窗口计数器**：精度和性能折中，工程里很常见。
- **漏桶**：最平滑，适合严格控制输出速率。
- **令牌桶**：最灵活，适合既要限流又要允许短时突发的场景。

### 5.2 每种限流算法的核心参数怎么设置

实际落地时，限流效果好不好，往往不取决于“选了哪种算法”，而取决于**核心参数是否和业务特征匹配**。下面按算法分别说明。

#### 5.2.1 固定窗口计数器

核心参数通常有两个：

- **窗口大小**：如 `1s`、`10s`、`1min`
- **窗口内最大请求数**：如 `100 req/s`、`1000 req/min`

设置思路：

- 如果业务对瞬时流量比较敏感，窗口不要设太大，通常优先用 `1s` 或几秒级窗口。
- 如果只是做粗粒度防刷，可以设成 `1min` 这种更长窗口。
- 最大请求数通常按“系统安全吞吐量”打折来定，比如服务实际稳定处理能力是 `1200 QPS`，限流阈值可以先设在 `800~1000 QPS`。

经验建议：

- **窗口越大**：统计越粗，越容易在大窗口内掩盖瞬时尖峰。
- **阈值越贴近系统极限**：越容易在流量抖动时把系统打满。

#### 5.2.2 滑动日志

核心参数通常有两个：

- **滑动窗口大小**：如最近 `1s`、最近 `10s`
- **窗口内最大请求数**

设置思路：

- 窗口大小一般和你想约束的时间尺度一致，比如限制“最近 1 秒内最多 200 次请求”，那窗口就设 `1s`。
- 阈值仍然要略低于系统稳定处理能力，给线程切换、GC、网络抖动留余量。
- 因为滑动日志要保存每次请求时间戳，所以高并发场景下窗口不宜过长，否则内存压力会明显上升。

经验建议：

- **窗口越长、QPS 越高**，时间戳存储成本越高。
- 这类算法适合“精度优先”，不适合极高吞吐且资源紧张的场景。

#### 5.2.3 滑动窗口计数器

核心参数通常有三个：

- **总窗口大小**
- **窗口内最大请求数**
- **桶数量 `numBuckets`**

设置思路：

- 总窗口大小和滑动日志一样，取决于你想限制“最近多长时间”的请求量。
- `numBuckets` 决定统计精度。桶越多，每个桶越小，越接近真实滑动窗口，但计算和维护成本也会略高。
- 常见做法是把 `1s` 窗口拆成 `5`、`10`、`20` 个桶。

经验建议：

- 如果是普通接口限流，`1s + 10 个桶` 已经比较常见。
- 如果对精度要求更高，可以增加桶数；如果更关心性能，可以适当减少桶数。
- **桶数太少** 会让算法更接近固定窗口，平滑效果变差。

#### 5.2.4 漏桶

核心参数通常有两个：

- **桶容量 `capacity`**
- **漏出速率 `leakRate`**，即每秒允许稳定处理多少请求

设置思路：

- `leakRate` 一般按**下游系统长期稳定处理能力**来定，而不是按峰值能力来定。  
  例如下游服务稳定只能扛 `200 QPS`，那漏出速率就应该接近 `200/s`，而不是按短时峰值 `300/s` 去配。
- `capacity` 决定允许积压多少请求，本质上决定“高峰来了以后，你愿意排队多久”。

可以用一个简单公式帮助理解：

```text
最大排队时间 ≈ capacity / leakRate
```

例如：

- `leakRate = 200 req/s`
- `capacity = 400`

那就表示：

- 系统稳定以 `200 QPS` 往下游放流量
- 最多允许积压 `400` 个请求
- 极端情况下，请求最多可能排队约 `2s`

经验建议：

- 如果你**不希望排队太久**，就把桶容量设小一点。
- 如果你希望**尽量多接住短时流量峰值**，可以把桶容量设大一些，但这会增加延迟。
- 漏桶更适合“宁可排队，也不要冲垮下游”的场景。

#### 5.2.5 令牌桶

核心参数通常有两个：

- **桶容量 `capacity`**
- **令牌生成速率 `refillRate`**

设置思路：

- `refillRate` 决定系统长期平均允许多少请求通过，通常按系统的**长期稳定吞吐量**来定。
- `capacity` 决定系统允许多大的**瞬时突发**。

可以这样理解：

```text
平均速率由 refillRate 决定
瞬时突发能力由 capacity 决定
```

例如：

- `refillRate = 100 req/s`
- `capacity = 300`

含义是：

- 长期看，系统平均每秒只会放行大约 `100` 个请求
- 但如果前一段时间流量较低，桶里攒满了令牌，短时间内最多可以连续放行 `300` 个请求

经验建议：

- 如果业务**允许一定突发**，`capacity` 可以设成 `refillRate` 的 `2~5` 倍，表示允许 `2~5` 秒左右的突发余量。
- 如果业务对瞬时洪峰敏感，`capacity` 不要设太大，否则会在短时间内一下子放过过多请求。
- 如果你发现系统“平均没超，但瞬间还是被打高了”，优先检查是不是令牌桶容量设得过大。

#### 5.2.6 一个通用的配置原则

无论哪种算法，参数都不要直接按系统极限值配置，最好遵循下面的顺序：

1. 先测出系统的**稳定处理能力**，而不是峰值能力。
2. 限流阈值按稳定能力留出一定冗余，通常先保守一些。
3. 观察真实流量的峰谷特征，再决定要不要允许突发，以及允许多大突发。
4. 结合监控数据反复调参，重点看：`限流比例`、`接口 RT`、`错误率`、`下游负载`。

一句话概括：

- **固定窗口 / 滑动窗口**：重点是设置“多长时间内允许多少请求”
- **漏桶**：重点是设置“稳定放流速度”和“允许排队多少”
- **令牌桶**：重点是设置“长期平均速率”和“允许多大突发”
