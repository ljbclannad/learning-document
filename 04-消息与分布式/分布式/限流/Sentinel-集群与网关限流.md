# Sentinel：集群与网关限流

## 1. 集群限流的边界

单机限流状态存在各实例内存中，不能严格控制集群总量。集群限流由 Token Client 向 Token Server 请求配额，在**单一权威 Server 正常通信**时可统一判定。

这带来三个边界：

- 网络超时与 Server 故障会影响请求路径。
- `fallbackToLocalWhenFail=true` 时可用性更高，但会退回本地阈值，不再保证全局总量。
- Sentinel 不提供 Token Server 主从复制或状态同步；多个独立 Server 不会自动共享一个严格配额。

因此，严格配额优先时应在 Server 故障后拒绝；可用性优先时应回退本地，并为“配额可能放宽”建立告警与补偿方案。

## 2. 网关与业务层协同

网关适合按路由、API 分组、来源或参数做入口削峰；业务层适合保护方法、线程池和下游依赖。两层不应机械叠加阈值：网关承担总量和低优先级流量，业务层只保护本机或真实瓶颈。

Spring Cloud Gateway 接入需要兼容版本的 Sentinel Starter 与 Gateway Adapter。网关规则数据源应使用 `gw-flow`，而不是普通 `flow`。

```yaml
spring:
  cloud:
    sentinel:
      datasource:
        gateway-flow:
          nacos:
            server-addr: localhost:8848
            data-id: gateway-flow-rules
            group-id: SENTINEL_GROUP
            rule-type: gw-flow
```

## 3. 设计检查

- 超限请求是否返回可恢复的 `429`，写操作是否有幂等键？
- 支付回调、内部探针等关键流量是否被错误归入普通用户配额？
- Token Server 超时、规则下发失败、本地回退是否都有可观测指标？
- 入口规则与业务规则同时触发时，是否能解释最终拒绝比例？

## 4. Token Server 的工作方式

集群规则在 Client 侧命中后，会向被分配的 Token Server 请求令牌。Server 在自己的统计窗口中检查该资源是否还能放行，然后返回通过或阻断结果。它控制的是**配额判定**，不是服务发现、负载均衡或消息队列。

```text
Client 请求 → 集群规则命中 → 请求 Token Server
  → Server 在统计窗口内检查配额
  → granted：Client 执行业务
  → blocked：Client 返回限流响应
  → timeout / unavailable：按回退策略处理
```

选择策略前先回答：当配额服务不可用时，业务更不能接受“多放一点”，还是“多拒一些”？前者选择失败即拒绝，后者可回退本地；两者没有通用正确答案。

## 5. 网关规则与业务规则

网关规则的资源通常是路由 ID 或自定义 API 分组。它更适合做以下事情：

- 给整个路由设入口上限，挡住无效重试和爬虫。
- 按来源、请求参数或 API 分组区分配额。
- 对低优先级查询、导出、轮询设更严格的额度。

业务规则则用于保护真正瓶颈，例如库存扣减、三方支付、数据库慢查询。一个常见配置原则是：网关阈值小于集群稳定容量，业务阈值只作为局部兜底，而不是再次把所有请求按同等比例削掉。

```text
客户端
  → 网关：路由/租户/IP 粗粒度限流
  → 服务：方法/热点参数/并发线程保护
  → 下游：熔断与业务降级
```

## 6. 返回语义与关键流量

被限流的 HTTP 请求通常应返回 `429 Too Many Requests`；能够估算恢复时间时可增加 `Retry-After`。写操作的自动重试必须带幂等键，否则“先被限流、后重试”可能变成重复创建。

支付回调、内部健康检查、消息补偿等流量不应与普通用户请求共用一个粗粒度配额。它们可以使用独立路由、来源识别或更高优先级规则，但仍需保留并发和系统保护，避免所谓“白名单”成为过载入口。

## 7. 验证场景

| 场景 | 预期现象 |
| --- | --- |
| 单实例持续超阈值 | 本地规则稳定 block，不依赖网络 |
| 多实例争抢集群配额 | Server 正常时总通过量受统一阈值约束 |
| Token Server 超时 | 观察到拒绝或本地回退，且指标可区分 |
| 网关先限流 | 业务层通常不触发，但仍保留局部保护能力 |
| 单一热点参数突发 | 仅命中的参数值被阻断，其他值不受误伤 |

## 8. 集群规则的配置模型

集群流控规则仍以 `FlowRule` 为核心，只是在规则中开启 cluster mode，并附带集群配置。需要区分两类阈值：

| 阈值思路 | 含义 | 适合场景 |
| --- | --- | --- |
| 全局阈值 | 所有 Client 向同一权威 Server 竞争一个总额度 | 秒杀库存、第三方全局配额 |
| 平均本地阈值 | 按参与实例数分摊的额度 | 实例稳定、只需近似均分的场景 |

规则的数值本身没有脱离拓扑的意义。实例扩容、Client 列表变化、Server 分配变化与本地回退都会改变实际通过量；每次变更都应同时记录规则版本和参与实例数。

## 9. 故障决策表

| 故障 | 可用优先方案 | 配额优先方案 | 必须观测 |
| --- | --- | --- | --- |
| Token Server 超时 | 回退本地规则 | 拒绝本次请求 | 超时率、回退次数 |
| Server 重启 | 短暂回退 | 预先摘流或拒绝 | 恢复时间、配额偏差 |
| Client 无法获取分配 | 本地保护 | 拒绝集群规则资源 | 分配状态、规则加载日志 |
| 网络抖动 | 设置合理超时并回退 | 收紧超时后拒绝 | P99、连接错误 |

“回退本地”不等于“不限流”，它只意味着判断从共享配额切换为本机阈值。该阈值应按最坏情况下的实例数和下游承受能力预先计算，而不是随手填一个很大的数。

## 10. 网关维度选择

### 10.1 路由维度

路由限流最容易理解：所有匹配同一路由的流量共同消耗额度。它适合给一个后端服务或一个明确业务入口设总闸门，但不能区分不同用户的重要性。

### 10.2 API 分组

把多个路径归为一组可表达共同预算，例如“订单写操作”“支付查询”“后台导出”。分组应按资源成本与业务优先级划分，而不是只按 URL 前缀；`/pay/submit` 与 `/pay/notify` 虽同属支付，却可能有完全不同的保护目标。

### 10.3 参数与来源

参数限流适合有限值域，如租户等级、业务类型；来源限流适合可信的调用方身份。客户端 IP 通常只适合作为辅助信号：NAT、代理和伪造头会让它不等于真实用户身份。

## 11. 网关 Block 响应

网关的阻断处理要统一，但不能失去业务信息：

```json
{
  "code": "RATE_LIMITED",
  "message": "当前请求过多，请稍后重试",
  "requestId": "..."
}
```

返回中避免泄漏内部规则、阈值或下游拓扑；日志中则应记录命中的资源、规则类型、来源维度和 requestId，便于把用户反馈关联到限流事件。

## 12. 双层限流的计算例子

假设网关对某路由放行率为 70%，业务层又因本机瓶颈只放行其中的 80%，最终通过比例约为 `0.7 × 0.8 = 56%`，总拒绝比例约为 44%。

这个计算说明：两层规则不能独立“各削一点”而不评估叠加影响。观察时要分别统计 gateway block、service block 和下游错误，避免把所有用户失败归因于一个规则。

## 13. 集群与网关练习

1. 在两个实例上分别配置本地限流，比较总量与单实例流量倾斜。
2. 启用集群规则并模拟 Token Server 超时，记录两种回退策略的通过量。
3. 为 `/pay/submit`、`/pay/query`、`/pay/notify` 定义不同 API 分组和阈值。
4. 让网关和业务层同时触发限流，验证日志能明确指出阻断位置。
5. 对带幂等键的写请求压测重试，确认不会重复创建业务数据。

## 14. 部署与规则加载

集群限流至少涉及两类配置：Client 知道哪些规则需要集群判定，Client 知道应向哪个 Token Server 请求配额。规则、Server 分配和 Client 身份应来自可追溯的数据源；手工在单台机器修改列表只适合短暂排查。

部署前确认：

- Token Server 与 Client 的网络、端口、超时和鉴权策略可用；
- Server 的容量压测覆盖目标 QPS 与并发连接；
- 规则更新、Server 重启、Client 扩缩容均有观测；
- 回退阈值与业务优先级一致，不会在故障时放大下游压力。

独立部署可避免业务实例重启直接带走 Server，但不自动提供状态复制。若配置多个独立 Server，应明确它们各自负责的资源或分区；不要让多个 Server 各自对同一个“全局 1000 QPS”做独立统计。

## 15. 集群限流排障

| 现象 | 排查路径 |
| --- | --- |
| 规则看似开启却走本地 | 检查 cluster mode、Client 分配、规则加载日志 |
| Token 请求超时 | 检查网络、Server 饱和度、超时配置和连接数 |
| 全局通过量异常偏高 | 排查本地回退、多个独立 Server、Client 未加入集群规则 |
| 全局通过量异常偏低 | 排查重复网关/业务规则、阈值单位、Server 统计窗口 |
| 仅某些实例被阻断 | 对比实例规则版本、Client 身份、流量倾斜和本地规则 |

排障必须同时收集 Client 与 Server 两侧证据。只看 Client 的 429 无法判断是网关、业务本地规则还是 Token Server 拒绝。

## 16. 网关接入注意点

Gateway Adapter 的资源模型以路由和 API 分组为中心。路由 ID 变更、路径重写、StripPrefix 等网关行为会改变实际匹配结果，因此规则上线前要用真实请求验证资源名。

自定义 Block 响应通常在网关统一处理，但下游服务仍应能处理自身 Sentinel 阻断。不要假定所有 429 都来自网关；日志中至少记录层级、资源名和请求标识。

当网关位于反向代理之后，客户端 IP 需要由可信代理正确传递并限制伪造头。若来源识别不可靠，不要把 IP 当作高价值租户配额的唯一依据。

## 17. 设计复盘问题

1. 这个全局阈值保护的是库存、下游配额还是成本预算？
2. Server 故障时多放行和多拒绝，哪个业务损失更大？
3. 回调、补偿、内部调用是否使用独立资源？
4. 网关规则和业务规则是否能从指标上拆分责任？
5. 客户端重试是否会把短暂限流扩大为持续洪峰？
