# Sentinel：源码与统计模型

## 1. 调用链

请求进入 Sentinel 后，会经过 `ProcessorSlotChain`。不同版本的 Slot 顺序和实现细节可能不同，但职责可概括为：建立资源节点与调用链、统计指标、校验授权/系统规则/流控规则/熔断规则。任一规则阻断都会抛出 `BlockException` 并中断后续业务调用。

源码走读时请固定 Git tag；不要把概念伪代码当作真实类字段或固定执行顺序。

## 2. 滑动窗口

`LeapArray` 将统计周期切成多个桶，`WindowWrap` 保存桶起始时间和统计值。请求到来时定位当前桶，统计侧累计 pass、block、exception、RT 等事件；读取 QPS 时聚合有效桶。

关键性质：

- 桶数组会循环复用，过期桶通常按访问时机替换。
- 常规统计路径以原子累加为主；跨窗口时才需要协调桶的创建或替换。
- 统计是面向高吞吐的近似实时读，不应把它误解为强一致审计账本。
- `sampleCount`、统计周期和版本实现共同决定窗口精度与开销，不能脱离版本写死为唯一默认值。

## 3. 热点参数限流

热点参数不是“任意对象自动限流”。规则指定资源、参数下标和默认阈值；可用例外项为特定参数值配置不同阈值。典型流程：

1. 从调用参数中取出目标下标的值。
2. 查找该值是否命中特例阈值，否则使用默认阈值。
3. 在参数值维度读取滑动窗口 QPS。
4. 超限则抛出 `ParamFlowException`，否则在统计路径累计通过量。

参数值空间必须有上限。对用户 ID、订单号等高基数值直接做热点统计会增加内存压力；应选择真正的热点维度（商品、租户、医院等），并依赖版本提供的容量控制或在业务侧分级。

## 4. 源码验证清单

- 固定 Sentinel 版本、JDK 与接入方式。
- 对照 `LeapArray`、`MetricBucket`、`DefaultSlotChainBuilder` 与参数流控相关类。
- 用压测验证跨窗口、并发、参数淘汰和规则更新，而不是仅凭断点推断。

## 5. 从 `entry` 到 `exit`

无论通过注解、Web 适配器还是 `SphU.entry()` 进入，Sentinel 都围绕一次 entry 建立上下文、执行 SlotChain、统计结果并在退出时归还上下文。可以把它理解为下面的概念流程：

```text
请求进入资源
  → 建立/复用 Context 与资源节点
  → 统计当前请求和历史窗口
  → 依次检查授权、系统、流控、熔断等规则
  → 通过：执行业务并在 exit 时记录 RT / 异常
  → 阻断：抛出 BlockException，业务方法不执行
```

这里有两个经常混淆的点：

- **阻断不是业务异常**。`BlockException` 表示规则主动保护，应该单独统计；业务代码抛出的异常才参与异常指标和 fallback 判断。
- **RT 在 exit 时才能完整得到**。入口时可做 QPS、线程数等判断，业务结束后才能累计调用时长和异常。

## 6. 滑动窗口如何计算 QPS

假设统计窗口为 1 秒，划分为 2 个 500ms 桶：

```text
时间轴:   [0, 500)       [500, 1000)
桶:       bucket[0]      bucket[1]
通过数:       80             120

最近 1 秒 pass QPS = (80 + 120) / 1s = 200
```

当时间来到下一个周期时，数组槽位可以被复用为新的时间片；已过期的值不应再参与聚合。桶越多，边界误差通常越小，但需要更多遍历和维护。统计窗口不是“越细越好”：若阈值只按秒级保护，过多桶不会自动提高业务正确性。

读取聚合值与并发累加之间通常是弱一致关系，这对于限流保护足够，但不适合用来做财务、计费或精确审计。

## 7. 热点参数的规则语义

```java
ParamFlowRule rule = new ParamFlowRule("productDetail")
    .setParamIdx(0)
    .setCount(30);
```

这个规则的含义是：对资源 `productDetail` 的第一个参数，按“参数值”分别统计 QPS；某个具体值在窗口内超过 30 才会被阻断，而不是所有商品 ID 合计只能 30 QPS。若需要给爆款额外配置阈值，可使用参数例外项；例外项应少而稳定，不能把它变成大型用户白名单。

调试时同时压测两个参数值：让 A 超过阈值、B 保持低流量。期望结果是 A 被 `ParamFlowException` 阻断，B 仍能通过；若 B 也被阻断，应先检查是否另有资源级 FlowRule 生效。

## 8. 走读与压测路线

1. 在资源入口、`ParamFlowSlot`、统计窗口切换处分别设置断点。
2. 用固定节奏和跨窗口突发两组流量对比 pass/block。
3. 修改规则并观察本地规则管理器是否更新，而不是只看 Dashboard 表单。
4. 用不同参数基数压测内存与 GC，验证容量控制是否符合预期。

源码阅读的产出应是“版本、结论、验证方式”，而不是摘录大量类名。每个结论最好能回答：它保护了什么、牺牲了什么、在什么条件下不成立。

## 9. 资源节点与上下文

Sentinel 不只记录一个“全局 QPS”。资源、调用来源和调用链会形成不同层级的统计节点，用来回答不同问题：某资源总共被调用多少次、某来源调用了多少次、某条调用路径是否异常。节点越细，定位能力越强，但内存与维护成本也越高。

上下文决定当前 entry 属于哪条调用链。同步嵌套调用一般能自然继承上下文；跨线程、消息消费、Reactive 链路等场景需要由对应适配器或应用代码保证语义连续。若上下文丢失，链路规则和调用关系可能与预期不同，但资源级规则仍可能生效。

## 10. 统计事件与业务语义

| 事件 | 含义 | 不应混同为 |
| --- | --- | --- |
| pass | 规则允许进入资源 | 业务最终成功 |
| block | 被 Sentinel 规则阻断 | 下游业务异常 |
| exception | 业务执行中抛出异常 | 所有 HTTP 非 2xx |
| success | 正常结束的调用 | pass 的同义词 |
| RT | 已完成调用的耗时 | 仅网络耗时 |

因此监控中“pass 很高”不代表下游健康；还要看 RT、异常和业务成功率。同样，“block 很高”不必然是故障，它可能是规则按预期吸收峰值。判断规则质量必须比较规则前后资源饱和度与核心业务结果。

## 11. 跨窗口边界

滑动窗口的一个常见误解是“每个请求都严格按真实最近 1 秒计算”。实际实现通过有限个桶近似时间范围，边界时刻可能出现小误差；这是为了让统计和判定能承受高并发。

测试窗口边界时应避免只用 `Thread.sleep` 猜测时间。可以记录每个请求的时间戳，分别构造：

```text
窗口开始前 1ms 的请求
窗口开始后 1ms 的请求
长时间空闲后第一个请求
多个线程同时跨桶的请求
```

重点不是某一次输出是否恰好等于预想，而是统计是否持续有界、过期数据是否退出聚合、规则是否在可接受误差内保护资源。

## 12. 热点参数的内存权衡

参数流控通常需要维护“参数下标 × 参数值”的统计状态。参数值数量若不受控制，攻击者可以不断提交新值，迫使统计结构增长。设计时应：

- 只选择值域较小且确有热点意义的参数；
- 为规则设置合理的最大参数数，并理解淘汰后的行为；
- 用业务分级替代无限例外项，例如按租户等级映射为有限的资源或参数类别；
- 在压测中观察老值淘汰后再访问的统计变化。

热点参数限流保护的是局部热点，不会自动替代资源整体 QPS 限流。常见组合是资源级规则兜住总量，参数级规则阻断单一爆款或异常租户。

## 13. 源码阅读问题清单

阅读一个版本的源码时，尝试逐项回答：

1. 当前资源的规则从哪里加载、何时替换？
2. 一个 entry 经过哪些 Slot，阻断后还会不会统计？
3. `exit` 如何累计 RT、异常和并发线程数？
4. 当前桶为空、有效、过期、时间回退时分别如何处理？
5. 参数值达到容量上限后如何淘汰，是否影响规则命中？
6. 集群规则和本地规则在失败时如何选择？

这些问题能把“记类名”变成对运行时行为的验证，也能防止不同版本的文章相互拼接造成误解。

## 14. 源码走读：心跳与 Dashboard

Dashboard 不参与每个请求的本地限流判定，它通过客户端主动心跳发现机器，并通过客户端命令端口推送临时规则。概念流程如下：

```text
客户端启动
  → 初始化 transport 与心跳发送器
  → 周期性向 Dashboard 上报应用名、IP、端口、版本等信息
  → Dashboard 更新内存中的机器列表

运维在 Dashboard 编辑规则
  → Dashboard 请求客户端命令端口
  → 客户端替换本地规则管理器中的规则
```

因此应区分三件事：Dashboard 看不到机器、规则未成功推送、客户端本地规则是否仍在生效。第一件不必然意味着第三件失效；但 Dashboard 本身也不是可靠的规则持久化来源。

## 15. 时间回退与时钟

窗口统计依赖当前时间。系统时钟被 NTP 回调、虚拟机迁移或人工修改时，当前时间可能小于桶的起始时间。成熟实现通常会避免把“未来桶”直接当作正常当前桶，并以保守方式处理异常时间；具体分支要以版本源码为准。

工程上最重要的不是背出实现细节，而是：不要在业务代码中人为修改系统时钟；容器和宿主机应使用可靠的时间同步；压测跨窗口问题时使用单调、可记录的时间序列，而不是只依赖肉眼观察。

## 16. 规则替换的原子性

动态数据源收到新规则后，规则管理器通常以整组规则替换当前视图。规则替换与正在执行的请求可以并发发生，因此某个边界请求命中旧规则或新规则都可能出现；这不等于规则“随机失效”。

变更时要避免把一个逻辑规则拆成多次不一致的发布。例如先降低网关阈值、后提高业务阈值，若中间间隔较长，可能造成额外误伤。需要跨资源原子变更时，应由配置发布流程提供版本化与灰度，而不是依赖单个规则管理器的原子替换。

## 17. 用伪代码理解判定

```java
Entry entry(String resource) {
    Context context = selectContext();
    Node node = selectNode(resource, context);

    recordThreadAndRequest(node);
    checkAuthority(context, resource);
    checkSystem(node);
    checkFlow(node);
    checkDegrade(node);
    return new Entry(node);
}

void exit(Entry entry, Throwable error, long rt) {
    recordRtAndException(entry.node(), rt, error);
    releaseThread(entry.node());
}
```

这不是 Sentinel 的逐行源码，只用来强调顺序上的两个事实：部分规则依赖入口统计，RT/异常只能在退出后完整记录；规则阻断与业务异常是不同信号。具体 Slot 顺序、参数与统计细节必须回到目标版本。

## 18. 调试断点建议

| 目标 | 观察点 | 要确认的现象 |
| --- | --- | --- |
| 资源是否正确 | entry 与资源包装对象 | 资源名没有携带高基数参数 |
| 规则是否加载 | 规则管理器更新点 | 新旧规则列表、来源与版本 |
| 窗口是否轮转 | 当前桶获取逻辑 | 桶起始时间、索引、过期替换 |
| 流控为何阻断 | Flow/ParamFlow 检查点 | 当前统计、阈值、来源或参数值 |
| 熔断为何打开 | CircuitBreaker 评估点 | 最小请求数、比例、状态转换 |

断点调试只适合小流量复现；并发和性能问题应辅以日志、指标和压测。不要在生产高峰给统计热路径长时间打断点。
