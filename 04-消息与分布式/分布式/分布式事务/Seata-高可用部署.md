# Seata 高可用部署运行手册

> 主文：[[Seata]]。本文只描述 Seata 的可用性决策与演练，不替代 Nacos、数据库或基础设施的专门部署手册。

## 1. 先定义恢复目标

| 目标 | 需要回答的问题 |
|------|----------------|
| SLA | 哪些业务依赖全局事务，故障时可以拒绝还是必须降级？ |
| RTO | TC、注册中心或存储故障后，多久恢复事务协调能力？ |
| RPO | 是否允许丢失未决事务状态？不同存储模式如何保证？ |
| 降级 | TC 不可用时，哪些写请求拒绝，哪些可切到本地事务消息？ |

这些目标来自业务与演练结果，不能把固定节点数、可用性百分比或恢复秒数当作框架默认能力。

## 2. 架构原则

1. TC 多实例部署，客户端通过注册中心或明确的服务发现策略连接；验证实例切换与会话恢复。
2. TC 会话和锁状态使用与目标版本匹配的存储模式，并评估其一致性、持久化和恢复能力。
3. 注册/配置中心、TC 存储与业务数据库是不同故障域；各自需要独立监控和恢复预案。
4. 避免单一管理脚本直接删除 TC 元数据或 AT `undo_log`；恢复操作必须先停止新流量并保留审计证据。

## 3. 发布与故障演练

每次升级或变更至少演练：

- 单个 TC 实例宕机、滚动重启和网络抖动；
- TC 存储短暂不可用、主从/共识切换、备份恢复；
- 注册中心不可用时客户端缓存、重连和降级表现；
- 存在未决 AT/TCC 事务时的恢复、超时回滚和异常池处理；
- 降级开关从 AT/TCC 切换到“拒绝写入”或“本地事务 + 消息”的业务结果。

演练完成后记录：事务是否重复执行、是否出现脏回滚、锁是否正确释放、对账是否能收敛。

## 4. 经版本核对的存储配置项（Seata 2.6）

根据 [Seata 2.6 参数配置](https://seata.apache.org/docs/user/configurations/)，Seata 支持 `file`、`db`、`redis` 和 `raft` 等会话存储模式；其中 `file` 不支持高可用。选择 `db`、`redis` 或 `raft` 时，仍需分别验证底层存储的故障切换与恢复边界。

| 配置项 | 用途 | 部署验证 |
|--------|------|----------|
| `store.mode` | 选择事务会话存储模式 | 故障后未决事务状态是否可恢复 |
| `store.lock.mode` / `store.session.mode` | 在支持的版本中分别指定锁和会话存储 | 锁与会话的一致性、切换行为 |
| `server.raft.group` / `server.raft.server-addr` | Raft 模式的事务组与服务端地址 | 选主、快照、节点故障和恢复 |
| `metrics.enabled` / `metrics.exporterList` | 暴露 TC 健康和运行指标 | 监控是否覆盖每个 TC 实例 |

不要直接套用旧版 `file.conf`、`registry.conf` 或固定数据库主从脚本；配置文件格式和可用项随 Seata 版本变化，应以当前依赖版本的官方参数表为准。

## 5. 上线检查

- [ ] TC 实例、存储、注册/配置中心的依赖关系和故障域已画清。
- [ ] 已明确各业务的 RTO、RPO 与降级策略。
- [ ] 已验证升级、回滚、存储恢复和未决事务恢复。
- [ ] TC、存储、注册中心、全局事务状态和锁冲突均有告警。
- [ ] 运维人员有停止新流量、保留现场、恢复和对账的操作权限与流程。
