# Seata 监控与故障排查运行手册

> 主文：[[Seata]]。目标是让故障处理从“查日志猜原因”变成“按事务状态和分段指标定位”。

## 1. 最小观测面

| 层级 | 必备观测 | 优先排查的问题 |
|------|----------|----------------|
| 业务入口 | 请求 ID、业务键、xid、事务结果 | 同一业务是否重复发起全局事务？ |
| TM/RM | Begin/Register 耗时、异常、二阶段队列 | 调用传播、客户端线程池、重试是否异常？ |
| TC | 活跃/超时事务、分支状态、锁冲突、CPU/GC | 协调端是否拥塞、不可用或存储变慢？ |
| 数据库 | 慢 SQL、行锁、`undo_log` 增长和清理延迟 | 一阶段、回滚或清理是否阻塞？ |
| 对账与异常池 | 长期未终态事务、补偿次数、人工处理年龄 | 技术重试是否已经无法自动收敛？ |

## 2. 排障顺序

1. **关联身份**：以业务单号、xid、branchId 串起应用日志、TC 状态和数据库记录。
2. **确认状态**：区分一阶段未完成、全局提交中、回滚中、二阶段积压和已终态遗留数据。
3. **确认阻塞点**：分别检查 TC RPC、全局锁、数据库行锁/慢 SQL、下游 RPC 与 RM 线程池。
4. **先止血**：限流或关闭新增全局事务；核心资产类请求宁可明确失败，也不要绕过一致性保护。
5. **再恢复**：有限重试可恢复的事务；隔离长期异常数据；通过对账、补偿或人工后台收敛。

## 3. 三类常见事故

### 全局锁冲突激增

检查热点 `lockKey`、事务时长、锁重试和是否有绕过代理的写路径。处置顺序是热点限流/串行化、缩小事务范围、将可异步动作移出 AT；不要通过手工删除锁记录“解锁”。

### `undo_log` 持续增长

先确认二阶段清理积压、未终态事务、回滚失败或保留策略；只可在确认终态、完成对账并有备份时小批次清理。按创建时间直接删除会破坏尚需补偿的镜像。

### TC 不可用或恢复后事务堆积

先切断新全局事务流量，确认 TC 存储和注册发现，再观察事务恢复与超时策略。对无法自动收敛的分支进入异常池，以业务账本和对账结果决定补偿，不直接改业务数据。

## 4. 告警与复盘

告警要包含业务影响、xid/业务键、当前状态、持续时间和推荐操作。每次事故复盘至少回答：哪个阶段变慢、为什么监控未提前发现、降级是否有效、是否产生待对账数据，以及如何通过限流/超时/模式选择避免复发。

## 5. 经版本核对的观测配置（Seata 2.6）

根据 [Seata 2.6 参数配置](https://seata.apache.org/docs/user/configurations/)，可通过 `metrics.enabled` 启用指标，并使用 `metrics.exporterList` 选择导出器；Prometheus 导出端口由 `metrics.exporterPrometheusPort` 配置。采集地址、认证与端口暴露策略属于部署环境配置，不能照搬其他集群。

排查时优先保留以下证据，而不是先执行删除或强制回滚命令：

```text
业务单号 / requestId → xid → branchId → TC 全局与分支状态 → RM 日志 → 业务库与 undo_log 状态
```

这条关联链比单独查看某个日志文件或直接操作 TC 存储更可靠。
