#### 我的解释或答案要点

1. 以商品 42 为例。应用先查 Redis 的 product:42，命中就返回。未命中就查 MySQL，查到商品后回填 Redis。这个按需加载的模式叫 Cache-Aside（旁路缓存）
2. 旁路缓存的旧值回填发生在读写并发时：读请求 A 发现 Redis 缓存未命中，从数据库读到旧值，但尚未回填。此时写请求 B 更新数据库、提交事务，并删除对应的缓存键。随后 A 恢复执行，把之前读到的旧值写入 Redis，导致后续请求命中缓存时仍读到旧数据。关键时序是 **A 在 B 提交前读到旧值，却在 B 删除缓存后才回填**。

4. 普通 SET 会覆盖同名键的整个值。 如果 b 原来是 Hash，误执行 SET b hello 会成功，原有字段随即丢失。等到业务代码再次执行 HGET 或 HSET 时，才会收到 WRONGTYPE
5. Redis 通过**惰性删除和定期主动删除**清理过期键。设置 TTL 时，Redis 会记录键的到期时间。访问某个键时，如果发现它已过期，Redis 就将其删除，读取时按键不存在处理。同时，Redis 会定期分批检查设置了 TTL 的键，在一定的时间预算内清理已过期的键，使长期无人访问的键也能得到回收。因此，**键到期后就读不到旧值，但实际删除和内存释放可能稍晚发生**。

8. 按键合并（single-flight）解决缓存击穿的机制是：缓存命中时直接返回；未命中时，第一个请求按业务键登记一个回源任务，再检查一次缓存，仍未命中才查库并回填。此时到达的同键请求等待这个任务，共享它的结果或异常，不再各自查库。任务结束后移除登记，下次未命中可以重新加载。不同键可以并行回源，合并只在共享同一个组件实例的 JVM 内生效。 ^study-link-0537efc25903471e8553295f9781ebe3

9. 针对穿透两种方案：如果请求经常重复查询同一个不存在的 ID，优先用**短 TTL 空值缓存**：数据库确认查无记录后缓存一个空值标记，后续请求就能直接返回。若大量请求查询的是各不相同的无效 ID，空值很少被复用，而且已经给数据库造成压力，再考虑**布隆过滤器**，前提是能及时把新增的有效 ID 加入过滤器。两类流量都明显时，可以先查缓存，仅在未命中时查布隆过滤器，让正常缓存命中仍然只需一次读取。

10. 处理缓存雪崩，平时可以在业务允许的范围内为每个缓存键独立设置随机 TTL，把批量过期的时间错开。发生大面积未命中时，先合并同一键的回源请求，再限制所有键合计的数据库回源并发。如果 Redis 持续超时，就暂时熔断缓存访问，绕过缓存的请求仍要遵守回源上限。超出上限时，允许短暂陈旧的查询可以返回本地旧值，其余请求短暂等待或提示稍后重试。缓存恢复后继续保留回源限制，优先预热热点数据，等命中率回升、数据库负载稳定后再逐步放量。

| --- | --- | --- |
| **缓存击穿** | 数据库里有数据。**某个热点键**失效后，在第一笔查询完成回填之前，其他并发请求也查了同一条数据。重建越慢，重复查询越多。 | **按键合并回源请求**，让一笔查询负责重建，其余请求短暂等待并复用结果。如果业务允许短时陈旧，也可以在后台刷新时继续返回旧值。 |

```
import java.math.BigDecimal;
import java.util.concurrent.Callable;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.FutureTask;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.TimeoutException;
import java.util.function.Supplier;

public final class QueryService {

    public record ProfileKey(long tenantId, long patientId) {}
    public record ProductKey(long productId, String region) {}

    public record Profile(String summary) {}
    public record Product(String name, BigDecimal price) {}

    public interface Cache<K, V> {
        // 返回 null 表示未命中；缓存访问失败通过异常传递。
        V get(K key);
        void put(K key, V value);
    }

    public interface Repository<K, V> {
        // 返回业务对象；记录不存在或查询失败时抛出相应异常。
        V findRequired(K key) throws Exception;
    }

    private final Cache<ProfileKey, Profile> profileCache;
    private final Repository<ProfileKey, Profile> profileRepository;
    private final Cache<ProductKey, Product> productCache;
    private final Repository<ProductKey, Product> productRepository;

    // 每个业务长期复用一个实例，同一业务的并发请求才能共享进行中的任务。
    private final SingleFlight<ProfileKey, Profile> profileFlights = new SingleFlight<>();
    private final SingleFlight<ProductKey, Product> productFlights = new SingleFlight<>();

    public QueryService(
            Cache<ProfileKey, Profile> profileCache,
            Repository<ProfileKey, Profile> profileRepository,
            Cache<ProductKey, Product> productCache,
            Repository<ProductKey, Product> productRepository) {
        this.profileCache = profileCache;
        this.profileRepository = profileRepository;
        this.productCache = productCache;
        this.productRepository = productRepository;
    }

    public Profile getProfile(long tenantId, long patientId)
            throws InterruptedException, ExecutionException, TimeoutException {
        ProfileKey key = new ProfileKey(tenantId, patientId);

        return profileFlights.get(key, () -> profileCache.get(key), () -> {
            Profile profile = profileRepository.findRequired(key);
            profileCache.put(key, profile);
            return profile;
        }, 200);
    }

    public Product getProduct(long productId, String region)
            throws InterruptedException, ExecutionException, TimeoutException {
        ProductKey key = new ProductKey(productId, region);

        return productFlights.get(key, () -> productCache.get(key), () -> {
            Product product = productRepository.findRequired(key);
            productCache.put(key, product);
            return product;
        }, 100);
    }

    private static final class SingleFlight<K, V> {
        private final ConcurrentHashMap<K, FutureTask<V>> inFlight =
                new ConcurrentHashMap<>();

        V get(K key, Supplier<V> readCache, Callable<V> loadAndCache, long waitMillis)
                throws InterruptedException, ExecutionException, TimeoutException {
            V cached = readCache.get();
            if (cached != null) {
                return cached;
            }

            FutureTask<V> task = new FutureTask<>(() -> {
                // 从首次未命中到登记任务之间，另一个请求可能已经完成回填。
                V latest = readCache.get();
                return latest != null ? latest : loadAndCache.call();
            });

            FutureTask<V> existing = inFlight.putIfAbsent(key, task);
            if (existing != null) {
                // 同键已有任务。等待超时只影响当前请求，原任务继续执行。
                return existing.get(waitMillis, TimeUnit.MILLISECONDS);
            }

            try {
                // 只有登记成功的请求才执行任务，其他同键请求共享结果或异常。
                task.run();
                return task.get();
            } finally {
                inFlight.remove(key, task);
            }
        }
    }
}
```

#### 我的解释或答案要点

1. 以“支付成功后加积分”为例，消费失败后先判断再次执行有没有机会成功：遇到已回滚的数据库死锁，可以由积分服务在本地短暂重试；如果依赖需要时间恢复，可以让 RabbitMQ 延迟重投。RabbitMQ 4.3+ 的仲裁队列能管理延迟和失败次数；使用 classic queue 时，积分服务用 `retryAttempt` 记录重试轮次，依次把消息发到 10 秒、20 秒、30 秒的等待队列，确认发布并路由成功后再 ACK 当前投递，RabbitMQ 在 TTL 到期后通过死信交换机把消息送回积分队列。任意一次加积分成功，都在事务提交后 ACK；如果首次处理和随后 3 次重试全部失败，或一开始就发现消息缺少必填字段，则拒绝消息并设置 `requeue=false`，让它进入最终死信队列，供告警、排查和修复后重放。所有重试和重放都沿用同一个 `eventId`，避免重复加积分。 ^study-link-d4e7a8b0307845b7ae17e2f33a9c07a4

   [[#^study-block-4b2b1a14d06847139b245b4b7c61bc8a|查看实践证据：延迟重投]]

2. RabbitMQ 的仲裁队列（quorum queue）是一种基于 Raft 的持久化队列，在 Spring Boot 中可以用 `QueueBuilder.durable("points.queue").quorum()` 声明。它将消息复制到多个节点，生产者开启发布确认后，只有多数副本接受消息，RabbitMQ 才会返回 ACK；典型的三副本队列因此可以容忍一个节点故障。从 RabbitMQ 4.3 开始，仲裁队列还支持延迟重投：在前面的积分示例中，消费者在积分事务提交后发送 ACK，遇到可重试失败则调用 `basicReject(deliveryTag, true)`，由 RabbitMQ 记录失败次数，按配置分别等待 10 秒、20 秒、30 秒再投递。若第 3 次重试仍失败，消息就经配置好的死信交换机进入死信队列。积分服务仍需按 `eventId` 幂等入账，以处理“积分已提交、ACK 尚未送达”时可能发生的重复投递。 ^study-link-beaed2b2e59f490f8a881cdd2f9ae982

   [[#^study-block-e684d14e53fa44ec932d83cc9ea1e3e1|查看实践证据：import org.springframework.amqp.core.Queue;]]

3. 判断 RabbitMQ 消息积压，要看一段时间内的趋势：`Ready` 持续上涨，说明等待投递的消息越来越多；`Unacked` 长时间居高且 ACK 速率下降，说明消息已投递，但处理或确认变慢。再结合入队速率、消费者数量和实际入账延迟定位原因：如果是**短时流量高峰**，峰后队列能在业务时限内清空，就让它自然消峰；如果**消费者数量为零**，先恢复实例或监听器；如果**单条处理耗时正常，但长期消费不过来**，确认下游有余量后增加并发；如果**数据库或外部接口变慢**，先修复慢查询、锁等待或依赖故障，必要时限制并发；如果**业务已完成但消息迟迟未确认**，检查手动 ACK 是否遗漏；如果**同一批消息反复重投**，对瞬时故障采用有限次延迟重试，对永久错误直接转死信。最后用**积压量持续下降、业务延迟恢复正常**两项指标确认处理有效。
4. 为什么会重复消费。 支付事件已进入 RabbitMQ，但生产者没收到发布确认，可能重发同一事件；积分已入账，但 RabbitMQ 没收到消费 ACK，也可能重新投递。因此，即使支付只成功一次，积分服务也可能多次收到同一笔支付，必须保证只加一次积分。
5. 从支付成功到积分入账。 支付服务在同一事务中将支付单更新为“已支付”，并写入 `PENDING` 的 Outbox 事件。后台任务用固定的 `eventId` 发布消息，收到发布 ACK 且确认消息未被退回后，将事件标为 `SENT`；发布失败或确认超时则保留 `PENDING`，后续重发。积分服务在同一事务中先插入以 `paymentId` 为唯一键的积分流水，插入成功才增加余额，提交后发送消费 ACK。消费 ACK 结束本次投递，不改变 Outbox 状态；积分是否到账以已提交的流水为准。
6. 并发消费时如何保证只加一次。 两个消费者无需先查流水，可以直接插入同一个 `paymentId`。A 先插入但尚未提交时，B 的普通快照读看不到这条流水，但 B 的 `INSERT` 必须检查唯一索引，因此会等待 A 的事务结果。若 A 提交，流水和余额同时生效，B 收到该支付单的重复键错误，跳过加分；若 A 回滚，B 可以继续插入并加分。若 B 遇到锁超时或死锁，则按失败重试。
7. 唯一键冲突在哪里捕获，影响何时 ACK。 在 MySQL InnoDB + Spring JDBC 下，如果在 `@Transactional` 方法内直接捕获流水 `INSERT` 抛出的 `DuplicateKeyException`，InnoDB 只回滚这条语句，异常也没有传到 Spring 事务代理。确认是同一支付单重复后，方法可以正常结束，消费者在最外层事务提交后 ACK。如果异常先穿过内层事务代理，而内外层以默认的 `REQUIRED` 共享事务，内层代理会按默认规则将事务标记为 `rollback-only`；外层再捕获也无法清除标记，最终提交时可能抛出 `UnexpectedRollbackException`，此时应按失败处理。

8. 我们选 RabbitMQ，主要是因为支付成功后加积分是一个按笔处理的异步任务：支付接口可以先返回，积分服务处理完一笔就确认一笔，临时失败就延迟重试，多次失败再进死信队列。支付侧用 Outbox 保证事件可重发，积分侧用 `paymentId` 唯一流水防止重复加分，事务提交后才 ACK。Kafka 的优势是长期保留事件，让多个消费组独立读取、回放；这条链路更关心每笔积分能否及时到账，历史回放需求不强。RocketMQ 也适合这个场景，它的事务消息能通过回查协调支付事务和事件发布，但我们已经用 Outbox 解决了这个问题，所以选 RabbitMQ 就能满足需求。

9. 支付成功后异步加积分时，RocketMQ 的做法是：支付服务先发送一条积分服务暂时看不到的**半消息**，再执行本地事务，将支付单更新为已支付；事务提交后发送 `COMMIT`，Broker 才让积分服务消费。如果支付服务在提交后宕机，导致 Broker 没收到 `COMMIT`，**Broker 会主动向支付服务回查**，由支付服务按支付单号查询本地事务结果：确认已提交就返回 `COMMIT`，确认已回滚就返回 `ROLLBACK`，暂时无法判断就返回 `UNKNOWN`。**RabbitMQ + Outbox 则由支付服务主动补发**：先在同一数据库事务中写入支付成功记录和 `PENDING` 事件，再由后台任务发布；收到发布确认且消息未被退回后标为 `SENT`，否则沿用原 `eventId` 重试。两种方案都可能重复投递，积分服务仍要用 `paymentId` 唯一流水保证同一笔支付只加一次积分。

1. Redis 在 Linux 上使用 `epoll` 实现 I/O 多路复用：它先向内核登记要监听的套接字和关注的事件，再通过一次 `epoll_wait` 同时等待多个连接。当有新连接可以接受，或已有连接可以读写时，内核会返回就绪的套接字及事件类型，Redis 的事件循环再调用相应的处理函数。这样，一个线程就能管理大量连接，无需为每个连接单独创建线程。**就绪只表示可以进行 I/O，命令仍由 Redis 在读到并解析出完整请求后执行。**

3. RDB 和 AOF 是 Redis 的两种持久化方式。**RDB 保存某一时刻的数据快照**，重启时直接加载快照，适合备份和恢复大批数据；如果发生故障，只靠 RDB 恢复会丢失最近一次成功快照之后的修改。**AOF 追加记录修改数据的写命令**，重启时通过重放日志恢复数据；采用常见的每秒刷盘策略时，故障后通常可能丢失最近约一秒的写入。两者可以同时启用，Redis 重启时默认优先使用 AOF 恢复，因为它通常保留了更新的数据。
