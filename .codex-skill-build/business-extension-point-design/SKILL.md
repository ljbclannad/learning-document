# 业务扩展点设计

## 来源

本技能由项目笔记 [扩展点编程](../../05-系统设计与工程实践/工程思想/扩展点编程.md) 提炼而来。该笔记从 Spring 容器生命周期中的扩展点出发，将“稳定主流程 + 阶段契约 + 可插拔能力 + 显式装配”的结构迁移到业务系统设计。

使用本技能时，先阅读该笔记中与当前问题相关的章节；不要把其中的订单示例或 Spring API 当作固定实现模板。

## 适用范围

当用户需要为一个业务主流程增加或梳理校验、风控、审计、通知、租户差异化规则、配置开关或后置动作时使用，尤其是在以下信号同时出现时：

- 主流程中的 `if/else`、开关判断或后置逻辑持续增长；
- 能力有独立的配置、顺序、负责人或迭代节奏；
- 不同环境、租户或产品线需要启用不同能力；
- 新能力只是挂接在稳定流程的某个阶段，而不改变核心业务定义。

不适用于只有少量且稳定的逻辑、强一致的核心业务不变量，或多个步骤共享大量隐式状态的情况。此时应优先保持逻辑在应用服务或领域模型中，而不是为了可插拔而拆分。

## 工作方式

1. 先澄清主流程的目标、核心业务动作、状态变化、事务边界和不可破坏的业务不变量。
2. 识别稳定的业务生命周期阶段，再决定是否需要扩展点；不要先定义万能的 `process()` 接口。
3. 为每个拟定阶段明确阶段契约：
   - 哪些数据在此时已可靠可用；
   - 扩展能力可修改请求、中间结果，还是只能执行副作用；
   - 失败时是中断、回滚、重试，还是记录后继续。
4. 为每项能力分类：校验型、变换型或副作用型，并明确其顺序、启用条件、幂等要求和观测信息。
5. 选择机制：
   - 主流程必须等待结果且顺序重要时，使用同步处理器链；
   - 稳定主流程或框架需要在固定节点开放受控能力时，使用生命周期回调；
   - 核心结果已经确定、后续能力可以低耦合执行时，使用事件。
6. 在提出代码改动前，给出简洁的设计结论：生命周期阶段、扩展接口或事件契约、装配与排序方式、失败处理，以及为何该方案优于直接写在主流程中。

## 设计约束

- 主流程负责稳定的核心业务编排，扩展能力只负责阶段性规则或附加行为。
- 不依赖注册先后等隐式行为；顺序和启用条件必须显式且可测试。
- 不让后置的外部调用拖垮核心事务。需要可靠执行的副作用，应在核心数据提交后通过可靠事件、Outbox 或重试任务处理。
- 处理器上下文使用明确类型，区分只读输入、受控中间结果和最终输出；不要使用无约束的 `Map` 承载协议。
- 每个可重试或异步执行的能力都要说明幂等方案，并记录处理器名称、阶段、耗时、结果与失败原因。

## 交付物

根据任务规模，输出其中必要部分：

- 是否采用扩展点的判断及理由；
- 生命周期阶段表，包含可用数据、修改权限和失败语义；
- 扩展能力清单及分类、顺序和启用条件；
- 处理器链、生命周期回调或事件的选型理由；
- 关键接口或事件契约，以及测试、观测、幂等和回滚要点。

不要仅因为某个流程有多个步骤就生成处理器链代码。若阶段不稳定、业务不变量被拆散，或失败语义无法统一，应明确建议维持或重构核心业务模型。
