# Redis 生产高频专题：复制、Stream、安全与客户端

> **本文定位：**补齐 Redis 在生产与面试中常见的决策边界；命令与基础机制见 [Redis 主线知识笔记](Redis.md)，Lua 原子组合见 [Redis Lua](RedisLua.md)。

## 1. 复制确认与读写一致性

Redis 主从复制通常异步：主库返回写成功时，副本可能尚未收到该写入。主库故障切换后，最近写入可能丢失；从副本读也可能读到旧值。

- `WAIT <replicas> <timeout>`：等待指定数量副本确认已收到此前写入，可降低“写后立刻故障”的丢失概率。
- 它**不等于强一致或持久化确认**：副本确认后仍可能发生故障、未持久化或不被选为新主；超时返回也不回滚主库写入。
- 读副本只适合允许短暂陈旧的读；支付、库存、订单状态等关键决策应读主库或数据库事实，并以幂等、版本/状态机、唯一约束兜底。

**决策口诀：**`WAIT` 是风险收敛，不是最终正确性；缓存与副本是加速层，不是事实源。

## 2. Stream 消费组：Pending 与故障恢复

`XREADGROUP` 把已投递但尚未确认的消息放入 Pending Entries List（PEL）。业务成功后才执行 `XACK`；消费者宕机或超时未确认的消息必须被发现、认领和重试。

建议流程：

1. 正常消费：`XREADGROUP` → 执行业务 → `XACK`。
2. 定期巡检：用 `XPENDING` 观察积压、空闲时长和所属消费者。
3. 故障接管：使用 `XAUTOCLAIM` 自动认领长期空闲消息；旧版本可用 `XCLAIM`，但需要自己先筛选候选消息。
4. 重试有上限：记录重试次数；超过阈值进入死信 Stream / 人工补偿，而不是无限重放。
5. 消费端必须幂等：认领与网络超时都可能造成重复投递。

> `XAUTOCLAIM` 需要 Redis 6.2+；部署前应按实际版本确认命令可用性。

## 3. 安全基线

- 不将 Redis 直接暴露公网；通过网络隔离、安全组和绑定地址限制访问范围。
- 启用认证并使用 ACL 为应用配置最小命令、最小 key 前缀权限；不要让业务账号拥有 `CONFIG`、`FLUSHALL`、`KEYS` 等高危权限。
- 管理员与应用账号分离，凭证可轮换；生产链路按需要启用 TLS。
- 保留审计与告警：认证失败、高危命令、异常连接数、命令拒绝和慢客户端都应可观测。

## 4. 客户端治理

| 主题 | 建议 | 常见误区 |
| --- | --- | --- |
| 连接池 | 复用连接、限制上限并监控等待时间 | 每次请求新建连接，或无限增大连接池 |
| 超时与重试 | 区分连接、命令与业务总超时；重试要有退避和上限 | 超时后无脑重试，形成重试风暴 |
| Pipeline | 批量大小有界，控制返回结果的内存 | 一次塞入海量命令或大返回值 |
| 重定向 | Cluster 客户端应支持 `MOVED`/`ASK` | 把重定向当普通业务错误反复失败 |
| 慢客户端 | 监控输出缓冲、阻塞连接与副本延迟 | 只看 Redis CPU，忽略 client buffer |

排障先区分“Redis 真慢”与“客户端在排队”：结合连接池等待、应用线程池、网络 RTT、`SLOWLOG`、`LATENCY`、连接数和输出缓冲一起判断。
