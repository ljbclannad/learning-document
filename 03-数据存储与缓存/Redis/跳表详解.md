# 跳表详解：从有序链表到 Redis ZSet 的排名、范围与更新机制

> 本文以 **Redis Open Source 7.2.6** 的 `src/t_zset.c`、`src/server.h` 为源码基线，核查日期为 2026-10-28。内部指针布局、编码转换和优化分支只对应此版本；命令语义与实现细节分开讨论。
>
> Redis 的整体执行、缓存与故障模型见 [[Redis]]；完整业务链路见 [[Redis项目实践]]。本文用同一组节点推导跳表，再结合医生积分榜、延迟任务和时间索引解释工程边界。案例是教学模型，不代表已在生产落地。

跳表解决的不是“怎样把元素排好序”这么简单的问题，而是：**在频繁插入、删除和改分时，既保持顺序，又能快速定位一个范围或第 k 个元素。**

Redis ZSet 还多了一项要求：成员唯一，输入 member 就能找到分数。跳表擅长按顺序找位置，字典擅长按成员定位；两者协作才构成大 ZSet 的完整实现。只背“ZSet 底层是跳表”，会把唯一性、排名、编码和复杂度混在一起。

## 1. 从 ZSet 要回答的问题出发

### 1.1 一份医生积分榜需要两种索引

假设成员是稳定的医生 ID，score 是本月积分：

```redis
ZADD demo:doctors 10 doctor:a 20 doctor:b 30 doctor:c 40 doctor:d 50 doctor:e
ZSCORE demo:doctors doctor:c
ZRANK demo:doctors doctor:c
ZRANGE demo:doctors 0 2 REV WITHSCORES
ZRANGE demo:doctors 20 40 BYSCORE WITHSCORES
```

这些请求分别在问：某个成员的分数、某个成员的位置、最高的几个人、某个分数区间的人。只用哈希表，后面几种请求需要额外排序；只用按 `(score, member)` 排序的结构，又无法仅凭 member 直接确定搜索位置。

| 结构 | 主要回答的问题 | 自身不能直接解决的问题 |
| --- | --- | --- |
| 字典 | 这个 member 是否存在，score 是多少 | 第 k 个元素、分数区间 |
| 跳表 | 某个有序位置在哪里，附近有哪些节点 | 只知道 member 时的快速定位 |
| 带 span 的跳表 | 某元素排名是多少，第 k 个元素是谁 | 业务积分是否可靠、重复事件是否重复计分 |

在 skiplist 编码中，字典先取得 score，跳表再使用 `(score, member)` 定位。ZSCORE 平均可用哈希查找完成，ZRANK 仍需遍历跳表的搜索路径，并累加跨度。

### 1.2 唯一的是 member，不是 score

同一个 member 再次 ZADD 会更新原成员，元素数不会因此增加；不同 member 可以拥有相同 score。相同分数下，Redis 按 member 的字节序确定次序，不按插入时间、语言排序规则或 ID 的数值大小。

```redis
ZADD demo:ties 100 doctor:2 100 doctor:10 100 doctor:3
ZRANGE demo:ties 0 -1
```

顺序是 `doctor:10`、`doctor:2`、`doctor:3`。REV 会反转整个排序顺序，同分成员的顺序也会反转。若产品要求“积分高优先，同分按更早达成优先”，需要显式设计第二排序维度，不能期待 ZSet 默认知道达成时间。

这里的排名是每个成员占一个位置的序号，不是“同分并列第二，下一位第四”这种竞赛排名。

## 2. 先确认编码：不是每个 ZSet 都有跳表

### 2.1 小对象用紧凑布局，大对象用双索引

Redis 7.2.6 的 ZSet 主要有两种编码：

| 编码 | 数据布局 | 为什么选择它 |
| --- | --- | --- |
| listpack | 按顺序紧凑保存 member、score 对 | 小集合减少对象、指针与分配开销 |
| skiplist | 字典与跳表共同维护成员 | 规模增大后提高查找、排名与范围定位效率 |

listpack 没有本文后面讨论的多层 forward 与 span；成员查找或定位可能需要线性扫描。小集合扫描连续内存的常数成本可能很低，不能仅凭 O(N) 就断言比跳表慢。

7.2.6 默认配置中，`zset-max-listpack-entries` 为 128，`zset-max-listpack-value` 为 64，后者按成员字节长度判断。超过数量、成员长度限制，或不满足 listpack 安全扩展条件，都可能触发转换。实际实例可改配置，所以默认值不能代替 `CONFIG GET` 和 `OBJECT ENCODING` 的观察。

### 2.2 编码转换有成本，也有路径差异

从 listpack 转换时，需要把成员装入新建的字典与跳表，然后释放旧紧凑结构。这次写入承担了整个已有集合的转换工作，不能只按“新增一个元素”估算延迟。

在本版本普通 ZREM 路径中，删除到阈值以下不会立即自动缩回 listpack；但源码确实存在向 listpack 转换的函数，某些结果构造等路径会使用它。因此两个同样只有几条数据的 ZSet，编码可能因历史和生成路径而不同。

排查内存时先看编码、成员长度、数量与变更历史，不能按当前元素数直接认定“这个 key 应该占多少字节”。

## 3. 从有序链表推导多层索引

### 3.1 普通链表慢在定位，不慢在已知位置的接线

底层先保存一个完整有序链表：

```text
head → A(10) → B(20) → C(30) → D(40) → E(50) → null
```

如果已经知道 B 与 C，插入一个新节点的指针修改很少；真正花时间的是从 head 找到插入位置。给链表叠加稀疏索引，可以一次跨过多个底层节点。

下面人为指定节点高度，用于解释机制，不表示真实随机生成时必然得到这种布局：

```text
L2：head ───────────────────────→ D ───────→ null
L1：head ─────────→ B ───────────→ D ───────→ null
L0：head → A ─────→ B → C ───────→ D → E ───→ null
```

A、C、E 高度为 1，B 高度为 2，D 高度为 3。索引层中的 B 和底层的 B 是同一个节点的不同 level 槽位，不是复制了多份 member。

### 3.2 查找是在前进受阻时下降

查找插入 `(35, X)` 的位置：

1. L2 的下一节点 D 为 40，超过目标，停在 head，下降。
2. L1 可以跳到 B；下一节点 D 仍超过目标，停在 B，下降。
3. L0 从 B 走到 C；下一节点 D 超过目标，最终停在 C。

记录各层最后一个严格小于目标的节点，得到 `update = [C, B, head]`。这些前驱稍后用于接线和维护跨度。

“没有高层索引就查不到元素”是误解：底层始终完整，继续下降仍能找到。高层稀疏影响路径长度，不改变底层包含所有元素这个正确性基础。

### 3.3 随机层高代替确定性的再平衡

Redis 7.2.6 使用 `P = 0.25`，最高 32 层。以理想独立随机模型理解，节点先拥有一层，每次再以概率 p 晋升一层；实际随机数与封顶实现以源码为准。

对层数 L，在未触及上限时：

```text
P(L ≥ k) = p^(k-1)
P(L = k) = (1-p) × p^(k-1)
E[L] = 1 + p + p² + … ≈ 1/(1-p)
```

有 32 层封顶时，最后一层聚合更高层数的尾部概率，期望是有限几何和 `(1-p^32)/(1-p)`；p 为 0.25 时非常接近 1.333。

期望层数是**单个节点有几组 level 字段**，不是整个跳表高度，也不是一次查询的比较次数。整个结构的典型高度量级约为 `log_(1/p)(N)`；每层还会横向走若干步，因此不能因为 `log₄N` 比 `log₂N` 小，就断言 p=0.25 的查询快一倍。

随机层高让结构在期望意义上保持高效，并不提供红黑树式的最坏 O(log N) 保证。极端情况下可以接近线性扫描；“退化概率就是 p^k”也没有定义退化事件，不能作为严谨结论。32 层是实现上限，不是限制最多只能保存 `2^32` 个成员的容量公式。

## 4. Redis 节点布局：forward、span、backward 各管什么

### 4.1 结构字段与所有权

下面是字段关系示意，不是逐字复制的完整 C 声明：

```text
zset
  dict：member → 跳表节点中 score 的地址
  zsl：跳表头、尾、长度、当前有效层数

zskiplistNode
  ele：成员 SDS
  score：double
  backward：底层前驱
  level[节点高度]
    forward：这一层的后继
    span：这一跳跨过的底层位置数
```

在本版本实现中，字典 key 与跳表成员共享 SDS，字典 value 指向节点内的 score，并不是再复制一整份 member 和 score。共享可以节省内容开销，但字典桶、字典项、跳表节点、level 数组和分配器开销仍存在。

改分若换了节点，字典中的 score 地址必须更新；释放时还要避免重复释放共享成员。理解这点，才能看懂为什么 `zslUpdateScore` 返回新节点后，调用方仍需执行字典更新。

### 4.2 span 是位置差，不是 score 差

规定 header 的内部位置为 0，A 到 E 的内部位置依次为 1 到 5。若 forward 非空：

```text
span(u → v) = position(v) - position(u)
```

它不包括起点，包括终点。前面的结构对应：

```text
L2：head --4--> D --1--> null
L1：head --2--> B --2--> D --1--> null
L0：head --1--> A --1--> B --1--> C --1--> D --1--> E --0--> null
```

**forward 为 null 时，span 不一定是 0。** 在本文版本维护规则下，它可以表示当前节点后还剩多少底层成员：D 的高层后继是 null，但底层后面还有 E，因此跨度为 1。尾节点 E 后面没有成员，其底层末端跨度为 0。

搜索不会沿 null 前进；这些末端跨度是插入、删除公式能够一致工作的维护信息。将所有 null 边的 span 清零，可能暂时不影响遍历，却会破坏后续高层插入的计算。

### 4.3 backward 只需放在底层

先用高层定位区间末端，再沿 backward 逐个输出，可以实现逆序范围遍历。最高分开始的简单 Top N 可以直接从 tail 出发；一般逆序区间仍要定位起点。

不必每层都建 backward，因为高层负责定位，完整输出仍发生在底层。增加反向层索引会增加字段和维护成本，但不能简单说总内存“正好翻倍”：现有节点还包含 score、SDS、span 和其他对象开销。

## 5. 插入：为什么要同时记录 update 和 rank

### 5.1 两个数组保存不同信息

沿第 3 节路径插入 X(35)，尚未真正插入时：

| 层 | update[i] | rank[i]：前驱的内部位置 |
| --- | --- | --- |
| L2 | head | 0 |
| L1 | B | 2 |
| L0 | C | 3 |

`rank[0] = 3` 是**底层前驱 C 的位置**，不是新节点位置。插入后 X 的内部位置才是 `rank[0] + 1 = 4`。

下降到下一层时，要继承已走过的距离，再累加横向 span。如果每层都把 rank 清零，就会丢失高层已经跳过的节点数。

### 5.2 拆分跨度的公式来自位置差

假设 X 随机得到两层。对它参与的每一层 i，设：

```text
d = rank[0] - rank[i]
s = 插入前 update[i].span

插入后：
update[i].span = d + 1
X.span        = s - d
```

d 是前驱到旧底层插入前驱之间的距离；前半段再加 1，才包括 X 自身。两段相加为 `s + 1`，因为整个区间增加了一个节点。

逐层代入：

- L0：C 原来指向 D，s=1、d=0；变成 C→X 的 1、X→D 的 1。
- L1：B 原来指向 D，s=2、d=1；变成 B→X 的 2、X→D 的 1。
- L2：X 不参与这一层，但 head→D 跨过的底层节点增加了一个，span 从 4 增为 5。

```text
L2：head --5----------------> D --1--> null
L1：head --2--> B --2--> X --1--> D --1--> null
L0：head → A → B → C → X → D → E → null
内部位置：    1   2   3   4   5   6
```

**没有新 forward 的高层也要更新 span。** 只接好 X 参与的层，会出现按 score 查询正确、按 rank 查询错误的隐蔽故障。

### 5.3 新增最高层与维护边界

若 X 高度超过当前有效层数，新层前驱初始化为 header，rank 为 0，header 的旧 span 初始化为原长度。再套用同一拆分公式即可，包括新 forward 为 null 的情况。

最后要维护底层 successor.backward、X.backward、tail、length 和有效层数。header 是哨兵，不应作为第一个实际节点的 backward；空表的 tail 为 null。

插入成本不只有一次随机数：还包含前驱查找、节点分配、若干指针与跨度更新，ZSet 外层还要维护字典。表述为期望 O(log N) 是数量级，不是固定时延承诺。

## 6. 删除：连接合上了，跨度也必须合上

### 6.1 找到前驱之后分两类处理

删除 X 时，再按 `(score, member)` 找到各层前驱。对每一层：

```text
如果 update[i].forward == X：
    update[i].span = update[i].span + X.span - 1
    update[i].forward = X.forward
否则：
    update[i].span = update[i].span - 1
```

第一种情况合并两段，减掉被删除的 X；第二种情况虽然没有直接指向 X，当前边跨过的底层区间仍少了一个节点。

沿第 5 节示例删除 X：L1 的 B→D 变回 `2 + 1 - 1 = 2`，L2 的 head→D 从 5 变回 4。插入与删除的跨度变化互为逆过程。

### 6.2 连续删除可以复用边界

按 score 或 rank 删除连续区间时，先定位第一个目标之前的各层前驱，然后依次删除目标。因为删除连续发生在这些前驱之后，前驱路径可继续复用，不必每删一个都从 header 重新搜索。

但每个节点仍要更新结构、从字典移除并释放内存。大范围删除的成本与删除数相关，不是一次 O(log N) 就完成全部工作；一次删除几百万成员会占用主线程执行窗口。

还要更新后继 backward、尾节点，并在最高有效层为空时降低 level。降层不表示重新给其他节点抽取随机高度，也不要求销毁 header 预留的所有 level 字段。

## 7. 改分：ZADD 不总是简单删除再插入

### 7.1 ZSet 外层先决定是否允许修改

对于已存在成员，外层先处理 NX/XX、GT/LT、INCR 等语义，再判断分数是否实际变化。默认 ZADD 返回新增成员数；只是修改已存在成员时可以返回 0，不能据此认定“更新失败”。CH 才把发生修改的已有成员也纳入相应计数。

GT/LT 用于限制已有成员的新旧分数关系，单独使用不等于禁止添加新成员；需要时与 XX 配合。重试 ZINCRBY 会再次累加，因此原子加分并不等于按事件幂等计分。[ZADD 命令说明](https://redis.io/docs/latest/commands/zadd/)

### 7.2 本版本有一个保守的原地改分分支

`zslUpdateScore` 先找到旧节点。如果新 score 严格大于底层前驱的 score，且严格小于底层后继的 score，缺少相邻节点的一侧视为满足条件，就可直接改 score，位置与 span 都不变。

例如 C 从 30 改为 31，仍严格处于 B(20) 与 D(40) 之间，可以复用节点。不过搜索旧节点仍有成本，不能把整个 ZADD 改分路径说成 O(1)。

如果不满足这个充分条件，Redis 删除旧节点，再插入新节点，随后修正字典中的 score 地址。同分相邻时，即使从完整 `(score, member)` 次序看也许无需移动，这个严格 score 判断仍可能进入重插路径。因此“位置没变就一定原地改”也不符合该版本实现。

### 7.3 共享字符串为什么不会被顺手释放

重插可以复用旧 SDS 成员，但旧节点需要释放。实现会先转移成员所有权，避免释放旧节点时一并释放仍被新节点和字典使用的字符串。

教学实现如果使用 Map 保存 member→Node，必须在替换节点后同步更新 Map；如果保存 member→score，也必须同步新分数。只保证底层链表排序正确，不足以保证字典和跳表描述的是同一份集合。

## 8. 排名：把每条跳跃边理解为长度

### 8.1 查 member 的排名，是沿搜索路径累加 span

ZSet 先通过字典取得 score，然后按 `(score, member)` 查找。每次向右走都累加 span，最终到目标节点时得到其内部 1-based 位置。

原始 A 到 E 中，查 C：从 L1 跳到 B，累计 2；下降到 L0 再到 C，累计 3。Redis 对外 ZRANK 为 0-based，因此返回 2。

由于一次高层跳跃已经跨过中间节点，后续不能再补数这些节点，否则重复计数。span 的价值就是把一次跳跃带过的数量显式记录下来。

### 8.2 查第 k 个元素，是不超过目标位置地前进

从 header 开始，累计距离 traversed=0。在每一层，只要下一节点非空且：

```text
traversed + 当前边.span ≤ 目标内部位置 k
```

就可以前进。达到 k 即找到目标；本层再走会超过 k 时下降。对外 rank=2 对应内部 k=3。

调用方应限制 `1 ≤ k ≤ length`。不能让调用方把内部 rank=0 当普通元素传入，再期待底层函数替它屏蔽 header；内部函数的有效参数前提与公开命令的边界处理不是一回事。

### 8.3 正序、逆序、负下标分别换算

设总数为 N，一个元素内部位置为 r：

```text
正序 0-based 排名 = r - 1
逆序 0-based 排名 = N - r
逆序 rank=s 对应内部位置 = N - s
```

`ZRANGE key 0 1 REV` 取最高的两个，不是“取正序的第 0 到 1 个再反转”。`-1` 表示当前方向的末尾索引，负数先按 N 换算，再处理越界；简单把所有负下标钳成 0 并不兼容 Redis。

`start`、`stop` 两端包含，取 10 个元素常用 0 到 9。空范围、超出长度和空集合都应有明确返回，不能让教学代码示例只在中间位置工作。

## 9. 范围查询：定位、跳过、输出分别计成本

### 9.1 按 score：先下界定位，再底层扫描

头尾检查只能排除一定没有交集的情况，不能证明范围内一定有元素：集合只有 10 与 50 时，区间 [20,40] 与整体最小最大值范围重合，但没有结果。

沿高层跳过所有小于下界的节点，到底层取得候选后，再检查上界。闭区间下界需要 `score ≥ min`，开区间需要 `score > min`。定位到第一个匹配后沿 L0 输出，直至超过上界。

逆序则定位最后一个符合上界的节点，再沿 backward 输出。指针能跳得远并不意味着输出也可以跳着给；高层不包含全部成员，直接遍历高层会漏结果。

### 9.2 深分页的两种 offset 不是一回事

```redis
ZRANGE demo:doctors 100000 100009
ZRANGE demo:doctors -inf +inf BYSCORE LIMIT 100000 10
```

对 skiplist 编码，第一条按全局 rank 定位，可利用 span 跳到起点；第二条在 7.2.6 的 score 范围实现中，先定位下界，再逐个跳过 offset。因此后者需要考虑 `O(log N + offset + M)`，不能看到 LIMIT 10 就认为只访问十个节点。

小 listpack、输出字节数和客户端解码另有实际成本；上述比较针对指定编码与实现路径。未来版本可能优化某条路径，不能把本版本代码当永久 API 承诺。

### 9.3 BYLEX 不是任意 ZSet 的第二棵字典序索引

BYLEX 的可靠使用前提是相关集合成员具有相同 score，字节序因而与物理顺序一致。混合 score 时，成员整体按 score 分组，不能把 BYLEX 当成忽略 score 的全局字符串索引。[ZRANGE 命令说明](https://redis.io/docs/latest/commands/zrange/)

如果确实需要任意字典序检索，通常另外建同分索引，并明确双索引更新、恢复与一致性责任；不要把一份 ZSet 同时想象成多棵独立排序树。

## 10. 精度、比较器和内存里的隐藏坑点

### 10.1 double 不是任意精度整数容器

score 使用 IEEE 754 double，可精确表示 `[-2^53, 2^53]` 范围内的所有整数，超过范围后不是每个整数都可区分。`9007199254740992` 与 `9007199254740993` 会落到相同 double 值。

当前量级的 Unix 毫秒时间戳通常在精确整数范围内，但纳秒时间戳、超大 ID、`积分×大倍数+时间` 的复合值很容易越界。必须对整个取值域计算上界，不能只测几个小样本。

NaN 无法参与正常的全序比较，Redis 不接受它作为 score；正负无穷可以表达极值。本文 Java 教学实现只接受有限数，以减少边界面，不声称完整复制 Redis 数值语义。

### 10.2 Java 自然字符串序不总等于 Redis 字节序

Java String 的自然比较基于 UTF-16 代码单元，Redis 比较成员字节串；当应用使用 UTF-8 编码时，不能宣称两者对所有 Unicode 字符都同序。生产客户端还要保证相同业务身份序列化为相同 bytes。

`Double.compare(-0.0, +0.0)` 会区分两个值，而 Redis score 的数值比较并不把它们当成两档分数。教学实现若直接套一个语言比较器，需要说明偏差，或规范化零。

比较器必须稳定且满足顺序关系；插入后修改参与排序的字段会让节点实际位置与比较结果矛盾。即使线程安全，也无法自动修复这种“不经索引协议改键”的错误。

### 10.3 “平均 1.33 个指针”不能拿来算整个 ZSet 内存

1.33 是 p=0.25 下每节点 level 数的近似期望，每层还同时有 span。除此之外还有 backward、score、SDS 指针与内容、字典桶和 entry、header、分配器对齐以及碎片。

跳表节点通常独立分配，沿底层遍历的控制流连续不等于物理地址连续；它不天然具有数组或 listpack 那样的内存布局。比较红黑树时也不能只拿“两根子指针”对照全部跳表开销，而忽略树的父指针、子树大小和对象布局。

## 11. 一份可编译的 Java 教学实现

下面实现成员唯一、插入/改分、删除、排名、按排名取值和 score 范围查询，用来核对前面的公式。保存为 `TeachingZSet.java` 即可编译。

边界明确如下：只接受 ASCII member 和有限 score；rank 对外为 0-based，越界返回 null；范围只支持闭区间、正序，不实现 Redis 负下标与全部选项。它不做 listpack、网络、持久化和并发控制，不能作为生产 Redis 的替代品。更新已有成员统一删除再插入，便于核对正确性，没有复制 Redis 的原地改分优化。

```java
import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.Objects;
import java.util.Random;

public final class TeachingZSet {
    private static final int MAX_LEVEL = 32;
    private final Random random;
    private final Node head = new Node(MAX_LEVEL, 0, null);
    private final Map<String, Node> byMember = new HashMap<>();
    private Node tail;
    private int level = 1;
    private long size;

    private static final class Node {
        final double score;
        final String member;
        final Node[] next;
        final long[] span;
        Node prev;

        Node(int height, double score, String member) {
            this.score = score;
            this.member = member;
            this.next = new Node[height];
            this.span = new long[height];
        }
    }

    public TeachingZSet(long seed) {
        random = new Random(seed); // 固定种子便于重现实验。
    }

    private static int compare(Node node, double score, String member) {
        int c = Double.compare(node.score, score);
        return c != 0 ? c : node.member.compareTo(member);
    }

    private static void validate(double score, String member) {
        Objects.requireNonNull(member, "member");
        if (!Double.isFinite(score)) {
            throw new IllegalArgumentException("只接受有限分数");
        }
        for (int i = 0; i < member.length(); i++) {
            if (member.charAt(i) > 127) {
                throw new IllegalArgumentException("教学实现只接受 ASCII 成员");
            }
        }
    }

    public long size() {
        return size;
    }

    // 返回是否新增；已有成员改分返回 false，不表示更新失败。
    public boolean add(double score, String member) {
        validate(score, member);
        if (score == 0.0) score = 0.0; // 将负零规范化为正零。
        Node old = byMember.get(member);
        if (old != null && old.score == score) return false;
        if (old != null) remove(member);

        Node[] update = new Node[MAX_LEVEL];
        long[] rank = new long[MAX_LEVEL];
        Node x = head;
        for (int i = level - 1; i >= 0; i--) {
            rank[i] = i == level - 1 ? 0 : rank[i + 1];
            while (x.next[i] != null && compare(x.next[i], score, member) < 0) {
                rank[i] += x.span[i];
                x = x.next[i];
            }
            update[i] = x;
        }
        int height = 1;
        while (height < MAX_LEVEL && random.nextDouble() < 0.25) height++;
        if (height > level) {
            for (int i = level; i < height; i++) {
                update[i] = head;
                rank[i] = 0;
                head.span[i] = size;
            }
            level = height;
        }
        x = new Node(height, score, member);
        for (int i = 0; i < height; i++) {
            long distance = rank[0] - rank[i];
            x.next[i] = update[i].next[i];
            x.span[i] = update[i].span[i] - distance;
            update[i].next[i] = x;
            update[i].span[i] = distance + 1;
        }
        for (int i = height; i < level; i++) update[i].span[i]++;
        x.prev = update[0] == head ? null : update[0];
        if (x.next[0] == null) tail = x;
        else x.next[0].prev = x;
        size++;
        byMember.put(member, x);
        return old == null;
    }

    public boolean remove(String member) {
        Node target = byMember.get(member);
        if (target == null) return false;
        Node[] update = new Node[MAX_LEVEL];
        Node x = head;
        for (int i = level - 1; i >= 0; i--) {
            while (x.next[i] != null
                    && compare(x.next[i], target.score, member) < 0) {
                x = x.next[i];
            }
            update[i] = x;
        }
        for (int i = 0; i < level; i++) {
            if (update[i].next[i] == target) {
                update[i].span[i] += target.span[i] - 1;
                update[i].next[i] = target.next[i];
            } else {
                update[i].span[i]--;
            }
        }
        if (target.next[0] == null) tail = target.prev;
        else target.next[0].prev = target.prev;
        while (level > 1 && head.next[level - 1] == null) level--;
        size--;
        byMember.remove(member);
        return true;
    }

    public Long rank(String member) {
        Node target = byMember.get(member);
        if (target == null) return null;
        long traversed = 0;
        Node x = head;
        for (int i = level - 1; i >= 0; i--) {
            while (x.next[i] != null
                    && compare(x.next[i], target.score, member) <= 0) {
                traversed += x.span[i];
                x = x.next[i];
            }
            if (x == target) return traversed - 1;
        }
        throw new IllegalStateException("字典与跳表不一致");
    }

    public String at(long rank) {
        if (rank < 0 || rank >= size) return null;
        long target = rank + 1;
        long traversed = 0;
        Node x = head;
        for (int i = level - 1; i >= 0; i--) {
            while (x.next[i] != null && traversed + x.span[i] <= target) {
                traversed += x.span[i];
                x = x.next[i];
            }
            if (traversed == target) return x.member;
        }
        throw new IllegalStateException("跨度不一致");
    }

    public List<String> between(double min, double max) {
        if (!Double.isFinite(min) || !Double.isFinite(max)) {
            throw new IllegalArgumentException("只接受有限边界");
        }
        List<String> result = new ArrayList<>();
        if (min > max) return result;
        Node x = head;
        for (int i = level - 1; i >= 0; i--) {
            while (x.next[i] != null && x.next[i].score < min) x = x.next[i];
        }
        x = x.next[0];
        while (x != null && x.score <= max) {
            result.add(x.member);
            x = x.next[0];
        }
        return result;
    }
}
```

验证这份实现不能只打印“插入成功”。用一个 `Map<String, Double>` 作为简单参考模型，每次变更后将它按 `(score, member)` 排序，再比较每个成员的 rank、每个位置的 at 和范围结果。还应检查每层的 span 等于真实底层位置差，以及 backward 与 tail 一致。

特别测试：空表、首尾删除、删除后重插、已有成员改到最前/最后、大量同分、负零、非法 NaN、删除到只剩一层，以及 null 后继的末端跨度。它们比一段固定演示输出更容易发现结构损坏。

## 12. 工程取舍：为什么可选跳表，不意味着树不行

| 结构 | 按键定位 | 动态有序更新 | 按排名定位 | 范围输出 |
| --- | --- | --- | --- | --- |
| 哈希表 | 平均 O(1) | 不维护有序性 | 需额外结构 | 通常先筛选/排序 |
| 带 span 跳表 | 期望 O(log N) | 期望 O(log N) | 期望 O(log N) | 期望 O(log N+M) |
| 带子树大小的平衡树 | 最坏 O(log N) | 最坏 O(log N) | 最坏 O(log N) | O(log N+M) |
| 有序数组 | 二分 O(log N) | 移动元素 O(N) | O(1) | 定位后顺序输出 |

表中忽略键比较的字节成本、分配器和缓存效果；M 是输出规模。Redis 的字典+跳表是组合索引，因此 ZSCORE 与跳表按有序键定位不能混为一项比较。

跳表不需要旋转和颜色维护，span、底层双向链和局部接线比较直接；平衡树同样支持范围扫描，维护子树大小后也能提供排名。因此合理的论证是实现与维护成本的取舍，而不是“红黑树不能范围查询”或“跳表一定更省内存”。

普通跳表不天然线程安全，改一个 forward 的 CAS 也不能同时完成多层跨度与字典更新。Redis 常规命令串行执行为这些内部修改提供执行边界；Java 并发跳表是另外一套并发协议，不自动具有本文带排名跨度的能力。不要在教学类外随意加几把节点锁，就声称获得等价并发容器。

## 13. 医生积分榜：从有序结构到业务规则

### 13.1 member 保存稳定身份，score 保存可比较度量

key 可以按医院与月份划分，member 使用稳定医生 ID。把展示姓名拼入 member，改名会变成删除旧成员、插入新成员，还可能产生重复身份。展示资料宜从独立画像或数据库读取，并处理榜单成员与资料快照的版本关系。

如果一条积分事件到达两次，ZINCRBY 会加两次。应在持久积分流水中按稳定事件 ID 去重，再生成可重放的榜单更新。若采用绝对分数快照，乱序旧快照也可能覆盖新分数，仍需版本协议；只有业务保证分数绝不下降时，单纯 GT 才可能符合一部分需求。

### 13.2 同分规则不能靠过大的浮点拼接补救

若规则是积分降序、达成时间升序、医生 ID 升序，单个 score+member 可以表达的排序必须经过精确编码设计。用 `score = points × 10^13 + timestamp` 容易超精度，并且 REV 会反转所有次序，时间方向可能与需求相反。

可选择在有限取值域中设计可证明的整数编码，或使用固定宽度字节序成员辅助排序；但成员一旦包含可变排序字段，就要另存稳定 ID 到成员编码的映射并原子替换。也可以让数据库生成固定版本榜单，Redis 只缓存已确定顺序。选择应从业务排序规则出发。

### 13.3 分页需要定义是否允许榜单变化

读取第一页后，有人加分进入前列，第二页 offset 相同却可能重复或漏掉成员。一次 ZRANGE 内部结果不会被另一普通命令插入修改，但多次分页请求不是同一快照。

只用“上一页最后一个 score”作为游标，若下一页使用排他下界，会漏掉同分其他成员；使用包含下界又可能重复甚至无法前进。复合游标需携带 `(score, member)` 并设计服务端过滤或额外索引，原生 BYSCORE 边界不是任意二元组边界；大量同分时不能无界读回全部同分成员。

实时页面可以接受变化并去重，审计导出宜固定榜单版本。要同时查“我的排名”和“附近几人”，两条独立命令中间也可能变更；需要一次观察语义时，用有界 Lua 组合，或者返回明确的榜单版本。

### 13.4 拆榜后的全局排名不是免费得到的

一个 ZSet key 只能落在一个槽；增加 Cluster 节点不能把它内部跳表自动拆到多台机器。按医院、月份分榜可以分散负载，但跨分片全局 Top K 需要合并候选，全球排名还要额外计算。

在固定分区、统一全序且各分片读取同一快照的前提下，从每个分片取 Top K 再合并可以求全局 Top K；动态多次读取并不自动满足这个快照前提。不能把“单榜 ZRANK 很快”推导为“任意分片后全局排名也很快”。

## 14. 延迟任务与时间索引：排序不等于可靠执行

### 14.1 score 是截止时间，member 是任务身份

用毫秒时间作 score，可以快速取得到期候选；同一毫秒多个任务只要 member 不同就不会冲突。若 member 使用任务类型如 `close-order`，反复 ZADD 更新的是同一个成员，可能只剩最后一笔订单任务。

任务 payload 应有可靠保存与可恢复引用。ZSet 中存在一个 ID，不等于其对应数据仍可用；把 payload 放在更短 TTL 的缓存里可能得到无法执行的悬空任务。

### 14.2 弹出最小值不会判断“现在是否到期”

ZPOPMIN 原子移除最小元素，但没有“score 必须小于当前时间”的条件；BZPOPMIN 在集合非空时也可能立即取到未来任务。先查再删则存在多消费者竞争，需要原子校验与领取协议。

即使领取原子，领取后进程崩溃仍可能丢处理。可把 due 转入带租约的 processing，再确认完成；或让数据库保存任务真相，Redis 只加速候选发现。接管旧租约不会停止旧工作线程，业务操作仍需幂等。完整恢复路径见 [[Redis项目实践]]。

### 14.3 时间序列需要独立的事件唯一标识

用 timestamp 作 score、eventId 作 member，可以保存同一时刻的多条事件；若 member 是可重复的测量值，后一次相同值会更新旧成员而不是新增采样。

按时间查范围不自动提供降采样、压缩、去重窗口或跨实例聚合。长期时间序列应评估专门存储的能力。清理旧数据时，ZREMRANGEBYSCORE 的返回条数代表删除工作量，大批量清理需控制批次与执行时间，不能因定位起点快就忽略释放成本。

## 15. 用可复现实验核对命令与实现

以下命令仅用于独立测试实例，示例使用专属 key。编码阈值实验应在实例启动参数中设置，避免为了实验修改业务实例配置。

### 15.1 同分、改分、逆序与范围边界

```redis
ZADD demo:order 10 a 20 b 20 c 40 d
ZRANGE demo:order 0 -1
ZRANGE demo:order 0 1 REV
ZRANGE demo:order -2 -1
ZRANGE demo:order (10 20 BYSCORE
ZRANGE demo:order 20 (10 BYSCORE REV
ZADD demo:order 30 b
ZRANK demo:order b
ZREVRANK demo:order b
ZCARD demo:order
```

依次应观察：正序 `a,b,c,d`；逆序前两名 `d,c`；正序末两名 `c,d`；两个分数范围分别为 `b,c` 与 `c,b`。把 b 改为 30 后，ZADD 默认返回 0，正序排名为 2、逆序排名为 1，成员数仍为 4。

这里是 redis-cli 交互输入；若写成 shell 命令，`(10` 等参数需用引号包围，避免 shell 把括号当语法。

### 15.2 编码转换与删除后的历史

在独立实例将 `zset-max-listpack-entries` 设为 4，成员长度阈值保持足够大：

```redis
ZADD demo:encoding 1 a 2 b 3 c 4 d
OBJECT ENCODING demo:encoding
ZADD demo:encoding 5 e
OBJECT ENCODING demo:encoding
ZREM demo:encoding b c d e
OBJECT ENCODING demo:encoding
```

7.2.6 预期依次是 listpack、skiplist、skiplist。它同时验证“超过阈值会转换”与“普通删除到很小不立即缩回”。不要拿这个结果推断所有命令路径、版本或重建后的对象都永不缩回。

### 15.3 精度与业务语义反例

```redis
ZADD demo:precision 9007199254740992 a 9007199254740993 b
ZRANGE demo:precision 0 -1 WITHSCORES
ZADD demo:update GT 10 newcomer
ZADD demo:update XX GT 20 missing
```

前两个整数会以相同 score 存储；GT 单独使用可新增 newcomer，而 XX GT 不会创建 missing。另用负零、正零与 NaN 验证数值边界，避免客户端自己的预处理掩盖服务端行为。
