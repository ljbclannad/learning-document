# MySQL分库场景题

本文以省级医疗平台为教学场景，讨论患者主索引、就诊、收费、床位和医技报告在分库后的设计取舍。方案与容量数字均不代表已上线项目；没有压测依据时，不以“超过某个行数就必须分库”作为结论。

数据库机制以 MySQL 8.0 / InnoDB 为基线；ShardingSphere 概念和配置片段以 5.5.2 为例。片段不构成完整部署配置。单实例索引、锁与事务见 [[MySQL]]，表内分区见 [[数据分区]]；本文关注分片改变后的路由、约束和恢复边界。

## 1. 需求建模与拆分维度

### 1.1 先确定需要共同提交的数据

分片键决定“哪些记录能自然放在一起”，也决定本地唯一索引、事务和关联查询能够覆盖的范围。选择之前，先列出高频访问、必须原子提交的写集合、单个热点实体的峰值，以及允许延迟的读模型。

| 业务 | 主要写入与约束 | 常见查询 | 本文的候选设计 |
| --- | --- | --- | --- |
| 患者主索引 CPI / EMPI | 身份标识绑定、合并与拆分审计 | 证件定位、院内 ID 映射 | 初期独立关系型主库，达到瓶颈后再拆身份索引与患者档案 |
| 挂号、就诊、处方 | 单次操作内的状态与明细共同提交 | 医院、科室、日期 | 医院映射到物理库，明细按固定归属月份分表 |
| 收费流水 | 订单、账务明细、幂等结果一致 | 医院、收费号、账期 | 同一收费聚合共置，医保局查询走对账读模型 |
| 床位分配 | 一床至多一个有效占用 | 医院、病区、床位 | 优先按医院共置当前分配与请求记录 |
| 医技报告 | 审核状态、版本与发布事件一致 | 就诊详情、患者历史、项目检索 | 医院写模型 + 患者时间线；大文件放 PACS / 对象存储 |

先尝试索引、SQL、归档和访问隔离，再确认是否需要水平拆分。分表降低单表维护粒度，但如果表仍在同一实例，不会凭空增加 CPU、IO 或写入能力。按医院分库只能分散不同医院，不能把一家大医院的写热点自动拆开。

“一个医院一库”也不等于故障独立：多个 schema 若共享同一实例、连接池或代理，仍可能一起受影响。要按实例资源、依赖和故障域验证隔离效果。

### 1.2 患者主索引：身份唯一性不能靠随机 ID 解决

`global_patient_id` 适合成为长期稳定的技术标识。证件会补录、更正或失效，手机号可能家庭共用或被运营商重新分配，区域会随就诊与居住变化；这些都不宜直接成为患者档案的永久物理位置。

但“生成一个全局唯一 ID”和“同一个自然人只建一个档案”是两件事。雪花算法或号段解决前者，身份核验、映射约束、人工合并与拆分流程解决后者。以下是逻辑模型，不是可执行 DDL：

| 表 | 关键字段与约束 | 负责什么 |
| --- | --- | --- |
| `cpi_patient` | `global_patient_id, status, merge_version` | 患者档案及有效主身份 |
| `cpi_identifier` | `identifier_type, issuer, lookup_token, global_patient_id, validity` | 经核验的标识绑定；唯一范围依标识语义确定 |
| `cpi_hosp_mapping` | 唯一键 `(hospital_id, local_patient_id)` | 院内编号映射到全局身份 |
| `cpi_identity_change` | 操作 ID、原映射、新映射、理由、操作者、版本 | 合并和拆分的证据链 |

手机号只作为联系信息或候选线索时，应允许一号关联多人，不能套用所有标识统一唯一的规则。姓名模糊匹配也只能生成候选，不能自动成为合并依据。

**关键反例：**若所有 CPI 表按 `global_patient_id` 分到两个实例，请求 A、B 同时为同一证件生成不同 ID，就可能在两片各自通过 `UNIQUE(identifier_type, lookup_token)`。本地唯一索引没有比较另一片的数据。

因此，初期保持 CPI 权威表同库是一种合理选择，关系型主库也不限于 MySQL。真需要拆分时，可以让同一规范化身份标识路由到同一“身份占用”分片，先原子创建绑定，再建立患者档案，并用 `RESERVED → READY / CANCELED` 等持久状态恢复半完成动作。此时身份索引与患者档案可能跨片，不能再宣称它们天然属于一个本地事务；多证件绑定、合并两个人的档案也要另行协调。

同步调用 CPI 后再写医院库，同样只是两个依次提交的事务。CPI 成功、医院写失败会留下未使用映射；医院先写则会存在待绑定记录。可按业务契约选择预建身份或本地建档后异步绑定，并让调用可幂等、状态可查询、失败可重试。CPI 不可用时是否允许临时身份，需要业务明确，而非默认阻塞所有就诊。

ES 可以承担候选搜索和画像筛选，但不承担权威身份约束。合并要发布旧 ID 到新 ID 的映射版本；拆分应恢复原始证据归属，不能仅把一个指针改回去。旧事件、缓存和患者时间线都需要跟随身份版本修复。

### 1.3 就诊数据：医院、患者、就诊号分别优化什么

按 `hospital_id` 映射物理库，便于医院列表、院内资源与交易共置；库内再按时间分表，便于时间裁剪与历史维护。本文示例使用：

```text
数据库 = hospital_route[hospital_id].data_source
物理表 = t_visit_{route_month}
route_month = 建立就诊时确定并保存的归属月份
```

业务发生时间、补录时间、结算账期与 `route_month` 应分开。住院跨月、月底开方下月收费、历史补录都会打破“各表各取自己的当前月份就能共置”的假设。若关联表需按同一归属分表，就显式复制同一 `route_month`；更正业务时间不应隐式搬移物理记录。

| 分片维度 | 能改善什么 | 代价与边界 |
| --- | --- | --- |
| `patient_id` | 单患者历史、同患者聚合 | 医院今日列表扇出；号源、床位等共享资源可能跨片 |
| `visit_id` | 同次就诊明细共置 | 医院列表与患者跨次历史需要索引或扇出 |
| `hospital_id` | 医院列表、院内资源操作 | 大医院热点；跨院患者历史要二级索引 |
| 医院 + 时间 | 院内时间查询、归档 | 跨月查询多表，时间热点仍在最新表 |

不能说“按患者分片必然让同次就诊跨库”：如果相关表都按相同患者键与规则路由，同次就诊也能共置。真正需要检验的是收费还会修改哪些账户、库存、号源或共享资源，这些对象是否位于同一事务连接。

同一数据库实例上的多张 InnoDB 表可以参与同一连接的本地事务；多个数据源连接即使属于同一业务服务，也不会因一个 `@Transactional` 注解自动获得跨库原子性。挂号到收费可能持续数小时，不应把整个诊疗过程包装成长期数据库事务。

### 1.4 患者跨院历史：身份索引与就诊索引分工

CPI 回答“这个人对应哪些院内身份”；患者时间线回答“有哪些就诊或报告、在哪里”。仅有 CPI 映射仍可能要访问该患者到访过的所有医院与月份。

可建设按 `global_patient_id` 路由的时间线，保存：

```text
global_patient_id, hospital_id, local_patient_id,
visit_id/report_id, route_month, occurred_at,
source_version, status, identity_version
```

查询先定位患者，再从时间线分页得到路由信息，按 `(hospital_id, route_month)` 分组批量回源。`report_id` 全局唯一不代表中间件能从它推导物理位置；回源必须带齐路由字段，或者先访问 ID 路由目录。

列表可以接受已约定的索引延迟，但“没有查到”不等于“没有发生”。接口应暴露同步水位或新鲜度；刚写后的查询可携带写入版本等待读模型追平，或直接读取已知源分片。任一必要分片超时时，返回明确的未完成状态，不能默默把部分结果当作患者全量病史。

观测按业务接口统计，而非只看慢 SQL：

- `patient_query_ratio`：患者维度查询数 / 全部查询数。
- `patient_cross_shard_ratio`：其中跨物理库的查询数 / 患者维度查询数；分母为零单独处理。
- 分别记录物理库数、物理表数、执行 SQL 数、返回行数、P95/P99、超时率、索引落后量。

先定位高频且代价高的接口：低频小范围查询可做批量回源；高频患者历史适合时间线；全省复杂统计进入分析集群。只有读模型仍不能满足核心写入或查询约束时，才考虑改底层分片键。

### 1.5 医保对账：交易事实、清算结果与冷热分层

医院与医保机构不一定一一对应：同一家医院可能对接多个机构，同一机构也可能覆盖多家医院。因此按医院分库后，仅用 `insure_org_code + settle_period` 查询通常需要访问多库，但不等于每个库都全表扫描：时间规则可裁剪月份，局部索引可减少扫描行数，医院目录也能缩小候选库。要分别评估“路由扇出”和“单片执行成本”。

在线结算保留医院视角，对账读模型可按医保机构、账期组织，长周期统计放独立数仓。热、温、冷是访问频率和服务目标的设计，不必一开始建齐三套系统，也不能把 T+1 延迟作为所有对账场景的默认许可。

对账模型需保存 `(hospital_id, bill_no)`、原交易版本、冲正关联、源位点与清算批次。在线交易流水是业务事实；经确认的清算结果是另一类事实。对账副本不会因为“更全”就自动变成原交易的权威来源。关账时固定输入水位与口径，迟到交易、退款和冲正通过可追溯调整批次处理，避免反复覆盖已确认结果。

对指定医保机构、账期和批次做重算或冲正时，对账模型还应支持 `batch_no → (hospital_id, bill_no, route_month)` 的定位，先划定影响明细，再按权威源分组处理；不要在所有在线分片直接执行不带医院范围的批量修复。

按更新时间增量抽取会漏掉物理删除，也可能因相同时间戳、迟到提交而漏行；需要重叠窗口、稳定游标、删除日志和对账，或直接使用适配的 CDC。聚合校验不能替代明细校验：金额一增一减可能抵消，行数相同也可能是不同的交易。

### 1.6 医技报告：给不同查询建立不同读模型

医技主表保持医院与就诊归属，患者时间线服务个人历史，ES 服务授权范围内的文本检索，分析库服务项目、设备、批号等统计。DICOM、PDF 和影像文件放 PACS / 对象存储，数据库保存对象版本、校验值与关联元数据，ES 不存大文件本体。

新查询维度出现时，先量化访问频率、过滤选择性、时效要求、回源量和维护成本。偶发统计可进入离线任务；高频精确查询可增加索引或物化读模型；不要每出现一个字段就建设一个独立存储。

统一查询网关可以为未分片 HIS、分片报告库与 PACS 提供适配器。它应统一身份映射、权限、时间范围、排序与错误语义，同时保留来源系统、原报告 ID 和版本。多系统没有共享快照时，只能承诺带水位的聚合结果，不能虚构全局强一致。分页、超时、并发上限与部分失败都要进入接口契约。

## 2. 中间件选型与路由设计

### 2.1 中间件能隐藏表名，不能隐藏数据边界

| 方案 | 适合的接入方式 | 必须验证的成本 |
| --- | --- | --- |
| ShardingSphere-JDBC | Java 应用内接入 | 应用版本与规则发布、连接池放大、SQL 兼容性 |
| ShardingSphere-Proxy | 通过数据库协议代理统一接入 | 代理高可用、额外跳转、容量与会话行为 |
| MyCat 等代理 | 已有生态或代理接入需求 | 明确产品分支与版本，以真实 SQL、事务和故障用例验证 |
| 自研数据访问层 | 路由规则有限、查询边界明确 | 自行承担迁移、分页、监控、规则治理和故障恢复 |

这里比较的是架构责任，不是不同版本产品的功能承诺。评估应覆盖真实 SQL、批量写、事务失败、DDL、新月份建表、缺表与规则不一致，而非只验证一条查询能执行。

大表可以分片，小表可以是单表或广播表；是否接入中间件与是否水平拆分是两项独立决定。权限库、小型配置库不必为了“统一”而拆分。报表、日志和第三方数据库也不是技术上绝对不能接入，而是应根据访问方式与资源隔离决定是否值得。

绑定表描述一致的分片规则及正确关联关系，能减少无效表组合；它不会创建分布式事务。广播表在各数据源有相同结构和数据，适合小字典与分片表在当地关联。单表只有一个物理落点，与其他实例上的表关联仍可能跨库。[ShardingSphere 5.5.2 核心概念](https://shardingsphere.apache.org/document/5.5.2/en/features/sharding/concept/)

广播写需要验证所选事务模式、部分失败重试与副本校验；不能只配一个表名就承诺所有副本始终原子更新。药品当前名称可以来自字典，但历史处方的名称、剂量、价格等业务快照不应被字典更新反向改写。

### 2.2 同时支持 ID 查询与医院日期查询

三种方法解决“只有业务 ID，不知道分片”的问题：

1. ID 编入稳定逻辑槽或可识别的规则版本，服务端解析后路由。
2. ID 路由目录保存 `id → hospital_id, route_month, logical_slot`，再查询正文。
3. 上游保留并传递路由上下文，所有请求仍校验租户权限与 ID 归属。

不要把物理库编号永久固化进 ID。逻辑槽经映射表找到物理节点后可以迁移，但迁移数据和切换写主仍然必不可少。“改一下槽映射就完成扩容”会把查询送到尚无数据的节点。

原先低 4 位表示 16 个分片的 ID，不能直接改为取低 5 位读取历史数据：第 5 位原本可能属于序列。新增格式必须有无歧义的版本识别，旧格式继续按旧规则解释。日期切分也要处理补录：新请求的业务日期可以早于切换日期，不能混用“生成时间选写规则、业务时间选读规则”。

复合路由算法的责任是返回所有可能匹配的目标集合。等值、`IN`、闭区间、开区间、空集合、`NULL` 与缺失字段需要分别处理；日期范围不能当作日期值列表强制转换。多个 ID 可以覆盖全部分片，不能承诺 `IN` 永不全路由。

同时传入 ID 与医院日期时，应检查数据归属是否一致；尤其是插入，不能优先按 ID 路由后忽略其他字段。未知节点、缺表或无法解析的 ID 应报明确错误，不能静默返回空结果。对 `OR` 等复杂谓词，不能把不属于同一合取条件的键随意求交，以免漏路由。

以下仅展示 ShardingSphere 5.5.2 的自定义类配置位置，不提供算法实现、数据源或完整规则；类名是占位符。`complex` 是策略，自定义类算法类型使用 `CLASS_BASED`，并指定 `strategy: COMPLEX`。[官方算法配置](https://shardingsphere.apache.org/document/5.5.2/en/user-manual/common-config/builtin-algorithm/sharding/)

```yaml
shardingAlgorithms:
  registration_route:
    type: CLASS_BASED
    props:
      strategy: COMPLEX
      algorithmClassName: example.RegistrationRouteAlgorithm
```

若采用辅助目录，目录规模随业务记录增长，未必是“小表”。目录异步更新会带来新 ID 暂时无法定位，必须明确读后写兜底；目录与正文不共置时，也不能把“同事务写两者”当作无需验证的前提。

辅助索引还可以反向解决“正文按 registration_id 路由，但需要医院日期列表”：按医院组织查询索引，以医院和日期分页取得 registration_id，再按 ID 分组批量回源。这个索引与 `ID → 物理位置` 目录的访问方向不同，不能假定一张按 ID 分片的目录会自动支持高效医院列表。

ID 中若加入槽位，应重新核算时间、节点、序列与槽位的总位宽；序列空间减少会降低单节点单位时间的发号上限。节点编号不能并发复用，时钟回拨、序列耗尽和灾备恢复后的发号状态需要明确处理策略。位布局错误会导致碰撞，不能仅凭“用了雪花算法”宣称全局唯一。

### 2.3 路由规则是持久数据契约

规则至少记录算法版本、字符编码、输入规范化、时区、槽数、物理映射版本和生效范围。不能使用进程随机化的哈希作为持久路由函数；负数取模、大小写和前导零等差异都会造成写入与查询落点不同。

规则发布应先完成目标表、索引和节点准备，再让全部路由端具备识别新版本的能力，最后切换对应数据范围的写主。旧请求不能因为配置缓存尚未刷新就继续写旧节点；写入口需要校验该范围的权威版本。迁移期间规则、目录和数据水位必须一起检查。

## 3. SQL、跨月查询与分析隔离

### 3.1 路由裁剪和局部索引是两层优化

对医院分库、月份分表的表，查询应携带授权医院与明确范围，或携带可解析的路由 ID。对分片键套 `CAST`、算术或把条件藏在子查询里，可能使中间件无法提取路由条件；是否支持要以具体版本的路由结果验证。数据库能够使用某索引，不代表中间件也能定位单片。

对于在线写接口，禁止无确定作用域的更新、删除；对于查询，设置最大时间窗口、扇出数和返回量，并为经过审批的后台任务提供独立通道。“所有无分片键 SELECT 都是非法语法”不是产品事实，而可以是团队的访问策略。

跨库查询拆成应用层两段查询后，还要限制批量与并发，否则会把一个大 JOIN 改成大量小查询。`t_prescription JOIN t_drug` 是否可下推，要看药品表是否在处方节点有完整副本及当前 SQL 支持情况。广播表可支持本地关联，不能与远程单表混为一谈，也不能把所有跨库计划都描述为必然的 N×M 查询。

### 3.2 修正“查近半年，只查当月表”的遗漏

本节的简化查询示例约定 `visit_time` 与 `route_month` 的归属月份相同，输入已统一到固定业务时区；这一限制不适用于前文允许业务时间与归属月份分离的一般方案。若真实系统允许二者跨月，应从路由目录枚举候选表，而非用下面的月份算法推导落点。

以下 Python 3 教学函数枚举半开区间 `[start, end)` 涉及的月份，验证范围裁剪；它不是 ShardingSphere 实现。

```python
from datetime import datetime

def month_suffixes(start, end):
    if start >= end:
        raise ValueError("开始时间必须早于结束时间")
    cursor = start.replace(day=1, hour=0, minute=0, second=0, microsecond=0)
    result = []
    while cursor < end:
        result.append(cursor.strftime("%Y%m"))
        year = cursor.year + (cursor.month == 12)
        month = 1 if cursor.month == 12 else cursor.month + 1
        cursor = cursor.replace(year=year, month=month)
    return result

assert month_suffixes(datetime(2025, 12, 20), datetime(2026, 2, 1)) == ["202512", "202601"]
assert month_suffixes(datetime(2024, 2, 29), datetime(2024, 3, 1)) == ["202402"]
assert month_suffixes(datetime(2026, 5, 1), datetime(2026, 11, 1)) == [
    "202605", "202606", "202607", "202608", "202609", "202610"
]
```

针对每个候选月，在对应医院的数据源执行以下参数化查询。`t_visit_202610` 是服务端从可信目录选出的物理表；MyBatis 的 `${tableSuffix}` 是文本替换，不能接受前端传来的后缀。使用中间件逻辑表时则由中间件完成裁剪，不再同时手工选择物理表。

```sql
SELECT visit_id, hospital_id, local_patient_id, visit_time
FROM t_visit_202610
WHERE hospital_id = ?
  AND local_patient_id = ?
  AND visit_time >= ?
  AND visit_time < ?
ORDER BY visit_time DESC, visit_id DESC
LIMIT ?;
```

局部候选索引为 `(hospital_id, local_patient_id, visit_time, visit_id)`，需用真实数据分布确认执行计划。若一个全局患者在本院存在多个历史 ID，应逐一查询并归并，或评估 `IN` 条件下的排序成本，不能只取一个映射。

跨月或跨院取前 K 条时，各来源先取前 K 条，再按相同的全序归并取 K 条即可：任一来源排在第 K 条之后的行，其前方已有至少 K 行，不可能进入全局前 K。成立前提是候选来源完整、过滤条件一致、每条逻辑记录有唯一权威来源。迁移双读存在重复时，应先按权威目录过滤；先截断再去重可能不足 K 条，需要继续拉取。

跨页使用 `(visit_time, visit_id)` 游标；若 ID 不全局唯一，就把医院等字段加入排序和游标。降序下一页在每个候选分片 SQL 的 `WHERE` 内、`ORDER BY` 之前增加以下条件，并继续保留原时间范围：

```sql
AND (visit_time < ? OR (visit_time = ? AND visit_id < ?))
```

游标减少深分页的跳过成本，但不会为多个数据库自动创建共享快照。补录、修改排序字段或撤回可能改变翻页结果。严肃审计应固定快照/水位或导出批次；普通列表按约定提供当前视图。大偏移量 `LIMIT offset, size` 在多片执行时可能需要每片读取 `offset + size`，成本随页深和扇出放大。

### 3.3 聚合不能只把各片结果相加

| 聚合 | 正确合并方法 | 容易出错的情况 |
| --- | --- | --- |
| `COUNT(*)`、`SUM(x)` | 对不重叠数据集合求和 | 双读重复、JOIN 放大、同步缺行 |
| `AVG(x)` | 合并 `SUM(x)` 与 `COUNT(x)` 再相除 | 平均各片平均值；用 `COUNT(*)` 忽略 NULL 差异 |
| `MIN/MAX` | 合并局部极值 | 过滤口径不同、必要分片缺失 |
| `COUNT(DISTINCT patient_id)` | 跨片精确去重，或使用明确标注误差的可合并结构 | 同一患者跨院、跨日被重复累计 |
| 分组 Top K | 保留足够的局部候选或使用专用分布式算法 | 某组在每片都非前 K，合计后却进入前 K |

按日患者去重数不能相加得到月去重数。医保金额使用统一币种、精度与冲正口径；如果只看汇总相等，无法证明明细一致。

### 3.4 稽核大查询需要独立资源与明确水位

近三年多维 JOIN、聚合和临时统计适合通过 CDC / ETL 进入 ODS，再建设事实表、维度表和按需预聚合。历史医院等级、科室归属、药品目录要按事件时点或指定口径关联，不能一律用当前字典解释旧账。

读写分离可以分担短查询，但重报表仍可能占用复制节点 IO、缓存、连接和中间件归并资源。若该副本还承担故障晋升，复制落后会进一步影响恢复。独立分析集群、独立连接池、查询配额和导出队列提供更清晰的资源边界；吞吐与响应时间仍需实测。

## 4. 事务与一致性：收费、报告和床位

### 4.1 “要么都成功，要么都回滚”需要先定义可见性

收费订单、费用明细和本地医保流水若必须原子提交，首先尝试按同一收费聚合共置，在一个物理连接的 InnoDB 事务里完成。绑定表配置只帮助关联路由，不能代替事务连接与数据落点检查。调用外部医保或支付接口也不属于这个本地事务。

| 方案 | 可以提供什么 | 必须面对的失败 |
| --- | --- | --- |
| 本地事务 | 同一事务资源内的原子提交 | 提交响应丢失，调用方不知道是否成功 |
| XA | 多个支持 XA 的资源经协调完成提交决策 | prepare 后协调器失联、锁持有、恢复与未决事务处理 |
| TCC | 业务资源先预留，再确认或取消 | 重复确认、空回滚、取消后迟到 Try、资源预留超时 |
| Saga | 多个本地步骤和可重试补偿最终收敛 | 中间状态可见、补偿失败、不能撤销的外部副作用 |

MySQL InnoDB 支持 XA，但具体限制与恢复行为要按版本验证，不能因医疗场景就一概排除，也不能把它当作免费的一致性。[MySQL 8.0 XA 文档](https://dev.mysql.com/doc/refman/8.0/en/xa.html)

Saga 的冲正不是数据库回滚：收费已被外部观察或支付已完成，补偿只能追加退款、撤销等新事实。订单应允许 `PENDING`、`COMPENSATING`、`MANUAL_REVIEW` 等状态，不能声称任何故障下都立即落在成功或失败。若产品不允许任何中间可见状态，需要重新共置数据，或评估真正满足该语义的事务方案。

提交超时不能直接返回“未扣款”并使用新单号再扣一次。客户端重试同一业务键，服务端查询权威订单状态；外部支付也使用稳定商户订单号及其查询/幂等协议。数据库唯一索引无法替外部系统防重。

通知、BI 和部分展示可以异步，但监管上传、危急值通知、处方审核是否允许延迟必须由具体业务规则决定，不能统称为可降级外围。系统可优先保留核心入口，同时明确显示待处理状态、期限和人工处置队列。

### 4.2 Outbox 解决提交与发布窗口，不等于恰好一次

源业务表与 Outbox 必须在同一物理事务资源提交。事件至少包含 `event_id`、聚合 ID、源版本、事件类型、路由字段和必要负载。若 Outbox 固定在另一库，就又出现了跨库提交问题。

```text
源事务：更新报告版本 → 插入 Outbox → COMMIT
发布器：读取未完成事件 → 发布到 MQ → 收到确认 → 标记已发送
消费者：接收事件 → 本地事务写消费记录和读模型 → COMMIT → ACK
```

发布成功后、标记发送前进程崩溃会重复发布；消费者提交后、ACK 前崩溃会重复消费。消费记录的唯一约束和业务修改必须在同一本地事务内，不能先记录“处理成功”再更新业务。ES 与关系型时间线分别维护交付进度，一个成功不能掩盖另一个失败。

`event_id` 去重只识别同一消息；不同版本事件乱序还需要版本检查。版本必须在同一源聚合内单调递增，判断和写入必须是原子条件更新：先 SELECT 比版本、再无条件 UPDATE，会让并发的旧事件覆盖新事件。首次插入的竞争也要以唯一约束处理，并在冲突后重新执行版本判断。若事件携带完整快照，可仅应用更大的 `source_version`；若事件只有“余额减 10”这样的增量，不能简单跳过中间版本，必须按序处理或补齐缺失事件。

例如报告先发布 v2，随后撤回 v3，晚到的 v2 不能重新将其设为可见。删除/撤回应保留版本墓碑，至少覆盖可能的重放周期；直接物理删除读模型会丢失版本屏障。患者合并导致分片键变化时，还需删除或屏蔽旧患者分片上的条目，单在新分片 upsert 不会清理旧索引。

消费失败需要有退避重试、最大未完成时长告警和可检索的死信队列；进入 DLQ 不代表业务已同步完成。按源分片记录连续已应用水位及失败缺口，不能只报告“收到的最大位点”。修复后重放原 event_id 和源版本，并定期核对源表与读模型的数量、状态、版本和关键字段。

时间线或 ES 损坏时，可从权威源的一致性快照重建新副本，保留快照边界后的增量，追平并校验后再切读。全量重建与增量并发时仍须防止旧快照覆盖新状态；不能直接清空正在服务的索引后就把空结果解释为无记录。

ES `routing = patient_id` 是减少搜索扇出的可选优化：在未开启 routing partition 的单个索引内，相同 routing 值定位同一分片。写入、按 ID 读取、更新和删除都应传同一 routing；搜索显式传 routing 才能按它裁剪目标，同时仍须保留患者和权限过滤。不同 routing 值可能落到同片，相同 `_id` 配不同 routing 也不保证索引范围唯一；患者合并时需处理旧 routing 下的文档。跨多个时间索引查询仍会访问多个索引，不能说终身历史永远只访问一个分片。此处只说明机制，具体参数按部署版本确认。[Elasticsearch 自定义 routing 文档](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/mapping-routing-field)

缓存键应包含医院或授权范围、患者、过滤条件等，不能将“全省患者最近报告”缓存直接用于“本院最近报告”。乱序 `LPUSH` 会造成重复和顺序错误；可以失效后按权威读模型重建，但仍要处理“失效后旧查询回填”的窗口。对撤回、权限收回等敏感操作，详情与下载应回源校验，不能把长 TTL 当成一致性保证。

### 4.3 报告与对象存储的发布状态

数据库和对象存储之间通常没有共同本地事务，可以采用如下教学流程：

1. 以不可变对象键上传暂存文件，保存对象版本与校验值，确认上传完整。
2. 在源库事务中写报告元数据、审核状态和 Outbox；只有满足业务发布条件的状态对外可见。
3. 查询详情或签发短期下载链接时校验报告当前版本、状态和访问权限。
4. 定期比对元数据与对象；上传成功但数据库失败留下的孤儿对象，经过宽限期且确认无引用后再按流程清理。

签发下载链接时校验权限，并不意味着已签发链接会在报告撤回后立即失效。若要求即时撤回访问，应经每次请求都校验当前状态的下载网关，或使用存储层支持的撤销机制；否则只能承诺链接剩余有效期内的有界暴露窗口。

“先上传再写库”减少了发布时缺文件的窗口，却不能排除生命周期规则误删、覆盖、权限变更或对象存储不可用。对象应使用版本或不可变键，不能重复覆盖同一键后让旧报告意外指向新文件。孤儿清理也必须避开正在执行或重试的上传事务。

### 4.4 占床：先把不变量放到可约束的位置

需要分别确认三个业务约束：同一床位至多一个有效占用、同一次住院至多一张当前床、同一患者是否允许多个有效住院登记。第三条依医院和业务流程确定，不能由前两条推导。

原方案 `UNIQUE(bed_id, active_flag)` 有明确缺陷：床 101 第一条历史记录已为 `(101, 0)`，第二次占用释放时也变成 `(101, 0)`，会发生唯一冲突。它同时限制了有效记录和所有已释放记录。

一种修正是对有效状态生成非 NULL 约束键，对历史状态生成 NULL。MySQL 的唯一索引允许多个 NULL，生成列可建立索引。[唯一索引规则](https://dev.mysql.com/doc/refman/8.0/en/create-index.html)、[生成列规则](https://dev.mysql.com/doc/refman/8.0/en/create-table-generated-columns.html)

以下是 MySQL 8.0.16+ 的隔离实验 DDL，不是完整床位系统；该基线用于保证 `CHECK` 约束实际执行（见 [MySQL CHECK 文档](https://dev.mysql.com/doc/refman/8.0/en/create-table-check-constraints.html)）。假设同一医院的分配表不再按床位或月份拆开，从而同时约束床位和住院 ID；请求表与 Outbox 也必须位于该医院的同一事务资源。

```sql
CREATE TABLE bed_assignment_demo (
    assignment_id BIGINT NOT NULL,
    hospital_id BIGINT NOT NULL,
    bed_id BIGINT NOT NULL,
    inpatient_id BIGINT NOT NULL,
    status VARCHAR(16) NOT NULL,
    version BIGINT NOT NULL DEFAULT 0,
    active_bed_id BIGINT GENERATED ALWAYS AS (
        CASE WHEN status IN ('RESERVED', 'CONFIRMED') THEN bed_id ELSE NULL END
    ) STORED,
    active_inpatient_id BIGINT GENERATED ALWAYS AS (
        CASE WHEN status IN ('RESERVED', 'CONFIRMED') THEN inpatient_id ELSE NULL END
    ) STORED,
    PRIMARY KEY (hospital_id, assignment_id),
    UNIQUE KEY uq_active_bed (hospital_id, active_bed_id),
    UNIQUE KEY uq_active_inpatient (hospital_id, active_inpatient_id),
    CONSTRAINT ck_assignment_status CHECK (
        status IN ('RESERVED', 'CONFIRMED', 'RELEASED', 'CANCELED')
    )
) ENGINE=InnoDB;
```

若改成按 `bed_id` 分库，床位唯一性仍可局部保证，但同一住院在两床分片上各自插入就可能同时成功；`uq_active_inpatient` 不再具有医院级保证。需要独立的住院资源协调点或调整共置策略。患者有效住院唯一性则应在住院登记权威模型约束，而非误用床位表代替。

### 4.5 请求幂等、状态迁移与迟到补偿

持久请求表可以使用 `(hospital_id, request_id)` 为主键，保存操作类型、规范化参数摘要、结果分配 ID 和处理结果。同一业务动作重试必须保持 request_id；相同键但不同参数应拒绝，不能返回别人的旧结果。占床、释放、调床是不同动作，各有自己的幂等身份。

占床的事务编排如下，属于伪代码：

```text
BEGIN（医院权威分片）
  插入请求记录，唯一键冲突时结束本次事务并读取已提交原结果
    原参数不同：拒绝；原参数相同：返回原结果
  插入 CONFIRMED 分配记录（同步占床模型）
    有效床位/住院唯一键冲突：ROLLBACK，返回资源冲突
  插入 Outbox，记录分配 ID、版本和完整状态
  更新请求记录为成功及结果分配 ID
COMMIT
提交响应不明确：用同一 request_id 查询，不创建新动作
```

请求唯一冲突不等于床位唯一冲突；数据库异常要按约束和业务语义分类。上面只持久化成功结果，资源冲突时事务整体回滚，因此相同请求稍后可能重试成功；若业务要求失败结果也固定，应另外定义并保存拒绝结果。

释放通过原分配 ID、允许的状态和预期版本更新，不能只按床位号释放：

```sql
UPDATE bed_assignment_demo
SET status = 'RELEASED', version = version + 1
WHERE hospital_id = ?
  AND assignment_id = ?
  AND status = 'CONFIRMED'
  AND version = ?;
```

必须检查受影响行数。为零时先查询原请求结果，若不是已完成的重复请求，就区分版本冲突、非法状态或不存在，不得一律报告成功。更新、释放请求结果与 Outbox 在同一事务提交。

失败时序说明为什么需要分配 ID：A 占床 → A 已释放 → B 占用同一床 → A 的迟到补偿到达。若补偿只操作 `bed_id`，会错误释放 B；若操作 A 的分配 ID 与版本、状态，便不会触及 B。Redis 锁可以减少冲突，但租约失效后旧持有者仍可能执行，最终约束应由数据库状态与条件写兜底。

分配记录的 `version` 只在同一个 `assignment_id` 内比较。A 的释放版本 1 与 B 的新占用版本 0 属于不同分配，不能拿数值大小决定床位当前状态。若维护按床位汇总的展示表，应在床位权威行上维护跨分配递增的 `bed_version`，与分配修改及 Outbox 同事务递增；消费者按该版本条件写床位投影，或先保存各分配状态再从权威源重建床位视图。空床数来自有效床位主数据与当前分配的同一口径，还要排除停用、维修等不可分配床位；异步统计不能作为最终占床许可。

同步占床模型中，住院展示是可修复读模型，消费者失败不能自动推断占床失败并释放真实占用。如果入院业务确实需要下游确认，应显式使用 `RESERVED`，确认后转 `CONFIRMED`，取消只作用于同一预留版本；确认与取消都必须拒绝终态后的迟到动作。

同院同库调床可在单事务中串行化该住院的操作，按固定顺序锁定相关资源，释放旧分配并创建新分配；新床冲突则整笔回滚，旧床仍保留。跨库调床不能直接复用上面的 DDL 来“保留旧床，同时插入新床 RESERVED”：两条记录的 `active_inpatient_id` 相同，同表会触发唯一冲突；分到不同库时，该约束又无法全局防止双占。

跨库方案应另建调床流程与目标床位预留模型：目标床位的权威资源行统一约束预留和占用，使其不能同时授予两人；住院权威行仍只保存一个当前分配，另存待完成的 `transfer_id`。按住院版本串行化调床/退院，先取得目标预留，再以条件更新切换当前分配，随后幂等确认目标并释放旧床。切换前失败可取消目标预留、保留旧床；切换后的未知结果先查询持久流程状态，再前向恢复，不能盲目释放目标。预留若有到期机制，应先将目标预留以条件更新推进到不可自动过期的提交中状态，再切换住院当前分配；超时恢复查询持久流程决策，不能自行释放提交中的资源。仅在切换前查询一次“尚未过期”仍有竞态，可能在切换前被重新分配。过渡期可能暂时占用两份床位资源，但只能有一个权威“当前床位”；是否允许这种过渡语义要由业务确认。上面的单库 DDL 不宣称实现了此跨库协议。

验证时应覆盖：两请求争一床只有一个成功；同住院争两床只有一个成功；同床多次释放历史都能保存；同请求重放不产生新分配；参数冲突被拒绝；旧释放不影响新占用；提交后响应丢失可查回结果；Outbox 重复和乱序不会恢复旧状态。

## 5. 扩容、切流与归档

### 5.1 全量与增量必须共享边界

单库迁入分片集群、从 `hash(registration_id)` 改成 `hash(patient_id)`，都要回答：快照覆盖到哪里、后续事件从哪里开始、哪个系统此刻允许写入。

1. **准备目标。** 建立表、索引、路由目录和新规则，保留旧系统为唯一写主。确认 CDC 能捕获 INSERT、UPDATE、DELETE 以及路由所需旧值；分片键更新要处理旧位置删除和新位置写入，或在业务上禁止直接修改。
2. **建立快照边界。** 在受支持的快照协议下记录源位点并保留后续日志，再开始全量导入。不能先导完全量、过一段时间才启动增量，否则中间的更新和删除会丢失。
3. **回放增量。** 从快照边界继续处理，持久化每个源分片的消费位点。可先装载快照再有序重放；若并发写目标，必须用版本或位点防止旧快照覆盖新事件，并处理删除墓碑。
4. **校验。** 在相同水位、相同业务范围和相同字段规范化方式下，对比行数、金额、分块摘要与关键明细。持续变化的数据在不同时刻直接比较，会产生伪差异。
5. **影子读。** 对相同请求异步比较新旧结果，控制对生产源的额外负载。新库有同步延迟时，不应参与依赖最新状态的写决策。

Debezium MySQL 连接器将初始一致性快照与对应 binlog 位置关联，再继续流式读取；具体快照锁策略和权限依部署配置而定。这里借用其机制说明连续边界，不提供可直接部署的连接器参数。[Debezium MySQL 快照说明](https://debezium.io/documentation/reference/stable/connectors/mysql.html#mysql-snapshots)

迁移与切写窗口应冻结无关 DDL、大批量修改和大版本业务发布，避免源模式变化或额外负载破坏回放与校验；若必须变更，要将模式版本及转换规则纳入迁移协议并重新验证。分批导入保存已完成范围和校验结果，日志保留期须覆盖快照、追赶及故障恢复时间；位点落入已清理日志范围时，不能跳到最新位置伪装追平。

多个源库的 binlog 位点没有天然全局大小关系，应维护位点向量，并明确跨源事务或业务批次如何协调。一个源日志中的顺序也不等于经过多线程消费后仍有相同顺序。

应用直接双写若第一库提交、第二库失败且没有持久重试证据，就无法靠“之后再试”保证补齐。Outbox 和 CDC 可以构成可恢复的复制路径，但“影子库跟随权威写主”与“两边都接受独立业务写入”是不同架构。

### 5.2 写切换的关键是隔离旧写者

迁移单位应是能独立协调的医院、逻辑槽或业务范围。每个范围始终只有一个权威写主；有跨范围强事务时还需一起切换或另外协调。

```text
旧库权威写
  → 对该范围建立写屏障，短暂排队或明确拒绝新写
  → 等待旧库在途事务结束，并阻止旧连接/旧实例继续写
  → 记录最终位点 W，等待目标已应用到 W
  → 校验关键数据、请求幂等结果与路由目录
  → 发布新权威版本，启用目标写入
  → 解除屏障，旧端拒绝该范围的业务写入
```

屏障不能只是“通知配置中心”：落后的实例、定时任务、补偿任务、直连脚本和重试请求都可能绕过它。需有可强制执行的写入口/权限隔离或资源端版本检查，并证明旧在途提交已排空。数据范围内的老库唯一键和新库唯一键不是一个全局唯一键，两边同时写同一业务请求仍可能各成功一次。

按应用实例让 5% 写新库、95% 写旧库，会让同一医院出现双主，不能当作安全写灰度。可以按医院切，但必须让所有实例对该医院采用相同权威归属，并在旧端阻断它的写入。读接口可以独立灰度，依赖写后立即读取的链路需要跟随权威写主。

“零停机”应定义可接受的短暂排队、重试与尾延迟，并测试客户端是否维持同一请求键；它不是没有切换边界。迁移同时要处理 Outbox 发布者的所有权：已发送状态、事件 ID 与消费幂等记录不能丢失，旧新发布器重复发送也不能重复执行外部动作。

### 5.3 回滚不能只切配置

目标尚未接受新业务写时，回到旧库相对简单；目标已经提交新业务后，旧库就是落后的副本。立即指回旧库会丢掉新交易，还可能允许同一幂等键重新执行。

可回滚方案需要事先验证新到旧的反向复制、模式兼容和循环防护。回滚时再次封锁新写、排空在途事务，等待旧端追到新的最终位点，校验请求结果和业务事实，再交还写权。反向链路不完整时，应优先修复新端或暂时限制写入，不能把数据不完整的旧端宣传为随时可用的兜底。

当停止旧到新的正向同步并启动反向同步时，要明确边界与事件来源，避免旧事件覆盖新值、复制循环或重复外部通知。回滚保留多久取决于恢复目标与验证结果，不凭空规定一两周就足够。

### 5.4 从 8 表扩至 64 表：不同策略解决不同瓶颈

| 策略 | 历史数据如何处理 | 主要限制 |
| --- | --- | --- |
| 全量重分片 | 全量 + 增量迁到新规则 | 迁移 IO、校验、切写与回滚复杂 |
| 固定逻辑槽迁移 | 只迁指定槽，更新物理映射 | 仍需搬数据和逐槽屏障；热点槽可能需进一步拆分 |
| 新旧规则按时间/版本共存 | 旧数据原地，新数据按新规则写 | 旧大表与旧热点仍在；查询需覆盖相关版本 |
| 独立迁出热点医院 | 将医院映射到专用节点 | 不解决医院内部单实体热点 |

均匀散列下从 `h % 8` 改为 `h % 64`，只有余数 0～7 对应的约 1/8 数据仍落在原编号，约 7/8 的目标编号改变。直接改公式不会移动数据，而会让旧行查不到。

规则双轨期维护迁移状态：`OLD_PRIMARY → COPYING → CATCHING_UP → CUTOVER → NEW_PRIMARY`，每个状态规定读源、写主、可重试动作与推进水位。正常读取优先从目录选择唯一权威位置，避免无条件“新库没查到就查旧库”把已删除数据读回来。

医保全量抽查在固定路由版本和对账水位下枚举所有权威范围；复制中的影子行不重复计入，尚未切换的旧范围不遗漏。新规则按日期启用时，补录历史记录究竟归哪套规则必须显式规定并保存，不能只靠应用当前时间猜测。

### 5.5 冷数据归档与十年前记录查询

保留年限应由适用记录类型、地区要求和机构制度确定；本题若设定“保留 15 年”，只把它作为场景输入，不泛化成所有医疗数据的统一法律结论。

归档选择已结束、低变更且无待处理冲正或争议的范围。先生成归档清单，保存业务范围、记录数、校验摘要、格式/模式版本、加密密钥版本和源水位；复制到归档介质后校验可读性并演练恢复，再发布冷热位置目录。只有达到保留策略与已批准清理条件后，才清理在线副本。

归档实例适合继续 SQL 查询，对象存储适合低成本保留和批量扫描，但还需要查询引擎、目录与恢复机制。对象存在不代表十年后仍能解码、解密或还原业务含义；字段字典、历史代码映射和密钥恢复同样要保留。

统一 API 先用患者时间线或归档目录定位范围，再走在线库或归档查询服务。长期追溯用异步任务、配额和可恢复游标，不把十年全量记录一次拉进在线应用内存。冷库不可用时应报告范围未完成，而不是返回空病史。跨冷热边界的结果按权威来源去重，并保持版本与授权校验一致。

## 6. 故障排查与规则治理

### 6.1 只有某片区变慢，先从一条请求定位放大点

先选一个可复现的慢请求和一个相同接口的正常请求，关联 Trace、逻辑 SQL、物理 SQL 和路由版本，再比较各层耗时。不要仅凭“A 市慢”就认定分片不均。

| 观察到的证据 | 下一步检查 | 可能的处理方向 |
| --- | --- | --- |
| 命中库/表数突然上升 | 分片键是否丢失，日期类型、OR 条件和规则是否改变 | 修复条件或规则，限制异常扇出 |
| 路由正常，连接等待高 | 池大小、活跃事务、泄漏、总实例连接预算 | 限流、释放异常长事务；避免盲目加池 |
| 单片执行慢、锁等待高 | 阻塞链、长事务、热点行、批任务 | 针对阻塞源处置，缩短事务 |
| 单片扫描行数高 | 索引差异、统计信息、参数选择性、执行计划 | 修复索引或查询，验证计划变化 |
| 数据库快，应用归并慢 | 返回量、排序、去重、网络、堆内存与 GC | 减少传输、分页、转分析路径 |
| 同 SQL 仅大医院慢 | 数据倾斜、缓存命中、热点实体、租户峰值 | 隔离热点医院或重审内部拆分 |

记录每次操作前后的同类请求数据。只读 `EXPLAIN` 可以先检查计划；`EXPLAIN ANALYZE` 会实际执行查询，应在合适环境和限定范围运行。生产终止事务、修改索引或切换规则需要走对应操作流程，不能把诊断自动扩大为有副作用的修复。

连接预算要乘开：应用实例数 × 每实例可能访问的数据源数 × 每数据源池上限，再考虑代理、CDC 与后台任务。分片越多，默认池配置越容易超过数据库连接能力。

### 6.2 统一慢 SQL 需要同时看逻辑和物理指纹

采集逻辑 SQL 指纹、路由版本、物理数据源与表、执行时间、连接等待、扫描/返回行数、错误类别及事务持续时间。聚合时把 `t_visit_202609` 与 `t_visit_202610` 归入同一逻辑指纹，同时保留物理来源，以便识别索引漏建或新月份配置异常。

相同 SQL 在不同分片耗时不同，可能来自数据量、值分布、统计信息、索引结构、硬件、缓存或锁竞争。按同类参数与相近负载比较，不能只比较平均值。维护各片 DDL 与索引指纹，部署后核验一致性；计划优化应先在受影响分片验证。

医院、患者、请求 ID 不宜全部作为指标系统的高基数标签。详细定位放受控 Trace/日志，指标保留接口、规则版本、有限节点等维度；日志也不能直接输出完整证件或病历参数。

### 6.3 路由失败与 SQL 不支持不是同一种错误

“没有路由结果”可能是缺少键、类型转换失败、月份不存在、规则映射漏项或算法返回空集合；SQL 不支持可能发生在解析、改写或执行计划阶段。错误文本依中间件版本而异，应保留实际异常码和最小 SQL。

排查顺序是：确认部署版本与最近变更 → 获取脱敏参数类型和 SQL → 检查逻辑表规则及实际节点 → 复现路由目标 → 再确认物理 SQL 与数据库执行。避免一遇到失败就放开全路由，尤其不能把写操作变成广播更新。

治理要覆盖 Mapper 动态 SQL、ORM 生成语句、批量操作、范围边界、跨月、空 IN、补录和规则升级。静态扫描只能发现部分问题；固定版本中间件的集成用例应断言命中哪些节点、返回哪些行、失败时是否部分提交。上线前预建未来月份，规则和表结构分阶段发布，并提供旧版本应用兼容窗口。

## 7. 多租户、敏感信息与灾备

### 7.1 租户路由不是权限控制

| 隔离方式 | 收益 | 边界 |
| --- | --- | --- |
| 共享表 + `tenant_id` | 成本较低，租户管理统一 | 所有访问路径都需授权过滤；漏条件可能越权 |
| 独立 schema / 库 | 可按库配置应用账号权限 | 共享实例管理员仍可能读取所有库，资源仍共享 |
| 独立实例与账号 | 更强资源和管理边界 | 运维、备份、升级和连接成本更高 |

医院身份应从认证上下文确定，并校验操作者是否可访问请求中的患者和医院；客户端提交 `hospital_id` 只能作为待校验参数。按租户分片、ID 编码和 ES routing 都不是授权机制。

若要求医院 DBA 无法读取其他医院数据，就不能同时授予他共享实例的全局管理权限。需要管理域隔离、最小权限、受控运维入口与密钥隔离；应用层过滤对拥有底层高权限的人无效。备份、归档、日志、时间线、ES 和下载链接也应遵循相同边界。

跨院访问审计记录操作者、所属机构、患者、目的/授权依据、请求 ID、范围、结果状态和导出行为；对审计记录限制修改并提供完整性校验。仅有 binlog 无法替代业务访问审计，它通常不能说明谁基于什么授权读取了病历。

### 7.2 加密字段如何支持精确定位

脱敏显示、可逆加密和检索令牌解决不同问题。`138****0000` 丢失信息，不适合作为唯一身份键；随机化加密的相同明文可能得到不同密文，不能直接用密文等值匹配；普通无密钥哈希对手机号等低熵值容易被枚举。

一种设计是在授权服务内规范化标识，分别保存加密原文和带密钥的等值检索令牌，例如 `HMAC(key, 标识类型 || 签发域 || 规范化值)`。同时保存算法/密钥版本，令牌仅用于定位候选，身份是否有效仍由业务核验。令牌会泄露相等关系，不能称为匿名化，也不能据此支持明文前缀或模糊搜索。

轮换检索密钥时要安排新旧令牌重建、双版本读取和绑定唯一性检查，避免同一证件因版本不同重复建档。主档案仍以稳定患者 ID 路由，避免加密算法或密钥轮换触发全量档案迁移。

如果业务需要姓名、地址模糊检索，应单独评估可暴露的字段和访问范围；把敏感明文复制进 ES 并不会因为“只是索引”就减少保护责任。数据库之外的密钥托管与授权边界应独立设计。

### 7.3 多分片灾备需要恢复一组相互匹配的状态

灾备不只是把每个分片配置复制。还应保存规则版本、槽映射、CPI 身份映射、ID 分配状态、Outbox 与消费位点、对象版本、密钥及归档目录。数据库恢复到昨日、路由规则却使用今日迁移后的映射，会造成“数据还在但查不到”。

每个分片维护复制进度，平台按业务定义 RPO（可接受数据损失）与 RTO（恢复时间）。异步复制不能承诺已确认交易零损失；单个分片追平也不能证明跨片收费或 Saga 状态已形成一致业务切面。

切换前先隔离旧写主，核对目标规则与拓扑，再根据各片恢复水位判断哪些业务范围可服务。对跨片订单、外部扣款和医保请求，依据稳定业务键查询结果并对账；未知状态进入恢复流程，不能当作失败重新执行。旧机房网络恢复后仍应拒绝写入，避免脑裂。

回切应按迁移流程重新同步和校验，恢复 Outbox 发布与消费进度，验证重复消息不会导致再次扣款、重复发票或恢复已撤回报告。灾备演练需要验证可读性、权限、关键业务结果和外部对账，不只是数据库端口连通。恢复规则、索引目录与对象文件的顺序应进入可执行预案。
