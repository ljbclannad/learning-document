# 数据分区

## 1. 概念与用途

数据分区（Partitioning）是数据库按**分区键和分区规则**，将一张逻辑表的行放进多个分区。应用仍可查询同一张表；数据库负责把写入的行路由到相应分区。这属于**按行划分**，不是按列拆成多张表。分区的主要价值是缩小某些查询的扫描范围，以及按分区管理历史数据；不能只因表大就推断分区后一定更快。

分区键应从常用查询条件和数据生命周期出发选择。例如订单经常按下单时间范围查询、按月归档时，时间适合做分区键；如果多数查询只按订单 ID 定位，按时间分区可能无法减少需访问的分区数。

分区同时影响**数据放置、查询范围和维护粒度**：写入时用分区键决定目标分区；查询时优化器尝试排除不相关分区；归档或删除时可以按完整分区操作。这三个目标不一定一致，应先确定哪个是主要收益。分区不能替代索引、增加单机硬件容量，也不会自动把一个查询分给多台机器。

## 2. 常见分区策略

| 策略 | 行如何进入分区 | 典型用途 |
| --- | --- | --- |
| `RANGE` | 按值的区间 | 按日期、账期管理和范围查询 |
| `LIST` | 按预先列出的离散值 | 按地区、业务类别划分 |
| `HASH` | 对分区键计算哈希值 | 较均匀地分散数据，适合键值定位 |

具体类型和语法取决于数据库：MySQL 8.4 还提供 `KEY` 分区；崖山数据库 23.4.6 还提供 `INTERVAL`（按间隔扩展的范围分区）及复合分区。不要把某个产品的分区语法直接当成通用 SQL。

选择策略时，可先看查询形态：连续时间范围与定期清理通常偏向 `RANGE`；少量稳定类别可以考虑 `LIST`；按某个键做等值定位且希望数据较均匀分布，可以考虑 `HASH`。`HASH` 不保留键的大小顺序，因此通常不适合靠分区裁剪加速连续范围查询。`INTERVAL` 免去手工逐个创建后续范围分区，但仍需考虑自动增长的分区数量与维护成本。

## 3. 分区裁剪如何生效

以 **MySQL 8.4** 的范围分区为例：

```sql
CREATE TABLE sales (
    sale_year INT NOT NULL,
    id BIGINT NOT NULL,
    amount DECIMAL(10, 2) NOT NULL,
    PRIMARY KEY (sale_year, id)
)
PARTITION BY RANGE (sale_year) (
    PARTITION p_before_2025 VALUES LESS THAN (2025),
    PARTITION p_2025 VALUES LESS THAN (2026),
    PARTITION p_later VALUES LESS THAN MAXVALUE
);

SELECT * FROM sales WHERE sale_year = 2025 AND id = 42;
```

数据库可根据 `sale_year = 2025` 排除不可能匹配的分区，只访问 `p_2025`；这叫**分区裁剪**。如果只按 `id = 42` 查询，条件无法确定 `sale_year`，就可能访问多个分区。是否裁剪以及访问了哪些分区，要通过执行计划验证；裁剪后分区内部仍可能需要合适的索引。MySQL 要求分区表达式用到的列包含在表的**每个**唯一键中（包括主键），所以示例主键包含 `sale_year`；这也意味着原本只按 `id` 保证全表唯一的设计不能直接照搬。

### 3.1 分区裁剪与索引分别解决什么问题

分区裁剪回答“**需要进入哪些分区**”，索引回答“**进入分区后怎样找到行**”。例如上述 `sale_year = 2025 AND id = 42`，先确定 `p_2025`，再可借助主键查找；`sale_year = 2025` 即使只访问一个分区，该分区内仍可能有大量行。反过来，只按 `id` 查询时即使每个分区有可用索引，也可能需要在多个分区分别查找。

| 查询条件 | 可能访问的分区 | 原因 |
| --- | --- | --- |
| `sale_year = 2025` | `p_2025` | 等值条件直接确定分区 |
| `sale_year BETWEEN 2024 AND 2025` | `p_before_2025`、`p_2025` | 范围与两个分区相交 |
| `id = 42` | 全部分区 | 条件未限制分区键 |
| `sale_year = 2025 OR id = 42` | 可能是全部分区 | 第二个条件可能在任意分区命中 |

这些是依据分区定义作的推断，实际计划以数据库输出为准。MySQL 8.4 可运行 `EXPLAIN FORMAT=TRADITIONAL SELECT ...`，查看 `partitions` 列确认访问范围，再看 `key`、`rows` 判断分区内的索引访问与估算扫描量。`EXPLAIN` 是计划，不等于实际耗时；性能结论还要用代表性数据和真实查询测量。不要笼统认为“对分区键使用函数就一定不能裁剪”：是否支持取决于分区表达式和数据库版本，MySQL 对部分日期函数有专门支持。

### 3.2 分区键设计的约束

以 MySQL 8.4 + InnoDB 为例，分区表达式中的列必须出现在**每个**唯一键中；把主键从 `id` 改为 `(sale_year, id)` 后，数据库只保证这组值唯一，不能再单独保证 `id` 全表唯一。如果业务依赖单列 `id` 的数据库唯一约束，必须先重新设计键或重新评估是否分区。用户定义的 InnoDB 分区表也不能参与外键关系，既不能引用别的表，也不能被别的表引用。这些是 MySQL 的具体限制，不能直接套用到崖山数据库。

分区粒度同样需要控制。按天分区方便逐日清理，但多年数据会产生大量分区；按年分区数量少，单个分区却可能过大，也不适合按月淘汰。应根据单次查询覆盖的时间范围、保留期限、每个分区的数据量和维护窗口，在天、月、年之间取舍。示例中的 `p_later` 是兜底分区：后续年份都会落进去；如需以后按年份单独管理，就要提前规划拆分该分区。

## 4. 与分表、分片的区别

- **数据库原生分区**：同一张逻辑表下由数据库管理多个分区，应用通常仍使用同一个表名。
- **应用层分表／分库分片**：应用或中间件把数据路由到多张表、多个库；跨表查询、事务及全局约束通常需要额外设计。
- **分布式部署**：分区本身不表示数据一定分布在多台机器上。具体产品可以把分区用于分布式数据放置，但这是另一层能力。

## 5. 已有大表如何改造

建表时确定分区规则通常比事后改造简单。已有非分区大表要改为分区表，需要重新组织现有数据，并评估耗时、额外空间和写入影响。以 **MySQL 8.4 + InnoDB** 为例，`ALTER TABLE ... PARTITION BY ...` 可以给已有表添加分区，但相关重分区操作使用 `COPY` 算法，不能把它视为无写入影响的在线切换。

常见迁移方案是：创建新分区表 → 分批迁移历史数据 → 同步迁移期间的增量写入 → 校验数据 → 切换访问。数据库实例未必需要停机，但最终切换可能需要短暂限制写入；具体窗口取决于数据库版本、表类型和迁移方案。已有分区表增删分区，与把非分区表整体改成分区表是两类不同操作，也要分别评估锁和数据移动成本。

### 5.1 已分区表的日常维护

- **提前准备新分区**：避免新数据超出已定义的分区范围。使用 `MAXVALUE` 兜底时，后续若想从中拆出独立分区，需评估重组操作；崖山 `INTERVAL` 可按规则自动扩展，但仍应监控分区增长。
- **按保留期清理**：确认某个分区内的数据可以整体淘汰后，再执行删除分区。MySQL 的 `DROP PARTITION` 会连同该分区的数据一起删除；如果只想改变边界并保留数据，应使用相应的重组操作。删除前还要考虑备份、归档和恢复要求。
- **交换分区**：MySQL 支持把一个分区与一张非分区表交换；崖山从 23.4.4 起也提供 `EXCHANGE PARTITION`，但仅适用于符合条件的 HEAP 表，且表结构与约束需匹配。交换的是**一个分区与一张表**，不是把一张普通大表自动改造成完整分区表。是否逐行校验、是否维护索引及对并发的影响，需按具体产品和版本检查。

### 5.2 迁移前的核对清单

1. **结构约束**：核对主键、唯一键、外键、索引及数据类型是否允许目标分区方案；尤其不要为满足分区规则而无意改变业务唯一性。
2. **数据与写入**：预估全量数据重组的时间和额外空间，设计增量同步、失败重试与新旧表一致性校验；明确最终切换时允许多长时间限制写入。
3. **性能收益**：挑选高频、慢查询分别比较改造前后的执行计划、访问分区、扫描行数与耗时；同时观察写入和跨分区查询是否退化。
4. **运维节奏**：确定新增分区、历史归档、分区数量监控及恢复流程。分区边界应与实际保留和清理周期对齐。
