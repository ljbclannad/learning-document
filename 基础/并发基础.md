## 1. 线程同步基础

### 1.1 **synchronized**
- 可用于实例方法、静态方法、代码块：保护共享资源的原子性、可见性、有序性。
- 底层依赖对象监视器（monitorenter/monitorexit）与对象头 Mark Word。

```java
public class SyncSamples {
	public synchronized void syncInstance() { /* ... */ } //锁住的是“当前实例对象”——也就是 this
	public static synchronized void syncStatic() { /* ... */ } //所有线程，只要调用 Demo 的 static synchronized 方法，都会竞争同一把锁。
	public static void bar() { //所有线程，只要调用 Demo 的 static synchronized 方法，都会竞争同一把锁。
		synchronized (SyncSamples.class) {
			// ...
		}
	}
	public void block() {
		synchronized (this) { //锁住的是“当前实例对象”——也就是 this
			// 临界区
		  }
	  }
  }
  ```

### 1.2 **ReentrantLock**
- `java.util.concurrent.locks` 中的显式锁，支持可重入、公平/非公平策略、`tryLock`、`lockInterruptibly`。
- 必须在 `finally` 块中释放锁，支持条件变量（`Condition`）。
  
	```java
	ReentrantLock lock = new ReentrantLock(true);
	lock.lock();
	try {
		// 临界区
	} finally {
		lock.unlock();
	}
	```

### 1.3 **ReentrantReadWriteLock**
- 读写分离：多个读可以并行，写独占。
- 适合读多写少场景，可配合 `StampedLock` 获取乐观读。

```java
import java.util.concurrent.locks.ReentrantReadWriteLock;

class RWMap<K, V> {
	private final java.util.Map<K, V> map = new java.util.HashMap<>();
	private final ReentrantReadWriteLock rwLock = new ReentrantReadWriteLock();

	/*
	线程 A 拿到 writeLock 后，其他线程在想拿 readLock 或 writeLock 时都会被阻塞；
	map.put(key, value) 正好放在“持有写锁”的这段时间内执行；
	所以：逻辑上是“给 Map 的写操作加了一把锁”，但物理上锁的是 ReentrantReadWriteLock 维护的锁状态，而不是 map。
	*/

	// 读操作，可被多个线程并发访问
	public V get(K key) {
		rwLock.readLock().lock();
		try {
			return map.get(key);
		} finally {
			rwLock.readLock().unlock();
		}
	}

	// 写操作，独占锁
	public void put(K key, V value) {
		rwLock.writeLock().lock();
		try {
			map.put(key, value);
		} finally {
			rwLock.writeLock().unlock();
		}
	}
}
```


### 1.4 **Condition（条件变量）**
- 结合 `ReentrantLock` 使用，实现更精细的等待/唤醒。

```java
class BoundedBuffer {
	private final ReentrantLock lock = new ReentrantLock();
	  private final Condition notEmpty = lock.newCondition();
	  private final Condition notFull = lock.newCondition();
	private final int[] buffer = new int[10];
	private int putIdx, takeIdx, count;

	public void put(int val) throws InterruptedException {
		  lock.lock();
		  try {
			  while (count == buffer.length) {
				  notFull.await();
			  }
			buffer[putIdx] = val;
			putIdx = (putIdx + 1) % buffer.length;
			  count++;
			  notEmpty.signal();
		  } finally {
			  lock.unlock();
		  }
	  }
  
	  public int take() throws InterruptedException {
		  lock.lock();
		  try {
			  while (count == 0) {
				  notEmpty.await();
			  }
			int val = buffer[takeIdx];
			takeIdx = (takeIdx + 1) % buffer.length;
			  count--;
			  notFull.signal();
			return val;
		  } finally {
			  lock.unlock();
		  }
	  }
}
```

### 1.5 **原子变量家族**
- 位于 `java.util.concurrent.atomic`，内部使用 CAS。
- `AtomicInteger/Long`, `AtomicReference`, `AtomicStampedReference`（含版本号防 ABA）。

  ```java
	AtomicInteger counter = new AtomicInteger();
	int result = counter.incrementAndGet();
	```

### 1.6 ThreadLocal 概览
- 为每个线程提供独立副本，避免共享数据竞争。
- 适用存储上下文信息（如 TraceId、数据库连接）。详见 [ThreadLocal 实战](#11-threadlocal-实战)。

**小结**：`synchronized` 适合简单场景；需要更强控制能力时选择 `ReentrantLock` 及其配套工具。
| 类型                                         | 锁定对象/机制                        | 特点说明                                                                                                   |
| -------------------------------------------- | ------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| Lock 系列（如 ReentrantLock、ReadWriteLock） | “锁”实例本身，如 new ReentrantLock() | 锁只负责管理 lock/unlock，至于具体保护的数据（如 map/list/其它逻辑）它并不知情，灵活但更考程序员自律与规范 |
| synchronized(obj)                            | obj 的内置锁（monitor）              | 锁定的是 obj 对象（每个对象一个内置锁），只是实现互斥，也不会自动知道锁定的是何种数据                      |

## 2. 虚拟线程
- **定义**：JDK 19+（预览，JDK 21 默认可用）的轻量级线程，由 JVM 调度，不再直接绑定 OS 线程。
- **优势**：创建/切换成本低，易于在 IO 密集型场景实现“每请求一线程”的直观模型。
- **特性**：
  - `Thread.ofVirtual().start(() -> {...})`
  - 支持 `Executors.newVirtualThreadPerTaskExecutor()`
  - 与传统同步 API 兼容（阻塞操作会协作式挂起）。

```java
try (var executor = Thread.ofVirtual().factory().newThreadPerTaskExecutor()) {
	executor.submit(() -> Files.readString(Path.of("/tmp/data")));
}
```

- **适用场景**：高并发 IO（网关、RPC、爬虫）、大量短生命周期任务。
- **注意**：
  - 仍需关注外部资源限制（数据库连接、文件句柄）。
  - 监控/Profiler 需升级以识别虚拟线程。

## 3. 线程池与调度策略

### 3.1 核心概念
- 线程复用、任务排队、资源上限控制。
- 核心类：`Executor` -> `ExecutorService` -> `ThreadPoolExecutor`。

### 3.2 常用线程池类型
- `Executors.newFixedThreadPool(n)`：固定大小，适合稳定吞吐。
- `Executors.newCachedThreadPool()`：可伸缩，适合大量短任务。
- `Executors.newSingleThreadExecutor()`：顺序执行，常用于串行化任务。
- `Executors.newScheduledThreadPool(n)`：定时/周期任务。
- **最佳实践**：优先显式构造 `ThreadPoolExecutor`，避免默认无限队列或线程数。

### 3.3 ThreadPoolExecutor 参数
- `corePoolSize`：常驻线程。
- `maximumPoolSize`：峰值线程。
- `keepAliveTime`：非核心线程空闲超时。
- `workQueue`：如 `ArrayBlockingQueue`、`LinkedBlockingQueue`、`SynchronousQueue`。
- `ThreadFactory`：自定义线程名、优先级、异常处理。
- `RejectedExecutionHandler`：拒绝策略（Abort、CallerRuns、Discard、DiscardOldest 或自定义）。

### 3.4 提交与关闭
```java
ExecutorService executor = new ThreadPoolExecutor(
	4, 8, 60, TimeUnit.SECONDS,
	new LinkedBlockingQueue<>(100),
	new ThreadFactoryBuilder().setNameFormat("biz-%d").build(),
	new ThreadPoolExecutor.CallerRunsPolicy());

Future<String> future = executor.submit(() -> "result");
String value = future.get();
executor.shutdown();
```

### 3.5 监控指标
- `getPoolSize()` 当前线程数。
- `getActiveCount()` 正在执行的线程。
- `getQueue().size()` 积压任务。
- `getCompletedTaskCount()` 累计完成数。
- 配合 Micrometer/Prometheus 或 `ThreadPoolExecutor` 包装器输出指标。

### 3.6 异常捕获
1. **Future.get**：捕获 `ExecutionException`，定位任务内部异常。
2. **自定义 ThreadFactory**：设置线程名与 `UncaughtExceptionHandler`。
3. **任务内 try/catch**：对可恢复性错误就地处理，避免线程静默退出。

```java
executor.submit(() -> {
	try {
		riskyCall();
	} catch (Exception ex) {
		log.error("task failed", ex);
		throw ex;
	}
});
```

## 6. CAS 与原子类

### 6.1 基本概念
- Compare-And-Swap：比较期望值与内存中当前值相等，则写入新值；否则重试。
- 依赖 CPU 指令，保证单个变量更新的原子性。

### 6.2 优缺点
- **优点**：无锁、性能好、避免阻塞。
- **缺点**：ABA 问题、自旋开销、一次只能更新一个变量。

### 6.3 示例
```java
public class CasCounter {
	private final AtomicInteger counter = new AtomicInteger();
	public void inc() {
		int expect, update;
		do {
			expect = counter.get();
			update = expect + 1;
		} while (!counter.compareAndSet(expect, update));
	}
}
```

## 7. ABA 问题与解法

### 7.1 问题描述
- 线程读取值 A，准备写入 B；期间其他线程把值改成 C 再改回 A，CAS 仍然成功，但数据已变化。

### 7.2 方案
1. **AtomicStampedReference / AtomicMarkableReference**：引入版本号或标记。

```java
AtomicStampedReference<String> ref = new AtomicStampedReference<>("A", 0);
int stamp = ref.getStamp();
boolean ok = ref.compareAndSet("A", "B", stamp, stamp + 1);
```

2. **LongAdder / LongAccumulator**：分段累加，避免单点 CAS 热点，适合计数场景。
3. **锁（ReentrantLock / synchronized）**：在逻辑复杂或需要批量更新数据时，使用显式锁串行化。

## 8. AQS 工作原理
- `AbstractQueuedSynchronizer` 是多数同步器（`ReentrantLock`、`Semaphore`、`CountDownLatch` 等）的基础。

### 8.1 组成
- `state`：整型共享状态。
- FIFO 双向链表队列：保存等待线程（Node）。
- 模式：独占 (`EXCLUSIVE`) 与共享 (`SHARED`)。

### 8.2 核心模板方法
- `tryAcquire/tryRelease`
- `tryAcquireShared/tryReleaseShared`
- `isHeldExclusively`

### 8.3 获取/释放流程
1. 调用 `acquire(arg)`：若 `tryAcquire` 成功则返回，否则将线程封装为 Node 入队并挂起（`park`）。
2. 释放时调用 `release(arg)`：更新 `state`，唤醒队列下一个节点。
3. 共享模式下可同时唤醒多个节点。

### 8.4 自定义独占锁示例
```java
class MyLock {
	private static class Sync extends AbstractQueuedSynchronizer {
		protected boolean tryAcquire(int acquires) {
			if (compareAndSetState(0, 1)) {
				setExclusiveOwnerThread(Thread.currentThread());
				return true;
			}
			return false;
		}
		protected boolean tryRelease(int releases) {
			if (getState() == 0) throw new IllegalMonitorStateException();
			setExclusiveOwnerThread(null);
			setState(0);
			return true;
		}
		protected boolean isHeldExclusively() {
			return getState() == 1;
		}
	}
	private final Sync sync = new Sync();
	public void lock() { sync.acquire(1); }
	public void unlock() { sync.release(1); }
}
```

## 9. synchronized 深入理解

### 9.1 字节码指令
- `monitorenter` / `monitorexit` 包裹临界区。

### 9.2 对象头 & Mark Word
- 包含锁标志位、是否偏向、线程 ID、GC 信息。
- 锁状态：无锁 → 偏向锁 → 轻量级锁 → 重量级锁，根据竞争程度逐级升级。

### 9.3 JVM 锁优化
- **偏向锁**：单线程重复进入时直接绑定线程，避免 CAS。
- **轻量级锁**：自旋 + CAS，适合短时间锁竞争。
- **自旋锁与自适应自旋**：在释放预计很快的情况下自旋等待。
- **锁消除**：逃逸分析发现对象未逃逸线程，则消除锁。

### 9.4 与 ReentrantLock 对比

| 特性      | synchronized  | ReentrantLock                |
| --------- | ------------- | ---------------------------- |
| 加锁/释放 | 自动          | 手动                         |
| 公平性    | 不支持        | 支持公平/非公平              |
| 可中断    | 不可中断      | `lockInterruptibly`          |
| 条件队列  | `wait/notify` | 多个 `Condition`             |
| 监控指标  | 无直接 API    | `isLocked`、`getQueueLength` |

**结论**：简单场景首选 `synchronized`；需要灵活性或监控时使用 `ReentrantLock`。

## 10. 内存模型、指令重排与 volatile

### 10.1 指令重排类型
- 编译器优化、CPU 流水线、JIT 优化。
- 在单线程下等价，在多线程下可能破坏先后顺序。

### 10.2 Java 内存模型 (JMM)
- 线程之间通过主内存共享数据；每个线程有工作内存副本。
- `happens-before` 规则确保可见性与有序性。

### 10.3 volatile 的作用
- 保证对变量的读写直接发生在主内存。
- 禁止特定指令重排（插入内存屏障）。
- 不保证复合操作的原子性（如 `count++` 仍需锁或原子类）。volatile 只管“这一次读/写”和前后操作的有序与可见，不负责把“一串操作”变成一个不可分割的大原子块。（只是建立了屏障，不能保证屏障内的原子操作。）

```java
class StopFlag {
	private volatile boolean running = true;
	void stop() { running = false; }
	void work() {
		while (running) {
			// do work
		}
	}
}
```

### 10.4 双重检查锁 (DCL) 单例
```java
class Singleton {
	private static volatile Singleton INSTANCE;
	static Singleton getInstance() {
		if (INSTANCE == null) {
			synchronized (Singleton.class) {
				if (INSTANCE == null) {
					INSTANCE = new Singleton();
				}
			}
		}
		return INSTANCE;
	}
}
```

## 11. ThreadLocal 实战

### 11.1 基本用法
	```java
class ContextHolder {
	private static final ThreadLocal<String> TRACE_ID = ThreadLocal.withInitial(() -> "");
	static void set(String id) { TRACE_ID.set(id); }
	static String get() { return TRACE_ID.get(); }
	static void clear() { TRACE_ID.remove(); }
}
```

### 11.2 适用场景
- 请求上下文、用户会话、数据库连接、SimpleDateFormat 缓存。

### 11.3 注意事项
- 在线程池中必须调用 `remove()`，否则复用线程会携带旧数据，导致内存泄漏或脏数据。
- 对象过大或生命周期过长不适合放入 ThreadLocal。
- 可结合 `InheritableThreadLocal` 在子线程继承上下文（虚拟线程中需注意性能）。

## 12. 死锁：条件、排查与治理

### 12.1 四个必要条件
1. **互斥**：资源一次只供一个线程使用。
2. **占有且等待**：持有资源同时请求其他资源。
3. **不可抢占**：资源不能被强制抢走。
4. **循环等待**：两个或多个线程形成环状等待链。

### 12.2 示例
```java
Object lockA = new Object();
Object lockB = new Object();
		new Thread(() -> {
	synchronized (lockA) {
		sleep(100);
		synchronized (lockB) {}
	}
}).start();
		new Thread(() -> {
	synchronized (lockB) {
		sleep(100);
		synchronized (lockA) {}
	}
}).start();
```

### 12.3 排查手段
- `jps -l` 查进程 ID，`jstack <pid>` 定位死锁线程，输出 `Found one Java-level deadlock`。
- 可使用 `jconsole`、`VisualVM`、`Java Flight Recorder` 实时监控线程状态。

### 12.4 预防策略
- **统一加锁顺序**：所有线程按同样顺序申请锁，破坏循环等待。
- **tryLock + 超时**：获取失败时释放已持有锁并重试，避免长期阻塞。
- **资源层限流**：减少同时持有多把锁的需求。
- **监控告警**：线程池堆栈定期采样，发现长时间阻塞及时告警。

---

### 12.5 进一步实践建议
- 建立统一的线程池与锁使用规范（命名、监控、降级策略）。
- 在关键并发组件上补充单元测试 + JMH 基准，验证可见性与性能假设。
- 结合分布式场景（如分布式锁、跨 JVM 协调）时，先确保本地并发模型牢固，再延伸到多节点一致性策略。

## 13. 虚拟线程和普通线程

### 13.1 先给结论
- **普通线程（platform thread）**：OS 级线程，1:1 绑定内核线程，创建/切换成本高。
- **虚拟线程（virtual thread）**：JDK 自带的用户态线程，极轻量，可在同一 OS 线程上挂载和切换海量虚拟线程。
- **用法**：语法几乎一致，差别主要在创建方式与调度器。
- **场景**：虚拟线程适合 I/O 密集型高并发请求；CPU 密集且线程数有限的场景收益有限。

---

### 13.2 核心概念
**普通线程（Platform Thread）**
- `new Thread(...)`、`Executors.newFixedThreadPool(...)` 创建的就是平台线程。
- 每个 Java 线程都绑定一个 OS 线程，默认 1MB 左右栈空间，切换由操作系统完成。
- 高并发 I/O 场景下需要开大量线程，容易耗尽内存并导致上下文切换抖动。

**虚拟线程（Virtual Thread）**
- 来自 Project Loom，JDK 21 已 GA。
- JVM 在用户态调度，可将栈拆分成分段堆分配；阻塞 I/O 或 `LockSupport.park()` 时挂起虚拟线程、释放 carrier thread。
- 阻塞结束后再把虚拟线程挂回某个 carrier OS 线程继续执行。

> 一句话：普通线程“贵又大”，虚拟线程“便宜又小，可以批发”。

---

### 13.3 基本用法示例
**平台线程**
```java
Thread t = new Thread(() ->
	System.out.println("hello from platform thread: " + Thread.currentThread())
);
t.start();

ExecutorService executor = Executors.newFixedThreadPool(200);
executor.submit(() -> {
	// do something
});
```

**虚拟线程（推荐 `Thread.ofVirtual()`）**
```java
Thread t = Thread.ofVirtual().start(() ->
	System.out.println("hello from virtual thread: " + Thread.currentThread())
);
```

**按任务建虚拟线程的执行器**
```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
	for (int i = 0; i < 1_000_000; i++) {
		int id = i;
		executor.submit(() -> handleRequest(id));
	}
} // try-with-resources 自动优雅关闭
```

> 虚拟线程不适合放传统固定大小线程池，直接用 `newVirtualThreadPerTaskExecutor()` 让 JVM 决定承载线程即可。

### 13.4 工程维度差异
| 关注点   | 平台线程                 | 虚拟线程                                           |
| -------- | ------------------------ | -------------------------------------------------- |
| 调度模型 | OS 调度，1:1 映射        | JVM M:N 调度到少量 carrier 线程                    |
| 阻塞 I/O | 阻塞即占满 OS 线程       | 阻塞点挂起虚拟线程，释放 carrier                   |
| 线程数量 | 几百/几千已吃力          | 百万级取决于堆与任务规模                           |
| 内存开销 | 固定大栈                 | 栈分段、按需增长、可挂到堆上                       |
| 代码风格 | 为高并发常用 NIO/回调    | 直接写同步阻塞代码，JVM 伪非阻塞                   |
| 观测调试 | Thread dump 可见业务线程 | Thread dump 同样可见虚拟线程栈，carrier 主要跑调度 |

---

### 13.5 典型场景
**非常适合**
1. **高并发 I/O 服务**：Web/RPC 网关、HTTP 客户端、爬虫——“一个请求一个虚拟线程”，不再纠结线程池 size。
2. **批处理 / ETL / 爬虫**：大量网络或数据库 I/O，虚拟线程能自动弹性。
3. **长连接/协议服务**：IM、WebSocket、长连接网关——一个连接一个虚拟线程即可。

**收益有限**
1. **CPU 密集场景**：瓶颈在 CPU，虚拟线程不能“变出”额外核心，仍需合理的 platform 线程池/ForkJoinPool。
2. **依赖阻塞 native 调用**：若 native 层阻塞 OS 线程，虚拟线程无法解挂，会退化为平台线程的成本。

---

### 13.6 线程池与协程思维
- 虚拟线程极轻量，传统“少量线程复用任务”的线程池意义降低，`newVirtualThreadPerTaskExecutor()` 本质是“一任务一线程”。
- 模型类似 Go 的 goroutine（M:N 调度），不同之处在于 Java 仍然保留 `Thread` 抽象，对旧代码更友好。

---

### 13.7 实战注意事项
1. **避免 busy-wait**：虚拟线程里长时间 `while(!flag){}` 会占满 carrier 线程，改用 `LockSupport.park()`、`Condition`、`CountDownLatch` 等同步工具。
2. **评估第三方库**：大锁或长时间阻塞的库会拖慢虚拟线程；必要时隔离在 platform 线程池中。
3. **谨慎使用 ThreadLocal**：虚拟线程数量巨大，ThreadLocal 滥用会成为内存炸弹，能参数传递就传参。
4. **CPU 密集任务单独托管**：将重计算任务下发到专门的平台线程池，避免占用 carrier。

---

### 13.8 一句话总结
> 虚拟线程让 Java“写同步阻塞代码也能获得接近异步非阻塞的扩展性”。I/O 密集型服务值得优先尝试；CPU 密集或依赖阻塞 native 的场景则需结合算法与平台线程优化，虚拟线程并非银弹。
