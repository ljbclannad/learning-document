## 1. 线程同步基础

### 1.1 **synchronized**
- 可用于实例方法、静态方法、代码块：保护共享资源的原子性、可见性、有序性。
- 底层依赖对象监视器（monitorenter/monitorexit）与对象头 Mark Word。
    - 同步方法：靠 ACC_SYNCHRONIZED，JVM 隐式加解锁；
    - 同步代码块：靠 monitorenter/monitorexit，手动加解锁。
- synchronized 是可重入锁：同一线程拿到锁后再次进入同一 monitor 不会死锁，内部会维护进入次数（递归次数）。

```java
public class SyncSamples {
	public synchronized void syncInstance() { /* ... */ } //锁住的是“当前实例对象”——也就是 this
	public static synchronized void syncStatic() { /* ... */ } //所有线程，只要调用 Demo 的 static synchronized 方法，都会竞争同一把锁。
	public static void bar() { //所有线程，只要调用 Demo 的 static synchronized 方法，都会竞争同一把锁。
		synchronized (SyncSamples.class) {
			// ...
		}
	}
	public void block() {
		synchronized (this) { //锁住的是“当前实例对象”——也就是 this
			// 临界区
		  }
	  }
  }
  ```

### 1.2 **ReentrantLock**
- `java.util.concurrent.locks` 中的显式锁，支持可重入、公平/非公平策略、`tryLock`、`lockInterruptibly`。
- 必须在 `finally` 块中释放锁，支持条件变量（`Condition`）。
  
	```java
	ReentrantLock lock = new ReentrantLock(true);
	lock.lock();
	try {
		// 临界区
	} finally {
		lock.unlock();
	}
	```

### 1.3 **ReentrantReadWriteLock**
- 读写分离：多个读可以并行，写独占。
- 适合读多写少场景，可配合 `StampedLock` 获取乐观读。

```java
import java.util.concurrent.locks.ReentrantReadWriteLock;

class RWMap<K, V> {
	private final java.util.Map<K, V> map = new java.util.HashMap<>();
	private final ReentrantReadWriteLock rwLock = new ReentrantReadWriteLock();

	/*
	线程 A 拿到 writeLock 后，其他线程在想拿 readLock 或 writeLock 时都会被阻塞；
	map.put(key, value) 正好放在“持有写锁”的这段时间内执行；
	所以：逻辑上是“给 Map 的写操作加了一把锁”，但物理上锁的是 ReentrantReadWriteLock 维护的锁状态，而不是 map。
	*/

	// 读操作，可被多个线程并发访问
	public V get(K key) {
		rwLock.readLock().lock();
		try {
			return map.get(key);
		} finally {
			rwLock.readLock().unlock();
		}
	}

	// 写操作，独占锁
	public void put(K key, V value) {
		rwLock.writeLock().lock();
		try {
			map.put(key, value);
		} finally {
			rwLock.writeLock().unlock();
		}
	}
}
```


### 1.4 **Condition（条件变量）**
- 结合 `ReentrantLock` 使用，实现更精细的等待/唤醒。

```java
class BoundedBuffer {
	private final ReentrantLock lock = new ReentrantLock();
	private final Condition notEmpty = lock.newCondition();
	private final Condition notFull = lock.newCondition();
	private final int[] buffer = new int[10];
	private int putIdx, takeIdx, count;

	public void put(int val) throws InterruptedException {
		lock.lock();
		try {
			while (count == buffer.length) {
				notFull.await();
			}
			buffer[putIdx] = val;
			putIdx = (putIdx + 1) % buffer.length;
			count++;
			notEmpty.signal();
		} finally {
			lock.unlock();
		}
	  }
  
	  public int take() throws InterruptedException {
		  lock.lock();
		  try {
			while (count == 0) {
				  notEmpty.await();
			  }
			int val = buffer[takeIdx];
			takeIdx = (takeIdx + 1) % buffer.length;
			  count--;
			  notFull.signal();
			return val;
		  } finally {
			  lock.unlock();
		  }
	  }
}
```

### 1.5 **原子变量家族**
- 位于 `java.util.concurrent.atomic`，内部使用 CAS。
- `AtomicInteger/Long`, `AtomicReference`, `AtomicStampedReference`（含版本号防 ABA）。
    ```java
	AtomicInteger counter = new AtomicInteger();
	int result = counter.incrementAndGet();
	```
- *AtomicStampedReference：*
    - 内部维护 (reference, stamp) 二元组
    - CAS 时同时比较这两个：
    ```java
	AtomicStampedReference<String> ref = new AtomicStampedReference<>("A", 0);
	int stamp = ref.getStamp();
	boolean ok = ref.compareAndSet("A", "B", stamp, stamp + 1);
	```

### 1.6 ThreadLocal 概览
- 为每个线程提供独立副本，避免共享数据竞争。
- 适用存储上下文信息（如 TraceId、数据库连接）。详见 [ThreadLocal 实战](#11-threadlocal-实战)。

**小结**：`synchronized` 适合简单场景；需要更强控制能力时选择 `ReentrantLock` 及其配套工具。
| 类型                                         | 锁定对象/机制                        | 特点说明                                                                                                   |
| -------------------------------------------- | ------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| Lock 系列（如 ReentrantLock、ReadWriteLock） | “锁”实例本身，如 new ReentrantLock() | 锁只负责管理 lock/unlock，至于具体保护的数据（如 map/list/其它逻辑）它并不知情，灵活但更考程序员自律与规范 |
| synchronized(obj)                            | obj 的内置锁（monitor）              | 锁定的是 obj 对象（每个对象一个内置锁），只是实现互斥，也不会自动知道锁定的是何种数据                      |

### 1.7 LongAdder

1. 它把“所有线程都抢同一个原子变量”的热点，分散成多个分片计数槽（cells），线程各自更新自己的槽，最后再把所有槽加起来得到总和。
    1. *AtomicLong 为什么会慢：单点 CAS 热点*
        - AtomicLong.incrementAndGet() 本质是：
            - 读当前值 v
            - CAS 把 v 改成 v+1
            - 失败就自旋重试

        - 当并发很高时，很多线程同时 CAS 同一个内存地址：
            - cache line 在多个 CPU 核之间疯狂“抢所有权”
            - CAS 失败率高，自旋重试多
            - 总开销飙升

    2. LongAdder 的核心结构：base + cells[]
        - LongAdder 继承自 Striped64（内部实现核心），大致结构是：
            - volatile long base：低争用时直接更新 base（便宜）
            - volatile Cell[] cells：高争用时启用分片数组
            - 每个 Cell 本质上就是一个带 padding 的 volatile long value（避免伪共享）

    3. 更新逻辑大致是：
        - 先尝试 CAS 更新 base
        - 如果 CAS 失败（说明有竞争）：
            - 确保 cells 已初始化（按需懒初始化）
            - 根据线程的 probe/hash 选择一个 cell：cells[hash & (len-1)]
            - CAS 更新这个 cell.value
        - 如果更新 cell 也失败（这个槽也挤爆了）：
            - 可能 rehash（改变 probe）
            - 或者扩容 cells（通常翻倍），把冲突进一步摊薄

2. 为什么它更快：把竞争概率打散
    - 假设有 N 个线程同时 increment：
        - AtomicLong：所有 N 个线程竞争同一个点，冲突概率接近 1
        - LongAdder：如果 cells 长度是 M，线程被打散到 M 个槽
            - 平均每个槽大概 N/M 个线程竞争，冲突强度大幅下降

    - **在高并发下，只要 M 足够大（通常会扩到接近 CPU 核数/争用水平），每个 cell 上的 CAS 失败率就会明显降低，自旋次数也少，整体吞吐就上来了。**

3. 还有个隐藏大招：避免伪共享（false sharing）
    - Cell 里会做 padding（填充字段，或用 @Contended 之类的手段），目的：
        - 让不同 cell 的 value 尽量落在不同 cache line 上
        - 避免两个线程更新不同 cell，却因为共享同一 cache line 而互相干扰

    - 这点对高并发更新特别关键：不然“分片了”也可能被 cache line 争用拖慢。

4. 为什么它不是总比 AtomicLong 快：读取不是原子一致的
    - LongAdder 的代价是：
        - sum() 需要把 base + Σcells[i] 全部累加
        - sum() 期间别的线程可能还在更新，所以拿到的是近似值（通常叫 weakly consistent）
        - 它不提供像 AtomicLong.getAndIncrement() 那样严格的“全局原子序列语义”

    - 因此结论是：
        - 高频写、低频读（统计计数、QPS、指标埋点）→ LongAdder 完胜
        - 需要强一致读/精确时序语义（发号器、严格计数门槛）→ 用 AtomicLong / 锁

5. 总结
    - **AtomicLong 在高并发下是单点 CAS 热点，导致 cache line 争用和大量自旋失败；LongAdder 通过 base+cells 的分片计数把更新分散到多个槽，降低冲突，并通过 padding 避免伪共享，所以高并发写性能更好。但它的 sum 是弱一致的，不适合需要严格原子读的场景。**
    - LongAdder 用于“统计类”高并发计数；Atomic 用于“控制类”并发流程（CAS、状态机、发号、快照替换）。


## 2. 虚拟线程
- **定义**：JDK 19+（预览，JDK 21 默认可用）的轻量级线程，由 JVM 调度，不再直接绑定 OS 线程。
- **优势**：创建/切换成本低，易于在 IO 密集型场景实现“每请求一线程”的直观模型。
- **特性**：
  - `Thread.ofVirtual().start(() -> {...})`
  - 支持 `Executors.newVirtualThreadPerTaskExecutor()`
  - 与传统同步 API 兼容（阻塞操作会协作式挂起）。

    ```java
    try (var executor = Thread.ofVirtual().factory().newThreadPerTaskExecutor()) {
        executor.submit(() -> Files.readString(Path.of("/tmp/data")));
    }
    ```

- **适用场景**：高并发 IO（网关、RPC、爬虫）、大量短生命周期任务。
- **注意**：
  - 仍需关注外部资源限制（数据库连接、文件句柄）。
  - 监控/Profiler 需升级以识别虚拟线程。

## 3. 线程池与调度策略

### 3.1 核心概念
- 线程复用、任务排队、资源上限控制。
- 核心类：`Executor` -> `ExecutorService` -> `ThreadPoolExecutor`。

### 3.2 常用线程池类型
- `Executors.newFixedThreadPool(n)`：固定大小，适合稳定吞吐。
- `Executors.newCachedThreadPool()`：可伸缩，适合大量短任务。
- `Executors.newSingleThreadExecutor()`：顺序执行，常用于串行化任务。
- `Executors.newScheduledThreadPool(n)`：定时/周期任务。
- **最佳实践**：优先显式构造 `ThreadPoolExecutor`，避免默认无限队列或线程数。

### 3.3 ThreadPoolExecutor 参数
- `corePoolSize`：常驻线程。
- `maximumPoolSize`：峰值线程。
- `keepAliveTime`：非核心线程空闲超时。
- `workQueue`：如 `ArrayBlockingQueue`、`LinkedBlockingQueue`、`SynchronousQueue`。
- `ThreadFactory`：自定义线程名、优先级、异常处理。
- `RejectedExecutionHandler`：拒绝策略（Abort-抛异常、CallerRuns-自己执行、Discard-舍弃、DiscardOldest-舍弃最老的 或自定义）。

#### 3.3.1 ArrayBlockingQueue vs LinkedBlockingQueue

**核心区别对比**

| 维度 | ArrayBlockingQueue | LinkedBlockingQueue |
|------|-------------------|---------------------|
| **底层结构** | 数组（循环数组） | 链表（单向链表） |
| **容量** | 必须指定固定容量 | 可选容量（默认 Integer.MAX_VALUE） |
| **锁机制** | **单锁**（一把锁控制读写） | **双锁**（读锁 takeLock + 写锁 putLock） |
| **内存占用** | 预分配数组空间 | 按需分配节点（每个节点额外开销） |
| **吞吐量** | 较低（读写互斥） | 较高（读写可并发） |
| **公平性** | 支持公平/非公平 | 只支持非公平（FIFO 保证顺序） |

**1. 锁机制差异（最关键）**

*ArrayBlockingQueue：单锁*
```java
// 伪代码
final ReentrantLock lock = new ReentrantLock();

public void put(E e) {
    lock.lock();
    try {
        // 入队操作
    } finally {
        lock.unlock();
    }
}

public E take() {
    lock.lock();  // 和 put 竞争同一把锁
    try {
        // 出队操作
    } finally {
        lock.unlock();
    }
}
```
- **生产者和消费者互斥**：一个在写，另一个必须等待
- 适合读写速度接近的场景

*LinkedBlockingQueue：双锁*
```java
// 伪代码
final ReentrantLock takeLock = new ReentrantLock();  // 读锁
final ReentrantLock putLock = new ReentrantLock();   // 写锁

public void put(E e) {
    putLock.lock();
    try {
        // 入队操作
    } finally {
        putLock.unlock();
    }
}

public E take() {
    takeLock.lock();  // 不和 put 竞争
    try {
        // 出队操作
    } finally {
        takeLock.unlock();
    }
}
```
- **生产者和消费者可并发**：一个写头、一个读尾，互不干扰
- 吞吐量更高

**2. 容量限制**

*ArrayBlockingQueue*
```java
// 必须指定容量
BlockingQueue<String> queue = new ArrayBlockingQueue<>(100);
```
- 强制有界，防止内存溢出
- 适合需要严格流控的场景

*LinkedBlockingQueue*
```java
// 可以不指定（危险！）
BlockingQueue<String> queue1 = new LinkedBlockingQueue<>();  
// 默认 Integer.MAX_VALUE，相当于无界

// 也可以指定
BlockingQueue<String> queue2 = new LinkedBlockingQueue<>(100);
```
- 不指定容量时相当于无界队列，可能导致 OOM
- **Executors.newFixedThreadPool() 默认用的就是无界 LinkedBlockingQueue**，这是个坑

**3. 内存使用**

*ArrayBlockingQueue*
- 创建时就分配整个数组空间
- 内存占用固定，无额外节点开销
- 适合容量较小的场景

*LinkedBlockingQueue*
- 按需创建节点，每个节点有额外的 `next` 指针开销
- 空队列时几乎不占内存
- 适合容量较大或动态变化的场景

**4. 性能对比**

*高并发场景（生产消费都很快）*
- **LinkedBlockingQueue 更优**：双锁允许读写并发

*低并发或读写不均衡*
- **ArrayBlockingQueue 更优**：
  - 无节点分配开销
  - 缓存友好（数组连续内存）
  - 单锁开销更小

**使用场景建议**

*选择 ArrayBlockingQueue*
```java
// 1. 需要严格容量限制
new ArrayBlockingQueue<>(100);

// 2. 需要公平策略（按等待时间排队）
new ArrayBlockingQueue<>(100, true);

// 3. 队列容量较小（几百以内）
// 4. 生产消费速度接近
```

*选择 LinkedBlockingQueue*
```java
// 1. 高吞吐量场景（生产消费都很快）
new LinkedBlockingQueue<>(1000);

// 2. 容量较大或动态变化
// 3. 生产消费速度差异大（双锁优势明显）

// ⚠️ 避免无界队列
// 错误：new LinkedBlockingQueue<>();  // 可能 OOM
// 正确：new LinkedBlockingQueue<>(10000);
```

**线程池中的选择**

```java
// ❌ 不推荐：Executors 默认用无界 LinkedBlockingQueue
ExecutorService bad = Executors.newFixedThreadPool(10);

// ✅ 推荐：显式指定有界队列
ThreadPoolExecutor good = new ThreadPoolExecutor(
    10, 10, 0L, TimeUnit.MILLISECONDS,
    new ArrayBlockingQueue<>(100),  // 或 new LinkedBlockingQueue<>(100)
    new ThreadPoolExecutor.CallerRunsPolicy()
);
```

**总结**
- **ArrayBlockingQueue**：有界、单锁、数组实现，适合**容量小、需要严格限流**的场景
- **LinkedBlockingQueue**：可选有界、双锁、链表实现，适合**高吞吐、容量大**的场景，但**必须指定容量**避免 OOM

#### 3.3.2 ArrayBlockingQueue 为什么采用单锁模式

**核心原因：数组结构的限制**

ArrayBlockingQueue 使用**循环数组**作为底层存储，这导致读写操作必须共享同一组索引变量：

```java
// ArrayBlockingQueue 内部结构（简化）
final Object[] items;       // 存储元素的数组
int takeIndex;              // 下次取元素的位置
int putIndex;               // 下次放元素的位置
int count;                  // 当前元素数量
```

**1. 索引竞争问题**

如果用双锁，会出现这种情况：

```java
// 假设用双锁（错误示例）
final ReentrantLock takeLock = new ReentrantLock();
final ReentrantLock putLock = new ReentrantLock();

public void put(E e) {
    putLock.lock();
    try {
        items[putIndex] = e;
        putIndex = (putIndex + 1) % items.length;  // 循环
        count++;  // ⚠️ 问题：count 被两个锁同时访问
    } finally {
        putLock.unlock();
    }
}

public E take() {
    takeLock.lock();
    try {
        E x = items[takeIndex];
        items[takeIndex] = null;
        takeIndex = (takeIndex + 1) % items.length;
        count--;  // ⚠️ 问题：count 被两个锁同时访问
    } finally {
        takeLock.unlock();
    }
}
```

问题：
- `count`、`putIndex`、`takeIndex` 这些共享变量需要在两个锁之间同步
- 即使用 `volatile` 也无法保证 `count++` 和 `count--` 的原子性
- 需要额外的 CAS 或第三把锁来保护这些变量，反而更复杂

**2. 数组边界的特殊情况**

循环数组在满/空状态时，`putIndex` 和 `takeIndex` 可能指向同一位置：

```
空队列：putIndex == takeIndex == 0
满队列：putIndex == takeIndex（但 count == capacity）
```

如果用双锁：
- 生产者和消费者可能同时操作同一个数组位置
- 需要复杂的同步机制来判断"满"还是"空"

**3. 与 LinkedBlockingQueue 的对比**

LinkedBlockingQueue 为什么能用双锁？

```java
// LinkedBlockingQueue 内部结构
static class Node<E> {
    E item;
    Node<E> next;
}

Node<E> head;  // 消费者只操作 head
Node<E> last;  // 生产者只操作 last
AtomicInteger count;  // 用原子类解决计数问题
```

关键差异：
- **链表的头尾分离**：生产者只操作 `last`，消费者只操作 `head`，天然隔离
- **独立的计数器**：用 `AtomicInteger` 保证 `count` 的原子性
- **无循环索引**：不需要共享 `putIndex/takeIndex`

**单锁的优势**

对于 ArrayBlockingQueue 来说，单锁反而更简单高效：

```java
final ReentrantLock lock = new ReentrantLock();

public void put(E e) {
    lock.lock();
    try {
        // 所有操作都在锁保护下，逻辑简单清晰
        while (count == items.length) {
            notFull.await();  // 等待非满
        }
        items[putIndex] = e;
        putIndex = (putIndex + 1) % items.length;
        count++;
        notEmpty.signal();  // 通知消费者
    } finally {
        lock.unlock();
    }
}
```

优点：
1. **实现简单**：无需复杂的同步协议
2. **无竞态条件**：所有共享变量都在同一把锁保护下
3. **Condition 变量天然支持**：`notFull` 和 `notEmpty` 可以直接绑定到同一把锁

**性能权衡**

单锁的代价：
- 生产者和消费者互斥，吞吐量受限

但对于 ArrayBlockingQueue：
- 数组操作本身很快（O(1) 读写）
- 锁竞争的开销相对较小
- 适合**容量较小、操作快速**的场景

如果需要高吞吐量：
- 用 `LinkedBlockingQueue`（双锁）
- 或用 `ConcurrentLinkedQueue`（无锁）
- 或用 `Disruptor`（环形缓冲区 + 无锁）

**总结**

ArrayBlockingQueue 采用单锁是因为：
1. **数组结构决定**：循环数组的 `putIndex`、`takeIndex`、`count` 必须强同步
2. **双锁成本高**：需要额外机制保护共享变量，反而更复杂
3. **设计取舍**：牺牲并发度换取实现简单性和正确性
4. **适用场景**：本身定位就是**有界、容量小、操作快**的队列，单锁够用

如果需要高并发吞吐，应该选择 LinkedBlockingQueue（双锁）或其他无锁数据结构。

#### 3.3.3 线程池执行流程详解

**完整执行流程图：**

```
提交任务 execute(task)
    ↓
┌─────────────────────────────────────────┐
│ 1. 当前线程数 < corePoolSize ?         │
│    ├─ 是 → 创建核心线程执行任务 ✓      │
│    └─ 否 → 继续                        │
└─────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────┐
│ 2. 工作队列未满 ?                       │
│    ├─ 是 → 任务入队 ✓                  │
│    └─ 否 → 继续                        │
└─────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────┐
│ 3. 当前线程数 < maximumPoolSize ?      │
│    ├─ 是 → 创建非核心线程执行任务 ✓    │
│    └─ 否 → 继续                        │
└─────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────┐
│ 4. 执行拒绝策略 ⚠️                     │
│    - AbortPolicy: 抛异常               │
│    - CallerRunsPolicy: 调用者执行      │
│    - DiscardPolicy: 静默丢弃           │
│    - DiscardOldestPolicy: 丢弃最老任务 │
└─────────────────────────────────────────┘
```

**关键点说明：**

1. **核心线程优先**：即使有空闲核心线程，也会创建新线程（直到达到 corePoolSize）
2. **队列其次**：核心线程满后，任务进队列
3. **非核心线程兜底**：队列满后，创建非核心线程（直到 maximumPoolSize）
4. **拒绝策略最后**：所有资源耗尽，执行拒绝策略

**示例演示：**

```java
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    2,    // corePoolSize
    5,    // maximumPoolSize
    60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(3),  // 队列容量 3
    new ThreadPoolExecutor.AbortPolicy()
);

// 提交 10 个任务，每个任务执行 10 秒
for (int i = 1; i <= 10; i++) {
    try {
        int taskId = i;
        executor.execute(() -> {
            System.out.println("Task " + taskId + " running on " + 
                             Thread.currentThread().getName());
            sleep(10000);
        });
        System.out.println("Task " + i + " submitted");
    } catch (RejectedExecutionException e) {
        System.out.println("Task " + i + " rejected!");
    }
}
```

**执行过程分析：**

```
Task 1: 创建核心线程 1 执行 ✓          [核心线程: 1/2, 队列: 0/3, 总线程: 1/5]
Task 2: 创建核心线程 2 执行 ✓          [核心线程: 2/2, 队列: 0/3, 总线程: 2/5]
Task 3: 核心线程满，任务入队 ✓         [核心线程: 2/2, 队列: 1/3, 总线程: 2/5]
Task 4: 任务入队 ✓                    [核心线程: 2/2, 队列: 2/3, 总线程: 2/5]
Task 5: 任务入队 ✓                    [核心线程: 2/2, 队列: 3/3, 总线程: 2/5]
Task 6: 队列满，创建非核心线程 3 执行 ✓ [核心线程: 2/2, 队列: 3/3, 总线程: 3/5]
Task 7: 创建非核心线程 4 执行 ✓        [核心线程: 2/2, 队列: 3/3, 总线程: 4/5]
Task 8: 创建非核心线程 5 执行 ✓        [核心线程: 2/2, 队列: 3/3, 总线程: 5/5]
Task 9: 所有资源耗尽，拒绝 ⚠️          [核心线程: 2/2, 队列: 3/3, 总线程: 5/5]
Task 10: 拒绝 ⚠️                      [核心线程: 2/2, 队列: 3/3, 总线程: 5/5]
```

**常见误区：**

```java
// ❌ 误区 1：以为会先创建到 maximumPoolSize
// 实际：先填满队列，再创建非核心线程

// ❌ 误区 2：以为队列无界就不会拒绝
ThreadPoolExecutor bad = new ThreadPoolExecutor(
    2, 5, 60, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>()  // 无界队列
);
// 问题：maximumPoolSize 永远用不上！任务会一直入队，可能 OOM

// ✅ 正确：有界队列

    2, 5, 60, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(100)  // 有界队列
);
```

#### 3.3.4 四种拒绝策略详解

**1. AbortPolicy（默认）：抛异常**

```java
public static class AbortPolicy implements RejectedExecutionHandler {
    public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
        throw new RejectedExecutionException("Task " + r.toString() +
                                             " rejected from " + e.toString());
    }
}
```

**特点：**
- 抛出 `RejectedExecutionException`
- 调用者可以捕获异常并处理

**适用场景：**
- 任务不能丢失，必须感知拒绝
- 需要记录日志或告警
- 可以重试或降级

**实战示例：**
```java
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    2, 5, 60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(10),
    new ThreadPoolExecutor.AbortPolicy()
);

try {
    executor.execute(task);
} catch (RejectedExecutionException e) {
    log.error("任务被拒绝，尝试降级处理", e);
    fallbackHandler.handle(task);  // 降级处理
}
```

---

**2. CallerRunsPolicy：调用者执行**

```java
public static class CallerRunsPolicy implements RejectedExecutionHandler {
    public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
        if (!e.isShutdown()) {
            r.run();  // 在调用线程中执行
        }
    }
}
```

**特点：**
- 任务在调用线程（通常是主线程或 Web 请求线程）中执行
- 不会丢失任务
- 会阻塞调用线程

**适用场景：**
- 任务不能丢失
- 可以接受调用线程被阻塞
- 天然的负反馈机制（调用线程被占用，提交速度自然降低）

**实战示例：**
```java
// Web 应用中的异步任务处理
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    10, 20, 60, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(100),
    new ThreadPoolExecutor.CallerRunsPolicy()  // 请求线程自己执行
);

@GetMapping("/process")
public String process() {
    executor.execute(() -> {
        // 异步处理
    });
    // 如果线程池满，任务会在 Tomcat 线程中执行
    // 虽然慢，但不会丢失任务
    return "submitted";
}
```

**优缺点：**
- ✅ 优点：不丢任务，天然限流
- ❌ 缺点：阻塞调用线程，可能影响吞吐量

---

**3. DiscardPolicy：静默丢弃**

```java
public static class DiscardPolicy implements RejectedExecutionHandler {
    public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
        // 什么都不做，静默丢弃
    }
}
```

**特点：**
- 直接丢弃任务
- 不抛异常，不通知
- 调用者无感知

**适用场景：**
- 任务可以丢失（如日志、监控埋点）
- 允许部分数据丢失
- 对实时性要求不高

**实战示例：**
```java
// 监控指标上报（丢失部分数据可接受）
ThreadPoolExecutor metricsExecutor = new ThreadPoolExecutor(
    2, 4, 60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(1000),
    new ThreadPoolExecutor.DiscardPolicy()  // 丢弃超出的指标
);

public void reportMetric(Metric metric) {
    metricsExecutor.execute(() -> {
        httpClient.post("/metrics", metric);
    });
    // 如果线程池满，指标会被丢弃，但不影响主流程
}
```

**⚠️ 危险：**
- 任务丢失无感知，可能导致数据不一致
- 建议配合监控：记录拒绝次数

---

**4. DiscardOldestPolicy：丢弃最老任务**

```java
public static class DiscardOldestPolicy implements RejectedExecutionHandler {
    public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
        if (!e.isShutdown()) {
            e.getQueue().poll();  // 丢弃队列头部（最老）任务
            e.execute(r);         // 重新提交当前任务
        }
    }
}
```

**特点：**
- 丢弃队列中最老的任务
- 为新任务腾出空间
- 优先保证新任务

**适用场景：**
- 新任务优先级更高（如实时数据处理）
- 老任务可以丢弃（如过期的缓存刷新）

**实战示例：**
```java
// 实时数据处理（老数据可以丢弃）
ThreadPoolExecutor realtimeExecutor = new ThreadPoolExecutor(
    5, 10, 60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(50),
    new ThreadPoolExecutor.DiscardOldestPolicy()
);

public void processRealtimeData(Data data) {
    realtimeExecutor.execute(() -> {
        // 处理实时数据
        // 如果队列满，丢弃最老的数据，处理最新的
    });
}
```

**⚠️ 注意：**
- 可能导致任务饥饿（老任务永远得不到执行）
- 不适合所有任务优先级相同的场景

---

**5. 自定义拒绝策略**

```java
// 记录日志 + 降级处理
public class LogAndFallbackPolicy implements RejectedExecutionHandler {
    
    private final FallbackHandler fallbackHandler;
    
    @Override
    public void rejectedExecution(Runnable r, ThreadPoolExecutor executor) {
        // 1. 记录日志
        log.error("任务被拒绝: {}, 线程池状态: poolSize={}, queueSize={}, activeCount={}",
                 r, executor.getPoolSize(), executor.getQueue().size(), 
                 executor.getActiveCount());
        
        // 2. 监控告警
        metrics.increment("threadpool.rejected");
        
        // 3. 降级处理
        try {
            fallbackHandler.handle(r);
        } catch (Exception e) {
            log.error("降级处理失败", e);
        }
    }
}

// 使用
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    10, 20, 60, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(100),
    new LogAndFallbackPolicy(fallbackHandler)
);
```

---

**拒绝策略对比表：**

| 策略 | 任务丢失 | 异常抛出 | 阻塞调用线程 | 适用场景 |
|------|---------|---------|------------|---------|
| **AbortPolicy** | ❌ 否 | ✅ 是 | ❌ 否 | 任务不能丢失，需要感知拒绝 |
| **CallerRunsPolicy** | ❌ 否 | ❌ 否 | ✅ 是 | 任务不能丢失，可接受调用线程阻塞 |
| **DiscardPolicy** | ✅ 是 | ❌ 否 | ❌ 否 | 任务可丢失（日志、监控） |
| **DiscardOldestPolicy** | ✅ 是（老任务） | ❌ 否 | ❌ 否 | 新任务优先级更高 |
| **自定义** | 自定义 | 自定义 | 自定义 | 复杂业务逻辑 |

## 6. CAS 与原子类

### 6.1 基本概念
- Compare-And-Swap：比较期望值与内存中当前值相等，则写入新值；否则重试。
- 依赖 CPU 指令，保证单个变量更新的原子性。

### 6.2 优缺点
- **优点**：无锁、性能好、避免阻塞。
- **缺点**：ABA 问题、自旋开销、一次只能更新一个变量。

### 6.3 示例
```java
public class CasCounter {
	private final AtomicInteger counter = new AtomicInteger();
	public void inc() {
		int expect, update;
		do {
			expect = counter.get();
			update = expect + 1;
		} while (!counter.compareAndSet(expect, update));
	}
}
```

## 7. ABA 问题与解法

### 7.1 问题描述
- 线程读取值 A，准备写入 B；期间其他线程把值改成 C 再改回 A，CAS 仍然成功，但数据已变化。

**ABA 问题示例：**
```java
// ABA 问题示例
AtomicReference<Node> head = new AtomicReference<>(nodeA);

// 线程 1：准备 CAS
Node oldHead = head.get();  // 读到 A
// ... 准备把 A 改成 B

// 线程 2：快速执行
head.compareAndSet(nodeA, nodeC);  // A -> C
head.compareAndSet(nodeC, nodeA);  // C -> A（又变回 A）

// 线程 1：继续 CAS
head.compareAndSet(oldHead, nodeB);  // 成功！但 A 已经不是原来的 A
```

**问题本质：** CAS 只比较引用相等，不知道中间发生了什么。

### 7.2 方案
1. **AtomicStampedReference / AtomicMarkableReference**：引入版本号或标记。

```java
AtomicStampedReference<String> ref = new AtomicStampedReference<>("A", 0);
int stamp = ref.getStamp();
boolean ok = ref.compareAndSet("A", "B", stamp, stamp + 1);
```

2. **LongAdder / LongAccumulator**：分段累加，避免单点 CAS 热点，适合计数场景。
3. **锁（ReentrantLock / synchronized）**：在逻辑复杂或需要批量更新数据时，使用显式锁串行化。

### 7.3 什么情况下使用原子类

#### 1. 高并发计数/累加场景

```java
// ✅ 需要原子类：多线程共享的计数器
public class RequestCounter {
    private AtomicLong requestCount = new AtomicLong(0);
    
    public void recordRequest() {
        requestCount.incrementAndGet();  // 线程安全
    }
    
    public long getCount() {
        return requestCount.get();
    }
}

// ❌ 错误：普通变量
public class BadCounter {
    private long count = 0;  // 多线程下会丢失更新
    
    public void increment() {
        count++;  // 非原子操作：读-改-写
    }
}
```

**典型场景：**
- QPS 统计、请求计数
- 限流器的计数
- 监控指标埋点
- 分布式 ID 生成（本地部分）

#### 2. 无锁状态机/标志位

```java
// ✅ 需要原子类：状态切换
public class OrderService {
    private AtomicReference<OrderStatus> status = 
        new AtomicReference<>(OrderStatus.CREATED);
    
    public boolean tryPay() {
        // CAS：只有 CREATED 状态才能支付
        return status.compareAndSet(OrderStatus.CREATED, OrderStatus.PAYING);
    }
    
    public boolean tryComplete() {
        return status.compareAndSet(OrderStatus.PAYING, OrderStatus.COMPLETED);
    }
}

// ✅ 需要原子类：开关标志
public class ServiceSwitch {
    private AtomicBoolean enabled = new AtomicBoolean(true);
    
    public void disable() {
        enabled.set(false);
    }
    
    public boolean isEnabled() {
        return enabled.get();
    }
}
```

**典型场景：**
- 服务开关/熔断器
- 任务状态流转
- 单次初始化标志（`AtomicBoolean initialized`）
- 优雅停机标志

#### 3. 无锁数据结构/算法

```java
// ✅ 需要原子类：无锁栈
public class LockFreeStack<T> {
    private AtomicReference<Node<T>> top = new AtomicReference<>();
    
    public void push(T value) {
        Node<T> newNode = new Node<>(value);
        Node<T> oldTop;
        do {
            oldTop = top.get();
            newNode.next = oldTop;
        } while (!top.compareAndSet(oldTop, newNode));  // CAS 重试
    }
    
    public T pop() {
        Node<T> oldTop, newTop;
        do {
            oldTop = top.get();
            if (oldTop == null) return null;
            newTop = oldTop.next;
        } while (!top.compareAndSet(oldTop, newTop));
        return oldTop.value;
    }
}
```

**典型场景：**
- 无锁队列/栈
- 无锁链表
- 对象池的引用管理

#### 4. 替代简单的 synchronized

```java
// ✅ 原子类：简单场景更高效
public class IdGenerator {
    private AtomicLong id = new AtomicLong(0);
    
    public long nextId() {
        return id.incrementAndGet();
    }
}

// ❌ 过度设计：简单计数用锁太重
public class HeavyIdGenerator {
    private long id = 0;
    private final Object lock = new Object();
    
    public long nextId() {
        synchronized (lock) {
            return ++id;
        }
    }
}
```

**何时用原子类代替锁：**
- 单个变量的简单操作（读、写、CAS）
- 无需保护多个变量的一致性
- 追求更高性能（无锁）

### 7.4 什么情况下需要考虑 ABA 问题

#### 1. 需要考虑 ABA 的场景

**场景 1：链表/栈的节点复用**

```java
// ⚠️ 有 ABA 风险：节点可能被回收后重新分配到同一地址
public class LockFreeStack<T> {
    private AtomicReference<Node<T>> top = new AtomicReference<>();
    
    public T pop() {
        Node<T> oldTop, newTop;
        do {
            oldTop = top.get();  // 读到节点 A
            if (oldTop == null) return null;
            newTop = oldTop.next;
            
            // 问题：如果 oldTop 被其他线程 pop 后又 push 回来
            // 地址相同但 next 可能已经变了
        } while (!top.compareAndSet(oldTop, newTop));
        return oldTop.value;
    }
}

// ✅ 解决：使用 AtomicStampedReference
public class SafeLockFreeStack<T> {
    private AtomicStampedReference<Node<T>> top = 
        new AtomicStampedReference<>(null, 0);
    
    public T pop() {
        Node<T> oldTop, newTop;
        int[] stampHolder = new int[1];
        do {
            oldTop = top.get(stampHolder);
            int oldStamp = stampHolder[0];
            if (oldTop == null) return null;
            newTop = oldTop.next;
        } while (!top.compareAndSet(oldTop, newTop, oldStamp, oldStamp + 1));
        return oldTop.value;
    }
}
```

**场景 2：内存回收/对象池**

```java
// ⚠️ 有 ABA 风险：对象被回收后重新分配
public class ObjectPool<T> {
    private AtomicReference<T> available = new AtomicReference<>();
    
    public T acquire() {
        T obj;
        do {
            obj = available.get();
            if (obj == null) return createNew();
        } while (!available.compareAndSet(obj, null));
        return obj;
    }
    
    public void release(T obj) {
        T old;
        do {
            old = available.get();
        } while (!available.compareAndSet(old, obj));
        // 问题：obj 可能是之前被回收的对象，地址复用
    }
}
```

**场景 3：账户余额/库存扣减（业务逻辑依赖历史）**

```java
// ⚠️ 有 ABA 风险：余额从 100 -> 50 -> 100，但中间发生了交易
public class Account {
    private AtomicInteger balance = new AtomicInteger(100);
    
    public boolean withdraw(int amount) {
        int oldBalance, newBalance;
        do {
            oldBalance = balance.get();  // 读到 100
            if (oldBalance < amount) return false;
            newBalance = oldBalance - amount;
            
            // 问题：如果余额从 100 -> 50（消费）-> 100（充值）
            // CAS 会成功，但业务上可能需要知道中间发生了变化
        } while (!balance.compareAndSet(oldBalance, newBalance));
        return true;
    }
}

// ✅ 解决：使用版本号
public class SafeAccount {
    private AtomicStampedReference<Integer> balance = 
        new AtomicStampedReference<>(100, 0);
    
    public boolean withdraw(int amount) {
        int[] stampHolder = new int[1];
        Integer oldBalance, newBalance;
        do {
            oldBalance = balance.get(stampHolder);
            int oldStamp = stampHolder[0];
            if (oldBalance < amount) return false;
            newBalance = oldBalance - amount;
        } while (!balance.compareAndSet(oldBalance, newBalance, 
                                        oldStamp, oldStamp + 1));
        return true;
    }
}
```

**场景 1：简单计数/累加**


**场景 2：状态标志（只关心当前状态）**

### 7.5 决策树

```
是否需要多线程共享变量？
├─ 否 → 用普通变量
└─ 是 → 继续

是否只是简单的读/写/计数？
├─ 是 → 用 AtomicXxx（不用担心 ABA）
└─ 否 → 继续

是否涉及链表/栈/队列的节点操作？
├─ 是 → 考虑 ABA，用 AtomicStampedReference
└─ 否 → 继续

业务逻辑是否依赖"中间状态"或"变化历史"？
├─ 是 → 考虑 ABA，用 AtomicStampedReference
└─ 否 → 用普通 AtomicReference

是否需要保护多个变量的一致性？
├─ 是 → 用锁（synchronized/ReentrantLock）
└─ 否 → 用原子类
```

### 7.7 总结对比表

| 场景 | 是否用原子类 | 是否考虑 ABA |
|------|------------|------------|
| 计数/累加 | ✅ AtomicLong | ❌ 不需要 |
| 状态标志 | ✅ AtomicBoolean | ❌ 不需要 |
| 配置引用 | ✅ AtomicReference | ❌ 不需要（不可变对象） |
| 无锁栈/队列 | ✅ AtomicReference | ⚠️ **需要**（用 Stamped） |
| 对象池 | ✅ AtomicReference | ⚠️ **需要**（用 Stamped） |
| 账户余额（需追踪历史） | ✅ AtomicStampedReference | ⚠️ **需要** |
| 多变量一致性 | ❌ 用锁 | - |
| 复杂业务逻辑 | ❌ 用锁 | - |

**核心原则：**
- 简单的单变量操作 → 用原子类，不用担心 ABA
- 涉及节点复用/对象池/需要追踪变化历史 → 考虑 ABA，用 `AtomicStampedReference`
- 多变量或复杂逻辑 → 用锁

## 8. AQS 工作原理
- `AbstractQueuedSynchronizer` 是多数同步器（`ReentrantLock`、`Semaphore`、`CountDownLatch` 等）的基础。

### 8.1 组成
- `state`：整型共享状态。
- FIFO 双向链表队列：保存等待线程（Node）。
- 模式：独占 (`EXCLUSIVE`) 与共享 (`SHARED`)。

### 8.2 核心模板方法
- `tryAcquire/tryRelease`
- `tryAcquireShared/tryReleaseShared`
- `isHeldExclusively`

### 8.3 获取/释放流程
1. 调用 `acquire(arg)`：若 `tryAcquire` 成功则返回，否则将线程封装为 Node 入队并挂起（`park`）。
2. 释放时调用 `release(arg)`：更新 `state`，唤醒队列下一个节点。
3. 共享模式下可同时唤醒多个节点。

### 8.4 自定义独占锁示例
```java
class MyLock {
	private static class Sync extends AbstractQueuedSynchronizer {
		protected boolean tryAcquire(int acquires) {
			if (compareAndSetState(0, 1)) {
				setExclusiveOwnerThread(Thread.currentThread());
				return true;
			}
			return false;
		}
		protected boolean tryRelease(int releases) {
			if (getState() == 0) throw new IllegalMonitorStateException();
			setExclusiveOwnerThread(null);
			setState(0);
			return true;
		}
		protected boolean isHeldExclusively() {
			return getState() == 1;
		}
	}
	private final Sync sync = new Sync();
	public void lock() { sync.acquire(1); }
	public void unlock() { sync.release(1); }
}
```

### 8.5 自定义公平锁示例
```java
import java.util.concurrent.locks.AbstractQueuedSynchronizer;

class MyLock {
    private abstract static class Sync extends AbstractQueuedSynchronizer {
        abstract boolean fair();

        @Override
        protected final boolean tryAcquire(int acquires) {
            final Thread current = Thread.currentThread();

            // 公平锁：队列前面有人 -> 不能插队
            if (fair() && hasQueuedPredecessors()) {
                return false;
            }

            if (compareAndSetState(0, 1)) {
                setExclusiveOwnerThread(current);
                return true;
            }
            return false;
        }

        @Override
        protected final boolean tryRelease(int releases) {
            if (getState() == 0 || getExclusiveOwnerThread() != Thread.currentThread()) {
                throw new IllegalMonitorStateException();
            }
            setExclusiveOwnerThread(null);
            setState(0);
            return true;
        }

        @Override
        protected final boolean isHeldExclusively() {
            return getState() == 1 && getExclusiveOwnerThread() == Thread.currentThread();
        }
    }

    private static final class FairSync extends Sync {
        @Override boolean fair() { return true; }
    }
    private static final class NonFairSync extends Sync {
        @Override boolean fair() { return false; }
    }

    private final Sync sync;

    public MyLock() { this(false); } // 默认非公平
    public MyLock(boolean fair) { this.sync = fair ? new FairSync() : new NonFairSync(); }

    public void lock() { sync.acquire(1); }
    public void unlock() { sync.release(1); }
}
```

### 8.6 源码展示

1. AQS 里最关键的字段（就是这几个在撑全场）名字和语义和源码一致）
    - volatile int state：同步状态（锁/许可/门闩计数都塞这里）
    - volatile Node head, tail：同步队列的头尾指针（CLH 变体，有一个 dummy head）
    - CAS 方法族：compareAndSetState、compareAndSetHead、compareAndSetTail（底层 VarHandle/Unsafe）

2. Node 结构你要认识（源码里就是一个内部静态类）
    - volatile int waitStatus
        - 状态：CANCELLED、SIGNAL、CONDITION、PROPAGATE
    - volatile Node prev, next
    - volatile Thread thread
    - Node nextWaiter：给共享模式/Condition 用的

3. 队列是啥：CLH 变体 + dummy head（面试官爱你画）
    - head 是一个 dummy 节点（不代表线程）
    - 真实等待线程从 head.next 开始
    - 只有 head 的直接后继有资格去 tryAcquire（减少“惊群”）

4. 独占 acquire 的源码味流程（ReentrantLock 就走这条）
    1. 入口：acquire(arg)逻辑是（语义级伪码，和源码结构一致）：
        ```java
        public final void acquire(int arg) {
            if (!tryAcquire(arg) &&
                acquireQueued(addWaiter(Node.EXCLUSIVE), arg)) {
                selfInterrupt();
            }
        }
        ```
    2. 关键点：先走 快路径：tryAcquire失败才入队：addWaiter入队后在队列里“正确地等待并重试”：acquireQueued

    3. addWaiter(mode)：先试快速入队，失败再 enq
        ```java
        private Node addWaiter(Node mode) {
            Node node = new Node(Thread.currentThread(), mode);
            Node pred = tail;
            if (pred != null) {
                node.prev = pred;
                if (compareAndSetTail(pred, node)) {
                    pred.next = node;
                    return node;
                }
            }
            enq(node);
            return node;
        }
        ```
    4. acquireQueued(node, arg)：核心循环（队头资格 + park）
        ```java
        final boolean acquireQueued(final Node node, int arg) {
            boolean failed = true;
            try {
                boolean interrupted = false;
                for (;;) {
                    final Node p = node.predecessor();
                    if (p == head && tryAcquire(arg)) {
                        setHead(node);
                        p.next = null; // help GC
                        return interrupted;
                    }
                    if (shouldParkAfterFailedAcquire(p, node) &&
                        parkAndCheckInterrupt()) {
                        interrupted = true;
                    }
                }
            } finally {
                if (failed) {
                    cancelAcquire(node);
                }
            }
        }
        ```
    5. shouldParkAfterFailedAcquire(p, node)：SIGNAL 协议（精髓）
        ```java
        private static boolean shouldParkAfterFailedAcquire(Node pred, Node node) {
            int ws = pred.waitStatus;
            if (ws == Node.SIGNAL) {
                return true;
            }
            if (ws > 0) {
                do {
                    node.prev = pred = pred.prev;
                } while (pred.waitStatus > 0);
                pred.next = node;
            } else {
                compareAndSetWaitStatus(pred, ws, Node.SIGNAL);
            }
            return false;
        }
        ```
    6. parkAndCheckInterrupt()：真正阻塞点
        ```java
        private final boolean parkAndCheckInterrupt() {
            LockSupport.park(this);
            return Thread.interrupted();
        }
        ```
    7. unparkSuccessor(node)：唤醒后继
        ```java
        private final void unparkSuccessor(Node node) {
            int ws = node.waitStatus;
            if (ws < 0) {
                compareAndSetWaitStatus(node, ws, 0);
            }
            Node s = node.next;
            if (s == null || s.waitStatus > 0) {
                s = null;
                for (Node p = tail; p != null && p != node; p = p.prev) {
                    if (p.waitStatus <= 0) {
                        s = p;
                        break;
                    }
                }
            }
            if (s != null)
                LockSupport.unpark(s.thread);
        }
        ```
    8. release(arg)：谁来唤醒谁？（unparkSuccessor）
        ```java
        public final boolean release(int arg) {
            if (tryRelease(arg)) {
                Node h = head;
                if (h != null && h.waitStatus != 0)
                    unparkSuccessor(h);
                return true;
            }
            return false;
        }
        ```
    9. unparkSuccessor(head)
        ```java
        private final void unparkSuccessor(Node node) {
            int ws = node.waitStatus;
            if (ws < 0) {
                compareAndSetWaitStatus(node, ws, 0);
            }
            Node s = node.next;
            if (s == null || s.waitStatus > 0) {
                s = null;
                for (Node p = tail; p != null && p != node; p = p.prev) {
                    if (p.waitStatus <= 0) {
                        s = p;
                        break;
                    }
                }
            }
            if (s != null)
                LockSupport.unpark(s.thread);
        }
        ```
    10. 共享模式：Semaphore / CountDownLatch 的“传播唤醒”长啥样
        ```java
        public final void acquireShared(int arg) {
            if (tryAcquireShared(arg) < 0)
                doAcquireShared(arg);
        }
        ```
    11. doAcquireShared(arg)：共享模式下不是“只唤醒一个”，而是可能连续唤醒，让一串共享获取者通过（比如 latch 归零后大家都能过）。
        ```java
        private void doAcquireShared(int arg) {
            final Node node = addWaiter(Node.SHARED);
            boolean failed = true;
            try {
                boolean interrupted = false;
                for (;;) {
                    final Node p = node.predecessor();
                    if (p == head && tryAcquireShared(arg) >= 0) {
                        setHeadAndPropagate(node, arg);
                        p.next = null; // help GC
                        return interrupted;
                    }
                    if (shouldParkAfterFailedAcquire(p, node) &&
                        parkAndCheckInterrupt()) {
                        interrupted = true;
                    }
                }
            } finally {
                if (failed) {
                    cancelAcquire(node);
                }
            }
        }
        ```
    12. setHeadAndPropagate(node, arg)：传播唤醒
        ```java
        private void setHeadAndPropagate(Node node, int propagate) {
            Node h = head;
            setHead(node);
            if (propagate > 0 || h == null || h.waitStatus < 0) {
                Node s = node.next;
                if (s == null || s.isShared())
                    doReleaseShared();
            }
        }
        ```
    13. doReleaseShared()：传播唤醒
        ```java
        private void doReleaseShared() {
            if (head != null) {
                Node h = head;
                if (h.waitStatus != 0) {
                    unparkSuccessor(h);
                }
            }
        }
        ```
    14. doAcquireShared(arg)：共享模式下不是“只唤醒一个”，而是可能连续唤醒，让一串共享获取者通过（比如 latch 归零后大家都能过）。

### 8.7 示例解释
1. T0：初始状态
	•	state = 0（锁空闲）
	•	队列未初始化：head = null, tail = null

2. T1：线程 A 调用 lock()，直接拿到锁（快路径）
    - `A` 执行 `acquire(1)`：
        - `tryAcquire(1)`：CAS `state: 0 -> 1` 成功
        - `A` 成为 `owner`，返回
    此时：
        - `state=1`，`owner=A`
        - 队列仍然不存在（`head/tail` 还是 `null`）

3. T2：线程 B 调用 lock()，tryAcquire 失败 → 入队
    - `B` 执行 `acquire(1)`：
        - `tryAcquire(1)` 失败（`state=1`）
        - `addWaiter(EXCLUSIVE)` 发现 `tail==null`，走 `enq()` 初始化队列：
            - 创建 `H(dummy)`，令 `head=tail=H`
            - 把 `N(B)` 挂到 `tail` 后面：`H <-> N(B)`，更新 `tail=N(B)`
            - 进入 `acquireQueued(N(B),1)` 自旋
    - 此时队列大概长这样：
        - `H(ws=0) <-> N(B, ws=0)`
4. T3：B 在 acquireQueued 里准备 park：把前驱 head 标成 SIGNAL
    - `B` 在 `acquireQueued` 里循环：
        - 发现 `p = N(B).prev == head(H)`，说明“我排在队头后继”，有资格去 `tryAcquire`
        - 但 `tryAcquire` 仍失败（A 还持锁）
        - 接着会调用 `shouldParkAfterFailedAcquire(p, node)`：
            - **如果 `p.waitStatus != SIGNAL`，就 CAS 把 前驱 `p.waitStatus` 设为 `SIGNAL`**
            - 也就是把 `H.waitStatus` 从 0 改成 `SIGNAL`：
                - “head 释放锁时，记得叫醒你的后继（B）”

    - 此刻队列：
        - `H(ws=SIGNAL) <-> N(B, ws=0)`
    - `B`：park() 阻塞（LockSupport.park）

5. T4：线程 C 调用 lock()，tryAcquire 失败 → 入队到 B 后面
    - `C` 重复类似流程：
        - `tryAcquire` 失败
        - `addWaiter` 直接快入队：挂到 `tail` 后面
    - 队列变成：
        - `H(ws=SIGNAL) <-> N(B, ws=0) <-> N(C, ws=0)`

6. T5：C 在 acquireQueued 里也准备 park：把前驱 N(B) 标成 SIGNAL
    - `C` 在 `acquireQueued` 循环中：
        - `p = N(C).prev == N(B)`，不是 `head`，所以它没资格 `tryAcquire`（AQS 的规则：只有 `head` 的直接后继才有资格抢锁）
        - 于是进入 `shouldParkAfterFailedAcquire(p,node)`
        - 把 `N(B).waitStatus` CAS 成 `SIGNAL`
    - 队列现在：
        - `H(ws=SIGNAL) <-> N(B, ws=SIGNAL) <-> N(C, ws=0)`
    - `C`：park() 阻塞（LockSupport.park）

7. T6：线程 A unlock()：release 成功 → unparkSuccessor(head) 唤醒 B
    - `A` 执行 `release(1)`：
        - `tryRelease`：`state: 1 -> 0`，`owner=null`
        - 看到 `head!=null && head.waitStatus!=0`（此时 `head` 的 `ws=SIGNAL`）
        - 调 `unparkSuccessor(head)`：
            - 通常会先把 `head.waitStatus` 置回 0（清理 SIGNAL）
            - 找到 `head` 的后继（`head.next`，也就是 `N(B)`）
            - `LockSupport.unpark(B.thread)` → 唤醒 B
    - 队列此刻一般变成：
        - `H(ws=0) <-> N(B, ws=SIGNAL) <-> N(C, ws=0)`

8. T7：B 被唤醒，成为“队头后继”→ tryAcquire 成功 → setHead(B)
    - `B` 从 park 返回，继续 acquireQueued 循环：
        - 现在 `p = N(B).prev == head(H)`，且锁空闲 `state=0`
        - `B tryAcquire CAS 成功：state 0->1，owner=B`
        - `setHead(N(B))：B 节点变成新的 head（并清掉 thread 引用帮助 GC）`
        - 原 head(H) 会被断开（oldHead.next=null）帮助回收
    - 队列形态（逻辑上）变为：
        - `H(=原 N(B), ws=0) <-> N(C, ws=0)`
    - 注意：此时 新 head 是 B 的节点；你之前看到的 dummy head 已经被踢出队列（变成游离节点）。

9. T8：B unlock()：唤醒 C；C 重复同样流程
    - `B` 执行 `unlock()`：
        - `release`：`state: 0 -> 1`，`owner=B`
        - `unparkSuccessor(head)`：唤醒 `head` 的后继（`N(C)`）
    - `C` 被唤醒后：
        - 发现自己是 `head` 的直接后继
        - `tryAcquire` 成功
        - `setHead(N(C))`
        - 队列最终只剩一个 head（没有等待者）
10. 一句话把“SIGNAL 协议”讲明白
    - 谁负责唤醒我？ —— 我的前驱节点负责。
    - 所以我在 park 前，会先把 前驱的 waitStatus 改成 SIGNAL。
    - 释放锁的人只需要 `unparkSuccessor(head)`：唤醒 `head` 的后继即可。

11. 总结
    - AQS 是 CLH 变体 FIFO 队列。
    - B/C 抢不到锁会入队。
    - 每个等待者在 park 前会把前驱的 waitStatus 设为 SIGNAL，表示”前驱释放时要唤醒我”。
    - unlock 时 release 会调用 `unparkSuccessor(head)`，唤醒 `head.next`。
    - 被唤醒的线程只有在自己是 `head` 的直接后继时才会 `tryAcquire`，成功后 `setHead`，把自己变成新 head，队列向前推进。

### 8.8 AQS 经典时序图

**关键时刻说明：**

**T0-T1：线程 A 快速获取锁**
- A 直接 CAS `state: 0→1` 成功，无需入队

**T1-T2：线程 B 入队并初始化队列**
- B 的 `tryAcquire` 失败（A 持锁）
- 创建 dummy head + N(B) 节点
- B 发现自己是 head 的直接后继，有资格 `tryAcquire`，但失败（A 还持锁）

**T2-T3：线程 C 入队**
- C 也失败，入队到 B 后面
- C 发现前驱不是 head，无资格 `tryAcquire`

**T3-T4：B 和 C 都 park**
- B 把 head 的 `waitStatus` 设为 `SIGNAL`（”释放时叫醒我”）
- C 把 N(B) 的 `waitStatus` 设为 `SIGNAL`
- 两者都调用 `LockSupport.park()` 阻塞

**T5-T6：A 释放锁，唤醒 B**
- A 调用 `unparkSuccessor(head)`，找到 `head.next = N(B)`
- 唤醒 B
- B 被唤醒后，发现自己是 head 的直接后继，`tryAcquire` 成功
- B 调用 `setHead(N(B))`，把自己变成新 head

**T8-T9：B 释放锁，唤醒 C**
- 重复上述流程
- C 成为新 head，队列最终只剩一个 dummy head

**核心机制总结：**

1. **SIGNAL 协议**：每个节点 park 前，把前驱的 `waitStatus` 设为 `SIGNAL`
2. **队头资格**：只有 head 的直接后继才有资格 `tryAcquire`
3. **setHead 推进**：获取锁成功后，把自己变成新 head，队列向前推进
4. **公平性**：严格按入队顺序唤醒（FIFO）

**图例说明：**
- `H`：head（dummy 节点）
- `N(X)`：线程 X 的节点
- `ws`：waitStatus
- `⇄`：双向链表
- `✓`：成功
- `✗`：失败
- `💤`：阻塞
- `⏰`：被唤醒
- `🔔`：唤醒操作

## 9. synchronized 深入理解

### 9.1 字节码指令
- `monitorenter` / `monitorexit` 包裹临界区。

### 9.2 对象头 & Mark Word
- 包含锁标志位、是否偏向、线程 ID、GC 信息。
- 锁状态：无锁 → 偏向锁 → 轻量级锁 → 重量级锁，根据竞争程度逐级升级。

### 9.3 JVM 锁优化
- **偏向锁**：单线程重复进入时直接绑定线程，避免 CAS。
- **轻量级锁**：自旋 + CAS，适合短时间锁竞争。
- **自旋锁与自适应自旋**：在释放预计很快的情况下自旋等待。
- **锁消除**：逃逸分析发现对象未逃逸线程，则消除锁。

### 9.4 与 ReentrantLock 对比

| 特性      | synchronized  | ReentrantLock                |
| --------- | ------------- | ---------------------------- |
| 加锁/释放 | 自动          | 手动                         |
| 公平性    | 不支持        | 支持公平/非公平              |
| 可中断    | 不可中断      | `lockInterruptibly`          |
| 条件队列  | `wait/notify` | 多个 `Condition`             |
| 监控指标  | 无直接 API    | `isLocked`、`getQueueLength` |

**结论**：简单场景首选 `synchronized`；需要灵活性或监控时使用 `ReentrantLock`。

## 10. 内存模型、指令重排与 volatile

### 10.1 指令重排类型
- 编译器优化、CPU 流水线、JIT 优化。
- 在单线程下等价，在多线程下可能破坏先后顺序。

### 10.2 Java 内存模型 (JMM)
- 线程之间通过主内存共享数据；每个线程有工作内存副本。
- `happens-before` 规则确保可见性与有序性。

#### 10.2.1 happens-before 八大规则详解

**happens-before 的含义：**
- 如果操作 A happens-before 操作 B，那么 A 的结果对 B 可见
- 不是指时间上的先后，而是**可见性保证**

---

**规则 1：程序顺序规则（Program Order Rule）**

```java
int a = 1;      // 操作 1
int b = 2;      // 操作 2
int c = a + b;  // 操作 3
```

**规则：** 在单个线程中，按照代码顺序，前面的操作 happens-before 后面的操作。

**说明：**
- 操作 1 happens-before 操作 2
- 操作 2 happens-before 操作 3
- 但实际执行时，CPU 可能重排序（只要不影响单线程结果）

---

**规则 2：volatile 变量规则（Volatile Variable Rule）**

```java
class VolatileExample {
    private volatile boolean flag = false;
    private int data = 0;
    
    // 线程 A
    public void writer() {
        data = 42;          // 操作 1
        flag = true;        // 操作 2（volatile 写）
    }
    
    // 线程 B
    public void reader() {
        if (flag) {         // 操作 3（volatile 读）
            int x = data;   // 操作 4，一定能看到 data=42
        }
    }
}
```

**规则：** 对 volatile 变量的写操作 happens-before 后续对该变量的读操作。

**说明：**
- 操作 2（volatile 写）happens-before 操作 3（volatile 读）
- 根据程序顺序规则：操作 1 happens-before 操作 2
- 根据传递性：操作 1 happens-before 操作 4
- **结论：** 线程 B 读到 `flag=true` 时，一定能看到 `data=42`

---

**规则 3：锁规则（Monitor Lock Rule）**

```java
class LockExample {
    private int data = 0;
    private final Object lock = new Object();
    
    // 线程 A
    public void writer() {
        synchronized (lock) {
            data = 42;      // 操作 1
        }                   // 操作 2（unlock）
    }
    
    // 线程 B
    public void reader() {
        synchronized (lock) {  // 操作 3（lock）
            int x = data;      // 操作 4，一定能看到 data=42
        }
    }
}
```

**规则：** 对锁的解锁操作 happens-before 后续对同一把锁的加锁操作。

**说明：**
- 操作 2（unlock）happens-before 操作 3（lock）
- 操作 1 happens-before 操作 2（程序顺序）
- 操作 3 happens-before 操作 4（程序顺序）
- **结论：** 线程 B 获取锁后，一定能看到线程 A 在锁内的所有修改

---

**规则 4：线程启动规则（Thread Start Rule）**

```java
class StartExample {
    private int data = 0;
    
    public void test() {
        data = 42;          // 操作 1
        
        Thread t = new Thread(() -> {
            int x = data;   // 操作 2，一定能看到 data=42
        });
        
        t.start();          // 操作 3
    }
}
```

**规则：** 线程的 `start()` 方法 happens-before 该线程的所有操作。

**说明：**
- 操作 1 happens-before 操作 3（程序顺序）
- 操作 3 happens-before 操作 2（线程启动规则）
- **结论：** 子线程一定能看到 `start()` 之前的所有修改

---

**规则 5：线程终止规则（Thread Termination Rule）**

```java
class JoinExample {
    private int data = 0;
    
    public void test() throws InterruptedException {
        Thread t = new Thread(() -> {
            data = 42;      // 操作 1
        });
        
        t.start();
        t.join();           // 操作 2
        
        int x = data;       // 操作 3，一定能看到 data=42
    }
}
```

**规则：** 线程的所有操作 happens-before 其他线程检测到该线程终止（通过 `join()` 或 `isAlive()`）。

**说明：**
- 操作 1 happens-before 操作 2（线程终止规则）
- 操作 2 happens-before 操作 3（程序顺序）
- **结论：** `join()` 返回后，一定能看到子线程的所有修改

---

**规则 6：线程中断规则（Thread Interruption Rule）**

```java
class InterruptExample {
    private int data = 0;
    
    public void test() throws InterruptedException {
        Thread t = new Thread(() -> {
            while (!Thread.currentThread().isInterrupted()) {
                // 工作
            }
            int x = data;   // 操作 2，能看到 data=42
        });
        
        t.start();
        data = 42;          // 操作 1
        t.interrupt();      // 操作 3
    }
}
```

**规则：** 对线程的 `interrupt()` 调用 happens-before 被中断线程检测到中断事件。

**说明：**
- 操作 1 happens-before 操作 3（程序顺序）
- 操作 3 happens-before 操作 2（线程中断规则）
- **结论：** 线程检测到中断时，能看到 `interrupt()` 之前的修改

---

**规则 7：对象终结规则（Finalizer Rule）**

```java
class FinalizerExample {
    private int data = 0;
    
    public FinalizerExample() {
        data = 42;          // 操作 1
    }
    
    @Override
    protected void finalize() {
        int x = data;       // 操作 2，一定能看到 data=42
    }
}
```

**规则：** 对象的构造函数结束 happens-before 该对象的 `finalize()` 方法。

**说明：**
- 操作 1 happens-before 操作 2
- **结论：** `finalize()` 中能看到构造函数的所有修改

**注意：** `finalize()` 已被废弃，不推荐使用。

---

**规则 8：传递性规则（Transitivity）**

```java
class TransitivityExample {
    private int a = 0;
    private int b = 0;
    private volatile boolean flag = false;
    
    // 线程 A
    public void writer() {
        a = 1;              // 操作 1
        b = 2;              // 操作 2
        flag = true;        // 操作 3（volatile 写）
    }
    
    // 线程 B
    public void reader() {
        if (flag) {         // 操作 4（volatile 读）
            int x = a;      // 操作 5，一定能看到 a=1
            int y = b;      // 操作 6，一定能看到 b=2
        }
    }
}
```

**规则：** 如果 A happens-before B，B happens-before C，则 A happens-before C。

**说明：**
- 操作 1 happens-before 操作 2（程序顺序）
- 操作 2 happens-before 操作 3（程序顺序）
- 操作 3 happens-before 操作 4（volatile 规则）
- 操作 4 happens-before 操作 5（程序顺序）
- **结论：** 通过传递性，操作 1、2 happens-before 操作 5、6

---

**happens-before 规则总结表：**

| 规则 | 场景 | 保证 |
|------|------|------|
| **程序顺序** | 单线程内 | 前面操作对后面可见 |
| **volatile** | volatile 变量 | 写操作对后续读操作可见 |
| **锁** | synchronized/Lock | unlock 对后续 lock 可见 |
| **线程启动** | Thread.start() | start() 前的操作对线程内可见 |
| **线程终止** | Thread.join() | 线程内操作对 join() 后可见 |
| **线程中断** | Thread.interrupt() | interrupt() 前的操作对中断检测后可见 |
| **对象终结** | finalize() | 构造函数对 finalize() 可见 |
| **传递性** | 组合规则 | A→B, B→C ⇒ A→C |

---

**实战案例：双重检查锁为什么需要 volatile**

```java
// ❌ 错误：没有 volatile
class Singleton {
    private static Singleton INSTANCE;
    
    public static Singleton getInstance() {
        if (INSTANCE == null) {              // 操作 1
            synchronized (Singleton.class) {
                if (INSTANCE == null) {
                    INSTANCE = new Singleton();  // 操作 2
                }
            }
        }
        return INSTANCE;                     // 操作 3
    }
}
```

**问题：** `new Singleton()` 分为 3 步：
1. 分配内存
2. 初始化对象
3. 将引用指向内存

CPU 可能重排序为：1 → 3 → 2

**时间线：**
```
线程 A: 执行到操作 2，完成步骤 1、3（引用已赋值，但对象未初始化）
线程 B: 执行操作 1，发现 INSTANCE != null，直接返回
线程 B: 使用未初始化的对象 ⚠️ 空指针或错误数据
```

**解决：** 加 `volatile`

```java
// ✅ 正确：加 volatile
class Singleton {
    private static volatile Singleton INSTANCE;  // volatile 禁止重排序
    
    public static Singleton getInstance() {
        if (INSTANCE == null) {
            synchronized (Singleton.class) {
                if (INSTANCE == null) {
                    INSTANCE = new Singleton();
                    // volatile 写，禁止重排序
                    // 保证：内存分配 → 对象初始化 → 引用赋值
                }
            }
        }
        return INSTANCE;  // volatile 读，能看到完整初始化的对象
    }
}
```

**happens-before 分析：**
- `INSTANCE = new Singleton()`（volatile 写）happens-before 后续的 volatile 读
- 保证线程 B 读到 `INSTANCE != null` 时，对象已完全初始化

### 10.3 volatile 的作用
- 保证对变量的读写直接发生在主内存。
- 禁止特定指令重排（插入内存屏障）。
- 不保证复合操作的原子性（如 `count++` 仍需锁或原子类）。volatile 只管“这一次读/写”和前后操作的有序与可见，不负责把“一串操作”变成一个不可分割的大原子块。（只是建立了屏障，不能保证屏障内的原子操作。）

```java
class StopFlag {
	private volatile boolean running = true;
	void stop() { running = false; }
	void work() {
		while (running) {
			// do work
		}
	}
}
```

### 10.4 双重检查锁 (DCL) 单例
```java
class Singleton {
	private static volatile Singleton INSTANCE;
	static Singleton getInstance() {
		if (INSTANCE == null) {
			synchronized (Singleton.class) {
				if (INSTANCE == null) {
					INSTANCE = new Singleton();
				}
			}
		}
		return INSTANCE;
	}
}
```

## 11. ThreadLocal 实战

### 11.1 基本用法
	``` java
	class ContextHolder {
		private static final ThreadLocal<String> TRACE_ID = ThreadLocal.withInitial(() -> "");
		static void set(String id) { TRACE_ID.set(id); }
		static String get() { return TRACE_ID.get(); }
		static void clear() { TRACE_ID.remove(); }
	}
	```

### 11.2 适用场景
- 请求上下文、用户会话、数据库连接、SimpleDateFormat 缓存。

### 11.3 注意事项
- 在线程池中必须调用 `remove()`，否则复用线程会携带旧数据，导致内存泄漏或脏数据。
- 对象过大或生命周期过长不适合放入 ThreadLocal。
- 可结合 `InheritableThreadLocal` 在子线程继承上下文（虚拟线程中需注意性能）。

### 11.4 ThreadLocal 内存泄漏原理

#### 1. 底层数据结构

```java
// Thread 类中的字段
public class Thread {
    ThreadLocal.ThreadLocalMap threadLocals = null;  // 每个线程持有自己的 Map
}

// ThreadLocalMap 是 ThreadLocal 的静态内部类
static class ThreadLocalMap {
    static class Entry extends WeakReference<ThreadLocal<?>> {
        Object value;  // 强引用
        
        Entry(ThreadLocal<?> k, Object v) {
            super(k);  // key 是弱引用
            value = v;
        }
    }
    
    private Entry[] table;  // 数组存储
    private int size;
}
```

**关键结构：**
- 每个 `Thread` 对象持有一个 `ThreadLocalMap`
- `ThreadLocalMap` 内部是 `Entry[]` 数组
- `Entry` 的 key 是 `ThreadLocal` 对象（**弱引用**）
- `Entry` 的 value 是实际存储的值（**强引用**）

#### 2. 引用链关系

```
Thread (强引用)
  └─> ThreadLocalMap (强引用)
        └─> Entry[] (强引用)
              └─> Entry (强引用)
                    ├─> key: ThreadLocal (弱引用) ⚠️
                    └─> value: 实际对象 (强引用) ⚠️
```

#### 3. 内存泄漏发生过程

**场景：线程池中使用 ThreadLocal**

```java
// 步骤 1：创建 ThreadLocal 并设置值
ThreadLocal<BigObject> threadLocal = new ThreadLocal<>();
threadLocal.set(new BigObject());  // 10MB 对象

// 步骤 2：业务逻辑执行完毕
// threadLocal 局部变量出栈，没有强引用指向 ThreadLocal 对象

// 步骤 3：GC 发生
// - ThreadLocal 对象被回收（因为 Entry 的 key 是弱引用）
// - Entry 变成 key=null, value=BigObject(10MB)

// 步骤 4：线程池复用线程
// - Thread 对象还活着（线程池中）
// - ThreadLocalMap 还在
// - Entry[key=null, value=BigObject(10MB)] 还在 ⚠️ 内存泄漏！
```

**时间线演示：**

```
T0: threadLocal.set(bigObject)
    Thread → ThreadLocalMap → Entry[key=ThreadLocal对象, value=bigObject(10MB)]
    
T1: 方法执行完毕，threadLocal 局部变量出栈
    无强引用指向 ThreadLocal 对象
    
T2: GC 触发
    ThreadLocal 对象被回收（弱引用）
    Thread → ThreadLocalMap → Entry[key=null, value=bigObject(10MB)] ⚠️
    
T3: 线程被线程池复用，执行新任务
    bigObject(10MB) 仍然占用内存，无法回收 ⚠️
```

#### 4. 为什么 key 用弱引用？

**如果 key 是强引用会怎样？**

```java
// 假设 Entry 的 key 是强引用
Thread → ThreadLocalMap → Entry[key=ThreadLocal对象(强引用), value=bigObject]
                                    ↑
                                    永远无法回收！
```

- ThreadLocal 对象永远无法被 GC
- 即使业务代码不再使用，ThreadLocal 对象也会一直存在
- 更严重的内存泄漏

**用弱引用的好处：**
- ThreadLocal 对象可以被 GC
- 至少 key 能被回收，Entry 变成 `key=null`
- ThreadLocalMap 有机会清理这些 `key=null` 的 Entry

#### 5. ThreadLocalMap 的自清理机制

ThreadLocalMap 在以下时机会清理 `key=null` 的 Entry：

```java
// 1. set() 时
public void set(ThreadLocal<?> key, Object value) {
    // ... 
    // 遇到 key=null 的 Entry，会清理
    if (k == null) {
        replaceStaleEntry(key, value, i);
        return;
    }
}

// 2. get() 时
public Entry getEntry(ThreadLocal<?> key) {
    // ...
    // 遇到 key=null 的 Entry，会清理
    if (e != null && e.get() == null) {
        expungeStaleEntry(i);
    }
}

// 3. remove() 时
public void remove(ThreadLocal<?> key) {
    // 直接清理 Entry
    e.clear();
    expungeStaleEntry(i);
}
```

**但是：** 如果线程一直不调用 `set/get/remove`，这些 `key=null` 的 Entry 永远不会被清理！

#### 6. 内存泄漏的真正原因

```
❌ 常见误解：弱引用导致内存泄漏
✅ 真正原因：
   1. 线程长期存活（线程池）
   2. ThreadLocal 使用后没有调用 remove()
   3. Entry 的 value 是强引用，无法被 GC
   4. 自清理机制没有触发（线程不再调用 set/get）
```

#### 7. 实战案例：内存泄漏复现

```java
public class ThreadLocalLeakDemo {
    
    // 10MB 的大对象
    static class BigObject {
        private byte[] data = new byte[10 * 1024 * 1024];
    }
    
    public static void main(String[] args) throws Exception {
        ExecutorService executor = Executors.newFixedThreadPool(1);
        
        // 提交 10 个任务
        for (int i = 0; i < 10; i++) {
            executor.submit(() -> {
                // ❌ 错误：没有 remove()
                ThreadLocal<BigObject> local = new ThreadLocal<>();
                local.set(new BigObject());  // 10MB
                
                System.out.println("Task executed, memory leaked!");
                // local 出栈，ThreadLocal 对象被 GC
                // 但 BigObject(10MB) 还在 ThreadLocalMap 中
            });
            
            Thread.sleep(1000);
            System.gc();  // 手动 GC
        }
        
        // 结果：线程池中的 1 个线程，ThreadLocalMap 中有 10 个 Entry
        // 每个 Entry 的 value 是 10MB，总共 100MB 泄漏！
        
        executor.shutdown();
    }
}
```

```
    Entry[0]: key=null, value=BigObject(10MB)  // 第 1 次任务

    Entry[2]: key=null, value=BigObject(10MB)  // 第 3 次任务

    Entry[9]: key=null, value=BigObject(10MB)  // 第 10 次任务
```

#### 8. 正确使用方式

```java
// ✅ 方式 1：手动 remove（推荐）
public void handleRequest() {
    ThreadLocal<User> userContext = new ThreadLocal<>();
    try {
        userContext.set(getCurrentUser());
        // 业务逻辑
    } finally {
        userContext.remove();  // 必须调用！
    }
}

// ✅ 方式 2：使用 static final（避免重复创建）
public class UserContext {
    private static final ThreadLocal<User> USER = new ThreadLocal<>();
    
    public static void set(User user) {
        USER.set(user);
    }
    
    public static User get() {
        return USER.get();
    }
    
    public static void clear() {
        USER.remove();  // 必须在请求结束时调用
    }
}

// Controller 层
@RestController
public class UserController {
    
    @GetMapping("/user")
    public String getUser() {
        try {
            UserContext.set(loadUser());
            return service.process();
        } finally {
            UserContext.clear();  // 必须清理
        }
    }
}

// ✅ 方式 3：使用拦截器统一清理（Spring）
@Component
public class ThreadLocalCleanInterceptor implements HandlerInterceptor {
    
    @Override
    public void afterCompletion(HttpServletRequest request, 
                                HttpServletResponse response, 
                                Object handler, Exception ex) {
        UserContext.clear();  // 统一清理
        TraceContext.clear();
        // 清理所有 ThreadLocal
    }
}
```

#### 10. 总结

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| **内存泄漏** | 线程池复用线程 + 没有 remove() | 必须在 finally 中调用 remove() |
| **脏数据** | 线程复用，读到上次请求的数据 | 每次使用前 set()，使用后 remove() |
| **为什么 key 是弱引用** | 让 ThreadLocal 对象可以被 GC | 减轻泄漏程度，但不能完全避免 |
| **为什么还会泄漏** | value 是强引用 + 线程长期存活 | 主动调用 remove() |

**核心原则：**
```java
// 线程池环境下使用 ThreadLocal 的铁律
try {
    threadLocal.set(value);
    // 业务逻辑
} finally {
    threadLocal.remove();  // 必须！必须！必须！
}
```

## 12. 死锁：条件、排查与治理

### 12.1 四个必要条件
1. **互斥**：资源一次只供一个线程使用。
2. **占有且等待**：持有资源同时请求其他资源。
3. **不可抢占**：资源不能被强制抢走。
4. **循环等待**：两个或多个线程形成环状等待链。

### 12.2 示例
```java
Object lockA = new Object();
Object lockB = new Object();
		new Thread(() -> {
	synchronized (lockA) {
		sleep(100);
		synchronized (lockB) {}
	}
}).start();
		new Thread(() -> {
	synchronized (lockB) {
		sleep(100);
		synchronized (lockA) {}
	}
}).start();
```

### 12.3 排查手段
- `jps -l` 查进程 ID，`jstack <pid>` 定位死锁线程，输出 `Found one Java-level deadlock`。
- 可使用 `jconsole`、`VisualVM`、`Java Flight Recorder` 实时监控线程状态。

### 12.4 预防策略
- **统一加锁顺序**：所有线程按同样顺序申请锁，破坏循环等待。
- **tryLock + 超时**：获取失败时释放已持有锁并重试，避免长期阻塞。
- **资源层限流**：减少同时持有多把锁的需求。
- **监控告警**：线程池堆栈定期采样，发现长时间阻塞及时告警。

### 12.5 进一步实践建议
- 建立统一的线程池与锁使用规范（命名、监控、降级策略）。
- 在关键并发组件上补充单元测试 + JMH 基准，验证可见性与性能假设。
- 结合分布式场景（如分布式锁、跨 JVM 协调）时，先确保本地并发模型牢固，再延伸到多节点一致性策略。

## 13. 虚拟线程和普通线程

### 13.1 先给结论
- **普通线程（platform thread）**：OS 级线程，1:1 绑定内核线程，创建/切换成本高。
- **虚拟线程（virtual thread）**：JDK 自带的用户态线程，极轻量，可在同一 OS 线程上挂载和切换海量虚拟线程。
- **用法**：语法几乎一致，差别主要在创建方式与调度器。
- **场景**：虚拟线程适合 I/O 密集型高并发请求；CPU 密集且线程数有限的场景收益有限。

### 13.2 核心概念
**普通线程（Platform Thread）**
- `new Thread(...)`、`Executors.newFixedThreadPool(...)` 创建的就是平台线程。
- 每个 Java 线程都绑定一个 OS 线程，默认 1MB 左右栈空间，切换由操作系统完成。
- 高并发 I/O 场景下需要开大量线程，容易耗尽内存并导致上下文切换抖动。

**虚拟线程（Virtual Thread）**
- 来自 Project Loom，JDK 21 已 GA。
- JVM 在用户态调度，可将栈拆分成分段堆分配；阻塞 I/O 或 `LockSupport.park()` 时挂起虚拟线程、释放 carrier thread。
- 阻塞结束后再把虚拟线程挂回某个 carrier OS 线程继续执行。

> 一句话：普通线程“贵又大”，虚拟线程“便宜又小，可以批发”。

### 13.3 基本用法示例
**平台线程**
```java
Thread t = new Thread(() ->
	System.out.println("hello from platform thread: " + Thread.currentThread())
);
t.start();

ExecutorService executor = Executors.newFixedThreadPool(200);
executor.submit(() -> {
	// do something
});
```

**虚拟线程（推荐 `Thread.ofVirtual()`）**
```java
Thread t = Thread.ofVirtual().start(() ->
	System.out.println("hello from virtual thread: " + Thread.currentThread())
);
```

**按任务建虚拟线程的执行器**
```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
	for (int i = 0; i < 1_000_000; i++) {
		int id = i;
		executor.submit(() -> handleRequest(id));
	}
} // try-with-resources 自动优雅关闭
```

> 虚拟线程不适合放传统固定大小线程池，直接用 `newVirtualThreadPerTaskExecutor()` 让 JVM 决定承载线程即可。

### 13.4 工程维度差异
| 关注点   | 平台线程                 | 虚拟线程                                           |
| -------- | ------------------------ | -------------------------------------------------- |
| 调度模型 | OS 调度，1:1 映射        | JVM M:N 调度到少量 carrier 线程                    |
| 阻塞 I/O | 阻塞即占满 OS 线程       | 阻塞点挂起虚拟线程，释放 carrier                   |
| 线程数量 | 几百/几千已吃力          | 百万级取决于堆与任务规模                           |
| 内存开销 | 固定大栈                 | 栈分段、按需增长、可挂到堆上                       |
| 代码风格 | 为高并发常用 NIO/回调    | 直接写同步阻塞代码，JVM 伪非阻塞                   |
| 观测调试 | Thread dump 可见业务线程 | Thread dump 同样可见虚拟线程栈，carrier 主要跑调度 |

### 13.5 典型场景
**非常适合**
1. **高并发 I/O 服务**：Web/RPC 网关、HTTP 客户端、爬虫——“一个请求一个虚拟线程”，不再纠结线程池 size。
2. **批处理 / ETL / 爬虫**：大量网络或数据库 I/O，虚拟线程能自动弹性。
3. **长连接/协议服务**：IM、WebSocket、长连接网关——一个连接一个虚拟线程即可。

**收益有限**
1. **CPU 密集场景**：瓶颈在 CPU，虚拟线程不能“变出”额外核心，仍需合理的 platform 线程池/ForkJoinPool。
2. **依赖阻塞 native 调用**：若 native 层阻塞 OS 线程，虚拟线程无法解挂，会退化为平台线程的成本。

### 13.6 线程池与协程思维
- 虚拟线程极轻量，传统“少量线程复用任务”的线程池意义降低，`newVirtualThreadPerTaskExecutor()` 本质是“一任务一线程”。
- 模型类似 Go 的 goroutine（M:N 调度），不同之处在于 Java 仍然保留 `Thread` 抽象，对旧代码更友好。

### 13.7 实战注意事项
1. **避免 busy-wait**：虚拟线程里长时间 `while(!flag){}` 会占满 carrier 线程，改用 `LockSupport.park()`、`Condition`、`CountDownLatch` 等同步工具。
2. **评估第三方库**：大锁或长时间阻塞的库会拖慢虚拟线程；必要时隔离在 platform 线程池中。
3. **谨慎使用 ThreadLocal**：虚拟线程数量巨大，ThreadLocal 滥用会成为内存炸弹，能参数传递就传参。
4. **CPU 密集任务单独托管**：将重计算任务下发到专门的平台线程池，避免占用 carrier。

### 13.8 一句话总结
> 虚拟线程让 Java“写同步阻塞代码也能获得接近异步非阻塞的扩展性”。I/O 密集型服务值得优先尝试；CPU 密集或依赖阻塞 native 的场景则需结合算法与平台线程优化，虚拟线程并非银弹。

## 14. CompletableFuture实战

### 14.1 它到底是什么：Future + CompletionStage 的混合体

```java
 //这货有两个身份：
public class CompletableFuture<T>
        implements Future<T>, CompletionStage<T> {
}
```
- 作为 Future：表示“将来某个时间会给你一个 T 结果”，可以 get()/join()、cancel()。
- 作为 CompletionStage：可以在完成后触发一系列“后续动作”（thenXXX），形成 异步任务流水线。

多了两个字 "Completable"，意思是：
- 既可以自己跑异步得到结果（supplyAsync/runAsync），
- 也可以由别人来调用 complete() / completeExceptionally() 把它“完成”。

等价于 Java 版的 Promise。

### 14.2 常见创建姿势：谁来算、在哪儿算

1. 直接 new，之后手动 complete
```java
CompletableFuture<String> cf = new CompletableFuture<>();
```
2. 起一个“有返回值”的异步任务
```java
CompletableFuture<String> cf1 =
        CompletableFuture.supplyAsync(() -> {
            return queryFromDb();
        });
```
3. 起一个“无返回值”的异步任务
```java
CompletableFuture<Void> cf2 =
        CompletableFuture.runAsync(() -> {
            doSomething();
        });
```
4. 指定线程池
    ```java
    ExecutorService executor = Executors.newFixedThreadPool(8);
    CompletableFuture<String> cf3 =
            CompletableFuture.supplyAsync(() -> queryFromDb(), executor);
    ```
    - 不传 executor 时，会用 ForkJoinPool.commonPool() 这个全局池。
    - 在虚拟线程时代，可以这样配合：
        ```java
        ExecutorService vExecutor = Executors.newVirtualThreadPerTaskExecutor();
        CompletableFuture<String> cf4 =
                CompletableFuture.supplyAsync(() -> queryFromDb(), vExecutor);
        ```
        - 逻辑上就是“每个任务跑在一个虚拟线程里”。

### 14.3 最核心的能力：链式操作（流式异步）
1. 基于结果的“变换”/“消费”
    - 假设有一个 CompletableFuture<T>：
    - thenApply(fn)：接收前一步结果，计算一个新结果，返回 CompletableFuture
        ```java
            CompletableFuture<User> userFuture = queryUserAsync();
            CompletableFuture<String> nameFuture =
                userFuture.thenApply(user -> user.getName());
        ```
    - thenAccept(consumer)：接收结果，消耗一下，不返回新值
        ```java
        userFuture.thenAccept(user -> log.info("user: {}", user));
        ```

    - thenRun(runnable)：只关心“完成事件”，不关心结果
        ```java
        userFuture.thenRun(() -> log.info("user loaded."));
        ```
2. thenApply vs thenCompose
    - 这是面试爱问点。
    - thenApply：结果 -> 另一个 CompletableFuture，但不会“拆开”
        ```java
        CompletableFuture<CompletableFuture<Order>> nested =
            userFuture.thenApply(user -> queryOrderAsync(user.getId()));
        ```
    - thenCompose：把 CompletableFuture<CompletableFuture> 拉平成 CompletableFuture
        ```java
        CompletableFuture<Order> flat =
            userFuture.thenCompose(user -> queryOrderAsync(user.getId()));
        ```
    - 记忆方法：
        - thenApply：普通函数 T -> U
        - thenCompose：扁平化异步 T -> CompletableFuture，类似 Stream 里的 flatMap。
    - 典型场景：前一个异步结果出来后，发起下一个异步，不用嵌套 future。

3. 多任务组合：并发 + 汇总
    - 两个任务结果合并：thenCombine
        ```java
        CompletableFuture<User> userFuture = queryUserAsync();
        CompletableFuture<List<Order>> orderFuture = queryOrdersAsync();
        CompletableFuture<UserWithOrders> result =
            userFuture.thenCombine(orderFuture, (user, orders) -> {
                return new UserWithOrders(user, orders);
            });
        ```
    - 两者谁先完成都行，thenCombine 会在两者都完成后执行合并函数。

4. 等一群任务都完：allOf
    ```java
    CompletableFuture<Void> all =
        CompletableFuture.allOf(cf1, cf2, cf3);
    all.join(); // 等所有都执行完
    ```
    - 如果你想拿回结果：
        ```java
        List<Object> results = Stream.of(cf1, cf2, cf3)
            .map(CompletableFuture::join)
            .collect(Collectors.toList());
        ```
    - 常见用法：并行请求多个下游接口 / 多个库，最后一起汇总。

5. 谁先好用谁：anyOf
    ```java 
    CompletableFuture<Object> any =
        CompletableFuture.anyOf(cf1, cf2, cf3);
    Object fastest = any.join();
    ```
    - 典型场景：多机房/多实例“竞速请求”，谁先回就用谁，其它取消或忽略。

### 14.4 异常处理：异常不处理就是地雷
1. 异常怎么传下去？
    - 任意一个 stage 抛出异常，这个 CompletableFuture 会变为“完成异常”状态。
    - 默认情况：后续依赖它的 stage 会拿到这个异常：
    - join() 时会 CompletionException 包一层
    - 要么你绑处理器，要么就等它炸。
2. 三种常用处理 API
    - exceptionally(Function<Throwable, ? extends T>)
        - 给一个兜底值：
            ```java
            CompletableFuture<String> result =
                queryFromRemote()
                    .exceptionally(ex -> {
                        log.error("远程失败: {}", ex.getMessage());
                        return "fallback";
                    });
            ```
        - 只在前面出异常时执行。
    - handle(BiFunction<T, Throwable, U>)
        - 同时看到正常值 & 异常，二选一：
        ```java
        CompletableFuture<String> result =
            queryFromRemote()
                .handle((value, ex) -> {
                    if (ex != null) {
                        log.error("error", ex);
                        return "fallback";
                    }
                    return "ok: " + value;
                });
        ```
    - whenComplete(BiConsumer<T, Throwable>)
        - 像 finally：不改变结果，只做收尾
        ```java 
        CompletableFuture<String> result =
            queryFromRemote()
                .whenComplete((value, ex) -> {
                    log.info("调用结束，成功={}，值={}", ex == null, value);
                })
                .exceptionally(ex -> "fallback"); // 真正兜底在这里
        ```

### 14.5 同步 vs Async 回调：到底在哪个线程执行？

1. 每个 thenXXX 基本都有三个版本：
    - thenApply(...)              → 当前执行的线程里跑回调（“同步依附版”）
    - thenApplyAsync(...)         → 交给 默认 ForkJoinPool 执行
    - thenApplyAsync(..., exec)   → 交给你指定的 Executor 执行
    - 如果你在 web 线程里写：
        ```java
        cf.thenApply(r -> slowCall());
        ```
        - 只要 cf 在这个 web 线程里完成，那 slowCall() 也会在 web 线程里跑，
        - 等价于你自己同步调用，压根没“异步优化”。
    - 所以经验：
        - 想利用线程池并行 → 用 xxxAsync，或者保证前一个 stage 本身已是异步（在其他线程池跑）。
        - 在虚拟线程里用 thenApply 问题不大，因为虚拟线程本身很轻，你只是串起来任务逻辑而已。

### 14.6 典型业务场景示例
- 场景：下单接口，要并行查用户、库存、优惠券

### 14.7 取消 & 超时

1. 取消
    ```java
    CompletableFuture<String> cf = new CompletableFuture<>();
    cf.cancel(true);
    ```
    - cancel() 只是改变 future 状态为“已取消”，
    - 如果底层线程不检查这个状态，它还是会继续跑。
    - 想实现真正的“可取消”，你要在任务中轮询某种取消信号。

2. 超时（JDK 9+）
    ```java
    cf.orTimeout(3, TimeUnit.SECONDS)      // 超时后抛 TimeoutException
      .exceptionally(ex -> "timeout fallback");
    ```
    - 或者：
    ```java
    cf.completeOnTimeout("fallback", 3, TimeUnit.SECONDS);
    ```
    - 这个是“超时没结果就直接填一个默认值”。

### 14.8 内部实现大致长什么样（只说个轮廓）

1. 别太细抠源码，先建立抽象模型就行：
    - CompletableFuture 内部有：
        - 一个 结果字段（result）：可能是值，也可能是异常、取消标记
        - 一个 回调链表（stack / next）：所有 thenXXX 都会注册成“依赖这个结果的节点”
    - 当任务完成（正常 / 异常 / 取消）时：
        - 设置 result
        - 遍历这些依赖节点，挨个触发：
            - 如果是普通 thenApply：直接在当前线程调回调
            - 如果是 thenApplyAsync：丢到对应 executor 里去执行
    - 每个节点执行自己逻辑后，又会完成自己的 CompletableFuture，再触发下一批节点……

2. 所以：
    - 不要在回调里写长时间 blocking 操作（尤其是用 commonPool 时）。
    - 你可以通过自定义 executor，把某些 stage 确认放到独立线程池中跑（比如 IO 密集 vs 计算密集分开）。

### 14.10 commonPool的问题
1. CompletableFuture 默认把 supplyAsync/runAsync/thenApplyAsync 这些任务丢进 ForkJoinPool.commonPool。这个池子最擅长的是 短小、CPU 密集、可分治 的任务；最怕的是 阻塞 I/O。一旦你把阻塞任务塞进去，commonPool 被“占满”，就会出现很典型的级联故障：本来只是某个下游慢，最后变成整个应用的异步链路集体变慢/超时/雪崩。

2. commonPool 被阻塞会发生什么级联故障？

    - 现象 A：异步任务排队，链路整体延迟暴涨
        - commonPool 的线程数通常接近 CPU 核数（大概 NCPU-1 量级）。如果这些线程都在做阻塞 I/O（HTTP/JDBC/Redis 等）：
            - 线程被挂住（等待网络/磁盘/锁）
            - 新提交的异步任务只能排队
            - 你的 CompletableFuture 链条后续 stage（尤其 xxxAsync）也排队
        - 结果：一个接口里“并行查 4 个下游”的设计，反而变成“排队串行”。

    - 现象 B：超时成片出现，线程池“自我放大”故障
        - 当排队严重时，业务线程为了拿结果会开始：
            - join()/get() 阻塞等待
            - 或者继续提交更多异步任务（重试/降级/补偿）
        - 这会导致：
            - 任务更多 → 排队更长 → 超时更多 → 重试更多
            - 典型正反馈环（雪崩环）。

    - 现象 C：不相关业务被拖死（“旁路业务一起死”）
        - commonPool 是 JVM 进程级共享资源：
            - 你这个模块用它跑阻塞 I/O
            - 别的模块也可能用它跑计算/异步回调
            - 某些库也可能间接使用它
        - 于是你会看到：A 业务的下游慢，B 业务的异步逻辑也开始超时。这就是“级联”：跨业务传播。

    - 现象 D：回调链卡住，甚至看起来像“死锁”
        - 很多人写法是：
            - CompletableFuture.supplyAsync(ioCall) // 默认 commonPool
            - .thenApplyAsync(parse)            // 也默认 commonPool
            - .thenComposeAsync(nextIoCall);    // 还是 commonPool
        - 如果 commonPool 线程都卡在第一步 ioCall，后面的 parse/compose 任务根本拿不到线程执行，链条就“停在半路”。
        - 你会感觉像“future 不回调”，其实是回调没有线程可跑。

3. 为什么 commonPool 不适合阻塞 I/O？
    - 原因 1：ForkJoinPool 设计目标不是“很多阻塞等待”
        - ForkJoinPool 的设计假设是：
            - 任务短
            - CPU 密集
            - 线程不会长时间阻塞
        - 阻塞 I/O 恰恰相反：线程大部分时间在等，吞吐靠“更多线程覆盖等待”，而 commonPool 线程数很少（接近核数），一阻塞就没工人了。

    - 原因 2：工作窃取(work-stealing)对阻塞没用，还可能更糟
        - ForkJoin 的优势在于：线程忙完自己队列的任务，可以去偷别人的任务继续跑。
        - 但阻塞 I/O 时线程是“挂死”等待，没法偷，也没法跑，工作窃取优势发挥不出来。

    - 原因 3：共享池 + 不隔离 = 故障扩散
        - 阻塞 I/O 是“不可控延迟源”（网络抖动、下游超时、连接池耗尽都能让它卡很久）。
        - 把这种任务丢在全局共享池，相当于把不稳定性注入到全局调度器，自然容易“扩散”。

4. 实战解法
    - 做法 A：显式传业务线程池（I/O 专用）
        - CompletableFuture.supplyAsync(() -> httpCall(), ioPool);
        - 并把 I/O 池设置为：
            - 有界队列
            - 合理拒绝策略（CallerRuns 或快速失败）
            - 配合下游限流（Semaphore/Resilience4j/Sentinel）

    - 做法 B：JDK 21+：用虚拟线程 executor 承载阻塞 I/O
        - Executor vExec = Executors.newVirtualThreadPerTaskExecutor();
        - CompletableFuture.supplyAsync(() -> jdbcCall(), vExec);
        - 这样阻塞不再稀缺，但仍需限流资源（DB 连接数、下游 QPS）。

    - 做法 C：减少 join/get，链式组合把等待推迟到最外层
        - 避免在池内线程 join() 另一个 future，尽量用 thenCompose/thenCombine/allOf 做编排。

5. 总结
    - commonPool 线程数接近 CPU 核数，适合短小 CPU 任务；如果用它跑阻塞 I/O，会把池线程占满，导致后续异步任务排队、回调无线程执行、join/get 堵塞业务线程，触发超时重试的正反馈，甚至让不相关模块一起变慢，这是典型的 thread starvation 级联故障。所以阻塞 I/O 必须用隔离的 executor（或虚拟线程），并配合限流/超时/降级。

### 15.1 为什么需要 ConcurrentHashMap

**HashMap 的问题：**
```java
// ❌ HashMap 线程不安全

// 线程 B
map.put("key2", "value2");

// 可能导致：
// 1. 数据丢失
// 2. 死循环（JDK 7 扩容时）
// 3. 数据覆盖
```

**Hashtable 的问题：**
```java
// ❌ Hashtable 性能差
Map<String, String> map = new Hashtable<>();

public synchronized V get(Object key) { ... }
public synchronized V put(K key, V value) { ... }

// 问题：所有操作都用同一把锁，读写互斥，性能极差
```

**ConcurrentHashMap 的优势：**
- 线程安全
- 高并发性能好（分段锁/CAS）
- 读操作几乎无锁

### 15.2 JDK 7 vs JDK 8 实现对比

| 特性 | JDK 7 | JDK 8 |
|------|-------|-------|
| **底层结构** | Segment[] + HashEntry[] | Node[] + 红黑树 |
| **锁粒度** | Segment 级别（分段锁） | Node 级别（更细粒度） |

| **扩容** | 每个 Segment 独立扩容 | 全局协作扩容 |
| **读操作** | 几乎无锁（volatile） | 完全无锁（volatile） |

### 15.3 JDK 7 实现：分段锁（Segment）

#### 1. 数据结构

```java
// ConcurrentHashMap 结构
ConcurrentHashMap
  └─> Segment[] (默认 16 个)
        └─> HashEntry[] (每个 Segment 是一个小 HashMap)
              └─> HashEntry (链表节点)

// Segment 继承 ReentrantLock
static final class Segment<K,V> extends ReentrantLock {
    transient volatile HashEntry<K,V>[] table;
    transient int count;
}

// HashEntry 节点
static final class HashEntry<K,V> {
    final int hash;
    final K key;
    volatile V value;
    volatile HashEntry<K,V> next;
}
```

**关键点：**
- 16 个 Segment，每个 Segment 是一把锁
- 不同 Segment 之间可以并发访问
- 理论并发度：16

#### 2. put 操作

```java
public V put(K key, V value) {
    // 1. 计算 hash
    int hash = hash(key);
    
    // 2. 定位到 Segment
    int segmentIndex = (hash >>> segmentShift) & segmentMask;
    Segment<K,V> segment = segments[segmentIndex];
    
    // 3. 在 Segment 内加锁
    segment.lock();
    try {
        // 4. 定位到 HashEntry[] 的位置
        int index = hash & (segment.table.length - 1);
        HashEntry<K,V> first = segment.table[index];
        
        // 5. 遍历链表，查找或插入
        for (HashEntry<K,V> e = first; e != null; e = e.next) {
            if (e.hash == hash && key.equals(e.key)) {
                V oldValue = e.value;
                e.value = value;  // 更新
                return oldValue;
            }
        }
        
        // 6. 插入新节点（头插法）
        HashEntry<K,V> newEntry = new HashEntry<>(hash, key, value, first);
        segment.table[index] = newEntry;
        segment.count++;
        
    } finally {
        segment.unlock();
    }
}
```

**并发示例：**
```
线程 A: put("key1", "v1")  → Segment[0] 加锁
线程 B: put("key2", "v2")  → Segment[5] 加锁  ✓ 可以并发
线程 C: put("key3", "v3")  → Segment[0] 等待  ✗ 被阻塞
```

#### 3. get 操作（几乎无锁）

```java
public V get(Object key) {
    // 1. 计算 hash
    int hash = hash(key);
    
    // 2. 定位到 Segment
    int segmentIndex = (hash >>> segmentShift) & segmentMask;
    Segment<K,V> segment = segments[segmentIndex];
    
    // 3. 定位到 HashEntry[] 的位置（无锁）
    int index = hash & (segment.table.length - 1);
    HashEntry<K,V> first = segment.table[index];
    
    // 4. 遍历链表（无锁，依赖 volatile）
    for (HashEntry<K,V> e = first; e != null; e = e.next) {
        if (e.hash == hash && key.equals(e.key)) {
            return e.value;  // volatile 读
        }
    }
    return null;
}
```

**为什么 get 无锁？**
- `HashEntry.value` 是 `volatile`，保证可见性
- `HashEntry.next` 是 `volatile`，保证链表结构可见
- 读操作不修改数据，不需要加锁

### 15.4 JDK 8 实现：CAS + synchronized

#### 1. 数据结构

```java
// ConcurrentHashMap 结构
ConcurrentHashMap
  └─> Node[] table (数组)
        ├─> Node (链表节点)
        └─> TreeNode (红黑树节点，链表长度 ≥ 8 时转换)

// Node 节点
static class Node<K,V> {
    final int hash;
    final K key;
    volatile V val;        // volatile
    volatile Node<K,V> next;  // volatile
}
```

**关键变化：**
- 取消 Segment，直接用 Node[] 数组
- 锁粒度更细：每个数组位置（桶）一把锁
- 链表长度 ≥ 8 转红黑树（提升查询性能）

#### 2. put 操作

```java
public V put(K key, V value) {
    return putVal(key, value, false);
}

final V putVal(K key, V value, boolean onlyIfAbsent) {
    int hash = spread(key.hashCode());
    
    for (Node<K,V>[] tab = table;;) {
        Node<K,V> f; int n, i, fh;
        
        // 1. 数组未初始化，先初始化
        if (tab == null || (n = tab.length) == 0)
            tab = initTable();
        
        // 2. 桶为空，CAS 插入（无锁）
        else if ((f = tabAt(tab, i = (n - 1) & hash)) == null) {
            if (casTabAt(tab, i, null, new Node<K,V>(hash, key, value, null)))
                break;  // CAS 成功，直接返回
        }
        
        // 3. 正在扩容，帮助扩容
        else if ((fh = f.hash) == MOVED)
            tab = helpTransfer(tab, f);
        
        // 4. 桶不为空，加锁插入
        else {
            V oldVal = null;
            synchronized (f) {  // 锁住桶的头节点
                if (tabAt(tab, i) == f) {
                    // 4.1 链表
                    if (fh >= 0) {
                        for (Node<K,V> e = f;; ++binCount) {
                            K ek;
                            if (e.hash == hash && ((ek = e.key) == key || 
                                (ek != null && key.equals(ek)))) {
                                oldVal = e.val;
                                if (!onlyIfAbsent)
                                    e.val = value;  // 更新
                                break;
                            }
                            Node<K,V> pred = e;
                            if ((e = e.next) == null) {
                                pred.next = new Node<K,V>(hash, key, value, null);
                                break;
                            }
                        }
                    }
                    // 4.2 红黑树
                    else if (f instanceof TreeBin) {
                        Node<K,V> p;
                        if ((p = ((TreeBin<K,V>)f).putTreeVal(hash, key, value)) != null) {
                            oldVal = p.val;
                            if (!onlyIfAbsent)
                                p.val = value;
                        }
                    }
                }
            }
            
            // 5. 检查是否需要树化
            if (binCount != 0) {
                if (binCount >= TREEIFY_THRESHOLD)
                    treeifyBin(tab, i);
                if (oldVal != null)
                    return oldVal;
                break;
            }
        }
    }
    
    addCount(1L, binCount);
    return null;
}
```

**关键优化：**
1. **桶为空时用 CAS**：无锁插入，性能最优
2. **桶不为空时用 synchronized**：只锁当前桶，不影响其他桶
3. **链表转红黑树**：链表长度 ≥ 8 时转换，查询 O(log n)

#### 3. get 操作（完全无锁）

```java
public V get(Object key) {
    Node<K,V>[] tab; Node<K,V> e, p; int n, eh; K ek;
    int h = spread(key.hashCode());
    
    if ((tab = table) != null && (n = tab.length) > 0 &&
        (e = tabAt(tab, (n - 1) & h)) != null) {
        
        // 1. 头节点就是目标
        if ((eh = e.hash) == h) {
            if ((ek = e.key) == key || (ek != null && key.equals(ek)))
                return e.val;
        }
        // 2. 红黑树查找
        else if (eh < 0)
            return (p = e.find(h, key)) != null ? p.val : null;
        
        // 3. 链表查找
        while ((e = e.next) != null) {
            if (e.hash == h && ((ek = e.key) == key || 
                (ek != null && key.equals(ek))))
                return e.val;
        }
    }
    return null;
}
```

**为什么完全无锁？**
- `Node.val` 和 `Node.next` 都是 `volatile`
- 读操作只读取，不修改
- 依赖 volatile 的可见性保证

### 15.5 扩容机制

#### JDK 7：每个 Segment 独立扩容

```java
// Segment 内部扩容
void rehash() {
    HashEntry<K,V>[] oldTable = table;
    int oldCapacity = oldTable.length;
    int newCapacity = oldCapacity << 1;  // 扩容 2 倍
    
    HashEntry<K,V>[] newTable = new HashEntry[newCapacity];
    
    // 重新分配所有节点
    for (int i = 0; i < oldCapacity; i++) {
        HashEntry<K,V> e = oldTable[i];
        if (e != null) {
            // 重新计算位置，插入新表
        }
    }
    
    table = newTable;
}
```

**特点：**
- 每个 Segment 独立扩容
- 扩容时只锁当前 Segment
- 其他 Segment 不受影响

#### JDK 8：全局协作扩容

```java
// 多线程协作扩容
private final void transfer(Node<K,V>[] tab, Node<K,V>[] nextTab) {
    int n = tab.length, stride;
    
    // 1. 计算每个线程负责的桶数量
    if ((stride = (NCPU > 1) ? (n >>> 3) / NCPU : n) < MIN_TRANSFER_STRIDE)
        stride = MIN_TRANSFER_STRIDE;
    
    // 2. 每个线程领取一段桶进行迁移
    for (int i = 0, bound = 0;;) {
        // 领取任务
        if (--i >= bound || finishing)
            advance = false;
        else if ((nextIndex = transferIndex) <= 0) {
            i = -1;
            advance = false;
        }
        else if (U.compareAndSwapInt(this, TRANSFERINDEX, nextIndex,
                                      nextBound = (nextIndex > stride ?
                                                   nextIndex - stride : 0))) {
            bound = nextBound;
            i = nextIndex - 1;
            advance = false;
        }
        
        // 3. 迁移节点
        synchronized (f) {
            // 将节点从旧表迁移到新表
        }
    }
}
```

**特点：**
- 多线程协作扩容
- 每个线程领取一段桶进行迁移
- 扩容期间可以继续读写（读旧表，写新表）

### 15.6 size() 方法

#### JDK 7：累加所有 Segment 的 count

```java
public int size() {
    long sum = 0;
    
    // 1. 先尝试无锁累加（最多 3 次）
    for (int k = 0; k < RETRIES_BEFORE_LOCK; ++k) {
        sum = 0;
        int mcsum = 0;
        for (int i = 0; i < segments.length; ++i) {
            sum += segments[i].count;
            mcsum += segments[i].modCount;  // 修改次数
        }
        
        // 如果修改次数没变，说明没有并发修改，返回
        if (mcsum == lastMcsum)
            break;
        lastMcsum = mcsum;
    }
    
    // 2. 无锁失败，加锁累加
    if (sum > Integer.MAX_VALUE) {
        for (int i = 0; i < segments.length; ++i)
            segments[i].lock();
        try {
            sum = 0;
            for (int i = 0; i < segments.length; ++i)
                sum += segments[i].count;
        } finally {
            for (int i = 0; i < segments.length; ++i)
                segments[i].unlock();
        }
    }
    
    return (int) sum;
}
```

#### JDK 8：baseCount + counterCells

```java
public int size() {
    long n = sumCount();
    return ((n < 0L) ? 0 : (n > (long)Integer.MAX_VALUE) ? 
            Integer.MAX_VALUE : (int)n);
}

final long sumCount() {
    CounterCell[] as = counterCells;
    long sum = baseCount;  // 基础计数
    
    if (as != null) {
        for (int i = 0; i < as.length; ++i) {
            CounterCell a;
            if ((a = as[i]) != null)
                sum += a.value;  // 累加分片计数
        }
    }
    return sum;
}
```

**类似 LongAdder：**
- `baseCount`：基础计数
- `counterCells[]`：分片计数（减少竞争）
- `size()` = baseCount + Σ counterCells[i]

### 15.8 使用建议

**✅ 适合使用 ConcurrentHashMap：**
```java
// 1. 高并发读写
private static final Map<String, User> userCache = new ConcurrentHashMap<>();

// 2. 无需强一致性（弱一致性迭代器）
for (Map.Entry<String, User> entry : userCache.entrySet()) {
    // 迭代期间可能看不到最新的修改
}

// 3. 不需要锁整个 Map
userCache.computeIfAbsent(userId, id -> loadUser(id));
```

**❌ 不适合使用 ConcurrentHashMap：**
```java
// 1. 需要强一致性
// ❌ 错误：size() 是弱一致的
if (map.size() > 100) {
    map.clear();  // 可能 size() 已经变了
}

// 2. 需要原子复合操作
// ❌ 错误：非原子
if (!map.containsKey(key)) {
    map.put(key, value);  // 可能被其他线程插入
}

// ✅ 正确：使用原子方法
map.putIfAbsent(key, value);

// 3. 需要锁整个 Map
// ❌ 错误：无法锁整个 Map
synchronized (map) {  // 无效！
    // 批量操作
}
```

### 15.9 总结

| 特性 | HashMap | Hashtable | ConcurrentHashMap (JDK 8) |
|------|---------|-----------|---------------------------|
| **线程安全** | ❌ 否 | ✅ 是 | ✅ 是 |
| **锁粒度** | - | 整个表 | 每个桶 |
| **读性能** | 高 | 低（加锁） | 高（无锁） |
| **写性能** | 高 | 低（串行） | 高（细粒度锁） |
| **null key/value** | ✅ 允许 | ❌ 不允许 | ❌ 不允许 |
| **迭代器** | fail-fast | fail-fast | 弱一致性 |
| **适用场景** | 单线程 | 低并发 | 高并发 |

**核心原则：**
- 单线程用 HashMap
- 低并发用 Hashtable 或 Collections.synchronizedMap
- 高并发用 ConcurrentHashMap

5. 总结
    - commonPool 线程数接近 CPU 核数，适合短小 CPU 任务；如果用它跑阻塞 I/O，会把池线程占满，导致后续异步任务排队、回调无线程执行、join/get 堵塞业务线程，触发超时重试的正反馈，甚至让不相关模块一起变慢，这是典型的 thread starvation 级联故障。所以阻塞 I/O 必须用隔离的 executor（或虚拟线程），并配合限流/超时/降级。
