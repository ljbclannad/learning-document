DDD改造的个人经验总结：

	1. 当初提出DDD改造的时候，网上查阅各种文章，大多数文章都是理论化，领域设计，六边形架构等。怎么看怎么懵逼。真的是听君一席话如听一席话，后来总结下ddd其实就是一个设计思想，思想的核心是将我们的代码解耦（当然微服务也能做到），行为绑定（这点我觉得是个人处理下来感触最深的一点）。
	2. 平台代码实践时步骤：
	 	1. 将原来的代码划分各个领域（根据业务划分），将各个领域先建立不同的Controller，根据对各个业务的熟悉程度安排开发
	 	2. 正式着手，个人方面：按照CQRS原则优先处理查询逻辑，将原来的查询Service进行解耦，建立自己领域的查询，涉及其他领域的查询写上TODO处理
	 	3. 查询编写：建立一个通用的仓储PO，建立一个Convernt，所有关于领域查询的全部只返回PO，再由PO转换成domin或者响应的DTO，转化方法在Convernt类中编写，易懂且易维护，一般很少存在需要返回其他领域字段的情况，如果有，也可以通过domin中的实体或者值对象进行转化返回给前端，这样子就完成了查询，同时将原来到处连表查询等操作转为各个领域的原子操作（解耦）,整体调用步骤为：Controller->QueryApplication->queryRespority->mapper（由于mybatis-plus的原因，queryMapper被舍弃）。
	 	4. 业务代码编写：通过Command接受需要操作的内容（针对这个领域，如你要修改这个订单，command就传入这个订单的信息）。在application中对原来的Service进行业务编排。如果需要进行业务操作，通过领域的bind方法（一般行为可能通过直接写update set SQL语句进行操作，不直观，行为直接绑定在领域上，体现了充血模型）进行修改，然后调用save方法直接入库。
	 	5. 整体可根据demo展示一下ddd的架构迁移，PO,DTO,domin要区分好，代码规范要写的规范
