# 会话上下文设计方案

本文讲解如何从聊天原文构建摘要快照，如何补齐摘要尚未覆盖的消息，以及如何处理重复、乱序和迟到的更新。

## 1. 聊天原文、摘要与任务状态各是什么

这里的“会话上下文”特指业务维护的摘要快照，并不等于模型本次看到的全部上下文。模型输入还包括当前消息、必要的近期原文、画像、检索证据和可信规则。

| 对象 | 事实来源 | 保存目的 | 失效后的处理 |
| --- | --- | --- | --- |
| 原始消息 | 用户提交、系统实际回复 | 重放、审计、引用与纠错 | 按业务保留策略存储；不能写成永久保存 |
| 摘要快照 | 指定消息范围的派生结果 | 减少重复读取和模型输入体积 | 可从授权原文重建，不能以空摘要冒充历史为空 |
| 画像 | 已确认或标注来源的用户属性 | 跨会话复用的事实与偏好 | 见 [[用户画像存储设计方案]] |
| 长期记忆 | 具有来源的历史片段/候选事实 | 相关性检索 | 见 [[千问Embedding+Milvus向量搜索集成文档]] |
| 任务状态 | 执行系统的目标、审批和动作记录 | 控制是否可以继续执行 | 必须独立持久化，不依赖自然语言摘要恢复 |

摘要具有损失性。不能把摘要理解为原文的完全替代：需要精确数字、纠正信息或引用时应回查原文，当前消息也必须保留。概念机制见 [[Context Engineering（上下文工程）]]，本文只维护本项目的状态契约。

## 2. 一个快照需要表达什么

原 `currentTopic / userIntent / mentionedEntities / extractedData / recentSummaries / pendingQuestions / aiState` 可保留为内容字段，但需要补上覆盖范围与来源：

```json
{
  "tenantId": "tenant-demo",
  "customerId": "customer-demo",
  "groupId": "group-demo",
  "sessionEpoch": 3,
  "contextVersion": 12,
  "coveredThroughSeq": 40,
  "sourceMessageIds": ["m39", "m40"],
  "currentTopic": "活动记录",
  "userIntent": "报告数据",
  "extractedData": [
    {
      "name": "步数",
      "value": "5200",
      "unit": "步",
      "sourceMessageId": "m39",
      "status": "用户自述"
    }
  ],
  "recentSummaries": [
    {"role": "user", "summary": "补充昨日活动记录", "sourceMessageId": "m39"}
  ],
  "pendingQuestions": ["记录对应的日期尚待确认"],
  "templateVersion": "summary-v1"
}
```

这是设计数据示例，不是实际患者资料。`sourceMessageIds` 展示样例引用；真实实现要能定位整个已覆盖消息范围，不能只保留两条 ID 就证明覆盖了 1–40。

- `coveredThroughSeq` 表示快照连续覆盖到哪条已提交消息，不是最近一次收到的消息编号；消息编号如何分配、跳号如何表示，需要数据库消息流契约。
- `contextVersion` 用于条件更新；`sessionEpoch` 在清空/重开会话时推进，阻止旧任务把已清理状态复活。水位和 epoch 应有持久化来源，不能只放在会过期的 Redis Key 中。
- `sourceMessageId / unit / observedAt / status` 保留证据及不确定性。单个 `Map<字段, 字符串>` 会覆盖同名历史测量，丢失单位、否定关系和时间。
- `aiState` 仅表示应用可观察的字段，不是模型内部状态。供应商 `conversationId` 单独保存，不作为租户、患者或会话授权依据。

## 3. 本轮读取：摘要落后时如何补齐

在接收当前消息后，先确定本轮的持久化消息上界 `readThroughSeq`。读取摘要 `(epoch, version, coveredThroughSeq)`，再读取 `(coveredThroughSeq, readThroughSeq]` 的原始消息；这些内容共同组成输入快照。

```text
数据库已有 m1…m42；摘要只覆盖 m1…m40
本轮输入 = 已覆盖摘要 + m41 + 当前消息 m42 + 本轮检索证据
下一轮不能只读取 Redis 摘要并遗漏 m41、m42
```

如果当前消息已经包含在补齐窗口中，就不要再拼接一次。窗口过大时按业务规则降级、分段重建或等待；不要悄悄截断尚未覆盖的关键消息。近期原文与摘要同时存在时，通过来源范围去重，不靠内容字符串相等。

缓存没有快照时，以“待重建”进入：可先用受限近期原文回答，或在所需信息不足时请求补充。不能调用模型“预测用户可能咨询的话题”并当成实际意图；默认值应是未知。1 小时 TTL 是缓存策略的一个例子，不能代表会话的业务生命周期。

## 4. 后台提炼：计算与提交分开

摘要提炼可以是受控模型调用，也可以包含确定性字段提取。将实体、意图、关键数据和摘要合并为一次结构化提炼可作为候选优化，需与分步骤基线比较准确率；不要假定一个模型调用一定覆盖所有字段且更好。

候选输出必须校验：字段白名单、长度、枚举、来源消息是否属于快照、数值单位、时间及否定/纠正关系。不通过就保留原文并标记失败。关键词或正则降级只能产生待确认线索，不能把“我没有某疾病”识别成肯定患病，也不能把失败返回空对象当作“没有信息”。

以下是状态转换伪代码；原子条件需在实际数据库实现：

```text
base = readCommittedContext(groupId)
end = selectContiguousCommittedMessages(base.coveredThroughSeq, targetSeq)
candidate = summarize(base, messagesThrough(end))  // 在事务外调用模型
validate(candidate, sourceMessages)

条件提交：
  当前 epoch == base.epoch
  且 当前 contextVersion == base.contextVersion
  且 当前 coveredThroughSeq == base.coveredThroughSeq
成立：保存 candidate，version + 1，coveredThroughSeq = end
不成立：重新读取状态，判断已覆盖、会话已重置或需要重新计算；禁止盲写
```

`coveredThroughSeq` 不能取两个乱序摘要的最大值再直接覆盖内容，因为内容未必覆盖了被跨过的消息。异步调度、重试和交付归 [[AI消息后处理异步方案]]，本篇只决定结果是否可提交。

### 4.1 旧任务迟到的反例

```text
A 从 v5、覆盖到 m20 的快照开始，计算 m21…m22
B 也从 v5 开始，计算 m21…m24，先提交 v6
A 后完成：若直接 SET Redis，会把覆盖位置从 m24 退回 m22
修正：A 的条件提交失败；发现当前已覆盖 m22，结束为已被更新结果覆盖
```

如果用户在 A 计算时清空会话，epoch 应变化；即使 Redis 已无 Key，A 也不能把旧摘要重新创建出来。Redis TTL 到期与用户主动清除不是一回事：前者可按授权重建，后者按保留/删除语义处理。

### 4.2 成对消息、摘要顺序和计数

`recentSummaries` 约定按消息顺序升序保存，构建 Prompt 时取最后 N 条并保持顺序。如果从下标 0 取 3 条，若输入为 5 条升序摘要，实际取到的是较早 3 条。

用户消息和助手消息以来源 ID 与角色关联，不能按数组下标奇偶恢复角色；多条用户消息、工具结果和部分回复都会破坏交替假设。`messageCount` 若需要准确，应从持久化事件计算或幂等更新；只在用户消息时递增的计数，表示用户消息数，而不是全部消息数。

## 5. 与模型客户端的边界

会话服务通过模型客户端提炼资料，无需承担 HTTP 传输、连接池或供应商 API 适配。使用 Spring AI 等框架时，依赖与 API 写法应对应同一版本。客户端可以围绕以下职责封装：

| 能力 | 本项目需要的行为 |
| --- | --- |
| 普通/多轮调用 | 接收结构化角色消息，返回内容、usage、模型标识及请求 ID；历史角色来自记录 |
| 结构化提炼 | 解析成功后继续做业务校验；对象反序列化不证明内容真实 |
| 流式输出 | 区分片段、完成、失败和取消；返回可管理的订阅/取消句柄 |
| 异步或批量调用 | 使用有界执行器和统一截止时间；并发多次调用不等于上游批量 API，也不减少调用次数 |
| 缓存 | 绑定租户策略、模型、模板与来源版本；禁止只凭 Prompt 字符串跨权限复用 |
| 重试与限流 | 区分可重试故障与非法输入，限制总尝试、等待和预算；记录限流及降级 |
| 连接池与指标 | 验证配置确实注入所用客户端；usage 用实际返回值，日志不打印完整原文 |

默认代理模式下，`batchChat` 使用 `this::chatAsync` 不会因 `@Async` 自动并行。`1000 * retries` 是线性等待，不是指数退避。配置文件也不能重复定义多个顶层 `spring` 再假设全部生效。异步语义依据 [Spring 官方说明](https://docs.spring.io/spring-framework/reference/integration/scheduling.html)，具体 SDK 兼容性仍需在实施版本编译。

Tool Calling、RAG 和模板参数化是上层能力，不属于摘要存储服务。工具执行归医生助手方案；检索证据交给 [[动态Prompt构建方案]]，不能直接提升成可信 system 指令。上下文预算、短消息处理策略和 temperature 应根据任务质量、延迟与成本选择，不宜套用统一阈值。

## 6. 用边界场景检查摘要设计

以下场景适合用于理解摘要覆盖范围、版本条件和失败处理之间的关系：

| 场景 | 断言 |
| --- | --- |
| 摘要滞后两条消息，用户立即追问 | 本轮输入包含未覆盖原文，当前消息只出现一次 |
| 两个提炼任务反序完成 | 覆盖位置不倒退，旧基线结果不覆盖新版本 |
| 清空会话后旧任务返回 | epoch 不匹配，不能重新创建旧会话摘要 |
| 同一消息重复投递 | 不重复追加摘要、不重复累计计数 |
| 包含否定、纠正和单位的数据 | 保留来源与不确定状态，不将陈旧测量当成最新事实 |
| 模型超时或返回非法 JSON | 保留原文、显式失败或降级，不声称提炼完成 |

任务双版本的教学实验见 [[Agent（智能体）#5.2 最小可运行实验：旧结果、重复回调与草稿版本]]。可以先观察内存模型中的状态转换，再把相同条件映射到数据库条件更新和消息水位管理。

## 7. 两端会话隔离与轮次排序

统一系统将患者对话与医生内部讨论放在不同 groupId，并记录 audience/visibility。医生工具轨迹、内部报告和审批意见不作为患者摘要来源；后处理任务从来源记录重新检查可见范围，不能仅相信消息携带的患者ID。运行与审批状态独立保存在 agent_run/approval/action_execution，见 [[医生助手Agent开发方案]]。

首期每个会话一次只运行一个生成轮次。接收时先在 chat_turn 持久化排队内容；取得运行资格后，才在短事务中分配 chat_message.seq 并插入用户消息。回复使用 reply_to 绑定请求，回复提交或明确失败后才处理下一轮；这样排队请求不会提前进入当前轮次的摘要和Prompt。

分配 seq、插入消息和更新会话 next_seq 在同一事务中完成。失败后重试使用原turnId；用户消息已存在则不重复分配。摘要只覆盖已提交消息；被删除的来源保留可识别位置/墓碑并触发摘要重建，不能把缺口当作没有内容。若原文按保留策略已不可读，则明确历史不完整，不能宣称能无损重建。

后台提炼不能把模型报告中的推测二次总结成患者事实；sourceRole、confirmationStatus 和sourceVersion贯穿摘要。清空会话推进epoch并使旧任务失效；需要删除跨会话记忆时另外执行明确删除操作。摘要中包含已撤回来源时，在重建完成前不得继续作为有效事实提供。
