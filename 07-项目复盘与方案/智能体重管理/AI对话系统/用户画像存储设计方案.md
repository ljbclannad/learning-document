# 用户画像存储设计方案

本文以 MySQL 保存画像事实、Redis 提供读缓存为例，讲解数据模型、回源、更新与一致性边界。重点是理解缓存为什么可能返回旧值，以及不同方案如何处理这些窗口。

## 1. 画像的职责与事实来源

画像承载相对稳定、具有来源的用户属性，例如用户确认的偏好、业务系统维护的目标、经授权读取的资料。每轮话题、待回答问题和摘要归 [[会话上下文设计方案]]；相似历史资料的召回归 [[千问Embedding+Milvus向量搜索集成文档]]；哪些字段送入模型归 [[动态Prompt构建方案]]。

模型从消息中提取出的信息先作为候选，保存来源消息、发生时间和确认状态，不能直接覆盖权威画像。用户自述、业务记录、模型推断需要区分；缺失值不能填为“没有疾病”或“正常”。本文不定义临床判断规则。

推荐由 MySQL 保存可恢复的画像事实，Redis 提供可丢弃、可重建的读缓存。交互计数等统计字段另设更新链路，不以“只更新 Redis、以后同步”的 TODO 承诺持久化。

## 2. 数据模型与缓存契约

可以用以下字段表达画像的数据契约：

| 字段 | 含义与约束 |
| --- | --- |
| `tenantId / customerId` | 由认证和业务授权确定的资源范围，不能只信任请求参数 |
| `profileVersion` | 数据库内单调递增的业务版本；所有更新路径遵守同一规则 |
| `schemaVersion` | 缓存序列化结构版本，与业务版本区分 |
| `source / sourceId / observedAt` | 字段来源、来源记录及发生时间 |
| `confirmationStatus` | 已确认、用户自述或待核实，不通过字符串内容猜测 |
| `updatedAt` | 运维时间信息；不能代替并发版本条件 |

缓存键示意：`ai:profile:{tenantId}:{customerId}`。缓存值必须能判断是否完整，不能因为 Hash 非空就认为画像已加载。状态至少区分 `FOUND`、`NOT_FOUND` 和 `UNAVAILABLE`：数据库异常与不存在用户不是同一种情况，不能都返回 `null` 并创建空值缓存。

### 2.1 Hash 与 JSON 如何选

Hash 适合有明确字段契约的局部读取/更新；JSON String 适合整体快照和嵌套结构。本系统最终常常需要读取多项画像，若主要是全量读写，不能仅因 Hash 支持字段操作就认定其更省网络或内存。内存差异取决于字段数量、值长度、序列化方式和 Redis 编码，需要在同一数据集下比较。

多个 String Key 可以通过受约束的事务或脚本协调，不能概括为“无法原子操作”；Hash 的单次字段写也不自动让数据库提交、缓存写和 TTL 成为一个事务。采用 Hash 时，更新字段、版本和必要的 TTL 应在同一个缓存原子操作中完成；Redis Cluster 下相关键的布局要匹配原子操作范围。

数组字段使用明确的 JSON 编码，不用逗号拼接，否则带逗号的偏好会被错误拆分。空整数不能序列化为字符串 `"null"` 后再 `parseInt`。字段白名单、空值策略和 schema 迁移必须作为读写契约。

## 3. 读取链路：命中、回源和降级

以下是接口无关伪代码，不是可直接运行的 Java 服务：

```text
readProfile(auth, customerId):
    scope = authorize(auth, customerId)
    cached = readCache(scope)
    if cached 是当前 schema 的完整快照:
        return FOUND(cached)
    if cached 是有效的“不存在”快照:
        return NOT_FOUND

    在有界等待内尝试取得回源资格
    若未取得：短暂重读缓存；按限流策略回源或返回 UNAVAILABLE
    若取得：再次查完整缓存，再查数据库
        数据库无记录 → 写短期 NOT_FOUND（排除并发新建窗口后）
        数据库有记录 → 按版本发布完整快照及 TTL
        数据库异常 → UNAVAILABLE，不缓存成 NOT_FOUND
    仅释放自己仍持有的回源资格
```

回源锁主要减少重复查询，不是业务一致性证明。固定租约到期后旧查询仍可能返回；解锁前核验持有者只防止误释放别人的锁，不能阻止旧结果覆盖新画像。

如果 `tryLock(3, 10, SECONDS)` 失败就直接查库，会让所有等待者继续冲击数据库；取得锁后只查正缓存、不查负缓存，也可能重复查不存在记录。等待、回源并发数和降级必须有上界。

### 3.1 空值缓存与新建用户

如果先查独立 `ai:profile:null:*` 再查 Hash：负缓存尚未失效时，即使已有新画像，也会返回不存在。新建、恢复用户和画像更新都需使负缓存失效；更稳妥的设计是以同一版本化缓存载体表达 FOUND/NOT_FOUND，避免两个 Key 相互遮挡。即便这样，数据库与缓存之间的失效失败仍需重试或允许短期过期，不能声称强一致。

### 3.2 雪崩和 Redis 故障

随机 TTL 只打散集中到期，无法解决 Redis 整体不可用。例如，正缓存 24 小时 ±10%、负缓存 5 分钟可用于说明不同生命周期；画像新鲜度和变更频率决定 TTL，而非固定模板。布隆过滤器、多级缓存和永不过期策略适用于不同规模与访问模式；永不过期还需刷新和容量治理。

Redis 故障时可从 MySQL 重建的前提，是事实确已持久化且数据库承受得住受限回源。只在 Redis 累加的统计、未落库的偏好无法靠重建找回。

## 4. 更新链路与旧值回填窗口

推荐最小基线：在数据库事务中校验资源归属和 `profileVersion`，提交画像变更及失效事件；提交后执行缓存失效，失败由持久化任务补偿。可靠交付原理参见 [[RabbitMQ与Outbox可靠消息方案]]。

这能避免未提交数据先进入缓存，但**删除缓存仍不是强一致保证**：

```text
R 读取数据库 v7，暂未回填
W 提交数据库 v8，删除缓存
R 回填 v7；此时缓存不存在，简单“只与缓存版本比较”也会放行
后续请求读到 v7，直到过期或再次失效
```

可按实际要求选择：

- **允许有界陈旧**：明确最大 TTL、新鲜度标记和失效补偿；对关键动作再读权威来源。
- **需要更严格读写约束**：保存不会随值删除而丢失的更新水位/墓碑，发布快照时校验版本；还要覆盖墓碑丢失、缓存重启和所有写入路径。仅增加一个版本字段不足以完成这些约束。
- **必须读到本次提交后的事实**：写入返回版本，后续读取要求不低于该版本；缓存不足则读数据库或等待，失败应显式返回。

### 4.1 局部更新、统计与输入边界

动态 SQL 使用 `${field}` 时，字段名不能直接来自调用方；应映射到固定白名单 SQL。更新条件至少包含租户、用户和预期版本，并检查受影响行数。服务与 Mapper 应统一字段白名单、版本条件和更新时间的参数契约。

“先判断 Key 存在，再 HSET”之间 Key 可能过期，导致只包含一个字段的残缺 Hash；`HINCRBY` 对不存在 Key 同样可能创建仅有计数的 Hash，下一次 `entries` 非空便被当成完整画像。统计单独存储，或通过原子完整性校验后更新，不让计数操作创建画像快照。

若计数要求精确，使用稳定事件 ID 与数据库幂等记录；若允许近似，明确允许丢失的窗口。异步批量同步需要持久化事件、幂等合并和重试机制；仅在内存中累计无法覆盖进程退出。

## 5. 常见实现误区

将读取、更新和恢复连起来看，下面这些局部写法容易产生与预期不同的行为：

| 写法 | 容易产生的误解 | 正确处理 |
| --- | --- | --- |
| Hash `putAll` 后独立 `expire` | 写完必有 TTL | 原子发布或可恢复的过期补偿 |
| `updateById` 后立即写缓存 | 数据库与 Redis 同时成功 | 提交后失效、补偿及明确陈旧边界 |
| 宽泛 catch 后 `return null` | 异常等于用户不存在 | 使用区分错误与空结果的返回契约 |
| 字段日志输出 value、健康目标 | 调试日志可直接进入生产 | 只记录操作、版本和错误码，敏感内容最小化 |
| 正缓存、负缓存、计数共用隐含假设 | 任意非空数据都是完整画像 | 统一 schema、完整性与生命周期规则 |

## 6. 用故障时序理解一致性

可以在隔离环境中控制以下执行顺序，观察数据库与缓存的最终状态：

| 输入或故障时序 | 必须观察的结果 |
| --- | --- |
| 新建用户与旧负缓存并存 | 在约定新鲜度内可读取新版本，不能长期被负缓存遮挡 |
| 缓存过期后先执行计数 | 不产生可被当作完整画像的残缺 Hash |
| R 读旧值 → W 提交并失效 → R 回填 | 满足所选陈旧边界；严格模式拒绝旧回填 |
| Redis 不可用、大量请求同时回源 | 数据库并发受限，错误不伪装成 NOT_FOUND |
| 同一画像版本并发修改 | 至多一个条件更新成功，冲突能被调用方识别 |
| 空年龄、列表项包含逗号 | 编解码往返不丢字段、不抛错误的整数解析异常 |

实验时记录初始数据、并发执行顺序、数据库与缓存版本以及返回状态，比较观察结果是否符合所选的一致性边界。性能测量方法见 [[AI消息数据流性能分析]]。

## 7. 与医生任务共享画像的契约

两端通过统一 EvidenceService 读取画像，不再另写一套仅按 customerId 缓存的 PatientDataService。统一架构见 [[医生助手Agent开发方案]]。画像仍是事实/来源记录，医生内部分析另存草稿或报告，不能写回患者偏好或权威诊断字段。

缓存可以保存租户内受控的完整内部快照，但返回前必须按 actor、purpose、audience 做字段裁剪；若缓存已经裁剪的视图，缓存键还需包含可见字段策略版本与权限范围。不能把医生可见字段随共享缓存返回给患者。

`readProfile(scope, minProfileVersion)` 需明确最小版本要求。普通对话可在声明的新鲜度范围使用缓存；用户刚纠正资料时携带服务端返回的新版本，审核或动作执行前回查权威来源。返回低于最小版本的缓存不能算成功，数据库不可用时返回 UNAVAILABLE。

画像修正事务推进 profileVersion 并保存派生数据失效事件；摘要、记忆、报告的来源清单可据此重建或标记过期。失效通知可能滞后，所以关键提交仍直接核验当前来源版本，不仅等待事件将草稿标红。测试用“用户更正v8，旧v7回填，医生批准v7草稿”的时序验证：普通读取符合陈旧边界，审批必须被拒绝。
