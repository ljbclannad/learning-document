# 千问Embedding + Milvus向量搜索集成文档

本文以千问 Embedding 与 Milvus 为例，讲解记忆原文、向量索引和检索结果之间的关系，重点分析检索状态、版本演进与跨存储一致性。

## 1. 检索层的边界

输入是经过授权的用户范围、当前消息和会话快照；输出是可回查的证据及检索状态。摘要由 [[会话上下文设计方案]] 维护，最终模型输入由 [[动态Prompt构建方案]] 组织，任务交付与补偿由 [[AI消息后处理异步方案]] 负责。检索服务不自行生成欢迎词，也不把失败转换为“首次对话”。

三份数据各有职责：

| 存储 | 保存什么 | 不能承担什么 |
| --- | --- | --- |
| MySQL | 记忆原文、来源消息、租户/用户归属、版本、删除状态 | 不能仅因原文已提交，就认为向量可检索 |
| Milvus | 向量、原文 ID/版本及过滤字段 | 不是原文权限和有效状态的最终依据 |
| Redis（可选） | 热点结果或辅助时间索引 | 不能替代记忆原文，也不应成为唯一恢复来源 |

`Memory` 是带来源的候选资料，不是确认无误的长期事实。模型回复、用户自述和审核资料需要保留角色；不能直接把用户问题与模型答案拼接后全当成用户事实。固定返回的年龄和疾病只能作为测试桩，信息提取需要关联实际来源消息。

## 2. 向量生成契约

### 2.1 模型、维度与输入类型

本文以 `text-embedding-v3`、1024 维为例。实际可用模型、地域和端点以实施环境为准。DashScope 接口支持在 `parameters` 中指定 `text_type` 和 `dimension`；检索查询使用 query，底库文本使用 document。参考 [千问文本向量接口](https://help.aliyun.com/zh/model-studio/text-embedding-synchronous-api)（2026-10-29 核对）。

请求体示意，发送地址和密钥从部署配置读取，不在正文硬编码真实凭据：

```json
{
  "model": "text-embedding-v3",
  "input": {"texts": ["整理用户昨日的活动记录"]},
  "parameters": {"text_type": "query", "dimension": 1024}
}
```

底库写入应对**实际保存的片段**生成 document 向量。不能把“话题 + 当前问题”的 query 向量直接当作“问题 + 回答”的文档向量；文本和生成方式都不同。

将 `model / dimension / textType / normalization / chunkVersion` 作为向量空间契约。响应需检查 HTTP 与业务状态、条数、文本对应关系、维度和数值有限性；服务返回异常、空数组或错误维度时显式失败，不生成零向量补位。

`dimension` 必须传入请求，`timeout` 必须配置到实际使用的 HTTP 客户端。可以捕获请求体并模拟慢响应，观察维度参数和超时是否按预期生效。

### 2.2 缓存、批量与模型迁移

向量缓存至少绑定授权隔离范围、模型及版本、维度、query/document、预处理规则和文本摘要哈希；不要把患者原文直接放缓存键。批量请求需要按返回的输入索引匹配结果，不能假定任意客户端都保持原顺序。批量上限、限流和收费必须按实施时 API 确认。

更换模型、维度或文本切分规则时，建立新索引版本并重建向量；同为 1024 维也不保证两个模型的向量可混搜。切换前使用固定查询集比较召回、权限过滤、延迟与成本，保留旧集合直到在途请求和回滚窗口处理完毕。

## 3. Milvus 集合与检索路径

### 3.1 集合结构和启动检查

建议包含 `memory_id`、`tenant_id`、`customer_id`、`memory_version`、`embedding`、`created_at` 和索引代次。需要按会话检索时增加业务会话字段；若允许跨会话长期记忆，应明确用户授权范围，不默认所有记录都跨会话可见。

若 `hasCollection == true` 就立即返回，会跳过索引、加载状态与 Schema 检查。正确的就绪判断至少覆盖：服务连接成功、集合 Schema/维度匹配、预期索引可用、集合可搜索。非零状态应使初始化失败或进入显式降级，不只是记录日志继续启动。

加载、搜索参数与过滤方式可参考 [Milvus 2.4 单向量搜索文档](https://milvus.io/docs/v2.4.x/single-vector-search.md)。不同版本的 SDK 接口可能变化，选择示例时需同时匹配服务端、SDK、Spring Boot、Java 和 HTTP 客户端版本。

### 3.2 一次召回的完整步骤

```text
1. 核验租户、用户及业务会话范围
2. 从当前消息和仍有效的摘要字段构造查询文本
3. 生成 query 向量，校验向量空间契约
4. 按授权过滤表达式搜索，取得 memoryId、version、score 与排名
5. 回查 MySQL：再次过滤租户、用户、删除/撤回状态、当前版本
6. 按召回排名重建结果，保留来源与时间
7. 返回 FOUND / EMPTY / UNAVAILABLE 及原因，交给 Prompt 构建器
```

过滤参数不能直接把任意 `customerId` 拼成表达式；优先使用选定 SDK 支持的安全参数机制，或对内部生成的 ID 做严格白名单/转义。租户范围来自认证服务，不能由用户消息指定。

`selectBatchIds(memoryIds)` 只按 ID 回查，不能替代资源校验，也不保证按输入 ID 的顺序返回。回查后必须重新验证并按原排名排序。检索到已删除/旧版本片段时丢弃并触发修复；不能只信任向量库中的过滤字段。

### 3.3 相似度、阈值与缺失状态

例如，`COSINE + IVF_FLAT + nlist=1024 + nprobe=10 + score>=0.7` 仅是候选组合，不是最佳参数。索引与搜索的度量一致；相似度分数不是“正确概率”。阈值需要在带相关性标注的数据集上比较召回和误召，HNSW 也应使用同一指标与预算评估。

| 返回状态 | 判定 | 上层应如何使用 |
| --- | --- | --- |
| FOUND | 服务正常、回查校验后仍有证据 | 带 ID、时间、版本和排名使用 |
| EMPTY | 服务正常，但当前查询/权限/阈值下没有证据 | 只说明本次未命中，不能断言无历史或首次对话 |
| UNAVAILABLE | 向量服务、数据库、超时或解析失败 | 显式降级；需要完整证据的任务暂停或报错 |

如果候选只部分回查成功，结果还要有完整性标记及原因；不能把部分缺失静默归为完整 FOUND。真正的首次使用由业务账户/消息记录判定，不由 `List.isEmpty()` 判定。

如果 `searchSimilarVectors`、`retrieveRelevantMemories` 在 catch 后返回空列表，上层就无法区分熔断、超时和无命中，还可能错误生成首次用户提示。让正常路径与降级路径共享同一个结果类型，才能完整传递这些状态。

## 4. 写入、更新与删除：索引是派生数据

### 4.1 推荐交付边界

```text
事务一：保存记忆原文及版本 + 待建索引任务
  → 提交后返回“原文已保存、索引待同步”
后台：取得任务 → 读取指定版本原文 → document Embedding → 写入对应索引
  → 确认外部响应 → 条件更新同步状态
```

这与前台“回复与后处理任务一起落库”是不同层次：对话轮次任务负责从原文中产生记忆候选，索引任务负责将已持久化的记忆版本投影到 Milvus。应用可以复用同一任务框架，但要避免两条链路都创建同一记忆。身份建议为 `(tenantId, turnId, candidateKey)` 和 `(memoryId, memoryVersion, indexGeneration)`。

Embedding 和 Milvus 网络调用不应包在长数据库事务中。数据库事务可以原子保存原文和任务，不能回滚已经写到 Milvus 的数据；MySQL、Redis、Milvus 的连续三次调用不是跨存储事务。

### 4.2 重试和旧索引隔离

“同一个主键 insert 多次”是否幂等，取决于 SDK 和服务端的写入语义。应明确重复写入的处理规则，并用版本化投影标识避免旧任务覆盖新版本；必要时将 `memoryId + memoryVersion + indexGeneration` 编入外部主键，回查时只接纳当前有效版本。

```text
原文 v1 的任务慢；用户纠正后提交 v2，v2 索引先完成
v1 后完成：可以留下待清理的旧投影，但不得成为当前有效证据
读路径回查原文当前版本，拒绝 v1；清理任务再移除旧投影
```

删除先记录权威删除状态及删除任务，回查即刻拒绝使用已撤回资料；异步清理向量和可选 Redis 索引。旧插入迟到、删除结果不明、缓存结果尚未失效都需覆盖。若业务要求外部物理删除在截止时间内完成，还要单独记录清理确认，不能只把逻辑不可见当成完成删除。

## 5. Outbox 同步中的失败窗口

通用事务消息解释归 [[RabbitMQ与Outbox可靠消息方案]]，任务运行与人工恢复归 [[AI消息后处理异步方案]]。本节聚焦向量同步中的状态迁移、领取和补偿边界。

| 写法或场景 | 问题 | 处理方式 |
| --- | --- | --- |
| Milvus 返回非零状态只写日志 | 上层仍把 Outbox 标为 SUCCESS | 任何失败或结果不明都必须传播为非成功状态 |
| `@Version` 注解即称“已锁定” | 缺少插件与 SQL 条件证据 | 检查实际条件更新及行数，只有合法状态能被领取 |
| `processPendingOutboxes` 内调用事务方法 | 默认代理下同类调用绕过事务入口 | 独立事务服务或显式事务边界，并验证提交时点 |
| PROCESSING 后宕机 | 原扫描仅选 PENDING/FAILED，缺少过期领取回收 | 短事务领取、租约和 attempt token；旧 worker 不能提交新 attempt 结果 |
| 失败处理捕获后正常返回 | 通知会被标为 processed，容易误当业务完成 | 通知只是唤醒提示，真实状态由任务表维护并定时扫描 |
| 达到 max_retry 后仍是 PENDING | 扫描条件排除它，可能永远悬挂 | 在达到上限时明确转 MANUAL/DEAD 并告警 |
| 解析错误标 FAILED，计数未推进 | 原扫描仍可反复选中 | 不可重试错误进入终态，人工修改后另建恢复动作 |
| 触发器写通知表 | 只是同事务增加数据库行，不是主动推送 | 通知表 + 扫描是可选设计；直接扫任务表也可，需比较维护成本 |

触发器不能代替幂等、领取与恢复。回滚代码也不会回滚已写到外部系统的投影；应先停止新任务、核对在途状态和兼容版本，再决定回退。不能直接删触发器后恢复旧双写，任由现存任务无人处理。

## 6. 客户端、容错与监控属于实施配置

连接池、密钥配置、限流、熔断和监控分别解决资源复用、凭据管理、负载保护与可观测性问题。`RestTemplate` 若在字段初始化时创建，就不是每次调用都 new；是否复用连接取决于 request factory，性能收益应通过同负载对比测量。

密钥从部署注入，启动时校验缺失；连接、读取和连接池等待分别设置超时，并受整个请求截止时间约束。模型 query 与 document 两条路径都应接入相同治理，不能只给查询方法加注解。限流与熔断不自动提供业务重试；重试是否发生需显式实现并记录次数。

Sentinel 规则需要区分异常比例与异常数：[Sentinel 1.8.6 常量源码](https://raw.githubusercontent.com/alibaba/Sentinel/1.8.6/sentinel-core/src/main/java/com/alibaba/csp/sentinel/slots/block/RuleConstant.java)中异常比例为 1、异常数为 2。规则、注解与 Nacos 的绑定需按选定版本验证后再启用。阈值应根据故障恢复要求和实际流量选择。`SimpleMeterRegistry` 只能证明内存指标对象存在，不能证明 Prometheus 端点已暴露或已采集。

监控区分 Embedding 失败、搜索失败、无命中、回查过滤、索引待同步、最老未完成任务年龄、人工待处理及索引版本分布。模型输入和健康资料不得直接写普通日志。延迟与费用的口径统一见 [[AI消息数据流性能分析]]。

## 7. 通过故障实验理解检索一致性

围绕以下故障设置执行屏障，对比原文状态、索引状态与检索返回值，可以观察跨存储一致性由哪些约束维持。

| 用例 | 预期行为 |
| --- | --- |
| 错误维度、NaN、空向量或上游超时 | 明确失败，不写索引，不返回 EMPTY |
| 其他租户或已撤回片段进入候选 | 回查后不能出现在模型输入中 |
| 数据库原文提交后 Milvus 故障 | 原文可查、任务待重试，状态不能是索引成功 |
| 外部写入成功后状态提交失败 | 重试不生成逻辑重复证据，结果可查证 |
| 原文 v2 已生效、v1 任务迟到 | 旧投影不成为当前证据 |
| 删除后旧插入任务继续运行 | 读路径仍拒绝已删除原文，清理可重试 |
| 领取后进程退出 | 任务能重新领取，旧 attempt 结果不能覆盖新状态 |
| 模型或索引参数变更 | 固定查询集记录 Recall@K、误召率和端到端延迟 |

实验时固定服务端/SDK版本、数据规模与索引配置，观察故障前后的原文、任务和向量状态。健康检查成功只代表对应探针条件成立，业务一致性需要沿整条写入与读取链路判断。

## 8. 个人记忆、业务资料与知识库分开检索

统一 EvidenceService 可以聚合多个检索源，但不能共用一个隐含“都是可信资料”的结果集合。个人记忆绑定租户、患者与来源可见范围；医生内部报告只对获授权医生可见；知识库条目另带 corpusId、documentVersion、reviewStatus、effectiveAt 和适用范围。首期不启用跨患者 search_similar_cases，原13个工具清单不代表授权范围，见 [[医生助手Agent开发方案#5.3 工具能力路线图]]。

候选过滤包含语料域与可见范围，回查仍验证原文的当前权限和版本；检索个人消息的授权不能自动扩大为查看其他患者病例。原文没有明确授权/审核状态时，不因向量相似度较高就成为医生决策证据。

记忆写入前冻结候选集合：第一次提取结果成功提交后，以 `(tenantId, turnId, candidateKey)` 保存，重试读同一集合；不能每次重新让模型抽取再生成不同candidateKey。索引任务只投影这份已保存版本，不能反过来把检索到的模型回答写成已确认用户事实。

EvidenceSnapshot记录每个语料源的 FOUND/EMPTY/UNAVAILABLE 和complete。知识库正常但个人记忆故障时，不能合并成一个完整FOUND；医生任务根据必需来源策略选择等待或明确缺失。删除来源先阻止读取，并使依赖摘要和报告失效，再异步清理向量；物理删除期限和确认单独追踪。
