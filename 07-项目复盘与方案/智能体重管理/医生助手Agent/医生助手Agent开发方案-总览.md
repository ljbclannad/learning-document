## 系统要交付什么

患者端完成持续对话与个人记录整理；医生端在授权范围内查询资料，生成可回查证据的报告和回复草稿。首期审核草稿但不自动发送，正式处方和诊断流程不在首期范围内。

一次资料更新能被两端一致解释：用户自述与业务权威资料分开，摘要或索引落后有状态，旧资料生成的草稿不能继续批准，医生私有意见不能流入患者记忆。统一的是基础契约，入口、用途和内容权限分别管理。

## 本轮形成的关键决策

- 一个 EvidenceService 和 PromptBuilder 支持患者/医生两种模式；数据源、来源版本、完整性和可见范围统一表达。
- 固定业务工作流包围有限工具循环；工具只能通过统一授权执行入口调用。
- 请求、轮次、任务、调用、动作、重试各有独立身份；traceId 不作幂等键。
- 对话消息按运行顺序进入日志，摘要按连续水位提交；排队内容和医生私有内容不提前注入患者输入。
- 草稿审核、动作批准、动作成功是三件事；副作用超时保留 UNKNOWN 并查证。
- 先实现患者闭环与医生只读草稿，再逐个启用具有资源端幂等能力的动作。

## 实施顺序与责任

依次完成契约及构建基线、患者链路、医生只读草稿、单个业务动作、实测优化。每阶段按故障与质量门槛验收，不以“写完13个工具”作为上线条件。

产品/业务审核者确认用途、规则和质量标准；后端落地授权、表约束与状态迁移；前端展示版本、审批和真实进度；测试覆盖并发、故障及模型质量；运维接手配额、恢复与告警。实际人力和周期在完成版本锁定及外部接口能力核查后评估。

候选技术方向沿用 Java 17 / Spring Boot 3.x、MySQL、Redis；RabbitMQ 与 Milvus 随功能启用。模型与SDK通过适配器及配置锁定，不由文档中的历史型号决定部署。
