# 减重管理 Agent 设计思路

> 本文记录设计思路，不是已实现功能的证明。能力状态见 [[医生助手Agent开发方案-总览#能力状态与证据边界]]；项目总结应区分设计、示例与已验收功能。

## 1. 先定义这个 Agent 要解决什么问题

我在设计这个 Agent 的时候，第一步不是先想模型选型，而是先想清楚它到底要解决什么业务问题。

在减重管理场景里，我希望它解决的核心问题主要有几个：

- 帮助判断患者当前减重进展是否符合预期
- 识别减重停滞期、依从性下降、情绪波动、复胖风险等问题
- 整合体重、聊天、随访、知识库等多源信息，**减少人工判断成本**
- 自动生成结构化、可追溯、可审计的随访建议
- 辅助医生或健康管理师完成周期性随访，而不是只做一个问答机器人

## 2. 再反推这个 Agent 需要什么能力

目标明确之后，我会反推它需要哪些能力支撑。

我认为一个减重管理 Agent 至少要有这些能力：

- 能理解用户问题、减重诉求和当前所处阶段
- 能读取并整合体重、饮食、运动、历史随访等上下文信息
- 能调用知识库，补充减重相关知识和标准化管理建议
- 能调用外部工具或业务系统，比如随访系统、档案系统、指标查询接口
- 能识别异常信号，比如减重停滞、执行力下降、情绪波动
- 能按既定规则输出结构化结论和下一步建议

## 3. 工作流上不能完全靠模型自由发挥

我在做这类 Agent 时，一个很重要的判断是：`不能把它设计成纯聊天模式`。

因为减重管理不是开放闲聊，而是一个目标明确、风险敏感、需要稳定输出的场景。所以我更倾向于把它做成流程驱动的 Agent。

我的思路一般是：

1. 先识别用户当前意图，判断是日常咨询、阶段随访，还是风险预警场景
2. 再拉取相关上下文，包括体重变化、聊天记录、历史随访、知识库信息
3. 然后基于这些信息判断减重进展是否达标，是否存在潜在风险因素
4. 最后生成回答、结构化建议，或者提示需要人工介入

这一步其实决定了整个 Agent 是否稳定、是否可控。

## 4. 边界和安全是设计重点

在这个项目里，我会把边界和安全放得很前，因为健康管理类 Agent 最怕的就是乱给建议、越界决策。

所以我会先定义清楚：

- 它能做什么，比如生活方式建议、减重知识解释、随访建议生成
- 它不能做什么，比如直接替代医生下诊断、调整药物方案
- 哪些情况必须转人工或建议线下就医，比如明显不适、情绪异常、快速反弹
- 它输出的建议是不是要保留证据来源和规则依据，保证后续可追溯、可审计

对这类场景来说，这部分很多时候比模型本身更重要。

## 5. 真正落地时还要考虑工程化

如果只是 Demo，做到能回答问题就差不多了；但如果真要上线，我会把它当成一个完整系统来设计。

这里面通常会补齐几块：

- Prompt 管理，避免逻辑散落在代码里
- RAG / 知识库，保证回答有依据
- Tool Calling，让 Agent 能和业务系统联动
- 会话记忆，支持连续随访
- 多源数据整合，把体重、聊天、随访记录串起来
- 评测集，用来验证效果是否稳定
- 日志与可观测性，方便排查问题
- 合规与脱敏，保证数据使用安全

## 6. 最后一定要做 e2e 测试验证

我会把 e2e 测试看得比较重，因为 Agent 不是单模块产品，很多问题都出在模块组合之后。

对我来说，e2e 测试验证的核心就是：

`用接近真实用户场景的方式，验证 Agent 从输入到输出的整条链路是否正确、稳定、可控。`

在这个减重管理 Agent 里，我会重点验证：

- 用户问题和随访意图能不能识别正确
- 体重、聊天、随访、知识库等多源信息能不能整合正确
- 工具调用是不是成功，返回结果是不是可信
- 对减重进展、停滞期、依从性下降、情绪波动等风险判断是不是符合预期
- 最终建议是不是准确、完整、结构化，并且具备可执行性
- 遇到高风险情况时，能不能正确触发安全边界，而不是继续自由回答

## 7. 项目总结表达

如果要把这个项目用一句话概括，我会这样说：

`我设计的减重管理 Agent，计划围绕随访目标整合多源资料、整理风险线索并生成供专业人员核对的结构化建议；可追溯、审计和安全执行是待实现与验收的工程要求。`
