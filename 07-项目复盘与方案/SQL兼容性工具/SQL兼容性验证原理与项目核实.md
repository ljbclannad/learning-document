## 2. 通用原理：先定义“兼容”

### 2.1 成功执行只是第一层

一条 SQL 可以在目标库运行，却返回不同的行、不同的数值或不同的列类型。需要区分以下验证对象：

| 层次 | 观察对象 | 通过后仍不能证明什么 |
| --- | --- | --- |
| 解析与执行 | 是否能绑定参数并完成执行 | 结果含义相同 |
| 结果语义 | 列、值、重复次数、必要的顺序 | 应用对象映射正确 |
| JDBC 与框架集成 | JDBC 类型、TypeHandler、ResultMap、生成主键 | 所有业务流程正确 |
| 写入效果 | 修改了哪些记录、哪些字段及关联数据 | 提交阶段和并发行为一致 |
| 事务与并发 | 隔离、锁等待、回滚、约束检查时机 | 性能达到要求 |
| 性能 | 指定负载下的延迟、吞吐和资源 | 所有输入都兼容 |

若工具取出 SQL 后直接走 JDBC，就不能仅凭通过报告声称验证了应用中的完整 MyBatis 映射链。只执行后回滚的 DML 测试，也不能覆盖提交时才出现的约束检查或提交后行为。

### 2.2 一个结论需要绑定上下文

可以把一次用例表示为：

```text
C = 语句身份 + SQL 形态 + 参数及类型 + 数据基线 + 环境配置 + 比较规则
源结果 = 在源环境中执行 C
目标结果 = 在目标环境中执行 C
比较结论 = 按预先约定的规则比较源结果与目标结果
```

同参数不等于同实验。两侧表数据、时区、字符排序规则或默认 Schema 不同，都会让差异混入配置和数据因素。正确表述是“在这些条件和输入下没有发现差异”，而非“整个项目已完全兼容”。

数据库迁移还有两种测试目标，必须先选定：

- **原 SQL 可移植性**：两侧执行相同 SQL，检测是否需要改写。
- **迁移后语义等价性**：源侧原 SQL 与目标侧改写 SQL 配对执行，验证改写后是否保持语义。

第二种需要保留改写前后文本、映射关系和规则版本。不能把工具自动修正 SQL 后的通过率当成“原 SQL 直接兼容率”。

## 3. 通用原理：三阶段解耦与可复现产物

阶段独立的价值是保留因果关系：参数有问题时可以重新生成参数，比较规则有问题时可以重新比较已保存结果，不必重新扫描整个项目。

| 阶段 | 输入 | 建议保留的输出 | 主要失败类别 |
| --- | --- | --- | --- |
| 提取 | 项目资源、依赖、框架配置 | 语句清单、来源、命令类型、SQL 形态、未覆盖原因 | 资源缺失、框架启动失败、不支持的生成方式 |
| 参数准备 | 语句信息、显式参数、采样规则 | 参数清单、类型、分支、采样依据、固定值 | 缺参数、约束冲突、无有效样本 |
| 双库验证 | 前两阶段产物、环境、比较策略 | 执行状态、原始结果摘要、差异、回滚与恢复状态 | 执行异常、结果差异、基线不可比、恢复未知 |

这些输出是**建议设计，不是现有工具字段**。至少让 `statementId`、`caseId` 和本次 `runId` 可关联；重试应有独立尝试身份。源码位置、SQL 内容摘要和配置版本能够帮助识别“同名方法已经换了实现”。

固定参数应保存解析后的实际值和类型，只有随机种子不足以稳定重放，因为数据源内容、算法和依赖都可能变化。报告应记录脱敏后的环境标识与版本，不输出密码或完整敏感数据。

**待代码核实：**三个阶段是否真能从文件或明确接口独立启动；中间产物是否有版本；修改 SQL 后能否识别旧参数清单；失败项是否仍留在报告中。

## 4. 通用原理：SQL 提取与动态覆盖

### 4.1 源码模板、BoundSql 和实际执行 SQL

MyBatis 动态 SQL 根据输入求值。`MappedStatement` 表示语句定义，`SqlSource` 负责生成本次 SQL，`BoundSql` 保存 SQL、按顺序排列的参数映射及附加参数。具体职责见 [BoundSql 官方 API](https://mybatis.org/mybatis-3/apidocs/org/apache/ibatis/mapping/BoundSql.html)。

```text
Mapper / XML / 框架注入
  → MappedStatement / SqlSource
  → 输入对象驱动动态条件
  → BoundSql 与参数映射
  → 插件与参数处理
  → JDBC 执行
```

这条链中任何一个采样点都有边界：只读 XML 可能遗漏注解和生成语句；拿到 BoundSql 后，分页、租户或自定义插件仍可能改变最终行为。提取器必须标注采样阶段。

MyBatis-Plus 的 SQL 注入器可注册通用方法；运行时 Wrapper 又会提供条件，因此“扫描全部 XML”不能自然覆盖 `BaseMapper` 路径。参考 [MyBatis-Plus SQL 注入器](https://baomidou.com/guides/sql-injector/)。框架对象的详细机制复用 [[03-数据存储与缓存/数据库/Mybatis]]，这里重点关注覆盖边界。

| 路径 | 优点 | 不能自动覆盖的内容 |
| --- | --- | --- |
| 静态资源解析 | 不必启动完整应用，容易追踪文件来源 | 运行期 Wrapper、自定义脚本、插件改写 |
| 加载框架配置并生成 SQL | 能利用框架求值和注册结果 | 仍需构造有效输入；启动组件可能有副作用 |
| 执行链采集 | 接近实际 SQL 和参数 | 只覆盖被触发的流量或用例，缺失路径不可见 |

三条路径可以组合，但 AST 解析、框架加载和运行期采集是不同能力。不能因项目“提取 SQL”就推断它使用了某个 AST 库或具备完整语义分析。

### 4.2 分支覆盖与组合覆盖

假设教学查询有两个可选参数：`status` 与 `deptIds`。可以构造下列输入：

| 用例 | status | deptIds | 观察目标 |
| --- | --- | --- | --- |
| A | 未提供 | 未提供 | 默认 SQL 的范围是否符合契约 |
| B | 有值 | 未提供 | 单条件路径 |
| C | 未提供 | 单元素 | 集合展开、绑定顺序 |
| D | 有值 | 多元素 | 组合条件、多个占位符 |
| E | 有值 | 空集合 | 拒绝、无结果或省略条件中的哪一种语义 |
| F | 非法值 | 含 null | 参数校验与数据库约束边界 |

`choose` 只选择匹配分支，不能把所有条件同时置真来声称每条路径都执行过；`foreach` 则需要区分空、单元素和多元素。标签行为参考 [MyBatis 动态 SQL 文档](https://mybatis.org/mybatis-3/dynamic-sql.html)。

若 n 个条件独立可选，理论组合可达 2^n；实际还存在互斥和依赖条件。“每个条件取过真和假”并不等于验证所有交互。可以按风险选择组合或成对组合，但要保留未覆盖范围，不能保证不存在更高阶交互错误。

覆盖统计应分别记录：发现的语句数、可提取语句数、计划分支或形态数、有效参数用例数、已执行数、有效可比数。若“全部分支”的分母无法枚举，就报告已覆盖集合及限制，不编造百分比。SQL 形态去重也不能抹掉来源和不同语义输入。

**待代码核实：**XML 的 include、注解、Provider、自定义 LanguageDriver、MP Wrapper 分别是否支持；如何产生分支输入；是否采集插件后的 SQL；空集合如何处理；不支持的路径是明确跳过还是悄悄消失。

## 5. 通用原理：参数准备与 JDBC 绑定

### 5.1 有值不等于有效样本

患者与科室的教学查询同时需要 `patientId` 和 `deptId`。若独立随机抽两个 ID，它们可能没有关联，源库和目标库都会返回空集。这个结果只能说明该输入下结果相同，不能验证关联查询的正向行为。

参数准备应包含：能命中数据的关联样本、预期无结果的负向样本，以及空值、边界值和异常输入。采样要按关联关系构造，并记录样本在数据基线中的身份。抽样不能代替业务域分析，例如枚举、日期范围和字段组合约束无法仅靠列类型推断。

### 5.2 参数清单保存语义，不拼接“可读 SQL”执行

建议每个绑定位置记录：参数路径、值、Java/JDBC 类型、是否为 null、转换规则；保留原始顺序。`#{}` 常形成占位符，而 `${}` 是 SQL 文本构造，后者不能通过普通值绑定解决，需要限定合法结构。

`foreach` 和 `bind` 可能引入附加参数，不能只从原始入参 Map 读取；同一参数出现两次，也必须对应两个绑定位置。对自定义 TypeHandler，如果工具绕过它直接 `setObject`，就应把验证对象标为 JDBC 级，而非应用真实路径。

两侧可以采用各自正确的 JDBC 类型映射，但必须保持同一个业务值，并记录适配。例如同一时刻如何映射为有时区或无时区类型，要先定义契约，不能在比较失败后随意截断精度。SQL NULL 也不能和字符串 `"null"`、空串混为一谈。

**待代码核实：**采样是否保留关联关系；参数文件能否稳定重放；null 使用什么 JDBC 类型；附加参数和自定义 TypeHandler 是否保留；日期时区、枚举、二进制和大对象如何绑定。显式参数是否覆盖采样参数，也需要以实际优先级为准。

## 6. 通用原理：建立可比的双库执行环境

### 6.1 基线一致先于结果比较

两侧至少应记录数据库与驱动版本、Schema、字符集与排序规则、时区、隔离级别、影响语义的会话选项，以及参与测试的数据集版本。连接成功只能证明驱动可连接，不能证明方言、类型和事务行为兼容。

可控测试通常使用来自同一份合成数据或脱敏快照的两套隔离库。两个数据库各自开启可重复读事务，并不会自动建立同一业务时点的跨库快照。若仍有业务写入，需要冻结测试数据或证明复制水位和基线可比；做不到时将差异标为待排除数据因素。

`CURRENT_TIMESTAMP`、随机函数、序列、默认值和自动生成键都可能引入非确定性。可在独立教学用例中使用显式值以验证其他机制，但这会改变测试对象；原始非确定性表达式仍需单独验证，不能静默替换后宣称原 SQL 通过。

### 6.2 超时、资源和结果上限

连接获取、语句执行、结果读取和网络传输是不同阶段。应分别保存失败位置；一次超时不能证明 SQL 未执行。JDBC 的取消和查询超时依赖驱动及数据库支持，不能由客户端超时推断服务端已停止，参见 [Statement API](https://docs.oracle.com/en/java/javase/21/docs/api/java.sql/java/sql/Statement.html)。

大结果集若只取前 N 行，必须标为截断；如果两侧恰好前 N 行相同，也不能报告全量相同。流式读取能降低内存占用，但无序比较仍可能需要计数、分桶或外部排序；只比较哈希只能作为筛查，最终差异定位应保留可复核依据。

功能验证与性能验证分开：两侧硬件、数据分布、统计信息、索引、缓存和并发不同，单次耗时不能直接用于证明迁移性能改善。

**待代码核实：**环境指纹如何记录；是否检测基线不一致；超时能否落到具体阶段；取消后如何处理连接；结果是否截断；任务级并发是否挤占测试库连接。

## 7. 通用原理：结果等价与差异定位

### 7.1 先比较结构，再按契约比较行

不要把所有值 `toString()` 后直接比较。不同 JDBC 类型可能字符串相同，数值相等也可能字符串不同。建议保留列序号、标签、JDBC 类型、精度等元信息，再按显式规则对齐；只按列名建 Map 会丢失重名列。

| 对象 | 建议规则 | 容易掩盖的错误 |
| --- | --- | --- |
| 无顺序契约的结果 | 比较多重集合，即行值与出现次数 | Set 去重后漏掉重复行差异 |
| 有稳定顺序契约的结果 | 按序比较，并定位首个差异 | 排序后比较掩盖原 SQL 顺序差异 |
| 精确小数 | 按业务约定比较数值，类型与精度另报 | 转成浮点造成精度损失 |
| 浮点近似值 | 预先定义绝对/相对误差及特殊值规则 | 失败后扩大容差直到通过 |
| 时间 | 明确“时刻”或“本地日期时间”，再统一表示 | 无时区值被擅自解释为 UTC |
| NULL、空串、空白 | 默认分别保留，特殊等价需业务依据 | trim、大小写转换抹掉真实差异 |
| 二进制与大对象 | 比较内容、长度，明确截断和读取失败 | 比较驱动对象的字符串表示 |

归一化不是清洗掉所有差异，而是实现事先约定的等价关系。报告同时保留原值和归一化依据，才能定位是数据库行为不同还是比较器自身有误。

### 7.2 排序与分页的特殊边界

没有 ORDER BY 的结果不应假定自然顺序相同；即使有 ORDER BY，排序键相同的行也可能以不同次序返回。MySQL 8.4 文档明确说明了相同排序值与 LIMIT 组合的非确定性，见 [LIMIT 优化](https://dev.mysql.com/doc/refman/8.4/en/limit-optimization.html)。

例如按 `created_at` 分页，但多行时间相同，两侧可能选到不同的第 10 行。将这十行再排序不能修复入选集合不同的问题。可报告“原 SQL 排序不充分”，另用 `created_at, id` 的稳定排序变体定位原因；变体通过不等于原查询已验证通过。

### 7.3 两边空结果与两边异常

两边空集可以记录为该用例结果一致，但需另报“正向数据路径未覆盖”。如果用例本来就要求查不到，则它是有效负向证据。不要统一把空结果判为失败，也不要用它掩盖采样无效。

两边都抛异常同样不能默认兼容：驱动异常类或错误码不同不一定语义不同，错误文本相同也不一定原因相同。应保存 SQLState、厂商码、阶段和异常摘要；只有预先定义的负向用例，才能按约定的错误语义验证“拒绝行为符合预期”。

### 7.4 可执行的比较器教学实验

下面是完整 Python 标准库示例，只验证“无序结果保留重复次数、Decimal 数值比较、NULL 独立”的局部规则。它不是 JDBC 比较器，也不覆盖日期、容差和大对象。

```python
from collections import Counter
from decimal import Decimal


def cell_key(value):
    if value is None:
        return ("null",)
    if isinstance(value, Decimal):
        if not value.is_finite():
            raise ValueError("本教学模型只接受有限十进制数")
        return ("decimal", value)
    if isinstance(value, str):
        return ("text", value)
    raise TypeError("本教学模型只接受 Decimal、字符串和 None")


def bag(rows):
    return Counter(tuple(cell_key(v) for v in row) for row in rows)


a = [("A", Decimal("1.0")), ("A", Decimal("1.00")), ("B", None)]
b = [("B", None), ("A", Decimal("1")), ("A", Decimal("1.000"))]
c = [("B", None), ("A", Decimal("1"))]
assert bag(a) == bag(b)                   # 顺序、十进制表示差异被约定为等价
assert bag(a) != bag(c)                   # 少一条重复行必须发现
assert set(a) == set(c)                   # 反例：Set 比较会漏报
assert bag([("A", None)]) != bag([("A", "")])
assert bag([("A", Decimal("1.01"))]) != bag([("A", Decimal("1.00"))])
assert a != b                            # 有顺序契约时不能直接复用无序规则
```

**待代码核实：**现有比较器采用逐行、Set、多重集合还是哈希；排序模式由谁决定；列对齐如何处理重名列；归一化是否版本化；报告是否包含双方原值和差异行定位。

## 8. 通用原理：DML 验证、回滚与恢复证据

### 8.1 影响行数不够证明写入相同

教学更新将 `id=101` 的记录从 `PENDING` 改为 `DONE`。两侧都返回影响 1 行，仍可能因映射、触发器或表达式差异写入不同值。验证需要分别检查命中的记录身份、修改字段和受影响关联数据，再比较预期效果。

更新计数本身也要核实驱动和连接选项下表示匹配行还是实际改变行，不能把所有产品的计数规则视为一致。对于自动生成键，要分别验证业务关系和生成策略，不要把所有 ID 列无条件忽略。

### 8.2 两个本地事务不是一个跨库事务

下面是**设计时序，不是现有实现**。前提为隔离数据集、允许的事务型 DML、已确认的影响范围，且测试期间没有其他写入。

```text
1. 校验两侧环境和初始数据，保存各自 before 证据。
2. 各自获取受控连接，关闭自动提交，再执行本侧 DML。
3. 在各自执行连接中读取 after，检查写入效果及关联变化。
4. 无论执行或比较是否成功，都分别尝试结束两侧事务并回滚。
5. 两侧回滚互不阻塞清理：源侧回滚失败，仍尝试目标侧回滚。
6. 在已结束事务后的新读取上下文中检查恢复状态，各自与 before 比较。
7. 汇总比较结论和恢复结论；任一恢复失败或未知，都不能给出安全通过。
```

after 回查放在写连接内，才能观察本事务未提交修改；换连接可能只读到旧值。恢复检查则应避免继续使用旧快照或框架缓存。使用新连接也不代表原连接中的未决事务已经消失：若原连接丢失且事务状态未知，即使新连接读到 before，也不能直接宣布回滚完成，应结合数据库会话/事务状态确认，保持未知状态直至证据充分。

JDBC 默认自动提交；`rollback()` 需要正确的事务状态。关闭仍有活动事务的连接，其结果不能按统一规则假定；清理逻辑要显式处理事务，参见 [Connection API](https://docs.oracle.com/en/java/javase/21/docs/api/java.sql/java/sql/Connection.html)。原异常、双方回滚异常与验证异常应分别保存，不能让 finally 中的异常覆盖最初失败原因。

### 8.3 回滚的边界

“执行完调用 rollback”不等于“环境恢复到完全没运行过”。需要检查：

- 是否存在隐式提交、非事务对象、存储过程中的事务控制或连接切换。
- 触发器和级联影响的表是否在同一可回滚边界内，恢复检查是否覆盖它们。
- 序列、自增分配等内部状态是否会恢复；需按具体数据库确认，不能要求所有生成器完全无间隙。
- 是否触发了外部调用、文件或其他非数据库副作用。
- 测试结束能否证明锁和未决事务已释放，而不只是数据看起来相同。

MySQL 8.4 的部分 DDL 会导致隐式提交；某些临时表操作虽不隐式提交，却仍不能回滚。不能把 DDL 混入普通 DML 回滚验证流程，见 [隐式提交官方说明](https://dev.mysql.com/doc/refman/8.4/en/implicit-commit.html)。这不是对崖山行为的推断。

SQL 首词为 SELECT 也不足以作为任意语句无副作用的证明：函数、锁定读取和特定语法都需纳入执行策略。验证工具应采用明确支持范围、独立账号与隔离数据；配置化接入数据库不自动获得安全执行保证。

### 8.4 失败时序与判定

| 故障 | 必须保留的事实 | 合理判定 |
| --- | --- | --- |
| 源侧执行成功，目标侧失败 | 源侧效果、目标错误、双方回滚状态 | 执行失败或候选兼容性问题；恢复另判 |
| DML 返回后回查失败 | 已发生写尝试，效果未完整确认 | 不能按影响行数判通过，仍执行回滚 |
| 一侧回滚失败或断连 | 原事务可能未决 | 恢复未知或失败，停止依赖该基线的后续测试 |
| 回滚无异常，回查存在差异 | 检查范围内未恢复 | 恢复失败，检查事务边界、并发干扰和副作用 |
| 原语句超时 | 调用方不知道最终执行结果 | 查询执行/事务状态并处理，不直接重放 DML |

**待代码核实：**执行和 after 回查是否使用同一连接；自动提交在哪里关闭；是否混入 Spring 管理事务；两侧回滚是否独立尝试；是否真正检查 before/after/恢复数据；恢复失败是否阻止后续测试；恢复检查覆盖哪些表和状态。

## 9. 通用原理：报告表达与回归验证

### 9.1 比较结论与恢复结论分开

建议至少保留两个维度，避免“结果相同”掩盖环境未恢复。以下是设计词汇，不是现有状态枚举：

| 维度 | 建议表达 |
| --- | --- |
| 验证结论 | 在声明范围内通过、观察到差异、执行失败、无法判定、未覆盖/跳过 |
| 恢复结论 | 不适用、已验证恢复、恢复失败、恢复未知 |
| 覆盖说明 | 正向/负向样本、空结果、截断、非确定性、支持范围 |

“观察到差异”还不是根因。先核实相同参数、数据基线、配置与比较规则，再把问题归为 SQL 方言、类型转换、执行语义、工具缺陷或环境问题。源侧成功、目标侧语法错误是较明确的候选兼容性问题；目标库连接超时则不能直接算作 SQL 不兼容。

JSON 与 HTML 应由同一结果模型生成，避免统计口径不同。报告记录完整计数和未覆盖项；摘要只展示样本时明确标注。HTML 渲染数据库文本与异常内容时需要转义，防止结果值被当作页面脚本；复现参数也应按敏感性控制可见范围。

### 9.2 按机制验证，而非只看绿色报告

| 层次 | 最小用例 | 应证明的性质 |
| --- | --- | --- |
| 参数与比较器单元测试 | 重复行、顺序、null、精度、空样本 | 不会静默漏掉已定义的差异 |
| 框架集成 | 动态 XML、MP 通用方法、插件、TypeHandler | 捕获点与实际执行路径一致或明确差异 |
| 双库查询 | 相同基线下的正常、边界、异常输入 | 能区分真实差异与不可比因素 |
| 双库 DML | INSERT/UPDATE/DELETE 与 after 回查 | 写入效果符合预期，恢复状态可验证 |
| 故障注入 | 单侧失败、回查失败、回滚失败、结果截断 | 不会误报通过；清理路径仍被执行 |

真实集成实验应固定版本、输入、基线和比较规则，记录预期、观察、差异及限制。测试失败后修复比较器，需要同时重跑能够暴露该错误的反例，不能只重跑之前的成功样本。
