## 三个项目怎么串起来讲

共同主线是：**业务状态不断变化、任务可能重复执行时，如何保证动作仍有依据、有权限，并且不会产生重复效果。** 三者可以串成一道系统设计题，但当前材料不证明它们已经集成为一个上线系统。

| 项目 | 最值得讲的复杂性 | 核心取舍 | 当前可用证据 |
| --- | --- | --- | --- |
| 医生助手 Agent | 生成期间证据变化，旧草稿被审批；模型与工具失败后的恢复 | 固定工作流与有限 Agent 循环；可用性与证据完整性 | 设计基线、23 项内存状态实验的已有记录；不是业务系统上线结果 |
| 动态权限 | 个性覆盖、多角色范围、撤权与在途请求竞争 | 缓存性能与撤权时效；粗粒度串行与并发能力 | 简历陈述为开发及联调通过，尚未独立核实业务源码；深化方案另有教学实验 |
| RabbitMQ + Outbox | 提交、发布、消费、ACK 之间存在失败窗口 | 接受重复投递，以事务与幂等约束业务效果；复杂度与恢复能力 | 设计方案及共享的 16 项本地实验记录；不是真实 broker 集成结果 |

共享的 16 项实验同时被多个项目引用，不应分别计算成三套成果；其中包括 SQLite 事务实验和协议模型，不能替代 MySQL、RabbitMQ 与业务系统联调。

开场可以这样说：

> 我重点准备了三个相互关联的方向。动态权限关注谁能对哪些资源执行操作；医生助手关注建议基于什么证据、什么时候需要重新审核；可靠消息关注业务提交后任务如何恢复，以及重复投递如何不产生重复业务效果。我会分别说明实际参与的工作和后续设计验证，不把设计方案当成生产经历。

### 每个复杂场景都按六步展开

1. **业务目标**：谁要完成什么事情，做错的具体后果是什么。
2. **约束条件**：当前系统边界、依赖、时效要求、已有实现和我的职责。
3. **失败时序**：用三个到五个时间点解释普通实现为什么失败。
4. **候选方案**：至少比较简单基线、当前选择及一个更复杂的方案。
5. **取舍与边界**：为什么选它，付出什么代价，什么条件下换方案。
6. **验证证据**：构造什么故障、断言什么业务结果，以及哪些尚未验证。

避免只说“高并发、高可用、用了状态机”。可以改成：“请求通过授权检查后，管理员撤权先提交，而旧请求仍然写入成功。我的设计要约束的是这两个提交的顺序。”

## 医生助手 Agent：讲清证据变化与执行边界

### 约 90 秒口述稿

> 医生助手这一部分目前是设计与实验方案。目标是帮助医生整理资料、生成有证据的报告与回复草稿，首期保留人工审核，不开放自动发送和处方类动作。
>
> 我重点分析了一个场景：模型已经基于资料 v7 生成草稿，资料随后更新到 v8，但失效通知还没到，医生此时审批旧草稿。仅检查任务状态或者依赖消息通知，会漏掉这个窗口。
>
> 因此方案把证据来源版本、草稿版本和审批状态分开管理。审批时回查相关来源版本；发现变化后，旧草稿不能继续获批，重新生成的草稿也不能继承旧批准。多来源之间不默认具有同一时刻的事务快照，对最终检查后的变化仍需定义业务接受边界。
>
> 编排上选择固定工作流包围有限工具循环：授权、证据校验和提交规则由程序控制，模型只能在白名单中选择查询工具。这增加了版本管理、恢复和评估成本，但能把模型的不确定性限制在可检查的范围。现有状态实验支持部分规则，模型质量和真实业务集成仍待验证。

### 面试时主动展开的取舍

| 比较项 | 选择依据 | 代价与切换条件 |
| --- | --- | --- |
| 固定工作流 / 自主 Agent / 混合编排 | 固定任务先用工作流；需要按资料缺口调整查询时，才引入有限循环 | 循环增加耗时、费用和故障路径；若质量收益不明显，退回固定步骤 |
| 冻结证据 / 始终读取最新资料 | 冻结输入便于解释生成依据，审批再检查来源是否变化 | 不能宣称跨来源强一致；更新频繁可能反复作废，需要定义有效期和重审条件 |
| 必需来源失败即停止 / 部分来源降级 | 缺少必需证据不继续生成完整结论；可选来源缺失须显式标注 | 完成率可能下降；不能把读取失败当成“没有异常数据” |

| 面试官可能追问 | 回答应落到哪里 |
| --- | --- |
| 为什么一定需要 Agent，普通工作流不行吗？ | 先承认可固定任务直接用工作流；只有查询路径依赖中间结果才考虑 Agent，并用同输入、模型、预算进行对照评估。 |
| 一个 version 字段不够吗？ | 目标变化、来源变化、草稿编辑、执行状态变化处理不同；一个版本可以保守失效，但难以解释和精准恢复，拆分也会增加维护成本。 |

| 查完来源版本，提交前来源又变了呢？ | 回查并不自动消除竞态。同库可考虑共同事务协议；跨源需版本条件、冻结证据契约或明确接受时间边界，当前方案不能声称全局强一致。 |
| 人工审批等很久，是否一直占线程？ | 持久化等待状态，释放执行槽；恢复时重查权限与版本，累计预算不能因恢复而清零。 |
| Prompt 注入让模型越权调工具怎么办？ | 身份与资源范围来自服务端上下文，工具网关逐次授权；验证真实工具是否执行、数据是否泄漏，不能只看模型回复是否合规。 |
| 如何证明 Agent 比工作流好？ | 同一评测集比较任务完成质量、证据引用正确性、工具调用数、延迟和费用，再做去掉检索或循环的对照；当前没有实测收益就明确说明。 |
| 调外部接口超时，直接重试可以吗？ | 超时不等于失败；外部动作属于后续扩展，先查询回执或使用资源端幂等，无法查证则进入 UNKNOWN 并人工处理。 |

## 动态权限：讲清授权语义与撤权时效

### 约 90 秒口述稿

以下已有实现部分来自简历陈述；面试前应核实本人职责、真实代码和联调证据。“我负责”只用于自己实际完成的工作。

> 项目原来主要区分医生和管理员，后来增加科室主任、护士等角色，并且需要按机构和科室限定管理范围。复杂点是角色默认权限、用户个性配置、动作权限和资源范围要一起生效。
>
> 已有材料中采用用户配置覆盖角色默认，并用 Redis 保存运行时权限快照。这里必须区分“没有配置”和“显式清空”：前者继承，后者表示撤销，否则用户清空权限后反而会恢复角色默认权限。
>
> 我进一步分析了撤权时效：事务提交后更新缓存版本可以减少旧快照使用，但如果版本发布失败，或者请求已经通过检查，仍可能出现旧权限窗口。Outbox 能恢复通知，却不能单独保证撤权后所有在途写入立即失效。
>
> 对严格要求撤权顺序的同库敏感写，我设计了撤权和业务写共同参与的事务校验协议；代价是锁竞争和依赖管理。已有开发联调部分与这项深化设计需要分别说明，不能把实验结论说成生产强一致能力。

### 面试时主动展开的取舍

| 比较项 | 选择依据 | 代价与切换条件 |
| --- | --- | --- |
| 角色权限 / 角色加用户覆盖 | 个性授权确有业务需求才引入覆盖，并明确未配置与显式空 | 配置和审计更复杂；授权管理员还必须有合法委派权 |
| 每次查库 / 缓存加版本 | 根据动作风险选择检查强度；缓存适用于接受一定失效窗口的路径 | 版本源也可能滞后，不能以两个旧版本相等证明最新 |
| 机构级策略锁 / 更细粒度锁 | 粗粒度协议较易证明正确，作为同库严格撤权的设计基线 | 竞争更大；出现可测瓶颈后再细化，必须覆盖角色、组织等全部授权依赖 |

| 异步任务提交时已授权，执行时还要查吗？ | 要；执行、审批、结果读取可能发生在不同时间，服务账号不能扩大发起人的业务权限。 |

## RabbitMQ + Outbox：讲清失败窗口与幂等边界

### 约 90 秒口述稿

> RabbitMQ + Outbox 目前是可靠消息设计与本地实验。我要解决的是业务数据已提交，但后续事件未可靠发出，以及消费者重试导致重复效果的问题。
>
> 直接先写数据库再发 MQ，进程可能在两步之间退出；先发 MQ 再写数据库，又可能下游已执行而本地回滚。因此方案把业务记录和 Outbox 事件放进同一个本地事务，再由发布器独立发送。
>
> 这不等于消息只发送一次。Broker 已收消息但确认丢失时，发布器仍可能重发，所以使用稳定 eventId，消费者将 inbox 去重记录与本地业务修改同事务提交，提交后再 ACK。发布成功也不等于消费者业务完成。
>
> 代价是扫描、租约、积压、重试和去重记录的运维成本。同应用、低复杂度后台任务可以先用任务表，只有存在跨服务独立订阅等需求才选择 MQ。现有 SQLite 和协议模型实验验证了部分失败窗口，真实 RabbitMQ 网络故障及 MySQL 并发行为还需要集成测试。

### 用四个提交点讲明白复杂性

`P1：业务 + Outbox 提交 → P2：发布结果确认 → P3：消费者业务 + inbox 提交 → P4：ACK`

- P1 后退出：已落库事件由扫描恢复。
- Broker 已收消息但 P2 未记录：重发同一 eventId，允许重复投递。
- P3 后、P4 前退出：消息重投，消费者根据已提交的 inbox 识别重复。
- 外部接口已成功但本地未记录：本地 inbox 不能独自解决，依赖外部幂等键、回执查询或人工核实。

### 连续追问与回答落点

| 面试官可能追问 | 回答应落到哪里 |
| --- | --- |
| 为什么不直接用事务消息或者 CDC？ | 比较基础设施支持、维护成本、恢复与重放能力；当前本地事务方案易于说明边界，CDC 仍需处理日志保留、断点和消费者幂等。 |
| 同一个方法加 @Transactional 就够了吗？ | 需要实际处于同一数据源、本地事务与正确的事务代理边界；它不会让 RabbitMQ 或外部 HTTP 自动参与数据库回滚。 |
| 收到 publisher confirm ACK 就算成功吗？ | 还要结合 mandatory return 等发布结果；不可路由消息可能先 return 后 ACK，而且有路由成功不证明所有预期订阅队列存在。 |
| 多个发布器如何避免重复发送？ | 短事务领取、租约、attemptToken 条件更新约束状态；旧 worker 仍可能完成发送，因此目标是允许重复且正确处理。 |
| eventId 和 attemptToken 为什么分开？ | 前者标识同一逻辑事件，重试保持稳定；后者隔离不同执行尝试，防止旧回调覆盖新状态。 |
| 用 Redis SETNX 去重更快，为什么不用？ | 先写 key 再执行业务会有“标记成功、业务失败”窗口；业务和去重都在同库时优先同事务。性能选择须在正确性成立后比较。 |
| 同一事件不同消费者会不会互相去重？ | 去重键包含 consumerName 与 eventId，各消费者独立记录；相同 ID 不同载荷应识别为冲突。 |
| 不同 eventId 触发同一个业务动作呢？ | 事件去重不足，还需要 businessEffectKey 等业务唯一约束，明确什么叫同一效果。 |
| 发短信放进消费者事务不就行了吗？ | 短信不会随数据库回滚。先持久化通知任务再 ACK；发送器用稳定 actionId 和供应商幂等或回执查询处理不确定结果。 |
| 幂等之后是不是也保证有序？ | 不是。快照事件可按版本拒绝旧值，增量事件可能必须补齐缺口；不能把低 prefetch 当成全局有序。 |
| 去重记录保存多久？ | 至少结合最长允许重放窗口和业务重复风险制定策略；过早清理会让历史消息重新产生效果。 |
| 消息积压怎么恢复？ | 先判定下游故障还是消费能力不足，控制重试放大与补偿速率；只有恢复后有效消费速率高于新增速率，积压才会减少。 |

## 跨项目综合追问：把三个边界接起来

**题目：医生提交生成任务后被撤权，消息又重复投递；旧 worker 调用外部接口超时，此时应该怎么办？**

这是系统设计延伸，外部动作不属于当前医生助手首期开放范围。

1. 提交生成任务只表示请求被受理；执行时重查当前权限，无权则拒绝继续。
2. 生成与审批检查证据、草稿版本；权限有效也不意味着旧证据仍可用。
3. 有关任务与事件按本地事务原子落库，Outbox 负责可恢复发布，不能替代执行时授权。
4. 重复事件以消费幂等和业务唯一键约束效果；领取后的 attemptToken 只保护本地状态，不保证外部接口不会收到重复请求。
5. 外部超时标为结果未知，查询回执；有可靠外部幂等契约才按该契约重试，无契约则人工核实，不能随便换一个 actionId 重发。
6. 审计串联发起人、资源、授权版本、证据版本、草稿版本、eventId、actionId 与执行尝试，能够还原“谁依据什么授权和证据做了什么”。

收口可以说：“这三个机制分别解决授权、依据和可靠执行的问题，任何一个都不能替代另外两个。严格保证要落到具体事务边界、外部系统契约及验收用例上。”

## 面试官核实经历时，怎么回答

| 核实问题 | 准备方式与表达边界 |
| --- | --- |
| 你本人到底负责哪一块？ | 填清需求分析、接口、数据模型、联调、测试或方案的实际职责；团队实现、本人实现和后续研究分别说。 |
| 用户量、QPS、数据量是多少？ | 只给可追溯的真实统计；没有就说尚未做规模验证，继续说明计划测什么，不用估算冒充生产数据。 |
| 优化了多少？ | 提供同口径基线、输入负载、环境、指标与结果；当前材料没有性能收益，不填写百分比。 |
| 真遇到过这个事故吗？ | 区分真实故障、联调用例与主动构造的反例；可以说“我用实验复现这个窗口”，不能说“线上曾发生”。 |
| 为什么不用更简单的实现？ | 先解释简单方案适用条件，再给出使其失效的具体需求或时序；如果需求不成立，就选择简单方案。 |
| 你的测试到底证明什么？ | 说清输入、故障点与业务断言；内存模型、SQLite、本地 broker、真实环境结果分层，未测试部分明确保留。 |

面试前，每个项目补齐一张事实卡：**我的职责、交付状态、可展示证据、一个失败时序、一个被放弃的方案、当前局限**。事实未核实前，保留空缺，不写成完成式。

练习时先用 90 秒讲主线，再用 3 分钟展开一个故障窗口，最后进行 5 分钟连续追问。每次复盘只看四件事：是否说清业务后果、是否给出备选方案、是否承认代价、是否拿得出对应层级的证据。
