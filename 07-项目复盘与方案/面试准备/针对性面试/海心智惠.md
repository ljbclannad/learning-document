## 二、如何把我的 AI 对话经验迁移到海心智惠

### 2.1 患者智能问诊方案

#### 目标

面向肿瘤患者，智能问诊不应该只是普通问答，而是能结合患者病历、治疗阶段、副作用记录、既往咨询、日记和知识库，给出更贴合当前状态的解释、提醒和下一步建议。

#### 核心链路

```text
用户提问
-> 读取患者画像
-> 读取会话上下文
-> 意图识别
-> 判断是否需要补充信息
-> RAG 检索病历/日记/知识库/历史咨询
-> Prompt 组装
-> 大模型生成结构化回复
-> 风险识别
-> 必要时转医生/人工
-> 回写会话上下文和患者画像
```

#### 患者画像怎么设计

1. **基础画像**
   - 年龄、性别、肿瘤类型、治疗阶段、当前治疗方案、用药信息、过敏史。

2. **病程画像**
   - 手术、放疗、化疗、靶向、免疫治疗等阶段记录。
   - 最近一次复诊、检查报告、异常指标、医生建议。

3. **症状画像**
   - 恶心、呕吐、乏力、疼痛、食欲下降、睡眠、情绪、体重变化等副作用记录。

4. **行为画像**
   - 用户常问问题、日记内容、随访填写情况、依从性、最近触发的风险事件。

5. **画像字段元数据**
   - 每个字段不只存 `value`，还要存 `source`、`confidence`、`updatedAt`。
   - 例如来源区分：病历导入、用户填写、医生录入、AI 对话抽取、随访表单。

#### 画像补全怎么做

我的 AI 对话项目里有一个关键设计是“画像诊断与补全决策”，可以直接迁移到这里。

1. 用户提问后，先判断本轮回答是否强依赖患者画像。
2. 如果依赖，就根据意图找出必要槽位。
3. 如果缺少关键信息，不急着检索和生成，而是优先追问最关键的 1 到 2 个字段。
4. 用户补充后，在下一轮完整对话中同时返回自然语言回复和结构化画像更新 JSON。
5. 后端只允许模型更新白名单字段，并做标准化、置信度校验和审计记录。

示例：

```json
{
  "replyText": "为了判断这个恶心是否和治疗相关，我需要先确认一下你最近一次化疗时间和当前用药。",
  "needFollowup": true,
  "missingSlots": ["last_chemotherapy_date", "current_medication"]
}
```

#### RAG 检索怎么做

1. **MySQL**
   - 存患者主数据、病历、报告结构化字段、随访记录、问诊订单等权威数据。

2. **Redis**
   - 缓存用户画像、当前会话上下文、最近问答、热点知识。

3. **Milvus / 向量库**
   - 存长期对话摘要、日记摘要、患者教育知识、疾病知识片段。
   - 用户提问时按语义召回最相关的历史信息和知识片段。

4. **检索策略**
   - 简单问候或通用问题不检索，直接回答，减少延迟和 token 成本。
   - 涉及当前治疗、副作用、报告解读、用药、复诊时必须检索患者上下文。
   - 召回后做去重和重排，最终只把少量高价值内容注入 Prompt。

#### 安全边界

1. AI 可以做健康教育、症状解释、复诊提醒、生活方式建议。
2. 涉及诊断结论、治疗方案调整、停药、加药、剂量变化，必须转医生。
3. 高风险信号要触发人工介入，例如严重疼痛、持续高热、呼吸困难、出血、自伤倾向。
4. Prompt 里只放当前问题需要的信息，不把完整病历和全部隐私直接塞给模型。

#### 面试表达

> “我会把患者智能问诊设计成画像驱动的对话系统，而不是普通聊天机器人。用户提问后，系统先读患者画像和会话上下文，再判断当前问题是否需要病历、日记、随访或知识库检索。如果缺关键字段，先通过画像补全追问 1 到 2 个最重要的信息，而不是直接生成。画像足够后，再用 Redis + Milvus 做混合召回，把相关病程记录、历史日记和知识片段注入 Prompt。最终输出要经过风险识别，涉及诊断、用药、治疗方案调整的内容不让模型直接给结论，而是转医生确认。这样既能利用 AI 提升患者服务效率，又能把医疗安全边界控制住。”

### 2.2 患者日记与副作用随访 Agent

#### 目标

肿瘤患者的日记和副作用随访价值很高，不只是社区内容，也可以成为患者画像和医生管理的输入。

#### 设计方案

1. **日记结构化抽取**
   - 从日记里抽取症状、副作用、情绪、饮食、睡眠、疼痛、用药、复诊计划。
   - 抽取结果写入患者画像或随访记录，保留来源和置信度。

2. **副作用风险分级**
   - 按规则 + AI 识别低、中、高风险。
   - 低风险：自动给健康教育和观察建议。
   - 中风险：建议联系医生或进入随访提醒。
   - 高风险：生成医生待办或人工介入。

3. **连续趋势识别**
   - 不只看单篇日记，而是看最近 7 天、14 天趋势。
   - 例如疼痛持续升高、食欲持续下降、体重明显下降、情绪持续低落。

4. **医生端摘要**
   - 把患者近期日记和随访记录压缩成结构化摘要。
   - 输出：主要症状、变化趋势、风险等级、建议关注点、证据来源。

#### 面试表达

> “海心智惠的患者日记不应该只作为社区内容存起来，我会把它作为患者画像和随访体系的一部分。每篇日记发布后，可以用 AI 做结构化抽取，识别症状、副作用、情绪、用药和复诊信息，并结合规则做风险分级。低风险自动给健康教育，中高风险进入医生待办或人工复核。更重要的是看趋势，比如连续几天疼痛上升、食欲下降、情绪低落，这比单次问答更有医疗管理价值。”

## 三、如何把医生助手 Agent 经验迁移到海心智惠

### 3.1 医生提效助手方案

#### 目标

医生端的核心不是让 AI 替代医生，而是减少医生整理信息、查看历史、写随访建议和筛选高风险患者的时间。

#### 核心能力

1. **患者摘要生成**
   - 整合病历、报告、咨询记录、日记、副作用随访。
   - 生成结构化摘要：患者基本情况、治疗阶段、近期异常、主要诉求、风险点。

2. **随访建议生成**
   - 根据患者当前阶段和近期记录，生成随访重点。
   - 例如：是否需要关注恶心呕吐、疼痛、体重下降、睡眠、情绪。

3. **高风险患者筛选**
   - 按规则和模型识别高风险患者。
   - 生成医生待办：谁需要优先看、为什么、证据是什么。

4. **医生回复草稿**
   - AI 生成回复草稿，但不自动发送。
   - 医生确认后再发，保证医疗责任边界。

5. **患者分层管理**
   - 按治疗阶段、风险等级、依从性、近期活跃度给患者分层。
   - 帮助医生或运营优先处理关键患者。

### 3.2 Agent 工程架构

我的医生助手 Agent 项目里，核心不是让模型自由发挥，而是围绕 `agent_session` 做状态机控制。

```text
创建 agent_session
-> 初始化 AgentContext
-> 读取患者数据
-> 选择当前能力模块
-> 调用工具或知识库
-> 记录 evidence
-> 判断是否需要医生介入
-> 生成结构化结果
-> 记录审计和监控指标
```

#### agent_session 状态

1. `RUNNING`：Agent 正在执行。
2. `WAITING_DOCTOR`：命中高风险场景，等待医生确认。
3. `FINISHED`：正常完成，生成结构化结果。
4. `FAILED`：模型、工具或下游调用失败。
5. `BLOCKED_BY_SAFETY`：触发安全边界，被系统阻断。

#### AgentContext 设计

1. **显式状态**
   - 当前目标、当前患者、当前治疗阶段、风险等级、待补字段、待确认动作。

2. **证据列表**
   - 病历片段、检查指标、日记摘要、随访结果、知识库片段、人工确认结果。

3. **工具结果**
   - 查询病历、查询报告、查询随访、生成摘要、风险评分等工具返回值。

4. **审计信息**
   - 每一步调用了什么工具、用了哪些数据、模型输出了什么、为什么转人工。

#### 为什么要这样设计

1. 会话文本和运行时状态分离，避免把所有中间状态都塞进 Prompt。
2. Agent 可以暂停、人工确认、恢复执行，适合医疗高风险场景。
3. 结果基于 `state + evidence` 收敛，不完全依赖最后一次模型总结。
4. 审计更清楚，能解释“为什么给出这个建议”。

#### 面试表达

> “医生提效助手我不会设计成一个自由聊天机器人，而是设计成基于 agent_session 的任务型 Agent。系统先创建 session，初始化 AgentContext，把患者病历、日记、随访、检查报告等信息作为 evidence 管理。模型可以建议下一步 action，比如查询报告、生成摘要、识别风险，但每个 action 都要经过白名单、权限和安全规则校验。遇到诊断、用药、治疗方案这类高风险内容，session 进入 WAITING_DOCTOR，由医生确认后再继续。这样医生助手能提高信息整理和随访效率，但不会越过医疗责任边界。”

## 四、第三方药企技术能力支持怎么理解

### 4.1 可能的业务方向

1. **患者服务**
   - 药企关注患者用药教育、副作用管理、复诊提醒和依从性提升。

2. **临床招募**
   - 根据患者疾病类型、治疗阶段、检查指标、用药历史，辅助判断是否可能匹配某些临床试验。

3. **真实世界数据**
   - 对患者随访、日记、副作用、用药依从性做结构化沉淀和统计分析。

4. **患者教育内容分发**
   - 根据患者阶段推送不同内容，比如术后康复、化疗副作用、靶向药注意事项。

### 4.2 技术方案

1. **数据标准化**
   - 把病历、随访、日记、咨询记录转成标准字段和标签。
   - 保留来源、更新时间、置信度。

2. **患者分层**
   - 按疾病类型、治疗阶段、副作用风险、依从性、活跃度分层。
   - 对不同分层提供不同服务策略。

3. **隐私保护**
   - 对药企侧输出必须做脱敏、去标识化和权限控制。
   - 不直接暴露患者身份和完整病历。

4. **审计和授权**
   - 所有第三方数据调用都要记录调用方、用途、字段范围、授权依据和 traceId。

5. **可解释结果**
   - 药企或运营看到的不只是模型结论，还要看到匹配原因和证据来源。

### 4.3 面试表达

> “药企侧我会谨慎理解，不会简单说把患者数据开放出去。更合理的是把平台沉淀的随访、日记、副作用、依从性数据做标准化和脱敏治理，在用户授权和合规边界内，支持患者教育、临床招募线索、真实世界数据分析等能力。技术上要做患者分层、标签体系、数据权限、脱敏、审计和可解释结果输出，不能让第三方直接接触原始隐私数据。”

## 五、社区与内容审核专项

### 5.1 当前观察

1. 社区需要增强内容审核能力。
2. 需要 AI 识别涉黄、广告、错误诊疗建议、隐私泄露等风险。
3. 基础敏感词过滤需要和 AI 风险识别结合。
4. 社区日常存在卡顿现象，可以从列表查询、图片加载、缓存和分页方式排查。
5. 步骤教学有重复推荐问题，可以从推荐去重、用户行为记录和内容曝光记录优化。
6. 系统消息框交互可以进一步收敛，避免干扰用户主流程。

### 5.2 社区发帖设计

我会把社区发帖拆成内容生产、内容审核、媒体资源、互动计数、列表流和搜索几个模块。

主链路只做：

1. 登录校验。
2. 权限校验。
3. 限流。
4. 幂等。
5. 内容初筛。
6. 帖子落库。
7. 媒体绑定。

异步链路通过 MQ 做：

1. AI 审核。
2. 搜索索引。
3. 通知粉丝。
4. 热榜更新。
5. 计数聚合。

读侧优化：

1. 帖子详情做 Redis 缓存。
2. 社区首页缓存第一页或热门页。
3. 分页用游标分页，避免深分页。
4. 热榜用 Redis ZSet。

### 5.3 热榜排行

Redis ZSet 适合做热榜：

```text
key = community:hot:{communityId}:{window}
member = postId
score = hotScore
```

1. 点赞、评论、收藏时用 `ZINCRBY` 增加分数。
2. 查 TopN 用 `ZREVRANGE`。
3. 热榜不能只累加，要按小时榜、日榜拆 key，并设置 TTL。
4. 综合热榜可以用定时任务重算带时间衰减的分数。
5. MySQL 保存最终计数和帖子主数据，Redis 负责高频排行。

### 5.4 内容审核

内容审核分两层：

1. **内容安全审核**
   - 用户发帖、评论、日记、AI 回复、医生回复。
   - 做敏感词、规则、AI 审核和人工复核。
   - 按低、中、高风险决定直接发布、待审核、隐藏或拒绝。

2. **隐私访问审计**
   - 记录谁查看了患者病历、报告、处方、手机号、身份证。
   - 通过服务层 AOP 或拦截器记录 `operator`、`patientId`、资源类型、操作类型、IP、`traceId` 和访问原因。

用户日记审核策略：

1. 低风险：AI 自动通过。
2. 中风险：进入待审核或限制可见。
3. 高风险：先隐藏，再进入人工复核。
4. 隐私风险：提示用户打码后再发布。
5. 情绪危机：不只是拦截，要进入关怀或人工介入流程。

### 5.5 医疗隐私

医疗隐私保护不是单点加密，而是完整闭环：

1. 最小采集。
2. 传输加密。
3. 存储加密。
4. 权限隔离。
5. 展示脱敏。
6. 访问审计。
7. 第三方最小披露。
8. 数据生命周期治理。
9. AI Prompt 最小化。
10. Tool 调用权限控制。

   - 医疗业务不能忽略权限、隐私、审计、缓存、异步补偿、限流、降级和可观测性。

### 6.3 渐进式落地路线

我不会一上来就建议做完整 Agent，医疗场景更适合分阶段落地。

```text
第一阶段：患者画像 + RAG 问答 + 高风险转人工
第二阶段：日记/随访结构化 + 医生摘要 + 风险待办
第三阶段：agent_session + AgentContext + 工具调用 + 人工确认恢复
第四阶段：药企侧患者教育、临床招募线索、真实世界数据分析
```

面试表达：

> “我不会一开始就上完整 Agent。医疗场景更适合渐进式落地，先把患者画像、RAG、安全边界和医生确认机制做好，再逐步引入工具调用和多步骤 Agent。这样可以先解决真实业务问题，同时控制模型不稳定和系统复杂度。”

### 6.4 被质疑时的兜底回答

1. **如果对方问：这个方案会不会太复杂？**
   - “复杂度可以分阶段控制，第一版不需要完整 Agent，先做 RAG + 风险分级 + 人工介入；等患者画像、知识库和医生流程稳定后，再逐步加工具调用和多步骤编排。”

2. **如果对方问：AI 自动回答医疗问题靠谱吗？**
   - “我不会让模型直接做医疗裁决。模型主要做理解、归纳、风险识别和草稿生成，涉及诊断、用药、治疗方案调整的内容必须医生确认。”

3. **如果对方问：患者数据现在可能没打通，怎么做？**
   - “数据打通不一定一步到位，可以先从用户日记、随访表、病历摘要这些低侵入数据开始，再逐步接入检查报告、医生记录和外部系统。第一阶段先保证数据可用、可追溯、可审计。”

4. **如果对方问：你之前做的是体重管理，和肿瘤患者管理差异很大吧？**
   - “业务病种确实不同，所以医学规则和风险边界要重新设计。但底层工程问题是相通的，比如长期画像、上下文记忆、RAG 召回、Prompt 预算、风险转人工、医生确认和审计监控，这些经验可以迁移。”

### 6.5 我不是只会接模型 API

> “我对 AI 对话的理解不是把模型 API 接上就结束，而是要有画像、上下文、RAG、Prompt 预算、记忆回写、安全边界、人工介入和监控。尤其医疗场景里，模型只是能力之一，真正重要的是工程闭环和风险控制。”

### 6.6 我能把现有经验迁移到你们业务

> “我之前做的是体重管理方向，但底层方法可以迁移到肿瘤患者管理。体重管理里有用户画像、健康指标、长期记忆、随访建议和医生介入；肿瘤患者管理里对应的是病程阶段、检查报告、副作用、日记、复诊和医生随访。两者业务不同，但 AI 对话和 Agent 的工程方法是相通的。”

### 6.7 我对 Agent 的边界比较谨慎

> “医疗 Agent 不能让模型自由决定治疗方案。我更倾向于把模型放在受控编排里，通过 agent_session、AgentContext、工具白名单、风险规则和人工确认控制边界。模型负责理解、归纳和建议动作，系统负责权限、状态、审计和最终安全控制。”

## 七、可以反问面试官的问题

1. 目前患者智能问诊更偏规则问答、RAG 问答，还是已经在尝试 Agent 工具调用？
2. 医生提效助手现在最想优先解决的是患者摘要、随访提醒、风险筛选，还是医生回复草稿？
3. 患者日记和副作用随访目前是否已经结构化沉淀，还是主要作为文本记录？
4. 社区内容审核目前人工占比高不高？是否已经有敏感词、AI 审核或人工复核后台？
5. 药企侧更关注患者教育、临床试验招募，还是真实世界数据分析？
6. AI 生成内容在你们系统里是否需要医生确认后才能触达患者？
7. 患者隐私和第三方数据使用目前有哪些合规边界或授权流程？
