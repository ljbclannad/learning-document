# 三、医院分布式项目

## 项目背景

互联网医院项目采用Spring Cloud微服务架构，主要负责在线问诊、医生排班、患者预约等核心功能。通过微服务拆分实现业务解耦，提升系统可维护性和扩展性。

**技术栈：**
- 服务治理：Nacos、Gateway、Sentinel
- 服务调用：OpenFeign
- 分布式解决方案：Redisson、RabbitMQ、Outbox模式
- 数据存储：MySQL（读写分离）、Redis
- 监控追踪：Sleuth + Zipkin

### 1.1 Nacos - 服务注册与发现

**核心功能：**
- 服务注册：服务启动时自动注册到Nacos
- 健康检查：每5秒发送心跳，15秒未收到标记不健康，30秒剔除
- 服务发现：消费者从Nacos拉取服务列表，实现负载均衡

```yaml
        heart-beat-timeout: 15000  # 15秒未心跳标记不健康
        ip-delete-timeout: 30000   # 30秒未心跳剔除实例
```

**服务架构：**
```
Nacos注册中心
├── consultation-service（问诊服务）
├── doctor-service（医生服务）
├── schedule-service（排班服务）
```

**面试高频问题：**

**Q1: Nacos的AP模式和CP模式有什么区别？**

| 模式       | 一致性协议 | 适用场景         | 特点                           |
| ---------- | ---------- | ---------------- | ------------------------------ |
| **AP模式** | Distro协议 | 临时实例（默认） | 优先保证可用性，允许数据不一致 |
| **CP模式** | Raft协议   | 持久化实例       | 优先保证一致性，可能牺牲可用性 |

**我们的选择：AP模式（临时实例）**
- 理由：服务实例是临时的，宕机后应该立即剔除
- 可用性优先：即使Nacos集群部分节点故障，服务发现仍可用
- 最终一致性：短暂的数据不一致可接受

**Q2: 服务如何实现健康检查？**

Nacos支持两种健康检查方式：
1. **客户端心跳（默认）**：服务每5秒主动发送心跳
2. **服务端探测（只有配置了持久化实例的情况下）**：Nacos主动调用健康检查接口

```java
// 自定义健康检查
```

### 1.2 Gateway - 服务网关

**核心功能：**
- 统一入口：所有请求先到Gateway
- 路由转发：根据路径转发到不同服务
- 认证鉴权：JWT Token验证
- 限流熔断：保护后端服务
- 日志记录：统一记录请求日志

**路由配置：**
```yaml
spring:
  cloud:
    gateway:
      routes:
        # 问诊服务路由
        - id: consultation-service
          uri: lb://consultation-service  # lb表示负载均衡
          predicates:
            - Path=/api/consultation/**
          filters:
            - StripPrefix=1  # 去掉/api前缀
            - name: DepartmentSlotRateLimiter # 第一层：按科室 + 放号批次限流，保护单批次号源
              args:
                replenishRate: 20            # 单个科室单批次平均每秒放行 20 个请求
                burstCapacity: 40            # 允许短时突发 40 个请求
            - name: RequestRateLimiter       # 第二层：按用户维度限流，防止脚本刷和用户连点
              args:
                key-resolver: "#{@userKeyResolver}"    # 按 userId 限流
                redis-rate-limiter.replenishRate: 2    # 单用户平均每秒允许 2 个请求
                redis-rate-limiter.burstCapacity: 5    # 单用户短时最多允许 5 个请求
                redis-rate-limiter.requestedTokens: 1  # 每个请求消耗 1 个令牌
        
        # 医生服务路由
        - id: doctor-service
          uri: lb://doctor-service
          predicates:
            - Path=/api/doctor/**
          filters:
            - StripPrefix=1
```

**认证鉴权过滤器：**
```java
@Component
public class AuthFilter implements GlobalFilter, Ordered {
    
    @Autowired
    private JwtUtil jwtUtil;
    
    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        ServerHttpRequest request = exchange.getRequest();
        
        // 白名单：登录、注册等接口不需要认证
        if (isWhiteList(request.getPath().value())) {
            return chain.filter(exchange);
        }
        
        // 获取Token
        String token = request.getHeaders().getFirst("Authorization");
        if (token == null || !token.startsWith("Bearer ")) {
            return unauthorized(exchange);
        }
        
        try {
            // 验证Token
            String jwt = token.substring(7);
            Claims claims = jwtUtil.parseToken(jwt);
            String userId = claims.getSubject();
            
            // 将用户信息传递给下游服务
            ServerHttpRequest newRequest = request.mutate()
                .header("X-User-Id", userId)
                .header("X-User-Role", claims.get("role", String.class))
                .build();
            
            return chain.filter(exchange.mutate().request(newRequest).build());
            
        } catch (Exception e) {
            return unauthorized(exchange);
        }
    }
    
    private Mono<Void> unauthorized(ServerWebExchange exchange) {
        exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
        return exchange.getResponse().setComplete();
    }
    
    @Override
    public int getOrder() {
        return -100;  // 优先级最高
    }
}
```

**限流实现（令牌桶算法）：**
```java
@Configuration
public class RateLimiterConfig {

    // 生成科室批次限流 key：departmentId + slotTime
    @Bean
    public Function<ServerWebExchange, String> departmentSlotKeyResolver() {
        return exchange -> {
            String departmentId = exchange.getRequest().getQueryParams().getFirst("departmentId");
            String slotTime = exchange.getRequest().getQueryParams().getFirst("slotTime");
            return departmentId + ":" + slotTime;
        };
    }
    
    // 按用户ID限流
    @Bean
    public KeyResolver userKeyResolver() {
        return exchange -> {
            String userId = exchange.getRequest().getHeaders().getFirst("X-User-Id");
            return Mono.just(userId != null ? userId : "anonymous");
        };
    }
    
    // 按IP限流
    @Bean
    public KeyResolver ipKeyResolver() {
        return exchange -> {
            String ip = exchange.getRequest().getRemoteAddress().getAddress().getHostAddress();
            return Mono.just(ip);
        };
    }
}
```

```java
/**
 * 自定义批次限流过滤器：
 * 先按 departmentId + slotTime 做第一层限流，
 * 再进入 RequestRateLimiter 的 userId 第二层限流。
 */
@Component
public class DepartmentSlotRateLimiterGatewayFilterFactory
        extends AbstractGatewayFilterFactory<DepartmentSlotRateLimiterGatewayFilterFactory.Config> {

    @Autowired
    private StringRedisTemplate stringRedisTemplate;

    @Autowired
    private Function<ServerWebExchange, String> departmentSlotKeyResolver;

    public DepartmentSlotRateLimiterGatewayFilterFactory() {
        super(Config.class);
    }

    @Override
    public GatewayFilter apply(Config config) {
        return (exchange, chain) -> {
            String key = "dept_slot:" + departmentSlotKeyResolver.apply(exchange);
            // 生产里这里一般会配合 Lua 或 RedisRateLimiter 脚本做原子扣减
            Long current = stringRedisTemplate.opsForValue().increment(key);
            stringRedisTemplate.expire(key, Duration.ofSeconds(1));
            if (current != null && current > config.getBurstCapacity()) {
                exchange.getResponse().setStatusCode(HttpStatus.TOO_MANY_REQUESTS);
                return exchange.getResponse().setComplete();
            }
            return chain.filter(exchange);
        };
    }

    @Data
    public static class Config {
        private int replenishRate;
        private int burstCapacity;
    }
}
```

**面试高频问题：**

**Q1: Gateway如何实现限流？**

使用Redis + 令牌桶算法：
1. **令牌生成**：每秒生成N个令牌放入桶中
2. **令牌消费**：每个请求消费1个令牌
3. **桶满丢弃**：桶满时新令牌丢弃
4. **无令牌拒绝**：无令牌时请求被拒绝（429状态码）

**优势：**
- 允许突发流量（桶容量 > 生成速率）
- 分布式限流（基于Redis）
- 灵活配置（按用户、IP、接口限流）

**Q2: 如何传递用户信息到下游服务？**

通过请求头传递：

**Q3: Gateway和Nginx的区别？**

| 对比项   | Gateway                | Nginx              |
| -------- | ---------------------- | ------------------ |
| 层级     | 应用层网关             | 反向代理           |
| 功能     | 路由、限流、熔断、认证 | 负载均衡、静态资源 |
| 动态路由 | 支持（从Nacos获取）    | 需要重启           |
| 集成     | 与Spring Cloud无缝集成 | 独立组件           |
| 适用场景 | 微服务网关             | 入口负载均衡       |

**实际架构：**
```
用户请求 → Nginx（负载均衡） → Gateway集群 → 微服务
```

### 1.3 Sentinel - 服务熔断降级

**核心功能：**
- 流量控制：QPS限流、并发线程数限流
- 熔断降级：异常比例、慢调用比例
- 热点参数限流：针对特定参数限流
- 系统自适应保护：根据系统负载自动限流

**业务代码使用：**
```java
@Service
public class QueueService {
    
    @Autowired
    private QueueMapper queueMapper;
    
    @Autowired
    private DepartmentMapper departmentMapper;
    
    @Autowired
    private StringRedisTemplate stringRedisTemplate;
    
    @Autowired
    private RedisTemplate<String, Object> redisTemplate;
    
    // 查询科室叫号列表
    @SentinelResource(
        value = "queryDepartmentQueue",
        blockHandler = "handleQueueBlock",      // 限流/熔断时调用
        fallback = "handleQueueFallback"        // 业务异常时调用
    )
    public List<QueueInfoDTO> queryDepartmentQueue(String departmentId, String clinicDate) {
        return queueMapper.selectByDepartmentAndDate(departmentId, clinicDate);
    }
    
    // 查询接口被限流/熔断时走缓存兜底
    public List<QueueInfoDTO> handleQueueBlock(String departmentId, String clinicDate, BlockException e) {
        log.warn("查询科室叫号被限流，departmentId: {}, 异常: {}",
                departmentId, e.getClass().getSimpleName());
        
        String cacheKey = "queue:" + departmentId + ":" + clinicDate;
        List<QueueInfoDTO> cached = (List<QueueInfoDTO>) redisTemplate.opsForValue().get(cacheKey);
        if (cached != null) {
            return cached;
        }
        
        return Collections.emptyList();
    }
    
    public List<QueueInfoDTO> handleQueueFallback(String departmentId, String clinicDate, Throwable e) {
        log.error("查询科室叫号异常，departmentId: {}, 异常: {}",
                departmentId, e.getMessage());
        
        String cacheKey = "queue:" + departmentId + ":" + clinicDate;
        List<QueueInfoDTO> cached = (List<QueueInfoDTO>) redisTemplate.opsForValue().get(cacheKey);
        return cached != null ? cached : Collections.emptyList();
    }
    
    // 用户抢号
    @SentinelResource(
        value = "grabAppointment",
        blockHandler = "handleGrabBlock",
        fallback = "handleGrabFallback"
    )
    public String grabAppointment(String userId, String departmentId, String slotTime) {
        String stockKey = "stock:" + departmentId + ":" + slotTime;
        String userKey = "grab:" + userId + ":" + departmentId + ":" + slotTime;
        
        // 防止同一用户重复抢同一批号源
        if (Boolean.TRUE.equals(stringRedisTemplate.hasKey(userKey))) {
            return "请勿重复抢号";
        }
        
        // Redis + Lua 原子扣减库存
        Long result = deductStock(stockKey);
        if (result == null || result <= 0) {
            return "号已抢完";
        }
        
        // 记录抢号标记，防止重复提交
        stringRedisTemplate.opsForValue().set(userKey, "1", Duration.ofMinutes(15));
        
        // 创建待支付预约单
        queueMapper.insertAppointment(userId, departmentId, slotTime, "UNPAID");
        return "抢号成功，请尽快支付";
    }
    
    public String handleGrabBlock(String userId, String departmentId, String slotTime, BlockException e) {
        log.warn("用户抢号被限流，userId: {}, departmentId: {}, 异常: {}",
                userId, departmentId, e.getClass().getSimpleName());
        return "当前抢号人数过多，请稍后重试";
    }
    
    public String handleGrabFallback(String userId, String departmentId, String slotTime, Throwable e) {
        log.error("用户抢号异常，userId: {}, departmentId: {}, 异常: {}",
                userId, departmentId, e.getMessage());
        return "系统繁忙，请稍后再试";
    }
    
    @SentinelResource(value = "queryDepartmentInfo")
    public DepartmentDTO queryDepartmentInfo(String departmentId) {
        return departmentMapper.selectById(departmentId);
    }
    
    private Long deductStock(String stockKey) {
        DefaultRedisScript<Long> script = new DefaultRedisScript<>();
        script.setScriptText("""
            local stock = tonumber(redis.call('GET', KEYS[1]) or '0')
            if stock <= 0 then
                return 0
            end
            redis.call('DECR', KEYS[1])
            return 1
        """);
        script.setResultType(Long.class);
        
        return stringRedisTemplate.execute(script, Collections.singletonList(stockKey));
    }
}
```

**面试高频问题：**

**Q1: Sentinel和Hystrix的区别？**

| 对比项   | Sentinel             | Hystrix                 |
| -------- | -------------------- | ----------------------- |
| 维护状态 | 活跃维护             | 已停止维护              |
| 隔离策略 | 信号量隔离           | 线程池隔离 + 信号量隔离 |
| 熔断策略 | 异常比例、慢调用比例 | 异常比例                |
| 实时监控 | 支持（控制台）       | 需要额外组件            |
| 规则配置 | 动态配置（Nacos）    | 静态配置                |
| 性能     | 更好（无线程池开销） | 线程池有开销            |

**我们选择Sentinel的原因：**
1. 官方推荐，Spring Cloud Alibaba生态
2. 动态规则配置，无需重启
3. 可视化控制台，实时监控
4. 性能更好，资源消耗更低

**Q2: 熔断后如何恢复？**

Sentinel的熔断恢复机制（半开状态）：
```
正常状态 → 熔断状态（timeWindow秒） → 半开状态 → 正常状态/熔断状态
```

**流程：**
1. **触发熔断**：异常比例/慢调用比例超过阈值
2. **熔断期**：所有请求直接走降级方法，持续timeWindow秒
3. **半开状态**：熔断期结束后，放行1个请求
4. **恢复判断**：
   - 请求成功 → 恢复正常状态
   - 请求失败 → 继续熔断

**Q3: 如何选择限流策略？**

| 场景        | 策略           | 原因                       |
| ----------- | -------------- | -------------------------- |
| 查询接口    | QPS限流        | 保护数据库，防止慢查询堆积 |

| 外部API调用 | 并发线程数限流 | 避免占满线程池             |
| 热点数据    | 热点参数限流   | 防止某个热点被刷           |

**Q4: 写入接口做了限流，还需要加锁吗？**

**答案：需要！限流和锁解决的是不同问题，不能互相替代。**

**限流 vs 锁的区别：**

| 维度         | 限流（Sentinel）                   | 锁（乐观锁/悲观锁）  |
| ------------ | ---------------------------------- | -------------------- |
| **目的**     | 保护系统资源（线程池、数据库连接） | 保证数据一致性       |
| **作用范围** | 控制并发请求数量                   | 控制数据修改的正确性 |
| **解决问题** | 防止系统过载                       | 防止并发修改冲突     |

**典型场景分析：**

**场景1：库存扣减（必须加锁）**
```java
// ❌ 只有限流，不够！
@SentinelResource(value = "deductInventory")
public void deductInventory(Long productId, int quantity) {
    Inventory inv = inventoryMapper.selectById(productId);
    if (inv.getStock() >= quantity) {
        inv.setStock(inv.getStock() - quantity);
        inventoryMapper.updateById(inv);  // 并发问题：超卖！
    }
}

// ✅ 限流 + 乐观锁
@SentinelResource(value = "deductInventory")
public void deductInventory(Long productId, int quantity) {
    Inventory inv = inventoryMapper.selectById(productId);
    if (inv.getStock() >= quantity) {
        inv.setStock(inv.getStock() - quantity);
        // 乐观锁：WHERE id = ? AND version = ?
        int updated = inventoryMapper.updateByIdWithVersion(inv);
        if (updated == 0) {
            throw new ConcurrentModificationException("库存已被修改");
        }
    }
}
```

**为什么限流不够？**
- 限流只控制了**20个线程同时执行**
- 但这20个线程**仍然可能同时读取同一条库存记录**
- 导致超卖问题

**场景2：账户余额扣减（必须加锁）**
```java
// ✅ 限流 + 悲观锁
@SentinelResource(value = "deductBalance")
@Transactional
public void deductBalance(Long userId, BigDecimal amount) {
    // SELECT ... FOR UPDATE（悲观锁）
    Account account = accountMapper.selectByIdForUpdate(userId);
    if (account.getBalance().compareTo(amount) >= 0) {
        account.setBalance(account.getBalance().subtract(amount));
        accountMapper.updateById(account);
    }
}
```

**场景3：日志记录（可能不需要锁）**
```java
// ✅ 只需要限流
@SentinelResource(value = "saveLog")
public void saveLog(OperationLog log) {
    logMapper.insert(log);  // 每条日志独立，无并发冲突
}
```

**决策树：**
```
写入接口
  ↓
是否存在并发修改同一数据？
  ↓ 是
需要加锁（乐观锁/悲观锁）
  ↓ 否
只需要限流
```

**写入接口的完整保护方案：**
```java
@Service
public class OrderService {
    
    // 1. Sentinel限流：保护系统资源
    @SentinelResource(
        value = "createOrder",
        blockHandler = "handleBlock"
    )
    // 2. 分布式锁：防止重复提交
    @RedisLock(key = "#userId + ':' + #productId")
    // 3. 事务 + 乐观锁：保证数据一致性
    @Transactional
    public void createOrder(Long userId, Long productId) {
        // 业务逻辑
    }
    
    public void handleBlock(Long userId, Long productId, BlockException e) {
        throw new BusinessException("系统繁忙，请稍后重试");
    }
}
```

**总结：限流是第一道防线（保护系统），锁是第二道防线（保护数据）。**

**Q8: 技术选型决策 ⭐⭐**

**为什么选Sentinel而不是Hystrix？**

| 对比项       | Sentinel               | Hystrix                 |
| ------------ | ---------------------- | ----------------------- |
| **维护状态** | ✅ 活跃维护（阿里开源） | ❌ 已停止维护（2018年）  |
| **隔离策略** | 信号量隔离             | 线程池隔离 + 信号量隔离 |
| **性能**     | ✅ 更好（无线程池开销） | 线程池有上下文切换开销  |
| **规则配置** | ✅ 动态配置（Nacos）    | 静态配置，需重启        |
| **控制台**   | ✅ 官方控制台           | 需要额外组件（Turbine） |
| **生态**     | ✅ Spring Cloud Alibaba | Spring Cloud Netflix    |

**决策理由：**
1. Hystrix已停止维护，未来无法获得支持
2. Sentinel性能更好，单机QPS可达10000+
3. Sentinel支持动态规则，运维更友好
4. 项目使用Spring Cloud Alibaba生态，Sentinel是官方推荐

**为什么选Outbox而不是RocketMQ事务消息？**

| 对比项         | Outbox + RabbitMQ         | RocketMQ事务消息     |
| -------------- | ------------------------- | -------------------- |
| **实现复杂度** | ✅ 简单（本地表+定时任务） | 需要实现回查接口     |
| **切换成本**   | ✅ 低（已有RabbitMQ）      | 高（需引入RocketMQ） |
| **实时性**     | 1-2秒延迟                 | ✅ 实时（无轮询）     |
| **可控性**     | ✅ 高（代码可控）          | 依赖MQ特性           |
| **运维成本**   | ✅ 低（复用现有MQ）        | 高（新增组件）       |

**决策理由：**
1. 项目已使用RabbitMQ，切换到RocketMQ成本高
2. 预约场景对实时性要求不高（2秒延迟可接受）
3. Outbox实现简单，团队容易理解和维护
4. 可以复用现有的MQ基础设施和监控

## 二、分布式问题解决方案 ⭐⭐⭐⭐⭐

### 2.1 分布式事务

**业务场景：用户预约挂号**
```
用户预约 → 扣减号源 → 创建订单 → 发送通知
涉及3个服务：排班服务、订单服务、通知服务
如何保证一致性？
```

**方案对比：**

| 方案                     | 一致性   | 性能 | 复杂度 | 适用场景       |
| ------------------------ | -------- | ---- | ------ | -------------- |
| **Seata AT模式**         | 强一致   | 低   | 中     | 金融、支付     |
| **TCC**                  | 强一致   | 中   | 高     | 金融、核心业务 |
| **本地消息表（Outbox）** | 最终一致 | 高   | 低     | 互联网业务     |
| **RabbitMQ事务消息**     | 最终一致 | 高   | 低     | 异步通知       |

**我们的选择：Outbox模式**

**理由：**
1. 互联网医院对实时性要求不高（最终一致性即可）
2. 已有RabbitMQ基础设施，可复用
3. 开发成本低，可靠性高
4. 性能好，不影响主流程

**实现方案：**
```java
// 预约服务
@Service
public class AppointmentService {
    
    @Autowired
    private AppointmentMapper appointmentMapper;
    
    @Autowired
    private OutboxService outboxService;
    
    @Transactional
    public void createAppointment(AppointmentDTO dto) {
        // 1. 创建预约记录
        Appointment appointment = new Appointment();
        appointment.setUserId(dto.getUserId());
        appointment.setDoctorId(dto.getDoctorId());
        appointment.setScheduleId(dto.getScheduleId());
        appointment.setStatus("PENDING");
        appointmentMapper.insert(appointment);
        
        // 2. 插入Outbox事件（同一事务）
        outboxService.enqueue(
            "APPOINTMENT_CREATED",
            appointment.getId(),
            JSON.toJSONString(appointment),
            "appointment.exchange",
            "appointment.created"
        );
        
        // 事务提交后，Outbox异步发送MQ
    }
}

// 排班服务消费MQ
@Service
public class ScheduleConsumer {
    
    @RabbitListener(queues = "appointment.created.queue")
    public void handleAppointmentCreated(Message message, Channel channel) {
        try {
            Appointment appointment = JSON.parseObject(
                new String(message.getBody()), Appointment.class);
            
            // 扣减号源
            scheduleService.decreaseQuota(appointment.getScheduleId());
            
            // 手动ACK
            channel.basicAck(message.getMessageProperties().getDeliveryTag(), false);

            log.error("处理预约事件失败", e);
            // 重试或进入死信队列
            channel.basicNack(message.getMessageProperties().getDeliveryTag(), false, false);
        }
```

- 异步发送MQ，不阻塞主流程

- 消费者手动ACK，保证消息不丢失

**补充：TCC模式 - 金融核心业务场景**

**业务场景：用户充值到账户余额**
```
用户充值 → 第三方支付扣款 → 账户余额增加 → 记录流水
涉及3个服务：支付服务、账户服务、流水服务
要求：强一致性，不能出现扣款成功但余额未增加的情况
```

**为什么选择TCC而不是AT？**

| 对比项   | Seata AT         | TCC                  |
| -------- | ---------------- | -------------------- |
| 锁定资源 | 数据库行锁       | 业务资源（冻结金额） |
| 锁定时长 | 整个事务期间     | 仅Try阶段            |
| 性能     | 低（长时间持锁） | 高（不持数据库锁）   |
| 适用场景 | 短事务           | 长事务、跨异构系统   |

**TCC实现方案：**

```java
// ========== 1. 账户服务 - TCC接口 ==========
@LocalTCC
public interface AccountTccService {
    
    /**
     * Try阶段：冻结金额
     */
    @TwoPhaseBusinessAction(
        name = "accountTcc",
        commitMethod = "confirm",
        rollbackMethod = "cancel"
    )
    boolean tryFreeze(
        @BusinessActionContextParameter(paramName = "userId") Long userId,
        @BusinessActionContextParameter(paramName = "amount") BigDecimal amount,
        @BusinessActionContextParameter(paramName = "bizId") String bizId
    );
    
    /**
     * Confirm阶段：确认扣款
     */
    boolean confirm(BusinessActionContext context);
    
    /**
     * Cancel阶段：解冻金额
     */
    boolean cancel(BusinessActionContext context);
}

// ========== 2. 账户服务 - TCC实现 ==========
@Service
public class AccountTccServiceImpl implements AccountTccService {
    
    @Autowired
    private AccountMapper accountMapper;
    
    @Autowired
    private AccountFreezeMapper freezeMapper;
    
    @Override
    @Transactional
    public boolean tryFreeze(Long userId, BigDecimal amount, String bizId) {
        // 1. 检查是否重复Try（幂等性）
        AccountFreeze existing = freezeMapper.selectByBizId(bizId);
        if (existing != null) {
            return true;  // 已经Try过，直接返回成功
        }
        
        // 2. 检查余额是否足够
        Account account = accountMapper.selectByIdForUpdate(userId);
        if (account.getBalance().compareTo(amount) < 0) {
            throw new BusinessException("余额不足");
        }
        
        // 3. 冻结金额（不实际扣减）
        account.setBalance(account.getBalance().subtract(amount));
        account.setFrozenAmount(account.getFrozenAmount().add(amount));
        accountMapper.updateById(account);
        
        // 4. 记录冻结记录
        AccountFreeze freeze = new AccountFreeze();
        freeze.setUserId(userId);
        freeze.setAmount(amount);
        freeze.setBizId(bizId);
        freeze.setStatus("TRY");
        freezeMapper.insert(freeze);
        
        log.info("Try阶段成功，冻结金额：{}", amount);
        return true;
    }
    
    @Override
    @Transactional
    public boolean confirm(BusinessActionContext context) {
        Long userId = context.getActionContext("userId", Long.class);
        BigDecimal amount = context.getActionContext("amount", BigDecimal.class);
        String bizId = context.getActionContext("bizId", String.class);
        
        // 1. 检查是否已经Confirm（幂等性）
        AccountFreeze freeze = freezeMapper.selectByBizId(bizId);
        if (freeze == null) {
            return true;  // 已经处理过，直接返回成功
        }
        if ("CONFIRM".equals(freeze.getStatus())) {
            return true;  // 已经Confirm过
        }
        
        // 2. 确认扣款：减少冻结金额
        Account account = accountMapper.selectByIdForUpdate(userId);
        account.setFrozenAmount(account.getFrozenAmount().subtract(amount));
        accountMapper.updateById(account);
        
        // 3. 更新冻结记录状态
        freeze.setStatus("CONFIRM");
        freezeMapper.updateById(freeze);
        
        // 4. 删除冻结记录（可选，也可以保留用于审计）
        freezeMapper.deleteById(freeze.getId());
        
        log.info("Confirm阶段成功，扣减金额：{}", amount);
        return true;
    }
    
    @Override
    @Transactional
    public boolean cancel(BusinessActionContext context) {
        Long userId = context.getActionContext("userId", Long.class);
        BigDecimal amount = context.getActionContext("amount", BigDecimal.class);
        String bizId = context.getActionContext("bizId", String.class);
        
        // 1. 检查是否已经Cancel（幂等性）
        AccountFreeze freeze = freezeMapper.selectByBizId(bizId);
        if (freeze == null) {
            return true;  // 已经处理过
        }
        if ("CANCEL".equals(freeze.getStatus())) {
            return true;  // 已经Cancel过
        }
        
        // 2. 解冻金额：恢复余额
        Account account = accountMapper.selectByIdForUpdate(userId);
        account.setBalance(account.getBalance().add(amount));
        account.setFrozenAmount(account.getFrozenAmount().subtract(amount));
        accountMapper.updateById(account);
        
        // 3. 更新冻结记录状态
        freeze.setStatus("CANCEL");
        freezeMapper.updateById(freeze);
        
        // 4. 删除冻结记录
        freezeMapper.deleteById(freeze.getId());
        
        log.info("Cancel阶段成功，解冻金额：{}", amount);
        return true;
    }
}

// ========== 3. 充值服务 - 编排TCC事务 ==========
@Service
public class RechargeService {
    
    @Autowired
    private AccountTccService accountTccService;
    
    @Autowired
    private PaymentService paymentService;
    
    @Autowired
    private TransactionLogService logService;
    
    @GlobalTransactional  // Seata全局事务
    public void recharge(Long userId, BigDecimal amount) {
        String bizId = UUID.randomUUID().toString();
        
        try {
            // 1. Try阶段：冻结账户金额
            accountTccService.tryFreeze(userId, amount, bizId);
            
            // 2. 调用第三方支付（可能耗时较长）
            PaymentResult result = paymentService.pay(userId, amount);
            if (!result.isSuccess()) {
                throw new BusinessException("支付失败：" + result.getMessage());
            }
            
            // 3. 记录流水
            logService.recordRecharge(userId, amount, bizId);
            
            // 4. 全局事务提交 → 自动调用所有Confirm方法
            log.info("充值成功，用户：{}，金额：{}", userId, amount);
            
        } catch (Exception e) {
            log.error("充值失败，用户：{}，金额：{}", userId, amount, e);
            // 全局事务回滚 → 自动调用所有Cancel方法
            throw e;
        }
    }
}

-- 账户表
CREATE TABLE account (
    id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    balance DECIMAL(20, 2) NOT NULL DEFAULT 0,      -- 可用余额
    frozen_amount DECIMAL(20, 2) NOT NULL DEFAULT 0, -- 冻结金额

    INDEX idx_user_id (user_id)

    amount DECIMAL(20, 2) NOT NULL,
    biz_id VARCHAR(64) NOT NULL UNIQUE,  -- 业务ID（幂等性）
    status VARCHAR(20) NOT NULL,         -- TRY/CONFIRM/CANCEL
    create_time DATETIME NOT NULL,
    INDEX idx_biz_id (biz_id)
);
*/
```

**TCC三阶段详解：**

| 阶段        | 操作     | 数据库状态                     | 说明                 |
| ----------- | -------- | ------------------------------ | -------------------- |
| **Try**     | 冻结金额 | balance减少，frozen_amount增加 | 预留资源，不实际扣款 |
| **Confirm** | 确认扣款 | frozen_amount减少              | 确认业务，释放冻结   |
| **Cancel**  | 解冻金额 | balance增加，frozen_amount减少 | 回滚业务，恢复资源   |

**TCC关键点：**

1. **幂等性**：每个阶段都要检查是否已执行，防止重复调用
2. **空回滚**：Cancel可能在Try之前执行（网络延迟），需要处理
3. **悬挂**：Try在Cancel之后执行，需要拒绝
4. **资源预留**：Try阶段只预留资源，不实际扣减

**TCC vs Outbox 选择建议：**

```
强一致性 + 跨异构系统 → TCC
强一致性 + 纯数据库操作 + 短事务 → Seata AT
最终一致性 + 异步场景 → Outbox + MQ
```

**问题1：TCC空回滚导致资金异常**

**现象：**
- Try阶段因网络超时未执行
- Seata认为Try失败，触发Cancel
- Cancel先于Try执行，导致账户余额异常增加

**问题代码：**
```java
@Override
@Transactional
public boolean cancel(BusinessActionContext context) {
    String bizId = context.getActionContext("bizId", String.class);
    
    // ❌ 没有检查Try是否执行过
    AccountFreeze freeze = freezeMapper.selectByBizId(bizId);
    
    // freeze为null，说明Try未执行，但仍然执行了解冻逻辑
    Account account = accountMapper.selectByIdForUpdate(userId);
    account.setBalance(account.getBalance().add(amount));  // 余额异常增加！
    accountMapper.updateById(account);
}
```

**解决方案：**
```java
@Override
@Transactional
public boolean cancel(BusinessActionContext context) {
    Long userId = context.getActionContext("userId", Long.class);
    BigDecimal amount = context.getActionContext("amount", BigDecimal.class);
    String bizId = context.getActionContext("bizId", String.class);
    
    // 1. 检查Try是否执行过
    AccountFreeze freeze = freezeMapper.selectByBizId(bizId);
    
    if (freeze == null) {
        // 空回滚：Try未执行，Cancel先执行
        // 记录空回滚标记，防止后续Try执行
        AccountFreeze emptyRollback = new AccountFreeze();
        emptyRollback.setBizId(bizId);
        emptyRollback.setStatus("EMPTY_ROLLBACK");
        emptyRollback.setUserId(userId);
        emptyRollback.setAmount(BigDecimal.ZERO);
        freezeMapper.insert(emptyRollback);
        
        log.warn("空回滚，bizId: {}", bizId);
        return true;  // 直接返回成功
    }
    
    // 2. 检查是否已经Cancel过（幂等性）
    if ("CANCEL".equals(freeze.getStatus())) {
        return true;
    }
    
    // 3. 正常解冻
    Account account = accountMapper.selectByIdForUpdate(userId);
    account.setBalance(account.getBalance().add(amount));
    account.setFrozenAmount(account.getFrozenAmount().subtract(amount));
    accountMapper.updateById(account);
    
    freeze.setStatus("CANCEL");
    freezeMapper.updateById(freeze);
    
    log.info("Cancel成功，解冻金额: {}", amount);
    return true;
}

// Try阶段也要检查空回滚标记

        return false;
    }
    
    // 2. 正常Try逻辑
    // ...
}
```

- 彻底解决空回滚问题
- 防止悬挂（Try在Cancel之后执行）
- 资金账户数据100%准确

```java
// 2. 增加补偿任务，清理悬挂事务
@Component
public class TccCompensationTask {
    
    @Scheduled(cron = "0 */10 * * * ?")  // 每10分钟执行
    public void compensateHangingTransaction() {
        // 查询超过1小时的Try状态记录
        List<AccountFreeze> hangingList = freezeMapper.selectList(
            new QueryWrapper<AccountFreeze>()
                .eq("status", "TRY")
                .lt("create_time", LocalDateTime.now().minusHours(1))
        );
        
        for (AccountFreeze freeze : hangingList) {
            try {
                // 查询Seata全局事务状态
                GlobalStatus status = getGlobalTransactionStatus(freeze.getXid());
                
                if (status == GlobalStatus.TimeoutRollbacked) {
                    // 全局事务已超时回滚，执行Cancel补偿
                    compensateCancel(freeze);
                    log.info("补偿Cancel成功，bizId: {}", freeze.getBizId());
                }
            } catch (Exception e) {
                log.error("补偿失败，bizId: {}", freeze.getBizId(), e);
            }
        }
    }
    
    private void compensateCancel(AccountFreeze freeze) {
        // 解冻金额
        Account account = accountMapper.selectByIdForUpdate(freeze.getUserId());
        account.setBalance(account.getBalance().add(freeze.getAmount()));
        account.setFrozenAmount(account.getFrozenAmount().subtract(freeze.getAmount()));
        accountMapper.updateById(account);
        
        // 更新状态
        freeze.setStatus("COMPENSATE_CANCEL");
        freezeMapper.updateById(freeze);
    }
}
```

**问题3：Outbox消息重复消费导致号源多扣**

**现象：**
- 用户预约1次，号源被扣减2次
- 排查发现MQ消息被重复消费

**问题代码：**

**解决方案：**
```java
// 1. 增加消费记录表
CREATE TABLE mq_consume_log (
    id BIGINT PRIMARY KEY,
    message_id VARCHAR(64) NOT NULL UNIQUE,  -- 消息唯一ID
    consumer VARCHAR(100) NOT NULL,          -- 消费者
    status VARCHAR(20) NOT NULL,             -- SUCCESS/FAIL
    create_time DATETIME NOT NULL,
    INDEX idx_message_id (message_id)
);

// 2. 消费者增加幂等性控制
@RabbitListener(queues = "appointment.created.queue")
@Transactional
public void handleAppointmentCreated(Message message, Channel channel) {
    String messageId = message.getMessageProperties().getMessageId();
    
    // 检查是否已消费
    MqConsumeLog log = consumeLogMapper.selectByMessageId(messageId);
    if (log != null && "SUCCESS".equals(log.getStatus())) {
        log.info("消息已消费，跳过，messageId: {}", messageId);
        channel.basicAck(message.getMessageProperties().getDeliveryTag(), false);
        return;
    }
    
    try {
        Appointment appointment = JSON.parseObject(
            new String(message.getBody()), Appointment.class);
        
        // 扣减号源
        scheduleService.decreaseQuota(appointment.getScheduleId());
        
        // 记录消费成功
        MqConsumeLog consumeLog = new MqConsumeLog();
        consumeLog.setMessageId(messageId);
        consumeLog.setConsumer("ScheduleConsumer");
        consumeLog.setStatus("SUCCESS");
        consumeLogMapper.insert(consumeLog);
        
        // 手动ACK
        channel.basicAck(message.getMessageProperties().getDeliveryTag(), false);
        
    } catch (Exception e) {
        log.error("消费失败，messageId: {}", messageId, e);
        
        // 记录消费失败
        MqConsumeLog consumeLog = new MqConsumeLog();
        consumeLog.setMessageId(messageId);
        consumeLog.setConsumer("ScheduleConsumer");
        consumeLog.setStatus("FAIL");
        consumeLogMapper.insert(consumeLog);
        
        // NACK，重新入队
        channel.basicNack(message.getMessageProperties().getDeliveryTag(), false, true);
    }
}
```

**效果：**
- 消息重复消费率从5%降到0%
- 号源扣减100%准确
- 无用户投诉

### 2.2 分布式锁

**业务场景1：医生排班冲突**
```
问题：同一时间段，医生只能排一个班
并发场景：多个管理员同时给医生排班
```

**解决方案：Redisson分布式锁**
```java
@Service
public class ScheduleService {
    
    @Autowired
    private RedissonClient redissonClient;
    
    @Transactional
    public void createSchedule(ScheduleDTO dto) {
        String lockKey = "schedule:" + dto.getDoctorId() + ":" + dto.getTimeSlot();
        RLock lock = redissonClient.getLock(lockKey);
        
        try {
            // 等待3秒，持锁10秒自动释放
            if (lock.tryLock(3, 10, TimeUnit.SECONDS)) {
                // 检查是否已排班
                Schedule existing = scheduleMapper.selectByDoctorAndTime(
                    dto.getDoctorId(), dto.getTimeSlot());
                if (existing != null) {
                    throw new BusinessException("该时间段已排班");
                }
                
                // 创建排班记录
                Schedule schedule = new Schedule();
                schedule.setDoctorId(dto.getDoctorId());
                schedule.setTimeSlot(dto.getTimeSlot());
                schedule.setQuota(dto.getQuota());
                scheduleMapper.insert(schedule);
                
                log.info("排班成功，医生：{}，时间：{}", dto.getDoctorId(), dto.getTimeSlot());
            } else {
                throw new BusinessException("系统繁忙，请稍后重试");
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new BusinessException("操作被中断");
        } finally {
            // 只释放自己持有的锁
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
}
```

### 2.3 分布式ID生成

**业务场景：订单号、预约号生成**

**方案对比：**

| 方案           | 优点             | 缺点               | 适用场景         |
| -------------- | ---------------- | ------------------ | ---------------- |
| **UUID**       | 简单、无依赖     | 无序、占用空间大   | 不适合数据库主键 |
| **数据库自增** | 简单、有序       | 性能瓶颈、单点故障 | 小规模系统       |
| **Redis INCR** | 性能高           | 依赖Redis          | 中等规模         |
| **雪花算法**   | 高性能、趋势递增 | 依赖时钟           | 大规模分布式系统 |

**我们的选择：雪花算法（Snowflake）**

**结构：64位Long**
```
1位符号位 + 41位时间戳 + 10位机器ID + 12位序列号
0 - 0000000000 0000000000 0000000000 0000000000 0 - 0000000000 - 000000000000
```

**优势：**
- 趋势递增：有利于数据库索引
- 高性能：单机100万/秒
- 无依赖：不依赖数据库或Redis
- 信息量：包含时间戳，可反推生成时间

**实现：**
```java
@Component
public class SnowflakeIdGenerator {
    
    private final long workerId;
    private final long datacenterId;
    private long sequence = 0L;
    private long lastTimestamp = -1L;
    
    // 时间戳占41位，起始时间2020-01-01
    private final long twepoch = 1577808000000L;
    
    public SnowflakeIdGenerator(@Value("${snowflake.worker-id}") long workerId,
                                @Value("${snowflake.datacenter-id}") long datacenterId) {
        this.workerId = workerId;
        this.datacenterId = datacenterId;
    }
    
    public synchronized long nextId() {
        long timestamp = System.currentTimeMillis();
        
        // 时钟回拨检查
        if (timestamp < lastTimestamp) {
            throw new RuntimeException("时钟回拨，拒绝生成ID");
        }
        
        // 同一毫秒内，序列号递增
        if (timestamp == lastTimestamp) {
            sequence = (sequence + 1) & 4095;  // 12位序列号，最大4095
            if (sequence == 0) {
                // 序列号用完，等待下一毫秒
                timestamp = waitNextMillis(lastTimestamp);
            }
        } else {
            sequence = 0L;
        }
        
        lastTimestamp = timestamp;
        
        // 组装ID
        return ((timestamp - twepoch) << 22)
            | (datacenterId << 17)
            | (workerId << 12)
            | sequence;
    }
    
    private long waitNextMillis(long lastTimestamp) {
        long timestamp = System.currentTimeMillis();
        while (timestamp <= lastTimestamp) {
            timestamp = System.currentTimeMillis();
        }
        return timestamp;
    }
}
```

**使用：**
```java

    private SnowflakeIdGenerator idGenerator;
    
    public void createOrder(OrderDTO dto) {
        Order order = new Order();
        order.setOrderId(String.valueOf(idGenerator.nextId()));
        // ...
    }
}
```

**注意事项：**
1. **机器ID配置**：每个实例配置不同的workerId
2. **时钟回拨**：检测到时钟回拨，拒绝生成ID或等待
3. **序列号用完**：等待下一毫秒

## 五、性能优化 ⭐⭐⭐⭐

### 5.1 多级缓存策略

**缓存架构：**
```
请求 → 本地缓存（Caffeine） → Redis缓存 → 数据库
```

**实现：**
```java
@Service
public class DoctorService {
    
    @Autowired
    private DoctorMapper doctorMapper;
    
    @Autowired
    private RedisTemplate<String, Object> redisTemplate;
    
    // 本地缓存（Caffeine）
    private final Cache<String, DoctorDTO> localCache = Caffeine.newBuilder()
        .maximumSize(1000)           // 最多1000条
        .expireAfterWrite(5, TimeUnit.MINUTES)  // 5分钟过期
        .build();
    
    public DoctorDTO getDoctorInfo(String doctorId) {
        // 1. 查询本地缓存
        DoctorDTO doctor = localCache.getIfPresent(doctorId);
        if (doctor != null) {
            log.debug("命中本地缓存，doctorId: {}", doctorId);
            return doctor;
        }
        
        // 2. 查询Redis缓存
        String cacheKey = "doctor:" + doctorId;
        doctor = (DoctorDTO) redisTemplate.opsForValue().get(cacheKey);
        if (doctor != null) {
            log.debug("命中Redis缓存，doctorId: {}", doctorId);
            localCache.put(doctorId, doctor);  // 回写本地缓存
            return doctor;
        }
        
        // 3. 查询数据库
        doctor = doctorMapper.selectById(doctorId);
        if (doctor != null) {
            // 写入Redis（30分钟过期）
            redisTemplate.opsForValue().set(cacheKey, doctor, 30, TimeUnit.MINUTES);
            // 写入本地缓存
            localCache.put(doctorId, doctor);
        }
        
        return doctor;
    }
    
    // 更新医生信息时，清除缓存
    public void updateDoctorInfo(DoctorDTO dto) {
        doctorMapper.updateById(dto);
        
        // 清除本地缓存
        localCache.invalidate(dto.getId());
        
        // 清除Redis缓存
        redisTemplate.delete("doctor:" + dto.getId());
        
        // 发送MQ通知其他实例清除本地缓存
        rabbitTemplate.convertAndSend("cache.exchange", "cache.invalidate", dto.getId());
    }
}
```

**缓存数据分类：**

| 数据类型 | 缓存策略   | 过期时间 | 理由                 |
| -------- | ---------- | -------- | -------------------- |
| 医生信息 | 本地+Redis | 30分钟   | 变更频率低，查询频繁 |
| 科室列表 | 本地+Redis | 1小时    | 几乎不变             |

### 5.2 数据库优化

#### 5.2.1 读写分离

**架构：**
```
写操作 → 主库（Master）
读操作 → 从库（Slave1、Slave2）
```

**配置（ShardingSphere）：**
```yaml
spring:
  shardingsphere:
    datasource:
      names: master,slave1,slave2
      master:
        type: com.zaxxer.hikari.HikariDataSource
        driver-class-name: com.mysql.cj.jdbc.Driver
        jdbc-url: jdbc:mysql://master:3306/medical
      slave1:
        jdbc-url: jdbc:mysql://slave1:3306/medical
      slave2:
        jdbc-url: jdbc:mysql://slave2:3306/medical
    
    rules:
      readwrite-splitting:
        data-sources:
          medical_ds:
            type: Static
            props:
              write-data-source-name: master
              read-data-source-names: slave1,slave2
              load-balancer-name: round_robin
        load-balancers:
          round_robin:
            type: ROUND_ROBIN  # 轮询
```

**强制主库查询：**
```java
@Service
public class AppointmentService {
    
    // 场景：创建预约后立即查询，需要强制走主库
    @Transactional
    public AppointmentDTO createAndQuery(AppointmentDTO dto) {
        // 创建预约（写主库）
        appointmentMapper.insert(dto);
        
        // 立即查询（强制主库，避免主从延迟）
        HintManager.getInstance().setWriteRouteOnly();
        try {
            return appointmentMapper.selectById(dto.getId());
        } finally {
            HintManager.clear();
        }
    }
}
```

#### 5.2.2 分库分表

**场景：订单表数据量大**
```
订单表：1000万条/年
预计3年：3000万条
单表性能下降
```

**分表策略：按月分表**
```yaml
spring:
  shardingsphere:
    rules:
      sharding:
        tables:
          appointment:
            actual-data-nodes: medical_ds.appointment_$->{2024..2026}_$->{01..12}
            table-strategy:
              standard:
                sharding-column: create_time
                sharding-algorithm-name: appointment_month
        sharding-algorithms:
          appointment_month:
            type: INTERVAL
            props:
              datetime-pattern: yyyy-MM-dd HH:mm:ss
              datetime-interval-amount: 1
              datetime-interval-unit: MONTHS
```

**查询优化：**
```java
// 带分片键查询（高效）
appointmentMapper.selectByCreateTime("2024-01-15");  // 只查appointment_2024_01

// 不带分片键查询（全表扫描，慢）
appointmentMapper.selectByUserId("user123");  // 扫描所有分表
```

#### 5.2.3 索引优化

**案例：查询医生排班**
```sql
-- 慢查询（300ms）
SELECT * FROM schedule 
WHERE doctor_id = '123' AND date = '2024-01-15' AND status = 'AVAILABLE';

-- 优化：创建联合索引
CREATE INDEX idx_doctor_date_status ON schedule(doctor_id, date, status);

-- 优化后（5ms）
```

**索引设计原则：**
1. **最左前缀**：联合索引遵循最左前缀原则
2. **区分度高的列在前**：doctor_id > date > status
3. **覆盖索引**：索引包含查询的所有字段
4. **避免索引失效**：不在索引列上使用函数

### 5.3 异步解耦

**场景：预约成功后发送通知**
```
同步方式：
预约成功 → 发送短信 → 发送推送 → 返回结果
总耗时：100ms + 200ms + 150ms = 450ms

异步方式：
预约成功 → 返回结果（100ms）
         ↓
      发送MQ → 异步发送短信、推送
```

**实现：**
```java
@Service
public class AppointmentService {
    
    @Autowired
    private RabbitTemplate rabbitTemplate;
    
    @Transactional
    public void createAppointment(AppointmentDTO dto) {
        // 1. 创建预约
        Appointment appointment = new Appointment();
        // ...
        appointmentMapper.insert(appointment);
        
        // 2. 发送MQ（异步）
        AppointmentCreatedEvent event = new AppointmentCreatedEvent();
        event.setAppointmentId(appointment.getId());
        event.setUserId(appointment.getUserId());
        event.setDoctorId(appointment.getDoctorId());
        
        rabbitTemplate.convertAndSend(
            "appointment.exchange",
            "appointment.created",
            event
        );
        
        // 3. 立即返回（不等待通知发送）
    }
}

// 通知服务消费MQ
@Service
public class NotificationConsumer {
    
    @RabbitListener(queues = "appointment.created.queue")
    public void handleAppointmentCreated(AppointmentCreatedEvent event) {
        // 发送短信
        smsService.sendAppointmentSms(event);
        
        // 发送推送
        pushService.sendAppointmentPush(event);
    }
}
```

**优化效果：**
- 响应时间：从450ms降到100ms（提升4.5倍）
- 用户体验：立即返回，无需等待
- 系统解耦：通知服务故障不影响预约
