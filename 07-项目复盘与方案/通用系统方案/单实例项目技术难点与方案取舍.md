# 单实例项目技术难点与方案取舍

本文讨论一个 Java 应用实例下的并发、跨系统一致性、异步恢复和交付问题。“单实例”指部署拓扑，不是单例设计模式，也不意味着只运行一个线程。一个应用进程仍会同时处理 HTTP 请求、支付回调、定时任务和消息消费；数据库、缓存和外部接口也不会随应用一起原子成功或失败。

本文以体重管理业务中的“购买服务 → 支付回调 → 开通权益 → 后台处理 → AI 对话”为教学主线，穿插动态权限和文件处理。重点是把技术选择还原为可检查的工程判断：先尝试最简单方案，找出它无法满足的约束，再引入必要机制，同时说明替代方案与新增成本。

## 1. 事实边界与设计起点

用户已说明实际项目经验普遍以单实例为主；简历提到支付幂等、Redis、RabbitMQ、AI 接入和动态权限。本文没有读取对应业务工程，不把下述任务表、Outbox、恢复协议或实验结果写成已上线能力。

文中的“我会先……”“因此选择……”属于**设计推演的表达方式**，不是代写真实个人经历。后续要用真实代码、测试和故障记录说明哪些实际做过、哪些是现在理解后的改进。

教学前提如下：

- 一个 Java 应用进程，MySQL 保存业务事实；Redis、RabbitMQ 按实际需要引入，不设为必选。
- 订单和基础权益可以存放在同一数据库，单笔订单对应一次基础权益开通。跨库或外部权益系统需另建恢复协议。
- 核心状态不允许重复推进；非核心处理允许延迟，但若业务要求必达，就需要持久化恢复责任。
- 不假设具体 QPS、用户数或优化收益；容量数字仅在明确的教学算例中使用。

说明基线采用 Java 17 API、MySQL 8.4 锁定读文档、Spring Boot 3.4 系列停机文档及 RabbitMQ AMQP 0-9-1 确认机制。它们不是项目真实依赖版本。

### 1.1 我的第一步不是选中间件，而是定义不变量

| 业务动作 | 必须成立的事实 | 可以另行协商的部分 |
| --- | --- | --- |
| 支付回调 | 同一支付事实不能导致重复开通；金额与订单必须匹配 | 通知展示可以稍晚 |
| 基础权益开通 | 支付已确认后有明确的权益结果或恢复状态 | 外部权益系统可以任务化 |
| AI 回复 | 用户知道回复完整、部分完成还是失败 | 摘要可以稍后更新，但下轮要知道其新鲜度 |
| 权限变更 | 授权规则与管理范围明确 | 撤权允许多长传播窗口必须单独约定 |
| 报告上传/OCR | 文件与识别任务可追踪，失败不冒充成功 | OCR 可异步，原文件先保存 |

如果当前单实例已能满足负载，我会保留同进程模块和同库事务。拆服务意味着把一次本地调用变为网络调用，把一次事务变为多个提交点；只有独立扩容、交付或组织边界的收益足够明确时，才值得承担这个成本。

## 2. 支付重复回调：为什么优先用数据库约束

### 2.1 从“查一下是否支付”开始推导

最直观的实现是先查询订单，未支付就更新并开通权益。它在单线程演示中正常，但单实例并不能排除下面的交错：

```text
请求 A：读到 PENDING
请求 B：读到 PENDING
请求 A：写 PAID，开通权益
请求 B：写 PAID，再次开通权益
```

问题是“判断”和“修改”之间没有共同的并发边界。将方法加上 synchronized 能串行化当前进程、同一锁对象下的调用，但它本身不记录业务是否已发生。串行的第二次回调仍要检查持久状态；进程重启、其他写入口或未来第二个实例也不会共享这把锁。

因此，我会把最终约束放到保存业务事实的数据库：状态条件决定能否推进，唯一约束限制业务身份，事务保证相关修改一起提交。

### 2.2 最小模型与事务边界

以下是教学逻辑模型，不是现有项目表结构：

| 记录 | 核心字段/约束 | 作用 |
| --- | --- | --- |
| payment_order | orderId、userId、amount、currency、status | 定义应支付什么以及当前业务状态 |
| payment_receipt | 渠道、商户、渠道流水组合唯一；关联 orderId | 保存已核验支付事实，识别同流水冲突 |
| entitlement | orderId 唯一，userId、权益内容 | 本案例中一笔订单只产生一次基础权益 |
| background_job | 业务对象与动作类型组合唯一 | 保存需后续处理的工作，可选 |

唯一约束粒度来自业务：一个订单可能有多次支付尝试，不能因此把所有流水当作重复丢弃；一个订单也可能包含多项权益，此时需要订单加权益项身份。本文实验只使用单次支付、单项权益模型。

推荐的同库正常路径为：先按支付渠道协议核验消息，再在短事务内锁定订单或采用等价的条件更新协议，校验订单金额、币种、归属及状态，保存支付事实，推进订单、插入权益和必要后台任务，最后提交。对渠道的成功响应必须对应约定的持久接受边界，不能在事务真正提交前就确认成功。

```sql
-- 条件更新片段，不是完整支付接口；命名参数由应用绑定。
UPDATE payment_order
SET status = 'PAID'
WHERE id = :orderId
  AND status = 'PENDING';
```

影响一行才表示本请求取得这次状态转换。零行要读取并区分已处理、已关闭、不存在或冲突，不能统一当成功，也不能统一重试。保存权益失败时，应让同一事务回滚，而不是吞掉异常只保留 PAID。

复杂状态判断可使用短事务内的锁定读；锁定后重新检查状态，统一加锁顺序并处理死锁重试。锁定读的行为与事务条件见 [MySQL 8.4 锁定读](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)。重试必须重跑完整事务且不重复事务外副作用。

### 2.3 为什么不是先加 Redis 锁

Redis 锁可以减少同一业务的竞争，但应用与 Redis 多了一条故障链，租约到期后的旧执行者也可能继续工作。最后仍需数据库识别合法状态和业务身份。若瓶颈只是正确性，而不是重复请求造成的负载，直接利用现有数据库通常更容易验证。

| 方案 | 能解决什么 | 没解决什么 | 我会采用的条件 |
| --- | --- | --- | --- |
| synchronized + 数据库状态检查 | 限制当前实例内竞争 | 其他写入口、重启后的业务事实仍靠数据库 | 少量纯进程内协调 |
| 条件更新 + 唯一约束 + 本地事务 | 状态竞争、持久幂等、同库原子性 | 外部接口副作用 | 本案例优先基线 |
| 锁定读 + 本地事务 | 多字段判断后的串行状态推进 | 长事务和死锁成本 | 判断复杂、锁范围可控 |
| Redis 锁 + 数据库最终约束 | 热点竞争协调 | 不替代业务防重，不自动撤销旧执行者 | 已有明确竞争负载证据 |

### 2.4 关单与迟到支付为什么需要状态机

超时不是支付失败的证明。关单任务和成功回调可能竞争同一笔订单；如果关单已完成，后到的成功通知仍代表真实支付事实，不能把钱的事实丢掉，也不能直接恢复已释放的资源。

我会分别表达“订单是否可继续履约”和“渠道是否收款”。迟到成功可进入退款待处理或人工核对，而不是无条件 CLOSED → PAID。退款本身有业务身份、渠道结果和未知状态，不能在数据库里减个金额就当完成。

**如何验证：**并发投递相同回调；同流水不同金额或订单必须报冲突；在权益写入前注入异常，订单和收款记录应一起回滚；交错执行关单与回调，并检查钱、订单与权益最终去向。真实渠道验签与关单协议不在后面的本地实验范围内。

### 2.5 从“用户已付款但页面报错”定位提交边界

以购买多师共管服务为教学场景，支付回调、前端查询和主动查单应进入同一套支付事实处理协议。前端“支付成功”提示不是可信入账依据；主动查单也不能另写一套无幂等保护的开通代码。

| 中断位置 | 可能留下的状态 | 恢复责任与处理 |
| --- | --- | --- |
| 本地事务尚未提交 | 数据可能已回滚，渠道仍已扣款 | 原身份重投/查单；不能重新发起扣款 |
| 数据库已经提交，成功响应丢失 | PAID、收款与权益已在库，渠道认为未确认 | 相同业务身份再调用，校验既有结果后返回，不重复开通 |
| COMMIT 发出后连接断开 | 客户端无法确定数据库是否提交 | 按原业务键查权威状态；无法查证时保留未知，不能靠 catch 中一次 rollback 推断未提交 |
| 关单先提交，随后收到已核验的成功支付 | 订单关闭，但渠道确有收款 | 保存支付事实与退款/人工处理任务，不能直接丢弃通知 |
| 收到同订单另一笔真实支付 | 第二笔收款不能转换成第二份基础权益 | 另记收款并关联冲突，查证后退款；权益唯一约束只是阻止重复履约 |

原先将“任意异常”理解为回滚成功会遗漏第三行。死锁、锁等待超时和网络断开也不是同一种异常：InnoDB 死锁会回滚事务，锁等待超时默认主要回滚当前语句，配置还会影响行为。应用应显式结束失败事务、区分可重试与结果未知，再执行有界重试。参见 [MySQL 8.4 错误处理](https://dev.mysql.com/doc/refman/8.4/en/innodb-error-handling.html)。

收款与权益同事务适合本地、短且确定的开通。如果“开通服务”还要调用外部平台，选择应变化：先持久保存收款事实和 FULFILL_PENDING，再由可靠任务调用外部平台，状态对外显示“已付款，开通中”。我愿意承担可见的中间状态，换取不把外部不确定性塞进数据库长事务；代价是要建设恢复和人工处理入口。

同流水参数冲突不应被当作正常重复；唯一键异常也不能一律转成功，应确认究竟违反哪个约束、现存记录是否与本次业务意图一致。支付通知的成功应答格式和重试条件仍需按真实渠道协议实现。

## 3. 异步处理：为什么线程池不等于可靠任务

### 3.1 先判断是否真的需要异步

同库插入一条基础权益，如果耗时小且属于“支付成功后立即可用”的承诺，我会留在支付事务中，而不是为了使用 MQ 人为拆开。

短信、报表生成、AI 摘要和 OCR 常常耗时更长，且可以独立重试。把这些工作放在支付事务里，会长时间占有连接和锁，下游故障也会扩大为支付链路故障。此时异步化的目标是隔离等待与失败，不是让工作凭空消失。

### 3.2 最简单的线程池方案在哪里断裂

```text
数据库提交订单
→ executor.submit(发送通知)
→ 进程退出
→ 内存队列消失，数据库没有任何待处理凭据
```

如果通知允许丢失，且产品接受，这种轻量方式可以成立。若要求恢复，就必须有持久证据。仅在 submit 失败时补写任务表仍不够，因为入队成功后也可能退出。

因此我会先选“业务数据与任务记录同事务落库，定时扫描 + 有界 worker”。任务表是工作事实，线程池是执行资源；二者不是替代关系。

### 3.3 不用 MQ 的完整基线

任务至少有稳定 taskId、业务动作键、参数版本、状态、尝试次数、下次执行时间和错误摘要。扫描器取到任务并不代表完成，领取与业务效果也必须分开。

```text
PENDING / RETRY_WAIT
  → 短事务领取，写 PROCESSING、attemptToken、leaseUntil
  → 事务外执行耗时操作
  → 以本次 token 条件提交 SUCCEEDED / RETRY_WAIT / UNKNOWN / MANUAL
```

即使单实例也有多个 worker，以及超时后继续运行的旧任务。租约到期允许重新领取，却不能让旧线程自动停止；新旧执行可能重叠。完成记录要防旧 token 覆盖，实际业务效果仍需资源端幂等。外部通知成功但本地结果未落库，应使用原幂等键查询或重试；对不支持幂等也无法查询的接口，要明确重复风险与人工处理选择。

扫描器应覆盖到期重试和失联处理中任务，不只扫描 PENDING。任务领取后提交执行器被拒绝，必须释放领取或保证租约恢复；不能丢掉 Runnable 却保留永远不会恢复的 PROCESSING。

### 3.4 什么情况下才值得加 RabbitMQ

当需要独立消费者、多个订阅者、低延迟唤醒或更强的积压分发能力时，MQ 的价值才明确。单实例也可以用 MQ；理由应来自交付方式，而不是实例数量。

| 方案 | 收益 | 成本与适用边界 |
| --- | --- | --- |
| 同步调用 | 简单，结果直接可见 | 延迟和故障耦合；适合短核心操作 |
| 内存线程池 | 实现轻，移出请求等待 | 崩溃会丢工作；适合明确允许丢失的任务 |
| 数据库任务表 + worker | 可恢复，复用现有数据库 | 轮询、清理、任务索引和积压管理 |
| 任务表 + MQ 唤醒 | 工作事实可查，消息降低唤醒延迟 | 两条调度路径要统一幂等和领取 |
| Outbox + MQ + 消费者持久处理 | 跨服务分发、独立恢复 | 发布/消费确认、重投、消息版本和监控 |

数据库提交后直接发消息存在提交成功、发送失败窗口；反过来先发消息又可能让消费者读到未提交或最终回滚的数据。Outbox 的意义是把“需要发布”与业务事实原子保存，再独立重试发布，不是让数据库和 MQ 瞬间成为同一事务。

Publisher confirm 和 consumer ACK 分别确认不同方向，confirm 不代表业务完成；消费者在业务提交后 ACK，仍有提交成功但 ACK 丢失的重复投递窗口。依据 [RabbitMQ 确认机制](https://www.rabbitmq.com/docs/confirms)。若消费者先可靠落库任务再 ACK，则 ACK 表示恢复责任已交接，必须存在真实可运行的扫描器。

**如何验证：**在业务提交后、发送前中断；发送成功但记录发布状态前中断；业务效果提交后、ACK 前中断。检查任务最终能继续且效果不重复。详见 [[07-项目复盘与方案/通用系统方案/RabbitMQ与Outbox可靠消息方案]] 和 [[07-项目复盘与方案/智能体重管理/AI对话系统/AI消息后处理异步方案]]。

### 3.5 租约过期：保护任务状态和保护业务效果是两件事

以摘要任务 J1 为例，假设它处理会话消息 1～20，后续 J2 处理到消息 25：

```text
T1 worker A 领取 J1，attemptToken=7，开始模型调用
T2 A 调用超时但远端仍在生成；租约到期
T3 worker B 重新领取 J1，attemptToken=8
T4 J2 已生成到消息 25 的摘要
T5 A 返回旧结果，尝试保存摘要并标记 J1 完成
```

只在任务表上检查 token，最多阻止 A 把 J1 标成完成；如果 A 已先覆盖摘要正文，数据仍然倒退。因此业务写入需要绑定 `conversationId + sourceRevision/覆盖水位`，并在同库事务中检查任务领取身份与摘要当前版本，再保存业务结果和任务完成状态。对旧资料生成的结果，可以丢弃或重新计算，不能以“最终成功”为理由覆盖较新事实。任务 token 防同任务旧尝试，资料版本防不同任务之间的旧内容，二者不能互相替代。

对于 OCR 或短信这类外部动作，本地条件更新不能阻止远端已经执行。资源端若支持幂等键，重试沿用同一业务键；若只支持查询，先查证 UNKNOWN；若两者都不支持，必须在“可能重复”和“可能需要人工恢复”之间做业务选择。

领取租约最好从取得真实执行容量后开始，或把排队时间纳入租约与续约协议。提前领取大量任务再塞进长队列，会让尚未开始的任务租约过期。续约也需校验 token，旧 worker 不能给新领取延长租约。终态写入是否允许到期但尚未重领的 owner 提交，要明确采用的协议；本文后面的模型采用到期即拒绝。

### 3.6 为什么消息进入死信队列还不算解决

数据库任务与 MQ 同时存在时，我会指定一个持久重试责任方。若由任务表负责，消费者失败后只有在 RETRY_WAIT/UNKNOWN 已持久化且扫描器能继续接管时才可以 ACK；若只由 MQ 负责，就不能照搬这条规则。

死信表示投递遇到问题，不表示业务已恢复。人工重放也应保留原 taskId 和载荷身份；修改任务内容则产生新版本并关联旧任务。需要监控最老待处理年龄、重试耗尽数量与 UNKNOWN 数量，而不是只看队列是否清空。

不用 MQ 的轮询方案何时需要升级？看扫描耗时、数据库压力、唤醒延迟和恢复吞吐是否超出业务预算。假设停机积压 B 条、恢复处理速率 μ、持续到达速率 λ，在 μ>λ 且速率稳定时，理想排空约为 B/(μ−λ)。如果下游配额使 μ≤λ，加 MQ 也不能让积压消失；应先降低输入、提高有效处理能力或允许延迟。这个判断比“消息量大就上 MQ”更可验证。

## 4. 缓存：为什么我会先优化数据库，再决定用 Redis

### 4.1 从证据决定缓存对象

慢查询可能来自缺索引、一次列表查几十次关联数据、扫描过大或连接等待。若直接加缓存，低命中率和复杂失效可能使系统更难排查。我会先观察 SQL、执行计划、查询次数和数据分布，修复明显的访问问题，再评估重复读取是否值得缓存。

产品配置等读多写少数据可以缓存；支付事实和最终权益判定不能仅依赖一个可能过期的缓存。画像展示允许的短暂陈旧，也不等于撤权可以沿用同样策略。

### 4.2 不用 Redis 能怎么做

| 选择 | 为什么可能足够 | 什么时候不够 |
| --- | --- | --- |
| 直接查数据库 | 数据量和负载可控，语义简单 | 实测重复读取已影响数据库或响应 |
| 优化索引/批量查询/预计算 | 减少真正的工作量 | 仍有大量重复热点读取 |
| 本地有界缓存 | 单实例、可重建数据，网络开销低 | 内存预算、失效、发布冷启动与未来多实例 |
| Redis 缓存 | 独立容量、共享读取、统一失效入口 | 新增网络故障、运维和一致性成本 |

本地缓存不是低级方案；如果用途与单实例条件匹配，它可能比 Redis 更简单。但必须设置容量、生命周期和重建策略，不是无限增长的 ConcurrentHashMap。

### 4.3 为什么“提交后删缓存”仍不完全正确

```text
A 未命中，读到数据库旧值 v10，暂未回填
B 提交 v11，删除缓存
A 恢复执行，把 v10 写回空缓存
```

删除发生在提交后，只解决顺序的一部分，没有阻止旧读回填。另一个窗口是数据库提交后进程退出，删除根本没执行。对允许有限陈旧的展示数据，可以组合绝对 TTL、持久失效重试、回源合并和版本条件回填；需要说明上界与故障条件，不能把 TTL 本身说成强一致保证。

版本保护还需要独立的有效比较依据：只检查缓存中已有版本，缓存删除后旧写就可能被接受。读取旧副本、版本与数据分开获取、本地副本未失效也要考虑。详细机制复用 [[03-数据存储与缓存/Redis/Redis项目实践]]。

**如何验证：**用可控屏障暂停 A 的回填，完成 B 更新后再放行 A；分别测试 key 存在和已删除。模拟 Redis 不可用，检查回源是否有上限、关键写入是否仍以数据库为准。没有实测前不填写“命中率提升到多少”。

### 4.4 多师共管权益缓存：不把展示优化变成授权漏洞

教学场景中，用户刚支付，缓存仍显示“未开通”；或者退款已经完成，缓存仍显示“有效”。两种陈旧的后果不同：前者误拒服务，后者可能越权使用。不能只用同一个 TTL 把它们视为相同问题。

我会把支付响应里的权益状态用于页面反馈，把真正创建服务请求的判断放在明确的权益校验路径。数据量不大时直接查数据库更简单；需要缓存后，缓存键至少绑定用户、机构及权益类型，并处理负缓存失效。写后读可以携带服务端返回的最低版本，但请求不携带版本不能成为跳过授权的入口。

```text
T1 用户无权益，缓存 NOT_FOUND
T2 支付事务创建权益 v1
T3 正缓存已写入，但旧 NOT_FOUND key 未清理
T4 读取流程先查 NOT_FOUND，仍向用户返回未开通
```

我更倾向用一个带版本的 FOUND/NOT_FOUND 载体避免两个 key 互相遮挡，而非继续增加判断顺序。它仍需要解决数据库提交后失效失败；缓存重建失败不等于没有权益。

Redis 故障时，全量无条件回源会把缓存故障扩大成数据库故障。可以对同用户合并回源、限制总并发、优先保护关键权益查询；展示页可返回明确暂不可用或允许的旧展示数据，受保护动作不能把授权未知当成允许。验证时同时检查误放和误拒，以及缓存冷启动期间数据库等待是否可控。

## 5. AI 慢调用：为什么要控制并发，而不只是增加线程

### 5.1 瓶颈是等待占用的资源

模型调用等待十几秒，线程虽然未必持续消耗 CPU，却占用连接、内存、上下文和上游并发额度。如果请求到达速度超过完成速度，队列会增长，用户等到执行时可能已经取消。

教学算例：稳定到达 4 次/秒、平均占用 5 秒，大约有 20 个在途调用；平均耗时变成 15 秒时，在同样到达速率下需要约 60 个在途。它只说明等待时间影响在途量，不是建议线程数，也不能用 P99 替代平均值推导容量。

我会先拆分画像读取、检索、模型等待和后处理耗时，确认瓶颈在哪，再决定是否并行。已有毫秒级查询并行化可能增加调度成本，而不是主要收益来源。

### 5.2 有界执行器的技术理由

有界队列限制排队量，专用执行器隔离慢任务与支付等关键任务，显式拒绝策略让系统在过载时返回可解释结果。它们不增加上游模型的真实处理能力。

Java ThreadPoolExecutor 通常在核心线程达到后先入队，队列满才尝试增至最大线程数；使用无界队列时，最大线程数未必发挥预想作用。CallerRunsPolicy 在执行器仍运行时会把任务放到提交线程执行，可能重新拖住 HTTP 或消息线程；执行器已关闭时则会丢弃任务，因此它不保证任务必执行。见 [CallerRunsPolicy API](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/concurrent/ThreadPoolExecutor.CallerRunsPolicy.html)。不能无条件将它作为可靠任务的拒绝策略。见 [Java 17 ThreadPoolExecutor](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/concurrent/ThreadPoolExecutor.html)。

不用线程池也可以同步调用并设置并发信号量，或使用异步 I/O 客户端；前者简单但占请求线程，后者节约等待线程但仍需限制在途请求、连接与队列。改变编程模型不会取消资源预算。

### 5.3 超时、重试与降级要共享一个预算

外部请求的预算应包含排队、连接、读取、重试及本地处理。不能让每一层各重试三次，最后形成乘法放大；最好指定清晰的重试责任方，并限制总尝试与总时间。

`Future.get(timeout)` 只限制等待，取消也只是尝试，不能证明远端操作未发生。参考 [Java 17 Future](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/concurrent/Future.html)。对模型生成还要考虑重复计费；如果 Agent 调用了写工具，则必须按业务幂等与结果未知协议处理，不能把所有超时当成可安全重做。

流式输出已经发送部分文本时，切换模型重新生成可能造成拼接内容不一致。应明确结束本轮、标记部分结果，或提供有协议支持的恢复，而不是静默重试后继续向同一流追加。

降级要说明保留什么：可以跳过非必要检索、暂停摘要更新或改为基础对话；但不能假装工具已执行，也不能把缺失资料补成患者事实。恢复需要观察窗口、试探流量和回切条件，不能某一次请求成功就立刻全部恢复。

**如何验证：**用本地桩模拟慢响应、超时和断流；观察排队上界、拒绝结果、请求取消后的资源释放、支付接口是否受拖累。分别统计首字、完整回复及后台追平时间，见 [[07-项目复盘与方案/智能体重管理/AI对话系统/AI消息数据流性能分析]]。

### 5.4 线程隔离之后，为什么支付仍然变慢

假设 AI 调用和支付使用两个线程池，但共享同一个数据库连接池。若 AI 方法在事务内先查询画像，再等待模型完成，多个慢调用会一直占住连接。支付线程再多也拿不到连接，这时“线程隔离已做好”的结论不成立。

我会先把事务边界收窄：短事务读取带版本的输入快照，结束事务后调用模型，再用新的短事务按版本保存结果。输入期间发生变化时，输出要校验来源版本，必要时丢弃或重新计算。这里选择牺牲“长事务内看似连续”的写法，换取连接及时释放；代价是必须显式处理资料变更。

仍有资源争用时，再考虑连接并发配额、独立连接池或服务拆分，并核算数据库总连接预算。增加连接数可能把等待从连接池移到数据库，不能凭连接池不排队就宣布性能改善。

### 5.5 同一会话连续追问与客户端重试

```text
T1 用户提交消息 M20，服务端开始生成
T2 客户端等待超时，用同一 requestId 重试
T3 用户又提交新的 M21
T4 M21 的生成先结束，M20 的旧生成后结束
```

若每次 HTTP 请求都生成新的 turnId，就会重复保存 M20、重复计费；若仅按消息文本去重，又会误删用户有意重复发送的话。应让客户端重试保留一次意图的 requestId，在用户/机构/会话作用域内校验请求摘要，并映射为稳定 turnId。同 ID 不同内容返回冲突。

对于需要严格上下文顺序的健康对话，优先按会话串行推进，并向用户明确排队或忙碌状态；跨会话可以并行。若允许同会话并行分支，则每轮必须绑定输入上下文版本，保存时不能让迟到结果覆盖新分支。串行会增加等待，分支会增加产品与恢复复杂度，应按真实交互需求取舍。

流式响应建议把片段可见与回复完成分开：片段携带 turnId/序号，完成记录持久化后再发终止事件。若完成事件丢失，客户端按 turnId 查询；只有实现了持久事件日志才承诺从片段位置续传，否则只提供已保存结果或明确的部分完成状态。暂停摘要后处理时，下一轮还要用摘要水位后的原文补齐；预算不足就显式等待、缩小功能或提示限制，而非声称完全不影响上下文。

## 6. 动态权限：为什么单实例仍需要讨论生效边界

权限涉及数据库规则、Redis 快照和会话上下文，即使只有一个应用实例，也可能出现多个旧副本。我会先定义“未配置继承”“显式空授权”“用户覆盖”的计算规则，再明确撤权究竟要求下次登录、下次请求还是有界时间生效。

如果用户量小、授权查询成本可接受，每请求查询权威数据是合理基线，不必先缓存。它减少传播问题，但不能自动消除鉴权后到写入前的竞态。缓存只在读取成本有证据时引入，同时增加版本依赖和失败策略。

事务提交后刷新 Redis 版本可以避免未提交策略提前生效，但进程在提交后退出，旧版本仍可能存在。Outbox 可以修复传播遗漏，不等于撤权立即生效。对于要求严格控制的写操作，需要让最终授权检查与副作用进入共同的协调协议。

不用完整权限框架也能以过滤器/服务层策略实现，但需要自行保证入口覆盖、资源范围、委派规则和审计；采用框架能复用认证与执行入口，不能替业务定义“主任能管理哪些科室”。菜单隐藏始终不能独自保护 API。

**如何验证：**直接调用被隐藏功能的接口；跨机构和跨科室尝试；清空用户授权后检查是否错误回退；提交成功后断开 Redis；旧快照晚完成时检查当前请求是否也被阻止。完整机制与待核实证据见 [[07-项目复盘与方案/动态权限/动态权限原理与项目核实]]。

### 6.1 科室主任改用户：检查与使用之间的竞态

```text
T1 主任 A 按策略 v10 获得 D1 科室用户修改权限
T2 管理员撤销 A 的权限，提交 v11
T3 A 才执行修改用户资料的 SQL
```

若契约是“已经开始的请求允许完成”，T3 可以合法发生，应如实说明边界。如果要求撤权提交后不再产生新的受保护写入，仅在 HTTP 入口查数据库也不够。

一个可讨论的同库协议是：受保护写事务和撤权事务都先锁定同一个授权作用域的协调行；写事务锁内重新读取当前权限并检查资源范围，再修改业务数据；撤权在同一协调规则下更新策略。若写事务先获得锁，它应先完成，撤权提交在后；若撤权先提交，后来的写事务必须看到新策略并拒绝。所有相关策略、组织变更与写路径都必须遵守协议，使用当前读取且不能复用旧快照；否则这只是局部保护。

机构级协调行实现简单但锁粒度粗，可能串行化许多管理操作；更细的依赖锁降低冲突却增加加锁顺序和依赖覆盖难度。低频管理操作且要求严格时可评估，普通展示请求不必全部套用。涉及外部副作用时，本地锁仍不能回收已发送动作，需要另一套授权与执行契约。

因此，我会先确认撤权承诺，再决定版本缓存、逐请求查库还是资源端协调，不能先选机制再声称“实时撤权”。此协议未在本次本地实验中验证。

## 7. 文件与 OCR：为什么有数据库事务仍会出现半成品

上传报告时，数据库和 MinIO 没有共同的普通本地事务：先上传再落库，落库失败会留下孤立文件；先落库再上传，上传失败会留下不可用引用。加一个 @Transactional 不能回滚已存对象。

我会把流程表达为可恢复状态：创建受控上传记录和对象身份，上传并校验后标为 STORED，在同库事务记录 OCR 待办；OCR 独立推进 SUCCEEDED、RETRY_WAIT 或待人工处理。对象存储完成后、状态更新前退出，可以按对象身份回查而不是再次无条件上传。

不用 MQ 时由任务表扫描 OCR；不用对象存储时可以先用受控本地目录，但必须解决磁盘容量、备份、发布目录隔离和恢复，不能把容器临时文件层当成长期存储。小文件存数据库也有事务优势，但需承担数据库与备份体积成本。

清理孤立文件不能只看“没有业务引用就删”：上传可能仍在进行，数据库更新也可能滞后。需要状态、年龄、引用与重试记录共同判定，并保留审计。OCR 识别成功只表示接口返回结果，还需要字段校验和必要的人工修正，不能自动当成业务事实。

**如何验证：**分别在对象写入后、数据库状态提交前和 OCR 返回后中断，检查是否可回查、恢复，是否产生重复任务。以上为设计推演，真实上传和第三方 OCR 协议待核实。

### 7.1 同一份报告重新上传：对象身份与业务版本不能混用

建议把 `reportId` 作为业务报告身份，`reportRevision` 作为修订号，`uploadId` 标识一次上传尝试，对象 key 绑定不可变修订。OCR 任务身份至少包含报告修订和处理版本。这样重复确认同一上传不会重复建任务，用户换文件又不会被旧幂等键误挡。

| 失败时序 | 不能直接做的事 | 恢复判据 |
| --- | --- | --- |
| PUT 已成功，响应超时 | 直接生成新 key 重传并遗忘旧对象 | 按既定对象身份回查，校验长度和约定校验和；错误响应不等于不存在 |
| 对象存在，STORED 尚未提交 | 仅凭年龄删除对象 | 读取上传状态及恢复记录，确认是否可完成落库 |
| STORED 已提交，任务尚未创建 | 只依赖客户端再次点击 | STORED 与任务同事务提交，或有能够重建任务的持久扫描协议 |
| v1 OCR 慢返回，用户已上传 v2 | 用 v1 结果覆盖当前报告 | 按 reportRevision 条件写入；旧结果只归档到旧修订 |
| 人工已纠正字段，OCR 重试返回 | 无条件覆盖医生修改 | 记录人工修订版本，合并或转待审核，保留来源 |

仅检查对象 key 存在不等于内容相同。校验和算法与字段要跟实际存储和 SDK 对齐，不能一律把 ETag 当作整文件 MD5；例如 S3 的分段上传有不同语义，见 [S3 对象完整性说明](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity-upload.html)。此来源只用于说明不能泛化，MinIO 实际版本行为仍需核实。

清理也要有状态协议：先条件标记 DELETING，确认没有有效引用且阻止新引用，再删除准确对象版本，最后标记完成；删除超时保留可重试状态。若上传可能在删除后迟到完成，还需终止/过期上传资格并二次核对，否则对象可能重新出现。相关删除操作这里只作设计说明，本次不执行。

## 8. 发布与排障：单实例无法靠“有重试”获得高可用

### 8.1 停机窗口是真实约束

单实例停止期间没有另一个应用承接请求。优雅停机减少在途损失，但不创造零停机能力。Spring Boot 3.4 系列支持在应用上下文关闭时停止接纳请求并给现有请求一定完成时间，具体取决于服务器和配置，见 [优雅停机文档](https://docs.spring.io/spring-boot/3.4/reference/web/graceful-shutdown.html)。

我会将发布协议设计为：停止入口新流量与任务领取，等待有界的在途工作，更新已持久化任务的进度或恢复状态，随后停止进程；启动后先验证配置和数据库迁移，再恢复任务及流量。Web 请求优雅关闭不自动覆盖自建线程池、MQ 监听器和全部定时任务，它们需要各自生命周期管理。

强制结束、机器断电、OOM 仍可能绕过优雅停机，所以可靠性最终依赖持久状态与幂等。任务重试不能使停机期间的实时接口变为可用；若业务要求连续服务，应明确需要额外实例或其他承接能力。

### 8.2 回滚程序不等于回滚业务数据

新版本若修改任务载荷或数据库结构，旧程序必须能读取，或把不支持的版本持久保留并交给兼容 worker/人工处理，不能跳过后标成功，不能“镜像回滚成功”后才发现恢复任务无法解析。优先采用向后兼容的结构演进，分阶段移除旧字段。回滚已产生的业务动作需要独立业务协议。

排障时我会按一次请求的资源等待链定位：入口等待 → 线程池排队 → 数据库连接 → SQL/锁等待 → 外部调用 → 后处理。CPU 低不代表服务健康，线程可能全在等待。日志关联 requestId、orderId、taskId 和 attempt，区别请求失败与业务结果未知。

**如何验证：**在隔离环境停止进程并重启，检查待办恢复、重复效果和数据库连接；发布旧程序读取新任务格式；观察最老未完成任务年龄而不只看队列长度。实际停机时长、恢复耗时和发布事故必须以真实记录为准。

### 8.3 进程被直接终止时，恢复从哪里开始

未完成任务必须在接受工作时就有持久记录，不能等优雅停机回调才首次保存。若进程已经 OOM 或被强制结束，该回调可能根本不执行。

```text
T1 worker 领取任务 J1，任务表记录 token=7
T2 外部服务接受请求，但本地尚未保存回执
T3 应用进程被终止
T4 重启扫描器发现领取已失效
T5 根据任务类型选择幂等重试或转 UNKNOWN 查证，而非全部直接重发
```

恢复扫描需有速度上限，避免启动后积压任务抢走前台的数据库连接和外部配额。单实例也可能在部署切换时短暂同时运行新旧进程，因此启动扫描前应确认部署实际行为，不能把“平常只有一台”当作永远不存在双执行者的保证。

无兼容 worker 能处理新格式任务时，回滚旧程序只能恢复它支持的接口，不能保证全部后台任务恢复。应保留版本化任务并告警，选择修复前进或兼容发布；无声跳过会把可观察的停滞变成永久丢工作。

## 9. 本地实验：同库事务与幂等的可验证边界

配套脚本是可直接运行的 Python 3 标准库实验，使用内存 SQLite 验证教学协议：订单、收款记录与单项权益一起提交；处理中断一起回滚；同身份重试不重复开通；同流水参数冲突被拒绝。SQL 与事务由实验显式控制。

它不模拟 MySQL 行锁、真实并发、支付验签、关单、跨库、MQ 或进程崩溃。实验中的 rollback 是故障注入，不等于已完成断电恢复演练。

完整源码见 [支付幂等与事务实验](./实验/支付幂等与事务实验.py)；环境、副作用与运行说明见 [配套实验说明](./实验/README.md)。在仓库根目录执行：

### 9.1 租约实验：复现旧 worker 覆盖与外部重复效果

## 10. 如何把这些设计变成自己的项目复盘

一条可信的思路历程应该能被证据支撑：最初有什么约束，简单方案在哪里失败，比较过什么，实际选了什么，验证发现了什么，最后还保留什么限制。没有当时记录的决策，可以说明“这是现在复盘后的解释”，不要编造曾经发生的故障。

例如，若代码证实只用了唯一键和条件更新，就可以解释为什么它们足以解决重复回调；如果未做可靠任务表，则把“进程退出后内存任务可能丢失”作为现有边界，并说明任务表是后续改进。识别当前方案不足，本身也是工程判断。

| 主线 | 需要从实际项目取回的证据 | 没有证据时如何表达 |
| --- | --- | --- |
| 支付 | 唯一约束、状态更新条件、事务边界、重复回调用例 | 教学设计，不能承诺已有完整对账与退款 |
| 异步 | 任务存储、执行器配置、ACK 时点、重试责任方 | 区分实际线程池/MQ 与建议的恢复协议 |
| 缓存 | 缓存对象、失效代码、TTL、慢 SQL 与命中统计 | 不编造收益与最大陈旧时间 |
| AI | 调用链、超时/重试配置、队列指标、降级分支 | 不把方案文档当成上线效果 |
| 权限 | 覆盖规则、资源范围、版本发布、会话更新 | 不承诺未验证的即时撤权 |
| 交付 | 部署拓扑、停机流程、恢复与回滚记录 | 明确单实例，没有集群治理经验 |

如果未来扩成多实例，先复查进程内状态、任务重复领取、会话、本地缓存和连接池总预算；数据库约束与持久任务身份可以复用，但需要真实多实例验证。不能因为设计“理论可扩展”，就把它写成已验证的生产能力。
