# 动态权限：授权规则、变更一致性与项目核实

动态权限的核心是：在身份、组织关系和配置持续变化时，针对一次具体操作得到可解释的允许或拒绝决定。增加几张角色表和一份 Redis 缓存，只解决了存储问题；授权语义、生效边界与故障处理仍需单独设计。

本文以“科室主任管理本机构指定科室的用户”为贯穿案例。它是教学场景，不代表慢病智管项目已经实现本文所有机制，也不将用户管理范围扩大为全系统患者数据权限。

## 2. 通用原理：一次授权到底判断什么

### 2.1 认证、动作权限、资源范围与委派权限

认证解决“你是谁”；授权解决“你能否对这个对象做这件事”。一个可解释的授权决定至少需要主体、动作、资源、环境和策略版本。

| 对象 | 教学示例 | 不能混同的概念 |
| --- | --- | --- |
| 主体 | 已认证的主任用户 | 客户端传来的 userId 不自动可信 |
| 动作 | `user:update` | 能打开用户菜单不等于能修改用户 |
| 资源 | 机构 H1、科室 D1 中的用户 U2 | 有动作权限不等于能操作全部机构 |
| 环境 | 账号有效、机构有效、功能启用 | 登录成功不保证账号后来未被停用 |
| 策略版本 | 本次决定依据的授权修订号 | 令牌签发时间不是最新策略版本 |
| 委派范围 | 能给谁分配哪些角色或权限 | 自己能使用某功能，不一定能授予别人 |

一个教学表达式是：

```text
允许 = 身份有效
    且账号/机构状态有效
    且具有动作权限
    且目标资源在管理范围内
    且业务约束成立
```

业务约束可以包括禁止修改特定系统账号或限制自我提权，但是否需要这些规则要由产品契约确定。缺失机构、解析失败或策略未知，不应自动解释为“不限制”。默认拒绝、每次请求核验及资源级控制可参考 [OWASP 授权指南](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)。

### 2.2 RBAC、属性和关系各自负责什么

RBAC 用角色汇聚动作权限，减少逐用户维护。机构、科室、账号状态属于属性或关系维度：同一个“科室主任”角色，在不同机构对应的可管理对象并不一样。可以采用角色决定动作、组织关系决定范围的组合，不必为每个科室复制一个角色。

数据关系可以概念性表示为：用户关联角色，角色关联动作；用户或角色另有关联的管理范围。菜单关联动作供展示使用，功能开关控制可用能力。具体表是否合并、是否存在显式拒绝、多角色如何合并，都不能由这些概念图替项目决定。

多角色合并尤其需要规则：如果角色一允许编辑 D1，角色二只允许查看 D2，把所有动作与所有科室分别取并集后做笛卡尔积，会错误地产生“可编辑 D2”。应保留动作与范围的关联，或按明确规则计算每个动作的有效范围。

**待代码核实：**系统是否支持一人多角色；角色默认权限如何合并；管理范围绑定用户、角色还是角色分配关系；动作与范围是否可能被错误拆散；系统管理员是否有显式且可审计的例外。

## 3. 通用原理：覆盖规则与三态配置

### 3.1 未配置和空集合是两种业务意图

“未配置”表示继承角色默认；“显式空授权”表示使用空授权集。若用 `isEmpty()` 同时处理两种状态，就会把“全部清空”的意图错误地恢复为角色默认权限。

以下是与简历描述方向一致的**教学规则**，覆盖粒度仍待项目核实：

```text
角色默认动作集合 = R
用户配置状态 = INHERIT 或 OVERRIDE
用户显式动作集合 = U

基础动作集合 B = R                 当状态为 INHERIT
基础动作集合 B = U                 当状态为 OVERRIDE，包括 U 为空
有效动作集合 E = B ∩ 启用能力集合 ∩ 其他明确的授权约束
```

这里的覆盖是替换，不是 `R ∪ U`，也不是先取 U、为空再退回 R。替换整份授权和按菜单/模块逐项覆盖是不同协议，不能混用。

| 配置状态 | 角色默认 | 用户显式值 | 基础动作结果 | 原因 |
| --- | --- | --- | --- | --- |
| INHERIT | 查看、编辑 | 不适用 | 查看、编辑 | 继承默认 |
| OVERRIDE | 查看、编辑 | 查看 | 查看 | 显式替换 |
| OVERRIDE | 查看、编辑 | 空集合 | 空集合 | 主动清空，不回退 |
| INHERIT | 空集合 | 不适用 | 空集合 | 默认本来为空 |
| OVERRIDE | 查看 | 查看、编辑 | 查看、编辑，但须经过授权配置合法性校验 | 覆盖可能增加能力，不天然只能减少 |

最后一行说明：计算器按已存策略求值，与管理员是否有权写入这份策略，是两层不同检查。写配置时必须检查可委派范围；不要依赖运行时“交回角色集合”来偷偷改变覆盖语义。

### 3.2 API、持久化与旧数据必须保留同样的语义

建议使用显式模式字段，或一条能表示“已配置但为空”的配置记录。仅靠关联表有没有明细行，可能无法区分从未配置和清空后零行。

PATCH 请求中还需区分：字段缺失表示不修改；明确恢复继承表示修改模式；提交空列表表示显式清空。JSON `null` 代表什么必须单独约定，不能由序列化框架偶然决定。删除用户配置表示恢复继承还是撤销授权，也需要明确命名和测试。

旧数据迁移应先识别旧账号实际权限来源，再确定未配置状态如何映射；不能把所有 null 批量转换成空集合。建议针对旧医生、旧管理员及新角色比较迁移前后的决定差异，允许差异必须有明确业务依据。

### 3.3 菜单可见性与功能开关

菜单树负责展示，接口授权负责执行。隐藏菜单不能阻止直接请求 API；反过来，某些后台或无页面接口也不应该仅因没有菜单节点就被无意禁用。

项目简历明确写到菜单可见性参与有效权限计算，因此需要查清它究竟是：展示裁剪、动作授权的门控条件，还是两者兼有。若确实作为授权门控，关闭菜单后相关后端动作也必须通过同一规则被禁用，不能只更新前端。

功能开关也有两种用途：界面灰度开关与能力禁用开关。若开关影响授权，应进入缓存版本依赖；若只是展示控制，不应擅自改变接口授权语义。菜单删除、重挂父节点、功能开关变更是否使现有快照失效，需要逐项核实。

**待代码核实：**覆盖的粒度及优先级；空值如何从请求一路保存到数据库和缓存；多角色与用户覆盖的组合；菜单和功能开关分别在哪一层生效；角色默认变更是否影响显式覆盖用户。

## 4. 通用原理：机构与科室范围落到资源操作

### 4.1 客户端筛选条件只能收窄授权范围

对于机构 H1、允许科室集合 `{D1, D2}` 的用户，资源范围可示意为：

```text
目标机构 == 当前获准机构
且目标科室属于本动作的授权科室集合
且满足请求自身的筛选条件
```

客户端请求 `deptId=D3` 不能让后端改用 D3 替换授权范围。机构上下文必须来自认证主体及其获准成员关系；即使客户端可以切换机构，也要先验证切换资格。

查询应把授权范围与业务筛选相交。先查全量、分页后再过滤，会导致页数、统计与实际列表不一致，还可能让聚合和导出泄露范围外数据。详情、列表、计数、导出、批量操作应按各自入口落实同样的授权契约。

### 4.2 写操作检查当前对象和变更后的归属

教学 SQL 片段如下，冒号表示应用绑定参数；它只演示行范围约束，不包含动作检查和完整事务：

```sql
UPDATE managed_user
SET display_name = :newName
WHERE id = :targetId
  AND institution_id = :authorizedInstitutionId
  AND department_id IN (:authorizedDepartmentIds);
```

`authorizedDepartmentIds` 必须由后端授权结果产生。空集合应在调用前明确拒绝，不能为了避免 `IN ()` 而删除科室条件。更新零行时可能是记录不存在、范围不允许或并发状态变化，不应直接回报修改成功；对外错误粒度还需避免泄露对象存在性。

如果操作会把用户调到另一个科室，应同时检查当前对象是否可管理、目标科室是否可指派，以及是否需要更高一级权限。只检查旧科室会允许越权调出，只检查新科室可能允许劫持外部用户。批量输入中混入一个越界 ID，应明确整体拒绝或逐项返回结果，不允许静默扩大范围。

### 4.3 授权配置本身也是受保护资源

给用户分配角色、修改管理范围、启停功能属于管理动作，不是普通表单写入。应明确操作者能管理哪些目标、能授予哪些角色/权限、能分配哪些范围，并以服务端身份判断。普通管理员是否可以修改自己的授权、是否允许相互提权，都应有显式规则。

并发修改授权时需要防止无声覆盖，例如提交期望配置版本并执行条件更新；冲突后返回冲突并重新确认，而不是把最后一次请求当作必然正确。数据库唯一约束可防重复关联，但不能证明操作者具备委派权。

**待代码核实：**资源归属从哪里读取；列表和写入是否都包含范围；多科室成员关系如何解释；跨机构 ID、空范围、批量越界、组织转移是否有用例；授权管理接口是否检查委派范围和配置冲突。

## 5. 通用原理：权限快照与版本依赖

### 5.1 快照是一次策略计算结果

权限快照通常保存动作、动作对应范围及计算依据。下面是建议的信息，不是项目字段：

| 信息 | 用途 |
| --- | --- |
| 主体与机构身份 | 防止不同用户、机构之间复用 |
| 动作及各自动作范围 | 保留授权关联，避免形成错误组合 |
| 用户覆盖模式与策略来源 | 解释授权从哪里来 |
| 依赖版本 | 判断结果是否仍然适用 |
| 计算时间与绝对过期时间 | 约束生命周期、定位陈旧问题 |
| 规则版本 | 防止算法升级后继续使用旧算法产物 |

一个主体的有效权限可能依赖用户配置、角色关系、角色默认、科室归属、菜单、功能开关和账号状态。只在修改“用户授权”时增加用户版本，无法自动覆盖角色默认或组织变化。

### 5.2 版本粒度决定失效成本

| 方式 | 好处 | 必须处理的代价 |
| --- | --- | --- |
| 每用户版本 | 读取简单，重建集中于受影响用户 | 角色/组织变更需要可靠找到并失效全部相关用户 |
| 机构级策略版本 | 一次变更可使机构内快照失效 | 小改动也可能造成大批重算 |
| 用户、角色、组织等依赖版本组合 | 更精确地定位变更 | 校验成本高，依赖集合本身也会变化 |

使用哪一种取决于规模和一致性目标，不存在“用了版本号就一定正确”。版本应有明确权威来源和生命周期；若唯一版本 key 过期或 Redis 重建后从零开始，旧令牌或旧快照可能与新值碰巧相等，形成版本复用问题。应从持久版本恢复或使用不可混淆的代际标识，并使旧快照失效。

仅比较“令牌版本 == Redis 快照版本”也可能是两个旧副本彼此一致。必须说明谁代表当前已提交策略、它多久能获知变更，以及权威来源不可达时怎么办。

**待代码核实：**版本在哪里生成、是否持久化；key 维度和 TTL；哪些配置会推进哪些版本；角色变更如何影响所有用户；Redis 丢失、重启或故障切换后的旧令牌如何处理。

## 6. 通用原理：事务提交、版本发布与旧快照回填

### 6.1 提交后发布解决顺序，不自动解决可靠性

先提交授权数据，再发布失效版本，可以避免发布一个最终回滚的策略。但下面的窗口仍存在：

```text
T1 数据库提交撤权成功，策略从 v10 变为 v11
T2 进程退出，或 Redis 版本更新失败
T3 Redis 仍为 v10，旧快照仍包含被撤销动作
T4 请求只比较 Redis 与旧快照，两个版本相同，继续允许
```

Spring 的事务事件可以绑定 AFTER_COMMIT；未启用 fallback 时，没有事务的调用不会按该机制触发监听。参见 [Spring 6.2 事务事件](https://docs.spring.io/spring-framework/reference/6.2/data-access/transaction/event.html)。直接 `TransactionSynchronization.afterCommit()` 的异常可能传回调用方，但提交已完成；不能据此宣称授权数据库写入回滚。参见 [6.2 TransactionSynchronization API](https://docs.spring.io/spring-framework/docs/6.2.x/javadoc-api/org/springframework/transaction/support/TransactionSynchronization.html)。

如果业务需要持久重试，可在同一数据库事务写入授权变更、策略版本和 Outbox，由后台持续发布，提交后回调作为快速路径。这是可选改进方案，**不是现有项目事实**；它解决丢失通知的恢复，不会消除通知传播期间的旧权限窗口。需要更严格的撤权保证时，还要改变请求读取和操作执行的协议。

### 6.2 同一个版本必须对应同一份策略事实

一个错误重建时序是：先读旧授权，随后读到新版本，把两者打包成“v11 的旧权限”。版本检查从此无法识别错误，因为标签已经是最新的。

可选教学设计是：授权变更与持久版本在同一事务推进；重建从同一一致性读取视图获得策略和版本，或在具备明确隔离保证的读取协议中前后检查版本。必须证明所有相关变更都会推进该版本，且不能从落后副本读取旧策略再贴上主库新版本。单独调用两次 get 并不是一致性协议。

### 6.3 旧计算结果不能覆盖新快照

```text
T1 请求 A 读取 v10 的策略，开始计算
T2 管理员提交 v11，并完成版本发布
T3 请求 B 构建并缓存 v11
T4 A 计算结束，试图写入 v10
```

普通 SET 会把新快照覆盖成旧快照。设计上应在发布快照时原子检查当前水位与候选版本；不一致则丢弃候选，并按有界策略重新获取。只防覆盖已有 v11 不够：如果 v11 快照已经删除，A 仍可能将 v10 写进空 key，因此比较依据不能只存在于将被删除的快照里。

Redis 可用 WATCH 配合事务实现乐观条件更新，或由脚本完成校验与写入；它们只能保护 Redis 内的那段操作，不能把数据库读取和 Redis 写入变成同一事务。具体机制见 [Redis 事务文档](https://redis.io/docs/latest/develop/using-commands/transactions/)。集群跨槽、读副本和水位丢失时的行为还需按实际部署验证。

还要区别两件事：拒绝回填旧快照之后，当前请求是否仍拿它继续鉴权？缓存没被污染不等于请求没有错误放行。必须让“候选失效”反馈到当前授权流程，不能失败后直接返回旧结果。

### 6.4 乱序、重试与重建风暴

通知携带单调持久版本时，收到 v12 后再收到 v11，应保留 v12。若每条重复消息都简单 INCR，Redis 数字会逐渐偏离数据库版本，不能再按版本相等理解。设计可以使用其他失效代数，但必须明确映射与恢复规则。

大量用户同时失效会造成数据库重建压力。可以合并同主体的并发重建、限制回源并发并进行短等待；等待超时后进入明确失败策略，不能为了可用性悄悄使用已知撤销的旧权限。

**待代码核实：**提交后更新使用哪一种回调；失败有没有持久恢复责任；构建快照的数据与版本是否一致；条件回填是否原子；旧结果被拒后当前请求如何处理；重复与乱序版本事件如何收敛。

## 7. 通用原理：撤权何时生效与令牌上下文

### 7.1 先说清保证的对象和时点

“实时生效”必须拆成可测试的承诺：

| 承诺 | 能力要求 | 仍存在的边界 |
| --- | --- | --- |
| 下次登录生效 | 登录重建权限 | 已登录会话继续旧权限 |
| 下次请求校验后生效 | 每请求校验足够新的策略依据 | 正在执行的请求和传播窗口 |
| 有界时间内生效 | 可靠恢复、明确刷新/过期上限和故障策略 | 上界必须涵盖所有缓存与重建来源 |
| 撤权提交后禁止新的受保护写入 | 在受保护资源端协调授权版本校验与写入 | 需证明与撤权的并发顺序，不能只依赖入口缓存 |

“TTL 为 60 秒”本身不能证明最多旧 60 秒：续期、旧数据回填、落后副本或丢失版本都可能延长窗口。需要明确快照有效期起点、不可无条件续期、权威读取和失败时的限制；若传播故障无上界，就不能给出有限生效时间承诺。

撤权前已经返回的数据无法追回。入口检查通过、业务写入之前发生撤权，是检查与使用之间的竞态；再检查一次可以缩短窗口，但检查后仍可能竞争。严格协议需要把最终授权检查与副作用放到共同的协调边界，例如同数据库中所有相关写路径都遵守的锁/版本协议，并让撤权与操作在该边界排序。普通事务或一条不带完整并发协议的版本子查询，并不自动提供这种保证。

### 7.2 令牌形式决定“同步上下文”是什么意思

| 形式 | 权限更新方式 | 容易误讲的地方 |
| --- | --- | --- |
| 服务端 Session / 不透明 token | token 定位会话，服务端更新或重建授权状态 | 多实例本地会话和缓存可能未同步 |
| 自包含 JWT | 签发新 token，或请求时以服务端策略覆盖旧声明 | 不能原地修改已签发的 token 字节 |
| token 仅承载身份或版本 | 服务端查询当前有效权限 | 签名有效、未过期不等于动作授权仍有效 |

JWT 定义的是声明载体及相关声明语义，参见 [RFC 7519](https://www.rfc-editor.org/rfc/rfc7519.html)。授权变更如何影响旧 token 是应用协议。刷新前端拿到的新 token，也不意味着其他设备的旧 token 自动失效；服务器必须决定旧 token 如何校验、拒绝或只用于身份定位。

异步任务、导出、WebSocket/SSE 不能只在创建时检查就默认永久有效。需要约定按执行时当前权限还是某种经批准的任务授权运行，并处理结果下载时的权限；不要直接复用脱离生命周期的请求 ThreadLocal。具体上下文机制见 [[02-Spring与微服务/Spring/SpringMVC]]。

### 7.3 失败时保留三种状态

允许、拒绝、无法确定应在内部区分。数据库/Redis 超时不是“空权限配置”，也不是“继承角色默认”的理由。

对管理写操作，无法确认权限时拒绝执行或返回授权服务暂不可用；客户端是否重试由错误契约决定。对低风险读取是否允许已知旧快照，需要明确风险、绝对年龄和审计约定，不能统一缓存穿透后放行。限流回源可避免 Redis 故障把数据库拖垮，但限流失败也不能被解释为授权成功。

**待代码核实：**项目承诺哪种撤权语义；版本校验发生在什么请求路径；是否存在本地缓存、网关缓存和多端会话；令牌上下文实际存在哪里；鉴权依赖失败时是否错误回退；异步任务何时再校验。

## 8. 教学实验：覆盖语义与过期快照

下面是完整 Python 标准库模型。限定为单角色默认、用户整份覆盖、同机构科室集合及一个功能门控。`None` 表示已知的“继承模式”，不是数据库读取失败；示例的功能集合代表授权门控，不模拟单纯菜单展示。

快照实验将“版本检查与发布”视为单线程不可分步骤，且假定版本水位已经可靠发布。它只证明水位已知时拒绝迟到结果，不证明真实 Redis 原子性、跨库一致性或严格撤权。

```python
from dataclasses import dataclass


def effective(role_actions, override, enabled):
    base = role_actions if override is None else override
    return frozenset(base) & frozenset(enabled)


def can_manage(actions, action, actor_org, allowed_depts,
               target_org, target_dept, active=True):
    return (
        active
        and actor_org is not None
        and target_dept is not None
        and action in actions
        and actor_org == target_org
        and target_dept in allowed_depts
    )


@dataclass(frozen=True)
class Snapshot:
    version: int
    actions: frozenset


class CacheModel:
    def __init__(self, current_version):
        self.current_version = current_version
        self.snapshot = None

    def publish_version(self, version):
        self.current_version = max(self.current_version, version)

    def install(self, candidate):
        if candidate.version != self.current_version:
            return False
        self.snapshot = candidate
        return True

    def read(self):
        if self.snapshot is None:
            return None
        if self.snapshot.version != self.current_version:
            return None
        return self.snapshot


role = {"user:read", "user:update"}
assert effective(role, None, role) == frozenset(role)
assert effective(role, set(), role) == frozenset()
assert effective(role, {"user:read"}, role) == frozenset({"user:read"})
assert effective(role, None, {"user:read"}) == frozenset({"user:read"})
assert can_manage(role, "user:update", "H1", {"D1"}, "H1", "D1")
assert not can_manage(role, "user:update", "H1", {"D1"}, "H2", "D1")
assert not can_manage(role, "user:update", "H1", {"D1"}, "H1", "D2")
assert not can_manage(role, "user:update", "H1", set(), "H1", "D1")
assert not can_manage(role, "user:update", "H1", {"D1"}, "H1", "D1", False)
assert not can_manage({"user:read"}, "user:update", "H1", {"D1"}, "H1", "D1")

cache = CacheModel(10)
old = Snapshot(10, frozenset(role))
assert cache.install(old)
cache.publish_version(11)
assert cache.read() is None
assert not cache.install(old)
new = Snapshot(11, frozenset({"user:read"}))
assert cache.install(new)
cache.publish_version(10)              # 模拟旧通知晚到
assert cache.read() == new
cache.snapshot = None                 # 删除快照，水位仍保留
assert not cache.install(old)
assert cache.read() is None
assert cache.install(new)
```

这里故意让缓存未命中返回 `None`：调用方应进入受控重建或明确失败路径，不能把它转换为全部允许。将旧快照丢弃之后也不能继续用旧快照完成本次鉴权。

与此对应，真实集成测试还应覆盖版本未发布、key 丢失、故障切换、读取旧副本、版本与策略混搭等情况；这些不能由单进程模型证明。

## 9. 深入场景：主任调岗、并发授权与异步任务

本节是围绕现有用户管理范围的**设计深化**，不是已经核实的业务实现。沿用H1机构、D1/D2科室和user:update动作，不把用户管理权限自动扩展为患者资料权限。若未来复用到医生Agent，必须另定义患者关系与用途规则。

### 9.1 多角色与覆盖：先判断是哪一种授权，再决定怎么合并

主任角色允许更新D1，支援角色只允许读取D2。若分别合并动作与科室，会得到“可以更新D2”的错误结果。正确计算单元应是 `(action, resourceScope, source)`；默认授权按规则合并同一动作的范围，不能先丢掉动作和范围的关联。

用户显式覆盖还要确认覆盖什么：仅动作集合、各动作的范围，还是整套授权。本文第3节仅定义动作集合替换，资源范围仍由单独契约约束；不能因为用户覆盖了user:update，就获得所有科室。多角色中是否存在deny优先属于另一条产品规则，未经确认不引入。

| 候选 | 选择理由 | 验证边界 |
| --- | --- | --- |
| 按角色复制完整权限和科室 | 简单、角色数量很少时可用 | 科室增长导致角色爆炸、变更重复维护 |
| 角色给动作，角色分配关系给范围 | 适合相同角色跨科室使用 | 必须保留动作与分配范围的绑定 |
| 引入通用策略引擎 | 规则维度和解释需求已超出现有模型时评估 | 增加规则版本、发布、回滚和运维成本；不是替代业务规则定义 |

最小验收不是只看菜单：主任更新D1成功、更新D2失败、读取D2成功、显式空覆盖后两者失败。再加入机构不匹配与功能关闭，确认拒绝不会被后续默认回退覆盖。

### 9.2 调岗撤权：把“实时”改成可以证明的顺序

案例：主任在入口被允许更新D1用户，随后被调到D2，旧请求最后才写数据库。缓存版本更新或MQ及时通知，都不能单独保证这个旧请求不会写入。

对**同一数据库内的敏感管理写入**，可选用机构级policy_guard行串行化授权相关变更与最终写入。它是易验证但较粗的基线，适用于这种竞争较少的管理操作；不用于锁住整个模型调用或所有普通查询。

```text
受保护写入事务：
  锁定H1的policy_guard行（锁持续到事务结束）
  用当前锁定读/明确隔离协议读取策略、角色和组织关系
  锁目标用户，检查当前及修改后归属与委派约束
  允许则更新业务行与审计，COMMIT；拒绝则不写

撤权事务：
  同样先锁定H1的policy_guard行
  修改角色/科室关系，推进policyVersion，同事务写Outbox
  COMMIT后才向外报告撤权已提交
```

如果写入先获锁，它先提交，撤权随后提交；如果撤权先获锁，后来的写入必须看到新策略并被拒绝。由共同锁顺序保证“撤权提交之后，不会再提交基于旧策略的受保护写入”。这不是说撤权请求一到达，就能取消已在执行的事务。

协议成立需要：所有影响该机构授权的写路径都获取guard；所有受保护写路径都参与；策略不从旧Redis或落后副本读；MySQL实现使用当前读或经验证的隔离协议，不能混用旧快照。共享角色/全局功能影响多机构时，要定义全局guard并统一锁顺序，或可靠展开受影响机构；漏一条路径就失去严格保证。锁定读原理参见 [MySQL 8.0说明](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html)。

细粒度用户/角色guard可减少竞争，但依赖集合在变化，容易漏锁或形成死锁；只有测得粗粒度锁等待成为问题后，再设计依赖版本与固定锁顺序。选择依据是撤权语义和锁竞争数据，不是“分布式锁更高级”。跨库、外部发送、已经返回的数据不享有上述保证。

### 9.3 高频角色变更：版本粒度与重建成本的取舍

假设一个角色影响N个用户。逐用户通知需要可靠枚举N个目标；机构级版本只更新一次，但下一波请求可能触发N次重建；依赖版本组合更精确，但每次请求要验证更多依赖。N是工作负载参数，不填写未经测量的项目规模。

候选基线：小规模先用持久机构版本，按主体合并重建、限制回源并发；敏感写入仍走权威授权。测量变更频率、受影响人数、重建耗时及数据库读量，再决定是否细化依赖版本。不要先为可能存在的百万用户实现复杂失效图。

对允许有界陈旧的读取，若策略每Δ秒从权威库刷新一次、快照绝对有效期L从本次权威读取开始计算、时钟误差上界ε且不续期，陈旧窗口才可能由这些约束给出上界。权威读取失败后必须在到期时停止使用；不能无限用旧版本重建并延长TTL。严格管理写入不依赖这个缓存上界。

### 9.4 并发管理员与旧权限预览

管理员A和B同时编辑v7：A清空授权，B基于旧页面增加一项。若无条件覆盖，B会把A撤销的权限带回来。PATCH带expectedVersion，更新时CAS，只有一个提交；另一个409并展示当前策略差异。不能服务端自动合并，否则“明确清空”的意图可能被合并算法破坏。

权限预览也不是授权凭据。正式保存时重新验证操作者的委派权、目标范围和版本；预览后操作者被降权，不能用旧预览结果继续写配置。审计保留前后差异、操作者及实际提交版本，避免只记“修改成功”。

### 9.5 导出与Agent任务：创建时允许不等于下载时允许

主任在D1创建导出，执行前调岗到D2。按当前权限运行的策略下，worker执行时重新验证；生成后、下载前又撤权，则下载入口再次验证，临时文件不可因持有URL就永久公开。长任务分批检查并记录实际授权版本；已经传出的字节无法追回。

医生Agent还要分别检查发起人、审核人和执行主体。服务账号可以提供技术调用身份，但业务授权仍绑定患者、动作、用途和原审批；不能把服务账号的宽权限当成医生获得了授权。是否允许经批准任务在发起人离职后继续，是明确的委托授权产品决策，不能由后台worker默认继承。

关联 [[医生助手Agent开发方案#十一、复杂场景与技术决策依据]]；权限传播可靠性见 [[RabbitMQ与Outbox可靠消息方案#7. 与动态权限、医生助手的关联边界]]。两者是设计参考，不证明原动态权限项目已经接入Agent或Outbox。

### 9.6 如何证明这部分深度

[可靠执行边界实验](../通用系统方案/实验/可靠执行边界实验.py)用SQLite两个连接控制“检查后撤权”和“共同事务串行”两种时序，复现旧入口检查导致的越权写入，再验证撤权先提交后业务写入被拒绝。还检验多角色错误笛卡尔积和显式空覆盖。SQLite写事务锁比MySQL行锁更粗，这只是协议对照，不是MySQL压测或框架集成证明。

正式集成需要补充：机构guard竞争、共享角色变更、非MVC入口、组织转移、死锁重试、主从读差异、失效通知丢失、下载撤权和旧令牌跨设备。每个用例同时断言合法操作能完成与非法操作无效果。衡量权威检查次数、锁等待、误拒、旧候选拒绝和传播时间，避免把“所有请求都拒绝”当成安全方案成功。

| 主题 | 优先检查的入口 | 需要得到的证据 |

| 管理范围 | 机构/科室解析、列表与更新条件 | 跨机构、跨科室、批量混入和组织转移用例 |
| 委派与配置冲突 | 授权保存接口、版本条件更新 | 非法提权被拒绝、并发管理员修改不静默覆盖 |
| 快照依赖 | Redis key、序列化内容、版本生成 | 角色/组织/功能变化触发的失效范围 |
