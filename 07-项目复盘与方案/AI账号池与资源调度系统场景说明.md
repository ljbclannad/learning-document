# AI 账号池与资源调度系统场景说明

> 本文描述一种面向多账号、多上游 AI 服务的通用资源调度系统。它不依赖特定编程语言、框架或产品实现；Sub2API、CPA、模型网关及企业内部 AI 中转服务，都可以用这套思路理解和建设。

## 1. 场景与目标

企业接入多个 AI 服务商、多个订阅账号或多个资源配额时，调用方不应直接感知某个账号、令牌或上游服务。系统将这些差异抽象为可管理的资源，通过统一入口完成鉴权、路由、调度、保护、容错和运营。

```text
调用方 / 业务系统
        ↓
统一 API 网关（认证、配额、审计、协议适配）
        ↓
调度中心（按请求条件选择模型、渠道和资源）
        ↓
账号池 / 资源池（账号、Key、渠道、代理、算力及其实时状态）
        ↓
上游 AI API / 模型服务
```

系统的目标不是单纯“转发请求”，而是在资源有限、能力不一致且上游不稳定的情况下，持续提供可预测的服务：

- 对调用方提供统一且稳定的 API 与错误语义。
- 对资源实现按能力、配额、并发和健康状态的精细调度。
- 通过限流、熔断和故障转移控制风险，避免局部问题扩大。
- 让异步任务可恢复、可追踪，避免重复执行。
- 让运营人员能看见资源利用、故障和成本，并能安全干预。

### 1.1 能力建设原则：由风险驱动，而不是由名词驱动

本文列出的能力是用于识别风险的地图，不是必须一次性全部落地的功能清单。一个生产系统的成熟度，体现在能识别“当前业务已经存在什么风险、哪个最小能力能以可接受成本降低该风险”，而不是在流量、资源规模和故障模式尚未出现前，预先引入完整的复杂架构。

每项能力进入方案前，先回答四个问题：

1. **事实与影响**：已经发生或可量化的风险是什么？影响的是成功率、成本、延迟、数据正确性，还是合规性？
2. **现有措施**：当前用流程、配置或简单实现能否控制？其失效边界是什么？
3. **最小措施**：最小的可验证改动是什么？例如先记录账号状态，再考虑自动熔断；先做单实例限流，再根据横向扩容引入全局协调。
4. **引入代价**：该能力增加了哪些状态、依赖、运维负担和故障模式？是否有指标证明收益超过这些代价？

| 能力层级 | 适合引入的条件 | 可从什么最小形态开始 | 暂不应急于引入的内容 |
| --- | --- | --- | --- |
| 基础可用性 | 已有多账号/多模型，需要避免人工选号和定位困难 | 统一资源登记、静态优先级、请求与资源日志、账号级并发上限 | 复杂的动态权重、跨区域多活调度 |
| 保护与恢复 | 已出现配额打满、上游不稳定、长请求堆积或重复任务 | 分层限流、有界重试、资源冷却、基础异步队列 | 所有错误都自动切换、无限重试、过细的策略编排 |
| 规模化治理 | 多实例部署、资源达到数百/千级、人工运营明显失效 | 原子租约、候选集合索引、健康分、配置版本与仪表盘 | 为未来假想峰值预建复杂分布式协调体系 |
| 高可靠与精细运营 | 核心业务有明确 SLO、成本或合规要求，故障影响可量化 | 演练过的熔断/故障转移、容量预留、审计、按租户隔离 | 未验证备用容量时承诺自动无损切换 |

> 判断标准：如果无法说明“不做会造成什么可验证的损失”，或无法给出“上线后如何证明它解决了问题”的指标，就先不要把它作为系统能力引入。

### 1.2 训练生产敏感度的观察框架

阅读或设计一个模块时，不只问“还能加什么”，而要沿着以下链路思考：

```text
业务目标 / 约束
  → 可能失效的资源、数据或调用链路
  → 可观测的风险信号
  → 最小可行控制措施
  → 验证指标与回滚方式
```

例如，“是否要做全局分布式并发控制”不应从技术选型开始，而应从事实开始：若服务仍为单实例，本地并发上限可满足账号保护；当多实例已造成同一账号被并发超额调度，且这一问题影响成功率或触发上游限制时，才有充分理由引入原子租约。上线后应观察超额并发是否归零、租约泄漏是否可回收、调度延迟是否在可接受范围内。

## 2. 核心对象与边界

### 2.1 核心对象

| 对象 | 含义 | 典型字段或状态 |
| --- | --- | --- |
| 调用方 | 使用统一 API 的用户、租户、项目或应用 | 身份、套餐、权限、配额、限流规则 |
| 模型 | 对外暴露的逻辑能力，如对话、嵌入、图像生成 | 模型别名、能力标签、输入限制、价格策略 |
| 渠道 | 某个上游服务或其接入配置 | 协议、区域、模型映射、总体限额、健康状态 |
| 账号/凭证 | 可调用渠道的具体授权单位 | 密钥、订阅状态、剩余额度、账号级并发、失效状态 |
| 资源 | 可被调度的最小单位；可由账号、代理、模型能力等组成 | 权重、标签、可用性、租约、健康分 |
| 请求/任务 | 一次同步调用或异步工作单元 | 请求 ID、幂等键、状态、重试次数、结果位置 |

### 2.2 应明确的边界

- **账号池不是凭证仓库。** 凭证的保存只是基础；账号池还必须知道账号能做什么、还能做多少、当前是否适合被调度。
- **资源池不等于账号池。** 一个账号可以提供多个模型能力；一个模型也可由多个账号和渠道提供。调度的对象应是“满足当前请求约束的可用资源”。
- **网关与调度分工不同。** 网关负责入口治理和协议统一；调度负责选择资源及处理调用生命周期。
- **本地统计不等于上游真实状态。** 配额、余额和限速信息可能存在延迟或不完整，必须允许对账和纠偏。

## 3. 账号池与资源池

### 3.1 建设步骤

1. **统一资源模型**：将账号、API Key、订阅、代理节点、专属算力等纳入统一模型，同时保留渠道特有字段。
2. **登记能力与约束**：标记资源支持的模型、区域、流式能力、并发上限、频率限制、额度周期与成本。
3. **建立状态机**：至少区分可用、繁忙、冷却、配额耗尽、失效、禁用、待验证等状态，并明确各状态的进入和退出条件。
4. **维护实时指标**：记录当前并发、最近延迟、成功率、错误类型、剩余额度和最近探活时间。
5. **提供安全运营入口**：支持批量导入、分组、标签、权重调整、启停和审批审计；敏感凭证应脱敏展示并加密保存。

### 3.2 注意点与常见问题

| 环节 | 注意点 | 常见生产问题 |
| --- | --- | --- |
| 凭证管理 | 凭证加密、最小权限、轮换和访问审计 | 明文日志或后台页面泄露密钥；轮换后旧凭证仍被缓存调用 |
| 状态更新 | 明确由谁写入、何时过期、如何校正 | 并发计数未释放，账号长期显示繁忙；失效账号仍被调度 |
| 配额统计 | 区分已知额度、估算额度和上游确认额度 | 本地余额乐观扣减或同步滞后，导致频繁触发上游限额 |
| 标签设计 | 标签应描述稳定能力，如区域、模型、优先级 | 使用过多临时标签，筛选规则失控、资源无法解释 |
| 账号隔离 | 按租户、用途或风险等级设置隔离策略 | 高风险流量与核心业务共用账号，触发风控后影响全部用户 |

## 4. 调度策略

### 4.1 调度流程

一次请求的典型调度过程如下：

1. 校验调用方身份、权限、模型访问资格和请求参数。
2. 根据模型、区域、流式要求、成本和租户策略筛出候选资源。
3. 排除不可用、熔断、冷却、额度不足或已达并发上限的资源。
4. 依据策略排序，例如优先级、权重、最少并发、健康分和延迟。
5. 原子地获取一个资源的使用权（租约或并发令牌）。
6. 调用上游；根据结果更新资源指标，并释放或续期使用权。
7. 若可恢复失败，则按规则选择备用资源或延迟重试；记录完整路由链路。

### 4.2 常用策略与适用性

| 策略 | 适用场景 | 主要风险与控制 |
| --- | --- | --- |
| 轮询/加权轮询 | 资源能力相近，追求基本均衡 | 不感知实时压力；应叠加可用性和并发过滤 |
| 最少并发 | 请求耗时差异大，希望降低排队 | 并发计数必须可靠，异常请求要自动回收 |
| 健康度优先 | 上游稳定性差异明显 | 新资源没有历史数据时不能被永久边缘化，应有预热流量 |
| 延迟优先 | 实时交互、流式对话 | 不能只看平均延迟，需关注超时率和长尾延迟 |
| 配额/成本优先 | 多渠道成本差异明显 | 只追求低成本会耗尽廉价资源或牺牲体验，需设置保底策略 |
| 标签匹配 | 区域、合规、模型能力有硬性约束 | 标签或模型映射变更时应有校验，否则可能路由到错误资源 |

### 4.3 千级资源的实践要点

- 不要在每次请求时遍历所有资源；应按模型、渠道、区域或能力维度维护候选集合。
- 静态配置与高频动态状态分开管理。配置可持久化，实时并发和短期健康状态应支持低延迟读写。
- 调度结果要可解释：至少记录“候选为何被排除、最终为何选中”。否则故障期难以定位策略问题。
- 避免热点：相同权重下加入随机扰动或轮转游标，防止所有实例同时选中同一个最优资源。

## 5. 并发控制与限流

### 5.1 分层控制

限流和并发控制应覆盖多个层面：

```text
全局系统保护
  └─ 渠道 / 模型保护
      └─ 账号 / 资源保护
          └─ 租户 / 项目 / API Key 配额
              └─ 单请求参数与输入大小校验
```

- **限流**控制一定时间内允许进入的请求量，例如每秒请求数、令牌数或窗口总量。
- **并发控制**限制同一时刻正在执行的请求数，尤其适合流式或耗时长的调用。
- 两者不可互相替代：只限 QPS 仍可能被长连接堆满；只限并发又可能被短请求突发击穿。

### 5.2 实施步骤

1. 定义各层的保护指标和超限后的行为：拒绝、排队、降级或延迟重试。
2. 选择与业务匹配的计量方式：请求数、Token 数、并发数、金额或组合指标。
3. 为资源调用建立带过期时间的使用权，成功、失败、超时和进程异常都能释放。
4. 返回明确的限流错误和可重试建议，避免客户端无节制立即重试。
5. 监控限流命中率、排队长度和被拒绝请求，定期调整阈值。

### 5.3 常见生产问题

- 多实例下用本地计数限流，导致总体限额被突破。
- 流式响应断开后没有清理并发占用，最终所有资源都“满载”。
- 限流后客户端指数重试未加抖动，引发重试风暴。
- 使用固定窗口导致边界时刻双倍流量；对突发敏感的场景应考虑平滑策略。
- 把上游 429 当作普通异常无限重试，进一步恶化账号或渠道状态。

## 6. 熔断、降级与自动故障转移

### 6.1 三者的关系

- **熔断**：某资源失败达到阈值后暂时不再向它发送正常流量，防止持续放大故障。
- **降级**：无法满足理想服务时，以更低成本、更低能力或异步结果维持核心服务。
- **故障转移**：当前资源或渠道不可用时，把请求转到满足约束的备用资源。

### 6.2 状态与步骤

资源熔断通常经历“关闭 → 打开 → 半开”三个阶段：

1. 正常状态下持续采集超时率、5xx、认证失败、429 和业务错误。
2. 达到阈值后进入打开状态，并设置冷却时间，调度器不再选择该资源。
3. 冷却后只放行少量探测请求进入半开状态。
4. 探测成功则逐步恢复流量；持续失败则重新熔断并延长冷却。
5. 对一次请求，先区分错误是否允许重试，再选择同渠道备份、跨渠道备份或降级结果。

### 6.3 错误分类是前提

| 错误类型 | 通常处理 | 不应做什么 |
| --- | --- | --- |
| 认证/权限失败 | 停用或隔离凭证，触发告警和人工修复 | 继续切换同一失效凭证反复调用 |
| 频率或额度超限 | 短期冷却、降低权重或等下个额度周期 | 无延迟地立即重试 |
| 上游超时/5xx | 有界重试，必要时切换备用渠道 | 把所有请求同时切到单一备用资源 |
| 请求参数错误 | 直接反馈调用方 | 切换资源或不断重试 |
| 内容审核/策略拒绝 | 按明确策略反馈或走合规替代流程 | 伪装为基础设施故障自动绕过 |

### 6.4 注意点与生产问题

- 失败阈值不能只按数量设置，还应考虑时间窗口和最小样本量，否则低流量资源会被偶发错误误熔断。
- 故障转移会造成流量迁移，备用资源必须预留容量；否则会出现级联熔断。
- 非幂等请求不能简单重试。应使用请求 ID 或幂等键，明确哪些操作允许重放。
- 降级策略要事先产品化，例如返回排队任务、使用替代模型或提示稍后重试，而不是临时拼接错误信息。

## 7. 任务队列与异步处理

### 7.1 适用场景

批量生成、长耗时处理、账号探活、额度同步、失败重试、账单汇总、告警投递等任务，不宜长时间占用同步 API 连接，应进入异步处理流程。

### 7.2 任务状态机

```text
待处理 → 执行中 → 成功
             │
             ├─ 可重试失败 → 延迟重试 → 执行中
             │
             └─ 最终失败 → 死信记录 / 人工处理
```

建议每个任务都包含任务 ID、幂等键、创建时间、优先级、重试次数、下一次执行时间、处理结果和失败原因。

### 7.3 实施步骤

1. 区分同步必须返回的操作与可异步化的操作。
2. 在任务创建时完成参数校验并持久化任务意图，再投递给执行者。
3. 消费端以幂等方式执行：同一任务被重复投递也不会产生重复副作用。
4. 失败按错误类型决定立即重试、延迟重试或直接失败。
5. 超过重试上限后进入可检索的死信记录，并提供人工重放或终止能力。

### 7.4 常见生产问题

- 只做到“至少一次投递”，却没有幂等控制，导致重复扣费或重复生成。
- 任务已经写入业务记录但未成功投递，形成“数据有了、任务丢了”的不一致。
- 大量失败任务立即重试，挤占正常任务并打垮上游。
- 消费速度低于生产速度而没有积压告警，最终延迟无法恢复。
- 没有结果保留和可追踪 ID，调用方无法查询异步任务到底是否完成。

## 8. 状态一致性与分布式协调

### 8.1 需要协调的状态

- 某个资源的当前并发和可分配容量。
- 配额、余额和已消耗用量。
- 资源健康状态、熔断状态和冷却时间。
- 任务的归属、执行权和重试进度。
- 配置变更，例如账号禁用、权重修改、模型映射调整。

### 8.2 实施步骤

1. 为每类状态明确“事实来源”：上游、持久化记录、实时协调存储或计算结果。
2. 对抢占型操作使用原子获取与有期限的租约，避免多实例同时把同一账号调度到超额并发。
3. 使用超时、心跳或租约到期回收机制，防止实例宕机后资源永久锁死。
4. 对本地估算值与上游真实值定期对账，发现偏差时记录原因并纠正。
5. 配置更新采用版本号或变更事件，确保所有调度实例最终收到同一份有效配置。

### 8.3 一致性原则

- 对“不能超卖”的状态（如账号并发名额）优先保证原子性。
- 对统计、报表等允许短暂延迟的状态，可采用最终一致性以换取吞吐量。
- 不把分布式锁当成万能方案：锁必须有过期、续约、所有权校验和异常释放设计。
- 所有关键状态变更应可审计，可还原“谁在何时为何改变了资源状态”。

### 8.4 常见生产问题

- 锁没有过期，异常实例使资源永远不可用；或锁过期过短，长请求执行期间被其他实例重复抢占。
- 多处都能修改同一状态，没有单一写入规则，导致并发、配额和熔断状态互相覆盖。
- 依赖缓存状态但没有失效策略，禁用账号仍在一段时间内被继续调度。
- 时钟不一致导致任务提前执行、租约误判或额度周期切换错误。

## 9. 可观测性与运营后台

### 9.1 需要回答的问题

一个可运营的系统应能快速回答：

- 当前某模型的请求由哪些渠道和账号承接？
- 某次失败是调用方参数、网关、调度、资源还是上游造成的？
- 哪些账号即将耗尽、被频繁限流或已进入熔断？
- 哪个租户、模型或渠道带来了异常流量、成本或延迟？
- 故障转移是否成功，是否正在挤压备用资源？

### 9.2 建设步骤

1. **统一标识**：请求贯穿请求 ID、任务 ID、调用方、模型、渠道、资源和重试序号。
2. **记录三类信号**：日志记录单次事实，指标显示聚合趋势，链路追踪还原跨服务路径。
3. **建立仪表盘**：展示可用资源数、资源利用率、QPS、并发、成功率、P95/P99 延迟、429/5xx、队列积压、成本和额度。
4. **建立告警与分级**：例如资源池可用量过低、熔断比例升高、队列持续积压、凭证批量失效、成本异常增长。
5. **建设运营动作**：支持资源启停、权重调整、账号隔离、任务重放、流量切换和审计回溯；高风险操作需要权限控制和审批。

### 9.3 注意点与常见问题

- 指标标签不能无限细分，否则监控系统会因高基数而成本暴涨或查询失效；账号 ID、请求 ID 这类高基数信息更适合日志和追踪。
- 日志需脱敏，尤其是授权头、账号、提示词及模型输出可能包含敏感信息。
- 告警应基于用户影响和趋势，不要只按单次异常触发，否则告警疲劳会掩盖真正故障。
- 后台的“启用账号”“手动重放”等操作必须可审计、可撤销，并避免绕开调度保护规则。

## 10. 一次请求的完整生命周期

```text
请求进入
  → 身份与参数校验
  → 租户/模型限流
  → 筛选候选资源
  → 获取资源并发租约
  → 调用上游
  → 成功：记录用量、指标与审计，释放租约
  → 失败：分类
       ├─ 参数/策略问题：直接返回
       ├─ 可恢复上游问题：有界重试或故障转移
       ├─ 账号问题：隔离/冷却并告警
       └─ 长任务：转为异步任务，供后续查询
```

## 11. 能力演进与方案评审

### 11.1 推荐的渐进路径

```text
能调用
  → 能看见（日志、资源状态、基础指标）
  → 能保护（限流、并发上限、有界重试）
  → 能恢复（冷却、熔断、备用资源、任务重试）
  → 能规模化（多实例协调、批量运营、容量治理）
```

路径不是强制的阶段门槛。某些高风险场景可提前引入特定能力：例如账号存在严格上游并发约束，就应在初期做账号级并发控制；反之，单渠道、低频、可人工恢复的内部工具，未必需要完整任务队列或自动故障转移。

### 11.2 新增能力的评审模板

| 评审项 | 要求 | 示例：是否引入熔断 |
| --- | --- | --- |
| 触发事实 | 说明真实故障、数据或容量证据 | 某渠道在 10 分钟内连续超时，重试使整体成功率下降 |
| 用户影响 | 明确影响范围与优先级 | 对话请求平均等待升高，核心租户无法使用 |
| 最小方案 | 给出先落地的最小控制点 | 按渠道统计失败率；达到阈值后冷却并少量探测恢复 |
| 替代方案 | 比较流程、配置或更简单实现 | 人工停用仅适合低频故障，无法应对夜间突发 |
| 新复杂度 | 列出新增状态、依赖和故障风险 | 熔断状态误判、半开探测流量、备用容量不足 |
| 验证与回滚 | 定义成功指标、灰度范围和关闭方式 | 观察级联失败下降；可按渠道关闭熔断并保留日志 |

### 11.3 常见“为了用而用”的信号

- 方案先出现具体组件或术语，却没有对应的业务风险、容量数据或故障案例。
- 一项能力没有明确的责任边界，多个模块都在做重试、限流或状态更新。
- 新增状态不能被监控、查询或人工修复，只能依赖“它应该会自动恢复”。
- 为解决偶发问题加入全局协调，却没有先验证更简单的隔离、阈值或流程措施。
- 设计承诺高可用，但没有备用资源、压测结果、故障演练和降级说明。

## 12. 上线前检查清单

- [ ] 每一种资源状态都有明确含义、转换条件和恢复路径。
- [ ] 调度决策可追踪，能解释一次请求为何选择或排除某个资源。
- [ ] 限流、并发、配额在多实例部署下不会被绕过或超卖。
- [ ] 所有异常路径都会释放资源租约或等待其自动过期。
- [ ] 重试有最大次数、退避与抖动，并区分可重试和不可重试错误。
- [ ] 熔断、半开探测和故障转移经过压测，备用容量有余量。
- [ ] 异步任务具备幂等、可查询、死信处理和人工恢复能力。
- [ ] 凭证、日志和后台操作满足脱敏、权限与审计要求。
- [ ] 仪表盘、告警和故障演练能覆盖资源耗尽、上游超时、凭证失效和队列积压。

## 13. 总结

AI 账号池与资源调度系统的核心，是把不稳定、有限额、能力各异的账号和上游服务，转化为可描述、可选择、可保护、可恢复、可运营的资源。账号池提供资源事实，调度策略决定资源选择，限流与并发控制保护容量，熔断和故障转移处理不确定性，任务队列承接长耗时与重试，一致性机制保证多实例协作，而可观测性与运营后台使整个系统真正可长期维护。
