
# 1. 网关到底是什么？和反向代理 / Ingress / Service Mesh 有啥区别？

1. 网关（API Gateway）：系统的“统一入口”，在路由转发之外，重点做鉴权、限流、灰度、观测、协议适配等跨服务治理能力。
2. 反向代理（Nginx/HAProxy）：更偏“L7/L4 代理能力本身”，核心是转发、负载均衡、TLS、缓存；也能做一些治理，但通常缺少“面向 API 的治理体系/控制面”。
3. Ingress（K8s）：Kubernetes 的“入口声明规范 + Controller 实现”。它解决的是把集群外流量引入集群内 Service。功能取决于 Controller（Nginx Ingress/Traefik/Envoy 等），本身不是一个具体网关产品。
4. Service Mesh（服务网格，Istio/Linkerd）：把治理能力下沉到每个服务旁路代理（sidecar/ambient），做**服务到服务（east-west）**的流量管理与安全（mTLS、熔断、重试、路由、观测），入口（north-south）通常用 IngressGateway（本质是 Envoy）。
5. 一句话区分：
    - 反向代理：代理转发能力
    - 网关：面向 API 的统一治理入口（north-south）
    - Ingress：K8s 入口的配置/控制器机制
    - Service Mesh：服务间流量治理体系（east-west），入口只是其中一环


## 1.1 Nginx 也能转发，为什么还要网关？

1.	统一策略：鉴权（JWT/OAuth2/签名）、黑白名单、CORS、统一错误码、统一 header/traceId —— Nginx 能做一部分，但复杂度会上升，逻辑难维护。
2.	细粒度流量治理：按 route/userId/appKey/租户 限流、灰度（按人群/比例/标签）、A/B、动态开关 —— 这类更适合网关的过滤器链 + 配置中心。
3.	可观测与排障：统一 access log、指标（按路由/下游）、链路追踪注入；网关更容易把“入口视角”标准化。
4.	动态能力：路由/规则热更新、与注册发现（Nacos/Eureka）联动；Nginx 每次改配置/reload 的发布链路更重。
5.	纵深防御：外层 Nginx 做 TLS/连接与基础防护，内层网关做应用治理；服务里仍保留关键校验，出事可回退。
6. 一句话总结：Nginx 负责“扛流量和代理”，网关负责“业务入口治理与策略编排”。

## 1.2 Ingress Controller 和网关职责如何划分？

1. 划分的核心看两条：谁负责把流量“带进集群”，谁负责把流量“按业务治理”。

2. Ingress Controller（偏基础设施 / 平台层）
    - 解决 north-south 入口接入：域名/证书、L7/L4 转发、基础路由到 K8s Service
    - 更偏“集群级通用能力”：TLS 终止、静态/压缩、基础限流/黑白名单、WAF（看实现）
    - 目标是稳定、通用、低耦合，尽量不掺业务语义

3. API 网关（偏应用治理 / 业务入口层）
    - 解决 面向 API 的治理：鉴权（JWT/OAuth2/签名）、多租户、细粒度限流（按用户/租户/接口）、灰度/A-B、统一错误码、API 版本
    - 更容易接配置中心/注册发现，做动态策略与统一观测（route 维度指标）

4. 常见落地架构
    - 外层：Ingress Controller 暴露 *.company.com → 转发到内层 Gateway Service
    - 内层：Gateway 做应用级路由与治理 → 各微服务

# 2. Spring Cloud Gateway 的核心处理链路是什么？

1. SCG 的核心链路可以用一句话概括：
    - 请求进来 → 根据 Predicate 匹配 Route → 组装并执行 Filter 链 → 通过 Netty/HttpClient 转发到下游 → 返回时走响应 Filter 回写。

2. 更面试口径一点的要点：
    - Route 定位：RoutePredicateHandlerMapping 用一组 Predicates（Path/Host/Header 等）挑中一个 Route
    - Filter 链：把 GlobalFilter + 该 Route 的 GatewayFilter 按 order 排序，形成链（前置/后置）
    - 转发执行点：NettyRoutingFilter（核心）负责把请求发给下游（通常用 Reactor Netty HttpClient）
    - 返回链路：响应回来后按链路“倒序”执行后置逻辑（日志、改响应头、统一错误码等）

3. 一句记忆法：Mapping 找路由，Filters 做治理，NettyRoutingFilter 真转发，响应回程再过一遍后置 Filter。

## 2.1 Gateway 的 Filter 链如何执行？GlobalFilter 和 GatewayFilter 区别？

1. Filter 链执行方式：典型的“责任链”。
请求命中某个 Route 后，SCG 会把 GlobalFilter + 该 Route 配置的 GatewayFilter 合并、按 order 排序，依次调用；每个 filter 都是 filter(exchange, chain)，在 chain.filter(...) 之前是前置逻辑，之后是后置逻辑（响应回程时执行）。

2. GlobalFilter vs GatewayFilter 的区别：
    - 作用范围
        - GlobalFilter：对所有路由生效（全局）
        - GatewayFilter：只对某个 Route（或某个 RouteLocator 中定义的那组路由）生效
    - 典型用途
        - GlobalFilter：traceId 注入、统一鉴权入口、统一日志、全局 CORS、全局限流入口
        - GatewayFilter：某条路由的重写/加头/特定服务的灰度/某个 API 组的限流
    - 配置方式
        - GlobalFilter：代码注册 Bean（或框架内置）
        - GatewayFilter：可以配置化（yml 里 filters:）或代码自定义（实现 GatewayFilterFactory）

3. 一句话：GlobalFilter 管“全站通用”，GatewayFilter 管“路由定制”；执行上都是同一条链，按 order 排。

# 3. 为什么 SCG 基于 WebFlux/Netty，而不是 Servlet？

1. 因为网关是“高并发 I/O 转发器”，SCG 选 WebFlux + Netty主要为了：非阻塞、少线程扛更多连接、转发更高效。

2. 精简要点：
    - 线程模型更适合网关：Netty 事件循环（EventLoop）用少量线程处理大量连接/请求，避免 Servlet“一请求一线程”在高并发下线程爆炸、上下文切换重。
    - 天然适配流式转发：网关常做 proxy（请求/响应 body 流式传输），WebFlux 的响应式模型更容易做 backpressure（背压）和流式处理。
    - 更贴合异步生态：路由、过滤、调用下游都可以链式异步，不用靠线程池硬抗。

3. 面试加分的提醒（也算“坑”）：
    - Netty 线程不适合阻塞：在网关里做阻塞 I/O（查 DB、同步 HTTP、Thread.sleep）会卡住 EventLoop，导致吞吐骤降、延迟飙升。正确做法是：尽量无阻塞（JWT 校验、缓存命中），或把阻塞操作切到专用线程池。

## 3.1 Netty 线程模型大概是什么？事件循环（EventLoop）为什么不适合阻塞？
1. Netty 线程模型（简版）：
    - Boss（acceptor）：少量线程负责 accept 新连接，把连接分配给某个 worker。
    - Worker（EventLoop）：每个连接（Channel）绑定到一个 EventLoop（单线程），负责这个连接上的 读/写事件、定时任务、回调执行。
    - Pipeline：事件进来按 ChannelPipeline 的 handler 依次处理（编解码、业务 handler 等）。

2. 为什么 EventLoop 不适合阻塞？
    - EventLoop 是“单线程串行处理一堆连接的事件”。一旦你在这个线程里阻塞（DB 查询、同步 HTTP、sleep、等待锁），这个 EventLoop 管的所有连接的 I/O 事件都得排队等它醒来。
    - 结果是：延迟飙升、吞吐暴跌、连接堆积，进一步触发超时、重试、雪崩放大（在网关场景尤其致命）。

3. 一句话：Servlet 是“一个请求卡住只卡一条线程”，Netty EventLoop 是“卡住一次，卡一串连接”。

## 3.2 如果你在 Gateway 里做了阻塞 I/O（查 DB/调外部接口），会发生什么？

1. 会把网关从“高并发转发器”变成“排队等死器”，典型后果是链式雪崩：
    - EventLoop 被阻塞：同一个 EventLoop 负责的一批连接读写事件都处理不了 → 请求开始堆积。
    - 延迟飙升 + 超时增多：上游看到 RT 变长、504/502 增多；下游也会收到更突发、更不均匀的流量。
    - 连接与内存压力上来：积压导致连接占用、缓冲区/队列膨胀，最终可能 OOM 或 FD/连接耗尽。
    - 重试放大：客户端/上游重试（或网关重试）会进一步加压，形成正反馈雪崩。

2. 面试补一句“正确做法”更加分：
    - 网关尽量只做非阻塞/轻逻辑（JWT 校验、缓存命中、签名校验），需要阻塞操作就下沉到服务，或把阻塞切到专用线程池并做超时/舱壁隔离（bulkhead）。

## 3.3 如何正确做鉴权（比如 JWT 校验）又不阻塞？

1. 在 Gateway 里做 JWT 鉴权要做到“不阻塞”，核心原则是：只做 CPU 计算 + 本地/内存数据读取，避免任何同步 I/O。

2. 精简做法（面试口径）：
    - JWT 校验本身是纯计算：解析 token + 验签（HMAC/RSA/ECDSA）+ 校验 exp/nbf/aud/iss —— 这一步不需要阻塞。
    - 密钥获取不阻塞：用本地配置/内存缓存（定时刷新 JWK/公钥）；不要每个请求去调认证中心拿公钥/查 session。
    - 黑名单/登出态怎么做（避免每次查 DB）：用 Redis 也行，但要用异步客户端（Lettuce reactive）或在网关侧尽量减少依赖查询；更常见是用 短 token + refresh token，降低“强制撤销”的频率。
    - 必须查外部依赖时：把调用放到专用线程池/Reactive 客户端，并加超时、隔离（bulkhead），避免卡 EventLoop。

3. 一句总结：JWT 校验在网关做没问题；问题不在 JWT，而在“你为了校验去查库/调外部服务”。

# 4. 网关如何做灰度/金丝雀？（按比例/按用户/按 Header）

1. 主答（怎么做）
    - Header 灰度：X-Gray=true 或 X-Version=v2 命中就走 v2。
    - 按用户灰度：基于 userId/tenantId/deviceId 做哈希分桶（稳定命中）。
    - 按比例灰度：本质也是哈希分桶，只是阈值比例不同（比如 5%）。

2. 原理（为什么这样做才对）
    - 灰度的关键不是“分流”，而是“稳定分流”：同一用户/同一会话最好始终落在同一版本，否则会出现：
    - 体验抖动（同一操作一会儿正常一会儿异常）
    - 数据不一致（v1/v2 行为差异导致“半套流程”）
    - 排障困难（同一个 trace 混着走两个版本）

3. 落地例子
    - bucket = hash(userId) % 100，bucket < 5 → 5% 走 v2；白名单用户直接强制走 v2（优先级最高）。

## 4.1 “按比例”怎么做才能稳定？一致性哈希/会话粘滞怎么处理？
1. 结论：不要 random()，要用“确定性哈希”，必要时用 cookie 做粘滞。

2. 原理
    - random() 每次请求都可能不同 → 用户会在 v1/v2 来回跳。
    - 确定性哈希把“随机”变成“对某个用户恒定不变的随机”，从而稳定命中。
    - 没有用户标识（未登录）时，用 deviceId/cookie 作为哈希输入实现粘滞。

3. 例子
    - 已登录：hash(userId)
    - 未登录：网关种一个 device_id cookie，再 hash(device_id)
    - 会话粘滞不是为了“负载均衡粘住某台机器”，而是为了“版本粘住 v1/v2”。

## 4.2 灰度回滚如何做到“秒级止血”？

1. 结论：回滚不是重发版，是“改规则”：把灰度比例调 0/禁用 v2 route。

2. 原理
    - 网关的分流由配置/路由规则决定。只要规则来自配置中心（Nacos/Apollo/DB），并且网关支持热更新，回滚就变成一次配置变更，传播时间取决于刷新周期/推送机制，通常秒级～分钟级。

3. 落地动作
    - 一键开关：gray.enabled=false
    - 比例回退：gray.percent=0
    - 保险丝：一旦 v2 错误率超阈值，自动把比例降到 0（配合监控告警/自动化）。

## 4.3 多服务同时灰度如何避免版本不兼容？

1. 结论：靠两条：契约向后兼容 + 同一条链路版本一致。

2. 原理
    - 灰度期间会出现 v2 调 v1、v1 调 v2 的混搭，如果接口/消息不兼容就炸。解决方式：
    - 契约兼容：API 字段“只加不删”、语义不变；消息 schema 版本化；消费者按“能识别的字段子集”处理。
    - 链路一致：网关把灰度标签（header/cookie）透传到下游，服务间调用也透传，让整条链路同一个用户都走 v2（或者都走 v1）。

3. 例子
    - 网关加 X-Release=v2，所有服务调用都透传；下游根据该 header 选择 v2 的依赖或配置。

# 5. 网关鉴权应该放哪？网关验 JWT 够不够？

1. 主答（怎么放）
    - 网关做“通用粗校验”：JWT 验签、过期、issuer/audience、基础黑名单、IP/UA 风控。
    - 服务做“强业务校验”：资源级权限（是否能访问这个 patientId/订单/科室）、数据域隔离（tenant/hospital）。

2. 原理（为什么不只放网关）
    - 网关不知道业务语义：它只能判断“你是谁”，很难判断“你能不能操作这个资源”。
    - 只靠网关是单点信任：一旦出现旁路调用/内网误开放/网关漏洞，服务就裸奔。
    - 所以需要：纵深防御：外层挡垃圾流量，内层守业务边界。

## 5.1 网关验签后把 userId 透传到服务，服务还要不要再验？
1. 结论：要，至少做“信任边界校验”和“业务权限校验”。

2. 原理
    - X-User-Id 这种 header 不是加密的，客户端可以伪造。
    - 服务必须确认请求确实来自可信网关，否则任何人直连服务就能带个 X-User-Id=1 冒充管理员。
    - 其次，userId 只是身份，不代表对资源有权限，服务必须做授权（RBAC/ABAC）。

3. 落地
    - 网络层：服务只允许网关网段访问（安全组/ACL）。
    - 加固：网关对透传 header 做签名（HMAC + timestamp + nonce），服务验签。
    - 业务：服务再查权限/数据域。

## 5.2 如何防止客户端伪造 X-User-Id 之类头？

1. 结论：两步：清洗 + 证明来源。

2. 原理
    - 清洗：网关把来自客户端的 X-User-Id / X-Role 全部移除，只保留自己生成的。
    - 证明来源：服务只接受来自网关的请求（网络隔离），或校验“网关签名头”，让攻击者即便能直连也伪造不了签名。

3. 例子
    - 网关生成 X-Auth-Sign=HMAC(secret, userId|ts|nonce|path)
    - 服务验签 + 校验 ts 不过期 + nonce 防重放。

## 5.3 内外网调用、旁路调用（跳过网关）怎么处理？
1. 结论：默认“禁止旁路”，确需旁路就让服务自带鉴权，别把安全只押在网关上。

2. 原理
    - 旁路调用一旦存在，就等于你把信任边界打了洞。
    - 生产最稳：服务端口不对公网暴露，只对网关/LB 开放。
    - 内部调用：走内网网关或 service mesh（mTLS + policy）。
    - 需要直连：服务必须支持同等鉴权（JWT/签名），并做审计。


# 6. 限流怎么设计？网关限流 vs 服务限流怎么分工？

1. 主答（分工）
    - 网关限流：入口保护、总量控制、按 route/租户/appKey/user 维度，优先挡住洪水。
    - 服务限流：细粒度资源（热点参数）、关键接口、依赖隔离（下游慢/炸时保护自身）。

2. 原理（为什么要两层）
    - 网关挡住的是“进系统的流量”；挡不住“系统内部的流量”（服务间调用、重试风暴、定时任务）。
    - 服务最懂资源热点：例如挂号的 doctorId/scheduleId，只有服务知道哪个参数代表热点、如何降级。
    - 所以两层结合才能同时解决“外洪水”和“内失控”。

## 6.1 你会按 IP 限还是按 userId/appKey 限？为什么？

1. 结论：外部防刷优先 IP/网段；业务公平性优先 userId/appKey；通常组合使用。

2. 原理
    - IP 限流简单、成本低，但 NAT/代理会误伤（很多人共享一个 IP）。
    - userId/appKey 更符合“谁在用就限制谁”，更公平，但需要可靠身份（鉴权前置）和分布式计数。
    - 组合策略：先用 IP 做粗拦截（挡扫描/攻击），再用 user/app 做精细配额（SLA、租户隔离）。

3. 例子
    - 未登录接口：按 IP（注册/登录）
    - 已登录接口：按 userId
    - 第三方合作：按 appKey（配额/计费）

## 6.2 分布式限流怎么做（Redis/Lua、令牌桶、漏桶）？一致性和性能怎么权衡？

1. 结论：高一致性用 Redis+Lua 原子计数；高吞吐可用本地限流+集中校准；算法上令牌桶最常用。

2. 原理
    - 令牌桶：允许突发（burst），适合互联网流量；实现为“按时间补 token，取 token 才放行”。
    - 漏桶：更平滑，适合严格速率；但对突发不友好。
    - Redis+Lua：把“读计数+改计数+判断”放到一个脚本里原子执行，避免并发穿透。
    - 性能权衡：全都打 Redis 会有 RTT 成本，所以常见做法是“网关本地令牌桶 + 定期同步/配额”，或者用专门限流组件（Sentinel 集群流控）。

## 6.3 “重试 + 限流”会不会打架？如何避免雪崩放大？

1. 结论：会。限流触发后重试会放大流量；要对重试做“条件 + 上限 + 退避”。

2. 原理
    - 当系统已经忙（429/限流）时再重试，相当于在火场里加油。
    - 正确做法：
        - 只对幂等请求重试（GET/可幂等 POST）
        - 看到 429/503 直接失败或指数退避
        - 设置重试总次数和全链路超时预算
        - 服务端也要做幂等，避免重试造成重复写

# 7. 熔断降级应该在网关做还是在服务做？

1. 主答：网关做“入口级粗熔断/统一降级”，服务做“按下游/按接口细熔断”，以服务侧为主，网关兜底。

2. 原理
    - 网关看到的是“整体请求结果”，粒度容易过粗，误伤面大。
    - 服务能区分是 DB 慢、第三方慢、某个接口慢，并做针对性降级（返回缓存/异步化/兜底数据）。

## 7.1 熔断的触发信号来源是什么（RT、异常比例、异常数）？

1. 答（原理）
    - 慢调用/RT：下游变慢会占用线程/连接，先熔断避免拖垮。
    - 异常比例：持续失败说明下游不可用，熔断减少无效请求。
    - 异常数：在低流量场景异常比例不敏感，用异常数更稳定。
    - 触发后进入 open 状态，过一段进入 half-open 试探，成功再 close。

## 7.2 网关熔断会不会误伤（一个下游慢导致全站熔断）？

1. 结论：会；避免靠“细粒度”和“只对特定下游/路由熔断”。

2. 原理
    - 网关如果按“全站”熔断，一个服务慢可能导致所有接口都被降级。
    - 解决：熔断维度至少到 routeId 或 upstream，不要做全局一刀切；同时给关键接口更高优先级（白名单/独立配额）。

## 7.3 如何做“分下游/分接口”的熔断？

1. 答（原理）
    - 网关：按 routeId 统计指标并熔断（只影响那条 route）。
    - 服务：按“调用点”熔断（比如某个第三方 client、某个 DB 查询、某个接口），这才是真正精细的隔离。

# 8. 超时、重试、幂等：网关能不能重试？

1. 主答：能，但要非常克制：仅对幂等请求，并且遵守超时预算、退避、次数上限；写接口通常不在网关重试。

## 8.1 哪些请求可以重试？怎么判断幂等？

1. 答（原理）
    - GET/HEAD 通常幂等，可重试。
    - POST/写操作除非你有幂等键（Idempotency-Key / 业务唯一号），否则重试可能重复下单/重复扣款。
    - 判断标准：同一请求重复执行，系统最终状态是否一致、是否会产生额外副作用。

## 8.2 支付回调/下单重试会造成什么事故？怎么兜底？

1. 答（原理）
    - 事故：重复扣款、重复发货、状态机乱跳、消息重复。
    - 兜底：
    - 服务端必须幂等（唯一约束/状态机检查/去重表/Redis 处理态）
    - 网关不重试写请求；真正需要重试放在“可控的异步补偿”（MQ 重试、延迟队列）里，并且有上限与告警。

## 8.3 网关超时与服务超时如何配合（谁更小）？

1. 结论：网关超时应略小于服务端总超时预算，形成“逐层递减”。

2. 原理
    - 如果网关超时比服务更大，网关会一直占着连接等下游，积压更严重；逐层递减可以让上游更早释放资源，减少排队。
    - 实践：客户端 > 网关 > 服务入口 > 服务内部调用（DB/第三方）逐层更小。

# 9. 统一可观测性：日志、指标、链路追踪

1. 主答：入口统一生成/透传 traceId，网关记录“入口与下游耗时”，服务把 traceId 写入 MDC 日志，指标按 route 和 upstream 维度聚合。

## 9.1 traceId/requestId 谁生成？如何贯通到 MDC？

1. 答（原理）
    - 通常网关生成（或沿用客户端带来的），写入 X-Request-Id/traceparent 并透传。
    - 服务端 filter/interceptor 把该 header 放入 MDC（MDC.put("traceId", ...)），日志格式带 %X{traceId}。
    - 用同一个 ID 把“网关日志 → 服务日志 → 依赖日志”串起来。

## 9.2 网关如何记录 upstream_response_time、状态码分布？

1. 答（原理）
    - 网关在转发点前后打点：
    - gateway_time（网关自身处理）
    - upstream_time（从发到收的下游耗时）
    - 并按 routeId/upstream/status 打指标直方图；状态码做计数（2xx/4xx/5xx、429、502/504）。

## 9.3 如何用网关指标定位“网关慢还是下游慢”？

1. 答（原理）
对比两段时间：
    - total_latency ≈ gateway_overhead + upstream_latency
    - 若 upstream_latency 高，是下游慢；若 gateway_overhead 高，查网关 CPU/GC/EventLoop 阻塞/过滤器耗时。
    - 原理：把延迟拆成可归因的组成部分。

# 10. 网关高可用与扩展：如何避免单点？

1. 主答：网关必须无状态、可水平扩容，前面用 LB/Nginx 分发；配置与规则热更新要分批发布避免抖动；容量规划看连接数/FD/TLS。

## 10.1 网关横向扩容怎么做？无状态化要求是什么？

1. 答（原理）
    - 扩容：多实例 + LB；会话不要落本地（或用共享 session/Token）。
    - 无状态：不依赖本机内存保存用户态（或只做短期缓存可失效）；路由/规则来自配置中心；实例随时可替换。

## 10.2 配置热更新怎么做？发布配置如何避免全站抖动？

1. 答（原理）
    - 热更新：配置中心推送/轮询刷新，路由/限流规则动态生效。
    - 避免抖动：灰度发布配置（分批生效）、变更审计、回滚开关；避免频繁全量刷新导致路由重建/连接抖动。

## 10.3 连接数、FD、TLS 握手、HTTP2 对资源影响怎么评估？

1. 答（原理）
    - 连接数/FD：每连接占一个 FD，需调高 ulimit，监控连接数与 TIME_WAIT。
    - TLS：握手 CPU 贵，建议复用连接、启用 session resumption，把 TLS 终止放在更合适的一层。
    - HTTP/2：多路复用减少连接数，但单连接承载更大流量，需关注单连接队头阻塞与窗口设置。

# 11. 支付回调风暴把网关/服务打爆，你怎么止血？

1. 主答：先入口止血（限流/丢弃非法/降级），再服务幂等与队列治理，最后把重试变成“可控重试”。

## 11.1 入口限流按 IP 还是 appKey？
1. 答（原理）
    - 回调通常来自固定渠道/签约方：优先按 appKey/商户号 配额，更公平也更准确。
    - 同时加 IP/网段白名单做外层防刷。
    - 原理：IP 在 NAT 下不可靠，而 appKey 是业务身份维度。

## 11.2 追问：验签失败/解析失败如何快速丢弃？

1. 答（原理）
    - 网关/服务入口做“快速失败”：
    - 先做轻校验（必填字段、签名存在）
    - 验签失败直接 4xx，不进入业务链路
    - 原理：把无效请求挡在最便宜的地方，避免占用线程/DB。

## 11.3 追问：服务侧幂等如何设计（PROCESSING/DONE，唯一约束）？

1. 答（原理）
    - 以 paymentId/transactionId 做唯一键，先写入状态 PROCESSING（或用 Redis setnx）
    - 已 DONE 的直接返回成功（幂等）
    - 状态机推进必须校验“允许的前置状态”，乱序也不会跳状态
    - 原理：用“唯一性 + 状态机”把重复/乱序收敛成一次有效处理。

## 11.4 追问：如何避免错误重试造成风暴（nack requeue=true）？

1. 答（原理）
    - 区分“可重试/不可重试”异常；不可重试直接 ack 丢弃或进死信。
    - 可重试用延迟重试（TTL+DLX/延迟队列）+ 退避 + 次数上限。
    - 绝不在所有异常都 requeue=true。
    - 原理：立即 requeue 会形成热循环，把 MQ/CPU 打满。


# 12. 下游慢导致网关堆积，全站超时

1. 主答：先减少排队（限流/超时/熔断/隔离），再定位是下游慢还是网关慢，最后治理依赖与容量。

## 12.1 追问：如何从指标判断下游慢还是网关慢？

1. 答（原理）
    - 看网关拆分指标：upstream_latency vs gateway_overhead。
    - upstream 高：下游慢/连接池满/依赖慢
    - overhead 高：网关阻塞、CPU/GC、EventLoop backlog
    - 原理：延迟可拆分才能归因。

## 12.2 追问：网关与服务超时怎么设？

1. 答（原理）
    - 逐层递减：客户端 > 网关 > 服务入口 > 服务内部依赖。
    - 原理：越靠内层越应该更快失败，避免外层长时间占用连接导致堆积。

## 12.3 追问：EventLoop 被占满怎么恢复？如何避免排队等死？

1. 答（原理）
    - 恢复：限流/熔断把流量降下来，必要时扩容网关实例；排查是否有阻塞 I/O 在网关过滤器里。
    - 避免：禁止阻塞、把慢操作下沉或放专用线程池 + 舱壁隔离（bulkhead）。
    - 原理：EventLoop 单线程处理一堆连接，阻塞一次就卡一片。

# 13. 灰度后部分用户 401/403，如何排查？

1. 主答：先查“规则与透传”，再查“密钥/时钟”，最后查“网关与服务鉴权一致性”。

## 13.1 追问：header 透传丢失？Host/Path 重写影响鉴权？

1. 答（原理）
    - 检查网关是否把 Authorization/cookie strip 掉或重写路径导致签名串不一致。
    - 检查代理层 Host 变化导致回调域、aud/iss 校验不通过。
    - 原理：鉴权往往对 header/path/host 敏感，灰度路由链路变了就可能破。

## 13.2 追问：JWT 时钟偏移/密钥不同步怎么查？

1. 答（原理）
    - 对比网关/服务机器时间（NTP），exp/nbf 对时间敏感。
    - 灰度集群若用了不同密钥/JWK 未同步，会导致部分实例验签失败。
    - 原理：灰度把“配置不一致”问题放大成“只影响部分用户”。

## 13.3 追问：网关与服务鉴权逻辑不一致如何治理？

1. 答（原理）
    - 统一鉴权库/统一配置源（同一套 issuer/audience/jwk）。
    - 网关做粗校验，服务做业务授权；避免两边重复且规则不一致。
    - 原理：双处实现容易漂移，必须“单一事实来源”。

# 14. 按租户隔离的限流与熔断

主答：以 tenantId 作为治理维度，在网关做配额，在服务做热点/依赖隔离，关键是 tenantId 必须可信且贯通链路。

## 14.1 追问：tenantId 从哪来？如何可信获取？

1. 答（原理）
    - 来自 JWT claim/签名参数/网关认证后的会话。
    - 可信性靠：网关验签后注入 header + 服务端验来源（内网/签名头）。
    - 原理：不可信的 tenantId 会被伪造，隔离策略会被绕过。

## 14.2 追问：租户限流怎么落地（网关/服务/Redis key）？

1. 答（原理）
    - 网关：rate_limit:{tenantId}:{route} 令牌桶/计数器做配额。
    - 服务：热点资源再细分（如 tenantId + doctorId）。
    - 原理：入口配额保证公平，服务细分保护热点。

## 14.3 追问：租户 A 异常会拖垮租户 B 吗？怎么隔离？

1. 答（原理）
    - 资源隔离：线程池/连接池按租户配额或至少按接口隔离；限流按租户维度。
    - 依赖隔离：对 A 的慢调用熔断不影响 B（熔断维度要带 tenantId 或 route）。
    - 原理：隔离的本质是“共享资源变成可控共享或拆分”。

# 15. 同时支持 HTTP、WebSocket、gRPC：网关怎么选、怎么配？

主答：Nginx 擅长 HTTP/WebSocket；gRPC 更推荐 Envoy；SCG 做 HTTP 很舒服，但 gRPC/高性能代理上 Envoy 更合适，常见是“边缘 Envoy/Nginx + 内层 SCG”。

## 15.1 追问：Nginx/SCG/Envoy 协议支持差异？

1. 答（原理）
    - Nginx：HTTP 反代强，WebSocket 成熟；gRPC 支持存在但治理能力有限。
    - SCG：HTTP 路由/治理强（Java 生态），但本质是应用框架，做高性能多协议代理不如 Envoy 专业。
    - Envoy：为代理而生，HTTP/2、gRPC、mTLS、观测、限流熔断生态最完整。
    - 原理：是否“代理型基础设施”决定其协议与性能边界。

## 15.2 追问：WebSocket 超时与代理头怎么配？

1. 答（原理）
    - 需要 Upgrade/Connection 相关头正确透传；读写超时要拉长（proxy_read_timeout）。
    - 网关/代理层要避免把 WS 当短连接处理。
    - 原理：WS 是长连接，默认超时策略会误断。

## 15.3 追问：gRPC 需要 HTTP/2，TLS 在哪里终止更合理？

1. 答（原理）
    - 边缘终止 TLS（Nginx/Envoy）降低后端复杂度；需要端到端安全就做 mTLS（mesh/Envoy）。
    - 若要透传 HTTP/2/gRPC，代理层必须支持 h2，并正确配置 upstream。
    - 原理：TLS 终止位置影响 CPU、证书管理、以及是否能做端到端身份认证。
