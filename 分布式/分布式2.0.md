# 1. 微服务与DDD的区别
**微服务（Microservices）** 和 **领域驱动设计（DDD, Domain-Driven Design）** 是两个不同层面的概念，但它们可以结合使用来设计和实现复杂的分布式系统。以下是两者的核心区别和联系：

---

## **1. 定义与核心关注点**

### **微服务（Microservices）**

- **定义**：
  
    - 微服务是一种架构风格，将单一的应用程序拆分为多个小的、独立运行的服务。
    - 每个服务围绕特定的业务能力构建，能够独立开发、部署和扩展。
- **核心关注点**：
  
    - 服务的独立性：独立的开发、部署、扩展。
    - 技术的多样性：**不同服务可以使用不同的技术栈**。
    - 运维和扩展：支持分布式部署和自动化运维。

---

### **领域驱动设计（DDD, Domain-Driven Design）**

- **定义**：
  
    - DDD 是一种软件设计方法论，通过深度理解业务领域，将业务模型作为核心来设计和实现软件。
    - 强调通过与领域专家的紧密合作，构建准确的领域模型来解决复杂业务问题。
- **核心关注点**：
  
    - **领域模型**：以业务为核心，构建与现实领域相符合的模型。
    - **边界划分**：通过 **限界上下文（Bounded Context）** 明确业务子领域的边界。
    - **领域语言**：团队共享统一的 **通用语言（Ubiquitous Language）**。

---

## **2. 两者的区别**

| **对比维度**    | **微服务**                   | **领域驱动设计（DDD）**        |
| ----------- | ------------------------- | ---------------------- |
| **关注层次**    | 架构层次，关注系统的分布式部署和独立性       | 设计层次，关注业务逻辑和领域模型的表达    |
| **核心目标**    | 服务拆分与独立部署，解决技术复杂性         | 领域建模与业务抽象，解决业务复杂性      |
| **边界划分**    | 服务边界通常基于技术需求或功能划分         | 边界划分基于领域知识，强调限界上下文     |
| **技术实现**    | 更多关注技术实现，如 REST、gRPC、消息队列 | 更多关注业务实现，如实体、值对象、聚合等模型 |
| **是否独立**    | 独立运行的服务，部署与扩展独立           | 不涉及独立部署，更多是设计上的指导思想    |
| **与数据库关系**  | 每个服务通常拥有自己的数据库（强隔离）       | 不强调具体的存储方案，模型和持久化方式独立  |
| **团队协作**    | 技术团队驱动，强调 DevOps 和运维能力    | 业务和技术团队共同协作，强调领域专家的参与  |
| **解决问题的类型** | 系统复杂性、技术复杂性               | 业务复杂性                  |

---

## **3. 两者的联系**

### **3.1 微服务需要领域驱动设计**

- **划分服务的边界**：
  
    - 微服务架构需要明确服务的职责和边界，而 DDD 中的 **限界上下文（Bounded Context）** 是理想的服务边界划分依据。
    - 每个限界上下文可以对应一个微服务。
- **统一业务语言**：
  
    - DDD 的 **通用语言（Ubiquitous Language）** 帮助开发团队与业务团队对齐理解，确保微服务的接口、事件和模型一致。
- **降低跨服务耦合**：
  
    - DDD 的聚合根（Aggregate Root）和上下文映射（Context Mapping）能够帮助减少微服务间的数据依赖和耦合。

### **3.2 微服务实现领域模型**

- 在微服务内部，DDD 提供了指导业务逻辑实现的方法，例如：
    - 通过实体（Entity）和值对象（Value Object）建模领域对象。
    - 使用领域事件（Domain Events）实现领域行为的解耦。
    - 在复杂场景中使用领域服务（Domain Service）封装业务逻辑。

### **3.3 DDD 的架构落地**

- DDD 并不限定具体的技术实现，而微服务提供了一种架构实现方式，使得 DDD 的设计思想更容易落地到分布式系统中。

---

## **4. 示例：微服务和 DDD 的结合**

### **4.1 DDD 划分领域**

以电商系统为例，使用 DDD 识别核心领域和子领域：

- 核心领域：订单管理。
- 支持领域：库存管理、支付系统、物流系统。
- 每个子领域进一步划分限界上下文：
    - 订单管理：下单、订单状态、订单取消。
    - 库存管理：库存分配、库存更新。

### **4.2 限界上下文对应微服务**

- 根据 DDD 的限界上下文，每个上下文可以对应一个微服务：
    - **订单服务**：管理订单创建、更新、状态变更。
    - **库存服务**：负责库存分配与锁定。
    - **支付服务**：处理支付和退款。

### **4.3 领域模型设计**

- 在订单服务中，可以定义领域模型：
  
    ```java
    public class Order {
        private String orderId;
        private List<OrderItem> items;
        private OrderStatus status;
    
        public void placeOrder() {
            // 业务逻辑
        }
    
        public void cancelOrder() {
            // 业务逻辑
        }
    }
    ```
    
- 领域事件示例：
  
    ```java
    public class OrderPlacedEvent {
        private String orderId;
        private List<OrderItem> items;
    }
    ```
    

### **4.4 微服务的实现**

- 使用 RESTful API 或消息队列（如 Kafka）实现服务间通信。
- 服务间数据传递通过 DDD 的上下文映射（Context Mapping）进行解耦。

---

## **5. 微服务与 DDD 的优势互补**

### **微服务的优势**

- 支持不同团队并行开发。
- 提供独立部署和扩展的能力。
- 适合大规模分布式系统。

### **DDD 的优势**

- 专注于解决业务复杂性。
- 提供明确的模型和边界划分方法。
- 通过通用语言促进业务和技术团队的协作。

### **结合后的收益**

- **技术与业务的统一**：
    - DDD 的领域建模方法帮助微服务架构更加贴近业务需求。
- **服务划分更合理**：
    - 通过 DDD 的限界上下文划分微服务边界，避免了过度拆分或边界不清晰的问题。
- **解耦性更强**：
    - DDD 的聚合根和上下文映射减少了服务间的耦合。

---

## **6. 总结**

|**维度**|**微服务**|**领域驱动设计（DDD）**|
|---|---|---|
|**目标**|架构灵活、可独立部署|业务清晰、解决领域复杂性|
|**核心方法**|服务拆分、独立部署|领域模型、限界上下文|
|**典型应用**|电商、物流、金融等分布式系统|复杂业务系统的建模和实现|

### **微服务是技术架构层面的实现，DDD 是一种设计方法论。两者结合，可以更好地实现业务逻辑清晰、架构灵活的分布式系统。**

# 2. 分布式事务
**分布式事务** 是指在分布式系统中，由多个独立服务或组件参与的事务操作，需要保证所有操作要么全部成功，要么全部失败的机制。分布式事务的核心目标是确保数据最终一致性，同时满足分布式系统的高可用性和性能需求。

---

## **1. 为什么需要分布式事务？**

在分布式系统中，不同的服务或组件通常会有自己的独立数据库。例如：

- **订单服务**：负责生成订单，写入订单数据库。
- **库存服务**：负责扣减库存，更新库存数据库。
- **支付服务**：负责处理支付，记录支付状态。

当一个业务流程需要多个服务协同完成时，例如“下单”，需要保证所有服务操作成功或失败（ACID 特性）。这就引出了分布式事务的问题。

---

## **2. 分布式事务的挑战**

1. **分布式环境中 ACID 的难以保证**：
   
    - 由于网络通信、服务故障等问题，分布式系统很难原生支持原子性、一致性、隔离性和持久性。
2. **CAP 定理的限制**：
   
    - 在分布式系统中，一致性（Consistency）、可用性（Availability）和分区容错性（Partition Tolerance）不可同时满足。
    - 分布式事务需要在一致性和性能之间做权衡。
3. **网络不可靠**：
   
    - 分布式环境中，网络延迟、分区和节点故障是常见问题。
4. **Base理论**
	- 基本可用（Basically Available）:系统在出现故障时，仍然能够保证 **基本可用**，允许部分功能降级（如延迟、部分数据错误）。
	- 软状态（Soft state）:允许系统数据存在**一定时间的不一致性**，不要求强一致性。
	- 最终一致性（Eventual consistency）:经过一定时间后，所有副本数据最终能达到一致状态（弱一致性）。

---

## **3. 分布式事务的实现方式**

分布式事务可以通过多种方式实现，每种方式在一致性、性能和复杂性之间有所权衡。

### **3.1 两阶段提交协议（2PC, Two-Phase Commit）**

#### **流程**

1. **准备阶段（Prepare Phase）**：
   
    - 事务管理器向所有参与者发送准备请求。
    - 每个参与者执行本地事务并记录日志，但不提交，返回“准备就绪”或“失败”响应。
2. **提交阶段（Commit Phase）**：
   
    - 如果所有参与者都返回“准备就绪”，事务管理器发送“提交”指令，所有参与者正式提交事务。
    - 如果任何一个参与者返回“失败”，事务管理器发送“回滚”指令，所有参与者回滚事务。

#### **优点**

- 确保强一致性。

#### **缺点**

- 同步阻塞：参与者需要等待协调者的决策，可能导致资源长时间被锁定。
- 单点故障：事务管理器故障会导致事务无法完成。

---

### **3.2 三阶段提交协议（3PC, Three-Phase Commit）**

三阶段提交是在两阶段提交的基础上增加了超时机制，减少了阻塞问题。

#### **流程**

1. **CanCommit 阶段**：
   
    - 事务管理器询问所有参与者是否可以提交，参与者返回“可以”或“不可以”。
2. **PreCommit 阶段**：
   
    - 如果所有参与者返回“可以”，事务管理器发送预提交请求，参与者执行本地事务并预提交。
3. **Commit 阶段**：
   
    - 如果事务管理器确认没有超时或失败，则发送正式提交指令，否则回滚。

#### **优点**

- 比 2PC 更加可靠，减少阻塞。

#### **缺点**

- 更复杂，网络开销更高。

---

### **3.3 TCC（Try-Confirm-Cancel）模式**

TCC 是一种应用层面的事务解决方案，由业务开发者手动实现事务逻辑。

#### **流程**

1. **Try 阶段**：
    - 预留资源，不做最终提交。
2. **Confirm 阶段**：
    - 确认资源操作，正式提交事务。
3. **Cancel 阶段**：
    - 释放资源，回滚事务。

#### **优点**

- 业务灵活性高，适合多种场景。

#### **缺点**

- 开发复杂度高，需要业务代码实现每个阶段的逻辑。

---

### **3.4 本地消息表（事务消息）**

#### **原理**

1. 在本地事务中记录消息到数据库表中，并提交事务。
2. 消息服务异步处理消息，将其发送到目标服务。
3. 目标服务执行逻辑后返回处理结果。

#### **优点**

- 减少了分布式事务的复杂性，提升性能。

#### **缺点**

- 需要额外维护消息表，增加了开发成本。

---

### **3.5 基于 MQ 的最终一致性**

通过消息队列（如 RabbitMQ、Kafka）实现事务的异步处理和最终一致性。

#### **流程**

1. **事务发起方**：
    - 将消息发送到 MQ，并执行本地事务。
2. **消费方**：
    - 消费 MQ 中的消息，执行相应的操作。
3. **补偿机制**：
    - 如果某个环节失败，通过重试或补偿操作确保最终一致性。

#### **优点**

- 异步处理，性能较高。
- 适合高并发场景。

#### **缺点**

- 需要额外实现补偿逻辑。

---

### **3.6 Saga 模式**

Saga 是一种基于事件驱动的分布式事务管理模式，事务被拆分为一系列的本地事务，每个事务都有对应的补偿操作。

#### **流程**

1. **正向执行**：
    - 执行事务的每个步骤（本地事务）。
2. **异常回滚**：
    - 如果某个步骤失败，依次执行之前步骤的补偿操作。

#### **优点**

- 异步非阻塞，性能较高。
- 易于扩展。

#### **缺点**

- 补偿逻辑复杂。
- 一致性较弱，可能会出现短暂的不一致状态。

---

## **4. 分布式事务的使用场景**

1. **跨服务调用**：
   
    - 订单服务调用库存服务和支付服务，确保数据一致性。
2. **跨数据库操作**：
   
    - 一个业务需要同时修改多个数据库的表。
3. **跨系统操作**：
   
    - 需要与第三方系统交互（如支付网关）。

---

## **5. 分布式事务的选择策略**

|**场景**|**推荐方案**|**理由**|
|---|---|---|
|服务调用间需要强一致性|2PC、3PC|确保数据一致性，但性能较低。|
|业务需要灵活补偿|TCC|灵活性高，适合业务驱动的事务处理。|
|高性能、高并发场景|本地消息表、MQ 最终一致性|牺牲实时一致性，确保性能和可靠性。|
|复杂事务逻辑|Saga 模式|易扩展，适合分布式系统的长事务。|

---

## **6. 总结**

- **分布式事务** 是分布式系统中的核心问题，主要面临一致性、性能和复杂性之间的权衡。
- 根据业务场景选择适合的事务处理方式：
    - 强一致性：2PC/3PC。
    - 最终一致性：MQ、本地消息表、Saga。
    - 业务灵活性：TCC。
- 分布式事务的设计需要与系统的实际需求结合，避免过度设计，同时确保性能和可用性。

# 3. 基于MQ的事件补偿机制
是的，通过 **MQ 接受消息后判断订单状态是否变更，决定是否回滚操作**，属于分布式事务补偿机制的一种实现方式。具体来说，这种机制主要依赖于 **幂等性检查** 和 **业务补偿逻辑** 来确保系统的最终一致性，而不是直接使用传统的分布式事务协议（如 2PC、3PC）。

---

## **1. 背景分析**

在分布式系统中，消息队列（MQ）常被用来解耦服务之间的调用，实现异步处理和最终一致性。为了确保消息处理过程中数据的一致性，可以设计以下逻辑：

1. **业务场景**：
   
    - 系统 A 发送一条订单状态变更的消息到 MQ。
    - 系统 B 接收到该消息后，需要根据订单状态是否发生变化，执行后续的处理逻辑。
    - 如果订单状态未变更，则回滚（或忽略）该操作，避免冗余操作或数据异常。
2. **关键点**：
   
    - **幂等性**：确保消息不会被重复处理。
    - **状态检查**：在处理消息前，检查当前订单状态是否已经与消息内容一致。
    - **补偿机制**：如果发现状态未变更，则回滚或忽略操作。

---

## **2. 补偿机制工作原理**

### **2.1 消息处理逻辑**

1. **消息接收**：
   
    - 消费者从 MQ 中读取消息，获取订单的目标状态。
2. **状态校验**：
   
    - 查询本地数据库中当前订单的状态，判断是否与消息中目标状态一致。
3. **处理分支**：
   
    - 如果状态已经变更：
        - 忽略该消息（避免重复处理）。
    - 如果状态未变更：
        - 执行订单状态更新操作，并记录操作日志。
        - 确认处理完成，向 MQ 发送 ACK。
4. **回滚或忽略**：
   
    - 如果发生异常（如网络超时、数据库操作失败），触发补偿逻辑，回滚订单状态或重试操作。

---

### **2.2 幂等性检查**

为了防止消息重复处理，需要在消息消费过程中加入幂等性检查。

1. **方案 1：基于唯一标识（Message ID）**
   
    - 每条消息携带唯一的 `Message ID`。
    - 消费者在处理消息前，先查询本地是否已经处理过该 `Message ID`。
    - 如果已经处理过，则忽略该消息；否则执行处理逻辑并记录 `Message ID`。
2. **方案 2：基于订单状态**
   
    - 直接根据订单状态判断是否需要处理。
    - 如果状态已经与目标状态一致，则跳过操作。

---

### **2.3 状态一致性检查**

在分布式事务中，状态一致性是关键。如果状态检查发现不符，可能需要回滚或补偿操作：

- **订单状态未变更的处理**：
  
    - 如果发现状态未变更，可能是消息延迟或重复消费造成的。
    - 此时应忽略该消息，而不是执行重复操作。
- **状态冲突的处理**：
  
    - 如果发现当前订单状态与消息目标状态冲突（如订单已经被取消，但消息要求将其标记为已支付），可能需要人工介入处理。

---

## **3. 这种机制与分布式事务的关系**

### **3.1 为什么这属于补偿机制**

这种设计不是严格意义上的分布式事务，而是通过幂等性检查和业务补偿逻辑来实现最终一致性，属于 **分布式事务的补偿机制**。

1. **特点**：
   
    - **松散一致性**：允许系统在短时间内出现数据不一致，最终通过补偿机制恢复一致性。
    - **无全局锁**：避免了传统分布式事务的全局锁问题，提高了系统性能。
    - **基于业务逻辑**：补偿逻辑是根据业务场景定制的，而非依赖通用的事务协议。
2. **对比传统分布式事务**：
   
    - 传统分布式事务（如 2PC、TCC）追求强一致性，操作同步阻塞。
    - 基于 MQ 的补偿机制追求最终一致性，操作异步非阻塞。

---

### **3.2 适用场景**

- **高并发场景**：
    - 传统分布式事务可能导致性能瓶颈，而这种补偿机制更适合高并发场景。
- **异步处理场景**：
    - 当业务流程可以容忍短暂的不一致时，可使用 MQ 和补偿机制。
- **状态驱动的业务**：
    - 订单、支付等以状态变更为核心的业务逻辑非常适合这种设计。

---

## **4. 示例代码**

以下是一个基于 Spring 的简单示例，展示如何处理 MQ 消息，并通过状态校验实现补偿机制。

```java
@Service
public class OrderMessageConsumer {

    @Autowired
    private OrderRepository orderRepository;

    @Transactional
    public void processMessage(OrderStatusMessage message) {
        // 获取订单 ID 和目标状态
        String orderId = message.getOrderId();
        OrderStatus targetStatus = message.getTargetStatus();

        // 查询订单状态
        Order order = orderRepository.findById(orderId)
            .orElseThrow(() -> new IllegalArgumentException("Order not found"));

        // 检查状态是否需要更新
        if (order.getStatus().equals(targetStatus)) {
            // 状态已一致，忽略消息
            log.info("Order status already updated, ignoring message: {}", message);
            return;
        }

        // 更新订单状态
        order.setStatus(targetStatus);
        orderRepository.save(order);

        log.info("Order status updated successfully for orderId: {}", orderId);
    }
}
```

## **5. 优缺点**

### **优点**

1. **解耦服务**：
    - 使用 MQ 将服务之间的调用解耦，降低耦合度。
2. **性能高**：
    - 异步处理，避免传统事务带来的性能瓶颈。
3. **灵活性**：
    - 补偿逻辑可以根据业务需求定制。

### **缺点**

1. **实现复杂**：
    - 需要处理消息的幂等性、补偿逻辑和异常重试。
2. **一致性延迟**：
    - 数据一致性依赖补偿逻辑，可能会有一定延迟。
3. **需要额外监控**：
    - 需要监控 MQ 消息的消费状态，确保补偿机制生效。

---

## **6. 总结**

- 使用 **MQ 接受消息后判断订单状态是否变更** 是一种典型的分布式事务补偿机制，旨在通过幂等性检查和补偿操作实现系统的最终一致性。
- 这种设计避免了传统分布式事务的性能瓶颈，适合高并发和异步场景。
- 在实际应用中，需要针对业务场景设计合理的状态校验和补偿逻辑，并确保消息的幂等性和系统的可靠性。

# **4. 分布式限流策略**

在微服务架构中，**分布式限流**（Rate Limiting）是一种防止系统因过载而崩溃的重要技术。限流的主要目的是 **防止恶意请求、保护系统资源、提高系统的稳定性**。

---

## **1. 限流的常见策略**

分布式限流主要有以下 **5 种常见策略**：

| **策略**                             | **原理**                       | **适用场景**               |
| ---------------------------------- | ---------------------------- | ---------------------- |
| **固定窗口计数（Fixed Window Counter）**   | 在固定时间窗口内，允许请求次数不超过设定的阈值      | 适用于简单的限流，如每秒 N 次请求     |
| **滑动窗口计数（Sliding Window Counter）** | 结合时间窗口和队列，实现更均匀的限流           | 适用于更加精细化的限流，如 API 速率限制 |
| **令牌桶（Token Bucket）**              | 以固定速率生成令牌，请求必须消耗令牌           | 适用于**突发流量**，如秒杀、抢购等    |
| **漏桶（Leaky Bucket）**               | 以恒定速率处理请求，防止瞬时流量冲击           | 适用于**请求速率均匀化**，如支付请求   |
| **分布式唯一 ID（Redis + 滑动窗口）**         | 通过 Redis 存储唯一 ID 来防止短时间内过量请求 | 适用于 API 限流、恶意攻击防护      |

---

## **2. 基于 Sentinel 实现分布式限流**

## **3. 基于 Redis + Lua 脚本实现分布式限流**

**Redis** 具有 **高性能、天然分布式** 的特点，可以使用 **Lua 脚本** 实现**滑动窗口限流**。

### **（1）创建 Redis 限流 Lua 脚本**

```lua
local key = KEYS[1]
local limit = tonumber(ARGV[1])
local expire_time = tonumber(ARGV[2])

local current = redis.call("incr", key)

if current == 1 then
    redis.call("expire", key, expire_time)
end

if current > limit then
    return 0
else
    return 1
end
```

该脚本会：

- **增加当前窗口的请求次数**
- **如果是新窗口，设置过期时间**
- **如果请求数超过阈值，返回 0，表示拒绝请求**

### **（2）在 Spring Boot 中调用 Redis 限流**

```java
@Service
public class RateLimiterService {

    @Autowired
    private StringRedisTemplate redisTemplate;

    private static final String SCRIPT =
            "local key = KEYS[1] " +
            "local limit = tonumber(ARGV[1]) " +
            "local expire_time = tonumber(ARGV[2]) " +
            "local current = redis.call('incr', key) " +
            "if current == 1 then redis.call('expire', key, expire_time) end " +
            "if current > limit then return 0 else return 1 end";

    public boolean isAllowed(String key, int limit, int expireTime) {
        DefaultRedisScript<Long> redisScript = new DefaultRedisScript<>(SCRIPT, Long.class);
        Long result = redisTemplate.execute(redisScript, Collections.singletonList(key), String.valueOf(limit), String.valueOf(expireTime));
        return result != null && result == 1;
    }
}
```

### **（3）在 Controller 中使用**

```java
@RestController
@RequestMapping("/orders")
public class OrderController {

    @Autowired
    private RateLimiterService rateLimiterService;

    @GetMapping("/{id}")
    public ResponseEntity<String> getOrder(@PathVariable("id") String id) {
        boolean allowed = rateLimiterService.isAllowed("order_limit", 5, 10);
        if (!allowed) {
            return ResponseEntity.status(HttpStatus.TOO_MANY_REQUESTS).body("Too many requests. Try later.");
        }
        return ResponseEntity.ok("Order ID: " + id);
    }
}
```

- **每 10 秒最多允许 5 次请求**，超出则返回 `429 Too Many Requests`。

## **4. 令牌桶（Token Bucket）限流**

**令牌桶** 是一种**允许短时间突发流量**的限流策略。

- **系统以固定速率添加令牌**
- **请求需要消耗令牌**
- **如果桶为空，请求会被拒绝**

### **（1）使用 Guava RateLimiter**

```xml
<dependency>
    <groupId>com.google.guava</groupId>
    <artifactId>guava</artifactId>
</dependency>
```

### **（2）在 Spring Boot 代码中使用**

```java
@RestController
@RequestMapping("/orders")
public class OrderController {

    // 每秒生成 2 个令牌
    private final RateLimiter rateLimiter = RateLimiter.create(2);

    @GetMapping("/{id}")
    public ResponseEntity<String> getOrder(@PathVariable("id") String id) {
        if (!rateLimiter.tryAcquire()) {
            return ResponseEntity.status(HttpStatus.TOO_MANY_REQUESTS).body("Rate limit exceeded. Try later.");
        }
        return ResponseEntity.ok("Order ID: " + id);
    }
}
```

- **每秒最多 2 次请求**，否则返回 **HTTP 429**。

## **5. 分布式限流策略对比**

|**策略**|**优点**|**缺点**|**适用场景**|
|---|---|---|---|
|**固定窗口**|实现简单|请求可能集中|API 速率限制|
|**滑动窗口**|更均匀的限流|计算复杂|API 限流、攻击防护|
|**令牌桶**|允许突发流量|需要精确计算|秒杀、抢购、支付|
|**漏桶**|速率更稳定|瞬间高流量会被丢弃|支付、事务提交|
|**Redis + Lua**|**分布式支持**|依赖 Redis|分布式微服务|

## **6. 总结**

✅ **推荐使用 Sentinel 进行分布式限流**，它提供 **动态管理、流控、熔断、降级等完整能力**。  
✅ **Redis + Lua 适合高性能分布式限流**，适用于 API 速率限制。  
✅ **令牌桶（Token Bucket）适用于秒杀、支付等允许突发流量的业务场景**。


# 5. **Seata提供的AT模式**
### **AT（Automatic Transaction）模式**

**AT 模式** 是 **Seata** 提供的一种 **自动提交事务（Automatic Transaction）** 方案，主要用于 **关系型数据库（MySQL、PostgreSQL、Oracle）**，适用于 **Spring Boot、Spring Cloud、Dubbo** 等框架。

**AT 模式的特点：**

- **一阶段（Phase 1 - Try）：业务 SQL 执行**
    - 业务 SQL 会被拦截，并 **自动生成回滚日志（undo log）**，记录数据修改前的状态。
- **二阶段（Phase 2 - Commit/Rollback）**
    - **提交（Commit）：事务成功，删除 undo log**
    - **回滚（Rollback）：事务失败，使用 undo log 恢复数据**

📌 **适用场景：**

- 适用于 **单体数据库**
- 适用于 **短事务（业务 SQL 语句执行快）**
- 适用于 **OLTP（在线事务处理）应用**

import io.seata.spring.annotation.GlobalTransactional;

public class AccountService {

    }
}

## **📌 4. 账户服务（AccountService - 余额扣减）**

```java
import io.seata.rm.tcc.api.BusinessActionContext;
import io.seata.rm.tcc.api.TwoPhaseBusinessAction;
import io.seata.rm.tcc.api.BusinessActionContextParameter;
import org.springframework.stereotype.Service;

@Service
public class AccountService {

    // 1. Try 阶段：冻结账户余额
    @TwoPhaseBusinessAction(name = "accountTccAction", commitMethod = "commit", rollbackMethod = "rollback")
    public boolean tryFreezeBalance(
            @BusinessActionContextParameter(paramName = "userId") String userId,
            @BusinessActionContextParameter(paramName = "amount") double amount) {
        System.out.println("Try 阶段：冻结用户 " + userId + " 余额 " + amount);
        return true;
    }

    // 2. Confirm 阶段：扣减余额
    public boolean commit(BusinessActionContext context) {
        String userId = context.getActionContext("userId").toString();
        double amount = Double.parseDouble(context.getActionContext("amount").toString());
        System.out.println("Confirm 阶段：扣除用户 " + userId + " 余额 " + amount);
        return true;
    }

    // 3. Cancel 阶段：解冻余额
    public boolean rollback(BusinessActionContext context) {
        String userId = context.getActionContext("userId").toString();
        double amount = Double.parseDouble(context.getActionContext("amount").toString());
        System.out.println("Cancel 阶段：解冻用户 " + userId + " 余额 " + amount);
        return true;
    }
}
```
