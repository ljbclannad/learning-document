# 重复下单：从请求幂等到完整解决方案

> 面试表述：在订单及其关联变更位于同一 MySQL 数据库、应用允许多实例部署的前提下，我优先采用“稳定幂等键＋数据库业务唯一约束＋同一事务＋重复请求返回已有订单”。同一次下单的双击和超时重试复用幂等键，数据库拒绝并发重复写入，事务保证订单和本库库存等变更一致。token 可用于签发请求身份与前置校验，Redis 或 Redisson 按需减少重复执行；持久化结果查询、可靠事件和受控重试处理响应丢失及后续副作用，不依赖分布式锁永久有效。

本文是教学设计，重点解释正确性与故障边界，不代表已有生产实现。主要参考 MySQL 8.4 InnoDB、Java 17/21 与 Spring 代理事务语义；Redisson API 使用前应核对项目实际版本。主方案只覆盖单库事务，分库适用边界见第 5.9 节。

## 1. 问题：究竟什么算重复下单

### 1.1 按下单意图区分重复与合法新订单

用户双击按钮、浏览器或网关重试、提交成功后响应丢失，都可能让同一次下单到达多次。即使请求从不并发，第一次完成后再次到达，也可能重复创建，因此问题不仅是并发互斥，还包括完成后的重复识别。

同一用户购买同一商品两次，可以是合法业务。不能简单按 user_id 或 user_id＋sku_id 永久去重。先定义“一次下单意图”，例如一个不可变的结算快照或结算单版本，再给它稳定的 request_key。

```text
同一次意图：结算快照 C001 / request_key K001
    ├─ 首次提交
    ├─ 双击产生的提交
    └─ 超时后的重试
               ↓
        都应指向订单 O001

新的购买意图：新的结算快照 / request_key K002
               ↓
        允许创建订单 O002
```

刷新页面、返回结算页是否继续原意图，需要产品和后端共同规定；如果要求这些操作不产生新订单，必须恢复原结算标识，而不是每次重新生成随机 key。

### 1.2 需要维护的不变量

| 不变量 | 对应约束 |
| --- | --- |
| 一个有效下单意图最多创建一张订单 | 幂等键对应的业务唯一约束 |
| 相同幂等键只能表达同一请求内容 | 绑定结算快照并校验规范化请求摘要 |
| 订单创建、库存扣减等本库变更一致 | 同一事务，逐项检查写入结果 |
| 重试不会再次扣库存或重复产生业务事件 | 先取得唯一写入资格，相关事件与订单同事务写入 |
| 响应丢失后可以找回结果 | 持久化幂等身份与订单映射，并提供授权范围内的结果查询 |
| 新一次合法购买不被误拦截 | 不同下单意图使用不同 key |

幂等强调重复执行不产生额外业务效果，不要求所有响应字节始终相同。创建接口通常约定返回同一个 order_id 和当前订单状态；若要求重放首次响应，则另外保存响应快照，并明确其有效期。

### 1.3 三个不能替代业务约束的判断

- **“前端按钮已经禁用”**：不能覆盖刷新、其他客户端、网关重试和直接调用接口。
- **“查询不到订单就创建”**：两个请求可以同时查不到，查询与插入之间存在竞争窗口。
- **“渠道最终只有一笔成功，重复订单对账时作废”**：本地可能已重复占库存、锁优惠券或发权益；多个独立渠道支付对象也未必互相排斥。允许多条支付尝试记录，不等于允许重复创建和履约同一业务订单。

## 2. 解决技术：每一种技术实际解决哪部分问题

### 2.1 稳定幂等键与结算 token

服务端可以在创建结算快照时签发 token，并绑定可信用户、结算内容和有效期。token 可以直接承载或映射到 request_key；它不必只是“用过就删除”的标志。

同一意图的所有重试必须复用同一 key。若每次点击提交都生成新 key，后续唯一索引和锁均无法知道这些请求原本重复。user_id、tenant_id 应从认证上下文取得，不能相信客户端传入的归属。

一次性消费的难点在于时点：

| 时点 | 故障窗口 | 需要补齐的能力 |
| --- | --- | --- |
| 创建订单前消费 Redis token | token 消费成功，但订单事务失败或进程退出 | 原 key 可查询结果、识别未完成并按规则恢复 |
| 创建订单后才消费 | 并发请求可能同时校验 token 通过 | 数据库原子约束阻止重复写入 |
| 订单成功但响应丢失 | 重试时 token 已被消费 | 返回已有订单，不能直接断言下单失败 |

对已完成请求，应在授权和内容校验后优先返回持久化结果；token 到期不能抹掉“订单已经创建”的事实。未完成意图是否仍可提交，才由结算有效期决定。如果 token 存在数据库，可让其条件消费和订单变更加入同一事务；Redis 消费和数据库提交并非天然原子。

### 2.2 数据库主键与业务唯一约束

订单技术主键通常每次新生成，因此主键不同的两条重复订单都能插入。只有重复请求复用同一主键时，主键约束才可能承担幂等判定。更清晰的模型是：

```text
order_id：最终订单的技术身份
(tenant_id, user_id, request_key)：一次下单意图的业务身份
```

对后者设置 UNIQUE，且组成字段均为 NOT NULL，明确 key 的大小写和编码规则。MySQL 唯一索引允许多个 NULL，不能靠可空幂等字段可靠去重。[MySQL 唯一索引](https://dev.mysql.com/doc/refman/8.4/en/create-index.html)

唯一约束决定“哪些并发写入可以成功”，结果查询决定“重复请求返回什么”。只捕获异常并提示失败，没有完整实现接口的幂等返回契约。

### 2.3 本地锁与原子类

synchronized、ReentrantLock、AtomicBoolean 等只协调共享同一内存状态的执行者。可用于单实例中减少重复工作，但不能覆盖其他实例或重启后的请求，也不保存订单完成事实。

即使单实例，也应把“是否已创建”落实到持久化业务身份。加锁后释放，再来的请求仍需查询结果；互斥本身不识别历史重复。

### 2.4 Redis 原子占位与手写分布式锁

Redis 的 SET key owner NX PX timeout 可将“不存在才占位”和过期设置放在同一条命令中。它可以前置拦截重复执行，但占位成功不代表订单提交成功；超时释放后，旧执行者也不一定停止。

若把占位作为锁，owner 应使用每次获取生成的高熵随机值，不能只用时间戳。释放必须原子比较 owner 后删除；分开 GET、比较、DELETE 仍会误删：A 读到自己的值后锁过期，B 获得新锁，A 随后 DELETE 删除 B 的锁。

下面是 Redis Lua 释放片段，不是完整分布式锁实现：

```lua
-- KEYS[1] 为锁 key；ARGV[1] 为本次获取锁的 owner。
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
end
return 0
```

原子释放只避免误删新锁，不阻止已经失去锁的旧请求继续写数据库。续期、网络错误、释放失败、占位状态恢复等仍需设计，通常不为普通下单手写整套锁协议。[Redis 分布式锁说明](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

### 2.5 Redisson 锁、锁内查重与看门狗

使用同一业务 key 加锁，并在锁内查询持久化结果，可以形成正常路径上的幂等流程：A 创建并提交后释放锁，B 再取得锁时查询并返回 A 的订单。仅加锁、不查历史结果，仍可能串行创建两张订单。

看门狗可在正常运行时自动续期，业务超过默认 30 秒也不必因此失去锁；但长时间进程暂停或持续无法连接 Redis 时，续期仍可能失败。锁过期不会自动终止旧业务线程，最终写入仍需要唯一约束或资源端有效性校验。[Redisson 锁与看门狗](https://redisson.pro/docs/data-and-services/locks-and-synchronizers/)

尤其要区分以下两个同步 API：

| 调用 | 含义 |
| --- | --- |
| tryLock(3, TimeUnit.SECONDS) | 最多等待 3 秒，不显式指定 leaseTime，使用看门狗续期路径 |
| tryLock(3, 5, TimeUnit.SECONDS) | 最多等待 3 秒，显式租约为 5 秒，不能声称这次获取自动由看门狗无限续期 |

这一差异在原文所用的 Redisson 3.16.3 中也存在：显式租约路径设置租约，无显式租约路径才安排续期。该版本只用于核对历史示例，不作为新项目推荐依赖版本。[Redisson 3.16.3 获取与续期源码](https://raw.githubusercontent.com/redisson/redisson/redisson-3.16.3/redisson/src/main/java/org/redisson/RedissonLock.java)

获取失败或中断时不得执行 unlock；锁要覆盖所保护数据库事务的提交，而不只是业务方法最后一行。Spring 事务方法内部 finally 解锁可能早于代理提交，不能只凭加了 @Transactional 判断顺序正确。

### 2.6 数据库状态条件更新、乐观锁与悲观锁

已有结算单或任务记录时，可以用预期状态条件更新取得执行资格；如果计算依赖可变内容，可增加 version 校验。必须检查影响行数，并把资格变更、订单创建及相关资源变更放在正确事务边界中。

需要锁定已有结算数据后进行复杂校验时，可以使用 SELECT ... FOR UPDATE。锁定范围受索引、谓词与隔离级别影响，持锁期间避免远程调用；不能把“锁住不存在的订单行”当作可靠通用方案。数据库乐观控制仍可能遇到行锁等待，悲观锁仍需处理死锁和超时。

如果只需要创建一条唯一订单，业务唯一约束通常比增加版本、锁定读或额外执行状态更直接。详细原理见 [[03-数据存储与缓存/数据库/MySQL|MySQL]] 第 9～11、13 章，以及 [[01-Java基础与并发/并发编程/Java并发编程|Java并发编程]] 第 2.5 节。

### 2.7 队列、事务与可靠事件

队列可以削峰、按业务键串行消费，但重复投递和消费后确认丢失仍可能发生，消费者必须去重。多个独立安全步骤也不会因为排进同一队列就整体回滚。

数据库事务把订单、同库资源变更和 Outbox 事件一起提交；发送方随后可靠重试投递，消费者以稳定事件身份去重。Outbox 仍可能产生重复投递，不能声称自动实现全链路 exactly-once。[Transactional Outbox 模式](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

## 3. 各自优缺点：正确性与运行成本分别比较

| 技术 | 优势 | 弊端或失效边界 | 在方案中的定位 |
| --- | --- | --- | --- |
| 前端禁用按钮、防抖 | 改善交互，减少误操作 | 覆盖不了其他入口、重试与网络问题 | 体验优化 |
| 稳定 request_key / 结算 token | 能识别同一次意图，便于查结果 | 新 key 会被视为新请求；单独消费不等于事务成功 | 所有可靠去重的身份基础 |
| 订单技术主键 | 标识订单、支持关联查询 | 每次生成不同值时不能识别重复意图 | 技术身份 |
| 数据库业务唯一约束 | 多实例共同判定，持久化拒绝重复写入 | 有索引及热点竞争成本；范围只覆盖相应表和写入归属 | 单库主方案的最终写入约束 |
| 本地锁、原子类 | 本地开销小，易保护短临界区 | 不跨实例，不保存历史结果 | 本地运行状态或可选优化 |
| Redis 原子占位 | 前置分流重复请求，减少数据库重复尝试 | 过期、恢复、网络错误；与数据库双写不原子 | 可选的执行协调 |
| Redisson＋锁内查询 | 跨实例串行化，封装等待、释放与续期 | 续期可失败，旧持有者可继续执行，仍依赖持久化结果 | 重复工作昂贵时的优化 |
| 数据库条件更新 / 乐观锁 | 在更新时验证资格或旧依据 | 零行要分类，冲突重试必须重读重算 | 已有状态记录的原子认领 |
| SELECT ... FOR UPDATE | 在读取依据时保护复杂校验 | 持锁、连接占用、锁顺序和死锁成本 | 必须先读再改的短事务 |
| 消息队列 | 削峰，解耦接纳与执行 | 存在重复投递、积压、处理状态与结果查询成本 | 确有异步与容量需求时使用 |
| 同库事务＋Outbox＋消费幂等 | 数据库状态与待发送事件一致，可恢复后续处理 | 仍需投递扫描、去重、告警和恢复流程 | 有下游副作用时的可靠交付 |

## 4. 技术选型：主方案先保证正确，再按证据加组件

### 4.1 单库多实例的默认选择

主方案采用“稳定幂等身份＋业务唯一约束＋同库事务＋结果查询”。不要求所有实例共享 Java 锁，也不要求 Redis 始终可用；所有写入口必须使用一致的幂等身份和数据库约束。

- token 可以就是 request_key 的签发形式；不必再单独设计一次“先删除 token 才能下单”的跨存储提交。
- 不把 order_id、手机号或 user_id 单独当成一次下单意图。
- 多张表的 SQL 同属一个事务，并逐一检查条件更新结果。
- 重复请求返回已有结果；处理未确认时返回处理中、重试或查询指引，不伪报“确定失败”。

### 4.2 何时增加其他技术

| 已确认的需求或证据 | 增加的能力 | 保留的最终约束 |
| --- | --- | --- |
| 大量同 key 重复请求造成明显数据库争用 | Redis / Redisson 前置协调，或短期结果缓存 | 数据库唯一约束和持久化查询 |
| 锁内计算昂贵，需减少多个实例重复做相同工作 | Redisson＋锁内查重 | 唯一约束、事务和锁失效处理 |
| 已有结算单需要原子消费 | 结算状态条件更新，必要时版本校验 | 与订单创建同事务；或设计明确恢复状态机 |
| 存在复杂读后校验且能控制持锁时间 | 数据库悲观锁 | 合法状态、唯一约束和统一锁定协议 |
| 下单耗时超过同步接口预算，或需要削峰 | 持久化任务＋队列＋结果查询 | 任务和订单幂等、可靠投递、恢复与容量预算 |
| 订单提交后必须通知下游 | 同事务 Outbox＋下游幂等 | 稳定事件身份与可恢复业务状态 |

总 QPS 不等于同 key 冲突率；没有“并发高就必须 Redisson”的统一阈值。比较成功订单吞吐、重复命中率、唯一键等待、锁等待及持有时间、数据库尾延迟与额外组件故障成本。

## 5. 完整解决方案：单库事务主线与故障恢复

### 5.1 前提和最小业务模型

以下教学模型中，订单、库存和 Outbox 均为同一 MySQL 数据库中的 InnoDB 表；身份来自认证上下文。示例以单 SKU 下单串起流程，多 SKU 应定义统一资源访问顺序。支付渠道调用不放进创建订单事务。

服务端先保存或可可靠恢复一个不可变结算快照，包含 SKU、数量、报价版本、币种和其他影响订单含义的字段；价格由服务端确认。为该意图签发 32 字节随机 request_key，传输时可使用固定长度编码，数据库按原始字节保存。相同意图重试继续使用此 key，变化的购物内容应产生新结算版本和新 key。

以下是核心教学 DDL，不是完整商城表结构；结算快照、订单明细、优惠券及投递任务字段由实际项目扩展：

```sql
CREATE TABLE trade_order (
    order_id BIGINT NOT NULL,
    tenant_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    request_key VARBINARY(32) NOT NULL,
    request_hash BINARY(32) NOT NULL,
    sku_id BIGINT NOT NULL,
    quantity INT NOT NULL,
    amount_minor BIGINT NOT NULL,
    currency CHAR(3) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
    status VARCHAR(24) NOT NULL,
    created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    PRIMARY KEY (order_id),
    UNIQUE KEY uk_order_intent (tenant_id, user_id, request_key),
    CONSTRAINT ck_order_quantity CHECK (quantity > 0),
    CONSTRAINT ck_order_amount CHECK (amount_minor >= 0),
    CONSTRAINT ck_order_key_size CHECK (OCTET_LENGTH(request_key) = 32)
) ENGINE = InnoDB;

CREATE TABLE sku_stock (
    tenant_id BIGINT NOT NULL,
    sku_id BIGINT NOT NULL,
    available BIGINT NOT NULL,
    PRIMARY KEY (tenant_id, sku_id),
    CONSTRAINT ck_stock_available CHECK (available >= 0)
) ENGINE = InnoDB;

CREATE TABLE order_outbox (
    event_id BIGINT NOT NULL,
    order_id BIGINT NOT NULL,
    event_type VARCHAR(32) NOT NULL,
    payload JSON NOT NULL,
    status VARCHAR(16) NOT NULL DEFAULT 'PENDING',
    created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    PRIMARY KEY (event_id),
    UNIQUE KEY uk_order_event (order_id, event_type)
) ENGINE = InnoDB;
```

request_hash 是对确定的业务内容进行规范化后计算的摘要，不是对任意原始 JSON 字节直接哈希，也不能代替鉴权或服务端计价。绑定的结算快照用于校验原 key 的内容，订单中的 hash 用于核实重放。技术 ID 生成器只提供 order_id / event_id，不承担幂等识别。

本例订单初始状态为 WAIT_PAY，创建事件类型为 ORDER_CREATED。重放校验基于原结算快照和请求语义，不用当前价格重新计算旧订单摘要，避免价格变化使合法重试被误判为不同请求。

### 5.2 请求入口与已完成结果查询

1. 从认证上下文取得 tenant_id、user_id，解码并校验 key 长度与请求格式。
2. 用完整业务键在主库进行一次新鲜结果查询。命中时校验请求语义，返回同一 order_id 及当前状态；不因原 token 已消费或过期而否认已完成事实。
3. 未命中时校验结算快照归属、有效期、内容绑定和服务端报价，构造确定的订单输入。
4. 进入创建事务；此前的“查不到”只是减少重复工作，真正防重复仍由 uk_order_intent 完成。

事务前查询不是创建资格。主库暂时无记录也不证明别的请求没有未提交事务；不得据此取消去重或更换 key。

### 5.3 在一个事务内创建订单、扣库存并保存事件

以下为服务协议伪代码，省略 Mapper 与业务异常定义；所有 SQL 必须由同一个事务管理器在同一主库事务中执行：

```text
非事务入口 createOrReplay(command)：
    解析可信身份与稳定 key，执行结果查询和必要校验
    若已完成：校验内容，返回已有订单

    调用独立事务服务 createInTransaction(command)：
        BEGIN
        INSERT trade_order，包含完整业务键、request_hash、服务端金额与 WAIT_PAY 状态
        UPDATE sku_stock，按 tenant_id、sku_id 和库存条件原子扣减
        若影响行数不是 1：抛出业务异常，回滚本次全部变更
        INSERT order_outbox，保存本次 ORDER_CREATED 事件
        任意订单明细或其他必要本库写入失败：回滚全部变更
        COMMIT 成功后，事务服务才向外返回创建结果

    若明确为 uk_order_intent 重复：
        先确保失败尝试结束并回滚
        在新的主库读取上下文中查询原业务键
        找到并确认内容一致：返回已有订单
        内容不一致：返回 IDEMPOTENCY_KEY_REUSED
        尚不能确定结果：返回 PROCESSING / 可重试，不能绕过唯一约束

    若为其他唯一约束、资源不足或程序错误：
        按实际原因处理，不统一转换为“重复成功”

    若提交阶段超时、断线而结果未知：
        保留原 key，通过主库结果查询核实
        无法确定则返回未知或处理中，稍后仍用同一 key 重试
```

库存 SQL 片段如下，冒号表示绑定参数，quantity 必须预先验证为正数：

```sql
UPDATE sku_stock
SET available = available - :quantity
WHERE tenant_id = :tenant_id
  AND sku_id = :sku_id
  AND available >= :quantity;
```

顺序上先尝试插入唯一订单，再扣库存。若后续任一步失败，订单占位、库存和事件一起回滚；原 key 此后可按有效结算规则重试，不能留下已成功的本次扣减。若业务要求连确定失败响应也永久重放，应另存幂等处理记录和失败结果；这不是本模型自动提供的能力。

MySQL 的重复键错误通常只回滚当前语句，不等于整笔事务已结束。应用必须明确回滚失败尝试，再处理重放；死锁、等待超时和提交未知也不能混为一类。[InnoDB 错误处理](https://dev.mysql.com/doc/refman/8.4/en/innodb-error-handling.html)

Spring 场景下使用经代理调用的独立事务服务或正确的编程式事务；避免同类自调用导致事务失效。不要在失败事务中捕获异常后继续扣库存或发送成功消息，也不要为局部方便随意引入改变整体提交语义的 REQUIRES_NEW。[Spring 事务代理规则](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)

### 5.4 两个实例同时下单的执行过程

| 步骤 | 请求 A / 实例 1 | 请求 B / 实例 2 |
| --- | --- | --- |
| 1 | 使用 key K001，查询未命中 | 使用同一 key，查询也未命中 |
| 2 | 事务内插入订单 O001，尚未提交 | 尝试插入同业务键的订单 O002，在唯一键检查处可能等待 |
| 3 | 扣减库存，写入事件，提交 | A 提交后发生 uk_order_intent 冲突 |
| 4 | 返回 O001 | 结束失败事务，新的主库查询返回 O001 |
| 最终 | 一张订单，一次本次库存扣减，一个创建事件 | 不再扣库存，不再生成本次事件 |

若 A 最终回滚，B 可能继续插入并成功；不存在“A 一抢到机会就永远占用 key”的要求。唯一键竞争也可能产生死锁，应在失败事务结束后受控重试，而不是无限即时循环。

### 5.5 响应契约、结果保留与查询边界

| 已确认情况 | 对外语义 |
| --- | --- |
| 首次提交成功 | 返回 order_id 和订单状态 |
| 相同 key、相同内容，订单已存在 | 返回同一 order_id 和当前状态；可标识为重放 |
| 相同 key、不同内容 | 明确报告 key 复用冲突，不创建第二张订单 |
| 明确资源不足且事务已回滚 | 返回业务失败；原 key 是否可重试取决于结算有效性 |
| 锁等待、同 key 仍在处理或暂时查不到已确认结果 | 返回处理中或受控重试指引，继续使用原 key |
| 提交结果未知 | 查询核实，不能宣称肯定未创建，也不能生成新 key 重试 |

结果查询需在授权范围内使用主库或有明确一致性保证的读取，不能靠延迟从库、陈旧缓存或原 RR 快照判断订单不存在。单纯“等待几秒”不是副本追平的证明。

订单取消不意味着原下单意图可以再创建一张订单；新的购买应使用新意图。订单归档或删除时应保留必要的幂等映射或拒绝超出允许窗口的旧 key，否则删除历史记录后旧请求可能重新生效。Redis TTL 不应决定数据库业务键什么时候失去约束。

### 5.6 可选 Redisson 外层协调

仅当同 key 重复计算或数据库竞争已经成为实际成本时增加这一层。以下是调用顺序伪代码，等待预算按接口总期限制定：

```text
非事务外层：
    用 tenant_id + user_id + request_key 构造稳定锁 key
    acquired = false
    尝试 tryLock(waitTime, TimeUnit.MILLISECONDS)，不显式指定固定 leaseTime
    中断则传播或按策略结束；不得继续执行创建

    未获取到锁：
        查询已提交结果，找到则重放
        否则返回 PROCESSING / 重试指引；不要解释成订单一定失败
        不执行 unlock

    获取成功后才进入负责释放的 try/finally：
        调用第 5.3 节的非事务入口与独立事务服务
        确保所保护事务提交或回滚完成
    finally：
        释放本次成功取得的锁
```

外层不得悄悄加入一个直到解锁后才提交的更外层数据库事务。若释放阶段报告持有权丢失或网络错误，应记录并按原 key 核实业务结果；不能把已经提交的订单反报为“肯定失败”或换新 key 再执行。查询后 isHeldByCurrentThread 为真，也不能证明随后整个业务期间锁都有效。

```text
A 持锁查不到订单 → A 长时间暂停，续期不能及时完成
    → 锁过期 → B 获锁并创建订单，提交
    → A 恢复并尝试插入相同业务键
    → 数据库唯一约束拒绝重复写入
    → A 结束失败尝试，查询已有订单
```

数据库约束在上述窗口保护的是本库写入；已经向渠道发出的扣款请求，仍需渠道幂等标识。随机锁 owner 与可由资源比较的新旧执行代次不是同一种能力。

### 5.7 下游副作用与对账

创建订单事务只持久化订单、本库资源变更和待发送事件。提交后由投递器扫描已提交的 Outbox，失败后按预算重试，消费者用 event_id 或明确的业务键去重，并把本地去重记录和业务变更放在同一事务。

发送成功但标记成功前退出可能重复投递，所以消息 ID 之外还要定义业务效果的唯一身份。外部支付操作需使用渠道认可的稳定标识，核对其参数、有效期和查单规则；不能因为本地锁尚在就省略渠道幂等。[Stripe 幂等接口作为契约示例](https://docs.stripe.com/api/idempotent_requests)

对账用于发现缺失结果、未知支付和漏投事件，不能自动撤销重复扣款、重复发货或重复占用资源。允许多条本地支付尝试时，仍须唯一确认渠道交易的入账归属，履约不能按尝试条数重复触发。

### 5.8 故障验证与验收条件

以下是应在隔离集成环境执行的验收设计，不代表本文已经运行：

| 输入或故障时序 | 应检查的最终事实 |
| --- | --- |
| 两实例同 key 同内容并发提交 | 最多一张已提交订单；成功时仅一次本次扣库存和一个创建事件；等待失败有明确终态 |
| 同 key、不同内容并发或顺序提交 | 第二种内容被拒绝，不能伪装为原订单结果 |
| 同一用户不同 key 合法购买 | 在库存允许时分别成功，不被用户级锁永久误拦截 |
| 插入订单后库存不足 | 订单插入和相关事件回滚，库存不变 |
| 扣库存后、提交前异常退出 | 未提交订单、扣减与事件均不留成功效果 |
| 提交成功后响应丢失 | 原 key 查询或重试返回原订单，不再扣库存 |
| COMMIT 结果未知且原事务仍未确认 | 查询、等待或重试均保留原 key，最终仍受唯一约束保护 |
| Redis 不可用、锁过期或旧请求恢复 | 按是否允许降级执行既定策略；若允许进入数据库路径仍不产生重复订单 |
| Redis GET 和 DELETE 之间发生新持有者接替 | 原子 owner 校验释放不能删除新锁 |
| 未获锁或获取被中断 | 不执行业务，也不执行 unlock |
| 消息已发送但投递状态未落库 | 可重复投递，但下游业务效果不重复 |
| 历史订单归档后旧 key 再次到达 | 根据保留映射或有效期拒绝，不静默重建旧意图 |

可在两条 MySQL 会话中安排第 5.4 节的交错：A 开始事务并插入 K001，暂不提交；B 开始事务并插入同 key 的另一 order_id；A 提交后观察 B 的唯一键结果，再结束 B 的失败事务并新开查询。另做 A 回滚分支，并在每个实验后联合检查订单数、库存差值及事件数，不能只检查接口提示。

### 5.9 多实例、主从与分库的适用边界

| 架构 | 本文主方案是否适用 | 额外要求 |
| --- | --- | --- |
| 多实例连接同一个订单主库 | 适用 | 所有入口使用同一业务键及约束，不需要共享 Java 锁 |
| 主从复制，写入同一主库 | 适用 | 幂等结果查询避免复制延迟造成误判，写入资格仍由主库约束判定 |
| 订单按 user_id 等稳定维度分库 | 可将单分片视作本地唯一判定点 | 同一幂等身份必须路由同一权威分片；迁移时保持明确写入归属 |
| 同一幂等键可能随机写入多个独立订单库 | 不能直接保证全局唯一 | 改为固定路由，或增加具备一致性与恢复协议的全局幂等登记/归属服务 |
| 订单、库存、支付分别位于不同库 | 只能保护订单库内的重复创建 | 跨库资源变更需要独立的可靠事件、幂等及补偿/事务设计 |

不能用每次新生成的 order_id 随机路由，再期待各库的局部唯一约束识别同一个下单意图。全局登记也有“已登记但订单尚未创建”的窗口，必须记录处理状态与目标分片并支持接续恢复；加一把 Redisson 锁不会自动消除该跨库窗口。
