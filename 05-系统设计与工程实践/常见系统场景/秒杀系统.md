## 总体结论：怎么做到“不超卖 + 幂等 + 最终一致”

**推荐主链路（高并发秒杀常用组合拳）：**

1. **Redis 预扣库存（原子 Lua）**：把“是否有库存 + 是否买过 + 扣减 + 入队”放在**一次 Lua**里做原子操作 → **入口即不超卖**
2. **Redis Stream 作为“可靠缓冲队列”**：Lua 里同步 `XADD` 写入 Stream（与扣库存同原子）→ **不丢单、不靠应用发 MQ 的时序**
3. **异步消费者落 MySQL（本地事务）**：插订单 + 冻结/扣减 DB 库存（`where stock>0`）→ DB 再兜底一次，确保**再怎么抖也不超卖**
4. **事件驱动最终一致（Outbox / Stream Relay）**：订单状态变化、支付结果、超时取消 → 通过可靠事件推进状态机 → **最终一致**
5. **幂等三道闸**：入口幂等（Redis）+ 落库幂等（唯一索引/去重表）+ 消息幂等（消费幂等）→ **怎么重试都不重复下单/扣库存**

## 边界条件（默认你这套栈）

* 部署：K8s / Deployment，多实例水平扩容
* 峰值：10万 QPS 级别突刺（典型秒杀）
* 库存：单 SKU 100 ~ 10万不等
* 要求：不超卖（强），允许“用户看到排队/处理中”（最终一致），支付/取消可延迟几秒生效
* 组件：Redis Cluster + MySQL + MQ（可选）+ Spring Boot + Sentinel/网关限流

## 1）整体架构与链路

**组件划分：**

* **Gateway**：鉴权、动态路径、防刷、限流、熔断、黑白名单
* **Seckill Service（秒杀入口）**：校验活动/签名，执行 Redis Lua（预扣 + 入队），返回排队凭证
* **Order Worker（异步落库）**：读 Redis Stream（consumer group），落订单 + 冻结 DB 库存，写结果
* **Payment Service**：支付回调（至少一次），发事件
* **Stock/Order 状态机**：支付成功确认、超时取消回补
* **对账/补偿任务**：修复极端情况下的差异

**关键点：**
入口不做 DB 写（扛不住），**入口只做 Redis 原子 + 入队**，DB 只在异步侧写。

## 2）核心：如何“绝不超卖”

### 2.1 入口：Redis Lua 一次完成“资格 + 扣减 + 入队”

你要把这四件事绑死在一个原子操作里：

* 是否在活动时间窗口（可以在应用层校验，Lua 也可二次兜底）
* 用户是否已买过（`SISMEMBER buyers`）
* 库存是否 > 0（`GET stock`）
* 扣库存（`DECR stock`）
* 写入可靠队列（`XADD stream`）

**Lua 示例（最小可用，生产可扩展字段）：**

```lua
-- KEYS[1] stockKey        e.g. seckill:stock:sku:1001
-- KEYS[2] buyersKey       e.g. seckill:buyers:sku:1001
-- KEYS[3] streamKey       e.g. seckill:stream:orders
-- ARGV[1] userId
-- ARGV[2] reqId
-- ARGV[3] skuId

local stock = tonumber(redis.call('GET', KEYS[1]) or "0")
if stock <= 0 then
  return {0, "SOLD_OUT"}
end

if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
  return {0, "DUP_BUY"}
end

-- 预扣库存 + 标记已购买（避免重复点击）
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])

-- 可靠入队（与扣库存同原子，不会出现“扣了库存但没入队”）
redis.call('XADD', KEYS[3], '*',
  'reqId', ARGV[2],
  'userId', ARGV[1],
  'skuId', ARGV[3]
)

return {1, "OK"}
```

**为什么这一步就能保证“不超卖”？**
因为扣库存是 Redis 的原子递减，且只有库存>0 才允许进入队列，**队列里最多只有 N 条成功请求**（N=初始库存）。

> 额外：你要担心的不是超卖，而是“少卖”（扣了库存但后面失败没落库）——这属于最终一致性要补的账，下面解决。

---

### 2.2 异步侧：DB 再兜底一次“绝不超卖”

即便 Redis 层兜住了，DB 仍要用条件更新做最后保险，避免任何 bug/脏数据导致超卖。

**推荐 DB 库存模型（可回补、可对账）：**

* `available_stock` 可售
* `frozen_stock` 冻结（下单未支付）

下单时：`available--, frozen++`
支付成功：`frozen--, (sold++ 可选)`
超时取消：`frozen--, available++`

**SQL（强兜底，不超卖）：**

```sql
UPDATE t_stock
SET available_stock = available_stock - 1,
    frozen_stock    = frozen_stock + 1,
    version         = version + 1
WHERE sku_id = ?
  AND available_stock > 0
  AND version = ?; -- 可选乐观锁
```

---

## 3）全链路幂等：三道闸

### 3.1 入口幂等（防连点/重试）

* Lua 里用 `buyers set`（或 `SETNX user_sku_key`）直接挡掉重复购买
* 入口返回 `reqId`，客户端轮询结果，避免反复打“下单接口”

### 3.2 落库幂等（真正的底线）

MySQL 用唯一索引把重复下单彻底焊死：

```sql
CREATE TABLE t_order (
  order_id BIGINT UNSIGNED PRIMARY KEY,
  user_id  BIGINT UNSIGNED NOT NULL,
  sku_id   BIGINT UNSIGNED NOT NULL,
  status   VARCHAR(32) NOT NULL,
  create_time DATETIME NOT NULL,
  UNIQUE KEY uk_user_sku(user_id, sku_id),
  KEY idx_user_time(user_id, create_time)
);
```

消费者落库时：

* 插入成功：正常
* 若 `uk_user_sku` 冲突：说明重复消息/重复请求 → **当成功处理（幂等）**，查已有订单返回/写结果即可

### 3.3 消息幂等（至少一次投递必备）

Redis Stream / MQ 都是 **至少一次**，你必须让消费者做到：

* 用 `reqId` 或 `(userId, skuId)` 去重
* ack 前后崩溃都不怕：

  * **先 DB 提交，再 ack**
  * 崩溃后重投，DB 唯一索引兜住

---

## 4）最终一致性：怎么保证“扣了库存一定能对齐到订单/支付”

这里分三类一致性要对齐：

### 4.1 Redis 预扣 ↔ DB 冻结/订单

**风险：少卖**（Redis 扣了，DB 订单没落成）

* 典型原因：DB 临时不可用、消费者积压、代码异常

**处理策略：**

1. Stream 是可靠缓冲：只要入了 Stream 就不会“消失”
2. 消费失败重试：消费者组 pending 的消息会被重新 claim
3. 仍失败（例如 DB 长时间挂）：触发降级/止血（入口直接拒绝/熔断）
4. **对账补偿**（兜底）：定时扫描“Redis buyers 有记录但 DB 无订单/冻结”的 reqId/user-sku，做回补或补单（看业务）

> 工程原则：秒杀宁可“少卖可补”，不要“超卖不可救”。

### 4.2 未支付订单超时取消 ↔ 库存回补

做法：**延迟消息/定时器**推进状态机。

* 下单成功后发一条 `order_timeout` 延迟消息（如 15 分钟）
* 到期检查：若仍 UNPAID → 取消订单 + 回补库存（DB frozen->available）+ 回补 Redis（如果你维护 Redis 视图）

### 4.3 支付回调幂等 + 状态推进

支付回调必然会重复（支付平台重试、网络抖动），你必须：

* 以 `pay_txn_id` 或 `order_id` 做幂等
* 状态机只允许合法迁移：`UNPAID -> PAID`，重复 PAID 不二次生效

## 5）关键实现骨架（Spring Boot 伪代码级别，够你落地）

### 5.1 秒杀入口：调用 Lua

```java
// 伪代码：SeckillController
@PostMapping("/seckill")
public SeckillResp seckill(@RequestParam long skuId, @RequestParam long userId) {
    // 1) 网关已做动态路径/验签/限流，这里仍可做活动校验
    String reqId = UUID.randomUUID().toString();

    // 2) Lua 原子：扣库存 + 标记已买 + 入 Stream
    Object res = redis.eval(LUA, keys(stockKey, buyersKey, streamKey),
                            args(userId, reqId, skuId));
    // res = {1,"OK"} / {0,"SOLD_OUT"} / {0,"DUP_BUY"}
    return new SeckillResp(reqId, statusFrom(res));
}
```

### 5.2 Stream 消费者：落库事务 + ack

```java
@Scheduled(fixedDelay = 50) // demo 级：生产建议用独立线程/阻塞读取
public void consume() {
    List<StreamMessage> msgs = redis.xreadGroup("g1","c1","seckill:stream:orders", 100);
    for (StreamMessage m : msgs) {
        try {
            txTemplate.execute(status -> {
                long userId = m.userId();
                long skuId  = m.skuId();
                String reqId= m.reqId();

                // 幂等：唯一索引 uk_user_sku
                // 1) insert order (status=UNPAID)
                // 2) update stock available-- frozen++ where available>0
                //    若失败：说明 DB 库存不足（极端情况），回补 Redis（补偿事件）
                return null;
            });

            redis.xack("seckill:stream:orders","g1", m.id());
        } catch (DuplicateKeyException e) {
            // 已下过单：视作成功（幂等），ack
            redis.xack(...);
        } catch (Exception e) {
            // 不 ack，让它进入 pending，稍后重试/claim
            // 同时打点告警/记录死信
        }
    }
}
```

### 5.3 DB 库存不足时的 Redis 回补（补偿）

极端情况下（Redis 视图和 DB 不一致）DB update 失败，你要把 Redis 预扣撤销掉：

* `INCR stockKey`
* `SREM buyersKey userId`
* 记录补偿日志（便于追查）

这一步建议通过**补偿队列**异步做，避免在消费者事务里再搞 Redis 网络调用导致长事务。

## 6）止血与降级（真正生产会遇到）

### 6.1 DB/MQ/消费者积压怎么办？

* Stream lag（pending/lag）超过阈值 → **入口直接拒绝** 或把接口降级成“排队已满”
* DB 抖动 → 消费者重试 + 熔断；入口不要继续放量（否则只会制造更大 backlog）

### 6.2 Redis 故障怎么办？

* 秒杀强依赖 Redis，Redis 挂了基本就别秒杀了
* 你可以做“降级到 DB 乐观锁”但吞吐会雪崩，只适合小流量或演练
* 实战：Redis 集群 + AOF + min-replicas-to-write + 监控告警 + 熔断止血

---

## 7）热点与分库分表主键

你要“主键做分片键”，推荐：

* 订单 ID 用你前面那套 **Snowflake/号段**都行（趋势递增，利于 InnoDB）
* 分片规则一般用 `order_id % N` 或按时间路由（看业务）
* 秒杀写入是热点：**订单库分片 + 写入异步化** 是必要的

---

## 8）你可以直接照着答面试的“标准答案”

**一句话：**
入口用 Redis Lua 原子预扣+去重+入队保证不超卖，异步消费者用 DB 条件更新+唯一索引做最终兜底与幂等，支付/超时用状态机+延迟消息回补库存，配合对账补偿保证最终一致。

## 小结

* **不超卖**：Redis 原子预扣（第一道）+ DB 条件更新（第二道）
* **幂等**：入口去重 + DB 唯一索引 + 消费幂等
* **最终一致**：Stream/MQ 至少一次 + 状态机 + 延迟回补 + 对账补偿

# 分布式锁和redis lua脚本的区别
结论先说：**Lua 脚本是在 Redis 里把多步操作“原子化一次执行”**；分布式锁是把“互斥权”发给某个客户端，让客户端在锁保护下**自己执行多步命令**。
所以它们最大的区别不在“能不能串行”，而在 **原子边界、网络往返、失败语义、吞吐上限**。

---

## 1）原子性边界：谁来保证“不被插队”

### Lua

* 脚本在 Redis 里执行期间，Redis 会把它当成一个整体（单线程执行模型下）
* **脚本内部的 GET/DECR/SADD/XADD 不会被别的命令插队**
* 原子边界 = “脚本从开始到结束”

> 适合：库存判断 + 扣减 + 去重 + 入队 这种“必须同生共死”的逻辑

### 分布式锁（以 Redis 锁为例）

* 你做的是：`SETNX lock` 成功 → 客户端发多条 Redis 命令 → `DEL lock`
* 原子边界不再是 Redis，而是**客户端这段代码 + 网络**
* 虽然理论上互斥，但会出现：

  * 锁过期（TTL 到）但客户端还没执行完，另一个客户端拿到锁 → **并发进入临界区**
  * 客户端宕机/GC STW/网络抖动 → 锁续租失败 → 临界区被破坏

> 锁能“互斥”，但互斥的正确性依赖你对 TTL/续租/超时的工程控制。

---

## 2）性能与吞吐：一趟 vs 多趟网络往返

### Lua

* **一次网络 RTT**：请求发到 Redis，Redis 内部跑完返回结果
* 并发高时更稳：减少 RTT 和排队时间

### 锁

* 至少 3~N 次 RTT：

  1. 抢锁
  2. 多条业务命令（GET/DECR/…）
  3. 释放锁
* 再加上锁竞争导致的自旋/重试，吞吐更容易塌

> 秒杀这种“每个请求都要走临界区”的场景，锁会把 Redis 变成“全局单点闸门”，吞吐上限明显更低。

---

## 3）失败语义：谁更“不会留下烂摊子”

### Lua

* 要么脚本执行成功、所有写入都生效；要么不执行（比如超时/断连不会导致“执行了一半”这种客户端可见的半状态）
* 当然，脚本也可能因为逻辑 bug 写错数据，但**不会出现“写了一半被插队”**

### 锁

* 最典型的坑：**锁过期导致临界区并发**
  你以为只有你在扣库存，实际上另一个客户端也进来了
* 释放锁的正确性也要小心（必须“只删自己持有的锁”）——一般也得用 Lua 来安全释放锁

> 有点讽刺：你用锁，最后为了安全释放锁，还是得写 Lua。

---

## 4）一致性组合：为什么“扣库存 + 入队”更适合 Lua

你在秒杀里最想避免的是两类“半状态”：

1. 扣了库存，但没入队（订单没生成）→ 少卖、对账麻烦
2. 入队了，但没扣库存 → 超卖风险

Lua 可以把这两步绑在一起：

* `DECR stock` + `XADD stream` 同脚本原子完成
  锁方案做这两步是两条命令，中间有失败窗口。

---

## 5）什么时候锁反而更合适

**Lua 更适合“Redis 内部纯数据逻辑”**。锁更适合：

* 临界区包含 **跨资源操作**（比如：Redis + MySQL + 远程 RPC）
  Lua 管不了 MySQL/RPC，你只能靠事务/状态机/锁/消息
* 临界区逻辑很复杂、Lua 不好维护（可读性/调试性差）
* 需要“按某个业务键串行化一段较长的业务流程”（比如一个订单的状态机推进），这时你可能用 Redisson 的锁/信号量，但要做好超时/续租/降级

---

## 6）秒杀系统的推荐结论（落地选择）

* **入口防超卖（库存判断 + 扣减 + 去重 + 入队）**：优先 Lua（原子、少 RTT、吞吐高）
* **异步落库、支付回调、状态机推进（跨系统）**：不要用“大锁”硬串行
  用：DB 条件更新 + 唯一索引幂等 + 事件驱动 + 补偿

---

## 小结一句话

Lua 是“把临界区搬进 Redis 并原子执行”，锁是“把临界区留在客户端靠互斥约束”。
秒杀入口这种高并发、步骤必须同生共死的逻辑——**Lua 更稳更快更少坑**；锁更像一把“万能锤”，能用但容易砸脚，尤其在 TTL/续租/抖动面前。
