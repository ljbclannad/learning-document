# 对外提供下载 URL：安全控制与审计

## 总体结论：不要把存储地址直接交给第三方

文件对象应保持**私有**，第三方拿到的下载 URL 应当是短时、最小权限、可追溯的“领取凭证”。推荐链路：

1. 第三方先以自己的身份调用业务 API，请求某个文件；业务服务完成认证、授权和业务状态校验。
2. 服务记录一次“下载授权”审计事件，并签发一个短时下载凭证（或短时对象存储预签名 URL）。
3. 第三方使用该 URL 下载；CDN / 网关 / 对象存储记录实际访问结果，回传或汇聚为“下载完成”审计事件。
4. 审计、告警、吊销和对账围绕 `downloadGrantId`（下载授权 ID）关联，而不是只依赖 URL。

> 预签名 URL 解决的是“持有者可在有效期内访问对象”，**不是**“这个人仍有业务权限”。涉及敏感文件、一次性下载、动态吊销或严格审计时，URL 应先到自己的下载网关，再由网关实时决定是否向存储读取或重定向。

---

## 1. 先确定文件的安全等级和下载契约

不同文件不应共用一套宽松策略。至少按数据敏感度分级：

|等级|例子|推荐下载方式|有效期与限制|
|---|---|---|---|
|公开|安装包、公开白皮书|CDN 公共 URL|可较长；仍应限速、防盗链（按需要）|
|内部|合作方普通报表|业务授权后签发预签名 URL|5～15 分钟；限定 `GET` 和单对象|
|敏感|含个人信息、财务文件、合同|下载网关实时鉴权，必要时流式转发|1～5 分钟；单次、限 IP / 客户端证书、可水印|
|高度敏感|密钥材料、医疗原件、受监管数据|专用交付通道或受控数据室|不提供裸 URL；强认证、审批、完整留痕|

下载 API 的输入不要接受完整对象路径或任意 URL。客户端只传业务侧的 `fileId`；服务端再查出对象键、归属、状态和策略。这样可以避免路径遍历、越权枚举和 SSRF 类问题。

```http
POST /v1/files/{fileId}/download-grants
Authorization: Bearer <partner-token>
Idempotency-Key: 5c9d...

{
  "purpose": "monthly-settlement",
  "clientRequestId": "partner-20260720-001"
}
```

授权成功后只返回下载入口和过期时间，不返回 bucket、永久 object key、内部存储域名或其他文件元数据。

## 2. 推荐架构：业务服务管授权，存储服务管字节

```text
第三方系统
    │  认证 + 请求 fileId
    ▼
下载授权 API ── 查询文件元数据、合同/租户/状态、风控策略
    │                         │
    │ 写 download_grant / audit  │ 写拒绝原因、告警
    ▼                         ▼
下载网关或签名服务 ── 生成短时凭证 ──> 审计平台 / SIEM
    │
    ├─ 302 到私有对象的预签名 URL（普通内部文件）
    └─ 鉴权后代理 / 流式读取私有对象（敏感文件）
                                      │
                                      ▼
                                CDN / 对象存储访问日志
```

对象存储 bucket 必须保持私有：只允许下载网关、CDN 回源身份或签名请求读取。不要为了“让链接能下载”而把 bucket、目录或 ACL 改成 public-read；一个猜到或转发出去的永久 URL 就会变成绕过业务权限的后门。

### 两种交付方式的取舍

|方式|适合|优点|限制|
|---|---|---|---|
|302 重定向到预签名 URL|大文件、普通敏感级别|应用不承载文件流量，成本和吞吐更好|URL 在有效期内仍可被转发；通常难以做到下载中途吊销|
|下载网关代理 / 流式转发|高敏感、需单次下载或动态风控|每次请求都可鉴权、限速、审计；可隐藏存储地址|网关需要带宽、范围请求和断点续传能力|

不要把“预签名 URL 过期”误认为“文件只下载一次”。HTTP 客户端可在过期前多次使用它，也可能只下载了一部分。若业务要求一次性使用，应由下载网关消费一次性 token，并明确“消耗时机”是**开始下载**还是**完整传输成功**；后者需要处理断线重试和 Range 请求，通常更复杂。

## 3. 授权：每次签发前都重新判断

下载授权至少同时满足以下条件：

1. **认证可信**：第三方使用 OAuth 2.0 client credentials、mTLS、签名请求或其他可轮换的机器身份；不要使用共享的长期 API Key。
2. **主体匹配**：调用方的 `partnerId` / `tenantId` 与文件归属、合同范围、委托关系匹配。
3. **动作匹配**：权限是 `file:download`，不能因为拥有 `file:read` 或知道文件 ID 就默认允许下载。
4. **资源与状态匹配**：文件存在、未删除、未过期、未隔离，且业务单据已到允许交付的状态。
5. **上下文匹配**：需要时校验 IP 段、mTLS 证书指纹、调用时段、用途码、下载次数和单日额度。
6. **风控通过**：异常地域、短时间大量文件、失败率过高或文件枚举行为应触发拒绝、二次校验或人工审批。

授权服务应使用服务端可信的身份与属性，不能相信客户端传入的 `tenantId`、文件路径、过期时间或“这是我的文件”等声明。多租户查询必须把租户条件写进数据库查询或使用行级隔离，不能只在查到文件后再做一次可选判断。

### 防止 ID 枚举与越权

`fileId` 可使用不可预测的 UUID / ULID 或对外部 ID；即使如此，仍必须做授权校验。不可预测 ID 只是降低枚举概率，不是访问控制。对 `404` 与无权的 `403` 是否区分，要按是否需要隐藏资源存在性决定；对外 API 常统一返回不暴露文件信息的响应，但内部审计要保留真实拒绝原因。

## 4. 签发 URL 时的最小权限原则

若使用 S3、OSS、COS、Azure Blob 等对象存储的预签名机制，签名策略应尽量窄：

* 仅允许 `GET` / `HEAD`，只针对一个精确 object key；不要签整个前缀或 bucket。
* 过期时间按风险设定，通常 5～15 分钟；高敏感文件更短，并结合一次性 token。
* 不让调用方指定响应头、文件名、重定向地址等任意参数；服务端做白名单或固定值，避免响应头注入和开放重定向。
* 文件名由服务端生成并使用 `Content-Disposition: attachment`；对用户上传的原始文件名做字符过滤和编码。
* 需要时把 CDN 签名 Cookie / URL、IP 条件或 mTLS 放在 CDN / 网关层实施。注意：只有基础设施实际验证的条件才构成约束。
* 签名密钥只放在密钥管理系统或受限运行身份中；定期轮换，绝不下发给第三方或写入前端代码、日志。

对于浏览器下载，额外设置合适的 `Content-Type`、`X-Content-Type-Options: nosniff` 和 `Content-Disposition: attachment`，降低 HTML / SVG 等活跃内容在业务域直接打开造成的脚本执行风险。若需要在线预览，使用独立的无敏感 Cookie 域名，并配合严格 CSP / 沙箱策略。

## 5. 审计：区分“授权”“尝试”“完成”

只记录“已生成 URL”并不能说明文件已被下载；只看对象存储 access log 又很难还原是谁、为什么被授权。建议将审计拆成三个事件：

|事件|何时写入|核心字段|说明|
|---|---|---|---|
|`DOWNLOAD_GRANTED`|业务授权通过、凭证生成后|`grantId`、主体、fileId、策略、过期时间、用途|说明谁在何时获得了什么权限|
|`DOWNLOAD_ATTEMPTED`|网关收到下载请求时|`grantId`、请求 ID、IP、UA、认证结果、Range|说明凭证是否被使用及失败原因|
|`DOWNLOAD_COMPLETED`|代理发送完成，或由 CDN / 存储日志回流确认后|状态码、字节数、耗时、对象版本 / ETag|说明一次传输的结果；不应把 200 简化为“用户已阅读”|

推荐审计模型：

```sql
CREATE TABLE download_grant (
  grant_id          CHAR(26) PRIMARY KEY,
  file_id           CHAR(26) NOT NULL,
  object_version    VARCHAR(128) NOT NULL,
  subject_type      VARCHAR(32) NOT NULL,
  subject_id        VARCHAR(128) NOT NULL,
  tenant_id         VARCHAR(64) NOT NULL,
  policy_snapshot   JSON NOT NULL,
  purpose           VARCHAR(128),
  issued_at         TIMESTAMP NOT NULL,
  expires_at        TIMESTAMP NOT NULL,
  revoked_at        TIMESTAMP NULL,
  consumed_at       TIMESTAMP NULL,
  status            VARCHAR(32) NOT NULL,
  INDEX idx_file_time (file_id, issued_at),
  INDEX idx_subject_time (subject_id, issued_at)
);
```

每个审计事件都应至少带上：`eventId`、`occurredAt`、`traceId`、`grantId`、`fileId`、对象版本、调用主体、租户、结果码、拒绝原因、源 IP、User-Agent、请求 ID 和传输字节数。文件名、用途说明、IP 等字段可能含个人信息，应按数据分类设置访问权限、脱敏展示和保留期限。

### 审计日志的可靠性与防篡改

* 下载主链路可先同步写入最小的 `DOWNLOAD_GRANTED` 记录；其他高吞吐事件通过 outbox / 消息队列异步投递，避免审计系统短暂故障阻塞所有下载。
* 审计事件应使用不可变追加存储，并限制更新 / 删除权限；对合规要求高的场景可使用 WORM 存储、哈希链或定期签名校验。
* 应用日志、网关日志和对象存储 / CDN 日志使用 `grantId`、`traceId` 关联。不要把完整预签名 URL、Authorization、Cookie 或签名参数写进日志。
* 监控“授权数、实际尝试数、成功率、拒绝数、过期 URL 使用数、单主体下载字节数”，并针对异常峰值、枚举、跨租户访问、深夜批量下载建立告警。

## 6. 吊销、删除与版本控制

预签名 URL 一旦发出，通常无法由业务服务单方面提前失效；因此敏感文件不要只依赖它。吊销策略应在签发前设计清楚：

* **未使用授权**：将 `download_grant.status` 改为 `REVOKED`；下载网关每次校验状态即可即时拒绝。
* **已签发的预签名 URL**：等待其短过期，或在存储 / CDN 层通过禁用凭证、撤销签名密钥、更新对象策略等方式处理（具体能力依云厂商而定）。密钥轮换通常影响面很大，不能作为常规单文件吊销手段。
* **文件被替换**：将授权绑定到对象的版本号或不可变版本 ID，避免旧 URL 在同一 key 被覆盖后下载到新内容。
* **文件被删除或隔离**：业务元数据先标记不可下载，再异步清理对象；保留必要的审计元数据和文件哈希用于追溯。

对有法律留存要求的文件，还要区分“业务可下载期限”“在线保存期限”“审计保存期限”。删除文件内容不等于可以删除审计记录。

## 7. 典型实现骨架（下载网关）

下面的伪代码展示了关键顺序。重点不是框架，而是：**鉴权、状态校验、审计授权、发放短时能力**必须在同一条受控链路中完成。

```java
@PostMapping("/v1/files/{fileId}/download-grants")
public DownloadGrantResponse createGrant(@PathVariable String fileId,
                                         @AuthenticationPrincipal Partner partner,
                                         @RequestBody DownloadRequest request) {
    FileRecord file = fileRepository.findActiveByExternalId(fileId)
        .orElseThrow(NotFoundException::new);

    policyService.checkDownload(partner, file, request.purpose());

    DownloadGrant grant = txTemplate.execute(status -> {
        DownloadGrant g = DownloadGrant.issue(
            idGenerator.newId(), file, partner, request.purpose(), clock.instant().plusSeconds(300));
        grantRepository.insert(g);                 // DOWNLOAD_GRANTED 的事实来源
        outboxRepository.append(AuditEvent.granted(g));
        return g;
    });

    // 普通文件可返回短时预签名 URL；敏感文件返回网关 URL + 一次性 token。
    URI url = deliveryService.createDownloadUrl(grant);
    return new DownloadGrantResponse(grant.id(), url, grant.expiresAt());
}
```

下载网关处理 `GET /downloads/{grantId}?token=...` 时，应验证 token 签名和过期时间、`grantId` 状态、调用者绑定条件及文件版本；随后写 `DOWNLOAD_ATTEMPTED`。通过后再代理对象流或生成一次短得多的重定向 URL。流式代理还应正确支持 `Range`、客户端断开、限速和字节统计，不能把任何 `200` 响应都当作完整下载。

## 8. 上线前检查清单

* [ ] bucket / 容器 / CDN 回源默认私有，无法用永久 URL 匿名下载。
* [ ] 外部 API 仅接受 `fileId`，不接受对象 key、任意 URL 或客户端指定租户。
* [ ] 每次生成 URL 前都完成认证、授权、文件状态和风险校验。
* [ ] URL 只允许单对象读取、短过期；敏感文件使用下载网关和可吊销 token。
* [ ] 不在响应、埋点或日志中记录完整签名 URL、令牌、Cookie、Authorization。
* [ ] `grantId` 贯穿授权 API、网关、CDN / 存储访问日志和审计平台。
* [ ] 审计能够区分授权、请求尝试、传输完成 / 中断，并具有保留与防篡改策略。
* [ ] 有下载频控、额度、异常告警、吊销流程和故障演练。
* [ ] 测试越权访问、URL 转发、过期、重复使用、Range 续传、文件替换、审计投递失败和对象存储不可用等场景。

## 常见误区

1. **“URL 很长，别人猜不到就安全。”** URL 会出现在浏览器历史、代理、截图、日志和第三方系统中；不可预测性不能替代授权。
2. **“签名 URL 就已经审计下载。”** 它只表明有人拿到临时访问能力；要结合网关 / CDN / 对象存储日志确认实际请求和传输情况。
3. **“过期时间设一天，方便合作方。”** 有效期越长，泄漏窗口越大；应改为可重新申请的短时 URL，并提供可用的重试和对账机制。
4. **“用 IP 白名单就足够。”** NAT、代理和地址变更会让它不稳定；IP 限制应是主体认证与授权之外的附加条件。
5. **“删除文件后就没有风险。”** 已下载副本无法收回，且审计、监管留存和备份策略仍需单独处理。
